## オープンソースとは何か：4 つの自由と 10 の条件 {#definition}

ソフトウェアは**著作物**です。作った時点で、作った人に**著作権**が自動的に生まれます（届け出はいりません）。著作権者の許しがなければ、他人はコピーも改変も配布もできません。

その許しの条件を書いた文書が**ライセンス**です。オープンソースは著作権を捨てることではありません。著作権者が、ライセンスで「この条件を守れば、使ってよい・変えてよい・配ってよい」と認めている状態です。

オープンソースを定める考え方は 2 つあります。

| | フリーソフトウェア（FSF） | オープンソース（OSI） |
| --- | --- | --- |
| 中心 | 利用者の**自由**（free は「無料」ではなく「自由」） | 開発の方法としての良さ、**10 の条件**（オープンソースの定義） |
| 中身 | 4 つの自由 | 再配布の自由、ソースコード、派生物の許可…… |
| ライセンスの認定 | FSF が自由かどうかを判定 | OSI が条件を満たすライセンスを承認 |

**フリーソフトウェアの 4 つの自由**は、0 から数えます。

| 番号 | 自由 |
| --- | --- |
| 0 | 目的を問わず、プログラムを**実行**する自由 |
| 1 | プログラムがどう動くかを**研究**し、**改変**する自由（そのためにソースコードが必要） |
| 2 | **コピーを再配布**する自由 |
| 3 | **改変したものを配布**する自由 |

**オープンソースの定義（OSD）の 10 の条件**の要点です。

| | 条件 | 要点 |
| --- | --- | --- |
| 1 | 自由な再配布 | 再配布を制限しない。再配布にロイヤリティ（使用料）を求めない |
| 2 | ソースコード | ソースコードを含める。または無料（ほぼ無料）で入手できるようにする |
| 3 | 派生物 | 改変と派生物を許し、元と同じ条件で配布することを許す |
| 4 | 作者のソースコードの完全性 | 元のソースとパッチを分けて配るよう求めてよい。派生物に別の名前や版番号を求めてよい |
| 5 | 個人やグループの差別の禁止 | 特定の人や集団を除外しない |
| 6 | 利用分野の差別の禁止 | 「商用に使うな」「研究に使うな」などと分野を制限しない |
| 7 | ライセンスの分配 | 再配布を受けた全員に、追加の契約なしで同じ権利が及ぶ |
| 8 | 特定製品に限定しない | 特定のディストリビューションの一部であるときだけ、という条件を付けない |
| 9 | 他のソフトウェアを制限しない | 一緒に配る他のソフトウェアにまで条件を付けない |
| 10 | 技術的に中立 | 特定の技術や操作（「同意」ボタンなど）を前提にしない |

:::warn 試験の注意
- 「フリー」は**価格**ではなく**自由**です。オープンソースのソフトウェアを**有料で販売**しても、定義に反しません（GPL も販売を禁じていません）
- 「商用利用を禁止する」ライセンスは、オープンソースの定義（条件 6）に合いません
- オープンソースでも**著作権は放棄されていません**。放棄に近いのは、後で説明するパブリックドメインです
:::

**無保証**も大事な特徴です。ほとんどのライセンスは「現状のまま（AS IS）提供し、何も保証しない。損害が起きても作者は責任を負わない」と書いています。保証やサポートがほしい利用者は、それを売る企業（ディストリビューションのベンダーなど）と契約します。

一方で、ソースが公開されているので、**開発が続けられます**。作者がやめても、別の人が引き継げます。方針が合わなければ、ソースを複製して別のプロジェクトとして続けること（**フォーク**）もできます。OpenOffice.org から LibreOffice が、MySQL から MariaDB が分かれた例が有名です。

小さな Linux に、MIT ライセンスのプロジェクトを用意しました。ライセンスの本文を読んでみます。

```sh setup
cat > /home/you/greet/LICENSE <<'EOF'

of this software and associated documentation files (the "Software"), to deal

copies of the Software, and to permit persons to whom the Software is
furnished to do so, subject to the following conditions:

The above copyright notice and this permission notice shall be included in all
copies or substantial portions of the Software.

THE SOFTWARE IS PROVIDED "AS IS", WITHOUT WARRANTY OF ANY KIND, EXPRESS OR
IMPLIED, INCLUDING BUT NOT LIMITED TO THE WARRANTIES OF MERCHANTABILITY,
FITNESS FOR A PARTICULAR PURPOSE AND NONINFRINGEMENT. IN NO EVENT SHALL THE
AUTHORS OR COPYRIGHT HOLDERS BE LIABLE FOR ANY CLAIM, DAMAGES OR OTHER
LIABILITY, WHETHER IN AN ACTION OF CONTRACT, TORT OR OTHERWISE, ARISING FROM,
OUT OF OR IN CONNECTION WITH THE SOFTWARE OR THE USE OR OTHER DEALINGS IN THE

EOF
cat > /home/you/greet/src/greet.sh <<'EOF'
# SPDX-License-Identifier: MIT
if [ "$1" = "--version" ]; then echo "greet 1.2.0"; exit 0; fi
set -- $1
echo "Hello, $1!"
EOF
cat > /home/you/greet/vendor/colors.sh <<'EOF'
# SPDX-License-Identifier: MPL-2.0

EOF
cat > /home/you/greet/vendor/net.sh <<'EOF'

EOF
cat > /home/you/greet/NOTICE <<'EOF'
net.sh
Copyright 2025 Example Net Project
This product includes software developed by the Example Net Project.
EOF
```

```sh run title="著作権の表示とライセンスの名前"
cd /home/you/greet
ls
head -n 3 LICENSE
```

```sh run title="許可していること（使う、コピー、改変、配布、販売……）と、ただ 1 つの条件"
grep -n "copy, modify" LICENSE
grep -n "shall be included" LICENSE
```

```sh run title="無保証の条項"
grep -n "WITHOUT WARRANTY" LICENSE
```

MIT ライセンスが求めるのは「著作権の表示とこの許諾の文を、すべてのコピーに含めること」だけです。そして「AS IS」で、保証はありません。

## ライセンスは何を求めるか：コピーレフトの強さ {#copyleft}

**コピーレフト**は、「改変したもの（派生物）を配布するときも、同じライセンスで配布し、ソースコードを渡す」ことを求める仕組みです。自由が、配布の先でも失われないようにします。コピーレフトをどこまで及ぼすかで、ライセンスが分かれます。

### GPL：派生物の全体を GPL で出す

**GPL**（GNU General Public License）は、FSF が作った代表的なコピーレフトのライセンスです。GPL のプログラムを改変したり、GPL のコードを組み込んだりしたプログラムを**配布する**ときは、その全体を GPL で配布し、ソースコードを受け取った人が入手できるようにします。

条件がかかるのは**配布するとき**です。改変して自分や社内だけで使い、外に配らないなら、ソースを公開する義務はありません。また、GPL のソフトウェアを有料で売ることも許されています。

| | GPL v2（1991） | GPL v3（2007） |
| --- | --- | --- |
| 使われている例 | Linux カーネル（v2 のみ） | GNU のツールの多く |
| 特許 | はっきりした条項がない | 貢献者が特許の利用を許す条項がある |
| 機器への組み込み | 規定なし | 消費者向けの機器では、改変したソフトを入れ直すための情報も渡す（いわゆる「Tivo 化」の防止） |
| Apache 2.0 との組み合わせ | できない（両立しない） | Apache 2.0 のコードを取り込める |

:::note 「v2 のみ」と「v2 以降」
GPL では、作者が「バージョン 2、または（あなたの選択で）それ以降のバージョン」と書くことがあります。Linux カーネルはこの一文がなく、**GPL v2 のみ**です。そのため v3 には移っていません。
:::

### AGPL：ネットワーク越しに使わせるときもソースを渡す

GPL は「配布」をきっかけにします。サーバーで動かして Web サービスとして使わせるだけなら、プログラムを配布していないので、改変したソースを出さなくて済みます。**AGPL**（GNU Affero GPL v3）はここをふさぎます。

### LGPL：ライブラリを使うだけのプログラムには及ばない

**LGPL**（GNU Lesser GPL）は、ライブラリ向けの弱いコピーレフトです。LGPL のライブラリを**リンクして使うだけ**のプログラムは、GPL 以外のライセンス（ソースを公開しない商用のライセンスも）で配布できます。ライブラリ**そのもの**を改変したら、その改変は LGPL で出します。また、利用者がライブラリを差し替えられるようにしておく必要があります。代表は GNU C ライブラリ（glibc）です。

### MPL：ファイル単位のコピーレフト

**MPL**（Mozilla Public License 2.0）は、コピーレフトを**ファイル単位**にかけます。MPL のファイルを改変して配布したら、そのファイルは MPL のままソースを出します。同じプログラムの中でも、自分で書いた別のファイルは別のライセンスにできます。Firefox が使っています。

```sh run title="ファイルの先頭の SPDX の行で、ファイルごとのライセンスを見る"
grep -n "SPDX-License-Identifier" src/greet.sh vendor/colors.sh vendor/net.sh
```

`SPDX-License-Identifier` は、ファイルのライセンスを短い名前で書く決まった書き方です。この例では、`vendor/colors.sh` を改変して配布するなら、そのファイルだけは MPL のままソースを出します。

| ライセンス | 種類 | 改変して配布するとき求められること |
| --- | --- | --- |
| GPL | 強いコピーレフト | 派生物の全体を GPL で、ソースとともに |
| AGPL | 強いコピーレフト | GPL と同じ。さらに、ネットワーク越しに使わせるときも改変後のソースを入手できるように |
| LGPL | 弱いコピーレフト | ライブラリの改変は LGPL で。リンクするだけのプログラムは自由 |
| MPL 2.0 | 弱いコピーレフト | MPL のファイルの改変は MPL で。ほかのファイルは自由 |

## 寛容なライセンス、パブリックドメイン、デュアルライセンス {#permissive}

コピーレフトのないライセンスを、**寛容な（パーミッシブ）ライセンス**と呼びます。改変したものを、ソースを公開しない商用のソフトウェアに組み込んで配布できます。求めるのは、主に**著作権とライセンスの表示を残すこと**です。

| ライセンス | 求めること |
| --- | --- |
| MIT | 著作権の表示と許諾の文を、すべてのコピー（またはその主要な部分）に含める |
| BSD（3 条項） | ソースでも配布物でも著作権表示などを残す。作者の名前を、許しなく宣伝に使わない（2 条項版はこの宣伝の条項がない） |
| Apache 2.0 | ライセンスの写しを渡す。変更したファイルに「変更した」と目立つように書く。著作権などの表示と **NOTICE ファイル**を残す。貢献者が**特許**の利用を許す。特許侵害で訴えた者は、その特許の許諾を失う。商標の使用は許さない |

```sh run title="Apache 2.0 のコードを含むときは、NOTICE ファイルの中身も配布物に残す"
cat NOTICE
```

:::warn 試験の注意：Apache 2.0 と MIT の違いは「特許」
MIT と BSD には特許についての条項がありません。Apache 2.0 は、**貢献者からの特許の許諾**と、**特許で訴えたら許諾が終わる**条項を持ちます。「特許の条項がある寛容なライセンス」と聞かれたら Apache 2.0 です。
:::

**パブリックドメイン**は、著作権による制限がない状態です。著作権が切れたものや、作者が権利を放棄したものです。だれでも条件なしに使えます。データベースの SQLite がパブリックドメインです。日本のように作者が権利を完全には放棄できない国もあるので、放棄の意思を示しつつ、できない部分は自由に許諾する CC0 などの宣言が使われます。

**デュアルライセンス**は、著作権者が同じソフトウェアを**2 つ以上のライセンスで**提供することです。著作権者だから、条件を複数用意できます。

- MySQL：GPL と商用ライセンス。ソースを出したくない会社は商用ライセンスを買う
- Qt：GPL / LGPL と商用ライセンス
- Rust の多くのライブラリ：MIT または Apache 2.0 の、利用者が選べる形

:::tip 組み合わせるときは「ゆるい側から強い側へ」
MIT のコードは GPL のプログラムに取り込めます（全体を GPL で出せばよい）。逆に、GPL のコードを取り込んだ全体を MIT で出すことはできません。コピーレフトは、取り込んだ先の全体に条件を及ぼすからです。
:::

## コミュニティにどう関わるか {#community}

オープンソースは、世界中の人がインターネットで集まって作ります。やりとりの場所は主に 3 つです。

| 場所 | 使い方 |
| --- | --- |
| **メーリングリスト** | 登録した全員にメールが配られる。議論、告知、パッチの投稿。Linux カーネルは今もパッチをメールで送り、メーリングリストで審査する |
| **掲示板（フォーラム）** | 利用者どうしの質問と回答。過去のやりとりを検索できる |
| **開発サイト**（GitHub、GitLab など） | ソースの置き場所（Git のリポジトリ）、課題の管理（Issue）、変更の取り込みの依頼（**プルリクエスト**、GitLab ではマージリクエスト）、フォーク |

**開発体制**は、プロジェクトごとに違います。

- **メンテナ**：担当の範囲で、パッチを取り込むかどうかを決める人。Linux カーネルでは、各部分のメンテナが集めた変更をリーナス・トーバルズが最終的に取り込む
- **コミッタ**：リポジトリに直接書き込む権利を持つ人。貢献を重ねて認められた人に与えられる
- **コントリビュータ**：パッチ、文書、翻訳、報告などで貢献する人。だれでもなれる
- **財団**：Linux Foundation、Apache Software Foundation などが、資金や商標、法的な面を支える。企業の開発者も多く参加している

関わり方は、コードを書くことだけではありません。**使う**、ブログや勉強会で**紹介する**、不具合を**報告する**、文書を直す、翻訳する、寄付する。どれも貢献です。

```fig seq バグ報告から修正までの流れ。報告の質が、直る早さを決める
{
  actors: [
    { id: 'u', label: '利用者' },
    { id: 't', label: 'Issue（課題管理）' },
    { id: 'm', label: 'メンテナ' },
  ],
  msgs: [
    { self: 'u', label: '既存の報告を検索' },
    { from: 'u', to: 't', label: '再現手順・期待と実際・版と環境' },
    { from: 't', to: 'm', label: '通知' },
    { from: 'm', to: 'u', label: '追加の質問', style: 'dashed' },
    { self: 'm', label: '再現して修正' },
    { from: 'm', to: 't', label: '修正を取り込み、Issue を閉じる' },
  ],
}
```

小さな Linux の `greet` で、報告に書く材料を集めてみます。名前に空白があると、姓が消えてしまいます。

```sh run title="バグ報告の材料：版、環境、再現手順、期待と実際"
sh src/greet.sh --version
uname -sr
sh src/greet.sh "Taro Yamada"
```

良いバグ報告には、次のことを書きます。

| 書くこと | この例では |
| --- | --- |
| ソフトウェアの版 | greet 1.2.0 |
| 環境（OS、カーネル） | `uname -sr` の出力 |
| 再現手順 | `sh src/greet.sh "Taro Yamada"` を実行する |
| 期待した結果と実際の結果 | 期待 `Hello, Taro Yamada!`、実際 `Hello, Taro!` |
| エラーメッセージやログ | そのまま貼る（言い換えない） |

:::warn 試験の注意：してはいけない報告
- 「動きません」とだけ書く（版も手順もない）
- 同じ不具合を、検索せずに別の報告として何度も立てる
- 1 つの報告に、関係のない不具合をいくつも混ぜる
- **セキュリティの脆弱性**を、公開の Issue や掲示板にいきなり書く。プロジェクトが決めた非公開の窓口（セキュリティポリシー）に知らせる
:::

:::deep 「伽藍とバザール」
エリック・レイモンドは 1997 年の論文「伽藍とバザール」で、少人数が閉じて作る「伽藍」方式と、Linux のように早く頻繁に公開して多くの人の目で直す「バザール」方式を比べました。「目玉の数さえ十分あれば、どんなバグも深刻ではない」という言葉が知られています。この考えが、1998 年の「オープンソース」という呼び名と OSI の設立につながりました。
:::

:::key まとめ
- ソフトウェアは著作物。オープンソースは著作権を捨てるのではなく、ライセンスで利用・改変・再配布を許す
- FSF の 4 つの自由：実行（0）、研究と改変（1）、再配布（2）、改変版の配布（3）。free は「自由」
- OSI のオープンソースの定義は 10 の条件。再配布の自由、ソースコード、派生物の許可、人や分野で差別しない（商用の禁止は不可）
- ほとんどのライセンスは無保証（AS IS）。有料での販売は許される
- 強いコピーレフト：GPL（配布するとき全体を GPL で）、AGPL（ネットワーク越しの利用でも改変後のソースを）。弱い：LGPL（リンクするだけなら自由）、MPL（ファイル単位）
- 寛容：MIT、BSD（表示を残す）、Apache 2.0（表示 + NOTICE + 特許の条項）。パブリックドメインは条件なし
- デュアルライセンス：著作権者が複数のライセンスで提供（MySQL の GPL と商用）
- コミュニティ：メーリングリスト、掲示板、開発サイト（GitHub の Issue とプルリクエスト）。バグ報告は版・環境・再現手順・期待と実際。脆弱性は非公開の窓口へ
:::

## 練習問題 {#practice}

:::q 1.11.1-01 single
フリーソフトウェア財団（FSF）が掲げる「4 つの自由」に**含まれない**ものはどれか。
- [ ] 目的を問わず、プログラムを実行する自由
- [ ] プログラムを研究し、改変する自由
- [ ] コピーを再配布する自由
- [ ] 改変したものを配布する自由
- [x] 料金を払わずにプログラムを入手できること
:::why
4 つの自由は、実行（0）、研究と改変（1）、再配布（2）、改変版の配布（3）です。フリーソフトウェアの「フリー」は**自由**のことで、価格が無料であることは求めていません。有料で販売してもかまいません（[オープンソースとは何か](#definition)）。
:::
:::

:::q 1.11.1-02 single
OSI の「オープンソースの定義」に照らして、オープンソースのライセンスとして**認められない**条件はどれか。
- [ ] 再配布するときに、ライセンスの全文を添えること
- [ ] 派生物には、元と異なる名前や版番号を付けること
- [x] 営利を目的とする企業での利用を禁止すること
- [ ] 改変は、元のソースとパッチを分けた形で配布すること
:::why
定義の条件 6「利用分野の差別の禁止」により、商用など特定の分野での利用を禁じることはできません。ライセンスの全文を添えること（MIT や BSD も求める一般的な条件で、どの条件にも反しない）、派生物に別の名前や版番号を求めること、元のソースとパッチを分けて配るよう求めること（条件 4「作者のソースコードの完全性」）は、定義が認めています。
:::
:::

:::q 1.11.1-03 multi
あるプログラムを改変して、実行形式だけを配布したい。改変した部分のソースコードを公開する義務が**ない**ライセンスを 2 つ選択してください。
- [x] MIT License
- [ ] GPL v3
- [ ] AGPL v3
- [x] BSD License（3 条項）
- [ ] GPL v2
:::why
MIT と BSD は寛容なライセンスで、コピーレフトがありません。著作権の表示などを残せば、改変したものをソースなしで配布できます。GPL v2 / v3 と AGPL v3 は強いコピーレフトで、配布するなら改変後のソースも入手できるようにする必要があります（[コピーレフトの強さ](#copyleft)）。
:::
:::

:::q 1.11.1-04 single
AGPL v3 の説明として正しいものはどれか。
- [ ] ライブラリとしてリンクするだけのプログラムには、条件が及ばない
- [ ] コピーレフトをファイル単位でかける
- [x] 改変したプログラムをネットワーク越しに利用させる場合も、その利用者に改変後のソースコードを入手する機会を与える
- [ ] 特許で訴えた者は、ライセンスによる特許の許諾を失う、という条項が主な特徴である
:::why
AGPL は GPL v3 に、ネットワーク越しの利用者へのソース提供（第 13 条）を足したものです。サーバーで動かすだけの Web サービスでも、改変したなら利用者がソースを入手できるようにします。リンクするだけなら及ばないのは LGPL、ファイル単位は MPL、特許の訴訟で許諾を失う条項が特徴なのは Apache 2.0 です。
:::
:::

:::q 1.11.1-05 single
LGPL のライブラリを使ったアプリケーションの扱いとして正しいものはどれか。
- [ ] ライブラリを使うアプリケーションは、必ず LGPL で配布しなければならない
- [x] ライブラリをリンクして使うだけのアプリケーションは、LGPL 以外のライセンスで配布できる
- [ ] ライブラリ自体を改変して配布しても、その改変のソースを提供する必要はない
- [ ] LGPL のライブラリは、商用のアプリケーションから利用できない
:::why
LGPL は弱いコピーレフトです。リンクして使うだけのアプリケーションは、ソースを公開しない商用ライセンスを含め、別のライセンスで配布できます。ただし、ライブラリそのものを改変して配布するなら、その改変は LGPL で出し、ソースも入手できるようにします。そのため 1・3・4 は誤りです（[LGPL](#copyleft)）。
:::
:::

:::q 1.11.1-06 single
Mozilla Public License 2.0（MPL 2.0）の説明として正しいものはどれか。
- [ ] コピーレフトがなく、MIT License とほぼ同じ条件である
- [ ] MPL のコードを 1 行でも含むプログラムは、全体を MPL で配布しなければならない
- [x] MPL のファイルを改変して配布するときは、そのファイルを MPL のままソースとともに提供する。ほかのファイルは別のライセンスにできる
- [ ] ネットワーク越しに利用させるだけでも、ソースの提供が必要になる
:::why
MPL 2.0 は**ファイル単位**の弱いコピーレフトです。MPL のファイルの改変は MPL で出しますが、同じプログラムのほかのファイルには及びません。コピーレフトがない（1）は MIT や BSD、全体に及ぶ（2）は GPL、ネットワーク越しの利用（4）は AGPL の特徴です。
:::
:::

:::q 1.11.1-07 single
寛容なライセンスのうち、貢献者から利用者への特許の許諾と、特許侵害で訴えた者はその許諾を失うという条項を持つものはどれか。
- [ ] MIT License
- [ ] BSD License（2 条項）
- [x] Apache License 2.0
- [ ] LGPL v2.1
:::why
Apache License 2.0 は、貢献者が特許の利用を許し、その作品が特許を侵害すると訴えた者は許諾を失う、という条項を持ちます。MIT と BSD には特許の条項がありません。LGPL v2.1 は寛容なライセンスではなく、弱いコピーレフトです（[寛容なライセンス](#permissive)）。
:::
:::

:::q 1.11.1-08 fill
GPL v3 をもとに、改変したプログラムをネットワーク越しに利用させる場合にも、その利用者に改変後のソースコードを入手する機会を与えることを求めるライセンスがある。その略称を英字 4 文字で入力してください。
= AGPL
= agpl
:::why
AGPL（GNU Affero General Public License）です。GPL は「配布」をきっかけに条件がかかるので、サーバーで動かすだけの利用ではソースを出さなくて済みました。AGPL はこれをふさぎます（[AGPL](#copyleft)）。
:::
:::

:::q 1.11.1-09 multi
オープンソースのソフトウェアと著作権・保証について正しいものを 2 つ選択してください。
- [ ] オープンソースのソフトウェアは、著作権が放棄されている
- [x] 著作権者は、ライセンスによって利用・改変・再配布を許している
- [x] 多くのライセンスは、ソフトウェアを現状のまま提供し、何も保証しないと定めている
- [ ] GPL のソフトウェアを有料で販売することは禁止されている
- [ ] 不具合で損害が出たときは、ライセンスにより作者が賠償する
:::why
オープンソースは著作権を放棄したものではなく、著作権者がライセンスで利用を許しているものです。また、MIT の「AS IS」や GPL の無保証の条項のように、ほとんどのライセンスは保証も責任も負わないと定めています。GPL は販売を禁じていません（[オープンソースとは何か](#definition)）。
:::
:::

:::q 1.11.1-10 single
ライセンスに関する説明として**誤っている**ものはどれか。
- [ ] パブリックドメインのソフトウェアは、著作権による制限がなく、だれでも条件なしに利用できる
- [ ] デュアルライセンスとは、著作権者が同じソフトウェアを複数のライセンスで提供することである
- [ ] MIT License のコードは、GPL のプログラムに取り込んで、全体を GPL で配布できる
- [x] GPL のプログラムを改変して社内だけで使う場合も、改変したソースコードを一般に公開しなければならない
:::why
GPL の条件は、プログラムを**配布するとき**にかかります。改変しても社内だけで使い、外へ配布しないなら、ソースを公開する義務はありません。ほかの 3 つは正しい説明です。MySQL の GPL と商用ライセンスは、デュアルライセンスの例です（[寛容なライセンス、パブリックドメイン、デュアルライセンス](#permissive)）。
:::
:::

:::q 1.11.2-01 single
オープンソースのプロジェクトへのバグ報告として**適切でない**ものはどれか。
- [ ] 報告の前に、同じ不具合がすでに報告されていないか検索する
- [ ] 使っているソフトウェアの版と、OS などの環境を書く
- [ ] 再現手順と、期待した結果・実際の結果を書く
- [x] 見つけたセキュリティの脆弱性を、すぐに公開の掲示板に詳しく書き込む
:::why
脆弱性は、修正前に公開されると悪用されるおそれがあります。プロジェクトが定めた非公開の窓口に知らせます。ほかの 3 つは、良いバグ報告に欠かせないことです（[コミュニティにどう関わるか](#community)）。
:::
:::

:::q 1.11.2-02 single
Linux カーネルの開発で、パッチの投稿と審査の議論に主に使われているものはどれか。
- [ ] 利用者どうしが質問し合う掲示板
- [x] メーリングリスト
- [ ] チャットのボット
- [ ] 商用のサポート窓口
:::why
Linux カーネルは、パッチをメールでメーリングリストに送り、そこで審査して議論します。掲示板は主に利用者どうしの質問と回答の場です。サポート窓口は保証やサポートを買った利用者のためのもので、開発の議論の場ではありません。
:::
:::

:::q 1.11.2-03 fill
GitHub で、自分のリポジトリ（フォーク）やブランチで加えた変更を、元のプロジェクトに取り込んでもらうよう依頼する機能の名前を、カタカナで入力してください。
= プルリクエスト
= プル・リクエスト
:::why
プルリクエスト（pull request）です。メンテナが変更を読み、議論し、良ければ取り込みます。GitLab では同じ機能をマージリクエストと呼びます。不具合や要望を記録するのは Issue です。
:::
:::

:::q 1.11.2-04 multi
オープンソースの開発体制の説明として正しいものを 2 つ選択してください。
- [x] メンテナは、担当する範囲でパッチを取り込むかどうかを判断する
- [ ] リポジトリへ直接書き込む権利は、プロジェクトに登録した全員に自動で与えられる
- [x] 方針が合わない場合、ソースを複製して別のプロジェクトとして開発を続けること（フォーク）ができる
- [ ] 企業に所属する開発者は、オープンソースの開発に参加できない
- [ ] ライセンスの条件により、作者は開発をやめることができない
:::why
メンテナが取り込みを判断し、ソースが公開されているのでフォークもできます（LibreOffice や MariaDB）。直接書き込む権利（コミット権）は貢献を重ねて認められた人に与えられるもので、自動ではありません。企業の開発者も多く参加しています。作者はいつでも開発をやめられ、だからこそ引き継げることが大事です。
:::
:::

:::q 1.11.2-05 multi
プログラムを書かずにできる、オープンソースのプロジェクトへの貢献として適切なものを 2 つ選択してください。
- [x] ソフトウェアを使い、見つけた不具合を手順付きで報告する
- [ ] 著作権の表示を消して、自分の作品として再配布する
- [x] ブログや勉強会で、使い方を紹介する
- [ ] 同じ不具合を、目立つように何度も別々に報告する
- [ ] ライセンスを読まずに、他のプロジェクトのコードを貼り付けて投稿する
:::why
使って報告すること、紹介することは、どちらも大事な貢献です。著作権の表示を消すのはライセンス違反です（MIT でさえ表示を残すことを求めます）。重複した報告はメンテナの手間を増やします。ライセンスを確かめずに他のコードを持ち込むと、プロジェクトをライセンス違反に巻き込みます。
:::
:::
