## SUID ファイルとパスワードの期限を点検する {#audit}

### find -perm で SUID / SGID のファイルを探す

[図解 Linux 4.9](../../linux/site/ch04.html#special) で見たとおり、**SUID**（setuid）ビットの付いたプログラムは、起動した人ではなく**ファイルの持ち主**の権限で動きます。持ち主が root なら、だれが起動しても root として動きます。`passwd` や `sudo` に必要な仕組みですが、攻撃者が SUID root のシェルを置いていけば、それは裏口になります。

そこで管理者は、SUID と **SGID**（setgid）の付いたファイルを定期的に一覧にし、見覚えのないものがないかを調べます。使うのは `find` の `-perm`（permission）です。

```sh run title="SUID の付いたファイルを探す"
find /usr/bin -perm -4000 -ls
```

`-ls` は、見つけたファイルを `ls -dils` の形で表示します。3 つとも持ち主の `x` の場所が `s` になっています。特別なビットの数字を、もう一度確かめておきます。

| ビット | 数字 | `ls -l` の表示 | 探し方の例 |
| --- | --- | --- | --- |
| SUID | 4000 | 持ち主の `x` が `s`（`x` がなければ `S`） | `find / -perm -4000` |
| SGID | 2000 | グループの `x` が `s`（`x` がなければ `S`） | `find / -perm -2000` |
| スティッキー | 1000 | その他の `x` が `t`（`x` がなければ `T`） | `find / -perm -1000` |

`-perm` は、数字の前に付ける記号で意味が変わります。ここが試験でいちばん問われます。

| 書き方 | 意味 | `-perm ? 4000` に `4755` は合うか |
| --- | --- | --- |
| `-perm 4755` | 権限が**ぴったり**その値 | `-perm 4000` には合わない（4755 ≠ 4000） |
| `-perm -4000` | 書いたビットが**全部**立っている（ほかのビットは問わない） | 合う |
| `-perm /6000` | 書いたビットの**どれか 1 つでも**立っている | 合う |

SGID のファイルを 1 つ作って、3 つの書き方を比べます。

```sh run root title="-perm の 3 つの書き方を比べる"
cp /usr/bin/cat /usr/local/bin/gcat
chmod 2755 /usr/local/bin/gcat
ls -l /usr/local/bin/gcat
find /usr -perm /6000 -type f
find /usr -perm -2000 -type f
find /usr -perm -6000 -type f
```

`/6000` は「SUID か SGID の**どちらか**」なので、4 つ全部が出ました。`-2000` は SGID だけです。`-6000` は「SUID と SGID の**両方**」なので、1 つも出ません。

```sh run root title="片づける"
rm /usr/local/bin/gcat
```

:::warn 試験の注意：-perm の - と /
`-perm -4000` は「全部のビット」、`-perm /6000` は「どれか 1 つ」です。SUID と SGID の**どちらか**が付いたファイルを探すなら `/6000`、**両方**なら `-6000` です。記号なしの `-perm 4000` は「権限がちょうど 4000」という意味になり、ふつうは何も見つかりません。古い本には `+6000` という書き方もありますが、今の GNU find では使えません。記号の形（`-perm -u=s`、`-perm /u=s,g=s`）でも書けます。
:::

本物の Linux で `/` 全体を探すと、読めないディレクトリや `/proc` の中で消えたファイルのエラーが出ます。`find / -perm -4000 -type f 2>/dev/null` のように、標準エラーを捨てて使うのが定番です。

### passwd と usermod でアカウントをロックする

退職した人や、しばらく使わないアカウントは、消す前にまず**ロック**します。ロックすると、パスワードではログインできなくなります。

```sh run title="alice をロックし、状態を見る"
sudo passwd -S alice
sudo passwd -l alice
sudo passwd -S alice
sudo grep '^alice:' /etc/shadow
```

`passwd -S`（status）は、自分の状態なら一般ユーザーでも、他人の状態は root だけが見られます。2 つ目の欄が `P`（使えるパスワードがある）から `L`（locked）に変わりました。`/etc/shadow` を見ると、パスワードのハッシュの先頭に `!` が付いています。ロックの正体はこれだけです。ハッシュの頭に `!` が付くと、どんなパスワードを打っても合わなくなります。元のハッシュは残っているので、`!` を取れば元のパスワードで入れます。

```sh run title="ロックを外す"
sudo passwd -u alice
sudo passwd -S alice
```

他人のアカウントをロックできるのは root だけです。

```sh run error title="一般ユーザーは他人をロックできない"
passwd -l alice
```

`usermod` でも同じことができます。`-L`（大文字）でロック、`-U` で解除です。Debian で確かめると、`passwd -l` と同じく、ハッシュの先頭に `!` が付きます。

```console
# usermod -L alice
# grep '^alice:' /etc/shadow
alice:!$y$j9T$WW54jiwe9F7d2E55D2yF3/$3IBd…:20773:0:99999:7:::
# usermod -U alice
```

| したいこと | passwd | usermod |
| --- | --- | --- |
| ロックする | `passwd -l ユーザー` | `usermod -L ユーザー` |
| ロックを外す | `passwd -u ユーザー` | `usermod -U ユーザー` |
| 状態を見る | `passwd -S ユーザー` | — |
| アカウントの有効期限を決める | — | `usermod -e 2027-03-31 ユーザー` |

:::warn 試験の注意：ロックは「パスワードで入れない」だけ
`passwd -l` と `usermod -L` が止めるのは、**パスワードによる認証**です。SSH の公開鍵（1.10.3）で入る道は、これだけでは止まりません。アカウントそのものを使えなくするには、有効期限を過去の日付にする（`usermod -e` や `chage -E`）か、ログインシェルを `/usr/sbin/nologin` にします（[1.10.2](#login)）。また、`passwd -l` の `l` は小文字、`usermod -L` の `L` は大文字です。
:::

### chage でパスワードの期限を決める

パスワードを長く変えないままにしないよう、**期限**を決めます。期限の情報は `/etc/shadow` の 3〜8 番目の欄に入っていて、`chage`（change age）で見たり変えたりします。`chage` は小さな Linux にないので、Debian 12 で実行した結果を見ます。

```console
# chage -l alice
Last password change					: Nov 16, 2026
Password expires					: never
Password inactive					: never
Account expires						: never
Minimum number of days between password change		: 0
Maximum number of days between password change		: 99999
Number of days of warning before password expires	: 7
# chage -M 90 -m 7 -W 14 -I 30 -E 2027-03-31 alice
# chage -l alice
Last password change					: Nov 16, 2026
Password expires					: Feb 14, 2027
Password inactive					: Mar 16, 2027
Account expires						: Mar 31, 2027
Minimum number of days between password change		: 7
Maximum number of days between password change		: 90
Number of days of warning before password expires	: 14
# grep '^alice:' /etc/shadow
alice:$y$j9T$WW54jiwe9F7d2E55D2yF3/$3IBd…:20773:7:90:14:30:20908:
```

最後に変えた日（11 月 16 日）から 90 日で期限が切れ（2 月 14 日）、その 30 日後（3 月 16 日）にはパスワードが使えなくなります。それとは別に、アカウントそのものが 3 月 31 日で使えなくなります。`/etc/shadow` の数字の欄は、1970 年 1 月 1 日からの**日数**です（20773 が 2026 年 11 月 16 日）。

```fig layout /etc/shadow の 1 行。: で区切られた 9 つの欄。chage のオプションは、3〜8 番目の欄を書き換える
{
  unit: '',
  rows: [
    { label: '欄', cells: [
      { t: '1 名前', w: 1.4 }, { t: '2 ハッシュ', w: 1.6, kind: 'accent' }, { t: '3 最終変更日', w: 1.6 }, { t: '4 最短', w: 1 }, { t: '5 最長', w: 1 }, { t: '6 警告', w: 1 }, { t: '7 猶予', w: 1 }, { t: '8 失効日', w: 1.3 }, { t: '9', w: 0.5 } ] },
    { label: '例', cells: [
      { t: 'alice', w: 1.4 }, { t: '$y$…', w: 1.6, kind: 'accent' }, { t: '20773', w: 1.6 }, { t: '7', w: 1 }, { t: '90', w: 1 }, { t: '14', w: 1 }, { t: '30', w: 1 }, { t: '20908', w: 1.3 }, { t: '', w: 0.5 } ] },
    { label: 'chage', cells: [
      { t: '', w: 1.4 }, { t: 'passwd -l で先頭に !', w: 1.6 }, { t: '-d', w: 1.6 }, { t: '-m', w: 1 }, { t: '-M', w: 1 }, { t: '-W', w: 1 }, { t: '-I', w: 1 }, { t: '-E', w: 1.3 }, { t: '', w: 0.5 } ] },
  ],
}
```

| オプション | 意味 | `/etc/shadow` の欄 |
| --- | --- | --- |
| `-l` | 期限の情報を表示する（list） | — |
| `-d 日付` | 最後にパスワードを変えた日にする。**`-d 0` なら、次のログインで変更を強制** | 3 |
| `-m 日数` | 変えてから次に変えられるまでの最短日数（minimum） | 4 |
| `-M 日数` | パスワードの有効期間の最長日数（maximum） | 5 |
| `-W 日数` | 期限切れの何日前から警告するか（warning） | 6 |
| `-I 日数` | 期限が切れてから、使えなくなるまでの猶予（inactive） | 7 |
| `-E 日付` | **アカウント**の有効期限（expire）。`-E -1` で期限なし | 8 |

オプションを付けずに `chage alice` と打つと、1 つずつ質問される対話の形になります。

**-m と -M、-E と -M。** 小文字の `-m` は**最短**日数、大文字の `-M` は**最長**日数です。「90 日ごとに変えさせたい」なら `-M 90` です。また、`-M` が決めるのは**パスワード**の期限で、`-E` が決めるのは**アカウント**の期限です。`-E` の日を過ぎると、パスワードが正しくてもログインできません。

### ss と netstat：待ち受けているポートの一覧

[図解 Linux 16.6](../../linux/site/ch16.html#states) で使った `ss` です。Web サーバを起動して、待ち受けている TCP のポートを見ます。

```sh run title="待ち受けているポートを見る"
sudo systemctl start httpd
ss -tln
ss -tlnp
sudo ss -tlnp
```

`-p`（process）を付けると、そのソケットを持っているプロセスが出ます。ただし、**他人のプロセスは root でないと見えません**。`httpd` は root で動いているので、`sudo` を付けたときだけ `users:(("httpd",pid=…))` が出ました。

`netstat` は `ss` の前から使われてきたコマンドで、主なオプションの文字は同じです（Debian では net-tools というパッケージに入っています）。

```console
# netstat -tlnp
Active Internet connections (only servers)
Proto Recv-Q Send-Q Local Address           Foreign Address         State       PID/Program name    
tcp        0      0 0.0.0.0:8080            0.0.0.0:*               LISTEN      3352/python3        
```

| オプション | ss と netstat で共通の意味 |
| --- | --- |
| `-t` | TCP |
| `-u` | UDP |
| `-l` | 待ち受け中（LISTEN）だけ |
| `-a` | 待ち受け中も、接続中も全部 |
| `-n` | ポート番号やアドレスを名前に直さない（`:22` を `:ssh` にしない） |
| `-p` | 使っているプロセス（PID と名前） |

`ss -tulnp`（または `netstat -tulnp`）は「TCP と UDP の、待ち受け中のポートを、番号のまま、プロセス付きで」という、点検の定番の形です。

### lsof と fuser：だれが、それを使っているか

`lsof`（list open files）は、プロセスが開いているファイルを一覧にします。Linux ではソケットも fd の 1 つなので、ネットワークの接続も出ます（[図解 Linux 9.9](../../linux/site/ch09.html#deleted)）。

```sh run title="httpd が開いているもの"
sudo lsof -p $(pgrep httpd)
```

fd 3 の `sock` が、80 番で待ち受けているソケットです。本物の `lsof` には、ネットワークのファイルだけを選ぶ `-i` があります（小さな Linux の `lsof` には `-i` がないので、Debian 12 の結果を見ます）。

```console
# lsof -i :8080
COMMAND  PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
python3 3352 root    3u  IPv4 120195      0t0  TCP *:8080 (LISTEN)
# lsof -i tcp:8080 -P -n
COMMAND  PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
python3 3352 root    3u  IPv4 120195      0t0  TCP *:8080 (LISTEN)
```

| 書き方 | 意味 |
| --- | --- |
| `lsof -i` | ネットワークのファイル（ソケット）を全部 |
| `lsof -i :ポート` | そのポートを使っているもの |
| `lsof -i tcp:22` | TCP の 22 番 |
| `lsof -p PID` | そのプロセスが開いているもの全部 |
| `lsof ファイル` | そのファイルを開いているプロセス |

`fuser`（file user）は、逆向きに「このファイルやポートを使っているプロセスの PID」を出します。`-v` で詳しく、`-k` で**そのプロセスを殺します**（既定は SIGKILL）。

```console
# fuser -v -n tcp 8080
                     USER        PID ACCESS COMMAND
8080/tcp:            root       3352 F.... python3
# fuser -v /tmp
                     USER        PID ACCESS COMMAND
/tmp:                root       3362 ..c.. sh
                     root       3363 ..c.. sleep
# fuser -k /tmp
/tmp:                 3362c  3363c
```

`-n tcp 8080` は `8080/tcp` とも書けます。ACCESS の欄の `c` はカレントディレクトリ、`F` は開いているファイル、`e` は実行中のプログラム、`r` はルートディレクトリとして使っている、という意味です。`umount` が「target is busy」で失敗したとき、`fuser -vm /mnt/usb` で犯人を探し、`fuser -km` でまとめて終わらせる、という使い方をします。

### nmap：外から見て、開いているポート

`ss` は「この機械が待ち受けているつもりのポート」です。ファイアウォールで閉じていれば、外からは届きません。外から本当に開いて見えるかは、**ポートスキャナ**の `nmap` で、別の機械から確かめます。

```console
$ nmap 127.0.0.1
Starting Nmap 7.93 ( https://nmap.org ) at 2026-11-16 11:15 UTC
Nmap scan report for localhost (127.0.0.1)
Host is up (0.0000010s latency).
Not shown: 999 closed tcp ports (reset)
PORT     STATE SERVICE
8080/tcp open  http-proxy
$ nmap -p 22,80,8080 127.0.0.1
PORT     STATE  SERVICE
22/tcp   closed ssh
80/tcp   closed http
8080/tcp open   http-proxy
```

引数なしでは、よく使われる 1000 個のポートを調べます。`-p` で調べるポートを決められます。STATE の `open` は受け付けている、`closed` はだれも待ち受けていない、`filtered` はファイアウォールで応答がない、という意味です。

**他人の機械に nmap を使わない。** ポートスキャンは、攻撃の下調べと同じ動きです。自分が管理していない機械やネットワークに向けて実行すると、不正アクセスを疑われ、契約や法律に反することがあります。点検は、自分の管理する機械に、許可を得て行います。

### who、w、last、lastb：ログインの記録

だれがログインしているか、いつだれが入ったかも、点検の材料です。小さな Linux にはログインの記録がないので、Debian 12 に SSH で 2 人がログインし、root のパスワードを 1 回まちがえたあとの結果を見ます。

```console
# who
alice    pts/3        Nov 16 11:19 (127.0.0.1)
bob      pts/4        Nov 16 11:19 (127.0.0.1)
# w
 11:19:06 up 11 min,  2 users,  load average: 5.23, 4.21, 2.21
USER     TTY      FROM             LOGIN@   IDLE   JCPU   PCPU WHAT
alice    pts/3    127.0.0.1        11:19    4.00s  0.00s   ?    sleep 8
bob      pts/4    127.0.0.1        11:19    4.00s  0.00s   ?    top -b -d 1 -n 8
# last
bob      pts/4        127.0.0.1        Mon Nov 16 11:19   still logged in
alice    pts/3        127.0.0.1        Mon Nov 16 11:19   still logged in
alice    pts/1        127.0.0.1        Mon Nov 16 11:19 - 11:19  (00:00)

wtmp begins Mon Nov 16 11:19:00 2026
# lastb
root     ssh:notty    127.0.0.1        Mon Nov 16 11:19 - 11:19  (00:00)

btmp begins Mon Nov 16 11:19:03 2026
```

| コマンド | 何を出すか | 読むファイル |
| --- | --- | --- |
| `who` | いまログインしている人 | `/var/run/utmp` |
| `w` | いまログインしている人と、**何をしているか**（WHAT）。1 行目は `uptime` と同じ | `/var/run/utmp` |
| `last` | ログインの**履歴**（いつからいつまで）。再起動の記録も出る | `/var/log/wtmp` |
| `lastb` | ログインに**失敗した**記録。root だけが読める | `/var/log/btmp` |

`lastb` に見知らぬ送り元からの失敗が大量に並んでいたら、パスワードを当てようとする攻撃を受けています。

## 権限と資源を絞る：su、sudo、ulimit、TMOUT {#limits}

### su と su -

`su` は別のユーザーのシェルを始めるコマンドで、相手のパスワードをたずねます（[図解 Linux 4.8](../../linux/site/ch04.html#root)）。ユーザー名を省くと root です。試験で問われるのは、`-`（ハイフン）を付けるかどうかの違いです。

```sh run title="su と su - の違い"
pwd
sudo su alice -c 'pwd; echo $HOME'
sudo su - alice -c 'pwd; echo $HOME'
```

`su alice` は、ユーザーだけが alice に変わり、いる場所は `/home/you` のままです。`su - alice` は、alice が**ログインしたのと同じ**状態を作ります。ホームディレクトリへ移り、ログインのときに読む設定ファイル（`/etc/profile`、`~/.bash_profile` など）を読み直し、環境変数も alice のものに入れ替えます。

| 書き方 | 意味 |
| --- | --- |
| `su` | root になる。いまの場所と環境変数の多くは引き継ぐ |
| `su -`（`su -l`、`su --login`） | root として**ログインし直した**状態になる。root のホームへ移り、`PATH` なども root のもの |
| `su ユーザー` / `su - ユーザー` | そのユーザーになる |
| `su -c 'コマンド' ユーザー` | そのユーザーとしてコマンドを 1 つ実行して戻る |

:::warn 試験の注意：su - を使う理由
`su` だけで root になると、`PATH` が一般ユーザーのままのことがあり、`/usr/sbin` のコマンドが見つからない、自分の作った同名のコマンドが動いてしまう、といった事故が起きます。root の作業は `su -` で始めるのが安全です。また、`su` でたずねられるのは**なる相手の**パスワード、`sudo` でたずねられるのは**自分の**パスワードです。
:::

### sudo と /etc/sudoers

`sudo` は、`/etc/sudoers` で許されたコマンドだけを、root などの別のユーザーとして実行します。root のパスワードを教えずに、必要な権限だけを渡せます。

```sh run title="小さな Linux の /etc/sudoers"
sudo cat /etc/sudoers
sudo -l
sudo -u alice id
```

`-l` は自分に許されていることの一覧、`-u ユーザー` は root 以外のユーザーとして実行する、という意味です。

`/etc/sudoers` の 1 行は、次の形です。

```fig graph /etc/sudoers の 1 行の読み方。「だれが、どの機械で、だれとして、何を」の順に書く
{
  col: 170, row: 92,
  nodes: [
    { id: 'u', label: '%wheel', sub: 'だれが\n（% はグループ）', x: 0, y: 0 },
    { id: 'h', label: 'ALL=', sub: 'どの機械で', x: 1, y: 0 },
    { id: 'r', label: '(root)', sub: 'だれとして', x: 2, y: 0 },
    { id: 't', label: 'NOPASSWD:', sub: 'パスワードを\nたずねない', x: 3, y: 0, kind: 'stack' },
    { id: 'c', label: '/usr/bin/systemctl', sub: '何を\n（フルパス）', x: 4, y: 0, kind: 'accent' },
  ],
  edges: [ { from: 'u', to: 'h' }, { from: 'h', to: 'r' }, { from: 'r', to: 't' }, { from: 't', to: 'c' } ],
}
```

Debian 12 で、2 つの規則を書いてから確かめた例です。

```console
# cat /etc/sudoers.d/test
alice ALL=(root) /usr/bin/systemctl restart nginx, /usr/bin/journalctl
%ops ALL=(ALL) NOPASSWD: ALL
# visudo -c
/etc/sudoers: parsed OK
/etc/sudoers.d/README: parsed OK
/etc/sudoers.d/test: parsed OK
# sudo -l -U alice
…
User alice may run the following commands on 7a717555d2b0:
    (root) /usr/bin/systemctl restart nginx, /usr/bin/journalctl
```

alice は 2 つのコマンドだけを root として実行でき、そのたびに**自分の**パスワードをたずねられます。ops グループのメンバーは、何でも、パスワードなしで実行できます。

| 書き方 | 意味 |
| --- | --- |
| `alice` | ユーザー alice |
| `%wheel`、`%sudo` | そのグループのメンバー |
| `ALL` | すべて（機械、ユーザー、コマンド） |
| `(root)`、`(ALL)`、`(ALL:ALL)` | だれとして実行できるか（`:` の後ろはグループ） |
| `NOPASSWD:` | パスワードをたずねない |
| `コマンド, コマンド` | 許すコマンド。フルパスで、カンマで区切る |

管理者のグループは、Debian 系では `sudo`（`%sudo ALL=(ALL:ALL) ALL`）、Red Hat 系では `wheel`（`%wheel ALL=(ALL) ALL`）です。

`/etc/sudoers` は、エディタで直接開かずに **`visudo`** で編集します。`visudo` は、ほかの人と同時に編集しないようにロックし、保存するときに**書式を検査**します。書きまちがえたまま保存すると、`sudo` がまったく使えなくなるからです。`visudo -c` は検査だけをします。

```console
# echo "alice ALL=(root /usr/bin/ls" > /etc/sudoers.d/bad
# visudo -c
/etc/sudoers.d/bad:1:28: syntax error
alice ALL=(root /usr/bin/ls
                           ^
```

**規則は /etc/sudoers.d/ に分けて置ける。** 今の `/etc/sudoers` の最後には `@includedir /etc/sudoers.d`（古い形は `#includedir`）があり、`/etc/sudoers.d/` の中のファイルも読まれます。規則を用途ごとのファイルに分けると、管理しやすくなります。そのファイルも `visudo -f /etc/sudoers.d/ファイル` で編集します。

### ulimit：プロセスが使える資源の上限

1 人のユーザーがプロセスを作りすぎたり、巨大なファイルを書いたりすると、機械全体が止まります。シェルの組み込みコマンド `ulimit` は、そのシェルと、そこから起動するプロセスが使える資源に上限を付けます（[図解 Linux 8.3](../../linux/site/ch08.html#default) では core の大きさに使いました）。

```sh run title="いまの上限を全部見る"
ulimit -a
```

| オプション | 資源 |
| --- | --- |
| `-a` | 全部を表示する |
| `-n` | 開けるファイル（fd）の数 |
| `-u` | 作れるプロセスの数（ユーザーごと） |
| `-f` | 書けるファイルの大きさ |
| `-c` | core ファイルの大きさ |
| `-s` | スタックの大きさ |
| `-t` | 使える CPU 時間（秒） |
| `-v` | 仮想メモリの大きさ |

上限には 2 種類あります。**ソフトリミット**は実際に効く値で、**ハードリミット**はソフトリミットを上げられる天井です。`-S` と `-H` で選びます。

```sh run title="ソフトとハード"
ulimit -Sn
ulimit -Hn
ulimit -n
```

`-S` も `-H` も付けずに表示すると、ソフトリミットが出ます。一般ユーザーは、ハードリミットを**下げることはできますが、上げることはできません**。上げられるのは root だけです。

```sh run error title="一度下げたハードリミットは、一般ユーザーには戻せない"
sh -c 'ulimit -Hn 2048; ulimit -Hn; ulimit -Hn 4096'
```

`-S` も `-H` も付けずに値を**設定**すると、ソフトとハードの両方が変わります。ログインのたびに決まった上限を付けたいときは、`/etc/security/limits.conf` に `ユーザー soft nofile 4096` のように書きます。

**ulimit の n と u と f。** `-n` は number of open files（ファイルの**数**）、`-u` は user processes（プロセスの数）、`-f` は file size（ファイルの**大きさ**）です。「ファイル」が付くものが 2 つあるので注意します。`ulimit -c 0` は core ファイルを作らせない設定です。

### TMOUT：放置したシェルを自動でログアウトさせる

ログインしたまま席を離れた端末は、だれにでも使われてしまいます。bash は、環境変数 **`TMOUT`** に秒数が入っていると、プロンプトでその秒数だけ何も入力されなかったときに、自動でシェルを終わらせます（ログアウトします）。0 か空なら、何もしません。

全員に効かせるには `/etc/profile`（または `/etc/profile.d/` のファイル）に書き、`readonly` にして利用者が消せないようにします。

```console
# cat /etc/profile.d/tmout.sh
TMOUT=600
readonly TMOUT
export TMOUT
```

```sh run error title="readonly にした TMOUT は変えられない"
sh -c 'TMOUT=600; readonly TMOUT; TMOUT=0'
```

## ログインを止める：/etc/passwd、/etc/shadow、/etc/nologin {#login}

### パスワードは /etc/shadow に分けてある

`/etc/passwd` は、`ls -l` がユーザー名を表示するためなどに、だれでも読めなければなりません（[図解 Linux 4.1](../../linux/site/ch04.html#users)）。そこにパスワードのハッシュを置くと、だれでも持ち出して、総当たりで元のパスワードを探せてしまいます。そこで今の Linux は、ハッシュを root しか読めない `/etc/shadow` に分けています。`/etc/passwd` の 2 つ目の欄の `x` は、「パスワードは `/etc/shadow` にある」という印です。

```sh run title="/etc/passwd と /etc/shadow の権限"
ls -l /etc/passwd /etc/shadow
head -3 /etc/passwd
```

| ファイル | 権限（Debian 12） | 権限（Rocky Linux 9） | 中身 |
| --- | --- | --- | --- |
| `/etc/passwd` | `644`（だれでも読める） | `644` | ユーザー名、uid、gid、ホーム、ログインシェル。2 つ目の欄は `x` |
| `/etc/shadow` | `640`（root と shadow グループ） | `000`（root だけ） | パスワードのハッシュと期限 |

`/etc/shadow` の 2 つ目の欄の特別な値も覚えておきます。

| 2 つ目の欄 | 意味 |
| --- | --- |
| `$y$…`、`$6$…` | パスワードのハッシュ（`$y$` は yescrypt、`$6$` は SHA-512） |
| `!` や `!` で始まる値 | ロックされている（`passwd -l`、`usermod -L`） |
| `*` | パスワードが設定されていない。パスワードではログインできない |
| 空 | パスワードなしでログインできる（危険） |

### ログインシェルを nologin にする

`daemon` や `nobody` のような、サービスを動かすためのユーザーは、人がログインする必要がありません。そこで、ログインシェルを **`/usr/sbin/nologin`**（Red Hat 系では `/sbin/nologin` とも書く）にしてあります。

```sh run title="ログインできないユーザー"
grep nologin /etc/passwd
```

`nologin` は、「This account is currently not available.」と表示して、すぐに終わるだけのプログラムです。ログインシェルがすぐ終わるので、ログインした瞬間にログアウトします。`/bin/false`（何も表示せずに失敗で終わる）を使うこともあります。

```console
# usermod -s /usr/sbin/nologin bob
# su - bob
This account is currently not available.
```

### /etc/nologin で、一時的に全員を止める

メンテナンスのあいだ、一般ユーザーにログインしてほしくないときは、**`/etc/nologin`** というファイルを作ります。このファイルがあると、**root 以外**のログインが断られ、ファイルの中身が断られた人に表示されます。作業が終わったら、ファイルを消せば元に戻ります。

```console
# echo "メンテナンス中です。18 時に再開します。" > /etc/nologin
（一般ユーザーが ssh で入ろうとすると、この文が表示されて切断される）
# rm /etc/nologin
```

:::warn 試験の注意：nologin が 2 つある
**`/usr/sbin/nologin`**（`/sbin/nologin`）は、ユーザーごとのログインシェルに指定する**プログラム**で、そのユーザーだけを止めます。**`/etc/nologin`** は、置くだけで root 以外の**全員**を止める**ファイル**です。root は `/etc/nologin` があってもログインできます。
:::

## 不要なサービスを止める：inetd、xinetd、systemd {#services}

待ち受けているサービスが少ないほど、攻撃される入り口は減ります。使わないサービスは、止めるだけでなく、起動時に動かないようにします。

### inetd と xinetd：スーパーサーバ

昔の Linux では、telnet や ftp のようなたまにしか使わないサービスを、常に動かしておく代わりに、**スーパーサーバ**に任せました。スーパーサーバが代わりにたくさんのポートで待ち受け、接続が来たときにだけ、そのサービスのプログラムを起動します。

**inetd** は、1 つのファイル `/etc/inetd.conf` に、1 行 1 サービスで書きます（`/etc/inetd.d/` に分けて置ける実装もあります）。行の頭に `#` を付けると、そのサービスは無効になります。Debian 12 の openbsd-inetd の例です。

```console
# grep -E '^#[a-z]' /etc/inetd.conf
#echo		stream	tcp	nowait	root	internal
#discard		stream	tcp	nowait	root	internal
#discard		dgram	udp	wait	root	internal
```

欄は「サービス名、ソケットの種類、プロトコル、wait か nowait、実行するユーザー、プログラム、引数」の順です。

**xinetd**（extended inetd）は、inetd を改良したものです。全体の設定 `/etc/xinetd.conf` と、サービスごとのファイルを置くディレクトリ **`/etc/xinetd.d/`** に分かれています。サービスを止めるには、そのファイルで **`disable = yes`** にして、xinetd を再起動します。

```console
# cat /etc/xinetd.conf
defaults
{
}
includedir /etc/xinetd.d
# grep -v '^#' /etc/xinetd.d/daytime | head -10
service daytime
{
	disable		= yes
	type		= INTERNAL
	id		= daytime-stream
	socket_type	= stream
	protocol	= tcp
	user		= root
	wait		= no
}
```

| | inetd | xinetd |
| --- | --- | --- |
| 設定ファイル | `/etc/inetd.conf`（`/etc/inetd.d/`） | `/etc/xinetd.conf` と `/etc/xinetd.d/サービス名` |
| 止め方 | 行の頭に `#` を付ける | `disable = yes` にする |
| 反映 | inetd を再起動する | xinetd を再起動する |

今は systemd が同じ役目（ソケットで待ち受け、接続が来たらサービスを起動する）を持っているので、inetd と xinetd はほとんど使われません。Rocky Linux 9 には xinetd のパッケージがありません。試験では、ファイルの場所と止め方を覚えておきます。

### systemctl：起動時に動かさない、絶対に動かさない

systemd のサービスは `systemctl` で操作します（[図解 Linux 17.5](../../linux/site/ch17.html#systemctl)）。セキュリティで大事なのは、**いま止める**ことと、**次の起動で動かさない**ことが別の操作だという点です。

```sh run title="enable と disable の正体"
systemctl list-unit-files
sudo systemctl enable httpd
ls -l /etc/systemd/system/multi-user.target.wants
systemctl is-enabled httpd
sudo systemctl disable httpd
```

`enable` は、`/etc/systemd/system/multi-user.target.wants/` にシンボリックリンクを作るだけです。`disable` はそれを消します。どちらも、いま動いているかどうかは変えません。

さらに強い **`mask`** があります。unit ファイルの場所に `/dev/null` へのリンクを置き、手で `start` しても、ほかのサービスに引っぱられても、**起動できなく**します（小さな Linux の systemctl には mask がないので、Rocky Linux 9 の結果です）。

```console
# systemctl mask firewalld
Created symlink /etc/systemd/system/firewalld.service → /dev/null.
# systemctl unmask firewalld
Removed "/etc/systemd/system/firewalld.service".
```

| コマンド | 効果 | いつ効くか |
| --- | --- | --- |
| `systemctl stop サービス` | 止める | いま |
| `systemctl disable サービス` | 起動時に自動で起動しない | 次の起動から |
| `systemctl disable --now サービス` | 両方 | いま + 次から |
| `systemctl mask サービス` | どんな方法でも起動できなくする | いま + 次から |
| `systemctl unmask サービス` | mask を外す | — |
| `systemctl is-enabled サービス` | enabled / disabled / masked を表示 | — |

### /etc/init.d、service、chkconfig：SysV init の道具

systemd の前の **SysV init** では、サービスごとの起動スクリプトが **`/etc/init.d/`** に置かれていました（Red Hat 系では `/etc/rc.d/init.d/` へのシンボリックリンク）。スクリプトに `start`、`stop`、`status` を渡して操作します。`service` コマンドは、それを短く書くためのものです。

```console
# /etc/init.d/myapp status
running
# service myapp status
running
# service sshd status
Redirecting to /bin/systemctl status sshd.service
```

systemd の機械では、`service` は `systemctl` に読み替えて実行します。

起動時にどのランレベルで動かすかは、Red Hat 系では **`chkconfig`** で決めました。

```console
# chkconfig --list myapp
myapp          	0:off	1:off	2:off	3:on	4:on	5:on	6:off
# chkconfig myapp off
# chkconfig --level 35 myapp on
# chkconfig --list myapp
myapp          	0:off	1:off	2:off	3:on	4:off	5:on	6:off
# chkconfig sshd on
Note: Forwarding request to 'systemctl enable sshd.service'.
```

`--level` を付けずに `chkconfig サービス on` とすると、ランレベル 2・3・4・5 がまとめて on になります（Rocky Linux 9 で確かめました）。`--level 35` なら 3 と 5 だけです。`chkconfig --add` は、`/etc/init.d/` のスクリプトの中の `# chkconfig:` の行に従って登録します。

| SysV init（古い） | systemd（今） |
| --- | --- |
| `service サービス start` / `/etc/init.d/サービス start` | `systemctl start サービス` |
| `service サービス stop` | `systemctl stop サービス` |
| `chkconfig サービス on` | `systemctl enable サービス` |
| `chkconfig サービス off` | `systemctl disable サービス` |
| `chkconfig --list` | `systemctl list-unit-files` |

:::warn 試験の注意：stop と disable、disable と mask
`stop`（`service … stop`）は**いま**止めるだけで、再起動するとまた動きます。`disable`（`chkconfig … off`）は**次の起動から**動かさないだけで、いま動いているものは止まりません。不要なサービスは両方を行います。`mask` は、手で `start` することさえできなくします。
:::

## パケットを選ぶ：iptables と firewalld {#firewall}

### iptables：チェインと規則

Linux のカーネルには、パケットを調べて通すか捨てるかを決める仕組み（netfilter）があります。それに規則を設定する、昔からのコマンドが **`iptables`** です。

パケットは、どこからどこへ行くかによって、3 つの**チェイン**（規則の列）のどれかで調べられます。

```fig graph iptables の 3 つのチェイン（filter テーブル）。自分あてのパケットは INPUT、自分が出すパケットは OUTPUT、自分を通り抜けて別の機械へ行くパケットは FORWARD で調べられる
{
  col: 200, row: 90,
  nodes: [
    { id: 'in', label: 'ネットワーク', sub: '入ってくる', x: 0, y: 0, mono: false },
    { id: 'r', label: '行き先の判断', sub: 'ルーティング', x: 1, y: 0, mono: false },
    { id: 'I', label: 'INPUT', x: 2, y: 1, kind: 'accent' },
    { id: 'p', label: '自分のプロセス', sub: 'sshd、httpd …', x: 2, y: 2, kind: 'stack', mono: false },
    { id: 'F', label: 'FORWARD', x: 3, y: 0, kind: 'accent' },
    { id: 'O', label: 'OUTPUT', x: 3, y: 2, kind: 'accent' },
    { id: 'out', label: 'ネットワーク', sub: '出ていく', x: 4, y: 0, mono: false },
  ],
  edges: [
    { from: 'in', to: 'r' },
    { from: 'r', to: 'I', label: '自分あて' },
    { from: 'I', to: 'p' },
    { from: 'r', to: 'F', label: 'ほかの機械あて' },
    { from: 'F', to: 'out' },
    { from: 'p', to: 'O' },
    { from: 'O', to: 'out' },
  ],
}
```

チェインの中の規則は**上から順に**調べられ、最初に当てはまった規則の**ターゲット**（`-j` で指定）が実行されます。どの規則にも当てはまらなければ、チェインの**ポリシー**（既定の動作）が使われます。iptables は小さな Linux にないので、Debian 12 で実行した結果を見ます。

```console
# iptables -P INPUT DROP
# iptables -A INPUT -p tcp --dport 22 -s 192.168.1.0/24 -j ACCEPT
# iptables -A INPUT -p tcp --dport 80 -j ACCEPT
# iptables -I INPUT -p tcp --dport 23 -j REJECT
# iptables -L INPUT --line-numbers
Chain INPUT (policy DROP)
num  target     prot opt source               destination         
1    REJECT     tcp  --  anywhere             anywhere             tcp dpt:telnet reject-with icmp-port-unreachable
2    ACCEPT     tcp  --  192.168.1.0/24       anywhere             tcp dpt:ssh
3    ACCEPT     tcp  --  anywhere             anywhere             tcp dpt:http
# iptables -D INPUT 1
# iptables -F INPUT
# iptables -L INPUT
Chain INPUT (policy DROP)
target     prot opt source               destination         
```

`-I` で入れた 23 番の規則は、後から入れたのに**先頭**に入りました。`-F` で規則を全部消しても、ポリシーは `DROP` のままです。この状態では、自分あてのパケットはすべて捨てられます。

| オプション | 意味 |
| --- | --- |
| `-A チェイン 規則` | 規則を**最後**に足す（append） |
| `-I チェイン [番号] 規則` | 規則を**先頭**（または番号の位置）に入れる（insert） |
| `-D チェイン 番号` / `-D チェイン 規則` | 規則を消す（delete） |
| `-L [チェイン]` | 規則を表示する（list）。`-n` で番号のまま、`--line-numbers` で番号付き |
| `-P チェイン ターゲット` | ポリシーを決める（policy） |
| `-F [チェイン]` | 規則を全部消す（flush）。**ポリシーは変わらない** |
| `-p tcp` / `-p udp` / `-p icmp` | プロトコル |
| `--dport 22` / `--sport` | あて先 / 送り元のポート（`-p tcp` などと一緒に使う） |
| `-s 192.168.1.0/24` / `-d` | 送り元 / あて先のアドレス |
| `-i eth0` / `-o` | 入ってきた / 出ていくインターフェース |

| ターゲット | 動作 |
| --- | --- |
| `ACCEPT` | 通す |
| `DROP` | 黙って捨てる。送り主には何も返らない（相手はタイムアウトまで待つ） |
| `REJECT` | 捨てて、送り主に「拒否した」というエラー（ICMP など）を返す |

`iptables` の規則はメモリの中にあるだけで、再起動すると消えます。残すには `iptables-save` でファイルに書き出し、起動時に `iptables-restore` で読み込みます。

:::warn 試験の注意：-A と -I、-F とポリシー
規則は上から順に調べられるので、**順番が意味を持ちます**。`-A` は最後に、`-I` は先頭に入れます。すべてを DROP するポリシーの前に許可の規則を入れずに `-P INPUT DROP` を実行すると、SSH で作業中の自分も締め出されます。`-F` はポリシーを ACCEPT に戻さないことにも注意します。
:::

### firewalld と firewall-cmd：ゾーンとサービス

Red Hat 系の今の標準は **firewalld** です。規則を 1 本ずつ書く代わりに、ネットワークを**ゾーン**（public、home、trusted など、信頼の度合いの名前）に分け、ゾーンごとに「通してよい**サービス**（ssh、http など）とポート」を並べます。操作は `firewall-cmd` で行います。Rocky Linux 9 の既定のゾーンは public で、ssh などが許されています。

```console
# firewall-cmd --get-default-zone
public
# firewall-cmd --zone=public --list-all
public
  target: default
  …
  services: cockpit dhcpv6-client ssh
  ports: 
  …
# firewall-cmd --permanent --zone=public --add-service=http
success
# firewall-cmd --permanent --zone=public --add-port=8080/tcp
success
# firewall-cmd --reload
success
```

`--permanent` を付けた変更は、設定ファイル（`/etc/firewalld/zones/public.xml`）に書かれます。

```console
# cat /etc/firewalld/zones/public.xml
<?xml version="1.0" encoding="utf-8"?>
<zone>
  <short>Public</short>
  …
  <service name="ssh"/>
  <service name="dhcpv6-client"/>
  <service name="cockpit"/>
  <service name="http"/>
  <port port="8080" protocol="tcp"/>
  <forward/>
</zone>
```

firewalld の設定には、**いま効いている設定（ランタイム）**と、**保存された設定（パーマネント）**の 2 つがあります。

| 書き方 | 意味 |
| --- | --- |
| `--get-default-zone` | 既定のゾーンを表示する |
| `--zone=ゾーン` | 操作するゾーン（省くと既定のゾーン） |
| `--list-all` | ゾーンの設定を全部表示する |
| `--list-services` | 許しているサービスを表示する |
| `--add-service=http` / `--remove-service=http` | サービスを許す / 外す |
| `--add-port=8080/tcp` / `--remove-port=…` | ポートを許す / 外す |
| `--permanent` | 保存された設定を変える（すぐには効かない） |
| `--reload` | 保存された設定を読み直して、ランタイムにする |
| `--runtime-to-permanent` | いまのランタイムを保存する |

:::warn 試験の注意：--permanent だけでは効かない
`--permanent` を付けた変更は、`--reload` するまで効きません。逆に、`--permanent` を付けない変更はすぐ効きますが、`--reload` や再起動で消えます。「いますぐ、ずっと」効かせるには、`--permanent` 付きで変えてから `--reload` するか、両方の形で 2 回実行します。サービス名は `/usr/lib/firewalld/services/` の XML ファイルで定義されていて、`http` なら 80/tcp です。
:::

## SSH の鍵で認証する {#ssh-keys}

### 公開鍵と秘密鍵

SSH は、パスワードの代わりに**鍵の組**で本人を確かめられます。**秘密鍵**は自分だけが持ち、**公開鍵**は相手のサーバに置きます。秘密鍵で作った署名は、組になった公開鍵でしか確かめられません。秘密鍵そのものはネットワークに流れないので、パスワードを盗み見られる心配がなく、総当たりで当てられることもありません。

```fig seq 公開鍵認証の流れ。サーバは authorized_keys の公開鍵で、クライアントが秘密鍵を持っていることを確かめる。秘密鍵は送らない
{
  colw: 360,
  actors: [
    { id: 'c', label: 'クライアント（秘密鍵 ~/.ssh/id_ed25519）' },
    { id: 's', label: 'サーバ（~/.ssh/authorized_keys）' },
  ],
  msgs: [
    { from: 'c', to: 's', label: 'この公開鍵で入りたい' },
    { note: 'authorized_keys にその公開鍵があるか調べる', at: 's' },
    { from: 's', to: 'c', label: '毎回変わるデータ（チャレンジ）' },
    { self: 'c', label: '秘密鍵で署名する' },
    { from: 'c', to: 's', label: '署名', style: 'accent' },
    { note: '公開鍵で署名を確かめる → ログイン成功', at: 's', style: 'accent' },
```

鍵の組は **`ssh-keygen`** で作ります。`-t` で鍵の種類を選びます（`ssh-keygen` は小さな Linux にないので、Debian 12 の結果です）。

**パスフレーズ**は、秘密鍵のファイルを暗号化するための合言葉です。秘密鍵のファイルが盗まれても、パスフレーズがなければ使えません。

| `-t` の種類 | 秘密鍵 | 公開鍵 | 特徴 |
| --- | --- | --- | --- |
| `rsa` | `~/.ssh/id_rsa` | `~/.ssh/id_rsa.pub` | 昔からある。`-b 3072` などで鍵の長さを選ぶ |
| `ecdsa` | `~/.ssh/id_ecdsa` | `~/.ssh/id_ecdsa.pub` | 楕円曲線暗号。短い鍵で強い |
| `ed25519` | `~/.ssh/id_ed25519` | `~/.ssh/id_ed25519.pub` | 楕円曲線暗号。速くて短い。今いちばんすすめられる |
| `dsa` | `~/.ssh/id_dsa` | `~/.ssh/id_dsa.pub` | 弱いので使わない。新しい OpenSSH では既定で無効にされ、OpenSSH 10.0 で取り除かれた |

| ssh-keygen のオプション | 意味 |
| --- | --- |
| `-t 種類` | 鍵の種類 |
| `-b ビット数` | 鍵の長さ（rsa など） |
| `-f ファイル` | 秘密鍵のファイル名 |
| `-C コメント` | 公開鍵の最後に付くコメント |
| `-N パスフレーズ` | パスフレーズを引数で渡す |
| `-p` | 秘密鍵のパスフレーズを変える |
| `-l -f ファイル` | 鍵の指紋（fingerprint）を表示する |

### 公開鍵をサーバに置く：authorized_keys と ssh-copy-id

サーバ側では、ログインする**ユーザーのホーム**の **`~/.ssh/authorized_keys`** に、公開鍵を 1 行 1 鍵で書き足します。**`ssh-copy-id`** を使うと、パスワードでログインして、自分の公開鍵を相手の `authorized_keys` に足してくれます。

```console
$ ssh-copy-id -i ~/.ssh/id_ed25519.pub alice@server.example.com
```

権限が緩いと、sshd は鍵を使ってくれません。`~/.ssh` は `700`、秘密鍵と `authorized_keys` は `600` にします。

| ファイル | どこに | 中身 |
| --- | --- | --- |
| `~/.ssh/id_ed25519` など | クライアント | 自分の秘密鍵（`600`） |
| `~/.ssh/id_ed25519.pub` など | クライアント | 自分の公開鍵 |
| `~/.ssh/authorized_keys` | サーバ | ログインを許す公開鍵の一覧 |
| `~/.ssh/known_hosts` | クライアント | 接続したことのある**サーバの**公開鍵（なりすましを見抜くため） |
| `/etc/ssh/ssh_host_*_key` | サーバ | サーバ自身の鍵（ホスト鍵） |
| `/etc/ssh/sshd_config` | サーバ | sshd の設定 |

### ssh-agent と ssh-add：パスフレーズを毎回打たない

秘密鍵にパスフレーズを付けると、使うたびに打つことになります。**`ssh-agent`** は、パスフレーズで開いた秘密鍵をメモリに持っておくプログラムです。**`ssh-add`** で鍵を ssh-agent に預けると、それからの `ssh` は ssh-agent に署名を頼むので、パスフレーズを打たずに済みます。

```console
$ eval $(ssh-agent)
Agent pid 1373
$ ssh-add -l
The agent has no identities.
$ ssh-add ~/.ssh/id_ed25519
Identity added: /home/you/.ssh/id_ed25519 (you@pc)
$ ssh-add -l
256 SHA256:bcEA3rhYlfY2kIhuwBeykGRW461e6GUQeZaYdaVG7jI you@pc (ED25519)
$ ssh-add -D
All identities removed.
```

`ssh-agent` は、自分の居場所を環境変数（`SSH_AUTH_SOCK`、`SSH_AGENT_PID`）に入れるためのシェルのコマンドを出力します。そのため `eval $(ssh-agent)` の形で起動します。

| コマンド | 意味 |
| --- | --- |
| `ssh-add` | 既定の秘密鍵（`~/.ssh/id_rsa` など）を ssh-agent に預ける |
| `ssh-add ファイル` | その秘密鍵を預ける |
| `ssh-add -l` | 預けている鍵の一覧 |
| `ssh-add -d ファイル` / `ssh-add -D` | 1 つ / 全部を取り除く |
| `ssh-agent -k` | ssh-agent を終わらせる |

### sshd_config：root のログインとパスワード認証を止める

サーバの sshd の設定は **`/etc/ssh/sshd_config`** です。セキュリティで必ず見るのは次の 2 つです。

```console
# grep -nE '^#?(PermitRootLogin|PubkeyAuthentication|PasswordAuthentication)' /etc/ssh/sshd_config
33:#PermitRootLogin prohibit-password
38:#PubkeyAuthentication yes
57:#PasswordAuthentication yes
```

`#` で始まる行は、既定の値を示したコメントです。

| 設定 | 値 | 意味 |
| --- | --- | --- |
| `PermitRootLogin` | `no` | root は SSH でログインできない |
| | `prohibit-password` | root は鍵でだけログインできる（今の OpenSSH の既定） |
| | `yes` | root もパスワードでログインできる |
| `PasswordAuthentication` | `no` | パスワード認証を使わない（鍵だけにする） |
| `PubkeyAuthentication` | `yes` | 公開鍵認証を使う（既定） |
| `Port` | `22` | 待ち受けるポート |

書き換えたら、sshd を再起動（`systemctl restart sshd`。Debian ではサービス名が `ssh`）して読み直させます。`PasswordAuthentication no` にする前に、鍵でログインできることを必ず確かめます。

## SSH のポート転送 {#ssh-forward}

SSH の暗号化された接続の中に、ほかの TCP の通信を通すことができます。これを**ポート転送**（トンネル）と呼びます。暗号化されていないプロトコルを守ったり、ファイアウォールの内側にあるサーバへ、SSH のサーバを踏み台にして届いたりするのに使います。

```fig graph ローカル転送（-L）とリモート転送（-R）。-L は手元のポートで待ち受け、SSH サーバの側から目的地へつなぐ。-R は SSH サーバ側のポートで待ち受け、手元の側から目的地へつなぐ
{

  nodes: [
    { id: 'c', label: '手元の PC', sub: 'ssh を実行', x: 0, y: 0, mono: false },

    { id: 'd', label: 'db:5432', sub: 'gw からしか届かない', x: 3, y: 0, kind: 'stack', mono: false },
    { id: 'c2', label: '手元の PC', sub: 'localhost:8080 で Web', x: 0, y: 1.3, kind: 'stack', mono: false },
    { id: 's2', label: 'SSH サーバ gw', sub: '9000 番で待ち受け', x: 1.5, y: 1.3, kind: 'accent', mono: false },
  ],
  edges: [
    { from: 'c', to: 's', label: '-L 15432:db:5432\n手元の 15432 番へ', style: 'accent' },
    { from: 's', to: 'd', label: 'gw がつなぐ' },
    { from: 's2', to: 'c2', label: '-R 9000:localhost:8080\ngw の 9000 番へ', style: 'accent' },
  ],
}
```

```console
$ ssh -L 15432:db.internal:5432 you@gw.example.com
（別の端末で）$ psql -h localhost -p 15432 …   ← gw を通って db.internal:5432 へ届く
$ ssh -R 9000:localhost:8080 you@gw.example.com
（gw の上で）$ curl http://localhost:9000/       ← 手元の PC の 8080 番へ届く
$ ssh -D 1080 you@gw.example.com
（ブラウザの SOCKS プロキシを localhost:1080 にすると、通信が gw から出ていく）
```

Debian 12 のコンテナの中で、自分自身に SSH でつないで 3 つを確かめました。8080 番で `hello-from-8080` を返す Web サーバに、どれも転送で届きました。

```console
$ ssh -f -N -L 9000:localhost:8080 root@localhost
$ curl -s http://localhost:9000/
hello-from-8080
$ ssh -f -N -R 9100:localhost:8080 root@localhost
$ curl -s http://localhost:9100/
hello-from-8080
$ ssh -f -N -D 1080 root@localhost
$ curl -s --socks5-hostname localhost:1080 http://127.0.0.1:8080/
hello-from-8080
```

| オプション | 名前 | 待ち受ける場所 | 書き方 |
| --- | --- | --- | --- |
| `-L` | ローカル転送 | **手元**（ssh を実行した側） | `-L 手元のポート:目的地:目的地のポート` |
| `-R` | リモート転送 | **SSH サーバ**の側 | `-R サーバ側のポート:目的地:目的地のポート` |
| `-D` | ダイナミック転送 | 手元。SOCKS プロキシになる | `-D 手元のポート` |
| `-N` | — | コマンドを実行しない（転送だけ） | |
| `-f` | — | 認証の後、バックグラウンドに回る | |

**-L と -R の「目的地」。** `-L 15432:db.internal:5432` の `db.internal` は、**SSH サーバから見た**名前です。手元の PC から `db.internal` に届かなくてもかまいません。`-R` の `localhost:8080` は、**手元から見た** localhost です。どちらの側でポートが開くか（-L は手元、-R はサーバ側）で区別します。

### 鍵を作る、交換する

```console
$ gpg --gen-key
（名前とメールアドレス、パスフレーズを聞かれる）
$ gpg --list-keys
/home/you/.gnupg/pubring.kbx
------------------------
pub   rsa3072 2026-11-16 [SC]
      00238D49BE41B4C617BBED28FC83A032C61CC423
uid           [ultimate] Alice <alice@example.com>
sub   rsa3072 2026-11-16 [E]
$ gpg --export -a alice@example.com > alice.asc
$ head -1 alice.asc
-----BEGIN PGP PUBLIC KEY BLOCK-----
（相手の側で）
$ gpg --import alice.asc
gpg: key 5BA27ABF0915EAB2: public key "Alice <alice@example.com>" imported
gpg: Total number processed: 1
gpg:               imported: 1
```

`--gen-key` で鍵の組を作ります（細かく選ぶなら `--full-generate-key`）。`--export` は**公開鍵**を書き出し、`-a`（`--armor`）を付けると、メールに貼れる文字の形になります。受け取った人は `--import` で自分の**鍵束**（キーリング）に取り込みます。

鍵は **`~/.gnupg/`** に保存されます。

```console
$ ls -la ~/.gnupg
drwx------ 4 you you 4096 Nov 16 11:18 .
srwx------ 1 you you    0 Nov 16 11:18 S.gpg-agent
…
drwx------ 2 you you 4096 Nov 16 11:18 openpgp-revocs.d
drwx------ 2 you you 4096 Nov 16 11:18 private-keys-v1.d
-rw-r--r-- 1 you you 3874 Nov 16 11:18 pubring.kbx
-rw------- 1 you you 1280 Nov 16 11:18 trustdb.gpg
```

| `~/.gnupg/` の中 | 中身 |
| --- | --- |
| `pubring.kbx` | 公開鍵の鍵束（自分と、取り込んだ相手の公開鍵） |
| `private-keys-v1.d/` | 自分の秘密鍵 |
| `trustdb.gpg` | どの鍵をどれだけ信用するか |
| `openpgp-revocs.d/` | 鍵を無効にするための失効証明書 |
| `S.gpg-agent` | gpg-agent と話すためのソケット |

**gpg-agent** は、秘密鍵の操作とパスフレーズの記憶を受け持つプログラムです。`gpg` が必要なときに自動で起動し、一度打ったパスフレーズをしばらく覚えておきます。ssh-agent と同じ考え方です。

```console
$ ps ax | grep [g]pg-agent
```

### 暗号化、復号、署名、検証

```console
$ gpg -e -r bob@example.com memo.txt
$ ls memo*
memo.txt  memo.txt.gpg
（bob の側で）
$ gpg -d memo.txt.gpg

      "Bob <bob@example.com>"
secret
$ gpg -o memo.txt -d memo.txt.gpg
（alice の側で、署名する）

gpg:                using RSA key B2713349A0B7F13C0C619CB55BA27ABF0915EAB2
gpg: Good signature from "Alice <alice@example.com>" [ultimate]
```

| オプション | 意味 | 使う鍵 |
| --- | --- | --- |
| `--gen-key` | 鍵の組を作る | — |
| `--list-keys`（`-k`） | 鍵束の公開鍵を一覧にする | — |
| `--export [-a] 名前` | 公開鍵を書き出す | — |
| `--import ファイル` | 公開鍵を取り込む | — |
| `-e -r 相手` | 暗号化する（encrypt、recipient）。`ファイル.gpg` ができる | 相手の**公開鍵** |
| `-d ファイル` | 復号する（decrypt）。標準出力へ。`-o` で書き出し先 | 自分の**秘密鍵** |
| `-s ファイル` | 署名する（sign）。中身と署名を 1 つの `ファイル.gpg` に | 自分の**秘密鍵** |
| `--clearsign ファイル` | 中身を読めるまま署名を付ける（`.asc`） | 自分の秘密鍵 |
| `-b ファイル` | 署名だけを別のファイルに（`.sig`） | 自分の秘密鍵 |
| `--verify ファイル` | 署名を検証する | 署名した人の**公開鍵** |
| `-c ファイル` | 公開鍵を使わず、パスフレーズだけで暗号化する（symmetric） | — |
| `-a` | 出力を文字の形にする（armor） | — |

:::warn 試験の注意：署名は暗号化ではない
`gpg -s` で作った `.gpg` は、中身が圧縮されているだけで、暗号化されていません。だれでも `gpg -d` で中身を取り出せます。署名が保証するのは「だれが作ったか」と「途中で書き換えられていないか」です。中身を隠したいなら暗号化（`-e`）、両方なら `-e -s` を組み合わせます。
:::

## クラウドのアカウントを守る {#cloud-account}

クラウド（IaaS）では、物理的なサーバやネットワーク機器は事業者が管理し、その上の仮想マシン（インスタンス）の OS から先は利用者が管理します。この分担を**責任共有モデル**と呼びます。OS の更新、ファイアウォールの設定、アカウントの管理は、利用者の責任です。この章でここまで学んだことは、クラウドの仮想マシンにもそのまま当てはまります。

### 管理コンソールのアカウント

**管理コンソール**は、クラウドの資源（仮想マシン、ストレージ、ネットワーク）を Web の画面で操作する場所です。そこにログインできる人は、すべての仮想マシンを消すことも、データを持ち出すこともできます。仮想マシンの root より強い権限なので、いちばん念入りに守ります。

- **最上位のアカウント**（契約したときに作られる、すべての権限を持つアカウント。AWS ではルートユーザー）は、日々の作業に使わず、多要素認証を付けて大切に保管する
- 作業する人には、**1 人 1 つ**のアカウントを作り、仕事に必要な権限だけを与える（最小権限）。共有しない
- 使わなくなったアカウントや、プログラム用のアクセスキーは、すぐに無効にする
- 操作の記録（監査ログ）を残す

### 多要素認証とワンタイムパスワード

本人であることを確かめる材料（**認証の要素**）には、3 種類あります。

| 要素 | 例 |
| --- | --- |
| 知っているもの（知識） | パスワード、PIN、秘密の質問の答え |
| 持っているもの（所持） | スマートフォンの認証アプリ、ハードウェアトークン、IC カード |
| 本人の体（生体） | 指紋、顔 |

**多要素認証**（MFA、Multi-Factor Authentication）は、**種類の違う**要素を 2 つ以上組み合わせます。パスワードが漏れても、スマートフォンを持っていなければ入れません。**多段階認証**は、認証を何段階かに分けて行うことです。「パスワードの後に秘密の質問」は 2 段階ですが、どちらも「知っているもの」なので、多要素ではありません。

多要素認証でよく使われるのが、**ワンタイムパスワード**（OTP、One-Time Password）です。1 回しか使えない、短い数字です。スマートフォンの認証アプリが出す 6 桁の数字は、**TOTP**（Time-based OTP）という方式で、事前に共有した秘密と**いまの時刻**から計算され、30 秒ほどで変わります。盗み見られても、すぐに使えなくなります。

**多段階と多要素。** 「多要素」は要素の**種類**が 2 つ以上、「多段階」は確認の**回数**が 2 回以上です。パスワード + SMS や認証アプリのコードは、知識 + 所持なので多要素です。パスワード + 秘密の質問は、多段階ですが多要素ではありません。

## クラウドのネットワークとデータの置き場所 {#cloud-network}

### リージョンの選択とデータの所在地

**リージョン**は、事業者のデータセンターがある地域（東京、大阪、北米東部など）です。リージョンごとに、データが物理的に置かれる国が決まります。選ぶときに考えることは次のとおりです。

- **データの所在地**：個人情報などは、国の法令や契約で「国内に保管すること」と決められていることがある。データを置いた国の法律が適用される
- **遅延**：利用者に近いリージョンほど、応答が速い
- **料金と使える機能**：リージョンによって料金が違い、新しい機能がまだないこともある
- **災害への備え**：1 つのリージョンの中にも、離れた場所のデータセンター（アベイラビリティゾーン）がある。大事なシステムは複数に分けて置く

### 揮発性ストレージと永続ストレージ

仮想マシンのディスクには、2 種類あります。

| 種類 | 例 | データの寿命 | 向いている用途 |
| --- | --- | --- | --- |
| **揮発性**（エフェメラル）ストレージ | AWS のインスタンスストア | インスタンスを停止・削除したとき、物理サーバが故障したときに**消える** | 一時ファイル、キャッシュ、作り直せるデータ |
| **永続**ストレージ | ブロックストレージのボリューム（AWS の EBS）、オブジェクトストレージ | インスタンスと独立して残る | OS、データベース、ログ、バックアップ |

揮発性のストレージは、物理サーバに直接つながっていて速いのですが、仮想マシンが別の物理サーバに移ると中身はついてきません。消えて困るデータは、永続ストレージに置き、さらにバックアップを取ります。

### メンテナンスによる再起動

事業者は、物理サーバの部品の交換やソフトウェアの更新のために、**メンテナンス**を行います。そのとき、その上で動いている仮想マシンが、事前の通知の後に**再起動**や停止・起動を求められることがあります（予定された日時を過ぎると、事業者が行うこともあります）。停止・起動で別の物理サーバに移ると、揮発性ストレージの中身は消えます。

利用者が備えておくことは、次のとおりです。

- 必要なサービスは `systemctl enable` で、起動したら自動で動くようにしておく（[1.10.2](#services)）
- 残すデータは永続ストレージに置く
- 事業者からのメンテナンスの通知を受け取れるようにしておき、都合のよい時間に自分で再起動する
- 1 台が止まってもサービスが続くよう、複数の仮想マシンやゾーンに分けておく

:::key まとめ
- SUID / SGID の点検は `find / -perm -4000`（SUID）、`-perm -2000`（SGID）、`-perm /6000`（どちらか）。`-` は全部、`/` はどれか、記号なしはぴったり
- ロックは `passwd -l` / `usermod -L`（ハッシュの先頭に `!`）、解除は `passwd -u` / `usermod -U`。期限は `chage`：`-l` 表示、`-M` 最長、`-m` 最短、`-W` 警告、`-I` 猶予、`-E` アカウントの期限、`-d 0` 次回に変更を強制
- ポートは `ss -tulnp` / `netstat -tulnp`（内から）、`nmap`（外から）。プロセスは `lsof -i :ポート`、`fuser -v 8080/tcp`、`fuser -k` で殺す。`who`・`w` はいまの人、`last` は履歴（wtmp）、`lastb` は失敗（btmp）
- `ulimit`：`-n` ファイル数、`-u` プロセス数、`-f` ファイルの大きさ、`-c` core。`-S` ソフト、`-H` ハード。一般ユーザーはハードを上げられない。`TMOUT` は放置したシェルを自動ログアウト
- `su -` はログインし直した状態。`/etc/sudoers` は `visudo` で。書式は `ユーザー ホスト=(だれとして) コマンド`、`%グループ`、`NOPASSWD:`
- `/usr/sbin/nologin` はユーザーごとのシェル、`/etc/nologin` は root 以外の全員を止めるファイル。xinetd は `/etc/xinetd.d/` で `disable = yes`、inetd は `/etc/inetd.conf` の行を `#` に
- `systemctl stop`（いま）・`disable`（次から）・`mask`（絶対に）。古い形は `service`、`chkconfig`、`/etc/init.d/`
- iptables：INPUT・OUTPUT・FORWARD、`-A` 最後・`-I` 先頭・`-D` 削除・`-L` 表示・`-P` ポリシー・`-F` 全消し（ポリシーは残る）、DROP は黙って捨て、REJECT はエラーを返す。firewalld：`--permanent` + `--reload`
- SSH：`ssh-keygen -t rsa|ecdsa|ed25519`、秘密鍵 `~/.ssh/id_種類`、公開鍵 `.pub`、サーバの `~/.ssh/authorized_keys`（`ssh-copy-id`）、`ssh-agent` と `ssh-add`。転送は `-L`（手元で待つ）、`-R`（サーバ側で待つ）、`-D`（SOCKS）。`PermitRootLogin no`、`PasswordAuthentication no`
- GPG：暗号化は相手の公開鍵（`-e -r`）、復号は自分の秘密鍵（`-d`）、署名は自分の秘密鍵（`-s`）、検証は相手の公開鍵（`--verify`）。鍵は `~/.gnupg/`、パスフレーズは gpg-agent が覚える
- クラウド：管理コンソールの最上位アカウントは MFA を付けて封印。多要素は要素の種類が 2 つ以上。セキュリティグループとルーティングで入口を絞る。リージョンはデータの所在地と遅延で選ぶ。揮発性ストレージは停止で消える。メンテナンスの再起動に備えて enable と永続ストレージ
:::

## 練習問題 {#practice}

1.10.1〜1.10.4 の練習問題です。重要度はどれも 3 なので、15 問ずつあります。

:::q 1.10.1-01 single
SGID ビットが設定されているファイルだけを、システム全体から探すコマンドとして正しいものはどれか。
- [ ] `find / -perm -4000 -type f`
- [x] `find / -perm -2000 -type f`
- [ ] `find / -perm /6000 -type f`
- [ ] `find / -perm -1000 -type f`
- [ ] `find / -perm 2000 -type f`
:::why
SGID は 2000 です。`-perm -2000` は「2000 のビットが立っていれば、ほかのビットは問わない」という意味なので、`2755` のようなファイルが見つかります。

- `-perm -4000` は SUID のファイルです
- `-perm /6000` は SUID か SGID の**どちらか**なので、SUID だけのファイルも出てしまいます
- `-perm -1000` はスティッキービットです
- 記号なしの `-perm 2000` は「権限がちょうど 2000」で、`2755` には合いません

[SUID ファイルを探す](#audit)
:::
:::

:::q 1.10.1-02 multi
次の `ls -l` の表示のうち、SUID ビットが設定されているものを 2 つ選択してください。
- [x] `-rwsr-xr-x`
- [ ] `-rwxr-sr-x`
- [x] `-rwSr--r--`
- [ ] `drwxrwxrwt`
- [ ] `-rwxr-xr-x`
:::why
SUID は、**持ち主**の `x` の場所に `s` で表示されます。持ち主に実行権がないときは大文字の `S` です。だから `-rwsr-xr-x` と `-rwSr--r--` が SUID です。

- `-rwxr-sr-x` は、グループの場所が `s` なので SGID です
- `drwxrwxrwt` は、その他の場所が `t` なのでスティッキービット（`/tmp` など）です
- `-rwxr-xr-x` には特別なビットがありません

[SUID ファイルを探す](#audit)、[図解 Linux 4.9](../../linux/site/ch04.html#special)
:::

退職したユーザー bob のパスワードをロックし、パスワードでログインできないようにする。空欄に入るオプションを入力してください。


`passwd -l`（lock）は、`/etc/shadow` のハッシュの先頭に `!` を付けて、どのパスワードも合わないようにします。外すのは `passwd -u`（unlock）です。同じことは `usermod -L`（大文字）でもできます。[passwd と usermod でロックする](#audit)

:::q 1.10.1-04 single
ユーザー alice に、90 日ごとにパスワードを変えさせたい。実行するコマンドとして正しいものはどれか。
- [ ] `chage -m 90 alice`
- [x] `chage -M 90 alice`
- [ ] `chage -W 90 alice`
- [ ] `chage -I 90 alice`
- [ ] `chage -E 90 alice`
:::why
パスワードの有効期間の**最長**日数は `-M`（maximum）です。

- 小文字の `-m` は、一度変えてから次に変えられるまでの**最短**日数です
- `-W` は、期限切れの何日前から警告するかです
- `-I` は、期限が切れてから使えなくなるまでの猶予の日数です
- `-E` は、**アカウント**の有効期限の日付です

[chage でパスワードの期限を決める](#audit)
:::

:::q 1.10.1-05 multi
ユーザー bob のアカウントをロックし、パスワードで認証できないようにするコマンドを 2 つ選択してください。
- [x] `passwd -l bob`
- [x] `usermod -L bob`
- [ ] `passwd -u bob`
- [ ] `usermod -U bob`
- [ ] `chage -l bob`
:::why
`passwd -l` と `usermod -L` は、どちらも `/etc/shadow` のハッシュの先頭に `!` を付けてロックします。

- `passwd -u` と `usermod -U` は、ロックを**外す**オプションです
- `chage -l` は、パスワードの期限の情報を表示する（list）だけです

[passwd と usermod でロックする](#audit)
:::
:::

:::q 1.10.1-06 single
新しく作ったユーザー carol に、最初のログインのときにパスワードを必ず変えさせたい。実行するコマンドとして正しいものはどれか。
- [x] `chage -d 0 carol`
- [ ] `chage -M 0 carol`
- [ ] `chage -E 0 carol`
- [ ] `usermod -L carol`
:::why
`chage -d 0` は「最後にパスワードを変えた日」を 0（1970 年 1 月 1 日）にします。期限がとうに切れている扱いになるので、次のログインで変更を求められます。`chage -l` で見ると「password must be changed」と出ます。

- `-M 0` は最長日数を 0 にするもので、「最初の 1 回だけ」の目的には合いません
- `-E 0` はアカウントの有効期限を 1970 年 1 月 1 日にするので、アカウント自体が使えなくなります
- `usermod -L` はロックで、ログインできなくなります

[chage でパスワードの期限を決める](#audit)
:::

:::q 1.10.1-07 single
この機械で待ち受けている TCP のポートを、ポート番号のまま、それを使っているプロセスとともに一覧にしたい。最も適切なコマンドはどれか。
- [x] `ss -tlnp`
- [ ] `ss -ulnp`
- [ ] `ss -tan`
- [ ] `ss -xlp`
:::why
`-t` は TCP、`-l` は待ち受け中だけ、`-n` は番号のまま、`-p` はプロセスです。`netstat -tlnp` も同じ意味です。

- `-u` は UDP です
- `-tan` は TCP の全部（接続中も含む）で、プロセスは出ません
- `-x` は UNIX ドメインソケットです

他人のプロセスの名前は root でないと見えないので、ふつうは `sudo ss -tlnp` とします。[ss と netstat](#ports)
:::

:::q 1.10.1-08 single
管理しているサーバ web01 が、外から見てどのポートを開いているかを、別の機械からネットワーク越しに調べたい。使うコマンドとして最も適切なものはどれか。
- [ ] `lsof`
- [ ] `fuser`
- [ ] `ss`
- [x] `nmap`
:::why
`nmap` はポートスキャナで、相手の機械のポートに実際につないで、open / closed / filtered を調べます。ファイアウォールで閉じたポートは外からは開いて見えないので、外からの点検には `nmap` を使います。

`lsof`、`fuser`、`ss` は、どれも**その機械の中**で、カーネルの情報を見るコマンドです。別の機械のことは調べられません。[nmap](#ports)
:::

:::q 1.10.1-09 multi
TCP の 8080 番ポートを使っているプロセスを調べられるコマンドを 2 つ選択してください。
- [x] `lsof -i :8080`
- [x] `fuser -v 8080/tcp`
- [ ] `lsof -p 8080`
- [ ] `nmap -p 8080 localhost`
- [ ] `ulimit -n 8080`
:::why
`lsof -i :8080` は、8080 番を使っているネットワークのファイルと、そのプロセスを出します。`fuser -v 8080/tcp`（`fuser -v -n tcp 8080` と同じ）は、その番号を使っているプロセスの PID とユーザーを出します。

- `lsof -p 8080` は、**PID が 8080** のプロセスが開いているファイルです
- `nmap` は、ポートが開いているかどうかは分かりますが、どのプロセスかは分かりません
- `ulimit -n 8080` は、開けるファイルの数の上限を 8080 にする設定です

[lsof と fuser](#ports)

:::q 1.10.1-10 single
ログインに**失敗した**記録を表示するコマンドとして正しいものはどれか。
- [ ] `who`
- [ ] `w`
- [ ] `last`
- [x] `lastb`

`/etc/nologin` は一般ユーザーのログインを止めるもので、再起動は止められません。セキュリティグループを消すと、通信の規則がなくなるだけで、メンテナンスとは関係ありません。[メンテナンスによる再起動](#cloud-network)
:::

:::q 1.10.4-14 single
IaaS の仮想マシンを使うとき、責任共有モデルで**利用者**の責任になるものはどれか。
- [ ] データセンターの入退室の管理

:::q 1.10.4-15 single
「パスワードを入力した後に、秘密の質問の答えを入力する」認証の説明として正しいものはどれか。
- [x] 多段階認証だが、多要素認証ではない
- [ ] 多要素認証であり、多段階認証ではない
- [ ] 多段階認証であり、多要素認証でもある
- [ ] ワンタイムパスワードによる認証である
:::why
確認を 2 回に分けているので多段階認証です。しかし、パスワードも秘密の質問も「知っているもの」で、要素の種類は 1 つなので、多要素認証ではありません。答えは毎回同じなので、ワンタイムパスワードでもありません。[多段階と多要素](#cloud-account)
:::
