11.1オープンソースとは何か：4 つの自由と 10 の条件

ソフトウェアは著作物です。作った時点で、作った人に著作権が自動的に生まれます（届け出はいりません）。著作権者の許しがなければ、他人はコピーも改変も配布もできません。

その許しの条件を書いた文書がライセンスです。オープンソースは著作権を捨てることではありません。著作権者が、ライセンスで「この条件を守れば、使ってよい・変えてよい・配ってよい」と認めている状態です。

オープンソースを定める考え方は 2 つあります。

フリーソフトウェア（FSF）オープンソース（OSI）
中心利用者の自由（free は「無料」ではなく「自由」）開発の方法としての良さ、10 の条件（オープンソースの定義）
中身4 つの自由再配布の自由、ソースコード、派生物の許可……
ライセンスの認定FSF が自由かどうかを判定OSI が条件を満たすライセンスを承認

フリーソフトウェアの 4 つの自由は、0 から数えます。

番号自由
0目的を問わず、プログラムを実行する自由
1プログラムがどう動くかを研究し、改変する自由（そのためにソースコードが必要）
2コピーを再配布する自由
3改変したものを配布する自由

オープンソースの定義（OSD）の 10 の条件の要点です。

条件要点
1自由な再配布再配布を制限しない。再配布にロイヤリティ（使用料）を求めない
2ソースコードソースコードを含める。または無料（ほぼ無料）で入手できるようにする
3派生物改変と派生物を許し、元と同じ条件で配布することを許す
4作者のソースコードの完全性元のソースとパッチを分けて配るよう求めてよい。派生物に別の名前や版番号を求めてよい
5個人やグループの差別の禁止特定の人や集団を除外しない
6利用分野の差別の禁止「商用に使うな」「研究に使うな」などと分野を制限しない
7ライセンスの分配再配布を受けた全員に、追加の契約なしで同じ権利が及ぶ
8特定製品に限定しない特定のディストリビューションの一部であるときだけ、という条件を付けない
9他のソフトウェアを制限しない一緒に配る他のソフトウェアにまで条件を付けない
10技術的に中立特定の技術や操作（「同意」ボタンなど）を前提にしない
注意試験の注意
  • 「フリー」は価格ではなく自由です。オープンソースのソフトウェアを有料で販売しても、定義に反しません（GPL も販売を禁じていません）
  • 「商用利用を禁止する」ライセンスは、オープンソースの定義（条件 6）に合いません
  • オープンソースでも著作権は放棄されていません。放棄に近いのは、後で説明するパブリックドメインです

無保証も大事な特徴です。ほとんどのライセンスは「現状のまま（AS IS）提供し、何も保証しない。損害が起きても作者は責任を負わない」と書いています。保証やサポートがほしい利用者は、それを売る企業（ディストリビューションのベンダーなど）と契約します。

一方で、ソースが公開されているので、開発が続けられます。作者がやめても、別の人が引き継げます。方針が合わなければ、ソースを複製して別のプロジェクトとして続けること（フォーク）もできます。OpenOffice.org から LibreOffice が、MySQL から MariaDB が分かれた例が有名です。

小さな Linux に、MIT ライセンスのプロジェクトを用意しました。ライセンスの本文を読んでみます。

この章の準備最初の実行のときに、自動で流れるコマンド

許可していること（使う、コピー、改変、配布、販売……）と、ただ 1 つの条件⌘↵

MIT ライセンスが求めるのは「著作権の表示とこの許諾の文を、すべてのコピーに含めること」だけです。そして「AS IS」で、保証はありません。

11.2ライセンスは何を求めるか：コピーレフトの強さ

コピーレフトは、「改変したもの（派生物）を配布するときも、同じライセンスで配布し、ソースコードを渡す」ことを求める仕組みです。自由が、配布の先でも失われないようにします。コピーレフトをどこまで及ぼすかで、ライセンスが分かれます。

GPL：派生物の全体を GPL で出す

GPL（GNU General Public License）は、FSF が作った代表的なコピーレフトのライセンスです。GPL のプログラムを改変したり、GPL のコードを組み込んだりしたプログラムを配布するときは、その全体を GPL で配布し、ソースコードを受け取った人が入手できるようにします。

条件がかかるのは配布するときです。改変して自分や社内だけで使い、外に配らないなら、ソースを公開する義務はありません。また、GPL のソフトウェアを有料で売ることも許されています。

GPL v2（1991）GPL v3（2007）
使われている例Linux カーネル（v2 のみ）GNU のツールの多く
特許はっきりした条項がない貢献者が特許の利用を許す条項がある
機器への組み込み規定なし消費者向けの機器では、改変したソフトを入れ直すための情報も渡す（いわゆる「Tivo 化」の防止）
Apache 2.0 との組み合わせできない（両立しない）Apache 2.0 のコードを取り込める
メモ「v2 のみ」と「v2 以降」

GPL では、作者が「バージョン 2、または（あなたの選択で）それ以降のバージョン」と書くことがあります。Linux カーネルはこの一文がなく、GPL v2 のみです。そのため v3 には移っていません。

AGPL：ネットワーク越しに使わせるときもソースを渡す

GPL は「配布」をきっかけにします。サーバーで動かして Web サービスとして使わせるだけなら、プログラムを配布していないので、改変したソースを出さなくて済みます。AGPL（GNU Affero GPL v3）はここをふさぎます。

LGPL：ライブラリを使うだけのプログラムには及ばない

LGPL（GNU Lesser GPL）は、ライブラリ向けの弱いコピーレフトです。LGPL のライブラリをリンクして使うだけのプログラムは、GPL 以外のライセンス（ソースを公開しない商用のライセンスも）で配布できます。ライブラリそのものを改変したら、その改変は LGPL で出します。また、利用者がライブラリを差し替えられるようにしておく必要があります。代表は GNU C ライブラリ（glibc）です。

MPL：ファイル単位のコピーレフト

MPL（Mozilla Public License 2.0）は、コピーレフトをファイル単位にかけます。MPL のファイルを改変して配布したら、そのファイルは MPL のままソースを出します。同じプログラムの中でも、自分で書いた別のファイルは別のライセンスにできます。Firefox が使っています。

ファイルの先頭の SPDX の行で、ファイルごとのライセンスを見る⌘↵
grep -n "SPDX-License-Identifier" src/greet.sh vendor/colors.sh vendor/net.sh

SPDX-License-Identifier は、ファイルのライセンスを短い名前で書く決まった書き方です。この例では、vendor/colors.sh を改変して配布するなら、そのファイルだけは MPL のままソースを出します。

ライセンス種類改変して配布するとき求められること
GPL強いコピーレフト派生物の全体を GPL で、ソースとともに
AGPL強いコピーレフトGPL と同じ。さらに、ネットワーク越しに使わせるときも改変後のソースを入手できるように
LGPL弱いコピーレフトライブラリの改変は LGPL で。リンクするだけのプログラムは自由
MPL 2.0弱いコピーレフトMPL のファイルの改変は MPL で。ほかのファイルは自由

11.3寛容なライセンス、パブリックドメイン、デュアルライセンス

コピーレフトのないライセンスを、寛容な（パーミッシブ）ライセンスと呼びます。改変したものを、ソースを公開しない商用のソフトウェアに組み込んで配布できます。求めるのは、主に著作権とライセンスの表示を残すことです。

ライセンス求めること
MIT著作権の表示と許諾の文を、すべてのコピー（またはその主要な部分）に含める
BSD（3 条項）ソースでも配布物でも著作権表示などを残す。作者の名前を、許しなく宣伝に使わない（2 条項版はこの宣伝の条項がない）
Apache 2.0ライセンスの写しを渡す。変更したファイルに「変更した」と目立つように書く。著作権などの表示と NOTICE ファイルを残す。貢献者が特許の利用を許す。特許侵害で訴えた者は、その特許の許諾を失う。商標の使用は許さない
Apache 2.0 のコードを含むときは、NOTICE ファイルの中身も配布物に残す⌘↵
cat NOTICE
注意試験の注意：Apache 2.0 と MIT の違いは「特許」

MIT と BSD には特許についての条項がありません。Apache 2.0 は、貢献者からの特許の許諾と、特許で訴えたら許諾が終わる条項を持ちます。「特許の条項がある寛容なライセンス」と聞かれたら Apache 2.0 です。

パブリックドメインは、著作権による制限がない状態です。著作権が切れたものや、作者が権利を放棄したものです。だれでも条件なしに使えます。データベースの SQLite がパブリックドメインです。日本のように作者が権利を完全には放棄できない国もあるので、放棄の意思を示しつつ、できない部分は自由に許諾する CC0 などの宣言が使われます。

デュアルライセンスは、著作権者が同じソフトウェアを2 つ以上のライセンスで提供することです。著作権者だから、条件を複数用意できます。

  • MySQL：GPL と商用ライセンス。ソースを出したくない会社は商用ライセンスを買う
  • Qt：GPL / LGPL と商用ライセンス
  • Rust の多くのライブラリ：MIT または Apache 2.0 の、利用者が選べる形
コツ組み合わせるときは「ゆるい側から強い側へ」

MIT のコードは GPL のプログラムに取り込めます（全体を GPL で出せばよい）。逆に、GPL のコードを取り込んだ全体を MIT で出すことはできません。コピーレフトは、取り込んだ先の全体に条件を及ぼすからです。

11.4コミュニティにどう関わるか

オープンソースは、世界中の人がインターネットで集まって作ります。やりとりの場所は主に 3 つです。

場所使い方
メーリングリスト登録した全員にメールが配られる。議論、告知、パッチの投稿。Linux カーネルは今もパッチをメールで送り、メーリングリストで審査する
掲示板（フォーラム）利用者どうしの質問と回答。過去のやりとりを検索できる
開発サイト（GitHub、GitLab など）ソースの置き場所（Git のリポジトリ）、課題の管理（Issue）、変更の取り込みの依頼（プルリクエスト、GitLab ではマージリクエスト）、フォーク

開発体制は、プロジェクトごとに違います。

  • メンテナ：担当の範囲で、パッチを取り込むかどうかを決める人。Linux カーネルでは、各部分のメンテナが集めた変更をリーナス・トーバルズが最終的に取り込む
  • コミッタ：リポジトリに直接書き込む権利を持つ人。貢献を重ねて認められた人に与えられる
  • コントリビュータ：パッチ、文書、翻訳、報告などで貢献する人。だれでもなれる
  • 財団：Linux Foundation、Apache Software Foundation などが、資金や商標、法的な面を支える。企業の開発者も多く参加している

関わり方は、コードを書くことだけではありません。使う、ブログや勉強会で紹介する、不具合を報告する、文書を直す、翻訳する、寄付する。どれも貢献です。

小さな Linux の greet で、報告に書く材料を集めてみます。名前に空白があると、姓が消えてしまいます。

バグ報告の材料：版、環境、再現手順、期待と実際⌘↵
sh src/greet.sh --versionuname -srsh src/greet.sh "Taro Yamada"

良いバグ報告には、次のことを書きます。

書くことこの例では
ソフトウェアの版greet 1.2.0
環境（OS、カーネル）uname -sr の出力
再現手順sh src/greet.sh "Taro Yamada" を実行する
期待した結果と実際の結果期待 Hello, Taro Yamada!、実際 Hello, Taro!
エラーメッセージやログそのまま貼る（言い換えない）
注意試験の注意：してはいけない報告
  • 「動きません」とだけ書く（版も手順もない）
  • 同じ不具合を、検索せずに別の報告として何度も立てる
  • 1 つの報告に、関係のない不具合をいくつも混ぜる
  • セキュリティの脆弱性を、公開の Issue や掲示板にいきなり書く。プロジェクトが決めた非公開の窓口（セキュリティポリシー）に知らせる
深掘り「伽藍とバザール」

エリック・レイモンドは 1997 年の論文「伽藍とバザール」で、少人数が閉じて作る「伽藍」方式と、Linux のように早く頻繁に公開して多くの人の目で直す「バザール」方式を比べました。「目玉の数さえ十分あれば、どんなバグも深刻ではない」という言葉が知られています。この考えが、1998 年の「オープンソース」という呼び名と OSI の設立につながりました。

要点まとめ
  • ソフトウェアは著作物。オープンソースは著作権を捨てるのではなく、ライセンスで利用・改変・再配布を許す
  • FSF の 4 つの自由：実行（0）、研究と改変（1）、再配布（2）、改変版の配布（3）。free は「自由」
  • OSI のオープンソースの定義は 10 の条件。再配布の自由、ソースコード、派生物の許可、人や分野で差別しない（商用の禁止は不可）
  • ほとんどのライセンスは無保証（AS IS）。有料での販売は許される
  • 強いコピーレフト：GPL（配布するとき全体を GPL で）、AGPL（ネットワーク越しの利用でも改変後のソースを）。弱い：LGPL（リンクするだけなら自由）、MPL（ファイル単位）
  • 寛容：MIT、BSD（表示を残す）、Apache 2.0（表示 + NOTICE + 特許の条項）。パブリックドメインは条件なし
  • デュアルライセンス：著作権者が複数のライセンスで提供（MySQL の GPL と商用）
  • コミュニティ：メーリングリスト、掲示板、開発サイト（GitHub の Issue とプルリクエスト）。バグ報告は版・環境・再現手順・期待と実際。脆弱性は非公開の窓口へ

11.5練習問題

1.11.1-01

1.11.1-02

1.11.1-03複数選択

あるプログラムを改変して、実行形式だけを配布したい。改変した部分のソースコードを公開する義務がないライセンスを 2 つ選択してください。

1.11.1-04

AGPL v3 の説明として正しいものはどれか。

1.11.1-05

LGPL のライブラリを使ったアプリケーションの扱いとして正しいものはどれか。

1.11.1-06

Mozilla Public License 2.0（MPL 2.0）の説明として正しいものはどれか。

1.11.1-07

寛容なライセンスのうち、貢献者から利用者への特許の許諾と、特許侵害で訴えた者はその許諾を失うという条項を持つものはどれか。

1.11.1-08入力

GPL v3 をもとに、改変したプログラムをネットワーク越しに利用させる場合にも、その利用者に改変後のソースコードを入手する機会を与えることを求めるライセンスがある。その略称を英字 4 文字で入力してください。

1.11.1-09複数選択

オープンソースのソフトウェアと著作権・保証について正しいものを 2 つ選択してください。

1.11.1-10

1.11.2-01

オープンソースのプロジェクトへのバグ報告として適切でないものはどれか。

1.11.2-02

Linux カーネルの開発で、パッチの投稿と審査の議論に主に使われているものはどれか。

1.11.2-03入力

GitHub で、自分のリポジトリ（フォーク）やブランチで加えた変更を、元のプロジェクトに取り込んでもらうよう依頼する機能の名前を、カタカナで入力してください。

1.11.2-04複数選択

オープンソースの開発体制の説明として正しいものを 2 つ選択してください。

1.11.2-05複数選択

プログラムを書かずにできる、オープンソースのプロジェクトへの貢献として適切なものを 2 つ選択してください。
