13.1可用性：システムは、なぜ止まるのか

可用性（アベイラビリティ）は、「使いたいときに使える」度合いです。可用性が高いシステムを高可用（HA、High Availability）と呼びます。高可用にするには、まず「止まる理由」を分けて考えます。

分け方種類例
予定していたか計画停止部品の交換、OS やミドルウェアの更新、法定の電源点検。日時を決めて知らせてから止める
計画外停止障害による停止と、障害や脆弱性に対応するための緊急保守
何が壊れたか物理障害ディスク、電源、メモリ、NIC、ケーブル、空調、停電、災害
論理障害ソフトウェアの不具合、設定の間違い、操作の間違い（誤って消した）、データの破損

計画停止も、利用者から見れば「使えない時間」です。可用性を高めるには、障害を減らすだけでなく、計画停止を短くする（1 台ずつ順に更新する、など）ことも必要です。

物理障害と論理障害では、効く対策が違います。

  • 物理障害には冗長化が効きます。同じ役目の機械を 2 つ以上用意して、1 つが壊れても残りで続けます
  • 論理障害には冗長化が効きません。間違った設定や、誤った削除は、予備の機械にもそのまま伝わるからです。効くのは、バックアップからの復元、変更の前の検証、手順の自動化です
注意試験の注意：冗長化とバックアップは別のもの

RAID 1 やデータベースのレプリケーション（複製）は、物理障害への備えです。「誤って表を消した」は、ミラーの相手にもレプリカにも、すぐに同じように反映されます。論理障害から戻すには、過去の時点のデータ、つまりバックアップが必要です。「冗長化してあるからバックアップは要らない」という選択肢は、誤りです。

SPoF：そこが壊れると全部が止まる場所

SPoF（Single Point of Failure、単一障害点）は、そこ 1 か所が壊れただけで、システム全体が止まる部品です。Web サーバーを 10 台並べても、手前のロードバランサーが 1 台なら、そのロードバランサーが SPoF です。

冗長化は、SPoF を 1 つずつなくしていく作業です。サーバーだけでなく、電源、ネットワークの機器、回線、ストレージ、DNS、データセンターそのものも、SPoF になります。構成図を見て「1 つしかないもの」を探すのが、試験での見つけ方です。

回復性：壊れたあと、元に戻る力

回復性（レジリエンス）は、障害が起きたあとに、サービスを続ける、または早く元に戻る力です。壊れないこと（信頼性）だけを追うのではなく、「壊れる前提で、すぐ戻る」ように作ります。

  • 自動で切り替わる（フェイルオーバー。後の節）
  • 壊れた部品を、自動で作り直す（クラウドのオートスケーラー。後の節）
  • 一部が壊れても、残りの機能は動く（縮退運転）

13.2MTBF・MTTR・稼働率を計算する

可用性を数字で表すために、3 つの指標を使います。

指標英語意味良い方向
MTBFMean Time Between Failures（平均故障間隔）故障から次の故障まで、動いていた時間の平均。稼働時間の合計 ÷ 故障の回数大きいほど良い（壊れにくい = 信頼性）
MTTRMean Time To Repair（平均修復時間）1 回の故障で、直すのにかかった時間の平均。修理時間の合計 ÷ 故障の回数小さいほど良い（直しやすい = 保守性）
稼働率Availability全体の時間のうち、動いていた時間の割合大きいほど良い

稼働率の式は 1 つです。

稼働率 = MTBF ÷ (MTBF + MTTR)

分母の「MTBF + MTTR」は「動いていた時間 + 止まっていた時間」、つまり全体の時間です。小さな Linux の awk で計算してみます。

稼働率 = MTBF ÷ (MTBF + MTTR)⌘↵
# MTBF 490 時間、MTTR 10 時間awk 'BEGIN { printf "%.4f\n", 490 / (490 + 10) }'# MTBF 1990 時間、MTTR 10 時間awk 'BEGIN { printf "%.4f\n", 1990 / (1990 + 10) }'# MTBF 2000 時間、MTTR 2 時間awk 'BEGIN { printf "%.4f\n", 2000 / (2000 + 2) }'

稼働率を上げる方法は 2 つあります。MTBF を伸ばす（壊れにくい部品を使う）か、MTTR を縮める（早く直す。予備機への自動の切り替えは、MTTR を数秒〜数分に縮める方法です）。

注意試験の注意：MTBF と MTTR を取り違えない

MTBF は「Between Failures」で、動いていた時間です。MTTR は「To Repair」で、止まっていた時間です。分母を MTBF だけにする（MTTR ÷ MTBF）、分子を MTTR にする、といった選択肢が並びます。「動いていた時間 ÷ 全体の時間」と覚えてください。

稼働率と、1 年に止まってよい時間

稼働率は「99.9%」のように 9 を並べて言います（スリーナイン）。1 年（365 日 = 8,760 時間 = 525,600 分）に止まってよい時間に直すと、感覚がつかめます。

稼働率ごとの、1 年に止まる時間（分）⌘↵
echo "0.99 0.999 0.9999 0.99999" | tr ' ' '\n' | awk '{ printf "%s  %8.2f 分\n", $1, 365 * 24 * 60 * (1 - $1) }'
稼働率呼び方1 年に止まる時間30 日に止まる時間
99%ツーナイン約 87.6 時間（3.65 日）7.2 時間
99.9%スリーナイン約 8.76 時間43.2 分
99.99%フォーナイン約 52.6 分約 4.3 分
99.999%ファイブナイン約 5.3 分約 26 秒

9 が 1 つ増えると、止まってよい時間は 10 分の 1 になります。

直列と並列：組み合わせたときの稼働率

システムは、いくつもの部品でできています。部品の稼働率から全体の稼働率を出す式は、つなぎ方で決まります。

つなぎ方意味式（稼働率 a と b）
直列全部が動いていないと使えない（Web → AP → DB の流れ）a × b
並列どれか 1 つが動いていれば使える（冗長化）1 − (1 − a) × (1 − b)

並列の式は「両方が同時に止まっている割合」を 1 から引いています。(1 − a) は A が止まっている割合です。

直列と並列⌘↵
# 0.99 の機械 2 台。直列と並列awk 'BEGIN { a = 0.99; printf "直列 %.4f  並列 %.4f\n", a * a, 1 - (1 - a) * (1 - a) }'# 0.9 の機械。並列で 2 台、3 台awk 'BEGIN { a = 0.9; printf "2 台 %.3f  3 台 %.3f\n", 1 - (1 - a) ^ 2, 1 - (1 - a) ^ 3 }'# Web・AP・DB が 1 台ずつ（直列）。どれも 0.99awk 'BEGIN { printf "%.6f\n", 0.99 * 0.99 * 0.99 }'

直列は、つなぐほど稼働率が下がります（1 より小さい数を掛けるので）。並列は、並べるほど上がります。直列と並列が混ざった構成は、並列の部分を先に 1 つの数にまとめてから、直列の掛け算をします。

コツ計算問題の手順
  1. 構成図で、並列（冗長）になっている部分を囲む
  2. 囲んだ部分ごとに 1 − (1 − a)(1 − b) を計算する。0.9 が 2 台なら 0.99、0.99 が 2 台なら 0.9999 と、「止まる割合の掛け算」で暗算できる
  3. 残りを全部掛ける

13.3SLA・RPO・RTO：どこまで守るかを、数字で決める

可用性にはお金がかかります。どこまで守るかは、先に数字で決めます。

用語英語意味
SLAService Level Agreement（サービス品質保証）事業者と利用者の間の、サービスの水準についての合意。「月間の稼働率 99.9% 以上」などと決め、守れなかったときの扱い（料金の返還など）も書く
RPORecovery Point Objective（目標復旧時点）障害のとき、どの時点のデータまで戻すかの目標。失ってよいデータの量を時間で表す
RTORecovery Time Objective（目標復旧時間）障害から、どれだけの時間でサービスを再開するかの目標

図の例では、バックアップが 2 時、障害が 17 時なので、15 時間ぶんのデータを失いました。再開は 19 時なので、止まっていたのは 2 時間です。「RPO は 1 時間」と決めたのなら、1 日 1 回のバックアップでは足りません。1 時間ごとのバックアップか、別の機械への連続した複製（レプリケーション）が必要です。

目標短くする方法
RPO を短くバックアップの間隔を短くする、差分・増分バックアップ、データベースのレプリケーション（同期なら RPO はほぼ 0）
RTO を短く予備機を起動したまま待たせる（ホットスタンバイ）、自動のフェイルオーバー、復元の手順の自動化と訓練
注意試験の注意：RPO と RTO

RPO の P は Point（時点）で、障害から過去を見ます。「データをどこまで失ってよいか」です。RTO の T は Time（時間）で、障害から未来を見ます。「いつまでに再開するか」です。「RPO = 復旧にかかる時間」は誤りです。RPO も RTO も、短くするほど費用が上がります。

SLA の稼働率は、止まった時間から計算します。30 日（43,200 分）の月に 43.2 分を超えて止まると、99.9% を下回ります。SLA に計画停止を含めるかどうかは、合意の中で決めます。

13.4クラスタと負荷分散、Pacemaker と Corosync

何台かのサーバーを、1 つのシステムとして動かす仕組みをクラスタと呼びます。クラスタの 1 台 1 台をノードと呼びます。目的で 2 種類に分かれます。

種類目的動き方
HA クラスタ（フェイルオーバークラスタ）止めない（可用性）動いているノード（アクティブ）が壊れたら、待っているノード（スタンバイ）がサービスを引き継ぐ
負荷分散クラスタさばく量を増やす（性能）。結果として可用性も上がるロードバランサーが、同じ役目のノードに要求を振り分ける。壊れたノードは振り分け先から外す

HA クラスタの用語です。

  • アクティブ / スタンバイ：1 台が動き、もう 1 台は待つ。待ち方には、起動して同期まで済ませて待つホットスタンバイ、電源を切って置いておくコールドスタンバイなどがある
  • アクティブ / アクティブ：両方が同時に動く。片方が壊れたら、残りが全部を受け持つ
  • フェイルオーバー：障害を検知して、サービスを予備のノードに自動で切り替えること。元のノードが直ったあとに戻すのがフェイルバック
  • 仮想 IP アドレス（VIP）：クライアントが接続する、サービス用のアドレス。動いているノードに付け替えるので、クライアントは切り替わりを意識しない
  • ハートビート：ノードどうしが定期的に送り合う、「生きている」という合図。途切れたら相手の障害と判断する

Pacemaker と Corosync の役割

Linux の HA クラスタは、2 つのソフトウェアの組み合わせで作るのが標準です。

ソフトウェア層役目
Corosyncクラスタの通信（メッセージング）層ノードどうしの通信、メンバーシップ（だれが生きているか）の管理、クォーラム（定足数）の計算
Pacemakerクラスタのリソース管理（CRM）リソース（仮想 IP、ファイルシステム、サービス）の起動・停止・監視。障害のときに、どのノードで動かすかを決めて切り替える

Corosync が「node1 から返事がない」と知らせ、Pacemaker が「では、node2 で仮想 IP と Web サーバーを起動する」と決めて実行します。Pacemaker だけ、Corosync だけでは HA クラスタになりません。

Pacemaker が動かす対象をリソースと呼びます。リソースの起動・停止・監視の方法は、リソースエージェント（RA）というスクリプトに書いてあります。ocf:heartbeat:IPaddr2（仮想 IP を付ける）、ocf:heartbeat:apache、ocf:heartbeat:Filesystem、ocf:heartbeat:pgsql などが用意されています。名前は「規格:提供元:種類」の形です。

スプリットブレイン、STONITH、クォーラム

ノードの間の通信だけが切れると、どちらのノードも「相手が死んだ」と判断します。両方がアクティブになって、同じ共有ディスクに書き込むと、データが壊れます。これがスプリットブレインです。防ぐ仕組みが 2 つあります。

  • STONITH（Shoot The Other Node In The Head）：応答しないノードを、電源の制御装置などを使って強制的に止めてから、リソースを引き継ぐ。一般的な呼び方はフェンシング
  • クォーラム（定足数）：ノードの票の過半数を持つ側だけが、リソースを動かせる。過半数に届かない側は、リソースを止める。3 台なら 2 票、5 台なら 3 票が必要。2 台では片方が止まると過半数（2 票）に届かないので、corosync.conf に two_node: 1 を書いて、1 票で成立させる

設定ファイルと管理コマンド

Corosync の設定は /etc/corosync/corosync.conf です。Docker の debian:12 に入れたときの形（コメントを除いた要点）です。

totem {    version: 2    cluster_name: debian    crypto_cipher: none    crypto_hash: none} logging {    to_logfile: yes    logfile: /var/log/corosync/corosync.log    to_syslog: yes} quorum {    provider: corosync_votequorum} nodelist {    node {        name: node1        nodeid: 1        ring0_addr: 127.0.0.1    }}
セクション書くこと
totem { }クラスタの通信の設定。cluster_name（クラスタの名前）、暗号化
logging { }ログの出し先
quorum { }クォーラムの方式。provider: corosync_votequorum、2 台のときは two_node: 1
nodelist { }参加するノード。node { } ごとに name、nodeid、ring0_addr（通信に使うアドレス）

Pacemaker の設定（リソース、制約、クラスタの性質）は、CIB（Cluster Information Base）という XML にまとめられ、全ノードで同じ内容に保たれます。CIB のファイルを手で書き換えてはいけません。次のコマンドで変えます。

コマンド何をするか
crm_monクラスタの状態（ノード、リソース）を表示する。既定では画面を更新し続ける。-1（--one-shot）は 1 回だけ表示して終わる。-r は止まっているリソースも、-f は失敗の回数も表示する
pcsPacemaker と Corosync をまとめて設定する道具（Red Hat 系の標準）。pcs status、pcs cluster setup、pcs cluster start --all、pcs resource create、pcs constraint、pcs property set、pcs node standby
crmcrmsh。pcs と同じ役目の、もう 1 つの道具（SUSE 系の標準）。crm status、crm configure show
crm_resourceリソースの操作。--move（別のノードへ移す）、--cleanup（失敗の記録を消す）
crm_verify設定の検査。crm_verify -L -V は、動いているクラスタの設定を詳しく検査する
cibadminCIB を直接読む・変える。cibadmin -Q は CIB の XML を表示する
corosync-cfgtool -sCorosync の通信（リンク）の状態を表示する
corosync-quorumtool -sクォーラムの状態（票の数、成立しているか）を表示する

Red Hat 系では、pcs、pacemaker、corosync は「High Availability」のリポジトリにあります（rockylinux:9 では highavailability という名前で、既定では無効です）。systemd のユニットは corosync.service、pacemaker.service、pcsd.service です。

ターミナル

読み方です。

  • Stack: corosync：通信の層に Corosync を使っている
  • Current DC: node1：DC（Designated Controller）は、クラスタ全体の判断をまとめる役のノード。Pacemaker が自動で 1 台を選ぶ
  • partition with quorum：このノードのいる側は、クォーラム（過半数）を持っている。partition WITHOUT quorum なら、持っていない

pcs resource create の書式は「リソースの名前、エージェント、パラメータ（名前=値）、op に続けて操作の設定」です。op monitor interval=10s は、10 秒ごとにリソースの状態を確かめる指定です。作ったあと、ip addr で見ると、eth0 に 192.168.100.10/24 が付いていました。

ノードを保守するときは、スタンバイにします。スタンバイのノードはクラスタに参加したままですが、リソースを動かしません（動いていたリソースは、ほかのノードに移ります）。

13.5キャパシティプランニング：足りなくなる前に、測って見積もる

キャパシティプランニングは、「これからの利用の増え方に対して、資源（CPU、メモリ、ディスク、ネットワーク）がいつ、どれだけ足りなくなるか」を見積もり、先に手を打つことです。進め方は 3 段階です。

  1. 測る：いまの使用量を、続けて記録する（リソース監視）
  2. 見積もる：増え方の傾向（トレンド）と、ピークのときの値から、限界に届く時期を予想する
  3. 備える：届く前に、資源を増やす（次の節のスケールアップ・スケールアウト）

「いま遅い」を直すのは障害対応で、キャパシティプランニングは「これから足りなくなる」に備えるものです。そのために、ある瞬間の値ではなく、長い期間の記録が必要です。

13.6スケールアップとスケールアウト、ステートレスな設計

スケーラビリティ（拡張性）は、利用が増えたときに、資源を足して対応できる性質です。足し方は 2 通りで、それぞれ逆向きの言葉があります。

言葉すること別の呼び方
スケールアップ1 台の性能を上げる（CPU、メモリを増やす、上位の機種にする）垂直スケール
スケールダウン1 台の性能を下げる
スケールアウトサーバーの台数を増やす水平スケール
スケールインサーバーの台数を減らす

作業のときの停止ふつうは止める（再起動）止めずに足せる
可用性上がらない（1 台のまま。SPoF が残る）上がる（1 台が壊れても残りで続く）

ステートレスな設計：どのサーバーが受けても同じ

スケールアウトの条件は、サーバーが状態（ステート）を自分の中に持たないことです。状態とは、要求をまたいで覚えておくデータです。ログインしているか、買い物かごの中身（セッション）、アップロードされたファイルなどです。

Web サーバー 1 が自分のメモリやディスクにセッションを持っていると、次の要求が Web サーバー 2 に振り分けられたとき、「ログインしていません」になります。Web サーバー 1 が壊れると、そのセッションは消えます。台数を減らす（スケールイン）こともできません。

ステートレスな設計では、状態をサーバーの外に出します。

状態外に出す先
セッション全サーバーが共有する保存先（Redis や memcached などのキャッシュサーバー、データベース）。または、署名した Cookie やトークンとしてクライアントに持たせる
業務のデータデータベース
アップロードされたファイルオブジェクトストレージ、共有ファイルシステム（NFS）
ログログの集約サーバーへ送る

こうしておけば、Web サーバーはどれも同じで、いつ足しても、いつ捨ててもかまいません。データベースは状態そのものなので、ステートレスにはできません。データベースは、スケールアップ、レプリケーション（後の節）で対応します。

メモスティッキーセッション

ロードバランサーが、同じクライアントを毎回同じサーバーに振り分ける機能を、スティッキーセッション（セッションの維持、パーシステンス）と呼びます。アプリケーションを変えずにセッションを保てますが、そのサーバーが壊れればセッションは消え、負荷も偏ります。ステートレスにできるまでの、次善の方法です。

構成管理ツールと VM イメージ：同じサーバーを、すぐに作る

スケールアウトでは、同じ設定のサーバーを、速く、間違いなく作れなければなりません。手で 1 台ずつ設定していては、間に合わず、設定もずれます。方法は 2 つで、組み合わせて使います。

方法すること特徴
構成管理ツール（Ansible、Puppet、Chef）「あるべき状態」をコード（Ansible なら Playbook）に書き、サーバーに適用する何度実行しても同じ状態になる（冪等性）。設定の変更を全台にそろえて配れる。起動してから適用するので、少し時間がかかる
VM イメージ（マシンイメージ、テンプレート、ゴールデンイメージ）OS、ミドルウェア、アプリケーションを入れ終えたディスクをイメージとして保存し、そこからサーバーを起動する起動するだけで使えるので速い。オートスケーラー（後の節）が使う。内容を変えるには、イメージを作り直す

よくある組み合わせは、「構成管理ツールでイメージを作り、そのイメージから台数を増やす」です。Ansible は第 4 章で扱います。

13.7ロードバランサーと DNS ラウンドロビン

台数を増やしたら、要求を振り分ける仕組みが要ります。方法は 2 つあります。

ロードバランサー

ロードバランサー（負荷分散装置、LB）は、クライアントからの要求を受けて、後ろに並んだサーバーのどれかに渡します。クライアントが接続する先は、ロードバランサーの 1 つのアドレスです。

役目は 3 つあります。

  • 振り分け：決めた方式で、サーバーを選ぶ
  • ヘルスチェック：サーバーに定期的に接続して、応答しないサーバーを自動で振り分け先から外す。直ったら戻す
  • TLS の終端、セッションの維持（スティッキーセッション）など
振り分けの方式選び方HAProxynginx（upstream の中）
ラウンドロビン順番に 1 つずつbalance roundrobin既定（何も書かない）
最少接続いま接続がいちばん少ないサーバーbalance leastconnleast_conn;
送信元 IP のハッシュ同じクライアントの IP アドレスは、同じサーバーbalance sourceip_hash;
重み付け性能の高いサーバーに多くserver … weight 2server … weight=2;

ソフトウェアのロードバランサーには、HAProxy、nginx、LVS（Linux Virtual Server。カーネルの IPVS）があります。HAProxy の設定の例です（Docker の debian:12 で haproxy -c -f を通して確かめた形）。

frontend web    bind *:80    default_backend app backend app    balance roundrobin    option httpchk GET /health    server web1 192.168.10.11:80 check    server web2 192.168.10.12:80 check    server web3 192.168.10.13:80 check backup
  • frontend はクライアントから受ける側、backend は振り分け先のサーバーの集まり
  • balance が振り分けの方式
  • server の行の check が、そのサーバーへのヘルスチェックを有効にする。option httpchk は、HTTP の要求で確かめる指定
  • backup の付いたサーバーは、ほかのサーバーが全部使えなくなったときだけ使われる予備

nginx では、upstream にサーバーを並べ、proxy_pass でそこへ渡します（nginx -t で確かめた形）。

upstream app {    least_conn;    server 192.168.10.11:80 weight=2;    server 192.168.10.12:80;    server 192.168.10.13:80 backup;}server {    listen 8080;    location / { proxy_pass http://app; }}
注意試験の注意：ロードバランサーが SPoF になる

ロードバランサーは、すべての要求が通る場所です。1 台しかなければ、そこが SPoF です。ロードバランサーも 2 台にして、仮想 IP をアクティブ / スタンバイで持たせます（Pacemaker や、VRRP を使う keepalived）。クラウドのロードバランサーのサービスは、事業者の側で冗長化されています。

DNS ラウンドロビン

DNS ラウンドロビンは、1 つの名前に A レコードを何個も登録して、クライアントを分散させる方法です。DNS サーバーは、問い合わせのたびに、アドレスの並び順を変えて答えます。多くのクライアントは先頭のアドレスに接続するので、結果として分散します。

Docker の debian:12 で BIND に次のゾーンを読ませ、dig で 3 回問い合わせた結果です。

www IN A 192.0.2.11www IN A 192.0.2.12www IN A 192.0.2.13

13.8クラウドのストレージ、IP アドレス、ネットワーク

クラウド（IaaS）では、仮想マシンをインスタンスと呼びます。インスタンスは、数分で作れて、いつでも捨てられます。その代わり、「インスタンスと一緒に消えるもの」と「残るもの」を、はっきり分けて使います（図解 LinuC 10.12 の復習を含みます）。用語は OpenStack のものが出題範囲に使われています。

エフェメラルストレージと永続ストレージ

エフェメラルストレージ（揮発性、一時的）永続ストレージ（ブロックストレージのボリューム）
寿命インスタンスと同じ。インスタンスを削除すると消える（クラウドによっては、停止や、物理サーバーの故障でも消える）インスタンスと独立。インスタンスを削除しても残る
付け替えできない切り離して、別のインスタンスに付けられる
置くもの一時ファイル、キャッシュ、作り直せるデータ、スケールアウトで増やす Web サーバーの OS の領域データベースのデータ、消えては困るファイル
例OpenStack のエフェメラルディスク、AWS のインスタンスストアOpenStack Cinder のボリューム、AWS の EBS

「エフェメラル」（ephemeral）は「つかの間の」という意味です。OS の再起動（reboot）では消えませんが、インスタンスそのものを消せば、中身は戻りません。永続ボリュームも、障害や誤操作には備えが要ります。スナップショットやバックアップを別に取ります。

固定 IP アドレスフローティング IP アドレス

種類ふつうはプライベートアドレスグローバルアドレス（外から届く）
寿命インスタンスが存在する間、変わらない。インスタンスを削除すると手放すインスタンスと独立。外して、別のインスタンスに付け替えられる
使い道テナントの中のインスタンスどうしの通信外部への公開。障害のときに、予備のインスタンスへ付け替える

フローティング IP の「フローティング」は、「インスタンスの間を移せる」という意味です。Web サーバーのインスタンスを作り直しても、同じフローティング IP を新しいインスタンスに関連付ければ、利用者が接続する先は変わりません。HA クラスタの仮想 IP と同じ役目を、クラウドの機能で実現するものです。

多くのクラウドでは、フローティング IP はインスタンスの OS には設定されません。仮想ルーターが、フローティング IP 宛ての通信を、固定 IP に変換（NAT）して届けます。

注意試験の注意：「固定」という名前に引っかからない

「固定 IP アドレス」は「インスタンスに固定されている」という意味で、インスタンスを消せば一緒になくなります。インスタンスを作り直しても同じアドレスを使い続けられるのは、フローティング IP のほうです。

テナントネットワークとセキュリティグループ

クラウドは、多くの利用者が同じ設備を共有します。利用者（契約、プロジェクト）の単位をテナントと呼びます。

テナントネットワークは、テナントが自分で作る、ほかのテナントから切り離された仮想のネットワークです。アドレスの範囲（プライベートアドレス）も自分で決められ、ほかのテナントと同じ範囲を使っても、ぶつかりません。外部と通信するには、仮想ルーターで外部のネットワークにつなぎます。

セキュリティグループは、インスタンス（の仮想 NIC）に付ける、クラウドの側のファイアウォールです。

  • 許可する通信の規則を並べる。どの規則にも合わない受信は、拒否される
  • 規則は「方向（受信 / 送信）、プロトコル、ポート、相手（CIDR、または別のセキュリティグループ）」
  • ステートフル：許可した通信への戻りのパケットは、規則を書かなくても通る
  • 相手に「別のセキュリティグループ」を書ける。「db のグループは、web のグループからの 5432 番だけを許す」と書けば、Web サーバーが何台に増えても、規則を変えなくてよい
  • インスタンスの外で働くので、OS の中のファイアウォール（iptables、firewalld）とは別のもの。両方を通った通信だけが届く

13.9オブジェクトストレージ、メッセージキュー、オートスケーラー

クラウドには、サーバーを立てなくても使える部品（マネージドサービス）があります。出題範囲にあるのは 3 つです。

オブジェクトストレージ

オブジェクトストレージは、データを「オブジェクト」（ファイルの中身 + メタデータ）の単位で、HTTP の API（REST）を使って出し入れするストレージです。オブジェクトは、バケット（コンテナ）という入れ物の中に、キー（名前）を付けて置きます。

ブロックストレージ（ボリューム）オブジェクトストレージ
見え方ディスク（ブロックデバイス）。ファイルシステムを作ってマウントするHTTP の URL。PUT で置き、GET で取り出す
使う相手付けた 1 台のインスタンスネットワーク越しに、何台からでも
容量作るときに決める決めなくてよい（置いた分だけ）
更新一部だけを書き換えられるオブジェクト全体を置き換える
向いているものOS、データベース画像・動画などの静的なファイル、バックアップ、ログ、アップロードされたファイル
例OpenStack Cinder、AWS EBSOpenStack Swift、Amazon S3

オブジェクトストレージは、事業者の側で複数の場所に複製されるので、耐久性が高く、容量を気にせずに使えます。Web サーバーをステートレスにするときの、ファイルの置き場所として使います。一方、一部だけを頻繁に書き換えるデータ（データベースのデータファイル）には向きません。

メッセージキュー

メッセージキューは、プログラムの間で受け渡すメッセージを、いったん貯めておく仕組みです。送る側（プロデューサー）はキューに入れたら、すぐ次の仕事に進みます。受ける側（コンシューマー、ワーカー）は、自分の都合のよいときにキューから取り出して処理します。

  • 非同期：送る側は、処理が終わるのを待たない
  • 疎結合：送る側と受ける側は、相手の場所や台数を知らなくてよい。受ける側が止まっていても、メッセージはキューに残り、再開したら処理される
  • 平準化：要求が一度に集中しても、キューに貯まるだけで、受ける側は自分の速さで処理できる
  • スケールアウト：キューが長くなったら、ワーカーを増やす

代表的なソフトウェアは RabbitMQ、Apache Kafka、クラウドのサービスでは Amazon SQS です。使い方は、後の節（非同期処理）で見ます。

オートスケーラー

オートスケーラー（オートスケーリング）は、負荷に合わせて、インスタンスの台数を自動で増やしたり（スケールアウト）減らしたり（スケールイン）する仕組みです。

  • 条件：監視の値（CPU 使用率の平均、要求の数、キューの長さ）にしきい値を決める。「CPU 使用率が 70% を超えたら 2 台増やす、30% を下回ったら 1 台減らす」
  • 最小と最大：台数の下限と上限を決める。条件がどうであれ、この範囲を出ない（上限は、費用が際限なく増えるのを防ぐ）
  • VM イメージ：増やすインスタンスは、あらかじめ用意したイメージから起動する
  • ロードバランサー：増えたインスタンスは、自動で振り分け先に入る。減らすときは外してから消す
  • 自動の修復：ヘルスチェックに応答しないインスタンスを捨てて、新しく作り直す

オートスケーラーが使えるのは、インスタンスがステートレスなときです。いつ消されるか分からないので、消えては困るデータをエフェメラルストレージに置いてはいけません。

コツ4 つの部品は、1 つの考え方でつながる

「インスタンスは、いつでも捨てて作り直せるものにする」が、クラウドの設計の中心です。そのために、データは永続ボリュームかオブジェクトストレージに、セッションは共有の保存先に、アドレスはフローティング IP かロードバランサーに、時間のかかる処理はメッセージキューに出します。こうすると、オートスケーラーが台数を自由に変えられます。

13.10LAMP・LAPP と、Web 三層

ここからは、実際によく使われる構成を、小さいものから順に見ます。

LAMP と LAPP

Web アプリケーションを動かすソフトウェアの、定番の組み合わせです。頭文字を並べた名前が付いています。

LAM / PP
LAMPLinuxApacheMySQL（MariaDB）PHP（Perl、Python）
LAPPLinuxApachePostgreSQLPHP（Perl、Python）

違いは、データベースが MySQL（MariaDB）か PostgreSQL かだけです。どれもオープンソースで、小さなシステムなら、この 4 つを 1 台のサーバーに入れて動かせます。Apache の代わりに nginx を使う組み合わせは、LEMP（nginx を「エンジンエックス」と読むので E）と呼ばれます。

Web 三層：役目ごとに、サーバーを分ける

1 台に全部を入れた構成は、利用が増えると分けることになります。役目で 3 つの層に分けたものが、Web 三層（3 層アーキテクチャ）です。

層サーバー役目ソフトウェアの例
プレゼンテーション層Web サーバークライアントからの HTTP の要求を受ける。静的なファイル（画像、CSS）を返す。TLS を終端する。動的な処理は AP サーバーに渡すApache、nginx
アプリケーション層AP サーバー（アプリケーションサーバー）業務の処理（プログラム）を実行する。必要なデータを DB サーバーに問い合わせ、結果のページを作るTomcat、PHP-FPM、uWSGI など
データ層DB サーバーデータを保存し、検索するPostgreSQL、MySQL、MariaDB

要求は「クライアント → Web → AP → DB」と進み、応答は逆に戻ります。分ける利点は 3 つです。

  • 層ごとに増やせる：重い層だけを、スケールアウト・スケールアップできる
  • 守りやすい：外から届くのは Web サーバーだけにし、DB サーバーは内側のネットワークに置く。クライアントは DB に直接つながない
  • 入れ替えやすい：ある層のソフトウェアを替えても、ほかの層への影響が小さい

ただし、層を分けただけでは、可用性は上がりません。Web・AP・DB が 1 台ずつなら直列で、どれが止まっても全体が止まります。どれも稼働率 0.99 なら、全体は 0.99 × 0.99 × 0.99 = 約 0.970（97.0%）に下がります（直列と並列）。3 台とも SPoF です。

13.11三層にロードバランサー、HA、レプリケーションを入れる

三層の SPoF を、層ごとになくします。層によって、使う方法が違います。

層方法理由
入口ロードバランサーを置き、それ自身も 2 台で HA にする（仮想 IP）すべての要求が通るので、1 台では SPoF
Web / AP サーバースケールアウト（同じものを並べて、ロードバランサーで振り分ける）ステートレスにできるので、並べるだけでよい。性能と可用性が同時に上がる
DB サーバーHA クラスタ（アクティブ / スタンバイ）とレプリケーション状態を持つので、ただ並べることはできない。データを複製したうえで、切り替える

稼働率 0.99 のサーバーで計算すると、Web・AP・DB を 2 台ずつ並列にしたとき、各層は 0.9999、全体は 0.9999 × 0.9999 × 0.9999 = 約 0.9997 です。1 台ずつのときの 0.970 から、大きく上がります。

DB のレプリケーション

レプリケーションは、あるデータベース（プライマリ。マスター、ソースとも呼ぶ）への更新を、別のデータベース（レプリカ。スタンバイ、スレーブとも呼ぶ）に続けて複製する仕組みです。使い道は 2 つあります。

  • 可用性：プライマリが壊れたら、レプリカを昇格させてプライマリにする（フェイルオーバー）。Pacemaker などのクラスタソフトウェアが、昇格と仮想 IP の付け替えを自動で行う
  • 参照の負荷分散：検索（SELECT）をレプリカに振り分ける（リードレプリカ）。更新はプライマリだけが受ける
同期レプリケーション非同期レプリケーション
動きレプリカに届いたのを確かめてから、更新を完了するレプリカを待たずに、更新を完了する
プライマリが壊れたとき完了した更新は、レプリカにもある（RPO はほぼ 0）直前の更新が、レプリカに届いていないことがある
性能更新が遅くなる（レプリカを待つ）更新が速い
向いている場所近い場所（同じデータセンター）遠い場所（別のリージョン）
注意試験の注意：レプリケーションでできないこと
  • 更新の負荷分散はできない：レプリカは参照専用です。更新が多すぎるなら、プライマリをスケールアップするか、データを分ける
  • バックアップの代わりにならない：誤った DELETE も、レプリカにそのまま複製される（論理障害）
  • 非同期のレプリカは、少し古いデータを返すことがある（複製の遅れ）

ロードバランサーか、DNS ラウンドロビンか

Web サーバーをスケールアウトするとき、振り分けにはロードバランサーと DNS ラウンドロビンのどちらも使えます。違いは前の節の表のとおりです。まとめると、次のように使い分けます。

  • 壊れたサーバーを自動で外したい、負荷を見て振り分けたい、セッションを維持したい → ロードバランサー
  • 機器を足さずに、手軽に分散したい。障害のときの切り離しは別の方法で行う → DNS ラウンドロビン
  • 両方を組み合わせることもある。離れた拠点のロードバランサー（の仮想 IP）を、DNS で振り分ける

13.12プロキシキャッシュ、CDN、メッセージキューで軽くする

サーバーを増やす以外に、サーバーの仕事を減らす方法があります。「同じものを何度も作らない」（キャッシュ）と、「あとでよい仕事は、あとでする」（非同期処理）です。

プロキシキャッシュと CDN

キャッシュは、一度作った応答を取っておいて、次の同じ要求にはそれを返すことです。

プロキシキャッシュ（リバースプロキシ）CDN（Content Delivery Network、コンテンツ配信網）
置く場所自分の Web サーバーの手前（同じデータセンター）世界の各地にある、事業者のエッジサーバー
動きWeb サーバーの応答を保存し、同じ要求には、Web サーバーに聞かずに返す利用者に近いエッジサーバーが、保存した内容を返す。なければ元のサーバー（オリジン）に取りに行く
効果Web / AP サーバーの負荷が減るオリジンの負荷が減る。距離が近いので応答が速い。アクセスの集中や攻撃を、広い設備で受け止められる
ソフトウェア・サービスnginx（proxy_cache）、Squid、Varnish各社の CDN サービス

キャッシュに向くのは、だれが見ても同じで、あまり変わらない内容です。画像、CSS、JavaScript、動画などの静的なファイルです。向かないのは、利用者ごとに違う内容（ログインした後の画面、買い物かご）や、更新の要求（POST）です。これらをキャッシュすると、他人の情報が見えてしまう事故になります。

キャッシュには有効期限（TTL）があります。オリジンでファイルを更新しても、期限が切れるまでは、キャッシュが古い内容を返します。すぐに反映したいときは、キャッシュを消す（パージ）か、ファイル名を変えます。

メモフォワードプロキシとリバースプロキシ

クライアントの側に置いて、クライアントの代わりに外へ取りに行くのが、フォワードプロキシです（社内から Web を見るときの Squid。第 9 章）。サーバーの側に置いて、サーバーの代わりに要求を受けるのが、リバースプロキシです。ここで言うプロキシキャッシュと、ロードバランサーは、リバースプロキシの仲間です。

メッセージキューによる非同期処理

時間のかかる処理を、要求の中で全部済ませようとすると（同期処理）、利用者は待たされ、その間 AP サーバーの処理の枠がふさがります。非同期処理では、AP サーバーは仕事の内容をメッセージとしてキューに入れ、すぐに応答を返します。実際の処理は、別のプログラム（ワーカー）があとで行います。

同期処理メッセージキューを使った非同期処理
利用者への応答処理が全部終わってから受け付けた時点で、すぐ
処理の結果応答に含められる応答には含められない（あとで通知する、利用者が見に行く）
処理する側が止まっているとき要求がエラーになるメッセージはキューに残り、再開したあとに処理される
要求が集中したときサーバーがあふれるキューに貯まり、ワーカーは自分の速さで処理する（平準化）
増やし方AP サーバーを増やすワーカーだけを増やせる

向いているのは、結果をその場で返さなくてよい仕事です。メールの送信、画像や動画の変換、帳票の作成、集計、ほかのシステムへの連携などです。向かないのは、結果がないと次の画面を出せない処理（ログインの認証、残高の照会）です。

ワーカーが処理の途中で止まると、メッセージはキューに戻り、もう一度配られます。そのため、同じメッセージを 2 回処理しても困らないように作ります（冪等にする）。

深掘り全部を合わせた構成

大きな Web サービスの典型的な構成は、ここまでの部品を全部つないだものです。利用者 → CDN（静的なファイル）→ ロードバランサー（2 台、HA）→ Web / AP サーバー（ステートレス、オートスケーラーで増減）→ セッション用のキャッシュサーバー、DB（プライマリ + レプリカ、HA）、オブジェクトストレージ（ファイル）、メッセージキュー → ワーカー。試験では、この中の 1 か所を取り出して、「この部品の役目は」「ここがないと何が困るか」「SPoF はどこか」と問われます。

要点まとめ
  • 稼働率 = MTBF ÷ (MTBF + MTTR)。MTBF は動いていた時間の平均（大きいほど良い）、MTTR は直す時間の平均（小さいほど良い）
  • 直列は掛け算（a × b、下がる）。並列は 1 − (1 − a)(1 − b)（上がる）。0.99 が 2 台で、直列 0.9801、並列 0.9999
  • 99.9% は 1 年に約 8.76 時間、99.99% は約 52.6 分の停止
  • RPO はどの時点のデータまで戻すか（過去へ）、RTO はいつまでに再開するか（未来へ）。SLA はサービスの水準の合意
  • 物理障害には冗長化、論理障害にはバックアップ。SPoF は「1 つしかないもの」
  • Corosync はノード間の通信・メンバーシップ・クォーラム、Pacemaker はリソースの管理と切り替え。設定は /etc/corosync/corosync.conf と CIB。crm_mon -1、pcs status、pcs resource create、crm configure show
  • スプリットブレインは STONITH（フェンシング）とクォーラム（過半数）で防ぐ
  • スケールアップ / ダウンは 1 台の性能、スケールアウト / インは台数。スケールアウトにはステートレスな設計（セッションを外に出す）と、VM イメージ・構成管理ツールが要る
  • ロードバランサーはヘルスチェックで壊れたサーバーを外す。DNS ラウンドロビンは A レコードを並べるだけで、障害も負荷も見ない
  • エフェメラルストレージはインスタンスと一緒に消える。フローティング IP は別のインスタンスに付け替えられる。セキュリティグループは許可の規則を並べるステートフルなファイアウォール
  • オブジェクトストレージは HTTP の API でオブジェクト単位に出し入れする。オートスケーラーは最小と最大の間で、台数を自動で変える
  • LAMP = Linux + Apache + MySQL + PHP、LAPP は MySQL が PostgreSQL。Web 三層 = Web サーバー、AP サーバー、DB サーバー
  • Web / AP はスケールアウト、DB は HA とレプリケーション（更新はプライマリだけ。バックアップの代わりにはならない）
  • CDN とプロキシキャッシュは静的な内容に。メッセージキューは、あとでよい処理を非同期にする
