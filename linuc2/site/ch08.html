8.1DNS サーバーには 2 つの役目がある

DNS サーバーの仕事は、2 つに分かれます。1 台で両方をすることもできますが、役目は別です。

役目別の呼び方すること
権威サーバーコンテンツサーバー、authoritative server自分が受け持つ範囲（ゾーン）の情報を持ち、聞かれたら答える
キャッシュサーバーフルリゾルバ、recursive resolverクライアントの代わりにルートから順にたどって答えを見つけ、しばらく覚えておく

クライアントからキャッシュサーバーへの「最後の答えまで調べてほしい」という頼み方を、再帰問い合わせと呼びます。キャッシュサーバーが権威サーバーを 1 つずつたどる聞き方は、反復問い合わせです。

権威サーバーは、同じゾーンを複数の台で受け持ちます。元のデータを持つ台がプライマリ（マスター）、その写しをもらう台がセカンダリ（スレーブ）です。写しをもらうことをゾーン転送と呼びます。

DNS は 53 番ポートを使います。ふつうの問い合わせは UDP、ゾーン転送と大きな応答は TCP です（図解 LinuC 7.4）。

BIND と、ほかのネームサーバー

BIND（Berkeley Internet Name Domain）は、ISC が作っているいちばん広く使われてきた DNS サーバーです。デーモンの名前は named（name daemon）で、権威サーバーとキャッシュサーバーの両方になれます。

試験では、BIND 以外のサーバーの役目の違いも問われます。

ソフトウェア役目特徴
BIND（named）権威 + キャッシュ両方できる。設定は named.conf
dnsmasq小さなネットワーク向けの DNS キャッシュ（フォワーダー）+ DHCP サーバー軽い。/etc/hosts の中身をそのまま答える。設定は /etc/dnsmasq.conf
Unboundキャッシュサーバー専用DNSSEC の検証ができるフルリゾルバ。設定は /etc/unbound/unbound.conf、操作は unbound-control
NSD権威サーバー専用再帰問い合わせには答えない。設定は /etc/nsd/nsd.conf、操作は nsd-control
PowerDNS権威サーバー（pdns_server）と、別のプログラムのキャッシュサーバー（pdns_recursor）ゾーンの情報を MySQL や PostgreSQL などのデータベースに置ける

Unbound と NSD は、どちらも NLnet Labs が作っています。「キャッシュは Unbound、権威は NSD」と役目を分けて組み合わせる使い方が定番です。

注意試験の注意：専用はどちらか

Unbound = キャッシュ専用、NSD = 権威専用です。逆にした選択肢がよく出ます。dnsmasq は「DNS と DHCP を 1 つでまかなう」、PowerDNS は「バックエンドにデータベースが使える」が目印です。

8.2named.conf はどこにあり、どう書くか

BIND の設定ファイルは named.conf です。場所はディストリビューションで違います。

Red Hat 系（Rocky Linux 9）Debian 系（Debian 12）
パッケージbind（道具は bind-utils）bind9（道具は bind9-dnsutils、bind9-utils）
設定ファイル/etc/named.conf/etc/bind/named.conf（中で named.conf.options、named.conf.local、named.conf.default-zones を include）
directory の既定/var/named/var/cache/bind
ルートサーバーの一覧（ヒント）/var/named/named.ca/usr/share/dns/root.hints
localhost のゾーン/var/named/named.localhost など/etc/bind/db.local など
実行するユーザーnamedbind
systemd のユニットnamed.servicenamed.service（別名 bind9.service）
rndc の鍵/etc/rndc.key/etc/bind/rndc.key

Rocky Linux 9 の /etc/named.conf の主なところです（コメントを除いた抜粋）。

options {    listen-on port 53 { 127.0.0.1; };    listen-on-v6 port 53 { ::1; };    directory     "/var/named";    dump-file     "/var/named/data/cache_dump.db";    allow-query     { localhost; };    recursion yes;    dnssec-validation yes;    pid-file "/run/named/named.pid";}; zone "." IN {    type hint;    file "named.ca";}; include "/etc/named.rfc1912.zones";include "/etc/named.root.key";

入れた直後は、自分自身（127.0.0.1）からの問い合わせだけに答えるキャッシュサーバーになっています。ほかの機械から使うには、listen-on と allow-query の両方を広げます。

書き方の決まり

  • 文は ; で終わる。ブロックは { … }; で、閉じたあとにも ; が要る
  • アドレスの並びも、1 つずつ ; で区切る：{ 192.168.10.0/24; 127.0.0.1; };
  • コメントは //、#、/* … */ の 3 種類
  • ファイルの名前やゾーンの名前は "…" で囲む

; の付け忘れが、いちばん多いまちがいです。あとで見る named-checkconf が見つけてくれます。

options：全体の設定

ディレクティブ意味
directory "パス";作業ディレクトリ。file などの相対パスの基準
listen-on port 53 { アドレス; };待ち受ける IPv4 アドレス（IPv6 は listen-on-v6）
allow-query { … };問い合わせを受け付ける相手
recursion yes | no;再帰問い合わせに答えるか（キャッシュサーバーとして働くか）
allow-recursion { … };再帰問い合わせを受け付ける相手
allow-transfer { … };ゾーン転送を許す相手
forwarders { アドレス; };自分で解決できない問い合わせを回す先（forwarders）
forward only | first;フォワーダーだけを使うか、だめなら自分でもたどるか
version "文字列";バージョンを聞かれたときに答える文字列
dnssec-validation auto | yes | no;DNSSEC の署名を検証するか（DNSSEC）

{ … } の中には、アドレス（192.168.10.1）、ネットワーク（192.168.10.0/24）のほかに、あらかじめ決まった名前が書けます。

名前意味
anyすべて
noneなし
localhostこのサーバー自身のアドレス
localnetsこのサーバーがつながっているネットワーク

自分で名前を付けるには、acl 文を使います。acl "internal" { 192.168.10.0/24; localhost; }; と書いておけば、allow-query { internal; }; のように使えます。

zone：ゾーンごとの設定

zone "example.jp" {    type master;    file "example.jp.zone";}; zone "10.168.192.in-addr.arpa" {    type master;    file "192.168.10.rev";}; zone "example.com" {    type slave;    masters { 192.168.10.1; };    file "slaves/example.com.zone";};

file が相対パスなら、options の directory からの相対パスです。directory "/var/named"; のとき、上の example.jp.zone は /var/named/example.jp.zone を指します。ゾーンファイルの名前に決まりはなく、zone 文の file に書いたものが読まれます。

type意味一緒に書くもの
master（primary）このサーバーが元のデータを持つfile
slave（secondary）プライマリから写しをもらうmasters { プライマリのアドレス; };（primaries）、file（写しの保存先）
hintルートサーバーの一覧。ゾーン "." にだけ使うfile（named.ca など）
forwardこのゾーンの問い合わせだけ、指定したサーバーへ回すforwarders { … };
stub相手のゾーンの NS レコードだけを写すmasters { … };

新しい BIND では、master / slave / masters の代わりに primary / secondary / primaries とも書けます（9.18 でどちらも named-checkconf を通ることを確かめました）。試験と多くの資料は、まだ master と slave です。

注意試験の注意：hint と forward を取り違えない

type hint は「ルートサーバーの場所を書いたファイルを読む」で、キャッシュサーバーが最初にどこへ聞くかを知るためのものです。type forward は「このゾーンの問い合わせを別のサーバーへ回す」です。セカンダリに要るのは type slave と masters で、file はなくても動きますが、あると再起動のあとすぐ答えられます。

8.3rndc と named-checkconf で、動かしながら管理する

named-checkconf：設定の文法を調べる

named-checkconf は、named.conf の文法を調べるコマンドです。ファイルを指定しなければ、既定の場所（Red Hat 系は /etc/named.conf、Debian 系は /etc/bind/named.conf）を読みます。問題がなければ、何も表示せずに終了ステータス 0 で終わります。

ターミナル
# named-checkconf# echo $?0# named-checkconf /tmp/bad.conf/tmp/bad.conf:1: missing ';' before '}'/tmp/bad.conf:2: missing ';' before end of file# named-checkconf /tmp/bad2.conf/tmp/bad2.conf:3: boolean expected near 'maybe'

エラーは「ファイル名:行番号: 理由」の形です。1 つ目は ; の付け忘れ、2 つ目は recursion maybe; のように yes / no でない値を書いた例です。

オプション意味
（なし）文法だけを調べる。ゾーンファイルは読まない
-znamed.conf にあるマスターゾーンのゾーンファイルも読み込んで調べる
-p読み込んだ設定を、include を展開し、形を整えて表示する
-t ディレクトリchroot した先のディレクトリを基準にして調べる
ターミナル
# named-checkconf -zzone example.jp/IN: loaded serial 2026111701zone 10.168.192.in-addr.arpa/IN: loaded serial 2026111701zone localhost/IN: loaded serial 2zone 127.in-addr.arpa/IN: loaded serial 1

Rocky Linux 9 の named.service は、起動の前に named-checkconf -z を実行します。設定かゾーンファイルにまちがいがあれば、named は起動しません。

rndc：動いている named に指示する

rndc（remote name daemon control）は、動いている named に指示を送るコマンドです。named は TCP の 953 番で指示を待ち、rndc と named が同じ共有鍵を持っているときだけ受け付けます。

ターミナル
# rndc statusversion: BIND 9.18.49-1~deb12u3-Debian (Extended Support Version) <id:> (unknown)boot time: Mon, 16 Nov 2026 21:19:04 GMTlast configured: Mon, 16 Nov 2026 21:19:04 GMTconfiguration file: /etc/bind/named.confnumber of zones: 7 (0 automatic)debug level: 0xfers running: 0query logging is OFFrecursive clients: 0/900/1000tcp clients: 0/150server is up and running# rndc reload example.jpzone reload queued# rndc reloadserver reload successful
コマンド意味
rndc statusサーバーの状態を表示する
rndc reload設定ファイルとすべてのゾーンを読み直す
rndc reload ゾーンそのゾーンだけを読み直す
rndc reconfig設定ファイルを読み直し、新しく足したゾーンだけを読み込む（すでにあるゾーンのファイルは読み直さない）
rndc flushキャッシュをすべて捨てる（rndc flushname 名前 はその名前だけ）
rndc dumpdbキャッシュなどをファイル（named_dump.db）に書き出す

鍵は、named.conf の key 文と controls 文（named の側）と、/etc/rndc.conf か rndc.key（rndc の側）に書きます。controls 文を書かなければ、named は rndc.key を読んで 127.0.0.1 からの指示だけを受け付けます。鍵のファイルは rndc-confgen -a で作れます。

key "rndc-key" {    algorithm hmac-sha256;    secret "sM4kGMI6X08gXfRdbpeaT9PP3tljS87KsQPiPJsV3v8=";}; controls {    inet 127.0.0.1 port 953        allow { 127.0.0.1; } keys { "rndc-key"; };};

鍵が合わない、または named が鍵のファイルを読めないと、rndc は次のように失敗します。

ターミナル
# rndc statusrndc: connection to remote host closed.* This may indicate that the* remote server is using an older* version of the command protocol,* this host is not authorized to connect,* the clocks are not synchronized,* the key signing algorithm is incorrect* or the key is invalid.
注意試験の注意：reload と reconfig

rndc reload は全部読み直します。rndc reconfig は「設定ファイル + 新しいゾーンだけ」です。ゾーンファイルの中身を書き換えたときは、reconfig では反映されません。rndc reload か rndc reload ゾーン名 を使います。systemctl reload named も、中で rndc reload を実行します。

ログはどこに出るか

named のログは、既定では syslog に送られます。systemd の機械では journalctl -u named で見ます。ファイルでは、Red Hat 系は /var/log/messages、Debian 系は /var/log/syslog です。

16-Nov-2026 21:21:11.158 zone example.jp/IN: loaded serial 202611170116-Nov-2026 21:21:36.531 client @0xffff9a800098 127.0.0.1#48454 (www.example.jp): query: www.example.jp IN A +E(0)K (127.0.0.1)

1 行目は、ゾーンを読み込んだときのログです。読み込んだシリアルが出るので、書き換えが反映されたかを確かめられます。2 行目は rndc querylog on にしたときの問い合わせのログで、「だれが（127.0.0.1 の 48454 番ポート）、何を（www.example.jp の A）」聞いたかがわかります。

出す先を細かく決めたいときは、named.conf の logging 文で、channel（出す先）と category（ログの種類）を組み合わせます。

8.4dig・host・nslookup で、サーバーの答えを確かめる

レベル1 で使った dig と host は、DNS サーバーを作る側にとっては検査の道具です（図解 LinuC 7.12）。3 つとも /etc/hosts は見ずに、DNS サーバーに直接聞きます。

作ったばかりのサーバーに、@ で相手を指定して聞きます。

ターミナル
$ dig @127.0.0.1 www.example.jp ;; Got answer:;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 13350;; flags: qr aa rd; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1;; WARNING: recursion requested but not available ;; QUESTION SECTION:;www.example.jp.            IN    A ;; ANSWER SECTION:www.example.jp.        3600    IN    A    192.168.10.10 ;; Query time: 0 msec;; SERVER: 127.0.0.1#53(127.0.0.1) (UDP)

レベル2 では、flags: の行を読めるようにします。

フラグ名前意味
qrquery responseこれは応答である
aaauthoritative answerそのゾーンを持つ権威サーバー自身の答え（キャッシュではない）
rdrecursion desiredクライアントが再帰を頼んだ（dig は既定で頼む）
rarecursion availableサーバーが再帰に応じられる
adauthenticated dataDNSSEC の検証に成功した答え

上の例は、aa があって ra がありません。「このゾーンの権威サーバーが答えた。ただし、このサーバーは再帰に応じない」と読めます。WARNING: recursion requested but not available も同じことを言っています。

status意味
NOERROR成功（答えが 0 件でも、名前があれば NOERROR）
NXDOMAINその名前はない
SERVFAILサーバーが答えを作れなかった（ゾーンの読み込み失敗、フォワーダーに届かない、DNSSEC の検証失敗など）
REFUSED断られた（allow-query や allow-recursion で許されていない、そのゾーンを持っていない）

recursion no; の権威サーバーに、持っていないゾーンの名前を聞くと REFUSED です。

ターミナル
$ dig @127.0.0.1 www.debian.org | grep -E 'status|flags';; ->>HEADER<<- opcode: QUERY, status: REFUSED, id: 43987;; flags: qr rd; QUERY: 1, ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 1
使い方意味
dig @サーバー 名前 種類そのサーバーに聞く。種類は A（既定）、MX、NS、SOA、TXT、ANY など。-t 種類 でも同じ
dig -x アドレス逆引き（PTR）
dig +short …答えの値だけ
dig +norecurse …再帰を頼まない（rd を立てない）。権威サーバーの検査に使う
dig +trace 名前ルートから順に、反復問い合わせを自分でたどって見せる
dig +dnssec …DNSSEC の署名（RRSIG）も一緒にもらう
dig +tcp …TCP で聞く
dig -p ポート …53 番以外のポートに聞く
dig @サーバー ゾーン AXFRゾーン転送を試す
dig -k 鍵ファイル …、dig -y 名前:鍵 …TSIG の鍵を付けて聞く（TSIG）

host と nslookup は、サーバーを最後の引数に書きます。

ターミナル
$ host -t MX example.jp 127.0.0.1Using domain server:Name: 127.0.0.1Address: 127.0.0.1#53Aliases:  example.jp mail is handled by 10 mail.example.jp.$ nslookup -type=MX example.jp 127.0.0.1Server:        127.0.0.1Address:    127.0.0.1#53 example.jp    mail exchanger = 10 mail.example.jp.
コマンド使い方
host 名前 [サーバー]A・AAAA・MX をまとめて引く
host -t 種類 名前種類を指定する
host -a 名前くわしく、すべての種類（-v -t ANY と同じ）
host -l ゾーン [サーバー]ゾーン転送（AXFR）で、ゾーンの中のホストを一覧にする
nslookup 名前 [サーバー]名前を引く
nslookup -type=種類 名前種類を指定する
nslookup（引数なし）対話モード。server アドレス で聞く先、set type=MX で種類を変える
コツどのサーバーに聞いたかを必ず確かめる

設定を変えたのに答えが変わらないときは、まず dig の最後の SERVER: の行を見ます。@ を付け忘れると、/etc/resolv.conf のキャッシュサーバーに聞いていて、古い答え（キャッシュ）を見ていることがあります。キャッシュの残り時間は、答えの 2 列目の TTL です。

8.5ゾーンファイルはどう書くか

ゾーンファイルは、そのゾーンの情報をリソースレコード（資源レコード）の並びで書いたテキストファイルです。置く場所は named.conf の directory と file で決まります（Red Hat 系なら /var/named/ の下、Debian 系なら /etc/bind/ や /var/lib/bind/ の下に置くのがふつうです）。

example.jp のゾーンファイルの例です。Docker の中で named-checkzone を通し、named に読ませて確かめたものです。

$TTL 3600@    IN    SOA    ns1.example.jp. admin.example.jp. (        2026111701    ; Serial        10800        ; Refresh        3600        ; Retry        604800        ; Expire        900 )        ; Negative Cache TTL    IN    NS    ns1.example.jp. いちばん大事な決まりは、最後のドットです。

  • 名前の最後に . がある → 完全な名前（FQDN）。そのまま使われる

ゾーンファイルで FQDN を書くときは、最後に . を付けます。付け忘れると、オリジンが 2 重に付きます。文法としては正しいので、named はそのまま読み込んでしまいます（上の例も最後は OK です）。SOA、NS、MX、CNAME、PTR の右側が特にまちがえやすいところです。

SOA レコード：ゾーンの管理情報

SOA（Start Of Authority）は、ゾーンファイルの最初に 1 つだけ書くレコードです。

@  IN  SOA  ns1.example.jp. admin.example.jp. (       2026111701  10800  3600  604800  900 )
順番名前例意味
1MNAMEns1.example.jp.プライマリのネームサーバーの名前
2RNAMEadmin.example.jp.管理者のメールアドレス。@ を . に置き換えて書く（admin@example.jp）
3シリアル2026111701ゾーンの版の番号。書き換えるたびに増やす
4リフレッシュ10800セカンダリがプライマリのシリアルを確かめに行く間隔
5リトライ3600確かめに失敗したとき、次に試すまでの間隔
6エクスパイア604800プライマリに届かないまま、セカンダリが答え続けてよい期間
7ミニマム900ネガティブキャッシュの TTL（「その名前はない」という答えを覚えておく時間）

シリアルは、YYYYMMDDnn（年月日 + その日の何回目か）の形にする習慣があります。大事なのは形ではなく、前より大きい数にすることです。

決まりごとがいくつかあります。

  • NS は 1 つ以上要る。NS レコードのないゾーンは読み込めません（has no NS records）
  • MX の優先度は、数が小さいほうが先に使われます
  • NS と MX の右側は名前です。IP アドレスは書けません。その名前の A レコードを別に書きます
  • CNAME を書いた名前には、ほかのレコードを書けません。NS や MX の右側に、CNAME で付けた別名を書くのもまちがいです
  • 同じ名前に A レコードを複数書くと、順番を変えながら全部を答えます（DNS ラウンドロビン）
ターミナル

1 つ目は、ftp に CNAME と A の両方を書いた例です。2 つ目は、MX の右側に CNAME の名前を書いた例です。

8.6逆引きのゾーンは、アドレスを逆に並べる

IP アドレスから名前を引く逆引きも、ゾーンとして書きます。IPv4 の逆引きのゾーン名は、ネットワーク部のオクテットを逆の順に並べて、.in-addr.arpa を付けたものです。

ネットワーク逆引きのゾーン名
192.168.10.0/2410.168.192.in-addr.arpa
172.16.0.0/1616.172.in-addr.arpa
10.0.0.0/810.in-addr.arpa
IPv6 2001:db8::/328.b.d.0.1.0.0.2.ip6.arpa（16 進 1 桁ずつを逆に並べる）

named.conf と、ゾーンファイルの例です。

zone "10.168.192.in-addr.arpa" {    type master;    file "192.168.10.rev";};
$TTL 3600@    IN    SOA    ns1.example.jp. admin.example.jp. 2026111701 10800 3600 604800 900    IN    NS    ns1.example.jp.1    IN    PTR    ns1.example.jp.10    IN    PTR    www.example.jp.

左の 10 は相対の名前なので、オリジンが補われて 10.10.168.192.in-addr.arpa. になります。これが 192.168.10.10 の逆引きの名前です。右側は別のゾーンの名前なので、必ず FQDN で、最後に . を付けます。

ターミナル
$ dig @127.0.0.1 -x 192.168.10.10 +shortwww.example.jp.$ host 192.168.10.10 127.0.0.110.10.168.192.in-addr.arpa domain name pointer www.example.jp.

正引き（A）と逆引き（PTR）は、別のゾーンの別のレコードです。A レコードを足しても、PTR は自動では増えません。

8.7named-checkzone と named-compilezone、そしてゾーン転送

named-checkzone：ゾーンファイルを調べる

named-checkzone は、ゾーンファイルの文法と中身を調べます。引数は「ゾーン名、ファイル名」の順です。

ターミナル
# named-checkzone example.jp /etc/bind/db.example.jpzone example.jp/IN: loaded serial 2026111701OK# named-checkzone example.jp /tmp/e4zone example.jp/IN: has no NS recordszone example.jp/IN: not loaded due to errors.

成功すると、読み込んだシリアルと OK を表示して、終了ステータス 0 で終わります。ゾーン名を渡すのは、ファイルの中の @ や相対の名前に補うオリジンが、ファイルだけでは決まらないからです。

オプション意味
-D読み込んだゾーンを、名前をすべて FQDN にした形で表示する
-f 形式入力の形式（text か raw。既定は text）
-F 形式出力の形式
-o ファイル出力先（- は標準出力）
-t ディレクトリchroot した先を基準にする

named-compilezone：形式を変える

named-compilezone は named-checkzone と同じプログラムですが、調べたあとでゾーンを別の形式で書き出します。そのため、-o で出力先を必ず指定します。

ゾーンファイルには、人が読める text 形式のほかに、named が速く読める raw（バイナリ）形式があります。いまの BIND では、セカンダリがゾーン転送でもらって保存するファイルは、既定で raw 形式です。cat では読めないので、named-compilezone で text に直します。

ターミナル
# named-compilezone -f text -F raw -o example.jp.raw example.jp db.example.jpzone example.jp/IN: loaded serial 2026111701dump zone to example.jp.raw...doneOK# named-compilezone -f raw -F text -o example.jp.txt example.jp slaves/db.example.jpzone example.jp/IN: loaded serial 2026111701dump zone to example.jp.txt...doneOK

-f が入力（from）、-F が出力の形式です。大文字と小文字を取り違えないようにします。

ゾーン転送とシリアル

ゾーン転送には、ゾーン全体を送る AXFR と、変わったところだけを送る IXFR があります。セカンダリは、プライマリのシリアルが自分の持つ写しより大きいときだけ転送します。

Docker の中でプライマリとセカンダリを動かしたときの、セカンダリのログです。

zone example.jp/IN: Transfer started.transfer of 'example.jp/IN' from 127.0.0.1#53: connected using 127.0.0.1#53 TSIG xfer-keyzone example.jp/IN: transferred serial 2026111701: TSIG 'xfer-key'transfer of 'example.jp/IN' from 127.0.0.1#53: Transfer status: success
注意試験の注意：シリアルを増やし忘れると、セカンダリに伝わらない

プライマリのゾーンファイルを書き換えても、シリアルを増やさなければ、セカンダリは「変わっていない」と判断して転送しません。「プライマリでは新しい答え、セカンダリでは古い答えが返る」という問題の原因は、まずこれです。シリアルを前より小さくしてしまったときも同じで、プライマリのログには zone serial (2026111700/2026111701) has gone backwards と出ます。

だれにでもゾーン転送を許すと、ゾーンの中のホストの一覧が外に漏れます。プライマリでは allow-transfer で相手をセカンダリだけに絞ります。

zone "example.jp" {    type master;    file "example.jp.zone";    allow-transfer { 192.168.10.2; };};

許されていない相手が転送を試すと、dig は ; Transfer failed. と表示します。

8.8named を root でなく、chroot の中で動かす

DNS サーバーは、インターネットのだれからでも問い合わせが届く場所に置きます。named に弱点が見つかって乗っ取られたときの被害を小さくするために、2 つの手を打ちます。

手named のオプション効き目
root でないユーザーで動かす-u ユーザー乗っ取られても、そのユーザーの権限しか使えない
chroot の中で動かす-t ディレクトリ乗っ取られても、そのディレクトリの外のファイルが見えない

named は 53 番ポート（1024 番より小さい特権ポート）を開くので、起動は root でします。-u を付けると、ポートを開いたあとで、そのユーザーに切り替わります。

ターミナル
# grep ExecStart /usr/lib/systemd/system/named.serviceExecStart=/usr/sbin/named -u named -c ${NAMEDCONF} $OPTIONS# cat /etc/default/namedOPTIONS="-u bind"# ps -eo user,args | grep '[n]amed'bind     named -u bind

1 つ目は Rocky Linux 9、2 つ目からは Debian 12 です。どちらも、入れたときから root でないユーザー（named、bind）で動きます。このユーザーが、ゾーンファイルを読め、セカンダリの保存先（slaves/ など）に書ける必要があります。

chroot は、プロセスにとっての / を付け替える仕組みでした（図解 Linux 19.2）。named -t /var/named/chroot で起動すると、named には /var/named/chroot が / に見えます。設定ファイルもゾーンファイルも、その中に置きます。

named から見たパス本当の場所
/etc/named.conf/var/named/chroot/etc/named.conf
/var/named/example.jp.zone/var/named/chroot/var/named/example.jp.zone

Red Hat 系では、bind-chroot パッケージを入れ、named.service の代わりに named-chroot.service を使います。chroot の先は /var/named/chroot です。

ターミナル
# grep ExecStart /usr/lib/systemd/system/named-chroot.serviceExecStart=/usr/sbin/named -u named -c ${NAMEDCONF} -t /var/named/chroot $OPTIONS
named のオプション意味
-u ユーザーそのユーザーに切り替えて動く
-t ディレクトリそのディレクトリに chroot する
-c ファイル設定ファイルを指定する
-fフォアグラウンドで動く（-g は、さらにログを標準エラー出力に出す）
-p ポート待ち受けるポートを変える
メモ-t は -u と一緒に使う

root のままのプロセスは、chroot から抜け出す手段を持っています。そのため、-t だけでは守りになりません。-u と -t を両方付けるのが決まりです。chroot した設定を調べるときは、named-checkconf -t /var/named/chroot のように、検査のコマンドにも -t を付けます。

知らせる情報を減らす

権威サーバーとして外に見せる台では、余計な仕事と情報を止めます。

options {    recursion no;    allow-transfer { none; };    version "unknown";};
  • recursion no;：再帰問い合わせに応じません。自分が持つゾーンの問い合わせには、これまでどおり答えます。だれの再帰問い合わせにも応じるサーバー（オープンリゾルバ）は、ほかの機械を攻撃する踏み台にされます
  • allow-transfer { none; };：ゾーン転送を、既定ではだれにも許しません（zone 文の中で、セカンダリにだけ許します）
  • version "…";：dig @サーバー version.bind chaos txt でバージョンを聞かれたときに、本当のバージョンの代わりにこの文字列を答えます
ターミナル
$ dig @127.0.0.1 version.bind chaos txt +short"unknown"

8.9forwarders で、内向きと外向きを分ける

forwarders は、自分が持っていない名前の問い合わせを、自分でルートからたどる代わりに、別のキャッシュサーバーへ回す設定です。回す先をフォワーダーと呼びます。

options {    directory "/var/named";    forwarders { 192.168.1.1; 8.8.8.8; };    forward only;    allow-query { 192.168.10.0/24; localhost; };};
設定意味
forwarders { アドレス; … };回す先のサーバー
forward first;（既定）まずフォワーダーに聞き、答えがもらえなければ自分でもルートからたどる
forward only;フォワーダーにだけ聞く。答えがもらえなければ、自分ではたどらずに失敗（SERVFAIL）を返す

Docker の中で、forward only のサーバーに、フォワーダーが答えられない名前を聞いた結果です。

ターミナル
$ dig -p 5353 @127.0.0.1 www.debian.org | grep -E 'status|flags';; ->>HEADER<<- opcode: QUERY, status: SERVFAIL, id: 9985;; flags: qr rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 1

forwarders を使うと、役目の違うサーバーに分けられます。これが分割構成（スプリット DNS）です。

  • 内向きサーバー：社内のゾーン（社内だけで使う名前）を持ち、社内のクライアントの再帰問い合わせに答える。それ以外の名前は、forward only でフォワーダーに回す。インターネットへ直接出ていくのはフォワーダーだけなので、ファイアウォールで通す通信を絞れる
  • 外向きサーバー：公開するゾーンだけを持つ権威サーバー。recursion no にして、社内の名前は持たせない

特定のゾーンだけを別のサーバーに回すには、type forward のゾーンを書きます。

zone "corp.example" {    type forward;    forward only;    forwarders { 10.0.0.53; };};
深掘り1 台で見せ分ける：view

1 台の named で、聞いてきた相手によって答えを変えることもできます。view 文を使います。

view "internal" {    match-clients { 192.168.10.0/24; };    recursion yes;    zone "example.jp" { type master; file "example.jp.internal"; };};view "external" {    match-clients { any; };    recursion no;    zone "example.jp" { type master; file "example.jp.external"; };};

match-clients に合った最初の view が使われます。view を 1 つでも使うなら、すべての zone 文を view の中に書く決まりです。外に書くと when using 'view' statements, all zones must be in views というエラーになります。

8.10TSIG：共有鍵で、ゾーン転送の相手を確かめる

allow-transfer { 192.168.10.2; }; のように IP アドレスで相手を絞る方法は、送信元を偽られると破られます。TSIG（Transaction SIGnature）は、2 台のサーバーが同じ秘密の鍵（共有鍵）を持ち、やり取りするメッセージにその鍵で作った署名（HMAC）を付ける仕組みです。受け取った側は、同じ鍵で署名を確かめます。

TSIG が守るのは、サーバーどうしのやり取り（ゾーン転送、NOTIFY、動的更新、rndc）です。相手が本物であることと、途中で書き換えられていないことを確かめます。中身の暗号化はしません。

鍵を作る

いまの BIND では、tsig-keygen で作ります。named.conf にそのまま書ける key 文が出ます。

ターミナル
# tsig-keygen -a hmac-sha256 xfer-keykey "xfer-key" {    algorithm hmac-sha256;    secret "r/hHwDH1Jkk7lGOMqxVrdShmTIKSUIm29dp4FyozA8Y=";};
メモ古い作り方：dnssec-keygen -a HMAC-…

以前の BIND では、TSIG の鍵も dnssec-keygen で作りました。dnssec-keygen -a HMAC-SHA256 -b 256 -n HOST xfer-key のように、アルゴリズムに HMAC-…、鍵の種類に -n HOST を指定し、できた K*.private の Key: の値を secret に写します。試験の範囲の用語も dnssec-keygen と TSIG が並んでいるので、この形を覚えておきます。ただし、Rocky Linux 9 の BIND 9.16 と Debian 12 の BIND 9.18 では、dnssec-keygen: fatal: unknown algorithm HMAC-SHA256 となって使えません。

named.conf に書く

同じ key 文を、プライマリとセカンダリの両方に書きます。鍵の名前も同じにします。

プライマリ：

key "xfer-key" {    algorithm hmac-sha256;    secret "r/hHwDH1Jkk7lGOMqxVrdShmTIKSUIm29dp4FyozA8Y=";}; zone "example.jp" {    type master;    file "example.jp.zone";    allow-transfer { key xfer-key; };};

セカンダリ：

key "xfer-key" {    algorithm hmac-sha256;    secret "r/hHwDH1Jkk7lGOMqxVrdShmTIKSUIm29dp4FyozA8Y=";}; server 192.168.10.1 {    keys { xfer-key; };}; zone "example.jp" {    type slave;    masters { 192.168.10.1; };    file "slaves/example.jp.zone";};
文意味
key "名前" { algorithm …; secret "…"; };鍵を定義する
allow-transfer { key 名前; };この鍵の署名が付いた要求にだけ、ゾーン転送を許す
server アドレス { keys { 名前; }; };このサーバーと話すときは、この鍵で署名を付ける

dig で確かめます。鍵がなければ断られ、-k で鍵のファイルを渡すと転送できます。

ターミナル
$ dig @127.0.0.1 example.jp AXFR; Transfer failed.$ dig @127.0.0.1 -k /etc/bind/xfer.key example.jp AXFRexample.jp.        3600    IN    SOA    ns1.example.jp. admin.example.jp. 2026111701 10800 3600 604800 900example.jp.        3600    IN    NS    ns1.example.jp.…xfer-key.        0    ANY    TSIG    hmac-sha256. 1794863946 300 32 KStt+0PkrY0RtXrXldPmaKo7lM+4FhxmrByOAidR+W0= 45518 NOERROR 0
注意試験の注意：TSIG の 3 つの決まり
  • 鍵は共有鍵（共通鍵）。公開鍵と秘密鍵の組ではない。だから secret を書いたファイルは、ほかのユーザーに読めないようにする
  • 署名には時刻が入っている。2 台の時計がずれている（既定で 300 秒を超える）と失敗するので、NTP で合わせておく
  • 鍵の名前、アルゴリズム、secret の 3 つが、両方のサーバーで同じでなければならない

8.11DNSSEC：ゾーンに署名して、答えが本物かを確かめる

ふつうの DNS の応答には、「本物の権威サーバーが出した答えか」を確かめる手段がありません。偽の答えをキャッシュサーバーに覚えさせる攻撃（キャッシュポイズニング）が成り立ちます。

DNSSEC（DNS Security Extensions）は、ゾーンのレコードに公開鍵暗号の署名を付けます（図解 LinuC 10.10 の署名と同じ考え方）。権威サーバーは秘密鍵で署名し、キャッシュサーバーは公開鍵で確かめます。守るのは答えの出どころと、書き換えられていないことで、通信の暗号化はしません。

レコード中身
DNSKEYゾーンの公開鍵。フラグ 256 が ZSK、257 が KSK
RRSIGレコードの署名
DS子のゾーンの KSK の要約（ハッシュ）。親のゾーンに登録する
NSEC / NSEC3「その名前はない」ことを証明するための、次の名前を指すレコード

鍵は 2 種類を使います。

鍵名前何に署名するか
ZSKZone Signing Key（ゾーン署名鍵）ゾーンの中の 1 つずつのレコード

手順 1：dnssec-keygen で鍵を作る

dnssec-keygen は、鍵の組（公開鍵と秘密鍵）を作ります。-a でアルゴリズム、-f KSK で KSK を指定します。

ターミナル

-a アルゴリズムRSASHA256、ECDSAP256SHA256、ED25519 など。いまの BIND（9.18 で確認）では省略できない

-K ディレクトリ鍵を置くディレクトリ

8.12DANE：サーバー証明書を DNS で確かめる

DANE（DNS-based Authentication of Named Entities）は、TLS で使うサーバー証明書の情報を、DNS のレコードとして公開する仕組みです。クライアントは、サーバーが出してきた証明書を、DNS から引いた情報と比べます。認証局（CA）だけに頼らずに、「このサーバーの正しい証明書はこれ」とドメインの持ち主が自分で言えます。

そのためのレコードが TLSA です。名前は _ポート番号._プロトコル.ホスト名 の形にします。

_443._tcp.www    IN    TLSA    3 1 1 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef_25._tcp.mail    IN    TLSA    3 1 1 …
ターミナル
$ dig @127.0.0.1 _443._tcp.www.example.jp TLSA +short3 1 1 0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF01234567 89ABCDEF

データは、3 つの数字とハッシュ値です。

順番名前値
1証明書の使い方（usage）0 = CA を指定（公的な CA の検証も必要）、1 = サーバー証明書を指定（公的な CA の検証も必要）、2 = 自前の CA を信頼の起点にする、3 = サーバー証明書そのものを指定（CA の検証は不要）
2セレクター0 = 証明書全体、1 = 公開鍵だけ
3照合の方法0 = そのまま、1 = SHA-256、2 = SHA-512
4データ上の方法で作った値（16 進）

3 1 1 は「サーバー証明書の公開鍵の SHA-256 ハッシュ」で、いちばんよく使われる組み合わせです。

注意試験の注意：DANE は DNSSEC が前提

TLSA レコードが偽物なら、偽の証明書を本物と思わせることができてしまいます。そのため、DANE は、TLSA レコードが DNSSEC で署名され、検証できることを前提にしています。「DANE = TLSA レコード = DNSSEC が必要」をひとまとめで覚えます。TSIG はサーバーどうしの共有鍵なので、DANE とは関係がありません。

同じ考え方で、SSH のホスト鍵の指紋を公開する SSHFP、OpenPGP の公開鍵を公開する OPENPGPKEY、S/MIME の証明書を公開する SMIMEA というレコードもあります。

要点まとめ
  • 権威サーバーはゾーンを持って答え、キャッシュサーバーは再帰問い合わせを受けてたどる。BIND（named）は両方、Unbound はキャッシュ専用、NSD は権威専用、dnsmasq は DNS + DHCP、PowerDNS はデータベースが使える
  • named.conf は Red Hat 系 /etc/named.conf（directory "/var/named"）、Debian 系 /etc/bind/named.conf。文は ; で終わる。file の相対パスは directory から
  • zone の type：master、slave（+ masters）、hint（ルートの一覧）、forward
  • named-checkconf は文法の検査（問題なければ無言）、-z でゾーンファイルも読む。named-checkzone ゾーン名 ファイル はゾーンファイルの検査、named-compilezone -f 入力 -F 出力 -o ファイル は text と raw の変換
  • rndc reload（全部）、reconfig（設定と新しいゾーンだけ）、flush（キャッシュを捨てる）、status、stop。TCP 953 番と共有鍵（rndc.key）
  • dig @サーバー 名前 種類、-x、+short、+norecurse、+trace、+dnssec、AXFR。フラグ aa は権威の答え、ra は再帰に応じる、ad は DNSSEC の検証済み。host -t、host -l、nslookup -type=
  • ゾーンファイル：$TTL、$ORIGIN、@ はオリジン、先頭が空白なら上と同じ名前、FQDN の最後には .
  • SOA は「プライマリの名前、管理者のメール（@ → .）、シリアル、リフレッシュ、リトライ、エクスパイア、ネガティブキャッシュの TTL」。シリアルを増やさないとセカンダリに伝わらない
  • MX は小さい数が先。NS と MX の右側は名前。CNAME の名前にほかのレコードは書けない。逆引きは 10.168.192.in-addr.arpa に PTR
  • named -u ユーザー -t ディレクトリ で、非 root + chroot。Red Hat 系は bind-chroot と /var/named/chroot
  • forwarders で回す先、forward only はフォワーダーだけ、forward first（既定）はだめなら自分でたどる。外向きの権威サーバーは recursion no、version で版を隠す
  • TSIG は共有鍵でサーバーどうしを認証。key 文を両方に、allow-transfer { key 名前; }; と server アドレス { keys { 名前; }; };。時計を合わせる
  • DNSSEC は公開鍵の署名。dnssec-keygen（-f KSK）→ K名前.+アルゴリズム+ID.key / .private、dnssec-signzone -o ゾーン → .signed と dsset-。DNSKEY、RRSIG、DS（親に登録）、NSEC
  • DANE は _443._tcp.www の TLSA レコードで証明書を公開する。DNSSEC が前提
