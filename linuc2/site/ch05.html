5.2ホスト型とハイパーバイザー型は、どこが違うのか

仮想マシンを作り、ハードウェアを分け与えるソフトウェアがハイパーバイザーです（図解 LinuC 1.5）。置き場所で 2 つの型に分かれます。

型置き場所例
ホスト型（タイプ 2）ホスト OS の上で、アプリケーションとして動くVirtualBox、VMware Workstation
ハイパーバイザー型（タイプ 1、ベアメタル型）ハードウェアのすぐ上で動く。間にホスト OS をはさまないXen、KVM、VMware ESXi、Hyper-V

ホスト型は、ふだんの PC に入れてすぐ使えます。ただし、ゲストの処理がホスト OS を通るので、その分だけ遅くなります。ハイパーバイザー型は、間の層が少ないので速く、サーバーで使われます。

Xen は、ハードウェアの上で Xen 本体が動き、その上に仮想マシン（Xen ではドメインと呼ぶ）が並びます。最初に起動する特別なドメインが Dom0（ドメインゼロ）で、装置のドライバとほかのドメインの管理を受け持ちます。ふつうのゲストは DomU です。

KVM（Kernel-based Virtual Machine）は、Linux カーネルのモジュールです。読み込むと、Linux カーネルそのものがハイパーバイザーになります。ホストでふつうの Linux が動いているように見えますが、ハードウェアのすぐ上で動くカーネルが仮想化を受け持つので、ハイパーバイザー型に分類します。

注意試験の注意：KVM はホスト型ではない

「Linux の上で動くから、KVM はホスト型」と考えると、まちがえます。出題範囲でも、KVM と Xen はハイパーバイザー型、VirtualBox はホスト型です。Docker はコンテナの道具で、どちらの型でもありません。

5.3KVM と QEMU は、何を分担しているのか

KVM だけでは、仮想マシンは動きません。KVM が受け持つのは CPU とメモリの仮想化だけです。ディスク、ネットワークカード、画面などの装置のまね（エミュレーション）は QEMU が受け持ちます。

部品動く場所役目
KVMカーネル（モジュール kvm と kvm_intel か kvm_amd）CPU の仮想化支援機能を使って、ゲストの命令を本物の CPU でそのまま実行する。窓口は /dev/kvm
QEMUユーザー空間（ゲスト 1 台につき 1 プロセス）ディスク、NIC、画面などの装置をエミュレートする。KVM がなければ CPU もソフトウェアでまねる
libvirt（libvirtd）ユーザー空間（デーモン）QEMU の起動と停止、設定の保存、ネットワークとストレージの管理

QEMU は、単体でも動きます。その場合は CPU の命令も 1 つずつソフトウェアでまねるので、遅くなります。代わりに、ホストと違う種類の CPU（x86 の上で ARM など）のゲストも動かせます。KVM と組み合わせると、ゲストの CPU の命令を本物の CPU で直接実行するので、速くなります。

ゲスト 1 台は、ホストから見ると QEMU のふつうのプロセス 1 つです。ps や top に出ますし、kill もできます（図解 Linux 7 章）。

5.4この機械で KVM は使えるか：vmx、svm、lscpu、モジュール

KVM を使うには、3 つの条件がそろっている必要があります。

  1. CPU に仮想化支援機能がある（Intel は Intel VT = vmx、AMD は AMD-V = svm）
  2. ファームウェア（UEFI / BIOS）の設定で、その機能が有効になっている
  3. カーネルに KVM のモジュールが読み込まれている（/dev/kvm がある）

CPU の印を見る：/proc/cpuinfo と lscpu

CPU の機能は、/proc/cpuinfo の flags の行に並びます。その中に vmx か svm があるかを grep で探します。小さな Linux で試します。

仮想化支援機能の印を探す（この CPU にはない）エラーになる⌘↵
grep flags /proc/cpuinfogrep -E 'vmx|svm' /proc/cpuinfo

小さな Linux の CPU には fpu しかないので、grep は何も出さずに終了ステータス 1 で終わりました。本物の Intel の機械なら、長い flags の行が CPU の数だけ表示され、その中に vmx が見つかります。

lscpu は、同じ情報を読みやすくまとめます。Intel の機械では、次の行が出ます（抜粋）。

ターミナル
$ lscpu | grep -i virtualVirtualization:                  VT-x
調べ方IntelAMD
/proc/cpuinfo の flagsvmxsvm
lscpu の Virtualization: の行VT-xAMD-V
読み込むモジュールkvm_intelkvm_amd

lscpu を仮想マシンの中で実行すると、Hypervisor vendor: KVM と Virtualization type: full の行が出ます。これは「自分が KVM の上の、完全仮想化のゲストである」という意味で、ホストの Virtualization: の行とは別のものです。

モジュールを見る：kvm、kvm_intel、kvm_amd

KVM のモジュールは 2 段になっています。共通の部分が kvm、CPU ごとの部分が kvm_intel（Intel）か kvm_amd（AMD）です。Intel の機械での例です。

ターミナル
# lsmod | grep kvmkvm_intel             380928  0kvm                  1146880  1 kvm_intel# ls -l /dev/kvmcrw-rw---- 1 root kvm 10, 232 Nov 17 09:00 /dev/kvm

読み込まれていなければ、modprobe で読み込みます。modprobe は依存するモジュールも一緒に読み込むので、kvm_intel を指定すれば kvm も入ります（図解 LinuC 5.2）。

ターミナル
# modprobe kvm_intel

モジュールの名前は、出題範囲では kvm-intel、kvm-amd とハイフンで書かれています。modprobe はハイフンと下線を区別しないので、modprobe kvm-intel でも同じです。lsmod の表示は下線（kvm_intel）になります。

モジュールが入ると、/dev/kvm というデバイスファイルができます。QEMU はこれを開いて KVM を使います。小さな Linux には、ありません。

/dev/kvm があるか（KVM が使えるホストにはある）エラーになる⌘↵
ls -l /dev/kvm
コツ切り分けの順番

仮想マシンが遅い、または起動しないときは、下から順に確かめます。

  1. grep -E 'vmx|svm' /proc/cpuinfo … 印がなければ、CPU が対応していないか、ファームウェアで無効
  2. lsmod | grep kvm … 何も出なければ、modprobe kvm_intel（または kvm_amd）
  3. ls -l /dev/kvm … なければ、QEMU は KVM を使えず、ソフトウェアのエミュレーションになる
  4. systemctl status libvirtd … libvirtd が動いていなければ、virsh はつながらない

5.5libvirtd と管理の道具は、どうつながるのか

QEMU を直接起動すると、長いオプションを毎回書くことになります。そこで、libvirt という管理の層を使うのがふつうです。libvirt のデーモンが libvirtd で、仮想マシンの設定を XML で保存し、QEMU を起動したり止めたりします。

libvirt は、KVM / QEMU だけのものではありません。Xen や LXC（コンテナ）なども、同じコマンドで扱えます。どれにつなぐかは、接続先の URI で決まります。

URI接続先
qemu:///systemホスト全体の KVM / QEMU（root として libvirtd につなぐ。サーバーではふつうこれ）
qemu:///session一般ユーザー自身の KVM / QEMU
xen:///systemXen
lxc:///systemLXC のコンテナ

libvirtd を起動しておきます。止まっていると、virsh は接続に失敗します。

ターミナル
# systemctl enable --now libvirtd# virsh -c qemu:///system listerror: failed to connect to the hypervisorerror: Failed to connect socket to '/var/run/libvirt/libvirt-sock': No such file or directory

下の 2 行は、libvirtd が動いていないときのエラーです。-c（--connect）で、接続先の URI を指定します。

libvirt を使う道具は 3 つ覚えます。どれも libvirtd に頼むだけで、自分では仮想マシンを動かしません。

道具種類役目
virt-managerGUI（仮想マシンマネージャー）仮想マシンの作成、起動、停止、設定の変更、画面の表示を、ウィンドウで行う。SSH 越しにリモートのホストも管理できる
virshコマンド起動、停止、設定の表示と変更など、ほぼすべての操作
virt-installコマンド仮想マシンを新しく作る（後の節）

libvirt が使うファイルの場所です（Debian 12 に libvirt を入れて確かめました）。

場所中身
/etc/libvirt/libvirt の設定（libvirtd.conf、qemu.conf など）
/etc/libvirt/qemu/仮想マシン（ドメイン）の定義。名前.xml が 1 台ぶん
/etc/libvirt/qemu/networks/仮想ネットワークの定義（default.xml）。autostart/ にリンクがあるものは自動で起動する
/var/lib/libvirt/images/ディスクイメージの既定の置き場所
/var/log/libvirt/qemu/仮想マシンごとのログ（名前.log）
注意試験の注意：XML を直接書き換えない

/etc/libvirt/qemu/名前.xml をエディタで直接書き換えても、libvirtd は気づきません。設定を変えるときは、virsh edit 名前（後の節）を使います。

パッケージの名前は、ディストリビューションで違います。Debian 系では qemu-system-x86、libvirt-daemon-system、libvirt-clients（virsh）、virtinst（virt-install）、virt-manager、bridge-utils です。Red Hat 系では qemu-kvm、libvirt、virt-install、virt-manager です。

5.6仮想マシンは、どうやって外のネットワークにつながるのか

仮想マシンの NIC は、ホストの上の仮想ブリッジにつながります。ブリッジは、ソフトウェアで作ったスイッチングハブです。つなぎ方は 2 つあります。

つなぎ方しくみ向いている場面
NAT（libvirt の default ネットワーク）libvirt が virbr0 というブリッジを作り、ゲストに 192.168.122.0/24 の番地を DHCP で配る。外へはホストが NAT するゲストから外へ出るだけでよいとき。外からゲストへは直接届かない
ブリッジ接続管理者が br0 などのブリッジを作り、ホストの物理 NIC を入れる。ゲストは LAN の番地を持つゲストをサーバーとして LAN に公開するとき

default ネットワークの定義です。virsh net-dumpxml default で表示できます。

ターミナル
# virsh net-dumpxml default<network>  <name>default</name>  <uuid>dd8fe884-6c02-601e-7551-cca97df1c5df</uuid>  <forward mode='nat'/>  <bridge name='virbr0' stp='on' delay='0'/>  <ip address='192.168.122.1' netmask='255.255.255.0'>    <dhcp>      <range start='192.168.122.2' end='192.168.122.254'/>    </dhcp>  </ip></network>

<forward mode='nat'/> が NAT、<bridge name='virbr0'/> がブリッジの名前、<dhcp> の range が配る番地の範囲です。

bridge-utils：brctl でブリッジを作る

ブリッジ接続のための br0 は、自分で作ります。古くからの道具が bridge-utils パッケージの brctl です。Debian 12 の中で、試しに作った NIC（dummy0）を入れてみた結果です。

ターミナル
# brctl addbr br0# brctl addif br0 dummy0# brctl showbridge name    bridge id        STP enabled    interfacesbr0        8000.fe4136efb2ae    no        dummy0# brctl delif br0 dummy0# brctl delbr br0
コマンド意味
brctl addbr br0ブリッジ br0 を作る
brctl delbr br0ブリッジ br0 を消す（先に停止しておく）
brctl addif br0 eth0eth0 を br0 につなぐ（ブリッジの口にする）
brctl delif br0 eth0eth0 を br0 から外す
brctl showブリッジと、つながっているインターフェースの一覧
brctl stp br0 onスパニングツリー（輪になった経路を止めるしくみ）を有効にする

brctl show の interfaces の列に、そのブリッジにつながっている口が並びます。ゲストを起動すると、vnet0、vnet1 … という口が増えます。これが、ゲストの NIC のホスト側の端です。

メモbrctl は古い道具

brctl のマニュアルには「obsolete（旧式）」とあり、今は iproute2 の ip link add br0 type bridge、ip link set eth0 master br0、bridge link で同じことができます。Red Hat 系の新しい版には bridge-utils のパッケージがありません。試験の範囲には bridge-utils が入っているので、brctl の 5 つの命令は覚えます。

5.7完全仮想化と準仮想化、virtio は何が違うのか

ゲスト OS にハードウェアをどう見せるかには、2 つの方式があります（図解 LinuC 1.5）。

方式ゲスト OS特徴
完全仮想化修正なしでそのまま動く本物と同じハードウェアに見せる。Windows などもそのまま入る。CPU の仮想化支援機能（vmx / svm）を使う。KVM はこの方式
準仮想化仮想環境用に修正したもの、または専用のドライバが要るゲストが「仮想環境にいる」と知っていて、ハイパーバイザーに直接頼む。まねの手間が減って速い。Xen が始めた

完全仮想化には弱点があります。装置のまねが遅いことです。QEMU が実在のネットワークカード（e1000、rtl8139）や IDE のディスクをまねると、ゲストがレジスタを 1 回さわるたびに QEMU へ処理が移ります。

そこで、CPU は完全仮想化のまま、装置だけ準仮想化するという組み合わせが使われます。そのための装置の規格が virtio（バーチオ）です。

virtio の装置ゲストのドライバゲストからの見え方
ディスク（virtio-blk）virtio_blk/dev/vda、/dev/vdb …（IDE や SATA のまねなら /dev/sda）
ネットワーク（virtio-net）virtio_netふつうの NIC（eth0、enp1s0 など）
メモリバルーンvirtio_balloon動作中にゲストのメモリを増減するしくみ

virtio を使うには、ゲスト OS に virtio のドライバが必要です。Linux のカーネルには初めから入っています。Windows には入っていないので、別にドライバを入れます。

注意試験の注意：virtio は「準仮想化」の側
  • virtio は、準仮想化のドライバ（装置）の規格。CPU の仮想化支援機能の代わりにはならない
  • virtio のディスクは /dev/vda。/dev/sda ではない
  • 完全仮想化は「ゲスト OS を修正しない」、準仮想化は「ゲスト OS を修正する（専用のドライバを使う）」

5.8virt-install で仮想マシンを作るには

仮想マシンを作る道具は 2 つあります。GUI の virt-manager は、「新しい仮想マシン」のウィザードで、インストール元、メモリと CPU、ディスクを順に聞いてきます。コマンドの virt-install は、同じことをオプションで指定します。

ターミナル
# virt-install \    --name web01 \    --memory 2048 \    --vcpus 2 \    --disk path=/var/lib/libvirt/images/web01.qcow2,size=10,format=qcow2,bus=virtio \    --cdrom /var/lib/libvirt/images/debian-12.iso \    --os-variant debian11 \    --network bridge=br0,model=virtio \    --graphics vnc

これで、定義（XML）とディスクイメージが作られ、仮想マシンが起動して、ISO からインストーラが始まります。

基本のオプション

オプション意味
--name 名前（-n）仮想マシンの名前
--memory 2048メモリ。単位は MiB（古い書き方は --ram）
--vcpus 2仮想 CPU の数
--disk …ディスク。size=10 は GiB。path= で場所、format= で形式（qcow2、raw）、bus=virtio でつなぎ方
--network …（-w）NIC。bridge=br0（ホストのブリッジ）か network=default（libvirt の仮想ネットワーク）。model=virtio で種類
--graphics …画面。vnc、spice、none（画面なし。テキストのコンソールを使う）
--os-variant 名前（--osinfo）ゲスト OS の種類。virtio を使うかなど、最適な既定値を選ぶのに使われる。一覧は virt-install --osinfo list
--connect URI接続先（例 qemu:///system）

--disk size=10 とだけ書くと、既定の場所（/var/lib/libvirt/images/）に、qcow2 形式の 10 GiB のイメージが作られます。--network を省くと、物理 NIC の入ったブリッジがあればそれに、なければ default ネットワークにつながります。

ディスクイメージの形式は 2 つ覚えます。raw は中身をそのまま並べた形式で、単純で速い代わりに機能がありません。qcow2 は QEMU の形式で、使った分だけファイルが大きくなり、スナップショットが取れます。

インストール元のオプション

インストールの方法は、次のどれかを必ず指定します。指定しないと、An install method must be specified というエラーになります。

オプションインストール元
--cdrom ISO ファイルCD / DVD のイメージ（ISO）から起動する
--location URL（-l）ネットワーク上（または ISO の中）のインストール用のツリー。カーネルと initrd を取ってきて起動する
--pxeネットワークブート（PXE）
--importインストールしない。すでに OS が入っているディスクイメージから、そのまま起動する

カーネルに引数を渡す --extra-args（-x）は、--location のときだけ使えます。画面なしでインストールするときは、次のように組み合わせます。

ターミナル
# virt-install --name web02 --memory 1024 --disk size=8 \    --location http://deb.debian.org/debian/dists/bookworm/main/installer-amd64/ \    --os-variant debian11 --graphics none --extra-args 'console=ttyS0'

仮想化の種類と、そのほかのオプション

オプション意味
--hvm（-v）完全仮想化のゲストにする（QEMU / KVM ではこれが既定）
--paravirt（-p）準仮想化のゲストにする（Xen で使う）
--virt-type kvm使うハイパーバイザー（kvm、qemu、xen）。qemu は KVM を使わないエミュレーション
--autostartホストの起動時に、自動で起動する
--noautoconsole作成のあと、ゲストのコンソールに自動でつながない
--dry-run手順を最後までたどるが、ディスクも定義も作らない
--print-xml仮想マシンを定義する代わりに、作られる XML を表示する

--dry-run と --print-xml を付けて実行すると、ドメインの XML が見えます（抜粋。練習用の接続で試したので type は test ですが、KVM では <domain type='kvm'> になります）。

ターミナル
# virt-install --name web01 --memory 2048 --vcpus 2 \    --disk path=/tmp/web01.qcow2,size=10,format=qcow2,bus=virtio --cdrom /tmp/x.iso \    --os-variant debian11 --network bridge=br0,model=virtio --graphics vnc --dry-run --print-xml<domain type="test">  <name>web01</name>  <memory>2097152</memory>  <vcpu>2</vcpu>  <os>    <type arch="i686">hvm</type>  </os>  <devices>    <disk type="file" device="disk">      <source file="/tmp/web01.qcow2"/>      <target dev="vda" bus="virtio"/>    </disk>    <interface type="bridge">      <source bridge="br0"/>      <model type="virtio"/>    </interface>    <graphics type="vnc" port="-1"/>  </devices></domain>

読み方です。<memory> は KiB（2048 MiB = 2097152 KiB）、<type>hvm</type> は完全仮想化、<target dev="vda" bus="virtio"/> は virtio のディスク、<interface type="bridge"> と <source bridge="br0"/> は br0 へのブリッジ接続です。

注意試験の注意：virt-install の単位と必須のもの
  • --memory は MiB、--disk size= は GiB
  • インストール元（--cdrom、--location、--pxe、--import のどれか）がないと作れない
  • 既存のイメージを使うのは --import。--cdrom はインストーラを起動する
  • --extra-args は --location と組み合わせる。--cdrom とは使えない

5.9virsh で仮想マシンの状態を変えるには

libvirt では、仮想マシンをドメインと呼びます。レベル1 で学んだコマンド（図解 LinuC 1.6）を、状態の図で整理します。

練習用の接続で、順に実行した結果です。

ターミナル
# virsh list --all Id   Name   State----------------------- -    test   shut off # virsh define /tmp/d.xmlDomain 'web01' defined from /tmp/d.xml # virsh start web01Domain 'web01' started # virsh suspend web01Domain 'web01' suspended # virsh list Id   Name    State---------------------- 3    web01   paused # virsh resume web01Domain 'web01' resumed # virsh autostart web01Domain 'web01' marked as autostarted # virsh destroy web01Domain 'web01' destroyed # virsh list --all Id   Name    State------------------------ -    test    shut off -    web01   shut off

virsh list は動いているもの（running と paused）だけを出します。止まっているものも見るには --all を付けます。止まっているドメインの Id は - です。

コマンド意味
virsh list [--all]ドメインの一覧（--all で停止中も）
virsh define ファイル.xmlXML から登録する。起動はしない
virsh undefine 名前登録を消す。ディスクイメージは消えない（消すには --remove-all-storage）
virsh create ファイル.xmlXML から登録せずに起動する。止めると跡が残らない（一時的なドメイン）
virsh start 名前定義済みのドメインを起動する
virsh shutdown 名前ゲスト OS に頼んで、正しい手順で止める。ゲストが応じなければ止まらない
virsh destroy 名前強制停止。電源コードを抜くのと同じ。定義もディスクも消えない
virsh reboot 名前ゲスト OS に頼んで再起動する
virsh reset 名前リセットボタンを押すのと同じ（強制の再起動）
virsh suspend 名前 / resume 名前一時停止する（メモリに載ったまま CPU を止める）/ 再開する
virsh save 名前 ファイル / restore ファイルメモリの中身をファイルに保存して止める / そこから再開する
virsh autostart 名前ホストの起動時（libvirtd の起動時）に自動で起動する。やめるには --disable
注意試験の注意：名前にだまされない
  • destroy は消さない。強制停止するだけで、start でまた起動できる。登録を消すのは undefine
  • create は「作って登録」ではない。登録せずに起動する。登録は define
  • 一時停止からの再開は resume。start は shut off のドメインに使う
  • shutdown はゲストの協力が要る（ACPI の電源ボタンの信号をゲストが処理する）。止まらないときに destroy
深掘り動いているドメインを undefine すると

動作中のドメインに virsh undefine を実行しても、ドメインは止まりません。定義だけが消えて、一時的なドメインに変わります。virsh dominfo の Persistent: が yes から no になり、次に止まったときに一覧から消えます。練習用の接続で確かめた結果です。

ターミナル
# virsh undefine web01Domain 'web01' has been undefined # virsh list --all Id   Name    State------------------------ 5    web01   running -    test    shut off # virsh destroy web01Domain 'web01' destroyed # virsh list --all Id   Name   State----------------------- -    test   shut off

5.10virsh で設定を見る・変えるには

情報を見る

ターミナル
# virsh dominfo web01Id:             3Name:           web01UUID:           d297956f-b307-4c9f-aa4a-b77c3ddc3a43OS Type:        linuxState:          runningCPU(s):         2Max memory:     2097152 KiBUsed memory:    1048576 KiBPersistent:     yesAutostart:      disable
コマンド表示するもの
virsh dominfo 名前状態、CPU の数、メモリ、自動起動かどうかの要約
virsh domstate 名前状態だけ（running、paused、shut off）
virsh dumpxml 名前設定の XML 全体を標準出力に出す。> ファイル で保存すれば、define で別のホストに登録できる
virsh domblklist 名前ディスクの一覧（vda とイメージのパス）
virsh domiflist 名前NIC の一覧（vnet0、つなぎ先、MAC アドレス）
virsh vncdisplay 名前VNC の画面の番号（:0 なら 5900 番ポート）
virsh nodeinfoホストの CPU とメモリ

設定を変える

virsh edit 名前 は、ドメインの XML をエディタ（$VISUAL か $EDITOR。なければ vi）で開きます。保存して閉じると、内容を検査して登録し直します。変えた内容が効くのは、次に起動したときです。

CPU の数とメモリは、専用のコマンドでも変えられます。

ターミナル
# virsh setvcpus web01 2 --config# virsh setmem web01 1G --live
オプション変える対象
--config保存されている設定。次の起動から効く
--live動作中のドメイン。すぐに効く（止めると元に戻る）
--config --live両方

setvcpus と setmem で指定できるのは、XML の最大値（<vcpu>、<memory>）までです。最大値そのものを変えるには、virsh setvcpus 名前 数 --maximum --config や virsh setmaxmem を使い、ドメインを起動し直します。

コンソールにつなぐ

virsh console 名前 は、ゲストのシリアルコンソールにつなぎます。SSH が使えないときや、--graphics none で作ったときに使います。抜けるには Ctrl + ] を押します（exit はゲストからログアウトするだけです）。

スナップショット

ある時点の状態を取っておき、あとで戻せます（ディスクが qcow2 のとき）。

ターミナル
# virsh snapshot-create-as web01 snap1Domain snapshot snap1 created# virsh snapshot-list web01 Name    Creation Time               State---------------------------------------------- snap1   2026-11-16 21:21:46 +0000   running # virsh snapshot-revert web01 snap1Domain snapshot snap1 reverted# virsh snapshot-delete web01 snap1Domain snapshot snap1 deleted

ネットワークとストレージ

仮想ネットワークも、ドメインと同じ形のコマンドで扱います。頭に net- が付きます。

ターミナル
# virsh net-list --all Name      State      Autostart   Persistent---------------------------------------------- default   inactive   yes         yes # virsh net-start defaultNetwork default started
コマンド意味
virsh net-list [--all]仮想ネットワークの一覧
virsh net-start 名前 / net-destroy 名前開始する / 停止する（定義は残る）
virsh net-autostart 名前自動で開始するようにする
virsh net-dumpxml 名前 / net-edit 名前定義の XML を表示する / 編集する
virsh pool-list [--all]ストレージプール（ディスクイメージの置き場所）の一覧
virsh vol-list プールプールの中のボリューム（イメージ）の一覧

ゲストが default ネットワークにつながらないときは、まず virsh net-list --all で State が active かを見ます。inactive なら net-start で開始し、net-autostart で次からは自動にします。

要点まとめ
  • 型：ホスト型は VirtualBox。ハイパーバイザー型は Xen と KVM。Xen の管理用のドメインは Dom0
  • KVM はカーネルモジュール（kvm + kvm_intel / kvm_amd）で、CPU を仮想化する。QEMU は装置をエミュレートする。QEMU は単体でも動くが遅い。窓口は /dev/kvm
  • CPU の印は Intel が vmx、AMD が svm。grep -E 'vmx|svm' /proc/cpuinfo か lscpu の Virtualization: で確かめる
  • libvirtd が管理のデーモン。virt-manager（GUI）、virsh、virt-install はその利用者。定義は /etc/libvirt/qemu/名前.xml、イメージは /var/lib/libvirt/images/
  • ネットワーク：default は virbr0、192.168.122.0/24、NAT。LAN に直接つなぐならブリッジ。brctl addbr、addif、delif、delbr、show
  • 完全仮想化はゲスト OS を修正しない。準仮想化は修正する（専用ドライバ）。virtio は準仮想化の装置で、ディスクは /dev/vda
  • virt-install：--memory（MiB）、--disk size=（GiB）、--cdrom / --location / --pxe / --import、--network bridge=…,model=virtio、--graphics、--os-variant、--extra-args は --location と
  • virsh：define（登録）と create（登録せず起動）、shutdown（頼む）と destroy（強制。消さない）、undefine（登録を消す）、suspend / resume、autostart
  • virsh dumpxml（XML を表示）、edit（編集。次の起動から）、setvcpus / setmem の --config（次から）と --live（今すぐ）、console は Ctrl + ] で抜ける
