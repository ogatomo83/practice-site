9.13 つのサーバーは、どこに立つか

HTTP は、クライアントが要求（リクエスト）を 1 つ送り、サーバーが応答（レスポンス）を 1 つ返す、文字の会話でした（図解 Linux 16.8）。この章の 3 つのソフトウェアは、その会話のどこに立つかが違います。

9.2Apache の設定ファイルは、どこにあり、どう読まれるか

Apache HTTP サーバー（以下 Apache）は、プログラムの名前がディストリビューションで違います。Red Hat 系は httpd、Debian 系は apache2 です。設定ファイルの名前と場所も、それに合わせて違います。

Red Hat 系Debian 系

動かす利用者apachewww-data

Debian 系の *-available/ は「置いてあるだけ」、*-enabled/ は「有効」です。有効にするとは、*-enabled/ にシンボリックリンク（図解 Linux 11.4）を作ることです。a2ensite などのコマンドが、そのリンクを作ったり消したりします。

設定の 1 行をディレクティブ（指示）と呼びます。「名前 値」の形です。rockylinux:9 の httpd.conf から、コメントを除いた主な行です。

conf

囲み効く範囲

設定を変えたら、構文の検査 → 読み込み直しの順で反映します。管理コマンドは apachectl（Debian 系は apache2ctl）です。

ターミナル

メモapachectl はディストリビューションで少し違う

Apache 本家と Debian 系の apachectl（apache2ctl）は、知らない引数を httpd にそのまま渡します（apache2ctl -S、apache2ctl -M が使えます）。Red Hat 系の apachectl は systemctl を呼ぶ小さなスクリプトで、start、stop、restart、graceful、graceful-stop、configtest、status などに限られます。rockylinux:9 で apachectl -S は「The "-S" option is not supported.」でした。Red Hat 系では httpd -S を使います。systemd のもとでは、起動と停止は systemctl start httpd（Debian 系は apache2）でも行います。

アクセスログとエラーログ

アクセスログは、リクエスト 1 つにつき 1 行です。書式は LogFormat で名前を付け、CustomLog で選びます。

127.0.0.1 - alice [16/Nov/2026:21:19:39 +0000] "GET /ht/ HTTP/1.1" 401 381 "-" "curl/7.76.1"127.0.0.1 - - [16/Nov/2026:21:19:39 +0000] "GET /nothing HTTP/1.1" 404 196 "-" "curl/7.76.1"
書式の文字意味上の 1 行目
%hクライアントの番地（ホスト）127.0.0.1

common は %b までの 7 つ、combined はそれに Referer と User-Agent を足した書式です。

エラーログには、時刻、[モジュール:重さ]、プロセス、クライアント、メッセージが並びます。うまく動かないときは、まずここを見ます。

LogLevel の重さは、syslog と同じ並びです（図解 LinuC 9.3）。emerg、alert、crit、error、warn、notice、info、debug の順に軽くなり、指定した重さ以上が記録されます。

9.3アクセス制御と Basic 認証：Require、htpasswd、.htaccess

Apache が「このリクエストを通すか」を決める仕組みは、2 つに分かれます。

  • 認証（authentication）：相手が誰かを確かめる。モジュール名は mod_auth… と mod_authn_…
  • 認可（authorization）：その相手を通してよいかを決める。モジュール名は mod_authz_…
モジュール受け持つもの
mod_auth_basicBasic 認証（AuthType Basic）
mod_authn_fileパスワードファイルで確かめる（AuthUserFile）
mod_authz_coreRequire と <RequireAll> などの土台
mod_authz_host番地やホスト名で決める（Require ip、Require host、Require local）
mod_authz_user利用者で決める（Require user、Require valid-user）
mod_authz_groupfileグループで決める（AuthGroupFile、Require group）

Require：誰を通すか（Apache 2.4）

Apache 2.4 では、通す条件を Require で書きます。

書き方通す相手
Require all granted全員
Require all denied誰も通さない
Require ip 192.168.1.0/24その番地（ネットワーク）から来たもの
Require host example.com逆引きした名前が example.com で終わるもの
Require local同じ機械から来たもの（127.0.0.0/8、::1）
Require valid-user認証に成功した利用者すべて
Require user alice bob認証に成功した alice か bob
Require group staff認証に成功し、グループ staff に入っている利用者

Require を何行か並べると、どれか 1 つに合えば通ります（<RequireAny> と同じ）。すべてに合うことを求めるときは <RequireAll> で囲みます。Require not ip … のような否定は、<RequireAll> の中でだけ書けます。

conf
<Directory "/var/www/shop">    <RequireAll>        Require all granted        Require not ip 10.0.0.5    </RequireAll></Directory>

Apache 2.2 までは、Order、Allow、Deny で書きました。2.4 でも互換モジュール（mod_access_compat）で動きます。古い設定を読む問題のために、形を覚えておきます。

2.2 の書き方意味2.4 の書き方
Order allow,deny と Allow from all全員を通すRequire all granted
Order deny,allow と Deny from all誰も通さないRequire all denied
Order deny,allow と Deny from all と Allow from 192.168.1.0/24192.168.1.0/24 だけ通すRequire ip 192.168.1.0/24

Order deny,allow は「Deny を先に、Allow を後に調べ、後のものが勝つ。どちらにも合わなければ通す」です。Order allow,deny はその逆で、Deny が勝ち、どちらにも合わなければ拒否します。

Basic 認証を付ける

Basic 認証は、ディレクトリに名前とパスワードを求める、いちばん単純な認証です。4 つのディレクティブで書きます。

conf
<Directory "/var/www/html/secret">    AuthType Basic    AuthName "Members Only"    AuthUserFile /etc/httpd/.htpasswd    Require valid-user</Directory>
ディレクティブ意味
AuthType認証の方式。Basic か Digest
AuthName認証の領域の名前（realm）。ブラウザの入力の窓に出る
AuthUserFile利用者とパスワードのファイル（htpasswd で作る）
AuthGroupFileグループと利用者の対応を書いたファイル
Require通す利用者（valid-user、user 名前、group 名前）

パスワードのファイルは htpasswd で作ります。

ターミナル
# htpasswd -c /etc/httpd/.htpasswd aliceNew password:Re-type new password:Adding password for user alice# htpasswd /etc/httpd/.htpasswd bob# cat /etc/httpd/.htpasswdalice:$apr1$3rGCgc3u$IV89bSOTtduEn.R1a8DuZ/bob:$apr1$QGUwsJLD$XfS898UbAxjvhfXklBNdD.# htpasswd -D /etc/httpd/.htpasswd bobDeleting password for user bob
htpasswd のオプションすること
-cファイルを新しく作る。すでにあるファイルは上書きされ、ほかの利用者は消える
-bパスワードをコマンドラインの引数で渡す（htpasswd -b ファイル 名前 パスワード）
-nファイルを書き換えず、結果を標準出力に表示する
-D利用者を削除する
-mMD5 でハッシュにする（既定。$apr1$ で始まる）
-Bbcrypt でハッシュにする（$2y$ で始まる。より安全）
-s / -d / -pSHA-1 / crypt / 平文（どれも安全ではない）
-v利用者のパスワードが合っているかを確かめる

ファイルは「名前:ハッシュ」が 1 行に 1 人です。2 人目からは -c を付けません。

グループで許可するときは、AuthGroupFile に「グループ名: 利用者 利用者 …」を書いたファイルを指定します。

conf
# /etc/httpd/.htgroup の中身staff: alice carol # 設定<Directory "/var/www/html/staff">    AuthType Basic    AuthName "Staff"    AuthUserFile /etc/httpd/.htpasswd    AuthGroupFile /etc/httpd/.htgroup    Require group staff</Directory>

この設定で試すと、alice は 200、staff に入っていない bob は 401 でした。パスワードが合っていても、認可で落ちます。

注意試験の注意：Basic 認証と htpasswd
  • htpasswd -c は新規作成です。2 人目に -c を付けると、1 人目が消えます
  • Basic 認証は、名前とパスワードを Base64 にするだけで送ります。暗号ではないので、盗み見を防ぐには HTTPS と組み合わせます。Digest 認証（AuthType Digest、ファイルは htdigest で作る）は、パスワードそのものを送りません
  • パスワードファイルは、DocumentRoot の外に置きます。中に置くと、ブラウザから取られるおそれがあります

.htaccess：ディレクトリごとに設定を上書きする

.htaccess は、公開するディレクトリの中に置く設定ファイルです。主設定ファイルを触れない利用者が、自分のディレクトリだけ設定を変えられます。ファイルの名前は AccessFileName で決まり、既定が .htaccess です。

conf
# /var/www/html/ht/.htaccessAuthType BasicAuthName "ht"AuthUserFile /etc/httpd/.htpasswdRequire user bob

.htaccess に何を書いてよいかは、主設定ファイルの <Directory> の中の AllowOverride で決まります。

AllowOverride の値.htaccess に書けるもの
None何も書けない。.htaccess は読まれない（2.4 の既定）
All.htaccess に書けるディレクティブすべて
AuthConfig認証（AuthType、AuthName、AuthUserFile、Require など）
Limit番地によるアクセス制御（Order、Allow、Deny）
FileInfo文書の種類や転送（Redirect、ErrorDocument、RewriteRule など）
Indexesディレクトリの一覧（DirectoryIndex など）
OptionsOptions ディレクティブ

上の .htaccess を、AllowOverride を変えながら試した結果です。

主設定ファイルの設定/ht/ へのリクエスト（認証なし）
AllowOverride None200（.htaccess は無視され、認証なしで見える）
AllowOverride Limit500（エラーログに AuthType not allowed here）
AllowOverride AuthConfig401（認証を求められる）

.htaccess はリクエストのたびに読まれるので、書き換えたあとに Apache を読み込み直す必要はありません。その代わり、遅くなります。主設定ファイルを触れるなら、<Directory> に書くほうが速く安全です。.ht で始まるファイルは、既定の設定（<Files ".ht*"> Require all denied）でブラウザから取れないようになっています。

9.4バーチャルホスト、Redirect、プロセス数の調整

バーチャルホスト：1 台で何個ものサイトを出す

バーチャルホストは、1 つの Apache で複数のサイトを出す仕組みです。2 種類あります。

種類何で振り分けるか書き方
名前ベースリクエストの Host ヘッダー（ホスト名）。番地は 1 つでよい<VirtualHost *:80> と ServerName
IP ベース届いた先の IP アドレス。サイトの数だけ番地が要る<VirtualHost 192.168.1.10:80>
conf
<VirtualHost *:80>    ServerName www.example.com    DocumentRoot /var/www/html</VirtualHost> <VirtualHost *:80>    ServerName shop.example.com    ServerAlias shop    DocumentRoot /var/www/shop    CustomLog logs/shop_access_log combined    ErrorLog logs/shop_error_log</VirtualHost>

ServerName がそのサイトの名前、ServerAlias は別名です。DocumentRoot、CustomLog、ErrorLog は、バーチャルホストごとに書けます。解釈した結果は httpd -S（Debian 系は apache2ctl -S）で確かめます。

ターミナル
# httpd -SVirtualHost configuration:*:80                   is a NameVirtualHost         default server www.example.com (/etc/httpd/conf.d/test.conf:2)         port 80 namevhost www.example.com (/etc/httpd/conf.d/test.conf:2)         port 80 namevhost shop.example.com (/etc/httpd/conf.d/test.conf:27)                 alias shop         port 80 namevhost blog.example.com (/etc/httpd/conf.d/test.conf:37)

default server の行に注目します。Host ヘッダーがどの ServerName にも ServerAlias にも合わないリクエストは、設定ファイルで最初に書いたバーチャルホストが受けます。上の設定で Host: unknown.example.com を送ると、www.example.com の中身が返りました。

注意試験の注意：NameVirtualHost

Apache 2.2 までは、名前ベースのバーチャルホストを使うために NameVirtualHost *:80 の行が必要でした。2.4 では不要で、書くと「NameVirtualHost has no effect」という警告が出ます。同じ番地とポートの <VirtualHost> が 2 つ以上あれば、自動的に名前ベースになります。

Redirect：別の URL へ行かせる

Redirect（mod_alias）は、ある URL パスへのリクエストに「別の URL へ行ってください」と答えさせます。

conf
Redirect /old http://www.example.com/newRedirect permanent /old2 http://www.example.com/new2Redirect seeother /old3 http://www.example.com/new3Redirect gone /goneRedirectMatch ^/docs/(.*)$ http://docs.example.com/$1

MPM とプロセス数：何人まで同時に相手をするか

Apache は、親プロセス（root）が子プロセスを作り、子プロセス（apache や www-data）がリクエストを処理します。その作り方を決める部品が MPM（Multi-Processing Module）です。

MPM仕組み特徴
prefork1 つの子プロセスが 1 つの接続を受け持つ。スレッドは使わないスレッドに対応していないモジュールでも安全。メモリを多く使う
worker1 つの子プロセスの中の複数のスレッドが、1 つずつ接続を受け持つ少ないメモリで多くの接続をさばける
eventworker と同じ。Keep-Alive で待っているだけの接続を、専用のスレッドにまとめるいまの既定（rockylinux:9、debian:12 とも event）

いま使っている MPM は httpd -V の Server MPM: の行でわかります。プロセスとスレッドの数は、次のディレクティブで決めます。debian:12 の既定の値です。

conf
# mpm_prefork.conf                 # mpm_event.confStartServers            5          StartServers            2MinSpareServers         5          MinSpareThreads         25MaxSpareServers         10         MaxSpareThreads         75MaxRequestWorkers       150        ThreadsPerChild         25MaxConnectionsPerChild  0          MaxRequestWorkers       150                                   MaxConnectionsPerChild  0
ディレクティブ意味使う MPM
StartServers起動したときに作る子プロセスの数すべて
MinSpareServers待機している（暇な）子プロセスの最小の数。下回ると増やすprefork
MaxSpareServers待機している子プロセスの最大の数。上回ると減らすprefork
MinSpareThreads / MaxSpareThreads待機しているスレッドの最小 / 最大の数worker、event
ThreadsPerChild1 つの子プロセスが作るスレッドの数worker、event
MaxRequestWorkers同時に処理できるリクエストの最大の数。超えたぶんは待たされる。prefork では子プロセスの最大の数すべて
ServerLimit子プロセスの数の上限。MaxRequestWorkers をこれより大きくはできないすべて
MaxConnectionsPerChild1 つの子プロセスが、この数の接続を処理したら終了して作り直す。0 は無制限すべて

Apache 2.2 までの名前も問われます。MaxClients は MaxRequestWorkers の古い名前、MaxRequestsPerChild は MaxConnectionsPerChild の古い名前です（2.4 でも古い名前で書けます。httpd -L に「Deprecated name of MaxRequestWorkers」と出ます）。

MaxConnectionsPerChild を 0 以外にすると、長く動いた子プロセスが作り直されます。プログラムのメモリリーク（使ったメモリを返し忘れる不具合）があっても、メモリが増え続けるのを防げます。

接続を使い回す Keep-Alive の設定も、同時に相手をできる数に関係します。

ディレクティブ意味
KeepAlive On1 つの接続で複数のリクエストを受ける
MaxKeepAliveRequests 1001 つの接続で受けるリクエストの最大の数
KeepAliveTimeout 5次のリクエストを待つ秒数。長いと、待っているだけの接続がワーカーを占める
Timeout送受信が止まったときに待つ秒数
コツMaxRequestWorkers の決め方

prefork では、MaxRequestWorkers × 子プロセス 1 つのメモリが、機械のメモリを超えないようにします。超えるとスワップが始まり、急に遅くなります。prefork で 256 より大きくするときは、ServerLimit も一緒に上げます。

9.5証明書は、誰が何を証明するか：鍵、CSR、CA

HTTPS は、HTTP の会話を TLS（Transport Layer Security。古い名前は SSL）で包んだものです。ポートは 443 です。TLS は 2 つのことをします。通信の暗号化と、相手が本物のサーバーかの確認です。確認に使うのがサーバー証明書です。

公開鍵と秘密鍵の組は、SSH の鍵で見ました（図解 LinuC 10.8）。証明書に関わるファイルは 3 つです。

ファイル中身扱い
秘密鍵（server.key）サーバーだけが持つ鍵誰にも渡さない。root だけが読めるようにする（600）
CSR（server.csr）証明書署名要求（Certificate Signing Request）。公開鍵と、サーバーの名前（識別名）を入れ、自分の秘密鍵で署名したものCA に送る。秘密鍵は入っていない
証明書（server.crt）公開鍵と名前に、CA が署名したもの。有効期限がある公開してよい。クライアントに送られる

認証局（CA、Certificate Authority）は、申請者を確かめて、証明書に署名する組織です。ブラウザや OS は、信頼する CA の証明書（ルート証明書）を初めから持っています。CA の署名をたどれれば、そのサーバーを本物とみなします。

自己署名証明書は、CA の代わりに自分の秘密鍵で署名した証明書です。発行者（issuer）と持ち主（subject）が同じになります。暗号化はできますが、誰も本物だと保証していないので、ブラウザは警告を出します。試験や社内の検証に使います。

openssl コマンドで作る

openssl は、鍵や証明書を扱うコマンドです。openssl サブコマンド オプション の形で使います。

ターミナル

注意試験の注意：パスフレーズ付きの秘密鍵

秘密鍵をパスフレーズで暗号化すると、Apache は起動のたびにパスフレーズを聞きます。自動で起動できなくなるので、サーバーではパスフレーズなしの鍵（-nodes）にして、ファイルの許可（600、root）で守るのがふつうです。付いているパスフレーズは openssl rsa -in server.key -out server.key.nopass で外せます。

9.6Apache で HTTPS を有効にする：mod_ssl のディレクティブ

Apache の HTTPS は mod_ssl が受け持ちます。Red Hat 系は mod_ssl パッケージを入れると /etc/httpd/conf.d/ssl.conf が置かれます。Debian 系は a2enmod ssl と a2ensite default-ssl で有効にします。

conf
Listen 443 https <VirtualHost *:443>    ServerName www.example.com    DocumentRoot /var/www/html     SSLEngine on    SSLCertificateFile      /etc/pki/tls/certs/server.crt    SSLCertificateKeyFile   /etc/pki/tls/private/server.key     SSLProtocol             all -SSLv3 -TLSv1 -TLSv1.1    SSLCipherSuite          HIGH:!aNULL:!MD5    SSLHonorCipherOrder     on</VirtualHost>
ディレクティブ意味
SSLEngine onこのバーチャルホストで SSL/TLS を使う
SSLCertificateFileサーバー証明書のファイル（PEM）。2.4.8 以降は、後ろに中間 CA の証明書を続けて書ける
SSLCertificateKeyFileサーバーの秘密鍵のファイル
SSLCertificateChainFile中間 CA の証明書のファイル（2.4.8 より前の書き方。いまは非推奨）

中間 CA は、ルート CA に署名してもらい、サーバー証明書に署名する CA です。ブラウザはルート CA の証明書しか持っていないので、サーバーが中間 CA の証明書も送らないと、署名をたどれません。Apache 2.4.8 以降では、SSLCertificateFile のファイルに「サーバー証明書、中間 CA の証明書」の順で続けて入れます。

SSLCACertificateFile と SSLCACertificatePath は、名前が似ていますが、クライアント証明書（利用者の側が出す証明書）を確かめるときに、どの CA を信頼するかの設定です。File は 1 つのファイル、Path はディレクトリです。

安全でないプロトコルと暗号を止める

SSL/TLS には古い版があり、弱点が見つかっています。使ってよいのは TLS 1.2 と TLS 1.3 です。

版状態
SSLv2、SSLv3安全でない（SSLv3 は POODLE 攻撃）。使わない
TLS 1.0、TLS 1.1古く、非推奨。止める
TLS 1.2、TLS 1.3使う

SSLProtocol は、all から要らないものを - で引くか、-all に使うものを + で足します。

conf
SSLProtocol all -SSLv3 -TLSv1 -TLSv1.1SSLProtocol -all +TLSv1.2 +TLSv1.3

どちらも「TLS 1.2 と 1.3 だけ」です。TLSv1 は TLS 1.0 のことです。いまの Apache は SSLv2 に対応しておらず、+SSLv2 と書くと SSLProtocol: SSLv2 is no longer supported でエラーになります。

SSLCipherSuite は、OpenSSL の書き方で暗号の組を選びます。: で区切って並べます。

書き方意味
HIGH鍵の長い、強い暗号の組
MEDIUM / LOW中くらい / 弱い暗号の組
!aNULL認証をしない暗号を除く（! は、後で足しても戻らない除外）
!MD5、!RC4、!3DESその方式を使う暗号を除く
-RC4除く（後で足し直せる）
+RC4一覧の最後に回す

どの暗号が残るかは、openssl ciphers -v 'HIGH:!aNULL:!MD5' で一覧できます。止めるべき弱い暗号は、RC4、DES と 3DES、MD5、NULL（暗号化しない）、EXPORT（輸出用の短い鍵）、aNULL（認証しない） です。

つないで確かめる

ターミナル
# curl https://127.0.0.1/curl: (60) SSL certificate problem: self-signed certificate# curl -k https://127.0.0.1/main# openssl s_client -connect 127.0.0.1:443 -servername www.example.com…New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384Verify return code: 18 (self-signed certificate)# openssl s_client -connect 127.0.0.1:443 -tls1_1…error:0A0000BF:SSL routines:tls_setup_handshake:no protocols available…

メモ1 つの番地で、複数の HTTPS のサイト（SNI）

名前ベースのバーチャルホストは Host ヘッダーで振り分けますが、HTTPS では、ヘッダーを読む前に証明書を選ばなければなりません。SNI（Server Name Indication）は、クライアントが TLS の最初の挨拶でホスト名を伝える仕組みです。これで、1 つの番地とポートで、サイトごとに別の証明書を出せます。openssl s_client の -servername が、その名前です。

9.7nginx の設定は、入れ子のブロックでできている

nginx（エンジンエックス）は、少ないプロセスで多くの接続をさばく Web サーバーです。リバースプロキシ（後ろのサーバーへの中継役）としてよく使われます。設定は /etc/nginx/ にあります。

場所中身

HTTPS は、listen に ssl を付け、証明書と鍵を指定します。

nginx のディレクティブ意味Apache で対応するもの

rewrite 正規表現 置き換え permanent;合ったら 301 で転送する

rewrite 正規表現 置き換え last; / break;転送はせず、nginx の中でパスを書き換える

9.8nginx をリバースプロキシにする：proxy_pass

リバースプロキシは、クライアントからのリクエストを受けて、後ろのサーバー（バックエンド）へ中継します。TLS の処理、複数のサーバーへの振り分け、静的なファイルの配信を nginx に任せ、アプリケーションは後ろで HTTP だけを話します。

conf
upstream backend {    server 127.0.0.1:8081;    server 127.0.0.1:8082;} server {    listen 443 ssl;    server_name www.example.com;    ssl_certificate     /etc/pki/tls/certs/server.crt;    ssl_certificate_key /etc/pki/tls/private/server.key;     location /app/ {        proxy_pass http://backend/;        proxy_http_version 1.1;        proxy_set_header Host $host;        proxy_set_header X-Real-IP $remote_addr;        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;        proxy_set_header X-Forwarded-Proto $scheme;    }}
ディレクティブ意味既定
proxy_pass中継先の URL。location の中に書く—
proxy_http_version中継先と話す HTTP の版1.0（nginx 1.29.7 以降は 1.1）
proxy_set_header中継先へ送るリクエストのヘッダーを、付けるか書き換えるHost $proxy_host; と Connection close;
upstream 名前 { server …; }中継先のサーバーの組。既定では順番に（ラウンドロビンで）振り分ける—

proxy_pass に書く URL には、upstream の名前も使えます。上の設定で 2 回リクエストすると、8081 と 8082 が 1 回ずつ答えました。

proxy_pass の URL にパスがあるか、ないか

proxy_pass は、URL の後ろにパスを書くかどうかで、中継先に送るパスが変わります。実際に、後ろのサーバーに届いたパスを表示させて確かめました。

設定クライアントのリクエスト中継先に届くパス
location /api/ { proxy_pass http://127.0.0.1:8081; }/api/x/y/api/x/y（そのまま）
location /app/ { proxy_pass http://backend/; }/app/x/y/x/y（/app/ が / に置き換わる）

パスを書かなければ、元のパスがそのまま送られます。パス（/ だけでも）を書くと、location に合った部分が、そのパスに置き換わります。

後ろのサーバーに、本当の相手を伝える

後ろのサーバーから見ると、接続してくる相手はいつも nginx です。何も設定しないと、後ろのサーバーには次のように届きました。

host=127.0.0.1:8081 xri= xff= proto=HTTP/1.0 conn=close

Host ヘッダーは proxy_pass に書いた中継先（$proxy_host）になり、クライアントの番地は伝わらず、HTTP/1.0 で、接続は毎回閉じられます。proxy_set_header と proxy_http_version 1.1 を書いた location /app/ では、こうなりました。

host=127.0.0.1 xri=127.0.0.1 xff=127.0.0.1 xfp=https proto=HTTP/1.1
よく書くヘッダー伝えるもの
proxy_set_header Host $host;クライアントが指定した元のホスト名
proxy_set_header X-Real-IP $remote_addr;クライアントの IP アドレス
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;経由してきた番地の一覧（クライアント、プロキシ …）
proxy_set_header X-Forwarded-Proto $scheme;元が http か https か

proxy_http_version 1.1; は、中継先との接続を使い回す（Keep-Alive）ときと、WebSocket を中継するときに必要です。nginx 1.29.7 からは既定が 1.1 に変わりましたが（nginx 1.28 は HTTP/1.0、1.31 は HTTP/1.1 で届きました）、rockylinux:9（1.20）や debian:12（1.22）の版は 1.0 です。試験では「既定は 1.0、1.1 にするには明示する」と覚えます。

注意試験の注意：nginx と Apache の名前の対応

nginx のディレクティブは小文字と下線（ssl_certificate_key）、Apache は大文字で始まる単語のつなぎ（SSLCertificateKeyFile）です。選択肢に SSLCertificate と ssl_certificate が混ざっていたら、どちらのサーバーの設定かを先に見ます。nginx は行の終わりに ; が要り、Apache は要りません。

深掘り502 Bad Gateway が出たら

nginx が 502 を返すのは、中継先から正しい応答をもらえなかったときです。中継先のプロセスが止まっている、proxy_pass のポートがまちがっている、などです。/var/log/nginx/error.log に connect() failed (111: Connection refused) while connecting to upstream のような行が出ます。中継先が動いているかを ss -ltn や curl http://127.0.0.1:8081/ で先に確かめます（図解 LinuC 7.10）。

9.9Squid：acl で名前を付け、http_access で上から判定する

Squid は、プロキシサーバーです。社内のクライアントの代わりに外の Web サーバーへ取りに行き（フォワードプロキシ）、取ってきたものをキャッシュして、次の人には手元から返します。誰がどこへ行けるかも制限できます。

設定ファイルは /etc/squid/squid.conf です。主なディレクティブです。

ディレクティブ意味
http_port 3128待ち受けるポート。既定は 3128

acl と http_access

アクセス制御は 2 段階です。acl で条件に名前を付け、http_access でその名前を許可か拒否に結び付けます。

conf

acl の種類何と比べるか例
srcクライアントの IP アドレスacl localnet src 192.168.1.0/24
dst行き先のサーバーの IP アドレスacl srv dst 203.0.113.10
dstdomain行き先のドメイン名。先頭の . はサブドメインも含むacl blocked dstdomain .blocked.example

proxy_auth認証した利用者の名前。REQUIRED は「認証に成功した人すべて」acl authed proxy_auth REQUIRED

判定の決まりは 3 つです。

  1. http_access は上から順に調べ、最初に合った行で決まる。それより下は見ない
  2. 1 つの http_access の行に名前を並べると AND（すべてに合うとき）。! は否定
  3. 1 つの acl に値を並べる（または同じ名前の acl を何行も書く）と OR（どれかに合うとき）

http_access deny CONNECT !SSL_ports は、「メソッドが CONNECT で、かつポートが SSL_ports でない」ものを拒否します。最後は必ず http_access deny all で閉じます。

注意試験の注意：行の順番

http_access deny all より下に書いた http_access allow … は、決して使われません。逆に、http_access allow localnet を http_access deny blocked より上に書くと、localnet の人は blocked のサイトにも行けてしまいます。拒否したいものを先、許可を後、最後に deny all が基本です。

クライアントのユーザー認証

利用者に名前とパスワードを求めるには、auth_param で認証のプログラムを指定し、proxy_auth の acl を作ります。

行意味
auth_param basic program …Basic 認証を受け持つ外部のプログラム（ヘルパー）と、その引数
auth_param basic children 5ヘルパーのプロセスの数
auth_param basic realm …入力の窓に出す領域の名前
auth_param basic credentialsttl 2 hours確かめた結果を覚えておく時間
acl authed proxy_auth REQUIRED認証に成功した利用者すべて

basic_ncsa_auth は、Apache の htpasswd で作ったファイルで確かめるヘルパーです（Red Hat 系は /usr/lib64/squid/、Debian 系は /usr/lib/squid/）。ほかに basic_ldap_auth（LDAP）、basic_pam_auth（PAM）などがあります。

メモ既定の squid.conf

配布されている squid.conf には、acl localnet src 10.0.0.0/8 などのプライベートアドレス（図解 LinuC 7.3）、acl SSL_ports port 443、acl Safe_ports port 80 などが初めから書いてあります。http_access deny !Safe_ports と http_access deny CONNECT !SSL_ports は、プロキシを踏み台にして変わったポートへつなぐのを防ぐ行です。消さずに、その下に自分の規則を足します。

要点まとめ
  • Apache：Red Hat 系は httpd と /etc/httpd/conf/httpd.conf、Debian 系は apache2 と /etc/apache2/apache2.conf。Debian 系は a2ensite、a2enmod で有効にする
  • 検査は apachectl configtest（httpd -t）、接続を切らない読み込み直しは apachectl graceful。httpd -S はバーチャルホスト、-M はモジュール、-l は組み込みモジュール
  • アクセスログの combined は %h %l %u %t "%r" %>s %b に Referer と User-Agent を足したもの
  • Basic 認証は AuthType、AuthName、AuthUserFile、Require。ファイルは htpasswd -c（新規。2 人目からは -c なし）。グループは AuthGroupFile と Require group
  • .htaccess に書けるものは AllowOverride で決まる。None なら読まれない
  • 名前ベースのバーチャルホストは Host ヘッダーで選ぶ。合わなければ最初の <VirtualHost>。Redirect の既定は 302、permanent で 301
  • MaxRequestWorkers（古い名前は MaxClients）は同時に処理できる数、MaxConnectionsPerChild（古い名前は MaxRequestsPerChild）は子プロセスを作り直すまでの接続の数。MinSpareServers と MaxSpareServers は prefork
  • 証明書は「秘密鍵 → CSR（openssl req -new）→ CA の署名」。自己署名は openssl req -x509。CSR に秘密鍵は入らない
  • 置き場所は Debian 系 /etc/ssl/certs、/etc/ssl/private、Red Hat 系 /etc/pki/tls/certs、/etc/pki/tls/private
  • mod_ssl：SSLEngine on、SSLCertificateFile、SSLCertificateKeyFile、SSLProtocol all -SSLv3 -TLSv1 -TLSv1.1、SSLCipherSuite HIGH:!aNULL:!MD5。SSLCACertificateFile（ファイル）と SSLCACertificatePath（ディレクトリ）はクライアント証明書の検証用
  • nginx：/etc/nginx/nginx.conf。nginx -t で検査、nginx -s reload で読み込み直し。行の終わりは ;
  • nginx の HTTPS は listen 443 ssl;、ssl_certificate、ssl_certificate_key、ssl_protocols、ssl_ciphers。リダイレクトは return 301 URL;
  • リバースプロキシは location の中の proxy_pass。proxy_http_version の既定は 1.0、proxy_set_header でクライアントの情報を伝える
  • Squid：/etc/squid/squid.conf、ポート 3128。acl で名前を付け、http_access は上から最初に合った行で決まる。最後は http_access deny all
  • Squid の認証は auth_param basic program … と acl 名前 proxy_auth REQUIRED。認証がなければ 407。検査は squid -k parse、試すのは squidclient
