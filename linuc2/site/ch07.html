7.1DHCP は、4 つのメッセージでアドレスを貸す

DHCP（Dynamic Host Configuration Protocol）は、ネットワークにつないだ機械に、IP アドレス、ネットマスク、デフォルトゲートウェイ、DNS サーバーなどを自動で配る仕組みです。配る側が DHCP サーバー、もらう側が DHCP クライアントです。

やりとりは 4 つのメッセージです。クライアントはまだ自分のアドレスを持たないので、最初の DHCPDISCOVER はブロードキャスト（同じネットワークの全員あて）で送ります。サーバーは UDP の 67 番、クライアントは UDP の 68 番を使います。

順メッセージ向き意味
1DHCPDISCOVERクライアント → 全員DHCP サーバーを探す
2DHCPOFFERサーバー → クライアント貸せるアドレスを申し出る
3DHCPREQUESTクライアント → 全員申し出の 1 つを選んで、使うと伝える
4DHCPACKサーバー → クライアント貸し出しを確定する

アドレスは「あげる」のではなく、期限つきで「貸す」ものです。この貸し出しをリース（lease）と呼びます。クライアントは期限の半分が過ぎると、DHCPREQUEST を送って延長します。使い終わったクライアントは DHCPRELEASE で返します。

ブロードキャストはルーターを越えません。別のサブネットにあるサーバーを使うときは、ルーターの上で DHCP リレーエージェント（dhcrelay）を動かして、要求を中継します。

Linux で広く使われてきた DHCP サーバーは、ISC（Internet Systems Consortium）の dhcpd です。試験の範囲も、この dhcpd の設定ファイルです。

Debian 系Red Hat 系
パッケージisc-dhcp-serverdhcp-server
設定ファイル/etc/dhcp/dhcpd.conf/etc/dhcp/dhcpd.conf
リースの記録/var/lib/dhcp/dhcpd.leases/var/lib/dhcpd/dhcpd.leases
unit の名前isc-dhcp-serverdhcpd
待ち受けるインターフェースの指定/etc/default/isc-dhcp-server の INTERFACESv4/etc/sysconfig/dhcpd（DHCPDARGS）

7.2dhcpd.conf は、サブネットごとに「範囲とオプション」を書く

/etc/dhcp/dhcpd.conf の例です。192.168.1.0/24 のネットワークで、100 番から 200 番までを配ります。

option domain-name "example.jp";option domain-name-servers 192.168.1.1, 8.8.8.8;default-lease-time 600;max-lease-time 7200;authoritative; subnet 192.168.1.0 netmask 255.255.255.0 {  range 192.168.1.100 192.168.1.200;  option routers 192.168.1.1;  option subnet-mask 255.255.255.0;  option broadcast-address 192.168.1.255;} host printer {  hardware ethernet 00:11:22:33:44:55;  fixed-address 192.168.1.10;}

書き方の決まりは 3 つです。

  • 1 つの設定は ;（セミコロン）で終わる
  • subnet や host は { } で囲む。{ } の外に書いたものは全体に、中に書いたものはその中だけに効く（中が優先）
  • クライアントに配る値は option 名前 値;、サーバー自身の動きを決めるものは option を付けない
書き方意味
subnet ネットワーク netmask マスク { … }配る先のサブネットを宣言する。/24 ではなく netmask で書く
range 最初 最後;動的に割り当てる範囲。この中から空いているものを貸す
option routersデフォルトゲートウェイ
option subnet-maskネットマスク
option broadcast-addressブロードキャストアドレス
option domain-name-serversDNS サーバー（カンマ区切りで複数）
option domain-nameドメイン名（文字列なので " で囲む）
option ntp-serversNTP サーバー
default-lease-time 秒;クライアントが期限を指定しないときのリースの長さ
max-lease-time 秒;クライアントが長い期限を求めても、これより長くは貸さない
host 名前 { hardware ethernet MAC; fixed-address IP; }固定の割り当て。この MAC アドレスの機械には、いつもこのアドレスを貸す
authoritative;このサーバーが、このネットワークの正式な DHCP サーバーだと宣言する
注意試験の注意：routers と fixed-address

デフォルトゲートウェイのオプションの名前は option gateway ではなく option routers です。固定の割り当ては host の中に hardware ethernet（MAC アドレス）と fixed-address（IP アドレス）を書きます。fixed-address には、range の外のアドレスを使います。range の中にあると、同じアドレスをほかの機械に動的に貸してしまうおそれがあります。

書いたら、起動する前に文法を調べます。dhcpd -t は設定ファイルを読んで、まちがいがあれば行番号を出して終わります。

ターミナル
# dhcpd -t -cf /etc/dhcp/dhcpd.confConfig file: /etc/dhcp/dhcpd.confDatabase file: /var/lib/dhcp/dhcpd.leasesPID file: /var/run/dhcpd.pid# dhcpd -t -cf /tmp/bad.conf/tmp/bad.conf line 3: semicolon expected.} ^Configuration file errors encountered -- exiting

2 つ目は、range の行の ; を忘れた例です。「semicolon expected」（セミコロンがあるはず）と、次の行の番号で知らせます。

dhcpd のオプション意味
-t設定ファイルの文法を調べて終わる
-Tリースのファイルを調べて終わる
-cf ファイル設定ファイルを指定する（既定は /etc/dhcp/dhcpd.conf）
-lf ファイルリースのファイルを指定する
-fフォアグラウンドで動かす（systemd の unit はこれを使う）
-dログを syslog ではなく、標準エラー出力に出す
-4 / -6DHCPv4 / DHCPv6 のサーバーとして動かす（既定は -4）
末尾のインターフェース名そのインターフェースだけで待ち受ける（dhcpd eth1）
注意試験の注意：subnet の宣言がないと起動しない

dhcpd は、待ち受けるインターフェースのアドレスが属するサブネットの subnet 宣言を、dhcpd.conf の中に探します。見つからないと、次のメッセージを出して起動しません。

No subnet declaration for veth0 (192.168.1.1).Not configured to listen on any interfaces!

アドレスを配らないインターフェースしかないときも、空の subnet … { } を書いておく必要があります。

7.3リースとログで、貸し出しを確かめる

dhcpd は、貸したアドレスを dhcpd.leases に書き足していきます。再起動しても、誰に何を貸したかを忘れないためのファイルです。クライアントが 1 台アドレスをもらったあとの中身です。

ターミナル
# cat /var/lib/dhcp/dhcpd.leaseslease 192.168.1.100 {  starts 1 2026/11/16 21:18:39;  ends 1 2026/11/16 21:28:39;  cltt 1 2026/11/16 21:18:39;  binding state active;  next binding state free;  rewind binding state free;  hardware ethernet be:e4:73:7c:b9:9a;  client-hostname "52f8273d7994";}
行意味
lease 192.168.1.100貸したアドレス
starts / endsリースの始まりと終わり（UTC。先頭の数字は曜日で、0 が日曜）
binding state activeいま貸している。返されると free になる
hardware ethernet借りたクライアントの MAC アドレス
client-hostnameクライアントが名乗ったホスト名

ends − starts が 10 分なのは、default-lease-time 600; のためです。

このファイルは追記されるので、同じアドレスの lease が何度も出てきます。有効なのは、いちばん後ろのものです。dhcpd はときどきファイルを作り直し、古いほうを dhcpd.leases~ という名前で残します。

注意試験の注意：dhcpd.leases は、空でも「ある」ことが必要

dhcpd は、起動のときに dhcpd.leases がないと「Can't open lease database」と出して止まります。パッケージで入れたときは最初から作られていますが、自分で場所を変えたときは touch /var/lib/dhcp/dhcpd.leases で空のファイルを作ってから起動します。手で書き換えるファイルではありません。

ログを読む

dhcpd は、やりとりを 1 メッセージ 1 行で syslog（facility は daemon）に出します。見る場所は、ログの仕組みで決まります（図解 LinuC 9.3 rsyslog、9.4 journalctl）。

仕組み見方
rsyslog（Debian 系）/var/log/syslog を grep dhcpd
rsyslog（Red Hat 系）/var/log/messages を grep dhcpd
systemd journaljournalctl -u dhcpd（Debian 系は -u isc-dhcp-server）

サーバー側のログは、DORA の順に 4 行です。

DHCPDISCOVER from be:e4:73:7c:b9:9a via veth0DHCPOFFER on 192.168.1.100 to be:e4:73:7c:b9:9a (52f8273d7994) via veth0DHCPREQUEST for 192.168.1.100 (192.168.1.1) from be:e4:73:7c:b9:9a (52f8273d7994) via veth0DHCPACK on 192.168.1.100 to be:e4:73:7c:b9:9a (52f8273d7994) via veth0

from の後ろがクライアントの MAC アドレス、via の後ろが受け取ったインターフェースです。どこまで進んだかで、原因の場所が分かります。

ログの様子考えられる原因
DHCPDISCOVER の行が出ない要求がサーバーに届いていない（配線、VLAN、ファイアウォールの UDP 67、リレーがない）
DHCPDISCOVER from … via eth0: network 192.168.1.0/24: no free leasesrange を書いていないか、範囲のアドレスを全部貸し出している
DHCPOFFER のあと DHCPREQUEST が来ないクライアントが別の DHCP サーバーの申し出を選んだ

arp で、アドレスと MAC アドレスの対応を見る

固定の割り当てには、クライアントの MAC アドレスが要ります。同じネットワークの相手の MAC アドレスは、カーネルの ARP テーブル（IP アドレスと MAC アドレスの対応表）で調べられます。古くからのコマンドが arp、いまのコマンドが ip neigh です。

ターミナル
# arp -nAddress                  HWtype  HWaddress           Flags Mask            Iface172.17.0.1               ether   2e:4c:63:ab:0e:92   C                     eth0# ip neigh172.17.0.1 dev eth0 lladdr 2e:4c:63:ab:0e:92 REACHABLE
コマンド意味
arp -nARP テーブルを表示する。-n は名前に直さず、IP アドレスのまま出す
arp -aBSD 風の形（? (172.17.0.1) at 2e:4c:… [ether] on eth0）で表示する
arp -d アドレス1 件を消す
arp -s アドレス MAC手で 1 件を登録する（静的なエントリ）

「配ったはずのアドレスに、別の機械が応えている」という重なりを疑うときも、arp -n でその IP アドレスの MAC アドレスを見て、dhcpd.leases の hardware ethernet と比べます。

7.4IPv6 は、ルーター広告と DHCPv6 で配る

IPv6 では、DHCP がなくてもアドレスが決まります（図解 LinuC 7.5 IPv6）。ルーターが定期的に流すルーター広告（RA、Router Advertisement）に、そのネットワークのプレフィックス（先頭の 64 ビット）が入っています。クライアントは、それに自分で作った後ろの 64 ビットをつないで、アドレスにします。これを SLAAC（ステートレスアドレス自動設定）と呼びます。デフォルトゲートウェイは、RA を送ってきたルーターです。

Linux をルーターにして RA を流すデーモンが radvd（Router ADVertisement Daemon）、設定ファイルが /etc/radvd.conf です。

interface eth0 {    AdvSendAdvert on;    MinRtrAdvInterval 3;    MaxRtrAdvInterval 10;    AdvManagedFlag off;    AdvOtherConfigFlag off;    prefix 2001:db8:1::/64 {        AdvOnLink on;        AdvAutonomous on;    };    RDNSS 2001:db8:1::53 {    };};
書き方意味
interface eth0 { … };RA を流すインターフェース。閉じる } の後ろにも ; が要る
AdvSendAdvert on;RA を送る。off（既定）のままでは何も送らない
prefix 2001:db8:1::/64 { … };広告するプレフィックス
AdvAutonomous on;このプレフィックスで SLAAC をしてよい
AdvManagedFlag on;M フラグ。アドレスを DHCPv6 でもらえ、と伝える
AdvOtherConfigFlag on;O フラグ。アドレスは SLAAC、DNS サーバーなど「そのほか」を DHCPv6 でもらえ、と伝える
RDNSS アドレス { };RA で DNS サーバーを知らせる
MinRtrAdvInterval / MaxRtrAdvIntervalRA を送る間隔（秒）の下限と上限

文法は radvd -c（--configtest）で調べます。設定ファイルは -C で指定します。

ターミナル
# radvd -c -C /etc/radvd.conf[Nov 16 21:18:18] radvd (246): config file, /etc/radvd.conf, syntax ok

radvd を動かす機械は IPv6 のルーターなので、IPv6 の転送を有効にしておきます（sysctl -w net.ipv6.conf.all.forwarding=1）。

DHCPv6 は、IPv6 版の DHCP です。ISC の dhcpd では、dhcpd -6 で動かし、設定は /etc/dhcp/dhcpd6.conf に書きます。

default-lease-time 2592000;option dhcp6.name-servers 2001:db8:1::53;subnet6 2001:db8:1::/64 {  range6 2001:db8:1::1000 2001:db8:1::1fff;}
DHCPv4DHCPv6
ポートサーバー UDP 67、クライアント UDP 68サーバー UDP 547、クライアント UDP 546
サブネットの宣言subnet … netmask … { }subnet6 プレフィックス/長さ { }
範囲rangerange6
オプションの名前option domain-name-serversoption dhcp6.name-servers
デフォルトゲートウェイoption routers で配る配らない（RA で知る）
リースのファイルdhcpd.leasesdhcpd6.leases
メモDHCPv6 だけでは足りない

DHCPv6 には、デフォルトゲートウェイを配るオプションがありません。ゲートウェイは必ず RA で知らせるので、DHCPv6 を使うネットワークでも radvd（またはルーターの RA の機能）は要ります。M フラグを on にした RA と DHCPv6 サーバーを組み合わせるのが、IPv4 の DHCP にいちばん近い形です。

7.5PAM は、認証を「プログラムの外」に出す仕組み

PAM（Pluggable Authentication Modules、差し替えできる認証モジュール）は、「この人は本人か」「いまログインしてよいか」を確かめる処理を、プログラムの外に出す仕組みです。login、sshd、su、sudo、passwd などは、自分でパスワードを確かめず、PAM のライブラリを呼びます。

そのおかげで、パスワードの置き場所を /etc/shadow から LDAP に変えるときも、プログラムを作り直す必要がありません。設定ファイルの行を変えるだけで、認証の方法を差し替えられます。

設定の置き場所は 2 つあります。

場所形
/etc/pam.d/サービス（プログラム）ごとに 1 ファイル。ファイル名がサービス名（/etc/pam.d/sshd、/etc/pam.d/su）
/etc/pam.conf1 ファイルに全部書く古い形。各行の先頭にサービス名の欄が増える
注意試験の注意：/etc/pam.d/ があると、pam.conf は読まれない

/etc/pam.d/ ディレクトリがあるとき、/etc/pam.conf は無視されます。いまのディストリビューションはどれも /etc/pam.d/ を使います。サービス名のファイルがないときは、/etc/pam.d/other が使われます。モジュールの本体（pam_unix.so など）は、Red Hat 系では /usr/lib64/security/、Debian 系では /lib/x86_64-linux-gnu/security/ にあります。

7.6/etc/pam.d/ の 1 行は「タイプ・制御・モジュール・引数」

/etc/pam.d/ のファイルは、1 行が 1 つのモジュールの呼び出しです。Rocky Linux 9 の /etc/pam.d/system-auth（抜粋）で読み方を見ます。

auth        required      pam_env.soauth        sufficient    pam_unix.so try_first_pass nullokauth        required      pam_deny.so account     required      pam_unix.so password    requisite     pam_pwquality.so try_first_pass local_users_only retry=3password    sufficient    pam_unix.so try_first_pass use_authtok nullok sha512 shadowpassword    required      pam_deny.so session     required      pam_limits.sosession     required      pam_unix.so

欄は左から 4 つです。/etc/pam.conf に書くときだけ、先頭に「サービス名」の欄が足されます。

タイプ    制御        モジュール     引数auth      required    pam_unix.so    nullok

タイプ：4 つの場面

タイプ（モジュールタイプ）は、その行がどの場面で使われるかです。同じタイプの行が、上から順に実行されます。この並びをスタックと呼びます。

タイプ場面例
auth本人かを確かめるパスワードを聞いて照合する
accountいま使ってよいかを確かめる（認証とは別）アカウントやパスワードの期限、時間帯、/etc/nologin
passwordパスワードを変えるとき新しいパスワードの強さを調べ、書き換える
sessionログインの前後の準備と後片付け資源の上限、ホームディレクトリの作成、ログへの記録

制御：結果をどう扱うか

制御（コントロールフラグ）は、モジュールが成功・失敗したときに、スタックの続きをどうするかです。試験でいちばん問われるところです。

制御失敗したとき成功したとき
required最後は失敗になる。ただし残りの行も実行する次の行へ進む
requisiteその場で失敗を返す（残りは実行しない）次の行へ進む
sufficient無視して次の行へ進むそれより前の required が失敗していなければ、その場で成功を返す
optional結果に影響しない（ほかにモジュールがないときだけ使われる）同じ
includeほかのファイルの、同じタイプの行をここに読み込む
substackinclude と同じだが、読み込んだ中での「その場で終わる」は、読み込んだ中だけで終わる

required が失敗しても残りを実行するのは、どのモジュールで失敗したかを相手に知らせないためです。ユーザー名がまちがっていても、パスワードを聞いてから「失敗」と答えます。

上の system-auth の auth は、次のように動きます。

  1. pam_env.so（環境変数を用意する）は成功するので、次へ
  2. pam_unix.so が /etc/shadow と照合する。合えば sufficient なので、ここで成功して終わる
  3. 合わなければ次の pam_deny.so（必ず失敗するモジュール）が required で失敗し、認証は失敗

Docker の中で、pamtester（PAM を試すコマンド）を使って制御の違いを確かめた結果です。pam_permit.so は必ず成功、pam_deny.so は必ず失敗するモジュールです。

スタック（上から）結果理由
sufficient pam_permit.so → required pam_deny.so成功sufficient が成功した時点で終わり、2 行目は実行されない
required pam_deny.so → sufficient pam_permit.so失敗先に required が失敗しているので、sufficient が成功しても覆らない
optional pam_deny.so → required pam_permit.so成功optional の失敗は結果に影響しない
注意試験の注意：required と requisite

どちらも「失敗したら、全体が失敗」です。違いは、失敗のあとです。required は残りのモジュールも実行してから失敗を返し、requisite はその場で失敗を返します。「sufficient は成功したら即終了、requisite は失敗したら即終了」と対にして覚えます。

深掘り[success=1 default=ignore] という書き方

Debian 系の /etc/pam.d/common-auth には、auth [success=1 default=ignore] pam_unix.so nullok のような行があります。[ ] の中は「結果=動作」の並びで、success=1 は「成功したら次の 1 行を飛ばす」、default=ignore は「それ以外は無視」です。次の行が pam_deny.so、その次が pam_permit.so なので、成功すれば deny を飛ばして permit に着きます。required などの 4 つの語は、この書き方の決まった組み合わせに名前を付けたものです。

共通の設定を読み込む

どのサービスにも同じ行を書くのは大変なので、共通の部分は別のファイルにまとめて読み込みます。まとめ方がディストリビューションで違います。

共通のファイル読み込み方
Red Hat 系/etc/pam.d/system-auth（ローカルのログイン）、/etc/pam.d/password-auth（sshd などリモート）auth include system-auth、auth substack password-auth
Debian 系/etc/pam.d/common-auth、common-account、common-password、common-session@include common-auth

Red Hat 系の system-auth と password-auth は、authselect コマンド（authselect select sssd など）が作るファイルです。

引数意味
retry=3弱いパスワードだったとき、3 回まで入力し直させる
minlen=12最小の長さ。ただし、プラスの *credit（既定はどれも 1）がある種類の文字を使うと、その分だけ短くてもよい
difok=3前のパスワードと、少なくとも 3 文字は違うこと
dcredit=-1数字（digit）を最低 1 文字含むこと
ucredit=-1 / lcredit=-1大文字（upper）/ 小文字（lower）を最低 1 文字含むこと

*credit は、マイナスの値にすると「その種類を最低その数だけ含む」という意味になります。逆に 0 以上の値は、その種類の文字を使ったときに、長さに足してもらえる点数（クレジット）の上限です。dcredit、ucredit、lcredit、ocredit の既定はどれも 1 なので、minlen=12 と書いただけでは、4 種類を混ぜた 9 文字のパスワードも「9 + 3 = 12」として通ります（Debian 11 の pam_cracklib で確かめた結果です）。minlen をそのまま文字数の下限にしたいときは、ucredit=0 lcredit=0 ocredit=0 のように、クレジットを 0 かマイナスにします。

pam_cracklib は必ず pam_unix より上に書きます。先に強さを調べ、通ったパスワードを use_authtok で pam_unix に渡して書き換えさせるためです。

メモpam_cracklib はいまは pam_pwquality

Debian 12 と Rocky Linux 9 には pam_cracklib はもう入っておらず、同じ引数（retry、minlen、difok、dcredit など）が使える後継の pam_pwquality に置き換わっています。pam_pwquality は、引数のほかに /etc/security/pwquality.conf でも設定できます。試験の範囲には pam_cracklib の名前で載っているので、役目と引数を覚えておきます。

pam_limits

pam_limits は、ログインのときに /etc/security/limits.conf と /etc/security/limits.d/*.conf を読み、そのセッションに資源の上限を付けます。ulimit で見える値の出どころです（図解 LinuC 10.4 ulimit）。

session   required   pam_limits.so

/etc/security/limits.conf は、1 行が「誰に・種類・項目・値」の 4 つの欄です。

#<domain>   <type>  <item>     <value>*           soft    core       0@student    hard    nproc      20ken         soft    nofile     4096ken         hard    nofile     8192@student    -       maxlogins  4
欄書くもの
domain（誰に）ユーザー名、@グループ名、*（全員）
type（種類）soft（ソフトリミット。自分でハードまで上げられる）、hard（ハードリミット。上限の上限）、-（両方）

小さな Linux でも、いまのシェルに付いている上限を ulimit で見られます。本物の Linux では、この値を pam_limits がログインのときに付けています。

ulimit -Snulimit -Hn

pam_listfile

pam_listfile は、ファイルに 1 行 1 つで書いた名前の一覧と照らして、成功か失敗かを返します。「このユーザーは SSH でログインさせない」のような、名前の一覧での制限に使います。

auth  required  pam_listfile.so item=user sense=deny file=/etc/ssh/denyusers onerr=succeed
引数意味
item=何を照らすか。user（ユーザー名）、group、tty、rhost（接続元のホスト）、ruser、shell
sense=一覧にあったときの扱い。allow（あれば成功、なければ失敗）、deny（あれば失敗、なければ成功）
file=一覧のファイル
onerr=ファイルが開けないなどのエラーのときの扱い。succeed か fail

Docker で確かめると、/etc/denyusers に ken と書いて sense=deny にしたとき、ken の認証は失敗し、書いていない mika は成功します。同じファイルで sense=allow にすると逆になり、ken だけが成功します。

7.8nsswitch.conf と SSSD：リモートのユーザーでログインする

ユーザーの情報を LDAP サーバーにまとめると、クライアントの /etc/passwd にはそのユーザーがいません。それでもログインできるようにするには、2 つの別の仕組みの両方に、LDAP を見るよう教える必要があります。

仕組み答える問い設定
NSS（Name Service Switch）このユーザー名の UID、GID、ホーム、シェルは何か/etc/nsswitch.conf
PAM入力されたパスワードは正しいか、ログインしてよいか/etc/pam.d/

/etc/nsswitch.conf は、レベル1 で hosts: files dns を読んだファイルです（図解 LinuC 7.6）。ユーザーとグループの行も同じ読み方です。左から順に試し、見つかったところで止まります。

passwd:     files sssgroup:      files sssshadow:     files ssshosts:      files dns
書く語引く先
filesローカルのファイル（/etc/passwd、/etc/group、/etc/hosts）
sssSSSD
ldapLDAP サーバーに直接（古い nss_ldap の方式）
dnsDNS（hosts の行だけ）
systemdsystemd が動的に作るユーザー

getent passwd ユーザー名 は、この nsswitch.conf の順に引くコマンドです（図解 LinuC 8.2）。LDAP のユーザーが getent passwd ken で出れば、NSS の側は正しく設定できています。小さな Linux には files しかありませんが、引き方は同じです。

getent は nsswitch.conf の順に引く⌘↵
getent passwd rootgetent group root
注意試験の注意：nsswitch.conf は認証をしない

/etc/nsswitch.conf が決めるのは、情報をどこから引くかだけです。パスワードを確かめるのは PAM です。「getent passwd ken では出るのにログインできない」なら PAM（pam_sss）の側、「id ken で no such user と出る」なら NSS（nsswitch.conf の passwd: 行）の側を疑います。

SSSD の基本

SSSD（System Security Services Daemon）は、LDAP、Active Directory、Kerberos などのリモートのサーバーに問い合わせるデーモン（sssd）です。NSS からは sss、PAM からは pam_sss を通して呼ばれます。

SSSD を間に入れる利点は、キャッシュです。一度引いた情報を覚えておくので、サーバーへの問い合わせが減ります。認証の情報も覚えさせれば（cache_credentials = true）、ノートパソコンがネットワークから外れていても、前にログインしたユーザーはログインできます（オフライン認証）。

設定ファイルは /etc/sssd/sssd.conf です。[sssd] に全体の設定、[domain/名前] に問い合わせ先ごとの設定を書きます。

[sssd]services = nss, pamdomains = example [domain/example]id_provider = ldapauth_provider = ldapldap_uri = ldap://ldap.example.jpldap_search_base = dc=example,dc=jpcache_credentials = true
項目意味
[sssd] の servicesSSSD が受け持つ窓口。nss（情報を引く）、pam（認証）など
[sssd] の domains使うドメイン（[domain/…] の名前）の並び。ここに書かないドメインは使われない
id_providerユーザーの情報の引き先（ldap、ad、ipa、files）
auth_provider認証の方法（ldap、krb5、ad）
ldap_uriLDAP サーバーの URI
ldap_search_base検索の起点の DN
cache_credentials認証の情報を覚えて、オフラインでもログインできるようにする
注意試験の注意：sssd.conf は root の 0600

/etc/sssd/sssd.conf は、所有者が root、パーミッションが 0600 でないと、sssd が読み込みを拒みます。Rocky Linux 9 で 0644 にして sssctl config-check を実行すると、「File ownership and permissions check failed. Expected root:root and 0600.」と出ます。

PAM の側は、pam_unix の下に pam_sss を足します。Rocky Linux 9 で authselect select sssd を実行したあとの system-auth（抜粋）です。

auth        sufficient    pam_unix.so nullokauth        sufficient    pam_sss.so forward_passauth        required      pam_deny.so account     required      pam_unix.soaccount     [default=bad success=ok user_unknown=ignore] pam_sss.so password    sufficient    pam_unix.so sha512 shadow nullok use_authtokpassword    sufficient    pam_sss.so use_authtok session     required      pam_unix.sosession     optional      pam_sss.so

ローカルのユーザーは pam_unix で成功して終わり、/etc/shadow にいないユーザーは次の pam_sss が SSSD に聞きます。どちらもだめなら pam_deny で失敗です。

7.9LDAP は、木の形のデータベース

LDAP（Lightweight Directory Access Protocol）は、ディレクトリ（directory）に問い合わせるためのプロトコルです。ここでのディレクトリは、ファイルを入れるフォルダではなく、「人や機械の情報を、木の形に整理して引けるようにしたデータベース」のことです。読み出しが多く、書き込みが少ない使い方に向いています。

人の名前から電話番号やメールアドレスを引く使い方を、個人名の電話帳になぞらえてホワイトページと呼びます。社内のアドレス帳がその例です。ユーザーの認証の情報（UID、パスワード）を入れておけば、ログインにも使えます。

用語意味
エントリ木の 1 つの節。1 人の人、1 つのグループなどにあたる
属性エントリが持つ「名前: 値」の組（mail: ken@example.jp）。同じ属性を複数持てる
DN（識別名、Distinguished Name）エントリを木の中でただ 1 つに決める名前。uid=ken,ou=People,dc=example,dc=jp
RDN（相対識別名）DN のいちばん左の 1 つ（uid=ken）。同じ親の下で重ならない
DIT（ディレクトリ情報ツリー）エントリが作る木の全体
サフィックスその木の根の DN（dc=example,dc=jp）
objectClassそのエントリが何の種類かを表す属性。持てる属性は、これで決まる

DN は、下（自分）から上（根）へ、カンマでつないで書きます。ファイルのパス（/home/ken）とは向きが逆です。

DN に出てくる属性の名前は、決まった略語です。

略語元の語使いどころ
dcdomain componentドメイン名の 1 区切り（example.jp → dc=example,dc=jp）
oorganization組織
ouorganizational unit組織の中の部門、入れ物
cncommon name一般的な名前（人の氏名、グループの名前）
snsurname姓
uiduser IDログイン名
c / lcountry / locality国 / 地域

LDIF：エントリをテキストで書く

LDIF（LDAP Data Interchange Format）は、エントリをテキストで表す形式です。登録、変更、バックアップのどれにも使います。

dn: ou=People,dc=example,dc=jpobjectClass: organizationalUnitou: People dn: uid=ken,ou=People,dc=example,dc=jpobjectClass: inetOrgPersonobjectClass: posixAccountcn: Ken Satosn: Satouid: kenuidNumber: 2001gidNumber: 2001homeDirectory: /home/kenmail: ken@example.jp
決まり内容
最初の行dn: で、そのエントリの DN を書く
2 行目から属性名: 値。コロンの後ろに空白 1 つ
エントリの区切り空行
値が base64 のとき属性名:: 値（コロン 2 つ）。日本語やバイナリの値、パスワードのハッシュ
長い行の続き次の行を空白 1 つで始める
コメント行頭が #
順番親のエントリを、子より先に書く（親がないと登録できない）

7.10LDAP のクライアントコマンドは、-x -D -W -b が共通

LDAP サーバーにネットワークごしに（LDAP のプロトコルで）問い合わせるコマンドは、名前が ldap で始まります。Debian 系は ldap-utils、Red Hat 系は openldap-clients パッケージに入っています。

コマンドすること
ldapsearchエントリを検索する
ldapaddエントリを追加する
ldapmodifyエントリを変更する（追加、削除もできる）
ldapdeleteエントリを削除する
ldappasswdエントリのパスワードを変える

サーバーへのつなぎ方と名乗り方のオプションは、5 つとも同じです。

オプション意味
-x簡易認証（DN とパスワード）を使う。付けないと SASL 認証になる
-H URI接続先（ldap://ldap.example.jp、ldaps://…、ldapi:///）
-D DNこの DN でサーバーにバインド（ログイン）する。省くと匿名
-Wバインドのパスワードを、プロンプトで聞く
-w パスワードバインドのパスワードを、コマンドラインに書く
-f ファイルLDIF（や DN の一覧）をファイルから読む。省くと標準入力
-cエラーがあっても止まらず、続ける
-ZStartTLS で暗号化する（-ZZ は、できなければやめる）
注意試験の注意：大文字と小文字で意味が違う

-W は「パスワードを聞く」、-w secret は「パスワードを書く」です。-D はバインドする DN、-b は検索の起点、-H は接続先の URI です。-x を忘れると SASL 認証を試みて失敗します。

接続先と検索の起点の既定値は、クライアントの設定ファイル ldap.conf に書けます。Debian 系は /etc/ldap/ldap.conf、Red Hat 系は /etc/openldap/ldap.conf です。

BASE    dc=example,dc=jpURI     ldap://ldap.example.jp

LDAP の標準のポートは 389 番（ldap://。StartTLS もこのポート）、最初から TLS で包む ldaps:// は 636 番です。ldapi:/// は、同じ機械の UNIX ドメインソケットでつなぎます。

ldapsearch：検索する

ターミナル
$ ldapsearch -x -LLL -b dc=example,dc=jp "(uid=ken)" cn maildn: uid=ken,ou=People,dc=example,dc=jpcn: Ken Satomail: ken@example.jp

並びは「オプション、フィルタ、欲しい属性」です。属性を省くと、読める属性を全部出します。

オプション意味
-b DN検索の起点（search base）。この DN から下を探す
-s 範囲探す範囲。sub（起点とその下の全部。既定）、one（起点の 1 つ下だけ）、base（起点のエントリだけ）
-L / -LL / -LLL出力を素の LDIF に近づける。-LLL はコメントも版の行も出さない

-LLL を付けないと、結果の前後に # extended LDIF や # numEntries: 1 などのコメントが付きます。スクリプトで使うときは -LLL にします。

範囲の違いを、上の図の木で確かめた結果です。

ターミナル
$ ldapsearch -x -LLL -b dc=example,dc=jp -s base dndn: dc=example,dc=jp $ ldapsearch -x -LLL -b dc=example,dc=jp -s one dndn: ou=People,dc=example,dc=jp

-s one では、2 つ下にいる uid=ken は出ません。

フィルタは、かっこで囲んだ「属性=値」です。組み合わせる記号は、かっこの前に書きます。

フィルタ意味
(uid=ken)uid が ken
(cn=Ken*)cn が Ken で始まる（* は任意の文字列）
(mail=*)mail の属性を持っている
(&(objectClass=inetOrgPerson)(mail=*@example.jp))AND。両方を満たす
(|(uid=ken)(uid=mika))OR。どちらかを満たす
(!(uid=ken))NOT。満たさない
(uidNumber>=2000)2000 以上（<= もある）

フィルタを省くと (objectClass=*)（すべてのエントリ）になります。シェルが * や & や | を解釈しないように、フィルタは引用符で囲みます。

ldapadd と ldapmodify：追加する、変える

ldapadd は、LDIF に書いたエントリを追加します。書き込みには権限が要るので、管理者の DN でバインドします。

ターミナル
$ ldapadd -x -D cn=admin,dc=example,dc=jp -W -f base.ldifEnter LDAP Password:adding new entry "ou=People,dc=example,dc=jp" adding new entry "uid=ken,ou=People,dc=example,dc=jp"

同じ LDIF をもう一度流すと、1 つ目のエントリで ldap_add: Already exists (68) と出て止まります。-c を付ければ、エラーのエントリを飛ばして最後まで進みます。

ldapmodify は、どう変えるかを書いた LDIF を読みます。ふつうの LDIF に、changetype: と操作の行が増えます。

dn: uid=ken,ou=People,dc=example,dc=jpchangetype: modifyreplace: mailmail: ken.sato@example.jp-add: descriptiondescription: sales-delete: telephoneNumber
行意味
changetype: modifyこのエントリの属性を変える。ほかに add（エントリを足す）、delete（エントリを消す）、modrdn（RDN を変える）
replace: 属性その属性の値を、次の行の値に置き換える
add: 属性その属性に、値を足す
delete: 属性その属性を消す（値を書けば、その値だけを消す）
-（ハイフンだけの行）1 つのエントリの中で、操作を区切る
ターミナル

アクセス制御（slapd.access）

誰が、どのエントリのどの属性を、読めるか・書けるかを決めるのが olcAccess（slapd.conf では access）です。書き方の説明は、man slapd.access にあります。

access to <何に> by <誰が> <どこまで> [by <誰が> <どこまで> …]

上の既定の 3 行を読みます。

olcAccess: {0}to attrs=userPassword by self write by anonymous auth by * noneolcAccess: {1}to attrs=shadowLastChange by self write by * readolcAccess: {2}to * by * read
  1. userPassword 属性は、本人（self）は書ける。匿名（anonymous）は認証に使えるだけ。ほかの人（*）は何もできない
  2. shadowLastChange 属性は、本人は書ける。ほかの人は読める
  3. それ以外（to *）は、誰でも読める
<何に>意味
*すべてのエントリ
attrs=属性,属性その属性
dn.base="DN" / dn.subtree="DN"その DN のエントリ / その DN から下の全部
<誰が>意味
*誰でも（匿名も含む）
anonymousバインドしていない人
usersバインドした（認証された）人
selfそのエントリ自身の DN でバインドした人
dn.exact="DN"その DN の人

<どこまで> は、下にいくほど強く、強いものは弱いものを含みます。

レベルできること
none何もできない
discloseエラーのときに、存在を知らせてもらえる
authバインド（認証）に使える
compare値を比べられる
search検索のフィルタに使える
read検索の結果を読める
write書ける
manage管理の操作ができる
注意試験の注意：アクセス制御は、最初に合ったところで決まる

olcAccess は上から順に調べ、to <何に> が最初に合った行で決まります。その行の中でも、by <誰が> は左から調べて、最初に合ったものが使われます。だから、細かい条件（attrs=userPassword）を上に、広い条件（to *）を下に書きます。逆にすると、to * by * read が先に合って、パスワードのハッシュまで誰でも読めてしまいます。どの by にも合わなかった人は none、どの行にも合わなかったときも読めません。olcRootDN だけは、この制御を受けません。

実際に、匿名で userPassword を検索しても、DN だけが返り、属性は出ません。匿名で書き換えようとすると「Strong(er) authentication required (8)」で断られます。

7.12スキーマは、エントリに書ける属性を決める

エントリに、好きな属性を自由に書けるわけではありません。どんな属性があり、どの種類のエントリがどの属性を持てるかを決めた定義が、スキーマです。スキーマは 2 種類の定義からできています。

定義決めること
属性型（attributetype）属性の名前、値の書式（文字列、数、電話番号）、比べ方（大文字と小文字を区別するか）
オブジェクトクラス（objectclass）エントリの種類。必ず要る属性（MUST）と、あってもよい属性（MAY）

cn=schema,cn=config の下に入っている定義を見ます（折り返しを直してあります）。

olcAttributeTypes: ( 0.9.2342.19200300.100.1.3 NAME ( 'mail' 'rfc822Mailbox' )  DESC 'RFC1274: RFC822 Mailbox' EQUALITY caseIgnoreIA5Match  SUBSTR caseIgnoreIA5SubstringsMatch SYNTAX 1.3.6.1.4.1.1466.115.121.1.26{256} ) olcObjectClasses: ( 2.5.6.6 NAME 'person' DESC 'RFC2256: a person' SUP top STRUCTURAL  MUST ( sn $ cn ) MAY ( userPassword $ telephoneNumber $ seeAlso $ description ) ) olcObjectClasses: ( 1.3.6.1.1.1.2.0 NAME 'posixAccount' SUP top AUXILIARY  MUST ( cn $ uid $ uidNumber $ gidNumber $ homeDirectory )  MAY ( userPassword $ loginShell $ gecos $ description ) )
語意味
先頭の数字（2.5.6.6）オブジェクト ID（OID）。属性型やオブジェクトクラスを、世界でただ 1 つに決める番号。ドットで区切った数の並び
NAME名前。別名を並べて書ける（mail と rfc822Mailbox）
SUP親（superior）。親の MUST と MAY を受け継ぐ
MUST ( … )必ず要る属性。$ で区切る
MAY ( … )あってもよい属性
STRUCTURAL構造型。エントリの本体になるクラス。1 つのエントリに、必ず 1 系統だけ要る
AUXILIARY補助型。構造型のクラスに付け足して、属性を増やす
ABSTRACT抽象型。ほかのクラスの親になるためだけのクラス（top）
EQUALITY / SYNTAX値の比べ方 / 値の書式（これも OID で指す）

LDIF の例の ken は、inetOrgPerson（構造型。親をたどると person）と posixAccount（補助型）を持っています。person の MUST が sn と cn なので、sn を書き忘れると登録できません。

ターミナル
$ ldapadd -x -D cn=admin,dc=example,dc=jp -W -f z.ldifadding new entry "uid=z,ou=People,dc=example,dc=jp"ldap_add: Object class violation (65)    additional info: object class 'inetOrgPerson' requires attribute 'sn'

どのオブジェクトクラスにもない属性（foo: bar）を書くと、「Undefined attribute type (17)」になります。

スキーマは、ファイルとして配られています。Debian 系は /etc/ldap/schema/、Red Hat 系は /etc/openldap/schema/ に、slapd.conf 用の .schema と、slapd-config 用の .ldif が入っています。

スキーマ主なオブジェクトクラス用途
coreperson、organization、organizationalUnit基本。必ず要る
cosine（mail などの属性型）inetorgperson と nis が使う
inetorgpersoninetOrgPerson人（メール、電話、部署）。ホワイトページ向け
nisposixAccount、posixGroup、shadowAccountUNIX のユーザーとグループ。ログインに使う

slapd.conf では include /etc/ldap/schema/nis.schema と書いて読み込みます。slapd-config では、ldapadd -Y EXTERNAL -H ldapi:/// -f /etc/ldap/schema/nis.ldif のように、スキーマの LDIF を cn=schema,cn=config の下に追加します。inetorgperson と nis は、cosine が定義する属性型を使うので、core → cosine → nis・inetorgperson の順に読み込みます。

7.13slapcat・slapadd・slapindex は、データベースを直接扱う

名前が slap で始まるコマンドは、サーバーの上で root が使う管理用の道具です。slapd に頼まず、/var/lib/ldap/ のデータベースを直接読み書きします。そのため、バインドの DN やパスワード（-D、-W）は要らず、アクセス制御も受けません。

コマンドすることslapd が動いているとき
slapcatデータベースの中身を LDIF で書き出す（バックアップ）使える（読むだけ）
slapaddLDIF をデータベースに入れる（リストア、最初の一括登録）止めてから
slapindex索引を作り直す止めてから
slappasswdパスワードのハッシュを作る関係しない
slaptest設定を検査する関係しない

共通のオプションです。

オプション意味
-l ファイルLDIF のファイル（slapcat は書き出し先、slapadd は読み込み元）。省くと標準出力 / 標準入力
-n 番号何番目のデータベースか。-n 0 は設定（cn=config）、-n 1 は最初のデータのデータベース（既定）
-b サフィックスデータベースをサフィックスの DN で選ぶ（-b dc=example,dc=jp）
-F ディレクトリ設定のディレクトリ（slapd.d）を指定する
-f ファイル設定ファイル（slapd.conf）を指定する
-vくわしく表示する
-cエラーがあっても続ける

バックアップとリストアの流れです。

ターミナル
# slapcat -l backup.ldif# slapcat -n 0 -l config.ldif# systemctl stop slapd# slapadd -v -l backup.ldifadded: "dc=example,dc=jp" (00000001)added: "ou=People,dc=example,dc=jp" (00000002)added: "uid=ken,ou=People,dc=example,dc=jp" (00000003)added: "uid=mika,ou=People,dc=example,dc=jp" (00000004)# chown -R openldap:openldap /var/lib/ldap# systemctl start slapd

1 行目がデータ、2 行目が設定のバックアップです。slapcat の LDIF には、entryUUID、createTimestamp、modifiersName など、サーバーが内部で付けた属性も入っています。ldapsearch の結果より完全なので、バックアップには slapcat を使います。

slapindex は、olcDbIndex を足したり変えたりしたあとに、すでに入っているエントリの索引を作り直すコマンドです。

ターミナル
# systemctl stop slapd# slapindex -vindexing id=00000001indexing id=00000002indexing id=00000003indexing id=00000004
注意試験の注意：slapadd と slapindex のあとは、所有者を確かめる

root で slapadd や slapindex を実行すると、/var/lib/ldap/ のファイルの所有者が root になることがあります。slapd は専用のユーザー（Debian 系は openldap、Red Hat 系は ldap）で動くので、そのままでは起動に失敗します。chown -R で所有者を戻します。slapindex は「Running as root! There's a fair chance slapd will fail to start. Check file permissions!」と警告を出します。

コツldapadd と slapadd を取り違えない

ldapadd は、動いている slapd にネットワークごしに頼むので、バインドの DN とパスワードが要り、アクセス制御とスキーマの検査を受けます。slapadd は、止めた slapd のデータベースに直接書くので、認証は要りません。大量のエントリを最初に入れるときや、バックアップから戻すときは slapadd です。

要点まとめ
  • DHCP は DISCOVER → OFFER → REQUEST → ACK。サーバー UDP 67、クライアント UDP 68。DHCPv6 はサーバー 547、クライアント 546
  • /etc/dhcp/dhcpd.conf：subnet … netmask … { range 最初 最後; option routers …; }、default-lease-time、max-lease-time、固定は host { hardware ethernet …; fixed-address …; }。行末は ;。検査は dhcpd -t
  • リースは dhcpd.leases（Debian 系 /var/lib/dhcp/、Red Hat 系 /var/lib/dhcpd/）。空でもファイルが要る。ログは syslog（/var/log/syslog、/var/log/messages）か journalctl -u dhcpd。no free leases は範囲切れ
  • arp -n で IP アドレスと MAC アドレスの対応を見る
  • IPv6 は radvd（/etc/radvd.conf）がルーター広告を流す。AdvSendAdvert on;、prefix … { AdvAutonomous on; };、M フラグは AdvManagedFlag、O フラグは AdvOtherConfigFlag。ゲートウェイは RA で知る
  • PAM の設定は /etc/pam.d/サービス名（あれば /etc/pam.conf は無視。なければ other）。1 行は「タイプ 制御 モジュール 引数」
  • タイプ：auth（本人か）、account（使ってよいか）、password（変更）、session（前後の準備）
  • 制御：required（失敗でも残りを実行）、requisite（失敗で即終了）、sufficient（成功で即終了）、optional、include
  • pam_unix（/etc/shadow）、pam_cracklib（パスワードの強さ。minlen、retry、difok、dcredit=-1）、pam_limits（/etc/security/limits.conf）、pam_listfile（item= sense= file= onerr=）、pam_sss（SSSD）
  • /etc/nsswitch.conf の passwd: files sss は情報を引く順番。認証は PAM。SSSD の設定は /etc/sssd/sssd.conf（root の 0600、[sssd] と [domain/名前]）。キャッシュでオフラインでも認証できる
  • LDAP：エントリ、属性、DN（下から上へカンマでつなぐ）、LDIF（空行で区切る、base64 は ::）。ポートは 389、ldaps は 636
  • クライアント：-x（簡易認証）、-D（バインド DN）、-W（聞く）/ -w（書く）、-H（URI）、-b（検索の起点）、-s base|one|sub、-LLL。フィルタは (&(a=1)(b=2))、(|…)、(!…)
  • ldapadd = ldapmodify -a。ldapmodify の LDIF は changetype: modify と add: / replace: / delete:、区切りは -。ldapdelete DN（-r で下ごと）、ldappasswd -s 新 DN
  • slapd のデータは /var/lib/ldap/。設定は slapd-config（slapd.d/ の cn=config、属性は olc…、再起動なしで反映）。olcSuffix、olcRootDN、olcRootPW、olcDbIndex、olcAccess
  • アクセス制御は to <何に> by <誰が> <どこまで>。上から最初に合った行で決まる。none < auth < compare < search < read < write
  • スキーマ：属性型とオブジェクトクラス。OID、MUST、MAY、SUP、STRUCTURAL / AUXILIARY。core、cosine、nis、inetorgperson
  • slapcat（LDIF に書き出す。-n 0 は設定）、slapadd（LDIF を入れる。slapd を止める）、slapindex（索引を作り直す。slapd を止める）、slappasswd（ハッシュを作る）
