DNS サーバーの仕事は、2 つに分かれます。1 台で両方をすることもできますが、役目は別です。

| 役目 | 別の呼び方 | すること |
| --- | --- | --- |
| **権威サーバー** | コンテンツサーバー、authoritative server | 自分が受け持つ範囲（**ゾーン**）の情報を持ち、聞かれたら答える |
| **キャッシュサーバー** | フルリゾルバ、recursive resolver | クライアントの代わりにルートから順にたどって答えを見つけ、しばらく覚えておく |

クライアントからキャッシュサーバーへの「最後の答えまで調べてほしい」という頼み方を、**再帰問い合わせ**と呼びます。キャッシュサーバーが権威サーバーを 1 つずつたどる聞き方は、**反復問い合わせ**です。

権威サーバーは、同じゾーンを複数の台で受け持ちます。元のデータを持つ台が**プライマリ**（マスター）、その写しをもらう台が**セカンダリ**（スレーブ）です。写しをもらうことを**ゾーン転送**と呼びます。

DNS は **53 番ポート**を使います。ふつうの問い合わせは UDP、ゾーン転送と大きな応答は TCP です（[図解 LinuC 7.4](../../linuc/site/ch07.html#ports)）。

### BIND と、ほかのネームサーバー

**BIND**（Berkeley Internet Name Domain）は、ISC が作っているいちばん広く使われてきた DNS サーバーです。デーモンの名前は **`named`**（name daemon）で、権威サーバーとキャッシュサーバーの両方になれます。

試験では、BIND 以外のサーバーの**役目の違い**も問われます。

| ソフトウェア | 役目 | 特徴 |
| --- | --- | --- |
| **BIND**（`named`） | 権威 + キャッシュ | 両方できる。設定は `named.conf` |
| **dnsmasq** | 小さなネットワーク向けの DNS キャッシュ（フォワーダー）+ **DHCP サーバー** | 軽い。`/etc/hosts` の中身をそのまま答える。設定は `/etc/dnsmasq.conf` |
| **Unbound** | **キャッシュサーバー専用** | DNSSEC の検証ができるフルリゾルバ。設定は `/etc/unbound/unbound.conf`、操作は `unbound-control` |
| **NSD** | **権威サーバー専用** | 再帰問い合わせには答えない。設定は `/etc/nsd/nsd.conf`、操作は `nsd-control` |
| **PowerDNS** | 権威サーバー（`pdns_server`）と、別のプログラムのキャッシュサーバー（`pdns_recursor`） | ゾーンの情報を MySQL や PostgreSQL などの**データベース**に置ける |

Unbound と NSD は、どちらも NLnet Labs が作っています。「キャッシュは Unbound、権威は NSD」と役目を分けて組み合わせる使い方が定番です。

:::warn 試験の注意：専用はどちらか
**Unbound = キャッシュ専用**、**NSD = 権威専用**です。逆にした選択肢がよく出ます。dnsmasq は「DNS と DHCP を 1 つでまかなう」、PowerDNS は「バックエンドにデータベースが使える」が目印です。
:::

## named.conf はどこにあり、どう書くか {#named-conf}

```fig tree named.conf の骨組み。options は全体の設定、zone はゾーン 1 つずつの設定。include で別のファイルを取り込める
{
  root: { label: 'named.conf', note: '文は ; で終わる。ブロックは { … };', children: [
    { label: 'acl "internal" { … };', note: 'アドレスの集まりに名前を付ける' },
    { label: 'options { … };', note: '全体の設定（1 つだけ）', children: [
      { label: 'directory "/var/named";', note: '相対パスの基準になるディレクトリ' },
      { label: 'listen-on / allow-query / recursion …', note: '待ち受けとアクセス制限' },
      { label: 'forwarders { … };', note: '問い合わせを回す先' },
    ] },
    { label: 'zone "example.jp" { … };', note: 'ゾーンごとに 1 つ', children: [
      { label: 'type master;', note: 'master / slave / hint / forward / stub' },
      { label: 'file "example.jp.zone";', note: 'ゾーンファイル（directory からの相対パス）' },
    ] },
    { label: 'key / controls / logging / view', note: '鍵、rndc の受け口、ログ、見せ分け' },
    { label: 'include "…";', note: '別のファイルを取り込む' },
  ] },
}
```

BIND の設定ファイルは **`named.conf`** です。場所はディストリビューションで違います。

| | Red Hat 系（Rocky Linux 9） | Debian 系（Debian 12） |
| --- | --- | --- |
| パッケージ | `bind`（道具は `bind-utils`） | `bind9`（道具は `bind9-dnsutils`、`bind9-utils`） |
| 設定ファイル | **`/etc/named.conf`** | **`/etc/bind/named.conf`**（中で `named.conf.options`、`named.conf.local`、`named.conf.default-zones` を include） |
| `directory` の既定 | **`/var/named`** | `/var/cache/bind` |
| ルートサーバーの一覧（ヒント） | `/var/named/named.ca` | `/usr/share/dns/root.hints` |
| localhost のゾーン | `/var/named/named.localhost` など | `/etc/bind/db.local` など |
| 実行するユーザー | `named` | `bind` |
| systemd のユニット | `named.service` | `named.service`（別名 `bind9.service`） |
| rndc の鍵 | `/etc/rndc.key` | `/etc/bind/rndc.key` |

Rocky Linux 9 の `/etc/named.conf` の主なところです（コメントを除いた抜粋）。

```text
options {
	listen-on port 53 { 127.0.0.1; };
	listen-on-v6 port 53 { ::1; };
	directory 	"/var/named";
	dump-file 	"/var/named/data/cache_dump.db";
	allow-query     { localhost; };
	recursion yes;
	dnssec-validation yes;
	pid-file "/run/named/named.pid";
};

zone "." IN {
	type hint;
	file "named.ca";
};

include "/etc/named.rfc1912.zones";
include "/etc/named.root.key";
```

入れた直後は、**自分自身（127.0.0.1）からの問い合わせだけに答えるキャッシュサーバー**になっています。ほかの機械から使うには、`listen-on` と `allow-query` の両方を広げます。

### 書き方の決まり

- 文は **`;`** で終わる。ブロックは `{ … };` で、閉じたあとにも `;` が要る
- アドレスの並びも、1 つずつ `;` で区切る：`{ 192.168.10.0/24; 127.0.0.1; };`
- コメントは `//`、`#`、`/* … */` の 3 種類
- ファイルの名前やゾーンの名前は `"…"` で囲む

`;` の付け忘れが、いちばん多いまちがいです。あとで見る `named-checkconf` が見つけてくれます。

### options：全体の設定

| ディレクティブ | 意味 |
| --- | --- |
| `directory "パス";` | 作業ディレクトリ。`file` などの**相対パスの基準** |
| `listen-on port 53 { アドレス; };` | 待ち受ける IPv4 アドレス（IPv6 は `listen-on-v6`） |
| `allow-query { … };` | 問い合わせを受け付ける相手 |
| `recursion yes \| no;` | 再帰問い合わせに答えるか（キャッシュサーバーとして働くか） |
| `allow-recursion { … };` | 再帰問い合わせを受け付ける相手 |
| `allow-transfer { … };` | ゾーン転送を許す相手 |
| `forwarders { アドレス; };` | 自分で解決できない問い合わせを回す先（[forwarders](#split)） |
| `forward only \| first;` | フォワーダーだけを使うか、だめなら自分でもたどるか |
| `version "文字列";` | バージョンを聞かれたときに答える文字列 |
| `dnssec-validation auto \| yes \| no;` | DNSSEC の署名を検証するか（[DNSSEC](#dnssec)） |

`{ … }` の中には、アドレス（`192.168.10.1`）、ネットワーク（`192.168.10.0/24`）のほかに、あらかじめ決まった名前が書けます。

| 名前 | 意味 |
| --- | --- |
| `any` | すべて |
| `none` | なし |
| `localhost` | このサーバー自身のアドレス |
| `localnets` | このサーバーがつながっているネットワーク |

自分で名前を付けるには、**`acl`** 文を使います。`acl "internal" { 192.168.10.0/24; localhost; };` と書いておけば、`allow-query { internal; };` のように使えます。

### zone：ゾーンごとの設定

```text
zone "example.jp" {
	type master;
	file "example.jp.zone";
};

zone "10.168.192.in-addr.arpa" {
	type master;
	file "192.168.10.rev";
};

zone "example.com" {
	type slave;
	masters { 192.168.10.1; };
	file "slaves/example.com.zone";
};
```

`file` が相対パスなら、`options` の **`directory` からの相対パス**です。`directory "/var/named";` のとき、上の `example.jp.zone` は `/var/named/example.jp.zone` を指します。ゾーンファイルの名前に決まりはなく、`zone` 文の `file` に書いたものが読まれます。

| `type` | 意味 | 一緒に書くもの |
| --- | --- | --- |
| **`master`**（`primary`） | このサーバーが元のデータを持つ | `file` |
| **`slave`**（`secondary`） | プライマリから写しをもらう | `masters { プライマリのアドレス; };`（`primaries`）、`file`（写しの保存先） |
| **`hint`** | ルートサーバーの一覧。ゾーン `"."` にだけ使う | `file`（`named.ca` など） |
| **`forward`** | このゾーンの問い合わせだけ、指定したサーバーへ回す | `forwarders { … };` |
| `stub` | 相手のゾーンの NS レコードだけを写す | `masters { … };` |

新しい BIND では、`master` / `slave` / `masters` の代わりに `primary` / `secondary` / `primaries` とも書けます（9.18 でどちらも `named-checkconf` を通ることを確かめました）。試験と多くの資料は、まだ `master` と `slave` です。

:::warn 試験の注意：hint と forward を取り違えない
`type hint` は「**ルートサーバーの場所を書いたファイル**を読む」で、キャッシュサーバーが最初にどこへ聞くかを知るためのものです。`type forward` は「このゾーンの問い合わせを**別のサーバーへ回す**」です。セカンダリに要るのは `type slave` と **`masters`** で、`file` はなくても動きますが、あると再起動のあとすぐ答えられます。
:::

## rndc と named-checkconf で、動かしながら管理する {#rndc}

### named-checkconf：設定の文法を調べる

**`named-checkconf`** は、`named.conf` の文法を調べるコマンドです。ファイルを指定しなければ、既定の場所（Red Hat 系は `/etc/named.conf`、Debian 系は `/etc/bind/named.conf`）を読みます。**問題がなければ、何も表示せずに終了ステータス 0 で終わります**。

```console
# named-checkconf
# echo $?
0
# named-checkconf /tmp/bad.conf
/tmp/bad.conf:1: missing ';' before '}'
/tmp/bad.conf:2: missing ';' before end of file
# named-checkconf /tmp/bad2.conf
/tmp/bad2.conf:3: boolean expected near 'maybe'
```

エラーは「ファイル名:行番号: 理由」の形です。1 つ目は `;` の付け忘れ、2 つ目は `recursion maybe;` のように yes / no でない値を書いた例です。

| オプション | 意味 |
| --- | --- |
| （なし） | 文法だけを調べる。ゾーンファイルは読まない |
| **`-z`** | `named.conf` にある**マスターゾーンのゾーンファイルも読み込んで**調べる |
| `-p` | 読み込んだ設定を、include を展開し、形を整えて表示する |
| `-t ディレクトリ` | chroot した先のディレクトリを基準にして調べる |

```console
# named-checkconf -z
zone example.jp/IN: loaded serial 2026111701
zone 10.168.192.in-addr.arpa/IN: loaded serial 2026111701
zone localhost/IN: loaded serial 2
zone 127.in-addr.arpa/IN: loaded serial 1
```

Rocky Linux 9 の `named.service` は、起動の前に `named-checkconf -z` を実行します。設定かゾーンファイルにまちがいがあれば、`named` は起動しません。

### rndc：動いている named に指示する

**`rndc`**（remote name daemon control）は、動いている `named` に指示を送るコマンドです。`named` は **TCP の 953 番**で指示を待ち、`rndc` と `named` が同じ**共有鍵**を持っているときだけ受け付けます。

```console
# rndc status
version: BIND 9.18.49-1~deb12u3-Debian (Extended Support Version) <id:> (unknown)
boot time: Mon, 16 Nov 2026 21:19:04 GMT
last configured: Mon, 16 Nov 2026 21:19:04 GMT
configuration file: /etc/bind/named.conf
number of zones: 7 (0 automatic)
debug level: 0
xfers running: 0
query logging is OFF
recursive clients: 0/900/1000
tcp clients: 0/150
server is up and running
# rndc reload example.jp
zone reload queued
# rndc reload
server reload successful
```

| コマンド | 意味 |
| --- | --- |
| `rndc status` | サーバーの状態を表示する |
| **`rndc reload`** | 設定ファイルと**すべてのゾーン**を読み直す |
| `rndc reload ゾーン` | そのゾーンだけを読み直す |
| **`rndc reconfig`** | 設定ファイルを読み直し、**新しく足したゾーンだけ**を読み込む（すでにあるゾーンのファイルは読み直さない） |
| **`rndc flush`** | キャッシュをすべて捨てる（`rndc flushname 名前` はその名前だけ） |
| `rndc dumpdb` | キャッシュなどをファイル（`named_dump.db`）に書き出す |
| `rndc querylog on \| off` | 問い合わせのログを出す / 止める |
| `rndc retransfer ゾーン` | セカンダリで、シリアルを比べずにゾーン転送をやり直す |
| `rndc refresh ゾーン` | セカンダリで、プライマリのシリアルを確かめに行く |
| `rndc notify ゾーン` | プライマリで、セカンダリへ NOTIFY を送り直す |
| `rndc freeze` / `thaw` | 動的更新を止める / 再開する |
| **`rndc stop`** | 書きかけの更新を保存してから止める |
| `rndc halt` | 保存せずにすぐ止める |

鍵は、`named.conf` の `key` 文と `controls` 文（`named` の側）と、`/etc/rndc.conf` か `rndc.key`（`rndc` の側）に書きます。`controls` 文を書かなければ、`named` は `rndc.key` を読んで 127.0.0.1 からの指示だけを受け付けます。鍵のファイルは **`rndc-confgen -a`** で作れます。

```text
key "rndc-key" {
	algorithm hmac-sha256;
	secret "sM4kGMI6X08gXfRdbpeaT9PP3tljS87KsQPiPJsV3v8=";
};

controls {
	inet 127.0.0.1 port 953
		allow { 127.0.0.1; } keys { "rndc-key"; };
};
```

鍵が合わない、または `named` が鍵のファイルを読めないと、`rndc` は次のように失敗します。

```console
# rndc status
rndc: connection to remote host closed.
* This may indicate that the
* remote server is using an older
* version of the command protocol,
* this host is not authorized to connect,
* the clocks are not synchronized,
* the key signing algorithm is incorrect
* or the key is invalid.
```

:::warn 試験の注意：reload と reconfig
`rndc reload` は**全部**読み直します。`rndc reconfig` は「設定ファイル + **新しいゾーンだけ**」です。ゾーンファイルの中身を書き換えたときは、`reconfig` では反映されません。`rndc reload` か `rndc reload ゾーン名` を使います。`systemctl reload named` も、中で `rndc reload` を実行します。
:::

### ログはどこに出るか

`named` のログは、既定では syslog に送られます。systemd の機械では `journalctl -u named` で見ます。ファイルでは、Red Hat 系は `/var/log/messages`、Debian 系は `/var/log/syslog` です。

```text
16-Nov-2026 21:21:11.158 zone example.jp/IN: loaded serial 2026111701
16-Nov-2026 21:21:36.531 client @0xffff9a800098 127.0.0.1#48454 (www.example.jp): query: www.example.jp IN A +E(0)K (127.0.0.1)
```

1 行目は、ゾーンを読み込んだときのログです。読み込んだ**シリアル**が出るので、書き換えが反映されたかを確かめられます。2 行目は `rndc querylog on` にしたときの問い合わせのログで、「だれが（127.0.0.1 の 48454 番ポート）、何を（www.example.jp の A）」聞いたかがわかります。

出す先を細かく決めたいときは、`named.conf` の **`logging`** 文で、`channel`（出す先）と `category`（ログの種類）を組み合わせます。

## dig・host・nslookup で、サーバーの答えを確かめる {#dig}

レベル1 で使った `dig` と `host` は、DNS サーバーを作る側にとっては**検査の道具**です（[図解 LinuC 7.12](../../linuc/site/ch07.html#dig)）。3 つとも `/etc/hosts` は見ずに、DNS サーバーに直接聞きます。

作ったばかりのサーバーに、`@` で相手を指定して聞きます。

```console
$ dig @127.0.0.1 www.example.jp

;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 13350
;; flags: qr aa rd; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
;; WARNING: recursion requested but not available

;; QUESTION SECTION:
;www.example.jp.			IN	A

;; ANSWER SECTION:
www.example.jp.		3600	IN	A	192.168.10.10

;; Query time: 0 msec
;; SERVER: 127.0.0.1#53(127.0.0.1) (UDP)
```

レベル2 では、`flags:` の行を読めるようにします。

| フラグ | 名前 | 意味 |
| --- | --- | --- |
| `qr` | query response | これは応答である |
| **`aa`** | authoritative answer | **そのゾーンを持つ権威サーバー自身の答え**（キャッシュではない） |
| `rd` | recursion desired | クライアントが再帰を頼んだ（`dig` は既定で頼む） |
| **`ra`** | recursion available | サーバーが再帰に応じられる |
| `ad` | authenticated data | DNSSEC の検証に成功した答え |

上の例は、`aa` があって `ra` がありません。「このゾーンの権威サーバーが答えた。ただし、このサーバーは再帰に応じない」と読めます。`WARNING: recursion requested but not available` も同じことを言っています。

| `status` | 意味 |
| --- | --- |
| `NOERROR` | 成功（答えが 0 件でも、名前があれば NOERROR） |
| `NXDOMAIN` | その名前はない |
| `SERVFAIL` | サーバーが答えを作れなかった（ゾーンの読み込み失敗、フォワーダーに届かない、DNSSEC の検証失敗など） |
| `REFUSED` | 断られた（`allow-query` や `allow-recursion` で許されていない、そのゾーンを持っていない） |

`recursion no;` の権威サーバーに、持っていないゾーンの名前を聞くと `REFUSED` です。

```console
$ dig @127.0.0.1 www.debian.org | grep -E 'status|flags'
;; ->>HEADER<<- opcode: QUERY, status: REFUSED, id: 43987
;; flags: qr rd; QUERY: 1, ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 1
```

| 使い方 | 意味 |
| --- | --- |
| `dig @サーバー 名前 種類` | そのサーバーに聞く。種類は `A`（既定）、`MX`、`NS`、`SOA`、`TXT`、`ANY` など。`-t 種類` でも同じ |
| `dig -x アドレス` | 逆引き（PTR） |
| `dig +short …` | 答えの値だけ |
| `dig +norecurse …` | 再帰を頼まない（`rd` を立てない）。権威サーバーの検査に使う |
| `dig +trace 名前` | ルートから順に、反復問い合わせを自分でたどって見せる |
| `dig +dnssec …` | DNSSEC の署名（RRSIG）も一緒にもらう |
| `dig +tcp …` | TCP で聞く |
| `dig -p ポート …` | 53 番以外のポートに聞く |
| `dig @サーバー ゾーン AXFR` | ゾーン転送を試す |
| `dig -k 鍵ファイル …`、`dig -y 名前:鍵 …` | TSIG の鍵を付けて聞く（[TSIG](#tsig)） |

`host` と `nslookup` は、サーバーを**最後の引数**に書きます。

```console
$ host -t MX example.jp 127.0.0.1
Using domain server:
Name: 127.0.0.1
Address: 127.0.0.1#53
Aliases: 

example.jp mail is handled by 10 mail.example.jp.
$ nslookup -type=MX example.jp 127.0.0.1
Server:		127.0.0.1
Address:	127.0.0.1#53

example.jp	mail exchanger = 10 mail.example.jp.
```

| コマンド | 使い方 |
| --- | --- |
| `host 名前 [サーバー]` | A・AAAA・MX をまとめて引く |
| `host -t 種類 名前` | 種類を指定する |
| `host -a 名前` | くわしく、すべての種類（`-v -t ANY` と同じ） |
| `host -l ゾーン [サーバー]` | ゾーン転送（AXFR）で、ゾーンの中のホストを一覧にする |
| `nslookup 名前 [サーバー]` | 名前を引く |
| `nslookup -type=種類 名前` | 種類を指定する |
| `nslookup`（引数なし） | 対話モード。`server アドレス` で聞く先、`set type=MX` で種類を変える |

:::tip どのサーバーに聞いたかを必ず確かめる
設定を変えたのに答えが変わらないときは、まず `dig` の最後の `SERVER:` の行を見ます。`@` を付け忘れると、`/etc/resolv.conf` のキャッシュサーバーに聞いていて、古い答え（キャッシュ）を見ていることがあります。キャッシュの残り時間は、答えの 2 列目の TTL です。
:::

## ゾーンファイルはどう書くか {#zonefile}

```fig graph リソースレコード 1 行の読み方。名前・TTL・クラスは省略できる。名前を省くと、すぐ上の行と同じ名前になる
{
  col: 176, row: 92,
  nodes: [
    { id: 'n', label: 'www', sub: '名前\n（省略 = 上と同じ）', x: 0, y: 0 },
    { id: 't', label: '3600', sub: 'TTL（秒）\n（省略 = $TTL）', x: 1, y: 0 },
    { id: 'c', label: 'IN', sub: 'クラス\n（インターネット）', x: 2, y: 0 },
    { id: 'y', label: 'A', sub: 'タイプ\n（レコードの種類）', x: 3, y: 0, kind: 'accent' },
    { id: 'd', label: '192.168.10.10', sub: 'データ\n（種類で形が違う）', x: 4, y: 0, kind: 'stack' },
  ],
  edges: [ { from: 'n', to: 't' }, { from: 't', to: 'c' }, { from: 'c', to: 'y' }, { from: 'y', to: 'd' } ],
}
```

**ゾーンファイル**は、そのゾーンの情報を**リソースレコード**（資源レコード）の並びで書いたテキストファイルです。置く場所は `named.conf` の `directory` と `file` で決まります（Red Hat 系なら `/var/named/` の下、Debian 系なら `/etc/bind/` や `/var/lib/bind/` の下に置くのがふつうです）。

`example.jp` のゾーンファイルの例です。Docker の中で `named-checkzone` を通し、`named` に読ませて確かめたものです。

```text
$TTL 3600
@	IN	SOA	ns1.example.jp. admin.example.jp. (
		2026111701	; Serial
		10800		; Refresh
		3600		; Retry
		604800		; Expire
		900 )		; Negative Cache TTL
	IN	NS	ns1.example.jp.
	IN	NS	ns2.example.jp.
	IN	MX	10 mail.example.jp.
	IN	TXT	"v=spf1 mx -all"
ns1	IN	A	192.168.10.1
ns2	IN	A	192.168.10.2
mail	IN	A	192.168.10.5
www	IN	A	192.168.10.10
www	IN	AAAA	2001:db8::10
ftp	IN	CNAME	www
```

### 書式の決まり

| 書き方 | 意味 |
| --- | --- |
| **`$TTL 3600`** | TTL を省いたレコードの既定の TTL（キャッシュしてよい秒数） |
| `$ORIGIN example.jp.` | 名前の後ろに補うドメイン（**オリジン**）を変える。書かなければ、`named.conf` の `zone` 文のゾーン名 |
| `$INCLUDE ファイル` | 別のファイルを取り込む |
| `$GENERATE 1-3 host$ A 192.168.30.$` | 連番のレコードをまとめて作る（`host1`〜`host3`） |
| **`@`** | オリジン（ゾーン名）そのもの |
| 行の先頭が空白 | **すぐ上のレコードと同じ名前** |
| `;` | そこから行末までコメント |
| `( … )` | 1 つのレコードを複数行に分けて書く |
| 時間の単位 | 数字だけなら秒。`3H`（時間）、`1D`（日）、`1W`（週）、`15M`（分）とも書ける |

いちばん大事な決まりは、**最後のドット**です。

- 名前の最後に `.` がある → **完全な名前**（FQDN）。そのまま使われる
- 最後に `.` がない → **相対の名前**。後ろにオリジンが補われる

上の例の `ns1` は `ns1.example.jp.` になり、`ftp IN CNAME www` の `www` は `www.example.jp.` になります。逆に、`IN MX 10 mail.example.jp`（最後のドットなし）と書くと、`mail.example.jp.example.jp.` になってしまいます。`named-checkzone` で確かめると、次のように警告が出ます。

```console
# named-checkzone example.jp /tmp/e1
zone example.jp/IN: example.jp/MX 'mail.example.jp.example.jp' has no address records (A or AAAA)
zone example.jp/IN: loaded serial 2026111701
OK
```

:::warn 試験の注意：ドットの付け忘れ
ゾーンファイルで FQDN を書くときは、**最後に `.` を付けます**。付け忘れると、オリジンが 2 重に付きます。文法としては正しいので、`named` はそのまま読み込んでしまいます（上の例も最後は `OK` です）。SOA、NS、MX、CNAME、PTR の右側が特にまちがえやすいところです。
:::

### SOA レコード：ゾーンの管理情報

**SOA**（Start Of Authority）は、ゾーンファイルの最初に 1 つだけ書くレコードです。

```text
@  IN  SOA  ns1.example.jp. admin.example.jp. (
       2026111701  10800  3600  604800  900 )
```

| 順番 | 名前 | 例 | 意味 |
| --- | --- | --- | --- |
| 1 | MNAME | `ns1.example.jp.` | プライマリのネームサーバーの名前 |
| 2 | RNAME | `admin.example.jp.` | 管理者のメールアドレス。**`@` を `.` に置き換えて**書く（admin@example.jp） |
| 3 | **シリアル** | `2026111701` | ゾーンの版の番号。**書き換えるたびに増やす** |
| 4 | リフレッシュ | `10800` | セカンダリがプライマリのシリアルを確かめに行く間隔 |
| 5 | リトライ | `3600` | 確かめに失敗したとき、次に試すまでの間隔 |
| 6 | エクスパイア | `604800` | プライマリに届かないまま、セカンダリが答え続けてよい期間 |
| 7 | ミニマム | `900` | **ネガティブキャッシュの TTL**（「その名前はない」という答えを覚えておく時間） |

シリアルは、`YYYYMMDDnn`（年月日 + その日の何回目か）の形にする習慣があります。大事なのは形ではなく、**前より大きい数にする**ことです。

### よく使うレコード

| タイプ | データ | 例 |
| --- | --- | --- |
| **`NS`** | そのゾーンのネームサーバーの**名前** | `@ IN NS ns1.example.jp.` |
| **`A`** | IPv4 アドレス | `www IN A 192.168.10.10` |
| **`AAAA`** | IPv6 アドレス | `www IN AAAA 2001:db8::10` |
| **`MX`** | **優先度**とメールサーバーの**名前** | `@ IN MX 10 mail.example.jp.` |
| **`CNAME`** | 別名の本当の名前（正式名） | `ftp IN CNAME www` |
| **`PTR`** | アドレスに対応する名前（逆引き） | `10 IN PTR www.example.jp.` |
| `TXT` | 文字列（SPF などに使う） | `@ IN TXT "v=spf1 mx -all"` |
| `SRV` | 優先度、重み、ポート、サーバーの名前 | `_sip._tcp IN SRV 10 60 5060 sip.example.jp.` |

決まりごとがいくつかあります。

- **NS は 1 つ以上要る**。NS レコードのないゾーンは読み込めません（`has no NS records`）
- **MX の優先度は、数が小さいほうが先**に使われます
- **NS と MX の右側は名前**です。IP アドレスは書けません。その名前の A レコードを別に書きます
- **CNAME を書いた名前には、ほかのレコードを書けません**。NS や MX の右側に、CNAME で付けた別名を書くのもまちがいです
- 同じ名前に A レコードを複数書くと、順番を変えながら全部を答えます（**DNS ラウンドロビン**）

```console
# named-checkzone example.jp /tmp/e2
dns_master_load: /tmp/e2:18: ftp.example.jp: CNAME and other data
zone example.jp/IN: loading from master file /tmp/e2 failed: CNAME and other data
zone example.jp/IN: not loaded due to errors.
# named-checkzone example.jp /tmp/e3
zone example.jp/IN: example.jp/MX 'ftp.example.jp' is a CNAME (illegal)
```

1 つ目は、`ftp` に CNAME と A の両方を書いた例です。2 つ目は、MX の右側に CNAME の名前を書いた例です。

## 逆引きのゾーンは、アドレスを逆に並べる {#reverse}

IP アドレスから名前を引く**逆引き**も、ゾーンとして書きます。IPv4 の逆引きのゾーン名は、**ネットワーク部のオクテットを逆の順に並べて、`.in-addr.arpa` を付けた**ものです。

| ネットワーク | 逆引きのゾーン名 |
| --- | --- |
| `192.168.10.0/24` | **`10.168.192.in-addr.arpa`** |
| `172.16.0.0/16` | `16.172.in-addr.arpa` |
| `10.0.0.0/8` | `10.in-addr.arpa` |
| IPv6 `2001:db8::/32` | `8.b.d.0.1.0.0.2.ip6.arpa`（16 進 1 桁ずつを逆に並べる） |

`named.conf` と、ゾーンファイルの例です。

```text
zone "10.168.192.in-addr.arpa" {
	type master;
	file "192.168.10.rev";
};
```

```text
$TTL 3600
@	IN	SOA	ns1.example.jp. admin.example.jp. 2026111701 10800 3600 604800 900
	IN	NS	ns1.example.jp.
1	IN	PTR	ns1.example.jp.
10	IN	PTR	www.example.jp.
```

左の `10` は相対の名前なので、オリジンが補われて `10.10.168.192.in-addr.arpa.` になります。これが `192.168.10.10` の逆引きの名前です。右側は別のゾーンの名前なので、**必ず FQDN で、最後に `.` を付けます**。

```console
$ dig @127.0.0.1 -x 192.168.10.10 +short
www.example.jp.
$ host 192.168.10.10 127.0.0.1
10.10.168.192.in-addr.arpa domain name pointer www.example.jp.
```

正引き（A）と逆引き（PTR）は、別のゾーンの別のレコードです。A レコードを足しても、PTR は自動では増えません。

## named-checkzone と named-compilezone、そしてゾーン転送 {#checkzone}

### named-checkzone：ゾーンファイルを調べる

**`named-checkzone`** は、ゾーンファイルの文法と中身を調べます。引数は「**ゾーン名、ファイル名**」の順です。

```console
# named-checkzone example.jp /etc/bind/db.example.jp
zone example.jp/IN: loaded serial 2026111701
OK
# named-checkzone example.jp /tmp/e4
zone example.jp/IN: has no NS records
zone example.jp/IN: not loaded due to errors.
```

成功すると、読み込んだシリアルと `OK` を表示して、終了ステータス 0 で終わります。ゾーン名を渡すのは、ファイルの中の `@` や相対の名前に補うオリジンが、ファイルだけでは決まらないからです。

| オプション | 意味 |
| --- | --- |
| `-D` | 読み込んだゾーンを、名前をすべて FQDN にした形で表示する |
| `-f 形式` | 入力の形式（`text` か `raw`。既定は text） |
| `-F 形式` | 出力の形式 |
| `-o ファイル` | 出力先（`-` は標準出力） |
| `-t ディレクトリ` | chroot した先を基準にする |

### named-compilezone：形式を変える

**`named-compilezone`** は `named-checkzone` と同じプログラムですが、調べたあとで**ゾーンを別の形式で書き出します**。そのため、**`-o` で出力先を必ず指定**します。

ゾーンファイルには、人が読める **text** 形式のほかに、`named` が速く読める **raw**（バイナリ）形式があります。いまの BIND では、**セカンダリがゾーン転送でもらって保存するファイルは、既定で raw 形式**です。`cat` では読めないので、`named-compilezone` で text に直します。

```console
# named-compilezone -f text -F raw -o example.jp.raw example.jp db.example.jp
zone example.jp/IN: loaded serial 2026111701
dump zone to example.jp.raw...done
OK
# named-compilezone -f raw -F text -o example.jp.txt example.jp slaves/db.example.jp
zone example.jp/IN: loaded serial 2026111701
dump zone to example.jp.txt...done
OK
```

`-f` が入力（from）、`-F` が出力の形式です。大文字と小文字を取り違えないようにします。

### ゾーン転送とシリアル

```fig seq プライマリからセカンダリへゾーンが伝わるまで。セカンダリは SOA のシリアルを比べ、プライマリのほうが大きいときだけ転送する
{
  colw: 380,
  actors: [
    { id: 'p', label: 'プライマリ（type master）' },
    { id: 's', label: 'セカンダリ（type slave）' },
  ],
  msgs: [
    { self: 'p', label: 'ゾーンファイルを直し、シリアルを増やして rndc reload' },
    { from: 'p', to: 's', label: 'NOTIFY（ゾーンが変わった）' },
    { from: 's', to: 'p', label: 'SOA を問い合わせる' },
    { self: 's', label: 'シリアルが自分のものより大きいか比べる' },
    { from: 's', to: 'p', label: 'ゾーン転送を頼む（AXFR / IXFR、TCP 53）', style: 'accent' },
    { from: 'p', to: 's', label: 'ゾーンの中身' },
    { note: 'NOTIFY がなくても、リフレッシュの間隔ごとに SOA を確かめる', at: ['p', 's'] },
  ],
}
```

ゾーン転送には、ゾーン全体を送る **AXFR** と、変わったところだけを送る **IXFR** があります。セカンダリは、**プライマリのシリアルが自分の持つ写しより大きいときだけ**転送します。

Docker の中でプライマリとセカンダリを動かしたときの、セカンダリのログです。

```text
zone example.jp/IN: Transfer started.
transfer of 'example.jp/IN' from 127.0.0.1#53: connected using 127.0.0.1#53 TSIG xfer-key
zone example.jp/IN: transferred serial 2026111701: TSIG 'xfer-key'
transfer of 'example.jp/IN' from 127.0.0.1#53: Transfer status: success
```

:::warn 試験の注意：シリアルを増やし忘れると、セカンダリに伝わらない
プライマリのゾーンファイルを書き換えても、**シリアルを増やさなければ、セカンダリは「変わっていない」と判断して転送しません**。「プライマリでは新しい答え、セカンダリでは古い答えが返る」という問題の原因は、まずこれです。シリアルを前より小さくしてしまったときも同じで、プライマリのログには `zone serial (2026111700/2026111701) has gone backwards` と出ます。
:::

だれにでもゾーン転送を許すと、ゾーンの中のホストの一覧が外に漏れます。プライマリでは **`allow-transfer`** で相手をセカンダリだけに絞ります。

```text
zone "example.jp" {
	type master;
	file "example.jp.zone";
	allow-transfer { 192.168.10.2; };
};
```

許されていない相手が転送を試すと、`dig` は `; Transfer failed.` と表示します。

## named を root でなく、chroot の中で動かす {#chroot}

DNS サーバーは、インターネットのだれからでも問い合わせが届く場所に置きます。`named` に弱点が見つかって乗っ取られたときの被害を小さくするために、2 つの手を打ちます。

| 手 | `named` のオプション | 効き目 |
| --- | --- | --- |
| **root でないユーザーで動かす** | **`-u ユーザー`** | 乗っ取られても、そのユーザーの権限しか使えない |
| **chroot の中で動かす** | **`-t ディレクトリ`** | 乗っ取られても、そのディレクトリの外のファイルが見えない |

`named` は 53 番ポート（1024 番より小さい特権ポート）を開くので、起動は root でします。`-u` を付けると、ポートを開いたあとで、そのユーザーに切り替わります。

```console
# grep ExecStart /usr/lib/systemd/system/named.service
ExecStart=/usr/sbin/named -u named -c ${NAMEDCONF} $OPTIONS
# cat /etc/default/named
OPTIONS="-u bind"
# ps -eo user,args | grep '[n]amed'
bind     named -u bind
```

1 つ目は Rocky Linux 9、2 つ目からは Debian 12 です。どちらも、入れたときから root でないユーザー（`named`、`bind`）で動きます。このユーザーが、ゾーンファイルを読め、セカンダリの保存先（`slaves/` など）に書ける必要があります。

**chroot** は、プロセスにとっての `/` を付け替える仕組みでした（[図解 Linux 19.2](../../linux/site/ch19.html#chroot)）。`named -t /var/named/chroot` で起動すると、`named` には `/var/named/chroot` が `/` に見えます。設定ファイルもゾーンファイルも、その中に置きます。

| `named` から見たパス | 本当の場所 |
| --- | --- |
| `/etc/named.conf` | `/var/named/chroot/etc/named.conf` |
| `/var/named/example.jp.zone` | `/var/named/chroot/var/named/example.jp.zone` |

Red Hat 系では、**`bind-chroot`** パッケージを入れ、`named.service` の代わりに **`named-chroot.service`** を使います。chroot の先は `/var/named/chroot` です。

```console
# grep ExecStart /usr/lib/systemd/system/named-chroot.service
ExecStart=/usr/sbin/named -u named -c ${NAMEDCONF} -t /var/named/chroot $OPTIONS
```

| `named` のオプション | 意味 |
| --- | --- |
| `-u ユーザー` | そのユーザーに切り替えて動く |
| `-t ディレクトリ` | そのディレクトリに chroot する |
| `-c ファイル` | 設定ファイルを指定する |
| `-f` | フォアグラウンドで動く（`-g` は、さらにログを標準エラー出力に出す） |
| `-p ポート` | 待ち受けるポートを変える |

:::note -t は -u と一緒に使う
root のままのプロセスは、chroot から抜け出す手段を持っています。そのため、`-t` だけでは守りになりません。**`-u` と `-t` を両方付ける**のが決まりです。chroot した設定を調べるときは、`named-checkconf -t /var/named/chroot` のように、検査のコマンドにも `-t` を付けます。
:::

### 知らせる情報を減らす

権威サーバーとして外に見せる台では、余計な仕事と情報を止めます。

```text
options {
	recursion no;
	allow-transfer { none; };
	version "unknown";
};
```

- **`recursion no;`**：再帰問い合わせに応じません。自分が持つゾーンの問い合わせには、これまでどおり答えます。だれの再帰問い合わせにも応じるサーバー（**オープンリゾルバ**）は、ほかの機械を攻撃する踏み台にされます
- **`allow-transfer { none; };`**：ゾーン転送を、既定ではだれにも許しません（`zone` 文の中で、セカンダリにだけ許します）
- **`version "…";`**：`dig @サーバー version.bind chaos txt` でバージョンを聞かれたときに、本当のバージョンの代わりにこの文字列を答えます

```console
$ dig @127.0.0.1 version.bind chaos txt +short
"unknown"
```

## forwarders で、内向きと外向きを分ける {#split}

```fig graph forwarders による分割構成。社内のサーバーは社内のゾーンだけを自分で答え、ほかは全部フォワーダーへ回す。外に公開する権威サーバーは、再帰をしない
{
  col: 235, row: 104,
  nodes: [
    { id: 'cl', label: '社内のクライアント', x: 0, y: 0, kind: 'ext', mono: false },
    { id: 'in', label: '内向きサーバー', sub: '社内のゾーン + キャッシュ\nforwarders、forward only', x: 1, y: 0, kind: 'accent', mono: false },
    { id: 'fw', label: 'フォワーダー', sub: 'DMZ や ISP の\nキャッシュサーバー', x: 2, y: 0, mono: false },
    { id: 'net', label: 'インターネット', sub: 'ルート、jp、…', x: 3, y: 0.5, kind: 'muted', mono: false },
    { id: 'ex', label: '外向きサーバー', sub: '公開するゾーンだけ\nrecursion no', x: 2, y: 1, kind: 'stack', mono: false },
  ],
  edges: [
    { from: 'cl', to: 'in', label: '再帰' },
    { from: 'in', to: 'fw', label: '回す' },
    { from: 'fw', to: 'net', label: '反復' },
    { from: 'net', to: 'ex', label: '問い合わせ', style: 'dashed' },
  ],

```

**`forwarders`** は、自分が持っていない名前の問い合わせを、**自分でルートからたどる代わりに、別のキャッシュサーバーへ回す**設定です。回す先を**フォワーダー**と呼びます。

```text
options {
	directory "/var/named";
	forwarders { 192.168.1.1; 8.8.8.8; };
	forward only;
	allow-query { 192.168.10.0/24; localhost; };
};
```

| 設定 | 意味 |
| --- | --- |
| `forwarders { アドレス; … };` | 回す先のサーバー |
| **`forward first;`**（既定） | まずフォワーダーに聞き、答えがもらえなければ**自分でもルートからたどる** |
| **`forward only;`** | フォワーダーにだけ聞く。答えがもらえなければ、**自分ではたどらずに失敗**（SERVFAIL）を返す |

Docker の中で、`forward only` のサーバーに、フォワーダーが答えられない名前を聞いた結果です。

```console
$ dig -p 5353 @127.0.0.1 www.debian.org | grep -E 'status|flags'
;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL, id: 9985
;; flags: qr rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 1
```

`forwarders` を使うと、役目の違うサーバーに分けられます。これが**分割構成**（スプリット DNS）です。

- **内向きサーバー**：社内のゾーン（社内だけで使う名前）を持ち、社内のクライアントの再帰問い合わせに答える。それ以外の名前は、`forward only` でフォワーダーに回す。インターネットへ直接出ていくのはフォワーダーだけなので、ファイアウォールで通す通信を絞れる
- **外向きサーバー**：公開するゾーンだけを持つ権威サーバー。`recursion no` にして、社内の名前は持たせない

特定のゾーンだけを別のサーバーに回すには、`type forward` のゾーンを書きます。

```text
zone "corp.example" {
	type forward;
	forward only;
	forwarders { 10.0.0.53; };
};
```

:::deep 1 台で見せ分ける：view
1 台の `named` で、聞いてきた相手によって答えを変えることもできます。`view` 文を使います。

```text
view "internal" {
	match-clients { 192.168.10.0/24; };
	recursion yes;
	zone "example.jp" { type master; file "example.jp.internal"; };
};
view "external" {
	match-clients { any; };
	recursion no;
	zone "example.jp" { type master; file "example.jp.external"; };
};
```

`match-clients` に合った最初の view が使われます。view を 1 つでも使うなら、**すべての zone 文を view の中に書く**決まりです。外に書くと `when using 'view' statements, all zones must be in views` というエラーになります。
:::

## TSIG：共有鍵で、ゾーン転送の相手を確かめる {#tsig}

`allow-transfer { 192.168.10.2; };` のように IP アドレスで相手を絞る方法は、送信元を偽られると破られます。**TSIG**（Transaction SIGnature）は、**2 台のサーバーが同じ秘密の鍵（共有鍵）を持ち**、やり取りするメッセージにその鍵で作った署名（HMAC）を付ける仕組みです。受け取った側は、同じ鍵で署名を確かめます。

TSIG が守るのは、**サーバーどうしのやり取り**（ゾーン転送、NOTIFY、動的更新、`rndc`）です。相手が本物であることと、途中で書き換えられていないことを確かめます。**中身の暗号化はしません**。

### 鍵を作る

いまの BIND では、**`tsig-keygen`** で作ります。`named.conf` にそのまま書ける `key` 文が出ます。

```console
# tsig-keygen -a hmac-sha256 xfer-key
key "xfer-key" {
	algorithm hmac-sha256;
	secret "r/hHwDH1Jkk7lGOMqxVrdShmTIKSUIm29dp4FyozA8Y=";
};
```

:::note 古い作り方：dnssec-keygen -a HMAC-…
以前の BIND では、TSIG の鍵も **`dnssec-keygen`** で作りました。`dnssec-keygen -a HMAC-SHA256 -b 256 -n HOST xfer-key` のように、アルゴリズムに `HMAC-…`、鍵の種類に `-n HOST` を指定し、できた `K*.private` の `Key:` の値を `secret` に写します。試験の範囲の用語も `dnssec-keygen` と TSIG が並んでいるので、この形を覚えておきます。ただし、Rocky Linux 9 の BIND 9.16 と Debian 12 の BIND 9.18 では、`dnssec-keygen: fatal: unknown algorithm HMAC-SHA256` となって使えません。
:::

### named.conf に書く

**同じ `key` 文を、プライマリとセカンダリの両方**に書きます。鍵の名前も同じにします。

プライマリ：

```text
key "xfer-key" {
	algorithm hmac-sha256;
	secret "r/hHwDH1Jkk7lGOMqxVrdShmTIKSUIm29dp4FyozA8Y=";
};

zone "example.jp" {
	type master;
	file "example.jp.zone";
	allow-transfer { key xfer-key; };
};
```

セカンダリ：

```text
key "xfer-key" {
	algorithm hmac-sha256;
	secret "r/hHwDH1Jkk7lGOMqxVrdShmTIKSUIm29dp4FyozA8Y=";
};

server 192.168.10.1 {
	keys { xfer-key; };
};

zone "example.jp" {
	type slave;
	masters { 192.168.10.1; };
	file "slaves/example.jp.zone";
};
```

| 文 | 意味 |
| --- | --- |
| `key "名前" { algorithm …; secret "…"; };` | 鍵を定義する |
| `allow-transfer { key 名前; };` | **この鍵の署名が付いた要求にだけ**、ゾーン転送を許す |
| `server アドレス { keys { 名前; }; };` | **このサーバーと話すときは、この鍵で署名を付ける** |

`dig` で確かめます。鍵がなければ断られ、`-k` で鍵のファイルを渡すと転送できます。

```console
$ dig @127.0.0.1 example.jp AXFR
; Transfer failed.
$ dig @127.0.0.1 -k /etc/bind/xfer.key example.jp AXFR
example.jp.		3600	IN	SOA	ns1.example.jp. admin.example.jp. 2026111701 10800 3600 604800 900
example.jp.		3600	IN	NS	ns1.example.jp.
…
xfer-key.		0	ANY	TSIG	hmac-sha256. 1794863946 300 32 KStt+0PkrY0RtXrXldPmaKo7lM+4FhxmrByOAidR+W0= 45518 NOERROR 0
```

:::warn 試験の注意：TSIG の 3 つの決まり
- 鍵は**共有鍵**（共通鍵）。公開鍵と秘密鍵の組ではない。だから `secret` を書いたファイルは、ほかのユーザーに読めないようにする
- 署名には時刻が入っている。**2 台の時計がずれている**（既定で 300 秒を超える）と失敗するので、NTP で合わせておく
- 鍵の**名前**、アルゴリズム、`secret` の 3 つが、両方のサーバーで同じでなければならない
:::

## DNSSEC：ゾーンに署名して、答えが本物かを確かめる {#dnssec}

```fig graph DNSSEC の信頼の連鎖。親のゾーンの DS が子の KSK を保証し、KSK が ZSK を、ZSK が 1 つずつのレコードを保証する
{
  col: 215, row: 104,
  nodes: [
    { id: 'ta', label: 'ルートの公開鍵', sub: 'トラストアンカー\n（キャッシュサーバーが持つ）', x: 0, y: 0, kind: 'ext', mono: false },
    { id: 'jp', label: 'jp ゾーン', sub: 'DS レコード\n= example.jp の KSK の要約', x: 1, y: 0, mono: false },
    { id: 'ksk', label: 'KSK', sub: '鍵署名鍵\nDNSKEY 257', x: 2, y: 0, kind: 'accent', mono: false },
    { id: 'zsk', label: 'ZSK', sub: 'ゾーン署名鍵\nDNSKEY 256', x: 3, y: 0, kind: 'accent', mono: false },
    { id: 'rr', label: 'www A', sub: '+ RRSIG（署名）', x: 3, y: 1, kind: 'stack', mono: false },
  ],
  edges: [
    { from: 'ta', to: 'jp', label: '順にたどる' },
    { from: 'jp', to: 'ksk', label: 'DS が保証' },
    { from: 'ksk', to: 'zsk', label: '署名' },
    { from: 'zsk', to: 'rr', label: '署名' },
  ],

```

ふつうの DNS の応答には、「本物の権威サーバーが出した答えか」を確かめる手段がありません。偽の答えをキャッシュサーバーに覚えさせる攻撃（**キャッシュポイズニング**）が成り立ちます。

**DNSSEC**（DNS Security Extensions）は、ゾーンのレコードに**公開鍵暗号の署名**を付けます（[図解 LinuC 10.10](../../linuc/site/ch10.html#gpg) の署名と同じ考え方）。権威サーバーは秘密鍵で署名し、キャッシュサーバーは公開鍵で確かめます。守るのは**答えの出どころと、書き換えられていないこと**で、**通信の暗号化はしません**。

| レコード | 中身 |
| --- | --- |
| **`DNSKEY`** | ゾーンの**公開鍵**。フラグ 256 が ZSK、257 が KSK |
| **`RRSIG`** | レコードの**署名** |
| **`DS`** | 子のゾーンの KSK の要約（ハッシュ）。**親のゾーンに登録する** |
| `NSEC` / `NSEC3` | 「その名前はない」ことを証明するための、次の名前を指すレコード |

鍵は 2 種類を使います。

| 鍵 | 名前 | 何に署名するか |
| --- | --- | --- |
| **ZSK** | Zone Signing Key（ゾーン署名鍵） | ゾーンの中の 1 つずつのレコード |
| **KSK** | Key Signing Key（鍵署名鍵） | DNSKEY レコード（つまり ZSK） |

### 手順 1：dnssec-keygen で鍵を作る

**`dnssec-keygen`** は、鍵の組（公開鍵と秘密鍵）を作ります。`-a` でアルゴリズム、`-f KSK` で KSK を指定します。

```console
# dnssec-keygen -a ECDSAP256SHA256 -n ZONE example.jp
Kexample.jp.+013+15412
# dnssec-keygen -a ECDSAP256SHA256 -f KSK -n ZONE example.jp
Kexample.jp.+013+55096
# ls
Kexample.jp.+013+15412.key      Kexample.jp.+013+55096.key
Kexample.jp.+013+15412.private  Kexample.jp.+013+55096.private
```

ファイル名は **`K` + ゾーン名 + `.+` アルゴリズムの番号（3 桁）+ `+` 鍵の ID（5 桁）** です。**`.key` が公開鍵**（DNSKEY レコードがそのまま入っている）、**`.private` が秘密鍵**です。

```console
# cat Kexample.jp.+013+55096.key
; This is a key-signing key, keyid 55096, for example.jp.
example.jp. IN DNSKEY 257 3 13 tUtKr204Q9rBS7R35HTH1zXnpAPGV+u/zPMilS6mJ+rQsbjAAtcqFSLw KnhnglBvzZhr0jYWlzuapnBewUCfNQ==
```

| オプション | 意味 |
| --- | --- |
| `-a アルゴリズム` | `RSASHA256`、`ECDSAP256SHA256`、`ED25519` など。いまの BIND（9.18 で確認）では省略できない |
| `-b ビット数` | 鍵の長さ（RSA のとき。例 `-b 2048`） |
| `-n ZONE` | ゾーンの鍵（DNSKEY の既定） |
| **`-f KSK`** | KSK を作る。付けなければ ZSK |
| `-K ディレクトリ` | 鍵を置くディレクトリ |

### 手順 2：dnssec-signzone で署名する

**`dnssec-signzone`** は、ゾーンファイルに署名を足した新しいファイルを作ります。

```console
# dnssec-signzone -S -o example.jp example.jp.zone
Fetching example.jp/ECDSAP256SHA256/55096 (KSK) from key repository.
Fetching example.jp/ECDSAP256SHA256/15412 (ZSK) from key repository.
Verifying the zone using the following algorithms:
- ECDSAP256SHA256
Zone fully signed:
Algorithm: ECDSAP256SHA256: KSKs: 1 active, 0 stand-by, 0 revoked
                            ZSKs: 1 active, 0 stand-by, 0 revoked
example.jp.zone.signed
# ls
dsset-example.jp.  example.jp.zone  example.jp.zone.signed  K…
```

| オプション | 意味 |
| --- | --- |
| **`-o ゾーン名`** | オリジン。省くと、ゾーンファイルの名前をゾーン名とみなす |
| `-S` | スマート署名。鍵のファイルを自分で探し、DNSKEY をゾーンに足す |
| `-k 鍵` | KSK として使う鍵を指定する |
| `-f ファイル` | 出力先。既定は **ゾーンファイル名 + `.signed`** |
| `-e 日時` | 署名の期限。既定は **30 日後** |
| `-K ディレクトリ` | 鍵を探すディレクトリ |

`-S` を使わない昔からのやり方では、ゾーンファイルに 2 つの `.key` の中身を足してから（`$INCLUDE Kexample.jp.+013+55096.key` のように）、`dnssec-signzone -o example.jp -k KSK の名前 example.jp.zone ZSK の名前` と実行します。

できるものは 2 つです。

- **`example.jp.zone.signed`**：RRSIG、NSEC、DNSKEY が足された、署名済みのゾーンファイル
- **`dsset-example.jp.`**：親のゾーンに登録する **DS レコード**

```console
# cat dsset-example.jp.
example.jp.		IN DS 55096 13 2 D4C43A5AF4E9639AA14F7E3F39D7DAD2C3103B5DC1805678CEE5E2B9 6401A94F
```

### 手順 3：署名済みのファイルを読ませ、DS を親に登録する

`named.conf` の `file` を、署名済みのファイルに変えます。

```text
zone "example.jp" {
	type master;
	file "example.jp.zone.signed";
};
```

```console
# named-checkconf -z
zone example.jp/IN: loaded serial 2026111701 (DNSSEC signed)
$ dig @127.0.0.1 www.example.jp +dnssec
;; ANSWER SECTION:
www.example.jp.		3600	IN	A	192.168.10.10
www.example.jp.		3600	IN	RRSIG	A 13 3 3600 20261216201957 20261116201957 15412 example.jp. MX4erxBy…
```

RRSIG の中の 2 つの日時は、署名の期限と開始です。**期限（既定で 30 日）が切れる前に、署名をやり直す**必要があります。切れると、検証するキャッシュサーバーからは、そのゾーン全体が引けなくなります（SERVFAIL）。

最後に、`dsset-` の DS レコードを**親のゾーン**（`example.jp` なら `jp`）に登録してもらいます。これで、ルートから自分のゾーンまで信頼の連鎖がつながります。

### キャッシュサーバーの側：検証する

検証するのは、キャッシュサーバーです。`named.conf` の `options` に書きます。

| 設定 | 意味 |
| --- | --- |
| `dnssec-validation auto;` | 検証する。ルートの公開鍵（**トラストアンカー**）は、BIND に組み込みのものを使う |
| `dnssec-validation yes;` | 検証する。トラストアンカーは自分で設定する |
| `dnssec-validation no;` | 検証しない |

検証に成功した答えには、`dig` の `flags:` に **`ad`** が付きます。

## DANE：サーバー証明書を DNS で確かめる {#dane}

**DANE**（DNS-based Authentication of Named Entities）は、TLS で使う**サーバー証明書の情報を、DNS のレコードとして公開する**仕組みです。クライアントは、サーバーが出してきた証明書を、DNS から引いた情報と比べます。認証局（CA）だけに頼らずに、「このサーバーの正しい証明書はこれ」とドメインの持ち主が自分で言えます。

そのためのレコードが **`TLSA`** です。名前は **`_ポート番号._プロトコル.ホスト名`** の形にします。

```text
_443._tcp.www	IN	TLSA	3 1 1 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
_25._tcp.mail	IN	TLSA	3 1 1 …
```

```console
$ dig @127.0.0.1 _443._tcp.www.example.jp TLSA +short
3 1 1 0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF01234567 89ABCDEF
```

データは、3 つの数字とハッシュ値です。

| 順番 | 名前 | 値 |
| --- | --- | --- |
| 1 | 証明書の使い方（usage） | 0 = CA を指定（公的な CA の検証も必要）、1 = サーバー証明書を指定（公的な CA の検証も必要）、2 = 自前の CA を信頼の起点にする、**3 = サーバー証明書そのものを指定**（CA の検証は不要） |
| 2 | セレクター | 0 = 証明書全体、1 = 公開鍵だけ |
| 3 | 照合の方法 | 0 = そのまま、1 = SHA-256、2 = SHA-512 |
| 4 | データ | 上の方法で作った値（16 進） |

`3 1 1` は「サーバー証明書の公開鍵の SHA-256 ハッシュ」で、いちばんよく使われる組み合わせです。

:::warn 試験の注意：DANE は DNSSEC が前提
TLSA レコードが偽物なら、偽の証明書を本物と思わせることができてしまいます。そのため、**DANE は、TLSA レコードが DNSSEC で署名され、検証できること**を前提にしています。「DANE = TLSA レコード = DNSSEC が必要」をひとまとめで覚えます。TSIG はサーバーどうしの共有鍵なので、DANE とは関係がありません。
:::

同じ考え方で、SSH のホスト鍵の指紋を公開する `SSHFP`、OpenPGP の公開鍵を公開する `OPENPGPKEY`、S/MIME の証明書を公開する `SMIMEA` というレコードもあります。

### 3 つの仕組みを並べる

| | TSIG | DNSSEC | DANE |
| --- | --- | --- | --- |
| 守るもの | サーバーどうしのやり取り（ゾーン転送など） | ゾーンのレコードが本物であること | TLS のサーバー証明書が本物であること |
| 鍵 | **共有鍵**（HMAC） | **公開鍵と秘密鍵**（KSK、ZSK） | （DNSSEC の上に乗る） |
| レコード / 設定 | `key` 文、`server` 文、`allow-transfer { key …; }` | DNSKEY、RRSIG、DS、NSEC | **TLSA** |
| 道具 | `tsig-keygen`（古くは `dnssec-keygen -a HMAC-…`） | `dnssec-keygen`、`dnssec-signzone` | `dig … TLSA` |
| 暗号化 | しない | しない | （TLS がする） |

:::key まとめ
- 権威サーバーはゾーンを持って答え、キャッシュサーバーは再帰問い合わせを受けてたどる。BIND（`named`）は両方、**Unbound はキャッシュ専用、NSD は権威専用**、dnsmasq は DNS + DHCP、PowerDNS はデータベースが使える
- `named.conf` は Red Hat 系 `/etc/named.conf`（`directory "/var/named"`）、Debian 系 `/etc/bind/named.conf`。文は `;` で終わる。`file` の相対パスは `directory` から
- `zone` の `type`：`master`、`slave`（+ `masters`）、`hint`（ルートの一覧）、`forward`
- `named-checkconf` は文法の検査（問題なければ無言）、`-z` でゾーンファイルも読む。`named-checkzone ゾーン名 ファイル` はゾーンファイルの検査、`named-compilezone -f 入力 -F 出力 -o ファイル` は text と raw の変換
- `rndc reload`（全部）、`reconfig`（設定と新しいゾーンだけ）、`flush`（キャッシュを捨てる）、`status`、`stop`。TCP 953 番と共有鍵（`rndc.key`）
- `dig @サーバー 名前 種類`、`-x`、`+short`、`+norecurse`、`+trace`、`+dnssec`、`AXFR`。フラグ `aa` は権威の答え、`ra` は再帰に応じる、`ad` は DNSSEC の検証済み。`host -t`、`host -l`、`nslookup -type=`
- ゾーンファイル：`$TTL`、`$ORIGIN`、`@` はオリジン、先頭が空白なら上と同じ名前、**FQDN の最後には `.`**
- SOA は「プライマリの名前、管理者のメール（`@` → `.`）、シリアル、リフレッシュ、リトライ、エクスパイア、ネガティブキャッシュの TTL」。**シリアルを増やさないとセカンダリに伝わらない**
- MX は小さい数が先。NS と MX の右側は名前。CNAME の名前にほかのレコードは書けない。逆引きは `10.168.192.in-addr.arpa` に PTR
- `named -u ユーザー -t ディレクトリ` で、非 root + chroot。Red Hat 系は `bind-chroot` と `/var/named/chroot`
- `forwarders` で回す先、`forward only` はフォワーダーだけ、`forward first`（既定）はだめなら自分でたどる。外向きの権威サーバーは `recursion no`、`version` で版を隠す
- TSIG は**共有鍵**でサーバーどうしを認証。`key` 文を両方に、`allow-transfer { key 名前; };` と `server アドレス { keys { 名前; }; };`。時計を合わせる
- DNSSEC は**公開鍵の署名**。`dnssec-keygen`（`-f KSK`）→ `K名前.+アルゴリズム+ID.key` / `.private`、`dnssec-signzone -o ゾーン` → `.signed` と `dsset-`。DNSKEY、RRSIG、DS（親に登録）、NSEC
- DANE は `_443._tcp.www` の **TLSA** レコードで証明書を公開する。DNSSEC が前提
:::

### 2.08.1 BIND の設定と管理

:::q 2.08.1-01 single
Red Hat 系のディストリビューションでパッケージから入れた BIND の、主な設定ファイルの既定の場所として正しいものはどれか。

- [x] `/etc/named.conf`
- [ ] `/var/named/named.conf`

- [ ] `/etc/resolv.conf`
:::why
Red Hat 系では `/etc/named.conf` です（[named.conf の場所](#named-conf)）。

- `/etc/bind/named.conf` は Debian 系の場所です
- `/var/named/` は Red Hat 系の `directory` の既定で、ゾーンファイルを置く場所です。設定ファイルは置きません
- `named.ca` はルートサーバーの一覧（ヒント）のファイルで、Red Hat 系では `/var/named/named.ca` にあります
- `/etc/resolv.conf` は、クライアントが聞く先の DNS サーバーを書くファイルです（[図解 LinuC 7.11](../../linuc/site/ch07.html#resolv)）

:::q 2.08.1-02 single

```text
options {

};
```

- [ ] `/var/named/example.jp`
- [ ] `/etc/named/zones/example.jp.db`
:::why
`file` が相対パスのときは、`options` の `directory` からの相対パスです。`/var/named` + `zones/example.jp.db` で `/var/named/zones/example.jp.db` になります（[zone：ゾーンごとの設定](#named-conf)）。

- `/etc/` や `/etc/named/` は、named.conf のある場所からの相対パスと考えたときのまちがいです。基準は設定ファイルの場所ではなく `directory` です
- `/zones/example.jp.db` は、`/` からの相対とみなしたまちがいです
- `/var/named/example.jp` は、ゾーン名をファイル名とみなしたまちがいです。読まれるのは `file` に書いた名前です
:::
:::

:::q 2.08.1-03 single

セカンダリは `type slave;` で、`masters` にプライマリのアドレスを書きます（新しい BIND では `secondary` と `primaries` とも書けます）（[zone：ゾーンごとの設定](#named-conf)）。

- `master` は、元のデータを持つプライマリです。`masters` は書きません
- `hint` は、ルートサーバーの一覧を読むための種類で、ゾーン `"."` に使います
- `forward` は、そのゾーンの問い合わせを `forwarders` に書いたサーバーへ回す種類です。写しは持ちません

:::q 2.08.1-04 single
次の named.conf の抜粋の説明として正しいものはどれか。

```text
zone "." IN {
	type hint;
	file "named.ca";
};
```
- [ ] すべての問い合わせを、named.ca に書かれたフォワーダーへ回す
- [ ] このサーバーがルートゾーンのプライマリサーバーになる
- [x] ルートサーバーの名前とアドレスの一覧を named.ca から読み、再帰問い合わせをたどる出発点にする

`type hint` は、ルートサーバーの一覧（ヒント）のファイルを読む種類です。キャッシュサーバーは、ここに書かれたルートサーバーから順にたどります（[zone：ゾーンごとの設定](#named-conf)）。

- 問い合わせを回すのは `forwarders`、または `type forward` のゾーンです
- プライマリになるのは `type master` です
- キャッシュはメモリに持ちます。ファイルに書き出すのは `rndc dumpdb` で、出力先は `dump-file` です
- ルートの公開鍵（トラストアンカー）は、Red Hat 系では `/etc/named.root.key` を include して読みます。`dnssec-validation auto` なら組み込みのものが使われます
:::
:::

:::q 2.08.1-05 fill
named.conf を書き換えた。named を再起動する前に、設定ファイルの文法にまちがいがないかを調べたい。空欄に入るコマンドを入力してください。


`named-checkconf` は named.conf の文法を調べます。まちがいがあれば「ファイル名:行番号: 理由」を表示し、問題がなければ何も表示せずに終了ステータス 0 で終わります（[named-checkconf](#rndc)）。`named-checkzone` はゾーンファイルを調べるコマンドで、引数は「ゾーン名、ファイル名」です。
:::
:::

:::q 2.08.1-06 single
`named-checkconf -z` の説明として正しいものはどれか。
- [ ] 設定を、include を展開した形で表示する
- [ ] chroot した先のディレクトリを指定する
- [x] 設定ファイルの文法に加えて、設定にあるマスターゾーンのゾーンファイルも読み込んで調べる
- [ ] 問題がなくても「OK」と表示する
- [ ] 動いている named に設定を読み直させる

`-z` を付けると、named.conf にあるマスターゾーンを実際に読み込んでみて、`zone example.jp/IN: loaded serial …` のように結果を表示します（[named-checkconf](#rndc)）。

- include を展開して表示するのは `-p` です
- chroot した先を指定するのは `-t ディレクトリ` です
- `-z` はゾーンごとの `loaded serial` の行を出しますが、「OK」という行は出しません。「OK」を出すのは `named-checkzone` です
- 読み直させるのは `rndc reload` や `rndc reconfig` です。`named-checkconf` は、動いている named には何もしません
:::
:::

:::q 2.08.1-07 single
named.conf に新しいゾーンの zone 文を 1 つ足した。すでに読み込んであるゾーンのファイルは読み直さずに、設定ファイルと新しいゾーンだけを読み込ませる rndc のコマンドはどれか。
- [ ] `rndc reload`
- [x] `rndc reconfig`
- [ ] `rndc flush`
- [ ] `rndc refresh`
- [ ] `rndc status`
:::why
`rndc reconfig` は、設定ファイルを読み直し、新しく足されたゾーンだけを読み込みます（[rndc](#rndc)）。

- `rndc reload` は、設定ファイルとすべてのゾーンを読み直します。目的は果たせますが、「すでにあるゾーンは読み直さない」という条件に合いません
- `rndc flush` は、キャッシュを捨てます
- `rndc refresh ゾーン` は、セカンダリでプライマリのシリアルを確かめに行かせます
- `rndc status` は、状態を表示するだけです
:::
:::

:::q 2.08.1-08 multi
rndc の説明として正しいものを 2 つ選択してください。
- [x] `rndc flush` は、サーバーが持っているキャッシュを捨てる
- [x] rndc と named は、共有鍵で相手を確かめ、既定では TCP の 953 番ポートでやり取りする
- [ ] `rndc reload example.jp` は、example.jp を含むすべてのゾーンを読み直す
- [ ] `rndc halt` は、書きかけの更新をファイルに保存してから named を止める
- [ ] `rndc querylog on` は、ゾーンファイルの書き換えの履歴を記録する
:::why
`rndc flush` はキャッシュを捨てます。rndc は、`rndc.key` などに書いた共有鍵を使い、named の 953 番ポート（TCP）に指示を送ります（[rndc](#rndc)）。

- `rndc reload ゾーン名` は、そのゾーンだけを読み直します。全部を読み直すのは、引数なしの `rndc reload` です
- 保存してから止めるのは `rndc stop` です。`rndc halt` は保存せずにすぐ止めます
- `rndc querylog on` は、クライアントからの問い合わせを 1 件ずつログに出します
:::
:::

:::q 2.08.1-09 single
次の dig の出力（抜粋）の説明として正しいものはどれか。

```text
$ dig @192.168.10.1 www.example.jp

;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 13350
;; flags: qr aa rd; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
;; WARNING: recursion requested but not available

;; ANSWER SECTION:
www.example.jp.		3600	IN	A	192.168.10.10
```
- [ ] 192.168.10.1 はキャッシュサーバーで、キャッシュしていた答えを返した
- [x] 192.168.10.1 は example.jp のゾーンを持つ権威サーバーとして答えた。このサーバーは再帰問い合わせに応じない
- [ ] 192.168.10.1 は問い合わせを断った
- [ ] この答えは、DNSSEC の検証に成功している
- [ ] www.example.jp という名前はない
:::why
`aa`（authoritative answer）は、そのゾーンを持つ権威サーバー自身の答えであることを表します。`ra`（recursion available）がなく、`recursion requested but not available` と出ているので、このサーバーは再帰に応じません（[dig](#dig)）。

- キャッシュからの答えなら、`aa` は付きません
- 断られたなら、`status` は `REFUSED` になり、ANSWER は 0 です
- DNSSEC の検証に成功した答えには `ad` が付きます
- 名前がなければ、`status` は `NXDOMAIN` です
:::
:::

:::q 2.08.1-10 single
/etc/resolv.conf の設定に関係なく、DNS サーバー `192.168.10.1` に `example.jp` の MX レコードを問い合わせるコマンドはどれか。
- [ ] `dig example.jp MX 192.168.10.1`
- [x] `dig @192.168.10.1 example.jp MX`
- [ ] `dig -x 192.168.10.1 example.jp MX`
- [ ] `dig -s 192.168.10.1 -t MX example.jp`
- [ ] `host -t MX 192.168.10.1 example.jp`
:::why
`dig` は、聞く先のサーバーを `@サーバー` で指定します（[dig](#dig)）。

- `dig example.jp MX 192.168.10.1` は、`192.168.10.1` をもう 1 つの調べる名前とみなします。`@` がないので、聞く先は resolv.conf のサーバーのままです
- `-x` は逆引きです。`192.168.10.1` の PTR を引いてしまいます
- `dig` に、サーバーを指定する `-s` というオプションはありません
- `host` は「調べる名前、サーバー」の順です。この書き方では、`192.168.10.1` を調べる対象、`example.jp` をサーバーとみなします
:::
:::

:::q 2.08.1-11 fill
IP アドレス 192.168.10.10 の逆引き（PTR レコード）を、DNS サーバー 192.168.10.1 に問い合わせる。空欄に入るオプションを入力してください。

```text

```

:::why
`dig -x アドレス` は、アドレスを `10.10.168.192.in-addr.arpa` の形に直して、PTR レコードを引きます（[dig](#dig)、[逆引きのゾーン](#reverse)）。`-t` は種類の指定で、`-t PTR 192.168.10.10` と書いても、アドレスは逆順の名前に直されません。
:::
:::

:::q 2.08.1-12 multi
名前解決を確かめるコマンドの説明として正しいものを 2 つ選択してください。
- [x] `host -t MX example.jp` は、example.jp の MX レコードを引く
- [x] `nslookup -type=MX example.jp 192.168.10.1` は、DNS サーバー 192.168.10.1 に example.jp の MX レコードを問い合わせる
- [ ] `host -l example.jp` は、example.jp の逆引きをする
- [ ] `dig +short example.jp` は、ヘッダーとフラグだけを表示する
- [ ] `nslookup www.example.jp` は、DNS より先に /etc/hosts を調べる
:::why
`host` は `-t 種類`、`nslookup` は `-type=種類` で種類を指定します。どちらも、名前の後ろにサーバーを書けます（[dig・host・nslookup](#dig)）。

- `host -l ゾーン` は、ゾーン転送（AXFR）で、ゾーンの中のホストを一覧にします。逆引きは、`host` に IP アドレスを渡します
- `dig +short` は、答えの値だけを表示します。ヘッダーは出ません
- `nslookup`、`host`、`dig` は、DNS サーバーに直接聞きます。`/etc/hosts` は見ません。`/etc/hosts` も含めて確かめるのは `getent hosts` です（[図解 LinuC 7.12](../../linuc/site/ch07.html#dig)）
:::
:::

:::q 2.08.1-13 single
権威サーバーの機能だけを持ち、再帰問い合わせには答えない（キャッシュサーバーの機能を持たない）ネームサーバーのソフトウェアはどれか。
- [ ] Unbound
- [ ] dnsmasq
- [x] NSD
- [ ] BIND
- [ ] Squid
:::why
NSD は、権威サーバー専用です（[ほかのネームサーバー](#roles)）。

- Unbound は逆で、キャッシュサーバー（フルリゾルバ）専用です
- dnsmasq は、小さなネットワーク向けの DNS キャッシュ（フォワーダー）と DHCP サーバーです
- BIND は、権威サーバーにもキャッシュサーバーにもなれます
- Squid は、HTTP のプロキシサーバーです。ネームサーバーではありません
:::
:::

:::q 2.08.1-14 multi
BIND 以外のネームサーバーの説明として正しいものを 2 つ選択してください。
- [x] dnsmasq は、DNS のキャッシュ（フォワーダー）と DHCP サーバーの機能を 1 つで持つ
- [x] Unbound は、DNSSEC の検証ができるキャッシュサーバーである
- [ ] NSD は、キャッシュサーバー専用のソフトウェアである
- [ ] PowerDNS は、ゾーンの情報をテキストのゾーンファイルにしか置けない
- [ ] Unbound の設定ファイルは named.conf である
:::why
dnsmasq は DNS と DHCP を 1 つでまかなう軽いサーバー、Unbound は DNSSEC の検証ができるキャッシュサーバー専用のソフトウェアです（[ほかのネームサーバー](#roles)）。

- NSD は権威サーバー専用です。キャッシュ専用は Unbound です
- PowerDNS の特徴は、ゾーンの情報を MySQL や PostgreSQL などのデータベースに置けることです
- named.conf は BIND の設定ファイルです。Unbound は `unbound.conf` です
:::
:::

:::q 2.08.1-15 multi
Red Hat 系で BIND を入れた直後の named.conf は、次のようになっている。192.168.10.0/24 のクライアントからの問い合わせに答えるキャッシュサーバーにするために、書き換える必要があるディレクティブを 2 つ選択してください。

```text
options {
	listen-on port 53 { 127.0.0.1; };
	directory 	"/var/named";
	allow-query     { localhost; };
	recursion yes;
	dnssec-validation yes;
};
```
- [x] `listen-on`
- [ ] `directory`
- [x] `allow-query`
- [ ] `recursion`
- [ ] `dnssec-validation`
:::why
このままでは、127.0.0.1 でしか待ち受けず（`listen-on`）、自分自身からの問い合わせしか受け付けません（`allow-query { localhost; }`）。`listen-on port 53 { 127.0.0.1; 192.168.10.1; };` のようにサーバーのアドレスを足し、`allow-query { localhost; 192.168.10.0/24; };` のように相手を広げます（[named.conf](#named-conf)）。

- `directory` は、ゾーンファイルなどの相対パスの基準です。待ち受けには関係しません
- `recursion yes` は、すでに再帰問い合わせに答える設定です。キャッシュサーバーにはこのままでよく、`no` にするとキャッシュサーバーとして働かなくなります
- `dnssec-validation` は、署名を検証するかどうかです。クライアントを受け付けるかどうかには関係しません
:::

### 2.08.2 ゾーン情報の管理

:::q 2.08.2-01 single
次の SOA レコードから読み取れる、このゾーンの管理者のメールアドレスはどれか。

```text
@	IN	SOA	ns1.example.jp. hostmaster.example.jp. (
		2026111701 10800 3600 604800 900 )
```
- [ ] `ns1@example.jp`
- [x] `hostmaster@example.jp`
- [ ] `hostmaster.example.jp@ns1.example.jp`
- [ ] `root@ns1.example.jp`
- [ ] `2026111701@example.jp`
:::why
SOA の 2 つ目の欄（RNAME）が管理者のメールアドレスで、`@` を `.` に置き換えて書きます。`hostmaster.example.jp.` は `hostmaster@example.jp` です（[SOA レコード](#zonefile)）。

- 1 つ目の欄 `ns1.example.jp.` は、プライマリのネームサーバーの名前（MNAME）です。メールアドレスではありません
- `2026111701` はシリアルです
- 先頭の `@` はオリジン（ゾーン名）を表す記号で、メールアドレスの `@` とは関係がありません
:::
:::

:::q 2.08.2-02 single
ゾーン `example.jp` のゾーンファイルに、次の行がある（`$ORIGIN` は書いていない）。この MX レコードが指すメールサーバーの名前として正しいものはどれか。

```text
@	IN	MX	10 mail.example.jp
```
- [ ] `mail.example.jp.`
- [x] `mail.example.jp.example.jp.`
- [ ] `mail.`
- [ ] `10.mail.example.jp.`
- [ ] 文法エラーになり、ゾーンが読み込まれない
:::why
最後に `.` のない名前は相対の名前で、後ろにオリジン（ここでは `example.jp.`）が補われます。`mail.example.jp` は `mail.example.jp.example.jp.` になります（[書式の決まり](#zonefile)）。

- `mail.example.jp.` にしたければ、最後に `.` を付けるか、`mail` とだけ書きます
- 文法としては正しいので、エラーにはなりません。`named-checkzone` は、その名前に A レコードがないという警告を出しますが、最後は `OK` と表示します
- `10` は MX の優先度で、名前の一部ではありません
:::
:::

:::q 2.08.2-03 single
プライマリサーバーでゾーンファイルに A レコードを 1 行足し、`rndc reload` を実行した。プライマリに問い合わせると新しいレコードが返るが、セカンダリサーバーに問い合わせると「その名前はない」と返る。ゾーン転送の設定とネットワークには問題がない。原因として最も考えられるものはどれか。
- [ ] ゾーンファイルの `$TTL` が短すぎる
- [x] SOA レコードのシリアルを増やしていない
- [ ] SOA レコードのエクスパイアの値が大きすぎる
- [ ] プライマリで `rndc flush` を実行していない
- [ ] セカンダリの named.conf に `type hint` のゾーンがない
:::why
セカンダリは、プライマリの SOA のシリアルが自分の写しより大きいときだけ、ゾーン転送をします。シリアルが同じままなら「変わっていない」と判断し、古い写しで答え続けます（[ゾーン転送とシリアル](#checkzone)）。

- `$TTL` は、キャッシュサーバーが答えを覚えておく時間です。セカンダリへの転送には関係しません
- エクスパイアは、プライマリに届かないときにセカンダリが答え続けてよい期間です。大きくても、転送が起きない原因にはなりません
- `rndc flush` が捨てるのは、キャッシュサーバーとしてのキャッシュです。ゾーンのデータは変わりません
- `type hint` は、ルートサーバーの一覧です。セカンダリがゾーンをもらうことには関係しません
:::
:::

:::q 2.08.2-04 single
次の SOA レコードの最後の値 `900` の、いまの BIND での意味として正しいものはどれか。

```text
@	IN	SOA	ns1.example.jp. admin.example.jp. (
		2026111701	; (1)
		10800		; (2)
		3600		; (3)
		604800		; (4)
		900 )		; (5)
```
- [ ] セカンダリが、プライマリのシリアルを確かめに行く間隔
- [ ] シリアルの確認に失敗したとき、次に試すまでの間隔
- [ ] プライマリに届かないまま、セカンダリが答え続けてよい期間
- [x] 「その名前はない」という答えを、キャッシュサーバーが覚えておく時間（ネガティブキャッシュの TTL）
- [ ] ゾーンファイルを書き換えた回数
:::why
SOA の数字は、順に「シリアル、リフレッシュ、リトライ、エクスパイア、ミニマム」です。最後のミニマムは、ネガティブキャッシュの TTL として使われます（[SOA レコード](#zonefile)）。

- 確かめに行く間隔は、(2) のリフレッシュです
- 失敗したあとの間隔は、(3) のリトライです
- 答え続けてよい期間は、(4) のエクスパイアです
- 版の番号は、(1) のシリアルです
:::
:::

:::q 2.08.2-05 fill
ゾーン `example.jp` のゾーンファイルを書いた。named に読ませる前に、文法と中身を調べたい。空欄に入るコマンドを入力してください。

```text

zone example.jp/IN: loaded serial 2026111701
OK
```
= named-checkzone
= /usr/sbin/named-checkzone
= /usr/bin/named-checkzone
:::why
`named-checkzone ゾーン名 ファイル名` で、ゾーンファイルを調べます。成功すると、読み込んだシリアルと `OK` を表示します（[named-checkzone](#checkzone)）。`named-checkconf` は named.conf を調べるコマンドです。`named-compilezone` は、`-o` で出力先を指定しないとエラーになります。
:::
:::

:::q 2.08.2-06 single
ネットワーク `192.168.10.0/24` の逆引きのために named.conf に書くゾーン名として正しいものはどれか。
- [ ] `192.168.10.in-addr.arpa`
- [x] `10.168.192.in-addr.arpa`
- [ ] `0.10.168.192.in-addr.arpa`
- [ ] `10.168.192.ip6.arpa`
- [ ] `192.168.10.0.arpa`
:::why
IPv4 の逆引きのゾーン名は、ネットワーク部のオクテットを逆の順に並べて `.in-addr.arpa` を付けます。`192.168.10` → `10.168.192.in-addr.arpa` です（[逆引きのゾーン](#reverse)）。

- `192.168.10.in-addr.arpa` は、逆の順にしていません
- `0.10.168.192.in-addr.arpa` は、ホスト部の 0 まで入れています。これは `192.168.10.0` という 1 つのアドレスの名前です
- `ip6.arpa` は IPv6 の逆引きです
- `192.168.10.0.arpa` というドメインはありません
:::
:::

:::q 2.08.2-07 multi
ゾーンファイルのリソースレコードの説明として正しいものを 2 つ選択してください。
- [x] CNAME レコードを書いた名前には、A レコードなどほかのレコードを書けない
- [x] MX レコードは、優先度の数が小さいメールサーバーから先に使われる
- [ ] PTR レコードは、ホスト名に IPv6 アドレスを対応させる
- [ ] NS レコードのデータには、ネームサーバーの IP アドレスを書く
- [ ] 同じ名前に A レコードを 2 つ書くと、ゾーンの読み込みに失敗する
:::why
CNAME と同じ名前にほかのレコードがあると、`CNAME and other data` というエラーで読み込めません。MX は、優先度の数が小さいほうが先です（[よく使うレコード](#zonefile)）。

- PTR は、アドレスに名前を対応させる逆引きのレコードです。名前に IPv6 アドレスを対応させるのは AAAA です
- NS のデータは、ネームサーバーの名前です。その名前の A レコードを別に書きます
- 同じ名前に A レコードを複数書くことはでき、すべてを答えます（DNS ラウンドロビン）
:::
:::

:::q 2.08.2-08 single
セカンダリサーバーが保存した raw 形式のゾーンファイル `slaves/example.jp.zone` を、人が読める text 形式のファイル `example.jp.txt` に変えるコマンドはどれか。ゾーン名は `example.jp` とする。
- [ ] `named-compilezone -f text -F raw -o example.jp.txt example.jp slaves/example.jp.zone`
- [x] `named-compilezone -f raw -F text -o example.jp.txt example.jp slaves/example.jp.zone`
- [ ] `named-compilezone -f raw -F text example.jp slaves/example.jp.zone example.jp.txt`
- [ ] `named-checkconf -f raw -F text -o example.jp.txt example.jp slaves/example.jp.zone`
- [ ] `named-compilezone -F raw -o example.jp.txt slaves/example.jp.zone example.jp`
:::why
`named-compilezone` は、`-f` で入力の形式、`-F` で出力の形式、`-o` で出力先を指定し、そのあとに「ゾーン名、入力ファイル」を書きます（[named-compilezone](#checkzone)）。

- `-f text -F raw` は逆向き（text から raw）です
- `-o` は省略できません。出力先を最後の引数に書くことはできません
- `named-checkconf` は named.conf を調べるコマンドで、ゾーンの形式は変えられません
- 最後の選択肢は、出力を raw にしているうえ、ゾーン名とファイル名の順が逆です
:::
:::

:::q 2.08.2-09 fill
ゾーンファイルの先頭で、TTL を省略したレコードに使われる既定の TTL を 1 日（86400 秒）にする。空欄に入るものを入力してください。

```text
____ 86400
@	IN	SOA	ns1.example.jp. admin.example.jp. (
		2026111701 10800 3600 604800 900 )
```
= $TTL
= $ttl
:::why
`$TTL` は、TTL を書かなかったレコードの既定の TTL を決めます（大文字でも小文字でも読まれますが、大文字で書くのがふつうです）（[書式の決まり](#zonefile)）。`$ORIGIN` は名前の後ろに補うドメイン、`$INCLUDE` は別のファイルの取り込みです。SOA の最後の値（ミニマム）は、いまはネガティブキャッシュの TTL です。
:::
:::

:::q 2.08.2-10 multi
ゾーン `example.jp` の次のゾーンファイル（抜粋）の説明として正しいものを 2 つ選択してください。

```text
$TTL 3600
@	IN	SOA	ns1.example.jp. admin.example.jp. 2026111701 10800 3600 604800 900
	IN	NS	ns1.example.jp.
	IN	MX	10 mail
www	IN	A	192.168.10.10
```
- [x] 1 つ目の欄の `@` は、ゾーン名 `example.jp.` を表す
- [x] 空白で始まる NS と MX の行は、すぐ上のレコードと同じ名前（`example.jp.`）のレコードである
- [ ] MX レコードが指すメールサーバーは `mail.` である
- [ ] `www` の A レコードの TTL は 900 秒である
- [ ] NS レコードの行は名前がないので、文法エラーになる
:::why
`@` はオリジン（ゾーン名）です。行の先頭が空白なら、すぐ上のレコードと同じ名前になるので、NS と MX は `example.jp.` のレコードです（[書式の決まり](#zonefile)）。

- `mail` は最後に `.` がない相対の名前なので、`mail.example.jp.` になります
- `www` の行は TTL を省いているので、`$TTL` の 3600 秒です。900 は SOA のミニマム（ネガティブキャッシュの TTL）です
- 名前の省略は正しい書き方で、エラーにはなりません
:::
:::

### 2.08.3 セキュアな DNS サーバーの実現

:::q 2.08.3-01 fill
named を、ユーザー named の権限で、/var/named/chroot に chroot して起動する。空欄に入るオプションを入力してください。

```text
# named -u named ____ /var/named/chroot
```
= -t
:::why
`named` の `-t ディレクトリ` は、そのディレクトリに chroot します。`-u ユーザー` は、そのユーザーに切り替えて動きます。root のままでは chroot の守りにならないので、2 つを一緒に使います（[chroot](#chroot)）。`-c` は設定ファイルの指定、`-p` はポートの指定です。
:::
:::

:::q 2.08.3-02 single
次の named.conf の抜粋の説明として正しいものはどれか。

```text
options {
	directory "/var/named";
	forwarders { 192.168.1.1; };
	forward only;
};
```
- [ ] 192.168.1.1 からの問い合わせだけを受け付ける
- [ ] 192.168.1.1 へ、ゾーン転送を許す
- [ ] 自分で解決できない問い合わせは 192.168.1.1 へ回し、答えがもらえなければ、自分でルートサーバーからたどる
- [x] 自分で解決できない問い合わせは 192.168.1.1 へ回し、答えがもらえなくても、自分ではルートサーバーからたどらない
- [ ] 自分が持つゾーンへの問い合わせも、すべて 192.168.1.1 へ回す
:::why
`forwarders` は問い合わせを回す先です。`forward only` は、フォワーダーにだけ聞き、だめなら失敗を返します（[forwarders](#split)）。

- 問い合わせを受け付ける相手は `allow-query` です
- ゾーン転送を許す相手は `allow-transfer` です
- 「だめなら自分でたどる」のは `forward first` で、こちらが既定です
- 自分が権威を持つゾーンは、自分で答えます。回すのは、自分で答えられない名前だけです
:::
:::

:::q 2.08.3-03 single
プライマリサーバーの named.conf の、次の抜粋の説明として正しいものはどれか。

```text
key "xfer-key" {
	algorithm hmac-sha256;
	secret "r/hHwDH1Jkk7lGOMqxVrdShmTIKSUIm29dp4FyozA8Y=";
};

zone "example.jp" {
	type master;
	file "example.jp.zone";
	allow-transfer { key xfer-key; };
};
```
- [ ] ゾーン example.jp のレコードに、xfer-key で DNSSEC の署名を付ける
- [x] xfer-key という共有鍵（TSIG）の署名が付いた要求にだけ、example.jp のゾーン転送を許す
- [ ] xfer-key という名前のホストにだけ、ゾーン転送を許す
- [ ] ゾーン転送の中身を、xfer-key で暗号化して送る
- [ ] rndc からの指示を、xfer-key を持つ相手にだけ許す
:::why
`allow-transfer { key 名前; };` は、その TSIG の鍵で署名された要求にだけ、ゾーン転送を許します（[TSIG](#tsig)）。

- DNSSEC の署名は、`dnssec-keygen` で作った公開鍵と秘密鍵の組を使い、`dnssec-signzone` で付けます。`key` 文の共有鍵は使いません
- `key` のあとに書くのは鍵の名前で、ホスト名ではありません
- TSIG は、相手の確認と改ざんの検出をします。中身は暗号化しません
- rndc を許す相手は、`controls` 文の `keys` に書きます
:::
:::

:::q 2.08.3-04 fill
ゾーン example.jp を DNSSEC で署名するために、鍵署名鍵（KSK）を作る。空欄に入るコマンドを入力してください。

```text
# ____ -a ECDSAP256SHA256 -f KSK -n ZONE example.jp

```
= dnssec-keygen
= /usr/sbin/dnssec-keygen
= /usr/bin/dnssec-keygen
:::why
`dnssec-keygen` は、DNSSEC の鍵の組を作ります。`-a` でアルゴリズム、`-f KSK` で鍵署名鍵を指定します。付けなければ、ゾーン署名鍵（ZSK）です（[dnssec-keygen](#dnssec)）。`dnssec-signzone` は、できた鍵でゾーンに署名するコマンドです。
:::
:::

:::q 2.08.3-05 single
`dnssec-keygen` を実行すると、`Kexample.jp.+013+15412` と表示された。このときに作られるファイルの説明として正しいものはどれか。
- [ ] `Kexample.jp.+013+15412.pub` に公開鍵、`Kexample.jp.+013+15412.key` に秘密鍵が入る
- [x] `Kexample.jp.+013+15412.key` に公開鍵（DNSKEY レコード）、`Kexample.jp.+013+15412.private` に秘密鍵が入る
- [ ] `Kexample.jp.+013+15412.key` に秘密鍵、`Kexample.jp.+013+15412.private` に公開鍵が入る
- [ ] `Kexample.jp.+013+15412.signed` に、署名済みのゾーンが入る
- [ ] `dsset-example.jp.` に、公開鍵と秘密鍵の両方が入る
:::why
`dnssec-keygen` は、`.key`（公開鍵。DNSKEY レコードの形）と `.private`（秘密鍵）の 2 つを作ります。名前の `013` はアルゴリズムの番号、`15412` は鍵の ID です（[dnssec-keygen](#dnssec)）。

- `.pub` は、`ssh-keygen` が作る公開鍵のファイルの拡張子です
- `.key` と `.private` の中身を逆にした選択肢は、まちがいです。`.private` は名前のとおり秘密鍵で、所有者だけが読める権限で作られます
- `.signed` と `dsset-` は、`dnssec-signzone` が作るファイルです。`dsset-` には、親のゾーンに登録する DS レコードが入ります
:::
:::

:::q 2.08.3-06 single
鍵のファイルがあるディレクトリで、次のコマンドが成功した。署名済みのゾーンが書き出されるファイルはどれか。

```text
# dnssec-signzone -S -o example.jp example.jp.zone
```
- [ ] `example.jp.zone`（元のファイルが上書きされる）
- [x] `example.jp.zone.signed`
- [ ] `example.jp.signed`
- [ ] `dsset-example.jp.`
- [ ] `Kexample.jp.zone.key`
:::why
`dnssec-signzone` の出力先は、`-f` で指定しなければ「ゾーンファイルの名前 + `.signed`」です。元のファイルは変わりません。named.conf の `file` を、この `.signed` のファイルに変えて読ませます（[dnssec-signzone](#dnssec)）。

- `-o example.jp` はゾーン名（オリジン）の指定で、出力するファイルの名前ではありません
- `dsset-example.jp.` も一緒に作られますが、入っているのは親のゾーンに登録する DS レコードです
- `K` で始まるファイルは、`dnssec-keygen` が作る鍵です
:::
:::

:::q 2.08.3-07 multi
DNSSEC で使うレコードの説明として正しいものを 2 つ選択してください。
- [x] RRSIG レコードには、レコードに対する署名が入る
- [x] DS レコードには子のゾーンの KSK の要約（ハッシュ）が入り、親のゾーンに登録する
- [ ] DNSKEY レコードには、ゾーンの秘密鍵が入る
- [ ] NSEC レコードは、問い合わせと応答を暗号化するために使う
- [ ] TSIG の共有鍵は、DNSKEY レコードとしてゾーンに公開する
:::why
RRSIG は署名、DS は子のゾーンの KSK の要約で、親のゾーンに登録して信頼の連鎖をつなぎます（[DNSSEC](#dnssec)）。

- DNSKEY に入るのは公開鍵です。秘密鍵は `.private` のファイルに置き、公開しません
- NSEC（NSEC3）は、「その名前はない」ことを証明するためのレコードです。DNSSEC は、通信の暗号化はしません
- TSIG の鍵は 2 台のサーバーだけが知る共有鍵で、named.conf の `key` 文に書きます。公開してはいけません
:::
:::

:::q 2.08.3-08 single
Web サーバー `www.example.jp` の HTTPS（TCP の 443 番）で使うサーバー証明書の情報を、DANE で公開する。ゾーン `example.jp` のゾーンファイルに書くレコードとして正しいものはどれか（ハッシュ値は省略している）。
- [ ] `www  IN  TLSA  443 tcp 3 1 1 …`
- [x] `_443._tcp.www  IN  TLSA  3 1 1 …`
- [ ] `_tcp._443.www  IN  TLSA  3 1 1 …`
- [ ] `_443._tcp.www  IN  DS  3 1 1 …`
- [ ] `www._tcp._443  IN  DNSKEY  3 1 1 …`
:::why
DANE は TLSA レコードを使い、名前は `_ポート番号._プロトコル.ホスト名` の形です。`_443._tcp.www`（オリジンが補われて `_443._tcp.www.example.jp.`）に書きます（[DANE](#dane)）。

- ポートとプロトコルは、データではなく名前の中に書きます
- `_tcp._443` は、順番が逆です
- DS は、子のゾーンの KSK の要約を親のゾーンに登録するレコードです
- DNSKEY は、ゾーンの公開鍵のレコードです
:::
:::

:::q 2.08.3-09 multi
TSIG の説明として正しいものを 2 つ選択してください。
- [x] やり取りする 2 台のサーバーの両方に、同じ名前で同じ内容の鍵を設定する
- [x] 署名に時刻が入っているので、2 台のサーバーの時計が大きくずれていると失敗する
- [ ] 公開鍵と秘密鍵の組を使い、公開鍵を DNS で配る
- [ ] ゾーン転送の中身を暗号化して、盗み見を防ぐ
- [ ] クライアントが、キャッシュサーバーからの答えが本物かを確かめるために使う
:::why
TSIG は共有鍵（HMAC）を使うので、両方のサーバーに同じ `key` 文を書きます。署名には時刻が入っていて、時計のずれが大きい（既定で 300 秒を超える）と検証に失敗します（[TSIG](#tsig)）。

- 公開鍵と秘密鍵の組を使い、公開鍵を DNSKEY レコードで配るのは DNSSEC です
- TSIG は、相手の確認と改ざんの検出だけをします。暗号化はしません
- レコードが本物かを確かめる仕組みは DNSSEC です。TSIG は、ゾーン転送や動的更新など、鍵をあらかじめ分け合ったサーバーどうしのやり取りを守ります
:::
:::

:::q 2.08.3-10 single
インターネットに公開する権威サーバーの named.conf に、次の設定を書いた。説明として**誤っている**ものはどれか。

```text
options {
	recursion no;
	allow-transfer { none; };
	version "unknown";
};
```
- [ ] `recursion no;` により、クライアントの代わりにほかのサーバーをたどって答える再帰問い合わせには応じなくなる
- [x] `recursion no;` により、このサーバーが持つゾーンへの問い合わせにも答えなくなる
- [ ] `allow-transfer { none; };` により、zone 文で別に許さないかぎり、ゾーン転送はだれにも許されない
- [ ] `version "unknown";` により、`version.bind` を問い合わせられたとき、本当のバージョンの代わりに `unknown` と答える
- [ ] この設定のサーバーに、持っていないゾーンの名前を問い合わせると、`dig` の status は `REFUSED` になる
:::why
`recursion no;` が止めるのは、再帰問い合わせ（キャッシュサーバーとしての働き）だけです。自分が持つゾーンには、`aa` フラグを付けてこれまでどおり答えます。したがって 2 つ目の説明が誤りです（[知らせる情報を減らす](#chroot)、[dig](#dig)）。

- 1 つ目は正しい説明です。だれの再帰問い合わせにも応じるオープンリゾルバにしないための設定です
- `allow-transfer { none; };` は、ゾーン転送をだれにも許しません。`zone` 文の中の `allow-transfer` が優先されるので、セカンダリにはそこで許します
- `version` は、`dig @サーバー version.bind chaos txt` への答えを変えます
- 再帰をしないサーバーは、持っていないゾーンの問い合わせを `REFUSED` で断ります
:::
:::
