| 型 | 置き場所 | 例 |
| --- | --- | --- |
| **ホスト型**（タイプ 2） | ホスト OS の上で、アプリケーションとして動く | **VirtualBox**、VMware Workstation |
| **ハイパーバイザー型**（タイプ 1、ベアメタル型） | ハードウェアのすぐ上で動く。間にホスト OS をはさまない | **Xen**、**KVM**、VMware ESXi、Hyper-V |

ホスト型は、ふだんの PC に入れてすぐ使えます。ただし、ゲストの処理がホスト OS を通るので、その分だけ遅くなります。ハイパーバイザー型は、間の層が少ないので速く、サーバーで使われます。

**Xen** は、ハードウェアの上で Xen 本体が動き、その上に仮想マシン（Xen ではドメインと呼ぶ）が並びます。最初に起動する特別なドメインが **Dom0**（ドメインゼロ）で、装置のドライバとほかのドメインの管理を受け持ちます。ふつうのゲストは **DomU** です。

**KVM**（Kernel-based Virtual Machine）は、Linux カーネルのモジュールです。読み込むと、**Linux カーネルそのものがハイパーバイザーになります**。ホストでふつうの Linux が動いているように見えますが、ハードウェアのすぐ上で動くカーネルが仮想化を受け持つので、ハイパーバイザー型に分類します。

:::warn 試験の注意：KVM はホスト型ではない
「Linux の上で動くから、KVM はホスト型」と考えると、まちがえます。出題範囲でも、KVM と Xen はハイパーバイザー型、VirtualBox はホスト型です。Docker はコンテナの道具で、どちらの型でもありません。
:::

## KVM と QEMU は、何を分担しているのか {#kvm-qemu}

| 部品 | 動く場所 | 役目 |
| --- | --- | --- |
| **KVM** | カーネル（モジュール `kvm` と `kvm_intel` か `kvm_amd`） | CPU の仮想化支援機能を使って、ゲストの命令を**本物の CPU でそのまま実行**する。窓口は `/dev/kvm` |
| **QEMU** | ユーザー空間（ゲスト 1 台につき 1 プロセス） | ディスク、NIC、画面などの**装置をエミュレート**する。KVM がなければ CPU もソフトウェアでまねる |
| **libvirt**（`libvirtd`） | ユーザー空間（デーモン） | QEMU の起動と停止、設定の保存、ネットワークとストレージの管理 |

**QEMU は、単体でも動きます**。その場合は CPU の命令も 1 つずつソフトウェアでまねるので、遅くなります。代わりに、ホストと違う種類の CPU（x86 の上で ARM など）のゲストも動かせます。KVM と組み合わせると、ゲストの CPU の命令を本物の CPU で直接実行するので、速くなります。

ゲスト 1 台は、ホストから見ると **QEMU のふつうのプロセス 1 つ**です。`ps` や `top` に出ますし、`kill` もできます（[図解 Linux 7 章](../../linux/site/ch07.html)）。

## この機械で KVM は使えるか：vmx、svm、lscpu、モジュール {#check}

KVM を使うには、3 つの条件がそろっている必要があります。

1. CPU に**仮想化支援機能**がある（Intel は **Intel VT** = `vmx`、AMD は **AMD-V** = `svm`）
2. ファームウェア（UEFI / BIOS）の設定で、その機能が**有効**になっている
3. カーネルに **KVM のモジュール**が読み込まれている（`/dev/kvm` がある）

### CPU の印を見る：/proc/cpuinfo と lscpu

CPU の機能は、`/proc/cpuinfo` の `flags` の行に並びます。その中に `vmx` か `svm` があるかを `grep` で探します。小さな Linux で試します。

```sh run error title="仮想化支援機能の印を探す（この CPU にはない）"
grep flags /proc/cpuinfo
grep -E 'vmx|svm' /proc/cpuinfo
```

小さな Linux の CPU には `fpu` しかないので、`grep` は何も出さずに終了ステータス 1 で終わりました。本物の Intel の機械なら、長い `flags` の行が CPU の数だけ表示され、その中に `vmx` が見つかります。

`lscpu` は、同じ情報を読みやすくまとめます。Intel の機械では、次の行が出ます（抜粋）。

```console
$ lscpu | grep -i virtual
Virtualization:                  VT-x
```

| 調べ方 | Intel | AMD |
| --- | --- | --- |
| `/proc/cpuinfo` の `flags` | **`vmx`** | **`svm`** |
| `lscpu` の `Virtualization:` の行 | `VT-x` | `AMD-V` |
| 読み込むモジュール | **`kvm_intel`** | **`kvm_amd`** |

`lscpu` を仮想マシンの**中**で実行すると、`Hypervisor vendor: KVM` と `Virtualization type: full` の行が出ます。これは「自分が KVM の上の、完全仮想化のゲストである」という意味で、ホストの `Virtualization:` の行とは別のものです。

### モジュールを見る：kvm、kvm_intel、kvm_amd

KVM のモジュールは 2 段になっています。共通の部分が `kvm`、CPU ごとの部分が `kvm_intel`（Intel）か `kvm_amd`（AMD）です。Intel の機械での例です。

```console
# lsmod | grep kvm
kvm_intel             380928  0
kvm                  1146880  1 kvm_intel
# ls -l /dev/kvm
crw-rw---- 1 root kvm 10, 232 Nov 17 09:00 /dev/kvm
```

読み込まれていなければ、`modprobe` で読み込みます。`modprobe` は依存するモジュールも一緒に読み込むので、`kvm_intel` を指定すれば `kvm` も入ります（[図解 LinuC 5.2](../../linuc/site/ch05.html#modules)）。

```console
# modprobe kvm_intel
```

モジュールの名前は、出題範囲では `kvm-intel`、`kvm-amd` とハイフンで書かれています。`modprobe` はハイフンと下線を区別しないので、`modprobe kvm-intel` でも同じです。`lsmod` の表示は下線（`kvm_intel`）になります。

モジュールが入ると、**`/dev/kvm`** というデバイスファイルができます。QEMU はこれを開いて KVM を使います。小さな Linux には、ありません。

```sh run error title="/dev/kvm があるか（KVM が使えるホストにはある）"
ls -l /dev/kvm
```

:::tip 切り分けの順番
仮想マシンが遅い、または起動しないときは、下から順に確かめます。

1. `grep -E 'vmx|svm' /proc/cpuinfo` … 印がなければ、CPU が対応していないか、ファームウェアで無効
2. `lsmod | grep kvm` … 何も出なければ、`modprobe kvm_intel`（または `kvm_amd`）
3. `ls -l /dev/kvm` … なければ、QEMU は KVM を使えず、ソフトウェアのエミュレーションになる
4. `systemctl status libvirtd` … libvirtd が動いていなければ、`virsh` はつながらない
:::

## libvirtd と管理の道具は、どうつながるのか {#libvirt}

QEMU を直接起動すると、長いオプションを毎回書くことになります。そこで、**libvirt** という管理の層を使うのがふつうです。libvirt のデーモンが **`libvirtd`** で、仮想マシンの設定を XML で保存し、QEMU を起動したり止めたりします。

libvirt は、KVM / QEMU だけのものではありません。Xen や LXC（コンテナ）なども、同じコマンドで扱えます。どれにつなぐかは、**接続先の URI** で決まります。

| URI | 接続先 |
| --- | --- |
| `qemu:///system` | ホスト全体の KVM / QEMU（root として libvirtd につなぐ。サーバーではふつうこれ） |
| `qemu:///session` | 一般ユーザー自身の KVM / QEMU |
| `xen:///system` | Xen |
| `lxc:///system` | LXC のコンテナ |

`libvirtd` を起動しておきます。止まっていると、`virsh` は接続に失敗します。

```console
# systemctl enable --now libvirtd
# virsh -c qemu:///system list
error: failed to connect to the hypervisor
error: Failed to connect socket to '/var/run/libvirt/libvirt-sock': No such file or directory
```

下の 2 行は、libvirtd が動いていないときのエラーです。`-c`（`--connect`）で、接続先の URI を指定します。

libvirt を使う道具は 3 つ覚えます。どれも libvirtd に頼むだけで、自分では仮想マシンを動かしません。

| 道具 | 種類 | 役目 |
| --- | --- | --- |
| **`virt-manager`** | GUI（仮想マシンマネージャー） | 仮想マシンの作成、起動、停止、設定の変更、画面の表示を、ウィンドウで行う。SSH 越しにリモートのホストも管理できる |
| **`virsh`** | コマンド | 起動、停止、設定の表示と変更など、ほぼすべての操作 |
| **`virt-install`** | コマンド | 仮想マシンを**新しく作る**（[後の節](#virt-install)） |

libvirt が使うファイルの場所です（Debian 12 に libvirt を入れて確かめました）。

| 場所 | 中身 |
| --- | --- |
| `/etc/libvirt/` | libvirt の設定（`libvirtd.conf`、`qemu.conf` など） |
| `/etc/libvirt/qemu/` | 仮想マシン（ドメイン）の定義。**`名前.xml`** が 1 台ぶん |
| `/etc/libvirt/qemu/networks/` | 仮想ネットワークの定義（`default.xml`）。`autostart/` にリンクがあるものは自動で起動する |
| `/var/lib/libvirt/images/` | ディスクイメージの既定の置き場所 |
| `/var/log/libvirt/qemu/` | 仮想マシンごとのログ（`名前.log`） |

:::warn 試験の注意：XML を直接書き換えない
`/etc/libvirt/qemu/名前.xml` をエディタで直接書き換えても、libvirtd は気づきません。設定を変えるときは、`virsh edit 名前`（[後の節](#virsh-config)）を使います。
:::

パッケージの名前は、ディストリビューションで違います。Debian 系では `qemu-system-x86`、`libvirt-daemon-system`、`libvirt-clients`（virsh）、`virtinst`（virt-install）、`virt-manager`、`bridge-utils` です。Red Hat 系では `qemu-kvm`、`libvirt`、`virt-install`、`virt-manager` です。

| つなぎ方 | しくみ | 向いている場面 |
| --- | --- | --- |
| **NAT**（libvirt の `default` ネットワーク） | libvirt が **`virbr0`** というブリッジを作り、ゲストに `192.168.122.0/24` の番地を DHCP で配る。外へはホストが NAT する | ゲストから外へ出るだけでよいとき。**外からゲストへは直接届かない** |
| **ブリッジ接続** | 管理者が `br0` などのブリッジを作り、ホストの物理 NIC を入れる。ゲストは LAN の番地を持つ | ゲストをサーバーとして LAN に公開するとき |

`default` ネットワークの定義です。`virsh net-dumpxml default` で表示できます。

```console
# virsh net-dumpxml default
<network>
  <name>default</name>
  <uuid>dd8fe884-6c02-601e-7551-cca97df1c5df</uuid>
  <forward mode='nat'/>
  <bridge name='virbr0' stp='on' delay='0'/>
  <ip address='192.168.122.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='192.168.122.2' end='192.168.122.254'/>
    </dhcp>
  </ip>
</network>
```

`<forward mode='nat'/>` が NAT、`<bridge name='virbr0'/>` がブリッジの名前、`<dhcp>` の `range` が配る番地の範囲です。

### bridge-utils：brctl でブリッジを作る

ブリッジ接続のための `br0` は、自分で作ります。古くからの道具が **bridge-utils** パッケージの **`brctl`** です。Debian 12 の中で、試しに作った NIC（`dummy0`）を入れてみた結果です。

```console
# brctl addbr br0
# brctl addif br0 dummy0
# brctl show
bridge name	bridge id		STP enabled	interfaces
br0		8000.fe4136efb2ae	no		dummy0
# brctl delif br0 dummy0
# brctl delbr br0
```

| コマンド | 意味 |
| --- | --- |
| `brctl addbr br0` | ブリッジ `br0` を**作る** |
| `brctl delbr br0` | ブリッジ `br0` を**消す**（先に停止しておく） |
| `brctl addif br0 eth0` | `eth0` を `br0` に**つなぐ**（ブリッジの口にする） |
| `brctl delif br0 eth0` | `eth0` を `br0` から**外す** |
| `brctl show` | ブリッジと、つながっているインターフェースの一覧 |
| `brctl stp br0 on` | スパニングツリー（輪になった経路を止めるしくみ）を有効にする |

`brctl show` の `interfaces` の列に、そのブリッジにつながっている口が並びます。ゲストを起動すると、`vnet0`、`vnet1` … という口が増えます。これが、ゲストの NIC のホスト側の端です。

:::note brctl は古い道具
`brctl` のマニュアルには「obsolete（旧式）」とあり、今は iproute2 の `ip link add br0 type bridge`、`ip link set eth0 master br0`、`bridge link` で同じことができます。Red Hat 系の新しい版には bridge-utils のパッケージがありません。試験の範囲には bridge-utils が入っているので、`brctl` の 5 つの命令は覚えます。
:::

## 完全仮想化と準仮想化、virtio は何が違うのか {#virtio}

ゲスト OS にハードウェアをどう見せるかには、2 つの方式があります（[図解 LinuC 1.5](../../linuc/site/ch01.html#vm-container)）。

| 方式 | ゲスト OS | 特徴 |
| --- | --- | --- |
| **完全仮想化** | **修正なし**でそのまま動く | 本物と同じハードウェアに見せる。Windows などもそのまま入る。CPU の仮想化支援機能（vmx / svm）を使う。KVM はこの方式 |
| **準仮想化** | 仮想環境用に**修正したもの**、または専用のドライバが要る | ゲストが「仮想環境にいる」と知っていて、ハイパーバイザーに直接頼む。まねの手間が減って速い。Xen が始めた |

完全仮想化には弱点があります。装置のまねが遅いことです。QEMU が実在のネットワークカード（`e1000`、`rtl8139`）や IDE のディスクをまねると、ゲストがレジスタを 1 回さわるたびに QEMU へ処理が移ります。

そこで、**CPU は完全仮想化のまま、装置だけ準仮想化する**という組み合わせが使われます。そのための装置の規格が **virtio**（バーチオ）です。

```fig graph エミュレーション（左）は、実在の装置のふりをする。ゲストは標準のドライバで動くが遅い。virtio（右）は、仮想環境専用の装置。ゲストに virtio のドライバが要るが速い
{
  col: 250, row: 74,
```

| virtio の装置 | ゲストのドライバ | ゲストからの見え方 |
| --- | --- | --- |
| ディスク（virtio-blk） | `virtio_blk` | **`/dev/vda`**、`/dev/vdb` …（IDE や SATA のまねなら `/dev/sda`） |
| ネットワーク（virtio-net） | `virtio_net` | ふつうの NIC（`eth0`、`enp1s0` など） |
| メモリバルーン | `virtio_balloon` | 動作中にゲストのメモリを増減するしくみ |

virtio を使うには、**ゲスト OS に virtio のドライバが必要**です。Linux のカーネルには初めから入っています。Windows には入っていないので、別にドライバを入れます。

:::warn 試験の注意：virtio は「準仮想化」の側
- virtio は、準仮想化の**ドライバ**（装置）の規格。CPU の仮想化支援機能の代わりにはならない
- virtio のディスクは `/dev/vda`。`/dev/sda` ではない
- 完全仮想化は「ゲスト OS を**修正しない**」、準仮想化は「ゲスト OS を**修正する**（専用のドライバを使う）」
:::

## virt-install で仮想マシンを作るには {#virt-install}

仮想マシンを作る道具は 2 つあります。GUI の **`virt-manager`** は、「新しい仮想マシン」のウィザードで、インストール元、メモリと CPU、ディスクを順に聞いてきます。コマンドの **`virt-install`** は、同じことをオプションで指定します。

```console
# virt-install \
    --name web01 \
    --memory 2048 \
    --vcpus 2 \
    --disk path=/var/lib/libvirt/images/web01.qcow2,size=10,format=qcow2,bus=virtio \
    --cdrom /var/lib/libvirt/images/debian-12.iso \
    --os-variant debian11 \
    --network bridge=br0,model=virtio \
    --graphics vnc
```

これで、定義（XML）とディスクイメージが作られ、仮想マシンが起動して、ISO からインストーラが始まります。

### 基本のオプション

| オプション | 意味 |
| --- | --- |
| `--name 名前`（`-n`） | 仮想マシンの名前 |
| `--memory 2048` | メモリ。単位は **MiB**（古い書き方は `--ram`） |
| `--vcpus 2` | 仮想 CPU の数 |
| `--disk …` | ディスク。`size=10` は **GiB**。`path=` で場所、`format=` で形式（`qcow2`、`raw`）、`bus=virtio` でつなぎ方 |
| `--network …`（`-w`） | NIC。`bridge=br0`（ホストのブリッジ）か `network=default`（libvirt の仮想ネットワーク）。`model=virtio` で種類 |
| `--graphics …` | 画面。`vnc`、`spice`、`none`（画面なし。テキストのコンソールを使う） |
| `--os-variant 名前`（`--osinfo`） | ゲスト OS の種類。virtio を使うかなど、**最適な既定値を選ぶ**のに使われる。一覧は `virt-install --osinfo list` |
| `--connect URI` | 接続先（例 `qemu:///system`） |

`--disk size=10` とだけ書くと、既定の場所（`/var/lib/libvirt/images/`）に、**qcow2 形式**の 10 GiB のイメージが作られます。`--network` を省くと、物理 NIC の入ったブリッジがあればそれに、なければ `default` ネットワークにつながります。

ディスクイメージの形式は 2 つ覚えます。**raw** は中身をそのまま並べた形式で、単純で速い代わりに機能がありません。**qcow2** は QEMU の形式で、使った分だけファイルが大きくなり、スナップショットが取れます。

### インストール元のオプション

インストールの方法は、次のどれかを必ず指定します。指定しないと、`An install method must be specified` というエラーになります。

| オプション | インストール元 |
| --- | --- |
| `--cdrom ISO ファイル` | CD / DVD のイメージ（ISO）から起動する |
| `--location URL`（`-l`） | ネットワーク上（または ISO の中）のインストール用のツリー。カーネルと initrd を取ってきて起動する |
| `--pxe` | ネットワークブート（PXE） |
| `--import` | **インストールしない**。すでに OS が入っているディスクイメージから、そのまま起動する |

カーネルに引数を渡す **`--extra-args`**（`-x`）は、**`--location` のときだけ**使えます。画面なしでインストールするときは、次のように組み合わせます。

```console
# virt-install --name web02 --memory 1024 --disk size=8 \
    --location http://deb.debian.org/debian/dists/bookworm/main/installer-amd64/ \
    --os-variant debian11 --graphics none --extra-args 'console=ttyS0'
```

### 仮想化の種類と、そのほかのオプション

| オプション | 意味 |
| --- | --- |
| `--hvm`（`-v`） | **完全仮想化**のゲストにする（QEMU / KVM ではこれが既定） |
| `--paravirt`（`-p`） | **準仮想化**のゲストにする（Xen で使う） |
| `--virt-type kvm` | 使うハイパーバイザー（`kvm`、`qemu`、`xen`）。`qemu` は KVM を使わないエミュレーション |
| `--autostart` | ホストの起動時に、自動で起動する |
| `--noautoconsole` | 作成のあと、ゲストのコンソールに自動でつながない |
| `--dry-run` | 手順を最後までたどるが、ディスクも定義も**作らない** |
| `--print-xml` | 仮想マシンを定義する代わりに、作られる **XML を表示**する |

`--dry-run` と `--print-xml` を付けて実行すると、ドメインの XML が見えます（抜粋。練習用の接続で試したので `type` は `test` ですが、KVM では `<domain type='kvm'>` になります）。

```console
# virt-install --name web01 --memory 2048 --vcpus 2 \
    --disk path=/tmp/web01.qcow2,size=10,format=qcow2,bus=virtio --cdrom /tmp/x.iso \
    --os-variant debian11 --network bridge=br0,model=virtio --graphics vnc --dry-run --print-xml
<domain type="test">
  <name>web01</name>
  <memory>2097152</memory>
  <vcpu>2</vcpu>
  <os>
    <type arch="i686">hvm</type>
  </os>
  <devices>
    <disk type="file" device="disk">
      <source file="/tmp/web01.qcow2"/>
      <target dev="vda" bus="virtio"/>
    </disk>
    <interface type="bridge">
      <source bridge="br0"/>
      <model type="virtio"/>
    </interface>
    <graphics type="vnc" port="-1"/>
  </devices>
</domain>
```

読み方です。`<memory>` は KiB（2048 MiB = 2097152 KiB）、`<type>hvm</type>` は完全仮想化、`<target dev="vda" bus="virtio"/>` は virtio のディスク、`<interface type="bridge">` と `<source bridge="br0"/>` は br0 へのブリッジ接続です。

:::warn 試験の注意：virt-install の単位と必須のもの
- `--memory` は **MiB**、`--disk size=` は **GiB**
- インストール元（`--cdrom`、`--location`、`--pxe`、`--import` のどれか）がないと作れない
- 既存のイメージを使うのは `--import`。`--cdrom` はインストーラを起動する
- `--extra-args` は `--location` と組み合わせる。`--cdrom` とは使えない
:::

libvirt では、仮想マシンを**ドメイン**と呼びます。レベル1 で学んだコマンド（[図解 LinuC 1.6](../../linuc/site/ch01.html#virsh)）を、状態の図で整理します。

```console
# virsh list --all

# virsh define /tmp/d.xml
```

`virsh list` は動いているもの（`running` と `paused`）だけを出します。止まっているものも見るには `--all` を付けます。止まっているドメインの `Id` は `-` です。

| コマンド | 意味 |
| --- | --- |
| `virsh list [--all]` | ドメインの一覧（`--all` で停止中も） |
| `virsh define ファイル.xml` | XML から**登録する**。起動はしない |
| `virsh undefine 名前` | **登録を消す**。ディスクイメージは消えない（消すには `--remove-all-storage`） |
| `virsh create ファイル.xml` | XML から**登録せずに起動する**。止めると跡が残らない（一時的なドメイン） |
| `virsh start 名前` | 定義済みのドメインを起動する |
| `virsh shutdown 名前` | ゲスト OS に頼んで、**正しい手順で**止める。ゲストが応じなければ止まらない |
| `virsh destroy 名前` | **強制停止**。電源コードを抜くのと同じ。定義もディスクも消えない |
| `virsh reboot 名前` | ゲスト OS に頼んで再起動する |
| `virsh reset 名前` | リセットボタンを押すのと同じ（強制の再起動） |
| `virsh suspend 名前` / `resume 名前` | 一時停止する（メモリに載ったまま CPU を止める）/ 再開する |
| `virsh save 名前 ファイル` / `restore ファイル` | メモリの中身をファイルに保存して止める / そこから再開する |
| `virsh autostart 名前` | ホストの起動時（libvirtd の起動時）に**自動で起動**する。やめるには `--disable` |

:::warn 試験の注意：名前にだまされない
- **`destroy` は消さない**。強制停止するだけで、`start` でまた起動できる。登録を消すのは `undefine`
- **`create` は「作って登録」ではない**。登録せずに起動する。登録は `define`
- 一時停止からの再開は **`resume`**。`start` は `shut off` のドメインに使う
- `shutdown` はゲストの協力が要る（ACPI の電源ボタンの信号をゲストが処理する）。止まらないときに `destroy`
:::

:::deep 動いているドメインを undefine すると
動作中のドメインに `virsh undefine` を実行しても、ドメインは止まりません。**定義だけが消えて、一時的なドメインに変わります**。`virsh dominfo` の `Persistent:` が `yes` から `no` になり、次に止まったときに一覧から消えます。練習用の接続で確かめた結果です。

```console
# virsh undefine web01
Domain 'web01' has been undefined

# virsh list --all
 Id   Name    State
------------------------
 5    web01   running
 -    test    shut off

# virsh destroy web01
Domain 'web01' destroyed

# virsh list --all
 Id   Name   State
-----------------------
 -    test   shut off
```
:::

## virsh で設定を見る・変えるには {#virsh-config}

### 情報を見る

```console
# virsh dominfo web01
Id:             3
Name:           web01
UUID:           d297956f-b307-4c9f-aa4a-b77c3ddc3a43
OS Type:        linux
State:          running
CPU(s):         2
Max memory:     2097152 KiB
Used memory:    1048576 KiB
Persistent:     yes
Autostart:      disable
```

| コマンド | 表示するもの |
| --- | --- |
| `virsh dominfo 名前` | 状態、CPU の数、メモリ、自動起動かどうかの**要約** |
| `virsh domstate 名前` | 状態だけ（`running`、`paused`、`shut off`） |
| `virsh dumpxml 名前` | 設定の **XML 全体**を標準出力に出す。`> ファイル` で保存すれば、`define` で別のホストに登録できる |
| `virsh domblklist 名前` | ディスクの一覧（`vda` とイメージのパス） |
| `virsh domiflist 名前` | NIC の一覧（`vnet0`、つなぎ先、MAC アドレス） |
| `virsh vncdisplay 名前` | VNC の画面の番号（`:0` なら 5900 番ポート） |
| `virsh nodeinfo` | **ホスト**の CPU とメモリ |

### 設定を変える

**`virsh edit 名前`** は、ドメインの XML をエディタ（`$VISUAL` か `$EDITOR`。なければ vi）で開きます。保存して閉じると、内容を検査して登録し直します。変えた内容が効くのは、**次に起動したとき**です。

CPU の数とメモリは、専用のコマンドでも変えられます。

```console
# virsh setvcpus web01 2 --config
# virsh setmem web01 1G --live
```

| オプション | 変える対象 |
| --- | --- |
| `--config` | 保存されている設定。**次の起動から**効く |
| `--live` | **動作中**のドメイン。すぐに効く（止めると元に戻る） |
| `--config --live` | 両方 |

`setvcpus` と `setmem` で指定できるのは、XML の最大値（`<vcpu>`、`<memory>`）までです。最大値そのものを変えるには、`virsh setvcpus 名前 数 --maximum --config` や `virsh setmaxmem` を使い、ドメインを起動し直します。

### コンソールにつなぐ

**`virsh console 名前`** は、ゲストのシリアルコンソールにつなぎます。SSH が使えないときや、`--graphics none` で作ったときに使います。抜けるには **Ctrl + ]** を押します（`exit` はゲストからログアウトするだけです）。

### スナップショット

ある時点の状態を取っておき、あとで戻せます（ディスクが qcow2 のとき）。

```console
# virsh snapshot-create-as web01 snap1
Domain snapshot snap1 created
# virsh snapshot-list web01
 Name    Creation Time               State
----------------------------------------------
 snap1   2026-11-16 21:21:46 +0000   running

# virsh snapshot-revert web01 snap1
Domain snapshot snap1 reverted
# virsh snapshot-delete web01 snap1
Domain snapshot snap1 deleted
```

### ネットワークとストレージ

仮想ネットワークも、ドメインと同じ形のコマンドで扱います。頭に `net-` が付きます。

```console
# virsh net-list --all
 Name      State      Autostart   Persistent
----------------------------------------------
 default   inactive   yes         yes

# virsh net-start default
Network default started
```

| コマンド | 意味 |
| --- | --- |
| `virsh net-list [--all]` | 仮想ネットワークの一覧 |
| `virsh net-start 名前` / `net-destroy 名前` | 開始する / 停止する（定義は残る） |
| `virsh net-autostart 名前` | 自動で開始するようにする |
| `virsh net-dumpxml 名前` / `net-edit 名前` | 定義の XML を表示する / 編集する |
| `virsh pool-list [--all]` | ストレージプール（ディスクイメージの置き場所）の一覧 |
| `virsh vol-list プール` | プールの中のボリューム（イメージ）の一覧 |

ゲストが `default` ネットワークにつながらないときは、まず `virsh net-list --all` で `State` が `active` かを見ます。`inactive` なら `net-start` で開始し、`net-autostart` で次からは自動にします。

:::key まとめ
- 型：**ホスト型**は VirtualBox。**ハイパーバイザー型**は Xen と **KVM**。Xen の管理用のドメインは Dom0
- **KVM** はカーネルモジュール（`kvm` + `kvm_intel` / `kvm_amd`）で、CPU を仮想化する。**QEMU** は装置をエミュレートする。QEMU は単体でも動くが遅い。窓口は `/dev/kvm`
- CPU の印は Intel が **`vmx`**、AMD が **`svm`**。`grep -E 'vmx|svm' /proc/cpuinfo` か `lscpu` の `Virtualization:` で確かめる
- **libvirtd** が管理のデーモン。`virt-manager`（GUI）、`virsh`、`virt-install` はその利用者。定義は `/etc/libvirt/qemu/名前.xml`、イメージは `/var/lib/libvirt/images/`
- ネットワーク：`default` は `virbr0`、`192.168.122.0/24`、NAT。LAN に直接つなぐならブリッジ。`brctl addbr`、`addif`、`delif`、`delbr`、`show`
- **完全仮想化**はゲスト OS を修正しない。**準仮想化**は修正する（専用ドライバ）。**virtio** は準仮想化の装置で、ディスクは `/dev/vda`
- `virt-install`：`--memory`（MiB）、`--disk size=`（GiB）、`--cdrom` / `--location` / `--pxe` / `--import`、`--network bridge=…,model=virtio`、`--graphics`、`--os-variant`、`--extra-args` は `--location` と
- `virsh`：`define`（登録）と `create`（登録せず起動）、`shutdown`（頼む）と `destroy`（強制。消さない）、`undefine`（登録を消す）、`suspend` / `resume`、`autostart`
- `virsh dumpxml`（XML を表示）、`edit`（編集。次の起動から）、`setvcpus` / `setmem` の `--config`（次から）と `--live`（今すぐ）、`console` は **Ctrl + ]** で抜ける
:::

### 2.05.1 仮想マシンの仕組みと KVM

:::q 2.05.1-01 single
ホスト OS の上でアプリケーションとして動く、ホスト型の仮想化ソフトウェアはどれか。
- [ ] KVM
- [ ] Xen
- [x] VirtualBox
- [ ] VMware ESXi
:::why
VirtualBox は、Windows や Linux などのホスト OS に入れて使う、ホスト型です（[ホスト型とハイパーバイザー型](#types)）。

- KVM は Linux カーネルのモジュールで、カーネルそのものをハイパーバイザーにします。ハイパーバイザー型です
- Xen と VMware ESXi は、ハードウェアのすぐ上で動くハイパーバイザー型です
:::
:::

:::q 2.05.1-02 single
KVM の説明として、正しいものはどれか。
- [ ] ディスクやネットワークカードなどの装置を、ソフトウェアでエミュレートするユーザー空間のプログラムである
- [x] Linux カーネルのモジュールで、CPU の仮想化支援機能を使ってゲストの命令を実行する。装置のエミュレーションは QEMU と組み合わせて行う
- [ ] ホスト OS のカーネルを共有し、名前空間でプロセスを分けて動かすしくみである
- [ ] 仮想マシンの定義を XML で保存し、起動や停止を受け付けるデーモンである
:::why
KVM が受け持つのは CPU とメモリの仮想化で、カーネルの中で動きます。装置のまねは QEMU の役目です（[KVM と QEMU の分担](#kvm-qemu)）。

- 装置をエミュレートするユーザー空間のプログラムは、**QEMU** です
- カーネルを共有して名前空間で分けるのは、**コンテナ**です
- 定義を XML で保存して起動や停止を受け付けるデーモンは、**libvirtd** です
:::
:::

:::q 2.05.1-03 single
あるホストで、次の結果が得られた（`flags` の行は一部を省略している）。

```text
# grep -m1 flags /proc/cpuinfo
flags		: fpu vme de pse tsc msr pae mce cx8 apic sep mtrr ... lm svm ... npt
```

このホストで KVM を使うために、CPU に合わせて読み込むモジュールはどれか。
- [ ] `kvm_intel`
- [x] `kvm_amd`
- [ ] `kvm_svm`
- [ ] `virtio_blk`
:::why
`svm` は AMD の仮想化支援機能（AMD-V）の印です。AMD 用のモジュールは `kvm_amd` です（[KVM が使えるか確かめる](#check)）。

- `kvm_intel` は、`vmx`（Intel VT）がある CPU 用です
- `kvm_svm` というモジュールはありません。印の名前（svm）とモジュールの名前（kvm_amd）は別です
- `virtio_blk` は、**ゲストの中**で使う virtio のディスクのドライバです
:::
:::

:::q 2.05.1-04 fill
Intel の CPU を持つホストで、`/proc/cpuinfo` に `vmx` の印がある。KVM の、Intel 用のモジュールを読み込みたい。空欄に入るモジュールの名前を入力してください。

```text

```
= kvm_intel
= kvm-intel
:::why
Intel 用は `kvm_intel` です。`modprobe` は依存する `kvm` も一緒に読み込みます。`modprobe` はハイフンと下線を区別しないので、出題範囲の表記の `kvm-intel` でも同じです。AMD 用は `kvm_amd`（`kvm-amd`）です（[モジュールを見る](#check)）。
:::
:::

:::q 2.05.1-05 single
Intel の CPU を持つホストで、次の結果が得られた。

```text
# grep -c vmx /proc/cpuinfo
8
# lsmod | grep kvm
# ls /dev/kvm
ls: cannot access '/dev/kvm': No such file or directory
```

KVM を使えるようにするために、まず行うこととして最も適切なものはどれか。
- [ ] `brctl addbr br0` でブリッジを作る
- [ ] `virsh define` で仮想マシンを登録し直す
- [x] `modprobe kvm_intel` でモジュールを読み込む
- [ ] `virt-install --virt-type xen` で仮想マシンを作り直す
:::why
CPU に `vmx` の印はありますが、`lsmod` に KVM のモジュールがなく、そのため `/dev/kvm` もありません。`modprobe kvm_intel` で読み込むと、`kvm` も一緒に入り、`/dev/kvm` ができます（[切り分けの順番](#check)）。

- ブリッジはネットワークのつなぎ方の話で、`/dev/kvm` とは関係しません
- `virsh define` は定義を登録するだけです。モジュールは読み込みません
- `--virt-type xen` は Xen を使う指定で、KVM は有効になりません
:::
:::

:::q 2.05.1-06 single
ホストで `lscpu` を実行したところ、次の行があった。

```text
Virtualization:                  VT-x
```

この行の説明として、正しいものはどれか。
- [ ] この機械は、KVM の上で動いている仮想マシンである
- [ ] CPU が AMD の仮想化支援機能を持っている。`/proc/cpuinfo` の印は `svm` である
- [x] CPU が Intel の仮想化支援機能を持っている。`/proc/cpuinfo` の印は `vmx` である
- [ ] ゲスト OS が、準仮想化のドライバ（virtio）を使っている
:::why
`Virtualization: VT-x` は、CPU が Intel VT に対応しているという意味です。`/proc/cpuinfo` では `vmx` の印にあたります（[CPU の印を見る](#check)）。

- 仮想マシンの中で実行すると出るのは、`Hypervisor vendor: KVM` と `Virtualization type: full` の行です
- AMD なら `Virtualization: AMD-V` と表示され、印は `svm` です
- virtio を使っているかどうかは、`lscpu` のこの行ではわかりません
:::
:::

:::q 2.05.1-07 single
QEMU の説明として、正しいものはどれか。
- [ ] KVM のモジュールがないと、仮想マシンを 1 台も動かせない
- [ ] カーネルのモジュールとして動き、`/dev/kvm` を提供する
- [x] KVM がなくても単体で仮想マシンを動かせるが、CPU の命令もソフトウェアでエミュレートするので遅い
- [ ] 仮想マシンの NIC をつなぐブリッジを作るための、コマンドの集まりである
:::why
QEMU は、CPU を含めた機械全体をソフトウェアでまねできるエミュレータです。単体でも動きますが遅く、KVM と組み合わせると CPU の命令を本物の CPU で実行できるので速くなります（[KVM と QEMU の分担](#kvm-qemu)）。

- KVM がなくても動きます。ホストと違う種類の CPU のゲストも動かせます
- `/dev/kvm` を提供するのは、カーネルの KVM のモジュールです。QEMU はユーザー空間のプロセスです
- ブリッジを作るコマンド（`brctl`）の集まりは、bridge-utils です
:::
:::

:::q 2.05.1-08 multi
libvirtd の説明として、正しいものを 2 つ選択してください。
- [x] 仮想マシンを管理するデーモンで、`virsh` や `virt-manager` はこれに接続して操作を頼む
- [ ] CPU の仮想化支援機能を直接使う、カーネルのモジュールである
- [x] KVM / QEMU だけでなく、Xen や LXC なども、接続先の URI を変えて同じ操作で扱える
- [ ] ゲスト OS の中で動かし、ホストにゲストの状態を知らせるエージェントである
- [ ] 止まっていても、`virsh -c qemu:///system list` は仮想マシンの一覧を表示できる
:::why
libvirtd は、仮想マシンの定義を保存し、QEMU の起動や停止を行う管理のデーモンです。`qemu:///system`、`xen:///system`、`lxc:///system` のように、URI で接続先の種類を選べます（[libvirtd と管理の道具](#libvirt)）。

- カーネルのモジュールは `kvm`、`kvm_intel`、`kvm_amd` です。libvirtd はユーザー空間のデーモンです
- libvirtd はホストで動きます。ゲストの中で動かすものではありません
- 止まっていると、`virsh` は `failed to connect to the hypervisor` というエラーで接続に失敗します
:::
:::

:::q 2.05.1-09 single
libvirt を入れたホストで、次の結果が得られた。


このネットワークにつないだゲストの説明として、正しいものはどれか。
- [ ] ゲストはホストの物理 NIC と同じ LAN の番地を持ち、LAN のほかの機械から直接つながる
- [x] ゲストは `virbr0` につながり、192.168.122.0/24 の番地を DHCP で受け取る。外へはホストの NAT を通って出る
- [ ] ゲストどうしは通信できるが、ホストとも外とも通信できない

`<forward mode='nat'/>` は NAT、`<bridge name='virbr0'/>` はブリッジの名前、`<dhcp>` の `range` は配る番地の範囲です。ゲストは内側の番地を持ち、外へはホストの番地に変換されて出ます（[仮想マシンのネットワーク](#bridge)）。

- LAN の番地を持って直接つながるのは、ホストの物理 NIC を入れたブリッジ（`br0` など）につないだときです
- NAT なので、外へ出られます。ホスト（192.168.122.1）とも通信できます
- `brctl addif` は、インターフェースをブリッジにつなぐコマンドです。番地は配りません
:::
:::

:::q 2.05.1-10 fill
ホストの物理 NIC `eth0` を、ブリッジ `br0` につなぎたい。空欄に入る `brctl` のサブコマンドを入力してください。

= addif
:::why
`brctl addif ブリッジ インターフェース` で、インターフェースをブリッジの口にします。ブリッジを作るのは `addbr`、口を外すのは `delif`、ブリッジを消すのは `delbr`、一覧は `show` です（[bridge-utils](#bridge)）。
:::
:::

:::q 2.05.1-11 single

:::q 2.05.1-12 multi

- [x] `grep -E 'vmx|svm' /proc/cpuinfo` を実行して、行が表示されるかを見る
- [ ] `brctl show` を実行して、ブリッジがあるかを見る
- [x] `lscpu` を実行して、`Virtualization:` の行に `VT-x` か `AMD-V` があるかを見る

- `brctl show` はブリッジの一覧で、CPU の機能は出ません
- `virsh net-list` は libvirt の仮想ネットワークの一覧です
- `/dev/vda` は、virtio のディスクをゲストの中から見た名前です。ホストの CPU の機能とは関係しません
:::
:::

:::q 2.05.1-13 multi
ハードウェアのすぐ上で動く、ハイパーバイザー型に分類されるものを 2 つ選択してください。

- [x] Xen

- [ ] VMware Workstation

KVM は Linux カーネルそのものをハイパーバイザーにし、Xen はハードウェアの上で Xen 本体が動きます。どちらもハイパーバイザー型です。Xen では、管理用のドメインを Dom0、ふつうのゲストを DomU と呼びます（[ホスト型とハイパーバイザー型](#types)）。

- VirtualBox と VMware Workstation は、ホスト OS の上のアプリとして動く、ホスト型です
- Docker はコンテナの道具です。ハイパーバイザーではありません
:::
:::

:::q 2.05.1-14 single

- [ ] 仮想マシンの定義を XML で保存し、QEMU を起動するデーモンである

virt-manager（仮想マシンマネージャー）は、libvirtd に接続して使う GUI の道具です。新しい仮想マシンをウィザードで作れ、SSH 越しにリモートのホストも管理できます（[libvirtd と管理の道具](#libvirt)）。

- bridge-utils のコマンドは `brctl` です
- 仮想化支援機能は、`lscpu` や `grep -E 'vmx|svm' /proc/cpuinfo` で調べます
- 定義を保存して QEMU を起動するデーモンは、libvirtd です。virt-manager はその利用者です
:::
:::

:::q 2.05.1-15 multi

- [x] `/etc/libvirt/qemu/` には、仮想マシンごとの定義が `名前.xml` として置かれる
- [ ] `/proc/kvm/` には、動作中の仮想マシンごとのディレクトリが作られる
- [x] `/var/lib/libvirt/images/` は、ディスクイメージの既定の置き場所である
- [ ] `/var/log/libvirt/qemu/` には、仮想マシンの定義の XML が置かれる
- [ ] `/dev/kvm` は、仮想マシンのディスクイメージを表すブロックデバイスである

- `/var/log/libvirt/qemu/` に置かれるのは、仮想マシンごとの**ログ**（`名前.log`）です
- `/dev/kvm` は、QEMU が KVM を使うための窓口の、キャラクタデバイスです。ディスクではありません

### 2.05.2 仮想マシンの作成と管理

:::q 2.05.2-01 single
次のコマンドで作られる仮想マシンの説明として、正しいものはどれか。

```text
# virt-install --name db01 --memory 4096 --vcpus 2 --disk size=20 \
    --cdrom /var/lib/libvirt/images/rocky9.iso --os-variant rocky9
```

- [ ] メモリは 4096 KiB、ディスクは 20 MiB
- [ ] メモリは 4096 MiB、ディスクは 20 MiB
- [x] メモリは 4096 MiB、ディスクは 20 GiB
- [ ] メモリは 4096 GiB、ディスクは 20 GiB
:::why
`--memory` の単位は MiB、`--disk` の `size=` の単位は GiB です。`path=` を書かなければ、既定の場所に qcow2 形式で作られます（[基本のオプション](#virt-install)）。
:::
:::

:::q 2.05.2-02 single
`virt-install` の `--os-variant`（`--osinfo`）オプションの説明として、正しいものはどれか。
- [ ] インストールに使う ISO イメージの場所を指定する
- [x] ゲスト OS の種類を伝えて、virtio を使うかなどの最適な既定値を選ばせる
- [ ] ゲスト OS を、完全仮想化ではなく準仮想化で動かすように指定する
- [ ] 使うハイパーバイザーを、`kvm`、`qemu`、`xen` から選ぶ
:::why
`--os-variant` に `debian11` や `rocky9` などの名前を渡すと、その OS に合った装置の種類（virtio のディスクや NIC など）が選ばれます。使える名前は `virt-install --osinfo list` で見られます（[基本のオプション](#virt-install)）。

- ISO の場所は `--cdrom` です
- 準仮想化のゲストにするのは `--paravirt`、完全仮想化は `--hvm` です
- ハイパーバイザーを選ぶのは `--virt-type` です
:::
:::

:::q 2.05.2-03 fill
OS がすでに入っているディスクイメージ `/var/lib/libvirt/images/app01.qcow2` がある。インストールを行わずに、このイメージからそのまま起動する仮想マシンを作りたい。空欄に入るオプションを入力してください。

```text
# virt-install --name app01 --memory 2048 --os-variant debian11 \
    --disk /var/lib/libvirt/images/app01.qcow2 ____
```

:::why
`--import` は、OS のインストールを飛ばして、`--disk` で指定した既存のイメージから起動する仮想マシンを作ります。インストール元のオプションは、`--cdrom`（ISO）、`--location`（インストール用のツリー）、`--pxe`（ネットワークブート）、`--import` のどれかが必要です（[インストール元のオプション](#virt-install)）。
:::
:::

:::q 2.05.2-04 single
`virt-install` に次のオプションを付けた。説明として正しいものはどれか。

```text
--network bridge=br0,model=virtio
```

- [ ] libvirt の仮想ネットワーク `br0` を新しく作り、NAT で外へ出られるようにする
- [x] ゲストの NIC をホストのブリッジ `br0` につなぎ、NIC の種類を virtio にする
- [ ] ホストの `br0` に、物理 NIC の `virtio` をつなぐ
- [ ] ゲストに NIC を付けずに作る
:::why
`bridge=br0` は、ホストにすでにあるブリッジ `br0` につなぐ指定です。`model=virtio` は、ゲストから見える NIC の種類で、ほかに `e1000`、`rtl8139` などがあります（[基本のオプション](#virt-install)）。

- libvirt の仮想ネットワークにつなぐのは `network=名前`（例 `--network network=default`）です。`virt-install` はブリッジを作りません
- 物理 NIC をブリッジにつなぐのは、`brctl addif br0 eth0` です
- NIC を付けないのは `--network none` です
:::
:::

:::q 2.05.2-05 single
`virt-install` で、インストーラのカーネルに `console=ttyS0` という引数を渡すために `--extra-args 'console=ttyS0'` を付けたい。組み合わせて使うインストール元のオプションはどれか。
- [ ] `--cdrom`
- [x] `--location`
- [ ] `--import`
- [ ] `--pxe`
:::why
`--extra-args`（`-x`）は、`--location` で取ってきたインストール用のカーネルに引数を渡すオプションです。`--location` は、カーネルと initrd を virt-install が直接読み込んで起動するので、引数を足せます（[インストール元のオプション](#virt-install)）。

- `--cdrom` は ISO のブートローダから起動するので、virt-install からはカーネルの引数を渡せません
- `--import` はインストールをせず、既存のディスクから起動します
- `--pxe` はネットワークブートで、カーネルは PXE のサーバーが渡します
:::
:::

:::q 2.05.2-06 multi
virtio の説明として、正しいものを 2 つ選択してください。
- [x] 使うには、ゲスト OS に virtio 用のドライバが必要である
- [ ] 使うと、ホストの CPU に仮想化支援機能（vmx / svm）がなくても KVM が動く
- [x] virtio でつないだディスクは、Linux のゲストから `/dev/vda` のような名前で見える
- [ ] 実在するネットワークカードやディスクコントローラの動きを、忠実にまねる方式である
- [ ] ホストのカーネルに読み込む、`kvm_intel` の代わりのモジュールである
:::why
virtio は、仮想環境専用の装置の規格です。ゲストが専用のドライバ（`virtio_blk`、`virtio_net`）を使うことで、実在の装置をまねるより速くなります。virtio のディスクは `/dev/vda` と見えます（[完全仮想化と準仮想化、virtio](#virtio)）。

- virtio は装置（入出力）の話です。CPU の仮想化支援機能の代わりにはなりません
- 実在の装置（`e1000`、IDE など）を忠実にまねるのは、エミュレーションです。virtio はその逆です
- `kvm_intel` はホストの KVM のモジュールです。virtio のドライバはゲストの側に入れます
:::
:::

:::q 2.05.2-07 single
完全仮想化の説明として、正しいものはどれか。
- [ ] ゲスト OS のカーネルを仮想環境用に修正し、ハイパーバイザーを直接呼び出させる
- [ ] ホスト OS のカーネルを共有し、ゲストはカーネルを持たない
- [x] 本物と同じハードウェアに見せるので、ゲスト OS を修正せずにそのまま動かせる
- [ ] ゲスト OS は Linux に限られ、Windows は動かせない
:::why
完全仮想化は、ゲスト OS から本物の機械と同じに見えるので、修正なしで動きます。CPU の仮想化支援機能を使う KVM は、この方式です（[完全仮想化と準仮想化、virtio](#virtio)）。

- ゲスト OS を修正してハイパーバイザーを直接呼び出させるのは、**準仮想化**です
- カーネルを共有するのは、**コンテナ**です
- 修正が要らないので、Windows などもそのまま動かせます
:::
:::

:::q 2.05.2-08 single
次の状態のとき、`db01` をふたたび動かすコマンドはどれか。

```text
# virsh list --all
 Id   Name    State
------------------------
 2    db01    paused
 -    web01   shut off
```

- [ ] `virsh start db01`
- [x] `virsh resume db01`
- [ ] `virsh restore db01`
- [ ] `virsh create db01`
:::why
`paused` は、`virsh suspend` で一時停止した状態です。再開するのは `virsh resume` です（[virsh で状態を変える](#virsh-life)）。

- `virsh start` は、`shut off`（停止中）のドメインを起動します。この例では `web01` に使います
- `virsh restore` は、`virsh save` で保存した**ファイル**から再開します。引数はファイルの名前です
- `virsh create` は、XML ファイルから登録せずに起動します。引数は XML ファイルです
:::
:::

:::q 2.05.2-09 single
`virsh define` で登録して起動した、動作中のドメイン `web01` に対して、`virsh undefine web01` を実行した。結果として正しいものはどれか。
- [ ] ドメインはただちに強制停止され、ディスクイメージも削除される
- [ ] 動作中のドメインには使えないので、エラーになって何も変わらない
- [x] ドメインは動き続けるが、定義が消えて一時的なドメインになり、止まると一覧から消える
- [ ] ドメインは正しい手順でシャットダウンされ、定義は残る
:::why
`virsh undefine` は、登録（保存された定義）を消すコマンドです。動作中のドメインは止めずに、一時的なドメインに変えます。`virsh dominfo` の `Persistent:` が `no` になり、止めると `virsh list --all` からも消えます（[動いているドメインを undefine すると](#virsh-life)）。

- 強制停止は `virsh destroy` です。`undefine` はディスクイメージも消しません（消すには `--remove-all-storage`）
- 動作中でも実行できます
- 正しい手順のシャットダウンは `virsh shutdown` です
:::
:::

:::q 2.05.2-10 multi
`virsh define` と `virsh create` の説明として、正しいものを 2 つ選択してください。どちらも、まだ登録していない仮想マシンの XML ファイルを引数に渡すものとする。
- [x] `virsh define` は、定義を登録するだけで、仮想マシンを起動しない
- [ ] `virsh define` は、定義を登録して、すぐに仮想マシンを起動する
- [ ] `virsh create` は、空のディスクイメージを新しく作成する
- [x] `virsh create` は、仮想マシンを起動するが、定義を登録しないので、止めると一覧に残らない
- [ ] `virsh create` で起動した仮想マシンは、ホストの起動時に自動で起動する
:::why
`define` は登録だけ、`create` は登録せずに起動です。`create` で起動したドメインは一時的で、`virsh destroy` などで止めると、`virsh list --all` にも出なくなります（[virsh で状態を変える](#virsh-life)）。

- `define` のあとに起動するには、`virsh start` を使います
- ディスクイメージを作るのは、`virt-install` の `--disk size=…` や `qemu-img create` です
- 自動で起動するのは、`virsh autostart` を設定した、登録済みのドメインです
:::
:::

:::q 2.05.2-11 fill
登録済みのドメイン `web01` を、ホストの起動時に自動で起動するようにしたい。空欄に入る `virsh` のサブコマンドを入力してください。

```text
# virsh ____ web01
Domain 'web01' marked as autostarted
```
= autostart
:::why
`virsh autostart 名前` で、ホスト（libvirtd）の起動時に自動で起動するようになります。やめるには `virsh autostart --disable 名前` です。`virsh dominfo` の `Autostart:` の行で確かめられます（[virsh で状態を変える](#virsh-life)）。
:::
:::

:::q 2.05.2-12 single
`virsh console web01` でゲストのシリアルコンソールにつないだ。ゲストを止めずに、コンソールから抜けてホストのシェルに戻るキー操作はどれか。
- [ ] Ctrl + C
- [ ] Ctrl + D
- [x] Ctrl + ]
- [ ] Ctrl + Z

- Ctrl + C、Ctrl + D、Ctrl + Z は、どれもゲストの中の端末に送られます。Ctrl + D はゲストのシェルからログアウトするだけで、コンソールの接続は続きます

:::q 2.05.2-13 single
動作中のドメイン `web01` に対して、次のコマンドを実行した。説明として正しいものはどれか。

```text
# virsh setvcpus web01 2 --config
```

- [ ] 動作中のゲストの仮想 CPU が、ただちに 2 個になる。停止すると元に戻る
- [x] 保存されている設定が書き換えられ、次に起動したときから仮想 CPU が 2 個になる
- [ ] ホストの CPU のうち、2 番の CPU だけをゲストに使わせる
- [ ] ゲストが再起動され、仮想 CPU が 2 個になる
:::why
`--config` は、保存されている設定（XML）を変える指定で、次の起動から効きます。動作中のドメインをすぐに変えるのは `--live` で、両方を付けることもできます。`setmem` でも同じです（[設定を変える](#virsh-config)）。

- ただちに変えて、停止すると戻るのは `--live` だけを付けたときです

:::
:::

:::q 2.05.2-14 multi
`virsh` でドメインの設定を扱うコマンドの説明として、正しいものを 2 つ選択してください。
- [x] `virsh dumpxml 名前` は、ドメインの設定の XML を標準出力に表示する
- [ ] `virsh dominfo 名前` は、ドメインの設定の XML 全体を表示する
- [x] `virsh edit 名前` は、設定の XML をエディタで開く。保存した内容は、次の起動から効く

`dumpxml` は XML を表示するだけです。`> ファイル` で保存すれば、`virsh define` でほかのホストに登録できます。`edit` は、XML をエディタ（`$VISUAL` か `$EDITOR`、なければ vi）で開き、保存すると登録し直します。効くのは次の起動からです（[virsh で設定を見る・変える](#virsh-config)）。

- `dominfo` が出すのは、状態、CPU の数、メモリなどの要約です
- `dumpxml` が出すのは設定で、ディスクの中身ではありません
:::

:::q 2.05.2-15 multi
`virt-install` で、インストール元を指定するオプションを 2 つ選択してください。

- [x] `--location`
