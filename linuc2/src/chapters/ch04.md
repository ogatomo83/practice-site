ふつう、ソフトウェアはパッケージ（`.deb`、`.rpm`）で入れます（[図解 LinuC 4 章](../../linuc/site/ch04.html)）。しかし、パッケージがまだない新しい版を使いたいとき、機能の有効・無効を自分で選びたいときは、**ソースコード**から自分で組み立てます。これを**ビルド**と呼びます。

手順は、ほとんどのソフトで同じです。

| 段階 | コマンド | すること | 権限 |
| --- | --- | --- | --- |
| 1. 取る | `git clone URL`、または `.tar.gz` をダウンロード | ソースコードを手元に置く | 一般ユーザー |
| 2. 展開する | `tar xf`、`unzip`、必要なら `patch` | アーカイブをほどき、修正を当てる | 一般ユーザー |
| 3. 調べる | `./configure` | コンパイラやライブラリがあるかを調べ、**Makefile を作る** | 一般ユーザー |
| 4. 組み立てる | `make` | Makefile を読んで**コンパイル**する | 一般ユーザー |
| 5. 入れる | `make install` | できたファイルを、インストール先へ**コピー**する | **root**（`/usr/local` に書くため） |

ソースの中には、たいてい `README` と `INSTALL` という文書があります。そのソフトだけの手順やオプションは、そこに書いてあります。まず読みます。

:::warn 試験の注意：root が要るのは make install だけ
`./configure` と `make` は、ソースのディレクトリの中にファイルを作るだけなので、一般ユーザーで実行します。root が要るのは、`/usr/local` などシステムのディレクトリへ書き込む `make install` だけです。「`make` を root で実行する必要がある」という選択肢は誤りです。
:::

## ソースを手に入れる：git clone とタグ、tar と圧縮 {#get-source}

### git clone、git tag -l、git checkout

多くのソフトは、**Git** のリポジトリ（変更の履歴を持つ置き場所）で公開されています。使うコマンドは 3 つです。

| コマンド | すること |
| --- | --- |
| `git clone URL [ディレクトリ]` | リポジトリを**履歴ごと**手元に複製する。ディレクトリを省くと、リポジトリの名前（最後の `.git` を除いたもの）で作る |
| `git clone -b 名前 URL` | 複製して、そのブランチか**タグ**を取り出す |
| `git clone --depth 1 URL` | 最新の 1 つの版だけを複製する（履歴を取らないので速い） |
| `git tag -l`（`git tag`） | **タグの一覧**を表示する。`git tag -l 'v1.*'` のようにパターンで絞れる |
| `git checkout タグ` | 作業ディレクトリを、**そのタグの版**の中身に切り替える |
| `git checkout -b 新ブランチ タグ` | そのタグの版から、新しいブランチを作って切り替える |

**タグ**は、リリースした版に付ける名前（`v1.0` など）です。複製した直後の作業ディレクトリは、開発中の最新の状態です。安定した版をビルドしたいときは、`git tag -l` でタグを調べ、`git checkout` でその版に切り替えます。Debian 12 で実際に動かした結果です。

```console
$ git clone /root/up proj
Cloning into 'proj'...
done.
$ cd proj
$ git tag -l
v1.0
v1.1
v2.0
$ git tag -l 'v1.*'
v1.0
v1.1
$ git checkout v1.1
Note: switching to 'v1.1'.
…
HEAD is now at a957c41 two
$ git branch
* (HEAD detached at v1.1)
  main
```

タグを `git checkout` すると、**detached HEAD**（どのブランチにも乗っていない状態）になります。エラーではありません。その版を見たりビルドしたりするだけなら、このままでかまいません。元に戻るには `git checkout main` のようにブランチの名前を指定します。

### アーカイブを展開する：tar、gzip、bzip2、xz、unzip

配布されるソースは、`名前-版.tar.gz` のような **tarball**（tar でまとめて圧縮したファイル）が普通です。tar と 3 つの圧縮コマンドは [図解 LinuC 2.5](../../linuc/site/ch02.html#archive) で学びました。対応を表で復習します。

| 拡張子 | 圧縮のコマンド | 展開のコマンド | 中身を標準出力へ | tar のオプション |
| --- | --- | --- | --- | --- |
| `.gz`（`.tar.gz`、`.tgz`） | `gzip` | `gunzip`、`gzip -d` | `zcat`、`gzip -dc` | `z` |
| `.bz2`（`.tar.bz2`） | `bzip2` | `bunzip2`、`bzip2 -d` | `bzcat`、`bzip2 -dc` | `j` |
| `.xz`（`.tar.xz`） | `xz` | `unxz`、`xz -d` | `xzcat`、`xz -dc` | `J`（大文字） |
| `.zip` | `zip -r` | `unzip` | `unzip -p` | —（tar は使わない） |

圧縮率は、ふつう gzip < bzip2 < xz の順に高くなり、かかる時間もその順に長くなります。3 つとも、圧縮すると**元のファイルは消えて**圧縮したファイルだけが残ります。元を残すのは `-k`（keep）か、`-c` で標準出力に書く方法です。

```console
$ tar xzf hello-2.12.1.tar.gz          … gzip の tarball を展開
$ tar xjf proj.tar.bz2 -C /usr/local/src … bzip2。-C で展開先を指定
$ tar xJf linux-6.1.tar.xz             … xz
$ tar xf d.tar.bz2                     … GNU tar は、展開のときは圧縮の種類を自分で見分ける
$ tar tzf hello-2.12.1.tar.gz | head -3  … 展開せずに中身の一覧を見る
$ tar xzf d.tar.xz
gzip: stdin: not in gzip format
tar: Child returned status 1
```

最後の例のように、圧縮の種類と違うオプション（xz のファイルに `z`）を付けると失敗します。`z`、`j`、`J` を付けずに `tar xf` とすれば、GNU tar が自分で見分けます。

`.zip` は、まとめることと圧縮を 1 つのコマンドでする別の形式です。展開は **`unzip`** です。

| 書き方 | 意味 |
| --- | --- |
| `unzip file.zip` | いまのディレクトリに展開する |
| `unzip file.zip -d ディレクトリ` | **`-d`** で指定したディレクトリに展開する |
| `unzip -l file.zip` | 展開せずに、中身の**一覧**を表示する |
| `unzip -t file.zip` | 壊れていないかを**検査**する |
| `unzip -o file.zip` | 確認せずに**上書き**する |

**`-d` の意味はコマンドで違います**。`gzip -d`、`bzip2 -d`、`xz -d` の `-d` は「展開する（decompress）」です。`unzip -d` の `-d` は「展開先のディレクトリ」です。tar で展開先を決めるのは `-C`（大文字）です。

## patch、configure、make、make install は、それぞれ何をするか {#configure-make}

### patch：差分を当てる

**パッチ**は、古いソースと新しいソースの**差分**を書いたファイルです。`diff` で作り、`patch` で当てます。ソース全体を配り直さなくても、修正だけを小さなファイルで配れます。

```console
$ diff -Nur hello-1.0 hello-1.1 > d.patch       … 2 つのディレクトリの差分を作る
$ cat d.patch
diff -Nur hello-1.0/src/a.txt hello-1.1/src/a.txt
--- hello-1.0/src/a.txt	2026-11-16 21:20:01.311614003 +0000
+++ hello-1.1/src/a.txt	2026-11-16 21:20:01.311614003 +0000
@@ -1,3 +1,4 @@
 line1
-line2
+line2 changed
 line3
+line4
```

`-` で始まる行が消える行、`+` で始まる行が足される行です。`---` と `+++` の行に、対象のファイルの**パス**が書いてあります。このパスの先頭を何個削って使うかを決めるのが、**`-p`** です。

```fig layout patch -pN は、パッチに書かれたパスの先頭から N 個の部分を削る。ソースのディレクトリの中で当てるなら -p1
{
  unit: 13,
  rows: [
    { label: 'パッチの中', cells: [{ t: 'hello-1.0/', w: 9, kind: 'accent' }, { t: 'src/', w: 5, kind: 'stack' }, { t: 'a.txt', w: 6, kind: 'plain' }] },
    { label: '-p0', cells: [{ t: 'hello-1.0/', w: 9, kind: 'accent' }, { t: 'src/', w: 5, kind: 'stack' }, { t: 'a.txt', w: 6, kind: 'plain' }], note: 'そのまま使う' },
    { label: '-p1', cells: [{ t: '', w: 9, kind: 'empty' }, { t: 'src/', w: 5, kind: 'stack' }, { t: 'a.txt', w: 6, kind: 'plain' }], note: '先頭の 1 個を削る' },
    { label: '-p2', cells: [{ t: '', w: 9, kind: 'empty' }, { t: '', w: 5, kind: 'empty' }, { t: 'a.txt', w: 6, kind: 'plain' }], note: '2 個削る' },
  ],
}
```

```console
$ cd work                                  … hello-1.0 と同じ中身のディレクトリ
$ patch --dry-run -p1 < ../d.patch         … 試すだけ。ファイルは変えない
checking file src/a.txt
$ patch -p1 < ../d.patch                   … 当てる
patching file src/a.txt
$ patch -R -p1 < ../d.patch                … -R で元に戻す
patching file src/a.txt
$ patch -p0 < ../d.patch                   … -p の数がまちがっていると、ファイルが見つからない
can't find file to patch at input line 4
Perhaps you used the wrong -p or --strip option?
```

| オプション | 意味 |
| --- | --- |
| `-p数`（`--strip=数`） | パッチの中のパスの先頭から、その数だけディレクトリの部分を削る。`-p0` は削らない。`-p` を付けないと、ファイル名だけ（ディレクトリの部分を全部削ったもの）を使う |
| `-R`（`--reverse`） | 逆向きに当てる。**当てたパッチを取り消す** |
| `--dry-run` | 当てられるかを試すだけで、ファイルを変えない |
| `-b`（`--backup`） | 元のファイルを `名前.orig` として残す |
| `-i ファイル` | パッチを標準入力ではなく、そのファイルから読む（`patch -p1 -i x.patch` は `patch -p1 < x.patch` と同じ） |
| `-d ディレクトリ` | そのディレクトリに移ってから当てる |

パッチがソースと合わず、当てられなかった部分（ハンク）は、**`名前.rej`** というファイルに書き出されます。

### configure：環境を調べて Makefile を作る

**`configure`** は、ソースに付いてくるシェルスクリプトです。ソースのディレクトリの中で `./configure` として実行します。コンパイラ、必要なライブラリ、ヘッダファイルがその機械にあるかを調べ、結果に合わせた **Makefile** を作ります。

```console
$ ./configure --prefix=/opt/hello
checking for a BSD-compatible install... /usr/bin/install -c
checking whether build environment is sane... yes
…
configure: creating ./config.status
config.status: creating Makefile
config.status: creating config.h
$ ls Makefile config.status config.log
Makefile
config.log
config.status
```

| オプション | 意味 |
| --- | --- |
| `--prefix=ディレクトリ` | **インストール先の起点**。既定は **`/usr/local`**（実行ファイルは `/usr/local/bin`、ライブラリは `/usr/local/lib` に入る） |
| `--help` | そのソフトで使えるオプションの一覧を表示する |
| `--bindir=`、`--sysconfdir=`、`--mandir=` など | 種類ごとの置き場所を細かく指定する |
| `--enable-機能`、`--disable-機能`、`--with-パッケージ` | 機能や、使う外部のライブラリを選ぶ（ソフトごとに違う） |

必要なライブラリが足りないと、`configure` は `error:` を出して止まり、Makefile を作りません。調べた記録は **`config.log`** に残るので、原因はそこで調べます。

### make と make install

**`make`** は、カレントディレクトリの **Makefile** を読み、そこに書かれた手順でコンパイルします。Makefile には「**ターゲット**（作るもの）」と、その作り方が並んでいます。`make ターゲット` で、そのターゲットを作ります。ターゲットを省くと、Makefile の最初のターゲット（ふつうは全体をビルドする `all`）を作ります。

```console
$ make                                 … コンパイルする
…
gcc  -g -O2   -o hello src/hello.o  ./lib/libhello.a
$ ls -l hello
-rwxr-xr-x 1 root root 204312 Nov 16 21:20 hello
# make install                         … root で。prefix の下へコピーする
 /usr/bin/mkdir -p '/opt/hello/share/man/man1'
 /usr/bin/install -c -m 644 hello.1 '/opt/hello/share/man/man1'
$ /opt/hello/bin/hello
Hello, world!
```

| 書き方 | すること |
| --- | --- |
| `make` | 最初のターゲット（ふつう `all`）を作る。コンパイルする |
| `make install` | できたファイルを、prefix の下へコピーする |
| `make clean` | コンパイルでできたファイル（`.o` や実行ファイル）を消す。Makefile は残る |
| `make distclean` | `make clean` に加えて、configure が作ったもの（Makefile など）も消す。配布された状態に戻す |
| `make uninstall` | インストールしたファイルを消す（Makefile に用意されているときだけ） |
| `make -j 4` | 4 つの仕事を並行して実行する（速くなる） |
| `make -n` | 実行するコマンドを表示するだけで、実行しない |
| `make -f ファイル` | `Makefile` ではなく、そのファイルを読む |
| `make -C ディレクトリ` | そのディレクトリに移ってから実行する |
| `make install DESTDIR=/tmp/stage` | インストール先の前に `DESTDIR` を付ける（`/tmp/stage/opt/hello/bin/hello` に入る。パッケージを作るときに使う） |

:::note パッケージ管理の外に入る
`make install` で入れたソフトは、`dpkg -l` や `rpm -qa` に出ません。更新も削除も自分でします。`make uninstall` が用意されていないソフトもあります。だから、既定のインストール先は、パッケージが使う `/usr` と分けた **`/usr/local`** になっています。`--prefix=/opt/名前` のように 1 つのディレクトリにまとめておくと、消すときはそのディレクトリを消すだけで済みます。
:::

## バックアップは、何を・どれだけ・どこへ取るか {#backup-types}

### フル、差分、増分

毎日全部を写すと、時間も場所もかかります。そこで、**前のバックアップから変わったものだけ**を取る方法を組み合わせます。

```fig graph 日曜にフルを取り、月〜水は変わった分だけを取る。差分は「日曜のフルから」、増分は「前の日のバックアップから」
{
  col: 170, row: 92,
  nodes: [
    { id: 'f', label: '日：フル', sub: '全部', x: 0, y: 0.5, kind: 'accent', mono: false },
    { id: 'd1', label: '月：差分', sub: '日曜からの変更', x: 1, y: 0, kind: 'stack', mono: false },
    { id: 'd2', label: '火：差分', sub: '日曜からの変更', x: 2, y: 0, kind: 'stack', mono: false },
    { id: 'd3', label: '水：差分', sub: '日曜からの変更', x: 3, y: 0, kind: 'stack', mono: false },
    { id: 'i1', label: '月：増分', sub: '日曜からの変更', x: 1, y: 1, kind: 'crate', mono: false },
    { id: 'i2', label: '火：増分', sub: '月曜からの変更', x: 2, y: 1, kind: 'crate', mono: false },
    { id: 'i3', label: '水：増分', sub: '火曜からの変更', x: 3, y: 1, kind: 'crate', mono: false },
  ],
  edges: [
    { from: 'f', to: 'd1', style: 'muted' }, { from: 'f', to: 'd2', style: 'muted', curve: -30 }, { from: 'f', to: 'd3', style: 'muted', curve: -50 },
    { from: 'f', to: 'i1', style: 'muted' }, { from: 'i1', to: 'i2', style: 'muted' }, { from: 'i2', to: 'i3', style: 'muted' },
  ],
}
```

| 種類 | 取るもの | 1 回の量と時間 | 元に戻す（リストア）のに要るもの |
| --- | --- | --- | --- |
| **フル**バックアップ | 全部 | いちばん大きい | そのフル **1 つ** |
| **差分**バックアップ（differential） | **最後のフル**から変わったもの | 日がたつほど大きくなる | フル + **最新の差分 1 つ** |
| **増分**バックアップ（incremental） | **直前のバックアップ**（フルでも増分でも）から変わったもの | いちばん小さい | フル + **その後の増分を全部、順番に** |

上の図で、水曜の夜に壊れたとします。差分なら「日曜のフル → 水曜の差分」の 2 つで戻せます。増分なら「日曜のフル → 月 → 火 → 水」の 4 つを順に戻します。増分は取るのが速い代わりに、戻すのに手間がかかり、途中の 1 つが壊れるとそれより後が戻せません。

### ファイル、ブロック、イメージ

「何の単位で写すか」にも種類があります。

| 単位 | 写すもの | 道具の例 | 特徴 |
| --- | --- | --- | --- |
| **ファイル**単位 | ファイルとディレクトリ | `tar`、`rsync`、`cpio` | 必要なファイルだけ選べる。1 つのファイルだけ戻せる。ファイルシステムの種類が違う所へも戻せる |
| **ブロック**単位 | デバイスのブロック（中身を解釈しない） | `dd` | ファイルシステムの種類に関係なく、そっくり写せる。使っていない領域も写すので大きい |
| **イメージ** | ディスクやパーティションの全体を 1 つのファイル（イメージ）にしたもの | `dd if=/dev/sda of=sda.img` | ブートローダやパーティション表も含めて、システムを丸ごと戻せる |

### 媒体：テープ、ハードディスク、光学メディア

| 媒体 | 読み書き | 向いている使い方 |
| --- | --- | --- |
| **テープ**（LTO など） | **順番に**しか読み書きできない（シーケンシャルアクセス）。途中のファイルを取り出すのは遅い | 容量あたりの値段が安く、長く保管できる。大量のデータの長期保管 |
| **ハードディスク** | 好きな場所をすぐ読み書きできる（ランダムアクセス） | 速い。日々のバックアップと、すばやいリストア |
| **光学メディア**（CD-R、DVD-R、BD-R） | 書き込みは 1 回だけのものが多い。容量は小さい | 書き換えられないので、改ざんされては困るデータの保管 |

### ネットワークバックアップのソフト

たくさんの機械のバックアップを 1 台のサーバーで集中して管理する、オープンソースのソフトです。名前と特徴の組み合わせが問われます。

| 名前 | 特徴 |
| --- | --- |
| **Amanda** | 1 台のバックアップサーバーから、ネットワーク上の多くのクライアントをテープやディスクへ取る。中では OS に標準の **`dump` や `tar`** を使うので、Amanda がなくても戻せる |
| **Bacula** | **Director**（全体の指揮）、**Storage Daemon**（媒体への読み書き）、**File Daemon**（クライアント側）、**Catalog**（何をどこに取ったかのデータベース）、Console に分かれた構成。企業向けの大きな構成に使われる |
| **Bareos** | **Bacula から分かれた**（フォークした）ソフト。構成は Bacula と同じ（Director、Storage Daemon、File Daemon） |
| **BackupPC** | **ディスク**へ取る。Web の画面で操作する。クライアントに専用のソフトを入れず、**rsync、tar（ssh 経由）、SMB** で取る。同じ中身のファイルは 1 つだけ保存して、場所を節約する |

## tar、dd、rsync でバックアップを取る {#backup-tools}

### tar：増分バックアップは -g

`tar` でファイル単位のバックアップを取ります。基本の `c`、`x`、`t`、`f`、`v`、`z` は [図解 LinuC 2.5](../../linuc/site/ch02.html#tar) の通りです。バックアップで使うオプションを足します。

| オプション | 意味 |
| --- | --- |
| `-g ファイル`（`--listed-incremental=ファイル`） | **増分バックアップ**。そのファイル（スナップショットファイル）に「前回どこまで取ったか」を記録し、次からは変わったものだけを取る |
| `-N 日付`（`--newer=日付`） | その日付より新しいファイルだけを取る |
| `-p`（`--preserve-permissions`） | 展開のとき、パーミッションをアーカイブの通りに戻す |
| `--exclude=パターン` | パターンに合うファイルを除く |
| `-M`（`--multi-volume`） | 1 本のテープに入りきらないとき、複数の媒体に分ける |
| `-W`（`--verify`） | 書いた後に、正しく書けたかを確かめる |
| `-C ディレクトリ` | そのディレクトリに移ってから処理する |

`-g` の使い方を、Debian 12 で確かめます。スナップショットファイルがまだないときは、全部を取ります（フル）。同じスナップショットファイルを指定してもう一度実行すると、変わったものだけを取ります（増分）。

```console
# tar -czf full.tar.gz -g snap.snar data        … 1 回目：snap.snar がないので、フル
# echo c > data/c.txt; echo a2 >> data/a.txt    … 1 つ足し、1 つ書き換える
# tar -czvf inc1.tar.gz -g snap.snar data       … 2 回目：変わったものだけ
data/
data/sub/
data/a.txt
data/c.txt
# echo d > data/d.txt; rm data/sub/b.txt
# tar -czvf inc2.tar.gz -g snap.snar data       … 3 回目：2 回目から変わったものだけ
data/
data/sub/
data/d.txt
```

戻すときは、**フルから順番に**、`-g /dev/null` を付けて展開します。増分のアーカイブには「消されたファイル」の情報も入っているので、途中で消した `b.txt` は、戻した先でも消えます。

Debian 12 で、上の 3 つを `for f in full inc1 inc2; do tar -xzf $f.tar.gz -g /dev/null -C r; done` の順に戻すと、`a.txt`、`c.txt`、`d.txt` が戻り、`b.txt` はありませんでした。

テープに直接書くときは、`f` にテープのデバイスを指定します（`tar cvf /dev/st0 /home`）。

### dd：ブロック単位で丸ごと写す

`dd` は、ファイルシステムの中身を解釈せず、ブロックをそのまま写します（[図解 LinuC 2.5](../../linuc/site/ch02.html#dd)、[図解 Linux 15.7](../../linux/site/ch15.html#dd)）。ディスクやパーティションの**イメージ**を取るのに使います。

```console
# dd if=/dev/sda of=/backup/sda.img bs=4M            … ディスク全体をイメージファイルへ
# dd if=/backup/sda.img of=/dev/sda bs=4M            … イメージからディスクへ戻す
# dd if=/dev/sda of=/dev/sdb bs=4M                   … ディスクからディスクへ複製
# dd if=/dev/sda of=mbr.bin bs=512 count=1           … 先頭の 512 バイト（MBR）だけ
# dd if=/dev/sda1 bs=4M | gzip > sda1.img.gz         … 圧縮しながら取る
# dd if=/dev/sda of=sda.img bs=4M conv=noerror,sync  … 読めないブロックがあっても続ける
```

`if=` が読む元、`of=` が書く先です。`bs=` は 1 回に読み書きする大きさ、`count=` は回数です。`conv=noerror` は読み取りエラーがあっても止まらずに続け、`sync` は読めなかった分を 0 で埋めて位置がずれないようにします。壊れかけたディスクを写すときの組み合わせです。

### rsync：変わった分だけを送って、同じにする

**`rsync`** は、コピー元とコピー先を比べて、**違うところだけ**を送り、2 つのディレクトリを同じにするコマンドです。2 回目からは変わったファイルだけを送るので、速く終わります。ネットワーク越しのコピーにも使えます。

```console
$ rsync -av data/ dst2                 … data の中身を dst2 へ
sending incremental file list
a.txt
c.txt
sub/
sub/b.txt

sent 274 bytes  received 81 bytes  710.00 bytes/sec
total size is 9  speedup is 0.03
```

| オプション | 意味 |
| --- | --- |
| `-a`（`--archive`） | **アーカイブモード**。`-rlptgoD` と同じ。ディレクトリの中をたどり（r）、シンボリックリンク（l）、パーミッション（p）、時刻（t）、グループ（g）、所有者（o）、デバイスファイル（D）を保つ |
| `-v` | 送ったファイルの名前を表示する |
| `-z` | 送るときにデータを**圧縮**する（回線が遅いときに効く。コピー先のファイルは圧縮されない） |
| `-n`（`--dry-run`） | 何が起きるかを表示するだけで、実際には何もしない |
| `--delete` | コピー元に**ない**ファイルを、コピー先から**消す** |
| `-e ssh`（`--rsh=ssh`） | リモートへつなぐのに使うコマンドを指定する |
| `-u`（`--update`） | コピー先のほうが新しいファイルは飛ばす |
| `--exclude=パターン` | パターンに合うファイルを除く |
| `-P` | `--partial --progress` と同じ。進み具合を表示し、途中まで送ったファイルを残す |

`-a` には、ハードリンク（`-H`）、ACL（`-A`）、拡張属性（`-X`）は**入っていません**。必要なら足します。

何もオプションを付けないと、コピー元にないファイルはコピー先に**残ります**。コピー元とまったく同じにする（ミラーにする）には `--delete` を付けます。

```console
$ rm data/c.txt; touch dst2/extra
$ rsync -av --delete data/ dst2
sending incremental file list
deleting extra
deleting c.txt
```

**コピー元の最後の `/`** で、結果が変わります。これは必ず覚えます。`rsync -a data/ dst` は、data の**中身**を dst の直下に入れます（`dst/a.txt`）。`rsync -a data dst` は、dst の下に **data というディレクトリ**を作ります（`dst/data/a.txt`）。

リモートの機械は、`ホスト:パス` で指定します。

| 書き方 | 意味 |
| --- | --- |
| `rsync -av /home/ backup@srv:/backup/home/` | **SSH** で srv につなぎ、ローカルからリモートへ送る |
| `rsync -av srv:/var/www/ /backup/www/` | リモートからローカルへ取ってくる |
| `rsync -av -e "ssh -p 2222" /home/ srv:/backup/` | SSH のポートを変えてつなぐ |
| `rsync -av /home/ srv::module/` 、`rsync://srv/module/` | コロン 2 つ、または `rsync://` は、**rsync デーモン**（TCP 873 番）につなぐ |

:::warn 試験の注意：--delete とドライラン
`--delete` は、コピー元とコピー先を取り違えると、大事なファイルを消します。先に `-n`（`--dry-run`）を付けて、何が消されるかを確かめます。`rsync -avn --delete …` の出力の最後には `(DRY RUN)` と出ます。
:::

## テープは、巻き戻すデバイスと巻き戻さないデバイスを使い分ける {#tape}

SCSI のテープ装置は、2 つの名前で見えます。どちらも同じ装置ですが、**使い終わった（デバイスファイルを閉じた）ときの動き**が違います。

| デバイスファイル | 閉じたとき | 使いどころ |
| --- | --- | --- |
| **`/dev/st0`** | テープを**先頭まで巻き戻す**（rewind） | 1 本のテープに 1 つだけアーカイブを書くとき |
| **`/dev/nst0`** | **巻き戻さない**（no rewind）。書き終わった位置で止まる | 1 本のテープに、**続けていくつも**アーカイブを書くとき |

`st` は SCSI tape、先頭の `n` は no rewind です。2 台目の装置は `/dev/st1` と `/dev/nst1` になります。

`/dev/st0` に 2 回続けて `tar` で書くと、1 回目の後に巻き戻るので、2 回目は先頭から書いて **1 回目を上書き**します。続けて書きたいときは `/dev/nst0` を使います。

```fig layout /dev/nst0 で 2 つ続けて書いたテープ。アーカイブの間には「ファイルの終わりの印（EOF マーク）」が入る
{
  unit: 13,
  rows: [
    { label: 'テープ', cells: [{ t: 'tar（1 つ目）/etc', w: 13, kind: 'accent' }, { t: 'EOF', w: 4, kind: 'pad' }, { t: 'tar（2 つ目）/home', w: 14, kind: 'stack' }, { t: 'EOF', w: 4, kind: 'pad' }, { t: '空き', w: 6, kind: 'empty' }] },
    { label: '位置', cells: [{ t: 'rewind の後はここ', w: 13, kind: 'plain' }, { t: '', w: 4, kind: 'empty' }, { t: 'fsf 1 の後はここ', w: 14, kind: 'plain' }, { t: '', w: 4, kind: 'empty' }, { t: 'eod', w: 6, kind: 'plain' }] },
  ],
}
```

テープの位置を動かすのが **`mt`**（magnetic tape）です。書式は `mt -f デバイス 操作 [回数]` です。`-f` を省くと、環境変数 `TAPE` に書かれたデバイスを使います。

| 操作 | すること |
| --- | --- |
| `status` | 装置とテープの状態を表示する |
| `rewind` | 先頭まで**巻き戻す** |
| `fsf 数` | **その数だけ先のファイル**（アーカイブ）の先頭へ進む（forward space file） |
| `bsf 数` | その数だけ前へ戻る（backward space file） |
| `eod` | 書かれているデータの終わりへ進む（続きを書き足すとき） |
| `offline`（`rewoffl`） | 巻き戻して、テープを取り出せる状態にする |
| `erase` | テープを消去する |

```console
# tar cvf /dev/nst0 /etc           … 1 つ目を書く。巻き戻さない
# tar cvf /dev/nst0 /home          … 続けて 2 つ目を書く
# mt -f /dev/nst0 rewind           … 先頭へ巻き戻す
# mt -f /dev/nst0 fsf 1            … 1 つ先（2 つ目のアーカイブ）へ進む
# tar tvf /dev/nst0                … 2 つ目の中身の一覧
# mt -f /dev/nst0 offline          … 巻き戻して取り出す
```

「n が付いたら no rewind」です。続けて書く、`mt fsf` で位置を合わせて読む、という操作は、勝手に巻き戻されると困るので、必ず `/dev/nst0` を使います。

| ファイル・コマンド | いつ、だれに表示されるか |
| --- | --- |
| **`/etc/issue`** | **ログインの前**。ローカルの端末（コンソール）の `login:` プロンプトの上 |

| **`shutdown`** | 止める前に、ログインしている全員の端末へ警告を送る |

小さな Linux にも `/etc/issue` と `/etc/motd` があります。

```sh run title="/etc/issue と /etc/motd"
cat /etc/issue
cat /etc/motd
```

### /etc/issue と /etc/issue.net

`/etc/issue` の `\n` や `\l` は、表示するときに置き換えられる記号です。ログインの前に出るので、OS の名前やホスト名を見せるのに使います。

| 記号 | 置き換わるもの |
| --- | --- |
| `\n` | ホスト名（`uname -n`） |
| `\l` | 端末の名前（`tty1` など） |
| `\r` | カーネルのリリース番号（`uname -r`） |
| `\m` | 機械の種類（`uname -m`。`x86_64` など） |
| `\s` | OS の名前（`uname -s`。`Linux`） |
| `\d`、`\t` | いまの日付、時刻 |

```console
$ cat /etc/issue            … Debian 12
Debian GNU/Linux 12 \n \l

$ cat /etc/issue.net
Debian GNU/Linux 12
$ cat /etc/issue            … Rocky Linux 9
\S
Kernel \r on an \m
```

`/etc/issue.net` は、ネットワーク越しのログインのためのファイルです。SSH は、既定ではこのファイルを**表示しません**。SSH でログインの前にメッセージを出したいときは、`/etc/ssh/sshd_config` の **`Banner`** にファイルを指定します。

```text
# /etc/ssh/sshd_config
Banner /etc/issue.net
```

:::warn 試験の注意：前か後か
「ログインの**前**」が issue、「ログインの**後**」が motd です。ログインの前に出る文は、まだ認証していない相手にも見えます。カーネルのバージョンなどの細かい情報を出すと、攻撃の手がかりになります。メンテナンスの予定のように、ログインできた人にだけ知らせたいものは `/etc/motd` に書きます。
:::

### wall と shutdown

**`wall`**（write all）は、ログインしている**全員の端末**に、いますぐメッセージを表示します。

```console
# wall "15 時からメンテナンスです。作業を保存してください"
# wall < notice.txt          … ファイルや標準入力からも読める
```

受け取る側は、`mesg n` で、ほかのユーザーからのメッセージを断れます。ただし、**root が送った wall は、断っていても届きます**。

**`shutdown`** は、止める時刻の後ろに書いたメッセージを、wall と同じ仕組みで全員に送ります（[図解 LinuC 1.4](../../linuc/site/ch01.html#logout)）。

| 書き方 | 意味 |
| --- | --- |
| `shutdown -h +10 "10 分後に停止します"` | 10 分後に止める。全員にメッセージを送る |
| `shutdown -r 22:00 "22 時に再起動します"` | 22 時に再起動する |
| `shutdown -k +5 "訓練です"` | **メッセージを送るだけ**で、実際には止めない |
| `shutdown -c` | 予約した shutdown を**取り消す** |
| `shutdown --no-wall -r now` | メッセージを送らずに再起動する |

時刻を予約すると、止まる 5 分前から `/run/nologin` が作られ、root 以外は新しくログインできなくなります。管理者が自分で `/etc/nologin` を作っても、同じように root 以外のログインを止められます（[図解 LinuC 10.5](../../linuc/site/ch10.html#login)）。そのファイルの中身が、ログインしようとした人に表示されます。

**`systemctl`** で止めるときも、全員にメッセージが送られます。

| コマンド | すること |
| --- | --- |
| `systemctl poweroff` / `reboot` / `halt` | 電源を切る / 再起動する / 止める。ログイン中の全員に知らせる |
| `systemctl rescue` / `emergency` | レスキューモード / 緊急モードに切り替える。全員に知らせる |
| `systemctl --no-wall reboot` | **`--no-wall`** を付けると、知らせずに実行する |

| `htop` | top を見やすくしたもの。色、スクロール、マウス、木の表示 | プロセス | htop |
| `ps` | その瞬間のプロセスの一覧 | プロセス | procps |
| `vmstat` | プロセス、メモリ、スワップ、I/O、CPU をまとめて 1 行で | システム全体 | procps |
| `free` | メモリとスワップの使用量 | システム全体 | procps |
| `iostat` | CPU の使用率と、**デバイスごと**の I/O | デバイス | **sysstat** |
| `sar` | CPU、メモリ、I/O、ネットワークなど。**過去の記録**も表示 | システム全体 | **sysstat** |
| `iotop` | **プロセスごと**のディスク I/O | プロセス | iotop |
| `iftop` | **接続（相手のホスト）ごと**の通信量 | 接続 | iftop |
| `iptraf`（`iptraf-ng`） | インターフェースや接続ごとの通信の統計。メニュー形式の画面 | 接続 | iptraf-ng |
| `ss`、`netstat` | ソケット（待ち受けているポート、接続）の一覧 | ソケット | iproute2、net-tools |
| `lsof` | プロセスが開いているファイル | ファイル | lsof |

### top、htop、ps

`top` の読み方とキー操作は [図解 LinuC 1.13](../../linuc/site/ch01.html#watch) で学びました。上の 5 行（まとめ）を、もう一度読みます。

```sh run title="top の上の 5 行"
top -b -n 1 | head -7
```

| 行 | 意味 |
| --- | --- |
| 1 行目 | 時刻、起動からの時間、ログイン中のユーザー数、**ロードアベレージ**（1 分、5 分、15 分。`uptime` と同じ） |
| `Tasks:` | プロセスの数と状態（running、sleeping、stopped、zombie） |
| `%Cpu(s):` | CPU 時間の内訳。下の表 |
| `MiB Mem :` | 物理メモリ（total、free、used、buff/cache） |
| `MiB Swap:` | スワップ（total、free、used）と、使えるメモリ（avail Mem） |

`%Cpu(s)` の内訳は、vmstat、iostat、sar にも同じ意味で出てきます。

| 記号 | 意味 |
| --- | --- |
| `us` | ユーザーのプログラムを実行していた時間（user） |
| `sy` | カーネルの中を実行していた時間（system） |
| `ni` | nice 値を変えたプロセスを実行していた時間 |
| `id` | 何もしていなかった時間（idle） |
| `wa` | **ディスクなどの I/O を待っていた**時間（iowait） |
| `hi`、`si` | ハードウェア割り込み、ソフトウェア割り込みの処理 |
| `st` | 仮想マシンで、ハイパーバイザーにほかの仕事へ**取られた**時間（steal） |

`us` が高ければプログラムが CPU を使っています。**`wa` が高い**ときは、CPU ではなく**ディスクが遅い**のが原因です。

`top` の主なオプションは、`-d 秒`（更新の間隔）、`-n 回数`、`-b`（バッチモード。ファイルやパイプに書く）、`-p PID`、`-u ユーザー` です。動かしている間は、`M` でメモリ順、`P` で CPU 順、`k` でシグナルを送る、`r` で nice 値を変える、`1` で CPU ごとの表示、`q` で終わりです。

**`htop`** は、top と同じ情報を、色付きのバーと、矢印キーで動かせる一覧で表示します。ファンクションキーで操作します（F5 で木の表示、F6 で並べ替え、F9 でシグナルを送る、F10 で終わり）。標準では入っていないことが多く、`htop` パッケージを入れます。

`ps` は、その瞬間の一覧を 1 回だけ表示します（[図解 Linux 7.2](../../linux/site/ch07.html#ps)）。

```sh run title="ps の 2 つの書き方"
ps aux
ps -ef
ps -eo pid,ni,stat,pcpu,pmem,rss,comm
```

| 書き方 | 意味 |
| --- | --- |
| `ps aux` | 全部のプロセス（BSD の書き方。`-` を付けない）。`%CPU`、`%MEM`、`VSZ`、`RSS`、`STAT` の列がある |
| `ps -ef` | 全部のプロセス（UNIX の書き方）。`PPID`（親の PID）の列がある |
| `ps -eo 列,列…` | 表示する列を自分で選ぶ。`--sort=-pmem` でメモリの多い順に並べる |
| `ps -eLf` | スレッドも表示する |

`ps aux` には PPID の列がなく、`ps -ef` には %MEM の列がありません。`STAT` の文字は、`R`（実行中・実行待ち）、`S`（待っている）、`D`（I/O を待っていて割り込めない）、`T`（止められている）、`Z`（ゾンビ）です（[図解 Linux 7.8](../../linux/site/ch07.html#state)）。

## vmstat、free、iostat、sar の列を読む {#vmstat-sar}

### vmstat

**`vmstat`** は、システム全体の様子を 1 行にまとめます。`vmstat 間隔 回数` で、その間隔（秒）ごとに、その回数だけ表示します。

```console
$ vmstat 1 3
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
11  3     12 983928 289524 3299120    0    0     5    81  439  701  2  1 97  0  0
 7  2     12 983904 289524 3299200    0    0 32924 100672 48213 73988 33 11 47 10  0
 9  1     12 983904 289524 3299200    0    0 38272 367200 41660 62774 29 10 47 14  0
```

| 列 | 意味 | 困っているときの見え方 |
| --- | --- | --- |
| `r` | **実行を待っている**（走れる）プロセスの数 | CPU の数より大きい状態が続く → CPU が足りない |
| `b` | I/O などを待って**ブロックされている**プロセスの数 | 大きい → ディスクが遅い |
| `swpd` | 使っているスワップの量 | |
| `free`、`buff`、`cache` | 空きメモリ、バッファ、ページキャッシュ | |
| `si`、`so` | **スワップから読み込んだ量**（swap in）、**スワップへ書き出した量**（swap out）。1 秒あたり | 0 でない状態が続く → **メモリが足りない** |
| `bi`、`bo` | ブロックデバイスから**読んだ**量（blocks in）、**書いた**量（blocks out）。1 秒あたり | |
| `in`、`cs` | 1 秒あたりの割り込みの数、コンテキストスイッチの数 | |
| `us`、`sy`、`id`、`wa`、`st` | CPU 時間の内訳（top と同じ） | `wa` が高い → I/O 待ち |

:::warn 試験の注意：vmstat の 1 行目
`vmstat` の**最初の 1 行は、起動してからの平均**です。いまの様子は 2 行目からです。だから、いまを見るときは `vmstat 1 5` のように間隔と回数を付けます。`iostat` も同じで、最初の報告は起動してからの平均です。
:::

そのほか、`vmstat -s` はメモリなどの統計を縦に並べ、`vmstat -d` はディスクごとの統計、`vmstat -a` は active と inactive のメモリを表示します。

### free

**`free`** は、メモリとスワップの使用量です（[図解 Linux 13.7](../../linux/site/ch13.html#free)、[15.3](../../linux/site/ch15.html#free)）。

```sh run title="free と uptime"
free -h
uptime
```

| 列 | 意味 |
| --- | --- |
| `total` | 物理メモリの全体 |
| `used` | 使っている量 |
| `free` | **何にも使っていない**量 |
| `buff/cache` | バッファとページキャッシュ。ディスクの中身の写しで、**必要になればすぐ空けられる** |
| `available` | 新しいプログラムが**実際に使える**量の見積もり（free と、空けられるキャッシュの合計に近い） |

「free が小さい = メモリが足りない」ではありません。Linux は空いているメモリをキャッシュに使うので、free は小さくなるのが普通です。足りているかどうかは **available** で見ます。オプションは、`-h`（読みやすい単位）、`-m`（MiB）、`-g`（GiB）、`-s 秒`（その間隔で繰り返す）、`-c 回数`、`-t`（メモリとスワップの合計の行を足す）です。

`uptime` の**ロードアベレージ**は、実行中・実行待ちのプロセスの数の、過去 1 分、5 分、15 分の平均です（[図解 Linux 14.8](../../linux/site/ch14.html#loadavg)）。CPU が 4 つの機械なら、4.00 で「ちょうど使い切っている」状態です。

### iostat

**`iostat`** は、CPU の使用率と、**デバイスごと**の I/O を表示します。`sar` と同じ **sysstat** パッケージに入っています。

```console
$ iostat
Linux 6.10.14-linuxkit (0905ba29b539) 	11/16/26 	_aarch64_	(14 CPU)

avg-cpu:  %user   %nice %system %iowait  %steal   %idle
           1.68    0.00    0.89    0.06    0.00   97.36

Device             tps    kB_read/s    kB_wrtn/s    kB_dscd/s    kB_read    kB_wrtn    kB_dscd
vda              45.51        59.37      1137.83     31509.10    2182437   41828484 1158325372
vdb               0.10         6.84         0.00         0.00     251368          0          0
```

| オプション | 意味 |
| --- | --- |
| `iostat 間隔 回数` | その間隔（秒）で、その回数だけ表示する |
| `-c` | **CPU** の部分だけ |
| `-d` | **デバイス**の部分だけ |
| `-x` | 詳しい列（`r/s`、`w/s`、`r_await`、`w_await`、**`%util`** など）を足す（extended） |
| `-k`、`-m` | kB、MB 単位で表示する |
| `-p デバイス` | そのデバイスと、パーティションごとに表示する |

`tps` は 1 秒あたりの I/O 要求の数、`kB_read/s` と `kB_wrtn/s` は 1 秒あたりに読んだ量と書いた量です。`-x` で出る `%util` は、デバイスが仕事をしていた時間の割合で、100% に近ければそのディスクは手一杯です。

## ネットワークと、開いているファイルを調べる {#net-io}

### ss と netstat

待ち受けているポートと接続の一覧は、`ss`、古くは `netstat` で見ます（[図解 LinuC 7.10](../../linuc/site/ch07.html#ss)）。オプションの文字は、ほぼ同じです。

```console
$ ss -tlnp
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      5            0.0.0.0:8081      0.0.0.0:*    users:(("python3",pid=3926,fd=3))
$ netstat -tlnp
Active Internet connections (only servers)
Proto Recv-Q Send-Q Local Address           Foreign Address         State       PID/Program name
tcp        0      0 0.0.0.0:8081            0.0.0.0:*               LISTEN      3926/python3
```

| オプション | `ss` | `netstat` |
| --- | --- | --- |
| `-t` / `-u` | TCP / UDP だけ | 同じ |
| `-l` | 待ち受け中（LISTEN）だけ | 同じ |
| `-a` | 全部（待ち受け中も、接続中も） | 同じ |
| `-n` | 名前に直さず、数字で表示する | 同じ |
| `-p` | 使っているプロセスを表示する | 同じ |
| `-s` | まとめ（ソケットの数） | プロトコルごとの**統計** |
| `-r` | （ホスト名に直す） | **ルーティングテーブル**（`ip route`、`route` と同じ） |
| `-i` | （TCP の内部の情報） | **インターフェースごと**の送受信パケット数とエラー数 |

`netstat` は net-tools パッケージの古いコマンドで、新しいディストリビューションには標準では入っていません。`netstat -r` と `netstat -i` は、`ss` にはない使い方なので、区別して覚えます。

### iftop と iptraf：通信量を見る

`ss` は「どんな接続があるか」を見せますが、「どの接続がどれだけ流しているか」は分かりません。それを見るのが `iftop` と `iptraf` です。どちらも root で実行します。

**`iftop`** は、インターフェースを流れるパケットを数えて、**相手のホストの組ごと**の通信量を、多い順に表示し続けます。top のネットワーク版です。直近 2 秒、10 秒、40 秒の平均が並びます。

| オプション | 意味 |
| --- | --- |
| `-i インターフェース` | 見るインターフェースを指定する（`iftop -i eth0`） |
| `-n` | ホスト名に直さない |
| `-N` | ポート番号をサービス名に直さない |
| `-P` | ホストだけでなく**ポート**も表示する |
| `-B` | ビットではなくバイトで表示する |

**`iptraf`**（いまの名前は `iptraf-ng`）は、メニューから選ぶ画面で、接続ごとのパケット数、インターフェースごとの統計、プロトコルごとの内訳などを表示します。`iptraf-ng -i eth0` は IP トラフィックモニター、`-d eth0` はインターフェースの詳しい統計、`-g` は全インターフェースのまとめ、`-s eth0` は TCP と UDP のポートごとの統計を、メニューを通らずに始めます。

### iotop：ディスクを使っているプロセス

`iostat` で「このディスクが忙しい」と分かっても、**だれが**使っているかは分かりません。**`iotop`** は、プロセス（スレッド）ごとのディスクの読み書きの量を、多い順に表示します。root で実行します。

| オプション | 意味 |
| --- | --- |
| `-o`（`--only`） | **実際に I/O をしている**ものだけを表示する |
| `-b`（`--batch`） | 対話なしで出力する（ファイルに記録するとき） |
| `-n 回数` | その回数で終わる |
| `-d 秒` | 更新の間隔（既定は 1 秒） |
| `-p PID`、`-u ユーザー` | そのプロセス、そのユーザーだけ |
| `-a`（`--accumulated`） | 速さではなく、起動してからの**合計**を表示する |
| `-P` | スレッドではなく、プロセス単位で表示する |

### lsof：開いているファイル

**`lsof`**（list open files）は、プロセスが開いているファイルの一覧です（[図解 LinuC 10.3](../../linuc/site/ch10.html#ports)、[図解 Linux 9.9](../../linux/site/ch09.html#deleted)）。ここでいうファイルには、ソケットやディレクトリも入ります。

```sh run title="lsof で、プロセスが開いているファイルを見る"
sleep 30 > /tmp/held.log &
lsof -p $!
```

`FD` の列の `cwd` はカレントディレクトリ、`txt` は実行しているプログラム、数字はファイルディスクリプタの番号です。数字の後ろの `r`、`w`、`u` は、読み、書き、読み書きです。`1w` は、標準出力（1 番）が `/tmp/held.log` に書き込みで開かれていることを表します。

| 書き方 | 表示するもの |
| --- | --- |
| `lsof ファイル` | **そのファイルを開いている**プロセス |
| `lsof -p PID` | そのプロセスが開いているファイル |
| `lsof -u ユーザー` | そのユーザーのプロセスが開いているファイル |
| `lsof -c 名前` | コマンド名がその文字で始まるプロセス |
| `lsof -i` | **ネットワークのソケット**。`lsof -i :22`（22 番ポート）、`lsof -i TCP`、`lsof -i TCP:80` |
| `lsof +D ディレクトリ` | そのディレクトリの**下の全部**について、開いているもの |
| `lsof -t ファイル` | PID だけを表示する（`kill $(lsof -t ファイル)` のように使う） |
| `lsof -a 条件 条件` | 条件を「かつ」でつなぐ（既定は「または」） |

`umount` が `target is busy` で失敗するときは、`lsof +D マウントポイント` で、そこを使っているプロセスを探します。

## OOM Killer は、メモリが尽きたときにだれを終わらせるか {#oom}

物理メモリもスワップも使い切ると、カーネルは **OOM Killer**（Out Of Memory Killer）を動かします。プロセスを 1 つ選んで `SIGKILL` で終わらせ、そのメモリを取り返します（[図解 Linux 13.10](../../linux/site/ch13.html#oom)）。小さな Linux で、メモリを食い尽くすプログラムを動かして確かめます。

```sh run error title="メモリを使い切ると、Killed で終わる"
memhog 8M > /dev/null
```

```sh run title="カーネルのログに記録が残る"
dmesg | grep 'Out of memory'
```

「プログラムが何も言わずに消えた」ときは、`dmesg` か `journalctl -k` で **`Out of memory: Killed process`** を探します。

だれを選ぶかは、プロセスごとの点数で決まります。

| ファイル | 意味 |
| --- | --- |
| `/proc/PID/oom_score` | いまの**点数**。メモリを多く使っているほど高い。**高いものから**終わらせる。読むだけ |
| `/proc/PID/oom_score_adj` | 点数の**調整値**。**-1000 〜 1000**。大きくすると選ばれやすく、小さくすると選ばれにくい。**-1000 にすると、そのプロセスは選ばれない** |
| `/proc/PID/oom_adj` | 古い調整値（-17 〜 15。-17 で選ばれない）。いまは `oom_score_adj` を使う |

```sh run title="oom_score_adj で、選ばれやすさを変える"
cat /proc/$$/oom_score /proc/$$/oom_score_adj
echo 500 > /proc/$$/oom_score_adj
cat /proc/$$/oom_score
sudo sh -c "echo -1000 > /proc/$$/oom_score_adj"
cat /proc/$$/oom_score
```

調整値を 500 にすると点数が上がり、-1000 にすると 0 になりました。**0 より小さい値にする**（既定より選ばれにくくする）には root の権限が要ります。一般ユーザーが自分のプロセスに書けるのは、選ばれやすくする向きだけです。データベースのように、終わらせられては困るプロセスに -1000 を設定する、という使い方をします。systemd のサービスなら、unit ファイルに `OOMScoreAdjust=-1000` と書けます。

メモリの確保をどこまで許すかは、カーネルのパラメータで決まります。

| パラメータ（`sysctl` の名前） | 意味 |
| --- | --- |
| `vm.overcommit_memory` | **0**（既定）：明らかに無理な要求だけ断る。**1**：いつも許す。**2**：スワップ + 物理メモリの一定の割合（`vm.overcommit_ratio`。既定 50%）までしか許さない |
| `vm.panic_on_oom` | **0**（既定）：OOM Killer がプロセスを終わらせる。1：プロセスを終わらせる代わりに、カーネルパニックにする |
| `vm.oom_kill_allocating_task` | 0（既定）：点数の高いプロセスを選ぶ。1：メモリを要求したプロセス自身を終わらせる |

## 監視ツールと SNMP は、何をどう集めるか {#monitoring}

### 3 つの監視

| 監視 | 見るもの | 例 |
| --- | --- | --- |
| **死活監視** | 機械やサービスが**生きているか** | ping が返るか、80 番ポートにつながるか、プロセスがあるか |
| **リソース監視** | CPU、メモリ、ディスク、通信量の**数値と、その移り変わり** | ディスクの使用率のグラフ、ロードアベレージがしきい値を超えたか |
| **運用監視** | 上の 2 つに、ログの監視、障害の通知、対応の記録までを合わせた、運用全体 | エラーのログが出たらメールで知らせる |

### SNMP：監視のための共通のプロトコル

**SNMP**（Simple Network Management Protocol）は、ルーター、スイッチ、サーバー、プリンターなどの状態を、ネットワーク越しに同じやり方で聞くためのプロトコルです。

```fig graph SNMP。マネージャーが聞き（161 番）、エージェントが答える。異常のときは、エージェントのほうからトラップを送る（162 番）
{
  col: 300, row: 110,
  nodes: [
    { id: 'm', label: 'SNMP マネージャー', sub: '監視サーバー（Zabbix、MRTG など）', x: 0, y: 0, kind: 'accent', mono: false },
    { id: 'a', label: 'SNMP エージェント', sub: '監視される機器（snmpd）。MIB を持つ', x: 1, y: 0, kind: 'stack', mono: false },
  ],
  edges: [
    { from: 'm', to: 'a', label: 'Get / GetNext / Set → UDP 161', curve: -34 },
    { from: 'a', to: 'm', label: 'Trap → UDP 162', curve: -34, style: 'accent' },
  ],
}
```

| 用語 | 意味 |
| --- | --- |
| **マネージャー** | 情報を集める側（監視サーバー） |
| **エージェント** | 監視される機器の上で動き、聞かれたら答えるプログラム（Linux では net-snmp の `snmpd`） |
| **MIB**（Management Information Base） | エージェントが持っている、管理情報の**木の形のデータベース** |
| **OID**（Object Identifier） | MIB の中の 1 つ 1 つの項目を指す番号。`.1.3.6.1.2.1.1.5.0`（ホスト名）のように、点で区切った数字 |
| **コミュニティ名** | v1 と v2c で使う、**パスワード代わりの文字列**。暗号化されずに流れる。読み取り用の既定の値として `public` がよく使われる |
| **ポーリング** | マネージャーが定期的に聞きに行くこと。エージェントの **UDP 161 番**へ |
| **トラップ** | 異常が起きたとき、エージェントのほうから知らせること。マネージャーの **UDP 162 番**へ |

| バージョン | 認証 | 特徴 |
| --- | --- | --- |
| v1 | コミュニティ名（平文） | 最初の版 |
| v2c | コミュニティ名（平文） | まとめて取る GetBulk などを足した。広く使われている |
| **v3** | **ユーザーごとの認証と、通信の暗号化** | 安全。新しく組むならこれ |

net-snmp のコマンドで、エージェントに聞きます。Rocky Linux 9 で `snmpd` を動かして確かめました。

```console
$ snmpwalk -v 2c -c public localhost system        … system の下を順に全部
SNMPv2-MIB::sysDescr.0 = STRING: Linux 1b357d082f9c 6.10.14-linuxkit #1 SMP Thu Aug 14 19:26:13 UTC 2025 aarch64
SNMPv2-MIB::sysObjectID.0 = OID: NET-SNMP-MIB::netSnmpAgentOIDs.10
DISMAN-EVENT-MIB::sysUpTimeInstance = Timeticks: (202) 0:00:02.02
SNMPv2-MIB::sysContact.0 = STRING: Root <root@localhost> (configure /etc/snmp/snmp.local.conf)
SNMPv2-MIB::sysName.0 = STRING: 1b357d082f9c
…
$ snmpget -v 2c -c public localhost sysName.0      … 1 つだけ
SNMPv2-MIB::sysName.0 = STRING: 1b357d082f9c
$ snmpget -v 2c -c public localhost .1.3.6.1.2.1.1.5.0   … 同じものを OID の番号で
SNMPv2-MIB::sysName.0 = STRING: 1b357d082f9c
```

| コマンド | すること |
| --- | --- |
| `snmpget` | OID を 1 つ指定して、その値を取る |
| `snmpwalk` | 指定した OID の**下にある項目を、順に全部**取る |
| `snmpset` | 値を書き換える |
| `snmptrap` | トラップを送る（受けるのは `snmptrapd`） |

オプションは共通で、`-v` がバージョン（`1`、`2c`、`3`）、`-c` がコミュニティ名です。エージェントの設定は `/etc/snmp/snmpd.conf` で、読み取りだけを許すコミュニティは `rocommunity public` のように書きます。

### 監視ツール

名前と特徴の組み合わせを覚えます。

| 名前 | 何をするか | 特徴 |
| --- | --- | --- |
| **Nagios** | 死活監視とサービス監視、障害の通知 | 検査は**プラグイン**（小さなプログラム）が行い、結果を**終了ステータス**で返す。グラフを描くのは得意でない |
| **Icinga2** | Nagios と同じ分野 | **Nagios から分かれた** Icinga を作り直したもの。Nagios のプラグインがそのまま使える。独自の設定の書き方、REST API、複数台に分けた構成 |
| **Zabbix** | 監視、通知、グラフまでを **1 つにまとめた**統合監視 | Zabbix サーバー + データベース + Web の画面。監視される側に **Zabbix エージェント**（TCP 10050 番）を入れる。SNMP やエージェントなしの監視もできる。テンプレートで設定をまとめる |
| **collectd** | リソースの数値を**集める**デーモン | 軽い。プラグインで CPU、メモリ、ディスクなどを定期的に集め、RRD ファイルに書いたり、ネットワークで送ったりする。**グラフを描く機能や通知の画面は持たない** |
| **MRTG** | **SNMP** でルーターなどの通信量を集め、**グラフの画像と HTML** を作る | Multi Router Traffic Grapher。5 分ごとに集め、日・週・月・年のグラフを作る。`cfgmaker` で設定ファイルを作る |
| **Cacti** | SNMP で集めた数値を、**RRDtool** で保存してグラフにする **Web の画面** | PHP とデータベース（MySQL / MariaDB）で動く。グラフの設定をブラウザでできる |

Nagios のプラグインは、結果を終了ステータスで返します。この 4 つの値は Icinga2 でも同じです。

| 終了ステータス | 状態 |
| --- | --- |
| 0 | **OK** |
| 1 | **WARNING**（警告のしきい値を超えた） |
| 2 | **CRITICAL**（危険のしきい値を超えた） |
| 3 | **UNKNOWN**（調べられなかった） |

```console
$ /usr/lib/nagios/plugins/check_disk -w 20% -c 10% -p /     … 空きが 20% を切ったら警告、10% で危険
DISK OK - free space: / 830282MiB (93% inode=97%);| /=57531170816B;782316548915;880106117529;0;977895686144
$ echo $?
0
$ /usr/lib/nagios/plugins/check_disk -w 99% -c 10% -p /     … 警告のしきい値をわざと厳しくする
DISK WARNING - free space: / 830282MiB (93% inode=97%);| /=57532219392B;9778956861;880106117529;0;977895686144
$ echo $?
1
```

MRTG、Cacti、collectd が数値をしまうのに使う **RRD**（Round Robin Database）は、大きさが決まっているデータベースです。古いデータは、粗い平均にまとめながら上書きしていくので、何年動かしてもファイルが大きくなりません。

## Ansible は、エージェントなしで、SSH で設定を配る {#ansible}

```fig graph Ansible の登場人物。コントロールノードが、インベントリに書かれた管理対象ノードへ SSH でつなぎ、モジュールを実行する
{
  col: 230, row: 100,
  nodes: [
    { id: 'pb', label: 'Playbook', sub: 'YAML。何をするか', x: 0, y: 0, kind: 'crate', mono: false },
    { id: 'inv', label: 'インベントリ', sub: 'どのホストに', x: 0, y: 2, kind: 'crate', mono: false },
    { id: 'cn', label: 'コントロールノード', sub: 'Ansible を入れる機械', x: 1, y: 1, kind: 'accent', mono: false },
    { id: 'w1', label: 'web01', sub: '管理対象ノード', x: 2.2, y: 0, kind: 'stack', mono: true },
    { id: 'w2', label: 'web02', sub: 'SSH と Python があればよい', x: 2.2, y: 1, kind: 'stack', mono: true },
    { id: 'db', label: 'db01', sub: 'エージェントは要らない', x: 2.2, y: 2, kind: 'stack', mono: true },
  ],
  edges: [
    { from: 'pb', to: 'cn', style: 'muted' }, { from: 'inv', to: 'cn', style: 'muted' },
    { from: 'cn', to: 'w1', label: 'SSH' }, { from: 'cn', to: 'w2', label: 'SSH' }, { from: 'cn', to: 'db', label: 'SSH' },
  ],
}
```

サーバーが 1 台なら、手でコマンドを打って設定できます。50 台になると、同じ操作を 50 回まちがえずに繰り返すのは無理です。**構成管理ツール**は、「サーバーがどういう状態であるべきか」をファイルに書いておき、その通りにたくさんの機械を設定します。**Ansible** は、その代表です。

| 用語 | 意味 |
| --- | --- |
| **コントロールノード** | Ansible を入れて、コマンドを実行する機械 |
| **管理対象ノード** | 設定される側の機械。**SSH でログインできて、Python が入っていればよい** |
| **インベントリ** | 管理対象ノードの一覧。グループに分けて書く |
| **モジュール** | 1 つの仕事をする部品（パッケージを入れる、ファイルを置く、サービスを起動する） |
| **タスク** | モジュールを 1 回呼び出すこと |
| **Playbook** | タスクを順に並べた、**YAML** のファイル |
| **冪等性**（べきとうせい） | **何回実行しても、結果が同じになる**性質 |

Ansible の特徴は 3 つです。

- **エージェントレス**：管理対象ノードに、専用の常駐プログラム（エージェント）を入れません。SSH でつないで、その場でモジュールを送り込んで実行します
- **プッシュ型**：コントロールノードのほうから、設定を送りつけます
- **YAML で書く**：手順（Playbook）は、プログラミング言語ではなく、読みやすい YAML で書きます

### 冪等性

Ansible のモジュールは、「この操作をしろ」ではなく、「**この状態であれ**」と書きます。`state: present`（入っている状態）と書いたパッケージは、入っていなければ入れ、**すでに入っていれば何もしません**。だから、同じ Playbook を何回実行しても、結果は同じです。これが冪等性です。

シェルスクリプトで `echo "port=8080" >> app.conf` と書くと、実行するたびに行が増えます。これは冪等ではありません。Ansible で同じファイルを 2 回コピーした結果を見ます（Debian 12、ansible-core 2.14）。

```console
$ ansible localhost -i hosts -m copy -a 'content=hello dest=/tmp/x.txt mode=0644'
localhost | CHANGED => {
    "changed": true,
    "dest": "/tmp/x.txt",
…
$ ansible localhost -i hosts -m copy -a 'content=hello dest=/tmp/x.txt mode=0644'
localhost | SUCCESS => {
    "changed": false,
    "dest": "/tmp/x.txt",
…
```

1 回目は **`CHANGED`**（変えた）、2 回目は **`SUCCESS`** で `"changed": false`（すでにその状態なので、何もしなかった）です。

### 設定ファイル ansible.cfg

Ansible 自身の設定は、**`ansible.cfg`** に書きます。次の順に探し、**最初に見つかった 1 つだけ**を使います。

| 順 | 場所 |
| --- | --- |
| 1 | 環境変数 **`ANSIBLE_CONFIG`** に書かれたファイル |
| 2 | カレントディレクトリの **`./ansible.cfg`** |
| 3 | ホームディレクトリの **`~/.ansible.cfg`**（先頭に点） |
| 4 | **`/etc/ansible/ansible.cfg`** |

```text
[defaults]
inventory = /etc/ansible/hosts
remote_user = admin
forks = 5
host_key_checking = True

[privilege_escalation]
become = True
become_method = sudo
become_user = root
```

| 項目 | 意味 | 既定 |
| --- | --- | --- |
| `inventory` | インベントリのファイル | **`/etc/ansible/hosts`** |
| `remote_user` | SSH でログインするユーザー | いまのユーザー |
| `forks` | 同時に処理するホストの数 | **5** |
| `host_key_checking` | SSH のホスト鍵を確かめるか | True |
| `become`、`become_method`、`become_user` | 権限を上げるか、その方法、なるユーザー | False、**sudo**、**root** |

どの設定ファイルを使っているかは、`ansible --version` の `config file =` の行で分かります。

## インベントリには、どのホストを、どうグループに分けるかを書く {#inventory}

**インベントリ**は、管理対象ノードの一覧です。既定の場所は `/etc/ansible/hosts` で、`-i ファイル` でほかのファイルを指定できます。いちばんよく使うのは、INI 形式です。

```text
mail.example.com

[web]
web[01:03].example.com
localhost ansible_connection=local

[db]
db1.example.com ansible_host=192.168.1.20 ansible_port=2222 ansible_user=admin

[prod:children]
web
db

[web:vars]
http_port=8080
```

| 書き方 | 意味 |
| --- | --- |
| `[web]` | **グループ**の名前。その下に、属するホストを 1 行に 1 つ書く |
| `web[01:03].example.com` | **範囲**。web01、web02、web03 の 3 台 |
| グループの見出しより前のホスト | どのグループにも入らない。`ungrouped` という特別なグループに入る |
| `ホスト 変数=値` | **ホスト変数**。そのホストだけの変数 |
| `[prod:children]` | **グループのグループ**。prod は、web と db を子に持つ |
| `[web:vars]` | **グループ変数**。web グループの全部のホストに付く変数 |

`all`（全部のホスト）と `ungrouped`（どのグループにも入っていないホスト）は、書かなくてもいつもあるグループです。

接続のしかたを決める変数は、名前が決まっています。

| 変数 | 意味 |
| --- | --- |
| `ansible_host` | 実際につなぐ先のアドレス（インベントリの名前と違うとき） |
| `ansible_port` | SSH のポート（既定は 22） |
| `ansible_user` | SSH でログインするユーザー |
| `ansible_ssh_private_key_file` | SSH の秘密鍵のファイル |
| `ansible_connection` | つなぎ方。`local` は SSH を使わず、コントロールノード自身で実行する |
| `ansible_become` | そのホストで権限を上げるか |

`ansible-inventory` で、インベントリがどう読まれたかを確かめられます。

```console
$ ansible-inventory -i hosts --graph
@all:
  |--@ungrouped:
  |  |--mail.example.com
  |--@prod:
  |  |--@web:
  |  |  |--web01.example.com
  |  |  |--web02.example.com
  |  |  |--web03.example.com
  |  |  |--localhost
  |  |--@db:
  |  |  |--db1.example.com
$ ansible web -i hosts --list-hosts
  hosts (4):
    web01.example.com
    web02.example.com
    web03.example.com
    localhost
```

インベントリは YAML でも書けます（`all:` の下に `children:`、グループの下に `hosts:` と `vars:` を字下げして書きます）。

変数が増えたら、インベントリと同じ場所に `group_vars/グループ名.yml` と `host_vars/ホスト名.yml` を作って、そこに YAML で書きます。Ansible が自動で読み込みます。

## ansible コマンドは、モジュールを 1 つだけその場で実行する {#ansible-adhoc}

**`ansible`** コマンドは、Playbook を書かずに、モジュールを 1 つだけ実行します。これを**アドホックコマンド**と呼びます。つながるかの確認や、ちょっとした調べものに使います。

```text
ansible ホストのパターン -i インベントリ -m モジュール -a '引数'
```

```console
$ ansible localhost -i hosts -m ping
localhost | SUCCESS => {
    "ansible_facts": {
        "discovered_interpreter_python": "/usr/bin/python3"
    },
    "changed": false,
    "ping": "pong"
}
$ ansible localhost -i hosts -a 'uname -s'            … -m を省くと command モジュール
localhost | CHANGED | rc=0 >>
Linux
$ ansible web01.example.com -i hosts -m ping          … つながらないとき
web01.example.com | UNREACHABLE! => {
    "changed": false,
    "msg": "Failed to connect to the host via ssh: ssh: Could not resolve hostname web01.example.com: Name or service not known",
    "unreachable": true
}
```

| オプション | 意味 |
| --- | --- |
| `-i インベントリ` | インベントリのファイル（`--inventory`） |
| `-m モジュール` | 使うモジュール（`--module-name`）。省くと **`command`** |
| `-a '引数'` | モジュールに渡す引数（`--args`） |
| `-b` | 権限を上げて実行する（`--become`。既定では sudo で root になる） |
| `-K` | 権限を上げるときのパスワード（sudo のパスワード）をたずねる（`--ask-become-pass`） |
| `-k` | SSH の接続のパスワードをたずねる（`--ask-pass`） |
| `-u ユーザー` | SSH でログインするユーザー（`--user`） |
| `-f 数` | 同時に処理するホストの数（`--forks`。既定 5） |
| `-e '変数=値'` | 変数を渡す（`--extra-vars`） |
| `-C`、`-D` | 変更しないで試す（`--check`）、変わる内容を表示する（`--diff`） |
| `-o` | 結果を 1 行にまとめる（`--one-line`） |
| `--list-hosts` | 対象になるホストを表示するだけで、実行しない |

ホストのパターンには、ホスト名、グループ名、`all` のほか、組み合わせも書けます。

| パターン | 対象 |
| --- | --- |
| `all` | 全部のホスト |
| `web` | web グループ |
| `web:db` | web **または** db（合わせたもの） |
| `web:&prod` | web **かつ** prod（両方に入っているもの） |
| `web:!web01.example.com` | web のうち、web01 を**除く** |

### よく使うモジュール

| モジュール | すること | 主な引数 |
| --- | --- | --- |
| `ping` | SSH でログインできて、Python が使えるかを確かめる。成功すると **`pong`** を返す。**ICMP の ping ではない** | — |
| `command` | コマンドを実行する（**シェルを通さない**ので、`|`、`>`、`&&` は使えない）。`-m` を省いたときの既定 | `creates=`（そのファイルがあれば実行しない） |
| `shell` | コマンドを **`/bin/sh` を通して**実行する（パイプやリダイレクトが使える） | |
| `raw` | Python を使わずに、SSH でコマンドをそのまま実行する（Python がまだない機械に） | |
| `copy` | コントロールノードのファイルを、管理対象ノードへコピーする | `src=`、`dest=`、`mode=`、`owner=`、`content=` |
| `template` | **Jinja2** のテンプレート（`.j2`）の変数を埋めてから、コピーする | `src=`、`dest=` |
| `file` | ファイルやディレクトリの状態（あるか、権限、持ち主）を決める | `path=`、`state=directory` / `touch` / `absent` / `link`、`mode=` |
| `lineinfile` | ファイルの中に、その 1 行があるようにする | `path=`、`line=`、`regexp=` |
| `apt`、`dnf`（`yum`） | パッケージを入れる・消す（Debian 系、Red Hat 系） | `name=`、`state=present` / `absent` / `latest`、`update_cache=` |
| `package` | ディストリビューションに合ったパッケージ管理を自動で選ぶ | `name=`、`state=` |
| `service`、`systemd` | サービスを起動する・止める、自動起動を決める | `name=`、`state=started` / `stopped` / `restarted` / `reloaded`、`enabled=` |
| `user`、`group` | ユーザー、グループを作る・消す | `name=`、`state=`、`groups=`、`shell=` |
| `setup` | 管理対象ノードの情報（**ファクト**：OS、IP アドレス、メモリなど）を集める | `filter=` |
| `debug` | 変数の中身やメッセージを表示する | `msg=`、`var=` |

`state` の値は、パッケージなら `present`（入っている）、`absent`（入っていない）、`latest`（最新）、サービスなら `started`、`stopped`、`restarted`、`reloaded` です。「操作」ではなく「状態」を書くのが、冪等性の元です。

```console
$ ansible web -i hosts -m command -a 'ls /etc/hostname | wc -l'    … command はパイプを解釈しない
localhost | FAILED | rc=2 >>
-rw-r--r-- 1 root root 13 Nov 16 21:24 /etc/hostnamels: cannot access '|': No such file or directory
ls: cannot access 'wc': No such file or directorynon-zero return code
$ ansible web -i hosts -m shell -a 'ls /etc/hostname | wc -l'      … shell なら使える
localhost | CHANGED | rc=0 >>
1
```

:::warn 試験の注意：command と shell は冪等ではない
`command` と `shell` は、「状態」ではなく「操作」を実行するので、Ansible には変わったかどうかが分かりません。**実行するたびに `changed` と報告します**。できるだけ、専用のモジュール（`apt`、`copy`、`service` など）を使います。どうしても使うときは、`creates=ファイル`（そのファイルがあれば実行しない）を付けます。
:::

モジュールの説明は、**`ansible-doc`** で読めます。`ansible-doc -l` はモジュールの一覧、`ansible-doc モジュール名` はそのモジュールの説明と引数です。

## Playbook は、YAML で「あるべき状態」を上から順に書く {#playbook}

### YAML の書き方

| 決まり | 例 |
| --- | --- |
| ファイルの最初に `---`（省ける） | `---` |
| **字下げ（インデント）で入れ子を表す**。字下げは**空白**で。**タブは使えない** | |
| `- ` で始まる行は、**リスト**（並び）の要素 | `- nginx` |
| `キー: 値` は、**マッピング**（辞書）。コロンの後ろに空白が要る | `name: nginx` |
| `#` から行末まではコメント | `# コメント` |
| 真偽値は `true` / `false`（`yes` / `no` も使える） | `enabled: true` |
| 値が `{{` で始まるときは、全体を**引用符で囲む** | `dest: "{{ dir }}/a.conf"` |

### Playbook の形

```fig tree Playbook の入れ子。Playbook はプレイのリスト、プレイは「どのホストに」と「タスクのリスト」を持つ
{
  root: { label: 'Playbook（site.yml）', kind: 'dir', children: [
    { label: 'プレイ（- name: …）', kind: 'dir', hl: true, children: [
      { label: 'hosts:', note: 'どのホスト・グループに' },
      { label: 'become:', note: '権限を上げるか' },
      { label: 'vars:', note: '変数' },
      { label: 'tasks:', kind: 'dir', hl: true, note: '上から順に実行するタスクのリスト', children: [
        { label: '- name: …', note: 'タスクの名前（表示に出る）' },
        { label: '  モジュール名:', note: 'モジュールと、その引数' },
        { label: '  notify: / when: / loop: / register: / tags:', note: 'タスクに付ける指示' },
      ] },
      { label: 'handlers:', kind: 'dir', note: 'notify で呼ばれたときだけ動くタスク' },
    ] },
  ] },
}
```

nginx を入れて、設定ファイルを置き、起動する Playbook です。

```text
---
- name: Web サーバーを整える
  hosts: web
  become: true
  vars:
    http_port: 8080
  tasks:
    - name: nginx を入れる
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: 設定ファイルを置く
      ansible.builtin.template:
        src: site.conf.j2
        dest: /etc/nginx/conf.d/site.conf
        mode: "0644"
      notify: nginx を再読み込みする

    - name: nginx を起動し、自動起動にする
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: nginx を再読み込みする
      ansible.builtin.service:
        name: nginx
        state: reloaded
```

| キー | 意味 |
| --- | --- |
| `hosts:` | このプレイの対象（インベントリのホスト名、グループ名、`all`） |
| `become: true` | 権限を上げて（既定では sudo で root になって）実行する |
| `vars:` | 変数を決める。使うときは **`{{ 変数名 }}`** |
| `tasks:` | タスクのリスト。**上から順に**実行する |
| `name:` | プレイやタスクの名前。実行中の表示に出る |
| `ansible.builtin.apt:` | モジュールの名前。`apt:` と短く書いてもよい。その下に字下げして引数を書く |
| `notify:` | このタスクが **changed になったときだけ**、その名前のハンドラーを呼ぶ |
| `handlers:` | ハンドラーのリスト。呼ばれたものだけが、**全部のタスクが終わった後に 1 回**動く |

テンプレート `site.conf.j2` の中では、`{{ http_port }}` のように変数を書きます。`template` モジュールが、値を埋めてからコピーします。

タスクには、次の指示も付けられます。

| キー | 意味 | 例 |
| --- | --- | --- |
| `when:` | **条件**が真のときだけ実行する | `when: ansible_facts['os_family'] == "Debian"` |
| `loop:` | リストの要素ごとに繰り返す。要素は `{{ item }}` | `loop: [git, curl]` |
| `register:` | タスクの結果を変数に入れる | `register: result` |
| `tags:` | タスクに印を付ける。`--tags` で、その印のタスクだけ実行できる | `tags: conf` |
| `ignore_errors: true` | 失敗しても、次のタスクへ進む | |
| `changed_when: false` | このタスクを changed と報告させない | |

プレイの最初には、`setup` モジュールが自動で動いて、**ファクト**（管理対象ノードの情報）を集めます。表示では `TASK [Gathering Facts]` と出ます。集めた値は `ansible_facts['os_family']` のように使えます。要らないときは、プレイに `gather_facts: false` と書きます。

### ansible-playbook で実行する

```console
$ ansible-playbook -i hosts site.yml --syntax-check       … 文法だけを確かめる

playbook: site.yml
$ ansible-playbook -i hosts site.yml                      … 1 回目

PLAY [Web サーバーを整える] ****************************************************

TASK [Gathering Facts] *********************************************************
ok: [localhost]

TASK [nginx を入れる] **********************************************************
changed: [localhost]

TASK [設定ファイルを置く] ******************************************************
changed: [localhost]

TASK [nginx を起動し、自動起動にする] ******************************************
changed: [localhost]

RUNNING HANDLER [nginx を再読み込みする] ***************************************
changed: [localhost]

PLAY RECAP *********************************************************************
localhost                  : ok=5    changed=4    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
```

同じ Playbook を、もう一度実行します。

```console
$ ansible-playbook -i hosts site.yml                      … 2 回目

TASK [nginx を入れる] **********************************************************
ok: [localhost]

TASK [設定ファイルを置く] ******************************************************
ok: [localhost]

TASK [nginx を起動し、自動起動にする] ******************************************
ok: [localhost]

PLAY RECAP *********************************************************************
localhost                  : ok=4    changed=0    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
```

2 回目は、**全部が `ok` で、`changed=0`** です。すでにあるべき状態なので、何も変えていません。設定ファイルが変わらなかったので、ハンドラーも呼ばれていません。これが冪等性です。

| 表示 | 意味 |
| --- | --- |
| `ok` | すでにその状態だった。何も変えなかった |
| `changed` | 状態を変えた |
| `skipping` | `when` の条件に合わないなどで、実行しなかった |
| `failed` | 失敗した。**そのホストでは、残りのタスクを実行しない**（ほかのホストは続ける） |
| `unreachable` | SSH でつながらなかった |

| オプション | 意味 |
| --- | --- |
| `-i インベントリ` | インベントリのファイル |
| `--syntax-check` | Playbook の**文法だけ**を確かめる。実行しない |
| `-C`（`--check`） | **チェックモード（ドライラン）**。変更しないで、何が変わるはずかを報告する |
| `-D`（`--diff`） | ファイルがどう変わるかを、差分で表示する。`--check` と組み合わせることが多い |
| `--list-hosts` | 対象のホストを表示するだけ |
| `--list-tasks` | 実行されるタスクを表示するだけ |
| `--list-tags` | 使われているタグを表示するだけ |
| `-l パターン`（`--limit`） | 対象を、そのホストやグループに**絞る** |
| `-t タグ`（`--tags`） | そのタグの付いたタスクだけ実行する。`--skip-tags` は逆 |
| `-e '変数=値'`（`--extra-vars`） | 変数を渡す。Playbook の `vars:` より**優先される** |
| `-b`、`-K`、`-k`、`-u`、`-f` | `ansible` コマンドと同じ（become、sudo のパスワード、SSH のパスワード、ユーザー、同時に処理する数） |
| `--start-at-task 名前` | その名前のタスクから始める |
| `--step` | タスクを 1 つずつ、確かめながら実行する |
| `-v`（`-vvv`） | 詳しく表示する |

`--check --diff` を付けて実行すると、設定ファイルのどの行が変わるか（`-    listen 8080;` と `+    listen 8081;`）が表示され、タスクは `changed` と報告されますが、実際のファイルは変わりません。

:::warn 試験の注意：--syntax-check と --check
`--syntax-check` は、YAML と Playbook の**書き方**を確かめるだけで、管理対象ノードにはつなぎません。`--check`（`-C`）は、管理対象ノードにつないで、**変更せずに**何が変わるかを調べます。「実際には変更しないで試す（ドライラン）」は `--check` です。なお、`command` と `shell` のタスクは、チェックモードでは実行されず、`skipping` になります。
:::

:::deep ロール、Galaxy、Vault
Playbook が大きくなったら、**ロール**に分けます。ロールは `roles/名前/` の下に `tasks/`、`handlers/`、`templates/`、`files/`、`vars/`、`defaults/` を決まった名前で置いたもので、Playbook からは `roles:` で呼び出します。ほかの人が作ったロールやコレクションは、**`ansible-galaxy`** コマンドで取ってこられます。パスワードなどの秘密を書いたファイルは、**`ansible-vault`** で暗号化しておけます（`ansible-vault create`、`edit`、`encrypt`）。
:::

:::key まとめ
- ソースからのビルドは `./configure`（環境を調べて **Makefile を作る**。`--prefix=` の既定は `/usr/local`）→ `make`（コンパイル）→ `make install`（コピー。**root**）。`make clean`、`make -j`、`DESTDIR=`
- `git clone URL`、`git tag -l`（タグの一覧）、`git checkout タグ`（その版に切り替える。detached HEAD）
- 展開は `gunzip` / `bunzip2` / `unxz`、tar の `z` / `j` / `J`、`unzip`（`-d` 展開先、`-l` 一覧）。`patch -p数`（パスの先頭を削る数）、`-R`（取り消す）、`--dry-run`
- フル（全部）、差分（**最後のフル**から）、増分（**直前のバックアップ**から）。戻すのは、差分ならフル + 最新の差分、増分ならフル + 全部の増分を順に
- `tar -g スナップショット` で増分。`dd` はブロック単位（イメージ）。`rsync -a`（= `-rlptgoD`）、`-z`、`-n`、`--delete`、`-e ssh`、コピー元の最後の `/` は「中身」
- `/dev/st0` は閉じると**巻き戻す**、`/dev/nst0` は**巻き戻さない**。`mt -f デバイス rewind` / `fsf 数` / `status` / `offline` / `erase`
- Amanda（dump と tar を使う）、Bacula（Director、Storage Daemon、File Daemon、Catalog）、Bareos（Bacula から分かれた）、BackupPC（ディスクへ。Web の画面。クライアントにソフト不要）
- `/etc/issue`（ログインの前、ローカル）、`/etc/issue.net`（ログインの前、ネットワーク。SSH は `Banner`）、`/etc/motd`（ログインの後）、`wall`（いますぐ全員へ）、`shutdown -k`（警告だけ）、`--no-wall`
- `vmstat` の `r`（実行待ち）、`b`（ブロック）、`si` / `so`（スワップ）、`bi` / `bo`（ディスク）、`wa`（I/O 待ち）。1 行目は起動からの平均
- `iostat`（デバイスごとの I/O。`-x` で `%util`）、`iotop`（プロセスごとの I/O）、`iftop`（接続ごとの通信量）、`lsof`（開いているファイル。`-i`、`-p`、`-u`、`+D`）
- `sar` は sysstat。`sadc` が集め、`sa1` が 10 分ごと、`sa2` が 1 日 1 回。`/var/log/sa/saDD`（Red Hat 系）、`/var/log/sysstat/saDD`（Debian 系）。`-u` CPU、`-r` メモリ、`-b` I/O、`-d` デバイス、`-n DEV` ネットワーク、`-q` 実行キュー、`-f` ファイル
- OOM Killer は `oom_score` の高いプロセスを SIGKILL。`/proc/PID/oom_score_adj` は -1000 〜 1000、**-1000 で対象外**。記録は `dmesg`
- SNMP：マネージャーとエージェント、MIB と OID、コミュニティ名、**UDP 161**（問い合わせ）と **UDP 162**（トラップ）、v3 で認証と暗号化。`snmpwalk -v 2c -c public ホスト OID`
- Nagios（プラグイン。終了ステータス 0 OK、1 WARNING、2 CRITICAL、3 UNKNOWN）、Icinga2（Nagios 由来）、Zabbix（統合監視。エージェント）、collectd（集めるだけ）、MRTG（SNMP で通信量のグラフ）、Cacti（RRDtool の Web の画面）
- Ansible：**エージェントレス**（SSH と Python）、**冪等性**、インベントリ（既定 `/etc/ansible/hosts`。`[グループ]`、`[親:children]`、`[グループ:vars]`）、モジュール、Playbook（YAML。`hosts`、`become`、`vars`、`tasks`、`handlers` と `notify`）
- `ansible パターン -m モジュール -a 引数`（`-m` の既定は `command`）、`ansible-playbook`（`--syntax-check`、`-C` / `--check`、`-D`、`-l`、`-t`、`-e`、`-b`、`-K`）。`ok` / `changed` / `failed` / `unreachable`
:::

## 練習問題 {#practice}

### 2.04.1 make によるソースコードからのビルドとインストール

:::q 2.04.1-01 single
ソースコードに付属する `configure` スクリプトの役割として正しいものはどれか。
- [ ] ソースコードをコンパイルして、実行ファイルを作る
- [x] コンパイラやライブラリなどの環境を調べ、その環境に合った Makefile を作る
- [ ] できた実行ファイルを `/usr/local` の下へコピーする
- [ ] ソースコードのアーカイブを展開する
- [ ] ソースコードにパッチを当てる
:::why
`./configure` は環境を調べて **Makefile を作る**段階です。コンパイルするのは `make`、インストール先へコピーするのは `make install`、展開は `tar`、パッチを当てるのは `patch` です（[ソースからインストールする流れ](#build-flow)、[configure](#configure-make)）。
:::
:::

:::q 2.04.1-02 single
ソースコードから既定の設定でソフトウェアをインストールする。次の手順のうち、通常 root の権限が必要になるものはどれか。
- [ ] `tar xzf app-1.0.tar.gz`
- [ ] `./configure`
- [ ] `make`
- [x] `make install`
- [ ] `make clean`
:::why
既定のインストール先 `/usr/local` は、root しか書き込めません。そこへコピーする `make install` だけが root を必要とします。展開、`./configure`、`make`、`make clean` は、ソースのディレクトリの中のファイルを作ったり消したりするだけなので、一般ユーザーで実行します（[ソースからインストールする流れ](#build-flow)）。
:::
:::

:::q 2.04.1-03 fill
インストール先を `/opt/app` の下にして Makefile を作りたい。空欄に入るオプションを入力してください。

```text
$ ./configure ____=/opt/app
```
= --prefix
:::why
`--prefix=ディレクトリ` がインストール先の起点です。実行ファイルは `/opt/app/bin` に入ります。省略すると `/usr/local` になります（[configure](#configure-make)）。
:::
:::

:::q 2.04.1-04 single
`./configure` をオプションなしで実行し、`make`、`make install` を行った。実行ファイル `hello` がインストールされる場所として、通常正しいものはどれか。
- [ ] `/usr/bin/hello`
- [ ] `/bin/hello`
- [x] `/usr/local/bin/hello`
- [ ] `/opt/hello/bin/hello`
- [ ] `/usr/src/hello`
:::why
`--prefix` の既定は `/usr/local` で、実行ファイルはその下の `bin` に入ります。`/usr/bin` と `/bin` はパッケージ管理が使う場所で、自分でビルドしたものと混ざらないように分けてあります。`/opt/hello` に入れるには `--prefix=/opt/hello` を指定します。`/usr/src` はソースコードを置く場所です（[configure](#configure-make)）。
:::
:::

:::q 2.04.1-05 single
`git clone` で複製したリポジトリの中で実行する `git tag -l` の説明として正しいものはどれか。
- [x] リポジトリにあるタグの一覧を表示する
- [ ] 現在の版に新しいタグを付ける
- [ ] 最新のタグの版に作業ディレクトリを切り替える
- [ ] リモートのリポジトリからタグを取得する
- [ ] タグをすべて削除する
:::why
`git tag -l`（`--list`）はタグの一覧を表示します。`git tag -l 'v1.*'` のようにパターンで絞れます。タグを付けるのは `git tag 名前`、その版に切り替えるのは `git checkout タグ` です。`-l` には取得や削除の働きはありません（[git clone とタグ](#get-source)）。
:::
:::

:::q 2.04.1-06 fill
`git clone` で複製したリポジトリで、作業ディレクトリをタグ `v2.0` の版の内容に切り替えたい。空欄に入る git のサブコマンドを入力してください。

```text
$ git ____ v2.0
```
= checkout
:::why
`git checkout タグ` で、作業ディレクトリがそのタグの版になります。どのブランチにも乗っていない detached HEAD の状態になりますが、ビルドするだけなら問題ありません（[git clone とタグ](#get-source)）。
:::
:::

:::q 2.04.1-07 single
パッチファイル `fix.patch` の先頭は次の通りである。`src` ディレクトリを直下に持つソースのディレクトリ（`hello-1.0` と同じ内容）に移動してから、このパッチを当てたい。正しいコマンドはどれか。

```text
--- hello-1.0/src/a.txt	2026-11-16 21:20:01.311614003 +0000
+++ hello-1.1/src/a.txt	2026-11-16 21:20:01.311614003 +0000
@@ -1,3 +1,4 @@
```
- [ ] `patch -p0 < fix.patch`
- [x] `patch -p1 < fix.patch`
- [ ] `patch -p2 < fix.patch`
- [ ] `patch -R < fix.patch`
- [ ] `patch -d < fix.patch`
:::why
カレントディレクトリから見た対象は `src/a.txt` です。パッチの中のパス `hello-1.0/src/a.txt` から先頭の 1 個（`hello-1.0/`）を削ればよいので `-p1` です。`-p0` は削らないので `hello-1.0/src/a.txt` を探し、`-p2` は `a.txt` を探して、どちらも見つかりません。`-R` は逆向きに当てる（取り消す）オプション、`-d` は移動先のディレクトリを引数に取るオプションです（[patch](#configure-make)）。
:::
:::

:::q 2.04.1-08 single
`patch -p1 < fix.patch` で当てたパッチを取り消して、元の状態に戻したい。正しいコマンドはどれか。
- [ ] `patch -p1 --dry-run < fix.patch`
- [ ] `patch -p1 -b < fix.patch`
- [x] `patch -p1 -R < fix.patch`
- [ ] `patch -p1 -N < fix.patch`
- [ ] `unpatch -p1 < fix.patch`
:::why
`-R`（`--reverse`）は、パッチを逆向きに当てます。当ててあるパッチを取り消せます。`--dry-run` は試すだけでファイルを変えません。`-b` は元のファイルを `.orig` として残すオプションです。`-N` は、すでに当ててあるように見えるパッチを飛ばすオプションです。`unpatch` というコマンドはありません（[patch](#configure-make)）。
:::
:::

:::q 2.04.1-09 multi
GNU tar で、xz で圧縮された `src.tar.xz` を展開できるコマンドを 2 つ選択してください。
- [x] `tar xJf src.tar.xz`
- [ ] `tar xzf src.tar.xz`
- [ ] `tar xjf src.tar.xz`
- [x] `tar xf src.tar.xz`
- [ ] `tar tJf src.tar.xz`
:::why
xz は大文字の `J` です。GNU tar は、展開のときは圧縮の種類を自分で見分けるので、`tar xf` だけでも展開できます。`z` は gzip、小文字の `j` は bzip2 で、種類が合わないと `not in gzip format` のように失敗します。`t` は中身の一覧を表示するだけで、展開しません（[アーカイブを展開する](#get-source)）。
:::
:::

:::q 2.04.1-10 single
`src.zip` を、`/tmp/src` ディレクトリの下に展開したい。正しいコマンドはどれか。
- [ ] `unzip -C /tmp/src src.zip`
- [x] `unzip src.zip -d /tmp/src`
- [ ] `unzip -l src.zip /tmp/src`
- [ ] `gunzip -d /tmp/src src.zip`
- [ ] `unzip -o /tmp/src src.zip`
:::why
`unzip` の展開先は `-d ディレクトリ` です。`-C` は tar の展開先のオプションで、unzip では「ファイル名の大文字と小文字を区別しない」という別の意味です。`-l` は一覧を表示するだけ、`-o` は確認せずに上書きするオプションです。`gunzip` は `.gz` を展開するコマンドで、`.zip` は扱えません（[アーカイブを展開する](#get-source)）。
:::
:::

:::q 2.04.1-11 single
`configure` と `make` を使ってビルドしたソースのディレクトリで実行する `make clean` の説明として、通常正しいものはどれか。
- [ ] インストールしたファイルを、インストール先から削除する
- [x] コンパイルでできたオブジェクトファイルや実行ファイルを削除する。Makefile は残る
- [ ] configure が作った Makefile も含めて削除し、配布されたときの状態に戻す
- [ ] ソースコードのディレクトリ全体を削除する
:::why
`make clean` は、コンパイルの生成物を消します。Makefile は残るので、すぐに `make` し直せます。Makefile まで消して配布時の状態に戻すのは `make distclean`、インストールしたファイルを消すのは `make uninstall` です（[make と make install](#configure-make)）。
:::
:::

:::q 2.04.1-12 multi
`make` コマンドの説明として正しいものを 2 つ選択してください。
- [x] ターゲットを指定しないと、Makefile の最初のターゲットを作る
- [ ] Makefile がないときは、自動的に `./configure` を実行する
- [x] `make -j 4` は、4 つの仕事を並行して実行する
- [ ] `make -n` は、エラーが起きても無視して最後まで続ける
- [ ] `make install` は、`--prefix` の指定にかかわらず `/usr` の下へコピーする
:::why
ターゲットを省くと最初のターゲット（ふつう `all`）を作ります。`-j 数` は並行して実行する仕事の数です。`make` が `configure` を呼ぶことはなく、Makefile がなければエラーになります。`-n` は実行するコマンドを表示するだけで、実行しません。`make install` のコピー先は、`configure` の `--prefix`（既定は `/usr/local`）で決まります（[make と make install](#configure-make)）。
:::
:::

:::q 2.04.1-13 fill
bzip2 で圧縮されたファイル `patch-1.1.bz2` を展開して、`patch-1.1` に戻したい。`bzip2` 以外のコマンドを使う。空欄に入るコマンド名を入力してください。

```text
$ ____ patch-1.1.bz2
```
= bunzip2
:::why
bzip2 の展開は `bunzip2`（または `bzip2 -d`）です。gzip は `gunzip`、xz は `unxz` です。`bzcat` は中身を標準出力に書くだけで、`patch-1.1` というファイルは作りません（[アーカイブを展開する](#get-source)）。
:::
:::

:::q 2.04.1-14 multi
`git clone` の説明として正しいものを 2 つ選択してください。
- [x] ディレクトリ名を省略すると、リポジトリの名前のディレクトリを作って複製する
- [ ] 既定では、最新の版のファイルだけを取得し、過去の履歴は取得しない
- [x] `--depth 1` を付けると、最新の版だけを取得する
- [ ] 複製した直後の作業ディレクトリは、いちばん古いタグの版になっている
- [ ] 複製するには、複製元のサーバーの root 権限が必要である

`git clone URL` は、リポジトリの名前（末尾の `.git` を除く）のディレクトリを作り、**履歴ごと**複製します。履歴を取らないのは `--depth 1` を付けたときです。複製した直後は、既定のブランチの最新の状態です。タグの版にするには `git checkout タグ` か `git clone -b タグ` を使います。公開されたリポジトリの複製に root は要りません（[git clone とタグ](#get-source)）。
:::

:::q 2.04.1-15 single
`./configure` が `error:` を表示して途中で止まり、Makefile が作られなかった。原因を調べるために、まず見るファイルとして最も適切なものはどれか。

- [x] `config.log`
- [ ] `/var/log/messages`
- [ ] `config.status`
- [ ] `/etc/ld.so.conf`

### 2.04.2 バックアップとリストア

:::q 2.04.2-01 single
増分バックアップ（incremental backup）の説明として正しいものはどれか。
- [ ] 毎回、すべてのファイルをバックアップする
- [ ] 最後のフルバックアップの後に変更されたファイルを、毎回すべてバックアップする
- [x] 直前のバックアップ（フルでも増分でも）の後に変更されたファイルだけをバックアップする
- [ ] ディスクのブロックを、ファイルシステムを解釈せずにそのまま写す
:::why
増分は「直前のバックアップから」の変更です。「最後のフルから」の変更を毎回取るのは差分バックアップ、全部を取るのはフルバックアップです。ブロックをそのまま写すのは、`dd` などによるブロック単位（イメージ）のバックアップで、フル・差分・増分とは別の分け方です（[フル、差分、増分](#backup-types)）。
:::
:::

:::q 2.04.2-02 single
日曜日にフルバックアップ、月曜日から土曜日は毎日**差分**バックアップを取っている。水曜日のバックアップの後、木曜日の朝にディスクが壊れた。水曜日のバックアップの時点に戻すために必要なものはどれか。
- [ ] 水曜日の差分バックアップだけ
- [x] 日曜日のフルバックアップと、水曜日の差分バックアップ
- [ ] 日曜日のフルバックアップと、月曜日・火曜日・水曜日の差分バックアップ
- [ ] 月曜日・火曜日・水曜日の差分バックアップ
:::why
差分バックアップは、毎回「最後のフルから変わったもの」を全部含みます。水曜日の差分には、月曜日と火曜日の変更も入っているので、フルと最新の差分の 2 つで戻せます。差分だけでは、変わっていないファイルが戻りません。月・火・水の全部が要るのは、増分バックアップのときです（[フル、差分、増分](#backup-types)）。
:::
:::

:::q 2.04.2-03 single
日曜日にフルバックアップ、月曜日から土曜日は毎日**増分**バックアップを取っている。水曜日のバックアップの後、木曜日の朝にディスクが壊れた。水曜日のバックアップの時点に戻す手順として正しいものはどれか。
- [ ] 水曜日の増分バックアップだけをリストアする
- [ ] 日曜日のフルバックアップ、水曜日の増分バックアップの順にリストアする
- [x] 日曜日のフルバックアップ、月曜日、火曜日、水曜日の増分バックアップの順にリストアする
- [ ] 水曜日、火曜日、月曜日の増分バックアップ、日曜日のフルバックアップの順にリストアする
:::why
増分バックアップは、直前のバックアップからの変更しか含みません。フルを戻した後、その後の増分を**古いほうから順に全部**戻します。水曜日の分だけでは、月曜日と火曜日の変更が抜けます。新しいほうから先に戻すと、古い内容で上書きしてしまいます（[フル、差分、増分](#backup-types)）。
:::
:::

:::q 2.04.2-04 multi
週に 1 回のフルバックアップと組み合わせる、差分バックアップと増分バックアップの比較として正しいものを 2 つ選択してください。
- [x] 1 回のバックアップで取る量は、ふつう増分のほうが差分より小さい
- [ ] 差分バックアップは、直前の差分バックアップの後に変更されたファイルだけを取る
- [x] リストアに必要なバックアップの数は、ふつう差分のほうが増分より少ない
- [ ] 増分バックアップは、フルバックアップがなくてもリストアできる
- [ ] 差分バックアップで取る量は、フルバックアップからの日数がたっても変わらない
:::why
増分は直前のバックアップからの変更だけなので、1 回の量は小さくなります。その代わり、リストアにはフルとその後の増分が全部要ります。差分は「最後のフルから」の変更を毎回取るので、日がたつほど大きくなりますが、リストアはフルと最新の差分の 2 つで済みます。どちらも、元になるフルバックアップがなければ戻せません（[フル、差分、増分](#backup-types)）。
:::
:::

:::q 2.04.2-05 single
SCSI テープ装置のデバイスファイル `/dev/st0` と `/dev/nst0` の違いとして正しいものはどれか。
- [ ] `/dev/st0` は 1 台目、`/dev/nst0` は 2 台目のテープ装置である
- [ ] `/dev/st0` は読み取り専用、`/dev/nst0` は読み書きができる
- [x] `/dev/st0` は使い終わると先頭まで巻き戻し、`/dev/nst0` は巻き戻さない
- [ ] `/dev/st0` は圧縮しないで書き、`/dev/nst0` は圧縮して書く
- [ ] `/dev/st0` はブロックデバイス、`/dev/nst0` はネットワーク越しのテープ装置である
:::why
`n` は no rewind です。`/dev/st0` はデバイスファイルを閉じたときに自動で巻き戻し、`/dev/nst0` は書き終えた位置で止まります。1 本のテープに続けて複数のアーカイブを書くときは `/dev/nst0` を使います。2 台目の装置は `/dev/st1` と `/dev/nst1` です（[テープ](#tape)）。
:::
:::

:::q 2.04.2-06 fill
テープ装置 `/dev/nst0` のテープを、先頭まで巻き戻したい。空欄に入る mt の操作を入力してください。

```text
# mt -f /dev/nst0 ____
```
= rewind
:::why
`mt -f デバイス rewind` で先頭まで巻き戻します。`fsf 数` は先のファイルへ進む、`status` は状態の表示、`offline` は巻き戻して取り出せる状態にする操作です（[テープ](#tape)）。
:::
:::

:::q 2.04.2-07 single
次のコマンドで、1 本のテープに 2 つのアーカイブを書いた。テープを先頭まで巻き戻した後、2 つ目のアーカイブ（`/home`）の一覧を `tar tvf /dev/nst0` で表示したい。その前に実行するコマンドとして正しいものはどれか。

```text
# tar cvf /dev/nst0 /etc
# tar cvf /dev/nst0 /home
# mt -f /dev/nst0 rewind
```
- [x] `mt -f /dev/nst0 fsf 1`
- [ ] `mt -f /dev/nst0 bsf 1`
- [ ] `mt -f /dev/nst0 eod`
- [ ] `mt -f /dev/nst0 offline`
- [ ] `mt -f /dev/nst0 erase`
:::why
`fsf 1`（forward space file）は、1 つ先のファイル（アーカイブ）の先頭へ進みます。巻き戻した直後は 1 つ目の先頭にいるので、`fsf 1` で 2 つ目の先頭になります。`bsf` は前へ戻る、`eod` は書かれたデータの終わりへ進む、`offline` は巻き戻して取り出す、`erase` はテープを消去する操作です（[テープ](#tape)）。
:::
:::

:::q 2.04.2-08 single
`/srv/data` ディレクトリに `a.txt` がある。空のディレクトリ `/backup` に対して次のコマンドを実行した。`a.txt` がコピーされる場所として正しいものはどれか。

```text
# rsync -a /srv/data /backup
```
- [ ] `/backup/a.txt`
- [x] `/backup/data/a.txt`
- [ ] `/backup/srv/data/a.txt`
- [ ] `/backup/data/data/a.txt`
:::why
コピー元の最後に `/` がないと、ディレクトリ**そのもの**がコピーされ、`/backup/data/` が作られます。`/backup/a.txt` になるのは、`rsync -a /srv/data/ /backup` と最後に `/` を付けたとき（中身をコピー）です。途中のパス（`srv/`）は作られません（[rsync](#backup-tools)）。
:::
:::

:::q 2.04.2-09 single
`rsync -av --delete /srv/www/ /backup/www/` の `--delete` の働きとして正しいものはどれか。
- [ ] コピーが終わったファイルを、コピー元（`/srv/www/`）から削除する
- [x] コピー元にないファイルを、コピー先（`/backup/www/`）から削除する
- [ ] コピー先のファイルをすべて削除してから、全体をコピーし直す
- [ ] 途中まで転送したファイルを削除する
- [ ] コピー先にあるコピー元より古いファイルだけを削除する
:::why
`--delete` は、コピー元に存在しないファイルをコピー先から消して、コピー先をコピー元と同じ内容（ミラー）にします。コピー元は変えません。全部を消してコピーし直すわけではなく、変わったファイルだけを送るのは変わりません。付けなければ、コピー元で消したファイルはコピー先に残ります（[rsync](#backup-tools)）。
:::
:::

:::q 2.04.2-10 multi
`rsync` の `-a`（`--archive`）オプションに含まれるものを 2 つ選択してください。
- [x] ディレクトリの中を再帰的にたどる（`-r`）
- [ ] 転送するデータを圧縮する（`-z`）
- [x] パーミッションを保つ（`-p`）
- [ ] コピー元にないファイルをコピー先から消す（`--delete`）
- [ ] ハードリンクをハードリンクのまま保つ（`-H`）
:::why
`-a` は `-rlptgoD` と同じで、再帰（r）、シンボリックリンク（l）、パーミッション（p）、時刻（t）、グループ（g）、所有者（o）、デバイスファイル（D）です。圧縮の `-z`、`--delete`、ハードリンクの `-H`（ACL の `-A`、拡張属性の `-X` も）は入っていないので、必要なら別に指定します（[rsync](#backup-tools)）。
:::
:::

:::q 2.04.2-11 fill
`--delete` を付けた rsync を実行する前に、実際には何も変更せず、何がコピーされ何が消されるかだけを表示させたい。空欄に入るオプションを入力してください。

```text
# rsync -av ____ --delete /srv/www/ /backup/www/
```
= -n
= --dry-run
:::why
`-n`（`--dry-run`）は、実際の変更をせずに、行われるはずの操作を表示します。出力の最後に `(DRY RUN)` と出ます。`-v` と組み合わせて、消されるファイル（`deleting …`）を先に確かめます（[rsync](#backup-tools)）。
:::
:::

:::q 2.04.2-12 single
GNU tar で、スナップショットファイルに前回のバックアップの状態を記録し、次の実行ではそれ以降に変更されたファイルだけをアーカイブする（増分バックアップ）ためのオプションはどれか。
- [ ] `-M`
- [x] `-g`
- [ ] `-p`
- [ ] `-W`
- [ ] `-C`
:::why
`-g ファイル`（`--listed-incremental=ファイル`）が増分バックアップです。スナップショットファイルがなければフル、あれば前回からの変更だけを取ります。`-M` は複数の媒体に分ける、`-p` はパーミッションを保って展開する、`-W` は書いた後に検証する、`-C` はディレクトリを移るオプションです（[tar：増分バックアップは -g](#backup-tools)）。
:::
:::

:::q 2.04.2-13 single
ディスク `/dev/sda` の先頭 512 バイト（MBR）を、ファイル `mbr.bin` にバックアップするコマンドとして正しいものはどれか。
- [x] `dd if=/dev/sda of=mbr.bin bs=512 count=1`
- [ ] `dd if=mbr.bin of=/dev/sda bs=512 count=1`
- [ ] `dd if=/dev/sda of=mbr.bin bs=1 count=1`
- [ ] `dd if=/dev/sda1 of=mbr.bin bs=512 count=1`
- [ ] `dd if=/dev/zero of=/dev/sda bs=512 count=1`
:::why
`if=` が読む元、`of=` が書く先で、写す量は `bs × count` です。512 バイトを 1 回で 512 バイトになります。`if` と `of` が逆のものは、ファイルの内容を**ディスクに書き込む**（リストアの）コマンドです。`bs=1 count=1` は 1 バイトしか写しません。`/dev/sda1` は 1 番目のパーティションで、その先頭は MBR ではありません。`if=/dev/zero of=/dev/sda` は MBR を 0 で消してしまいます（[dd](#backup-tools)）。
:::
:::

:::q 2.04.2-14 multi
オープンソースのバックアップソフトウェアの説明として正しいものを 2 つ選択してください。
- [x] Bareos は、Bacula から分かれて開発されているソフトウェアである
- [ ] Amanda は独自の形式だけを使い、OS 標準の dump や tar は使わない
- [x] BackupPC は、クライアントに専用のソフトウェアを入れず、rsync や SMB などでバックアップを取る
- [ ] Bacula は 1 つのプログラムだけで動き、Director や Storage Daemon といった役割の分かれた部品はない
- [ ] BackupPC は、テープだけにバックアップを保存する
:::why
Bareos は Bacula のフォークで、構成（Director、Storage Daemon、File Daemon）も同じです。BackupPC は、ディスクへ保存し、Web の画面で操作し、クライアントには専用のソフトが要りません。Amanda は中で dump や tar を使うので、Amanda がなくても戻せるのが特徴です。Bacula は Director、Storage Daemon、File Daemon、Catalog に分かれています（[ネットワークバックアップのソフト](#backup-types)）。
:::
:::

:::q 2.04.2-15 single
Bacula の構成要素のうち、バックアップされるクライアントの機械で動き、ファイルを読み出して送る役目を持つものはどれか。
- [ ] Director
- [ ] Storage Daemon
- [x] File Daemon
- [ ] Catalog
- [ ] Console
:::why
File Daemon がクライアント側のプログラムです。Director は全体を指揮してジョブを予定通りに動かし、Storage Daemon はテープやディスクへの読み書きを受け持ち、Catalog は何をどこにバックアップしたかを記録するデータベース、Console は管理者が操作するための窓口です（[ネットワークバックアップのソフト](#backup-types)）。
:::
:::

### 2.04.3 ユーザへの通知

:::q 2.04.3-01 single
来週のメンテナンスの予定を、ログインに成功したユーザーにだけ、ログインの直後に表示したい。メッセージを書くファイルとして最も適切なものはどれか。
- [ ] `/etc/issue`
- [ ] `/etc/issue.net`
- [x] `/etc/motd`
- [ ] `/etc/nologin`
- [ ] `/etc/profile.d/motd`
:::why
`/etc/motd`（message of the day）は、ログインに成功した後に表示されます。`/etc/issue` と `/etc/issue.net` はログインの**前**に表示されるので、認証していない相手にも見えます。`/etc/nologin` は、あると root 以外のログインを拒むファイルです。`/etc/profile.d/motd` という決まったファイルはありません（[ユーザーに知らせる文](#notify)）。
:::
:::

:::q 2.04.3-02 single
`/etc/issue` の内容が次の通りである。ローカルの端末にこのファイルが表示されるとき、`\n` の部分に表示されるものはどれか。

```text
Debian GNU/Linux 12 \n \l
```
- [ ] 改行
- [x] その機械のホスト名
- [ ] カーネルのリリース番号
- [ ] 端末の名前（tty1 など）
- [ ] ログインしているユーザーの数
:::why
`/etc/issue` の中の `\n` は、改行ではなく**ホスト名**（nodename。`uname -n`）に置き換えられます。端末の名前は `\l`、カーネルのリリース番号は `\r`、機械の種類は `\m` です（[/etc/issue と /etc/issue.net](#notify)）。
:::
:::

:::q 2.04.3-03 multi
ユーザーがログインする**前**に表示するメッセージを書くファイルを 2 つ選択してください。
- [x] `/etc/issue`

- [ ] `/etc/motd`

`/etc/issue` はローカルの端末、`/etc/issue.net` はネットワーク越しのログインで、どちらもログインの前に表示するためのファイルです。`/etc/motd` はログインの後です。`/etc/profile` と `~/.bash_login` は、ログインした後にシェルが読む設定ファイルです（[ユーザーに知らせる文](#notify)）。
:::
:::

:::q 2.04.3-04 fill

```text

```
= -k
:::why
`shutdown -k` は、警告のメッセージを送るだけで、停止も再起動もしません。予約した停止を取り消すのは `-c`、メッセージを送らずに止めるのは `--no-wall` です（[wall と shutdown](#notify)）。
:::
:::

:::q 2.04.3-05 single
OpenSSH サーバーで、ユーザーが認証する前に `/etc/issue.net` の内容を表示させたい。正しい設定はどれか。

- [x] `/etc/ssh/sshd_config` に `Banner /etc/issue.net` と書く

sshd は、既定ではログイン前のメッセージを表示しません（`#Banner none`）。`Banner` にファイルを指定すると、認証の前にその内容を表示します。`PrintMotd` は、ログインの**後**に `/etc/motd` を表示するかどうかの設定です。`/etc/motd` へのリンクでは、表示はログインの後になります。`wall` は、すでにログインしているユーザーの端末に送るコマンドです（[/etc/issue と /etc/issue.net](#notify)）。
:::
:::

### 2.04.4 リソース使用状況の把握

:::q 2.04.4-01 single
`vmstat` の出力の `si` と `so` の列が表すものとして正しいものはどれか。
- [ ] システムコールの回数と、シグナルの回数
- [ ] ブロックデバイスから読んだ量と、書いた量
- [x] スワップから読み込んだ量と、スワップへ書き出した量
- [ ] 割り込みの回数と、コンテキストスイッチの回数
- [ ] 実行待ちのプロセスの数と、ブロックされているプロセスの数
:::why
`si`（swap in）と `so`（swap out）は、1 秒あたりにスワップから読み込んだ量と、スワップへ書き出した量です。0 でない状態が続くなら、メモリが足りていません。ブロックデバイスの読み書きは `bi` と `bo`、割り込みとコンテキストスイッチは `in` と `cs`、プロセスの数は `r` と `b` です（[vmstat](#vmstat-sar)）。
:::
:::

:::q 2.04.4-02 single
CPU が 4 つあるサーバーで、応答が遅いときに `vmstat 5` を実行すると、次のような行が続いた。この出力から読み取れることとして最も適切なものはどれか。

```text
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 1  6      0 812344 102400 2048000    0    0  9800 42000 1200 2400  3  4 13 80  0
```
- [ ] CPU を使うプロセスが多すぎて、CPU が足りない
- [ ] 物理メモリが足りず、スワップが多発している
- [x] ディスクなどの I/O を待つ時間が長く、I/O が詰まっている
- [ ] 仮想マシンのホストに CPU 時間を取られている
- [ ] システムに異常はなく、ほとんど何もしていない
:::why
`wa`（I/O 待ち）が 80% で、`b`（ブロックされているプロセス）が 6、`bi` と `bo` も大きいので、原因はディスクの I/O です。CPU が足りないなら `r` が CPU の数（4）を超え、`us` や `sy` が高くなりますが、`r` は 1、`us` と `sy` は合わせて 7% です。スワップは `swpd`、`si`、`so` がすべて 0 なので起きていません。ホストに取られた時間 `st` も 0 です。`id` は 13% しかなく、暇ではありません（[vmstat](#vmstat-sar)）。
:::
:::

:::q 2.04.4-03 single
応答が遅いサーバーで `vmstat 5` を実行すると、次のような行が続いた。原因として最も疑わしいものはどれか。

```text
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 2  3 1843200  61200   1200  24800 4200 6800  4300  6900 1500 3100  8 12 30 50  0
```
- [x] 物理メモリが足りない
- [ ] ネットワークの帯域が足りない
- [ ] CPU の数が足りない
- [ ] ディスクの空き容量が足りない
- [ ] 開けるファイルの数の上限に達した
:::why
`swpd`（使っているスワップ）が大きく、`si` と `so` が続けて大きな値です。メモリが足りず、ページをスワップへ出し入れし続けている状態です。`free`、`buff`、`cache` も小さくなっています。`wa` が高いのは、スワップの読み書きがディスクの I/O だからで、結果であって原因ではありません。vmstat には、ネットワークの帯域、ディスクの空き容量、ファイル数の上限は表示されません（[vmstat](#vmstat-sar)）。
:::
:::

:::q 2.04.4-04 single
`vmstat 2 5` を実行したときの、最初に表示される 1 行の説明として正しいものはどれか。
- [ ] 直前の 2 秒間の平均である
- [x] システムが起動してからの平均である
- [ ] 直前の 1 分間の平均である
- [ ] 過去 24 時間の最大値である
- [ ] コマンドを実行した瞬間の値である
:::why
vmstat の最初の 1 行は、起動してから今までの平均です。2 行目からが、指定した間隔（ここでは 2 秒）ごとの値です。いまの様子を見るときは、1 行目を無視します。`iostat` の最初の報告も、同じく起動してからの平均です（[vmstat](#vmstat-sar)）。
:::
:::

:::q 2.04.4-05 fill

```text

```

:::why
`vmstat 間隔 回数` です。`vmstat 5 3` は、5 秒おきに 3 回表示して終わります。回数を省くと、止めるまで表示し続けます。`iostat`、`sar` も同じ順番（間隔、回数）です（[vmstat](#vmstat-sar)）。
:::
:::

:::q 2.04.4-06 single

`iotop` は、プロセス（スレッド）ごとのディスクの読み書きの量を、多い順に表示します。`iftop` と `iptraf-ng` はネットワークの通信量を見る道具です。`vmstat -d` はディスクごとの統計で、プロセスは分かりません。`free` はメモリの使用量です（[iotop](#net-io)）。
:::

:::q 2.04.4-07 single
sysstat パッケージで、cron や systemd のタイマーから定期的（ふつう 10 分ごと）に呼び出され、`sadc` を使ってその日の記録ファイルに統計を書き足すものはどれか。

- [ ] `iostat`

`sa1` が、定期的に `sadc` を呼んで記録を書き足すスクリプトです。`sa2` は 1 日 1 回、その日のまとめの報告を作ります。`sar` は記録を読んで表示するコマンド、`sadf` は記録を CSV や JSON などで書き出すコマンド、`iostat` は CPU とデバイスの I/O をその場で表示するコマンドです（[sar](#vmstat-sar)）。
:::

:::q 2.04.4-08 multi
`sar` のオプションと、表示される内容の組み合わせとして正しいものを 2 つ選択してください。

:::
:::

:::q 2.04.4-09 single
Red Hat 系のディストリビューションで、sysstat が毎日の記録ファイル（`sa01`、`sa02` …）を保存する既定のディレクトリはどれか。

:::q 2.04.4-10 fill

= -f
:::why
`-f ファイル` で、読む記録のファイルを指定します。省くと、今日の記録ファイルを読みます。`-o ファイル` は逆に、いま集めた統計をファイルに保存するオプションです。時刻の範囲は `-s` と `-e` で絞れます（[sar](#vmstat-sar)）。

:::q 2.04.4-11 single
次は `free -h` の出力である。新しいプログラムを起動するときに実際に使えるメモリの量の目安として、見るべき値はどれか。

```text
Mem:           7.7Gi       3.6Gi       416Mi        16Mi       3.8Gi       4.0Gi
```

### 2.04.5 死活監視、リソース監視、運用監視ツール

:::q 2.04.5-01 single
データベースのプロセス（PID 1234）が OOM Killer に選ばれないようにしたい。root で実行するコマンドとして正しいものはどれか。
- [ ] `echo 1000 > /proc/1234/oom_score_adj`
- [x] `echo -1000 > /proc/1234/oom_score_adj`
- [ ] `echo 0 > /proc/1234/oom_score`
- [ ] `echo 1 > /proc/sys/vm/panic_on_oom`
- [ ] `renice -n -20 -p 1234`
:::why
`oom_score_adj` は -1000 〜 1000 の調整値で、-1000 にするとそのプロセスは OOM Killer の対象から外れます。1000 は逆に、いちばん選ばれやすくします。`oom_score` は読むだけのファイルで、書き込めません。`panic_on_oom` を 1 にすると、プロセスを終わらせる代わりにカーネルパニックになります。`renice` は CPU の優先度で、OOM Killer とは関係ありません（[OOM Killer](#oom)）。
:::
:::

:::q 2.04.5-02 single
夜の間に、あるサービスのプロセスがエラーメッセージも残さずに終了していた。OOM Killer に終了させられたかどうかを確かめる方法として最も適切なものはどれか。
- [x] `dmesg` や `journalctl -k` で `Out of memory` の行を探す
- [ ] `free -h` で、いまの available の値を見る
- [ ] `lastlog` で、最後にログインしたユーザーを調べる
- [ ] `vmstat -s` で、起動してからの統計を見る
- [ ] `/etc/motd` を確認する
:::why
OOM Killer がプロセスを終わらせると、カーネルのログに `Out of memory: Killed process PID (名前)` が残ります。カーネルのログは `dmesg` か `journalctl -k` で読みます。`free` と `vmstat -s` はいまの量や合計を見せるだけで、どのプロセスが終了させられたかは分かりません。`lastlog` はログインの記録、`/etc/motd` はログイン後のお知らせです（[OOM Killer](#oom)）。
:::
:::

:::q 2.04.5-03 single
SNMP マネージャーが、SNMP エージェントに情報を問い合わせる（ポーリングする）ときに、標準で使われるエージェント側のポートはどれか。
- [ ] TCP 161
- [x] UDP 161
- [ ] UDP 162
- [ ] TCP 10050
- [ ] UDP 514
:::why
エージェントは UDP 161 番で問い合わせを待ちます。UDP 162 番は、エージェントからマネージャーへ送るトラップを、マネージャーが受けるポートです。TCP 10050 は Zabbix エージェント、UDP 514 は syslog です（[SNMP](#monitoring)）。
:::
:::

:::q 2.04.5-04 multi
SNMP の説明として正しいものを 2 つ選択してください。
- [x] トラップは、異常などをエージェントのほうからマネージャーへ知らせる仕組みである
- [ ] コミュニティ名は SNMPv3 で初めて導入された、暗号化された認証情報である
- [x] SNMPv3 では、ユーザーごとの認証と通信の暗号化が使える
- [ ] MIB は、マネージャーが集めた値を保存しておく時系列のデータベースである
- [ ] SNMPv2c は、コミュニティ名を暗号化して送る
:::why
トラップはエージェントからの通知で、マネージャーの UDP 162 番へ送られます。認証と暗号化が入ったのは v3 です。コミュニティ名は v1 と v2c で使うパスワード代わりの文字列で、暗号化されずに流れます。MIB は、エージェントが持つ管理情報の木の形の定義で、集めた値をためておく場所ではありません（[SNMP](#monitoring)）。
:::
:::

:::q 2.04.5-05 single
SNMP で、`.1.3.6.1.2.1.1.5.0` のように、点で区切った数字で管理情報の 1 つの項目を指すものを何と呼ぶか。
- [ ] MIB
- [x] OID
- [ ] コミュニティ名
- [ ] トラップ
- [ ] RRD
:::why
OID（Object Identifier）が、項目を指す番号です。MIB は、その項目が木の形に並んだデータベース全体のことです。コミュニティ名は v1 / v2c のパスワード代わりの文字列、トラップはエージェントからの通知、RRD は MRTG や Cacti が使う大きさの決まったデータベースです（[SNMP](#monitoring)）。
:::
:::

:::q 2.04.5-06 fill

```text

```

:::why
`snmpwalk` は、指定した OID の下にある項目を順にたどって全部取ります（v2c 以降では、まとめて取る `snmpbulkwalk` も同じ書き方で使えます）。`snmpget` は、指定した 1 つの項目だけを取ります。`-v 2c` はバージョン、`-c public` はコミュニティ名です（[SNMP](#monitoring)）。

:::q 2.04.5-07 single
Nagios のプラグインを手で実行したところ、次の結果になった。このプラグインが Nagios に報告する状態はどれか。

```text
$ /usr/lib/nagios/plugins/check_disk -w 20% -c 10% -p /data
…
$ echo $?
2
```
- [ ] OK
- [ ] WARNING
- [x] CRITICAL
- [ ] UNKNOWN
- [ ] PENDING
:::why
Nagios のプラグインは、状態を終了ステータスで返します。0 が OK、1 が WARNING、2 が CRITICAL、3 が UNKNOWN です。終了ステータス 2 なので CRITICAL です（ここでは、空きが `-c 10%` のしきい値を下回っています）。PENDING は、まだ 1 回も検査していないときの Nagios の画面上の表示で、プラグインが返す値ではありません（[監視ツール](#monitoring)）。
:::
:::

:::q 2.04.5-08 single
MRTG の説明として最も適切なものはどれか。
- [ ] サーバーにエージェントを入れ、監視、障害の通知、グラフの表示までを 1 つの製品で行う統合監視ソフトウェア
- [x] SNMP でルーターなどの通信量を定期的に集め、グラフの画像と HTML のページを作るツール
- [ ] プラグインの終了ステータスで、ホストやサービスの状態を判定して通知する監視ソフトウェア
- [ ] メモリが足りなくなったときに、プロセスを選んで終了させるカーネルの機能
- [ ] リソースの数値を集めるだけの軽いデーモンで、グラフを描く機能は持たない
:::why
MRTG（Multi Router Traffic Grapher）は、SNMP で集めた通信量をグラフにします。エージェントを使う統合監視は Zabbix、プラグインの終了ステータスで判定するのは Nagios や Icinga2、プロセスを終了させるカーネルの機能は OOM Killer、集めるだけのデーモンは collectd です（[監視ツール](#monitoring)）。
:::
:::

:::q 2.04.5-09 multi
監視ツールの説明として正しいものを 2 つ選択してください。
- [x] Icinga2 では、Nagios のプラグインを利用できる
- [ ] collectd は、集めた数値を Web の画面でグラフにして表示する機能を中心としたソフトウェアである
- [x] Zabbix は、Zabbix サーバー、データベース、Web の画面と、監視される側のエージェントで構成できる
- [ ] Cacti は SNMP を使わず、専用のエージェントだけで数値を集める
- [ ] MRTG を使うには、監視される機器に Zabbix エージェントを入れる必要がある
:::why
Icinga2 は Nagios 由来で、プラグインに互換性があります。Zabbix は、サーバー、データベース、Web の画面、エージェントからなる統合監視です。collectd は数値を集めるデーモンで、グラフの画面は持ちません。Cacti は SNMP で数値を集め、RRDtool でグラフにする Web の画面です。MRTG は機器の SNMP エージェントに問い合わせるので、Zabbix エージェントは関係ありません（[監視ツール](#monitoring)）。
:::
:::

:::q 2.04.5-10 multi
Linux の OOM Killer の説明として正しいものを 2 つ選択してください。
- [x] 既定では、`oom_score` の高いプロセスを選んで SIGKILL で終了させる
- [ ] 既定では、必ずメモリを要求したプロセス自身を終了させる
- [x] 自分のプロセスであっても、`oom_score_adj` を -1000 に設定するには root の権限が要る
- [ ] `/proc/PID/oom_score` に値を書き込んで、点数を直接設定する
- [ ] `oom_score_adj` に指定できる値の範囲は 0 〜 100 である
:::why
OOM Killer は、点数（`oom_score`）の高いプロセスを SIGKILL で終わらせます。メモリを要求したプロセス自身を終わらせるのは、`vm.oom_kill_allocating_task` を 1 にしたときだけです。`oom_score_adj` を 0 より小さくするには root の権限が要ります（大きくすることは一般ユーザーにもできます）。`oom_score` は読むだけで、調整は `oom_score_adj`（-1000 〜 1000）に書きます（[OOM Killer](#oom)）。
:::

### 2.04.6 システム構成ツール

:::q 2.04.6-01 single
Ansible の特徴として正しいものはどれか。
- [ ] 管理対象ノードに専用のエージェントを常駐させ、エージェントが定期的に設定を取りに来る
- [x] 管理対象ノードにエージェントを入れず、コントロールノードから SSH でつないで設定する
- [ ] 手順は、C 言語に似た独自のプログラミング言語で書く
- [ ] 管理対象ノードには、Ansible 本体のインストールが必要である
- [ ] 1 回の実行で設定できる管理対象ノードは 1 台だけである
:::why
Ansible はエージェントレスで、コントロールノードから SSH でつないでモジュールを実行します（プッシュ型）。管理対象ノードに要るのは、SSH でログインできることと Python だけです。手順（Playbook）は YAML で書きます。インベントリに書いた多くのホストを、1 回の実行でまとめて設定できます（[Ansible とは](#ansible)）。
:::
:::

:::q 2.04.6-02 single
構成管理における「冪等性」の説明として正しいものはどれか。
- [ ] 複数のホストに対して、同時に並行して処理を実行できる性質
- [ ] 実行に失敗したとき、自動的に実行前の状態へ戻る性質
- [x] 同じ処理を何回実行しても、結果が同じ状態になる性質
- [ ] 実行する前に、変更の内容を確認できる性質
- [ ] 管理対象のホストにエージェントを必要としない性質
:::why
冪等性は「何回実行しても同じ結果になる」ことです。Ansible のモジュールは「あるべき状態」を書くので、すでにその状態なら何もしません。並行して処理するのは forks、変更の内容を前もって確かめるのはチェックモード（`--check`）、エージェントが要らないのはエージェントレスという別の性質です。Ansible には、失敗したら自動で元に戻す仕組みはありません（[冪等性](#ansible)）。
:::
:::

:::q 2.04.6-03 single

:::

:::q 2.04.6-07 single

:::q 2.04.6-08 single

:::

:::q 2.04.6-09 multi
Ansible の `command` モジュールと `shell` モジュールの説明として正しいものを 2 つ選択してください。
- [x] `command` モジュールはシェルを通さないので、パイプ（`|`）やリダイレクト（`>`）は使えない
- [ ] `shell` モジュールは、管理対象ノードに Python がなくても使える
- [x] どちらも、特に指定しなければ、実行するたびに changed と報告する

:::q 2.04.6-13 single

:::q 2.04.6-17 multi
`ansible-playbook` のオプションの説明として正しいものを 2 つ選択してください。
- [x] `-l`（`--limit`）は、対象を指定したホストやグループに絞る
- [ ] `-t` は、SSH の接続のタイムアウトを秒で指定する
- [x] `-e`（`--extra-vars`）は、変数を渡す
- [ ] `-K` は、SSH の秘密鍵のファイルを指定する
- [ ] `-C` は、使う設定ファイル（ansible.cfg）を指定する
:::why
`-l` は対象を絞り、`-e '変数=値'` は変数を渡します（Playbook の `vars:` より優先されます）。`-t` は `--tags` で、そのタグのタスクだけを実行します。`-K` は `--ask-become-pass` で、権限を上げるとき（sudo）のパスワードをたずねます。`-C` は `--check` です。設定ファイルは、環境変数 `ANSIBLE_CONFIG` などで決まります（[ansible-playbook で実行する](#playbook)）。
:::
:::

:::q 2.04.6-18 single
環境変数 `ANSIBLE_CONFIG` は設定されていない。次の 3 つの設定ファイルがすべて存在するとき、カレントディレクトリで実行した `ansible-playbook` が使う設定として正しいものはどれか。

```text
./ansible.cfg
~/.ansible.cfg
/etc/ansible/ansible.cfg
```
- [x] `./ansible.cfg` だけを使う
- [ ] `~/.ansible.cfg` だけを使う
- [ ] `/etc/ansible/ansible.cfg` だけを使う
- [ ] 3 つとも読み、同じ項目は `/etc/ansible/ansible.cfg` の値が優先される
- [ ] 3 つとも読み、同じ項目は `./ansible.cfg` の値が優先される
:::why
Ansible は、`ANSIBLE_CONFIG`、`./ansible.cfg`、`~/.ansible.cfg`、`/etc/ansible/ansible.cfg` の順に探し、**最初に見つかった 1 つだけ**を使います。ほかのファイルと合わせて読むことはありません。どれを使っているかは、`ansible --version` の `config file =` で確かめられます（[設定ファイル ansible.cfg](#ansible)）。
:::
:::

:::q 2.04.6-19 multi
Ansible のモジュールの説明として正しいものを 2 つ選択してください。
- [x] `template` モジュールは、Jinja2 のテンプレートの変数を埋めてから、管理対象ノードへ置く
- [ ] `copy` モジュールは、管理対象ノードのファイルを、コントロールノードへ取ってくる
- [x] `setup` モジュールは、管理対象ノードの OS や IP アドレスなどの情報（ファクト）を集める
- [ ] `service` モジュールは、パッケージをインストールする
- [ ] `file` モジュールは、ファイルの中の特定の 1 行を書き換える
:::why
`template` は `.j2` のテンプレートに変数を埋めて配り、`setup` はファクトを集めます。`copy` の向きは、コントロールノードから管理対象ノードへです。`service` はサービスの起動・停止と自動起動の設定で、パッケージは `apt`、`dnf`、`package` で入れます。`file` はファイルやディレクトリの有無・権限・持ち主を決めるモジュールで、中の 1 行を扱うのは `lineinfile` です（[よく使うモジュール](#ansible-adhoc)）。
:::
:::

:::q 2.04.6-20 single
3 台のホストを対象に Playbook を実行したところ、2 番目のタスクが 1 台のホストでだけ failed になった（`ignore_errors` は指定していない）。その後の動作として正しいものはどれか。
- [ ] 3 台すべてで、Playbook の実行がその場で止まる
- [x] 失敗したホストでは残りのタスクを実行せず、ほかの 2 台では残りのタスクを続ける
- [ ] 失敗したホストでも、残りのタスクをそのまま続ける
- [ ] 失敗したホストで、それまでに行った変更を自動的に元に戻す
- [ ] 失敗したタスクを、成功するまで自動的に繰り返す
:::why
タスクが失敗したホストは、そのプレイの対象から外され、残りのタスクは実行されません。成功しているほかのホストは、そのまま続きます。失敗しても続けたいタスクには `ignore_errors: true` を付けます。Ansible は、変更を自動で元に戻したり、自動で繰り返したりはしません（[ansible-playbook で実行する](#playbook)）。
:::
:::
