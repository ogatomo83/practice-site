## 可用性：システムは、なぜ止まるのか {#availability}

**可用性**（アベイラビリティ）は、「使いたいときに使える」度合いです。可用性が高いシステムを**高可用**（HA、High Availability）と呼びます。高可用にするには、まず「止まる理由」を分けて考えます。

| 分け方 | 種類 | 例 |
| --- | --- | --- |
| 予定していたか | **計画停止** | 部品の交換、OS やミドルウェアの更新、法定の電源点検。日時を決めて知らせてから止める |
| | **計画外停止** | 障害による停止と、障害や脆弱性に対応するための**緊急保守** |
| 何が壊れたか | **物理障害** | ディスク、電源、メモリ、NIC、ケーブル、空調、停電、災害 |
| | **論理障害** | ソフトウェアの不具合、設定の間違い、操作の間違い（誤って消した）、データの破損 |

計画停止も、利用者から見れば「使えない時間」です。可用性を高めるには、障害を減らすだけでなく、計画停止を短くする（1 台ずつ順に更新する、など）ことも必要です。

物理障害と論理障害では、効く対策が違います。

- **物理障害**には**冗長化**が効きます。同じ役目の機械を 2 つ以上用意して、1 つが壊れても残りで続けます
- **論理障害**には冗長化が効きません。間違った設定や、誤った削除は、予備の機械にもそのまま伝わるからです。効くのは、**バックアップ**からの復元、変更の前の検証、手順の自動化です

:::warn 試験の注意：冗長化とバックアップは別のもの
RAID 1 やデータベースのレプリケーション（複製）は、物理障害への備えです。「誤って表を消した」は、ミラーの相手にもレプリカにも、すぐに同じように反映されます。論理障害から戻すには、**過去の時点**のデータ、つまりバックアップが必要です。「冗長化してあるからバックアップは要らない」という選択肢は、誤りです。
:::

### SPoF：そこが壊れると全部が止まる場所

**SPoF**（Single Point of Failure、**単一障害点**）は、そこ 1 か所が壊れただけで、システム全体が止まる部品です。Web サーバーを 10 台並べても、手前のロードバランサーが 1 台なら、そのロードバランサーが SPoF です。

冗長化は、SPoF を 1 つずつなくしていく作業です。サーバーだけでなく、電源、ネットワークの機器、回線、ストレージ、DNS、データセンターそのものも、SPoF になります。構成図を見て「1 つしかないもの」を探すのが、試験での見つけ方です。

### 回復性：壊れたあと、元に戻る力

**回復性**（レジリエンス）は、障害が起きたあとに、サービスを続ける、または早く元に戻る力です。壊れないこと（信頼性）だけを追うのではなく、「壊れる前提で、すぐ戻る」ように作ります。

- 自動で切り替わる（**フェイルオーバー**。後の節）
- 壊れた部品を、自動で作り直す（クラウドのオートスケーラー。後の節）
- 一部が壊れても、残りの機能は動く（縮退運転）

## MTBF・MTTR・稼働率を計算する {#mtbf}

```fig layout 1,000 時間の観察。稼働 490 時間 → 修理 10 時間 → 稼働 490 時間 → 修理 10 時間。MTBF は稼働の平均（490 時間）、MTTR は修理の平均（10 時間）、稼働率は 490 ÷ (490 + 10) = 0.98
{
  unit: 14,
  rows: [
    { label: '状態', cells: [{ t: '稼働 490 時間', w: 19, kind: 'accent' }, { t: '修理 10', w: 5, kind: 'heap' }, { t: '稼働 490 時間', w: 19, kind: 'accent' }, { t: '修理 10', w: 5, kind: 'heap' }] },
    { label: '平均', cells: [{ t: 'MTBF = (490 + 490) ÷ 2 = 490', w: 24, kind: 'stack' }, { t: 'MTTR = (10 + 10) ÷ 2 = 10', w: 24, kind: 'plain' }] },
  ],
}
```

可用性を数字で表すために、3 つの指標を使います。

| 指標 | 英語 | 意味 | 良い方向 |
| --- | --- | --- | --- |
| **MTBF** | Mean Time Between Failures（平均故障間隔） | 故障から次の故障まで、**動いていた時間**の平均。稼働時間の合計 ÷ 故障の回数 | 大きいほど良い（壊れにくい = 信頼性） |
| **MTTR** | Mean Time To Repair（平均修復時間） | 1 回の故障で、**直すのにかかった時間**の平均。修理時間の合計 ÷ 故障の回数 | 小さいほど良い（直しやすい = 保守性） |
| **稼働率** | Availability | 全体の時間のうち、動いていた時間の割合 | 大きいほど良い |

稼働率の式は 1 つです。

```text
稼働率 = MTBF ÷ (MTBF + MTTR)
```

分母の「MTBF + MTTR」は「動いていた時間 + 止まっていた時間」、つまり全体の時間です。小さな Linux の `awk` で計算してみます。

```sh run title="稼働率 = MTBF ÷ (MTBF + MTTR)"
# MTBF 490 時間、MTTR 10 時間
awk 'BEGIN { printf "%.4f\n", 490 / (490 + 10) }'
# MTBF 1990 時間、MTTR 10 時間
awk 'BEGIN { printf "%.4f\n", 1990 / (1990 + 10) }'
# MTBF 2000 時間、MTTR 2 時間
awk 'BEGIN { printf "%.4f\n", 2000 / (2000 + 2) }'
```

稼働率を上げる方法は 2 つあります。MTBF を伸ばす（壊れにくい部品を使う）か、MTTR を縮める（早く直す。予備機への自動の切り替えは、MTTR を数秒〜数分に縮める方法です）。

:::warn 試験の注意：MTBF と MTTR を取り違えない
MTBF は「**B**etween **F**ailures」で、動いていた時間です。MTTR は「**T**o **R**epair」で、止まっていた時間です。分母を MTBF だけにする（MTTR ÷ MTBF）、分子を MTTR にする、といった選択肢が並びます。「動いていた時間 ÷ 全体の時間」と覚えてください。
:::

### 稼働率と、1 年に止まってよい時間

稼働率は「99.9%」のように 9 を並べて言います（スリーナイン）。1 年（365 日 = 8,760 時間 = 525,600 分）に止まってよい時間に直すと、感覚がつかめます。

```sh run title="稼働率ごとの、1 年に止まる時間（分）"
echo "0.99 0.999 0.9999 0.99999" | tr ' ' '\n' | awk '{ printf "%s  %8.2f 分\n", $1, 365 * 24 * 60 * (1 - $1) }'
```

| 稼働率 | 呼び方 | 1 年に止まる時間 | 30 日に止まる時間 |
| --- | --- | --- | --- |
| 99% | ツーナイン | 約 87.6 時間（3.65 日） | 7.2 時間 |
| 99.9% | スリーナイン | 約 8.76 時間 | 43.2 分 |
| 99.99% | フォーナイン | 約 52.6 分 | 約 4.3 分 |
| 99.999% | ファイブナイン | 約 5.3 分 | 約 26 秒 |

9 が 1 つ増えると、止まってよい時間は 10 分の 1 になります。

```fig graph 直列は「両方が動いていないと使えない」。並列は「どちらかが動いていれば使える」。稼働率 0.99 の機械 2 台で、直列は 0.9801 に下がり、並列は 0.9999 に上がる
{
  col: 190, row: 84,

    { id: 'a', label: 'A', sub: '0.99', x: 1, y: 0, kind: 'accent' },
    { id: 'b', label: 'B', sub: '0.99', x: 2, y: 0, kind: 'accent' },
    { id: 'r1', label: '0.99 × 0.99', sub: '= 0.9801', x: 3, y: 0, kind: 'stack' },
    { id: 'u2', label: '利用者', x: 0, y: 2, mono: false, kind: 'ext' },

    { id: 'd', label: 'B', sub: '0.99', x: 1.5, y: 2.5, kind: 'accent' },
    { id: 'r2', label: '1 − 0.01 × 0.01', sub: '= 0.9999', x: 3, y: 2, kind: 'stack' },

    { label: '並列（冗長化）', nodes: ['c', 'd'] },
  ],

```

システムは、いくつもの部品でできています。部品の稼働率から全体の稼働率を出す式は、つなぎ方で決まります。

| つなぎ方 | 意味 | 式（稼働率 a と b） |
| --- | --- | --- |
| **直列** | **全部**が動いていないと使えない（Web → AP → DB の流れ） | a × b |
| **並列** | **どれか 1 つ**が動いていれば使える（冗長化） | 1 − (1 − a) × (1 − b) |

並列の式は「両方が同時に止まっている割合」を 1 から引いています。(1 − a) は A が止まっている割合です。

```sh run title="直列と並列"
# 0.99 の機械 2 台。直列と並列
awk 'BEGIN { a = 0.99; printf "直列 %.4f  並列 %.4f\n", a * a, 1 - (1 - a) * (1 - a) }'
# 0.9 の機械。並列で 2 台、3 台
awk 'BEGIN { a = 0.9; printf "2 台 %.3f  3 台 %.3f\n", 1 - (1 - a) ^ 2, 1 - (1 - a) ^ 3 }'
# Web・AP・DB が 1 台ずつ（直列）。どれも 0.99
awk 'BEGIN { printf "%.6f\n", 0.99 * 0.99 * 0.99 }'
```

直列は、つなぐほど稼働率が**下がります**（1 より小さい数を掛けるので）。並列は、並べるほど**上がります**。直列と並列が混ざった構成は、並列の部分を先に 1 つの数にまとめてから、直列の掛け算をします。

:::tip 計算問題の手順
1. 構成図で、並列（冗長）になっている部分を囲む
2. 囲んだ部分ごとに `1 − (1 − a)(1 − b)` を計算する。0.9 が 2 台なら 0.99、0.99 が 2 台なら 0.9999 と、「止まる割合の掛け算」で暗算できる
3. 残りを全部掛ける
:::

## SLA・RPO・RTO：どこまで守るかを、数字で決める {#rpo-rto}

```fig timeline RPO は障害の時点から過去へさかのぼる時間（どの時点のデータまで戻せるか）。RTO は障害の時点から先へ進む時間（いつまでに再開するか）
{
  items: [
    { at: '02:00', label: '最後のバックアップ', sub: 'ここまでのデータは戻せる', kind: 'stack' },
    { at: '', label: '↑ この間のデータは失われる（RPO はこの長さの上限）', sub: 'バックアップが 1 日 1 回なら、最大で 24 時間ぶん' },
    { at: '17:00', label: '障害の発生', sub: 'データが壊れる・サービスが止まる', hl: true },
    { at: '', label: '↓ この間はサービスが止まっている（RTO はこの長さの上限）', sub: '検知、切り替え、復元、確認にかかる時間' },
    { at: '19:00', label: 'サービスの再開', sub: 'バックアップから復元して再開', kind: 'heap' },
  ],
}
```

可用性にはお金がかかります。どこまで守るかは、先に数字で決めます。

| 用語 | 英語 | 意味 |
| --- | --- | --- |
| **SLA** | Service Level Agreement（サービス品質保証） | 事業者と利用者の間の、サービスの水準についての**合意**。「月間の稼働率 99.9% 以上」などと決め、守れなかったときの扱い（料金の返還など）も書く |
| **RPO** | Recovery Point Objective（目標復旧**時点**） | 障害のとき、**どの時点のデータまで戻すか**の目標。失ってよいデータの量を時間で表す |
| **RTO** | Recovery Time Objective（目標復旧**時間**） | 障害から、**どれだけの時間でサービスを再開するか**の目標 |

図の例では、バックアップが 2 時、障害が 17 時なので、15 時間ぶんのデータを失いました。再開は 19 時なので、止まっていたのは 2 時間です。「RPO は 1 時間」と決めたのなら、1 日 1 回のバックアップでは足りません。1 時間ごとのバックアップか、別の機械への連続した複製（レプリケーション）が必要です。

| 目標 | 短くする方法 |
| --- | --- |
| RPO を短く | バックアップの間隔を短くする、差分・増分バックアップ、データベースのレプリケーション（同期なら RPO はほぼ 0） |
| RTO を短く | 予備機を起動したまま待たせる（ホットスタンバイ）、自動のフェイルオーバー、復元の手順の自動化と訓練 |

:::warn 試験の注意：RPO と RTO
RPO の **P** は Point（時点）で、障害から**過去**を見ます。「データをどこまで失ってよいか」です。RTO の **T** は Time（時間）で、障害から**未来**を見ます。「いつまでに再開するか」です。「RPO = 復旧にかかる時間」は誤りです。RPO も RTO も、短くするほど費用が上がります。
:::

SLA の稼働率は、止まった時間から計算します。30 日（43,200 分）の月に 43.2 分を超えて止まると、99.9% を下回ります。SLA に計画停止を含めるかどうかは、合意の中で決めます。


何台かのサーバーを、1 つのシステムとして動かす仕組みを**クラスタ**と呼びます。クラスタの 1 台 1 台を**ノード**と呼びます。目的で 2 種類に分かれます。

| 種類 | 目的 | 動き方 |
| --- | --- | --- |
| **HA クラスタ**（フェイルオーバークラスタ） | 止めない（可用性） | 動いているノード（アクティブ）が壊れたら、待っているノード（スタンバイ）がサービスを**引き継ぐ** |
| **負荷分散クラスタ** | さばく量を増やす（性能）。結果として可用性も上がる | ロードバランサーが、同じ役目のノードに要求を**振り分ける**。壊れたノードは振り分け先から外す |

HA クラスタの用語です。

- **アクティブ / スタンバイ**：1 台が動き、もう 1 台は待つ。待ち方には、起動して同期まで済ませて待つ**ホットスタンバイ**、電源を切って置いておく**コールドスタンバイ**などがある
- **アクティブ / アクティブ**：両方が同時に動く。片方が壊れたら、残りが全部を受け持つ
- **フェイルオーバー**：障害を検知して、サービスを予備のノードに**自動で**切り替えること。元のノードが直ったあとに戻すのが**フェイルバック**
- **仮想 IP アドレス**（VIP）：クライアントが接続する、サービス用のアドレス。動いているノードに付け替えるので、クライアントは切り替わりを意識しない
- **ハートビート**：ノードどうしが定期的に送り合う、「生きている」という合図。途切れたら相手の障害と判断する

### Pacemaker と Corosync の役割

Linux の HA クラスタは、2 つのソフトウェアの組み合わせで作るのが標準です。

| ソフトウェア | 層 | 役目 |
| --- | --- | --- |
| **Corosync** | クラスタの通信（メッセージング）層 | ノードどうしの通信、**メンバーシップ**（だれが生きているか）の管理、**クォーラム**（定足数）の計算 |
| **Pacemaker** | クラスタの**リソース管理**（CRM） | リソース（仮想 IP、ファイルシステム、サービス）の起動・停止・監視。障害のときに、どのノードで動かすかを決めて切り替える |

Corosync が「node1 から返事がない」と知らせ、Pacemaker が「では、node2 で仮想 IP と Web サーバーを起動する」と決めて実行します。Pacemaker だけ、Corosync だけでは HA クラスタになりません。

Pacemaker が動かす対象を**リソース**と呼びます。リソースの起動・停止・監視の方法は、**リソースエージェント**（RA）というスクリプトに書いてあります。`ocf:heartbeat:IPaddr2`（仮想 IP を付ける）、`ocf:heartbeat:apache`、`ocf:heartbeat:Filesystem`、`ocf:heartbeat:pgsql` などが用意されています。名前は「規格:提供元:種類」の形です。

### スプリットブレイン、STONITH、クォーラム

ノードの間の通信だけが切れると、どちらのノードも「相手が死んだ」と判断します。両方がアクティブになって、同じ共有ディスクに書き込むと、データが壊れます。これが**スプリットブレイン**です。防ぐ仕組みが 2 つあります。

- **STONITH**（Shoot The Other Node In The Head）：応答しないノードを、電源の制御装置などを使って**強制的に止めて**から、リソースを引き継ぐ。一般的な呼び方は**フェンシング**
- **クォーラム**（定足数）：ノードの票の**過半数**を持つ側だけが、リソースを動かせる。過半数に届かない側は、リソースを止める。3 台なら 2 票、5 台なら 3 票が必要。2 台では片方が止まると過半数（2 票）に届かないので、corosync.conf に `two_node: 1` を書いて、1 票で成立させる

### 設定ファイルと管理コマンド

Corosync の設定は **`/etc/corosync/corosync.conf`** です。Docker の debian:12 に入れたときの形（コメントを除いた要点）です。

```text
totem {
	version: 2
	cluster_name: debian
	crypto_cipher: none
	crypto_hash: none
}

logging {
	to_logfile: yes
	logfile: /var/log/corosync/corosync.log
	to_syslog: yes
}

quorum {
	provider: corosync_votequorum
}

nodelist {
	node {
		name: node1
		nodeid: 1
		ring0_addr: 127.0.0.1
	}
}
```

| セクション | 書くこと |
| --- | --- |
| `totem { }` | クラスタの通信の設定。`cluster_name`（クラスタの名前）、暗号化 |
| `logging { }` | ログの出し先 |
| `quorum { }` | クォーラムの方式。`provider: corosync_votequorum`、2 台のときは `two_node: 1` |
| `nodelist { }` | 参加するノード。`node { }` ごとに `name`、`nodeid`、`ring0_addr`（通信に使うアドレス） |

Pacemaker の設定（リソース、制約、クラスタの性質）は、**CIB**（Cluster Information Base）という XML にまとめられ、全ノードで同じ内容に保たれます。CIB のファイルを手で書き換えてはいけません。次のコマンドで変えます。

| コマンド | 何をするか |
| --- | --- |
| **`crm_mon`** | クラスタの状態（ノード、リソース）を表示する。既定では画面を更新し続ける。`-1`（`--one-shot`）は 1 回だけ表示して終わる。`-r` は止まっているリソースも、`-f` は失敗の回数も表示する |
| **`pcs`** | Pacemaker と Corosync をまとめて設定する道具（Red Hat 系の標準）。`pcs status`、`pcs cluster setup`、`pcs cluster start --all`、`pcs resource create`、`pcs constraint`、`pcs property set`、`pcs node standby` |
| **`crm`** | crmsh。pcs と同じ役目の、もう 1 つの道具（SUSE 系の標準）。`crm status`、`crm configure show` |
| `crm_resource` | リソースの操作。`--move`（別のノードへ移す）、`--cleanup`（失敗の記録を消す） |
| `crm_verify` | 設定の検査。`crm_verify -L -V` は、動いているクラスタの設定を詳しく検査する |
| `cibadmin` | CIB を直接読む・変える。`cibadmin -Q` は CIB の XML を表示する |
| `corosync-cfgtool -s` | Corosync の通信（リンク）の状態を表示する |
| `corosync-quorumtool -s` | クォーラムの状態（票の数、成立しているか）を表示する |

Red Hat 系では、pcs、pacemaker、corosync は「High Availability」のリポジトリにあります（rockylinux:9 では `highavailability` という名前で、既定では無効です）。systemd のユニットは `corosync.service`、`pacemaker.service`、`pcsd.service` です。

Docker の debian:12 で、1 ノードのクラスタを実際に起動し、仮想 IP のリソースを作ったときの出力です。

```console
# pcs property set stonith-enabled=false
# pcs resource create vip ocf:heartbeat:IPaddr2 ip=192.168.100.10 cidr_netmask=24 nic=eth0 op monitor interval=10s
# pcs resource create dummy ocf:pacemaker:Dummy op monitor interval=10s
# pcs resource group add web vip dummy
# crm_mon -1
Cluster Summary:
  * Stack: corosync
  * Current DC: node1 (version 2.1.5-a3f44794f94) - partition with quorum
  * Last updated: Mon Nov 16 21:21:40 2026
  * Last change:  Mon Nov 16 21:21:32 2026 by root via cibadmin on node1
  * 1 node configured
  * 2 resource instances configured

Node List:
  * Online: [ node1 ]

Full List of Resources:
  * Resource Group: web:
    * vip	(ocf:heartbeat:IPaddr2):	 Started node1
    * dummy	(ocf:pacemaker:Dummy):	 Started node1
```

読み方です。

- `Stack: corosync`：通信の層に Corosync を使っている
- `Current DC: node1`：**DC**（Designated Controller）は、クラスタ全体の判断をまとめる役のノード。Pacemaker が自動で 1 台を選ぶ
- `partition with quorum`：このノードのいる側は、クォーラム（過半数）を持っている。`partition WITHOUT quorum` なら、持っていない
- `Online: [ node1 ]`：クラスタに参加して、リソースを動かせるノード
- `Started node1`：そのリソースが node1 で動いている

`pcs resource create` の書式は「リソースの名前、エージェント、パラメータ（`名前=値`）、`op` に続けて操作の設定」です。`op monitor interval=10s` は、10 秒ごとにリソースの状態を確かめる指定です。作ったあと、`ip addr` で見ると、eth0 に 192.168.100.10/24 が付いていました。

ノードを保守するときは、**スタンバイ**にします。スタンバイのノードはクラスタに参加したままですが、リソースを動かしません（動いていたリソースは、ほかのノードに移ります）。

```console
# pcs node standby node1
# crm_mon -1
（前半は省略）
Node List:
  * Node node1: standby

Active Resources:
  * No active resources
# pcs node unstandby node1
```

この例は 1 ノードなので移る先がなく、リソースは止まりました。2 ノードなら、node2 で `Started` になります。

リソースの関係は、3 種類の**制約**（constraint）で決めます。

| 制約 | 決めること | pcs での書き方 |
| --- | --- | --- |
| **location**（場所） | どのノードで動かしたいか | `pcs constraint location web prefers node1=100` |
| **order**（順序） | 起動の順番 | `pcs constraint order vip then httpd` |
| **colocation**（同居） | 同じノードで動かす | `pcs constraint colocation add httpd with vip INFINITY` |

リソースを**グループ**にまとめると（`pcs resource group add`）、グループの中のリソースは同じノードで、並べた順に起動します。仮想 IP とサービスは、グループにするのが普通です。

:::warn 試験の注意：STONITH がないと、リソースは起動しない
Pacemaker は、既定で STONITH が有効（`stonith-enabled=true`）です。STONITH の装置を 1 つも設定していないと、リソースは起動しません。Docker で `crm_verify -L -V` を実行すると、`error: Resource start-up disabled since no STONITH resources have been defined` と表示されました。検証用の環境では `pcs property set stonith-enabled=false` で無効にできますが、共有するデータがある本番のクラスタでは、STONITH を設定します。
:::

:::note pcs と crm の対応
同じ設定を、crmsh では `crm configure show` で次のように表示します（Docker で確かめた出力の一部）。`primitive` が 1 つのリソース、`group` がグループ、`property` がクラスタの性質です。

```text
primitive vip IPaddr2 \
	params cidr_netmask=24 ip=192.168.100.10 nic=eth0 \
	op monitor interval=10s
group web vip dummy
property cib-bootstrap-options: \
	cluster-infrastructure=corosync \
	stonith-enabled=false
```
:::

### 置く場所を分ける：物理的・地理的な分散

冗長化した 2 台を、同じ電源タップにつないでいたら、電源タップが SPoF です。**どの範囲の障害まで耐えたいか**で、予備を置く場所が決まります。

| 分ける範囲 | 耐えられる障害 | 耐えられない障害 | 気をつけること |
| --- | --- | --- | --- |
| 同じラックの中の 2 台 | サーバー 1 台の故障 | ラックの電源・スイッチの故障 | — |
| 別のラック、別の電源系統 | ラック単位の故障 | 建物の停電、火災、空調の故障 | — |
| 同じ地域の別のデータセンター（クラウドの**アベイラビリティゾーン**） | データセンター 1 つの障害 | 地域全体の災害（大地震など） | 距離が近いので遅延が小さく、同期の複製ができる |
| 遠く離れた地域（クラウドの**リージョン**） | **広域の災害** | — | 遅延が大きいので、複製は**非同期**になることが多い（RPO が 0 にならない）。費用も高い |

遠くの拠点に予備のシステムを用意して、災害のときに切り替える備えを**ディザスタリカバリ**（DR、災害復旧）と呼びます。距離を離すほど大きな災害に耐えられますが、通信の遅延と費用が増えます。

## キャパシティプランニング：足りなくなる前に、測って見積もる {#capacity}

**キャパシティプランニング**は、「これからの利用の増え方に対して、資源（CPU、メモリ、ディスク、ネットワーク）がいつ、どれだけ足りなくなるか」を見積もり、先に手を打つことです。進め方は 3 段階です。

1. **測る**：いまの使用量を、続けて記録する（リソース監視）
2. **見積もる**：増え方の傾向（トレンド）と、ピークのときの値から、限界に届く時期を予想する
3. **備える**：届く前に、資源を増やす（次の節のスケールアップ・スケールアウト）

「いま遅い」を直すのは障害対応で、キャパシティプランニングは「**これから**足りなくなる」に備えるものです。そのために、ある瞬間の値ではなく、**長い期間の記録**が必要です。

### 何を測るか

小さな Linux で、4 つの資源のいまの値を見ます（[図解 Linux 14.8](../../linux/site/ch14.html#loadavg)、[13.7](../../linux/site/ch13.html#free)）。

```sh run title="CPU、メモリ、ディスクのいまの値"
uptime
nproc
free -m
df -h /
```

| 資源 | 見る値 | 道具 |
| --- | --- | --- |
| CPU | 使用率（us、sy、id、wa）、ロードアベレージ、実行待ちの数 | `top`、`uptime`、`vmstat`、`sar -u`、`sar -q` |
| メモリ | 空き（available）、スワップの出入り（si、so） | `free`、`vmstat`、`sar -r` |
| ディスク | 使用率（容量）、I/O の量と待ち | `df`、`iostat`、`sar -d` |
| ネットワーク | 送受信の量、接続の数 | `sar -n DEV`、`ss` |

ロードアベレージは、CPU の数（`nproc`）と比べて読みます。CPU が 4 つの機械でロードアベレージが 4 なら、CPU はちょうど埋まっています。

`vmstat` は、1 行で CPU・メモリ・I/O をまとめて見られます。Docker の debian:12 での出力です（`vmstat 1 2` の 2 行目）。

```console
$ vmstat 1 2
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
12  0   4120 337956 334712 4018764    0    0 27684 289872 41452 60505 17  7 69  6  0
```

| 列 | 意味 | 足りないときの見え方 |
| --- | --- | --- |
| `r` | 実行できる（CPU を待っている・使っている）プロセスの数 | CPU の数よりずっと大きい → CPU が足りない |
| `b` | I/O などを待って止まっているプロセスの数 | 大きい → ディスクが遅い |
| `si` / `so` | スワップから読んだ量 / スワップへ書いた量（毎秒） | 0 でない値が続く → メモリが足りない |
| `bi` / `bo` | ブロックデバイスから読んだ / 書いた量 | — |
| `us` / `sy` / `id` / `wa` | CPU 時間の割合：ユーザー / カーネル / 何もしていない / **I/O 待ち** | `id` が 0 に近い → CPU が足りない。`wa` が大きい → ディスクが遅い |

長い期間の記録には、**`sar`**（sysstat パッケージ）が使えます。sysstat は一定の間隔（Debian 系の既定では 10 分ごと）で値をファイルに貯めるので、あとから「先月の同じ曜日」と比べられます。何台ものサーバーをまとめてグラフにするには、Zabbix、Cacti、MRTG、collectd などの監視ツールを使います（第 4 章で扱います）。

### 見積もる：あと何台、いつまでに

見積もりは、平均ではなく**ピーク**で行います。また、限界ぎりぎりではなく**余裕**を残します（1 台が壊れても、残りでさばけるように）。

例：ピークのとき、毎秒 1,200 件の要求が来ます。Web サーバー 1 台は毎秒 300 件までさばけますが、使用率 70% までで使いたいとします。

```sh run title="必要な台数を見積もる"
# 1 台が安全にさばける量 = 300 × 0.7 = 210 件 / 秒
awk 'BEGIN { x = 1200 / (300 * 0.7); n = int(x); if (n < x) n++; print x, "→", n, "台" }'
```

5.71 台なので、切り上げて 6 台です。端数は必ず**切り上げ**ます（5 台では足りません）。

:::note 増え方も見る
ディスクの使用量が、毎月 20 GB ずつ増えているとします。空きが 100 GB なら、あと 5 か月で一杯です。機材の手配に 2 か月かかるなら、3 か月後には注文していなければなりません。「いまの値」と「増える速さ」の両方を記録して、はじめて時期が見積もれます。
:::

**スケーラビリティ**（拡張性）は、利用が増えたときに、資源を足して対応できる性質です。足し方は 2 通りで、それぞれ逆向きの言葉があります。

| 言葉 | すること | 別の呼び方 |
| --- | --- | --- |
| **スケールアップ** | 1 台の性能を**上げる**（CPU、メモリを増やす、上位の機種にする） | 垂直スケール |
| **スケールダウン** | 1 台の性能を**下げる** | |
| **スケールアウト** | サーバーの**台数を増やす** | 水平スケール |
| **スケールイン** | サーバーの**台数を減らす** | |

| | スケールアップ | スケールアウト |
| --- | --- | --- |
| アプリケーションの変更 | 要らない | 分散できる作り（ステートレス）が要る |
| 上限 | 買える最大の機種まで。上位の機種ほど割高 | 台数を足せるかぎり |
| 作業のときの停止 | ふつうは止める（再起動） | 止めずに足せる |
| 可用性 | 上がらない（1 台のまま。SPoF が残る） | 上がる（1 台が壊れても残りで続く） |
| 向いているもの | データベースなど、分けにくいもの | Web サーバー、AP サーバーなど、同じものを並べられるもの |

### ステートレスな設計：どのサーバーが受けても同じ

スケールアウトの条件は、サーバーが**状態**（ステート）を自分の中に持たないことです。状態とは、要求をまたいで覚えておくデータです。ログインしているか、買い物かごの中身（**セッション**）、アップロードされたファイルなどです。

Web サーバー 1 が自分のメモリやディスクにセッションを持っていると、次の要求が Web サーバー 2 に振り分けられたとき、「ログインしていません」になります。Web サーバー 1 が壊れると、そのセッションは消えます。台数を減らす（スケールイン）こともできません。

**ステートレス**な設計では、状態をサーバーの外に出します。

| 状態 | 外に出す先 |
| --- | --- |
| セッション | 全サーバーが共有する保存先（Redis や memcached などのキャッシュサーバー、データベース）。または、署名した Cookie やトークンとしてクライアントに持たせる |
| 業務のデータ | データベース |
| アップロードされたファイル | オブジェクトストレージ、共有ファイルシステム（NFS） |
| ログ | ログの集約サーバーへ送る |

こうしておけば、Web サーバーはどれも同じで、いつ足しても、いつ捨ててもかまいません。データベースは状態そのものなので、ステートレスにはできません。データベースは、スケールアップ、レプリケーション（後の節）で対応します。

:::note スティッキーセッション
ロードバランサーが、同じクライアントを毎回**同じサーバー**に振り分ける機能を、スティッキーセッション（セッションの維持、パーシステンス）と呼びます。アプリケーションを変えずにセッションを保てますが、そのサーバーが壊れればセッションは消え、負荷も偏ります。ステートレスにできるまでの、次善の方法です。
:::

### 構成管理ツールと VM イメージ：同じサーバーを、すぐに作る

スケールアウトでは、**同じ設定のサーバーを、速く、間違いなく**作れなければなりません。手で 1 台ずつ設定していては、間に合わず、設定もずれます。方法は 2 つで、組み合わせて使います。

| 方法 | すること | 特徴 |
| --- | --- | --- |
| **構成管理ツール**（Ansible、Puppet、Chef） | 「あるべき状態」をコード（Ansible なら Playbook）に書き、サーバーに適用する | 何度実行しても同じ状態になる（**冪等性**）。設定の変更を全台にそろえて配れる。起動してから適用するので、少し時間がかかる |
| **VM イメージ**（マシンイメージ、テンプレート、ゴールデンイメージ） | OS、ミドルウェア、アプリケーションを入れ終えたディスクを**イメージ**として保存し、そこからサーバーを起動する | 起動するだけで使えるので速い。オートスケーラー（後の節）が使う。内容を変えるには、イメージを作り直す |

よくある組み合わせは、「構成管理ツールでイメージを作り、そのイメージから台数を増やす」です。Ansible は第 4 章で扱います。

## ロードバランサーと DNS ラウンドロビン {#lb}

台数を増やしたら、要求を振り分ける仕組みが要ります。方法は 2 つあります。

### ロードバランサー

**ロードバランサー**（負荷分散装置、LB）は、クライアントからの要求を受けて、後ろに並んだサーバーのどれかに渡します。クライアントが接続する先は、ロードバランサーの 1 つのアドレスです。

役目は 3 つあります。

- **振り分け**：決めた方式で、サーバーを選ぶ
- **ヘルスチェック**：サーバーに定期的に接続して、応答しないサーバーを**自動で**振り分け先から外す。直ったら戻す
- **TLS の終端**、セッションの維持（スティッキーセッション）など

| 振り分けの方式 | 選び方 | HAProxy | nginx（upstream の中） |
| --- | --- | --- | --- |
| ラウンドロビン | 順番に 1 つずつ | `balance roundrobin` | 既定（何も書かない） |
| 最少接続 | いま接続がいちばん少ないサーバー | `balance leastconn` | `least_conn;` |
| 送信元 IP のハッシュ | 同じクライアントの IP アドレスは、同じサーバー | `balance source` | `ip_hash;` |
| 重み付け | 性能の高いサーバーに多く | `server … weight 2` | `server … weight=2;` |

ソフトウェアのロードバランサーには、HAProxy、nginx、LVS（Linux Virtual Server。カーネルの IPVS）があります。HAProxy の設定の例です（Docker の debian:12 で `haproxy -c -f` を通して確かめた形）。

```text
frontend web
    bind *:80
    default_backend app

backend app
    balance roundrobin
    option httpchk GET /health
    server web1 192.168.10.11:80 check
    server web2 192.168.10.12:80 check
    server web3 192.168.10.13:80 check backup
```

- `frontend` はクライアントから受ける側、`backend` は振り分け先のサーバーの集まり
- `balance` が振り分けの方式
- `server` の行の **`check`** が、そのサーバーへのヘルスチェックを有効にする。`option httpchk` は、HTTP の要求で確かめる指定
- **`backup`** の付いたサーバーは、ほかのサーバーが全部使えなくなったときだけ使われる予備

nginx では、`upstream` にサーバーを並べ、`proxy_pass` でそこへ渡します（`nginx -t` で確かめた形）。

```text
upstream app {
    least_conn;
    server 192.168.10.11:80 weight=2;
    server 192.168.10.12:80;
    server 192.168.10.13:80 backup;
}
server {
    listen 8080;
    location / { proxy_pass http://app; }
}
```

:::warn 試験の注意：ロードバランサーが SPoF になる
ロードバランサーは、すべての要求が通る場所です。1 台しかなければ、そこが SPoF です。ロードバランサーも 2 台にして、仮想 IP をアクティブ / スタンバイで持たせます（Pacemaker や、VRRP を使う keepalived）。クラウドのロードバランサーのサービスは、事業者の側で冗長化されています。
:::

### DNS ラウンドロビン

**DNS ラウンドロビン**は、1 つの名前に A レコードを何個も登録して、クライアントを分散させる方法です。DNS サーバーは、問い合わせのたびに、アドレスの**並び順を変えて**答えます。多くのクライアントは先頭のアドレスに接続するので、結果として分散します。

Docker の debian:12 で BIND に次のゾーンを読ませ、`dig` で 3 回問い合わせた結果です。

```text
www IN A 192.0.2.11
www IN A 192.0.2.12
www IN A 192.0.2.13
```

```console
$ dig @127.0.0.1 www.example.com A +short
192.0.2.13
192.0.2.11
192.0.2.12
$ dig @127.0.0.1 www.example.com A +short
192.0.2.13
192.0.2.12
192.0.2.11
$ dig @127.0.0.1 www.example.com A +short
192.0.2.12
192.0.2.11
192.0.2.13
```

毎回 3 つとも返り、順番だけが変わります（`dig` は [図解 LinuC 7.12](../../linuc/site/ch07.html#dig)）。特別な機器が要らず、DNS のレコードを足すだけでできるのが利点です。欠点は、DNS がサーバーの状態を知らないことから来ます。

| | ロードバランサー | DNS ラウンドロビン |
| --- | --- | --- |
| 必要なもの | ロードバランサー（機器、ソフトウェア、クラウドのサービス） | DNS の A レコードを足すだけ |
| 壊れたサーバー | ヘルスチェックで**自動で外す** | **外さない**。壊れたサーバーのアドレスも答え続ける |
| 負荷に応じた振り分け | できる（最少接続、重み付け） | できない（順番に答えるだけ。負荷を見ない） |
| 変更が効くまで | すぐ | キャッシュされるので、TTL が切れるまで古い答えが使われる |
| セッションの維持 | できる | できない |
| それ自身の冗長化 | 別に必要（SPoF になりうる） | DNS サーバーはもともと複数台 |

:::warn 試験の注意：DNS ラウンドロビンは、障害を検知しない
DNS ラウンドロビンだけでは、サーバーが 1 台壊れると、その台に当たったクライアントは接続できません。レコードを手で消しても、キャッシュの TTL が切れるまで、古い答えが残ります。「負荷の少ないサーバーを選んで答える」「壊れたサーバーを自動で外す」は、DNS ラウンドロビンの説明としては誤りです。
:::

クラウド（IaaS）では、仮想マシンを**インスタンス**と呼びます。インスタンスは、数分で作れて、いつでも捨てられます。その代わり、「インスタンスと一緒に消えるもの」と「残るもの」を、はっきり分けて使います（[図解 LinuC 10.12](../../linuc/site/ch10.html#cloud-network) の復習を含みます）。用語は OpenStack のものが出題範囲に使われています。

### エフェメラルストレージと永続ストレージ

| | **エフェメラルストレージ**（揮発性、一時的） | **永続ストレージ**（ブロックストレージのボリューム） |
| --- | --- | --- |
| 寿命 | **インスタンスと同じ**。インスタンスを削除すると消える（クラウドによっては、停止や、物理サーバーの故障でも消える） | インスタンスと**独立**。インスタンスを削除しても残る |
| 付け替え | できない | 切り離して、別のインスタンスに付けられる |
| 置くもの | 一時ファイル、キャッシュ、作り直せるデータ、スケールアウトで増やす Web サーバーの OS の領域 | データベースのデータ、消えては困るファイル |
| 例 | OpenStack のエフェメラルディスク、AWS のインスタンスストア | OpenStack Cinder のボリューム、AWS の EBS |

「エフェメラル」（ephemeral）は「つかの間の」という意味です。OS の再起動（reboot）では消えませんが、インスタンスそのものを消せば、中身は戻りません。永続ボリュームも、障害や誤操作には備えが要ります。スナップショットやバックアップを別に取ります。

### 固定 IP アドレスとフローティング IP アドレス

| | **固定 IP アドレス** | **フローティング IP アドレス** |
| --- | --- | --- |
| 何か | インスタンスを作ったときに、テナントネットワークから割り当てられるアドレス | 外部のネットワーク（インターネット側）のアドレス。利用者が確保して、インスタンスに**関連付ける** |
| 種類 | ふつうはプライベートアドレス | グローバルアドレス（外から届く） |
| 寿命 | インスタンスが存在する間、変わらない。インスタンスを削除すると手放す | インスタンスと独立。**外して、別のインスタンスに付け替えられる** |
| 使い道 | テナントの中のインスタンスどうしの通信 | 外部への公開。障害のときに、予備のインスタンスへ付け替える |

フローティング IP の「フローティング」は、「インスタンスの間を移せる」という意味です。Web サーバーのインスタンスを作り直しても、同じフローティング IP を新しいインスタンスに関連付ければ、利用者が接続する先は変わりません。HA クラスタの仮想 IP と同じ役目を、クラウドの機能で実現するものです。

多くのクラウドでは、フローティング IP はインスタンスの OS には設定されません。仮想ルーターが、フローティング IP 宛ての通信を、固定 IP に変換（NAT）して届けます。

:::warn 試験の注意：「固定」という名前に引っかからない
「固定 IP アドレス」は「インスタンスに固定されている」という意味で、インスタンスを消せば一緒になくなります。**インスタンスを作り直しても同じアドレスを使い続けられる**のは、フローティング IP のほうです。
:::

### テナントネットワークとセキュリティグループ

クラウドは、多くの利用者が同じ設備を共有します。利用者（契約、プロジェクト）の単位を**テナント**と呼びます。

**テナントネットワーク**は、テナントが自分で作る、**ほかのテナントから切り離された**仮想のネットワークです。アドレスの範囲（プライベートアドレス）も自分で決められ、ほかのテナントと同じ範囲を使っても、ぶつかりません。外部と通信するには、仮想ルーターで外部のネットワークにつなぎます。

**セキュリティグループ**は、インスタンス（の仮想 NIC）に付ける、クラウドの側の**ファイアウォール**です。

- **許可する**通信の規則を並べる。どの規則にも合わない受信は、**拒否**される
- 規則は「方向（受信 / 送信）、プロトコル、ポート、相手（CIDR、または別のセキュリティグループ）」
- **ステートフル**：許可した通信への**戻り**のパケットは、規則を書かなくても通る
- 相手に「別のセキュリティグループ」を書ける。「db のグループは、web のグループからの 5432 番だけを許す」と書けば、Web サーバーが何台に増えても、規則を変えなくてよい
- インスタンスの外で働くので、OS の中のファイアウォール（iptables、firewalld）とは**別のもの**。両方を通った通信だけが届く

| 方向 | プロトコル | ポート | 相手 | 意味 |
| --- | --- | --- | --- | --- |
| 受信 | TCP | 443 | 0.0.0.0/0 | HTTPS を、どこからでも許す |
| 受信 | TCP | 22 | 203.0.113.0/24 | SSH を、管理用のネットワークからだけ許す |
| 受信 | TCP | 5432 | セキュリティグループ web | PostgreSQL を、web のグループのインスタンスからだけ許す |

## オブジェクトストレージ、メッセージキュー、オートスケーラー {#cloud-services}

クラウドには、サーバーを立てなくても使える部品（マネージドサービス）があります。出題範囲にあるのは 3 つです。

### オブジェクトストレージ

**オブジェクトストレージ**は、データを「**オブジェクト**」（ファイルの中身 + メタデータ）の単位で、**HTTP の API**（REST）を使って出し入れするストレージです。オブジェクトは、**バケット**（コンテナ）という入れ物の中に、**キー**（名前）を付けて置きます。

| | ブロックストレージ（ボリューム） | オブジェクトストレージ |
| --- | --- | --- |
| 見え方 | ディスク（ブロックデバイス）。ファイルシステムを作ってマウントする | HTTP の URL。`PUT` で置き、`GET` で取り出す |
| 使う相手 | 付けた 1 台のインスタンス | ネットワーク越しに、何台からでも |
| 容量 | 作るときに決める | 決めなくてよい（置いた分だけ） |
| 更新 | 一部だけを書き換えられる | オブジェクト**全体**を置き換える |
| 向いているもの | OS、データベース | 画像・動画などの静的なファイル、バックアップ、ログ、アップロードされたファイル |
| 例 | OpenStack Cinder、AWS EBS | OpenStack Swift、Amazon S3 |

オブジェクトストレージは、事業者の側で複数の場所に複製されるので、耐久性が高く、容量を気にせずに使えます。Web サーバーをステートレスにするときの、ファイルの置き場所として使います。一方、一部だけを頻繁に書き換えるデータ（データベースのデータファイル）には向きません。

### メッセージキュー

**メッセージキュー**は、プログラムの間で受け渡す**メッセージ**を、いったん**貯めておく**仕組みです。送る側（プロデューサー）はキューに入れたら、すぐ次の仕事に進みます。受ける側（コンシューマー、ワーカー）は、自分の都合のよいときにキューから取り出して処理します。

- **非同期**：送る側は、処理が終わるのを待たない
- **疎結合**：送る側と受ける側は、相手の場所や台数を知らなくてよい。受ける側が止まっていても、メッセージはキューに残り、再開したら処理される
- **平準化**：要求が一度に集中しても、キューに貯まるだけで、受ける側は自分の速さで処理できる
- **スケールアウト**：キューが長くなったら、ワーカーを増やす

代表的なソフトウェアは RabbitMQ、Apache Kafka、クラウドのサービスでは Amazon SQS です。使い方は、後の節（[非同期処理](#cache-queue)）で見ます。

### オートスケーラー

**オートスケーラー**（オートスケーリング）は、負荷に合わせて、インスタンスの台数を**自動で**増やしたり（スケールアウト）減らしたり（スケールイン）する仕組みです。

- **条件**：監視の値（CPU 使用率の平均、要求の数、キューの長さ）にしきい値を決める。「CPU 使用率が 70% を超えたら 2 台増やす、30% を下回ったら 1 台減らす」
- **最小と最大**：台数の下限と上限を決める。条件がどうであれ、この範囲を出ない（上限は、費用が際限なく増えるのを防ぐ）
- **VM イメージ**：増やすインスタンスは、あらかじめ用意したイメージから起動する
- **ロードバランサー**：増えたインスタンスは、自動で振り分け先に入る。減らすときは外してから消す
- **自動の修復**：ヘルスチェックに応答しないインスタンスを捨てて、新しく作り直す

オートスケーラーが使えるのは、インスタンスが**ステートレス**なときです。いつ消されるか分からないので、消えては困るデータをエフェメラルストレージに置いてはいけません。

:::tip 4 つの部品は、1 つの考え方でつながる
「インスタンスは、いつでも捨てて作り直せるものにする」が、クラウドの設計の中心です。そのために、データは永続ボリュームかオブジェクトストレージに、セッションは共有の保存先に、アドレスはフローティング IP かロードバランサーに、時間のかかる処理はメッセージキューに出します。こうすると、オートスケーラーが台数を自由に変えられます。
:::

## LAMP・LAPP と、Web 三層 {#three-tier}

ここからは、実際によく使われる構成を、小さいものから順に見ます。

### LAMP と LAPP

Web アプリケーションを動かすソフトウェアの、定番の組み合わせです。頭文字を並べた名前が付いています。

| | L | A | M / P | P |
| --- | --- | --- | --- | --- |
| **LAMP** | **L**inux | **A**pache | **M**ySQL（MariaDB） | **P**HP（Perl、Python） |
| **LAPP** | **L**inux | **A**pache | **P**ostgreSQL | **P**HP（Perl、Python） |

違いは、データベースが MySQL（MariaDB）か PostgreSQL かだけです。どれもオープンソースで、小さなシステムなら、この 4 つを 1 台のサーバーに入れて動かせます。Apache の代わりに nginx を使う組み合わせは、LEMP（nginx を「エンジンエックス」と読むので E）と呼ばれます。

### Web 三層：役目ごとに、サーバーを分ける

1 台に全部を入れた構成は、利用が増えると分けることになります。役目で 3 つの層に分けたものが、**Web 三層**（3 層アーキテクチャ）です。

| 層 | サーバー | 役目 | ソフトウェアの例 |
| --- | --- | --- | --- |
| プレゼンテーション層 | **Web サーバー** | クライアントからの HTTP の要求を受ける。静的なファイル（画像、CSS）を返す。TLS を終端する。動的な処理は AP サーバーに渡す | Apache、nginx |
| アプリケーション層 | **AP サーバー**（アプリケーションサーバー） | 業務の処理（プログラム）を実行する。必要なデータを DB サーバーに問い合わせ、結果のページを作る | Tomcat、PHP-FPM、uWSGI など |
| データ層 | **DB サーバー** | データを保存し、検索する | PostgreSQL、MySQL、MariaDB |

要求は「クライアント → Web → AP → DB」と進み、応答は逆に戻ります。分ける利点は 3 つです。

- **層ごとに増やせる**：重い層だけを、スケールアウト・スケールアップできる
- **守りやすい**：外から届くのは Web サーバーだけにし、DB サーバーは内側のネットワークに置く。クライアントは DB に直接つながない
- **入れ替えやすい**：ある層のソフトウェアを替えても、ほかの層への影響が小さい

ただし、層を分けただけでは、可用性は上がりません。Web・AP・DB が 1 台ずつなら**直列**で、どれが止まっても全体が止まります。どれも稼働率 0.99 なら、全体は 0.99 × 0.99 × 0.99 = 約 0.970（97.0%）に下がります（[直列と並列](#mtbf)）。3 台とも SPoF です。

```fig graph 冗長化した Web 三層。ロードバランサーは 2 台で仮想 IP を持つ。Web / AP サーバーはステートレスにして並べる（スケールアウト）。DB はプライマリからレプリカへ複製し、プライマリが壊れたらレプリカを昇格させる（HA）
}
```

三層の SPoF を、層ごとになくします。層によって、使う方法が違います。

| 層 | 方法 | 理由 |
| --- | --- | --- |
| 入口 | **ロードバランサー**を置き、それ自身も 2 台で HA にする（仮想 IP） | すべての要求が通るので、1 台では SPoF |
| Web / AP サーバー | **スケールアウト**（同じものを並べて、ロードバランサーで振り分ける） | ステートレスにできるので、並べるだけでよい。性能と可用性が同時に上がる |
| DB サーバー | **HA クラスタ**（アクティブ / スタンバイ）と**レプリケーション** | 状態を持つので、ただ並べることはできない。データを複製したうえで、切り替える |

稼働率 0.99 のサーバーで計算すると、Web・AP・DB を 2 台ずつ並列にしたとき、各層は 0.9999、全体は 0.9999 × 0.9999 × 0.9999 = 約 0.9997 です。1 台ずつのときの 0.970 から、大きく上がります。

### DB のレプリケーション

**レプリケーション**は、あるデータベース（**プライマリ**。マスター、ソースとも呼ぶ）への更新を、別のデータベース（**レプリカ**。スタンバイ、スレーブとも呼ぶ）に続けて**複製**する仕組みです。使い道は 2 つあります。

- **可用性**：プライマリが壊れたら、レプリカを**昇格**させてプライマリにする（フェイルオーバー）。Pacemaker などのクラスタソフトウェアが、昇格と仮想 IP の付け替えを自動で行う
- **参照の負荷分散**：検索（SELECT）をレプリカに振り分ける（**リードレプリカ**）。**更新はプライマリだけ**が受ける

| | 同期レプリケーション | 非同期レプリケーション |
| --- | --- | --- |
| 動き | レプリカに届いたのを確かめてから、更新を完了する | レプリカを待たずに、更新を完了する |
| プライマリが壊れたとき | 完了した更新は、レプリカにもある（RPO はほぼ 0） | 直前の更新が、レプリカに**届いていないことがある** |
| 性能 | 更新が遅くなる（レプリカを待つ） | 更新が速い |
| 向いている場所 | 近い場所（同じデータセンター） | 遠い場所（別のリージョン） |

:::warn 試験の注意：レプリケーションでできないこと
- **更新の負荷分散はできない**：レプリカは参照専用です。更新が多すぎるなら、プライマリをスケールアップするか、データを分ける
- **バックアップの代わりにならない**：誤った DELETE も、レプリカにそのまま複製される（論理障害）
- 非同期のレプリカは、**少し古い**データを返すことがある（複製の遅れ）
:::

### ロードバランサーか、DNS ラウンドロビンか

Web サーバーをスケールアウトするとき、振り分けには[ロードバランサーと DNS ラウンドロビン](#lb)のどちらも使えます。違いは前の節の表のとおりです。まとめると、次のように使い分けます。

- 壊れたサーバーを自動で外したい、負荷を見て振り分けたい、セッションを維持したい → **ロードバランサー**
- 機器を足さずに、手軽に分散したい。障害のときの切り離しは別の方法で行う → **DNS ラウンドロビン**
- 両方を組み合わせることもある。離れた拠点のロードバランサー（の仮想 IP）を、DNS で振り分ける

## プロキシキャッシュ、CDN、メッセージキューで軽くする {#cache-queue}

サーバーを増やす以外に、**サーバーの仕事を減らす**方法があります。「同じものを何度も作らない」（キャッシュ）と、「あとでよい仕事は、あとでする」（非同期処理）です。

### プロキシキャッシュと CDN

**キャッシュ**は、一度作った応答を取っておいて、次の同じ要求にはそれを返すことです。

| | **プロキシキャッシュ**（リバースプロキシ） | **CDN**（Content Delivery Network、コンテンツ配信網） |
| --- | --- | --- |
| 置く場所 | 自分の Web サーバーの**手前**（同じデータセンター） | 世界の各地にある、事業者の**エッジサーバー** |
| 動き | Web サーバーの応答を保存し、同じ要求には、Web サーバーに聞かずに返す | 利用者に**近い**エッジサーバーが、保存した内容を返す。なければ元のサーバー（**オリジン**）に取りに行く |
| 効果 | Web / AP サーバーの負荷が減る | オリジンの負荷が減る。距離が近いので応答が速い。アクセスの集中や攻撃を、広い設備で受け止められる |
| ソフトウェア・サービス | nginx（`proxy_cache`）、Squid、Varnish | 各社の CDN サービス |

キャッシュに向くのは、**だれが見ても同じ**で、**あまり変わらない**内容です。画像、CSS、JavaScript、動画などの静的なファイルです。向かないのは、利用者ごとに違う内容（ログインした後の画面、買い物かご）や、更新の要求（POST）です。これらをキャッシュすると、他人の情報が見えてしまう事故になります。

キャッシュには**有効期限**（TTL）があります。オリジンでファイルを更新しても、期限が切れるまでは、キャッシュが**古い内容**を返します。すぐに反映したいときは、キャッシュを消す（パージ）か、ファイル名を変えます。

:::note フォワードプロキシとリバースプロキシ
クライアントの側に置いて、クライアントの代わりに外へ取りに行くのが、**フォワードプロキシ**です（社内から Web を見るときの Squid。第 9 章）。サーバーの側に置いて、サーバーの代わりに要求を受けるのが、**リバースプロキシ**です。ここで言うプロキシキャッシュと、ロードバランサーは、リバースプロキシの仲間です。
:::

### メッセージキューによる非同期処理

```fig seq 注文を受けたら、AP サーバーは「メールを送る」「帳票を作る」という仕事をキューに入れて、すぐに応答を返す。ワーカーが、あとでキューから取り出して処理する
{
  colw: 170,
  actors: [
    { id: 'c', label: 'クライアント' },
    { id: 'ap', label: 'AP サーバー' },
    { id: 'q', label: 'メッセージキュー' },
    { id: 'w', label: 'ワーカー' },
  ],
  msgs: [
    { from: 'c', to: 'ap', label: '注文する' },
    { from: 'ap', to: 'q', label: '「メールを送る」を入れる', style: 'accent' },
    { from: 'ap', to: 'c', label: 'すぐに「受け付けました」' },
    { gap: true },
    { from: 'w', to: 'q', label: '取り出す' },
    { self: 'w', label: 'メールを送る（時間がかかる）' },
    { from: 'w', to: 'q', label: '完了を知らせる（メッセージを消す）', style: 'dashed' },
  ],
}
```

時間のかかる処理を、要求の中で全部済ませようとすると（**同期処理**）、利用者は待たされ、その間 AP サーバーの処理の枠がふさがります。**非同期処理**では、AP サーバーは仕事の内容をメッセージとしてキューに入れ、すぐに応答を返します。実際の処理は、別のプログラム（ワーカー）があとで行います。

| | 同期処理 | メッセージキューを使った非同期処理 |
| --- | --- | --- |
| 利用者への応答 | 処理が全部終わってから | 受け付けた時点で、すぐ |
| 処理の結果 | 応答に含められる | 応答には含められない（あとで通知する、利用者が見に行く） |
| 処理する側が止まっているとき | 要求がエラーになる | メッセージはキューに残り、**再開したあとに処理される** |
| 要求が集中したとき | サーバーがあふれる | キューに貯まり、ワーカーは自分の速さで処理する（平準化） |
| 増やし方 | AP サーバーを増やす | ワーカーだけを増やせる |

向いているのは、**結果をその場で返さなくてよい**仕事です。メールの送信、画像や動画の変換、帳票の作成、集計、ほかのシステムへの連携などです。向かないのは、結果がないと次の画面を出せない処理（ログインの認証、残高の照会）です。

ワーカーが処理の途中で止まると、メッセージはキューに戻り、もう一度配られます。そのため、同じメッセージを 2 回処理しても困らないように作ります（冪等にする）。

:::deep 全部を合わせた構成
大きな Web サービスの典型的な構成は、ここまでの部品を全部つないだものです。利用者 → CDN（静的なファイル）→ ロードバランサー（2 台、HA）→ Web / AP サーバー（ステートレス、オートスケーラーで増減）→ セッション用のキャッシュサーバー、DB（プライマリ + レプリカ、HA）、オブジェクトストレージ（ファイル）、メッセージキュー → ワーカー。試験では、この中の 1 か所を取り出して、「この部品の役目は」「ここがないと何が困るか」「SPoF はどこか」と問われます。
:::

:::key まとめ
- **稼働率 = MTBF ÷ (MTBF + MTTR)**。MTBF は動いていた時間の平均（大きいほど良い）、MTTR は直す時間の平均（小さいほど良い）
- **直列**は掛け算（a × b、下がる）。**並列**は 1 − (1 − a)(1 − b)（上がる）。0.99 が 2 台で、直列 0.9801、並列 0.9999
- 99.9% は 1 年に約 8.76 時間、99.99% は約 52.6 分の停止
- **RPO** はどの時点のデータまで戻すか（過去へ）、**RTO** はいつまでに再開するか（未来へ）。**SLA** はサービスの水準の合意
- 物理障害には冗長化、論理障害にはバックアップ。**SPoF** は「1 つしかないもの」
- **Corosync** はノード間の通信・メンバーシップ・クォーラム、**Pacemaker** はリソースの管理と切り替え。設定は `/etc/corosync/corosync.conf` と CIB。`crm_mon -1`、`pcs status`、`pcs resource create`、`crm configure show`
- スプリットブレインは **STONITH**（フェンシング）と**クォーラム**（過半数）で防ぐ
- **スケールアップ / ダウン**は 1 台の性能、**スケールアウト / イン**は台数。スケールアウトには**ステートレス**な設計（セッションを外に出す）と、VM イメージ・構成管理ツールが要る
- **ロードバランサー**はヘルスチェックで壊れたサーバーを外す。**DNS ラウンドロビン**は A レコードを並べるだけで、障害も負荷も見ない
- **エフェメラルストレージ**はインスタンスと一緒に消える。**フローティング IP** は別のインスタンスに付け替えられる。**セキュリティグループ**は許可の規則を並べるステートフルなファイアウォール
- **オブジェクトストレージ**は HTTP の API でオブジェクト単位に出し入れする。**オートスケーラー**は最小と最大の間で、台数を自動で変える
- **LAMP** = Linux + Apache + MySQL + PHP、**LAPP** は MySQL が PostgreSQL。**Web 三層** = Web サーバー、AP サーバー、DB サーバー
- Web / AP はスケールアウト、DB は HA とレプリケーション（更新はプライマリだけ。バックアップの代わりにはならない）
- **CDN** とプロキシキャッシュは静的な内容に。**メッセージキュー**は、あとでよい処理を非同期にする
:::

## 練習問題 {#practice}

:::q 2.13.1-01 single
あるサーバーの MTBF が 1,990 時間、MTTR が 10 時間であった。このサーバーの稼働率として正しいものはどれか。
- [ ] 99.0%
- [x] 99.5%
- [ ] 99.9%
- [ ] 99.95%
- [ ] 0.5%
:::why
稼働率 = MTBF ÷ (MTBF + MTTR) = 1,990 ÷ (1,990 + 10) = 1,990 ÷ 2,000 = 0.995、つまり 99.5% です。0.5% は止まっている割合（MTTR ÷ 全体）です。分母を MTBF だけにして 10 ÷ 1,990 を引く、といった計算では合いません（[MTBF・MTTR・稼働率](#mtbf)）。
:::
:::

:::q 2.13.1-02 single
稼働率 0.9 のサーバーを 2 台用意し、どちらか 1 台が動いていればサービスを続けられる構成（並列）にした。全体の稼働率として正しいものはどれか。
- [ ] 0.81
- [ ] 0.9
- [ ] 0.95
- [x] 0.99
- [ ] 1.8
:::why
並列の稼働率は 1 − (1 − a)(1 − b) です。1 − 0.1 × 0.1 = 1 − 0.01 = 0.99 です。0.81 は 0.9 × 0.9 で、2 台とも動いていないと使えない**直列**のときの値です。稼働率は 1 を超えないので、足し算の 1.8 はありえません（[直列と並列](#mtbf)）。
:::
:::

:::q 2.13.1-03 fill
障害が起きてから、サービスを再開するまでにかけてよい時間の目標を表す用語を、英字 3 文字で入力してください。
= RTO
= rto
:::why
RTO（Recovery Time Objective、目標復旧時間）です。RPO（Recovery Point Objective、目標復旧時点）は「どの時点のデータまで戻すか」で、失ってよいデータの量を表します。MTTR は実際に修復にかかった時間の平均で、目標ではありません（[SLA・RPO・RTO](#rpo-rto)）。
:::
:::

:::q 2.13.1-04 single
データベースのバックアップを、毎日午前 2 時に 1 回だけ取得している。レプリケーションは行っていない。この運用で、「RPO は 1 時間」という要件について正しい説明はどれか。
- [ ] 復元の作業が 1 時間以内に終わるなら、要件を満たしている
- [x] 障害の時刻によっては最大で約 24 時間ぶんのデータを失うので、要件を満たしていない
- [ ] バックアップが毎日取れているので、要件を満たしている
- [ ] RPO はサービスの稼働率の目標なので、バックアップの間隔とは関係がない
:::why
RPO は「どの時点のデータまで戻せるか」の目標です。1 日 1 回のバックアップでは、次のバックアップの直前に障害が起きると、約 24 時間ぶんの更新を失います。RPO 1 時間を満たすには、1 時間以内の間隔のバックアップか、レプリケーションが必要です。復元にかかる時間は RTO の話です。稼働率の目標は SLA などで決めるもので、RPO ではありません（[SLA・RPO・RTO](#rpo-rto)）。
:::
:::

:::q 2.13.1-05 multi
Pacemaker と Corosync の役割の説明として正しいものを 2 つ選択してください。
- [x] Corosync は、ノード間の通信、メンバーシップの管理、クォーラムの計算を受け持つ
- [x] Pacemaker は、リソースの起動・停止・監視と、障害のときの切り替えを受け持つ
- [ ] Corosync は、クライアントからの要求を複数のサーバーに振り分けるロードバランサーである
- [ ] Pacemaker は、ノード間でブロックデバイスの内容を複製するソフトウェアである
- [ ] Pacemaker の設定は、`/etc/corosync/corosync.conf` の `totem` セクションに書く
:::why
Corosync はクラスタの通信の層、Pacemaker はリソース管理の層です。2 つを組み合わせて HA クラスタを作ります。要求を振り分けるのは HAProxy や nginx、LVS などのロードバランサーです。ブロックデバイスの複製は DRBD などの役目で、Pacemaker はそれをリソースとして動かす側です。`corosync.conf` の `totem` は Corosync の通信の設定で、Pacemaker の設定（リソース、制約）は CIB に入り、`pcs` や `crm` で変えます（[Pacemaker と Corosync](#pacemaker)）。
:::
:::

:::q 2.13.1-06 single
2 ノード（node1、node2）の HA クラスタで、次のように表示された。この状態の説明として正しいものはどれか。

```text
# crm_mon -1
Cluster Summary:
  * Stack: corosync
  * Current DC: node2 (version 2.1.5-a3f44794f94) - partition with quorum
  * 2 nodes configured
  * 2 resource instances configured

Node List:
  * Node node1: standby
  * Online: [ node2 ]

Full List of Resources:
  * Resource Group: web:
    * vip	(ocf:heartbeat:IPaddr2):	 Started node2
    * httpd	(ocf:heartbeat:apache):	 Started node2
```
- [ ] node1 は障害で停止しており、STONITH によって電源を切られた
- [ ] クォーラムを失っているので、リソースは近いうちに停止する
- [x] node1 はクラスタに参加しているが、リソースを動かさない状態（スタンバイ）にされており、リソースは node2 で動いている
- [ ] vip と httpd は、node1 と node2 の両方で動いている
:::why
`Node node1: standby` は、node1 がスタンバイにされていることを表します（`pcs node standby node1` など）。スタンバイのノードはクラスタのメンバーのままですが、リソースを動かしません。リソースは 2 つとも `Started node2` です。停止したノードは `OFFLINE` と表示されます。`partition with quorum` なので、クォーラムは成立しています（[設定ファイルと管理コマンド](#pacemaker)）。
:::
:::

:::q 2.13.1-07 fill
Pacemaker のクラスタの状態を、画面を更新し続けずに 1 回だけ表示して終了したい。空欄に入るオプションを入力してください。

```text
# crm_mon ____
```
= -1
= --one-shot
:::why
`crm_mon` は、既定では状態を表示し続けます。`-1`（`--one-shot`）で、1 回だけ表示して終わります。`-r` は止まっているリソースも表示する、`-f` は失敗の回数を表示するオプションです（[設定ファイルと管理コマンド](#pacemaker)）。
:::
:::

:::q 2.13.1-08 single
HA クラスタで、ノード間の通信だけが途切れ、両方のノードが「相手が停止した」と判断して同じリソースを起動してしまう状態（スプリットブレイン）がある。Pacemaker で、応答しないノードを強制的に停止させてからリソースを引き継ぐことで、これを防ぐ仕組みはどれか。
- [ ] フェイルバック
- [ ] ハートビート
- [x] STONITH
- [ ] colocation 制約
- [ ] DNS ラウンドロビン
:::why
STONITH（Shoot The Other Node In The Head、フェンシング）は、応答しないノードの電源を切るなどして確実に止め、二重に起動するのを防ぎます。フェイルバックは、直ったノードにサービスを戻すことです。ハートビートは生死を確かめる合図で、途切れたことは分かりますが、相手を止めはしません。colocation 制約は、リソースを同じノードで動かす指定です（[スプリットブレイン、STONITH、クォーラム](#pacemaker)）。
:::
:::

:::q 2.13.1-09 multi
サーバーを 2 台に冗長化（データは 2 台の間で常に複製）しても防げない障害を 2 つ選択してください。
- [ ] 片方のサーバーの電源ユニットの故障
- [x] 管理者が、必要なデータを誤って削除した
- [ ] 片方のサーバーのディスクの故障
- [x] アプリケーションの不具合で、誤った値がデータベースに書き込まれた
- [ ] 片方のサーバーの NIC の故障
:::why
誤った削除と、不具合による誤った書き込みは**論理障害**です。複製によって、もう 1 台にも同じ内容が伝わるので、冗長化では防げません。過去の時点に戻せるバックアップが必要です。電源、ディスク、NIC の故障は**物理障害**で、片方が壊れても残りの 1 台で続けられます（[可用性](#availability)）。
:::
:::

:::q 2.13.1-10 single
2 ノードの HA クラスタの `/etc/corosync/corosync.conf` に、次の設定がある。この設定の説明として正しいものはどれか。

```text
quorum {
    provider: corosync_votequorum
    two_node: 1
}
```
- [ ] ノードが 2 台とも動いているときだけ、リソースを起動できるようにする
- [x] 2 ノードのクラスタで、1 票でもクォーラムが成立するようにする
- [ ] 2 番目のノードを、常にスタンバイにする
- [ ] ノード間の通信に、2 本のネットワークを使う
- [ ] STONITH を無効にする
:::why
クォーラムは票の過半数で成立します。2 ノードでは過半数が 2 票なので、そのままでは 1 台が止まるとクォーラムを失います。`two_node: 1` は、2 ノードのクラスタに限って、1 票で成立させる指定です。通信に使うアドレスは `nodelist` の `ring0_addr` などに書きます。STONITH の無効化は Pacemaker の性質（`pcs property set stonith-enabled=false`）で、corosync.conf には書きません（[スプリットブレイン、STONITH、クォーラム](#pacemaker)）。
:::
:::

:::q 2.13.2-01 single
アクセスの増加に対応するために、同じ構成の Web サーバーの台数を 2 台から 5 台に増やした。この対応を表す用語はどれか。
- [ ] スケールアップ
- [ ] スケールダウン
- [x] スケールアウト
- [ ] スケールイン
- [ ] フェイルオーバー
:::why
台数を増やすのがスケールアウト、減らすのがスケールインです。スケールアップは 1 台の性能を上げること（CPU やメモリを増やす）、スケールダウンは下げることです。フェイルオーバーは、障害のときに予備へ切り替えることです（[スケールアップとスケールアウト](#scaling)）。
:::
:::

:::q 2.13.2-02 single
スケールアップの説明として誤っているものはどれか。
- [ ] CPU やメモリを増やす、上位の機種に替えるなど、1 台の性能を上げることである
- [ ] アプリケーションを分散できる作りに変えなくても行える
- [ ] 性能には、手に入る機種の上限がある
- [x] サーバーが 1 台のままでも、そのサーバーが単一障害点（SPoF）ではなくなる
- [ ] 作業のときに、サーバーの停止が必要になることが多い
:::why
スケールアップでは台数は変わらないので、1 台しかないサーバーは SPoF のままです。可用性も上げたいなら、台数を増やすスケールアウト（冗長化）が必要です。ほかの 4 つは、スケールアップの正しい説明です（[スケールアップとスケールアウト](#scaling)）。
:::
:::

:::q 2.13.2-03 multi
Web サーバーをスケールアウトしやすくするための、ステートレスな設計として適切なものを 2 つ選択してください。
- [x] セッションの情報を、全 Web サーバーが共有するキャッシュサーバーやデータベースに保存する
- [ ] セッションの情報を、要求を受けた Web サーバーのメモリの中だけに保存する
- [x] 利用者がアップロードしたファイルを、Web サーバーのローカルディスクではなく、オブジェクトストレージに保存する
- [ ] Web サーバーごとに、別々のデータベースを持たせる
- [ ] Web サーバー 1 台の CPU とメモリを増やす
:::why
ステートレスとは、要求をまたぐ状態を Web サーバー自身が持たないことです。セッションを共有の保存先に、ファイルをオブジェクトストレージに出せば、どのサーバーが要求を受けても同じ結果になり、台数を自由に増減できます。サーバーのメモリの中だけに持つと、ほかのサーバーに振り分けられたときにセッションが見つかりません。サーバーごとに別のデータベースでは、データが食い違います。CPU とメモリを増やすのはスケールアップで、設計の話ではありません（[ステートレスな設計](#scaling)）。
:::
:::

:::q 2.13.2-04 single
HAProxy に次の設定がある。この設定の説明として正しいものはどれか。

```text
    server web3 192.168.10.13:80 check backup
```

- [ ] 要求は、接続の数がいちばん少ないサーバーに振り分けられる
- [x] 通常は web1 と web2 に順番に振り分けられ、web3 は、その 2 台がどちらも使えないときだけ使われる

- [ ] 同じ送信元 IP アドレスからの要求は、常に同じサーバーに振り分けられる

`balance roundrobin` は順番に振り分ける方式です。`backup` の付いたサーバーは予備で、ほかのサーバーが全部使えなくなったときだけ使われます。`check` は、そのサーバーへのヘルスチェックを有効にする指定で、3 台すべてに付いています。接続のいちばん少ないサーバーを選ぶのは `balance leastconn`、送信元 IP で決めるのは `balance source` です（[ロードバランサー](#lb)）。

```text
    server web1 192.168.10.11:80 check
    server web2 192.168.10.12:80 check
```
= leastconn
:::why
`balance leastconn` が最少接続の方式です。`roundrobin` は順番、`source` は送信元 IP アドレスのハッシュです。nginx では、`upstream` の中に `least_conn;` と書きます（つづりが違います）（[ロードバランサー](#lb)）。

- [x] 1 つの名前に A レコードが 3 つ登録されており、DNS サーバーが答えの順番を変えて返している（DNS ラウンドロビン）

- [ ] 専用の負荷分散装置を用意しなくても実現できる

- [ ] レコードを変更しても、キャッシュの TTL が切れるまでは、古い応答が使われることがある
- [ ] 各サーバーの負荷を見て振り分けているわけではない
:::why
DNS は、登録されたレコードを答えるだけで、サーバーが動いているかどうかを調べません。停止したサーバーのアドレスも答え続けるので、そこに当たったクライアントは接続できません。障害を検知して自動で外すのは、ヘルスチェックを持つロードバランサーです。ほかの 4 つは、DNS ラウンドロビンの正しい説明です（[DNS ラウンドロビン](#lb)）。
:::

- [x] CPU 使用率などの監視の値に条件を決めておき、条件に応じてインスタンスの台数を自動で増減させる
- [x] 台数の最小と最大を決めておき、その範囲の中で台数を変える

- [ ] インスタンスがローカルに持つセッションの情報は、スケールインのときに、自動でほかのインスタンスに引き継がれる

オートスケーラーは、条件に応じて**台数**を自動で増減させます（スケールアウト / スケールイン）。最小と最大の台数の範囲を出ません。増やすインスタンスは、用意しておいた VM イメージから起動するので、手作業は要りません。消されるインスタンスのローカルの状態は失われるので、セッションは外の共有の保存先に置いておきます（ステートレス）（[オートスケーラー](#cloud-services)）。

:::q 2.13.4-03 single
Web 三層の構成における AP サーバー（アプリケーションサーバー）の役割として正しいものはどれか。
- [ ] クライアントからの HTTP の要求を最初に受け、画像などの静的なファイルを返す
- [x] 業務の処理を行うプログラムを実行し、必要なデータを DB サーバーに問い合わせて、結果を作る
- [ ] データを保存し、SQL による検索や更新に応える
- [ ] 要求を複数の Web サーバーに振り分け、応答しないサーバーを外す
- [ ] 利用者に近い場所から、キャッシュした内容を配信する

三層は、Web サーバー（要求を受ける、静的なファイルを返す）、AP サーバー（業務の処理を実行する）、DB サーバー（データを保存する）です。要求を振り分けるのはロードバランサー、近い場所から配信するのは CDN です（[Web 三層](#three-tier)）。

:::q 2.13.4-04 single
Web サーバー、AP サーバー、DB サーバーが 1 台ずつの Web 三層の構成がある。3 台の稼働率はどれも 0.99 で、1 台でも止まるとサービスは使えない。全体の稼働率として最も近いものはどれか。
- [ ] 0.9999
- [ ] 0.99
- [ ] 0.98
- [x] 0.97
- [ ] 0.33
:::why
3 台とも動いていないと使えないので、直列です。0.99 × 0.99 × 0.99 = 0.970299 で、約 0.97 です。直列は、つなぐほど稼働率が下がります。0.9999 は、0.99 の 2 台を並列にしたときの値です（[Web 三層](#three-tier)、[直列と並列](#mtbf)）。

:::q 2.13.4-05 single
次の構成の Web システムがある。単一障害点（SPoF）になっているものはどれか。

```text
クライアント
   │
ロードバランサー（1 台）
   │
Web / AP サーバー（3 台。ロードバランサーが振り分ける）
   │
DB サーバー（2 台。アクティブ / スタンバイの HA クラスタ）
```
- [x] ロードバランサー
- [ ] Web / AP サーバー
- [ ] DB サーバー
- [ ] Web / AP サーバーと DB サーバーの両方
- [ ] SPoF はない
:::why
SPoF は、そこ 1 か所が壊れると全体が止まる部品です。Web / AP サーバーは 3 台、DB サーバーは 2 台で冗長化されていますが、ロードバランサーは 1 台しかなく、すべての要求がそこを通ります。ロードバランサーも 2 台にして、仮想 IP をアクティブ / スタンバイで持たせます（[SPoF](#availability)、[ロードバランサー](#lb)）。

:::q 2.13.4-06 multi
データベースのレプリケーション（プライマリ 1 台、レプリカ 1 台）の説明として正しいものを 2 つ選択してください。
- [x] 検索（参照）の要求をレプリカにも振り分けることで、参照の負荷を分散できる
- [x] 非同期レプリケーションでは、プライマリが故障したとき、直前の更新がレプリカに届いていないことがある
- [ ] 更新の要求をプライマリとレプリカに交互に振り分けることで、更新の負荷を分散できる
- [ ] 誤って実行した DELETE 文はレプリカには伝わらないので、バックアップを取る必要はない
- [ ] 同期レプリケーションは、レプリカの応答を待たないので、非同期レプリケーションより更新が速い
:::why
レプリカは参照に使えるので、参照の負荷を分散できます（リードレプリカ）。更新を受けるのはプライマリだけです。非同期レプリケーションは、レプリカを待たずに更新を完了するので、障害の直前の更新が届いていないことがあります。レプリカの応答を待つのは同期のほうで、そのぶん更新は遅くなります。誤った DELETE もそのまま複製されるので、レプリケーションはバックアップの代わりになりません（[DB のレプリケーション](#ha-three-tier)）。
:::

:::q 2.13.4-07 single
Web サーバーを 4 台にスケールアウトした。「停止した Web サーバーには、自動的に要求を送らないようにする」という要件を満たすために、最も適切な方法はどれか。
- [ ] 1 つの名前に、4 台の A レコードを登録する（DNS ラウンドロビン）
- [x] ヘルスチェックの機能を持つロードバランサーを Web サーバーの手前に置き、要求を振り分ける
- [ ] 4 台の Web サーバーのメモリを増やす
- [ ] クライアントの `/etc/hosts` に、4 台のアドレスを書く
- [ ] DB サーバーをレプリケーションの構成にする
:::why
ロードバランサーは、ヘルスチェックで応答しないサーバーを見つけ、自動で振り分け先から外します。DNS ラウンドロビンは、サーバーの状態を調べないので、停止したサーバーのアドレスも答え続けます。メモリを増やすのはスケールアップで、障害の切り離しとは関係がありません。`/etc/hosts` は、名前とアドレスの対応を固定で書くだけで、サーバーの状態は調べません。DB のレプリケーションは DB 層の話です（[ロードバランサーか、DNS ラウンドロビンか](#ha-three-tier)）。
:::

:::q 2.13.4-08 fill
nginx をロードバランサーとして使い、同じクライアントの IP アドレスからの要求を、常に同じ Web サーバーに振り分けたい。空欄に入るディレクティブを入力してください（末尾の `;` は含めない）。

```text
upstream app {
    ____;
    server 192.168.10.11:80;
    server 192.168.10.12:80;
}
```
= ip_hash
= ip_hash;
= hash $remote_addr
= hash $remote_addr;
:::why
`ip_hash;` は、クライアントの IP アドレスからサーバーを決めるので、同じクライアントは同じサーバーに当たります（`hash $remote_addr;` と書いても、同じ目的を果たせます）。`least_conn;` は接続のいちばん少ないサーバーを選びます。何も書かなければ、ラウンドロビンです。HAProxy では `balance source` が同じ働きをします（[ロードバランサー](#lb)）。

:::q 2.13.4-09 single
nginx に次の設定がある。この設定の説明として正しいものはどれか。

```text
upstream app {
    server 192.168.10.11:80 weight=2;
    server 192.168.10.12:80;
    server 192.168.10.13:80 backup;
}
server {
    listen 80;
    location / { proxy_pass http://app; }
}
```
- [ ] 3 台のサーバーに、同じ割合で要求が振り分けられる
- [x] 通常は .11 と .12 に振り分けられ、.11 には .12 のおよそ 2 倍の要求が渡る。.13 は、ほかの 2 台が使えないときに使われる
- [ ] .13 は、.11 と .12 の内容のバックアップを保存するサーバーである
- [ ] `weight=2` は、.11 に同時に 2 接続までしか渡さないという意味である
- [ ] 接続の数がいちばん少ないサーバーに振り分けられる
:::why
`upstream` に方式を書かなければ、重み付きのラウンドロビンです。`weight=2` のサーバーには、重み 1（既定）のサーバーの 2 倍の割合で要求が渡ります。`backup` は予備のサーバーの印で、ほかのサーバーが使えないときだけ要求を受けます。データのバックアップとは関係がありません。最少接続にするには `least_conn;` を書きます（[ロードバランサー](#lb)）。
:::

:::q 2.13.4-10 single
CDN（Content Delivery Network）の説明として正しいものはどれか。
- [ ] データベースへの更新を、別のデータベースに続けて複製する仕組みである
- [x] 各地に置かれたサーバーが、元のサーバー（オリジン）の内容をキャッシュし、利用者に近い場所から配信する仕組みである
- [ ] 時間のかかる処理をキューに貯めて、あとで別のプログラムに処理させる仕組みである
- [ ] 負荷に応じて、インスタンスの台数を自動で増減させる仕組みである
- [ ] ノードの障害を検知して、リソースを別のノードで起動する仕組みである
:::why
CDN は、各地のエッジサーバーに内容をキャッシュして、利用者に近いところから返します。応答が速くなり、オリジンの負荷も減ります。ほかは順に、レプリケーション、メッセージキューによる非同期処理、オートスケーラー、HA クラスタ（Pacemaker など）の説明です（[プロキシキャッシュと CDN](#cache-queue)）。
:::

:::q 2.13.4-11 multi
Web サーバーの手前に置いたプロキシキャッシュや、CDN でキャッシュするのに適した内容を 2 つ選択してください。
- [x] サイトのロゴなどの画像ファイル
- [ ] ログインした利用者ごとに内容が違う、注文履歴のページ
- [x] 全利用者に共通の CSS ファイルと JavaScript ファイル
- [ ] 買い物かごに商品を追加する POST の要求への応答
- [ ] 利用者ごとの、口座の残高を表示するページ
:::why
キャッシュに向くのは、だれが見ても同じで、あまり変わらない静的な内容です。画像、CSS、JavaScript がその例です。注文履歴や残高のように利用者ごとに違う内容をキャッシュすると、他人の情報が表示される事故になります。POST は状態を変える要求なので、毎回サーバーが処理しなければなりません（[プロキシキャッシュと CDN](#cache-queue)）。
:::

:::q 2.13.4-12 single
CDN を使っている Web サイトで、オリジンのサーバーにある画像ファイルを新しいものに置き換えた。しかし、利用者には古い画像が表示され続けている。原因として最も考えられるものはどれか。
- [ ] CDN は画像ファイルをキャッシュできないので、オリジンの設定が壊れている
- [x] CDN のキャッシュの有効期限（TTL）がまだ切れておらず、エッジサーバーが保存済みの古い内容を返している
- [ ] DNS ラウンドロビンが、停止したサーバーのアドレスを返している
- [ ] データベースのレプリケーションが遅れている
- [ ] セキュリティグループが、HTTPS の通信を拒否している
:::why
キャッシュは、有効期限が切れるまで、保存した内容を返し続けます。オリジンを更新しても、すぐには反映されません。すぐに反映するには、CDN のキャッシュを消す（パージ）か、ファイル名を変えて別の URL にします。通信が拒否されているなら、古い画像すら表示されません。画像ファイルは、データベースのレプリケーションとは関係がありません（[プロキシキャッシュと CDN](#cache-queue)）。
:::

:::q 2.13.4-13 single
注文を受け付ける Web システムで、メッセージキューを使って非同期に処理するのに最も適したものはどれか。
- [ ] ログインのときの、パスワードの照合
- [ ] 注文の画面に表示する、商品の現在の価格の取得
- [x] 注文が確定したあとの、確認メールの送信
- [ ] 利用者が入力した届け先の、必須項目の検査
:::why
非同期処理に向くのは、結果をその場で利用者に返さなくてよい、時間のかかる処理です。確認メールは、数秒〜数分遅れて届いても困らず、メールサーバーが一時的に止まっていても、キューに残ってあとで送れます。パスワードの照合、価格の取得、入力の検査は、結果がないと次の画面を出せないので、同期で処理します（[メッセージキューによる非同期処理](#cache-queue)）。
:::
:::

:::q 2.13.4-14 multi
AP サーバーが時間のかかる処理をメッセージキューに入れ、別のワーカーが取り出して処理する構成にした。この構成の説明として正しいものを 2 つ選択してください。
- [x] AP サーバーは、処理の完了を待たずに、利用者に応答を返せる
- [x] 要求が一時的に集中しても、キューに貯まるので、ワーカーは自分の処理できる速さで処理を続けられる
- [ ] AP サーバーは、処理の結果を、その要求への応答に必ず含めて返せる
- [ ] ワーカーを増やすには、同じ数だけ AP サーバーも増やさなければならない
- [ ] ワーカーが停止している間に入れたメッセージは、すべて失われる
:::why
キューに入れたら、AP サーバーはすぐに応答を返せます。集中した要求はキューに貯まり、負荷がならされます（平準化）。処理はあとで行われるので、結果を同じ応答に含めることはできません。AP サーバーとワーカーは別々に増減できます。ワーカーが止まっていても、メッセージはキューに残り、再開したあとに処理されます（[メッセージキューによる非同期処理](#cache-queue)）。
:::
