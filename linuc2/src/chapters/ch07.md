## DHCP は、4 つのメッセージでアドレスを貸す {#dhcp}

```fig seq DHCP の 4 つのメッセージ。クライアントはまだアドレスを持たないので、ブロードキャストで探す。頭文字を並べて DORA と覚える
{
  colw: 330,
  actors: [
    { id: 'c', label: 'クライアント\nUDP 68 番' },
    { id: 's', label: 'DHCP サーバー（dhcpd）\nUDP 67 番', kind: 'accent' },
  ],
  msgs: [
    { from: 'c', to: 's', label: '① DHCPDISCOVER（サーバーはいますか。ブロードキャスト）', style: 'accent' },
    { from: 's', to: 'c', label: '② DHCPOFFER（192.168.1.100 を貸せます）' },
    { from: 'c', to: 's', label: '③ DHCPREQUEST（192.168.1.100 を使います）', style: 'accent' },
    { from: 's', to: 'c', label: '④ DHCPACK（どうぞ。期限は 600 秒）' },
    { note: 'クライアントはアドレス、マスク、ゲートウェイ、DNS サーバーを設定する。サーバーは dhcpd.leases に記録する', at: 'c', span: 2 },
  ],
}
```

**DHCP**（Dynamic Host Configuration Protocol）は、ネットワークにつないだ機械に、IP アドレス、ネットマスク、デフォルトゲートウェイ、DNS サーバーなどを自動で配る仕組みです。配る側が DHCP サーバー、もらう側が DHCP クライアントです。

やりとりは 4 つのメッセージです。クライアントはまだ自分のアドレスを持たないので、最初の DHCPDISCOVER は**ブロードキャスト**（同じネットワークの全員あて）で送ります。サーバーは **UDP の 67 番**、クライアントは **UDP の 68 番**を使います。

| 順 | メッセージ | 向き | 意味 |
| --- | --- | --- | --- |
| 1 | DHCPDISCOVER | クライアント → 全員 | DHCP サーバーを探す |
| 2 | DHCPOFFER | サーバー → クライアント | 貸せるアドレスを申し出る |
| 3 | DHCPREQUEST | クライアント → 全員 | 申し出の 1 つを選んで、使うと伝える |
| 4 | DHCPACK | サーバー → クライアント | 貸し出しを確定する |

アドレスは「あげる」のではなく、期限つきで「貸す」ものです。この貸し出しを**リース**（lease）と呼びます。クライアントは期限の半分が過ぎると、DHCPREQUEST を送って延長します。使い終わったクライアントは DHCPRELEASE で返します。

ブロードキャストはルーターを越えません。別のサブネットにあるサーバーを使うときは、ルーターの上で **DHCP リレーエージェント**（`dhcrelay`）を動かして、要求を中継します。

Linux で広く使われてきた DHCP サーバーは、ISC（Internet Systems Consortium）の **`dhcpd`** です。試験の範囲も、この dhcpd の設定ファイルです。

| | Debian 系 | Red Hat 系 |
| --- | --- | --- |
| パッケージ | `isc-dhcp-server` | `dhcp-server` |
| 設定ファイル | `/etc/dhcp/dhcpd.conf` | `/etc/dhcp/dhcpd.conf` |
| リースの記録 | `/var/lib/dhcp/dhcpd.leases` | `/var/lib/dhcpd/dhcpd.leases` |
| unit の名前 | `isc-dhcp-server` | `dhcpd` |
| 待ち受けるインターフェースの指定 | `/etc/default/isc-dhcp-server` の `INTERFACESv4` | `/etc/sysconfig/dhcpd`（`DHCPDARGS`） |

## dhcpd.conf は、サブネットごとに「範囲とオプション」を書く {#dhcpd-conf}

`/etc/dhcp/dhcpd.conf` の例です。192.168.1.0/24 のネットワークで、100 番から 200 番までを配ります。

```text
option domain-name "example.jp";
option domain-name-servers 192.168.1.1, 8.8.8.8;
default-lease-time 600;
max-lease-time 7200;
authoritative;

subnet 192.168.1.0 netmask 255.255.255.0 {
  range 192.168.1.100 192.168.1.200;
  option routers 192.168.1.1;
  option subnet-mask 255.255.255.0;
  option broadcast-address 192.168.1.255;
}

host printer {
  hardware ethernet 00:11:22:33:44:55;
  fixed-address 192.168.1.10;
}
```

書き方の決まりは 3 つです。

- 1 つの設定は **`;`（セミコロン）で終わる**
- `subnet` や `host` は `{ }` で囲む。`{ }` の外に書いたものは全体に、中に書いたものはその中だけに効く（中が優先）
- クライアントに**配る値**は `option 名前 値;`、サーバー自身の動きを決めるものは `option` を付けない

| 書き方 | 意味 |
| --- | --- |
| `subnet ネットワーク netmask マスク { … }` | 配る先のサブネットを宣言する。`/24` ではなく `netmask` で書く |
| `range 最初 最後;` | **動的に割り当てる範囲**。この中から空いているものを貸す |
| `option routers` | デフォルトゲートウェイ |
| `option subnet-mask` | ネットマスク |
| `option broadcast-address` | ブロードキャストアドレス |
| `option domain-name-servers` | DNS サーバー（カンマ区切りで複数） |
| `option domain-name` | ドメイン名（文字列なので `"` で囲む） |
| `option ntp-servers` | NTP サーバー |
| `default-lease-time 秒;` | クライアントが期限を指定しないときのリースの長さ |
| `max-lease-time 秒;` | クライアントが長い期限を求めても、これより長くは貸さない |
| `host 名前 { hardware ethernet MAC; fixed-address IP; }` | **固定の割り当て**。この MAC アドレスの機械には、いつもこのアドレスを貸す |
| `authoritative;` | このサーバーが、このネットワークの正式な DHCP サーバーだと宣言する |

:::warn 試験の注意：routers と fixed-address
デフォルトゲートウェイのオプションの名前は `option gateway` ではなく **`option routers`** です。固定の割り当ては `host` の中に **`hardware ethernet`**（MAC アドレス）と **`fixed-address`**（IP アドレス）を書きます。`fixed-address` には、`range` の**外**のアドレスを使います。`range` の中にあると、同じアドレスをほかの機械に動的に貸してしまうおそれがあります。
:::

書いたら、起動する前に文法を調べます。`dhcpd -t` は設定ファイルを読んで、まちがいがあれば行番号を出して終わります。

```console
# dhcpd -t -cf /etc/dhcp/dhcpd.conf
Config file: /etc/dhcp/dhcpd.conf
Database file: /var/lib/dhcp/dhcpd.leases
PID file: /var/run/dhcpd.pid
# dhcpd -t -cf /tmp/bad.conf
/tmp/bad.conf line 3: semicolon expected.
}
 ^
Configuration file errors encountered -- exiting
```

2 つ目は、`range` の行の `;` を忘れた例です。「semicolon expected」（セミコロンがあるはず）と、次の行の番号で知らせます。

| `dhcpd` のオプション | 意味 |
| --- | --- |
| `-t` | 設定ファイルの文法を調べて終わる |
| `-T` | リースのファイルを調べて終わる |
| `-cf ファイル` | 設定ファイルを指定する（既定は `/etc/dhcp/dhcpd.conf`） |
| `-lf ファイル` | リースのファイルを指定する |
| `-f` | フォアグラウンドで動かす（systemd の unit はこれを使う） |
| `-d` | ログを syslog ではなく、標準エラー出力に出す |
| `-4` / `-6` | DHCPv4 / DHCPv6 のサーバーとして動かす（既定は `-4`） |
| 末尾のインターフェース名 | そのインターフェースだけで待ち受ける（`dhcpd eth1`） |

:::warn 試験の注意：subnet の宣言がないと起動しない
dhcpd は、待ち受けるインターフェースのアドレスが属するサブネットの `subnet` 宣言を、dhcpd.conf の中に探します。見つからないと、次のメッセージを出して起動しません。

```text
No subnet declaration for veth0 (192.168.1.1).
Not configured to listen on any interfaces!
```

アドレスを配らないインターフェースしかないときも、空の `subnet … { }` を書いておく必要があります。
:::

## リースとログで、貸し出しを確かめる {#dhcp-leases}

dhcpd は、貸したアドレスを **`dhcpd.leases`** に書き足していきます。再起動しても、誰に何を貸したかを忘れないためのファイルです。クライアントが 1 台アドレスをもらったあとの中身です。

```console
# cat /var/lib/dhcp/dhcpd.leases
lease 192.168.1.100 {
  starts 1 2026/11/16 21:18:39;
  ends 1 2026/11/16 21:28:39;
  cltt 1 2026/11/16 21:18:39;
  binding state active;
  next binding state free;
  rewind binding state free;
  hardware ethernet be:e4:73:7c:b9:9a;
  client-hostname "52f8273d7994";
}
```

| 行 | 意味 |
| --- | --- |
| `lease 192.168.1.100` | 貸したアドレス |
| `starts` / `ends` | リースの始まりと終わり（**UTC**。先頭の数字は曜日で、0 が日曜） |
| `binding state active` | いま貸している。返されると `free` になる |
| `hardware ethernet` | 借りたクライアントの MAC アドレス |
| `client-hostname` | クライアントが名乗ったホスト名 |

`ends` − `starts` が 10 分なのは、`default-lease-time 600;` のためです。

このファイルは**追記**されるので、同じアドレスの `lease` が何度も出てきます。有効なのは、いちばん後ろのものです。dhcpd はときどきファイルを作り直し、古いほうを `dhcpd.leases~` という名前で残します。

:::warn 試験の注意：dhcpd.leases は、空でも「ある」ことが必要
dhcpd は、起動のときに dhcpd.leases がないと「Can't open lease database」と出して止まります。パッケージで入れたときは最初から作られていますが、自分で場所を変えたときは `touch /var/lib/dhcp/dhcpd.leases` で空のファイルを作ってから起動します。手で書き換えるファイルではありません。
:::

### ログを読む

dhcpd は、やりとりを 1 メッセージ 1 行で **syslog**（facility は daemon）に出します。見る場所は、ログの仕組みで決まります（[図解 LinuC 9.3 rsyslog](../../linuc/site/ch09.html#rsyslog)、[9.4 journalctl](../../linuc/site/ch09.html#journal)）。

| 仕組み | 見方 |
| --- | --- |
| rsyslog（Debian 系） | `/var/log/syslog` を `grep dhcpd` |
| rsyslog（Red Hat 系） | `/var/log/messages` を `grep dhcpd` |
| systemd journal | `journalctl -u dhcpd`（Debian 系は `-u isc-dhcp-server`） |

サーバー側のログは、DORA の順に 4 行です。

```text
DHCPDISCOVER from be:e4:73:7c:b9:9a via veth0
DHCPOFFER on 192.168.1.100 to be:e4:73:7c:b9:9a (52f8273d7994) via veth0
DHCPREQUEST for 192.168.1.100 (192.168.1.1) from be:e4:73:7c:b9:9a (52f8273d7994) via veth0
DHCPACK on 192.168.1.100 to be:e4:73:7c:b9:9a (52f8273d7994) via veth0
```

`from` の後ろがクライアントの MAC アドレス、`via` の後ろが受け取ったインターフェースです。どこまで進んだかで、原因の場所が分かります。

| ログの様子 | 考えられる原因 |
| --- | --- |
| DHCPDISCOVER の行が出ない | 要求がサーバーに届いていない（配線、VLAN、ファイアウォールの UDP 67、リレーがない） |
| `DHCPDISCOVER from … via eth0: network 192.168.1.0/24: no free leases` | `range` を書いていないか、範囲のアドレスを全部貸し出している |
| DHCPOFFER のあと DHCPREQUEST が来ない | クライアントが別の DHCP サーバーの申し出を選んだ |

### arp で、アドレスと MAC アドレスの対応を見る

固定の割り当てには、クライアントの MAC アドレスが要ります。同じネットワークの相手の MAC アドレスは、カーネルの **ARP テーブル**（IP アドレスと MAC アドレスの対応表）で調べられます。古くからのコマンドが `arp`、いまのコマンドが `ip neigh` です。

```console
# arp -n
Address                  HWtype  HWaddress           Flags Mask            Iface
172.17.0.1               ether   2e:4c:63:ab:0e:92   C                     eth0
# ip neigh
172.17.0.1 dev eth0 lladdr 2e:4c:63:ab:0e:92 REACHABLE
```

| コマンド | 意味 |
| --- | --- |
| `arp -n` | ARP テーブルを表示する。`-n` は名前に直さず、IP アドレスのまま出す |
| `arp -a` | BSD 風の形（`? (172.17.0.1) at 2e:4c:… [ether] on eth0`）で表示する |
| `arp -d アドレス` | 1 件を消す |
| `arp -s アドレス MAC` | 手で 1 件を登録する（静的なエントリ） |

「配ったはずのアドレスに、別の機械が応えている」という重なりを疑うときも、`arp -n` でその IP アドレスの MAC アドレスを見て、dhcpd.leases の `hardware ethernet` と比べます。

## IPv6 は、ルーター広告と DHCPv6 で配る {#radvd}

```fig graph IPv6 のアドレスの決め方は 2 つ。ルーター広告（RA）のプレフィックスから自分で作る SLAAC と、DHCPv6 サーバーからもらう方法。どちらを使うかは、RA の中の M と O のフラグでクライアントに伝える
{
  col: 250, row: 100,
  nodes: [
    { id: 'c', label: 'IPv6 のクライアント', sub: 'アドレスが欲しい', x: 0, y: 0.5, kind: 'accent', mono: false },
    { id: 'r', label: 'ルーター（radvd）', sub: 'ルーター広告（RA）を流す', x: 1.4, y: 0, kind: 'stack', mono: false },
    { id: 'd', label: 'DHCPv6 サーバー（dhcpd -6）', sub: 'UDP 547 番', x: 1.4, y: 1, kind: 'heap', mono: false },
  ],
  edges: [
    { from: 'r', to: 'c', label: 'プレフィックス /64 と M・O フラグ' },
    { from: 'd', to: 'c', label: 'アドレス、DNS サーバー', style: 'dashed' },
  ],
}
```

IPv6 では、DHCP がなくてもアドレスが決まります（[図解 LinuC 7.5 IPv6](../../linuc/site/ch07.html#ipv6)）。ルーターが定期的に流す**ルーター広告**（RA、Router Advertisement）に、そのネットワークのプレフィックス（先頭の 64 ビット）が入っています。クライアントは、それに自分で作った後ろの 64 ビットをつないで、アドレスにします。これを **SLAAC**（ステートレスアドレス自動設定）と呼びます。デフォルトゲートウェイは、RA を送ってきたルーターです。

Linux をルーターにして RA を流すデーモンが **`radvd`**（Router ADVertisement Daemon）、設定ファイルが **`/etc/radvd.conf`** です。

```text
interface eth0 {
    AdvSendAdvert on;
    MinRtrAdvInterval 3;
    MaxRtrAdvInterval 10;
    AdvManagedFlag off;
    AdvOtherConfigFlag off;
    prefix 2001:db8:1::/64 {
        AdvOnLink on;
        AdvAutonomous on;
    };
    RDNSS 2001:db8:1::53 {
    };
};
```

| 書き方 | 意味 |
| --- | --- |
| `interface eth0 { … };` | RA を流すインターフェース。**閉じる `}` の後ろにも `;`** が要る |
| `AdvSendAdvert on;` | RA を送る。`off`（既定）のままでは何も送らない |
| `prefix 2001:db8:1::/64 { … };` | 広告するプレフィックス |
| `AdvAutonomous on;` | このプレフィックスで SLAAC をしてよい |
| `AdvManagedFlag on;` | **M フラグ**。アドレスを DHCPv6 でもらえ、と伝える |
| `AdvOtherConfigFlag on;` | **O フラグ**。アドレスは SLAAC、DNS サーバーなど「そのほか」を DHCPv6 でもらえ、と伝える |
| `RDNSS アドレス { };` | RA で DNS サーバーを知らせる |
| `MinRtrAdvInterval` / `MaxRtrAdvInterval` | RA を送る間隔（秒）の下限と上限 |

文法は `radvd -c`（`--configtest`）で調べます。設定ファイルは `-C` で指定します。

```console
# radvd -c -C /etc/radvd.conf
[Nov 16 21:18:18] radvd (246): config file, /etc/radvd.conf, syntax ok
```

radvd を動かす機械は IPv6 のルーターなので、IPv6 の転送を有効にしておきます（`sysctl -w net.ipv6.conf.all.forwarding=1`）。

**DHCPv6** は、IPv6 版の DHCP です。ISC の dhcpd では、`dhcpd -6` で動かし、設定は `/etc/dhcp/dhcpd6.conf` に書きます。

```text
default-lease-time 2592000;
option dhcp6.name-servers 2001:db8:1::53;
subnet6 2001:db8:1::/64 {
  range6 2001:db8:1::1000 2001:db8:1::1fff;
}
```

| | DHCPv4 | DHCPv6 |
| --- | --- | --- |
| ポート | サーバー UDP 67、クライアント UDP 68 | サーバー UDP **547**、クライアント UDP **546** |
| サブネットの宣言 | `subnet … netmask … { }` | `subnet6 プレフィックス/長さ { }` |
| 範囲 | `range` | `range6` |
| オプションの名前 | `option domain-name-servers` | `option dhcp6.name-servers` |
| デフォルトゲートウェイ | `option routers` で配る | **配らない**（RA で知る） |
| リースのファイル | `dhcpd.leases` | `dhcpd6.leases` |

:::note DHCPv6 だけでは足りない
DHCPv6 には、デフォルトゲートウェイを配るオプションがありません。ゲートウェイは必ず RA で知らせるので、DHCPv6 を使うネットワークでも radvd（またはルーターの RA の機能）は要ります。M フラグを `on` にした RA と DHCPv6 サーバーを組み合わせるのが、IPv4 の DHCP にいちばん近い形です。
:::

```fig graph login、sshd、su などは、パスワードの確かめ方を自分では持たない。PAM のライブラリを呼ぶと、/etc/pam.d/ のサービス名のファイルに書かれたモジュールが、上から順に動く
    { id: 'unix', label: 'pam_unix.so', sub: '/etc/shadow で確かめる', x: 3.1, y: 0, kind: 'ext' },
    { id: 'sss', label: 'pam_sss.so', sub: 'SSSD（LDAP など）に聞く', x: 3.1, y: 1, kind: 'ext' },
    { id: 'lim', label: 'pam_limits.so', sub: '資源の上限を付ける', x: 3.1, y: 2, kind: 'ext' },
  ],
  edges: [
    { from: 'login', to: 'lib' }, { from: 'sshd', to: 'lib' }, { from: 'su', to: 'lib' },
    { from: 'lib', to: 'conf', label: '読む' },
    { from: 'conf', to: 'unix' }, { from: 'conf', to: 'sss' }, { from: 'conf', to: 'lim' },
  ],
}
```

**PAM**（Pluggable Authentication Modules、差し替えできる認証モジュール）は、「この人は本人か」「いまログインしてよいか」を確かめる処理を、プログラムの外に出す仕組みです。`login`、`sshd`、`su`、`sudo`、`passwd` などは、自分でパスワードを確かめず、PAM のライブラリを呼びます。

そのおかげで、パスワードの置き場所を `/etc/shadow` から LDAP に変えるときも、プログラムを作り直す必要がありません。**設定ファイルの行を変えるだけ**で、認証の方法を差し替えられます。

設定の置き場所は 2 つあります。

| 場所 | 形 |
| --- | --- |
| **`/etc/pam.d/`** | サービス（プログラム）ごとに 1 ファイル。ファイル名がサービス名（`/etc/pam.d/sshd`、`/etc/pam.d/su`） |
| `/etc/pam.conf` | 1 ファイルに全部書く古い形。各行の**先頭にサービス名**の欄が増える |

:::warn 試験の注意：/etc/pam.d/ があると、pam.conf は読まれない
`/etc/pam.d/` ディレクトリがあるとき、`/etc/pam.conf` は**無視されます**。いまのディストリビューションはどれも `/etc/pam.d/` を使います。サービス名のファイルがないときは、**`/etc/pam.d/other`** が使われます。モジュールの本体（`pam_unix.so` など）は、Red Hat 系では `/usr/lib64/security/`、Debian 系では `/lib/x86_64-linux-gnu/security/` にあります。
:::

## /etc/pam.d/ の 1 行は「タイプ・制御・モジュール・引数」 {#pam-syntax}

`/etc/pam.d/` のファイルは、1 行が 1 つのモジュールの呼び出しです。Rocky Linux 9 の `/etc/pam.d/system-auth`（抜粋）で読み方を見ます。

```text
auth        required      pam_env.so
auth        sufficient    pam_unix.so try_first_pass nullok
auth        required      pam_deny.so

account     required      pam_unix.so

password    requisite     pam_pwquality.so try_first_pass local_users_only retry=3
password    sufficient    pam_unix.so try_first_pass use_authtok nullok sha512 shadow
password    required      pam_deny.so

session     required      pam_limits.so
session     required      pam_unix.so
```

欄は左から 4 つです。`/etc/pam.conf` に書くときだけ、先頭に「サービス名」の欄が足されます。

```text
タイプ    制御        モジュール     引数
auth      required    pam_unix.so    nullok
```

### タイプ：4 つの場面

**タイプ**（モジュールタイプ）は、その行がどの場面で使われるかです。同じタイプの行が、上から順に実行されます。この並びを**スタック**と呼びます。

| タイプ | 場面 | 例 |
| --- | --- | --- |
| `auth` | **本人か**を確かめる | パスワードを聞いて照合する |
| `account` | **いま使ってよいか**を確かめる（認証とは別） | アカウントやパスワードの期限、時間帯、`/etc/nologin` |
| `password` | **パスワードを変える**とき | 新しいパスワードの強さを調べ、書き換える |
| `session` | ログインの**前後の準備と後片付け** | 資源の上限、ホームディレクトリの作成、ログへの記録 |

### 制御：結果をどう扱うか

**制御**（コントロールフラグ）は、モジュールが成功・失敗したときに、スタックの続きをどうするかです。試験でいちばん問われるところです。

| 制御 | 失敗したとき | 成功したとき |
| --- | --- | --- |
| `required` | 最後は失敗になる。ただし**残りの行も実行する** | 次の行へ進む |
| `requisite` | **その場で失敗を返す**（残りは実行しない） | 次の行へ進む |
| `sufficient` | 無視して次の行へ進む | それより前の required が失敗していなければ、**その場で成功を返す** |
| `optional` | 結果に影響しない（ほかにモジュールがないときだけ使われる） | 同じ |
| `include` | ほかのファイルの、同じタイプの行をここに読み込む | |
| `substack` | include と同じだが、読み込んだ中での「その場で終わる」は、読み込んだ中だけで終わる | |

`required` が失敗しても残りを実行するのは、**どのモジュールで失敗したかを相手に知らせないため**です。ユーザー名がまちがっていても、パスワードを聞いてから「失敗」と答えます。

上の system-auth の auth は、次のように動きます。

1. `pam_env.so`（環境変数を用意する）は成功するので、次へ
2. `pam_unix.so` が `/etc/shadow` と照合する。合えば `sufficient` なので、**ここで成功**して終わる
3. 合わなければ次の `pam_deny.so`（必ず失敗するモジュール）が `required` で失敗し、認証は失敗

Docker の中で、`pamtester`（PAM を試すコマンド）を使って制御の違いを確かめた結果です。`pam_permit.so` は必ず成功、`pam_deny.so` は必ず失敗するモジュールです。

| スタック（上から） | 結果 | 理由 |
| --- | --- | --- |
| `sufficient pam_permit.so` → `required pam_deny.so` | 成功 | sufficient が成功した時点で終わり、2 行目は実行されない |
| `required pam_deny.so` → `sufficient pam_permit.so` | 失敗 | 先に required が失敗しているので、sufficient が成功しても覆らない |
| `optional pam_deny.so` → `required pam_permit.so` | 成功 | optional の失敗は結果に影響しない |

:::warn 試験の注意：required と requisite
どちらも「失敗したら、全体が失敗」です。違いは、失敗の**あと**です。`required` は残りのモジュールも実行してから失敗を返し、`requisite` はその場で失敗を返します。「sufficient は成功したら即終了、requisite は失敗したら即終了」と対にして覚えます。
:::

:::deep [success=1 default=ignore] という書き方
Debian 系の `/etc/pam.d/common-auth` には、`auth [success=1 default=ignore] pam_unix.so nullok` のような行があります。`[ ]` の中は「結果=動作」の並びで、`success=1` は「成功したら次の 1 行を飛ばす」、`default=ignore` は「それ以外は無視」です。次の行が `pam_deny.so`、その次が `pam_permit.so` なので、成功すれば deny を飛ばして permit に着きます。`required` などの 4 つの語は、この書き方の決まった組み合わせに名前を付けたものです。
:::

### 共通の設定を読み込む

どのサービスにも同じ行を書くのは大変なので、共通の部分は別のファイルにまとめて読み込みます。まとめ方がディストリビューションで違います。

| | 共通のファイル | 読み込み方 |
| --- | --- | --- |
| Red Hat 系 | `/etc/pam.d/system-auth`（ローカルのログイン）、`/etc/pam.d/password-auth`（sshd などリモート） | `auth include system-auth`、`auth substack password-auth` |
| Debian 系 | `/etc/pam.d/common-auth`、`common-account`、`common-password`、`common-session` | `@include common-auth` |

Red Hat 系の system-auth と password-auth は、`authselect` コマンド（`authselect select sssd` など）が作るファイルです。

## よく使う PAM モジュール {#pam-modules}

範囲に名前が挙がっているモジュールは 5 つです。まわりでよく一緒に出るものと合わせて整理します。

| モジュール | 役目 | 主に使うタイプ |
| --- | --- | --- |
| **`pam_unix`** | `/etc/passwd` と `/etc/shadow` を使う、ふつうの認証とパスワードの変更 | 4 つ全部 |
| **`pam_cracklib`** | 新しいパスワードの強さを調べる（辞書にある語、短すぎる、前と似ている） | password |
| **`pam_limits`** | `/etc/security/limits.conf` に従って、資源の上限を付ける | session |
| **`pam_listfile`** | ファイルに書いた名前の一覧で、許可・拒否する | auth |
| **`pam_sss`** | SSSD を通して、LDAP などのリモートのユーザーを認証する | 4 つ全部 |
| `pam_deny` / `pam_permit` | 必ず失敗する / 必ず成功する | |
| `pam_nologin` | `/etc/nologin` があると、root 以外のログインを拒否する | auth、account |
| `pam_securetty` | root のログインを、`/etc/securetty` に書いた端末だけに限る | auth |
| `pam_wheel` | `su` で root になれる人を、wheel グループに限る | auth |
| `pam_env` | 環境変数を設定する（`/etc/environment` など） | auth、session |

### pam_unix

```text
auth      sufficient  pam_unix.so try_first_pass nullok
password  sufficient  pam_unix.so try_first_pass use_authtok nullok sha512 shadow remember=5
```

| 引数 | 意味 |
| --- | --- |
| `nullok` | 空のパスワードのアカウントを認める（ないと、空のパスワードでは認証できない） |
| `try_first_pass` | 前のモジュールが聞いたパスワードをまず試し、だめなら聞き直す |
| `use_first_pass` | 前のモジュールが聞いたパスワードだけを使う（聞き直さない） |
| `use_authtok` | （password で）前のモジュール（強さの検査）が受け取った新しいパスワードを、そのまま使う |
| `sha512` / `yescrypt` | 新しいパスワードをこの方式でハッシュにする |
| `shadow` | `/etc/shadow` を使う |
| `remember=5` | 過去 5 個のパスワードを `/etc/security/opasswd` に覚えておき、使い回しを断る |

### pam_cracklib（と、後継の pam_pwquality）

```text
password  requisite  pam_cracklib.so retry=3 minlen=12 difok=3 dcredit=-1 ucredit=-1
password  sufficient pam_unix.so use_authtok sha512 shadow
```

| 引数 | 意味 |
| --- | --- |
| `retry=3` | 弱いパスワードだったとき、3 回まで入力し直させる |
| `minlen=12` | 最小の長さ。ただし、プラスの `*credit`（既定はどれも 1）がある種類の文字を使うと、その分だけ短くてもよい |
| `difok=3` | 前のパスワードと、少なくとも 3 文字は違うこと |
| `dcredit=-1` | 数字（digit）を最低 1 文字含むこと |
| `ucredit=-1` / `lcredit=-1` | 大文字（upper）/ 小文字（lower）を最低 1 文字含むこと |
| `ocredit=-1` | 記号（other）を最低 1 文字含むこと |

`*credit` は、**マイナスの値にすると「その種類を最低その数だけ含む」**という意味になります。逆に 0 以上の値は、その種類の文字を使ったときに、長さに足してもらえる点数（クレジット）の上限です。`dcredit`、`ucredit`、`lcredit`、`ocredit` の既定はどれも 1 なので、`minlen=12` と書いただけでは、4 種類を混ぜた 9 文字のパスワードも「9 + 3 = 12」として通ります（Debian 11 の pam_cracklib で確かめた結果です）。`minlen` をそのまま文字数の下限にしたいときは、`ucredit=0 lcredit=0 ocredit=0` のように、クレジットを 0 かマイナスにします。

pam_cracklib は必ず **pam_unix より上**に書きます。先に強さを調べ、通ったパスワードを `use_authtok` で pam_unix に渡して書き換えさせるためです。

:::note pam_cracklib はいまは pam_pwquality
Debian 12 と Rocky Linux 9 には pam_cracklib はもう入っておらず、同じ引数（`retry`、`minlen`、`difok`、`dcredit` など）が使える後継の **`pam_pwquality`** に置き換わっています。pam_pwquality は、引数のほかに `/etc/security/pwquality.conf` でも設定できます。試験の範囲には pam_cracklib の名前で載っているので、役目と引数を覚えておきます。
:::

### pam_limits

`pam_limits` は、ログインのときに `/etc/security/limits.conf` と `/etc/security/limits.d/*.conf` を読み、そのセッションに資源の上限を付けます。`ulimit` で見える値の出どころです（[図解 LinuC 10.4 ulimit](../../linuc/site/ch10.html#limits)）。

```text
session   required   pam_limits.so
```

`/etc/security/limits.conf` は、1 行が「誰に・種類・項目・値」の 4 つの欄です。

```text
#<domain>   <type>  <item>     <value>
*           soft    core       0
@student    hard    nproc      20
ken         soft    nofile     4096
ken         hard    nofile     8192
@student    -       maxlogins  4
```

| 欄 | 書くもの |
| --- | --- |
| domain（誰に） | ユーザー名、`@グループ名`、`*`（全員） |
| type（種類） | `soft`（ソフトリミット。自分でハードまで上げられる）、`hard`（ハードリミット。上限の上限）、`-`（両方） |
| item（項目） | `nofile`（開けるファイルの数）、`nproc`（プロセスの数）、`core`（core ファイルの大きさ）、`maxlogins`（同時にログインできる数）、`fsize`（ファイルの大きさ）など |
| value（値） | 数、または `unlimited` |

小さな Linux でも、いまのシェルに付いている上限を `ulimit` で見られます。本物の Linux では、この値を pam_limits がログインのときに付けています。

```sh run title="いまのセッションの上限（開けるファイルの数）"
ulimit -Sn
ulimit -Hn
```

### pam_listfile

`pam_listfile` は、ファイルに 1 行 1 つで書いた名前の一覧と照らして、成功か失敗かを返します。「このユーザーは SSH でログインさせない」のような、名前の一覧での制限に使います。

```text
auth  required  pam_listfile.so item=user sense=deny file=/etc/ssh/denyusers onerr=succeed
```

| 引数 | 意味 |
| --- | --- |
| `item=` | 何を照らすか。`user`（ユーザー名）、`group`、`tty`、`rhost`（接続元のホスト）、`ruser`、`shell` |
| `sense=` | 一覧に**あった**ときの扱い。`allow`（あれば成功、なければ失敗）、`deny`（あれば失敗、なければ成功） |
| `file=` | 一覧のファイル |
| `onerr=` | ファイルが開けないなどのエラーのときの扱い。`succeed` か `fail` |

Docker で確かめると、`/etc/denyusers` に `ken` と書いて `sense=deny` にしたとき、ken の認証は失敗し、書いていない mika は成功します。同じファイルで `sense=allow` にすると逆になり、ken だけが成功します。

ユーザーの情報を LDAP サーバーにまとめると、クライアントの `/etc/passwd` にはそのユーザーがいません。それでもログインできるようにするには、**2 つの別の仕組み**の両方に、LDAP を見るよう教える必要があります。

| 仕組み | 答える問い | 設定 |
| --- | --- | --- |
| **NSS**（Name Service Switch） | このユーザー名の UID、GID、ホーム、シェルは何か | `/etc/nsswitch.conf` |
| **PAM** | 入力されたパスワードは正しいか、ログインしてよいか | `/etc/pam.d/` |

`/etc/nsswitch.conf` は、レベル1 で `hosts: files dns` を読んだファイルです（[図解 LinuC 7.6](../../linuc/site/ch07.html#hostname)）。ユーザーとグループの行も同じ読み方です。左から順に試し、見つかったところで止まります。

```text
passwd:     files sss
group:      files sss
shadow:     files sss
hosts:      files dns
```

| 書く語 | 引く先 |
| --- | --- |
| `files` | ローカルのファイル（`/etc/passwd`、`/etc/group`、`/etc/hosts`） |
| `sss` | SSSD |
| `ldap` | LDAP サーバーに直接（古い nss_ldap の方式） |
| `dns` | DNS（hosts の行だけ） |
| `systemd` | systemd が動的に作るユーザー |

`getent passwd ユーザー名` は、この nsswitch.conf の順に引くコマンドです（[図解 LinuC 8.2](../../linuc/site/ch08.html#account-files)）。LDAP のユーザーが `getent passwd ken` で出れば、NSS の側は正しく設定できています。小さな Linux には `files` しかありませんが、引き方は同じです。

```sh run title="getent は nsswitch.conf の順に引く"
getent passwd root
getent group root
```

:::warn 試験の注意：nsswitch.conf は認証をしない
`/etc/nsswitch.conf` が決めるのは、**情報をどこから引くか**だけです。パスワードを確かめるのは PAM です。「`getent passwd ken` では出るのにログインできない」なら PAM（pam_sss）の側、「`id ken` で no such user と出る」なら NSS（nsswitch.conf の `passwd:` 行）の側を疑います。
:::

### SSSD の基本

**SSSD**（System Security Services Daemon）は、LDAP、Active Directory、Kerberos などのリモートのサーバーに問い合わせるデーモン（`sssd`）です。NSS からは `sss`、PAM からは `pam_sss` を通して呼ばれます。

SSSD を間に入れる利点は、**キャッシュ**です。一度引いた情報を覚えておくので、サーバーへの問い合わせが減ります。認証の情報も覚えさせれば（`cache_credentials = true`）、ノートパソコンがネットワークから外れていても、前にログインしたユーザーはログインできます（オフライン認証）。

設定ファイルは **`/etc/sssd/sssd.conf`** です。`[sssd]` に全体の設定、`[domain/名前]` に問い合わせ先ごとの設定を書きます。

```text
[sssd]
services = nss, pam
domains = example

[domain/example]
id_provider = ldap
auth_provider = ldap
ldap_uri = ldap://ldap.example.jp
ldap_search_base = dc=example,dc=jp
cache_credentials = true
```

| 項目 | 意味 |
| --- | --- |
| `[sssd]` の `services` | SSSD が受け持つ窓口。`nss`（情報を引く）、`pam`（認証）など |
| `[sssd]` の `domains` | 使うドメイン（`[domain/…]` の名前）の並び。ここに書かないドメインは使われない |
| `id_provider` | ユーザーの**情報**の引き先（`ldap`、`ad`、`ipa`、`files`） |
| `auth_provider` | **認証**の方法（`ldap`、`krb5`、`ad`） |
| `ldap_uri` | LDAP サーバーの URI |
| `ldap_search_base` | 検索の起点の DN |
| `cache_credentials` | 認証の情報を覚えて、オフラインでもログインできるようにする |

:::warn 試験の注意：sssd.conf は root の 0600
`/etc/sssd/sssd.conf` は、**所有者が root、パーミッションが 0600** でないと、sssd が読み込みを拒みます。Rocky Linux 9 で 0644 にして `sssctl config-check` を実行すると、「File ownership and permissions check failed. Expected root:root and 0600.」と出ます。
:::

PAM の側は、pam_unix の下に pam_sss を足します。Rocky Linux 9 で `authselect select sssd` を実行したあとの system-auth（抜粋）です。

```text
auth        sufficient    pam_unix.so nullok
auth        sufficient    pam_sss.so forward_pass
auth        required      pam_deny.so

account     required      pam_unix.so
account     [default=bad success=ok user_unknown=ignore] pam_sss.so

password    sufficient    pam_unix.so sha512 shadow nullok use_authtok
password    sufficient    pam_sss.so use_authtok

session     required      pam_unix.so
session     optional      pam_sss.so
```

ローカルのユーザーは pam_unix で成功して終わり、`/etc/shadow` にいないユーザーは次の pam_sss が SSSD に聞きます。どちらもだめなら pam_deny で失敗です。

## LDAP は、木の形のデータベース {#ldap}

```fig tree LDAP のディレクトリ情報ツリー（DIT）。1 つの箱が 1 つのエントリ。エントリの名前（DN）は、自分の RDN から根に向かって、カンマでつないで書く
{
  root: { label: 'dc=example,dc=jp', kind: 'dir', note: 'サフィックス（木の根）', children: [
    { label: 'ou=People', kind: 'dir', note: '人を入れる入れ物', children: [
      { label: 'uid=ken', hl: true, note: 'DN は uid=ken,ou=People,dc=example,dc=jp' },
      { label: 'uid=mika', note: 'DN は uid=mika,ou=People,dc=example,dc=jp' },
    ] },
    { label: 'ou=Group', kind: 'dir', note: 'グループを入れる入れ物', children: [
      { label: 'cn=sales', note: 'DN は cn=sales,ou=Group,dc=example,dc=jp' },
    ] },
  ] },
}
```

**LDAP**（Lightweight Directory Access Protocol）は、**ディレクトリ**（directory）に問い合わせるためのプロトコルです。ここでのディレクトリは、ファイルを入れるフォルダではなく、「人や機械の情報を、木の形に整理して引けるようにしたデータベース」のことです。読み出しが多く、書き込みが少ない使い方に向いています。

人の名前から電話番号やメールアドレスを引く使い方を、個人名の電話帳になぞらえて**ホワイトページ**と呼びます。社内のアドレス帳がその例です。ユーザーの認証の情報（UID、パスワード）を入れておけば、ログインにも使えます。

| 用語 | 意味 |
| --- | --- |
| **エントリ** | 木の 1 つの節。1 人の人、1 つのグループなどにあたる |
| **属性** | エントリが持つ「名前: 値」の組（`mail: ken@example.jp`）。同じ属性を複数持てる |
| **DN**（識別名、Distinguished Name） | エントリを木の中でただ 1 つに決める名前。`uid=ken,ou=People,dc=example,dc=jp` |
| **RDN**（相対識別名） | DN のいちばん左の 1 つ（`uid=ken`）。同じ親の下で重ならない |
| **DIT**（ディレクトリ情報ツリー） | エントリが作る木の全体 |
| **サフィックス** | その木の根の DN（`dc=example,dc=jp`） |
| **objectClass** | そのエントリが何の種類かを表す属性。持てる属性は、これで決まる |

DN は、**下（自分）から上（根）へ**、カンマでつないで書きます。ファイルのパス（`/home/ken`）とは向きが逆です。

DN に出てくる属性の名前は、決まった略語です。

| 略語 | 元の語 | 使いどころ |
| --- | --- | --- |
| `dc` | domain component | ドメイン名の 1 区切り（example.jp → `dc=example,dc=jp`） |
| `o` | organization | 組織 |
| `ou` | organizational unit | 組織の中の部門、入れ物 |
| `cn` | common name | 一般的な名前（人の氏名、グループの名前） |
| `sn` | surname | 姓 |
| `uid` | user ID | ログイン名 |
| `c` / `l` | country / locality | 国 / 地域 |

### LDIF：エントリをテキストで書く

**LDIF**（LDAP Data Interchange Format）は、エントリをテキストで表す形式です。登録、変更、バックアップのどれにも使います。

```text
dn: ou=People,dc=example,dc=jp
objectClass: organizationalUnit
ou: People

dn: uid=ken,ou=People,dc=example,dc=jp
objectClass: inetOrgPerson
objectClass: posixAccount
cn: Ken Sato
sn: Sato
uid: ken
uidNumber: 2001
gidNumber: 2001
homeDirectory: /home/ken
mail: ken@example.jp
```

| 決まり | 内容 |
| --- | --- |
| 最初の行 | `dn:` で、そのエントリの DN を書く |
| 2 行目から | `属性名: 値`。**コロンの後ろに空白 1 つ** |
| エントリの区切り | **空行** |
| 値が base64 のとき | `属性名:: 値`（**コロン 2 つ**）。日本語やバイナリの値、パスワードのハッシュ |
| 長い行の続き | 次の行を**空白 1 つ**で始める |
| コメント | 行頭が `#` |
| 順番 | 親のエントリを、子より先に書く（親がないと登録できない） |

## LDAP のクライアントコマンドは、-x -D -W -b が共通 {#ldap-client}

LDAP サーバーに**ネットワークごしに**（LDAP のプロトコルで）問い合わせるコマンドは、名前が `ldap` で始まります。Debian 系は `ldap-utils`、Red Hat 系は `openldap-clients` パッケージに入っています。

| コマンド | すること |
| --- | --- |
| `ldapsearch` | エントリを検索する |
| `ldapadd` | エントリを追加する |
| `ldapmodify` | エントリを変更する（追加、削除もできる） |
| `ldapdelete` | エントリを削除する |
| `ldappasswd` | エントリのパスワードを変える |

サーバーへのつなぎ方と名乗り方のオプションは、5 つとも同じです。

| オプション | 意味 |
| --- | --- |
| `-x` | **簡易認証**（DN とパスワード）を使う。付けないと SASL 認証になる |
| `-H URI` | 接続先（`ldap://ldap.example.jp`、`ldaps://…`、`ldapi:///`） |
| `-D DN` | この DN でサーバーに**バインド**（ログイン）する。省くと匿名 |
| `-W` | バインドのパスワードを、プロンプトで聞く |
| `-w パスワード` | バインドのパスワードを、コマンドラインに書く |
| `-f ファイル` | LDIF（や DN の一覧）をファイルから読む。省くと標準入力 |
| `-c` | エラーがあっても止まらず、続ける |
| `-Z` | StartTLS で暗号化する（`-ZZ` は、できなければやめる） |

:::warn 試験の注意：大文字と小文字で意味が違う
`-W` は「パスワードを**聞く**」、`-w secret` は「パスワードを**書く**」です。`-D` はバインドする DN、`-b` は検索の起点、`-H` は接続先の URI です。`-x` を忘れると SASL 認証を試みて失敗します。
:::

接続先と検索の起点の既定値は、クライアントの設定ファイル **`ldap.conf`** に書けます。Debian 系は `/etc/ldap/ldap.conf`、Red Hat 系は `/etc/openldap/ldap.conf` です。

```text
BASE    dc=example,dc=jp
URI     ldap://ldap.example.jp
```

LDAP の標準のポートは **389 番**（`ldap://`。StartTLS もこのポート）、最初から TLS で包む `ldaps://` は **636 番**です。`ldapi:///` は、同じ機械の UNIX ドメインソケットでつなぎます。

### ldapsearch：検索する

```console
$ ldapsearch -x -LLL -b dc=example,dc=jp "(uid=ken)" cn mail
dn: uid=ken,ou=People,dc=example,dc=jp
cn: Ken Sato
mail: ken@example.jp
```

並びは「オプション、**フィルタ**、**欲しい属性**」です。属性を省くと、読める属性を全部出します。

| オプション | 意味 |
| --- | --- |
| `-b DN` | 検索の起点（search base）。この DN から下を探す |
| `-s 範囲` | 探す範囲。`sub`（起点とその下の全部。既定）、`one`（起点の 1 つ下だけ）、`base`（起点のエントリだけ） |
| `-L` / `-LL` / `-LLL` | 出力を素の LDIF に近づける。`-LLL` はコメントも版の行も出さない |

`-LLL` を付けないと、結果の前後に `# extended LDIF` や `# numEntries: 1` などのコメントが付きます。スクリプトで使うときは `-LLL` にします。

範囲の違いを、上の図の木で確かめた結果です。

```console
$ ldapsearch -x -LLL -b dc=example,dc=jp -s base dn
dn: dc=example,dc=jp

$ ldapsearch -x -LLL -b dc=example,dc=jp -s one dn
dn: ou=People,dc=example,dc=jp
```

`-s one` では、2 つ下にいる `uid=ken` は出ません。

**フィルタ**は、かっこで囲んだ「属性=値」です。組み合わせる記号は、**かっこの前**に書きます。

| フィルタ | 意味 |
| --- | --- |
| `(uid=ken)` | uid が ken |
| `(cn=Ken*)` | cn が Ken で始まる（`*` は任意の文字列） |
| `(mail=*)` | mail の属性を持っている |
| `(&(objectClass=inetOrgPerson)(mail=*@example.jp))` | **AND**。両方を満たす |
| `(\|(uid=ken)(uid=mika))` | **OR**。どちらかを満たす |
| `(!(uid=ken))` | **NOT**。満たさない |
| `(uidNumber>=2000)` | 2000 以上（`<=` もある） |

フィルタを省くと `(objectClass=*)`（すべてのエントリ）になります。シェルが `*` や `&` や `|` を解釈しないように、フィルタは引用符で囲みます。

### ldapadd と ldapmodify：追加する、変える

`ldapadd` は、LDIF に書いたエントリを追加します。書き込みには権限が要るので、管理者の DN でバインドします。

```console
$ ldapadd -x -D cn=admin,dc=example,dc=jp -W -f base.ldif
Enter LDAP Password:
adding new entry "ou=People,dc=example,dc=jp"

adding new entry "uid=ken,ou=People,dc=example,dc=jp"
```

同じ LDIF をもう一度流すと、1 つ目のエントリで `ldap_add: Already exists (68)` と出て止まります。`-c` を付ければ、エラーのエントリを飛ばして最後まで進みます。

`ldapmodify` は、**どう変えるかを書いた LDIF** を読みます。ふつうの LDIF に、`changetype:` と操作の行が増えます。

```text
dn: uid=ken,ou=People,dc=example,dc=jp
changetype: modify
replace: mail
mail: ken.sato@example.jp
-
add: description
description: sales
-
delete: telephoneNumber
```

| 行 | 意味 |
| --- | --- |
| `changetype: modify` | このエントリの属性を変える。ほかに `add`（エントリを足す）、`delete`（エントリを消す）、`modrdn`（RDN を変える） |
| `replace: 属性` | その属性の値を、次の行の値に**置き換える** |
| `add: 属性` | その属性に、値を**足す** |
| `delete: 属性` | その属性を消す（値を書けば、その値だけを消す） |
| `-`（ハイフンだけの行） | 1 つのエントリの中で、操作を区切る |

```console
$ ldapmodify -x -D cn=admin,dc=example,dc=jp -W -f mod.ldif
modifying entry "uid=ken,ou=People,dc=example,dc=jp"
```

:::warn 試験の注意：ldapadd は ldapmodify -a
`ldapadd` は、**`ldapmodify -a`** と同じです。`-a` は「`changetype:` のない LDIF を、追加として扱う」という意味です。`-a` を付けない `ldapmodify` に `changetype:` のない LDIF を渡すと、「modify operation type is missing」というエラーになります。
:::

### ldapdelete と ldappasswd

`ldapdelete` は、引数（または `-f` のファイル）に書いた DN のエントリを消します。LDIF は要りません。

```console
$ ldapdelete -x -D cn=admin,dc=example,dc=jp -W uid=taro,ou=People,dc=example,dc=jp
$ ldapdelete -x -D cn=admin,dc=example,dc=jp -W ou=People,dc=example,dc=jp
ldap_delete: Operation not allowed on non-leaf (66)
	additional info: subordinate objects must be deleted first
```

子を持つエントリは、そのままでは消せません。**`-r`** を付けると、下のエントリごと消します。

`ldappasswd` は、エントリの `userPassword` 属性を変えます。サーバーがハッシュにして保存します。

```console
$ ldappasswd -x -D cn=admin,dc=example,dc=jp -W -s newpass uid=ken,ou=People,dc=example,dc=jp
$ ldappasswd -x -D cn=admin,dc=example,dc=jp -W uid=mika,ou=People,dc=example,dc=jp
New password: zKIh58ji
```

| オプション | 意味 |
| --- | --- |
| `-s 新パスワード` | 新しいパスワードをコマンドラインに書く |
| `-S` | 新しいパスワードをプロンプトで聞く |
| `-a 旧パスワード` / `-A` | 古いパスワードを書く / プロンプトで聞く |
| 最後の引数（DN） | パスワードを変える相手。**省くと、バインドした自分** |

`-s` も `-S` も付けないと、2 つ目の例のように、サーバーが新しいパスワードを作って表示します。

:::tip ldappasswd と slappasswd
名前が似ている `slappasswd` は、パスワードのハッシュ（`{SSHA}t405Rk8s…`）を**作って表示するだけ**のコマンドです。サーバーには何も送りません。設定の `olcRootPW` に書く値を作るときに使います。
:::

## slapd の設定は、cn=config という LDAP の木に入っている {#slapd}

```fig graph OpenLDAP のサーバー slapd と、2 種類の道具。ldap で始まるコマンドは、動いている slapd にネットワークごしに頼む。slap で始まるコマンドは、slapd を通さずにデータベースのファイルを直接読み書きする
{
  col: 250, row: 100,
  nodes: [
    { id: 'cli', label: 'ldapsearch・ldapadd\nldapmodify・ldapdelete', sub: 'クライアント（オンライン）', x: 0, y: 0, kind: 'accent' },
    { id: 'slapd', label: 'slapd', sub: 'TCP 389 / 636', x: 1.1, y: 0, kind: 'stack' },
    { id: 'conf', label: 'slapd.d/', sub: '設定（cn=config）', x: 2.2, y: 0, kind: 'heap' },
    { id: 'db', label: '/var/lib/ldap/', sub: 'データ（data.mdb）', x: 2.2, y: 1, kind: 'heap' },
    { id: 'tool', label: 'slapcat・slapadd\nslapindex', sub: '管理用（オフライン）', x: 0, y: 1, kind: 'ext' },
  ],
  edges: [
    { from: 'cli', to: 'slapd', label: 'LDAP' },
    { from: 'slapd', to: 'conf' }, { from: 'slapd', to: 'db' },
    { from: 'tool', to: 'db', label: '直接', style: 'dashed' },
  ],
}
```

**OpenLDAP** は、Linux で広く使われる LDAP サーバーです。サーバーのデーモンが **`slapd`**（Standalone LDAP Daemon）で、エントリは **`/var/lib/ldap/`** のデータベースのファイルに入ります（いまの既定の形式は MDB で、`data.mdb` と `lock.mdb` の 2 つ）。

設定の方法は、新旧 2 つあります。

| | slapd.conf（古い） | **slapd-config**（いまの方法） |
| --- | --- | --- |
| 置き場所 | `slapd.conf` という 1 つのテキスト | `slapd.d/` ディレクトリの中の LDIF（`cn=config` という木） |
| Debian 系 | `/etc/ldap/slapd.conf` | `/etc/ldap/slapd.d/` |
| Red Hat 系 | `/etc/openldap/slapd.conf` | `/etc/openldap/slapd.d/` |
| 変え方 | ファイルを書き換える | `ldapmodify` などで `cn=config` のエントリを変える |
| 反映 | slapd の**再起動が要る** | **再起動なし**で、その場で効く |
| 属性の名前 | `suffix`、`rootdn` | `olcSuffix`、`olcRootDN`（先頭に **olc**） |

slapd-config では、設定そのものが LDAP のエントリです。`olc` は OpenLDAP Configuration の略です。`slapd.d/` の下の LDIF ファイルは slapd が管理するものなので、**エディタで直接書き換えてはいけません**。

`cn=config` の木は、次の形です。Debian 12 に slapd を入れた直後の DN を並べます。

```console
# slapcat -n 0 | grep ^dn:
dn: cn=config
dn: cn=module{0},cn=config
dn: cn=schema,cn=config
dn: cn={0}core,cn=schema,cn=config
dn: cn={1}cosine,cn=schema,cn=config
dn: cn={2}nis,cn=schema,cn=config
dn: cn={3}inetorgperson,cn=schema,cn=config
dn: olcDatabase={-1}frontend,cn=config
dn: olcDatabase={0}config,cn=config
dn: olcDatabase={1}mdb,cn=config
```

| エントリ | 中身 |
| --- | --- |
| `cn=config` | サーバー全体の設定（ログのレベル、PID ファイルの場所） |
| `cn=schema,cn=config` | スキーマ。その下に、読み込んだスキーマが 1 つずつ並ぶ |
| `olcDatabase={-1}frontend` | すべてのデータベースに共通の設定 |
| `olcDatabase={0}config` | 設定の木（cn=config）自身のデータベース |
| `olcDatabase={1}mdb` | エントリを入れる、ふつうのデータベース |

`{0}`、`{1}` は順番を表す番号です。データを入れるデータベースの設定を見ます。

```text
dn: olcDatabase={1}mdb,cn=config
objectClass: olcDatabaseConfig
objectClass: olcMdbConfig
olcDatabase: {1}mdb
olcDbDirectory: /var/lib/ldap
olcSuffix: dc=example,dc=jp
olcAccess: {0}to attrs=userPassword by self write by anonymous auth by * none
olcAccess: {1}to attrs=shadowLastChange by self write by * read
olcAccess: {2}to * by * read
olcRootDN: cn=admin,dc=example,dc=jp
olcRootPW:: e1NTSEF9d0o4bzIxdjZnSm91VlI1a0NoVWl2aUlSSitnTWt3V2w=
olcDbIndex: objectClass eq
olcDbIndex: cn,uid eq
```

| slapd-config の属性 | slapd.conf での名前 | 意味 |
| --- | --- | --- |
| `olcDatabase` | `database` | データベースの種類（`mdb` など） |
| `olcSuffix` | `suffix` | このデータベースが受け持つ木の根の DN |
| `olcRootDN` | `rootdn` | 管理者の DN。**アクセス制御を受けず**、何でもできる |
| `olcRootPW` | `rootpw` | 管理者のパスワード（`slappasswd` で作ったハッシュ） |
| `olcDbDirectory` | `directory` | データベースのファイルを置くディレクトリ（`/var/lib/ldap`） |
| `olcDbIndex` | `index` | 検索を速くする索引。`属性 種類`（`eq` は一致、`sub` は部分一致、`pres` は有無） |
| `olcAccess` | `access` | アクセス制御 |
| `olcLogLevel` | `loglevel` | ログに出す内容 |

`olcRootPW::` のコロンが 2 つなのは、値が base64 だからです（[LDIF の決まり](#ldap)）。

設定を変えるときも、LDIF と ldapmodify です。Debian 系の既定では、root が `ldapi:///`（UNIX ドメインソケット）に **`-Y EXTERNAL`**（OS のユーザーで名乗る SASL の方式）でつなぐと、cn=config を書き換えられます。

```console
# cat index.ldif
dn: olcDatabase={1}mdb,cn=config
changetype: modify
add: olcDbIndex
olcDbIndex: mail eq,sub
# ldapmodify -Q -Y EXTERNAL -H ldapi:/// -f index.ldif
modifying entry "olcDatabase={1}mdb,cn=config"
```

slapd を再起動しなくても、この時点で索引の設定が効いています。設定全体の検査は `slaptest` で行います（`slaptest -F /etc/ldap/slapd.d` で「config file testing succeeded」）。

### アクセス制御（slapd.access）

誰が、どのエントリのどの属性を、読めるか・書けるかを決めるのが `olcAccess`（slapd.conf では `access`）です。書き方の説明は、`man slapd.access` にあります。

```text
access to <何に> by <誰が> <どこまで> [by <誰が> <どこまで> …]
```

上の既定の 3 行を読みます。

```text
olcAccess: {0}to attrs=userPassword by self write by anonymous auth by * none
olcAccess: {1}to attrs=shadowLastChange by self write by * read
olcAccess: {2}to * by * read
```

1. `userPassword` 属性は、本人（`self`）は書ける。匿名（`anonymous`）は認証に使えるだけ。ほかの人（`*`）は何もできない
2. `shadowLastChange` 属性は、本人は書ける。ほかの人は読める
3. それ以外（`to *`）は、誰でも読める

| `<何に>` | 意味 |
| --- | --- |
| `*` | すべてのエントリ |
| `attrs=属性,属性` | その属性 |
| `dn.base="DN"` / `dn.subtree="DN"` | その DN のエントリ / その DN から下の全部 |

| `<誰が>` | 意味 |
| --- | --- |
| `*` | 誰でも（匿名も含む） |
| `anonymous` | バインドしていない人 |
| `users` | バインドした（認証された）人 |
| `self` | そのエントリ自身の DN でバインドした人 |
| `dn.exact="DN"` | その DN の人 |

`<どこまで>` は、下にいくほど強く、**強いものは弱いものを含みます**。

| レベル | できること |
| --- | --- |
| `none` | 何もできない |
| `disclose` | エラーのときに、存在を知らせてもらえる |
| `auth` | バインド（認証）に使える |
| `compare` | 値を比べられる |
| `search` | 検索のフィルタに使える |
| `read` | 検索の結果を読める |
| `write` | 書ける |
| `manage` | 管理の操作ができる |

:::warn 試験の注意：アクセス制御は、最初に合ったところで決まる
`olcAccess` は**上から順**に調べ、`to <何に>` が最初に合った行で決まります。その行の中でも、`by <誰が>` は左から調べて、最初に合ったものが使われます。だから、**細かい条件（`attrs=userPassword`）を上に、広い条件（`to *`）を下に**書きます。逆にすると、`to * by * read` が先に合って、パスワードのハッシュまで誰でも読めてしまいます。どの `by` にも合わなかった人は `none`、どの行にも合わなかったときも読めません。`olcRootDN` だけは、この制御を受けません。
:::

実際に、匿名で `userPassword` を検索しても、DN だけが返り、属性は出ません。匿名で書き換えようとすると「Strong(er) authentication required (8)」で断られます。

## スキーマは、エントリに書ける属性を決める {#schema}

エントリに、好きな属性を自由に書けるわけではありません。どんな属性があり、どの種類のエントリがどの属性を持てるかを決めた定義が、**スキーマ**です。スキーマは 2 種類の定義からできています。

| 定義 | 決めること |
| --- | --- |
| **属性型**（attributetype） | 属性の名前、値の書式（文字列、数、電話番号）、比べ方（大文字と小文字を区別するか） |
| **オブジェクトクラス**（objectclass） | エントリの種類。**必ず要る属性（MUST）**と、**あってもよい属性（MAY）** |

`cn=schema,cn=config` の下に入っている定義を見ます（折り返しを直してあります）。

```text
olcAttributeTypes: ( 0.9.2342.19200300.100.1.3 NAME ( 'mail' 'rfc822Mailbox' )
  DESC 'RFC1274: RFC822 Mailbox' EQUALITY caseIgnoreIA5Match
  SUBSTR caseIgnoreIA5SubstringsMatch SYNTAX 1.3.6.1.4.1.1466.115.121.1.26{256} )

olcObjectClasses: ( 2.5.6.6 NAME 'person' DESC 'RFC2256: a person' SUP top STRUCTURAL
  MUST ( sn $ cn ) MAY ( userPassword $ telephoneNumber $ seeAlso $ description ) )

olcObjectClasses: ( 1.3.6.1.1.1.2.0 NAME 'posixAccount' SUP top AUXILIARY
  MUST ( cn $ uid $ uidNumber $ gidNumber $ homeDirectory )
  MAY ( userPassword $ loginShell $ gecos $ description ) )
```

| 語 | 意味 |
| --- | --- |
| 先頭の数字（`2.5.6.6`） | **オブジェクト ID（OID）**。属性型やオブジェクトクラスを、世界でただ 1 つに決める番号。ドットで区切った数の並び |
| `NAME` | 名前。別名を並べて書ける（`mail` と `rfc822Mailbox`） |
| `SUP` | 親（superior）。親の MUST と MAY を受け継ぐ |
| `MUST ( … )` | 必ず要る属性。`$` で区切る |
| `MAY ( … )` | あってもよい属性 |
| `STRUCTURAL` | **構造型**。エントリの本体になるクラス。1 つのエントリに、必ず 1 系統だけ要る |
| `AUXILIARY` | **補助型**。構造型のクラスに付け足して、属性を増やす |
| `ABSTRACT` | **抽象型**。ほかのクラスの親になるためだけのクラス（`top`） |
| `EQUALITY` / `SYNTAX` | 値の比べ方 / 値の書式（これも OID で指す） |

[LDIF の例](#ldap)の ken は、`inetOrgPerson`（構造型。親をたどると person）と `posixAccount`（補助型）を持っています。person の MUST が `sn` と `cn` なので、`sn` を書き忘れると登録できません。

```console
$ ldapadd -x -D cn=admin,dc=example,dc=jp -W -f z.ldif
adding new entry "uid=z,ou=People,dc=example,dc=jp"
ldap_add: Object class violation (65)
	additional info: object class 'inetOrgPerson' requires attribute 'sn'
```

どのオブジェクトクラスにもない属性（`foo: bar`）を書くと、「Undefined attribute type (17)」になります。

スキーマは、ファイルとして配られています。Debian 系は `/etc/ldap/schema/`、Red Hat 系は `/etc/openldap/schema/` に、slapd.conf 用の `.schema` と、slapd-config 用の `.ldif` が入っています。

| スキーマ | 主なオブジェクトクラス | 用途 |
| --- | --- | --- |
| `core` | `person`、`organization`、`organizationalUnit` | 基本。必ず要る |
| `cosine` | （`mail` などの属性型） | inetorgperson と nis が使う |
| `inetorgperson` | `inetOrgPerson` | 人（メール、電話、部署）。ホワイトページ向け |
| `nis` | `posixAccount`、`posixGroup`、`shadowAccount` | UNIX のユーザーとグループ。ログインに使う |

slapd.conf では `include /etc/ldap/schema/nis.schema` と書いて読み込みます。slapd-config では、`ldapadd -Y EXTERNAL -H ldapi:/// -f /etc/ldap/schema/nis.ldif` のように、スキーマの LDIF を `cn=schema,cn=config` の下に追加します。inetorgperson と nis は、cosine が定義する属性型を使うので、**core → cosine → nis・inetorgperson の順**に読み込みます。

## slapcat・slapadd・slapindex は、データベースを直接扱う {#slaptools}

名前が `slap` で始まるコマンドは、サーバーの上で root が使う管理用の道具です。slapd に頼まず、**`/var/lib/ldap/` のデータベースを直接**読み書きします。そのため、バインドの DN やパスワード（`-D`、`-W`）は要らず、アクセス制御も受けません。

| コマンド | すること | slapd が動いているとき |
| --- | --- | --- |
| **`slapcat`** | データベースの中身を LDIF で書き出す（バックアップ） | 使える（読むだけ） |
| **`slapadd`** | LDIF をデータベースに入れる（リストア、最初の一括登録） | **止めてから** |
| **`slapindex`** | 索引を作り直す | **止めてから** |
| `slappasswd` | パスワードのハッシュを作る | 関係しない |
| `slaptest` | 設定を検査する | 関係しない |

共通のオプションです。

| オプション | 意味 |
| --- | --- |
| `-l ファイル` | LDIF のファイル（slapcat は書き出し先、slapadd は読み込み元）。省くと標準出力 / 標準入力 |
| `-n 番号` | 何番目のデータベースか。**`-n 0` は設定（cn=config）**、`-n 1` は最初のデータのデータベース（既定） |
| `-b サフィックス` | データベースをサフィックスの DN で選ぶ（`-b dc=example,dc=jp`） |
| `-F ディレクトリ` | 設定のディレクトリ（slapd.d）を指定する |
| `-f ファイル` | 設定ファイル（slapd.conf）を指定する |
| `-v` | くわしく表示する |
| `-c` | エラーがあっても続ける |

バックアップとリストアの流れです。

```console
# slapcat -l backup.ldif
# slapcat -n 0 -l config.ldif
# systemctl stop slapd
# slapadd -v -l backup.ldif
added: "dc=example,dc=jp" (00000001)
added: "ou=People,dc=example,dc=jp" (00000002)
added: "uid=ken,ou=People,dc=example,dc=jp" (00000003)
added: "uid=mika,ou=People,dc=example,dc=jp" (00000004)
# chown -R openldap:openldap /var/lib/ldap
# systemctl start slapd
```

1 行目がデータ、2 行目が設定のバックアップです。slapcat の LDIF には、`entryUUID`、`createTimestamp`、`modifiersName` など、サーバーが内部で付けた属性も入っています。ldapsearch の結果より完全なので、**バックアップには slapcat** を使います。

`slapindex` は、`olcDbIndex` を足したり変えたりしたあとに、すでに入っているエントリの索引を作り直すコマンドです。

```console
# systemctl stop slapd
# slapindex -v
indexing id=00000001
indexing id=00000002
indexing id=00000003
indexing id=00000004
```

:::warn 試験の注意：slapadd と slapindex のあとは、所有者を確かめる
root で `slapadd` や `slapindex` を実行すると、`/var/lib/ldap/` のファイルの所有者が root になることがあります。slapd は専用のユーザー（Debian 系は `openldap`、Red Hat 系は `ldap`）で動くので、そのままでは起動に失敗します。`chown -R` で所有者を戻します。slapindex は「Running as root! There's a fair chance slapd will fail to start. Check file permissions!」と警告を出します。
:::

:::tip ldapadd と slapadd を取り違えない
`ldapadd` は、**動いている** slapd にネットワークごしに頼むので、バインドの DN とパスワードが要り、アクセス制御とスキーマの検査を受けます。`slapadd` は、**止めた** slapd のデータベースに直接書くので、認証は要りません。大量のエントリを最初に入れるときや、バックアップから戻すときは slapadd です。
:::

:::key まとめ
- DHCP は DISCOVER → OFFER → REQUEST → ACK。サーバー UDP 67、クライアント UDP 68。DHCPv6 はサーバー 547、クライアント 546
- `/etc/dhcp/dhcpd.conf`：`subnet … netmask … { range 最初 最後; option routers …; }`、`default-lease-time`、`max-lease-time`、固定は `host { hardware ethernet …; fixed-address …; }`。行末は `;`。検査は `dhcpd -t`
- リースは `dhcpd.leases`（Debian 系 `/var/lib/dhcp/`、Red Hat 系 `/var/lib/dhcpd/`）。空でもファイルが要る。ログは syslog（`/var/log/syslog`、`/var/log/messages`）か `journalctl -u dhcpd`。`no free leases` は範囲切れ
- `arp -n` で IP アドレスと MAC アドレスの対応を見る
- IPv6 は radvd（`/etc/radvd.conf`）がルーター広告を流す。`AdvSendAdvert on;`、`prefix … { AdvAutonomous on; };`、M フラグは `AdvManagedFlag`、O フラグは `AdvOtherConfigFlag`。ゲートウェイは RA で知る
- PAM の設定は `/etc/pam.d/サービス名`（あれば `/etc/pam.conf` は無視。なければ `other`）。1 行は「タイプ 制御 モジュール 引数」
- タイプ：`auth`（本人か）、`account`（使ってよいか）、`password`（変更）、`session`（前後の準備）
- 制御：`required`（失敗でも残りを実行）、`requisite`（失敗で即終了）、`sufficient`（成功で即終了）、`optional`、`include`
- `pam_unix`（/etc/shadow）、`pam_cracklib`（パスワードの強さ。`minlen`、`retry`、`difok`、`dcredit=-1`）、`pam_limits`（`/etc/security/limits.conf`）、`pam_listfile`（`item=` `sense=` `file=` `onerr=`）、`pam_sss`（SSSD）
- `/etc/nsswitch.conf` の `passwd: files sss` は情報を引く順番。認証は PAM。SSSD の設定は `/etc/sssd/sssd.conf`（root の 0600、`[sssd]` と `[domain/名前]`）。キャッシュでオフラインでも認証できる
- LDAP：エントリ、属性、DN（下から上へカンマでつなぐ）、LDIF（空行で区切る、base64 は `::`）。ポートは 389、ldaps は 636
- クライアント：`-x`（簡易認証）、`-D`（バインド DN）、`-W`（聞く）/ `-w`（書く）、`-H`（URI）、`-b`（検索の起点）、`-s base|one|sub`、`-LLL`。フィルタは `(&(a=1)(b=2))`、`(|…)`、`(!…)`
- `ldapadd` = `ldapmodify -a`。ldapmodify の LDIF は `changetype: modify` と `add:` / `replace:` / `delete:`、区切りは `-`。`ldapdelete DN`（`-r` で下ごと）、`ldappasswd -s 新 DN`
- slapd のデータは `/var/lib/ldap/`。設定は slapd-config（`slapd.d/` の `cn=config`、属性は `olc…`、再起動なしで反映）。`olcSuffix`、`olcRootDN`、`olcRootPW`、`olcDbIndex`、`olcAccess`
- アクセス制御は `to <何に> by <誰が> <どこまで>`。上から最初に合った行で決まる。none < auth < compare < search < read < write
- スキーマ：属性型とオブジェクトクラス。OID、`MUST`、`MAY`、`SUP`、STRUCTURAL / AUXILIARY。`core`、`cosine`、`nis`、`inetorgperson`
- `slapcat`（LDIF に書き出す。`-n 0` は設定）、`slapadd`（LDIF を入れる。slapd を止める）、`slapindex`（索引を作り直す。slapd を止める）、`slappasswd`（ハッシュを作る）
:::

## 練習問題 {#practice}

### 2.07.1 DHCP サーバーの設定と管理

:::q 2.07.1-01 single
`/etc/dhcp/dhcpd.conf` に次の設定がある。この設定の説明として正しいものはどれか。

```text
default-lease-time 600;
max-lease-time 7200;

subnet 192.168.1.0 netmask 255.255.255.0 {
  range 192.168.1.100 192.168.1.200;
  option routers 192.168.1.1;
}
```
- [ ] `range` の 2 つの値は、ネットワークアドレスとブロードキャストアドレスである
- [x] クライアントがリースの長さを指定しなければ、600 秒の期限でアドレスを貸す
- [ ] `max-lease-time 7200;` は、同時に貸し出せるアドレスの数の上限である
- [ ] `option routers` は、クライアントに知らせる DNS サーバーである
- [ ] クライアントには 192.168.1.1 から順にアドレスを貸す
:::why
`default-lease-time` は、クライアントが期限を指定しないときのリースの長さ（秒）です（[dhcpd.conf](#dhcpd-conf)）。

- `range` は、動的に割り当てる範囲の最初と最後のアドレスです。貸すのは 192.168.1.100〜200 の中の空いているものです
- `max-lease-time` は、クライアントが長い期限を求めたときの上限（秒）で、台数ではありません
- `option routers` はデフォルトゲートウェイです。DNS サーバーは `option domain-name-servers` です
:::
:::

:::q 2.07.1-02 fill
dhcpd.conf で、クライアントにデフォルトゲートウェイ 192.168.1.1 を知らせる。空欄に入るオプションの名前を入力してください。

```text
subnet 192.168.1.0 netmask 255.255.255.0 {
  range 192.168.1.100 192.168.1.200;
  option ____ 192.168.1.1;
}
```
= routers
:::why
デフォルトゲートウェイは `option routers` です（[dhcpd.conf](#dhcpd-conf)）。`gateway` や `router`（単数）という名前のオプションはありません。DNS サーバーは `option domain-name-servers`、ネットマスクは `option subnet-mask` です。
:::
:::

:::q 2.07.1-03 single
MAC アドレスが `00:11:22:33:44:55` のプリンターに、いつも 192.168.1.10 を割り当てたい。dhcpd.conf の書き方として正しいものはどれか。
- [ ] `host printer { mac-address 00:11:22:33:44:55; ip-address 192.168.1.10; }`
- [x] `host printer { hardware ethernet 00:11:22:33:44:55; fixed-address 192.168.1.10; }`
- [ ] `host printer { hardware ethernet 00:11:22:33:44:55; range 192.168.1.10; }`
- [ ] `subnet printer { hardware ethernet 00:11:22:33:44:55; option routers 192.168.1.10; }`
- [ ] `fixed-address 192.168.1.10 hardware ethernet 00:11:22:33:44:55;`
:::why
固定の割り当ては、`host 名前 { }` の中に、`hardware ethernet`（MAC アドレス）と `fixed-address`（IP アドレス）を書きます（[dhcpd.conf](#dhcpd-conf)）。

- `mac-address`、`ip-address` という書き方は dhcpd.conf にはありません
- `range` は動的に割り当てる範囲で、最初と最後を書きます。固定の割り当てには使いません
- `subnet` は `subnet ネットワーク netmask マスク` の形で、`option routers` はゲートウェイです
- `fixed-address` は `host { }` の中に、1 つの文として書きます
:::
:::

:::q 2.07.1-04 single
`dhcpd.leases` の説明として**誤っているもの**はどれか。
- [ ] dhcpd が、貸し出したアドレスと相手の MAC アドレス、期限を記録するファイルである
- [ ] 追記されていくので、同じアドレスの `lease` が複数あるときは、後ろにあるものが有効である
- [x] 起動のときにこのファイルがなければ、dhcpd は何も言わずに作って動き始めるので、用意する必要はない
- [ ] Red Hat 系では `/var/lib/dhcpd/dhcpd.leases` にある
- [ ] `starts` と `ends` の時刻は UTC で書かれる
:::why
dhcpd は、起動のときに dhcpd.leases がないと「Can't open lease database」と出して止まります。空でもよいので、`touch` でファイルを作っておく必要があります（[リースとログ](#dhcp-leases)）。

ほかはどれも正しい説明です。場所は Debian 系が `/var/lib/dhcp/`、Red Hat 系が `/var/lib/dhcpd/` です。
:::
:::

:::q 2.07.1-05 single
クライアントがアドレスをもらえない。DHCP サーバーのログには、次の行が繰り返し出ている。原因として最も考えられるものはどれか。

```text
DHCPDISCOVER from 12:02:12:ec:ac:01 via eth0: network 192.168.1.0/24: no free leases
```
- [ ] クライアントの要求が、サーバーに届いていない
- [ ] dhcpd.conf に、192.168.1.0/24 の `subnet` の宣言がない
- [x] `range` で決めた範囲のアドレスをすべて貸し出している（または `range` を書いていない）
- [ ] dhcpd.leases のファイルがない
- [ ] クライアントが、別の DHCP サーバーの申し出を選んだ
:::why
「no free leases」は、そのサブネットに貸せる空きのアドレスがない、という意味です。`range` が狭くて使い切ったか、`range` を書いていないときに出ます（[ログを読む](#dhcp-leases)）。

- DHCPDISCOVER の行が出ているので、要求はサーバーに届いています
- `subnet` の宣言がないと、「No subnet declaration for …」と出て dhcpd は起動しません。ログに `network 192.168.1.0/24` と出ているので、宣言はあります
- dhcpd.leases がなければ、dhcpd は起動できません
- 別のサーバーが選ばれたのなら、こちらは DHCPOFFER まで進んでいるはずです
:::
:::

:::q 2.07.1-06 multi
DHCP（IPv4）の説明として正しいものを 2 つ選択してください。
- [x] DHCP サーバーは UDP の 67 番ポートで待ち受ける
- [ ] DHCP は TCP の 67 番と 68 番を使う
- [x] クライアントが最初に送る DHCPDISCOVER は、ブロードキャストで送られる
- [ ] メッセージの順番は、DHCPDISCOVER、DHCPREQUEST、DHCPOFFER、DHCPACK である
- [ ] DHCPACK は、クライアントがサーバーに送る確認のメッセージである
:::why
サーバーは UDP 67 番、クライアントは UDP 68 番です。クライアントはまだアドレスを持たないので、DHCPDISCOVER をブロードキャストで送ります（[DHCP の 4 つのメッセージ](#dhcp)）。

- DHCP は TCP ではなく UDP です
- 順番は DISCOVER → OFFER → REQUEST → ACK（DORA）です
- DHCPACK は、サーバーがクライアントに送る「確定」のメッセージです
:::
:::

:::q 2.07.1-07 single
DHCP で 192.168.1.100 を配ったはずだが、そのアドレスに別の機械が応えている疑いがある。同じネットワークにあるサーバーの上で、192.168.1.100 に対応する MAC アドレスを調べるコマンドとして適切なものはどれか。
- [ ] `dhcpd -T`
- [x] `arp -n`
- [ ] `radvd -c`
- [ ] `getent hosts 192.168.1.100`
- [ ] `ip route`
:::why
`arp -n` は、カーネルの ARP テーブル（IP アドレスと MAC アドレスの対応）を表示します。ここで見えた MAC アドレスを、dhcpd.leases の `hardware ethernet` と比べます（[arp](#dhcp-leases)）。

- `dhcpd -T` は、リースのファイルの検査です
- `radvd -c` は、radvd.conf の文法の検査です
- `getent hosts` は、名前と IP アドレスの対応を引きます。MAC アドレスは出ません
- `ip route` は経路の表です。MAC アドレスは `ip neigh` で見ます
:::
:::

:::q 2.07.1-08 fill
dhcpd を起動する前に、設定ファイルの文法だけを調べたい。空欄に入るオプションを入力してください。

```text
dhcpd ____ -cf /etc/dhcp/dhcpd.conf
```
= -t
:::why
`dhcpd -t` は、設定ファイルを読んで文法を調べ、起動せずに終わります。まちがいがあれば「line 3: semicolon expected.」のように行番号を出します（[dhcpd.conf](#dhcpd-conf)）。大文字の `-T` はリースのファイルの検査、`-cf` は設定ファイルの指定、`-d` はログを標準エラー出力に出すオプションです。
:::
:::

:::q 2.07.1-09 single
`/etc/radvd.conf` に次の設定がある。クライアントに「アドレスは DHCPv6 サーバーからもらうこと」と伝えるために、空欄に入るものはどれか。

```text
interface eth0 {
    AdvSendAdvert on;
    ____ on;
    prefix 2001:db8:1::/64 {
        AdvOnLink on;
    };
};
```
- [ ] `AdvAutonomous`
- [ ] `AdvOtherConfigFlag`
- [x] `AdvManagedFlag`
- [ ] `AdvDhcpAddress`
- [ ] `fixed-address`
:::why
`AdvManagedFlag on;` は、ルーター広告の M フラグを立てて、アドレスを DHCPv6 でもらうようにクライアントに伝えます（[radvd](#radvd)）。

- `AdvAutonomous` は `prefix { }` の中に書く設定で、そのプレフィックスで SLAAC をしてよい、という意味です
- `AdvOtherConfigFlag` は O フラグで、アドレス以外（DNS サーバーなど）を DHCPv6 でもらえ、という意味です
- `AdvDhcpAddress` という設定はありません
- `fixed-address` は dhcpd.conf の `host` の中に書くものです
:::
:::

:::q 2.07.1-10 multi
IPv6 のアドレスの配布について、正しいものを 2 つ選択してください。
- [x] radvd の設定で `AdvSendAdvert on;` を書かないと、そのインターフェースからルーター広告は送られない
- [ ] DHCPv6 サーバーは、DHCPv4 と同じ UDP の 67 番ポートで待ち受ける
- [x] DHCPv6 にはデフォルトゲートウェイを配るオプションがなく、クライアントはルーター広告でゲートウェイを知る
- [ ] radvd は、貸し出したアドレスを `dhcpd6.leases` に記録する
- [ ] ISC の dhcpd を DHCPv6 サーバーにするときも、サブネットは `subnet … netmask …` で宣言する
:::why
`AdvSendAdvert` の既定は `off` で、`on` にして初めてルーター広告を送ります。DHCPv6 はゲートウェイを配らないので、ルーター広告が必ず要ります（[radvd と DHCPv6](#radvd)）。

- DHCPv6 は、サーバーが UDP 547 番、クライアントが UDP 546 番です
- radvd はプレフィックスを広告するだけで、アドレスを貸しません。`dhcpd6.leases` は `dhcpd -6` のリースのファイルです
- DHCPv6 では `subnet6 2001:db8:1::/64 { range6 …; }` と書きます
:::
:::

### 2.07.2 PAM 認証

:::q 2.07.2-01 single
PAM のモジュールタイプのうち、「パスワードは合っているが、アカウントの有効期限が切れていないか、いまログインしてよいか」を確かめるものはどれか。
- [ ] `auth`
- [x] `account`
- [ ] `password`
- [ ] `session`
:::why
`account` は、認証とは別に、そのアカウントをいま使ってよいか（期限、時間帯、`/etc/nologin` など）を確かめます（[タイプ](#pam-syntax)）。`auth` は本人かどうかの確認、`password` はパスワードを変えるときの処理、`session` はログインの前後の準備と後片付けです。
:::
:::

:::q 2.07.2-02 single
PAM の制御 `required` と `requisite` の違いとして正しいものはどれか。
- [ ] `required` は失敗しても全体の結果に影響しないが、`requisite` は失敗すると全体が失敗になる
- [x] どちらも失敗すると全体が失敗になるが、`required` は残りのモジュールも実行し、`requisite` はその場で失敗を返す
- [ ] `required` は成功するとその場で成功を返し、`requisite` は残りのモジュールも実行する
- [ ] `required` は auth と account で、`requisite` は password と session でだけ使える
:::why
`required` も `requisite` も、失敗すれば全体が失敗です。`required` は、どこで失敗したかを相手に知らせないために残りも実行します。`requisite` は、その場で打ち切ります（[制御](#pam-syntax)）。

- 失敗しても影響しないのは `optional` です
- 成功したらその場で成功を返すのは `sufficient` です
- 制御は、どのタイプでも使えます
:::
:::

:::q 2.07.2-03 single
あるサービスの `/etc/pam.d/` のファイルに、auth の行が次の 2 つだけある。このサービスの認証の結果として正しいものはどれか。`pam_permit.so` は必ず成功し、`pam_deny.so` は必ず失敗するモジュールである。

```text
auth  sufficient  pam_permit.so
auth  required    pam_deny.so
```
- [x] 1 行目が成功した時点で認証は成功し、2 行目は実行されない
- [ ] 2 行目の required が失敗するので、認証は失敗する
- [ ] sufficient は結果に影響しないので、2 行目だけで決まり、認証は失敗する
- [ ] 2 つの結果が食い違うので、`/etc/pam.d/other` の設定で決まる
:::why
`sufficient` のモジュールが成功し、それより前に失敗した `required` がなければ、その場で成功を返します。2 行目の `pam_deny.so` は実行されません（[制御](#pam-syntax)）。

2 行の順番が逆（`required pam_deny.so` が先）なら、先に required が失敗しているので、認証は失敗します。結果に影響しないのは `optional` です。`/etc/pam.d/other` は、サービス名のファイルがないときに使われるものです。
:::
:::

:::q 2.07.2-04 single
`/etc/pam.d/` ディレクトリと `/etc/pam.conf` の両方に、sshd の設定が書かれている。このときの動きとして正しいものはどれか。
- [ ] `/etc/pam.conf` が優先され、`/etc/pam.d/sshd` は読まれない
- [ ] 両方を読み、`/etc/pam.conf` の行を先に実行する
- [x] `/etc/pam.d/` があるので、`/etc/pam.conf` は無視される
- [ ] 両方に設定があるとエラーになり、sshd にログインできなくなる
:::why
`/etc/pam.d/` ディレクトリがあるとき、`/etc/pam.conf` は読まれません（[PAM の設定の場所](#pam)）。`/etc/pam.conf` は 1 ファイルに全部を書く古い形で、各行の先頭にサービス名の欄があります。
:::
:::

:::q 2.07.2-05 fill
`pam_limits` モジュールが読む、ユーザーやグループごとの資源の上限（開けるファイルの数、プロセスの数など）を書くファイルを、絶対パスで入力してください（`.d` のディレクトリではなく、ファイルのほう）。
= /etc/security/limits.conf
:::why
`pam_limits` は、`/etc/security/limits.conf` と `/etc/security/limits.d/*.conf` を読んで、セッションに上限を付けます（[pam_limits](#pam-modules)）。`session required pam_limits.so` の行があるサービスで効きます。
:::
:::

:::q 2.07.2-06 single
`/etc/security/limits.conf` に次の行がある。意味として正しいものはどれか。

```text
@student  hard  nproc  20
```
- [ ] student というユーザーが開けるファイルの数の上限を、20 にする
- [ ] student グループのユーザーのプロセスの数のソフトリミットを 20 にする。ユーザーは自分で引き上げられる
- [x] student グループのユーザーのプロセスの数のハードリミットを、20 にする
- [ ] student グループのユーザーが同時にログインできる数を、20 にする
:::why
欄は「誰に・種類・項目・値」です。`@student` はグループ、`hard` はハードリミット（一般ユーザーは越えられない上限）、`nproc` はプロセスの数です（[pam_limits](#pam-modules)）。

- 先頭に `@` があるのでグループです。開けるファイルの数は `nofile` です
- ソフトリミットは `soft` です
- 同時にログインできる数は `maxlogins` です
:::
:::

:::q 2.07.2-07 single
`/etc/pam.d/sshd` に次の行を足した。動きの説明として正しいものはどれか。

```text
auth  required  pam_listfile.so item=user sense=deny file=/etc/ssh/denyusers onerr=succeed
```
- [ ] `/etc/ssh/denyusers` に書かれたユーザーだけが、SSH でログインできる
- [x] `/etc/ssh/denyusers` に書かれたユーザーは、SSH の認証に失敗する
- [ ] `/etc/ssh/denyusers` に書かれた接続元のホストからのログインを拒否する
- [ ] `/etc/ssh/denyusers` が存在しないと、だれも SSH でログインできなくなる
:::why
`item=user` はユーザー名を、`file=` の一覧と照らします。`sense=deny` なので、一覧に**ある**と失敗です。制御が `required` なので、認証全体が失敗します（[pam_listfile](#pam-modules)）。

- 一覧にある人だけを通すのは `sense=allow` です
- 接続元のホストで照らすのは `item=rhost` です
- `onerr=succeed` なので、ファイルが開けないときは成功として扱われます。全員を止めるのは `onerr=fail` です
:::
:::

:::q 2.07.2-08 multi
パスワードを変えるときの設定として、次の行がある。説明として正しいものを 2 つ選択してください。

```text
password  requisite  pam_cracklib.so retry=3 minlen=12 dcredit=-1 ucredit=0 lcredit=0 ocredit=0
```
- [x] 新しいパスワードには、12 文字以上の長さが求められる
- [ ] 新しいパスワードに含められる数字は、1 文字までである
- [x] 新しいパスワードには、数字が少なくとも 1 文字要る
- [ ] パスワードを 3 回まちがえると、アカウントがロックされる
- [ ] 過去 3 回ぶんのパスワードは、もう一度使えない
:::why
`minlen=12` は最小の長さです。`*credit` がどれも 0 かマイナスなので、長さの割り引き（クレジット）はなく、12 文字がそのまま下限になります。`dcredit=-1` のように `*credit` をマイナスにすると、「その種類を最低その数だけ含む」という意味になります（[pam_cracklib](#pam-modules)）。

- `ucredit` などを書かないと既定の 1 が効き、大文字・小文字・記号を使うごとに 1 文字ぶん短くても通るので、「12 文字以上」とは言えなくなります

- `dcredit=-1` は「最低 1 文字」で、上限ではありません
- `retry=3` は、弱いパスワードだったときに入力し直せる回数です。アカウントのロックではありません
- 過去のパスワードの使い回しを断るのは、pam_unix の `remember=` です
:::
:::

:::q 2.07.2-09 single
`/etc/nsswitch.conf` に次の行がある。意味として正しいものはどれか。

```text
passwd:     files sss
```
- [ ] ユーザーのパスワードを、まず `/etc/shadow` で、次に SSSD で照合する
- [x] ユーザーの情報（UID、ホームなど）を、まず `/etc/passwd` で、見つからなければ SSSD で引く
- [ ] ユーザーの情報を SSSD で引き、結果を `/etc/passwd` に書き込む
- [ ] `passwd` コマンドでパスワードを変えると、`/etc/passwd` と SSSD の両方に反映される
:::why
nsswitch.conf は、情報をどこから、どの順に引くかを決めます。`files` は `/etc/passwd`、`sss` は SSSD で、左から順に試して見つかったところで止まります（[nsswitch.conf と SSSD](#sssd)）。

パスワードの照合（認証）をするのは PAM で、nsswitch.conf ではありません。SSSD が `/etc/passwd` に書き込むこともありません。
:::
:::

:::q 2.07.2-10 single
LDAP にユーザー ken を登録し、クライアントに SSSD を設定した。クライアントで `id ken` を実行すると「no such user」と表示される。sssd は動いており、LDAP サーバーにも届いている。見直す設定として最も適切なものはどれか。
- [ ] `/etc/pam.d/` の auth の行に `pam_sss.so` があるか
- [x] `/etc/nsswitch.conf` の `passwd:` の行に `sss` があるか
- [ ] `/etc/security/limits.conf` に ken の行があるか
- [ ] `/etc/pam.d/` の session の行に `pam_limits.so` があるか
- [ ] sssd.conf の `cache_credentials` が `true` か
:::why
`id` は、ユーザーの情報を NSS（nsswitch.conf の順）で引きます。`passwd:` の行に `sss` がなければ、SSSD には聞きに行かず、`/etc/passwd` にいない ken は「いない」ことになります（[nsswitch.conf は認証をしない](#sssd)）。

- pam_sss は認証（パスワードの確認）の道です。`id` は PAM を通りません
- limits.conf と pam_limits は、資源の上限です
- `cache_credentials` は、オフラインでも認証できるようにする設定です
:::
:::

:::q 2.07.2-11 multi
SSSD の設定ファイルの説明として正しいものを 2 つ選択してください。
- [ ] 設定ファイルは `/etc/sssd.conf` である
- [x] `[sssd]` セクションの `domains` に書いたドメインだけが使われる
- [ ] `id_provider` は認証の方法、`auth_provider` はユーザーの情報の引き先を指定する
- [x] 所有者が root、パーミッションが 0600 でないと、sssd は設定ファイルを受け付けない
- [ ] `cache_credentials = true` にすると、SSSD はサーバーに一切問い合わせなくなる
:::why
`[domain/名前]` を書いても、`[sssd]` の `domains` に名前を並べなければ使われません。sssd.conf は root の 0600 が必須です（[SSSD の基本](#sssd)）。

- 場所は `/etc/sssd/sssd.conf` です
- 逆です。`id_provider` が情報の引き先、`auth_provider` が認証の方法です
- `cache_credentials` は、認証の情報を覚えておいて、サーバーに届かないときにも認証できるようにする設定です。届くときは問い合わせます
:::
:::

:::q 2.07.2-12 fill
ローカルの `/etc/shadow` にいないユーザーを、SSSD を通して LDAP で認証させたい。空欄に入るモジュールの名前を入力してください。

```text
auth   sufficient   pam_unix.so nullok
auth   sufficient   ____.so forward_pass
auth   required     pam_deny.so
```
= pam_sss
= pam_sss.so
:::why
SSSD に認証を頼む PAM のモジュールは `pam_sss` です（[SSSD の基本](#sssd)）。pam_unix で成功しなかったユーザーを、次の pam_sss が SSSD に問い合わせます。nsswitch.conf に書く語は `sss` で、モジュールの名前とは別です。
:::
:::

:::q 2.07.2-13 single
次の行の `nullok` の意味として正しいものはどれか。

```text
auth  sufficient  pam_unix.so nullok
```
- [ ] パスワードの入力を省いて、だれでも認証に成功させる
- [x] パスワードが空のアカウントでも、認証を認める
- [ ] `/etc/shadow` がなくても、エラーにしない
- [ ] 前のモジュールが受け取ったパスワードを、聞き直さずに使う
:::why
`nullok` は、パスワードが設定されていない（空の）アカウントを認めます。付けないと、空のパスワードのアカウントは pam_unix で認証できません（[pam_unix](#pam-modules)）。前のモジュールのパスワードを使うのは `use_first_pass`（聞き直さない）と `try_first_pass`（だめなら聞き直す）です。
:::
:::

:::q 2.07.2-14 multi
PAM のモジュールと役目の組み合わせとして正しいものを 2 つ選択してください。
- [x] `pam_limits` ― セッションに、資源の上限を付ける
- [ ] `pam_listfile` ― `/etc/shadow` のハッシュと、入力されたパスワードを照合する
- [ ] `pam_cracklib` ― ログインに続けて失敗したアカウントをロックする
- [x] `pam_nologin` ― `/etc/nologin` があるとき、root 以外のログインを拒否する
- [ ] `pam_unix` ― LDAP サーバーに問い合わせて認証する
:::why
`pam_limits` は limits.conf の上限を付け、`pam_nologin` は `/etc/nologin` があると root 以外を拒否します（[よく使う PAM モジュール](#pam-modules)）。

- `pam_listfile` は、ファイルに書いた名前の一覧で許可・拒否します。`/etc/shadow` と照合するのは `pam_unix` です
- `pam_cracklib` は、新しいパスワードの強さを調べます
- LDAP などリモートの認証は、SSSD を通す `pam_sss` です
:::
:::

:::q 2.07.2-15 multi
PAM の設定ファイルの説明として正しいものを 2 つ選択してください。
- [x] Red Hat 系では、多くのサービスのファイルが `include` や `substack` で `/etc/pam.d/system-auth` や `password-auth` を読み込む
- [ ] サービス名のファイルが `/etc/pam.d/` にないときは、`/etc/pam.d/default` が使われる
- [x] Debian 系では、`@include common-auth` のように書いて、共通のファイルを読み込む
- [ ] `/etc/pam.d/` のファイルの各行は、サービス名の欄から始まる

:::why
共通の設定は、Red Hat 系では system-auth と password-auth、Debian 系では common-auth などにまとめ、各サービスのファイルから読み込みます（[共通の設定を読み込む](#pam-syntax)）。

- サービス名のファイルがないときに使われるのは `/etc/pam.d/other` です
- `/etc/pam.d/` のファイルの行は、タイプ（`auth` など）から始まります。サービス名の欄があるのは `/etc/pam.conf` です
- モジュールの本体は、`/usr/lib64/security/`（Red Hat 系）などにあります。`/etc/pam.d/` は設定の場所です
:::

### 2.07.3 LDAP クライアントの利用方法

:::q 2.07.3-01 single
LDAP サーバーに匿名の簡易認証でつなぎ、`dc=example,dc=jp` から下で、uid が ken のエントリを検索する。コマンドとして正しいものはどれか（接続先は ldap.conf に書いてある）。
- [x] `ldapsearch -x -b dc=example,dc=jp "(uid=ken)"`
- [ ] `ldapsearch -x -D dc=example,dc=jp "(uid=ken)"`
- [ ] `ldapsearch -x -s dc=example,dc=jp "(uid=ken)"`
- [ ] `ldapsearch -b dc=example,dc=jp -W uid=ken`
- [ ] `ldapsearch -x -H dc=example,dc=jp "(uid=ken)"`
:::why
`-x` が簡易認証、`-b` が検索の起点です。`-D` を付けなければ匿名でつなぎます（[ldapsearch](#ldap-client)）。

- `-D` はバインドする DN です。検索の起点にはなりません
- `-s` は範囲（`base`、`one`、`sub`）です
- `-x` がないと SASL 認証を試みます。`-W` はバインドのパスワードを聞くオプションで、匿名には要りません
- `-H` は `ldap://ホスト` の形の URI です
:::
:::

:::q 2.07.3-02 single
LDAP クライアントの設定ファイル `ldap.conf` の説明として正しいものはどれか。
- [ ] slapd のアクセス制御を書くファイルである
- [x] `BASE`（検索の起点）や `URI`（接続先）の既定値を書くファイルで、Red Hat 系では `/etc/openldap/ldap.conf` にある
- [ ] SSSD が LDAP サーバーにつなぐための設定を書くファイルである
- [ ] `/var/lib/ldap/` にあり、slapd が自動で書き換える
:::why
`ldap.conf` は、`ldapsearch` などのクライアントが使う既定値（`BASE`、`URI`）を書くファイルです。Red Hat 系は `/etc/openldap/ldap.conf`、Debian 系は `/etc/ldap/ldap.conf` です（[クライアントコマンド](#ldap-client)）。

- アクセス制御は、サーバーの設定の `olcAccess`（slapd.conf では `access`）です
- SSSD の設定は `/etc/sssd/sssd.conf` です
- `/var/lib/ldap/` は、slapd のデータベースの場所です
:::
:::

:::q 2.07.3-03 single
objectClass が inetOrgPerson で、**かつ** mail の属性を持っているエントリを検索するフィルタとして正しいものはどれか。
- [ ] `(objectClass=inetOrgPerson)&(mail=*)`
- [ ] `(objectClass=inetOrgPerson && mail=*)`
- [x] `(&(objectClass=inetOrgPerson)(mail=*))`
- [ ] `(|(objectClass=inetOrgPerson)(mail=*))`
- [ ] `(objectClass=inetOrgPerson AND mail=*)`
:::why
LDAP のフィルタは、組み合わせの記号を**かっこの前**に書きます。AND は `(&(条件)(条件))` です。`(mail=*)` は「mail の属性を持っている」です（[フィルタ](#ldap-client)）。

- `|` は OR で、どちらかを満たすエントリになります
- `&&`、`AND`、条件の間に `&` を置く書き方は、LDAP のフィルタにはありません
:::
:::

:::q 2.07.3-04 single
ディレクトリに、次の 4 つのエントリがある。下のコマンドで表示される DN はどれか。

```text
dc=example,dc=jp
ou=People,dc=example,dc=jp
uid=ken,ou=People,dc=example,dc=jp
uid=mika,ou=People,dc=example,dc=jp
```

```text
ldapsearch -x -LLL -b dc=example,dc=jp -s one dn
```
- [ ] `dc=example,dc=jp` だけ
- [x] `ou=People,dc=example,dc=jp` だけ
- [ ] `dc=example,dc=jp` と `ou=People,dc=example,dc=jp`
- [ ] `uid=ken,…` と `uid=mika,…` の 2 つ
- [ ] 4 つすべて
:::why
`-s one` は、起点の**1 つ下**のエントリだけを探します。起点そのものと、2 つ下の ken と mika は入りません（[ldapsearch の範囲](#ldap-client)）。

- 起点だけを見るのは `-s base` です
- 4 つすべてが出るのは、既定の `-s sub`（起点とその下の全部）です
:::
:::

:::q 2.07.3-05 fill
`ldapmodify` で、ken の mail 属性のいまの値を、新しい値に置き換える。空欄に入る語を入力してください。

```text
dn: uid=ken,ou=People,dc=example,dc=jp
changetype: modify
____: mail
mail: ken.sato@example.jp
```
= replace
:::why
`replace: 属性` は、その属性の値を次の行の値に置き換えます（[ldapmodify](#ldap-client)）。`add: mail` は値を足すので、古い値も残ります。`delete: mail` は属性を消します。1 つのエントリで操作を続けるときは、`-` だけの行で区切ります。
:::
:::

:::q 2.07.3-06 single
`ldapadd` と同じ働きをするコマンドはどれか。
- [ ] `ldapmodify -c`
- [x] `ldapmodify -a`
- [ ] `ldapmodify -r`
- [ ] `slapadd`
- [ ] `ldapsearch -a`
:::why
`ldapadd` は `ldapmodify -a` と同じです。`-a` は、`changetype:` のない LDIF を追加として扱います（[ldapadd は ldapmodify -a](#ldap-client)）。

- `-c` は、エラーがあっても続けるオプションです
- `slapadd` は、slapd を通さずにデータベースへ直接書く、サーバーの上の管理用コマンドです。認証もアクセス制御も通らないので、同じ働きではありません
:::
:::

:::q 2.07.3-07 multi
`ldapdelete` の説明として正しいものを 2 つ選択してください。
- [x] 消したいエントリの DN を、引数（または `-f` で渡すファイル）に書く
- [ ] `changetype: delete` と書いた LDIF を渡さないと、エントリを消せない
- [x] 下に子のエントリがあるエントリは、`-r` を付けないと消せない
- [ ] slapd を止めてから実行する
- [ ] バインドの DN を指定しなくても、既定の設定でエントリを消せる
:::why
`ldapdelete` は DN を引数に取ります。子を持つエントリを消そうとすると「Operation not allowed on non-leaf (66)」になり、`-r` で下ごと消せます（[ldapdelete](#ldap-client)）。

- `changetype: delete` の LDIF は、`ldapmodify` で消すときの書き方です。ldapdelete には要りません
- `ldap` で始まるコマンドは、動いている slapd に頼みます。止めてから使うのは `slapadd` と `slapindex` です
- 書き込みには権限が要ります。匿名での変更は「Strong(er) authentication required」で断られます
:::
:::

:::q 2.07.3-08 single
次のコマンドの説明として正しいものはどれか。

```text
ldappasswd -x -D cn=admin,dc=example,dc=jp -W -s newpass uid=ken,ou=People,dc=example,dc=jp
```
- [ ] cn=admin のパスワードを newpass に変える。ken の DN は検索の起点である
- [ ] ken のパスワードのハッシュを作って表示する。サーバーには何も送らない
- [x] cn=admin としてバインドし（そのパスワードはプロンプトで聞かれる）、ken のパスワードを newpass に変える
- [ ] ken としてバインドし、古いパスワード newpass を新しいものに変える
:::why
`-D` と `-W` は、だれとしてバインドするか（ここでは管理者。パスワードはプロンプト）です。`-s` が新しいパスワード、最後の DN がパスワードを変える相手です（[ldappasswd](#ldap-client)）。

- 最後の DN を省いたときに、バインドした自分のパスワードが変わります
- ハッシュを作って表示するだけなのは `slappasswd` です
- 古いパスワードを渡すオプションは `-a`（聞くのは `-A`）です
:::
:::

:::q 2.07.3-09 fill
`ldapsearch` の結果を、コメントの行も LDIF の版の行も付けずに、エントリだけの LDIF で出したい。空欄に入るオプションを入力してください。

```text
ldapsearch -x ____ -b dc=example,dc=jp "(uid=ken)" cn mail
```
= -LLL
:::why
`-LLL` を付けると、`# extended LDIF` などのコメントも版の行も出ず、`dn:` から始まるエントリだけになります（[ldapsearch](#ldap-client)）。`-L` は LDIFv1 の形、`-LL` はコメントを消すところまでです。
:::
:::

:::q 2.07.3-10 multi
LDAP のクライアントコマンドに共通するオプションの説明として正しいものを 2 つ選択してください。
- [x] `-x` は、SASL ではなく簡易認証を使う
- [ ] `-w` は、バインドのパスワードをプロンプトで聞く
- [x] `-H` は、接続先を `ldap://ホスト` のような URI で指定する
- [ ] `-D` は、検索の起点の DN を指定する
- [ ] `-f` は、エラーがあっても処理を続ける
:::why
`-x` は簡易認証、`-H` は接続先の URI です（[共通のオプション](#ldap-client)）。

- `-w パスワード` はコマンドラインに書くほうです。プロンプトで聞くのは大文字の `-W` です
- `-D` はバインドする DN です。検索の起点は `-b` です
- `-f` は読み込むファイルの指定です。エラーでも続けるのは `-c` です
:::

### 2.07.4 OpenLDAP サーバーの設定

:::q 2.07.4-01 single
OpenLDAP の slapd-config（`cn=config` を使う設定の方法）の説明として正しいものはどれか。
- [ ] 設定は `slapd.conf` という 1 つのテキストファイルに書き、変えたら slapd を再起動する
- [x] 設定は `slapd.d/` の下に LDIF として入っていて、`ldapmodify` などで変えると、slapd を再起動しなくても効く
- [ ] `slapd.d/` の下の LDIF ファイルをエディタで書き換えるのが、正式な変え方である
- [ ] 設定の属性の名前は、`suffix`、`rootdn` のように、slapd.conf と同じである
:::why
slapd-config では、設定そのものが `cn=config` という木のエントリで、LDAP の操作で変えます。変更はその場で効きます（[slapd の設定](#slapd)）。

- 1 つのテキストファイルに書いて再起動するのは、古い slapd.conf の方法です
- `slapd.d/` のファイルは slapd が管理するもので、手で書き換えてはいけません
- 属性の名前は、`olcSuffix`、`olcRootDN` のように、先頭に `olc` が付きます
:::
:::

:::q 2.07.4-02 single
データベースのアクセス制御が、次の順に設定されている。結果として正しいものはどれか。

```text
olcAccess: {0}to * by * read
olcAccess: {1}to attrs=userPassword by self write by anonymous auth by * none
```
- [ ] userPassword 属性は本人だけが書け、ほかの人は読めない
- [x] {0} が先に合うので、userPassword 属性も含めて、だれでもすべての属性を読める
- [ ] 2 つの行のうち、制限のきびしい {1} が優先される
- [ ] 番号の大きい {1} が後から上書きするので、userPassword 属性はだれも読めない
:::why
アクセス制御は上（番号の小さいほう）から調べ、`to <何に>` が最初に合った行で決まります。`to *` はすべてに合うので、{1} は使われず、パスワードのハッシュまでだれでも読めてしまいます（[アクセス制御](#slapd)）。細かい条件を上に、`to *` を最後に書くのが決まりです。
:::
:::

:::q 2.07.4-03 fill
slapd の設定（`cn=config`）のデータベースを、LDIF に書き出してバックアップしたい。空欄に入るオプションと値を入力してください。

```text
slapcat ____ -l config.ldif
```
= -n 0
= -n0
= -b cn=config
:::why
`slapcat -n 0` は、0 番のデータベース、つまり設定（`cn=config`）を書き出します。何も付けないと、最初のデータのデータベース（1 番）が出ます（[slapcat](#slaptools)）。データベースはサフィックスでも選べるので、`-b cn=config` でも同じです。
:::
:::

:::q 2.07.4-04 single
`slapadd` の説明として正しいものはどれか。
- [ ] 動いている slapd に LDAP でつなぐので、`-D` でバインドする DN を指定する
- [ ] `ldapadd` の別名で、働きは同じである
- [x] slapd を通さずにデータベースへ直接書くので、slapd を止めてから実行する
- [ ] データベースの中身を LDIF で書き出す
- [ ] 設定の `olcAccess` で書き込みを許された DN だけが実行できる
:::why
`slapadd` は、LDIF を `/var/lib/ldap/` のデータベースに直接入れる、サーバーの上の管理用コマンドです。slapd を止めてから使い、認証もアクセス制御も通りません（[slapcat・slapadd・slapindex](#slaptools)）。

- LDAP でつないで `-D` を使うのは、`ldapadd` です。`ldapadd` は `ldapmodify -a` と同じで、slapadd とは別のものです
- LDIF に書き出すのは `slapcat` です
:::
:::

:::q 2.07.4-05 single
`slapindex` を実行する必要があるのは、どのときか。
- [ ] `ldapadd` でエントリを 1 つ追加したあと
- [x] `olcDbIndex`（索引の設定）を足したり変えたりして、すでにあるエントリの索引を作り直すとき
- [ ] `olcRootPW` に書く、パスワードのハッシュを作るとき
- [ ] 設定の文法を検査するとき
- [ ] データベースを LDIF に書き出すとき
:::why
`slapindex` は、いまの索引の設定に合わせて、すでに入っているエントリの索引を作り直します。slapd を止めてから実行し、あとで `/var/lib/ldap/` の所有者を確かめます（[slapindex](#slaptools)）。

- 動いている slapd にエントリを足したときは、slapd が索引も更新します
- ハッシュを作るのは `slappasswd`、設定の検査は `slaptest`、書き出しは `slapcat` です
:::
:::

:::q 2.07.4-06 multi
スキーマに、次の定義がある。説明として正しいものを 2 つ選択してください。

```text
objectclass ( 2.5.6.6 NAME 'person' SUP top STRUCTURAL
  MUST ( sn $ cn )
  MAY ( userPassword $ telephoneNumber $ seeAlso $ description ) )
```
- [x] `2.5.6.6` は、このオブジェクトクラスのオブジェクト ID（OID）である
- [ ] person のエントリには、telephoneNumber 属性が必ず要る
- [x] person のエントリには、sn と cn の属性が必ず要る
- [ ] person は補助型のクラスで、ほかの構造型のクラスに付け足して使う
- [ ] `SUP top` は、top が person の定義を受け継ぐことを表す
:::why
先頭の数字の並びが OID、`MUST` が必ず要る属性です（[スキーマ](#schema)）。

- telephoneNumber は `MAY`（あってもよい属性）です
- `STRUCTURAL` は構造型です。付け足して使う補助型は `AUXILIARY` です
- `SUP top` は、person の親が top で、**person が top を**受け継ぐ、という意味です
:::
:::

:::q 2.07.4-07 single
サフィックスが `dc=example,dc=jp` のディレクトリで、`ou=People` の下にある、uid が ken のエントリの DN として正しいものはどれか。
- [ ] `dc=jp,dc=example,ou=People,uid=ken`
- [ ] `uid=ken/ou=People/dc=example/dc=jp`
- [x] `uid=ken,ou=People,dc=example,dc=jp`
- [ ] `ou=People,uid=ken,dc=example,dc=jp`
- [ ] `uid=ken,ou=People,dc=example.jp`
:::why
DN は、自分の RDN（`uid=ken`）から根に向かって、カンマでつなぎます（[LDAP の木](#ldap)）。ファイルのパスとは向きが逆で、区切りは `/` ではありません。ドメイン名 example.jp は、`dc=example,dc=jp` と区切りごとに分けて書きます。
:::
:::

:::q 2.07.4-08 fill
OpenLDAP の slapd が、エントリを入れるデータベースのファイルを置く既定のディレクトリ（設定の `olcDbDirectory` の値）を、絶対パスで入力してください。
= /var/lib/ldap
= /var/lib/ldap/
:::why
データベースのファイル（MDB なら `data.mdb` と `lock.mdb`）は `/var/lib/ldap/` にあります（[slapd](#slapd)）。`/etc/ldap/slapd.d/`（Red Hat 系は `/etc/openldap/slapd.d/`）は、設定の置き場所です。
:::
:::

:::q 2.07.4-09 multi
LDIF の書き方として正しいものを 2 つ選択してください。
- [x] エントリとエントリの間は、空行で区切る
- [ ] 属性の名前と値は、`mail=ken@example.jp` のように `=` でつなぐ
- [x] 値が base64 で書かれているときは、`cn:: 5L2Q6Jek` のように、コロンを 2 つにする
- [ ] 1 つのエントリに、同じ名前の属性は 1 行しか書けない
- [ ] 子のエントリを、親のエントリより先に書く
:::why
エントリの区切りは空行、base64 の値は `属性名::` です（[LDIF](#ldap)）。

- 属性は `mail: ken@example.jp` のように、コロンと空白 1 つで書きます。`=` を使うのは DN の中です
- `objectClass` を 2 行書くように、同じ属性を複数持てます
- 親がないと子は登録できないので、親を先に書きます
:::
:::

:::q 2.07.4-10 single
`ldapadd` でエントリを追加しようとしたら、次のエラーになった。原因として正しいものはどれか。

```text
adding new entry "uid=z,ou=People,dc=example,dc=jp"
ldap_add: Object class violation (65)
	additional info: object class 'inetOrgPerson' requires attribute 'sn'
```
- [ ] バインドした DN に、書き込みの権限がない
- [ ] 同じ DN のエントリが、すでにある
- [ ] inetOrgPerson を定義するスキーマが、サーバーに読み込まれていない
- [x] LDIF に、オブジェクトクラスが必須（MUST）としている sn 属性が書かれていない
- [ ] 親のエントリ `ou=People,dc=example,dc=jp` がない
:::why
inetOrgPerson は、親の person から「`sn` と `cn` は必須（MUST）」を受け継いでいます。LDIF に `sn:` の行がないので、スキーマに反するとして断られました（[スキーマ](#schema)）。

- 権限がないときは、アクセスが足りないというエラーになります
- 同じ DN があるときは「Already exists (68)」です
- スキーマが読み込まれていなければ、オブジェクトクラスが必須の属性を求めることもできません
- 親がないときは「No such object (32)」です
:::
:::
