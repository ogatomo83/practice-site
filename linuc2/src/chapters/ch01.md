## 電源からカーネルまで：BIOS と UEFI の 2 つの道 {#firmware}

### BIOS と MBR

BIOS は、起動ディスクの最初のセクタ（**MBR**、512 バイト）を読み込んで実行します。MBR の中身は 3 つに分かれます。

| 位置 | 大きさ | 中身 |
| --- | --- | --- |
| 先頭 | 446 バイト | ブートローダの 1 段目（GRUB の `boot.img`） |
| 次 | 64 バイト | パーティション表（16 バイト × 4 つ） |
| 最後 | 2 バイト | 署名（`0x55AA`） |

446 バイトには GRUB の全部は入りません。1 段目は、すぐ後ろに置かれた 2 段目（`core.img`）を読み込み、2 段目が `/boot/grub/` のモジュールと `grub.cfg` を読みます。GPT のディスクを BIOS で起動するときは、`core.img` の置き場所として **BIOS ブートパーティション**を作ります。

### UEFI と ESP

UEFI は、FAT のファイルシステムを自分で読めます。ブートローダは、**EFI システムパーティション（ESP）** の中の `.efi` ファイルです。Linux では ESP を **`/boot/efi`** にマウントします。

```console
# ls /boot/efi/EFI/rocky
BOOTAA64.CSV  grubaa64.efi  mmaa64.efi  shim.efi  shimaa64-rocky.efi  shimaa64.efi
```

（ARM 64 ビットの Rocky Linux 9 の例です。x86_64 の機械では `shimx64.efi`、`grubx64.efi` という名前になります）

`shim` は、セキュアブート（署名のあるプログラムだけを起動する UEFI の機能）のための小さなブートローダです。UEFI が `shim` を実行し、`shim` が GRUB を実行します。

どの `.efi` をどの順番で試すかは、基板の不揮発メモリ（NVRAM）に**起動エントリ**として記録されています。これを Linux から見て、変えるのが **`efibootmgr`** です。

```console
# efibootmgr -v
BootCurrent: 0001
Timeout: 0 seconds
BootOrder: 0001,0000,0002
Boot0000* UEFI: PXE IPv4
Boot0001* Rocky Linux	HD(1,GPT,…)/File(\EFI\rocky\shimx64.efi)
Boot0002* debian	HD(1,GPT,…)/File(\EFI\debian\shimx64.efi)
```

| efibootmgr | すること |
| --- | --- |
| （オプションなし） | 起動エントリと順番（`BootOrder`）を表示する |
| `-v` | 詳しく表示する（`.efi` ファイルのパスも出る） |
| `-o 0002,0001` | 起動の順番（BootOrder）を決める |
| `-n 0002` | **次の 1 回だけ**起動するエントリ（BootNext）を決める |
| `-c -d /dev/sda -p 1 -L 名前 -l '\EFI\…\grubx64.efi'` | エントリを新しく作る（`-d` ディスク、`-p` パーティション番号、`-L` ラベル、`-l` ローダのパス） |
| `-b 0002 -B` | エントリ 0002 を消す |
| `-t 秒` | メニューを待つ時間を決める |

`efibootmgr` は、UEFI で起動した機械でしか使えません。UEFI で起動したかどうかは、**`/sys/firmware/efi` ディレクトリがあるか**で見分けられます。

**UEFI シェル**は、ファームウェアが持つコマンドラインです。OS が起動しないときに、`fs0:` のように ESP を選び、`.efi` ファイルを直接実行できます。起動エントリを編集する `bcfg` コマンドもあります。

| | BIOS | UEFI |
| --- | --- | --- |
| ブートローダの場所 | MBR（先頭 446 バイト）とその後ろ | ESP（FAT）の中の `.efi` ファイル |
| 典型のパーティション表 | MBR | GPT |
| 起動順の記録 | BIOS の設定画面 | NVRAM の起動エントリ（`efibootmgr`） |
| Linux でのマウント先 | — | `/boot/efi` |
| セキュアブート | ない | ある（`shim`） |

:::warn 試験の注意：ESP と /boot
- **`/boot`** … カーネル（`vmlinuz-…`）、initramfs、GRUB の設定とモジュール。ext4 や XFS でよい
- **`/boot/efi`** … ESP。UEFI が読むので **FAT**（vfat）。`.efi` ファイルを置く
- MBR の 512 バイトは「446 + 64 + 2」。パーティション表は 64 バイトで、基本パーティションが 4 つまでなのはこのため
:::

## GRUB 2 の設定：grub.cfg は書かずに、作る {#grub}

**GRUB 2** は、メニューを出し、選ばれたカーネルと initramfs をメモリに読み込み、カーネルに引数を渡して実行します。メニューの中身は `grub.cfg` に書かれていますが、このファイルは**手で編集しません**。元になるファイルから、コマンドで作ります。

Debian 系と Red Hat 系では、コマンドとディレクトリの名前が違います。Red Hat 系は、名前に **2** が付きます。

| | Debian 系 | Red Hat 系 |
| --- | --- | --- |
| 設定を作る | `grub-mkconfig -o /boot/grub/grub.cfg`（`update-grub` でも同じ） | `grub2-mkconfig -o /boot/grub2/grub.cfg` |
| ブートローダを入れる | `grub-install` | `grub2-install` |
| 設定の置き場所 | `/boot/grub/grub.cfg` | `/boot/grub2/grub.cfg` |
| 編集するファイル | `/etc/default/grub`、`/etc/grub.d/` | 同じ |

`grub-mkconfig` は、`-o` を付けないと結果を**標準出力**に出すだけで、ファイルは変わりません。Debian 系の `update-grub` は、中で `grub-mkconfig -o /boot/grub/grub.cfg` を実行するだけの短いスクリプトです。

```console
# cat /usr/sbin/update-grub
#!/bin/sh
set -e
exec grub-mkconfig -o /boot/grub/grub.cfg "$@"
```

### /etc/default/grub

Debian 12 の `/etc/default/grub` の主な行です。

```text
GRUB_DEFAULT=0
GRUB_TIMEOUT=5
GRUB_DISTRIBUTOR=`lsb_release -i -s 2> /dev/null || echo Debian`
GRUB_CMDLINE_LINUX_DEFAULT="quiet"
GRUB_CMDLINE_LINUX=""
#GRUB_DISABLE_RECOVERY="true"
```

| 変数 | 意味 |
| --- | --- |
| `GRUB_DEFAULT` | 既定で選ぶメニューの項目。**0 が 1 番上**。`saved` なら、`grub-set-default`（`grub2-set-default`）で保存した項目 |
| `GRUB_TIMEOUT` | メニューを出して待つ秒数。0 ならすぐ起動、-1 なら選ぶまで待つ |
| `GRUB_CMDLINE_LINUX` | **すべての** Linux の項目で、カーネルに渡す引数 |
| `GRUB_CMDLINE_LINUX_DEFAULT` | **ふつうの項目だけ**に足す引数（リカバリーモードの項目には付かない） |
| `GRUB_DISABLE_RECOVERY` | `true` なら、リカバリーモードの項目を作らない |

`/etc/grub.d/` には、番号で始まるスクリプトが並びます。`grub-mkconfig` は番号の順に実行し、出力をつないで `grub.cfg` にします。

| ファイル | 役目 |
| --- | --- |
| `00_header` | `/etc/default/grub` の変数を読み、全体の設定を出す |
| `10_linux` | `/boot` にあるカーネルを探して、メニューの項目を作る |
| `30_os-prober` | ほかの OS（Windows など）を探して、項目を作る |
| `40_custom` | 自分で書いた項目を足す場所 |

:::warn 試験の注意：変えたら、作り直す
`/etc/default/grub` や `/etc/grub.d/` を書き換えただけでは、何も変わりません。**`grub-mkconfig -o …`（`grub2-mkconfig -o …`）を実行して、はじめて `grub.cfg` に反映されます**。逆に、`grub.cfg` を直接編集しても、次に `grub-mkconfig` を実行した（カーネルを更新した）ときに消えます。
:::

### grub.cfg の 1 つの項目を読む

作られた `grub.cfg` の中で、メニューの 1 項目は `menuentry` のかたまりです。

```text
menuentry 'Debian GNU/Linux' {
        set root='hd0,gpt2'
        linux   /vmlinuz-6.1.0-18-amd64 root=UUID=3f1c… ro quiet
        initrd  /initrd.img-6.1.0-18-amd64
}
```

| 行 | 意味 |
| --- | --- |
| `set root='hd0,gpt2'` | **GRUB が**ファイルを探すパーティション。ディスクは **0 から**、パーティションは **1 から**数える。`hd0,gpt2` は 1 台目のディスクの 2 番目（GPT）、MBR なら `hd0,msdos1` のように書く |
| `linux` | 読み込むカーネルのファイルと、カーネルに渡す引数（**カーネルパラメータ**） |
| `initrd` | 読み込む initramfs のファイル |

`set root=` は GRUB から見た場所で、`linux` の行の `root=` は**カーネルがルートファイルシステムとしてマウントする装置**です。名前が同じでも別のものです。

メニューが出ているときに使うキーは 2 つです。

- **`e`** … 選んだ項目を、その場で編集する（`linux` の行に引数を足すなど）。編集したら `Ctrl + x` か `F10` で起動する。変更は**その 1 回だけ**
- **`c`** … GRUB のコマンドライン（`grub>`）に入る。`ls` でディスクを調べ、`linux`、`initrd`、`boot` を手で打って起動できる

### grub-install：ブートローダそのものを入れる

`grub-mkconfig` が作るのは設定（`grub.cfg`）だけです。ブートローダのプログラムをディスクに書き込むのは **`grub-install`**（`grub2-install`）です。MBR を壊した、ディスクを替えた、というときに使います。

```console
# grub-install /dev/sda                    ← BIOS：ディスク（パーティションではない）の MBR に書く
# grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=debian
                                           ← UEFI：ESP に .efi を置き、NVRAM にエントリを作る
```

| オプション | 意味 |
| --- | --- |
| `--boot-directory=DIR` | GRUB のファイルを `DIR/grub`（Red Hat 系は `DIR/grub2`）に置く。既定は `/boot` |
| `--efi-directory=DIR` | ESP のマウント先（ふつう `/boot/efi`） |
| `--bootloader-id=ID` | ESP の中のディレクトリ名と、NVRAM のエントリの名前 |
| `--target=TARGET` | 対象の種類。`i386-pc`（BIOS）、`x86_64-efi`（UEFI）など |
| `--removable` | NVRAM に頼らない既定のパス（`EFI/BOOT/`）に入れる |

### /boot の中身

```console
# ls /boot
System.map-5.14.0-741.22.1.el9_9.aarch64  efi    initramfs-5.14.0-741.22.1.el9_9.aarch64.img
config-5.14.0-741.22.1.el9_9.aarch64      grub2  vmlinuz-5.14.0-741.22.1.el9_9.aarch64
```

| ファイル | 中身 |
| --- | --- |
| `vmlinuz-バージョン` | 圧縮されたカーネルのイメージ |
| `initramfs-バージョン.img`（Red Hat 系）、`initrd.img-バージョン`（Debian 系） | initramfs（次の節） |
| `System.map-バージョン` | カーネルのシンボル（関数や変数の名前）と番地の対応表 |
| `config-バージョン` | そのカーネルをビルドしたときの設定（`.config` の写し） |
| `grub/`（Debian 系）、`grub2/`（Red Hat 系） | `grub.cfg` と GRUB のモジュール |
| `efi/` | ESP のマウントポイント |

:::deep Red Hat 系の新しい形：BLS と grubby
RHEL 8 以降では、メニューの各項目は `grub.cfg` の中ではなく、`/boot/loader/entries/*.conf` に 1 項目 1 ファイルで置かれます（BootLoaderSpec、BLS）。中身は `title`、`linux`、`initrd`、`options` の行です。カーネルパラメータを変えるには、`grubby --update-kernel=ALL --args="…"` を使います。古い教材の「UEFI では `/boot/efi/EFI/redhat/grub.cfg` に出力する」は RHEL 7・8 の話で、RHEL 9 では UEFI でも `/boot/grub2/grub.cfg` です。試験では「Red Hat 系は `grub2-mkconfig` と `/boot/grub2/`」を押さえておけば足ります。
:::

## initramfs とカーネルパラメータ {#initramfs}

GRUB は、カーネルと一緒に **initramfs** をメモリに読み込みます。initramfs は、**本当のルートファイルシステムをマウントするまでの、仮の小さなルートファイルシステム**です。

なぜ要るのでしょうか。ルートが LVM や RAID、暗号化ディスクの上にあると、マウントするにはそのためのドライバ（モジュール）が要ります。しかし、モジュールはルートファイルシステムの `/lib/modules/` にあります。この「鶏と卵」を解くために、必要なモジュールと道具をまとめた initramfs を、先にメモリに広げます。

名前が 2 つあるのは、歴史のためです。

| | initrd（初期 RAM ディスク） | initramfs |
| --- | --- | --- |
| 形 | ファイルシステムのイメージ（ext2 など） | **cpio アーカイブ**（gzip などで圧縮） |
| 使い方 | RAM ディスクというブロックデバイスとしてマウントする | メモリ上のファイルシステム（tmpfs）に展開する |
| 時代 | カーネル 2.4 まで | カーネル 2.6 から。いまはこちら |

いまの Linux が使うのは initramfs ですが、ファイル名（Debian 系の `initrd.img-…`）や GRUB のコマンド（`initrd`）には、古い名前が残っています。作るコマンドは [1.10](#modules-install) で見ます。

### カーネルパラメータ

GRUB が `linux` の行でカーネルに渡した引数は、起動した後も `/proc/cmdline` で見られます。小さな Linux で確かめます。

```sh run title="カーネルに渡された引数と、起動の記録"
cat /proc/cmdline
dmesg | grep -i -e "command line" -e initramfs -e "init process"
```

`dmesg` の 3 行は、「引数を受け取った」「initramfs を広げた」「`/init` を実行した」です。上の図の順番が、カーネルの記録に残っています。

| パラメータ | 意味 |
| --- | --- |
| `root=/dev/sda2`、`root=UUID=…` | ルートファイルシステムにする装置 |
| `ro` / `rw` | ルートを最初は読み取り専用 / 読み書きでマウントする |
| `quiet` | 起動中のカーネルのメッセージを減らす |
| `init=/bin/bash` | PID 1 として実行するプログラムを変える（既定は `/sbin/init`） |
| `systemd.unit=rescue.target` | systemd が目指すターゲットを変える（[1.7](#rescue)） |
| `single`、`1`、`S` | レスキューモード（シングルユーザーモード）で起動する |
| `crashkernel=256M` | kdump のためにメモリを取っておく（[1.14](#kdump)） |

`systemd.unit=` のように、名前に点が付いた引数は、カーネルではなく systemd が読みます。カーネルは自分の知らない引数を、そのまま PID 1 に渡します。

## unit ファイルの 3 つの置き場所と優先順位 {#unit-dirs}

systemd が管理するものは、すべて **unit** でした（[図解 LinuC 1.8](../../linuc/site/ch01.html#boot)、[図解 Linux 17.4](../../linux/site/ch17.html#unit)）。unit ファイルの置き場所は 3 つあり、**同じ名前のファイルがあれば、優先順位の高いほうだけが使われます**。

```fig graph unit ファイルの置き場所。上ほど優先順位が高い。パッケージが入れたファイルは書き換えず、/etc/systemd/system/ に置いて上書きする
{
  col: 300, row: 78,
  nodes: [
    { id: 'e', label: '/etc/systemd/system/', sub: '管理者が置く。優先順位 1（最高）', x: 0, y: 0, kind: 'accent' },
    { id: 'r', label: '/run/systemd/system/', sub: '実行中に作られる。再起動で消える。優先順位 2', x: 0, y: 1, kind: 'stack' },
    { id: 'u', label: '/usr/lib/systemd/system/', sub: 'パッケージが入れる。優先順位 3（最低）', x: 0, y: 2, kind: 'static' },
    { id: 's', label: 'systemd', sub: '同じ名前なら、上にあるものだけを読む', x: 1, y: 1, kind: 'ext', mono: false },
  ],
  edges: [ { from: 'e', to: 's' }, { from: 'r', to: 's', style: 'muted' }, { from: 'u', to: 's', style: 'muted' } ],
}
```

| ディレクトリ | だれが置くか | 優先順位 |
| --- | --- | --- |
| `/etc/systemd/system/` | **システムの管理者**。`enable` のシンボリックリンクもここ | 1（最高） |
| `/run/systemd/system/` | 実行中に作られるもの。`/run` は tmpfs なので**再起動で消える** | 2 |
| `/usr/lib/systemd/system/` | **パッケージ**（ディストリビューション）。更新で上書きされる | 3（最低） |

Debian 系では `/lib/systemd/system/` と書かれることがありますが、`/lib` は `/usr/lib` へのシンボリックリンクなので同じ場所です。`/etc/systemd/` には、unit のほかに systemd 自身の設定（`system.conf`、`journald.conf`、`logind.conf`）もあります。

パッケージの unit を変えたいときは、`/usr/lib/systemd/system/` のファイルを書き換えません。パッケージの更新で元に戻るからです。方法は 2 つあります。

| 方法 | 置くもの | コマンド |
| --- | --- | --- |
| **全体を置き換える** | `/etc/systemd/system/名前.service`（同じ名前のファイル） | `systemctl edit --full 名前` |
| **一部だけ変える**（ドロップイン） | `/etc/systemd/system/名前.service.d/*.conf`（変えたい行だけ） | `systemctl edit 名前`（`override.conf` ができる） |

小さな Linux で、全体を置き換えてみます。`ticker.service` は `/usr/lib/systemd/system/` にあります。

```sh run root title="/etc に同じ名前の unit を置くと、そちらが使われる"
systemctl cat ticker | head -3
cp /usr/lib/systemd/system/ticker.service /etc/systemd/system/ticker.service
sed -i 's/^Description=.*/Description=My ticker/' /etc/systemd/system/ticker.service
systemctl daemon-reload
systemctl cat ticker | head -3
```

`systemctl cat` の 1 行目が、読まれているファイルのパスです。`/etc/systemd/system/` に置いた後は、そちらに変わりました。unit ファイルを手で置いたり書き換えたりしたら、**`systemctl daemon-reload`** で systemd に読み直させます。

### systemd-delta：どこが上書きされているかを調べる

「このサーバーでは、パッケージの設定からどこが変えられているか」を一覧するのが **`systemd-delta`** です。Rocky Linux 9 で、`chronyd.service` を `/etc` に置き換え、`sshd.service` にドロップインを足し、`crond.service` を mask した後の出力です。

```console
# systemd-delta --no-pager
[OVERRIDDEN] /etc/systemd/system/chronyd.service → /usr/lib/systemd/system/chronyd.service
[MASKED]     /etc/systemd/system/crond.service → /usr/lib/systemd/system/crond.service
[EQUIVALENT] /etc/systemd/system/ctrl-alt-del.target → /usr/lib/systemd/system/ctrl-alt-del.target
[EXTENDED]   /usr/lib/systemd/system/sshd.service → /etc/systemd/system/sshd.service.d/override.conf
# systemd-delta --type=overridden      ← 種類をしぼる
```

| 表示 | 意味 |
| --- | --- |
| `[OVERRIDDEN]` | 優先順位の高い場所に同じ名前のファイルがあり、**中身が違う**（差分も表示される） |
| `[EQUIVALENT]` | 上書きされているが、中身は同じ |
| `[MASKED]` | `/dev/null` へのリンクで封じられている |
| `[EXTENDED]` | `.d/` のドロップインで、設定が足されている |
| `[REDIRECTED]` | 別のファイルへのシンボリックリンクで置き換えられている |

:::warn 試験の注意：優先順位は /etc > /run > /usr/lib
- **管理者の `/etc/systemd/system/` がいちばん強い**。パッケージの `/usr/lib/systemd/system/` がいちばん弱い
- `/run/systemd/system/` はその間。再起動で消える（`systemctl mask --runtime` などが使う）
- 上書きの一覧は `systemd-delta`。`systemctl list-unit-files` は unit の一覧で、上書きの関係は出ない
:::

## systemctl：状態を見る、変える、封じる {#systemctl}

`systemctl` の基本はレベル1 で見ました（[図解 LinuC 1.8](../../linuc/site/ch01.html#boot)）。ここでは、出力の読み方と、**mask** を足します。

```sh run root title="enable、start、status"
systemctl enable ticker
systemctl start ticker
systemctl status ticker
```

`status` の出力は、上から次のように読みます。

| 行 | 読み方 |
| --- | --- |
| `Loaded:` | 読んだ unit ファイルのパス。その後ろが **enable の状態**（`enabled` / `disabled` / `static` / `masked`）と、ディストリビューションの既定（`preset`） |
| `Active:` | **いまの状態**。`active (running)`、`inactive (dead)`、`failed` など |
| `Main PID:` | サービスの主なプロセス |
| `CGroup:` | サービスに属するプロセスの一覧 |
| 最後の数行 | ジャーナルに残った最近のログ |

「起動時に動くか」（Loaded の行）と「いま動いているか」（Active の行）は、別のものです。

### list-units と list-unit-files

```sh run root title="メモリにある unit と、ファイルとしてある unit"
systemctl list-units
systemctl list-unit-files
```

| コマンド | 見せるもの |
| --- | --- |
| `systemctl list-units` | systemd が**いまメモリに読み込んでいる** unit。既定では active なものだけ。列は UNIT、LOAD、ACTIVE、SUB、DESCRIPTION |
| `systemctl list-units --all` | 動いていない（inactive）ものも含める |
| `systemctl list-units --type=service` | 種類でしぼる（`-t service` でも同じ） |
| `systemctl list-units --state=failed`、`systemctl --failed` | 失敗したものだけ |
| `systemctl list-unit-files` | **インストールされている unit ファイル**と、enable の状態。列は UNIT FILE、STATE、PRESET |

`list-unit-files` の STATE には、次の値が出ます。

| STATE | 意味 |
| --- | --- |
| `enabled` | 起動時に自動で起こす（`.wants/` にリンクがある） |
| `disabled` | 自動では起こさない。手で `start` はできる |
| `static` | `[Install]` セクションがなく、enable できない。ほかの unit から必要とされたときに起きる |
| `masked` | 封じられている。**手でも起こせない** |

### mask：手でも起こせなくする

`disable` したサービスは、手で `start` できます。ほかの unit が必要としたときにも起きます。**どんな方法でも起こせなくする**のが `mask` です。Rocky Linux 9 で確かめた結果です。

```console
# systemctl mask sshd
Created symlink /etc/systemd/system/sshd.service → /dev/null.
# systemctl is-enabled sshd
masked
# systemctl enable sshd
Failed to enable unit, unit /etc/systemd/system/sshd.service is masked.
# systemctl unmask sshd
Removed "/etc/systemd/system/sshd.service".
```

`mask` の正体は、**優先順位がいちばん高い `/etc/systemd/system/` に、同じ名前で `/dev/null` へのシンボリックリンクを置く**ことです。systemd は空のファイルを読むことになり、何も起こせません。前の節の優先順位が、そのまま使われています。

| コマンド | いま | 次の起動 | 手で start |
| --- | --- | --- | --- |
| `systemctl stop 名前` | 止める | 変えない | できる |
| `systemctl disable 名前` | 変えない | 自動で起こさない | **できる** |
| `systemctl disable --now 名前` | 止める | 自動で起こさない | できる |
| `systemctl mask 名前` | 変えない | 起こさない | **できない** |
| `systemctl unmask 名前` | mask を解く（`/dev/null` へのリンクを消す） | | |

:::warn 試験の注意：enable と start、disable と mask
- `enable` は**次の起動から**。いまは起こさない。いまも起こすなら `enable --now` か、`start` も実行する
- `disable` したサービスは手で起こせる。**`mask` したサービスは、`unmask` するまで起こせない**
- `mask` は `/etc/systemd/system/名前` → `/dev/null` のシンボリックリンク。`enable` は `…target.wants/名前` → unit ファイルのシンボリックリンク
:::

小さな Linux の `systemctl` に `mask` はありません。後片付けをしておきます。

```sh run root title="止めて、自動起動もやめる"
systemctl stop ticker
systemctl disable ticker
rm /etc/systemd/system/ticker.service
systemctl daemon-reload
```

| | レスキューモード（`rescue.target`） | 緊急モード（`emergency.target`） |
| --- | --- | --- |
| 昔の名前 | シングルユーザーモード（ランレベル 1） | — |
| どこまで進むか | `sysinit.target` まで。**ローカルのファイルシステムをマウントする** | ほぼ何もしない。**ルートだけを読み取り専用で**マウント |
| ネットワーク、ほかのサービス | 起こさない | 起こさない |
| 入るとき | root のパスワードを聞かれる | root のパスワードを聞かれる |
| 使う場面 | ふつうの修理（パスワード、サービスの設定） | レスキューモードにも入れないとき（`/etc/fstab` のまちがいなど） |

unit ファイルを見ると、違いがそのまま書かれています（Rocky Linux 9）。

```text
# /usr/lib/systemd/system/rescue.target
[Unit]
Description=Rescue Mode
Requires=sysinit.target rescue.service
After=sysinit.target rescue.service
AllowIsolate=yes

# /usr/lib/systemd/system/emergency.target
[Unit]
Description=Emergency Mode
Requires=emergency.service
After=emergency.service
AllowIsolate=yes
```

`rescue.target` は `sysinit.target` を必要とし、`emergency.target` は必要としません。`/etc/fstab` に存在しない装置を書いてしまうと、`sysinit.target` の途中（ローカルのマウント）で失敗します。このときに使えるのが緊急モードです。

入り方は 2 通りあります。

| 入り方 | レスキューモード | 緊急モード |
| --- | --- | --- |
| 動いているシステムで | `systemctl rescue`（`systemctl isolate rescue.target`） | `systemctl emergency`（`systemctl isolate emergency.target`） |
| 起動時に（GRUB で `e` を押し、`linux` の行の最後に足す） | `systemd.unit=rescue.target`、`rescue`、`single`、`s`、`S`、`1` | `systemd.unit=emergency.target`、`emergency`、`-b` |

緊急モードでは、ルートが読み取り専用です。ファイルを直すには、まず読み書きできるようにマウントし直します。

```console
# mount -o remount,rw /
# vi /etc/fstab
# systemctl reboot            ← または systemctl default で、既定のターゲットへ進む
```

:::tip root のパスワードを忘れたとき
レスキューモードも緊急モードも、root のパスワードを聞いてきます。パスワードを忘れたときは、GRUB で `linux` の行に `init=/bin/bash`（Red Hat 系では `rd.break`）を足して起動し、systemd を通さずにシェルを得ます。その後、`mount -o remount,rw /` をしてから `passwd` で付け直します。GRUB の編集は機械の前にいればだれでもできるので、サーバーには GRUB のパスワードや、物理的な鍵が要ります。
:::

## カーネルのイメージと、ソースの置き場所 {#kernel-image}

Linux カーネルは、**本体（イメージ）** と、あとから足せる**モジュール**（`.ko`）でできています（[図解 LinuC 5.2](../../linuc/site/ch05.html#modules)）。本体は起動のときに GRUB がメモリへ読み込む 1 つのファイルで、モジュールは `/lib/modules/カーネルバージョン/` の下に並びます。

```fig tree カーネルの部品が置かれる場所。本体は /boot、モジュールは /lib/modules、ソースは /usr/src/linux
{
  root: { label: '/', kind: 'dir', children: [
    { label: 'boot', kind: 'dir', hl: true, children: [
      { label: 'vmlinuz-6.1.0-18-amd64', note: 'カーネルの本体（圧縮された bzImage）' },
      { label: 'initrd.img-6.1.0-18-amd64', note: 'initramfs' },
      { label: 'config-6.1.0-18-amd64', note: 'ビルドしたときの設定' },

    { label: 'lib/modules/6.1.0-18-amd64', kind: 'dir', hl: true, children: [
      { label: 'kernel/', kind: 'dir', note: 'モジュール（.ko）。drivers、fs、net … に分かれる' },
      { label: 'modules.dep', note: 'モジュールの依存の表（depmod が作る）' },
    ] },
    { label: 'usr/src/linux', kind: 'dir', hl: true, note: 'カーネルのソース', children: [

```

### イメージの名前：vmlinux、zImage、bzImage、vmlinuz

カーネルのイメージには、似た名前が 4 つあります。

| 名前 | 何か |
| --- | --- |
| `vmlinux` | **圧縮されていない**カーネル（ELF 形式）。ビルドするとソースの一番上にできる。そのままでは起動に使わない。デバッグに使う |
| `zImage` | 圧縮されたイメージの古い形。大きさに制限があり（512 KB ほどまで）、いまの x86 では使わない |
| **`bzImage`** | **big zImage**。大きなカーネルも扱える、圧縮されたイメージ。x86 では `arch/x86/boot/bzImage` にできる |
| `vmlinuz` | `/boot` に置かれた、圧縮されたカーネルのファイルの名前。中身は bzImage |

イメージの先頭には、自分を展開する小さなプログラムが付いています。GRUB がメモリに読み込むと、まずこのプログラムが動いて、圧縮された本体を展開します。

:::warn 試験の注意：bzImage の bz は bzip2 ではない
`bzImage` の **b は big** です。bzip2 で圧縮されているという意味ではありません。圧縮の方式は、ビルドの設定で選びます。既定は **gzip** で、ほかに bzip2、LZMA、**xz**、LZO、LZ4、zstd が選べます。
:::

### 圧縮の方式：gzip と xz

圧縮の方式は、カーネルの設定（[1.9](#build)）の「Kernel compression mode」で選びます。

| 方式 | 設定の名前 | 特徴 |
| --- | --- | --- |
| gzip | `CONFIG_KERNEL_GZIP` | 既定。圧縮率と展開の速さのつり合いがよい |
| bzip2 | `CONFIG_KERNEL_BZIP2` | gzip より 1 割ほど小さい。展開は遅い |
| **xz** | `CONFIG_KERNEL_XZ` | **gzip より 3 割ほど小さい**。圧縮に時間がかかる |

モジュールも圧縮できます。Red Hat 系では、モジュールは xz で圧縮されて `.ko.xz` という名前になっています。

```console
# modinfo -n xfs
/lib/modules/5.14.0-741.22.1.el9_9.aarch64/kernel/fs/xfs/xfs.ko.xz
```

（Rocky Linux 9 の例です。Debian 12 では、圧縮されていない `.ko` です）

### ソースの置き場所とバージョン

カーネルのソースは、昔から **`/usr/src/linux/`** に置く習慣です。ふつうは、`/usr/src/linux-6.1.0/` のようにバージョンの付いたディレクトリに展開し、`/usr/src/linux` をそこへのシンボリックリンクにします。

| ディレクトリ・ファイル | 中身 |
| --- | --- |
| `/usr/src/linux/Makefile` | ビルドの手順。先頭にバージョンが書かれている |
| `/usr/src/linux/.config` | ビルドの設定（[1.9](#build)） |
| **`/usr/src/linux/Documentation/`** | カーネルの文書。カーネルパラメータ、`/proc/sys` の項目、各ドライバの説明など |
| `/usr/src/linux/arch/` | CPU の種類ごとのコード（`arch/x86/` など）。できたイメージもこの下 |
| `/usr/src/linux/drivers/`、`fs/`、`net/`、`kernel/`、`mm/` | ドライバ、ファイルシステム、ネットワーク、中心の部分、メモリ管理 |

バージョンは、`Makefile` の先頭の 4 行で決まります。

```text
VERSION = 6
PATCHLEVEL = 1
SUBLEVEL = 0
EXTRAVERSION =
```

この例は「6.1.0」です。`EXTRAVERSION` に `-custom` と書けば「6.1.0-custom」になり、`uname -r` の出力と、モジュールのディレクトリ（`/lib/modules/6.1.0-custom/`）の名前が変わります。

```sh run title="動いているカーネルのバージョン"
uname -r
ls /boot
cat /proc/version
```

:::note モノリシックカーネルと、モジュール
Linux は、ファイルシステムもドライバもカーネルの中で動く**モノリシックカーネル**です。ただし、多くの部品を**ローダブルモジュール**として本体から分け、必要なときに読み込めるようにしています。本体に組み込むか、モジュールにするか、入れないかは、次の節の `.config` で 1 つずつ決めます。
:::

## カーネルをコンパイルする：.config と make のターゲット {#build}

カーネルを自分でビルドする場面は減りましたが、手順と `make` のターゲットは試験に出ます。流れは「設定を作る → ビルドする → 入れる」です。

```fig graph カーネルのコンパイルの流れ。設定（.config）を作り、ビルドし、モジュールとカーネルを入れ、initramfs と GRUB を更新する
{
```

### .config：1 行が 1 つの機能

設定は、ソースの一番上の **`/usr/src/linux/.config`** に書かれます。1 行が 1 つの機能です。

```text
CONFIG_EXT4_FS=y
CONFIG_XFS_FS=m
# CONFIG_BTRFS_FS is not set
CONFIG_LOCALVERSION="-custom"
```

| 書き方 | 意味 |
| --- | --- |
| `CONFIG_…=y` | カーネルの**本体に組み込む** |
| `CONFIG_…=m` | **モジュール**としてビルドする |
| `# CONFIG_… is not set` | 入れない |

ルートファイルシステムのドライバを `=m` にすると、起動のときに initramfs が要ります。`=y` にすれば、initramfs なしでもマウントできます。いま動いているカーネルの設定は、`/boot/config-$(uname -r)` に残っています。

### make のターゲット

`.config` を作るターゲットは、**画面の違い**で覚えます。

| ターゲット | 画面 | 特徴 |
| --- | --- | --- |
| `make config` | 文字だけ。1 項目ずつ質問に答える | 項目が数千あるので、実用的ではない |
| `make menuconfig` | 端末の中の**メニュー**（ncurses） | いちばんよく使う。X は要らない |
| `make xconfig` | X の GUI（**Qt**） | X が要る |
| `make gconfig` | X の GUI（**GTK+**） | X が要る |
| `make oldconfig` | 文字だけ | **いまある `.config` を元に**、新しく増えた項目だけ質問する |
| `make defconfig` | なし | その CPU の種類の既定の設定を作る |

掃除、ビルド、インストールのターゲットです。

| ターゲット | すること |
| --- | --- |
| `make clean` | ビルドでできたファイルの大部分を消す。**`.config` は残す** |
| `make mrproper` | ビルドでできたファイルを**すべて**消す。**`.config` とバックアップも消す** |
| `make distclean` | `mrproper` に加えて、エディタのバックアップやパッチの残りも消す |
| `make all`（`make` だけでも同じ） | カーネル本体（`vmlinux`、x86 では `bzImage`）と、モジュールをビルドする |
| `make bzImage` | 圧縮されたカーネルのイメージだけをビルドする（`arch/x86/boot/bzImage`） |
| `make modules` | `=m` にしたモジュールだけをビルドする |
| `make modules_install` | モジュールを **`/lib/modules/カーネルバージョン/`** にコピーし、`depmod` を実行する |
| `make install` | カーネルを `/boot` にコピーする（ディストリビューションの `installkernel` スクリプトを呼ぶ） |

パッケージにするターゲットもあります。ビルドしたカーネルをほかのサーバーに配るときに使います。

| ターゲット | 作るもの |
| --- | --- |
| `make rpm-pkg` | **ソースとバイナリの両方**の RPM パッケージ |
| `make binrpm-pkg` | **バイナリだけ**の RPM パッケージ |
| `make deb-pkg` | ソースとバイナリの両方の deb パッケージ |

:::warn 試験の注意：clean と mrproper、config の 4 つ
- **`mrproper` は `.config` も消す**。`clean` は残す。設定を取っておきたいときは、`mrproper` の前に `.config` を別の場所へ写す
- `menuconfig` は ncurses（端末）、`xconfig` は Qt、`gconfig` は GTK+。**`oldconfig` は既存の `.config` を引き継ぐ**
- `make modules` はビルドするだけ。`/lib/modules/` に入れるのは **`make modules_install`**
:::

## モジュールの置き場所、initramfs、DKMS {#modules-install}

### /lib/modules/カーネルバージョン/

`make modules_install` は、モジュールを `/lib/modules/カーネルバージョン/` に置きます。ディレクトリの名前は、そのカーネルの `uname -r` の出力と同じです。カーネルのバージョンごとに別のディレクトリなので、複数のカーネルを入れておけます。

```console
# ls /lib/modules/6.1.0-56-arm64
build   modules.alias      modules.builtin  modules.dep      modules.order    modules.symbols
kernel  modules.alias.bin  modules.devname  modules.dep.bin  modules.softdep  source
```

| ファイル | 中身 |
| --- | --- |
| `kernel/` | モジュール（`.ko`）。`drivers/`、`fs/`、`net/` などに分かれる |
| **`modules.dep`** | モジュールの**依存関係の表**。`depmod` が作り、`modprobe` が読む |
| `modules.alias` | 装置の ID などの別名と、モジュールの対応 |
| `modules.builtin` | 本体に組み込まれている（`=y`）もの |
| `build`、`source` | そのカーネルのヘッダやソースへのリンク。外部のモジュールをビルドするときに使う |

モジュールを足したり消したりしたら、**`depmod`** で `modules.dep` を作り直します（`make modules_install` は、最後に自分で `depmod` を実行します）。

### initramfs を作る：mkinitramfs、dracut、mkinitrd

新しいカーネルを入れたら、そのカーネルのモジュールが入った initramfs（[1.4](#initramfs)）を作ります。コマンドは、ディストリビューションで違います。

| | コマンド | 例 |
| --- | --- | --- |
| Debian 系 | **`mkinitramfs`** | `mkinitramfs -o /boot/initrd.img-6.1.0-custom 6.1.0-custom` |
| Debian 系 | `update-initramfs`（`mkinitramfs` を呼ぶ上位のコマンド） | `update-initramfs -u -k 6.1.0-custom`（`-c` 作る、`-u` 更新する、`-d` 消す） |
| Red Hat 系 | **`dracut`** | `dracut /boot/initramfs-5.14.0-custom.img 5.14.0-custom` |
| Red Hat 系（古い） | **`mkinitrd`** | `mkinitrd /boot/initramfs-5.14.0-custom.img 5.14.0-custom` |

```console
# mkinitramfs --help
Usage: mkinitramfs [option]... -o outfile [version]
# dracut --help
Usage: /usr/bin/dracut [OPTION]... [<initramfs> [<kernel-version>]]
  -f, --force           Overwrite existing initramfs file.
```

どちらも、カーネルバージョンを省くと、いま動いているカーネル（`uname -r`）のものを作ります。`mkinitramfs` は出力先を **`-o`** で指定し、`dracut` は引数の 1 つ目に書きます。`dracut` は、同じ名前のファイルがすでにあると上書きしないので、作り直すときは **`-f`**（`--force`）を付けます。

**Dracut** は、initramfs を作る仕組みの名前でもあります。`/usr/lib/dracut/modules.d/` の部品（dracut モジュール）を組み合わせて initramfs を作り、設定は `/etc/dracut.conf` と `/etc/dracut.conf.d/` に書きます。`mkinitrd` は昔の Red Hat 系のコマンドで、RHEL 8 までは `dracut` を呼び出す互換用のスクリプトとして残っていました（RHEL 9 にはありません）。

中身を見るコマンドもあります。Debian 系は `lsinitramfs ファイル`、Red Hat 系は `lsinitrd ファイル` です。initramfs の実体は cpio アーカイブで、gzip、bzip2、xz、zstd などで圧縮されています。

### DKMS：カーネルを更新しても、外部のモジュールを作り直す

カーネルのソースに入っていないドライバ（外部のモジュール）は、**カーネルのバージョンごとにビルドし直す**必要があります。カーネルを更新するたびに手でビルドするのは大変です。これを自動でするのが **DKMS**（Dynamic Kernel Module Support）です。

DKMS には、モジュールの**ソース**を登録しておきます。新しいカーネルが入ると、DKMS がそのカーネル用にビルドして、インストールします。

```console
# ls /usr/src/hello-1.0
Makefile  dkms.conf  hello.c
# dkms add -m hello -v 1.0
Creating symlink /var/lib/dkms/hello/1.0/source -> /usr/src/hello-1.0
# dkms build -m hello -v 1.0
# dkms install -m hello -v 1.0
# dkms status
hello/1.0, 6.1.0-56-arm64, aarch64: installed
# modinfo -n hello
/lib/modules/6.1.0-56-arm64/updates/dkms/hello.ko
```

（Debian 12 で、小さなモジュールを実際に登録した結果です）

| 項目 | 内容 |
| --- | --- |
| ソースの置き場所 | `/usr/src/モジュール名-バージョン/`。その中の **`dkms.conf`** に、名前、バージョン、ビルドのしかたを書く |
| 作業の場所 | `/var/lib/dkms/` |
| `dkms add` | ソースを DKMS に登録する |
| `dkms build` | 指定したカーネル（既定はいまのカーネル）用にビルドする |
| `dkms install` | `/lib/modules/カーネルバージョン/` の下に入れて、`depmod` を実行する |
| `dkms status` | 登録されているモジュールと、状態を表示する |
| `dkms remove` | 登録を消す |
| `dkms autoinstall` | `AUTOINSTALL="yes"` のモジュールを、まとめてビルドして入れる。カーネルの更新のときに自動で呼ばれる |

`-m` がモジュール名、`-v` がモジュールのバージョン、`-k` がカーネルバージョンです。ビルドには、そのカーネルのヘッダ（`kernel-devel` や `linux-headers-…` のパッケージ）とコンパイラが要ります。

## モジュールを実行時に管理する {#modules}

モジュールのコマンドは、レベル1 で 6 つ見ました（[図解 LinuC 5.2](../../linuc/site/ch05.html#modules)）。レベル2 では、オプションと設定ファイルまで問われます。

| コマンド | すること | 依存の解決 |
| --- | --- | --- |
| `lsmod` | 読み込まれているモジュールの一覧（`/proc/modules` を整えたもの） | — |
| `modinfo 名前` | モジュールの情報（ファイル、説明、依存、引数） | — |
| `modprobe 名前` | **名前**で読み込む | **する**（`modules.dep` を見る） |
| `modprobe -r 名前` | 外す。使われなくなった依存も外す | する |
| `insmod ファイル` | **ファイルのパス**で読み込む | しない |
| `rmmod 名前` | 外す | しない |
| `depmod` | `modules.dep` を作り直す | — |

### modinfo と modules.dep

```console
# modinfo xfs
filename:       /lib/modules/5.14.0-741.22.1.el9_9.aarch64/kernel/fs/xfs/xfs.ko.xz
license:        GPL
description:    SGI XFS with ACLs, security attributes, scrub, quota, no debug enabled
author:         Silicon Graphics, Inc.
alias:          fs-xfs
depends:        libcrc32c
name:           xfs
vermagic:       5.14.0-741.22.1.el9_9.aarch64 SMP preempt mod_unload modversions aarch64
# grep "/xfs.ko" /lib/modules/$(uname -r)/modules.dep
kernel/fs/xfs/xfs.ko.xz: kernel/lib/libcrc32c.ko.xz
```

`modinfo` の `depends:` が、このモジュールが必要とするモジュールです。`vermagic:` は、ビルドされたカーネルのバージョンで、動いているカーネルと合わないモジュールは読み込めません。`parm:` の行があれば、それがモジュールに渡せる引数です。

`modules.dep` の 1 行は、**「モジュールのファイル: それが必要とするモジュールのファイル」** です。パスは `/lib/modules/カーネルバージョン/` からの相対パスです。`modprobe` はこの表を見て、コロンの右側を先に読み込みます。

| modinfo | 表示するもの |
| --- | --- |
| `-n` | ファイルのパス（`filename`）だけ |
| `-d` | 説明（`description`）だけ |
| `-a` | 作者（`author`）だけ |
| `-l` | ライセンスだけ |
| `-p` | 引数（`parm`）だけ |
| `-F 項目` | 指定した項目だけ（`-F depends` など） |
| `-k バージョン` | いまのカーネルではなく、指定したカーネルのモジュールを調べる |

### modprobe と depmod のオプション

```console
# modprobe -n -v xfs
insmod /lib/modules/5.14.0-741.22.1.el9_9.aarch64/kernel/lib/libcrc32c.ko.xz
insmod /lib/modules/5.14.0-741.22.1.el9_9.aarch64/kernel/fs/xfs/xfs.ko.xz
```

`-n` は「実行せずに、することを表示するだけ」です。依存する `libcrc32c` が先に読み込まれることが分かります。

| modprobe | 意味 |
| --- | --- |
| `-r`、`--remove` | 外す |
| `-a`、`--all` | 引数に並べたモジュールを全部読み込む |
| `-n`、`--dry-run` | 実行しない。`-v` と合わせて、何をするかを見る |
| `-v`、`--verbose` | していることを表示する |
| `-D`、`--show-depends` | 依存するモジュールを、読み込む順に表示する（読み込みはしない） |
| `-c`、`--showconfig` | いまの設定（`/etc/modprobe.d/` などを合わせたもの）を表示する |
| `-f`、`--force` | バージョンの検査を無視して、むりに読み込む |

| depmod | 意味 |
| --- | --- |
| `-a`、`--all` | すべてのモジュールを調べる（**引数なしのときの既定**） |
| `-A`、`--quick` | 新しいモジュールがあるときだけ作り直す |
| `-n`、`--show` | ファイルに書かず、標準出力に出す |

### /etc/modprobe.d/：modprobe の設定

`modprobe` の動きは、**`/etc/modprobe.d/`** の中の `.conf` ファイルで変えられます。

```text
# /etc/modprobe.d/local.conf
options bonding max_bonds=0
blacklist nouveau
alias mynet e1000e
install usb-storage /bin/false
```

| 行 | 意味 |
| --- | --- |
| `options モジュール 引数=値` | そのモジュールを読み込むときに、いつも渡す引数 |
| `blacklist モジュール` | 装置を見つけたときの**自動の読み込みをしない**（手で `modprobe` すれば読み込める） |
| `alias 別名 モジュール` | 別の名前を付ける |
| `install モジュール コマンド` | 読み込む代わりに、そのコマンドを実行する（`/bin/false` にすれば、読み込みを完全に止められる） |

ディストリビューションが用意した設定は `/usr/lib/modprobe.d/`（Debian 系は `/lib/modprobe.d/`）にあり、同じ名前のファイルは `/etc/modprobe.d/` のほうが優先されます。なお、起動時にいつも読み込むモジュールは、`/etc/modules-load.d/*.conf`（Debian 系は `/etc/modules` でもよい）に名前を 1 行ずつ書きます。

### uname：動いているカーネルを知る

モジュールのディレクトリは `uname -r` の名前なので、`$(uname -r)` をよく使います。

```sh run title="uname のオプション"
uname -r
uname -m
uname -a
```

| uname | 表示するもの |
| --- | --- |
| （なし）、`-s` | カーネルの名前（`Linux`） |
| `-n` | ホスト名 |
| **`-r`** | カーネルの**リリース**（`6.1.0-18-amd64`）。`/lib/modules/` のディレクトリ名 |
| `-v` | カーネルの**バージョン**（ビルドの番号と日時。`#1 SMP …`） |
| `-m` | 機械の種類（`x86_64`、`aarch64`） |
| `-o` | OS の名前（`GNU/Linux`） |
| `-a` | 全部 |

:::warn 試験の注意：uname -r と -v
「6.1.0-18-amd64」のような、ふつうに言うカーネルのバージョン番号を出すのは **`-r`（release）** です。`-v`（version）は、ビルドの番号と日時です。名前と中身が逆に感じられるので、注意します。
:::

## /proc/sys と sysctl：カーネルのパラメータを変える {#sysctl}

カーネルの動きの多くは、**動かしたまま**変えられます。その入口が **`/proc/sys/`** です（[図解 Linux 12.3](../../linux/site/ch12.html#procfs)）。ここのファイルを読むといまの値が分かり、書き込むと値が変わります。

```sh run title="/proc/sys/kernel の中"
ls /proc/sys
ls /proc/sys/kernel
cat /proc/sys/kernel/ostype /proc/sys/kernel/osrelease
```

```sh run root title="書き込むと、その場で変わる"
cat /proc/sys/kernel/hostname
echo web01 > /proc/sys/kernel/hostname
hostname
echo zukai > /proc/sys/kernel/hostname
```

| ディレクトリ | 中身 |
| --- | --- |
| **`/proc/sys/kernel/`** | カーネル全体のパラメータ。`hostname`、`osrelease`、`ostype`、`pid_max`、`panic`、`sysrq`、`modules_disabled` など |
| `/proc/sys/net/` | ネットワーク。`net/ipv4/ip_forward`（IP フォワーディング）など |
| `/proc/sys/vm/` | メモリ管理。`swappiness`、`drop_caches` など |
| `/proc/sys/fs/` | ファイルシステム。`file-max`（開けるファイルの数の上限）など |

同じことを、名前で扱うのが **`sysctl`** コマンドです。名前は、`/proc/sys/` から後ろのパスの **`/` を `.` に変えたもの**です。`/proc/sys/net/ipv4/ip_forward` は `net.ipv4.ip_forward` になります。小さな Linux に `sysctl` はないので、Rocky Linux 9 で確かめた結果を見ます。

```console
# sysctl net.ipv4.ip_forward              ← 読む
net.ipv4.ip_forward = 1
# sysctl -w net.ipv4.ip_forward=0         ← 書く
net.ipv4.ip_forward = 0
# cat /proc/sys/net/ipv4/ip_forward
0
# sysctl -n kernel.ostype                 ← 値だけ
Linux
# sysctl -a | grep -c .                   ← 全部
1799
```

| sysctl | 意味 |
| --- | --- |
| `sysctl 名前` | 値を表示する |
| `sysctl -a` | すべてのパラメータを表示する |
| `sysctl -n 名前` | 名前を付けずに、値だけを表示する |
| `sysctl -w 名前=値` | 値を変える（`-w` は省ける） |
| `sysctl -p [ファイル]` | ファイルを読んで設定する。ファイルを省くと **`/etc/sysctl.conf`** |
| `sysctl --system` | すべての設定ファイル（`/usr/lib/sysctl.d/`、`/run/sysctl.d/`、`/etc/sysctl.d/`、`/etc/sysctl.conf`）を読んで設定する |

### 再起動しても残す：/etc/sysctl.conf と /etc/sysctl.d/

`echo` や `sysctl -w` で変えた値は、**再起動すると元に戻ります**。残すには、設定ファイルに書きます。

```text
# /etc/sysctl.d/90-forward.conf
net.ipv4.ip_forward = 1
kernel.panic = 10
```

| ファイル | 役目 |
| --- | --- |
| **`/etc/sysctl.conf`** | 昔からの設定ファイル |
| **`/etc/sysctl.d/*.conf`** | 管理者が置く設定。名前の順に読まれる |
| `/usr/lib/sysctl.d/*.conf` | パッケージが置く設定。同じ名前のファイルは `/etc/sysctl.d/` が優先 |

書式は「`名前 = 値`」です。起動のときに読み込まれます。書いた後、再起動せずにいますぐ反映するには、`sysctl -p`（`/etc/sysctl.conf` だけ）か `sysctl -p ファイル`、または `sysctl --system` を実行します。

:::warn 試験の注意：sysctl -w は一時的
- `sysctl -w` と `echo 値 > /proc/sys/…` は**いまだけ**。再起動で消える
- 残すなら `/etc/sysctl.conf` か `/etc/sysctl.d/*.conf` に書く。**書いただけでは反映されない**ので、`sysctl -p` で読み込む
- `sysctl -p` は引数なしなら `/etc/sysctl.conf` を読む。`-a` は表示、`-w` は書き込み
:::

### /sys（sysfs）

`/proc/sys` がカーネルの「調整つまみ」なのに対して、**`/sys`**（sysfs）は**装置とドライバのつながり**を木で見せるファイルシステムです（[図解 LinuC 5.3](../../linuc/site/ch05.html#devices)）。

| ディレクトリ | 中身 |
| --- | --- |
| `/sys/block/` | ブロックデバイス（ディスク） |
| `/sys/bus/` | バスの種類ごと（`pci`、`usb`） |
| `/sys/class/` | 装置の種類ごと（`net`、`block`） |
| `/sys/devices/` | 装置の木の本体 |
| `/sys/module/` | 読み込まれているモジュール。`/sys/module/名前/parameters/` にモジュールの引数 |
| `/sys/firmware/efi/` | UEFI で起動したときだけある |

### カーネルのメッセージ：dmesg と journalctl -k

カーネルが出すメッセージは、メモリの中の**リングバッファ**（輪になった入れ物）に入ります。大きさが決まっていて、いっぱいになると古いものから消えます。これを読むのが `dmesg` です（[図解 Linux 17.2](../../linux/site/ch17.html#dmesg)）。

```sh run title="dmesg と journalctl -k"
dmesg | grep -i sda
dmesg -T | tail -2
journalctl -k -n 3 --no-pager -q
```

| dmesg | 意味 |
| --- | --- |
| `-T` | 時刻を、人が読める形で表示する |
| `-H` | 読みやすい形（色、相対時刻、ページャ）で表示する |
| `-w` | 新しいメッセージを待って、出続ける |
| `-l err,warn` | レベルでしぼる |
| `-k` | カーネルのメッセージだけ |
| `-c` | 表示してから、バッファを**消す** |
| `-C` | 表示せずに、バッファを消す |

systemd のシステムでは、カーネルのメッセージはジャーナルにも入ります（[図解 LinuC 9.5](../../linuc/site/ch09.html#journal)）。リングバッファから消えた古いものや、前の起動のものも読めます。

| journalctl | 意味 |
| --- | --- |
| **`-k`**（`--dmesg`） | **いまの起動の、カーネルのメッセージ**だけ |
| `-b` | いまの起動のログ。`-b -1` で 1 つ前の起動 |
| `-u ユニット` | その unit のログ |
| `-p err` | 優先度が err 以上のもの |
| `-f` | 新しいログを待って、出続ける |
| `-S 時刻`、`--since=時刻` | 指定した時刻より後 |

### lspci、lsusb、lsdev

`lspci` と `lsusb` はレベル1 で見ました（[図解 LinuC 5.3](../../linuc/site/ch05.html#devices)）。トラブルの切り分けでは、**`lspci -k`** が役に立ちます。各装置を扱っているドライバが出ます。

```console
# lspci -k
00:01.0 Ethernet controller: Red Hat, Inc. Virtio 1.0 network device (rev 01)
	Subsystem: Red Hat, Inc. Device 0041
	Kernel driver in use: virtio-pci
```

「Kernel driver in use」の行がなければ、その装置にはドライバが結びついていません。

| コマンド | 見せるもの | 主なオプション |
| --- | --- | --- |
| `lspci` | PCI の装置 | `-v` 詳しく、`-k` ドライバ、`-t` 木の形、`-n` 番号で、`-nn` 名前と番号 |
| `lsusb` | USB の装置 | `-v` 詳しく、`-t` 木の形 |
| **`lsdev`** | 装置ごとの **IRQ、I/O ポート、DMA** の一覧 | — |

`lsdev` は、`/proc/interrupts`（IRQ）、`/proc/ioports`（I/O ポート）、`/proc/dma`（DMA）の 3 つを読んで、装置ごとに 1 つの表にまとめるコマンドです。`procinfo` パッケージに入っています。

### udev：ルールと、udevadm monitor

カーネルが装置を見つけると、**udev**（`systemd-udevd`）に知らせ（uevent）が届きます。udev は**ルール**に従って、`/dev` にデバイスファイルを作り、名前やリンクを付けます（[図解 LinuC 5.4](../../linuc/site/ch05.html#udev)）。

| 場所 | 中身 |
| --- | --- |
| **`/etc/udev/rules.d/`** | 管理者が置くルール。`/usr/lib/udev/rules.d/` の同じ名前のファイルより優先 |
| `/usr/lib/udev/rules.d/` | パッケージが置くルール（Debian 系は `/lib/udev/rules.d/`） |
| `/etc/udev/udev.conf` | udev 自身の設定 |

ルールのファイルは `70-usb-disk.rules` のように、**番号で始まり `.rules` で終わる**名前にします。番号の小さい順に読まれます。

```text
# /etc/udev/rules.d/70-usb-disk.rules
ACTION=="add", SUBSYSTEM=="block", ATTRS{serial}=="AB12CD34", SYMLINK+="backupdisk"
```

`==` は**条件**（一致するか）、`=` と `+=` は**設定**（値を入れる、足す）です。この行は「ブロックデバイスが追加され、シリアル番号が AB12CD34 なら、`/dev/backupdisk` というシンボリックリンクを足す」という意味です。

届いている知らせをその場で見るのが **`udevadm monitor`** です。

```console
# udevadm monitor
monitor will print the received events for:
UDEV - the event which udev sends out after rule processing
KERNEL - the kernel uevent

KERNEL[36974.592077] add      /devices/…/block/sdb (block)
UDEV  [36974.611204] add      /devices/…/block/sdb (block)
```

`KERNEL` の行がカーネルからの知らせ、`UDEV` の行が、udev がルールを処理し終えた知らせです。USB メモリを挿しても `KERNEL` の行が出なければカーネル（ドライバ）の問題、`KERNEL` は出るのに `/dev` に期待した名前ができなければルールの問題、と切り分けられます。

| コマンド | すること |
| --- | --- |
| `udevadm monitor` | カーネルと udev の知らせを表示し続ける。`-k` カーネルだけ、`-u` udev だけ、`-p` プロパティも表示 |
| `udevadm info /dev/sda` | 装置の情報（ルールの条件に使える属性）を表示する |
| `udevadm control --reload` | ルールを読み直させる |
| `udevadm trigger` | 装置の知らせをもう一度起こして、ルールを適用し直す |

`udevmonitor` は、`udevadm monitor` の**昔の名前**です。いまのディストリビューションには `udevadm` しかありません。

## kdump と kexec：クラッシュの記録を取る {#kdump}

カーネルが続けられないほどのエラーを起こすことを、**カーネルパニック**と呼びます。パニックの原因を調べるには、そのときのメモリの中身（クラッシュダンプ）が要ります。しかし、壊れたカーネルは自分でファイルを書けません。そこで、**別のカーネルに切り替えて**、そちらに書かせます。

```fig seq kdump の流れ。ふだんから 2 つ目のカーネルをメモリに置いておき、パニックのときに kexec でそちらへ飛ぶ
{
  colw: 225,
  actors: [
    { id: 'a', label: '1 つ目のカーネル（ふだん）', kind: 'accent' },
    { id: 'b', label: '2 つ目のカーネル（キャプチャ用）', kind: 'stack' },
    { id: 'd', label: 'ディスク', kind: 'ext' },
  ],
  msgs: [
    { note: '起動時：crashkernel= でメモリを取っておく', at: 'a' },
    { from: 'a', to: 'b', label: 'kdump サービスが kexec -p で読み込んでおく' },
    { note: 'カーネルパニック', at: 'a' },
    { from: 'a', to: 'b', label: 'kexec で直接起動（ファームウェアを通らない）', style: 'accent' },
    { from: 'b', to: 'd', label: '/proc/vmcore を /var/crash/ に保存' },
    { note: '保存したら再起動する', at: 'b' },
  ],
}
```

- **kexec** … 動いているカーネルから、**別のカーネルを直接起動する**仕組みとコマンド。ファームウェア（BIOS / UEFI）とブートローダを通らないので、ふつうの再起動より速い
- **kdump** … kexec を使って、パニックのときにキャプチャ用のカーネルを起動し、**クラッシュダンプを保存する**仕組み

| 項目 | 内容 |
| --- | --- |
| メモリの予約 | カーネルパラメータ **`crashkernel=`**（`crashkernel=256M` など）。2 つ目のカーネルが使うメモリを、起動のときに取っておく |
| 設定ファイル | Red Hat 系は `/etc/kdump.conf`、Debian 系は `/etc/default/kdump-tools` |
| サービス | Red Hat 系は `kdump.service`（`kdumpctl status` で状態を見る）、Debian 系は `kdump-tools.service` |
| ダンプの元 | 2 つ目のカーネルから見える **`/proc/vmcore`**（1 つ目のカーネルのメモリ） |
| 保存先 | 既定は **`/var/crash/`** |
| 調べる道具 | `crash` コマンド |

Rocky Linux 9 の `/etc/kdump.conf` の、コメントでない行です。

```text
path /var/crash
core_collector makedumpfile -l --message-level 7 -d 31
```

`path` が保存先、`core_collector` がダンプを作るコマンドです。`makedumpfile` は、要らないページを除いて圧縮し、ダンプを小さくします。

`kexec` コマンドは、手で使うこともできます。

```console
# kexec -l /boot/vmlinuz-5.14.0-custom --initrd=/boot/initramfs-5.14.0-custom.img --reuse-cmdline
# kexec -e                    ← 読み込んでおいたカーネルを、すぐに起動する
# systemctl kexec             ← サービスを順に止めてから、kexec で起動する
```

| kexec | 意味 |
| --- | --- |
| `-l`（`--load`） | 次に起動するカーネルを読み込む |
| `-e`（`--exec`） | 読み込んであるカーネルを起動する |
| `-p`（`--load-panic`） | **パニックのときに**起動するカーネルを読み込む（kdump が使う） |
| `-u`（`--unload`） | 読み込んだカーネルを捨てる |
| `--initrd=ファイル` | initramfs を指定する |
| `--append=文字列` | カーネルパラメータを指定する |
| `--reuse-cmdline` | いまのカーネルパラメータ（`/proc/cmdline`）をそのまま使う |

:::note パニックのときの動きを決めるパラメータ
`/proc/sys/kernel/panic`（`kernel.panic`）は、パニックの後に自動で再起動するまでの秒数です。0 なら再起動せずに止まったままになります。`kernel.panic_on_oops` を 1 にすると、軽いエラー（oops）でもパニックにします。kdump を仕掛けたサーバーでは、こうした値を `/etc/sysctl.d/` に書いておきます。
:::

:::key まとめ
- **BIOS** は MBR（446 + 64 + 2 バイト）のブートローダを実行する。**UEFI** は ESP（FAT、`/boot/efi`）の `.efi` を実行し、起動エントリは `efibootmgr` で見る・変える
- `grub.cfg` は手で書かない。`/etc/default/grub` と `/etc/grub.d/` を編集し、**`grub-mkconfig -o /boot/grub/grub.cfg`**（Red Hat 系は `grub2-mkconfig -o /boot/grub2/grub.cfg`）で作る。ブートローダ本体は `grub-install`（`grub2-install`）
- **initramfs** は、本当のルートをマウントするための仮のルート（cpio アーカイブ）。カーネルパラメータは `/proc/cmdline` で見られる
- unit ファイルの優先順位は **`/etc/systemd/system/` ＞ `/run/systemd/system/` ＞ `/usr/lib/systemd/system/`**。上書きの一覧は `systemd-delta`
- `disable` は自動起動をやめるだけ。**`mask`** は `/dev/null` へのリンクで、手でも起こせなくする
- **レスキューモード**（`rescue.target`）はローカルのファイルシステムをマウントする。**緊急モード**（`emergency.target`）はルートだけを読み取り専用で。どちらも root のパスワードが要る
- `bzImage` は **big** zImage。圧縮は既定で gzip、xz も選べる。ソースは `/usr/src/linux/`、文書は `Documentation/`
- 設定は `.config`（`=y` 組み込み、`=m` モジュール）。`menuconfig`（ncurses）、`xconfig`（Qt）、`gconfig`（GTK+）、`oldconfig`（既存を引き継ぐ）。**`mrproper` は `.config` も消す**
- `make modules_install` → `/lib/modules/カーネルバージョン/`。initramfs は `mkinitramfs -o`（Debian 系）、`dracut`（Red Hat 系）。外部のモジュールは **DKMS** が作り直す
- `modprobe` は `modules.dep`（`depmod` が作る）で依存を解決する。設定は `/etc/modprobe.d/`（`options`、`blacklist`、`alias`、`install`）
- `sysctl -w` は一時的。残すなら `/etc/sysctl.conf` か `/etc/sysctl.d/` に書き、`sysctl -p` で読み込む。`net.ipv4.ip_forward` ＝ `/proc/sys/net/ipv4/ip_forward`
- カーネルのメッセージは `dmesg` と `journalctl -k`。装置は `lspci -k`、`lsusb`、`lsdev`。udev の知らせは `udevadm monitor`、ルールは `/etc/udev/rules.d/`
- **kexec** はカーネルから別のカーネルを直接起動する。**kdump** はそれを使ってクラッシュダンプを `/var/crash/` に保存する。メモリは `crashkernel=` で予約する
:::

## 練習問題 {#practice}

### 2.01.1 ブートプロセスと GRUB

:::q 2.01.1-01 single
UEFI のシステムで、ブートローダの `.efi` ファイルが置かれる場所はどれか。
- [ ] MBR の先頭 446 バイト
- [x] EFI システムパーティション（ESP）
- [ ] BIOS ブートパーティション
- [ ] `/boot/grub/` のあるパーティションの先頭セクタ
- [ ] スワップパーティション
:::why
UEFI は FAT のファイルシステムを読めるので、ブートローダは ESP の中のファイル（`shimx64.efi`、`grubx64.efi` など）です（[1.2](#firmware)）。MBR の先頭 446 バイトにブートローダの 1 段目を置くのは BIOS の方式です。BIOS ブートパーティションは、GPT のディスクを BIOS で起動するときに GRUB の `core.img` を置く場所で、UEFI では使いません。
:::
:::

:::q 2.01.1-02 single
MBR（マスターブートレコード）の 512 バイトのうち、ブートローダのプログラムが入る領域の大きさはどれか。
- [ ] 2 バイト
- [ ] 64 バイト
- [x] 446 バイト
- [ ] 510 バイト
:::why
MBR は「ブートローダ 446 バイト + パーティション表 64 バイト + 署名 2 バイト」です（[1.2](#firmware)）。64 バイトはパーティション表（16 バイト × 4 つ）、2 バイトは署名（`0x55AA`）の大きさです。446 バイトには GRUB の全部は入らないので、1 段目が後ろの `core.img` を読み込みます。
:::
:::

:::q 2.01.1-03 fill
Debian 系のシステムで `/etc/default/grub` を書き換えた。GRUB 2 の設定ファイルを作り直すために、空欄に入るオプションを入力してください。

```text
grub-mkconfig ____ /boot/grub/grub.cfg
```
= -o
= --output
:::why
`grub-mkconfig` は、`-o`（`--output=FILE`）を付けないと結果を標準出力に出すだけです（[1.3](#grub)）。`-o` で出力先のファイルを指定します（長い形は `--output` で、空白で区切っても書けます）。Debian 系の `update-grub` は、この `grub-mkconfig -o /boot/grub/grub.cfg` を実行するスクリプトです。
:::
:::

:::q 2.01.1-04 single
Red Hat 系のシステム（BIOS で起動）で、GRUB 2 の設定ファイルを作り直すコマンドとして正しいものはどれか。
- [ ] `grub2-install -o /boot/grub2/grub.cfg`
- [ ] `grub-mkconfig > /etc/grub.conf`
- [x] `grub2-mkconfig -o /boot/grub2/grub.cfg`
- [ ] `grub2-mkconfig /etc/default/grub`
- [ ] `update-grub2 /boot/grub2/grub.cfg`
:::why
Red Hat 系では、コマンドは `grub2-mkconfig`、設定ファイルは `/boot/grub2/grub.cfg` です（[1.3](#grub)）。`grub2-install` はブートローダのプログラムをディスクに書き込むコマンドで、設定は作りません。`grub2-mkconfig` は入力のファイルを引数に取りません（`/etc/default/grub` と `/etc/grub.d/` を自動で読みます）。`update-grub` は Debian 系のスクリプトで、引数に出力先は取りません。
:::
:::

:::q 2.01.1-05 single
`/etc/default/grub` に次の行がある。この設定の説明として正しいものはどれか。

```text
GRUB_DEFAULT=0
GRUB_TIMEOUT=5
```
- [ ] メニューを出さずに、5 番目の項目を起動する
- [x] メニューを 5 秒間出し、何も選ばなければ 1 番上の項目を起動する
- [ ] メニューを出したまま待ち、5 回失敗すると 1 番上の項目を起動する
- [ ] 起動に 5 秒以上かかったら、既定の項目を無効にする
:::why
`GRUB_TIMEOUT` はメニューを出して待つ秒数、`GRUB_DEFAULT` は既定で選ぶ項目で、0 が 1 番上です（[1.3](#grub)）。`GRUB_TIMEOUT=0` ならすぐ起動、`-1` なら選ぶまで待ちます。失敗の回数や起動にかかった時間を数える設定ではありません。
:::
:::

:::q 2.01.1-06 multi
`grub-mkconfig` が `grub.cfg` を作るときに読むものを 2 つ選択してください。
- [x] `/etc/default/grub`
- [x] `/etc/grub.d/` の中のスクリプト
- [ ] `/boot/grub/menu.lst`
- [ ] `/etc/fstab.d/`
- [ ] `/proc/cmdline`
:::why
`grub-mkconfig` は、`/etc/default/grub` の変数を読み、`/etc/grub.d/` のスクリプト（`00_header`、`10_linux`、`40_custom` など）を番号の順に実行して、出力をつなぎます（[1.3](#grub)）。`menu.lst` は昔の GRUB（GRUB Legacy）の設定ファイルです。`/proc/cmdline` は、いま動いているカーネルが受け取った引数を見るファイルで、設定の元にはなりません。
:::
:::

:::q 2.01.1-07 single
`efibootmgr -n 0002` を実行した。その結果として正しいものはどれか。
- [ ] 起動エントリ 0002 が削除される
- [ ] 起動エントリ 0002 が新しく作られる
- [x] 次の 1 回の起動だけ、エントリ 0002 から起動する
- [ ] 起動の順番（BootOrder）が、今後ずっと 0002 だけになる
:::why
`-n`（`--bootnext`）は、次の 1 回だけ使うエントリ（BootNext）を決めます（[1.2](#firmware)）。削除は `-b 0002 -B`、新しく作るのは `-c`、今後の起動の順番を決めるのは `-o 0002,0001` です。
:::
:::

:::q 2.01.1-08 single
Debian 系のサーバーで、`/etc/default/grub` の `GRUB_CMDLINE_LINUX` にカーネルパラメータを足して再起動した。しかし `/proc/cmdline` を見ると、足したパラメータがない。原因として最も考えられるものはどれか。
- [ ] `grub-install` を実行していない
- [x] `grub-mkconfig -o /boot/grub/grub.cfg`（`update-grub`）を実行していない
- [ ] `systemctl daemon-reload` を実行していない
- [ ] `depmod -a` を実行していない
:::why
GRUB が起動のときに読むのは `grub.cfg` です。`/etc/default/grub` は `grub.cfg` を作るための元で、書き換えた後に `grub-mkconfig -o …` を実行しないと反映されません（[1.3](#grub)）。`grub-install` はブートローダのプログラムを入れ直すコマンドで、設定の反映には要りません。`daemon-reload` は systemd の unit の読み直し、`depmod` はモジュールの依存の表の作り直しです。
:::
:::

:::q 2.01.1-09 fill

:::q 2.01.1-11 multi
initramfs の説明として正しいものを 2 つ選択してください。
- [x] 本当のルートファイルシステムをマウントするために必要なモジュールや道具を入れた、仮のルートファイルシステムである

:::q 2.01.1-12 single

### 2.01.2 システム起動のカスタマイズ

:::q 2.01.2-01 single
同じ名前の unit ファイルが次の 3 つのディレクトリにある。systemd が使うものはどれか。
- [x] `/etc/systemd/system/` のもの
- [ ] `/run/systemd/system/` のもの
- [ ] `/usr/lib/systemd/system/` のもの
- [ ] 更新時刻がいちばん新しいもの
- [ ] 3 つの内容を合わせたもの
:::why
優先順位は `/etc/systemd/system/` ＞ `/run/systemd/system/` ＞ `/usr/lib/systemd/system/` です（[1.5](#unit-dirs)）。管理者が `/etc` に置いたものが、パッケージの `/usr/lib` のものより優先されます。同じ名前のファイルは合わせられず、優先順位の高い 1 つだけが読まれます（一部だけ足したいときは `名前.d/` のドロップインを使います）。
:::
:::

:::q 2.01.2-02 single
`systemctl mask httpd` の説明として正しいものはどれか。
- [ ] httpd をいますぐ止め、unit ファイルを削除する
- [ ] httpd の自動起動をやめる。`systemctl start httpd` では起動できる
- [x] httpd を、手動でも、ほかの unit からの依存でも起動できないようにする
- [ ] httpd のログをジャーナルに記録しないようにする
:::why
`mask` は、`/etc/systemd/system/httpd.service` を `/dev/null` へのシンボリックリンクにして、どんな方法でも起動できなくします（[1.6](#systemctl)）。いま動いているプロセスは止めません。自動起動だけをやめて手動では起動できるのは `disable` です。unit ファイルは削除されず、`unmask` で元に戻せます。
:::
:::

:::q 2.01.2-03 fill
`/etc/systemd/system/` などに置かれたファイルが、パッケージの unit ファイルをどのように上書き・拡張しているかを一覧するコマンドの名前を入力してください。
= systemd-delta
= /usr/bin/systemd-delta
:::why
`systemd-delta` は、上書きされた設定を `[OVERRIDDEN]`、`[MASKED]`、`[EXTENDED]`、`[EQUIVALENT]`、`[REDIRECTED]` の印を付けて表示します（[1.5](#unit-dirs)）。`--type=masked` のように種類でしぼれます。
:::
:::

:::q 2.01.2-04 single
あるコマンドを実行したところ、次のように表示された。実行したコマンドはどれか。

```text
Created symlink /etc/systemd/system/sshd.service → /dev/null.
```
- [ ] `systemctl enable sshd`
- [ ] `systemctl disable sshd`
- [x] `systemctl mask sshd`
- [ ] `systemctl stop sshd`
- [ ] `systemctl unmask sshd`
:::why
`/dev/null` へのシンボリックリンクを作るのは `mask` です（[1.6](#systemctl)）。`enable` は `…/multi-user.target.wants/sshd.service` から unit ファイルへのリンクを作り、`disable` はそれを消します。`unmask` は `/dev/null` へのリンクを消します（`Removed …` と表示されます）。`stop` はリンクを作りません。
:::
:::

:::q 2.01.2-05 multi
レスキューモード（`rescue.target`）と緊急モード（`emergency.target`）の説明として正しいものを 2 つ選択してください。
- [x] レスキューモードは、ローカルのファイルシステムをマウントする
- [x] 緊急モードは、ルートファイルシステムだけを読み取り専用でマウントする
- [ ] レスキューモードでは、ネットワークとすべてのサービスが起動する
- [ ] 緊急モードは、root のパスワードなしでシェルが使える
- [ ] 緊急モードは、レスキューモードより多くの unit を起こす
:::why
`rescue.target` は `sysinit.target` を必要とするので、ローカルのファイルシステムのマウントまで進みます。`emergency.target` は `emergency.service` だけを必要とし、ルートが読み取り専用のままシェルを出します（[1.7](#rescue)）。どちらもネットワークやふつうのサービスは起こさず、root のパスワードを聞きます。起こす unit が少ないのは緊急モードのほうです。
:::
:::

:::q 2.01.2-06 single
`systemctl list-unit-files` の STATE の列に `static` と表示された unit の説明として正しいものはどれか。

- [ ] unit ファイルに書式のまちがいがあり、読み込めない
:::why
`static` は、`[Install]` セクションを持たない unit です。`enable` の対象にはならず、ほかの unit の依存として起こされます（[1.6](#systemctl)）。封じられているのは `masked`、自動で起動するのは `enabled` です。

:::q 2.01.2-07 single
`/run/systemd/system/` の説明として正しいものはどれか。

- [ ] 管理者が作った unit ファイルを置く。優先順位はいちばん高い

:::q 2.01.2-09 multi

- [x] `list-unit-files` は、インストールされている unit ファイルと、enabled / disabled などの状態を表示する

- [ ] `list-unit-files` は、unit ファイルの中身を表示する
- [ ] `list-units --type=service` は、サービスを種類の順に並べ替えて表示する
:::why
`list-units` はメモリにある unit の実行時の状態、`list-unit-files` はファイルとして存在する unit と enable の状態です（[1.6](#systemctl)）。`list-units` は既定では active なものだけで、inactive も見るには `--all` を付けます。unit ファイルの中身を表示するのは `systemctl cat` です。`--type=service` は、種類がサービスのものだけにしぼります。
:::
:::

:::q 2.01.2-14 single
`/etc/fstab` に、存在しない装置のマウントを書いてしまった。再起動すると、ローカルのファイルシステムのマウントで失敗して起動が止まる。GRUB から修理用のモードで起動して `/etc/fstab` を直したい。最も確実に入れるものはどれか。
- [ ] `systemd.unit=graphical.target` を足して起動する
- [ ] `systemd.unit=multi-user.target` を足して起動する
- [ ] `systemd.unit=rescue.target` を足して起動する
- [x] `systemd.unit=emergency.target` を足して起動する
:::why
`rescue.target` は `sysinit.target`（ローカルのファイルシステムのマウントを含む）を必要とするので、`/etc/fstab` のまちがいで同じように失敗することがあります。`emergency.target` は `sysinit.target` を必要とせず、ルートだけを読み取り専用でマウントした状態でシェルを出します（[1.7](#rescue)）。`multi-user.target` と `graphical.target` は、さらに先の段階です。
:::
:::

:::q 2.01.2-15 multi
動いている `telnet.socket` をいますぐ止め、さらに今後は手動でもほかの unit からでも起動できないようにしたい。実行するコマンドを 2 つ選択してください。
- [x] `systemctl stop telnet.socket`
- [x] `systemctl mask telnet.socket`
- [ ] `systemctl disable telnet.socket`
- [ ] `systemctl daemon-reload`
- [ ] `systemctl isolate telnet.socket`
:::why
`stop` でいま止め、`mask` で起動できなくします（[1.6](#systemctl)）。`mask` だけでは、いま動いているものは止まりません。`disable` は自動起動をやめるだけで、手動の `start` や、ほかの unit からの依存では起動できてしまいます。`isolate` は、指定したターゲットとその依存だけを残してほかを止めるコマンドです。
:::
:::

### 2.01.3 Linux カーネルの構成要素

:::q 2.01.3-01 single
`bzImage` の説明として正しいものはどれか。
- [ ] bzip2 で圧縮されたカーネルイメージで、gzip で圧縮したものは `gzImage` と呼ぶ
- [x] 「big zImage」の意味で、大きなカーネルも扱える圧縮されたカーネルイメージである
- [ ] 圧縮されていない ELF 形式のカーネルで、デバッグに使う
- [ ] カーネルモジュールを 1 つにまとめたアーカイブである
- [ ] initramfs を作るための元になるイメージである
:::why
`bzImage` の b は big で、bzip2 のことではありません。圧縮の方式は設定で選び、既定は gzip です（[1.8](#kernel-image)）。圧縮されていない ELF 形式のカーネルは `vmlinux` です。モジュールや initramfs とは別のものです。
:::
:::

:::q 2.01.3-02 single
カーネルのソースに付いている文書（カーネルパラメータや `/proc/sys` の項目の説明など）が置かれているディレクトリはどれか。
- [ ] `/usr/src/linux/arch/`
- [ ] `/usr/src/linux/scripts/`
- [x] `/usr/src/linux/Documentation/`
- [ ] `/usr/share/doc/kernel/README/`
- [ ] `/lib/modules/Documentation/`
:::why
カーネルの文書は、ソースの木の `Documentation/` ディレクトリにあります（[1.8](#kernel-image)）。`arch/` は CPU の種類ごとのコードで、ビルドしたイメージもこの下にできます。`/lib/modules/` はモジュールの置き場所で、文書はありません。
:::
:::

:::q 2.01.3-03 fill
カーネルのソースを置く、昔からの習慣のディレクトリ（ふつうは、バージョンの付いたディレクトリへのシンボリックリンク）を絶対パスで入力してください。
= /usr/src/linux
= /usr/src/linux/
:::why
カーネルのソースは `/usr/src/linux-6.1.0/` のようなディレクトリに展開し、`/usr/src/linux` をそこへのシンボリックリンクにする習慣です（[1.8](#kernel-image)）。設定は `/usr/src/linux/.config`、文書は `/usr/src/linux/Documentation/` です。
:::
:::

:::q 2.01.3-04 single
カーネルイメージの圧縮に xz を使うことの説明として正しいものはどれか。
- [ ] 圧縮しないので、起動がいちばん速い
- [ ] gzip より圧縮率は低いが、古いブートローダでも起動できる
- [x] gzip より 3 割ほど小さくなるが、圧縮に時間がかかる
- [ ] xz を選ぶと、イメージの名前が `bzImage` から `xzImage` に変わる
:::why
xz は圧縮率が高く、gzip と比べてカーネルが 3 割ほど小さくなります。その代わり、圧縮（ビルド）に時間がかかります（[1.8](#kernel-image)）。圧縮の方式を変えても、x86 のイメージの名前は `bzImage` のままです。既定の方式は gzip です。
:::
:::

:::q 2.01.3-05 multi
`vmlinux` と `vmlinuz` の説明として正しいものを 2 つ選択してください。
- [x] `vmlinux` は、圧縮されていないカーネル（ELF 形式）である
- [x] `vmlinuz` は、`/boot` に置かれる圧縮されたカーネルイメージの名前である
- [ ] `vmlinux` は、ブートローダが読み込む initramfs の別名である
- [ ] `vmlinuz` は、カーネルのソースを xz で固めたアーカイブである
- [ ] `vmlinux` と `vmlinuz` は、同じファイルへのハードリンクである
:::why
`vmlinux` はビルドするとソースの一番上にできる、圧縮されていないカーネルです。`/boot/vmlinuz-バージョン` は圧縮されたイメージ（中身は bzImage）で、GRUB が読み込むのはこちらです（[1.8](#kernel-image)）。名前の最後の z は、圧縮されていることを表します。
:::
:::

:::q 2.01.3-06 single
カーネルのソースの `Makefile` の先頭が次のようになっている。ほかの設定で文字列を足していないとき、このソースからビルドしたカーネルのリリース番号（`uname -r` の出力）はどれか。

```text

PATCHLEVEL = 1
SUBLEVEL = 12
EXTRAVERSION = -lab
```
- [ ] `6.1`
- [ ] `6.12.1-lab`
- [x] `6.1.12-lab`
- [ ] `lab-6.1.12`
:::why
リリース番号は「VERSION.PATCHLEVEL.SUBLEVEL」に `EXTRAVERSION` を続けたものです（[1.8](#kernel-image)）。`EXTRAVERSION` を変えると、モジュールのディレクトリ（`/lib/modules/6.1.12-lab/`）の名前も変わるので、元のカーネルのモジュールとぶつかりません。
:::
:::

:::q 2.01.3-07 single
x86_64 のカーネルを `/usr/src/linux` でビルドした。できあがった圧縮されたカーネルイメージの場所はどれか。
- [ ] `/usr/src/linux/vmlinux`
- [ ] `/usr/src/linux/kernel/bzImage`
- [x] `/usr/src/linux/arch/x86/boot/bzImage`
- [ ] `/usr/src/linux/Documentation/bzImage`
- [ ] `/lib/modules/バージョン/bzImage`
:::why
x86 の bzImage は `arch/x86/boot/bzImage` にできます（[1.8](#kernel-image)）。ソースの一番上の `vmlinux` は、圧縮されていないカーネルです。`make install` を実行すると、bzImage が `/boot/vmlinuz-バージョン` としてコピーされます。
:::
:::

:::q 2.01.3-08 fill
いま動いているカーネルのリリース番号（例：`6.1.0-18-amd64`）だけを表示するコマンドを、オプションを含めて入力してください。
= uname -r
= uname --kernel-release
= cat /proc/sys/kernel/osrelease
:::why
`uname -r` がカーネルのリリース番号を表示します（[1.11](#modules)）。モジュールのディレクトリ `/lib/modules/$(uname -r)/` や、`/boot/config-$(uname -r)` のように使います。`uname -v` はビルドの番号と日時、`uname -a` は全部です。同じ値は `/proc/sys/kernel/osrelease` にもあります。
:::
:::

:::q 2.01.3-09 multi
`/boot` に置かれるファイルの説明として正しいものを 2 つ選択してください。
- [x] `System.map-バージョン` は、カーネルのシンボルと番地の対応表である
- [x] `config-バージョン` は、そのカーネルをビルドしたときの設定である
- [ ] `vmlinuz-バージョン` は、カーネルモジュールの依存関係の表である
- [ ] `initramfs-バージョン.img` は、カーネルのソースを圧縮したものである
- [ ] `grub.cfg` は、`/boot` の直下に置かれる
:::why
`System.map` はシンボル（関数や変数の名前）と番地の表、`config-…` は `.config` の写しです（[1.3](#grub)）。`vmlinuz-…` は圧縮されたカーネル、`initramfs-….img` は起動のときの仮のルートファイルシステムです。依存関係の表は `/lib/modules/バージョン/modules.dep` です。`grub.cfg` は `/boot/grub/` か `/boot/grub2/` の中にあります。
:::
:::

:::q 2.01.3-10 single
Red Hat 系のシステムで `modinfo -n xfs` を実行したところ、次のように表示された。ファイル名の最後の `.xz` の説明として正しいものはどれか。

```text

```
- [ ] XFS のためのモジュールであることを表す
- [x] モジュールのファイルが xz で圧縮されていることを表す
- [ ] モジュールが無効にされていることを表す
- [ ] カーネル本体に組み込まれていることを表す
:::why
モジュールのファイル（`.ko`）は圧縮して置くことができ、Red Hat 系では xz で圧縮された `.ko.xz` になっています（[1.8](#kernel-image)）。`modprobe` は圧縮されたままのファイルを読み込めます。本体に組み込まれたもの（`=y`）は、`.ko` のファイルとしては存在しません。
:::
:::

### 2.01.4 Linux カーネルのコンパイル

:::q 2.01.4-01 single
カーネルのソースのディレクトリで `make mrproper` を実行した。その結果として正しいものはどれか。
- [ ] ビルドでできたファイルを消すが、`.config` は残す
- [x] ビルドでできたファイルをすべて消し、`.config` も消す
- [ ] `.config` を、その CPU の種類の既定の設定に戻す
- [ ] 古い `.config` を元に、新しい項目だけを質問する
- [ ] インストール済みのモジュールを `/lib/modules/` から消す
:::why
`mrproper` は、ビルドの結果と `.config`、バックアップをすべて消して、ソースを展開した直後に近い状態に戻します（[1.9](#build)）。`.config` を残すのは `make clean` です。既定の設定を作るのは `make defconfig`、古い設定を引き継ぐのは `make oldconfig` です。インストール済みのものには触れません。
:::
:::

:::q 2.01.4-02 single
X Window System のないサーバーに SSH で入り、端末の中のメニューでカーネルの設定を変えたい。使う `make` のターゲットはどれか。

- [ ] `make gconfig`
- [x] `make menuconfig`
- [ ] `make modules`
- [ ] `make mrproper`
:::why
`menuconfig` は ncurses を使った、端末の中のメニューです（[1.9](#build)）。`xconfig`（Qt）と `gconfig`（GTK+）は X の GUI なので、X が要ります。`make config` も端末で動きますが、メニューではなく 1 項目ずつ質問に答える形です。
:::
:::

:::q 2.01.4-03 single
`/usr/src/linux/.config` に次の行がある。この設定の説明として正しいものはどれか。

- [ ] ext4 はモジュール、XFS はカーネル本体に組み込み、Btrfs は入れない
- [x] ext4 はカーネル本体に組み込み、XFS はモジュール、Btrfs は入れない
- [ ] ext4 と XFS はカーネル本体に組み込み、Btrfs はモジュールにする
- [ ] 3 行目はコメントなので意味がなく、Btrfs は既定のとおり組み込まれる
:::why
`=y` は本体に組み込み、`=m` はモジュール、`# CONFIG_… is not set` は入れない、という意味です（[1.9](#build)）。3 行目は `#` で始まりますが、「入れない」ことを表す決まった書き方です。
:::
:::

:::q 2.01.4-04 fill
カーネルとモジュールのビルドが終わった。ビルドしたモジュールを `/lib/modules/カーネルバージョン/` にインストールするために、空欄に入るターゲットを入力してください。

```text

```

:::why
`make modules_install` が、モジュールを `/lib/modules/カーネルバージョン/` にコピーし、`depmod` を実行します（[1.9](#build)）。`make modules` はビルドするだけ、`make install` はカーネル本体を `/boot` に入れるターゲットです。
:::
:::

:::q 2.01.4-05 multi
カーネルの設定を作る `make` のターゲットのうち、X Window System の GUI を使うものを 2 つ選択してください。
- [x] `make xconfig`
- [x] `make gconfig`
- [ ] `make config`
- [ ] `make menuconfig`
- [ ] `make oldconfig`
:::why
`xconfig` は Qt、`gconfig` は GTK+ の GUI です（[1.9](#build)）。`config` と `oldconfig` は文字だけの質問、`menuconfig` は端末の中のメニュー（ncurses）で、X は要りません。
:::
:::

:::q 2.01.4-06 single
新しいバージョンのカーネルのソースに、いま使っているカーネルの `.config` をコピーした。古い設定を引き継ぎ、新しく増えた項目だけを質問させるターゲットはどれか。

- [ ] `make mrproper`

`make oldconfig` は、いまある `.config` を元にして、新しいバージョンで増えた項目だけを質問します（[1.9](#build)）。`make config` はすべての項目を質問します。`make defconfig` は `.config` を既定の設定で作り直します。`make mrproper` は `.config` を消してしまいます。

:::

:::q 2.01.4-07 single
Red Hat 系のシステムで、カーネル `5.14.0-custom` 用の initramfs を作るコマンドとして正しいものはどれか。

:::q 2.01.4-08 multi

:::
:::

:::q 2.01.4-09 single

### 2.01.5 カーネル実行時における管理とトラブルシューティング

:::q 2.01.5-01 single
`/lib/modules/$(uname -r)/` にモジュールのファイルを手でコピーした。`modprobe` で読み込めるように、依存関係の表を作り直すコマンドはどれか。
- [ ] `modinfo -a`
- [ ] `lsmod -a`
- [x] `depmod -a`
- [ ] `insmod -a`
- [ ] `sysctl -a`
:::why
`depmod` が `/lib/modules/カーネルバージョン/modules.dep` を作り直します（[1.11](#modules)）。`-a` はすべてのモジュールを調べる指定で、引数なしのときの既定です。`modinfo -a` はモジュールの作者を表示します。`lsmod` と `insmod` に `-a` はありません。`sysctl -a` はカーネルパラメータをすべて表示します。
:::

:::q 2.01.5-02 single

- [x] `ext4` を読み込むには、`crc16`、`mbcache`、`jbd2` が先に必要である
- [ ] `ext4` は、`crc16`、`mbcache`、`jbd2` のどれか 1 つがあれば読み込める

:::why
`modules.dep` の 1 行は「モジュール: それが必要とするモジュール」です。`modprobe ext4` は、コロンの右側の 3 つを先に読み込んでから `ext4` を読み込みます（[1.11](#modules)）。
:::
:::

:::q 2.01.5-03 fill

= net/ipv4/ip_forward
:::why
`sysctl` の名前は、`/proc/sys/` から後ろのパスの `/` を `.` に変えたものです。`/proc/sys/net/ipv4/ip_forward` は `net.ipv4.ip_forward` になります（[1.12](#sysctl)）。`sysctl` は `/` で区切った書き方も受け付けます。
:::
:::

:::q 2.01.5-04 single
`sysctl -w kernel.panic=10` を実行した。この設定の説明として正しいものはどれか。
- [ ] `/etc/sysctl.conf` に書き込まれ、再起動の後も有効である
- [x] いま動いているカーネルにだけ反映され、再起動すると元に戻る
- [ ] 次に再起動するまでは反映されない
- [ ] `sysctl -p` を実行するまでは反映されない
:::why
`sysctl -w` は `/proc/sys/kernel/panic` に書き込むのと同じで、その場で反映されますが、再起動で消えます（[1.12](#sysctl)）。再起動の後も残すには、`/etc/sysctl.conf` か `/etc/sysctl.d/*.conf` に `kernel.panic = 10` と書きます。`sysctl -p` は、そのファイルを読んで設定するコマンドです。
:::
:::

:::q 2.01.5-05 single
`/etc/modprobe.d/local.conf` に次の行がある。この設定の説明として正しいものはどれか。

```text
blacklist nouveau
options bonding max_bonds=0
```
- [ ] `nouveau` を起動時に必ず読み込み、`bonding` は読み込まない
- [ ] `nouveau` のファイルを削除し、`bonding` の別名を `max_bonds` にする
- [x] `nouveau` を装置の検出による自動の読み込みの対象から外し、`bonding` を読み込むときは引数 `max_bonds=0` を渡す
- [ ] `nouveau` と `bonding` の両方を、`modprobe` で読み込めなくする
:::why
`blacklist` は自動の読み込みをやめさせます（手で `modprobe nouveau` とすれば読み込めます）。`options` は、そのモジュールを読み込むときにいつも渡す引数です（[1.11](#modules)）。別名を付けるのは `alias`、読み込みを完全に止めるには `install モジュール /bin/false` と書きます。
:::
:::

:::q 2.01.5-06 multi
いまの起動でカーネルが出したメッセージを表示するコマンドを 2 つ選択してください。
- [x] `dmesg`
- [x] `journalctl -k`
- [ ] `lsmod -k`
- [ ] `sysctl -k`
- [ ] `systemctl list-units -k`
:::why
`dmesg` はカーネルのリングバッファを、`journalctl -k`（`--dmesg`）はジャーナルに入ったいまの起動のカーネルのメッセージを表示します（[1.13](#hw)）。ほかの 3 つに、カーネルのメッセージを表示する `-k` はありません。
:::
:::

:::q 2.01.5-07 single
引数を付けずに `sysctl -p` を実行した。読み込まれるファイルはどれか。
- [x] `/etc/sysctl.conf`
- [ ] `/etc/modprobe.d/` の中のすべての `.conf` ファイル
- [ ] `/proc/sys/` の下のすべてのファイル
- [ ] `/etc/default/sysctl`
- [ ] `/boot/config-$(uname -r)`
:::why
`sysctl -p` は、ファイルを指定しなければ `/etc/sysctl.conf` を読んで設定します（[1.12](#sysctl)）。`/etc/sysctl.d/` なども含めたすべての設定ファイルを読むのは `sysctl --system` です。`/etc/modprobe.d/` は `modprobe` の設定、`/boot/config-…` はカーネルをビルドしたときの設定です。
:::
:::

:::q 2.01.5-08 single
USB メモリを挿しても `/dev` にデバイスファイルができない。カーネルから届く知らせ（uevent）と、udev がルールを処理した結果を、その場で表示し続けるコマンドはどれか。
- [ ] `udevadm info`
- [x] `udevadm monitor`
- [ ] `udevadm control --reload`
- [ ] `lsusb -t`
- [ ] `modinfo usb_storage`
:::why
`udevadm monitor` は、`KERNEL[…]`（カーネルの uevent）と `UDEV[…]`（ルールを処理した後）の行を表示し続けます（[1.13](#hw)）。`udevadm info` は 1 つの装置の情報の表示、`udevadm control --reload` はルールの読み直しです。`lsusb -t` はいまつながっている USB の装置を木の形で表示するだけで、知らせは見られません。
:::
:::

:::q 2.01.5-09 fill
`modprobe` が `xfs` を読み込むときに何をするかを、実際には読み込まずに表示させたい。空欄に入るオプションを入力してください。

```text
modprobe ____ -v xfs
```
= -n
= --dry-run
= --show
= -D
= --show-depends
:::why
`-n`（`--dry-run`、`--show`）は、実行せずに、することだけを表示します。`-v` と合わせると、依存するモジュール（`libcrc32c`）から順に `insmod …` の行が出ます（[1.11](#modules)）。`-D`（`--show-depends`）も、読み込まずに同じ `insmod …` の行を出すので正解です（こちらは、すでに読み込まれているモジュールも含めて、依存をすべて表示します）。
:::
:::

:::q 2.01.5-10 single
あるコマンドの出力の一部である。実行したコマンドはどれか。

```text
filename:       /lib/modules/6.1.0-56-arm64/kernel/fs/ext4/ext4.ko
depends:        jbd2,mbcache,crc16
name:           ext4
```
- [ ] `lsmod ext4`
- [x] `modinfo ext4`
- [ ] `modprobe --show-depends ext4`
- [ ] `depmod -n ext4`
- [ ] `uname -a`
:::why
`filename:`、`depends:`、`name:` のように、項目の名前と値を並べるのは `modinfo` です（[1.11](#modules)）。`lsmod` は「Module、Size、Used by」の表、`modprobe --show-depends` は `insmod パス` の行、`depmod -n` は `modules.dep` の形（`パス: パス …`）を出します。
:::
:::

:::q 2.01.5-11 single
kdump を使うために、カーネルパラメータに `crashkernel=256M` を足した。このパラメータの役目はどれか。
- [ ] カーネルパニックの 256 秒後に、自動で再起動する
- [ ] クラッシュダンプの大きさを、256 MB までに制限する
- [x] パニックのときに起動するキャプチャ用のカーネルのために、メモリを取っておく
- [ ] メモリが 256 MB を下回ったら、カーネルパニックを起こす
:::why
kdump は、パニックのときに kexec で 2 つ目のカーネルを起動して、ダンプを保存します。そのカーネルが使うメモリを、`crashkernel=` で起動のときに取っておきます（[1.14](#kdump)）。パニックの後に再起動するまでの秒数は `kernel.panic`（`/proc/sys/kernel/panic`）です。
:::
:::

:::q 2.01.5-12 multi
kexec と kdump の説明として正しいものを 2 つ選択してください。
- [x] kexec は、動いているカーネルから、ファームウェアとブートローダを通さずに別のカーネルを起動する
- [x] kdump は、カーネルパニックのときに、クラッシュダンプを既定で `/var/crash/` に保存する
- [ ] kexec は、カーネルモジュールを外部のソースからビルドし直す
- [ ] kdump は、起動のたびに `/boot` のカーネルをバックアップする
- [ ] `kexec -e` は、パニックのときに使うカーネルを読み込むオプションである
:::why
kexec は、BIOS / UEFI とブートローダを通らずに次のカーネルを起動します。kdump はこれを使い、キャプチャ用のカーネルから `/proc/vmcore` を `/var/crash/` に保存します（[1.14](#kdump)）。モジュールをビルドし直すのは DKMS です。`kexec -e` は読み込んであるカーネルをすぐ起動するオプションで、パニック用に読み込むのは `-p` です。
:::
:::

:::q 2.01.5-13 multi
ハードウェアを調べるコマンドの説明として正しいものを 2 つ選択してください。
- [x] `lspci -k` は、PCI の各装置を扱っているカーネルドライバを表示する
- [x] `lsdev` は、装置ごとの IRQ、I/O ポート、DMA をまとめて表示する
- [ ] `lsusb -t` は、USB の装置を取り外す
- [ ] `lsmod` は、`/lib/modules/` にあるすべてのモジュールのファイルを一覧する
- [ ] `lspci -t` は、PCI の装置を試験する
:::why
`lspci -k` は「Kernel driver in use」の行を出します。`lsdev` は `/proc/interrupts`、`/proc/ioports`、`/proc/dma` を読んで 1 つの表にします（[1.13](#hw)）。`lsusb -t` と `lspci -t` は木の形で表示するオプションです。`lsmod` が一覧するのは、いま読み込まれているモジュールだけです。
:::
:::

:::q 2.01.5-14 single
`/etc/udev/rules.d/70-usb-disk.rules` に次の行がある。このルールの説明として正しいものはどれか。

```text
ACTION=="add", SUBSYSTEM=="block", ATTRS{serial}=="AB12CD34", SYMLINK+="backupdisk"
```
- [ ] すべてのブロックデバイスのシリアル番号を `AB12CD34` に書き換える
- [x] シリアル番号が `AB12CD34` のブロックデバイスが追加されたら、`/dev/backupdisk` というシンボリックリンクを足す
- [ ] `/dev/backupdisk` が追加されたら、シリアル番号が `AB12CD34` かどうかを記録する
- [ ] シリアル番号が `AB12CD34` の装置を、取り外せないようにする
:::why
udev のルールでは、`==` が条件、`=` と `+=` が設定です（[1.13](#hw)）。この行は、条件が 3 つ（追加された、ブロックデバイスである、シリアル番号が一致する）で、設定が 1 つ（`SYMLINK+=` でシンボリックリンクを足す）です。装置を挿す順番で `/dev/sdb` や `/dev/sdc` と名前が変わっても、いつも同じ名前で使えるようになります。
:::
:::

:::q 2.01.5-15 fill
システムの管理者が、自分で作った udev のルール（`.rules` ファイル）を置くディレクトリを、絶対パスで入力してください。
= /etc/udev/rules.d
= /etc/udev/rules.d/
:::why
管理者のルールは `/etc/udev/rules.d/` に置きます。パッケージのルールは `/usr/lib/udev/rules.d/`（Debian 系は `/lib/udev/rules.d/`）にあり、同じ名前のファイルは `/etc/udev/rules.d/` のほうが優先されます（[1.13](#hw)）。udev 自身の設定は `/etc/udev/udev.conf` です。
:::
:::
