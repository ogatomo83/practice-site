HTTP は、クライアントが要求（リクエスト）を 1 つ送り、サーバーが応答（レスポンス）を 1 つ返す、文字の会話でした（[図解 Linux 16.8](../../linux/site/ch16.html#http)）。この章の 3 つのソフトウェアは、その会話のどこに立つかが違います。

| ソフトウェア | 主な役目 | 既定のポート | 設定ファイル |
| --- | --- | --- | --- |
| **Apache HTTP サーバー** | Web サーバー。ファイルやプログラムの出力を返す | 80（HTTPS は 443） | `httpd.conf`（Debian 系は `apache2.conf`） |
| **nginx** | Web サーバー、**リバースプロキシ**（サーバーの手前で受けて、後ろへ中継する） | 80（HTTPS は 443） | `/etc/nginx/nginx.conf` |
| **Squid** | **フォワードプロキシ**（クライアントの代わりに外へ取りに行く）とキャッシュ | **3128** | `/etc/squid/squid.conf` |

応答の 3 桁の数字（ステータスコード）は、この章のあちこちに出てきます。先に整理しておきます。

| コード | 意味 | この章で出る場面 |
| --- | --- | --- |
| 200 | OK | 成功 |
| 301 / 302 | 恒久的な移動 / 一時的な移動 | `Redirect`、nginx の `return`、`rewrite` |
| 401 | 認証が必要（Unauthorized） | Apache の Basic 認証 |
| 403 | 禁止（Forbidden） | `Require` で拒否、Squid の `http_access deny` |
| 404 | 見つからない | ファイルがない |
| 407 | **プロキシの**認証が必要 | Squid のユーザー認証 |
| 500 | サーバー内部のエラー | `.htaccess` の書きまちがい |
| 502 / 503 | 後ろのサーバーから正しい応答が来ない / 一時的に使えない | リバースプロキシ |

Apache HTTP サーバー（以下 Apache）は、プログラムの名前がディストリビューションで違います。**Red Hat 系は `httpd`、Debian 系は `apache2`** です。設定ファイルの名前と場所も、それに合わせて違います。

| | Red Hat 系 | Debian 系 |
| --- | --- | --- |
| パッケージとプログラム | `httpd` | `apache2` |
| 主設定ファイル | **`/etc/httpd/conf/httpd.conf`** | **`/etc/apache2/apache2.conf`** |
| 追加の設定 | `/etc/httpd/conf.d/*.conf` | `sites-enabled/`、`mods-enabled/`、`conf-enabled/` |
| 動かす利用者 | `apache` | `www-data` |
| 公開するディレクトリ | `/var/www/html` | `/var/www/html` |
| ログ | `/var/log/httpd/access_log`、`error_log` | `/var/log/apache2/access.log`、`error.log` |
| 管理コマンド | `apachectl`、`httpd` | `apache2ctl`（`apachectl` はそのリンク） |

Debian 系の `*-available/` は「置いてあるだけ」、`*-enabled/` は「有効」です。有効にするとは、`*-enabled/` に**シンボリックリンク**（[図解 Linux 11.4](../../linux/site/ch11.html#symlink)）を作ることです。`a2ensite` などのコマンドが、そのリンクを作ったり消したりします。

```console
# a2ensite default-ssl
Enabling site default-ssl.
# ls -l /etc/apache2/sites-enabled
lrwxrwxrwx 1 root root 35 Nov 16 21:18 000-default.conf -> ../sites-available/000-default.conf
lrwxrwxrwx 1 root root 35 Nov 16 21:20 default-ssl.conf -> ../sites-available/default-ssl.conf
```

| コマンド（Debian 系） | すること |
| --- | --- |
| `a2ensite` / `a2dissite` | サイト（バーチャルホスト）を有効 / 無効にする |
| `a2enmod` / `a2dismod` | モジュールを有効 / 無効にする（例：`a2enmod ssl`） |
| `a2enconf` / `a2disconf` | `conf-available/` の設定を有効 / 無効にする |

### httpd.conf の基本のディレクティブ

設定の 1 行を**ディレクティブ**（指示）と呼びます。「名前 値」の形です。rockylinux:9 の `httpd.conf` から、コメントを除いた主な行です。

```conf
ServerRoot "/etc/httpd"
Listen 80
Include conf.modules.d/*.conf
User apache
Group apache
ServerAdmin root@localhost
DocumentRoot "/var/www/html"
<Directory "/var/www/html">
    Options Indexes FollowSymLinks
    AllowOverride None
    Require all granted
</Directory>
<IfModule dir_module>
    DirectoryIndex index.html
</IfModule>
ErrorLog "logs/error_log"
LogLevel warn
LogFormat "%h %l %u %t \"%r\" %>s %b \"%{Referer}i\" \"%{User-Agent}i\"" combined
LogFormat "%h %l %u %t \"%r\" %>s %b" common
CustomLog "logs/access_log" combined
IncludeOptional conf.d/*.conf
```

| ディレクティブ | 意味 |
| --- | --- |
| `ServerRoot` | 設定やログの**相対パスの起点**。`logs/error_log` は `/etc/httpd/logs/error_log` になる |
| `Listen` | 待ち受ける番地とポート（`Listen 80`、`Listen 192.168.1.10:8080`） |
| `User` / `Group` | リクエストを処理する子プロセスの利用者とグループ |
| `ServerName` | サーバーが名乗る名前（`www.example.com:80`） |
| `ServerAdmin` | 管理者のメールアドレス（エラーページに出る） |
| `DocumentRoot` | 公開するファイルの一番上のディレクトリ |
| `DirectoryIndex` | ディレクトリが指定されたときに返すファイル（`index.html`） |
| `LoadModule` | モジュールを読み込む（`LoadModule ssl_module modules/mod_ssl.so`） |
| `Include` / `IncludeOptional` | ほかの設定ファイルを読み込む。`IncludeOptional` は合うファイルがなくてもエラーにしない |
| `ErrorLog` / `LogLevel` | エラーログの場所と、どの重さから記録するか（既定は `warn`） |
| `LogFormat` / `CustomLog` | アクセスログの書式に名前を付ける / 書式を選んでファイルに書く |

`<Directory パス> … </Directory>` のように山かっこで囲んだ部分は、**その範囲だけ**に効く設定です。囲みには次の種類があります。

| 囲み | 効く範囲 |
| --- | --- |
| `<Directory>` | ファイルシステムの上のディレクトリ（とその下） |
| `<Files>` | ファイル名（`<Files ".ht*">`） |
| `<Location>` | URL のパス（ファイルシステムとは関係ない） |
| `<VirtualHost>` | バーチャルホスト（[後の節](#apache-vhost)） |
| `<IfModule>` | そのモジュールが読み込まれているときだけ |

### apachectl と httpd：検査してから読み込む

設定を変えたら、**構文の検査 → 読み込み直し**の順で反映します。管理コマンドは `apachectl`（Debian 系は `apache2ctl`）です。

```console
# apachectl configtest
Syntax OK
# apachectl graceful
```

| `apachectl` のサブコマンド | すること |
| --- | --- |
| `start` / `stop` | 起動 / 停止 |
| `restart` | 再起動。処理中の接続は**切られる** |
| **`graceful`** | 処理中のリクエストが**終わるのを待って**、設定を読み込み直す |
| `graceful-stop` | 処理中のリクエストが終わるのを待って、停止する |
| **`configtest`** | 設定ファイルの構文を検査する（`httpd -t` と同じ） |
| `status` / `fullstatus` | 状態を表示する（`fullstatus` は mod_status が必要） |

`httpd`（Debian 系は `apache2`。ふつうは `apache2ctl` 経由で使います）に直接オプションを付けると、設定の中身を調べられます。

| オプション | すること |
| --- | --- |
| **`-t`** | 設定ファイルの構文を検査する（`Syntax OK`） |
| **`-S`** | バーチャルホストの設定を解釈した結果を表示する |
| **`-M`** | 読み込まれているモジュールをすべて表示する（`(static)` と `(shared)`） |
| `-l` | **組み込まれている**（静的な）モジュールだけを表示する |
| `-v` / `-V` | バージョン / コンパイル時の設定（MPM、既定の設定ファイル）を表示する |
| `-f ファイル` | 別の設定ファイルを使う |
| `-k start` など | `start`、`restart`、`graceful`、`graceful-stop`、`stop` |

```console
# httpd -l
Compiled in modules:
  core.c
  mod_so.c
  http_core.c
# httpd -M | head -6
Loaded Modules:
 core_module (static)
 so_module (static)
 http_module (static)
 access_compat_module (shared)
 actions_module (shared)
```

:::note apachectl はディストリビューションで少し違う
Apache 本家と Debian 系の `apachectl`（`apache2ctl`）は、知らない引数を `httpd` にそのまま渡します（`apache2ctl -S`、`apache2ctl -M` が使えます）。Red Hat 系の `apachectl` は systemctl を呼ぶ小さなスクリプトで、`start`、`stop`、`restart`、`graceful`、`graceful-stop`、`configtest`、`status` などに限られます。rockylinux:9 で `apachectl -S` は「The "-S" option is not supported.」でした。Red Hat 系では `httpd -S` を使います。systemd のもとでは、起動と停止は `systemctl start httpd`（Debian 系は `apache2`）でも行います。
:::

### アクセスログとエラーログ

アクセスログは、リクエスト 1 つにつき 1 行です。書式は `LogFormat` で名前を付け、`CustomLog` で選びます。

```text
127.0.0.1 - alice [16/Nov/2026:21:19:39 +0000] "GET /ht/ HTTP/1.1" 401 381 "-" "curl/7.76.1"
127.0.0.1 - - [16/Nov/2026:21:19:39 +0000] "GET /nothing HTTP/1.1" 404 196 "-" "curl/7.76.1"
```

| 書式の文字 | 意味 | 上の 1 行目 |
| --- | --- | --- |
| `%h` | クライアントの番地（ホスト） | `127.0.0.1` |
| `%l` | identd の名前（ふつうは `-`） | `-` |
| `%u` | 認証した利用者の名前（認証がなければ `-`） | `alice` |
| `%t` | リクエストを受けた時刻 | `[16/Nov/2026:21:19:39 +0000]` |
| `%r` | リクエストの 1 行目 | `GET /ht/ HTTP/1.1` |
| `%>s` | 最後に返したステータスコード | `401` |
| `%b` | 応答の本体のバイト数 | `381` |
| `%{Referer}i` / `%{User-Agent}i` | リクエストのヘッダーの値 | `-` / `curl/7.76.1` |

`common` は `%b` までの 7 つ、**`combined`** はそれに Referer と User-Agent を足した書式です。

エラーログには、時刻、**[モジュール:重さ]**、プロセス、クライアント、メッセージが並びます。うまく動かないときは、まずここを見ます。

```text
[Mon Nov 16 21:19:39.838036 2026] [auth_basic:error] [pid 452:tid 624] [client 127.0.0.1:50196] AH01617: user alice: authentication failure for "/secret/": Password Mismatch
[Mon Nov 16 21:19:39.847302 2026] [authz_core:error] [pid 452:tid 609] [client 127.0.0.1:50232] AH01630: client denied by server configuration: /var/www/html/ht/.htaccess
```

`LogLevel` の重さは、syslog と同じ並びです（[図解 LinuC 9.3](../../linuc/site/ch09.html#rsyslog)）。`emerg`、`alert`、`crit`、`error`、`warn`、`notice`、`info`、`debug` の順に軽くなり、指定した重さ以上が記録されます。

## アクセス制御と Basic 認証：Require、htpasswd、.htaccess {#apache-auth}

```fig seq Basic 認証の流れ。1 回目は 401 で断られ、ブラウザが名前とパスワードを聞いて、Authorization ヘッダーを付けて送り直す
{
  colw: 250,
  actors: [
    { id: 'b', label: 'ブラウザ' },
    { id: 'a', label: 'Apache' },
    { id: 'f', label: 'AuthUserFile' },
  ],
  msgs: [
    { from: 'b', to: 'a', label: 'GET /secret/' },
    { from: 'a', to: 'b', label: '401  WWW-Authenticate: Basic realm="Members Only"', style: 'bad' },
    { note: '名前とパスワードを入力', at: 'b' },
    { from: 'b', to: 'a', label: 'GET /secret/  Authorization: Basic YWxpY2U6…', style: 'accent' },
    { from: 'a', to: 'f', label: 'alice のハッシュと比べる（mod_authn_file）' },
    { from: 'a', to: 'b', label: '200 OK' },
  ],
}
```

Apache が「このリクエストを通すか」を決める仕組みは、2 つに分かれます。

- **認証**（authentication）：相手が誰かを確かめる。モジュール名は `mod_auth…` と `mod_authn_…`
- **認可**（authorization）：その相手を通してよいかを決める。モジュール名は `mod_authz_…`

| モジュール | 受け持つもの |
| --- | --- |
| **`mod_auth_basic`** | Basic 認証（`AuthType Basic`） |
| `mod_authn_file` | パスワードファイルで確かめる（`AuthUserFile`） |
| `mod_authz_core` | `Require` と `<RequireAll>` などの土台 |
| **`mod_authz_host`** | 番地やホスト名で決める（`Require ip`、`Require host`、`Require local`） |
| `mod_authz_user` | 利用者で決める（`Require user`、`Require valid-user`） |
| `mod_authz_groupfile` | グループで決める（`AuthGroupFile`、`Require group`） |

### Require：誰を通すか（Apache 2.4）

Apache 2.4 では、通す条件を **`Require`** で書きます。

| 書き方 | 通す相手 |
| --- | --- |
| `Require all granted` | 全員 |
| `Require all denied` | 誰も通さない |
| `Require ip 192.168.1.0/24` | その番地（ネットワーク）から来たもの |
| `Require host example.com` | 逆引きした名前が example.com で終わるもの |
| `Require local` | 同じ機械から来たもの（127.0.0.0/8、::1） |
| `Require valid-user` | 認証に成功した利用者すべて |
| `Require user alice bob` | 認証に成功した alice か bob |
| `Require group staff` | 認証に成功し、グループ staff に入っている利用者 |

`Require` を何行か並べると、**どれか 1 つ**に合えば通ります（`<RequireAny>` と同じ）。**すべて**に合うことを求めるときは `<RequireAll>` で囲みます。`Require not ip …` のような否定は、`<RequireAll>` の中でだけ書けます。

```conf
<Directory "/var/www/shop">
    <RequireAll>
        Require all granted
        Require not ip 10.0.0.5
    </RequireAll>
</Directory>
```

Apache 2.2 までは、`Order`、`Allow`、`Deny` で書きました。2.4 でも互換モジュール（mod_access_compat）で動きます。古い設定を読む問題のために、形を覚えておきます。

| 2.2 の書き方 | 意味 | 2.4 の書き方 |
| --- | --- | --- |
| `Order allow,deny` と `Allow from all` | 全員を通す | `Require all granted` |
| `Order deny,allow` と `Deny from all` | 誰も通さない | `Require all denied` |
| `Order deny,allow` と `Deny from all` と `Allow from 192.168.1.0/24` | 192.168.1.0/24 だけ通す | `Require ip 192.168.1.0/24` |

`Order deny,allow` は「Deny を先に、Allow を後に調べ、**後のものが勝つ**。どちらにも合わなければ通す」です。`Order allow,deny` はその逆で、Deny が勝ち、どちらにも合わなければ拒否します。

### Basic 認証を付ける

Basic 認証は、ディレクトリに名前とパスワードを求める、いちばん単純な認証です。4 つのディレクティブで書きます。

```conf
<Directory "/var/www/html/secret">
    AuthType Basic
    AuthName "Members Only"
    AuthUserFile /etc/httpd/.htpasswd
    Require valid-user
</Directory>
```

| ディレクティブ | 意味 |
| --- | --- |
| `AuthType` | 認証の方式。`Basic` か `Digest` |
| `AuthName` | 認証の領域の名前（realm）。ブラウザの入力の窓に出る |
| **`AuthUserFile`** | 利用者とパスワードのファイル（`htpasswd` で作る） |
| **`AuthGroupFile`** | グループと利用者の対応を書いたファイル |
| `Require` | 通す利用者（`valid-user`、`user 名前`、`group 名前`） |

パスワードのファイルは **`htpasswd`** で作ります。

```console
# htpasswd -c /etc/httpd/.htpasswd alice
New password:
Re-type new password:
Adding password for user alice
# htpasswd /etc/httpd/.htpasswd bob
# cat /etc/httpd/.htpasswd
alice:$apr1$3rGCgc3u$IV89bSOTtduEn.R1a8DuZ/
bob:$apr1$QGUwsJLD$XfS898UbAxjvhfXklBNdD.
# htpasswd -D /etc/httpd/.htpasswd bob
Deleting password for user bob
```

| `htpasswd` のオプション | すること |
| --- | --- |
| **`-c`** | ファイルを**新しく作る**。すでにあるファイルは**上書きされ、ほかの利用者は消える** |
| `-b` | パスワードをコマンドラインの引数で渡す（`htpasswd -b ファイル 名前 パスワード`） |
| `-n` | ファイルを書き換えず、結果を標準出力に表示する |
| **`-D`** | 利用者を削除する |
| `-m` | MD5 でハッシュにする（既定。`$apr1$` で始まる） |
| `-B` | bcrypt でハッシュにする（`$2y$` で始まる。より安全） |
| `-s` / `-d` / `-p` | SHA-1 / crypt / 平文（どれも安全ではない） |
| `-v` | 利用者のパスワードが合っているかを確かめる |

ファイルは「名前:ハッシュ」が 1 行に 1 人です。2 人目からは `-c` を**付けません**。

グループで許可するときは、`AuthGroupFile` に「**グループ名: 利用者 利用者 …**」を書いたファイルを指定します。

```conf
# /etc/httpd/.htgroup の中身
staff: alice carol

# 設定
<Directory "/var/www/html/staff">
    AuthType Basic
    AuthName "Staff"
    AuthUserFile /etc/httpd/.htpasswd
    AuthGroupFile /etc/httpd/.htgroup
    Require group staff
</Directory>
```

この設定で試すと、alice は 200、staff に入っていない bob は 401 でした。パスワードが合っていても、認可で落ちます。

:::warn 試験の注意：Basic 認証と htpasswd
- `htpasswd -c` は**新規作成**です。2 人目に `-c` を付けると、1 人目が消えます
- Basic 認証は、名前とパスワードを **Base64 にするだけ**で送ります。暗号ではないので、盗み見を防ぐには HTTPS と組み合わせます。Digest 認証（`AuthType Digest`、ファイルは `htdigest` で作る）は、パスワードそのものを送りません
- パスワードファイルは、`DocumentRoot` の**外**に置きます。中に置くと、ブラウザから取られるおそれがあります
:::

### .htaccess：ディレクトリごとに設定を上書きする

**`.htaccess`** は、公開するディレクトリの中に置く設定ファイルです。主設定ファイルを触れない利用者が、自分のディレクトリだけ設定を変えられます。ファイルの名前は `AccessFileName` で決まり、既定が `.htaccess` です。

```conf
# /var/www/html/ht/.htaccess
AuthType Basic
AuthName "ht"
AuthUserFile /etc/httpd/.htpasswd
Require user bob
```

`.htaccess` に**何を書いてよいか**は、主設定ファイルの `<Directory>` の中の **`AllowOverride`** で決まります。

| `AllowOverride` の値 | `.htaccess` に書けるもの |
| --- | --- |
| **`None`** | 何も書けない。`.htaccess` は**読まれない**（2.4 の既定） |
| `All` | `.htaccess` に書けるディレクティブすべて |
| `AuthConfig` | 認証（`AuthType`、`AuthName`、`AuthUserFile`、`Require` など） |
| `Limit` | 番地によるアクセス制御（`Order`、`Allow`、`Deny`） |
| `FileInfo` | 文書の種類や転送（`Redirect`、`ErrorDocument`、`RewriteRule` など） |
| `Indexes` | ディレクトリの一覧（`DirectoryIndex` など） |
| `Options` | `Options` ディレクティブ |

上の `.htaccess` を、`AllowOverride` を変えながら試した結果です。

| 主設定ファイルの設定 | `/ht/` へのリクエスト（認証なし） |
| --- | --- |
| `AllowOverride None` | **200**（`.htaccess` は無視され、認証なしで見える） |
| `AllowOverride Limit` | **500**（エラーログに `AuthType not allowed here`） |
| `AllowOverride AuthConfig` | **401**（認証を求められる） |

`.htaccess` は**リクエストのたびに読まれる**ので、書き換えたあとに Apache を読み込み直す必要はありません。その代わり、遅くなります。主設定ファイルを触れるなら、`<Directory>` に書くほうが速く安全です。`.ht` で始まるファイルは、既定の設定（`<Files ".ht*"> Require all denied`）でブラウザから取れないようになっています。

### バーチャルホスト：1 台で何個ものサイトを出す

**バーチャルホスト**は、1 つの Apache で複数のサイトを出す仕組みです。2 種類あります。

| 種類 | 何で振り分けるか | 書き方 |
| --- | --- | --- |
| **名前ベース** | リクエストの **Host ヘッダー**（ホスト名）。番地は 1 つでよい | `<VirtualHost *:80>` と `ServerName` |
| **IP ベース** | 届いた先の **IP アドレス**。サイトの数だけ番地が要る | `<VirtualHost 192.168.1.10:80>` |

```conf
<VirtualHost *:80>
    ServerName www.example.com
    DocumentRoot /var/www/html
</VirtualHost>

<VirtualHost *:80>
    ServerName shop.example.com
    ServerAlias shop
    DocumentRoot /var/www/shop
    CustomLog logs/shop_access_log combined
    ErrorLog logs/shop_error_log
</VirtualHost>
```

`ServerName` がそのサイトの名前、`ServerAlias` は別名です。`DocumentRoot`、`CustomLog`、`ErrorLog` は、バーチャルホストごとに書けます。解釈した結果は **`httpd -S`**（Debian 系は `apache2ctl -S`）で確かめます。

```console
# httpd -S
VirtualHost configuration:
*:80                   is a NameVirtualHost
         default server www.example.com (/etc/httpd/conf.d/test.conf:2)
         port 80 namevhost www.example.com (/etc/httpd/conf.d/test.conf:2)
         port 80 namevhost shop.example.com (/etc/httpd/conf.d/test.conf:27)
                 alias shop
         port 80 namevhost blog.example.com (/etc/httpd/conf.d/test.conf:37)
```

`default server` の行に注目します。Host ヘッダーがどの `ServerName` にも `ServerAlias` にも合わないリクエストは、**設定ファイルで最初に書いたバーチャルホスト**が受けます。上の設定で `Host: unknown.example.com` を送ると、www.example.com の中身が返りました。

:::warn 試験の注意：NameVirtualHost
Apache 2.2 までは、名前ベースのバーチャルホストを使うために `NameVirtualHost *:80` の行が必要でした。**2.4 では不要**で、書くと「NameVirtualHost has no effect」という警告が出ます。同じ番地とポートの `<VirtualHost>` が 2 つ以上あれば、自動的に名前ベースになります。
:::

### Redirect：別の URL へ行かせる

**`Redirect`**（mod_alias）は、ある URL パスへのリクエストに「別の URL へ行ってください」と答えさせます。

```conf
Redirect /old http://www.example.com/new
Redirect permanent /old2 http://www.example.com/new2
Redirect seeother /old3 http://www.example.com/new3
Redirect gone /gone
RedirectMatch ^/docs/(.*)$ http://docs.example.com/$1
```

書式は `Redirect [ステータス] URL のパス 行き先の URL` です。ステータスを省くと **302**（一時的な移動）です。

| ステータスの書き方 | コード | 意味 |
| --- | --- | --- |
| `temp`（既定） | **302** | 一時的な移動 |
| `permanent` | **301** | 恒久的な移動 |
| `seeother` | 303 | 別のものを見よ |
| `gone` | 410 | なくなった（行き先の URL は書かない） |

パスは**前方一致**です。指定したパスより後ろの部分は、行き先の URL の後ろに付きます。curl で確かめた結果です。

| リクエスト | 応答 |
| --- | --- |
| `/old` | 302、`Location: http://www.example.com/new` |
| `/old/a.html` | 302、`Location: http://www.example.com/new/a.html` |
| `/old2` | 301、`Location: http://www.example.com/new2` |
| `/docs/x/y.html` | 302、`Location: http://docs.example.com/x/y.html` |
| `/gone` | 410 |

`RedirectMatch` は、パスを正規表現で書けます。`(.*)` で取った部分を `$1` で使います。

### MPM とプロセス数：何人まで同時に相手をするか

```fig graph MPM は、リクエストをプロセスとスレッドにどう割り当てるかを決める。prefork は 1 プロセスが 1 接続、worker と event は 1 プロセスの中の複数のスレッドが受け持つ
{
  col: 150, row: 78,
  nodes: [
    { id: 'p', label: '親プロセス', sub: 'root', x: 0, y: 0.5, kind: 'accent', mono: false },
    { id: 'c1', label: '子プロセス', sub: '1 接続', x: 1, y: 0, mono: false },
    { id: 'c2', label: '子プロセス', sub: '1 接続', x: 1, y: 1, mono: false },
    { id: 'q', label: '親プロセス', sub: 'root', x: 2.4, y: 0.5, kind: 'accent', mono: false },
    { id: 'd1', label: '子プロセス', sub: 'スレッド × 25', x: 3.4, y: 0, kind: 'ext', mono: false },
    { id: 'd2', label: '子プロセス', sub: 'スレッド × 25', x: 3.4, y: 1, kind: 'ext', mono: false },
  ],
  edges: [
    { from: 'p', to: 'c1' }, { from: 'p', to: 'c2' },
    { from: 'q', to: 'd1' }, { from: 'q', to: 'd2' },
  ],
  groups: [
    { label: 'prefork', nodes: ['p', 'c1', 'c2'] },
    { label: 'worker・event', nodes: ['q', 'd1', 'd2'] },
  ],
}
```

Apache は、親プロセス（root）が子プロセスを作り、子プロセス（apache や www-data）がリクエストを処理します。その作り方を決める部品が **MPM**（Multi-Processing Module）です。

| MPM | 仕組み | 特徴 |
| --- | --- | --- |
| **prefork** | 1 つの子プロセスが 1 つの接続を受け持つ。スレッドは使わない | スレッドに対応していないモジュールでも安全。メモリを多く使う |
| **worker** | 1 つの子プロセスの中の複数のスレッドが、1 つずつ接続を受け持つ | 少ないメモリで多くの接続をさばける |
| **event** | worker と同じ。Keep-Alive で待っているだけの接続を、専用のスレッドにまとめる | いまの既定（rockylinux:9、debian:12 とも event） |

いま使っている MPM は `httpd -V` の `Server MPM:` の行でわかります。プロセスとスレッドの数は、次のディレクティブで決めます。debian:12 の既定の値です。

```conf
# mpm_prefork.conf                 # mpm_event.conf
StartServers            5          StartServers            2
MinSpareServers         5          MinSpareThreads         25
MaxSpareServers         10         MaxSpareThreads         75
MaxRequestWorkers       150        ThreadsPerChild         25
MaxConnectionsPerChild  0          MaxRequestWorkers       150
                                   MaxConnectionsPerChild  0
```

| ディレクティブ | 意味 | 使う MPM |
| --- | --- | --- |
| `StartServers` | 起動したときに作る子プロセスの数 | すべて |
| `MinSpareServers` | 待機している（暇な）子プロセスの**最小**の数。下回ると増やす | prefork |
| `MaxSpareServers` | 待機している子プロセスの**最大**の数。上回ると減らす | prefork |
| `MinSpareThreads` / `MaxSpareThreads` | 待機しているスレッドの最小 / 最大の数 | worker、event |
| `ThreadsPerChild` | 1 つの子プロセスが作るスレッドの数 | worker、event |
| **`MaxRequestWorkers`** | **同時に処理できるリクエストの最大の数**。超えたぶんは待たされる。prefork では子プロセスの最大の数 | すべて |
| `ServerLimit` | 子プロセスの数の上限。`MaxRequestWorkers` をこれより大きくはできない | すべて |
| **`MaxConnectionsPerChild`** | 1 つの子プロセスが、この数の接続を処理したら終了して作り直す。**0 は無制限** | すべて |

Apache 2.2 までの名前も問われます。**`MaxClients` は `MaxRequestWorkers` の古い名前**、**`MaxRequestsPerChild` は `MaxConnectionsPerChild` の古い名前**です（2.4 でも古い名前で書けます。`httpd -L` に「Deprecated name of MaxRequestWorkers」と出ます）。

`MaxConnectionsPerChild` を 0 以外にすると、長く動いた子プロセスが作り直されます。プログラムのメモリリーク（使ったメモリを返し忘れる不具合）があっても、メモリが増え続けるのを防げます。

接続を使い回す **Keep-Alive** の設定も、同時に相手をできる数に関係します。

| ディレクティブ | 意味 |
| --- | --- |
| `KeepAlive On` | 1 つの接続で複数のリクエストを受ける |
| `MaxKeepAliveRequests 100` | 1 つの接続で受けるリクエストの最大の数 |
| `KeepAliveTimeout 5` | 次のリクエストを待つ秒数。長いと、待っているだけの接続がワーカーを占める |
| `Timeout` | 送受信が止まったときに待つ秒数 |

:::tip MaxRequestWorkers の決め方
prefork では、`MaxRequestWorkers` × 子プロセス 1 つのメモリが、機械のメモリを超えないようにします。超えるとスワップが始まり、急に遅くなります。prefork で 256 より大きくするときは、`ServerLimit` も一緒に上げます。
:::

## 証明書は、誰が何を証明するか：鍵、CSR、CA {#cert}

```fig seq サーバー証明書ができるまで。秘密鍵はサーバーから出さない。CA に送るのは CSR（公開鍵と名前）だけ
{
  colw: 270,
  actors: [
    { id: 's', label: 'サーバーの管理者' },
    { id: 'ca', label: '認証局（CA）' },
  ],
  msgs: [
    { self: 's', label: '1. 秘密鍵を作る：openssl genrsa -out server.key 2048' },
    { self: 's', label: '2. CSR を作る：openssl req -new -key server.key -out server.csr' },
    { from: 's', to: 'ca', label: 'server.csr（公開鍵 + 名前。秘密鍵で署名してある）', style: 'accent' },
    { self: 'ca', label: '3. 申請者を確かめ、CA の秘密鍵で署名する' },
    { from: 'ca', to: 's', label: 'server.crt（サーバー証明書）+ 中間 CA の証明書' },
    { self: 's', label: '4. Web サーバーに server.crt と server.key を設定する' },
  ],
}
```

**HTTPS** は、HTTP の会話を **TLS**（Transport Layer Security。古い名前は SSL）で包んだものです。ポートは **443** です。TLS は 2 つのことをします。通信の暗号化と、**相手が本物のサーバーかの確認**です。確認に使うのが**サーバー証明書**です。

公開鍵と秘密鍵の組は、SSH の鍵で見ました（[図解 LinuC 10.8](../../linuc/site/ch10.html#ssh-keys)）。証明書に関わるファイルは 3 つです。

| ファイル | 中身 | 扱い |
| --- | --- | --- |
| **秘密鍵**（`server.key`） | サーバーだけが持つ鍵 | **誰にも渡さない**。root だけが読めるようにする（600） |
| **CSR**（`server.csr`） | 証明書署名要求（Certificate Signing Request）。**公開鍵**と、サーバーの名前（識別名）を入れ、自分の秘密鍵で署名したもの | CA に送る。秘密鍵は**入っていない** |
| **証明書**（`server.crt`） | 公開鍵と名前に、**CA が署名**したもの。有効期限がある | 公開してよい。クライアントに送られる |

**認証局**（CA、Certificate Authority）は、申請者を確かめて、証明書に署名する組織です。ブラウザや OS は、信頼する CA の証明書（**ルート証明書**）を初めから持っています。CA の署名をたどれれば、そのサーバーを本物とみなします。

**自己署名証明書**は、CA の代わりに**自分の秘密鍵で署名した**証明書です。発行者（issuer）と持ち主（subject）が同じになります。暗号化はできますが、誰も本物だと保証していないので、ブラウザは警告を出します。試験や社内の検証に使います。

### openssl コマンドで作る

**`openssl`** は、鍵や証明書を扱うコマンドです。`openssl サブコマンド オプション` の形で使います。

```console
# openssl genrsa -out server.key 2048
# openssl req -new -key server.key -out server.csr
Country Name (2 letter code) [XX]:JP
State or Province Name (full name) []:Tokyo
Organization Name (eg, company) [Default Company Ltd]:Example
Common Name (eg, your name or your server's hostname) []:www.example.com
（ほかの項目は省略）
# openssl x509 -req -in server.csr -signkey server.key -days 365 -out server.crt
Certificate request self-signature ok
subject=C=JP, ST=Tokyo, O=Example, CN=www.example.com
```

1 行目で秘密鍵（RSA、2048 ビット）、2 行目で CSR を作ります。CSR を作るときに聞かれる項目が**識別名**（DN）です。**Common Name（CN）には、サーバーのホスト名（FQDN）**を入れます。3 行目は、CA に送る代わりに、**同じ鍵で署名**して自己署名証明書にしています（`-signkey`）。

鍵と自己署名証明書を、1 回で作ることもできます。

```console
# openssl req -x509 -newkey rsa:2048 -nodes -keyout server.key -out server.crt -days 365
```

| サブコマンドとオプション | すること |
| --- | --- |
| `openssl genrsa -out 鍵 2048` | RSA の秘密鍵を作る。`-aes256` などを付けると、鍵をパスフレーズで暗号化する |
| **`openssl req -new -key 鍵 -out CSR`** | CSR を作る |
| `openssl req -x509 …` | CSR ではなく、**自己署名証明書**を出力する |
| `-newkey rsa:2048` | 鍵も一緒に新しく作る（`-keyout` で書き出す先を指定） |
| `-nodes`（OpenSSL 3 では `-noenc`） | 秘密鍵を**暗号化しない**（パスフレーズを付けない） |
| `-days 365` | 証明書の有効期間（日数） |
| `-subj "/C=JP/CN=www.example.com"` | 識別名を、質問に答える代わりに引数で渡す |
| `openssl x509 -req -in CSR -signkey 鍵 -out 証明書` | CSR に、その鍵で署名して証明書にする（自己署名） |
| `openssl req -in CSR -noout -text` | CSR の中身を表示する |
| **`openssl x509 -in 証明書 -noout -text`** | 証明書の中身を表示する。`-subject`、`-issuer`、`-dates` で一部だけ |
| `openssl rsa -in 鍵 -out 鍵2` | 鍵を読み込んで書き直す。パスフレーズ付きの鍵から、パスフレーズを外すのに使う |
| `openssl verify -CAfile CA証明書 証明書` | 証明書の署名をたどれるかを確かめる |
| **`openssl s_client -connect ホスト:443`** | TLS でサーバーにつなぎ、証明書とプロトコルを表示する |

できた証明書を見ます。自己署名なので、subject と issuer が同じです。

```console
# openssl x509 -in server.crt -noout -subject -issuer -dates
subject=C=JP, ST=Tokyo, O=Example, CN=www.example.com
issuer=C=JP, ST=Tokyo, O=Example, CN=www.example.com
notBefore=Nov 16 21:19:17 2026 GMT
notAfter=Nov 16 21:19:17 2027 GMT
```

鍵と証明書は、ふつう **PEM** という文字の形式です。`-----BEGIN CERTIFICATE-----`（証明書）、`-----BEGIN CERTIFICATE REQUEST-----`（CSR）、`-----BEGIN PRIVATE KEY-----`（秘密鍵）の行で始まるので、`head -1` で種類がわかります。

:::warn 試験の注意：パスフレーズ付きの秘密鍵
秘密鍵をパスフレーズで暗号化すると、Apache は**起動のたびにパスフレーズを聞きます**。自動で起動できなくなるので、サーバーではパスフレーズなしの鍵（`-nodes`）にして、ファイルの許可（600、root）で守るのがふつうです。付いているパスフレーズは `openssl rsa -in server.key -out server.key.nopass` で外せます。
:::

### 鍵と証明書の置き場所

| | Debian 系 | Red Hat 系 |
| --- | --- | --- |
| OpenSSL の設定ファイル | `/etc/ssl/openssl.cnf` | `/etc/pki/tls/openssl.cnf` |
| 証明書 | **`/etc/ssl/certs/`** | **`/etc/pki/tls/certs/`** |
| 秘密鍵 | **`/etc/ssl/private/`**（root と ssl-cert グループだけが入れる） | **`/etc/pki/tls/private/`** |
| 信頼する CA の束 | `/etc/ssl/certs/ca-certificates.crt` | `/etc/pki/tls/certs/ca-bundle.crt`（元は `/etc/pki/ca-trust/`） |

Red Hat 系にも `/etc/ssl/` はありますが、中身は `/etc/pki/tls/` へのシンボリックリンクです（rockylinux:9 では `/etc/ssl/certs -> /etc/pki/tls/certs`）。

Apache の HTTPS は **mod_ssl** が受け持ちます。Red Hat 系は `mod_ssl` パッケージを入れると `/etc/httpd/conf.d/ssl.conf` が置かれます。Debian 系は `a2enmod ssl` と `a2ensite default-ssl` で有効にします。

```conf
Listen 443 https

<VirtualHost *:443>
    ServerName www.example.com
    DocumentRoot /var/www/html

    SSLEngine on
    SSLCertificateFile      /etc/pki/tls/certs/server.crt
    SSLCertificateKeyFile   /etc/pki/tls/private/server.key

    SSLProtocol             all -SSLv3 -TLSv1 -TLSv1.1
    SSLCipherSuite          HIGH:!aNULL:!MD5
    SSLHonorCipherOrder     on
</VirtualHost>
```

| ディレクティブ | 意味 |
| --- | --- |
| **`SSLEngine on`** | このバーチャルホストで SSL/TLS を使う |
| **`SSLCertificateFile`** | **サーバー証明書**のファイル（PEM）。2.4.8 以降は、後ろに中間 CA の証明書を続けて書ける |
| **`SSLCertificateKeyFile`** | サーバーの**秘密鍵**のファイル |
| `SSLCertificateChainFile` | 中間 CA の証明書のファイル（2.4.8 より前の書き方。いまは非推奨） |
| **`SSLCACertificateFile`** | **クライアント証明書を検証する**ための CA の証明書を、**1 つのファイル**にまとめたもの |
| **`SSLCACertificatePath`** | 同じ目的の CA の証明書を置いた**ディレクトリ**（1 ファイルに 1 つ。ハッシュ値の名前のリンクで探す） |
| `SSLVerifyClient` | クライアント証明書を求めるか。`none`（既定）、`optional`、`require` |
| **`SSLProtocol`** | 使ってよいプロトコルの版 |
| **`SSLCipherSuite`** | 使ってよい暗号の組（暗号スイート） |
| `SSLHonorCipherOrder on` | 暗号を選ぶとき、クライアントではなく**サーバーの順番**を優先する |

**中間 CA** は、ルート CA に署名してもらい、サーバー証明書に署名する CA です。ブラウザはルート CA の証明書しか持っていないので、サーバーが中間 CA の証明書も送らないと、署名をたどれません。Apache 2.4.8 以降では、`SSLCertificateFile` のファイルに「サーバー証明書、中間 CA の証明書」の順で続けて入れます。

`SSLCACertificateFile` と `SSLCACertificatePath` は、名前が似ていますが、**クライアント証明書**（利用者の側が出す証明書）を確かめるときに、どの CA を信頼するかの設定です。`File` は 1 つのファイル、`Path` はディレクトリです。

### 安全でないプロトコルと暗号を止める

SSL/TLS には古い版があり、弱点が見つかっています。使ってよいのは **TLS 1.2 と TLS 1.3** です。

| 版 | 状態 |
| --- | --- |
| SSLv2、**SSLv3** | 安全でない（SSLv3 は POODLE 攻撃）。使わない |
| **TLS 1.0、TLS 1.1** | 古く、非推奨。止める |
| TLS 1.2、TLS 1.3 | 使う |

`SSLProtocol` は、`all` から要らないものを `-` で引くか、`-all` に使うものを `+` で足します。

```conf
SSLProtocol all -SSLv3 -TLSv1 -TLSv1.1
SSLProtocol -all +TLSv1.2 +TLSv1.3
```

どちらも「TLS 1.2 と 1.3 だけ」です。`TLSv1` は TLS 1.0 のことです。いまの Apache は SSLv2 に対応しておらず、`+SSLv2` と書くと `SSLProtocol: SSLv2 is no longer supported` でエラーになります。

`SSLCipherSuite` は、OpenSSL の書き方で暗号の組を選びます。`:` で区切って並べます。

| 書き方 | 意味 |
| --- | --- |
| `HIGH` | 鍵の長い、強い暗号の組 |
| `MEDIUM` / `LOW` | 中くらい / 弱い暗号の組 |
| **`!aNULL`** | 認証をしない暗号を**除く**（`!` は、後で足しても戻らない除外） |
| `!MD5`、`!RC4`、`!3DES` | その方式を使う暗号を除く |
| `-RC4` | 除く（後で足し直せる） |
| `+RC4` | 一覧の最後に回す |

どの暗号が残るかは、`openssl ciphers -v 'HIGH:!aNULL:!MD5'` で一覧できます。止めるべき弱い暗号は、**RC4、DES と 3DES、MD5、NULL（暗号化しない）、EXPORT（輸出用の短い鍵）、aNULL（認証しない）** です。

### つないで確かめる

```console
# curl https://127.0.0.1/
curl: (60) SSL certificate problem: self-signed certificate
# curl -k https://127.0.0.1/
main
# openssl s_client -connect 127.0.0.1:443 -servername www.example.com
…
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
Verify return code: 18 (self-signed certificate)
# openssl s_client -connect 127.0.0.1:443 -tls1_1
…error:0A0000BF:SSL routines:tls_setup_handshake:no protocols available…
```

自己署名証明書なので、curl は検証に失敗します（終了コード 60）。`-k` は検証を省きます。`openssl s_client` は、決まったプロトコルと暗号、証明書の検証の結果を見せます。`-tls1_1` で古い版を指定すると、つながらないことを確かめられます。

証明書と秘密鍵の組が合っていないと、`httpd -t` は `Syntax OK` でも、**起動に失敗**します。エラーログには次のように出ました。

```text
[ssl:emerg] AH02565: Certificate and private key www.example.com:443:0 from /etc/pki/tls/certs/server.crt and /etc/pki/tls/private/localhost.key do not match
AH00016: Configuration Failed
```

:::note 1 つの番地で、複数の HTTPS のサイト（SNI）
名前ベースのバーチャルホストは Host ヘッダーで振り分けますが、HTTPS では、ヘッダーを読む前に証明書を選ばなければなりません。**SNI**（Server Name Indication）は、クライアントが TLS の最初の挨拶でホスト名を伝える仕組みです。これで、1 つの番地とポートで、サイトごとに別の証明書を出せます。`openssl s_client` の `-servername` が、その名前です。
:::

## nginx の設定は、入れ子のブロックでできている {#nginx-conf}

```fig tree nginx.conf の入れ子。外のブロックに書いた設定は、中のブロックに引き継がれる
{
  root: { label: 'main（一番外）', note: 'user、worker_processes、pid、error_log', kind: 'accent', children: [
    { label: 'events { }', note: 'worker_connections（1 つのワーカーが持てる接続の数）' },
    { label: 'http { }', note: 'access_log、include、ssl_protocols …', children: [
      { label: 'upstream 名前 { }', note: '中継先のサーバーの組' },
      { label: 'server { }', note: 'listen、server_name、ssl_certificate、root。バーチャルホスト 1 つ', children: [
        { label: 'location パス { }', note: 'root、proxy_pass、return。URL のパスごとの設定' },
      ] },
    ] },
  ] },
}
```

**nginx**（エンジンエックス）は、少ないプロセスで多くの接続をさばく Web サーバーです。**リバースプロキシ**（後ろのサーバーへの中継役）としてよく使われます。設定は **`/etc/nginx/`** にあります。

| 場所 | 中身 |
| --- | --- |
| **`/etc/nginx/nginx.conf`** | 主設定ファイル（Red Hat 系も Debian 系も同じ） |
| `/etc/nginx/conf.d/*.conf` | 追加の設定。`http { }` の中から `include` で読まれる |
| `/etc/nginx/sites-available/`、`sites-enabled/` | Debian 系だけ。`sites-enabled/` にシンボリックリンクを作って有効にする |
| `/etc/nginx/mime.types` | 拡張子と文書の種類の対応 |
| `/var/log/nginx/access.log`、`error.log` | ログ |

nginx.conf は、**ディレクティブ**と、`{ }` で囲んだ**ブロック**（コンテキスト）でできています。ディレクティブは**セミコロン `;` で終わります**（引用符で囲む必要はありません）。rockylinux:9 の nginx.conf の骨組みです。

```conf
user nginx;
worker_processes auto;
error_log /var/log/nginx/error.log;
pid /run/nginx.pid;

events {
    worker_connections 1024;
}

http {
    access_log  /var/log/nginx/access.log  main;
    include /etc/nginx/conf.d/*.conf;

    server {
        listen       80;
        server_name  www.example.com;
        root         /usr/share/nginx/html;

        location /images/ {
            root /data;
        }
    }
}
```

| ディレクティブ | 書く場所 | 意味 |
| --- | --- | --- |
| `user` | main | ワーカープロセスの利用者（Red Hat 系 `nginx`、Debian 系 `www-data`） |
| `worker_processes` | main | ワーカープロセスの数。`auto` は CPU の数 |
| `worker_connections` | events | 1 つのワーカーが同時に持てる接続の数 |
| `include` | どこでも | ほかのファイルを読み込む |
| `listen` | server | 待ち受けるポートと番地（`listen 80;`、`listen 443 ssl;`） |
| `server_name` | server | このサーバーの名前（Host ヘッダーと比べる） |
| `root` | http、server、location | 公開するファイルの一番上のディレクトリ |
| `index` | http、server、location | ディレクトリが指定されたときに返すファイル |
| `location` | server | URL のパスごとの設定 |

nginx のプロセスは 2 種類です。**マスタープロセス**（root）が設定を読み、ポートを開き、ワーカーを管理します。**ワーカープロセス**（`user` で指定した利用者）が、実際にリクエストを処理します。

`server { }` は Apache の `<VirtualHost>` にあたります。同じポートの `server` が複数あるとき、Host ヘッダーが `server_name` に合うものが選ばれます。**どれにも合わなければ、`listen` に `default_server` を付けたもの、それがなければ最初に書いた `server`** が受けます。

`location` の書き方には、次の種類があります。

| 書き方 | 合い方 |
| --- | --- |
| `location /app/ { }` | パスが `/app/` で始まる（前方一致） |
| `location = /ping { }` | パスが `/ping` に**完全に一致** |
| `location ~ \.php$ { }` | 正規表現（大文字と小文字を区別する） |
| `location ~* \.png$ { }` | 正規表現（大文字と小文字を区別しない） |

### nginx コマンド

```console
# nginx -t
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
# nginx -s reload
```

| オプション | すること |
| --- | --- |
| **`-t`** | 設定ファイルを検査する |
| `-T` | 検査したうえで、読み込んだ設定を**すべて表示**する |
| **`-s シグナル`** | 動いているマスタープロセスに合図を送る。`reload`（設定を読み込み直す）、`stop`（すぐ止める）、`quit`（処理中のリクエストを待って止める）、`reopen`（ログファイルを開き直す） |
| `-c ファイル` | 別の設定ファイルを使う（既定は `/etc/nginx/nginx.conf`） |
| `-v` / `-V` | バージョン / バージョンとコンパイル時のオプションを表示する |

オプションなしで `nginx` を実行すると、起動します。systemd のもとでは `systemctl start nginx`、`systemctl reload nginx` を使います。

設定のまちがいは `nginx -t` が場所を教えてくれます。セミコロンを忘れたときと、書けない場所にディレクティブを書いたときの出力です。

```console
# nginx -t          （server { listen 80; server_name x } と書いた）
nginx: [emerg] unexpected "}" in /etc/nginx/conf.d/bad.conf:1
nginx: configuration file /etc/nginx/nginx.conf test failed
# nginx -t          （server の直下に proxy_pass を書いた）
nginx: [emerg] "proxy_pass" directive is not allowed here in /etc/nginx/conf.d/bad.conf:1
```

### HTTPS とリダイレクト

HTTPS は、`listen` に **`ssl`** を付け、証明書と鍵を指定します。

```conf
server {
    listen 80;
    server_name www.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name www.example.com;

    ssl_certificate     /etc/pki/tls/certs/server.crt;
    ssl_certificate_key /etc/pki/tls/private/server.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;
    ssl_prefer_server_ciphers on;

    root /usr/share/nginx/html;
}
```

| nginx のディレクティブ | 意味 | Apache で対応するもの |
| --- | --- | --- |
| `listen 443 ssl;` | このポートで TLS を使う | `SSLEngine on` |
| **`ssl_certificate`** | サーバー証明書（中間 CA の証明書は、この後ろに続けて入れる） | `SSLCertificateFile` |
| **`ssl_certificate_key`** | 秘密鍵 | `SSLCertificateKeyFile` |
| **`ssl_protocols`** | 使ってよいプロトコルを**空白で区切って並べる** | `SSLProtocol` |
| **`ssl_ciphers`** | 使ってよい暗号の組（OpenSSL の書き方） | `SSLCipherSuite` |
| `ssl_prefer_server_ciphers on;` | サーバーの順番を優先する | `SSLHonorCipherOrder on` |

Apache の `SSLProtocol` は `all` から引く書き方でしたが、nginx の `ssl_protocols` は**使うものだけを並べます**。古い書き方の `ssl on;` は非推奨で、nginx 1.20 では「the "ssl" directive is deprecated, use the "listen ... ssl" directive instead」という警告が出ます（新しい版では使えません）。

**リダイレクト**は、`return` か `rewrite` で書きます。

```conf
return 301 https://$host$request_uri;
rewrite ^/blog/(.*)$ /news/$1 permanent;
rewrite ^/tmp/(.*)$  /t/$1    redirect;
```

| 書き方 | 意味 |
| --- | --- |
| **`return 301 URL;`** | ステータスコードと行き先を返す。`301` は恒久的、`302` は一時的 |
| `rewrite 正規表現 置き換え permanent;` | 合ったら **301** で転送する |
| `rewrite 正規表現 置き換え redirect;` | 合ったら **302** で転送する |
| `rewrite 正規表現 置き換え last;` / `break;` | 転送はせず、nginx の中でパスを書き換える |

上の設定で確かめると、`http://www.example.com/a/b?x=1` は 301 で `https://www.example.com/a/b?x=1` へ、`/blog/1.html` は 301 で `/news/1.html` へ、`/tmp/1.html` は 302 で `/t/1.html` へ転送されました。

| よく使う変数 | 中身 |
| --- | --- |
| `$host` | リクエストのホスト名（Host ヘッダー。なければ server_name） |
| `$request_uri` | リクエストのパスと問い合わせ文字列（`/a/b?x=1`） |
| `$remote_addr` | クライアントの IP アドレス |
| `$scheme` | `http` か `https` |
| `$proxy_add_x_forwarded_for` | 届いた `X-Forwarded-For` の値に、`$remote_addr` を足したもの |

## nginx をリバースプロキシにする：proxy_pass {#nginx-proxy}

```fig seq リバースプロキシの中継。nginx が TLS を受け持ち、後ろのサーバーへは HTTP で送る。後ろのサーバーから見ると、相手はいつも nginx になる
{
  colw: 260,
  actors: [
    { id: 'c', label: 'クライアント 203.0.113.9' },
    { id: 'n', label: 'nginx' },
    { id: 'b', label: 'バックエンド 127.0.0.1:8081' },
  ],
  msgs: [
    { from: 'c', to: 'n', label: 'HTTPS  GET /app/x/y  Host: www.example.com', style: 'accent' },
    { note: 'location /app/ に合う', at: 'n' },
    { from: 'n', to: 'b', label: 'HTTP/1.1  GET /x/y  X-Real-IP: 203.0.113.9' },
    { from: 'b', to: 'n', label: '200 OK' },
    { from: 'n', to: 'c', label: '200 OK', style: 'accent' },
  ],
}
```

**リバースプロキシ**は、クライアントからのリクエストを受けて、後ろのサーバー（バックエンド）へ中継します。TLS の処理、複数のサーバーへの振り分け、静的なファイルの配信を nginx に任せ、アプリケーションは後ろで HTTP だけを話します。

```conf
upstream backend {
    server 127.0.0.1:8081;
    server 127.0.0.1:8082;
}

server {
    listen 443 ssl;
    server_name www.example.com;
    ssl_certificate     /etc/pki/tls/certs/server.crt;
    ssl_certificate_key /etc/pki/tls/private/server.key;

    location /app/ {
        proxy_pass http://backend/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

| ディレクティブ | 意味 | 既定 |
| --- | --- | --- |
| **`proxy_pass`** | 中継先の URL。**`location` の中に書く** | — |
| **`proxy_http_version`** | 中継先と話す HTTP の版 | **1.0**（nginx 1.29.7 以降は 1.1） |
| **`proxy_set_header`** | 中継先へ送るリクエストのヘッダーを、付けるか書き換える | `Host $proxy_host;` と `Connection close;` |
| `upstream 名前 { server …; }` | 中継先のサーバーの組。既定では順番に（ラウンドロビンで）振り分ける | — |

`proxy_pass` に書く URL には、`upstream` の名前も使えます。上の設定で 2 回リクエストすると、8081 と 8082 が 1 回ずつ答えました。

### proxy_pass の URL にパスがあるか、ないか

`proxy_pass` は、URL の後ろに**パスを書くかどうか**で、中継先に送るパスが変わります。実際に、後ろのサーバーに届いたパスを表示させて確かめました。

| 設定 | クライアントのリクエスト | 中継先に届くパス |
| --- | --- | --- |
| `location /api/ { proxy_pass http://127.0.0.1:8081; }` | `/api/x/y` | **`/api/x/y`**（そのまま） |
| `location /app/ { proxy_pass http://backend/; }` | `/app/x/y` | **`/x/y`**（`/app/` が `/` に置き換わる） |

パスを書かなければ、元のパスが**そのまま**送られます。パス（`/` だけでも）を書くと、`location` に合った部分が、そのパスに**置き換わります**。

### 後ろのサーバーに、本当の相手を伝える

後ろのサーバーから見ると、接続してくる相手はいつも nginx です。何も設定しないと、後ろのサーバーには次のように届きました。

```text
host=127.0.0.1:8081 xri= xff= proto=HTTP/1.0 conn=close
```

Host ヘッダーは `proxy_pass` に書いた中継先（`$proxy_host`）になり、クライアントの番地は伝わらず、HTTP/1.0 で、接続は毎回閉じられます。`proxy_set_header` と `proxy_http_version 1.1` を書いた `location /app/` では、こうなりました。

```text
host=127.0.0.1 xri=127.0.0.1 xff=127.0.0.1 xfp=https proto=HTTP/1.1
```

| よく書くヘッダー | 伝えるもの |
| --- | --- |
| `proxy_set_header Host $host;` | クライアントが指定した元のホスト名 |
| `proxy_set_header X-Real-IP $remote_addr;` | クライアントの IP アドレス |
| `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` | 経由してきた番地の一覧（クライアント、プロキシ …） |
| `proxy_set_header X-Forwarded-Proto $scheme;` | 元が http か https か |

`proxy_http_version 1.1;` は、中継先との接続を使い回す（Keep-Alive）ときと、WebSocket を中継するときに必要です。nginx 1.29.7 からは既定が 1.1 に変わりましたが（nginx 1.28 は HTTP/1.0、1.31 は HTTP/1.1 で届きました）、rockylinux:9（1.20）や debian:12（1.22）の版は 1.0 です。試験では「既定は 1.0、1.1 にするには明示する」と覚えます。

:::warn 試験の注意：nginx と Apache の名前の対応
nginx のディレクティブは**小文字と下線**（`ssl_certificate_key`）、Apache は**大文字で始まる単語のつなぎ**（`SSLCertificateKeyFile`）です。選択肢に `SSLCertificate` と `ssl_certificate` が混ざっていたら、どちらのサーバーの設定かを先に見ます。nginx は行の終わりに `;` が要り、Apache は要りません。
:::

:::deep 502 Bad Gateway が出たら
nginx が 502 を返すのは、中継先から正しい応答をもらえなかったときです。中継先のプロセスが止まっている、`proxy_pass` のポートがまちがっている、などです。`/var/log/nginx/error.log` に `connect() failed (111: Connection refused) while connecting to upstream` のような行が出ます。中継先が動いているかを `ss -ltn` や `curl http://127.0.0.1:8081/` で先に確かめます（[図解 LinuC 7.10](../../linuc/site/ch07.html#ss)）。
:::

**Squid** は、**プロキシサーバー**です。社内のクライアントの代わりに外の Web サーバーへ取りに行き（フォワードプロキシ）、取ってきたものを**キャッシュ**して、次の人には手元から返します。誰がどこへ行けるかも制限できます。

設定ファイルは **`/etc/squid/squid.conf`** です。主なディレクティブです。

| ディレクティブ | 意味 |
| --- | --- |
| **`http_port 3128`** | 待ち受けるポート。既定は **3128** |
| **`acl 名前 種類 値 …`** | 条件に名前を付ける |
| **`http_access allow`** / **`deny`** `名前 …` | その条件に合うリクエストを許可 / 拒否する |
| `cache_dir ufs /var/spool/squid 100 16 256` | ディスクのキャッシュの場所。大きさ（MB）、1 段目と 2 段目のディレクトリの数 |
| `cache_mem 64 MB` | メモリの上のキャッシュの大きさ |
| `access_log /var/log/squid/access.log` | アクセスログ |
| `visible_hostname` | エラーページなどで名乗るホスト名 |
| `auth_param` | ユーザー認証の方式とプログラム |

### acl と http_access

アクセス制御は 2 段階です。**`acl` で条件に名前を付け**、**`http_access` でその名前を許可か拒否に結び付けます**。

```conf
acl localnet src 192.168.1.0/24
acl SSL_ports port 443
acl Safe_ports port 80 443 1025-65535
acl CONNECT method CONNECT
acl blocked dstdomain .blocked.example
acl badurl url_regex -i ^http://.*/ads/
acl worktime time MTWHF 09:00-18:00

http_access deny !Safe_ports
http_access deny CONNECT !SSL_ports
http_access deny blocked
http_access deny badurl
http_access allow localnet
http_access deny all
```

| `acl` の種類 | 何と比べるか | 例 |
| --- | --- | --- |
| **`src`** | **クライアント**の IP アドレス | `acl localnet src 192.168.1.0/24` |
| `dst` | 行き先のサーバーの IP アドレス | `acl srv dst 203.0.113.10` |
| **`dstdomain`** | 行き先の**ドメイン名**。先頭の `.` はサブドメインも含む | `acl blocked dstdomain .blocked.example` |
| `srcdomain` | クライアントのドメイン名（逆引き） | `acl inside srcdomain .example.com` |
| **`port`** | 行き先のポート | `acl Safe_ports port 80 443` |
| `method` | HTTP のメソッド | `acl CONNECT method CONNECT` |
| `proto` | プロトコル | `acl ftp proto FTP` |
| `time` | 曜日と時刻（S M T W H F A = 日〜土） | `acl worktime time MTWHF 09:00-18:00` |
| `url_regex` | URL 全体を正規表現で（`-i` は大文字と小文字を区別しない） | `acl badurl url_regex -i ^http://.*/ads/` |
| `urlpath_regex` | URL のパスの部分を正規表現で | `acl exe urlpath_regex \.exe$` |
| **`proxy_auth`** | 認証した利用者の名前。`REQUIRED` は「認証に成功した人すべて」 | `acl authed proxy_auth REQUIRED` |

判定の決まりは 3 つです。

1. **`http_access` は上から順に調べ、最初に合った行で決まる**。それより下は見ない
2. 1 つの `http_access` の行に名前を並べると **AND**（すべてに合うとき）。`!` は否定
3. 1 つの `acl` に値を並べる（または同じ名前の `acl` を何行も書く）と **OR**（どれかに合うとき）

`http_access deny CONNECT !SSL_ports` は、「メソッドが CONNECT で、**かつ**ポートが SSL_ports でない」ものを拒否します。最後は必ず **`http_access deny all`** で閉じます。

:::warn 試験の注意：行の順番
`http_access deny all` より**下**に書いた `http_access allow …` は、決して使われません。逆に、`http_access allow localnet` を `http_access deny blocked` より上に書くと、localnet の人は blocked のサイトにも行けてしまいます。**拒否したいものを先、許可を後、最後に deny all** が基本です。
:::

### クライアントのユーザー認証

利用者に名前とパスワードを求めるには、`auth_param` で認証のプログラムを指定し、`proxy_auth` の acl を作ります。

```conf
auth_param basic program /usr/lib64/squid/basic_ncsa_auth /etc/squid/passwd
auth_param basic children 5
auth_param basic realm Squid proxy
auth_param basic credentialsttl 2 hours

acl authed proxy_auth REQUIRED
http_access allow authed
http_access deny all
```

| 行 | 意味 |
| --- | --- |
| `auth_param basic program …` | Basic 認証を受け持つ外部のプログラム（ヘルパー）と、その引数 |
| `auth_param basic children 5` | ヘルパーのプロセスの数 |
| `auth_param basic realm …` | 入力の窓に出す領域の名前 |
| `auth_param basic credentialsttl 2 hours` | 確かめた結果を覚えておく時間 |
| `acl authed proxy_auth REQUIRED` | 認証に成功した利用者すべて |

**`basic_ncsa_auth`** は、Apache の **`htpasswd` で作ったファイル**で確かめるヘルパーです（Red Hat 系は `/usr/lib64/squid/`、Debian 系は `/usr/lib/squid/`）。ほかに `basic_ldap_auth`（LDAP）、`basic_pam_auth`（PAM）などがあります。

認証が必要なのに付けていないリクエストには、Squid は **407 Proxy Authentication Required** を返します。Web サーバーの 401 とは別の番号です。

```console
# curl -s -o /dev/null -w '%{http_code}\n' -x http://127.0.0.1:3128 http://127.0.0.1:8081/a
407
# curl -s -o /dev/null -w '%{http_code}\n' -x http://127.0.0.1:3128 -U alice:secret1 http://127.0.0.1:8081/a
200
```

### squid コマンド、squidclient、ログ

| コマンド | すること |
| --- | --- |
| **`squid -k parse`** | 設定ファイルを検査する |
| `squid -k check` | Squid が動いているかを確かめる |
| **`squid -k reconfigure`** | 動いている Squid に、設定を読み込み直させる |
| `squid -k rotate` | ログファイルを切り替える |
| `squid -k shutdown` | 止める |
| `squid -z` | キャッシュのディレクトリ（`cache_dir`）を作る |
| `squid -f ファイル` | 別の設定ファイルを使う |

**`squidclient`** は、Squid に URL を 1 つ要求して、応答を表示する試験用のクライアントです（Debian 系では squidclient という別のパッケージです）。

```console
# squidclient -h 127.0.0.1 -p 3128 -u alice -w secret1 http://127.0.0.1:8081/a
HTTP/1.1 200 OK
Server: nginx/1.20.1
X-Cache: MISS from proxy.example.com
Via: 1.1 proxy.example.com (squid/5.5)
…
```

| `squidclient` のオプション | 意味 |
| --- | --- |
| `-h ホスト` | つなぐ先の Squid（既定は localhost） |
| `-p ポート` | Squid のポート（既定は 3128） |
| `-u 名前` / `-w パスワード` | プロキシの認証に使う名前とパスワード |
| `-m メソッド` | HTTP のメソッド（既定は GET） |
| `-r` | キャッシュを使わず、取り直させる |
| `mgr:info` | URL の代わりに書くと、Squid の動作の統計を表示する |

応答の `X-Cache` ヘッダーの `MISS` は「キャッシュになかったので取りに行った」、`HIT` は「キャッシュから返した」です。

ログは `/var/log/squid/` にあります。**`access.log`** がリクエストの記録、`cache.log` が Squid 自身の動作とエラーの記録です。

```text
1794864056.061      0 127.0.0.1 TCP_DENIED/403 3463 GET http://www.blocked.example/ - HIER_NONE/- text/html
1794864056.067      0 127.0.0.1 TCP_DENIED/407 3538 GET http://127.0.0.1:8081/a - HIER_NONE/- text/html
1794864056.071      1 127.0.0.1 TCP_REFRESH_MODIFIED/200 381 GET http://127.0.0.1:8081/a alice HIER_DIRECT/127.0.0.1 application/octet-stream
```

左から、時刻（1970 年からの秒数）、かかった時間（ミリ秒）、クライアントの番地、**結果/ステータスコード**、バイト数、メソッド、URL、利用者、取りに行った先、文書の種類です。`TCP_DENIED` は Squid が自分で断ったもの（取りに行っていないので `HIER_NONE`）、`TCP_MISS` はキャッシュになく取りに行ったもの、`TCP_HIT` はキャッシュから返したものです。

:::note 既定の squid.conf
配布されている squid.conf には、`acl localnet src 10.0.0.0/8` などのプライベートアドレス（[図解 LinuC 7.3](../../linuc/site/ch07.html#private)）、`acl SSL_ports port 443`、`acl Safe_ports port 80` などが初めから書いてあります。`http_access deny !Safe_ports` と `http_access deny CONNECT !SSL_ports` は、プロキシを踏み台にして変わったポートへつなぐのを防ぐ行です。消さずに、その下に自分の規則を足します。
:::

:::key まとめ
- **Apache**：Red Hat 系は `httpd` と `/etc/httpd/conf/httpd.conf`、Debian 系は `apache2` と `/etc/apache2/apache2.conf`。Debian 系は `a2ensite`、`a2enmod` で有効にする
- 検査は `apachectl configtest`（`httpd -t`）、接続を切らない読み込み直しは `apachectl graceful`。`httpd -S` はバーチャルホスト、`-M` はモジュール、`-l` は組み込みモジュール
- アクセスログの `combined` は `%h %l %u %t "%r" %>s %b` に Referer と User-Agent を足したもの
- Basic 認証は `AuthType`、`AuthName`、`AuthUserFile`、`Require`。ファイルは `htpasswd -c`（新規。2 人目からは `-c` なし）。グループは `AuthGroupFile` と `Require group`
- `.htaccess` に書けるものは `AllowOverride` で決まる。`None` なら読まれない
- 名前ベースのバーチャルホストは Host ヘッダーで選ぶ。合わなければ最初の `<VirtualHost>`。`Redirect` の既定は 302、`permanent` で 301
- `MaxRequestWorkers`（古い名前は MaxClients）は同時に処理できる数、`MaxConnectionsPerChild`（古い名前は MaxRequestsPerChild）は子プロセスを作り直すまでの接続の数。`MinSpareServers` と `MaxSpareServers` は prefork
- 証明書は「秘密鍵 → CSR（`openssl req -new`）→ CA の署名」。自己署名は `openssl req -x509`。CSR に秘密鍵は入らない
- 置き場所は Debian 系 `/etc/ssl/certs`、`/etc/ssl/private`、Red Hat 系 `/etc/pki/tls/certs`、`/etc/pki/tls/private`
- mod_ssl：`SSLEngine on`、`SSLCertificateFile`、`SSLCertificateKeyFile`、`SSLProtocol all -SSLv3 -TLSv1 -TLSv1.1`、`SSLCipherSuite HIGH:!aNULL:!MD5`。`SSLCACertificateFile`（ファイル）と `SSLCACertificatePath`（ディレクトリ）はクライアント証明書の検証用
- **nginx**：`/etc/nginx/nginx.conf`。`nginx -t` で検査、`nginx -s reload` で読み込み直し。行の終わりは `;`
- nginx の HTTPS は `listen 443 ssl;`、`ssl_certificate`、`ssl_certificate_key`、`ssl_protocols`、`ssl_ciphers`。リダイレクトは `return 301 URL;`
- リバースプロキシは `location` の中の `proxy_pass`。`proxy_http_version` の既定は 1.0、`proxy_set_header` でクライアントの情報を伝える
- **Squid**：`/etc/squid/squid.conf`、ポート 3128。`acl` で名前を付け、`http_access` は上から最初に合った行で決まる。最後は `http_access deny all`
- Squid の認証は `auth_param basic program …` と `acl 名前 proxy_auth REQUIRED`。認証がなければ 407。検査は `squid -k parse`、試すのは `squidclient`
:::

## 練習問題 {#practice}

:::q 2.09.1-01 single
Red Hat 系のディストリビューションで、Apache HTTP サーバーの主設定ファイルの既定の場所はどれか。
- [ ] `/etc/apache2/apache2.conf`
- [x] `/etc/httpd/conf/httpd.conf`
- [ ] `/etc/httpd/httpd.conf`
- [ ] `/etc/httpd/conf.d/httpd.conf`
- [ ] `/var/www/conf/httpd.conf`
:::why
Red Hat 系では、プログラムが `httpd`、主設定ファイルが `/etc/httpd/conf/httpd.conf` です（rockylinux:9 で確かめました）。`/etc/apache2/apache2.conf` は Debian 系です。`/etc/httpd/conf.d/` は追加の設定（`ssl.conf` など）を置くディレクトリで、主設定ファイルの `IncludeOptional conf.d/*.conf` から読まれます。`/var/www/` は公開するファイルの置き場です（[Apache の設定ファイル](#apache-conf)）。
:::
:::

:::q 2.09.1-02 single
Debian 系のディストリビューションで、`/etc/apache2/sites-available/shop.conf` に書いたバーチャルホストを有効にするコマンドはどれか。
- [ ] `a2enmod shop`
- [ ] `a2enconf shop`
- [x] `a2ensite shop`
- [ ] `apache2ctl enable shop`
- [ ] `a2dissite shop`
:::why
`a2ensite` は、`sites-available/` のファイルへのシンボリックリンクを `sites-enabled/` に作ります。`a2enmod` はモジュール（`mods-available/`）、`a2enconf` はそのほかの設定（`conf-available/`）を有効にするコマンドです。`a2dissite` は逆に無効にします。`apache2ctl` に `enable` というサブコマンドはありません（[Apache の設定ファイル](#apache-conf)）。
:::
:::

:::q 2.09.1-03 fill
Apache の設定ファイルを書き換えた。読み込み直す前に、構文にまちがいがないかを検査したい。空欄に入るサブコマンドを入力してください。

```text
# apachectl ____
Syntax OK
```
= configtest
= -t
:::why
`apachectl configtest` は設定ファイルの構文を検査します。`httpd -t` と同じで、rockylinux:9 の `apachectl` は `-t` も受け付けます。問題がなければ `Syntax OK` と表示します（[apachectl と httpd](#apache-conf)）。
:::
:::

:::q 2.09.1-04 single
処理中のリクエストを途中で切らずに、Apache に設定ファイルを読み込み直させるコマンドはどれか。
- [ ] `apachectl restart`
- [x] `apachectl graceful`
- [ ] `apachectl configtest`
- [ ] `apachectl graceful-stop`
- [ ] `apachectl fullstatus`
:::why
`graceful` は、処理中のリクエストが終わるのを待ってから、設定を読み込み直します。`restart` は処理中の接続を切って再起動します。`configtest` は検査するだけで、反映はしません。`graceful-stop` は処理中のリクエストを待ちますが、そのあと**停止**します。`fullstatus` は状態の表示です（[apachectl と httpd](#apache-conf)）。
:::
:::

:::q 2.09.1-05 single
Apache のアクセスログ（combined 形式）に、次の行があった。説明として正しいものはどれか。

```text
192.168.1.20 - alice [16/Nov/2026:21:19:39 +0000] "GET /ht/ HTTP/1.1" 401 381 "-" "curl/7.76.1"
```
- [ ] alice という名前のホストから、利用者 192.168.1.20 がアクセスした
- [ ] 応答には 401 バイトの本体が含まれ、処理に 381 ミリ秒かかった
- [x] 利用者名 alice を付けたリクエストに、ステータスコード 401 を返した
- [ ] リクエストは成功し、381 番のプロセスが処理した
- [ ] Referer ヘッダーの値は curl/7.76.1 だった
:::why
combined は `%h %l %u %t "%r" %>s %b "Referer" "User-Agent"` の順です。`%h`（クライアント）が 192.168.1.20、`%u`（認証の利用者名）が alice、`%>s`（ステータスコード）が 401、`%b`（応答のバイト数）が 381 です。401 は認証の失敗なので、成功ではありません。最後の `curl/7.76.1` は User-Agent で、Referer は `-`（なし）です（[アクセスログとエラーログ](#apache-conf)）。
:::
:::

:::q 2.09.1-06 multi
`htpasswd` コマンドの説明として正しいものを 2 つ選択してください。
- [x] `-c` は、パスワードファイルを新しく作る。すでにあるファイルは上書きされる
- [ ] `-b` は、パスワードを bcrypt でハッシュにする
- [x] `-D` は、指定した利用者をファイルから削除する
- [ ] `-n` は、利用者をファイルの末尾に追加する
- [ ] オプションを付けないと、パスワードは平文で保存される
:::why
`-c` は新規作成で、既存のファイルを上書きします（ほかの利用者が消えます）。`-D` は削除です。`-b` はパスワードをコマンドラインの引数で渡すオプションで、bcrypt は `-B`（大文字）です。`-n` はファイルを書き換えずに、結果を標準出力に表示します。既定は MD5（`$apr1$` で始まるハッシュ）で、平文になるのは `-p` を付けたときです（[Basic 認証を付ける](#apache-auth)）。
:::
:::

:::q 2.09.1-07 fill
Basic 認証のためのパスワードファイル `/etc/httpd/.htpasswd` はまだない。ファイルを新しく作り、利用者 alice を登録したい。空欄に入るオプションを入力してください。

```text
# htpasswd ____ /etc/httpd/.htpasswd alice
New password:
```
= -c
:::why
`-c`（create）でファイルを新しく作ります。2 人目からは `-c` を付けずに `htpasswd /etc/httpd/.htpasswd bob` とします。付けると、ファイルが作り直されて 1 人目が消えます（[Basic 認証を付ける](#apache-auth)）。
:::
:::

:::q 2.09.1-08 single
次の設定で、パスワードファイルに登録されていて認証に成功した利用者なら、誰でもアクセスできるようにしたい。空欄に入るものはどれか。

```text
<Directory "/var/www/html/secret">
    AuthType Basic
    AuthName "Members Only"
    AuthUserFile /etc/httpd/.htpasswd
```

:::q 2.09.4-10 multi
Squid の access.log に次の行があった。説明として正しいものを 2 つ選択してください。

```text
1794864056.067      0 192.168.1.50 TCP_DENIED/407 3538 GET http://www.example.com/ - HIER_NONE/- text/html
```
- [x] Squid は、このリクエストを行き先の Web サーバーへ送らずに、自分で断った
- [x] クライアントに、プロキシの認証が必要であることを示すステータスコードを返した
- [ ] 行き先の Web サーバー www.example.com が、407 を返した
- [ ] キャッシュにあった内容を、クライアントに返した
- [ ] クライアントの番地は www.example.com である
:::why
`TCP_DENIED` は Squid が自分で断ったことを表し、取りに行っていないので `HIER_NONE` です。407 は Proxy Authentication Required で、プロキシの認証が必要という意味です（Web サーバーの認証は 401）。キャッシュから返したときは `TCP_HIT` です。クライアントの番地は 3 つめの `192.168.1.50` で、URL は行き先です（[squid コマンド、squidclient、ログ](#squid)）。
:::
