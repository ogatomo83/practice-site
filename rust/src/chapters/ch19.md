## Unsafe Rust {#unsafe}

ここまでのコードはすべて、コンパイル時にメモリ安全が保証されていました。しかし Rust には、その保証を一部外す **unsafe Rust** という「第 2 の言語」が隠れています。

なぜ必要なのでしょうか。静的解析は本質的に**保守的**だからです。正しいコードでも、コンパイラが正しさを証明できなければ拒否します。また、コンピュータのハードウェア自体は安全ではないので、OS とやりとりしたり、OS そのものを書いたりするには、低レベルの操作が必要です。

### unsafe の 5 つの「超能力」

`unsafe` キーワードでブロックを始めると、その中では次の 5 つのことができるようになります。

1. **生ポインタの参照外し**
2. unsafe な関数やメソッドの呼び出し
3. 可変な静的変数へのアクセスや変更
4. unsafe なトレイトの実装
5. `union` のフィールドへのアクセス

:::key unsafe は借用チェッカーを止めない
`unsafe` は、借用チェッカーやその他の安全性の検査を無効にするわけではありません。unsafe ブロックの中で参照を使えば、それは普通どおり検査されます。`unsafe` が許すのは、上の 5 つの操作**だけ**です。

`unsafe` ブロックを書くということは、「このブロックの中のメモリ安全は、コンパイラではなく**自分が**保証する」という宣言です。メモリ関連のバグが起きたら、原因は `unsafe` ブロックの中にあるはずだ、と探す範囲を絞れます。だから unsafe ブロックは小さく保ちます。
:::

### 生ポインタを参照外しする

unsafe Rust には、参照に似た**生ポインタ（raw pointer）**という型が 2 つあります。不変の `*const T` と、可変の `*mut T` です（`*` は参照外し演算子ではなく、型名の一部です）。

| | 参照 `&T` / `&mut T` | 生ポインタ `*const T` / `*mut T` |
| --- | --- | --- |
| 借用ルール | 守られる | **無視できる**（同じ場所への可変ポインタを複数持てる） |
| 有効なメモリを指す保証 | ある | ない |
| null | ありえない | ありうる |
| 自動の片付け | ある | ない |

```rust
let mut num = 5;

let r1 = &raw const num;   // *const i32
let r2 = &raw mut num;     // *mut i32
```

生ポインタを**作る**のは safe なコードでもできます。危険なのは、生ポインタが指す先を**読み書きする**ときで、それには `unsafe` ブロックが必要です。

```rust
let mut num = 5;

let r1 = &raw const num;
let r2 = &raw mut num;

unsafe {
    println!("r1 is: {}", *r1);
    println!("r2 is: {}", *r2);
}
```

`r1` と `r2` は同じ場所を指す不変と可変のポインタです。参照ではコンパイルエラーになる組み合わせですが、生ポインタなら作れます。その代わり、データ競合を起こさないのはプログラマの責任になります。

### unsafe な関数を呼ぶ

関数そのものに `unsafe` を付けると、「この関数を呼ぶ人は、ドキュメントに書かれた条件を自分で守らなければならない」という意味になります。

```rust
unsafe fn dangerous() {}

unsafe {
    dangerous();
}
```

### unsafe なコードを安全な抽象で包む

標準ライブラリの `split_at_mut` は、1 つのスライスを、添字の位置で 2 つの可変スライスに分けます。

```rust
let mut v = vec![1, 2, 3, 4, 5, 6];

let r = &mut v[..];

let (a, b) = r.split_at_mut(3);

assert_eq!(a, &mut [1, 2, 3]);
assert_eq!(b, &mut [4, 5, 6]);
```

これを safe な Rust だけで書こうとすると、失敗します。

```rust fail
fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();

    assert!(mid <= len);

    (&mut values[..mid], &mut values[mid..])
}
```

```console

  |
1 | fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
  |                         - let's call the lifetime of this reference `'1`
...
6 |     (&mut values[..mid], &mut values[mid..])
  |     --------------------------^^^^^^--------
  |     |     |                   |
  |     |     |                   second mutable borrow occurs here
  |     |     first mutable borrow occurs here
  |     returning this value requires that `*values` is borrowed for `'1`
```

借用チェッカーには、「同じスライスの、**重ならない** 2 つの部分を借用している」ことがわかりません。スライスを 2 回可変で借用している、としか見えないのです。でも、私たちには重ならないことがわかっています。こういうときこそ unsafe の出番です。

```rust
use std::slice;

fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    let ptr = values.as_mut_ptr();

    assert!(mid <= len);

    unsafe {
        (
            slice::from_raw_parts_mut(ptr, mid),
            slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}
```

関数自体には `unsafe` が付いていません。`assert!(mid <= len)` で範囲を確かめ、unsafe な操作を正しく使っていることをプログラマが保証しているので、**安全な API として公開できる**のです。これが unsafe の正しい使い方です。

### extern で他の言語の関数を呼ぶ

他の言語で書かれた関数を呼ぶには、`extern` ブロックを使います。これを **FFI**（Foreign Function Interface）と呼びます。

```rust
unsafe extern "C" {
    fn abs(input: i32) -> i32;
}

fn main() {
    unsafe {
        println!("Absolute value of -3 according to C: {}", abs(-3));
    }
}
```

`"C"` は **ABI**（Application Binary Interface）で、関数をアセンブリのレベルでどう呼ぶかを定めた規約です。他の言語の関数は Rust の規則を守っている保証がないので、呼ぶときは `unsafe` が必要です。

逆に、他の言語から Rust の関数を呼べるようにもできます。

```rust
#[unsafe(no_mangle)]
pub extern "C" fn call_from_c() {
    println!("Just called a Rust function from C!");
}
```

`#[unsafe(no_mangle)]` は、コンパイラが関数名を変更（マングリング）しないようにする指定です。

### 可変な静的変数

Rust では**グローバル変数**を**静的変数（static）**と呼びます。

```rust
static HELLO_WORLD: &str = "Hello, world!";

fn main() {
    println!("name is: {HELLO_WORLD}");
}
```

定数（`const`）との違いは、静的変数は**メモリ上の固定のアドレス**を持つことです。定数は使われる場所ごとにデータが複製されることがあります。また、静的変数は可変にできますが、可変な静的変数へのアクセスは unsafe です。複数のスレッドから同時にアクセスすると、データ競合が起きるかもしれないからです。

```rust
static mut COUNTER: u32 = 0;

/// SAFETY: 複数のスレッドから同時に呼んではならない
unsafe fn add_to_count(inc: u32) {
    unsafe {
        COUNTER += inc;
    }
}

fn main() {
    unsafe {
        // SAFETY: main の 1 スレッドからしか呼んでいない
        add_to_count(3);
        println!("COUNTER: {}", *(&raw const COUNTER));
    }
}
```

`// SAFETY:` コメントで、なぜ安全なのかを書いておくのが慣習です。可能なら、第 16 章の並行性の道具を使い、可変な静的変数は避けましょう。

### unsafe なトレイトと union

コンパイラが検証できない不変条件を持つトレイトは、`unsafe trait` として宣言します。第 16 章の `Send` と `Sync` がその例です。

```rust
unsafe trait Foo {
    // methods go here
}

unsafe impl Foo for i32 {
    // method implementations go here
}
```

`union` は C の共用体に相当する型で、主に C のコードとのやりとりに使います。どのフィールドが今有効なのかを Rust は知らないので、フィールドの読み出しは unsafe です。

:::tip Miri で unsafe なコードを検査する
**Miri** は、未定義動作を実行時に検出する公式ツールです。`rustup +nightly component add miri` で入れ、`cargo +nightly miri run` や `cargo +nightly miri test` で実行します。unsafe なコードを書いたら、Miri で確かめる習慣をつけましょう。
:::

## 高度なトレイト {#advanced-traits}

### 関連型

**関連型（associated type）**は、トレイトの中に型のプレースホルダを置く仕組みです。代表例は `Iterator` です。

```rust
pub trait Iterator {
    type Item;

    fn next(&mut self) -> Option<Self::Item>;
}
```

ジェネリクスで書いても同じように見えますが、違いがあります。

```rust
pub trait Iterator<T> {
    fn next(&mut self) -> Option<T>;
}
```

| | ジェネリクス `Iterator<T>` | 関連型 `type Item` |
| --- | --- | --- |
| 1 つの型に実装できる回数 | 何回でも（`Iterator<String>` と `Iterator<u32>` の両方など） | **1 回だけ** |
| 呼び出し時 | 毎回どの `T` かを指定する必要がある | 型が 1 つに決まるので指定不要 |

`Counter` が数を数えるイテレータなら、要素の型は `u32` の 1 つに決まっています。関連型を使えば、`counter.next()` を呼ぶたびに型を書かずに済みます。

```rust
impl Iterator for Counter {
    type Item = u32;

    fn next(&mut self) -> Option<Self::Item> {
        // --snip--
    }
}
```

### デフォルトの型引数と演算子のオーバーロード

ジェネリックな型引数には、デフォルトの型を指定できます。この機能がよく使われるのが、**演算子のオーバーロード**です。Rust では、`std::ops` のトレイトを実装すると、対応する演算子が使えるようになります。

```rust
use std::ops::Add;

#[derive(Debug, Copy, Clone, PartialEq)]
struct Point {
    x: i32,
    y: i32,
}

impl Add for Point {
    type Output = Point;

    fn add(self, other: Point) -> Point {
        Point {
            x: self.x + other.x,
            y: self.y + other.y,
        }
    }
}

fn main() {
    assert_eq!(
        Point { x: 1, y: 0 } + Point { x: 2, y: 3 },
        Point { x: 3, y: 3 }
    );
}
```

`Add` トレイトの定義はこうなっています。

```rust
trait Add<Rhs = Self> {
    type Output;

    fn add(self, rhs: Rhs) -> Self::Output;
}
```

`Rhs = Self` がデフォルトの型引数です。`impl Add for Point` のように何も指定しなければ、右辺の型は自分と同じ型になります。違う型を足したいときは、明示的に指定します。

```rust
use std::ops::Add;

struct Millimeters(u32);
struct Meters(u32);

impl Add<Meters> for Millimeters {   // Millimeters + Meters
    type Output = Millimeters;

    fn add(self, other: Meters) -> Millimeters {
        Millimeters(self.0 + (other.0 * 1000))
    }
}
```

### 同じ名前のメソッドを呼び分ける

2 つのトレイトに同じ名前のメソッドがあって、1 つの型が両方を実装していることがあります。

```rust
trait Pilot {
    fn fly(&self);
}

trait Wizard {
    fn fly(&self);
}

struct Human;

impl Pilot for Human {
    fn fly(&self) {
        println!("This is your captain speaking.");
    }
}

impl Wizard for Human {
    fn fly(&self) {
        println!("Up!");
    }
}

impl Human {
    fn fly(&self) {
        println!("*waving arms furiously*");
    }
}
```

```rust
fn main() {
    let person = Human;
    person.fly();          // *waving arms furiously*（型自身のメソッドが優先）
    Pilot::fly(&person);   // This is your captain speaking.
    Wizard::fly(&person);  // Up!
}
```

`self` を取らない関連関数の場合は、どの型の実装かを判断できないので、**完全修飾構文**を使います。

```rust
trait Animal {
    fn baby_name() -> String;
}

struct Dog;

impl Dog {
    fn baby_name() -> String {
        String::from("Spot")
    }
}

impl Animal for Dog {
    fn baby_name() -> String {
        String::from("puppy")
    }
}

fn main() {
    println!("A baby dog is called a {}", Dog::baby_name());               // Spot
    println!("A baby dog is called a {}", <Dog as Animal>::baby_name());   // puppy
}
```

`<Type as Trait>::function(...)` が完全修飾構文です。「`Dog` を `Animal` として扱って、その `baby_name` を呼ぶ」という意味です。

### スーパートレイト

あるトレイトが、別のトレイトの機能を前提にしていることがあります。そのとき、前提にするトレイトを**スーパートレイト**と呼びます。

```rust
use std::fmt;

trait OutlinePrint: fmt::Display {   // Display を実装している型にしか実装できない
    fn outline_print(&self) {
        let output = self.to_string();   // Display があるので to_string が使える
        let len = output.len();
        println!("{}", "*".repeat(len + 4));
        println!("*{}*", " ".repeat(len + 2));
        println!("* {output} *");
        println!("*{}*", " ".repeat(len + 2));
        println!("{}", "*".repeat(len + 4));
    }
}
```

```console
**********
*        *
* (1, 3) *
*        *
**********
```

### ニュータイプパターンで孤児ルールを回避する

第 10 章の孤児ルールでは、外部のトレイトを外部の型に実装することはできませんでした。たとえば `Vec<T>` に `Display` を実装することはできません。

**ニュータイプパターン**では、外部の型を、フィールド 1 つのタプル構造体で包んで**自分の型**にします。

```rust
use std::fmt;

struct Wrapper(Vec<String>);

impl fmt::Display for Wrapper {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "[{}]", self.0.join(", "))
    }
}

fn main() {
    let w = Wrapper(vec![String::from("hello"), String::from("world")]);
    println!("w = {w}");   // w = [hello, world]
}
```

`Wrapper` は新しい型なので、`Vec` のメソッドはそのままでは使えません。すべて使いたいなら、`Deref` を実装して中身を返す方法があります。

## 高度な型 {#advanced-types}

### ニュータイプで型安全と抽象化を得る

ニュータイプは、孤児ルールの回避以外にも役立ちます。

- **単位の取り違えを防ぐ**：`Millimeters` と `Meters` を別の型にすれば、うっかり混ぜることはない
- **内部の実装を隠す**：`People` 型が内部で `HashMap<i32, String>` を使っていても、公開 API には現れない

### 型エイリアス

`type` で、既存の型に別名を付けられます。

```rust
type Kilometers = i32;

let x: i32 = 5;
let y: Kilometers = 5;

println!("x + y = {}", x + y);   // Kilometers は i32 そのものなので足せる
```

ニュータイプと違い、`Kilometers` は**新しい型ではなく、`i32` の別名**です。型チェックの恩恵はありません。主な用途は、**長い型を短くする**ことです。

```rust
type Thunk = Box<dyn Fn() + Send + 'static>;

let f: Thunk = Box::new(|| println!("hi"));

fn takes_long_type(f: Thunk) { /* --snip-- */ }
fn returns_long_type() -> Thunk { /* --snip-- */ }
```

標準ライブラリの `std::io` は、`Result<T, std::io::Error>` を何度も書かずに済むように、こんな別名を定義しています。

```rust
type Result<T> = std::result::Result<T, std::io::Error>;
```

### never 型 `!`：決して戻らない

Rust には、`!` という特殊な型があります。**値を持たない空の型**で、「この関数は決して戻らない」ことを表します。

```rust
fn bar() -> ! {
    panic!("This call never returns.");
}
```

第 2 章の数当てゲームで、こんなコードがありました。

```rust
let guess: u32 = match guess.trim().parse() {
    Ok(num) => num,
    Err(_) => continue,
};
```

`match` のアームはすべて同じ型でなければならないはずです。`Ok` のアームは `u32` を返しますが、`continue` は何を返すのでしょうか。答えは `!` です。`continue` は値を返さず、ループの先頭に制御を移します。**`!` 型の式は、どんな型にも強制変換できる**ので、`match` 全体の型は `u32` になります。

`panic!`、`loop`（`break` しない限り）、`std::process::exit` も `!` 型です。

### 動的サイズ型と Sized

Rust は、すべての型の大きさをコンパイル時に知る必要があります。しかし、**動的サイズ型（DST）**と呼ばれる、大きさが実行時までわからない型もあります。代表例が `str` です（`&str` ではありません）。

```rust fail
let s1: str = "Hello there!";   // str の大きさは文字列によって違うので、変数にできない
let s2: str = "How's it going?";
```

だから、`str` は常にポインタの後ろに置いて、`&str` や `Box<str>` として使います。`&str` は**アドレスと長さの 2 つの値**を持つので、大きさが決まります。

```fig layout 動的サイズ型はポインタの後ろに置く。ポインタは「アドレス + 追加情報」のファットポインタになり、大きさが固定される
{
  unit: 22,
  rows: [
    { label: '&i32', cells: [{ w: 4, kind: 'stack', t: 'ptr' }], note: '8 バイト（ふつうのポインタ）' },
    { label: '&str', cells: [{ w: 4, kind: 'stack', t: 'ptr' }, { w: 4, kind: 'accent', t: 'len' }], note: '16 バイト（長さを持つ）' },
    { label: '&[T]', cells: [{ w: 4, kind: 'stack', t: 'ptr' }, { w: 4, kind: 'accent', t: 'len' }], note: '16 バイト（要素数を持つ）' },

```

トレイトも動的サイズ型です。だからトレイトオブジェクトは、`&dyn Trait` や `Box<dyn Trait>` のようにポインタの後ろに置くのでした。

大きさがコンパイル時にわかる型は、`Sized` トレイトを自動で実装します。そして、ジェネリックな関数の型パラメータには、**暗黙に `Sized` の境界が付いています**。

```rust
fn generic<T>(t: T) {}
// 実際にはこう扱われる
fn generic<T: Sized>(t: T) {}
```

動的サイズ型も受け付けたいときは、`?Sized` と書いてこの制約を外します。

```rust
fn generic<T: ?Sized>(t: &T) {}   // T は Sized でなくてもよい。だから &T で受ける
```

`?Trait` という書き方は、`Sized` にだけ使える特別な構文です。

## 高度な関数とクロージャ {#advanced-functions}

### 関数ポインタ

関数にクロージャを渡せることは第 13 章で学びました。普通の関数を渡すこともできます。関数の型は `fn`（小文字）で、**関数ポインタ**と呼びます。

```rust
fn add_one(x: i32) -> i32 {
    x + 1
}

fn do_twice(f: fn(i32) -> i32, arg: i32) -> i32 {
    f(arg) + f(arg)
}

fn main() {
    let answer = do_twice(add_one, 5);
    println!("The answer is: {answer}");   // 12
}
```

`fn` は**型**で、`Fn` は**トレイト**です。関数ポインタは 3 つのクロージャトレイト（`Fn`、`FnMut`、`FnOnce`）をすべて実装しているので、クロージャを受け取る関数には関数ポインタも渡せます。逆に、`fn` 型を要求する関数にはクロージャは渡せません（環境をキャプチャしないクロージャを除く）。C の関数とやりとりするときなどは、`fn` が必要です。

クロージャと関数ポインタは、多くの場面で置き換えられます。

```rust
let list_of_numbers = vec![1, 2, 3];
let list_of_strings: Vec<String> =
    list_of_numbers.iter().map(|i| i.to_string()).collect();   // クロージャ

let list_of_strings: Vec<String> =
    list_of_numbers.iter().map(ToString::to_string).collect(); // 関数ポインタ
```

enum の列挙子の名前も、引数を受け取って値を返す**初期化関数**なので、関数ポインタとして渡せます。

```rust
enum Status {
    Value(u32),
    Stop,
}

let list_of_statuses: Vec<Status> = (0u32..20).map(Status::Value).collect();
```

### クロージャを返す

クロージャは、それぞれが**固有の型**を持ちます（その型には名前が付けられません）。そのため、戻り値の型を直接書くことはできません。1 種類のクロージャを返すなら、`impl Trait` を使います。

```rust
fn returns_closure() -> impl Fn(i32) -> i32 {
    |x| x + 1
}
```

しかし、異なるクロージャを返す可能性があるなら、`impl Trait` は使えません。`impl Trait` は 1 つの具体的な型を表すからです。そのときは、トレイトオブジェクトを使います。

```rust
fn returns_closure() -> Box<dyn Fn(i32) -> i32> {
    Box::new(|x| x + 1)
}

fn returns_initialized_closure(init: i32) -> Box<dyn Fn(i32) -> i32> {
    Box::new(move |x| x + init)
}

fn main() {
    let handlers = vec![returns_closure(), returns_initialized_closure(123)];
    for handler in handlers {
        let output = handler(5);
        println!("{output}");
    }
}
```

## マクロ {#macros}

この本では `println!` などのマクロを使ってきましたが、マクロが何なのかはきちんと説明していませんでした。**マクロ**は、Rust のいくつかの機能をまとめて指す言葉です。

```fig tree Rust のマクロの種類

```

### マクロと関数の違い

マクロは、**コードを書くコード**です。これを**メタプログラミング**と呼びます。

| | 関数 | マクロ |
| --- | --- | --- |
| 引数の数 | シグネチャで固定 | **可変**（`println!("a")`, `println!("a {}", b)`） |
| 展開されるタイミング | 実行時に呼ばれる | **コンパイル時**に、コードに展開される |
| できること | 値を処理する | トレイトの実装を生成する、など |
| 定義の難しさ | 普通 | Rust のコードを書くコードなので、読み書きが難しい |
| 使う前の定義 | 不要（どこで定義してもよい） | 使う前に定義するか、スコープに持ち込む必要がある |

### macro_rules! で宣言的マクロを作る

最もよく使われるのは**宣言的マクロ**です。`match` 式に似ていて、**渡されたソースコードの構造**をパターンと照らし合わせ、合ったアームのコードに置き換えます。

`vec!` マクロの簡略版の定義を見てみましょう。

```rust
#[macro_export]
macro_rules! vec {
    ( $( $x:expr ),* ) => {
        {
            let mut temp_vec = Vec::new();
            $(
                temp_vec.push($x);
            )*
            temp_vec
        }
    };
}
```

- `#[macro_export]`：このクレートを持ち込んだ人が、マクロを使えるようにする
- `( $( $x:expr ),* )`：パターン。`$x:expr` は「任意の Rust の式に合い、それを `$x` と呼ぶ」。`$( ... ),*` は「カンマ区切りで 0 回以上繰り返す」
- `=>` の右側：展開後のコード。`$( temp_vec.push($x); )*` は、パターンで合った `$x` の数だけ繰り返される

```fig graph `vec![1, 2, 3]` の展開。パターンが 3 つの式に合い、push が 3 回生成される。コンパイラが見るのは右側のコード

### 手続き的マクロ

**手続き的マクロ**は、より関数に近い形のマクロです。Rust のコードをトークンの並び（`TokenStream`）として受け取り、加工して、新しいコードを出力します。

```rust
use proc_macro::TokenStream;

#[some_attribute]
pub fn some_name(input: TokenStream) -> TokenStream {
}
```

手続き的マクロは、`proc-macro` という特別な種類のクレートに置く必要があります。

### derive マクロを作る

`hello_macro` というクレートで、`HelloMacro` トレイトとその derive マクロを作ってみましょう。使う側は、`#[derive(HelloMacro)]` と書くだけで、`hello_macro` 関数の実装が手に入るようにします。

```rust file="src/main.rs"
use hello_macro::HelloMacro;
use hello_macro_derive::HelloMacro;

#[derive(HelloMacro)]
struct Pancakes;

fn main() {
    Pancakes::hello_macro();   // Hello, Macro! My name is Pancakes!
}
```

```fig graph derive マクロの仕組み。コンパイラが構造体のコードをマクロに渡し、マクロが impl ブロックのコードを生成して返す

トレイトは普通のライブラリクレートに定義します。

```rust file="hello_macro/src/lib.rs"
pub trait HelloMacro {
    fn hello_macro();
}
```

マクロ本体は、別の `hello_macro_derive` クレートに置きます。

```toml file="hello_macro_derive/Cargo.toml"
[lib]
proc-macro = true

[dependencies]
syn = "2.0"
quote = "1.0"
```

```rust file="hello_macro_derive/src/lib.rs"
use proc_macro::TokenStream;
use quote::quote;

#[proc_macro_derive(HelloMacro)]
pub fn hello_macro_derive(input: TokenStream) -> TokenStream {
    // Rust のコードを、操作しやすい構文木に変換する
    let ast = syn::parse(input).unwrap();

    // トレイトの実装を組み立てる
    impl_hello_macro(&ast)
}

fn impl_hello_macro(ast: &syn::DeriveInput) -> TokenStream {
    let name = &ast.ident;   // 構造体の名前（Pancakes）
    let generated = quote! {
        impl HelloMacro for #name {
            fn hello_macro() {
                println!("Hello, Macro! My name is {}!", stringify!(#name));
            }
        }
    };
    generated.into()
}
```

- `syn` クレートは、`TokenStream` を構文木（`DeriveInput`）に変換します
- `quote!` マクロは、テンプレートから `TokenStream` を組み立てます。`#name` の部分に変数 `name` の値が埋め込まれます
- `stringify!` は、式をそのまま文字列リテラルに変換する組み込みマクロです

### 属性風マクロと関数風マクロ

**属性風マクロ**は、`derive` のように新しい属性を作りますが、構造体や enum だけでなく、関数など任意の要素に付けられます。Web フレームワークでよく見かけます。

```rust
#[route(GET, "/")]
fn index() {
```

```rust
#[proc_macro_attribute]
pub fn route(attr: TokenStream, item: TokenStream) -> TokenStream {
```

`attr` には属性の中身（`GET, "/"`）、`item` には属性を付けた要素（`fn index() {}`）が渡されます。

**関数風マクロ**は、関数呼び出しのように見えるマクロです。`macro_rules!` より複雑な処理ができます。

```rust
let sql = sql!(SELECT * FROM posts WHERE id=1);
```

```rust
#[proc_macro]
pub fn sql(input: TokenStream) -> TokenStream {
```

このマクロは、コンパイル時に SQL の文法をチェックできます。`macro_rules!` ではできない芸当です。
