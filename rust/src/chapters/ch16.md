## 並行性と所有権 {#intro}

**並行（concurrent）プログラミング**はプログラムの異なる部分が独立して実行されること、**並列（parallel）プログラミング**は異なる部分が同時に実行されることです。マルチコアの CPU が当たり前になった今、どちらもますます重要になっています。

並行プログラミングは、昔から難しく、バグを生みやすいものとされてきました。Rust の開発チームは当初、メモリ安全と並行性の問題は別々の問題だと考えていました。ところが、**所有権と型システムが、両方の問題を解決する強力な道具になる**ことがわかったのです。

多くの並行性のバグは、実行時にしか現れず、再現も難しいものです。Rust ではそれらが**コンパイルエラー**になります。バグを本番環境で追いかける代わりに、書いている最中に直せるのです。

## スレッドでコードを同時に動かす {#threads}

今の OS では、プログラムは**プロセス**の中で動き、プロセスの中では複数の**スレッド**を同時に動かせます。計算を複数のスレッドに分けると性能が上がりますが、次のような問題も生まれます。

- **競合状態（race condition）**：スレッドがデータや資源に、予測できない順番でアクセスする
- **デッドロック**：2 つのスレッドが互いを待ち合い、どちらも先に進めなくなる
- 特定の状況でしか起きず、再現も修正も難しいバグ

Rust の標準ライブラリは、OS のスレッド 1 つにつき言語のスレッド 1 つを対応させる **1:1 モデル**を使っています。

### spawn で新しいスレッドを作る

`thread::spawn` に、新しいスレッドで実行したいコードをクロージャで渡します。

```rust file="src/main.rs"
use std::thread;
use std::time::Duration;

fn main() {
    thread::spawn(|| {
        for i in 1..10 {
            println!("hi number {i} from the spawned thread!");
            thread::sleep(Duration::from_millis(1));
        }
    });

    for i in 1..5 {
        println!("hi number {i} from the main thread!");
        thread::sleep(Duration::from_millis(1));
    }
}
```

```console
hi number 1 from the main thread!
hi number 1 from the spawned thread!
hi number 2 from the main thread!
hi number 2 from the spawned thread!
hi number 3 from the main thread!
hi number 3 from the spawned thread!
hi number 4 from the main thread!
hi number 4 from the spawned thread!
hi number 5 from the spawned thread!
```

出力の順番は実行するたびに変わります。そして、生成したスレッドは 9 まで数えるはずなのに、5 で止まっています。**メインスレッドが終わると、生成したスレッドもすべて終了させられる**からです。

### join で終わるのを待つ

`thread::spawn` は `JoinHandle` を返します。その `join` メソッドを呼ぶと、そのスレッドが終わるまで**今のスレッドを待たせ（ブロックし）**ます。

```rust file="src/main.rs"
use std::thread;
use std::time::Duration;

fn main() {
@@    let handle = thread::spawn(|| {
        for i in 1..10 {
            println!("hi number {i} from the spawned thread!");
            thread::sleep(Duration::from_millis(1));
        }
    });

    for i in 1..5 {
        println!("hi number {i} from the main thread!");
        thread::sleep(Duration::from_millis(1));
    }

@@    handle.join().unwrap();
}
```

## メッセージパッシングでデータを送る {#message-passing}

安全な並行性を実現する方法として人気があるのが**メッセージパッシング**です。スレッド同士がデータを入れたメッセージを送り合って、やりとりします。Go 言語のドキュメントには、こんな標語があります。

> メモリを共有することでやりとりするのではなく、やりとりすることでメモリを共有しよう。

Rust の標準ライブラリは、メッセージパッシングのために**チャネル（channel）**を提供しています。チャネルは川のようなもので、上流でアヒルのおもちゃを流すと、下流に届きます。チャネルには**送信側（transmitter）**と**受信側（receiver）**があり、どちらかが drop されると、チャネルは**閉じられ**ます。

```rust file="src/main.rs"
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        let val = String::from("hi");
        tx.send(val).unwrap();
    });

    let received = rx.recv().unwrap();
    println!("Got: {received}");
}
```

`mpsc` は **multiple producer, single consumer**（複数の生産者、1 つの消費者）の略です。送信側は複数作れますが、受信側は 1 つだけです。`mpsc::channel()` は `(送信側, 受信側)` のタプルを返します。

| メソッド | 動作 |
| --- | --- |
| `tx.send(val)` | 値を送る。受信側がすでに drop されていたら `Err` |
| `rx.recv()` | 値が届くまで**待つ**。すべての送信側が drop されたら `Err` |
| `rx.try_recv()` | 待たずにすぐ戻る。値があれば `Ok`、なければ `Err` |

### send は所有権を移す

値を送った後で、その値を使おうとするとどうなるでしょうか。

### 複数の値を送り、受信側をイテレータとして使う

```rust file="src/main.rs"
use std::sync::mpsc;
use std::thread;
use std::time::Duration;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        let vals = vec![
            String::from("hi"),
            String::from("from"),
            String::from("the"),
            String::from("thread"),
        ];

        for val in vals {
            tx.send(val).unwrap();
            thread::sleep(Duration::from_secs(1));
        }
    });

    for received in rx {          // 受信側をイテレータとして使う
        println!("Got: {received}");
    }
}
```

`rx` を `for` ループで回すと、値が届くたびに 1 つずつ処理し、チャネルが閉じたら（送信側のスレッドが終わって `tx` が drop されたら）ループが終わります。1 秒おきに 1 行ずつ表示されるのがわかります。

## 状態共有による並行性 {#shared-state}

メッセージパッシングは 1 つの方法ですが、唯一の方法ではありません。複数のスレッドが**同じデータにアクセスする**方法もあります。

チャネルは「単一所有権」に似ています。値を送ったら、もう使えません。一方、メモリの共有は「複数所有権」に似ていて、複数のスレッドが同時に同じメモリを使えます。第 15 章で見たとおり、複数所有権は便利ですが、管理が複雑になります。ここでも Rust の型システムが助けになります。

### Mutex で一度に 1 つのスレッドだけにアクセスさせる

**ミューテックス（mutex）**は、mutual exclusion（相互排他）の略で、**一度に 1 つのスレッドだけ**がデータにアクセスできるようにする仕組みです。データにアクセスしたいスレッドは、まず**ロック（lock）**を取得する必要があります。

パネルディスカッションでマイクが 1 本しかない状況を想像してください。話したい人はマイクを要求し、話し終わったら次の人に渡します。マイクを返し忘れると、誰も話せなくなります。

ミューテックスは難しいことで有名です。理由は 2 つあります。

1. データを使う前に、ロックの取得を試みなければならない
2. 使い終わったら、ロックを解放しなければならない

Rust では、型システムと所有権のおかげで、ロックの取得と解放を**間違えようがありません**。

```rust file="src/main.rs"
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(5);

    {
        let mut num = m.lock().unwrap();
        *num = 6;
    }   // num がスコープを抜けると、ロックは自動で解放される

    println!("m = {m:?}");
}
```

- `m` の型は `Mutex<i32>` で、`i32` ではありません。だから、`lock` を呼ばずに中の値を使うことは**型の上で不可能**です。ロックのかけ忘れが起こり得ません
- `lock` は `LockResult<MutexGuard<i32>>` を返します。ロックを持っている他のスレッドがパニックしていると `Err` になります
- `MutexGuard` は第 15 章のスマートポインタです。`Deref` で中身を参照でき、`Drop` でロックを解放します。だから、ロックの解放し忘れも起こり得ません

### Arc&lt;T&gt;：原子的な参照カウント

**`Arc<T>`** は、`Rc<T>` のスレッド安全版です。`A` は **atomic**（原子的）の略で、参照カウントの増減を、他のスレッドに割り込まれない**原子的な操作**で行います。

なぜすべての型が最初から原子的ではないのでしょうか。スレッド安全性には性能のコストがかかるからです。1 つのスレッドの中だけで使うなら、`Rc` のほうが速いのです。

```rust file="src/main.rs"
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            let mut num = counter.lock().unwrap();

            *num += 1;
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Result: {}", *counter.lock().unwrap());
}
```

### RefCell/Rc と Mutex/Arc の対応

`counter` は不変なのに、`lock` で中の値の可変参照が得られました。これは `RefCell<T>` と同じ**内部可変性**です。

| シングルスレッド | マルチスレッド | 役割 |
| --- | --- | --- |
| `Rc<T>` | `Arc<T>` | 複数の所有者（参照カウント） |
| `RefCell<T>` | `Mutex<T>` | 不変参照越しに中身を変更する |
| `Rc<RefCell<T>>` | `Arc<Mutex<T>>` | 複数の所有者が変更できる値 |

`Rc<T>` に循環参照のリスクがあったように、`Mutex<T>` には**デッドロック**のリスクがあります。

## Send と Sync で拡張できる並行性 {#send-sync}

ここまで扱ってきた並行性の機能（スレッド、チャネル、`Mutex`、`Arc`）は、ほとんどが言語ではなく**標準ライブラリ**のものです。言語そのものに組み込まれている並行性の概念は、`std::marker` の 2 つのトレイト、**`Send`** と **`Sync`** だけです。

| トレイト | 意味 | 実装していない代表例 |
| --- | --- | --- |
| `Send` | その型の値の**所有権を**、別のスレッドに**移せる** | `Rc<T>`（カウントの更新が原子的でない） |
| `Sync` | その型の値を、複数のスレッドから**参照しても**安全 | `RefCell<T>`, `Cell<T>`（借用の検査が原子的でない） |

正確には、「`&T`（`T` への不変参照）が `Send` なら、`T` は `Sync`」です。参照を別のスレッドに安全に送れるなら、複数のスレッドから参照しても安全だ、ということです。

`Send` と `Sync` は**マーカートレイト**と呼ばれ、実装すべきメソッドを持ちません。構成要素がすべて `Send` な型は自動的に `Send` になり、`Sync` も同じです。`thread::spawn` は、渡すクロージャが `Send` であることをトレイト境界で要求しています。だから `Rc` を送ろうとするとコンパイルエラーになったのです。

これらを手で実装するには `unsafe` なコード（第 19 章）が必要です。新しい並行性の型を自分で作らない限り、手で実装することはまずありません。そして逆に言えば、crates.io にある並行性のライブラリも、すべてこの 2 つのトレイトの上に作られていて、標準ライブラリと同じ安全性の保証を受けられます。

## この章のまとめ {#summary}

| 道具 | 用途 | 所有権との関係 |
| --- | --- | --- |
| `thread::spawn` + `move` | スレッドを作る | データの所有権をスレッドに移す |
| `JoinHandle::join` | スレッドの終了を待つ | |
| `mpsc::channel` | メッセージパッシング | `send` で所有権が受信側に移る |
| `Mutex<T>` | 状態の共有（相互排他） | ロックしないと中身に触れない |
| `Arc<T>` | スレッド間の複数所有権 | `Rc<T>` の原子的版 |
| `Send` / `Sync` | スレッド間で送れるか・共有できるか | コンパイラが自動で判定 |

Rust では、並行性の問題の多くが**コンパイル時**に見つかります。コードがコンパイルできれば、データ競合や、解放したメモリへのアクセスのような、追跡しにくい種類のバグはないと考えてよいのです。これが「恐れることのない並行性」です。
