## オブジェクト指向言語の特徴 {#characteristics}

オブジェクト指向プログラミング（OOP）が何であるかについて、プログラミングのコミュニティで合意された定義はありません。よく挙げられる特徴は、**オブジェクト**、**カプセル化**、**継承**の 3 つです。Rust がそれぞれをどう扱うかを見ていきます。

### オブジェクトはデータと振る舞いを持つ

「デザインパターン」（通称 GoF 本）は、オブジェクト指向をこう定義しています。

> オブジェクト指向プログラムは、オブジェクトで構成される。オブジェクトは、データと、そのデータを操作する手続きの両方をまとめたものである。

この定義なら、Rust はオブジェクト指向です。構造体と enum はデータを持ち、`impl` ブロックはメソッドを提供します。他の言語のように「オブジェクト」とは呼びませんが、同じ機能を持っています。

### カプセル化で実装を隠す

**カプセル化**とは、オブジェクトを使うコードから、そのオブジェクトの実装の詳細を隠すことです。公開 API を通してしかやりとりできないので、内部の実装を変えても、使う側のコードを変えずに済みます。

Rust では、`pub` で何を公開するかを決めます。数値のリストと、その平均値を保持する構造体を考えます。

```rust file="src/lib.rs"
pub struct AveragedCollection {
    list: Vec<i32>,     // 非公開
    average: f64,       // 非公開
}

impl AveragedCollection {
    pub fn add(&mut self, value: i32) {
        self.list.push(value);
        self.update_average();
    }

    pub fn remove(&mut self) -> Option<i32> {
        let result = self.list.pop();
        match result {
            Some(value) => {
                self.update_average();
                Some(value)
            }
            None => None,
        }
    }

    pub fn average(&self) -> f64 {
        self.average
    }

    fn update_average(&mut self) {
        let total: i32 = self.list.iter().sum();
        self.average = total as f64 / self.list.len() as f64;
    }
}
```

### 継承は、型システムとしても、コード共有としても使わない

**継承**とは、あるオブジェクトが、別のオブジェクトの定義から要素を引き継ぐ仕組みです。Rust には、構造体が親の構造体のフィールドやメソッドを引き継ぐ仕組みは**ありません**。

継承が使われる理由は、主に 2 つあります。

| 継承を使う理由 | Rust での代わり |
| --- | --- |
| **コードの再利用**：親の実装を子でも使いたい | トレイトの**デフォルト実装**。必要なら各型で上書き（オーバーライド）できる |
| **ポリモーフィズム**：親の型が求められる場所で子の型を使いたい | **ジェネリクスとトレイト境界**（コンパイル時）、**トレイトオブジェクト**（実行時） |

継承は、最近のプログラミング言語の設計では人気が下がっています。必要以上のコードを共有しがちで、子が親のすべての特性を受け継ぐことが、必ずしも適切ではないからです。親のメソッドの一部が子にはそぐわないこともありますし、単一継承しか許さない言語では、設計の柔軟さも制限されます。Rust は、トレイトを使う別の道を選びました。

## トレイトオブジェクトで異なる型の値を扱う {#trait-objects}

第 8 章では、ベクタに異なる型の値を入れるために enum を使いました。ただしこの方法は、**入れる型の種類が、コードを書く時点で決まっている**ときにしか使えません。

GUI ライブラリ `gui` を作る場面を考えます。ライブラリは `Button` や `TextField` を提供しますが、利用者は `Image` や `SelectBox` のような**独自の部品**を追加したくなるはずです。ライブラリを書く時点では、利用者がどんな型を作るかわかりません。わかっているのは、「どの部品も画面に描画できる（`draw` メソッドを持つ）」ことだけです。

### 共通の振る舞いをトレイトにする

```rust file="src/lib.rs"
pub trait Draw {
    fn draw(&self);
}

pub struct Screen {
    pub components: Vec<Box<dyn Draw>>,
}

impl Screen {
    pub fn run(&self) {
        for component in self.components.iter() {
            component.draw();
        }
    }
}
```

`Box<dyn Draw>` が**トレイトオブジェクト**です。「`Draw` トレイトを実装している、何らかの型の値」を指します。トレイトオブジェクトは、`&` 参照や `Box<T>` などのポインタの後ろに、`dyn` キーワードとトレイト名を書いて作ります。

### ジェネリクスとの違い

同じことをジェネリクスとトレイト境界で書くこともできます。

```rust
pub struct Screen<T: Draw> {
    pub components: Vec<T>,
}

impl<T> Screen<T>
where
    T: Draw,
{
    pub fn run(&self) {
        for component in self.components.iter() {
            component.draw();
        }
    }
}
```

しかしこれだと、`Screen` の `components` に入れられるのは**1 種類の型だけ**です。`Vec<Button>` か `Vec<TextField>` のどちらかで、混ぜることはできません。

### トレイトを実装する

ライブラリ側で `Button` を用意します。

```rust file="src/lib.rs"
pub struct Button {
    pub width: u32,
    pub height: u32,
    pub label: String,
}

impl Draw for Button {
    fn draw(&self) {
        // 実際にボタンを描画するコード
    }
}
```

利用者は、自分の型 `SelectBox` を作り、`Draw` を実装します。

```rust file="src/main.rs"
use gui::Draw;

struct SelectBox {
    width: u32,
    height: u32,
    options: Vec<String>,
}

impl Draw for SelectBox {
    fn draw(&self) {
        // 実際にセレクトボックスを描画するコード
    }
}
```

そして、異なる型を 1 つのベクタに入れて、`run` を呼びます。

```rust file="src/main.rs"
use gui::{Button, Screen};

fn main() {
    let screen = Screen {
        components: vec![
            Box::new(SelectBox {
                width: 75,
                height: 10,
                options: vec![
                    String::from("Yes"),
                    String::from("Maybe"),
                    String::from("No"),
                ],
            }),
            Box::new(Button {
                width: 50,
                height: 10,
                label: String::from("OK"),
            }),
        ],
    };

    screen.run();
}
```

`run` は、各部品の具体的な型を知りません。`Draw` を実装していることだけを知っていて、`draw` を呼びます。値の具体的な型ではなく、値が応答するメッセージだけに注目する、この考え方は動的型付け言語の**ダックタイピング**に似ています（アヒルのように歩き、アヒルのように鳴くなら、それはアヒルだ）。

違うのは、**`Draw` を実装していない型を入れようとすると、コンパイルエラーになる**ことです。

```rust fail
fn main() {
    let screen = Screen {
        components: vec![Box::new(String::from("Hi"))],
    };
    screen.run();
}
```

### 動的ディスパッチの仕組み

第 10 章で、ジェネリクスはコンパイル時に**単相化**され、具体的な型ごとのコードが生成されることを学びました。どのメソッドを呼ぶかがコンパイル時に決まるので、これを**静的ディスパッチ**と呼びます。

トレイトオブジェクトでは、コンパイラはどの型が使われるのか知りません。そのため、**実行時に**、どのメソッドを呼ぶかを決めます。これを**動的ディスパッチ**と呼びます。

その仕組みが、トレイトオブジェクトの**ファットポインタ**です。`Box<dyn Draw>` は、ポインタを 2 つ持っています。

| | 静的ディスパッチ（ジェネリクス） | 動的ディスパッチ（`dyn Trait`） |
| --- | --- | --- |
| 呼ぶメソッドが決まる時点 | コンパイル時 | 実行時（vtable を引く） |
| 異なる型を 1 つのコレクションに | できない | できる |
| 実行時のコスト | なし | vtable を引くわずかなコスト |
| インライン化などの最適化 | できる | できない |
| 生成されるコード量 | 型ごとに増える | 1 つで済む |

柔軟さと引き換えに、わずかな実行時コストを払う。どちらを選ぶかは場面次第です。

:::deep dyn にできるトレイトの条件
すべてのトレイトをトレイトオブジェクトにできるわけではありません。トレイトオブジェクトにできる（**dyn 互換**である）には、すべてのメソッドが次の条件を満たす必要があります。

- 戻り値の型が `Self` ではない
- ジェネリックな型パラメータを持たない

トレイトオブジェクトを使うと、具体的な型の情報は失われます。`Self` を返すメソッドがあっても、その `Self` が何の型なのか、もうわかりません。ジェネリックなメソッドも、型パラメータを埋める具体的な型がわからないので、単相化できません。例えば `Clone` トレイトは `fn clone(&self) -> Self` を持つので、`dyn Clone` は作れません。
:::

## オブジェクト指向のデザインパターンを実装する {#state-pattern}

**ステートパターン**は、オブジェクト指向のデザインパターンの 1 つです。値の内部状態を**状態オブジェクト**の集まりで表し、値の振る舞いを状態に応じて変えます。

ブログの投稿のワークフローを、ステートパターンで実装してみましょう。

1. 投稿は空の**下書き（Draft）**から始まる
2. 下書きが終わったら、**査読（PendingReview）**を依頼する
3. 承認されると、**公開（Published）**される
4. 公開された投稿だけが本文を返す。下書きや査読中の本文は空文字列

使う側のコードは、こうなる予定です。

```rust file="src/main.rs"
use blog::Post;

fn main() {
    let mut post = Post::new();

    post.add_text("I ate a salad for lunch today");
    assert_eq!("", post.content());

    post.request_review();
    assert_eq!("", post.content());

    post.approve();
    assert_eq!("I ate a salad for lunch today", post.content());
}
```

### 実装：状態をトレイトオブジェクトで持つ

```rust file="src/lib.rs"
pub struct Post {
    state: Option<Box<dyn State>>,
    content: String,
}

impl Post {
    pub fn new() -> Post {
        Post {
            state: Some(Box::new(Draft {})),
            content: String::new(),
        }
    }

    pub fn add_text(&mut self, text: &str) {
        self.content.push_str(text);
    }

    pub fn content(&self) -> &str {
        self.state.as_ref().unwrap().content(self)
    }

    pub fn request_review(&mut self) {
        if let Some(s) = self.state.take() {
            self.state = Some(s.request_review())
        }
    }

    pub fn approve(&mut self) {
        if let Some(s) = self.state.take() {
            self.state = Some(s.approve())
        }
    }
}

trait State {
    fn request_review(self: Box<Self>) -> Box<dyn State>;
    fn approve(self: Box<Self>) -> Box<dyn State>;
    fn content<'a>(&self, post: &'a Post) -> &'a str {
        ""   // デフォルトは空文字列
    }
}

struct Draft {}

impl State for Draft {
    fn request_review(self: Box<Self>) -> Box<dyn State> {
        Box::new(PendingReview {})
    }

    fn approve(self: Box<Self>) -> Box<dyn State> {
        self      // 下書きを承認しても何も起きない
    }
}

struct PendingReview {}

impl State for PendingReview {
    fn request_review(self: Box<Self>) -> Box<dyn State> {
        self
    }

    fn approve(self: Box<Self>) -> Box<dyn State> {
        Box::new(Published {})
    }
}

struct Published {}

impl State for Published {
    fn request_review(self: Box<Self>) -> Box<dyn State> {
        self
    }

    fn approve(self: Box<Self>) -> Box<dyn State> {
        self
    }

    fn content<'a>(&self, post: &'a Post) -> &'a str {
        &post.content     // 公開済みのときだけ本文を返す
    }
}
```

いくつかのポイントがあります。

- **`self: Box<Self>`**：このメソッドは、`Box` に包まれた値に対してだけ呼べ、その `Box` の所有権を取ります。古い状態を消費して、新しい状態を返すためです
- **`Option` と `take`**：`state` から一時的に値を取り出すために、`Option` に包んでいます。`take` は `Some` の値を取り出して、代わりに `None` を置きます。Rust では構造体のフィールドを空にしたままにはできないので、このテクニックで「古い状態をムーブして、新しい状態に入れ替える」を実現しています
- **`content` のデフォルト実装**：`Draft` と `PendingReview` は空文字列を返すデフォルト実装を使い、`Published` だけが上書きしています

```fig mem `request_review` で状態が入れ替わる様子。take で古い Draft を取り出して消費し、新しい PendingReview を入れる

### ステートパターンの利点と欠点

利点は、**状態ごとの振る舞いが、それぞれの状態の型に閉じている**ことです。`Post` のメソッドには `match` も `if` もありません。新しい状態を追加するときも、新しい構造体を作ってトレイトを実装するだけで済みます。

一方、欠点もあります。

- 状態が互いを知っている（`Draft` が `PendingReview` を作る）ので、状態の間に新しい状態を挟むと、複数の状態の実装を変える必要がある
- `request_review` と `approve` の実装に、ほとんど同じロジックが重複している
- **ありえない操作（下書きの本文を読む、など）が、実行時に空文字列を返すだけで、コンパイル時には見つからない**

### 状態を「型」として表す

Rust の強みを活かして、別の設計を考えてみましょう。状態ごとに**別の型**にしてしまうのです。

```rust file="src/lib.rs"
pub struct Post {
    content: String,
}

pub struct DraftPost {
    content: String,
}

impl Post {
    pub fn new() -> DraftPost {
        DraftPost {
            content: String::new(),
        }
    }

    pub fn content(&self) -> &str {
        &self.content
    }
}

impl DraftPost {
    pub fn add_text(&mut self, text: &str) {
        self.content.push_str(text);
    }

    pub fn request_review(self) -> PendingReviewPost {
        PendingReviewPost {
            content: self.content,
        }
    }
}

pub struct PendingReviewPost {
    content: String,
}

impl PendingReviewPost {
    pub fn approve(self) -> Post {
        Post {
            content: self.content,
        }
    }
}
```

`request_review` と `approve` は `self` の所有権を取るので、変換後は古い型の値は使えません。使う側のコードは、シャドーイングで新しい型の値を受け取ります。

```rust file="src/main.rs"
use blog::Post;

fn main() {
    let mut post = Post::new();

    post.add_text("I ate a salad for lunch today");

    let post = post.request_review();

    let post = post.approve();

    assert_eq!("I ate a salad for lunch today", post.content());
}
```

これはもう、厳密なオブジェクト指向のステートパターンではありません。でも、「下書きの本文を読む」「承認されていない投稿を公開する」といった無効な状態遷移は、**型システムによってコンパイル時に**防がれるようになりました。

| | ステートパターン（トレイトオブジェクト） | 状態を型で表す |
| --- | --- | --- |
| 状態の切り替え | `Post` の内部で、実行時に | 値の型そのものが変わる |
| 無効な操作 | 実行時に何もしない／空を返す | **コンパイルエラー** |
| 使う側のコード | 1 つの `post` を使い続ける | `let post = post.request_review();` と束縛し直す |
| 向いている場面 | 状態が実行時に決まる、外部に状態を隠したい | 遷移の順序をコンパイル時に保証したい |

オブジェクト指向のパターンは Rust でも使えます。でも、Rust の所有権と型システムを活かすと、別の、多くの場合より安全な設計が見つかることもあります。

## この章のまとめ {#summary}

- Rust は、オブジェクト（構造体と `impl`）とカプセル化（`pub`）を持つが、継承は持たない
- コードの共有にはトレイトのデフォルト実装、ポリモーフィズムにはジェネリクスかトレイトオブジェクトを使う
- `Box<dyn Trait>` は、データのポインタと vtable のポインタを持つファットポインタ。実行時にメソッドを決める（動的ディスパッチ）
- ステートパターンは Rust でも書けるが、状態を型で表すと、無効な遷移をコンパイル時に防げる

次の章では、これまで何度も使ってきたパターンの構文を、体系的に整理します。
