20.1作るものの全体像

最後のプロジェクトは、ブラウザに「hello」と表示する Web サーバです。ただし、ライブラリやフレームワークは使わず、標準ライブラリだけで一から作ります。

作業は 3 段階です。

完成したときの構成はこうなります。

メモ本番では使わないこと

この章で作るサーバは、学習のためのものです。本番環境で Web サーバが必要なら、crates.io にある、より完全で安全な実装（hyper、axum など）を使ってください。

20.2シングルスレッドの Web サーバ

TCP と HTTP

Web サーバで使われる主なプロトコルは 2 つです。

プロトコル層役割
TCP（Transmission Control Protocol）下位情報をあるサーバから別のサーバへ届ける方法。中身は問わない
HTTP（Hypertext Transfer Protocol）上位TCP の上で、リクエストとレスポンスの中身の形式を定める

どちらもリクエスト・レスポンス型のプロトコルです。クライアントがリクエストを送り、サーバがそれを受けてレスポンスを返します。

TCP の接続を待ち受ける

ターミナル
$ cargo new hello$ cd hello
src/main.rs
use std::net::TcpListener; fn main() {    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();     for stream in listener.incoming() {        let stream = stream.unwrap();         println!("Connection established!");    }}
  • TcpListener::bind は、指定したアドレスとポートで待ち受けを始めます。127.0.0.1 は自分のコンピュータ、7878 はポート番号です（電話のキーパッドで「rust」と打つと 7878 になります）
  • bind は失敗することもあるので Result を返します。管理者権限が必要なポート（1023 以下）や、他のプログラムが使っているポートだと失敗します
  • incoming は、接続の試み（TcpStream）のイテレータを返します。ストリームは、クライアントとサーバの間の 1 つの開いた接続です

cargo run して、ブラウザで 127.0.0.1:7878 を開いてみてください。ブラウザはエラーを表示しますが、ターミナルには Connection established! が何度か表示されます。

リクエストを読む

src/main.rs
use std::{    io::{prelude::*, BufReader},    net::{TcpListener, TcpStream},}; fn main() {    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();     for stream in listener.incoming() {        let stream = stream.unwrap();         handle_connection(stream);    }} fn handle_connection(mut stream: TcpStream) {    let buf_reader = BufReader::new(&stream);    let http_request: Vec<_> = buf_reader        .lines()        .map(|result| result.unwrap())        .take_while(|line| !line.is_empty())        .collect();     println!("Request: {http_request:#?}");}

BufReader でストリームを包むと、lines で 1 行ずつ読めます。HTTP のリクエストは、空行でヘッダが終わるので、take_while で空行が来るまでを集めます。

ターミナル
Request: [    "GET / HTTP/1.1",    "Host: 127.0.0.1:7878",    "User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10.15; rv:99.0) Gecko/20100101 Firefox/99.0",    "Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/avif,image/webp,*/*;q=0.8",    "Accept-Language: en-US,en;q=0.5",    "Accept-Encoding: gzip, deflate, br",    "DNT: 1",    "Connection: keep-alive",    "Upgrade-Insecure-Requests: 1",    "Sec-Fetch-Dest: document",    "Sec-Fetch-Mode: navigate",    "Sec-Fetch-Site: none",    "Sec-Fetch-User: ?1",    "Cache-Control: max-age=0",]

HTTP リクエストとレスポンスの形

リクエストの 1 行目はリクエスト行で、メソッド（GET）、URI（/）、HTTP のバージョンからなります。レスポンスの 1 行目はステータス行で、バージョン、ステータスコード（200）、理由句（OK）からなります。改行は \r\n（CRLF）です。

レスポンスを返す

まずは HTML ファイルを用意します。

hello.html
<!DOCTYPE html><html lang="en">  <head>    <meta charset="utf-8">    <title>Hello!</title>  </head>  <body>    <h1>Hello!</h1>    <p>Hi from Rust</p>  </body></html>
src/main.rs
use std::{    fs,    io::{prelude::*, BufReader},    net::{TcpListener, TcpStream},}; // --snip-- fn handle_connection(mut stream: TcpStream) {    let buf_reader = BufReader::new(&stream);    let http_request: Vec<_> = buf_reader        .lines()        .map(|result| result.unwrap())        .take_while(|line| !line.is_empty())        .collect();     let status_line = "HTTP/1.1 200 OK";    let contents = fs::read_to_string("hello.html").unwrap();    let length = contents.len();     let response =        format!("{status_line}\r\nContent-Length: {length}\r\n\r\n{contents}");     stream.write_all(response.as_bytes()).unwrap();}

Content-Length ヘッダで本文の長さを伝え、write_all で送ります。ブラウザで開くと、「Hello!」が表示されます。

リクエストに応じて返すものを変える

今はどんなリクエストにも同じ HTML を返しています。/ 以外のパスには 404 を返しましょう。

src/main.rs
fn handle_connection(mut stream: TcpStream) {    let buf_reader = BufReader::new(&stream);    let request_line = buf_reader.lines().next().unwrap().unwrap();     let (status_line, filename) = if request_line == "GET / HTTP/1.1" {        ("HTTP/1.1 200 OK", "hello.html")    } else {        ("HTTP/1.1 404 NOT FOUND", "404.html")    };     let contents = fs::read_to_string(filename).unwrap();    let length = contents.len();     let response =        format!("{status_line}\r\nContent-Length: {length}\r\n\r\n{contents}");     stream.write_all(response.as_bytes()).unwrap();}

404.html も用意しておきます。if と else で違うのはステータス行とファイル名だけなので、それだけを if 式でタプルとして選び、残りの処理は共通にしています。

20.3マルチスレッド化する

遅いリクエストを再現する

今のサーバは、リクエストを1 つずつ順番に処理します。時間のかかるリクエストが来ると、後ろのリクエストはすべて待たされます。/sleep にアクセスすると 5 秒かかる、というリクエストを追加して確かめましょう。

src/main.rs
use std::{    fs,    io::{prelude::*, BufReader},    net::{TcpListener, TcpStream},    thread,    time::Duration,}; // --snip-- fn handle_connection(mut stream: TcpStream) {    // --snip--     let (status_line, filename) = match &request_line[..] {        "GET / HTTP/1.1" => ("HTTP/1.1 200 OK", "hello.html"),        "GET /sleep HTTP/1.1" => {            thread::sleep(Duration::from_secs(5));            ("HTTP/1.1 200 OK", "hello.html")        }        _ => ("HTTP/1.1 404 NOT FOUND", "404.html"),    };     // --snip--}

ブラウザのタブを 2 つ開き、片方で /sleep、もう片方で / を開いてみてください。/ は一瞬で返るはずなのに、/sleep が終わるまで 5 秒待たされます。

スレッドプール

スレッドプールは、あらかじめ作っておいた、仕事を待っているスレッドの集まりです。新しい仕事が来たら、プールの中の空いているスレッドに割り当てます。仕事が終わったスレッドはプールに戻り、次の仕事を待ちます。

リクエストごとにスレッドを作るという方法もありますが、それだと大量のリクエストが来たときにスレッドを作りすぎて、システムが止まってしまいます（DoS 攻撃に弱い）。スレッドの数を固定しておけば、その心配はありません。

コンパイラ駆動開発で API を決める

まず、使う側のコードを先に書きます。そして、コンパイルエラーを頼りに、必要なものを 1 つずつ作っていきます。

src/main.rs
fn main() {    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();    let pool = ThreadPool::new(4);     for stream in listener.incoming() {        let stream = stream.unwrap();         pool.execute(|| {            handle_connection(stream);        });    }}

thread::spawn と同じような感覚で、pool.execute にクロージャを渡したい、というのが目標です。

ThreadPool の定義

src/lib.rs を作り、ThreadPool を定義します。

src/lib.rs
pub struct ThreadPool; impl ThreadPool {    /// 新しい ThreadPool を作る    ///    /// size はプールのスレッドの数    ///    /// # Panics    ///    /// size が 0 のとき、`new` はパニックする    pub fn new(size: usize) -> ThreadPool {        assert!(size > 0);         ThreadPool    }     pub fn execute<F>(&self, f: F)    where        F: FnOnce() + Send + 'static,    {    }}

execute のトレイト境界は、thread::spawn のシグネチャを参考にしています。

Rust
pub fn spawn<F, T>(f: F) -> JoinHandle<T>where    F: FnOnce() -> T,    F: Send + 'static,    T: Send + 'static,
境界理由
FnOnce()仕事（リクエストの処理）は 1 回だけ実行される
Sendクロージャを別のスレッドに送る必要がある
'staticスレッドがいつまで動くかわからないので、クロージャは借用を持てない

スレッドを保持する Worker

ThreadPool にスレッドを持たせたいのですが、thread::spawn は作った瞬間にコードの実行を始めてしまいます。プールのスレッドは「仕事が来るまで待つ」必要があります。

そこで、スレッドと ID を持つ Worker という構造体を用意し、ThreadPool は Worker のベクタを持つことにします。

src/lib.rs
use std::thread; pub struct ThreadPool {    workers: Vec<Worker>,} impl ThreadPool {    // --snip--    pub fn new(size: usize) -> ThreadPool {        assert!(size > 0);         let mut workers = Vec::with_capacity(size);         for id in 0..size {            workers.push(Worker::new(id));        }         ThreadPool { workers }    }    // --snip--} struct Worker {    id: usize,    thread: thread::JoinHandle<()>,} impl Worker {    fn new(id: usize) -> Worker {        let thread = thread::spawn(|| {});         Worker { id, thread }    }}

チャネルで仕事を Worker に届ける

ThreadPool から Worker へ仕事を届けるには、第 16 章のチャネルがぴったりです。

  1. ThreadPool がチャネルを作り、送信側を持つ
  2. 各 Worker が受信側を持つ
  3. 送る仕事の型として Job を定義する
  4. execute は、受け取ったクロージャを送信側から送る
  5. Worker のスレッドは、受信側をループで待ち、届いたクロージャを実行する

ところが、ここで問題が起きます。mpsc は「複数の生産者、1 つの消費者」なので、受信側をクローンして複数の Worker に配ることはできません。

Rustコンパイルエラーになる
for id in 0..size {    workers.push(Worker::new(id, receiver));   // 1 回目でムーブされる}
ターミナル
error[E0382]: use of moved value: `receiver`  --> src/lib.rs:26:42   |21 |         let (sender, receiver) = mpsc::channel();   |                      -------- move occurs because `receiver` has type `std::sync::mpsc::Receiver<Job>`, which does not implement the `Copy` trait...25 |         for id in 0..size {   |         ----------------- inside of this loop26 |             workers.push(Worker::new(id, receiver));   |                                          ^^^^^^^^ value moved here, in previous iteration of loop

複数のスレッドで 1 つの受信側を共有し、しかも 1 つの仕事を 1 つの Worker だけが受け取るようにしたい。第 16 章の答えが使えます。Arc<Mutex<T>> です。Arc で複数の Worker が受信側を所有でき、Mutex で一度に 1 つの Worker だけが受信側から仕事を取り出せます。

src/lib.rs
use std::{    sync::{mpsc, Arc, Mutex},    thread,}; pub struct ThreadPool {    workers: Vec<Worker>,    sender: mpsc::Sender<Job>,} type Job = Box<dyn FnOnce() + Send + 'static>; impl ThreadPool {    // --snip--    pub fn new(size: usize) -> ThreadPool {        assert!(size > 0);         let (sender, receiver) = mpsc::channel();         let receiver = Arc::new(Mutex::new(receiver));         let mut workers = Vec::with_capacity(size);         for id in 0..size {            workers.push(Worker::new(id, Arc::clone(&receiver)));        }         ThreadPool { workers, sender }    }     pub fn execute<F>(&self, f: F)    where        F: FnOnce() + Send + 'static,    {        let job = Box::new(f);         self.sender.send(job).unwrap();    }} struct Worker {    id: usize,    thread: thread::JoinHandle<()>,} impl Worker {    fn new(id: usize, receiver: Arc<Mutex<mpsc::Receiver<Job>>>) -> Worker {        let thread = thread::spawn(move || loop {            let job = receiver.lock().unwrap().recv().unwrap();             println!("Worker {id} got a job; executing.");             job();        });         Worker { id, thread }    }}

Job は、execute が受け取るクロージャの型を、トレイトオブジェクトとして Box に包んだものの型エイリアスです（第 19 章）。

Worker のスレッドは loop で回り続けます。

  1. receiver.lock() でミューテックスのロックを取る
  2. recv() で、チャネルから仕事が届くのを待つ
  3. 仕事を受け取ったら、job() で実行する
注意while let で書かない理由

ループを while let Ok(job) = receiver.lock().unwrap().recv() { job(); } と書きたくなるかもしれません。これはコンパイルできますが、意図どおりに動きません。

let job = receiver.lock().unwrap().recv().unwrap(); では、lock() が返した MutexGuard は、let 文の終わりですぐに drop され、ロックが解放されます。

一方、while let（や if let、match）では、条件式の中で作られた一時的な値は、ブロックの終わりまで生き続けます。つまり job() を実行している間もロックが握られたままになり、他の Worker は仕事を受け取れません。せっかくのマルチスレッドが、事実上シングルスレッドになってしまうのです。

これで、/sleep を開いている間も、他のタブの / はすぐに表示されるようになりました。

ターミナル
Worker 0 got a job; executing.Worker 2 got a job; executing.Worker 1 got a job; executing.Worker 3 got a job; executing.Worker 0 got a job; executing.

20.4正常なシャットダウンと片付け

今のサーバを Ctrl-C で止めると、処理中のリクエストがあっても、すべてのスレッドが即座に止まります。ここでは、Drop トレイトを実装して、プールが drop されるときに各スレッドの join を呼び、処理中の仕事を終えてから止まるようにします。

Drop で join する

src/lib.rsコンパイルエラーになる
impl Drop for ThreadPool {    fn drop(&mut self) {        for worker in &mut self.workers {            println!("Shutting down worker {}", worker.id);             worker.thread.join().unwrap();        }    }}
ターミナル
error[E0507]: cannot move out of `worker.thread` which is behind a mutable reference  --> src/lib.rs:52:13   |52 |             worker.thread.join().unwrap();   |             ^^^^^^^^^^^^^ ------ `worker.thread` moved due to this method call   |             |   |             move occurs because `worker.thread` has type `JoinHandle<()>`, which does not implement the `Copy` trait

join は JoinHandle の所有権を取ります。でも、worker は可変参照で借りているだけなので、中の thread をムーブできません。第 17 章の Option と take の技も使えますが、ここではもっと直接的に、Vec の drain(..) を使って、workers からすべての Worker を所有権ごと取り出します。

src/lib.rs
impl Drop for ThreadPool {    fn drop(&mut self) {        for worker in self.workers.drain(..) {            println!("Shutting down worker {}", worker.id);             worker.thread.join().unwrap();        }    }}

Worker にループを抜けさせる

しかし、これだけでは終わりません。Worker のスレッドは loop で永遠に仕事を待っているので、join は永遠に戻ってきません。デッドロックです。

Worker にループを抜けさせるには、チャネルを閉じるのが一番です。送信側を drop すると、受信側の recv は Err を返すようになります。Worker はそれを合図にループを抜ければよいのです。

送信側を先に drop できるように、sender を Option で包みます。

src/lib.rs
pub struct ThreadPool {    workers: Vec<Worker>,    sender: Option<mpsc::Sender<Job>>,} impl ThreadPool {    pub fn new(size: usize) -> ThreadPool {        // --snip--        ThreadPool {            workers,            sender: Some(sender),        }    }     pub fn execute<F>(&self, f: F)    where        F: FnOnce() + Send + 'static,    {        let job = Box::new(f);         self.sender.as_ref().unwrap().send(job).unwrap();    }} impl Drop for ThreadPool {    fn drop(&mut self) {        drop(self.sender.take());   // 送信側を drop してチャネルを閉じる         for worker in self.workers.drain(..) {            println!("Shutting down worker {}", worker.id);             worker.thread.join().unwrap();        }    }}

Worker 側は、recv の結果を match で見て、Err ならループを抜けます。

src/lib.rs
impl Worker {    fn new(id: usize, receiver: Arc<Mutex<mpsc::Receiver<Job>>>) -> Worker {        let thread = thread::spawn(move || {            loop {                let message = receiver.lock().unwrap().recv();                 match message {                    Ok(job) => {                        println!("Worker {id} got a job; executing.");                         job();                    }                    Err(_) => {                        println!("Worker {id} disconnected; shutting down.");                        break;                    }                }            }        });         Worker { id, thread }    }}

動作を確かめるために、main で 2 つのリクエストだけを受け付けて終わるようにします。

src/main.rs
fn main() {    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();    let pool = ThreadPool::new(4);     for stream in listener.incoming().take(2) {        let stream = stream.unwrap();         pool.execute(|| {            handle_connection(stream);        });    }     println!("Shutting down.");}   // ここで pool が drop される

20.6おわりに

これで、この本は終わりです。お疲れさまでした。

所有権から始まり、借用、ライフタイム、トレイト、スマートポインタ、並行性へと積み上げてきた考え方は、最後の Web サーバの中で 1 つにつながりました。Arc<Mutex<Receiver>> という型を見て、「複数の所有者がいて、一度に 1 つのスレッドだけが中身に触れる受信側」だと読めるなら、あなたはもう Rust の考え方を身につけています。
