第 12 章

入出力プロジェクト：コマンドラインツールを作る

簡易版の grep「minigrep」を作ります。引数の処理、ファイルの読み込み、エラー処理、モジュール分割、テスト駆動開発、環境変数、標準エラー出力。ここまでの章の総まとめです。

8 節図 5 点目安 120 分

12.1作るものと最終的な構成

grep（globally search a regular expression and print）は、ファイルの中から指定した文字列を含む行を探して表示するツールです。その簡易版 minigrep を作ります。

ターミナル
$ cargo run -- to poem.txtAre you nobody, too?How dreary to be somebody!

完成したときの構成を先に見ておきましょう。この章は、ここに向かって少しずつコードを育てていく章です。

ターミナル
$ cargo new minigrep$ cd minigrep

12.2コマンドライン引数を受け取る

最初の目標は、cargo run -- 検索文字列 ファイルパス の 2 つの引数を読むことです。-- は「ここから先は cargo ではなく、プログラムへの引数」という区切りです。

src/main.rs
use std::env; fn main() {    let args: Vec<String> = env::args().collect();    dbg!(args);}

std::env::args は、コマンドライン引数のイテレータ（第 13 章）を返します。collect で、イテレータの中身をベクタに集めます。collect はさまざまなコレクションを作れるので、Vec<String> と型注釈を書いて、何を作るかを指定します。

メモ関数は親モジュールを use する

use std::env::args; として args() と呼ぶこともできますが、第 7 章の慣習どおり、親モジュールの env までを持ち込んでいます。env::args() と書けば、現在のモジュールで定義された関数ではないことがひと目でわかります。

なお、引数に不正な Unicode が含まれていると env::args はパニックします。それを受け付けたいなら env::args_os を使いますが、ここでは扱いません。

ターミナル
$ cargo run -- needle haystack[src/main.rs:5:5] args = [    "target/debug/minigrep",    "needle",    "haystack",]

ベクタの最初の要素はプログラムの名前です。ほしい 2 つの値は、添字 1 と 2 にあります。

src/main.rs
use std::env; fn main() {    let args: Vec<String> = env::args().collect();     let query = &args[1];    let file_path = &args[2];     println!("Searching for {query}");    println!("In file {file_path}");}

12.3ファイルを読み込む

テスト用のファイル poem.txt を、プロジェクトの最上位に作ります。エミリー・ディキンソンの詩です。

poem.txt
I'm nobody! Who are you?Are you nobody, too?Then there's a pair of us - don't tell!They'd banish us, you know. How dreary to be somebody!How public, like a frogTo tell your name the livelong dayTo an admiring bog!
src/main.rs
use std::env;use std::fs; fn main() {    // --snip--    println!("In file {file_path}");     let contents = fs::read_to_string(file_path)        .expect("Should have been able to read the file");     println!("With text:\n{contents}");}

fs::read_to_string は、ファイルの中身を Result<String> で返します。

これで動くことは動きますが、問題がいくつもあります。main がいろいろな仕事を抱えすぎていますし、エラー処理も雑です。プログラムが小さいうちに、リファクタリングしておきましょう。

12.4リファクタリングでモジュール性とエラー処理を改善する

今のコードの問題は 4 つあります。

  1. main が引数の解析とファイルの読み込みの両方をしている。関数は 1 つの仕事に絞るべき
  2. query と file_path はプログラムの設定だが、ただの変数として散らばっている
  3. ファイルの読み込みに失敗すると、理由にかかわらず「Should have been able to read the file」と表示される
  4. 引数が足りないと、index out of bounds という、ユーザーには意味のわからないエラーでパニックする

バイナリプロジェクトの責任の分け方

Rust のコミュニティには、main が大きくなってきたときの定石があります。

要点バイナリプロジェクトの関心の分離
  • プログラムを main.rs と lib.rs に分け、ロジックは lib.rs に移す
  • 引数の解析が小さいうちは main.rs に置いてよい。複雑になってきたら lib.rs に移す

その結果、main に残る責任は次の 4 つだけになる。

  1. 引数の値で、引数を解析するロジックを呼ぶ
  2. その他の設定を準備する
  3. lib.rs の run 関数を呼ぶ
  4. run がエラーを返したら、それを処理する

main.rs はテストできませんが、lib.rs は第 11 章の方法でテストできます。main.rs を、読むだけで正しいとわかるくらい小さく保つのが狙いです。

段階 1：引数の解析を関数に抜き出す

src/main.rs
fn main() {    let args: Vec<String> = env::args().collect();     let (query, file_path) = parse_config(&args);     // --snip--} fn parse_config(args: &[String]) -> (&str, &str) {    let query = &args[1];    let file_path = &args[2];     (query, file_path)}

段階 2：設定を構造体にまとめる

タプルで 2 つの値を返していますが、この 2 つは「設定」という 1 つの概念に属しています。構造体にして、名前で意味を伝えましょう。

src/main.rs
fn main() {    let args: Vec<String> = env::args().collect();     let config = parse_config(&args);     println!("Searching for {}", config.query);    println!("In file {}", config.file_path);     let contents = fs::read_to_string(config.file_path)        .expect("Should have been able to read the file");    // --snip--} struct Config {    query: String,    file_path: String,} fn parse_config(args: &[String]) -> Config {    let query = args[1].clone();    let file_path = args[2].clone();     Config { query, file_path }}

Config には String を持たせ、args の要素を clone しています。参照を持たせることもできますが、ライフタイムの管理が必要になります。ここでは、少しの性能を犠牲にして簡潔さを取りました。

メモclone は悪か

所有権の問題を clone で解決するのを嫌う人もいます。実行時のコストがあるからです。でも、文字列 2 つを 1 回コピーするくらいは、まったく問題になりません。最初から完璧に最適化されたコードを目指すより、まず動くコードを書くほうが大事です。第 13 章で、この clone をなくす方法を学びます。

段階 3：コンストラクタにする

parse_config は Config を作る関数なので、Config の関連関数 new にするのが自然です。

src/main.rs
fn main() {    let args: Vec<String> = env::args().collect();     let config = Config::new(&args);    // --snip--} impl Config {    fn new(args: &[String]) -> Config {        let query = args[1].clone();        let file_path = args[2].clone();         Config { query, file_path }    }}

段階 4：エラー処理を直す

引数なしで実行すると、こうなります。

ターミナル
$ cargo runthread 'main' panicked at src/main.rs:27:21:index out of bounds: the len is 1 but the index is 1

ユーザーにとって意味のわからないメッセージです。引数の数を確認して、Result を返すようにしましょう。new という名前の関数は失敗しないことが期待されるので、名前も build に変えます。

src/main.rs
impl Config {    fn build(args: &[String]) -> Result<Config, &'static str> {        if args.len() < 3 {            return Err("not enough arguments");        }         let query = args[1].clone();        let file_path = args[2].clone();         Ok(Config { query, file_path })    }}

エラーの値は文字列リテラルなので、型は &'static str です。呼び出し側では、unwrap_or_else でエラーを処理します。

src/main.rs
use std::process; fn main() {    let args: Vec<String> = env::args().collect();     let config = Config::build(&args).unwrap_or_else(|err| {        println!("Problem parsing arguments: {err}");        process::exit(1);    });     // --snip--}

unwrap_or_else は、Ok なら中身を返し、Err なら渡したクロージャ（第 13 章）を呼びます。|err| の部分が引数です。process::exit(1) は、プログラムをすぐに終了コード 1 で終わらせます。0 以外の終了コードは「失敗した」ことを呼び出したプロセスに伝える慣習です。

ターミナル
$ cargo runProblem parsing arguments: not enough arguments

段階 5：run 関数を抜き出す

設定以外のロジック、つまりファイルを読んで処理する部分を run に移します。

src/main.rs
use std::error::Error; fn main() {    // --snip--     println!("Searching for {}", config.query);    println!("In file {}", config.file_path);     if let Err(e) = run(config) {        println!("Application error: {e}");        process::exit(1);    }} fn run(config: Config) -> Result<(), Box<dyn Error>> {    let contents = fs::read_to_string(config.file_path)?;     println!("With text:\n{contents}");     Ok(())}
  • 戻り値は Result<(), Box<dyn Error>>。成功時に返すものはないのでユニット ()、エラーは「Error トレイトを実装した何らかの型」です（トレイトオブジェクト、第 17 章）。どんな種類のエラーでも返せます
  • expect を ? に変えたので、パニックせずにエラーを呼び出し元に返します
  • main では、run の戻り値の Ok には興味がないので、unwrap_or_else ではなく if let で Err だけを処理しています

段階 6：ライブラリクレートに分ける

最後に、Config と run を src/lib.rs に移します。外から使う要素には pub を付けます。

src/lib.rs
use std::error::Error;use std::fs; pub struct Config {    pub query: String,    pub file_path: String,} impl Config {    pub fn build(args: &[String]) -> Result<Config, &'static str> {        // --snip--    }} pub fn run(config: Config) -> Result<(), Box<dyn Error>> {    // --snip--}
src/main.rs
use std::env;use std::process; use minigrep::Config; fn main() {    // --snip--    if let Err(e) = minigrep::run(config) {        // --snip--    }}

構造はこれで完成です。ここから先は、テストを書きながら検索機能を作ります。

12.5テスト駆動開発で検索機能を作る

検索のロジックはテスト駆動開発（TDD）で作ります。TDD は次の手順を繰り返す開発手法です。

失敗するテストを書く

src/lib.rs
#[cfg(test)]mod tests {    use super::*;     #[test]    fn one_result() {        let query = "duct";        let contents = "\Rust:safe, fast, productive.Pick three.";         assert_eq!(vec!["safe, fast, productive."], search(query, contents));    }}

"duct" を含むのは 2 行目（productive）だけなので、その行だけが入ったベクタが返ってくることを期待しています。文字列の最初の \ は、直後の改行を文字列に含めないための記号です。

テストを通すには search 関数が必要です。まずは、空のベクタを返すだけの関数を書きます。

src/lib.rs
pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {    vec![]}

ここでライフタイム 'a が出てきました。search が返すベクタには、contents の一部（各行のスライス）が入ります。つまり戻り値は contents から借用しているので、contents と同じだけ生きるように結びつけています。query とは関係ありません。

ライフタイムを書かないと、コンパイラは戻り値が query と contents のどちらから借用されたのかわからず、E0106 エラーになります（第 10 章）。

テストを実行すると、期待どおり失敗します。

ターミナル
---- tests::one_result stdout ----thread 'tests::one_result' panicked at src/lib.rs:44:9:assertion `left == right` failed  left: ["safe, fast, productive."] right: []

テストを通すコードを書く

src/lib.rs
pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {    let mut results = Vec::new();     for line in contents.lines() {      // 1 行ずつ        if line.contains(query) {        // query を含むか            results.push(line);          // 含むなら結果に追加        }    }     results}
ターミナル
running 1 testtest tests::one_result ... ok

run から search を呼ぶ

src/lib.rs
pub fn run(config: Config) -> Result<(), Box<dyn Error>> {    let contents = fs::read_to_string(config.file_path)?;     for line in search(&config.query, &contents) {        println!("{line}");    }     Ok(())}
ターミナル
$ cargo run -- frog poem.txtHow public, like a frog $ cargo run -- body poem.txtI'm nobody! Who are you?Are you nobody, too?How dreary to be somebody!

動きました。

12.6環境変数を扱う

大文字と小文字を区別しない検索を追加しましょう。オプションは、環境変数で切り替えられるようにします。環境変数で設定すると、ターミナルのセッションの間ずっと有効にしておけます。

失敗するテストを先に書く

src/lib.rs
#[cfg(test)]mod tests {    use super::*;     #[test]    fn case_sensitive() {        let query = "duct";        let contents = "\Rust:safe, fast, productive.Pick three.Duct tape.";         assert_eq!(vec!["safe, fast, productive."], search(query, contents));    }     #[test]    fn case_insensitive() {        let query = "rUsT";        let contents = "\Rust:safe, fast, productive.Pick three.Trust me.";         assert_eq!(            vec!["Rust:", "Trust me."],            search_case_insensitive(query, contents)        );    }}

search_case_insensitive を実装する

src/lib.rs
pub fn search_case_insensitive<'a>(    query: &str,    contents: &'a str,) -> Vec<&'a str> {    let query = query.to_lowercase();   // 新しい String（シャドーイング）    let mut results = Vec::new();     for line in contents.lines() {        if line.to_lowercase().contains(&query) {            results.push(line);        }    }     results}

to_lowercase は新しい String を作るので、query は &str から String に変わります。contains は &str を受け取るので、&query と参照を渡します。

Config に設定を追加して、環境変数から読む

src/lib.rs
use std::env; pub struct Config {    pub query: String,    pub file_path: String,    pub ignore_case: bool,} impl Config {    pub fn build(args: &[String]) -> Result<Config, &'static str> {        if args.len() < 3 {            return Err("not enough arguments");        }         let query = args[1].clone();        let file_path = args[2].clone();         let ignore_case = env::var("IGNORE_CASE").is_ok();         Ok(Config {            query,            file_path,            ignore_case,        })    }} pub fn run(config: Config) -> Result<(), Box<dyn Error>> {    let contents = fs::read_to_string(config.file_path)?;     let results = if config.ignore_case {        search_case_insensitive(&config.query, &contents)    } else {        search(&config.query, &contents)    };     for line in results {        println!("{line}");    }     Ok(())}

env::var は環境変数の値を Result で返します。設定されていれば Ok、なければ Err です。ここでは値の中身には興味がなく、「設定されているかどうか」だけを知りたいので、is_ok で bool にしています。

ターミナル
$ cargo run -- to poem.txtAre you nobody, too?How dreary to be somebody! $ IGNORE_CASE=1 cargo run -- to poem.txtAre you nobody, too?How dreary to be somebody!To tell your name the livelong dayTo an admiring bog!

PowerShell では次のように設定します。

ターミナル
PS> $Env:IGNORE_CASE=1; cargo run -- to poem.txt

12.7エラーは標準エラー出力に書く

今は、エラーメッセージも検索結果も、すべて println! で標準出力に書いています。ターミナルには 2 種類の出力先があります。

結果をファイルに保存しようとして > でリダイレクトすると、今のままではエラーメッセージまでファイルに入ってしまいます。

ターミナル
$ cargo run > output.txt

画面には何も表示されず、output.txt に Problem parsing arguments: not enough arguments が書き込まれます。ユーザーは失敗したことに気づけません。

エラーメッセージは、eprintln! で標準エラー出力に書きましょう。

src/main.rs
fn main() {    let args: Vec<String> = env::args().collect();     let config = Config::build(&args).unwrap_or_else(|err| {        eprintln!("Problem parsing arguments: {err}");        process::exit(1);    });     if let Err(e) = minigrep::run(config) {        eprintln!("Application error: {e}");        process::exit(1);    }}
ターミナル
$ cargo run > output.txtProblem parsing arguments: not enough arguments

エラーは画面に表示され、output.txt は空のままです。正しく引数を渡すと、結果だけがファイルに書かれます。

ターミナル
$ cargo run -- to poem.txt > output.txt
