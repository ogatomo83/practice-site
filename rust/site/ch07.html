第 7 章

パッケージ・クレート・モジュールでプロジェクトを整理する

コードが大きくなったら、分けて整理する必要があります。パッケージ、クレート、モジュール、パスという 4 つの道具の関係を、入れ子の図とモジュールの木で整理します。

7 節図 9 点目安 60 分

7.14 つの道具の全体像

Rust のコード整理の仕組みは、まとめてモジュールシステムと呼ばれます。登場する道具は 4 つです。

道具一言でいうと
パッケージCargo の単位。クレートをビルド・テスト・共有するためのまとまり
クレートコンパイルの単位。ライブラリか実行ファイルを 1 つ作るモジュールの木
モジュール と useクレートの中の整理の単位。中身の公開・非公開も決める
パス構造体・関数・モジュールなどの要素に付ける「住所」

これらは入れ子の関係になっています。

7.2パッケージとクレート

クレート

クレートは、Rust コンパイラが一度に扱うコードの最小単位です。rustc main.rs のように 1 つのファイルを渡しても、それは 1 つのクレートとして扱われます。クレートには 2 種類あります。

バイナリクレートライブラリクレート
できるもの実行ファイル他のクレートから使われるコード
main 関数必要ない
例第 2 章の数当てゲームrand

Rust のプログラマが単に「クレート」と言うときは、たいていライブラリクレートのことで、他の言語の「ライブラリ」とほぼ同じ意味です。

クレートルートは、コンパイラがコンパイルを開始するソースファイルで、クレートのモジュールの木の根になります。

パッケージ

パッケージは、1 つ以上のクレートをまとめたもので、Cargo.toml を持ちます。ルールは次のとおりです。

  • ライブラリクレートは最大 1 つ
  • バイナリクレートはいくつでも
  • 少なくとも 1 つのクレートを含む

Cargo は、ファイルの置き場所で自動的にクレートを見つけます。

cargo new my-project で作ったパッケージには src/main.rs しかないので、バイナリクレートを 1 つだけ含みます。src/lib.rs を追加すると、同じ名前のライブラリクレートも持つことになります。

7.3モジュールでスコープとプライバシーを決める

モジュールは、クレートの中のコードをグループに分けるための仕組みです。読みやすくするだけでなく、外から使える要素（公開）と、内部の実装の詳細（非公開）を分ける役割も持っています。

モジュールの早見表

まず、モジュールの規則を一覧で示します。細かい説明はこの後の節で行います。

要点モジュールの規則
  • クレートルートから始まる。 コンパイラはまずクレートルート（src/lib.rs か src/main.rs）を見る
  • モジュールの宣言。 クレートルートで mod garden; と書くと、コンパイラは次の場所からコードを探す - インライン：mod garden { ... } の波かっこの中 - ファイル：src/garden.rs - ファイル：src/garden/mod.rs（古い書き方）
  • サブモジュールの宣言。 src/garden.rs の中で mod vegetables; と書くと、src/garden/vegetables.rs（または src/garden/vegetables/mod.rs）を探す
  • パス。 モジュールの中の要素は、crate::garden::vegetables::Asparagus のようなパスで参照できる
  • 非公開がデフォルト。 モジュールの中身は親から見えない。公開するには pub を付ける
  • use。 use crate::garden::vegetables::Asparagus; と書くと、以降は Asparagus だけで参照できる

レストランを例にモジュールを作る

レストランの機能を提供するライブラリを作ってみます。レストランには、客から見える接客部門（front of house）と、客から見えない調理部門（back of house）があります。

ターミナル
$ cargo new restaurant --lib
src/lib.rs
mod front_of_house {    mod hosting {        fn add_to_waitlist() {}         fn seat_at_table() {}    }     mod serving {        fn take_order() {}         fn serve_order() {}         fn take_payment() {}    }}

mod キーワードの後にモジュール名を書き、波かっこの中に中身を書きます。モジュールの中にはモジュールを入れられますし、構造体、enum、定数、トレイト、関数なども入れられます。

このコードは、次のようなモジュールの木を作ります。

木の根にある crate は、クレートルート（src/lib.rs）の中身が作る暗黙のモジュールです。hosting と serving は front_of_house の子で、互いに兄弟です。家系図のような言葉で関係を表します。

7.4パスでモジュールの木の要素を指す

木の中の要素を使うには、その場所をパスで指定します。ファイルシステムのパスと同じく、2 種類あります。

  • 絶対パス：クレートの根から始まる。自分のクレートなら crate から、外部クレートならクレート名から書く
  • 相対パス：今いるモジュールから始まる。self、super、または今のモジュールの中の要素名から書く

どちらも、要素の名前を :: でつなぎます。

src/lib.rsコンパイルエラーになる
mod front_of_house {    mod hosting {        fn add_to_waitlist() {}    }} pub fn eat_at_restaurant() {    // 絶対パス    crate::front_of_house::hosting::add_to_waitlist();     // 相対パス    front_of_house::hosting::add_to_waitlist();}

どちらを使うかは、プロジェクト次第です。要素の定義と使う側を一緒に動かすことが多いなら相対パス、別々に動かすことが多いなら絶対パスが便利です。一般には、絶対パスが好まれます。

非公開の壁

ところが、このコードはコンパイルできません。

ターミナル
error[E0603]: module `hosting` is private --> src/lib.rs:9:28  |9 |     crate::front_of_house::hosting::add_to_waitlist();  |                            ^^^^^^^  --------------- function `add_to_waitlist` is not publicly re-exported  |                            |  |                            private module  |note: the module `hosting` is defined here --> src/lib.rs:2:5  |2 |     mod hosting {  |     ^^^^^^^^^^^
error[E0603]モジュール hosting は非公開です

パスは正しいのですが、hosting が非公開なので、外からはたどれません。Rust では、関数・メソッド・構造体・enum・モジュール・定数など、すべての要素がデフォルトで非公開です。

非公開のルールは、「子は親の中身を見られるが、親は子の非公開な中身を見られない」です。

レストランにたとえると、調理部門の中で何が起きているかは客からは見えませんが、厨房のスタッフはレストラン全体を見渡せる、という関係です。これにより、外部のコードを壊すことなく、内部の実装を自由に変更できます。

pub で公開する

hosting と add_to_waitlist に pub を付けます。

src/lib.rs
mod front_of_house {    pub mod hosting {        pub fn add_to_waitlist() {}    }} pub fn eat_at_restaurant() {    crate::front_of_house::hosting::add_to_waitlist();    front_of_house::hosting::add_to_waitlist();}

pub mod hosting だけでは足りません。モジュールを公開しても、それは「親がそのモジュールを参照できる」ようになるだけで、中身は非公開のままです。中の関数にも pub が必要です。

front_of_house 自体には pub が付いていませんが、eat_at_restaurant と同じモジュール（crate）の中で定義された兄弟なので、参照できます。

メモライブラリとバイナリを持つパッケージの定石

パッケージに src/lib.rs と src/main.rs の両方があるなら、ほとんどのコードをライブラリクレートに置き、バイナリクレートはライブラリの公開 API を呼ぶだけにするのが定石です。こうするとバイナリクレートがライブラリの「最初の利用者」になり、API の使い勝手を自分で確かめられます。第 12 章でこの構成を実践します。

super で親から始める

super は、ファイルシステムの .. と同じく、親モジュールから始まる相対パスを作ります。

src/lib.rs
fn deliver_order() {} mod back_of_house {    fn fix_incorrect_order() {        cook_order();        super::deliver_order(); // 親（crate）の deliver_order    }     fn cook_order() {}}

注文を作り直して客に届けるのは調理部門の仕事ですが、届ける関数は親モジュールにあります。back_of_house と deliver_order は一緒に移動する可能性が高いので、super を使った相対パスにしておけば、まとめて別のモジュールに移しても書き換えが要りません。

構造体と enum の公開

構造体に pub を付けると、構造体は公開されますが、フィールドは非公開のままです。フィールドごとに公開・非公開を選べます。

src/lib.rs
mod back_of_house {    pub struct Breakfast {        pub toast: String,          // 客が選べる        seasonal_fruit: String,     // 季節で厨房が決める    }     impl Breakfast {        pub fn summer(toast: &str) -> Breakfast {            Breakfast {                toast: String::from(toast),                seasonal_fruit: String::from("peaches"),            }        }    }} pub fn eat_at_restaurant() {    // ライ麦パンの朝食を注文    let mut meal = back_of_house::Breakfast::summer("Rye");    // やっぱり別のパンにする    meal.toast = String::from("Wheat");    println!("I'd like {} toast please", meal.toast);     // 次の行はコンパイルできない。フルーツは選べない    // meal.seasonal_fruit = String::from("blueberries");}

非公開のフィールドがある構造体は、外から直接 Breakfast { ... } と書いて作ることができません。そのため、インスタンスを作る公開の関連関数（ここでは summer）が必要になります。

一方、enum を公開すると、すべての列挙子が公開されます。列挙子の一部だけが見えない enum は役に立たないからです。

Rust
mod back_of_house {    pub enum Appetizer {        Soup,   // pub を付けなくても公開        Salad,    }}
pub を付けたとき中身
pub modモジュールが見える中身はそれぞれ pub が必要
pub struct型が見えるフィールドはそれぞれ pub が必要
pub enum型が見えるすべての列挙子が公開

7.5use でパスをスコープに持ち込む

毎回 crate::front_of_house::hosting::add_to_waitlist() と書くのは長すぎます。use でパスを一度持ち込めば、以降は短い名前で書けます。ファイルシステムのシンボリックリンクのようなものです。

src/lib.rs
mod front_of_house {    pub mod hosting {        pub fn add_to_waitlist() {}    }} use crate::front_of_house::hosting; pub fn eat_at_restaurant() {    hosting::add_to_waitlist();}

use の効果は、use を書いたスコープの中だけです。別のモジュールの中では使えません。

src/lib.rsコンパイルエラーになる
use crate::front_of_house::hosting; mod customer {    pub fn eat_at_restaurant() {        hosting::add_to_waitlist(); // error[E0433]: customer の中には hosting がない    }}

customer モジュールの中で使いたいなら、customer の中に use を移すか、super::hosting と書きます。

慣習的な use の書き方

なぜ add_to_waitlist まで持ち込まずに、親モジュールの hosting で止めたのでしょうか。

Rust
use crate::front_of_house::hosting::add_to_waitlist;  // 動くが、慣習的でない add_to_waitlist();           // どこで定義された関数か、ぱっと見でわからないhosting::add_to_waitlist();  // 他のモジュールの関数だとすぐわかる

慣習は次のとおりです。

持ち込むもの慣習例
関数親モジュールまで持ち込むuse std::io; → io::stdin()
構造体・enum など型そのものを持ち込むuse std::collections::HashMap; → HashMap::new()

型の名前が衝突するときは例外で、親モジュールで区別します。

Rust
use std::fmt;use std::io; fn function1() -> fmt::Result { /* --snip-- */ }fn function2() -> io::Result<()> { /* --snip-- */ }

as で別名を付ける

もう 1 つの解決策は、as で別名を付けることです。

Rust
use std::fmt::Result;use std::io::Result as IoResult; fn function1() -> Result { /* --snip-- */ }fn function2() -> IoResult<()> { /* --snip-- */ }

pub use で再公開する

use で持ち込んだ名前は、そのスコープの中では非公開です。pub use にすると、持ち込んだ名前をさらに外に公開できます。これを再公開（re-export）と呼びます。

src/lib.rs
mod front_of_house {    pub mod hosting {        pub fn add_to_waitlist() {}    }} pub use crate::front_of_house::hosting;

コードを書く人にとって都合のよい内部構造と、使う人にとってわかりやすい公開 API は、しばしば違います。pub use で、その 2 つを切り離せるのです。第 14 章で、ドキュメントとの関係も含めて再び扱います。

外部パッケージを使う

第 2 章で rand を使ったときも、use を使いました。

Cargo.toml
[dependencies]rand = "0.8.5"
Rust
use rand::Rng; fn main() {    let secret_number = rand::thread_rng().gen_range(1..=100);}

外部クレートのパスは、crate ではなくクレート名から始まります。標準ライブラリ std も外部クレートの一種ですが、Rust に同梱されているので Cargo.toml に書く必要はありません。

Rust
use std::collections::HashMap;

ネストしたパスと glob

同じクレートやモジュールから複数の要素を持ち込むときは、まとめて書けます。

Rust
// 2 行で書く代わりにuse std::cmp::Ordering;use std::io;// 1 行でuse std::{cmp::Ordering, io}; // 2 行で書く代わりにuse std::io;use std::io::Write;// self を使って 1 行でuse std::io::{self, Write};

公開されている要素をすべて持ち込みたいときは、glob 演算子 * を使います。

Rust
use std::collections::*;

ただし glob を使うと、どの名前がどこから来たのかわかりにくくなります。テストモジュールで use super::*; と書く場合（第 11 章）などに限って使うのが無難です。

7.6モジュールを複数のファイルに分ける

ここまではすべて 1 つのファイルに書いてきました。モジュールが大きくなったら、ファイルに分けます。

src/lib.rs
mod front_of_house;   // 中身は src/front_of_house.rs にある、という宣言 pub use crate::front_of_house::hosting; pub fn eat_at_restaurant() {    hosting::add_to_waitlist();}
src/front_of_house.rs
pub mod hosting;      // 中身は src/front_of_house/hosting.rs にある
src/front_of_house/hosting.rs
pub fn add_to_waitlist() {}
注意mod は「読み込み」ではない

mod 宣言は、C の #include や他の言語の import とは違います。モジュールの木の中で 1 回だけ宣言するもので、「このモジュールはここにある」とコンパイラに教えるためのものです。他のファイルからそのモジュールを使いたいときは、もう一度 mod を書くのではなく、宣言された場所へのパス（と use）を使います。

深掘り古い書き方：mod.rs

Rust 2015 エディションまでは、src/front_of_house/hosting.rs の代わりに src/front_of_house/hosting/mod.rs という置き方が主流でした。今もこの書き方はサポートされています。ただし、mod.rs という名前のファイルがエディタのタブにたくさん並んで区別がつかなくなるので、新しいコードでは使わないことが推奨されています。同じモジュールに両方の書き方を混ぜるとコンパイルエラーになります。

ファイルを分けても、モジュールの木もパスも変わりません。eat_at_restaurant の中身は 1 文字も変わっていないことに注目してください。

7.7この章のまとめ

  • パッケージは Cargo の単位、クレートはコンパイルの単位、モジュールは整理と公開範囲の単位
  • 要素はデフォルトで非公開。公開するには pub。構造体のフィールドは個別に、enum の列挙子はまとめて公開される
  • パスは crate から始まる絶対パスか、self / super / 名前から始まる相対パス
  • use で短い名前を持ち込み、pub use で再公開する
  • mod 名前; と書くと、コンパイラは 名前.rs を探す
