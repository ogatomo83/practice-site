スマートポインタ

ポインタのように振る舞いながら、追加の情報と機能を持つ構造体、スマートポインタ。ヒープに置く Box、所有者を複数にする Rc、実行時に借用を検査する RefCell。メモリがいつ確保され、いつ解放されるのかを図で追いかけます。

8 節図 15 点目安 120 分

15.1スマートポインタとは

ポインタは、メモリのアドレスを持つ変数のことです。Rust で最もよく使うポインタは、第 4 章の参照（&）です。参照は値を借用するだけで、それ以上の機能はなく、コストもありません。

スマートポインタは、ポインタのように振る舞うだけでなく、追加のメタデータと機能を持つデータ構造です。実は、すでに 2 つ使っています。String と Vec<T> です。どちらもメモリを所有し、容量などのメタデータを持ち、「中身は常に正しい UTF-8」のような保証を提供しています。

参照とスマートポインタの大きな違いは、参照は借りるだけだが、スマートポインタは多くの場合、指しているデータを所有することです。

スマートポインタは普通は構造体として実装され、2 つのトレイトを実装しています。

この章で扱う主なスマートポインタは次の 3 つです。

型一言でいうと所有者借用の検査
Box<T>値をヒープに置く1 つコンパイル時
Rc<T>参照カウントで、所有者を複数にする複数コンパイル時（不変のみ）
RefCell<T>不変の見た目のまま、中身を変更できる1 つ実行時

15.2Box<T> でヒープのデータを指す

最も単純なスマートポインタがボックス Box<T> です。値をヒープに置き、スタックにはヒープへのポインタだけを残します。性能上のオーバーヘッドはありません。

Rust
fn main() {    let b = Box::new(5);    println!("b = {b}");}

i32 1 つをヒープに置いてもあまり意味はありません。Box が役立つのは、次のような場面です。

  • コンパイル時に大きさがわからない型を、大きさが必要な場所で使いたいとき（この後の再帰的な型）
  • 大きなデータの所有権を、コピーせずに移したいとき（ムーブでポインタだけがコピーされる）
  • 具体的な型ではなく、特定のトレイトを実装していることだけが大事なとき（トレイトオブジェクト、第 17 章）

再帰的な型を Box で可能にする

再帰的な型とは、自分自身の型の値を一部として持つ型です。関数型言語でよく使われるコンスリストを例にとります。コンスリストは、「値」と「次のリスト」の組を入れ子にしたもので、最後は Nil で終わります。

(1, (2, (3, Nil)))

素直に enum で書いてみます。

Rustコンパイルエラーになる
enum List {    Cons(i32, List),    Nil,} use crate::List::{Cons, Nil}; fn main() {    let list = Cons(1, Cons(2, Cons(3, Nil)));}
ターミナル
error[E0072]: recursive type `List` has infinite size --> src/main.rs:1:1  |1 | enum List {  | ^^^^^^^^^2 |     Cons(i32, List),  |               ---- recursive without indirection  |help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle  |2 |     Cons(i32, Box<List>),  |               ++++    +
error[E0072]再帰的な型 List の大きさが無限になります

Rust は、すべての型の大きさをコンパイル時に知る必要があります。List の大きさを計算しようとすると、Cons は i32 と List を含むので、List の大きさを知るには List の大きさが必要で……と無限に続きます。

ヘルプのとおり、Box で間接参照（indirection）を入れます。Box<List> はポインタなので、大きさは中身に関係なく一定です。

Rust
enum List {    Cons(i32, Box<List>),    Nil,} use crate::List::{Cons, Nil}; fn main() {    let list = Cons(1, Box::new(Cons(2, Box::new(Cons(3, Box::new(Nil))))));}

15.3Deref トレイトで参照のように扱う

Deref トレイトを実装すると、参照外し演算子 * の振る舞いをカスタマイズできます。これによって、スマートポインタを普通の参照と同じように扱えるようになります。

参照をたどる

Rust
fn main() {    let x = 5;    let y = &x;     assert_eq!(5, x);    assert_eq!(5, *y);   // y は参照なので、* でたどって値を得る}

assert_eq!(5, y) と書くと、数値と参照は比較できないのでエラーになります。参照の指す先の値を得るには、* で参照外し（dereference）をします。

Box を参照のように使う

Rust
fn main() {    let x = 5;    let y = Box::new(x);     assert_eq!(5, x);    assert_eq!(5, *y);   // Box でも * が使える}

自分でスマートポインタを作る

Box<T> と似た型を自分で定義して、* が使えるようにしてみましょう。

Rustコンパイルエラーになる
struct MyBox<T>(T); impl<T> MyBox<T> {    fn new(x: T) -> MyBox<T> {        MyBox(x)    }} fn main() {    let x = 5;    let y = MyBox::new(x);     assert_eq!(5, *y);   // error[E0614]: type `MyBox<{integer}>` cannot be dereferenced}

MyBox は * の使い方を知りません。Deref トレイトを実装します。

Rust
use std::ops::Deref; impl<T> Deref for MyBox<T> {    type Target = T;     fn deref(&self) -> &Self::Target {        &self.0       // 中の値への参照を返す    }}

*y と書くと、Rust は内部で次のように書き換えます。

Rust
*(y.deref())

deref は参照を返します。もし値そのものを返したら、self から値がムーブされてしまうからです。その参照に対して、普通の * を 1 回適用します。この書き換えは 1 回だけ行われ、無限に続くことはありません。

参照外し型強制

参照外し型強制（deref coercion）は、Deref を実装した型への参照を、別の型への参照に自動で変換する機能です。関数やメソッドの引数の型と、渡した値の型が合わないときに、deref を必要な回数だけ呼んで合わせてくれます。

Rust
fn hello(name: &str) {    println!("Hello, {name}!");} fn main() {    let m = MyBox::new(String::from("Rust"));    hello(&m);   // &MyBox<String> → &String → &str と自動変換}

この機能がなければ、hello(&(*m)[..]) と書かなければなりません。読みにくいうえに、何をしているのかわかりません。

可変参照についても同じ仕組みがあり、変換のルールは次のとおりです。

元の型変換先条件
&T&UT: Deref<Target = U>
&mut T&mut UT: DerefMut<Target = U>
&mut T&UT: Deref<Target = U>

不変から可変への変換はありません。不変参照は他にもあるかもしれず、可変参照に変えると借用ルールを破る可能性があるからです。

15.4Drop トレイトで片付けをする

スマートポインタにとって大事なもう 1 つのトレイトが Drop です。値がスコープを抜けるときに実行するコードを定義できます。ファイルやネットワーク接続などの資源の解放に使われ、Box<T> の場合は、ヒープの領域の解放がこれにあたります。

C++ のデストラクタに似ていますが、Rust では片付けのコードを呼ぶ場所を自分で書く必要がありません。忘れることもありません。

Rust
struct CustomSmartPointer {    data: String,} impl Drop for CustomSmartPointer {    fn drop(&mut self) {        println!("Dropping CustomSmartPointer with data `{}`!", self.data);    }} fn main() {    let c = CustomSmartPointer {        data: String::from("my stuff"),    };    let d = CustomSmartPointer {        data: String::from("other stuff"),    };    println!("CustomSmartPointers created.");}
ターミナル
CustomSmartPointers created.Dropping CustomSmartPointer with data `other stuff`!Dropping CustomSmartPointer with data `my stuff`!

変数は、作られたのと逆の順番で drop されます。d が先、c が後です。

std::mem::drop で早めに片付ける

ロックを解放したいときなど、スコープの終わりを待たずに値を片付けたいことがあります。ただし、Drop の drop メソッドを直接呼ぶことはできません。

Rustコンパイルエラーになる
fn main() {    let c = CustomSmartPointer { data: String::from("some data") };    c.drop();   // error[E0040]: explicit use of destructor method}

直接呼べてしまうと、スコープの終わりで Rust がもう一度 drop を呼んで、二重解放になるからです。代わりに、標準ライブラリの std::mem::drop 関数を使います（prelude に入っているので drop で呼べます）。

Rust
fn main() {    let c = CustomSmartPointer {        data: String::from("some data"),    };    println!("CustomSmartPointer created.");    drop(c);   // c の所有権を渡す。関数の終わりで drop される    println!("CustomSmartPointer dropped before the end of main.");}
ターミナル
CustomSmartPointer created.Dropping CustomSmartPointer with data `some data`!CustomSmartPointer dropped before the end of main.

drop 関数の中身は実は空っぽです。c の所有権を受け取り、関数の終わりで（普通のルールどおり）drop されるだけ。所有権のシステムが、drop が 1 回しか呼ばれないことを保証しているのです。

15.5Rc<T>：参照カウント

ほとんどの場合、所有者は 1 つに決まります。でも、1 つの値に複数の所有者がいるのが自然な場面もあります。例えばグラフ構造では、複数の辺が同じノードを指し、そのノードはすべての辺がなくなるまで片付けてはいけません。

Rc<T>（reference counting、参照カウント）は、値への参照の数を数えておき、数がゼロになったときに値を片付けます。テレビのある居間を想像してください。最初の人が入ってきてテレビをつけ、他の人も入ってきて見ます。最後の人が部屋を出るときにテレビを消します。誰かが見ている間に消してはいけません。

注意Rc はシングルスレッド専用

Rc<T> は、1 つのスレッドの中だけで使えます。複数のスレッドで参照カウントを使う方法は、第 16 章で扱います。

Rc でデータを共有する

2 つのリスト b と c が、3 つ目のリスト a を共有する構造を作りたいとします。

Box では、これは書けません。

Rustコンパイルエラーになる
enum List {    Cons(i32, Box<List>),    Nil,} use crate::List::{Cons, Nil}; fn main() {    let a = Cons(5, Box::new(Cons(10, Box::new(Nil))));    let b = Cons(3, Box::new(a));   // a は b にムーブされた    let c = Cons(4, Box::new(a));   // error[E0382]: use of moved value: `a`}

Box を Rc に変えます。

Rust
enum List {    Cons(i32, Rc<List>),    Nil,} use crate::List::{Cons, Nil};use std::rc::Rc; fn main() {    let a = Rc::new(Cons(5, Rc::new(Cons(10, Rc::new(Nil)))));    let b = Cons(3, Rc::clone(&a));    let c = Cons(4, Rc::clone(&a));}

Rc::clone(&a) は、a のデータを深くコピーするのではなく、参照カウントを 1 増やすだけです。a.clone() と書くこともできますが、慣習として Rc::clone と書き、「これは安いクローンだ」と見分けられるようにします。

参照カウントの増減を見る

Rust
fn main() {    let a = Rc::new(Cons(5, Rc::new(Cons(10, Rc::new(Nil)))));    println!("count after creating a = {}", Rc::strong_count(&a));    let b = Cons(3, Rc::clone(&a));    println!("count after creating b = {}", Rc::strong_count(&a));    {        let c = Cons(4, Rc::clone(&a));        println!("count after creating c = {}", Rc::strong_count(&a));    }    println!("count after c goes out of scope = {}", Rc::strong_count(&a));}
ターミナル
count after creating a = 1count after creating b = 2count after creating c = 3count after c goes out of scope = 2

Rc<T> が共有できるのは不変参照だけです。複数の所有者がいる値を、それぞれが自由に書き換えられたら、データ競合や不整合が起きてしまいます。でも、書き換えたいこともありますよね。そこで登場するのが、次の RefCell<T> です。

15.6RefCell<T> と内部可変性

内部可変性（interior mutability）は、データへの不変参照しかなくても、そのデータを変更できるようにする設計パターンです。普通の借用ルールでは許されないことなので、内部では unsafe なコード（第 19 章）を使い、借用ルールの検査をコンパイル時から実行時に移しています。

借用ルールをいつ検査するか

参照・Box<T>RefCell<T>
借用ルールの検査コンパイル時実行時
違反したときコンパイルエラーパニック
利点実行時のコストなし。早く見つかるコンパイラが正しいと証明できない、でも実は正しいコードを書ける

コンパイラの検査は保守的です。正しいプログラムでも、正しさを証明できなければ拒否します。プログラマが「このコードは借用ルールを守っている」と確信できるのに、コンパイラを納得させられないとき、RefCell<T> を使います。

Rc<T> と同じく、RefCell<T> もシングルスレッド専用です。

3 つの型の使い分け

使いどころ：モックオブジェクト

テストのときに、本物の代わりに使うモックオブジェクトを考えます。値が上限にどれだけ近いかを監視して、メッセージを送るライブラリです。

src/lib.rs
pub trait Messenger {    fn send(&self, msg: &str);   // &self を取る（不変）} pub struct LimitTracker<'a, T: Messenger> {    messenger: &'a T,    value: usize,    max: usize,} impl<'a, T> LimitTracker<'a, T>where    T: Messenger,{    pub fn new(messenger: &'a T, max: usize) -> LimitTracker<'a, T> {        LimitTracker { messenger, value: 0, max }    }     pub fn set_value(&mut self, value: usize) {        self.value = value;         let percentage_of_max = self.value as f64 / self.max as f64;         if percentage_of_max >= 1.0 {            self.messenger.send("Error: You are over your quota!");        } else if percentage_of_max >= 0.9 {            self.messenger.send("Urgent warning: You've used up over 90% of your quota!");        } else if percentage_of_max >= 0.75 {            self.messenger.send("Warning: You've used up over 75% of your quota!");        }    }}

テストでは、send が呼ばれたときにメッセージを記録するだけのモックを作りたいところです。でも send は &self を受け取るので、記録用のベクタを書き換えられません。

Rustコンパイルエラーになる
struct MockMessenger {    sent_messages: Vec<String>,} impl Messenger for MockMessenger {    fn send(&self, message: &str) {        self.sent_messages.push(String::from(message));        // error[E0596]: cannot borrow `self.sent_messages` as mutable,        //               as it is behind a `&` reference    }}

トレイトの定義は変えたくありません（本物の Messenger は不変でよい）。ここで RefCell を使います。

Rust
#[cfg(test)]mod tests {    use super::*;    use std::cell::RefCell;     struct MockMessenger {        sent_messages: RefCell<Vec<String>>,    }     impl MockMessenger {        fn new() -> MockMessenger {            MockMessenger {                sent_messages: RefCell::new(vec![]),            }        }    }     impl Messenger for MockMessenger {        fn send(&self, message: &str) {            self.sent_messages.borrow_mut().push(String::from(message));        }    }     #[test]    fn it_sends_an_over_75_percent_warning_message() {        let mock_messenger = MockMessenger::new();        let mut limit_tracker = LimitTracker::new(&mock_messenger, 100);         limit_tracker.set_value(80);         assert_eq!(mock_messenger.sent_messages.borrow().len(), 1);    }}

RefCell は実行時に借用を数える

RefCell<T> には、2 つのメソッドがあります。

  • borrow() — Ref<T> を返す（不変の借用）
  • borrow_mut() — RefMut<T> を返す（可変の借用）

RefCell は、今いくつの Ref と RefMut が生きているかを実行時に数えています。そして、コンパイル時と同じルール（不変の借用は何個でも、可変の借用は 1 つだけ）に違反すると、パニックします。

わざと違反してみましょう。

Rust実行時にパニックする
impl Messenger for MockMessenger {    fn send(&self, message: &str) {        let mut one_borrow = self.sent_messages.borrow_mut();        let mut two_borrow = self.sent_messages.borrow_mut();   // 2 つ目の可変借用         one_borrow.push(String::from(message));        two_borrow.push(String::from(message));    }}
ターミナル
thread 'tests::it_sends_an_over_75_percent_warning_message' panicked at src/lib.rs:60:53:already borrowed: BorrowMutError

コンパイルは通りますが、実行時にパニックします。検査を実行時に移すということは、バグの発見が開発の後の段階にずれるということでもあります。また、借用の数を数えるわずかなコストもかかります。その代わりに、不変の見た目のまま内部を変更できる柔軟さが手に入るのです。

Rc と RefCell を組み合わせる

Rc<T> は複数の所有者を許しますが、不変です。そこに RefCell<T> を入れれば、複数の所有者がいて、しかも変更できる値が作れます。

Rust
#[derive(Debug)]enum List {    Cons(Rc<RefCell<i32>>, Rc<List>),    Nil,} use crate::List::{Cons, Nil};use std::cell::RefCell;use std::rc::Rc; fn main() {    let value = Rc::new(RefCell::new(5));     let a = Rc::new(Cons(Rc::clone(&value), Rc::new(Nil)));     let b = Cons(Rc::new(RefCell::new(3)), Rc::clone(&a));    let c = Cons(Rc::new(RefCell::new(4)), Rc::clone(&a));     *value.borrow_mut() += 10;     println!("a after = {a:?}");    println!("b after = {b:?}");    println!("c after = {c:?}");}
ターミナル
a after = Cons(RefCell { value: 15 }, Nil)b after = Cons(RefCell { value: 3 }, Cons(RefCell { value: 15 }, Nil))c after = Cons(RefCell { value: 4 }, Cons(RefCell { value: 15 }, Nil))
深掘りCell と Mutex

標準ライブラリには、内部可変性を提供する型が他にもあります。Cell<T> は、中の値への参照を渡す代わりに、値をコピーして出し入れします（Copy な型向け）。Mutex<T> は、スレッドをまたいで安全に使える内部可変性を提供します。第 16 章で扱います。

15.7循環参照はメモリをリークさせる

Rust のメモリ安全の保証は、メモリリーク（解放されないメモリ）を完全に防ぐものではありません。Rc<T> と RefCell<T> を使うと、互いを指し合う参照（循環参照）が作れてしまいます。そうなると、参照カウントが決して 0 にならず、値は永遠に解放されません。

循環参照を作ってみる

Rust
use crate::List::{Cons, Nil};use std::cell::RefCell;use std::rc::Rc; #[derive(Debug)]enum List {    Cons(i32, RefCell<Rc<List>>),   // 「次のリスト」を後から差し替えられる    Nil,} impl List {    fn tail(&self) -> Option<&RefCell<Rc<List>>> {        match self {            Cons(_, item) => Some(item),            Nil => None,        }    }} fn main() {    let a = Rc::new(Cons(5, RefCell::new(Rc::new(Nil))));    println!("a initial rc count = {}", Rc::strong_count(&a));      // 1     let b = Rc::new(Cons(10, RefCell::new(Rc::clone(&a))));    println!("a rc count after b creation = {}", Rc::strong_count(&a));  // 2    println!("b initial rc count = {}", Rc::strong_count(&b));      // 1     if let Some(link) = a.tail() {        *link.borrow_mut() = Rc::clone(&b);    // a の次を b にする → 循環    }     println!("b rc count after changing a = {}", Rc::strong_count(&b));  // 2    println!("a rc count after changing a = {}", Rc::strong_count(&a));  // 2}

この状態で println!("a next item = {:?}", a.tail()); と書くと、a → b → a → … を無限にたどって表示しようとし、スタックオーバーフローします。

循環参照は、コンパイラにも RefCell の実行時検査にも捕まりません。Rc<RefCell<T>> のように参照カウントと内部可変性を組み合わせるときは、循環を作らないように設計するのはプログラマの責任です。

Weak<T> で循環を防ぐ

循環を避ける方法の 1 つは、所有するものと所有しないものを区別することです。Rc::downgrade を呼ぶと、弱い参照 Weak<T> が作れます。

Rc<T>（強い参照）Weak<T>（弱い参照）
作り方Rc::clone(&rc)Rc::downgrade(&rc)
数えるカウンタstrong_countweak_count
値の解放を妨げるか妨げる（0 になるまで解放されない）妨げない
中身の使い方そのままupgrade() で Option<Rc<T>> に（解放済みなら None）

strong_count が 0 になれば、weak_count が残っていても値は解放されます。だから、Weak で指している値は、もう存在しないかもしれません。upgrade が Option を返すのはそのためです。

木構造：親を知っている子ノード

子ノードのリストを持ち、子からも親をたどれる木を作ってみましょう。

  • 親は子を所有する（親が消えたら子も消えるべき）→ Rc
  • 子は親を所有しない（子が消えても親は残るべき）→ Weak
Rust
use std::cell::RefCell;use std::rc::{Rc, Weak}; #[derive(Debug)]struct Node {    value: i32,    parent: RefCell<Weak<Node>>,        // 親への弱い参照    children: RefCell<Vec<Rc<Node>>>,   // 子への強い参照} fn main() {    let leaf = Rc::new(Node {        value: 3,        parent: RefCell::new(Weak::new()),        children: RefCell::new(vec![]),    });     println!("leaf parent = {:?}", leaf.parent.borrow().upgrade());   // None     let branch = Rc::new(Node {        value: 5,        parent: RefCell::new(Weak::new()),        children: RefCell::new(vec![Rc::clone(&leaf)]),    });     *leaf.parent.borrow_mut() = Rc::downgrade(&branch);     println!("leaf parent = {:?}", leaf.parent.borrow().upgrade());   // Some(Node { value: 5, … })}

カウントの変化を追う

branch を内側のスコープで作り、スコープを抜けたときに何が起きるかを見てみます。

Rust
fn main() {    let leaf = Rc::new(Node {        value: 3,        parent: RefCell::new(Weak::new()),        children: RefCell::new(vec![]),    });     println!(        "leaf strong = {}, weak = {}",        Rc::strong_count(&leaf),        Rc::weak_count(&leaf),    );     {        let branch = Rc::new(Node {            value: 5,            parent: RefCell::new(Weak::new()),            children: RefCell::new(vec![Rc::clone(&leaf)]),        });         *leaf.parent.borrow_mut() = Rc::downgrade(&branch);         println!(            "branch strong = {}, weak = {}",            Rc::strong_count(&branch),            Rc::weak_count(&branch),        );         println!(            "leaf strong = {}, weak = {}",            Rc::strong_count(&leaf),            Rc::weak_count(&leaf),        );    }     println!("leaf parent = {:?}", leaf.parent.borrow().upgrade());    println!(        "leaf strong = {}, weak = {}",        Rc::strong_count(&leaf),        Rc::weak_count(&leaf),    );}
ターミナル
leaf strong = 1, weak = 0branch strong = 1, weak = 1leaf strong = 2, weak = 0leaf parent = Noneleaf strong = 1, weak = 0

カウントの管理はすべて Rc と Weak が自動で行います。「所有する方向」と「所有しない方向」を型で表しておけば、循環参照とリークを避けられるのです。

15.8この章のまとめ

型何を解決するか注意点
Box<T>大きさの決まらない型（再帰）、ヒープへの移動なし。ポインタ 1 つ分のコストだけ
Derefスマートポインタを参照のように使う参照外し型強制はコンパイル時に解決
Dropスコープの終わりの片付け早めに片付けるなら drop(x)
Rc<T>1 つの値に複数の所有者不変のみ。シングルスレッド専用
RefCell<T>不変参照越しの変更（内部可変性）違反は実行時にパニック
Weak<T>循環参照によるリークを防ぐupgrade で Option として取り出す
