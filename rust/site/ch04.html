第 4 章

所有権を理解する

Rust を Rust たらしめている仕組み、所有権。GC なしでメモリ安全を保証するためのルールを、スタックとヒープの絵を動かしながら理解します。

4 節図 15 点目安 90 分

4.1所有権とは何か

どんなプログラムも、動いている間はメモリを使います。そして使い終わったメモリは、いつか片付けなければなりません。プログラミング言語は、この「片付け」をどうするかで大きく 3 つに分かれます。

方式代表的な言語片付けるのは誰か弱点
手動管理C, C++プログラマが free を書く忘れる・2 回呼ぶ・解放後に使う
ガベージコレクションJava, Go, Python実行時に GC が探して回収する実行時のコスト・停止
所有権Rustコンパイラが「ここで解放」と決めて埋め込むルールを覚える必要がある

Rust の方式では、コンパイラが「このメモリの持ち主（所有者）は誰か」を追いかけ、所有者が使えなくなった瞬間に片付けるコードを自動で差し込みます。実行時に余計な仕組みは動きません。その代わり、プログラマは所有権のルールに従ってコードを書く必要があります。ルールに違反したコードは、コンパイルが通りません。

最初はこのルールが窮屈に感じられるはずです。でも慣れてくると、「コンパイルが通ったなら、メモリまわりのバグはない」という安心感に変わります。

まずスタックとヒープを知る

所有権を理解するには、メモリの 2 つの置き場所、スタックとヒープの違いを知っておく必要があります。多くの言語ではこの違いを意識しなくても書けますが、Rust では「値がどちらに置かれるか」が言語の振る舞いに直接影響します。

スタックは、皿を積み重ねるようなデータ構造です。最後に積んだものから順に取り出します（後入れ先出し）。関数を呼ぶと、その関数のローカル変数がひとまとまり（スタックフレーム）として積まれ、関数から戻ると丸ごと取り除かれます。

  • 積む場所は常に「一番上」なので、空き場所を探す必要がなく、とても速い
  • ただし、置けるのはコンパイル時に大きさが決まっている値だけ（i32 は 4 バイト、bool は 1 バイト、など）

ヒープは、もっと自由な置き場所です。「これくらいの大きさが欲しい」と頼むと、メモリアロケータが空いている場所を探して確保し、その場所を指すポインタ（アドレス）を返します。

  • 実行中に大きさが変わるデータ（伸び縮みする文字列や配列）を置ける
  • 空き場所を探す手間があり、ポインタをたどってアクセスするので、スタックより遅い
  • 誰かが「もう要らない」と言って解放しないと、ずっと残り続ける

ポインタ自体はアドレスという固定サイズの値なので、スタックに置けます。上の図の v がまさにそれで、スタックには「ポインタ・長さ・容量」の 3 つだけがあり、本体の要素はヒープにあります。

所有権が解決しようとしている問題は、すべてヒープ側の問題です。

  • ヒープのどのデータを、コードのどこが使っているか追いかける
  • 同じデータがヒープに重複して置かれないようにする
  • 使われなくなったデータを確実に、ちょうど 1 回だけ片付ける

所有権の 3 つのルール

まず、ルールを先に示します。この章の残りは、すべてこの 3 行の説明です。

要点所有権のルール
  1. Rust の値は、それぞれ所有者（owner）と呼ばれる変数を持つ。
  2. 所有者は、同時にただ 1 つしか存在しない。
  3. 所有者がスコープから外れると、値は破棄（drop）される。

変数のスコープ

スコープとは、ある変数が有効な範囲のことです。Rust では基本的に { から } までのブロックがスコープになります。

Rust
{                      // s はまだ宣言されていないので無効    let s = "hello";   // ここから s が有効になる     // s を使った処理}                      // スコープが終わり、s はもう無効

ここでの s は文字列リテラルです。文字列リテラルはプログラムの実行ファイルの中に直接埋め込まれていて、プログラムが動いている間ずっと存在します。変更もできません。所有権の話をするには、ヒープに置かれる文字列型が必要です。

String 型

String は、ヒープ上に文字列を置く型です。リテラルと違って、実行中に長さを変えられます。

Rust
let mut s = String::from("hello"); // リテラルから String を作るs.push_str(", world!");            // 後ろに文字列を追加できるprintln!("{s}");                   // hello, world!

リテラル "hello" と String::from("hello") は、メモリ上での置かれ方がまったく違います。

メモリと確保

String が伸び縮みできるのは、中身をヒープに置いているからです。そのためには次の 2 つが必要です。

  1. 実行時に、メモリアロケータからメモリを確保する
  2. 使い終わったら、メモリをアロケータに返す

1 つ目は String::from を呼んだときに内部で行われます。これはどの言語でもほぼ同じです。問題は 2 つ目です。GC のある言語では GC が勝手にやってくれます。GC のない言語では、プログラマが自分で、ちょうど 1 回だけ解放する必要があります。早すぎても、2 回でも、忘れてもバグになります。

Rust の答えはシンプルです。所有者の変数がスコープを抜けた瞬間に、自動で解放する。

Rust
{    let s = String::from("hello"); // s が有効になる。ヒープに確保される     // s を使う}   // ここで s がスコープを抜ける → Rust が自動で drop を呼び、ヒープを解放

閉じ波かっこ } の位置で、Rust は drop という特別な関数を自動的に呼び出します。String の drop は、確保したヒープのメモリを解放します。

メモC++ を知っている人へ

この「スコープの終わりで資源を解放する」パターンは、C++ では RAII（Resource Acquisition Is Initialization）と呼ばれています。Rust はこれを言語の中心に据え、さらに「所有者は 1 つだけ」というルールを加えることで、二重解放を防いでいます。

ムーブ：所有権の移動

単純そうに見えるこのルールが、複数の変数が同じデータを扱うときに面白い振る舞いを生みます。まず整数の例です。

Rust
let x = 5;let y = x;

「5 を x に束縛し、x の値のコピーを y に束縛する」。直感どおりで、x と y の両方が 5 を持ちます。整数は大きさの決まった単純な値なので、2 つの 5 がどちらもスタックに積まれます。

では String で同じことをするとどうなるでしょうか。

Rust
let s1 = String::from("hello");let s2 = s1;

見た目は同じですが、起きることはまったく違います。ステップごとに見てみましょう。

ムーブの後で s1 を使おうとすると、コンパイルエラーになります。

Rustコンパイルエラーになる
let s1 = String::from("hello");let s2 = s1; println!("{s1}, world!");
ターミナル
error[E0382]: borrow of moved value: `s1` --> src/main.rs:5:15  |2 |     let s1 = String::from("hello");  |         -- move occurs because `s1` has type `String`, which does not implement the `Copy` trait3 |     let s2 = s1;  |              -- value moved here4 |5 |     println!("{s1}, world!");  |               ^^^^ value borrowed here after move  |help: consider cloning the value if the performance cost is acceptable  |3 |     let s2 = s1.clone();  |                ++++++++
error[E0382]ムーブされた値を借用しようとしています

メッセージが 3 か所を指していることに注目してください。どこで値が作られ（2 行目）、どこでムーブされ（3 行目）、どこで使おうとしたか（5 行目）。最後に help: で「コストを払ってもいいなら clone すれば？」と直し方まで提案しています。所有権のエラーは、たいていこの 3 点セットで読み解けます。

他の言語の「浅いコピー（shallow copy）」に似ていますが、元の変数を無効にする点が違うので、Rust ではムーブと呼びます。

ここから、Rust の設計上の大切な性質が 1 つ導かれます。Rust が勝手にデータの「深いコピー」を作ることは決してない。代入や関数呼び出しで起きるのはムーブ（＝スタック部分のコピー）だけなので、どれだけ大きな文字列でも代入のコストは一定で小さいのです。

クローン：本当にコピーしたいとき

ヒープのデータまで含めて丸ごと複製したいときは、clone メソッドを明示的に呼びます。

Rust
let s1 = String::from("hello");let s2 = s1.clone(); println!("s1 = {s1}, s2 = {s2}"); // どちらも使える

コードの中に clone が出てきたら、「ここで何かしらのコストがかかる処理をしている」という目印になります。

スタックだけのデータ：Copy

では、最初の整数の例はなぜムーブにならなかったのでしょうか。

Rust
let x = 5;let y = x;println!("x = {x}, y = {y}"); // x はまだ使える

整数のように大きさがコンパイル時に決まっていて、データ全体がスタックに収まる型は、コピーするのがとても安く済みます。深いコピーと浅いコピーの区別もありません。だから Rust は、こうした型については代入時に値をコピーし、元の変数も有効なままにします。

この性質を持つ型は Copy トレイトを実装しています（トレイトは第 10 章で詳しく扱います）。Copy な型の代表は次のとおりです。

型例
すべての整数型u32, i64, usize など
論理値型bool
浮動小数点型f64, f32
文字型char
Copy な型だけを含むタプル(i32, i32) は Copy、(i32, String) は Copy ではない
共有参照&T（後で説明）

ヒープを持つ型や、Drop（片付け処理）を実装している型は Copy にできません。「片付けが必要なものを黙ってコピーすると二重に片付けてしまう」からです。

関数と所有権

関数に値を渡すときも、代入と同じことが起きます。String を渡せばムーブ、i32 を渡せばコピーです。

Rust
fn main() {    let s = String::from("hello");  // s がスコープに入る     takes_ownership(s);             // s の値が関数にムーブされる                                    // ここから先、s は使えない     let x = 5;                      // x がスコープに入る     makes_copy(x);                  // x は Copy なので、コピーが渡される                                    // x はこの後も使える}   // x がスコープを抜ける。s はムーブ済みなので何も起きない fn takes_ownership(some_string: String) { // some_string がスコープに入る    println!("{some_string}");}   // some_string がスコープを抜け、drop が呼ばれる。ヒープが解放される fn makes_copy(some_integer: i32) {        // some_integer がスコープに入る    println!("{some_integer}");}   // some_integer がスコープを抜ける。特に何も起きない

関数を呼んだ後に s を使おうとすると、さきほどと同じ E0382 エラーになります。

戻り値と所有権

戻り値でも所有権は移動します。関数の中で作った値を返せば、所有権は呼び出し元に移ります。

Rust
fn main() {    let s1 = gives_ownership();         // 戻り値の所有権が s1 にムーブされる     let s2 = String::from("hello");     // s2 がスコープに入る     let s3 = takes_and_gives_back(s2);  // s2 は関数にムーブされ、                                        // 戻り値が s3 にムーブされる}   // s3 は drop される。s2 はムーブ済みなので何もしない。s1 は drop される fn gives_ownership() -> String {    let some_string = String::from("yours");    some_string                          // 呼び出し元にムーブして返す} fn takes_and_gives_back(a_string: String) -> String {    a_string                             // 受け取ったものをそのまま返す}

ルールは常に同じです。別の変数に代入するとムーブする。ヒープを持つ変数がスコープを抜けると、所有権が他に移っていない限り drop される。

ただ、これだけだと不便です。関数に値を渡して処理してもらうたびに、所有権を返してもらわないと元の変数がもう使えません。

Rust
fn main() {    let s1 = String::from("hello");     let (s2, len) = calculate_length(s1); // s1 を渡して、返してもらう     println!("The length of '{s2}' is {len}.");} fn calculate_length(s: String) -> (String, usize) {    let length = s.len();    (s, length) // 長さと一緒に、String も返さないといけない}

長さを知りたいだけなのに、文字列を渡して返してもらう。これはさすがに面倒です。そこで、所有権を渡さずに値を使わせる仕組みが用意されています。それが次の節の「参照」です。

4.2参照と借用

前節の最後の問題は、参照（reference）を使うと解決できます。

Rust
fn main() {    let s1 = String::from("hello");     let len = calculate_length(&s1); // s1 への参照を渡す     println!("The length of '{s1}' is {len}."); // s1 はまだ使える} fn calculate_length(s: &String) -> usize { // s は String への参照    s.len()}   // s はスコープを抜けるが、所有権を持っていないので何も drop されない

変わったのは 2 か所だけです。呼び出し側で &s1 と書き、関数の引数の型を &String にしました。この & が参照を表します。参照は、値の所有権を持たずに、その値を指し示すポインタのようなものです。

普通のポインタと違うのは、参照が指す先は、参照が生きている間ずっと有効であることを Rust が保証する点です。

参照を作ることを借用（borrowing）と呼びます。現実の世界と同じで、借りたものは使い終わったら返します。持ち主ではないので、勝手に捨てる（drop する）ことはできません。

借りたものは書き換えられない

借りた値を変更しようとするとどうなるでしょうか。

Rustコンパイルエラーになる
fn main() {    let s = String::from("hello");    change(&s);} fn change(some_string: &String) {    some_string.push_str(", world");}
ターミナル
error[E0596]: cannot borrow `*some_string` as mutable, as it is behind a `&` reference --> src/main.rs:8:5  |8 |     some_string.push_str(", world");  |     ^^^^^^^^^^^ `some_string` is a `&` reference, so the data it refers to cannot be borrowed as mutable  |help: consider changing this to be a mutable reference  |7 | fn change(some_string: &mut String) {  |                         +++

変数がデフォルトで不変なのと同じく、参照もデフォルトでは不変です。借りたものは見ることしかできません。

可変参照

変更を許したいときは、可変参照 &mut を使います。

Rust
fn main() {    let mut s = String::from("hello"); // 元の変数も mut にする     change(&mut s);                    // 可変参照を渡す    println!("{s}");                   // hello, world} fn change(some_string: &mut String) {  // 可変参照を受け取る    some_string.push_str(", world");}

可変参照には大きな制約が 1 つあります。ある値への可変参照があるとき、同じ値への参照を他に作ることはできません。

Rustコンパイルエラーになる
let mut s = String::from("hello"); let r1 = &mut s;let r2 = &mut s; println!("{r1}, {r2}");
ターミナル
error[E0499]: cannot borrow `s` as mutable more than once at a time --> src/main.rs:5:14  |4 |     let r1 = &mut s;  |              ------ first mutable borrow occurs here5 |     let r2 = &mut s;  |              ^^^^^^ second mutable borrow occurs here6 |7 |     println!("{r1}, {r2}");  |               ---- first borrow later used here

なぜこんな制約があるのでしょうか。それはデータ競合（data race）をコンパイル時に防ぐためです。データ競合は、次の 3 つが同時に起きたときに発生します。

データ競合は、実行するたびに結果が変わったり、再現が難しかったりする厄介なバグです。Rust は「書き込める参照があるなら、他の参照はない」ことを保証して、データ競合を起こすコードをそもそもコンパイルさせません。

共有参照と可変参照のルール

不変参照と可変参照を混ぜた場合も同じ考え方です。

Rustコンパイルエラーになる
let mut s = String::from("hello"); let r1 = &s;     // 問題なしlet r2 = &s;     // 問題なしlet r3 = &mut s; // 大問題 println!("{r1}, {r2}, and {r3}");

不変参照をいくつ作ってもかまいません。読むだけなら、何人で同時に読んでも誰も困らないからです。しかし、誰かが読んでいる最中に、別の誰かが書き換えてしまうのは困ります。

要点借用のルール

どの時点でも、ある値に対して作れる参照は、次のどちらか一方だけ。

  • 不変参照 &T をいくつでも（読み取り専用の共有）
  • 可変参照 &mut T をただ 1 つ（書き込みできる独占）

そして、参照は常に有効な値を指していなければならない。

参照の有効範囲は「最後に使った場所」まで

参照のスコープは、宣言した場所から始まり、最後に使われた場所で終わります。} までではありません。そのため、次のコードはコンパイルできます。

Rustコンパイルできる
let mut s = String::from("hello"); let r1 = &s;let r2 = &s;println!("{r1} and {r2}");// r1 と r2 はこれ以降使われないので、ここで借用は終わる let r3 = &mut s; // 問題なしprintln!("{r3}");

コンパイラが「参照が最後に使われた場所」を見て有効範囲を判断する仕組みは、NLL（Non-Lexical Lifetimes）と呼ばれています。

借用エラーは、最初はイライラするかもしれません。でも、それは Rust のコンパイラが「実行時に起きるはずだったバグ」を、コンパイルの時点で正確な場所つきで教えてくれているということです。

ダングリング参照

ポインタを持つ言語では、ダングリングポインタ（宙ぶらりんのポインタ）というバグがよく起きます。すでに解放されたメモリを指したままのポインタのことです。そのメモリは別の用途に再利用されているかもしれず、読み書きすると何が起きるかわかりません。

Rust では、コンパイラがダングリング参照を作らせません。

Rustコンパイルエラーになる
fn main() {    let reference_to_nothing = dangle();} fn dangle() -> &String {             // String への参照を返そうとしている    let s = String::from("hello");   // s は新しい String     &s                               // s への参照を返す}   // ここで s はスコープを抜けて drop される。ヒープは解放される    // つまり返した参照は、解放済みのメモリを指してしまう
ターミナル
error[E0106]: missing lifetime specifier --> src/main.rs:5:16  |5 | fn dangle() -> &String {  |                ^ expected named lifetime parameter  |  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed fromhelp: instead, you are more likely to want to return an owned value  |5 - fn dangle() -> &String {5 + fn dangle() -> String {  |
error[E0106]ライフタイム指定子がありません

「ライフタイム」は第 10 章で扱う概念ですが、help の 1 行目が核心です。この関数の戻り値は借用された値を含んでいますが、借用元となる値がありません。 関数の中で作った値への参照は、関数の外へ持ち出せないのです。直し方も提案されています。参照ではなく、値そのもの（String）を返せばよいのです。

Rustコンパイルできる
fn no_dangle() -> String {    let s = String::from("hello");    s // 所有権ごと呼び出し元にムーブする。何も解放されない}

まとめ

  • 参照には不変参照を何個でもか、可変参照を 1 つだけのどちらかしか同時に存在できない
  • 参照は常に有効な値を指していなければならない

4.3スライス型

スライスは、コレクションの全体ではなく、連続した一部分を参照するための型です。スライスも参照の一種なので、所有権を持ちません。

スライスがないと困ること

次のような関数を考えてみましょう。「スペースで区切られた文字列を受け取り、最初の単語を返す」。スペースがなければ、全体が 1 つの単語です。

スライスを知らないと、「最初の単語の終わりの位置（インデックス）」を返すくらいしかできません。

Rust
fn first_word(s: &String) -> usize {    let bytes = s.as_bytes();               // 文字列をバイトの配列として見る     for (i, &item) in bytes.iter().enumerate() {        if item == b' ' {                   // スペースを見つけたら            return i;                       // その位置を返す        }    }     s.len()                                 // スペースがなければ全体の長さ}

この関数自体は動きます。問題は、返した数値が元の文字列と切り離されていることです。

Rust
fn main() {    let mut s = String::from("hello world");     let word = first_word(&s); // word は 5     s.clear(); // 文字列を空にする     // word はまだ 5 のまま。でも s はもう空なので、    // 5 という数字にはもう意味がない。コンパイラはこれに気づけない}

word と s の状態がずれても、誰も教えてくれません。2 番目の単語を返す関数を作ろうとすると、開始位置と終了位置の 2 つの数字を管理する必要があり、ずれる危険はさらに増えます。

文字列スライス

文字列スライス &str は、String の一部への参照です。

Rust
let s = String::from("hello world"); let hello = &s[0..5];   // 0 番目から 5 番目の手前までlet world = &s[6..11];  // 6 番目から 11 番目の手前まで

[開始..終了] という範囲で指定します。開始は含み、終了は含みません。スライスの内部は、開始位置へのポインタと長さの 2 つだけでできています。

範囲の書き方にはいくつかの省略形があります。

書き方意味"hello" に対する結果
&s[0..2]0 から 2 の手前まで"he"
&s[..2]先頭から 2 の手前まで（0 は省略可）"he"
&s[3..len]3 から最後まで"lo"
&s[3..]3 から最後まで（終わりは省略可）"lo"
&s[..]全体"hello"
注意範囲はバイト単位

スライスの範囲はバイトの位置で指定します。英数字は 1 文字 1 バイトですが、日本語のひらがなや漢字は UTF-8 で 1 文字 3 バイトです。&"こんにちは"[0..1] のように文字の途中で切ろうとすると、プログラムはパニックします。文字列と UTF-8 については第 8 章で詳しく扱います。

スライスを使って first_word を書き直しましょう。

Rust
fn first_word(s: &String) -> &str {    let bytes = s.as_bytes();     for (i, &item) in bytes.iter().enumerate() {        if item == b' ' {            return &s[0..i];   // 最初の単語のスライスを返す        }    }     &s[..]                     // スペースがなければ全体}

戻り値は元のデータと結びついた 1 つの値になりました。そして、先ほどのバグがコンパイルエラーとして捕まるようになります。

Rustコンパイルエラーになる
fn main() {    let mut s = String::from("hello world");     let word = first_word(&s);  // 不変の借用が始まる     s.clear();                  // エラー！ 可変の借用が必要     println!("the first word is: {word}"); // 不変の借用がまだ生きている}
ターミナル
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable  --> src/main.rs:18:5   |16 |     let word = first_word(&s);   |                           -- immutable borrow occurs here17 |18 |     s.clear(); // error!   |     ^^^^^^^^^ mutable borrow occurs here19 |20 |     println!("the first word is: {word}");   |                                  ------ immutable borrow later used here

clear は文字列を空にするので、可変参照 &mut self を必要とします。しかし word という不変参照がまだ使われる予定なので、借用ルール違反になります。数値を返していたときは実行時まで気づけなかったバグが、スライスを使うとコンパイル時に見つかるのです。

文字列リテラルの正体はスライス

ここで、文字列リテラルの型の謎が解けます。

Rust
let s = "Hello, world!";

s の型は &str です。バイナリの中に埋め込まれた文字列データの、その場所を指すスライスなのです。&str は不変参照なので、文字列リテラルも変更できません。

引数は &str にするのが定石

first_word の引数の型は、&String より &str にしたほうが便利です。

Rust
fn first_word(s: &str) -> &str {   // 引数の型だけを変える。中身は同じ    let bytes = s.as_bytes();     for (i, &item) in bytes.iter().enumerate() {        if item == b' ' {            return &s[0..i];        }    }     &s[..]}

こうすると、String からも文字列リテラルからも呼び出せます。

Rust
let my_string = String::from("hello world"); let w1 = first_word(&my_string[0..6]);  // String のスライスlet w2 = first_word(&my_string[..]);    // String 全体のスライスlet w3 = first_word(&my_string);        // &String は自動で &str に変換される let my_literal = "hello world";let w4 = first_word(my_literal);        // リテラルはもともと &str

&String から &str への自動変換は参照外し型強制（deref coercion）という仕組みで、第 15 章で扱います。

他のスライス

スライスは文字列専用ではありません。配列の一部も同じように参照できます。

Rust
let a = [1, 2, 3, 4, 5]; let slice = &a[1..3];          // 型は &[i32] assert_eq!(slice, &[2, 3]);

この種類のスライスは、第 8 章で扱うベクタなど、さまざまなコレクションで使われます。

4.4この章のまとめ

所有権、借用、スライスという 3 つの概念で、Rust はコンパイル時にメモリ安全を保証しています。

状況起きること元の変数
let b = a;（a が String）ムーブ使えなくなる
let b = a;（a が i32）コピー使える
let b = a.clone();ヒープまで複製使える
let b = &a;不変の借用使える（読むだけ）
let b = &mut a;可変の借用b を使い終わるまで触れない

Rust の他の部分も、すべてこの所有権の上に組み立てられています。この先の章でも何度も出てくるので、迷ったらこの章の図に戻ってきてください。次の章では、複数のデータをまとめる構造体を見ていきます。
