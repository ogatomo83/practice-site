第 11 章

自動テストを書く

型システムが保証できるのは「型が正しいこと」まで。「やりたいことを正しくやっているか」はテストで確かめます。テストの書き方、走らせ方、そしてユニットテストと結合テストの置き場所を整理します。

4 節図 5 点目安 50 分

11.1テストの書き方

Rust の型システムは多くのバグを防いでくれますが、すべてではありません。「2 を足す」関数が実は 10 を足していても、型は正しいのでコンパイラは何も言いません。そこでテストを書きます。

テストは、テスト対象のコードが期待どおりに動くかを確かめる Rust の関数です。テスト関数の本体は、たいてい次の 3 つの動作をします。

テスト関数の構造

Rust のテストは、#[test] 属性が付いた関数です。cargo new --lib でライブラリを作ると、テストの雛形が最初から入っています。

ターミナル
$ cargo new adder --lib
src/lib.rs
pub fn add(left: u64, right: u64) -> u64 {    left + right} #[cfg(test)]mod tests {    use super::*;     #[test]    fn it_works() {        let result = add(2, 2);        assert_eq!(result, 4);    }}

cargo test で、すべてのテストを実行します。

ターミナル
$ cargo test   Compiling adder v0.1.0 (file:///projects/adder)    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.57s     Running unittests src/lib.rs (target/debug/deps/adder-92948b65e88960b4) running 1 testtest tests::it_works ... ok test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s    Doc-tests adder running 0 tests test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

出力の各部分の意味は次のとおりです。

部分意味
test tests::it_works ... okテストの名前と結果
1 passed; 0 failed成功・失敗の数
0 ignored#[ignore] で無視されたテスト（後述）
0 measuredベンチマークテスト（nightly 限定）
0 filtered out名前で絞り込まれて実行されなかったテスト
Doc-tests adderドキュメントの中のコード例のテスト（第 14 章）

テストが失敗するとき

テストは、テスト関数の中でパニックが起きると失敗します。各テストは別々のスレッドで実行され、メインスレッドはテスト用のスレッドが死んだことを検知して、そのテストを失敗とします。

Rust
#[cfg(test)]mod tests {    use super::*;     #[test]    fn exploration() {        let result = add(2, 2);        assert_eq!(result, 4);    }     #[test]    fn another() {        panic!("Make this test fail");    }}
ターミナル
running 2 teststest tests::another ... FAILEDtest tests::exploration ... ok failures: ---- tests::another stdout ----thread 'tests::another' panicked at src/lib.rs:17:9:Make this test failnote: run with `RUST_BACKTRACE=1` environment variable to display a backtrace  failures:    tests::another test result: FAILED. 1 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

assert! マクロ

assert! は、引数が true なら何もせず、false なら panic! を呼びます。第 5 章の Rectangle の can_hold をテストしてみましょう。

src/lib.rs
#[derive(Debug)]struct Rectangle {    width: u32,    height: u32,} impl Rectangle {    fn can_hold(&self, other: &Rectangle) -> bool {        self.width > other.width && self.height > other.height    }} #[cfg(test)]mod tests {    use super::*;     // 外側のモジュールの要素をすべて持ち込む     #[test]    fn larger_can_hold_smaller() {        let larger = Rectangle { width: 8, height: 7 };        let smaller = Rectangle { width: 5, height: 1 };         assert!(larger.can_hold(&smaller));    }     #[test]    fn smaller_cannot_hold_larger() {        let larger = Rectangle { width: 8, height: 7 };        let smaller = Rectangle { width: 5, height: 1 };         assert!(!smaller.can_hold(&larger));    }}

tests は普通のモジュールなので、外側のコードを使うにはパスが必要です。use super::*; は、親モジュールの要素をすべて持ち込みます（glob を使うのが慣習になっている数少ない場面です）。can_hold が非公開でも、子モジュールから親の要素は見えるのでテストできます。

assert_eq! と assert_ne!

値が等しいかどうかを確かめるなら、assert_eq!（等しい）と assert_ne!（等しくない）が便利です。失敗したときに、両方の値を表示してくれます。

Rust
pub fn add_two(a: u64) -> u64 {    a + 3   // わざとバグを入れる} #[cfg(test)]mod tests {    use super::*;     #[test]    fn it_adds_two() {        let result = add_two(2);        assert_eq!(result, 4);    }}
ターミナル
---- tests::it_adds_two stdout ----thread 'tests::it_adds_two' panicked at src/lib.rs:12:9:assertion `left == right` failed  left: 5 right: 4

assert!(result == 4) だと「失敗した」としかわかりませんが、assert_eq! は実際の値が 5 だったことまで教えてくれます。Rust では、2 つの引数を expected / actual ではなく left / right と呼ぶので、どちらの順番で書いてもかまいません。

比べる値の型は、PartialEq（比較）と Debug（表示）を実装している必要があります。自分で定義した構造体なら、#[derive(PartialEq, Debug)] を付けます。

失敗メッセージを付ける

assert! などの必須引数の後ろに、format! と同じ書き方で独自のメッセージを付けられます。

Rust
pub fn greeting(name: &str) -> String {    String::from("Hello!")   // バグ：名前を入れ忘れた} #[test]fn greeting_contains_name() {    let result = greeting("Carol");    assert!(        result.contains("Carol"),        "Greeting did not contain name, value was `{result}`"    );}
ターミナル
thread 'tests::greeting_contains_name' panicked at src/lib.rs:12:9:Greeting did not contain name, value was `Hello!`

実際の値が表示されるので、何が悪かったのかすぐわかります。

should_panic でパニックを確かめる

「この入力ではパニックするべき」ということも確かめられます。第 9 章の Guess を使います。

Rust
pub struct Guess {    value: i32,} impl Guess {    pub fn new(value: i32) -> Guess {        if value < 1 {            panic!("Guess value must be greater than or equal to 1, got {value}.");        } else if value > 100 {            panic!("Guess value must be less than or equal to 100, got {value}.");        }         Guess { value }    }} #[cfg(test)]mod tests {    use super::*;     #[test]    #[should_panic(expected = "less than or equal to 100")]    fn greater_than_100() {        Guess::new(200);    }}

#[should_panic] を付けると、パニックすれば成功、しなければ失敗になります。ただ、それだけだと意図しない理由でパニックしても成功してしまいます。expected を付けると、パニックのメッセージにその文字列が含まれているかまで確かめられます。

Result を返すテスト

テスト関数は Result<(), E> を返すこともできます。パニックの代わりに Err を返すと失敗です。

Rust
#[test]fn it_works() -> Result<(), String> {    let result = add(2, 2);     if result == 4 {        Ok(())    } else {        Err(String::from("two plus two does not equal four"))    }}

こうすると、テストの本体で ? 演算子が使えます。途中のどれかが Err を返したら、そこでテストが失敗します。なお、Result を返すテストには #[should_panic] は使えません。

11.2テストの実行を制御する

cargo test には、2 種類のオプションを渡せます。-- の前は cargo test 自体に、後はできあがったテストバイナリに渡されます。

ターミナル
$ cargo test --help          # cargo test のオプション$ cargo test -- --help       # テストバイナリのオプション

並列か、順番か

テストは、デフォルトで複数のスレッドで並列に実行されます。速く終わる反面、テスト同士が同じファイルや環境変数などを共有していると、互いに干渉することがあります。

1 つずつ順番に実行したいなら、スレッド数を 1 にします。

ターミナル
$ cargo test -- --test-threads=1

出力を表示する

テストが成功すると、テストの中の println! の出力は捕捉されて表示されません。成功したテストの出力も見たいなら、--show-output を付けます。

ターミナル
$ cargo test -- --show-output

名前でテストを絞り込む

cargo test に名前を渡すと、その文字列を含むテストだけが実行されます。

Rust
#[cfg(test)]mod tests {    use super::*;     #[test]    fn add_two_and_two() { assert_eq!(4, add_two(2)); }     #[test]    fn add_three_and_two() { assert_eq!(5, add_two(3)); }     #[test]    fn one_hundred() { assert_eq!(102, add_two(100)); }}
コマンド実行されるテスト
cargo test3 つすべて
cargo test one_hundredone_hundred だけ
cargo test add名前に add を含む 2 つ
cargo test tests::モジュール tests の中のすべて

時間のかかるテストを無視する

Rust
#[test]#[ignore]fn expensive_test() {    // 1 時間かかる処理}

#[ignore] を付けたテストは、普段の cargo test では実行されません。

コマンド実行されるテスト
cargo test無視されていないものだけ
cargo test -- --ignored無視されたものだけ
cargo test -- --include-ignoredすべて

11.3テストの体系化

Rust のコミュニティでは、テストを 2 種類に分けて考えます。

ユニットテスト結合テスト
目的1 つの部品を単独でテスト複数の部品が一緒に正しく動くかをテスト
置き場所テスト対象と同じファイル（src/ の中）tests/ ディレクトリ
非公開の関数テストできるテストできない（公開 API だけ）
視点内側から外部のコードと同じ、外側から

ユニットテスト

ユニットテストは、テスト対象のコードと同じファイルに tests という名前のモジュールを作り、そこに書くのが慣習です。

#[cfg(test)]

#[cfg(test)] は、「cargo test のときだけこのモジュールをコンパイルする」という意味です。cargo build のときはテストのコードがコンパイルされないので、時間も節約でき、できあがるファイルも小さくなります。cfg は configuration（設定）の略です。

非公開関数のテスト

非公開の関数をテストすべきかどうかは、議論の分かれるところです。他の言語では難しいこともありますが、Rust では簡単にできます。

src/lib.rs
pub fn add_two(a: u64) -> u64 {    internal_adder(a, 2)} fn internal_adder(left: u64, right: u64) -> u64 {   // pub ではない    left + right} #[cfg(test)]mod tests {    use super::*;     #[test]    fn internal() {        let result = internal_adder(2, 2);   // 子モジュールから親の非公開関数が見える        assert_eq!(result, 4);    }}

結合テスト

結合テストは、ライブラリの完全に外側にあり、他の利用者と同じように公開 API だけを使います。プロジェクトの最上位に tests ディレクトリを作ります。

tests/integration_test.rs
use adder::add_two; #[test]fn it_adds_two() {    let result = add_two(2);    assert_eq!(result, 4);}

tests ディレクトリの中の各ファイルは、それぞれが独立したクレートとしてコンパイルされます。そのため、use adder::add_two; でライブラリを持ち込む必要があります。また、Cargo が tests ディレクトリを特別扱いするので、#[cfg(test)] は不要です。

ターミナル
$ cargo test     Running unittests src/lib.rs (target/debug/deps/adder-1082c4b063a8fbe6) running 1 testtest tests::internal ... ok test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s      Running tests/integration_test.rs (target/debug/deps/integration_test-1082c4b063a8fbe6) running 1 testtest it_adds_two ... ok test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s    Doc-tests adder running 0 tests

特定の結合テストのファイルだけを実行するには、--test にファイル名を渡します。

ターミナル
$ cargo test --test integration_test

結合テストで使う共通コード

複数の結合テストのファイルで使う補助関数（初期化処理など）を tests/common.rs に置くと、common.rs 自体がテストのクレートとみなされ、テスト結果に「running 0 tests」という余計な項目が出てしまいます。

これを避けるには、tests/common/mod.rs という古い形式の名前で置きます。tests/ のサブディレクトリの中のファイルは、独立したテストクレートとはみなされません。

tests/common/mod.rs
pub fn setup() {    // ライブラリのテストに必要な準備}
tests/integration_test.rs
use adder::add_two; mod common; #[test]fn it_adds_two() {    common::setup();     let result = add_two(2);    assert_eq!(result, 4);}

バイナリクレートの結合テスト

プロジェクトが src/main.rs しか持たないバイナリクレートだと、tests ディレクトリから関数を use できません。結合テストで使えるのは、ライブラリクレートの公開 API だけだからです。

これが、第 7 章で紹介した「src/main.rs は薄くして、ロジックは src/lib.rs に置く」という構成をとる理由の 1 つです。src/lib.rs の重要な機能は結合テストでテストでき、src/main.rs の数行はテストするまでもない、という形にできます。
