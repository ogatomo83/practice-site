第 16 章

恐れずに並行性を扱う

スレッド、メッセージパッシング、共有状態。並行プログラミングの典型的なバグの多くを、Rust は所有権と型システムによってコンパイル時に捕まえます。「恐れることのない並行性（fearless concurrency）」の仕組みを見ていきます。

6 節図 9 点目安 90 分

16.1並行性と所有権

並行（concurrent）プログラミングはプログラムの異なる部分が独立して実行されること、並列（parallel）プログラミングは異なる部分が同時に実行されることです。マルチコアの CPU が当たり前になった今、どちらもますます重要になっています。

並行プログラミングは、昔から難しく、バグを生みやすいものとされてきました。Rust の開発チームは当初、メモリ安全と並行性の問題は別々の問題だと考えていました。ところが、所有権と型システムが、両方の問題を解決する強力な道具になることがわかったのです。

多くの並行性のバグは、実行時にしか現れず、再現も難しいものです。Rust ではそれらがコンパイルエラーになります。バグを本番環境で追いかける代わりに、書いている最中に直せるのです。

16.2スレッドでコードを同時に動かす

今の OS では、プログラムはプロセスの中で動き、プロセスの中では複数のスレッドを同時に動かせます。計算を複数のスレッドに分けると性能が上がりますが、次のような問題も生まれます。

  • 競合状態（race condition）：スレッドがデータや資源に、予測できない順番でアクセスする
  • デッドロック：2 つのスレッドが互いを待ち合い、どちらも先に進めなくなる
  • 特定の状況でしか起きず、再現も修正も難しいバグ

Rust の標準ライブラリは、OS のスレッド 1 つにつき言語のスレッド 1 つを対応させる 1:1 モデルを使っています。

spawn で新しいスレッドを作る

thread::spawn に、新しいスレッドで実行したいコードをクロージャで渡します。

src/main.rs
use std::thread;use std::time::Duration; fn main() {    thread::spawn(|| {        for i in 1..10 {            println!("hi number {i} from the spawned thread!");            thread::sleep(Duration::from_millis(1));        }    });     for i in 1..5 {        println!("hi number {i} from the main thread!");        thread::sleep(Duration::from_millis(1));    }}
ターミナル
hi number 1 from the main thread!hi number 1 from the spawned thread!hi number 2 from the main thread!hi number 2 from the spawned thread!hi number 3 from the main thread!hi number 3 from the spawned thread!hi number 4 from the main thread!hi number 4 from the spawned thread!hi number 5 from the spawned thread!

出力の順番は実行するたびに変わります。そして、生成したスレッドは 9 まで数えるはずなのに、5 で止まっています。メインスレッドが終わると、生成したスレッドもすべて終了させられるからです。

join で終わるのを待つ

thread::spawn は JoinHandle を返します。その join メソッドを呼ぶと、そのスレッドが終わるまで今のスレッドを待たせ（ブロックし）ます。

src/main.rs
use std::thread;use std::time::Duration; fn main() {    let handle = thread::spawn(|| {        for i in 1..10 {            println!("hi number {i} from the spawned thread!");            thread::sleep(Duration::from_millis(1));        }    });     for i in 1..5 {        println!("hi number {i} from the main thread!");        thread::sleep(Duration::from_millis(1));    }     handle.join().unwrap();}

join を呼ぶ位置で、振る舞いが変わります。for ループの前に handle.join() を置くと、生成したスレッドが全部終わってから、メインスレッドのループが始まります。

move クロージャとスレッド

生成するスレッドで、メインスレッドのデータを使いたいことがあります。

Rustコンパイルエラーになる
use std::thread; fn main() {    let v = vec![1, 2, 3];     let handle = thread::spawn(|| {        println!("Here's a vector: {v:?}");    });     handle.join().unwrap();}
ターミナル
error[E0373]: closure may outlive the current function, but it borrows `v`, which is owned by the current function --> src/main.rs:6:32  |6 |     let handle = thread::spawn(|| {  |                                ^^ may outlive borrowed value `v`7 |         println!("Here's a vector: {v:?}");  |                                     - `v` is borrowed here  |help: to force the closure to take ownership of `v` (and any other referenced variables), use the `move` keyword  |6 |     let handle = thread::spawn(move || {  |                                ++++
error[E0373]クロージャが現在の関数より長生きするかもしれないのに、v を借用しています

クロージャは v を読むだけなので、不変の借用でキャプチャしようとします。でも、生成したスレッドがいつまで動くのか、Rust にはわかりません。メインスレッドが先に v を drop してしまったら、参照はダングリングになります。

例えば、こんなことができてしまうと困ります。

Rustコンパイルエラーになる
fn main() {    let v = vec![1, 2, 3];     let handle = thread::spawn(|| {        println!("Here's a vector: {v:?}");    });     drop(v);   // スレッドが v を使っている最中かもしれないのに！     handle.join().unwrap();}

help のとおり、move を付けて、v の所有権をクロージャ（＝新しいスレッド）に移します。

Rust
use std::thread; fn main() {    let v = vec![1, 2, 3];     let handle = thread::spawn(move || {        println!("Here's a vector: {v:?}");    });     handle.join().unwrap();}

move を付けた状態で drop(v) を書くと、今度は「ムーブされた値を使っている」という E0382 エラーになります。所有権のルールが、どちらの書き方でもプログラムを守ってくれます。

16.3メッセージパッシングでデータを送る

安全な並行性を実現する方法として人気があるのがメッセージパッシングです。スレッド同士がデータを入れたメッセージを送り合って、やりとりします。Go 言語のドキュメントには、こんな標語があります。

メモリを共有することでやりとりするのではなく、やりとりすることでメモリを共有しよう。

Rust の標準ライブラリは、メッセージパッシングのためにチャネル（channel）を提供しています。チャネルは川のようなもので、上流でアヒルのおもちゃを流すと、下流に届きます。チャネルには送信側（transmitter）と受信側（receiver）があり、どちらかが drop されると、チャネルは閉じられます。

src/main.rs
use std::sync::mpsc;use std::thread; fn main() {    let (tx, rx) = mpsc::channel();     thread::spawn(move || {        let val = String::from("hi");        tx.send(val).unwrap();    });     let received = rx.recv().unwrap();    println!("Got: {received}");}

mpsc は multiple producer, single consumer（複数の生産者、1 つの消費者）の略です。送信側は複数作れますが、受信側は 1 つだけです。mpsc::channel() は (送信側, 受信側) のタプルを返します。

メソッド動作
tx.send(val)値を送る。受信側がすでに drop されていたら Err
rx.recv()値が届くまで待つ。すべての送信側が drop されたら Err
rx.try_recv()待たずにすぐ戻る。値があれば Ok、なければ Err

send は所有権を移す

値を送った後で、その値を使おうとするとどうなるでしょうか。

Rustコンパイルエラーになる
thread::spawn(move || {    let val = String::from("hi");    tx.send(val).unwrap();    println!("val is {val}");   // 送った後に使う});
ターミナル
error[E0382]: borrow of moved value: `val`  --> src/main.rs:10:26   |8  |         let val = String::from("hi");   |             --- move occurs because `val` has type `String`, which does not implement the `Copy` trait9  |         tx.send(val).unwrap();   |                 --- value moved here10 |         println!("val is {val}");   |                          ^^^^^ value borrowed here after move

送った値は、受信側のスレッドが書き換えたり drop したりしているかもしれません。send は引数の所有権を取って受信側に渡すので、送った後に使おうとするとコンパイルエラーになります。「送った後に触ってしまう」というバグが、構造的に起こり得ないのです。

複数の値を送り、受信側をイテレータとして使う

src/main.rs
use std::sync::mpsc;use std::thread;use std::time::Duration; fn main() {    let (tx, rx) = mpsc::channel();     thread::spawn(move || {        let vals = vec![            String::from("hi"),            String::from("from"),            String::from("the"),            String::from("thread"),        ];         for val in vals {            tx.send(val).unwrap();            thread::sleep(Duration::from_secs(1));        }    });     for received in rx {          // 受信側をイテレータとして使う        println!("Got: {received}");    }}

rx を for ループで回すと、値が届くたびに 1 つずつ処理し、チャネルが閉じたら（送信側のスレッドが終わって tx が drop されたら）ループが終わります。1 秒おきに 1 行ずつ表示されるのがわかります。

送信側をクローンして複数の生産者にする

tx.clone() で送信側を増やせます。

src/main.rs
let (tx, rx) = mpsc::channel(); let tx1 = tx.clone();thread::spawn(move || {    let vals = vec![        String::from("hi"),        String::from("from"),        String::from("the"),        String::from("thread"),    ];     for val in vals {        tx1.send(val).unwrap();        thread::sleep(Duration::from_secs(1));    }}); thread::spawn(move || {    let vals = vec![        String::from("more"),        String::from("messages"),        String::from("for"),        String::from("you"),    ];     for val in vals {        tx.send(val).unwrap();        thread::sleep(Duration::from_secs(1));    }}); for received in rx {    println!("Got: {received}");}

2 つのスレッドからのメッセージが混ざって届きます。順番は実行のたびに変わります。

16.4状態共有による並行性

メッセージパッシングは 1 つの方法ですが、唯一の方法ではありません。複数のスレッドが同じデータにアクセスする方法もあります。

チャネルは「単一所有権」に似ています。値を送ったら、もう使えません。一方、メモリの共有は「複数所有権」に似ていて、複数のスレッドが同時に同じメモリを使えます。第 15 章で見たとおり、複数所有権は便利ですが、管理が複雑になります。ここでも Rust の型システムが助けになります。

Mutex で一度に 1 つのスレッドだけにアクセスさせる

ミューテックス（mutex）は、mutual exclusion（相互排他）の略で、一度に 1 つのスレッドだけがデータにアクセスできるようにする仕組みです。データにアクセスしたいスレッドは、まずロック（lock）を取得する必要があります。

パネルディスカッションでマイクが 1 本しかない状況を想像してください。話したい人はマイクを要求し、話し終わったら次の人に渡します。マイクを返し忘れると、誰も話せなくなります。

ミューテックスは難しいことで有名です。理由は 2 つあります。

  1. データを使う前に、ロックの取得を試みなければならない
  2. 使い終わったら、ロックを解放しなければならない

Rust では、型システムと所有権のおかげで、ロックの取得と解放を間違えようがありません。

src/main.rs
use std::sync::Mutex; fn main() {    let m = Mutex::new(5);     {        let mut num = m.lock().unwrap();        *num = 6;    }   // num がスコープを抜けると、ロックは自動で解放される     println!("m = {m:?}");}
  • m の型は Mutex<i32> で、i32 ではありません。だから、lock を呼ばずに中の値を使うことは型の上で不可能です。ロックのかけ忘れが起こり得ません
  • lock は LockResult<MutexGuard<i32>> を返します。ロックを持っている他のスレッドがパニックしていると Err になります
  • MutexGuard は第 15 章のスマートポインタです。Deref で中身を参照でき、Drop でロックを解放します。だから、ロックの解放し忘れも起こり得ません

複数のスレッドで Mutex を共有する

10 個のスレッドで、1 つのカウンタを 1 ずつ増やしてみましょう。

Rustコンパイルエラーになる
use std::sync::Mutex;use std::thread; fn main() {    let counter = Mutex::new(0);    let mut handles = vec![];     for _ in 0..10 {        let handle = thread::spawn(move || {            let mut num = counter.lock().unwrap();             *num += 1;        });        handles.push(handle);    }     for handle in handles {        handle.join().unwrap();    }     println!("Result: {}", *counter.lock().unwrap());}
ターミナル
error[E0382]: borrow of moved value: `counter`  --> src/main.rs:21:29   |5  |     let counter = Mutex::new(0);   |         ------- move occurs because `counter` has type `Mutex<i32>`, which does not implement the `Copy` trait...8  |     for _ in 0..10 {   |     -------------- inside of this loop9  |         let handle = thread::spawn(move || {   |                                    ------- value moved into closure here, in previous iteration of loop

1 回目のループで counter が最初のスレッドにムーブされたので、2 回目以降は使えません。複数の所有者が必要です。第 15 章の Rc<T> を使えばよいでしょうか。

use std::rc::Rc;use std::sync::Mutex;use std::thread; fn main() {    let counter = Rc::new(Mutex::new(0));    let mut handles = vec![];     for _ in 0..10 {        let counter = Rc::clone(&counter);        let handle = thread::spawn(move || {            let mut num = counter.lock().unwrap();            *num += 1;        });        handles.push(handle);    }    // --snip--}
ターミナル
error[E0277]: `Rc<Mutex<i32>>` cannot be sent between threads safely  --> src/main.rs:11:36   |11 |           let handle = thread::spawn(move || {   |                        ------------- ^------   |                        |             |   |  ______________________|_____________within this `{closure@src/main.rs:11:36: 11:43}`   | |                      |   | |                      required by a bound introduced by this call12 | |             let mut num = counter.lock().unwrap();13 | |             *num += 1;14 | |         });   | |_________^ `Rc<Mutex<i32>>` cannot be sent between threads safely   |   = help: within `{closure@src/main.rs:11:36: 11:43}`, the trait `Send` is not implemented for `Rc<Mutex<i32>>`
error[E0277]Rc<Mutex<i32>> はスレッド間で安全に送れません

重要なのは「Send トレイトが実装されていない」という部分です。Rc<T> は参照カウントを増減するときに、他のスレッドに割り込まれないようにする仕組みを持っていません。2 つのスレッドが同時にカウントを変更すると、カウントがずれて、メモリリークや解放後の使用につながります。だから Rust は、Rc をスレッドの外に送ることを型で禁止しているのです。

Arc<T>：原子的な参照カウント

Arc<T> は、Rc<T> のスレッド安全版です。A は atomic（原子的）の略で、参照カウントの増減を、他のスレッドに割り込まれない原子的な操作で行います。

なぜすべての型が最初から原子的ではないのでしょうか。スレッド安全性には性能のコストがかかるからです。1 つのスレッドの中だけで使うなら、Rc のほうが速いのです。

src/main.rs
use std::sync::{Arc, Mutex};use std::thread; fn main() {    let counter = Arc::new(Mutex::new(0));    let mut handles = vec![];     for _ in 0..10 {        let counter = Arc::clone(&counter);        let handle = thread::spawn(move || {            let mut num = counter.lock().unwrap();             *num += 1;        });        handles.push(handle);    }     for handle in handles {        handle.join().unwrap();    }     println!("Result: {}", *counter.lock().unwrap());}
ターミナル
Result: 10

RefCell/Rc と Mutex/Arc の対応

counter は不変なのに、lock で中の値の可変参照が得られました。これは RefCell<T> と同じ内部可変性です。

シングルスレッドマルチスレッド役割
Rc<T>Arc<T>複数の所有者（参照カウント）
RefCell<T>Mutex<T>不変参照越しに中身を変更する
Rc<RefCell<T>>Arc<Mutex<T>>複数の所有者が変更できる値

Rc<T> に循環参照のリスクがあったように、Mutex<T> にはデッドロックのリスクがあります。

Rust の型システムは、デッドロックまでは防げません。複数のロックを使うときは、常に同じ順番で取得するなど、設計で避ける必要があります。

16.5Send と Sync で拡張できる並行性

ここまで扱ってきた並行性の機能（スレッド、チャネル、Mutex、Arc）は、ほとんどが言語ではなく標準ライブラリのものです。言語そのものに組み込まれている並行性の概念は、std::marker の 2 つのトレイト、Send と Sync だけです。

トレイト意味実装していない代表例
Sendその型の値の所有権を、別のスレッドに移せるRc<T>（カウントの更新が原子的でない）
Syncその型の値を、複数のスレッドから参照しても安全RefCell<T>, Cell<T>（借用の検査が原子的でない）

正確には、「&T（T への不変参照）が Send なら、T は Sync」です。参照を別のスレッドに安全に送れるなら、複数のスレッドから参照しても安全だ、ということです。

Send と Sync はマーカートレイトと呼ばれ、実装すべきメソッドを持ちません。構成要素がすべて Send な型は自動的に Send になり、Sync も同じです。thread::spawn は、渡すクロージャが Send であることをトレイト境界で要求しています。だから Rc を送ろうとするとコンパイルエラーになったのです。

これらを手で実装するには unsafe なコード（第 19 章）が必要です。新しい並行性の型を自分で作らない限り、手で実装することはまずありません。そして逆に言えば、crates.io にある並行性のライブラリも、すべてこの 2 つのトレイトの上に作られていて、標準ライブラリと同じ安全性の保証を受けられます。

16.6この章のまとめ

道具用途所有権との関係

Rust では、並行性の問題の多くがコンパイル時に見つかります。コードがコンパイルできれば、データ競合や、解放したメモリへのアクセスのような、追跡しにくい種類のバグはないと考えてよいのです。これが「恐れることのない並行性」です。
