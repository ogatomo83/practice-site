第 9 章

エラー処理

Rust はエラーを「回復できないもの」と「回復できるもの」にはっきり分けます。前者は panic!、後者は Result。そして ? 演算子で、エラー処理のコードを驚くほど短く書けます。

6 節図 6 点目安 60 分

9.12 種類のエラー

ソフトウェアにエラーはつきものです。Rust は、エラーが起きる可能性をコードの中で認め、コンパイルの前に対処させる設計になっています。

多くの言語は「例外（exception）」という 1 つの仕組みで、あらゆるエラーを扱います。Rust には例外がありません。代わりに、エラーを 2 種類に分けます。

  • 回復可能なエラー：ファイルが見つからない、など。ユーザーに伝えて、操作をやり直してもらえば済む
  • 回復不能なエラー：配列の範囲外アクセスのようなバグの兆候。続行すると何が起きるかわからないので、すぐに止めるべき

9.2panic! で回復不能なエラー

コードに明らかな問題があって、どうしようもないとき、Rust は panic! マクロを使います。パニックは、配列の範囲外アクセスのような操作で自動的に起きることもあれば、自分で panic! を呼んで起こすこともできます。

Rust実行時にパニックする
fn main() {    panic!("crash and burn");}
ターミナル
$ cargo run   Compiling panic v0.1.0 (file:///projects/panic)    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.25s     Running `target/debug/panic`thread 'main' panicked at src/main.rs:2:5:crash and burnnote: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

パニックが起きると、エラーメッセージを表示し、スタックを巻き戻し（unwind）ながら片付けをして、プログラムを終了します。

巻き戻しか、即中断か

巻き戻しは丁寧ですが、そのためのコードが実行ファイルに含まれます。実行ファイルをできるだけ小さくしたいなら、Cargo.toml で即中断（abort）に切り替えられます。

Cargo.toml
[profile.release]panic = 'abort'

バックトレースを読む

ライブラリの中でパニックが起きることもあります。ベクタの範囲外アクセスの例です。

Rust実行時にパニックする
fn main() {    let v = vec![1, 2, 3];     v[99];}

C 言語なら、範囲外のメモリを読んで何かしらの値を返してしまうかもしれません（バッファオーバーリード）。攻撃者はこれを利用して、読まれてはいけないデータを読み出します。Rust は実行を止めます。

ターミナル
thread 'main' panicked at src/main.rs:4:6:index out of bounds: the len is 3 but the index is 99note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

環境変数 RUST_BACKTRACE=1 を付けて実行すると、パニックに至るまでの関数呼び出しの一覧（バックトレース）が表示されます。

ターミナル
$ RUST_BACKTRACE=1 cargo runthread 'main' panicked at src/main.rs:4:6:index out of bounds: the len is 3 but the index is 99stack backtrace:   0: rust_begin_unwind             at /rustc/.../library/std/src/panicking.rs:645:5   1: core::panicking::panic_fmt             at /rustc/.../library/core/src/panicking.rs:72:14   2: core::panicking::panic_bounds_check             at /rustc/.../library/core/src/panicking.rs:208:5   3: <usize as core::slice::index::SliceIndex<[T]>>::index             at /rustc/.../library/core/src/slice/index.rs:255:10   ...   6: panic::main             at ./src/main.rs:4:6   7: core::ops::function::FnOnce::call_once             at /rustc/.../library/core/src/ops/function.rs:250:5

読み方のコツは、上から順に見ていき、自分が書いたファイルが最初に出てくる行を探すことです。ここでは 6: panic::main at ./src/main.rs:4:6 です。それより上はライブラリの中、下は自分のコードを呼んだ側です。

9.3Result で回復可能なエラー

ほとんどのエラーは、プログラム全体を止めるほど深刻ではありません。ファイルを開こうとして存在しなかったら、ファイルを作ればいいかもしれません。そんな場面で使うのが Result です。

Rust
enum Result<T, E> {    Ok(T),    Err(E),}

T は成功したときの値の型、E は失敗したときのエラーの型です。ファイルを開く例を見てみましょう。

Rust
use std::fs::File; fn main() {    let greeting_file_result = File::open("hello.txt");}

File::open の戻り値の型は Result<File, std::io::Error> です。成功すればファイルハンドル File が、失敗すればエラーの情報 io::Error が入っています。match で場合分けしましょう。

Rust
use std::fs::File; fn main() {    let greeting_file_result = File::open("hello.txt");     let greeting_file = match greeting_file_result {        Ok(file) => file,        Err(error) => panic!("Problem opening the file: {error:?}"),    };}

エラーの種類で分岐する

ファイルが「存在しない」ならファイルを作り、それ以外の理由（権限がないなど）で失敗したならパニックする、というふうに分けたいとします。

Rust
use std::fs::File;use std::io::ErrorKind; fn main() {    let greeting_file_result = File::open("hello.txt");     let greeting_file = match greeting_file_result {        Ok(file) => file,        Err(error) => match error.kind() {            ErrorKind::NotFound => match File::create("hello.txt") {                Ok(fc) => fc,                Err(e) => panic!("Problem creating the file: {e:?}"),            },            other_error => {                panic!("Problem opening the file: {other_error:?}");            }        },    };}

match を重ねると読みにくくなります。第 13 章で学ぶクロージャと Result のメソッドを使うと、同じことをこう書けます。

Rust
use std::fs::File;use std::io::ErrorKind; fn main() {    let greeting_file = File::open("hello.txt").unwrap_or_else(|error| {        if error.kind() == ErrorKind::NotFound {            File::create("hello.txt").unwrap_or_else(|error| {                panic!("Problem creating the file: {error:?}");            })        } else {            panic!("Problem opening the file: {error:?}");        }    });}

unwrap と expect

「失敗したらパニックでいい」という場面のために、Result には近道のメソッドがあります。

Rust
let greeting_file = File::open("hello.txt").unwrap();let greeting_file = File::open("hello.txt")    .expect("hello.txt should be included in this project");
メソッドOk(v) のときErr(e) のとき
unwrap()v を返す定型のメッセージでパニック
expect("msg")v を返す指定したメッセージでパニック
unwrap_or(d)v を返すd を返す
unwrap_or_else(f)v を返すクロージャ f(e) の結果を返す

実際のコードでは、unwrap より expect を使うのがおすすめです。メッセージに「なぜ成功するはずだと考えたのか」を書いておくと、パニックしたときに原因を探しやすくなります。

9.4エラーを呼び出し元に伝える

関数の中でエラーが起きたとき、その場で処理するのではなく、呼び出し元にエラーを返して判断を任せることができます。これをエラーの伝播（propagation）と呼びます。呼び出し元のほうが、どう処理すべきかの情報を多く持っていることが多いからです。

Rust
use std::fs::File;use std::io::{self, Read}; fn read_username_from_file() -> Result<String, io::Error> {    let username_file_result = File::open("hello.txt");     let mut username_file = match username_file_result {        Ok(file) => file,        Err(e) => return Err(e),       // エラーなら、すぐに呼び出し元に返す    };     let mut username = String::new();     match username_file.read_to_string(&mut username) {        Ok(_) => Ok(username),        Err(e) => Err(e),               // エラーなら返す    }}

このパターンはとてもよく出てくるので、専用の演算子 ? が用意されています。

? 演算子

Rust
use std::fs::File;use std::io::{self, Read}; fn read_username_from_file() -> Result<String, io::Error> {    let mut username_file = File::open("hello.txt")?;    let mut username = String::new();    username_file.read_to_string(&mut username)?;    Ok(username)}

? は、Result の値の後ろに置きます。

match で書いたものとの違いは 1 つだけです。? はエラーを返す前に、From トレイトの from 関数を通して、エラーの型を関数の戻り値のエラー型に変換します。そのため、関数の中でいろいろな種類のエラーが起きても、From の実装さえあれば、1 つのエラー型にまとめて返せます。

? は連鎖させることもできます。

Rust
fn read_username_from_file() -> Result<String, io::Error> {    let mut username = String::new();     File::open("hello.txt")?.read_to_string(&mut username)?;     Ok(username)}

ちなみに、ファイルを文字列に読み込むのはとてもよくある処理なので、標準ライブラリに 1 行で済む関数があります。

Rust
use std::fs;use std::io; fn read_username_from_file() -> Result<String, io::Error> {    fs::read_to_string("hello.txt")}

? が使える場所

? は「エラーなら早めに return する」ので、戻り値の型が ? を使う値と互換性のある関数の中でしか使えません。

Rustコンパイルエラーになる
use std::fs::File; fn main() {    let greeting_file = File::open("hello.txt")?;}
ターミナル
error[E0277]: the `?` operator can only be used in a function that returns `Result` or `Option` (or another type that implements `FromResidual`) --> src/main.rs:4:48  |3 | fn main() {  | --------- this function should return `Result` or `Option` to accept `?`4 |     let greeting_file = File::open("hello.txt")?;  |                                                ^ cannot use the `?` operator in a function that returns `()`
error[E0277]? 演算子は Result か Option を返す関数の中でしか使えません

main の戻り値は () なので、? がエラーを返そうにも返せません。直し方は 2 つあります。戻り値の型を Result にするか、match などで main の中でエラーを処理するかです。

? は Option<T> にも使えます。None なら関数から None を返し、Some(v) なら v を取り出します。

Rust
fn last_char_of_first_line(text: &str) -> Option<char> {    text.lines().next()?.chars().last()}

text.lines().next() は最初の行を Option<&str> で返します。空の文字列なら None なので、そこで関数から None を返します。ただし、Result を返す関数の中で Option に ? を使う（あるいはその逆）ことはできません。変換が必要なら ok_or や ok メソッドを使います。

main で Result を返す

main は Result<(), E> を返すこともできます。

Rust
use std::error::Error;use std::fs::File; fn main() -> Result<(), Box<dyn Error>> {    let greeting_file = File::open("hello.txt")?;     Ok(())}

Box<dyn Error> はトレイトオブジェクト（第 17 章）で、ここでは「どんな種類のエラーでも」という意味だと思ってください。main が Ok(()) を返すとプログラムは終了コード 0 で、Err を返すと 0 以外の終了コードで終わります。

9.5panic! するか、しないか

いつ panic! を使い、いつ Result を返すべきでしょうか。基本の方針は、迷ったら Result を返すです。Result を返せば、呼び出し元が「回復を試みる」か「ここでパニックする」かを選べます。パニックしてしまうと、呼び出し元から選択肢を奪います。

panic が適切な場面

3 つ目の「論理的に失敗しないとわかる」場合の例です。

Rust
use std::net::IpAddr; let home: IpAddr = "127.0.0.1"    .parse()    .expect("Hardcoded IP address should be valid");

ハードコードされた文字列 "127.0.0.1" が正しい IP アドレスであることは、人間には明らかです。でも parse の戻り値は Result なので、コンパイラは処理を求めます。こういうときは expect を使い、「なぜ失敗しないと考えたのか」をメッセージに書いておきます。

悪い状態に陥ったらパニック

コードが悪い状態（bad state）に陥る可能性があるなら、パニックさせるべきです。悪い状態とは、前提や保証、約束、不変条件が破られた状態で、次のような性質を持ちます。

  • 想定外のことである（ユーザーがときどき入力を間違える、のような「予想できること」ではない）
  • この時点から先のコードが、悪い状態にないことを前提に書かれている
  • この情報を型で表現する良い方法がない

逆に、失敗が予想されるなら（パーサが不正な形式のデータを受け取った、HTTP リクエストがレート制限に引っかかった、など）、Result を返すべきです。

型で検証を表現する

数当てゲームでは、ユーザーの予想が 1 から 100 の間かどうかを確認していませんでした。関数ごとに範囲をチェックするのは面倒ですし、忘れるかもしれません。代わりに、範囲内の値しか作れない型を作ってしまいましょう。

Rust
pub struct Guess {    value: i32,          // 非公開。外から直接書き換えられない} impl Guess {    pub fn new(value: i32) -> Guess {        if value < 1 || value > 100 {            panic!("Guess value must be between 1 and 100, got {value}.");        }         Guess { value }    }     pub fn value(&self) -> i32 {   // ゲッター        self.value    }}

value フィールドが非公開なので、Guess を作る方法は Guess::new しかありません。つまり、Guess 型の値が存在するなら、それは必ず 1 から 100 の間です。Guess を受け取る関数は、範囲のチェックをする必要がなくなります。チェックを 1 か所に集めて、型に「検証済み」という意味を持たせたのです。

9.6この章のまとめ

  • 回復不能なエラーは panic!。プログラムは巻き戻しながら止まる
  • 回復可能なエラーは Result<T, E>。match で処理するか、? で呼び出し元に伝える
  • ? は Ok なら値を取り出し、Err なら From で変換して早期リターンする
  • 迷ったら Result。panic は、プロトタイプ・テスト・論理的に失敗しない場合・悪い状態に陥った場合に
  • 検証を型に閉じ込めると、チェックし忘れを防げる

次の章では、型を抽象化するジェネリクス、振る舞いを抽象化するトレイト、そして参照の有効期間を表すライフタイムを学びます。
