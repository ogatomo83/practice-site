第 10 章

ジェネリクス・トレイト・ライフタイム

重複を消すための 3 つの抽象化。型を抽象化するジェネリクス、振る舞いを抽象化するトレイト、参照の有効範囲をコンパイラに伝えるライフタイム。特にライフタイムは、図で範囲を見ながら理解します。

6 節図 8 点目安 120 分

10.1重複を関数に抜き出すところから

この章の 3 つの道具は、どれも重複をなくすための仕組みです。その出発点は、誰でも知っている「関数への抜き出し」です。

リストの中の最大値を探すコードがあるとします。

Rust
fn main() {    let number_list = vec![34, 50, 25, 100, 65];     let mut largest = &number_list[0];    for number in &number_list {        if number > largest {            largest = number;        }    }    println!("The largest number is {largest}");     // 別のリストでも同じことをしたい → コードをコピーする？}

2 つのリストで同じことをしたいなら、コピーするのではなく関数にします。

Rust
fn largest(list: &[i32]) -> &i32 {    let mut largest = &list[0];     for item in list {        if item > largest {            largest = item;        }    }     largest}

では、i32 のリストと char のリストの両方で最大値を探したいときは？ 型だけが違う 2 つの関数を書くのは重複です。そこで型そのものを引数にするのがジェネリクスです。

10.2ジェネリックなデータ型

関数で

型の引数（型パラメータ）は、関数名の後ろの山かっこ <> で宣言します。慣習として、短い大文字の名前、多くは T（type の頭文字）を使います。

Rustコンパイルエラーになる
fn largest<T>(list: &[T]) -> &T {    let mut largest = &list[0];     for item in list {        if item > largest {            largest = item;        }    }     largest}

「largest は、ある型 T についてジェネリックで、T のスライスを受け取って T への参照を返す」と読みます。ところが、これはまだコンパイルできません。

ターミナル
error[E0369]: binary operation `>` cannot be applied to type `&T` --> src/main.rs:5:17  |5 |         if item > largest {  |            ---- ^ ------- &T  |            |  |            &T  |help: consider restricting type parameter `T` with trait `PartialOrd`  |1 | fn largest<T: std::cmp::PartialOrd>(list: &[T]) -> &T {  |             ++++++++++++++++++++++
error[E0369]> 演算子は &T 型には使えません

T はどんな型でもよいので、比較できない型が渡される可能性もあります。比較できる型だけに限定するには、T にトレイト境界を付けます（help に答えが書いてあります）。これは次の節で扱います。

構造体で

Rust
struct Point<T> {    x: T,    y: T,} fn main() {    let integer = Point { x: 5, y: 10 };    let float = Point { x: 1.0, y: 4.0 };}

x と y は同じ型 T なので、Point { x: 5, y: 4.0 } はエラーになります。別々の型を許したいなら、型パラメータを 2 つにします。

Rust
struct Point<T, U> {    x: T,    y: U,} let both_integer = Point { x: 5, y: 10 };let both_float = Point { x: 1.0, y: 4.0 };let integer_and_float = Point { x: 5, y: 4.0 };

enum で

すでに見た Option<T> と Result<T, E> が、ジェネリックな enum です。

Rust
enum Option<T> {    Some(T),    None,} enum Result<T, E> {    Ok(T),    Err(E),}

メソッドで

Rust
struct Point<T> {    x: T,    y: T,} impl<T> Point<T> {           // すべての T について実装    fn x(&self) -> &T {        &self.x    }} impl Point<f32> {            // f32 のときだけ実装    fn distance_from_origin(&self) -> f32 {        (self.x.powi(2) + self.y.powi(2)).sqrt()    }}

impl<T> の <T> は、「この後の Point<T> の T は具体的な型ではなく型パラメータですよ」という宣言です。impl Point<f32> のように具体的な型を書けば、その型のときだけ使えるメソッドを定義できます。

ジェネリクスのコスト

ジェネリクスを使うと、実行時に遅くなるのでしょうか。答えは いいえ です。Rust はコンパイル時に単相化（monomorphization）を行い、ジェネリックなコードを、実際に使われている具体的な型ごとのコードに展開します。

手で型ごとにコードを書いたのと同じものができあがるので、実行速度は変わりません。

10.3トレイト：共通の振る舞いを定義する

トレイト（trait）は、ある型が持つ機能を定義し、他の型と共有するための仕組みです。他の言語のインターフェースに似ています。

トレイトを定義する

ニュース記事（NewsArticle）とソーシャルメディアの投稿（SocialPost）という 2 つの型があり、どちらも「要約を表示する」機能を持たせたいとします。

src/lib.rs
pub trait Summary {    fn summarize(&self) -> String;}

トレイトの中には、メソッドのシグネチャだけを書き、本体は書きません。このトレイトを実装する型は、それぞれ独自の本体を用意しなければなりません。

トレイトを型に実装する

src/lib.rs
pub struct NewsArticle {    pub headline: String,    pub location: String,    pub author: String,    pub content: String,} impl Summary for NewsArticle {    fn summarize(&self) -> String {        format!("{}, by {} ({})", self.headline, self.author, self.location)    }} pub struct SocialPost {    pub username: String,    pub content: String,    pub reply: bool,    pub repost: bool,} impl Summary for SocialPost {    fn summarize(&self) -> String {        format!("{}: {}", self.username, self.content)    }}

使う側は、普通のメソッドと同じように呼べます。ただし、トレイトのメソッドを呼ぶには、トレイト自体もスコープに入っている必要があります。

Rust
use aggregator::{SocialPost, Summary}; fn main() {    let post = SocialPost {        username: String::from("horse_ebooks"),        content: String::from("of course, as you probably already know, people"),        reply: false,        repost: false,    };     println!("1 new post: {}", post.summarize());}

孤児ルール

トレイトの実装には 1 つ制約があります。トレイトか型のどちらか少なくとも一方が、自分のクレートのものでなければなりません。

自分の型（Tweet など）外部の型（Vec<T> など）
自分のトレイト（Summary など）できるできる
外部のトレイト（Display など）できるできない

このルールがないと、2 つのクレートが同じ型に同じトレイトを別々に実装して、どちらを使うべきか決められなくなってしまいます。

デフォルト実装

トレイトのメソッドに、デフォルトの本体を書いておくこともできます。

Rust
pub trait Summary {    fn summarize_author(&self) -> String;   // これは各型が実装する     fn summarize(&self) -> String {          // デフォルト実装。他のメソッドを呼べる        format!("(Read more from {}...)", self.summarize_author())    }} impl Summary for SocialPost {    fn summarize_author(&self) -> String {   // これだけ実装すれば summarize も使える        format!("@{}", self.username)    }}

impl Summary for NewsArticle {} のように空のブロックで実装すると、すべてデフォルト実装が使われます（この例では summarize_author にデフォルトがないので空にはできません）。

引数としてのトレイト

トレイトを使うと、「Summary を実装している何か」を受け取る関数が書けます。

Rust
pub fn notify(item: &impl Summary) {    println!("Breaking news! {}", item.summarize());}

&impl Summary は、「Summary を実装している任意の型への参照」という意味です。NewsArticle も SocialPost も渡せます。String や i32 は Summary を実装していないので、渡すとコンパイルエラーです。

トレイト境界

impl Trait は、実はトレイト境界（trait bound）という書き方の省略形です。

Rust
pub fn notify<T: Summary>(item: &T) {    println!("Breaking news! {}", item.summarize());}

「型パラメータ T は、Summary を実装している型に限る」と読みます。2 つの書き方には、次のような違いがあります。

Rust
pub fn notify(item1: &impl Summary, item2: &impl Summary)  // item1 と item2 は別の型でもよいpub fn notify<T: Summary>(item1: &T, item2: &T)            // item1 と item2 は同じ型でなければならない

複数のトレイトを要求するときは + でつなぎます。

Rust
pub fn notify(item: &(impl Summary + Display)) {}pub fn notify<T: Summary + Display>(item: &T) {}

境界が増えて関数のシグネチャが読みにくくなったら、where 句に分けて書けます。

Rust
fn some_function<T, U>(t: &T, u: &U) -> i32where    T: Display + Clone,    U: Clone + Debug,{    // --snip--}

戻り値としてのトレイト

戻り値の型にも impl Trait が使えます。「Summary を実装している何かを返す。具体的な型は秘密」という意味です。

Rust
fn returns_summarizable() -> impl Summary {    SocialPost {        username: String::from("horse_ebooks"),        content: String::from("of course, as you probably already know, people"),        reply: false,        repost: false,    }}

第 13 章で学ぶクロージャやイテレータは、コンパイラだけが知っている型や、書き切れないほど長い型を持つので、この書き方がとても役立ちます。

ただし、impl Trait で返せるのは 1 つの型だけです。条件によって NewsArticle か SocialPost のどちらかを返す、ということはできません。それが必要なら、第 17 章のトレイトオブジェクトを使います。

largest を完成させる

さっきの largest に戻りましょう。比較するには PartialOrd トレイトが必要でした。

Rust
fn largest<T: PartialOrd>(list: &[T]) -> &T {    let mut largest = &list[0];     for item in list {        if item > largest {            largest = item;        }    }     largest} fn main() {    let number_list = vec![34, 50, 25, 100, 65];    println!("The largest number is {}", largest(&number_list));     let char_list = vec!['y', 'm', 'a', 'q'];    println!("The largest char is {}", largest(&char_list));}

トレイト境界で条件付きでメソッドを実装する

トレイト境界は、impl ブロックにも付けられます。

Rust
use std::fmt::Display; struct Pair<T> {    x: T,    y: T,} impl<T> Pair<T> {                       // どんな T でも new は使える    fn new(x: T, y: T) -> Self {        Self { x, y }    }} impl<T: Display + PartialOrd> Pair<T> { // 表示も比較もできる T のときだけ    fn cmp_display(&self) {        if self.x >= self.y {            println!("The largest member is x = {}", self.x);        } else {            println!("The largest member is y = {}", self.y);        }    }}

さらに、「あるトレイトを実装しているすべての型に、別のトレイトを実装する」こともできます。これをブランケット実装と呼びます。標準ライブラリには次のような実装があります。

Rust
impl<T: Display> ToString for T {    // --snip--}

Display を実装している型ならどれでも、to_string メソッドが使えます。3.to_string() が動くのは、i32 が Display を実装しているからです。

要点トレイトとトレイト境界の効能

動的型付けの言語では、メソッドが存在しない型でそのメソッドを呼ぶと、実行時にエラーになります。Rust は、トレイト境界によってその問題をコンパイル時に見つけます。実行時に「このメソッドはあるか」を調べる必要がないので、柔軟さと速さを両立できます。

10.4ライフタイムで参照を検証する

ライフタイム（lifetime）は、参照が有効である範囲のことです。実はすべての参照にライフタイムがあり、これまでは型と同じくコンパイラが推論してくれていました。ライフタイムの注釈を書く必要があるのは、推論できないときだけです。

ライフタイムの目的は、第 4 章で見たダングリング参照を防ぐことです。

借用チェッカー

Rustコンパイルエラーになる
fn main() {    let r;                // ---------+-- 'a                          //          |    {                     //          |        let x = 5;        // -+-- 'b  |        r = &x;           //  |       |    }                     // -+       |                          //          |    println!("r: {r}");   //          |}                         // ---------+
ターミナル
error[E0597]: `x` does not live long enough --> src/main.rs:6:13  |5 |         let x = 5;  |             - binding `x` declared here6 |         r = &x;  |             ^^ borrowed value does not live long enough7 |     }  |     - `x` dropped here while still borrowed8 |9 |     println!("r: {r}");  |                  --- borrow later used here

Rust のコンパイラには借用チェッカーという部分があり、スコープを比較して、すべての借用が有効かどうかを判断します。ここでは、参照する側（r、'a）が、参照される側（x、'b）より長生きしています。参照先は、参照より長く生きていなければならないので、エラーです。

x のほうが長生きなら、問題ありません。

Rustコンパイルできる
fn main() {    let x = 5;            // ----------+-- 'b                          //           |    let r = &x;           // --+-- 'a  |                          //   |       |    println!("r: {r}");   //   |       |                          // --+       |}                         // ----------+

関数のジェネリックなライフタイム

2 つの文字列スライスのうち、長いほうを返す関数を書いてみます。

Rustコンパイルエラーになる
fn longest(x: &str, y: &str) -> &str {    if x.len() > y.len() {        x    } else {        y    }}
ターミナル
error[E0106]: missing lifetime specifier --> src/main.rs:9:33  |9 | fn longest(x: &str, y: &str) -> &str {  |               ----     ----     ^ expected named lifetime parameter  |  = help: this function's return type contains a borrowed value, but the signature does not say whether it is borrowed from `x` or `y`help: consider introducing a named lifetime parameter  |9 | fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {  |           ++++     ++          ++          ++
error[E0106]ライフタイム指定子がありません

help の 1 行目がすべてです。戻り値は借用された値を含んでいるが、それが x から借りたものか y から借りたものか、シグネチャからはわからない。 実際、if の結果によってどちらが返るかは実行時に決まります。借用チェッカーは、戻り値の参照がいつまで有効なのかを判断できないのです。

ライフタイム注釈の書き方

ライフタイム注釈は、アポストロフィ ' で始まる名前で、普通は 'a のように短い小文字を使います。参照の & の後に書きます。

Rust
&i32        // 参照&'a i32     // 明示的なライフタイム付きの参照&'a mut i32 // 明示的なライフタイム付きの可変参照

注釈は、参照が生きる長さを変えるものではありません。複数の参照のライフタイムが互いにどう関係しているかを、コンパイラに説明するためのものです。

longest にライフタイムを付ける

Rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {    if x.len() > y.len() {        x    } else {        y    }}

このシグネチャは、こう読みます。

ある生存期間 'a について、2 つの引数はどちらも少なくとも 'a の間は有効であり、戻り値の参照も少なくとも 'a の間は有効である。

実際に具体的な参照を渡すと、'a は x のスコープと y のスコープが重なる部分、つまり短いほうのライフタイムになります。そして戻り値は、その短いほうと同じだけしか使えません。

ターミナル
error[E0597]: `string2` does not live long enough --> src/main.rs:6:44  |5 |         let string2 = String::from("xyz");  |             ------- binding `string2` declared here6 |         result = longest(string1.as_str(), string2.as_str());  |                                            ^^^^^^^ borrowed value does not live long enough7 |     }  |     - `string2` dropped here while still borrowed8 |     println!("The longest string is {result}");  |                                     -------- borrow later used here

人間が見れば、string1 のほうが長いので result は string1 を指すはずだとわかります。でもコンパイラは、関数のシグネチャだけを見て判断します。シグネチャは「戻り値は短いほうと同じだけ生きる」と言っているので、エラーにするのです。

ライフタイムの観点で考える

どの引数にライフタイムを付けるべきかは、関数が何をするかで決まります。必ず x を返すなら、y にはライフタイムは要りません。

Rust
fn longest<'a>(x: &'a str, y: &str) -> &'a str {    x}

関数の中で作った値への参照を返そうとすると、どう注釈を付けてもダングリング参照になるのでエラーです。

Rustコンパイルエラーになる
fn longest<'a>(x: &str, y: &str) -> &'a str {    let result = String::from("really long string");    result.as_str()   // result は関数の終わりで drop される}

この場合は、参照ではなく String を返して、所有権ごと呼び出し元に渡すのが正解です。

要点ライフタイム構文の本質

ライフタイムの構文は、関数の引数と戻り値のライフタイムを結びつけるためのものです。結びつきさえわかれば、Rust はメモリ安全な操作を許可し、ダングリング参照を生む操作を拒否できます。

構造体のライフタイム

構造体に参照を持たせる場合は、すべての参照にライフタイム注釈が必要です。

Rust
struct ImportantExcerpt<'a> {    part: &'a str,} fn main() {    let novel = String::from("Call me Ishmael. Some years ago...");    let first_sentence = novel.split('.').next().unwrap();    let i = ImportantExcerpt {        part: first_sentence,    };}

この注釈は、「ImportantExcerpt のインスタンスは、part フィールドの参照より長生きできない」という意味です。

ライフタイムの省略規則

第 4 章で書いた first_word は、参照を受け取って参照を返すのに、ライフタイム注釈がありませんでした。

Rust
fn first_word(s: &str) -> &str {

初期の Rust では、これにも fn first_word<'a>(s: &'a str) -> &'a str と書く必要がありました。しかし同じパターンを何度も書くことになったので、コンパイラが決まったパターンを推論するようになりました。これをライフタイム省略規則（lifetime elision rules）と呼びます。

用語として、引数のライフタイムを入力ライフタイム、戻り値のライフタイムを出力ライフタイムと呼びます。

規則対象内容
1入力参照である引数それぞれに、別々のライフタイムを割り当てる
2出力入力ライフタイムがちょうど 1 つなら、それをすべての出力ライフタイムに割り当てる
3出力引数に &self か &mut self があれば、self のライフタイムをすべての出力ライフタイムに割り当てる

3 つの規則を適用しても出力ライフタイムが決まらなければ、エラーになり、注釈を求められます。

メソッドのライフタイム

構造体にライフタイムがあるなら、impl の後と型名の後にライフタイムを書きます。

Rust
impl<'a> ImportantExcerpt<'a> {    fn level(&self) -> i32 {        3    }     fn announce_and_return_part(&self, announcement: &str) -> &str {        println!("Attention please: {announcement}");        self.part    }}

announce_and_return_part は入力ライフタイムが 2 つありますが、規則 3 により、戻り値は &self と同じライフタイムになります。省略規則のおかげで、メソッドではライフタイムを書く場面がほとんどありません。

静的ライフタイム

特別なライフタイム 'static は、プログラムの実行中ずっと有効であることを表します。文字列リテラルはすべて 'static です。

Rust
let s: &'static str = "I have a static lifetime.";

文字列リテラルはバイナリに直接埋め込まれているので、常に存在します。

注意'static で黙らせない

ライフタイムのエラーを見て、「'static を付けろ」というヒントをもらうことがあります。でも、付ける前に「本当にプログラムの終わりまで生きている必要があるのか」を考えてください。ほとんどの場合、問題はダングリング参照を作ろうとしていることか、ライフタイムの不一致にあります。'static を付けるのではなく、そちらを直すべきです。

10.53 つを組み合わせる

ジェネリクス、トレイト境界、ライフタイムは、1 つの関数に同時に書けます。

Rust
use std::fmt::Display; fn longest_with_an_announcement<'a, T>(    x: &'a str,    y: &'a str,    ann: T,) -> &'a strwhere    T: Display,{    println!("Announcement! {ann}");    if x.len() > y.len() {        x    } else {        y    }}

ライフタイムもジェネリクスの一種なので、<'a, T> のように同じ山かっこの中に並べます。

10.6この章のまとめ

道具抽象化するもの書き方確認するタイミング
ジェネリクス型fn f<T>(x: T)コンパイル時（単相化）
