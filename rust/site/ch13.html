第 13 章

関数型言語の機能：クロージャとイテレータ

関数を値として扱うクロージャと、要素の並びを順に処理するイテレータ。Rust らしい簡潔なコードの土台であり、しかも手書きのループと同じ速さで動きます。

5 節図 8 点目安 90 分

13.1クロージャ：環境をキャプチャする無名関数

クロージャは、変数に入れたり、他の関数に引数として渡したりできる無名関数です。普通の関数と違って、定義された場所のスコープにある値を取り込んで（キャプチャして）使えるのが特徴です。

環境をキャプチャする

T シャツの会社が、メーリングリストの登録者に限定版の T シャツを配る、という例で考えます。登録者は好きな色を設定でき、設定していなければ、在庫が最も多い色がもらえます。

Rust
#[derive(Debug, PartialEq, Copy, Clone)]enum ShirtColor {    Red,    Blue,} struct Inventory {    shirts: Vec<ShirtColor>,} impl Inventory {    fn giveaway(&self, user_preference: Option<ShirtColor>) -> ShirtColor {        user_preference.unwrap_or_else(|| self.most_stocked())    }     fn most_stocked(&self) -> ShirtColor {        let mut num_red = 0;        let mut num_blue = 0;         for color in &self.shirts {            match color {                ShirtColor::Red => num_red += 1,                ShirtColor::Blue => num_blue += 1,            }        }        if num_red > num_blue {            ShirtColor::Red        } else {            ShirtColor::Blue        }    }}

unwrap_or_else(|| self.most_stocked()) の || self.most_stocked() がクロージャです。

  • || の間に引数を書く（ここでは引数なし）
  • その後に本体の式を書く
  • Option が None のときだけ、このクロージャが呼ばれる

ポイントは、クロージャの本体で self を使っていることです。self はクロージャの引数ではなく、giveaway メソッドの中にある値です。クロージャは、それをキャプチャしています。普通の関数ではこれはできません。

型の推論と注釈

関数と違って、クロージャは引数や戻り値の型を書かなくてもかまいません。クロージャは名前を付けて外部に公開するものではなく、短い範囲で使われるので、コンパイラが型を推論できるからです。もちろん、書くこともできます。

Rust
fn  add_one_v1   (x: u32) -> u32 { x + 1 }   // 関数let add_one_v2 = |x: u32| -> u32 { x + 1 };  // 型を全部書いたクロージャlet add_one_v3 = |x|             { x + 1 };  // 型を省略let add_one_v4 = |x|               x + 1  ;  // 本体が 1 つの式なら波かっこも省略

ただし、推論された型は 1 つに固定されます。

Rustコンパイルエラーになる
let example_closure = |x| x; let s = example_closure(String::from("hello"));  // ここで x は String に決まるlet n = example_closure(5);                       // error[E0308]: 整数は渡せない

3 つのキャプチャの方法

クロージャが環境の値をキャプチャする方法は、関数が引数を受け取る方法と同じく 3 通りあります。どれになるかは、クロージャの本体がその値をどう使うかで、コンパイラが自動的に決めます。

不変の借用

Rust
fn main() {    let list = vec![1, 2, 3];    println!("Before defining closure: {list:?}");     let only_borrows = || println!("From closure: {list:?}");     println!("Before calling closure: {list:?}");   // 不変の借用同士なので OK    only_borrows();    println!("After calling closure: {list:?}");}

可変の借用

Rust
fn main() {    let mut list = vec![1, 2, 3];    println!("Before defining closure: {list:?}");     let mut borrows_mutably = || list.push(7);     // ここで println!("{list:?}") とは書けない。可変の借用が生きているから    borrows_mutably();    println!("After calling closure: {list:?}");   // [1, 2, 3, 7]}

move で所有権を移す

本体が所有権を必要としていなくても、クロージャに強制的に所有権を移したいときは、引数リストの前に move を付けます。これが最も役立つのは、クロージャを新しいスレッドに渡すときです。

Rust
use std::thread; fn main() {    let list = vec![1, 2, 3];    println!("Before defining closure: {list:?}");     thread::spawn(move || println!("From thread: {list:?}"))        .join()        .unwrap();}

新しいスレッドは、メインスレッドより先に終わるかもしれないし、後に終わるかもしれません。もしメインスレッドが先に終わって list を drop したら、新しいスレッドの参照はダングリングになります。だから、所有権ごと新しいスレッドに渡す必要があるのです。move を付けないとコンパイルエラーになります（第 16 章で詳しく扱います）。

Fn トレイト

クロージャが、キャプチャした値を本体でどう扱うかによって、クロージャは 3 つのトレイトのうち 1 つ以上を自動的に実装します。

トレイト本体でキャプチャした値を呼べる回数例
FnOnceムーブする（消費する）1 回|| drop(s)
FnMut書き換える何度でも|| count += 1
Fn読むだけ（または何もキャプチャしない）何度でも|| println!("{s}")

関数の引数にクロージャを受け取るときは、トレイト境界でどのトレイトを要求するかを書きます。Option の unwrap_or_else の定義を見てみましょう。

Rust
impl<T> Option<T> {    pub fn unwrap_or_else<F>(self, f: F) -> T    where        F: FnOnce() -> T    {        match self {            Some(x) => x,            None => f(),        }    }}

f は最大 1 回しか呼ばれないので、最も緩い FnOnce を要求しています。こうしておけば、3 種類どのクロージャでも渡せます。

一方、スライスの sort_by_key は、要素ごとに何度もクロージャを呼ぶので FnMut を要求します。

Rust
#[derive(Debug)]struct Rectangle {    width: u32,    height: u32,} fn main() {    let mut list = [        Rectangle { width: 10, height: 1 },        Rectangle { width: 3, height: 5 },        Rectangle { width: 7, height: 12 },    ];     list.sort_by_key(|r| r.width);    println!("{list:#?}");}

値をムーブしてしまうクロージャを渡すと、エラーになります。

Rustコンパイルエラーになる
let mut sort_operations = vec![];let value = String::from("closure called"); list.sort_by_key(|r| {    sort_operations.push(value);   // value を何度もムーブすることはできない    r.width});
ターミナル
error[E0507]: cannot move out of `value`, a captured variable in an `FnMut` closure  --> src/main.rs:18:30   |15 |     let value = String::from("closure called");   |         ----- captured outer variable16 |17 |     list.sort_by_key(|r| {   |                      --- captured by this `FnMut` closure18 |         sort_operations.push(value);   |                              ^^^^^ move occurs because `value` has type `String`, which does not implement the `Copy` trait
error[E0507]FnMut クロージャの中で、キャプチャした変数 value をムーブできません

value は 1 つしかないので、1 回目の呼び出しでムーブしたら、2 回目に渡すものがありません。このクロージャは FnOnce しか実装できず、FnMut を要求する sort_by_key には渡せないのです。呼ばれた回数を数えたいなら、String をムーブする代わりに、数値を書き換えます（num_sort_operations += 1;）。

13.2イテレータで一連の要素を処理する

イテレータは、要素の並びを 1 つずつ順に処理するための仕組みです。どの要素から始めて、いつ終わるかといったロジックをイテレータが引き受けてくれるので、自分で添字を管理する必要がありません。

Rust のイテレータは怠惰（lazy）です。作っただけでは何も起きず、消費するメソッドを呼んだときに初めて動きます。

Rust
let v1 = vec![1, 2, 3]; let v1_iter = v1.iter();   // この時点では何もしていない for val in v1_iter {        // ここで初めて要素が取り出される    println!("Got: {val}");}

Iterator トレイトと next

すべてのイテレータは、標準ライブラリの Iterator トレイトを実装しています。

Rust
pub trait Iterator {    type Item;     fn next(&mut self) -> Option<Self::Item>;     // デフォルト実装のあるメソッドがたくさん続く}

type Item は関連型（第 19 章）で、イテレータが返す要素の型を表します。実装しなければならないのは next だけです。next は呼ぶたびに次の要素を Some で返し、終わったら None を返します。

Rust
#[test]fn iterator_demonstration() {    let v1 = vec![1, 2, 3];     let mut v1_iter = v1.iter();     assert_eq!(v1_iter.next(), Some(&1));    assert_eq!(v1_iter.next(), Some(&2));    assert_eq!(v1_iter.next(), Some(&3));    assert_eq!(v1_iter.next(), None);}

for ループでは mut を付けていませんでした。for がイテレータの所有権を取り、内部で可変にしているからです。

イテレータには、要素をどう取り出すかで 3 種類があります。

メソッド要素の型元のコレクション
iter()&T（不変参照）そのまま使える
iter_mut()&mut T（可変参照）要素を書き換えられる
into_iter()T（所有権ごと）ムーブされて使えなくなる

イテレータを消費するメソッド

next を呼んでイテレータを使い切るメソッドを、消費アダプタ（consuming adaptor）と呼びます。sum はその一例です。

Rust
#[test]fn iterator_sum() {    let v1 = vec![1, 2, 3];    let v1_iter = v1.iter();     let total: i32 = v1_iter.sum();   // v1_iter の所有権を取って使い切る     assert_eq!(total, 6);}

別のイテレータを作るメソッド

イテレータを受け取って、別のイテレータを返すメソッドを、イテレータアダプタ（iterator adaptor）と呼びます。map は各要素にクロージャを適用した新しいイテレータを返します。

Rust
let v1: Vec<i32> = vec![1, 2, 3]; v1.iter().map(|x| x + 1);   // 警告：イテレータアダプタは怠惰
ターミナル
warning: unused `Map` that must be used --> src/main.rs:4:5  |4 |     v1.iter().map(|x| x + 1);  |     ^^^^^^^^^^^^^^^^^^^^^^^^  |  = note: iterators are lazy and do nothing unless consumed

「イテレータは怠惰で、消費されない限り何もしない」と言われています。collect で消費しましょう。

Rust
let v1: Vec<i32> = vec![1, 2, 3]; let v2: Vec<_> = v1.iter().map(|x| x + 1).collect(); assert_eq!(v2, vec![2, 3, 4]);

環境をキャプチャするクロージャとイテレータ

filter は、各要素にクロージャを適用して、true を返した要素だけを残すイテレータを作ります。クロージャが環境をキャプチャできることを活かした例です。

Rust
#[derive(PartialEq, Debug)]struct Shoe {    size: u32,    style: String,} fn shoes_in_size(shoes: Vec<Shoe>, shoe_size: u32) -> Vec<Shoe> {    shoes.into_iter().filter(|s| s.size == shoe_size).collect()}

into_iter で shoes の所有権を取り、filter のクロージャが引数の shoe_size をキャプチャして比較し、合うものだけを collect で新しいベクタに集めています。

よく使うアダプタ

アダプタすること例
map(f)各要素を変換.map(|x| x * 2)
filter(p)条件に合う要素だけ残す.filter(|x| x % 2 == 0)
enumerate()(添字, 要素) の組にするfor (i, x) in v.iter().enumerate()
zip(other)2 つを組にするa.iter().zip(b.iter())
skip(n) / take(n)先頭を飛ばす / 先頭だけ取る.skip(1)
rev()逆順にする(1..4).rev()
sum() / count() / collect()消費して結果を作る.sum::<i32>()

13.3入出力プロジェクトを改善する

第 12 章の minigrep を、イテレータで書き直しましょう。

clone をなくす

Config::build では、args のスライスを借用していたので、clone して所有権のある String を作っていました。env::args() が返すイテレータそのものを受け取れば、要素の所有権を直接もらえます。

src/main.rs
fn main() {    let config = Config::build(env::args()).unwrap_or_else(|err| {        eprintln!("Problem parsing arguments: {err}");        process::exit(1);    });     // --snip--}
src/lib.rs
impl Config {    pub fn build(        mut args: impl Iterator<Item = String>,    ) -> Result<Config, &'static str> {        args.next();   // 最初の値はプログラム名なので読み飛ばす         let query = match args.next() {            Some(arg) => arg,            None => return Err("Didn't get a query string"),        };         let file_path = match args.next() {            Some(arg) => arg,            None => return Err("Didn't get a file path"),        };         let ignore_case = env::var("IGNORE_CASE").is_ok();         Ok(Config {            query,            file_path,            ignore_case,        })    }}

impl Iterator<Item = String> は、「String を返すイテレータなら何でも」という意味です。next を呼ぶとイテレータの状態が変わるので、args に mut を付けています。

ループをアダプタで書き直す

src/lib.rs
pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {    contents        .lines()        .filter(|line| line.contains(query))        .collect()}

可変の中間ベクタ results が消えました。「何をしたいか」（query を含む行だけを集める）が、そのままコードになっています。可変な状態が減ると、将来並列化したくなったときにも安全です。

search_case_insensitive も同じように書き直せます。どちらのスタイルを選ぶかは好みですが、Rust のプログラマの多くはイテレータのスタイルを好みます。

13.4性能比較：ループ vs イテレータ

イテレータは抽象度が高いので、遅くなるのではと心配になるかもしれません。アーサー・コナン・ドイルの「シャーロック・ホームズの冒険」の全文から「the」を探すベンチマークで、for ループ版とイテレータ版の search を比べてみます。

イテレータのほうがわずかに速いくらいです。イテレータは Rust のゼロコスト抽象化の 1 つで、高レベルな書き方をしても、手で最適化した低レベルのコードと同等の機械語にコンパイルされます。

深掘りゼロコスト抽象化の中身

C++ の設計者ビャーネ・ストロヴストルップは、ゼロオーバーヘッドの原則をこう表現しました。

使わないものにはコストを払わない。そして、使うものについては、手書きしてもそれ以上にはうまく書けない。

例えば、音声デコーダの中の次のようなコードがあります。

Rust
let buffer: &mut [i32];let coefficients: [i64; 12];let qlp_shift: i16; for i in 12..buffer.len() {    let prediction = coefficients.iter()                                 .zip(&buffer[i - 12..i])                                 .map(|(&c, &s)| c * s as i64)                                 .sum::<i64>() >> qlp_shift;    let delta = buffer[i];    buffer[i] = prediction as i32 + delta;}

zip、map、sum とアダプタを重ねていますが、コンパイラは coefficients が 12 要素だとわかっているので、ループを展開（unroll）して 12 回分の計算を直接並べます。係数はすべてレジスタに置かれ、範囲チェックも消えます。抽象的に書いても、速度を犠牲にしなくてよいのです。

13.5この章のまとめ

  • クロージャは環境をキャプチャできる無名関数。キャプチャの方法（借用・可変借用・ムーブ）は本体の使い方で決まる
  • クロージャは FnOnce / FnMut / Fn のうち 1 つ以上を自動で実装する
  • イテレータは怠惰。next を呼ぶ消費アダプタ（sum, collect など）で初めて動く
  • map, filter などのアダプタをつなぐと、何をしたいかがそのまま表現できる
  • イテレータはゼロコスト抽象化で、手書きのループと同じ速さ
