## VPC はグローバル、サブネットはリージョン {#global-vpc}

[第 8 章](ch08.html)では、VM を作ると内部 IP と外部 IP が付くのを見ました。その内部 IP は、どこから来たのでしょう。答えは **VPC ネットワーク**（Virtual Private Cloud。Google のデータセンターの中に作る、自分専用の仮想のネットワーク）です。VM は必ず、どれか 1 つの VPC につながっています。

```fig graph VPC はプロジェクトの中の「グローバル」なリソース。その下に、リージョンごとのサブネット（IP アドレスの範囲）がある
{
  col: 200, row: 96,
  nodes: [
    { id: 't', label: 'サブネット shop-tokyo', sub: 'asia-northeast1　10.10.0.0/24', x: 0, y: 0, kind: 'stack', mono: false },
    { id: 'o', label: 'サブネット shop-osaka', sub: 'asia-northeast2　10.20.0.0/24', x: 2, y: 0, kind: 'stack', mono: false },
    { id: 'vt', label: 'VM web1', sub: '10.10.0.2', x: 0, y: 1, kind: 'crate', mono: false },
    { id: 'vo', label: 'VM batch2', sub: '10.20.0.2', x: 2, y: 1, kind: 'crate', mono: false },
    { id: 'fw', label: 'ファイアウォールのルール', sub: 'VPC 全体に効く', x: 1, y: 0, kind: 'accent', mono: false },
  ],
  edges: [
    { from: 'vt', to: 'vo', label: '内部 IP でそのまま届く', both: true, style: 'accent' },
    { from: 't', to: 'vt' }, { from: 'o', to: 'vo' },
  ],
  groups: [{ label: 'VPC ネットワーク shop-vpc（グローバル）', nodes: ['t', 'o', 'vt', 'vo', 'fw'], kind: 'crate' }],
}
```

- **VPC はグローバル**です。1 つの VPC が、東京にも大阪にもアイオワにも広がります。リージョンをまたいでも、VM どうしは内部 IP のまま通信できます
- **サブネットはリージョン**のリソースです。サブネットは「このリージョンでは、この範囲の IP アドレスを使う」という決まりです。VM は、自分のゾーンがあるリージョンのサブネットから内部 IP をもらいます

この章の準備では、Compute Engine API を有効にして、既定のリージョンを東京にしてあります。Cloud Storage のバケットも 1 つ作ってあります（後の節で使います）。まず、いまあるネットワークを見ます。

```sh setup
gcloud services enable compute.googleapis.com
gcloud config set compute/region asia-northeast1
gcloud config set compute/zone asia-northeast1-b
gcloud storage buckets create gs://tsubame-shop-ch09-files --location=asia-northeast1
echo "注文の集計 2026-11" > report.txt
gcloud storage cp report.txt gs://tsubame-shop-ch09-files/
```

```sh run title="ネットワークの一覧"
gcloud compute networks list
```

`default` という名前のネットワークが 1 つあります。これは、Compute Engine API を有効にしたときに自動で作られたものです。`SUBNET_MODE` が `AUTO` になっています。この意味を次の節で見ます。

## default ネットワークと既定のルール {#default-network}

`default` は **自動モード**（auto mode）のネットワークです。自動モードでは、すべてのリージョンに 1 つずつ、決まった範囲のサブネットが自動で作られます。

```sh run title="default ネットワークのサブネット（最初の 4 つ）"
gcloud compute networks subnets list --network=default --format="table(region.basename(),ipCidrRange)" --limit=4
```

リージョンごとに `/20`（4,096 個のアドレス）の範囲が決まっています。東京（`asia-northeast1`）は `10.146.0.0/20` です。範囲を数で書くこの書き方を **CIDR**（サイダー）と呼びます。`/20` は「先頭の 20 ビットが同じアドレス」の意味で、数が小さいほど範囲が広くなります。

自動モードのサブネットは、どれも `10.128.0.0/9` という大きな範囲の中から割り当てられます。`default` には、もう 1 つ自動で作られたものがあります。ファイアウォールのルールです。

```sh run title="default ネットワークのファイアウォールのルール"
gcloud compute firewall-rules list
gcloud compute firewall-rules list --format="table(name,sourceRanges.list():label=SRC_RANGES)"
```

4 つのルールがあります。どれも `INGRESS`（外から VM へ入ってくる通信）を **許可** するルールです。

| ルール | 許可するもの | 送信元 |
| --- | --- | --- |
| `default-allow-internal` | TCP・UDP の全ポートと ICMP | `10.128.0.0/9`（default の全サブネット） |
| `default-allow-ssh` | TCP 22（SSH） | `0.0.0.0/0`（どこからでも） |
| `default-allow-rdp` | TCP 3389（Windows のリモートデスクトップ） | `0.0.0.0/0` |
| `default-allow-icmp` | ICMP（ping） | `0.0.0.0/0` |

`default` に作った VM にすぐ `gcloud compute ssh` で入れるのは、`default-allow-ssh` があるからです。逆に、80 番（HTTP）を許可するルールはありません。Web サーバーを公開するには、ルールを足す必要があります。

:::warn default は試すためのもの
`default-allow-ssh` と `default-allow-rdp` は、インターネットの**どこからでも** 22 番と 3389 番に届くルールです。世界中から、パスワードを当てる試みが絶えず来ます。また、自動モードの範囲（`10.128.0.0/9`）は、社内のネットワークや別の VPC とつなぐときに重なりやすい範囲です。本番では `default` を使わず、次の節のカスタムモードで、範囲とルールを自分で決めます。組織のポリシーで、新しいプロジェクトに `default` を作らないようにもできます。
:::

## カスタムモードで自分の VPC を作る {#custom-mode}

**カスタムモード**（custom mode）のネットワークは、サブネットを 1 つも持たずに生まれます。どのリージョンに、どの範囲のサブネットを置くかを、自分で決めます。つばめ文具の店のために、`shop-vpc` を作ります。

```sh run title="カスタムモードのネットワークを作る"
gcloud compute networks create shop-vpc --subnet-mode=custom
```

出力の後半の注意は「ファイアウォールのルールを作るまで、このネットワークの VM には届かない」です。次の節で確かめます。東京と大阪に、サブネットを 1 つずつ作ります。範囲は、つばめ文具の社内のネットワークと重ならないように `10.10.0.0/24` と `10.20.0.0/24` にします（それぞれ 256 個のアドレス）。

```sh run title="東京と大阪のサブネット"
gcloud compute networks subnets create shop-tokyo --network=shop-vpc --region=asia-northeast1 --range=10.10.0.0/24
gcloud compute networks subnets create shop-osaka --network=shop-vpc --region=asia-northeast2 --range=10.20.0.0/24
gcloud compute networks describe shop-vpc --format="yaml(subnetworks)"
```

`REGION` の列が別々でも、`NETWORK` はどちらも `shop-vpc` です。最後の `describe` は、ネットワークの側から見たサブネットの一覧です。URL の中の `regions/asia-northeast1` と `regions/asia-northeast2` が、サブネットのリージョンです。ネットワーク自身の URL は `global/networks/shop-vpc` で、リージョンを持ちません。

### 範囲が重なると作れない

1 つの VPC の中では、サブネットの範囲は重なってはいけません。同じアドレスが 2 か所にあると、どちらに届ければよいか決まらないからです。リージョンが違っても同じです。

```sh run error title="東京の範囲と重なる範囲で、サブネットを作ろうとする"
gcloud compute networks subnets create shop-osaka-2 --network=shop-vpc --region=asia-northeast2 --range=10.10.0.128/25
```

`10.10.0.128/25` は、`10.10.0.0/24` の後ろ半分です。エラーの文が、重なった相手（`'shop-tokyo' in region 'asia-northeast1'`）を教えてくれます。直すには、`10.30.0.0/24` のように重ならない範囲を選びます。

## ファイアウォールは、何も書かなければ拒否 {#implicit-deny}

`shop-vpc` に VM を 2 台作ります。`web1` には `web` という**ネットワークタグ**（VM に付ける目印の文字列）を付けます。`app1` にはタグを付けません。どちらも、起動時に nginx（Web サーバー）を入れます。

```sh run title="shop-vpc に VM を 2 台"
gcloud compute instances create web1 --network=shop-vpc --subnet=shop-tokyo --tags=web --metadata=startup-script='apt-get install -y nginx'
gcloud compute instances create app1 --network=shop-vpc --subnet=shop-tokyo --metadata=startup-script='apt-get install -y nginx'
WEB1=$(gcloud compute instances describe web1 --format="value(networkInterfaces[0].accessConfigs[0].natIP)")
APP1=$(gcloud compute instances describe app1 --format="value(networkInterfaces[0].accessConfigs[0].natIP)")
```

カスタムモードのネットワークでは、`--subnet` でサブネットを選びます。内部 IP は、`web1` が `10.10.0.2`、`app1` が `10.10.0.3` になりました。サブネットの範囲 `10.10.0.0/24` の中から、順に配られています（`.0` と `.1` は、ネットワーク自身とゲートウェイに予約されています）。

後ろの 2 行は、2 台の外部 IP をシェルの変数 `WEB1` と `APP1` に入れています。届かないとき、curl は長いあいだ待ち続けます。そこで `--connect-timeout 3`（3 秒でつながらなければあきらめる）を付けます。`-sS` は「進み具合は出さず、エラーだけは出す」です。

```sh run error title="Cloud Shell から web1 の 80 番へ"
curl -sS --connect-timeout 3 http://$WEB1
```

`Timeout was reached` で終わりました。nginx は動いているのに届かないのは、`shop-vpc` にファイアウォールのルールが 1 つもないからです。

```fig graph どの VPC にも、消せない 2 つの「暗黙のルール」がある。自分で書いたルールは、この上に重なる
{
  col: 230, row: 90,
  nodes: [
    { id: 'net', label: 'インターネット / 他の VM', x: 0, y: 0, mono: false },
    { id: 'vm', label: 'VM', sub: 'shop-vpc の中', x: 2, y: 0, kind: 'crate', mono: false },
    { id: 'in', label: '暗黙の拒否（入り）', sub: 'INGRESS　すべて deny　優先度 65535', x: 1, y: 0, kind: 'bad', mono: false },
    { id: 'out', label: '暗黙の許可（出）', sub: 'EGRESS　すべて allow　優先度 65535', x: 1, y: 1, kind: 'accent', mono: false },
  ],
  edges: [
    { from: 'net', to: 'in', label: '入ってくる' },
    { from: 'vm', to: 'out', label: '出ていく', style: 'accent' },
  ],
}
```

- **入ってくる通信（INGRESS）は、すべて拒否**。許可するルールに当てはまったものだけが通ります
- **出ていく通信（EGRESS）は、すべて許可**。VM からインターネットへ出るのは、ルールなしで通ります

この 2 つは**暗黙のルール**と呼ばれ、一覧には出ず、消すこともできません。`default` に最初から 4 つのルールがあったのは、この「入りは全部拒否」の上に、よく使う許可を重ねておいたからです。

拒否された通信には、返事がありません。だから curl は「断られた」ではなく「時間切れ」で終わります。いま `gcloud compute ssh web1` を打っても、`ssh: connect to host … port 22: Connection timed out` です。「Connection refused」（相手が断った）ではなく timed out（返事がない）なら、まずファイアウォールを疑います。

### SSH と、VPC の中どうしを許可する

SSH（TCP 22）を許可するルールを作ります。`--network` を書かないと `default` に作られてしまうので、必ず書きます。

```sh run title="SSH を許可する"
gcloud compute firewall-rules create shop-allow-ssh --network=shop-vpc --allow=tcp:22
gcloud compute ssh web1 --command="hostname -I"
```

`--source-ranges` を書かないと、送信元は `0.0.0.0/0`（どこからでも）になります。これで入れました。`hostname -I` が VM の内部 IP `10.10.0.2` を出しています。

次は、VM どうしです。`web1` の中から、`app1` の**内部 IP** に curl を打ちます。

```sh run error title="web1 から app1 の内部 IP へ"
gcloud compute ssh web1 --command="curl -sS --connect-timeout 3 http://10.10.0.3"
```

同じサブネットにいても、届きません。暗黙の拒否は、VPC の中から来た通信にも効くからです。VPC の中どうしを許可するルールを足します。送信元は、`shop-vpc` の 2 つのサブネットの範囲です。

```sh run title="VPC の中どうしを許可する"
gcloud compute firewall-rules create shop-allow-internal --network=shop-vpc --allow=tcp,udp,icmp --source-ranges=10.10.0.0/24,10.20.0.0/24
gcloud compute ssh web1 --command="curl -sS --connect-timeout 3 http://10.10.0.3 | head -4"
```

`Welcome to nginx!` が返りました。`--allow=tcp` のようにポートを書かないと、そのプロトコルの全ポートを許可します。

内部 IP は、VPC の外からは使えません。Cloud Shell は `shop-vpc` の中にいないので、Cloud Shell で `curl http://10.10.0.3` を打っても、ルールに関係なく届きません。

:::note このサイトの GCP では
ルールの判定は、入ってくる通信（INGRESS）だけをまねています。EGRESS のルール（出ていく通信を止めるルール）は作れますが、判定には使いません。また、`gcloud compute ssh` は `--command="…"` で 1 回だけコマンドを実行する使い方だけに対応しています。
:::

## タグで的を絞り、優先度で順番を決める {#tags-priority}

`web1` は Web サーバーとして、インターネットに公開したい VM です。`app1` は公開したくありません。そこで、80 番を許可するルールを、`web` タグの付いた VM だけに効かせます。

```sh run title="web タグの VM にだけ、80 番を許可する"
gcloud compute firewall-rules create shop-allow-http --network=shop-vpc --allow=tcp:80 --target-tags=web
curl -sS --connect-timeout 3 http://$WEB1 | head -4
```

`--target-tags=web` が**ターゲットタグ**です。ルールが「どの VM を守るか（どの VM へ入る通信か）」を決めます。書かなければ、ネットワークのすべての VM が対象です。`app1` には `web` タグがないので、届かないままです。

```sh run error title="タグのない app1 には届かない"
curl -sS --connect-timeout 3 http://$APP1
```

いまの `shop-vpc` のルールは、`gcloud compute firewall-rules list --filter="network:shop-vpc"` で一覧できます。1 つのルールは、次の 4 つで「どの通信に当てはまるか」を決めます。

| 項目 | フラグ | 書かなかったとき |
| --- | --- | --- |
| 向き | `--direction` | `INGRESS`（入ってくる通信） |
| 宛先の VM | `--target-tags`（または `--target-service-accounts`） | ネットワークのすべての VM |
| 送信元 | `--source-ranges`（または `--source-tags`） | `0.0.0.0/0`（どこからでも） |
| プロトコルとポート | `--allow` / `--rules` | 省略できない |

ここまでに作ったルールは、どれも出力の `PRIORITY` が `1000` でした。これが、`gcloud` で作ったルールの既定の優先度です。

### 優先度と deny

ルールには、許可（allow）のほかに**拒否**（deny）もあります。許可と拒否の両方に当てはまる通信は、どうなるのでしょう。決めるのは**優先度**（priority）です。0 から 65535 までの数で、**小さいほど強い**。


確かめます。Cloud Shell の外向きの IP（`34.146.93.21`）からの 80 番を拒否するルールを、優先度 900 で作ります。`/32` は「この 1 つのアドレスだけ」の意味です。

```sh run title="優先度 900 の deny"
gcloud compute firewall-rules create shop-deny-cs --network=shop-vpc --action=deny --rules=tcp:80 --source-ranges=34.146.93.21/32 --priority=900
```

拒否のルールは `--allow` ではなく、`--action=deny` と `--rules` で書きます。出力の `DENY` の列に `tcp:80` が出ました。もう一度 curl を打ちます。

```sh run error title="deny に当たって届かない"
curl -sS --connect-timeout 3 http://$WEB1
```

`shop-allow-http` があるのに、届かなくなりました。優先度を `firewall-rules update` で 1100 に下げると、1000 の allow が先に当たるようになります。確かめ終わったら、deny のルールは消しておきます。

```sh run title="deny を 1100 に下げて、消す"
gcloud compute firewall-rules update shop-deny-cs --priority=1100
curl -sS --connect-timeout 3 -o /dev/null -w "%{http_code}\n" http://$WEB1
gcloud compute firewall-rules delete shop-deny-cs --quiet
```

`-o /dev/null -w "%{http_code}\n"` は、中身を捨てて HTTP の状態コードだけを出す curl の書き方です。`200` が返りました。途中で優先度を allow と同じ 1000 にすると、図の 2 段目のとおり、まだ届きません。同じ優先度では deny が勝つからです。

:::deep ステートフルなので、返事は止まらない
VPC のファイアウォールは**ステートフル**（つながりを覚えている）です。入ってくる通信を許可すれば、その返事（VM から出ていくパケット）は、EGRESS のルールとは関係なく通ります。逆に、VM から外へ出た通信の返事も、INGRESS の許可がなくても戻ってきます。だから、外へ出るだけの VM には、INGRESS のルールは 1 つも要りません。
:::

## 外部 IP のない VM と、IAP 経由の SSH {#iap}

外部 IP を持つ VM は、インターネットから直接ねらわれます。ルールで守っていても、設定を 1 つ間違えれば外に開きます。そこで、公開する必要のない VM には、**外部 IP を付けない**のがふつうです。そういう VM に Cloud Shell から入るには、**IAP**（Identity-Aware Proxy）の TCP 転送を使います。

```fig seq IAP 経由の SSH。Cloud Shell は Google の IAP に HTTPS でつなぎ、IAP が VPC の中の VM の 22 番へ転送する
{
  actors: [
    { id: 'cs', label: 'Cloud Shell' },
    { id: 'iap', label: 'IAP', kind: 'accent' },
    { id: 'fw', label: 'ファイアウォール' },
    { id: 'vm', label: 'batch1（内部 IP だけ）' },
  ],
  msgs: [
    { from: 'cs', to: 'iap', label: 'HTTPS で接続。IAM で「入ってよい人か」を調べる' },
    { from: 'iap', to: 'fw', label: '送信元 35.235.240.0/20 から tcp:22' },
    { note: 'この範囲を許可するルールが要る', at: 'fw' },
    { from: 'fw', to: 'vm', label: '許可されれば 22 番へ' },
    { from: 'vm', to: 'cs', label: 'SSH の返事（IAP を通って戻る）', style: 'dashed' },
  ],
}
```

IAP は、Google の側にある「入口の番人」です。Cloud Shell は IAP に HTTPS でつなぎ、IAP が IAM で本人と権限を確かめてから、VM の 22 番へ転送します。VM から見ると、SSH は **`35.235.240.0/20`** という IAP の範囲から来ます。外部 IP のない VM を `--no-address` で作り、`--tunnel-through-iap` を付けて入ってみます。

```sh run title="外部 IP のない VM に、IAP 経由で入る"
gcloud compute instances create batch1 --network=shop-vpc --subnet=shop-tokyo --no-address
gcloud compute ssh batch1 --tunnel-through-iap --command="hostname -I"
```

`EXTERNAL_IP` の列が空の VM に、入れました。いまは `shop-allow-ssh` が送信元 `0.0.0.0/0` で 22 番を許可しているので、IAP の範囲も含まれているからです。でも、これでは外部 IP を持つ `web1` の 22 番が、世界中に開いたままです。`shop-allow-ssh` を消して、IAP の範囲だけを許可するルールに置き換えます。

```sh run title="どこからでもの SSH を消す"
gcloud compute firewall-rules delete shop-allow-ssh --quiet
```

```sh run error title="ルールがなければ、IAP でも届かない"
gcloud compute ssh batch1 --tunnel-through-iap --command="hostname"
```

`failed to connect to backend` は、「IAP までは来たが、その先の VM の 22 番に届かなかった」という意味です。IAP の範囲を許可します。

```sh run title="IAP の範囲（35.235.240.0/20）からの SSH だけを許可する"
gcloud compute firewall-rules create shop-allow-iap-ssh --network=shop-vpc --allow=tcp:22 --source-ranges=35.235.240.0/20
gcloud compute ssh batch1 --tunnel-through-iap --command="hostname"
gcloud compute ssh web1 --tunnel-through-iap --command="hostname"
```

`batch1` にも `web1` にも、IAP 経由でだけ入れるようになりました。`--tunnel-through-iap` を付けずに `web1` の外部 IP へ直接 SSH すると、もう `Connection timed out` になります。

:::note IAP にも IAM の権限が要る
本物の IAP では、ファイアウォールのほかに、使う人が IAM のロール **IAP-secured Tunnel User**（`roles/iap.tunnelResourceAccessor`）を持っている必要があります。プロジェクトのオーナーは持っています。このサイトの GCP では、IAP の IAM の判定は省いています。
:::

## Cloud NAT：外部 IP なしで外へ出る {#cloud-nat}

外部 IP のない `batch1` で、パッケージを入れてみます。

```sh run error title="batch1 で apt-get"
gcloud compute ssh batch1 --tunnel-through-iap --command="sudo apt-get install -y nginx"
```

`Could not connect to deb.debian.org:443 … connection timed out` です。EGRESS は暗黙に許可されているのに、なぜ出られないのでしょう。ファイアウォールの問題ではありません。**インターネットに出るための住所がない**のです。`10.10.0.4` のような内部 IP は、インターネットの中では意味を持たないので、返事が戻ってこられません。

ただし、VPC の中には出られます。内部 IP どうしの通信には、外部 IP は要りません（`batch1` から `curl http://10.10.0.2` を打てば、`web1` の nginx が返ります）。

インターネットへ出る道を作るのが **Cloud NAT** です。NAT（ネットワークアドレス変換）は、VM の内部 IP を、NAT が持つ外部 IP に付け替えて外へ出し、返事を元の VM へ戻します。外から VM へ新しく入ってくる道は作りません。

```fig graph 外部 IP のない VM から外への 3 つの行き先。Cloud NAT があると、インターネットにも Google の API にも出られる
{
  col: 210, row: 92,

    { id: 'vm', label: 'batch1', sub: '10.10.0.4　外部 IP なし', x: 0, y: 1, kind: 'crate', mono: false },
```

Cloud NAT は、**Cloud Router**（リージョンごとの、経路を扱う仮想のルーター）に付ける形で作ります。どちらもリージョンのリソースです。

```sh run title="Cloud Router と Cloud NAT を作る"
gcloud compute routers create shop-router --network=shop-vpc --region=asia-northeast1
gcloud compute routers nats create shop-nat --router=shop-router --region=asia-northeast1 --auto-allocate-nat-external-ips --nat-all-subnet-ip-ranges
```

- `--auto-allocate-nat-external-ips`：NAT が使う外部 IP を、Google に自動で割り当ててもらう
- `--nat-all-subnet-ip-ranges`：このリージョンの、このネットワークのすべてのサブネットを NAT の対象にする

もう一度、`apt-get` です。

```sh run title="NAT があれば apt-get が通る"
gcloud compute ssh batch1 --tunnel-through-iap --command="sudo apt-get install -y nginx"
gcloud compute ssh batch1 --tunnel-through-iap --command="curl -sS --connect-timeout 3 ifconfig.me; echo"
```

`Setting up nginx …` まで進み、nginx が入りました。`ifconfig.me` は、自分がどの IP から来たように見えるかを返すサイトです。出たのは `batch1` の内部 IP ではなく、NAT に割り当てられた外部 IP です。インターネットの側からは、この IP しか見えません。

## 限定公開の Google アクセス {#private-google-access}

Cloud NAT はリージョンのリソースです。東京に作った `shop-nat` は、大阪のサブネットには効きません。大阪の `shop-osaka` に、外部 IP のない VM を作って確かめます。

```sh run title="大阪に、外部 IP のない VM"
gcloud compute instances create batch2 --zone=asia-northeast2-a --network=shop-vpc --subnet=shop-osaka --no-address
```

この VM から、準備で作ったバケットを読みます。VM の中の `gcloud` は、VM のサービスアカウント（第 8 章）として動きます。

```sh run error title="batch2 から Cloud Storage を読む"
gcloud compute ssh batch2 --zone=asia-northeast2-a --tunnel-through-iap --command="gcloud storage ls gs://tsubame-shop-ch09-files"
```

`gcloud crashed (ConnectionError)` と、`storage.googleapis.com` に `Connection timed out` です。権限の問題（`403`）ではなく、**つながらない**という問題です。Cloud Storage の API の入口（`storage.googleapis.com`）は、インターネットの側にあります。外部 IP も NAT もない VM からは、そこへ行く道がありません。

Google の API に行きたいだけなら、NAT を作らなくても済みます。**限定公開の Google アクセス**（Private Google Access）を、サブネットで有効にします。

```sh run title="限定公開の Google アクセスを有効にして、もう一度読む"
gcloud compute networks subnets update shop-osaka --region=asia-northeast2 --enable-private-ip-google-access
gcloud compute networks subnets describe shop-osaka --region=asia-northeast2 --format="value(privateIpGoogleAccess)"
gcloud compute ssh batch2 --zone=asia-northeast2-a --tunnel-through-iap --command="gcloud storage ls gs://tsubame-shop-ch09-files"
gcloud compute ssh batch2 --zone=asia-northeast2-a --tunnel-through-iap --command="gcloud storage cat gs://tsubame-shop-ch09-files/report.txt"
```

`privateIpGoogleAccess` が `True` になり、バケットが読めました。これはサブネットの設定なので、VM を作り直す必要はありません。通信はインターネットに出ず、Google のネットワークの中だけを通って API に届きます。ただし、開くのは Google の API への道だけです。`batch2` で `apt-get install` を打つと、いまも `connection timed out` で失敗します。

最後に、VPC がグローバルであることを確かめます。大阪の `batch2` から、東京の `web1` の内部 IP へ curl を打ちます。

```sh run title="大阪の VM から、東京の VM の内部 IP へ"
gcloud compute ssh batch2 --zone=asia-northeast2-a --tunnel-through-iap --command="curl -sS --connect-timeout 3 http://10.10.0.2 | head -4"
```

リージョンをまたいでも、VPN も特別な設定も要りません。`shop-allow-internal` が `10.20.0.0/24` からの通信を許可しているので、そのまま届きます。

| 通信 | 外部 IP あり | 外部 IP なし + Cloud NAT | 外部 IP なし + 限定公開の Google アクセス |
| --- | --- | --- | --- |
| VM → 同じ VPC の VM（内部 IP） | 届く | 届く | 届く |
| VM → Google の API | 届く | 届く | 届く |
| VM → インターネット | 届く | 届く | 届かない |
| インターネット → VM | ルールしだい | 届かない | 届かない |

:::try やってみよう
`shop-vpc` を消そうとすると、何が起きるでしょう。`gcloud compute networks delete shop-vpc --quiet` を実行して、エラーの文が「何に使われているか」を教えてくれることを確かめてください。VM、ファイアウォールのルール、サブネットを先に消さないと、ネットワークは消せません。
:::

```sh run error title="使われているネットワークは消せない"
gcloud compute networks delete shop-vpc --quiet
```

:::key まとめ
- VPC ネットワークはグローバル、サブネットはリージョンのリソース。リージョンをまたいでも、VM どうしは内部 IP で通信できる
- `default` は自動モード。全リージョンに `10.128.0.0/9` の中のサブネットと、SSH・RDP・ICMP を世界に開くルールがある。本番ではカスタムモードで、範囲を自分で決める。サブネットの範囲は VPC の中で重なってはいけない
- ファイアウォールには、消せない「入りは全部拒否、出は全部許可」がある。ルールは、向き・ターゲットタグ・送信元の範囲・プロトコルとポートで当てはまる通信を決め、優先度の小さいものが勝つ。同じ優先度なら deny が勝つ
- 外部 IP のない VM へは、`35.235.240.0/20` からの 22 番を許可して、IAP 経由で SSH する
- 外部 IP のない VM がインターネットへ出るには Cloud NAT（リージョンごと）、Google の API だけなら限定公開の Google アクセス（サブネットの設定）
:::

## 確認問題 {#quiz}

ネットワーク、サブネット、ファイアウォールのルール、Cloud NAT を、自分のコマンドで作って確かめます。どの問題も、Compute Engine API は有効で、既定のリージョンは `asia-northeast1`、ゾーンは `asia-northeast1-b` です。

:::quiz lab-vpc のサブネット
カスタムモードのネットワーク `lab-vpc` に、いくつかのサブネットが作ってあります。`lab-vpc` のサブネットだけについて、**リージョンの名前と範囲**を、1 行に 1 つ（リージョン、タブ、範囲の順）表示してください。行の順番は問いません。

```sh prep
gcloud compute networks create lab-vpc --subnet-mode=custom
gcloud compute networks subnets create lab-a --network=lab-vpc --region=asia-northeast1 --range=10.30.0.0/24
gcloud compute networks subnets create lab-b --network=lab-vpc --region=us-central1 --range=10.31.0.0/24
```

```sh vary
gcloud compute networks subnets create lab-c --network=lab-vpc --region=europe-west1 --range=10.32.0.0/22
```

```sh answer unordered
gcloud compute networks subnets list --network=lab-vpc --format="value(region.basename(),ipCidrRange)"
```

:::

:::quiz API サーバーへの入口を開ける
ネットワーク `lab-vpc` に、ファイアウォールのルール `lab-allow-api` を作ってください。条件は次のとおりです。

- ネットワークタグ `api` の付いた VM にだけ効く
- 送信元は `10.30.0.0/24` だけ
- TCP の 8080 番だけを許可する

```sh prep
gcloud compute networks create lab-vpc --subnet-mode=custom
gcloud compute networks subnets create lab-a --network=lab-vpc --region=asia-northeast1 --range=10.30.0.0/24
```

```sh answer
gcloud compute firewall-rules create lab-allow-api --network=lab-vpc --allow=tcp:8080 --source-ranges=10.30.0.0/24 --target-tags=api
```

```sh check
gcloud compute firewall-rules describe lab-allow-api --format="yaml(allowed,direction,network.basename(),priority,sourceRanges,targetTags)"
```

:::hint
許可は `--allow=プロトコル:ポート`、送信元は `--source-ranges`、効かせる VM は `--target-tags` です。`--network` を忘れると `default` に作られます。
:::
:::

:::quiz web1 にだけ届くようにする
ネットワーク `lab-vpc` に、VM が 2 台あります。`web1`（タグ `web`）と `db1`（タグ `db`）で、どちらも 80 番で nginx が動いています。ファイアウォールのルールを 1 つ作って、**Cloud Shell から `web1` の外部 IP の 80 番には届き、`db1` には届かない**ようにしてください。ルールの名前は自由です。

```sh prep
gcloud compute networks create lab-vpc --subnet-mode=custom
gcloud compute networks subnets create lab-a --network=lab-vpc --region=asia-northeast1 --range=10.30.0.0/24
gcloud compute instances create db1 --network=lab-vpc --subnet=lab-a --tags=db --metadata=startup-script='apt-get install -y nginx'
gcloud compute instances create web1 --network=lab-vpc --subnet=lab-a --tags=web --metadata=startup-script='apt-get install -y nginx'
sleep 30
```

```sh answer
gcloud compute firewall-rules create lab-allow-http --network=lab-vpc --allow=tcp:80 --target-tags=web
```

```sh check
for v in web1 db1; do ip=$(gcloud compute instances describe $v --format="value(networkInterfaces[0].accessConfigs[0].natIP)"); curl -s -o /dev/null --connect-timeout 2 -w "$v %{http_code}\n" http://$ip || echo "$v timeout"; done
```

:::

:::quiz 外部 IP のない VM から apt-get
ネットワーク `lab-vpc` の東京のサブネット `lab-a` に、外部 IP のない VM `worker` があります。IAP 経由の SSH は許可してあります。`worker` の中で `sudo apt-get install -y nginx` が成功するようにしてください（VM は作り直さないこと）。

```sh prep
gcloud compute networks create lab-vpc --subnet-mode=custom
gcloud compute networks subnets create lab-a --network=lab-vpc --region=asia-northeast1 --range=10.30.0.0/24
gcloud compute firewall-rules create lab-allow-iap-ssh --network=lab-vpc --allow=tcp:22 --source-ranges=35.235.240.0/20
gcloud compute instances create worker --network=lab-vpc --subnet=lab-a --no-address
```

```sh answer
gcloud compute routers create lab-router --network=lab-vpc --region=asia-northeast1
gcloud compute routers nats create lab-nat --router=lab-router --region=asia-northeast1 --auto-allocate-nat-external-ips --nat-all-subnet-ip-ranges
```

```sh check
gcloud compute ssh worker --tunnel-through-iap --command="sudo apt-get install -y nginx > apt.log 2>&1 && echo ok || echo ng"
```

:::hint
インターネットへ出る道が要ります。Cloud NAT は Cloud Router に付けて作り、VM と同じリージョンに置きます。限定公開の Google アクセスで開くのは、Google の API への道だけです。
:::
:::
