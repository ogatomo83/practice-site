## BigQuery は何をするところか {#what}

**BigQuery**（ビッグクエリ）は、大量のデータを SQL で集計するためのサービスです。こうしたサービスを**データウェアハウス**（分析用のデータの倉庫）と呼びます。サーバーを用意する必要はありません。テーブルにデータを入れて SQL を投げれば、Google の側で何台もの計算機が手分けして答えを返します。

第 14 章の Cloud SQL も SQL を使います。違いは得意なことです。Cloud SQL は「注文を 1 件ずつ書き込み、1 件ずつ読む」アプリの仕事に向きます。BigQuery は「1 年分の注文を月ごと・経路ごとに合計する」ような、たくさんの行をまとめて読む仕事に向きます。

BigQuery の入れ物は 3 段です。**プロジェクト**の中に**データセット**（テーブルをまとめる入れ物。場所と権限の単位）があり、その中に**テーブル**と**ビュー**があります。

```fig graph BigQuery の入れ物。データセットが場所（ロケーション）と権限の単位になる
{
  col: 200, row: 80,
  nodes: [
    { id: 'p', label: 'tsubame-public', sub: 'プロジェクト', x: 0, y: 1, kind: 'stack', mono: false },
    { id: 'ds', label: 'bungu', sub: 'データセット（asia-northeast1）', x: 1, y: 1, kind: 'accent', mono: false },
    { id: 't1', label: 'products', sub: '商品 17 行', x: 2.2, y: 0, kind: 'crate', mono: false },
    { id: 't2', label: 'customers', sub: '顧客 60 行', x: 2.2, y: 1, kind: 'crate', mono: false },
    { id: 't3', label: 'orders', sub: '注文 2,183 行（日ごとのパーティション）', x: 2.2, y: 2, kind: 'crate', mono: false },
  ],
  edges: [ { from: 'p', to: 'ds' }, { from: 'ds', to: 't1' }, { from: 'ds', to: 't2' }, { from: 'ds', to: 't3' } ],
}
```

この章では、つばめ文具が公開している練習用のデータ `tsubame-public.bungu` を使います。BigQuery には、Google や各団体がだれでも読めるように置いている**公開データセット**があり、これはその模型です。中身は架空の販売データで、2026 年 1 月から 10 月までの注文が入っています。

コマンドは **`bq`**（ビーキュー）を使います。gcloud と同じく Cloud Shell に入っている、BigQuery 専用のコマンドです。

```sh run title="データセットとテーブルの一覧"
bq ls --project_id=tsubame-public
bq ls tsubame-public:bungu
```

1 つ目は `tsubame-public` のデータセットの一覧、2 つ目は `bungu` の中のテーブルの一覧です。`orders` の行には `DAY (field: order_date)` と `channel` が出ています。注文日で日ごとに分けてあり（パーティション）、経路で並べてある（クラスタ）という意味です。どちらも料金に関わるので、後の節で使います。

bq では、テーブルを `プロジェクト:データセット.テーブル` と書きます。SQL の中では `` `プロジェクト.データセット.テーブル` `` とバッククォートで囲み、すべて `.` で区切ります。書き方が 2 通りあるのは歴史の名残です。

```sh run title="テーブルの形と、最初の数行"
bq show tsubame-public:bungu.orders
bq head -n 5 tsubame-public:bungu.orders
```

`bq show` の `Schema` が列の名前と型です。`Total Rows` が 2183 行、`Total Bytes` が 117079 バイトです。`bq head` は、SQL を使わずに最初の数行を見せます。本物では、`bq head` のようなテーブルのプレビューはクエリではないので、処理したバイト数の料金はかかりません（公式ドキュメントを参照）。

## bq query と、標準 SQL {#query}

SQL を投げるのは `bq query` です。注文の数を数えてみます。まず、よくある失敗から見ます。

```sh run title="フラグを付け忘れる" error
bq query 'SELECT COUNT(*) FROM `tsubame-public.bungu.orders`'
```

`Invalid table name` と出て、最後に `[Try using standard SQL ...]` とあります。テーブルの名前は正しいのに、なぜでしょうか。

bq の `query` は、何も指定しないと**レガシー SQL**（BigQuery の初期の独自の SQL）として読みます。レガシー SQL ではテーブルを `[tsubame-public:bungu.orders]` と書くので、バッククォートの名前が分からないのです。いまの SQL（**GoogleSQL**。以前は標準 SQL と呼ばれていました）で読ませるには、`--use_legacy_sql=false` を付けます。

```sh run title="GoogleSQL で数える"
bq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-public.bungu.orders`'
```

2183 が返りました。上の `Waiting on bqjob_... Current status: DONE` は、クエリが 1 つの**ジョブ**（BigQuery に頼んだ仕事の単位）として実行されたという知らせです。ジョブには ID が付き、あとで記録を調べられます。

:::hist レガシー SQL と GoogleSQL
BigQuery は、最初はレガシー SQL だけを使っていました。あとから、ほかのデータベースに近い標準の SQL が加わり、今はそちらが推奨です（名前は GoogleSQL になりました）。コンソールや SDK の既定は GoogleSQL ですが、`bq query` の既定は互換のためレガシー SQL のままです。本物では、ホームディレクトリの `~/.bigqueryrc` に `[query]` と `--use_legacy_sql=false` を書いておくと、毎回付けずに済みます（このサイトの bq は `~/.bigqueryrc` を読まないので、毎回付けます）。
:::

月ごとに集計してみます。`FORMAT_DATE` は日付を文字列にする関数、`COUNTIF` は条件に合う行だけを数える関数です。どちらも GoogleSQL の関数です。

```sh run title="月ごとの注文数と売上"
bq query --use_legacy_sql=false 'SELECT FORMAT_DATE("%Y-%m", order_date) AS month, COUNT(*) AS orders, COUNTIF(channel = "web") AS web, SUM(quantity * unit_price) AS sales FROM `tsubame-public.bungu.orders` GROUP BY month ORDER BY month'
```

3 月と 4 月が多いのは、新学期の前だからでしょう。`web` の列は、Web の店からの注文の数です。GoogleSQL では文字列を `"web"` のように二重引用符でも書けるので、シェルの単一引用符の中に SQL を丸ごと入れられます。

SQL が長くなったら、ヒアドキュメント（`<<'SQL'` から `SQL` までを標準入力に渡す書き方）で渡すと読みやすくなります。`bq query` は、引数に SQL がなければ標準入力から読みます。

```sh run title="4 月のカテゴリ別の売上（テーブルを結合する）"
bq query --use_legacy_sql=false <<'SQL'
SELECT p.category,
       SUM(o.quantity * o.unit_price) AS sales
FROM `tsubame-public.bungu.orders` AS o
JOIN `tsubame-public.bungu.products` AS p USING (product_id)
WHERE o.order_date BETWEEN '2026-04-01' AND '2026-04-30'
GROUP BY p.category
ORDER BY sales DESC
SQL
```

`orders` と `products` を `product_id` で結合しました。万年筆が 3,200 円と高いので、ペンの売上がいちばん大きくなっています。

:::note このサイトの GCP では
BigQuery の SQL は、GoogleSQL を DuckDB（ブラウザで動くデータベース）の SQL に書き換えて実行しています。この章で使った関数（`COUNTIF`、`FORMAT_DATE`、`DATE_TRUNC`、`SAFE_DIVIDE`、`QUALIFY` など）は動くことを確かめてあります。書き換えに対応していない書き方は、エラーになったり、本物と違う結果になったりすることがあります。
:::

## 料金は「読んだ列のバイト数」で決まる {#bytes}

BigQuery のオンデマンド料金（使った分だけ払う方式）は、クエリが**処理したバイト数**で決まります。返した行の数でも、かかった時間でもありません。そして、読むのは**クエリで使った列だけ**です。これは、BigQuery がデータを**列指向**（列ごとにまとめて置く形）で持っているからです。

```fig layout 行指向と列指向。SELECT channel, quantity を実行したとき、読むところ（色付き）
{
  unit: 66,
  steps: [
    { title: '行指向', say: '1 行ぶんの値が並んで置かれる。2 つの列だけが欲しくても、行を丸ごと読むことになる。注文を 1 件ずつ出し入れするアプリには、この形が向く',
      rows: [
        { label: '注文 1', cells: [ { t: '100001', kind: 'accent' }, { t: '01-01', kind: 'accent' }, { t: '5', kind: 'accent' }, { t: 'web', kind: 'accent' } ] },
        { label: '注文 2', cells: [ { t: '100002', kind: 'accent' }, { t: '01-01', kind: 'accent' }, { t: '1', kind: 'accent' }, { t: 'web', kind: 'accent' } ] },
        { label: '注文 3', cells: [ { t: '100003', kind: 'accent' }, { t: '01-01', kind: 'accent' }, { t: '1', kind: 'accent' }, { t: 'web', kind: 'accent' } ] },
      ] },
    { title: '列指向（BigQuery）', say: '1 つの列の値が並んで置かれる。channel と quantity の 2 列だけを読めばよく、ほかの列は読まない。料金も読んだ列のぶんだけ',
      rows: [
        { label: 'order_id', cells: [ { t: '100001', kind: 'empty' }, { t: '100002', kind: 'empty' }, { t: '100003', kind: 'empty' } ], note: '読まない' },
        { label: 'order_date', cells: [ { t: '01-01', kind: 'empty' }, { t: '01-01', kind: 'empty' }, { t: '01-01', kind: 'empty' } ], note: '読まない' },
        { label: 'quantity', cells: [ { t: '5', kind: 'accent' }, { t: '1', kind: 'accent' }, { t: '1', kind: 'accent' } ], note: '読む' },
        { label: 'channel', cells: [ { t: 'web', kind: 'accent' }, { t: 'web', kind: 'accent' }, { t: 'web', kind: 'accent' } ], note: '読む' },
      ] },
  ],
}
```

実行する前に、何バイト処理するかを知る方法があります。**`--dry_run`**（予行演習）を付けると、BigQuery はクエリを検査して、処理するバイト数だけを返します。実行はしないので、料金はかかりません。

```sh run title="SELECT * の見積もり。LIMIT を付けても変わらない"
bq query --use_legacy_sql=false --dry_run 'SELECT * FROM `tsubame-public.bungu.orders`'
bq query --use_legacy_sql=false --dry_run 'SELECT * FROM `tsubame-public.bungu.orders` LIMIT 10'
```

どちらも 117079 バイトで、`bq show` の `Total Bytes` と同じです。`SELECT *` はすべての列を読むので、テーブル全体ぶんになります。

:::warn LIMIT では料金は減らない
`LIMIT 10` は「結果を 10 行だけ返す」という意味で、読む量は減りません。列はまとめて読まれ、行を数えて止めることはしないからです。データの中身をのぞくだけなら、`bq head` を使うか、列を絞ります。
:::

```sh run title="列を絞る。COUNT(*) は 0 バイト"
bq query --use_legacy_sql=false --dry_run 'SELECT channel, quantity FROM `tsubame-public.bungu.orders`'
bq query --use_legacy_sql=false --dry_run 'SELECT COUNT(*) FROM `tsubame-public.bungu.orders`'
```

2 列だけにすると 29759 バイトになりました。4 分の 1 ほどです。`COUNT(*)` は 0 バイトです。行の数はテーブルの情報として持っているので、列を読まずに答えられます。

バイト数は、型ごとに決まった数え方で計算されます。`INT64` と `DATE` は 1 つの値が 8 バイト、`STRING` は 2 バイトに UTF-8 のバイト数を足したものです。上の 29759 バイトは、次のように分けられます。

| 列 | 型 | 計算 | バイト数 |
| --- | --- | --- | --- |
| `quantity` | INT64 | 8 × 2183 行 | 17464 |
| `channel` | STRING | `web`（2 + 3 = 5）× 1493 行 + `store`（2 + 5 = 7）× 690 行 | 12295 |
| 合計 | | | 29759 |

本物の料金は、US のリージョンで 1 TiB（約 1.1 兆バイト）あたり 6.25 ドルで、リージョンによって違います。毎月最初の 1 TiB は無料です。ただし、1 つのクエリで参照したテーブルごとに、**最低 10 MB** が課金されます。小さなテーブルを何度読んでも、1 回ごとに 10 MB ぶんとして数えられます。

### 使いすぎを止める：--maximum_bytes_billed

うっかり巨大なテーブルを `SELECT *` すると、1 回で大きな料金になります。**`--maximum_bytes_billed`** を付けると、課金されるバイト数がその値を超えるクエリは、実行せずに失敗させられます。試しに、上限を 100 万バイトにしてみます。

```sh run title="上限を超えるクエリは失敗する" error
bq query --use_legacy_sql=false --maximum_bytes_billed=1000000 'SELECT * FROM `tsubame-public.bungu.orders`'
```

`Query exceeded limit for bytes billed: 1000000. 10485760 or higher required.` と出ました。処理するのは 117079 バイトなのに、必要なのは 10485760 バイト（10 MB = 10 × 1024 × 1024）以上だと言っています。これが最低 10 MB の課金です。上限を 10485760 以上にすれば通ります。上限で止まったクエリには、料金はかかりません。

## パーティションとクラスタで、読む行を減らす {#partition}

列を絞ると、読む「列」が減ります。読む「行」を減らすのが**パーティション**です。テーブルを、日付などの列の値で小さな区画（パーティション）に分けておきます。`WHERE` で区画を指定すれば、BigQuery はほかの区画を読みません。これを**パーティションの刈り込み**（プルーニング）と呼びます。

```fig layout orders は order_date で日ごとのパーティションに分かれている。WHERE の書き方で、読む区画（色付き）が変わる
{
  unit: 52,
  steps: [
    { title: 'WHERE なし', say: 'すべての区画（304 日ぶん）を読む',
      rows: [ { label: 'orders', cells: [ { t: '1/1', kind: 'accent' }, { t: '1/2', kind: 'accent' }, { t: '…', kind: 'accent' }, { t: '3/14', kind: 'accent' }, { t: '3/15', kind: 'accent' }, { t: '3/16', kind: 'accent' }, { t: '…', kind: 'accent' }, { t: '10/31', kind: 'accent' } ] } ] },
    { title: "order_date = '2026-03-15'", say: 'パーティションの列を定数と比べているので、3 月 15 日の区画だけを読む',
      rows: [ { label: 'orders', cells: [ { t: '1/1', kind: 'empty' }, { t: '1/2', kind: 'empty' }, { t: '…', kind: 'empty' }, { t: '3/14', kind: 'empty' }, { t: '3/15', kind: 'accent' }, { t: '3/16', kind: 'empty' }, { t: '…', kind: 'empty' }, { t: '10/31', kind: 'empty' } ] } ] },
    { title: 'EXTRACT(MONTH FROM order_date) = 3', say: '列に関数をかけて比べると、どの区画が当たるかを前もって決められない。全部の区画を読む',
      rows: [ { label: 'orders', cells: [ { t: '1/1', kind: 'accent' }, { t: '1/2', kind: 'accent' }, { t: '…', kind: 'accent' }, { t: '3/14', kind: 'accent' }, { t: '3/15', kind: 'accent' }, { t: '3/16', kind: 'accent' }, { t: '…', kind: 'accent' }, { t: '10/31', kind: 'accent' } ] } ] },
  ],
}
```

3 つの書き方で見積もりを比べます。

```sh run title="パーティションが効く書き方と、効かない書き方"
bq query --use_legacy_sql=false --dry_run 'SELECT channel, quantity FROM `tsubame-public.bungu.orders` WHERE order_date = "2026-03-15"'
bq query --use_legacy_sql=false --dry_run 'SELECT order_id FROM `tsubame-public.bungu.orders` WHERE order_date BETWEEN "2026-03-01" AND "2026-03-31"'
bq query --use_legacy_sql=false --dry_run 'SELECT order_id FROM `tsubame-public.bungu.orders` WHERE EXTRACT(MONTH FROM order_date) = 3'
```

- 1 つ目は 172 バイトです。列を絞った 29759 バイトから、さらに 3 月 15 日の 8 行ぶんだけになりました。`WHERE` で使った `order_date` も読む列に入ります
- 2 つ目は 4816 バイトです。3 月の 301 行 × （`order_id` と `order_date` の 8 + 8 バイト）です
- 3 つ目は 34928 バイトで、2183 行全部を読んでいます。同じ「3 月」でも、列に関数をかけると区画を絞れません。日付の範囲で書くのがコツです

区画の様子は、データセットの **`INFORMATION_SCHEMA`**（テーブルの情報を SQL で読むための特別なビュー）で見られます。`PARTITIONS` は区画ごとの行数、`COLUMNS` は列の一覧です。

```sh run title="区画と列の情報"
bq query --use_legacy_sql=false 'SELECT table_name, partition_id, total_rows FROM `tsubame-public.bungu.INFORMATION_SCHEMA.PARTITIONS` ORDER BY partition_id LIMIT 3'
bq query --use_legacy_sql=false 'SELECT column_name, data_type, is_partitioning_column, clustering_ordinal_position FROM `tsubame-public.bungu.INFORMATION_SCHEMA.COLUMNS` WHERE table_name = "orders"'
```

`partition_id` は `20260101` のような日付の文字列で、1 日に数行から十数行の注文があります。`COLUMNS` では、`order_date` の `is_partitioning_column` が `YES`、`channel` の `clustering_ordinal_position` が 1 です。

:::deep クラスタは、見積もりには出ない
**クラスタ**は、区画の中の行を、指定した列（ここでは `channel`）の値の順に並べて保存しておく仕組みです。`WHERE channel = "web"` のように絞ると、BigQuery は関係のないブロックを読み飛ばせます。ただし、どれだけ読み飛ばせるかは実行してみないと分からないので、`--dry_run` の見積もりはクラスタの効果を含まない上限になります。実際に課金されたバイト数は、次の節の `INFORMATION_SCHEMA.JOBS` で確かめます（本物の細かい振る舞いは公式ドキュメントを参照）。このサイトの BigQuery は、クラスタで読む量を減らす計算はしていません。
:::

## キャッシュと、ジョブの記録 {#cache}

同じクエリを 2 回実行すると、2 回目は**キャッシュ**（前の結果の保存）から返ります。テーブルが変わっていなければ、結果も同じはずだからです。キャッシュから返したクエリは、料金がかかりません。

```sh run title="同じクエリを 2 回。3 回目はキャッシュを使わない"
bq query --use_legacy_sql=false 'SELECT channel, SUM(quantity * unit_price) AS sales FROM `tsubame-public.bungu.orders` GROUP BY channel ORDER BY channel'
bq query --use_legacy_sql=false 'SELECT channel, SUM(quantity * unit_price) AS sales FROM `tsubame-public.bungu.orders` GROUP BY channel ORDER BY channel'
bq query --use_legacy_sql=false --nouse_cache 'SELECT channel, SUM(quantity * unit_price) AS sales FROM `tsubame-public.bungu.orders` GROUP BY channel ORDER BY channel'
```

3 回とも、結果は同じです。違いは、ジョブの記録を見ると分かります。`--nouse_cache` は「キャッシュを使わずに計算し直す」というフラグです。

ジョブの記録は、`region-場所`.INFORMATION_SCHEMA.JOBS というビューで読めます。ジョブはデータの場所（ここでは `asia-northeast1`）で実行されるので、その場所のビューを読みます。

```sh run title="最近のジョブ 3 つ"
bq query --use_legacy_sql=false 'SELECT statement_type, total_bytes_processed, total_bytes_billed, cache_hit FROM `region-asia-northeast1`.INFORMATION_SCHEMA.JOBS ORDER BY creation_time DESC LIMIT 3'
bq ls -j -n 3
```

新しい順に並んでいます。いちばん上（3 回目、`--nouse_cache`）と、いちばん下（1 回目）は `cache_hit` が `false` で、`total_bytes_billed` が 10485760 です。処理したのは `total_bytes_processed` の 47223 バイトですが、最低の 10 MB が課金されています。真ん中（2 回目）は `cache_hit` が `true` で、課金は 0 です。

`bq ls -j` は、ジョブの一覧を bq の形で出します。どれも `query` の種類で、`SUCCESS` です。

:::tip 費用を確かめる習慣
大きなテーブルを読む前に `--dry_run` で見積もり、実行した後に `INFORMATION_SCHEMA.JOBS` の `total_bytes_billed` で確かめる。この 2 つを習慣にすると、料金で驚くことがなくなります。プロジェクト全体の使いすぎは、第 4 章の予算とアラートで見張ります。
:::

## 自分のデータセットを作り、CSV を読み込む {#dataset}

公開データは読めるだけです。自分の表を作るには、自分のプロジェクトに**データセット**を作ります。データセットを作るときに大事なのは**場所**（`--location`）です。データセットの場所は、あとから変えられません。

```sh run title="データセットを 2 つ作る（場所を指定したものと、しないもの）"
bq mk --dataset --location=asia-northeast1 --description="つばめ文具の分析用" tsubame-shop:sales
bq mk --dataset tsubame-shop:sales_us
bq ls
```

`sales` は東京のリージョン（`asia-northeast1`）、`sales_us` は場所を指定しなかったので、既定の `US`（米国のマルチリージョン）にできます。データセットの名前に使えるのは英数字と `_` だけで、`-` は使えません。

```sh setup
cat > stores.csv <<'CSV'
store_id,store_name,prefecture,opened_on
1,渋谷店,東京都,2019-04-01
2,横浜店,神奈川県,2021-10-15
3,梅田店,大阪府,2023-03-20
CSV
```

次に、手元の CSV ファイルを読み込みます。この章の準備で、店舗の一覧 `stores.csv` をホームディレクトリに置いてあります。読み込みは **`bq load`** です。`--autodetect` は列の型を中身から推測させるフラグ、`--skip_leading_rows=1` は最初の 1 行（見出し）を飛ばすフラグです。

```sh run title="CSV を読み込む"
cat stores.csv
bq load --source_format=CSV --autodetect --skip_leading_rows=1 sales.stores ./stores.csv
bq show sales.stores
```

`Upload complete.` のあとに、読み込みのジョブが終わりました。`bq show` の `Schema` を見ると、`store_id` は integer、`opened_on` は date と、中身から型が判定されています。列の名前は見出しの行から取られました。型を自分で決めたいときは、`--autodetect` のかわりに `store_id:INTEGER,store_name:STRING,...` のようなスキーマを最後の引数に書きます。

自分のテーブルと公開データは、同じクエリで結合できます。店舗のある都道府県ごとに、顧客の数を数えます。

```sh run title="自分のテーブルと公開データを結合する"
bq query --use_legacy_sql=false 'SELECT s.store_name, COUNT(*) AS customers FROM sales.stores AS s JOIN `tsubame-public.bungu.customers` AS c ON s.prefecture = c.prefecture GROUP BY s.store_name ORDER BY customers DESC'
```

`sales.stores` のようにプロジェクトを省くと、いまのプロジェクト（`tsubame-shop`）のデータセットだと読まれます。渋谷店のある東京都の顧客がいちばん多く、27 人います。

では、`US` の `sales_us` に、公開データから表を作ろうとするとどうなるでしょうか。

```sh run title="場所の違うデータセットはまたげない" error
bq query --use_legacy_sql=false 'CREATE TABLE sales_us.products AS SELECT * FROM `tsubame-public.bungu.products`'
```

`Not found: Dataset tsubame-public:bungu was not found in location US` と出ました。データセットはあるのに「見つからない」と言われるのは、1 つのクエリ（ジョブ）が 1 つの場所で実行されるからです。`US` で動くジョブからは、`asia-northeast1` のデータは見えません。公開データと組み合わせるデータセットは、同じ場所に作ります。

## CTAS、ビュー、DML {#ctas}

クエリの結果を、そのまま新しいテーブルにできます。`CREATE TABLE ... AS SELECT` の形で、頭文字を取って **CTAS**（シータス）と呼びます。日ごと・経路ごとの集計表を作り、`PARTITION BY` で日ごとのパーティションにしておきます。

```sh run title="CTAS で集計表を作る"
bq query --use_legacy_sql=false 'CREATE TABLE sales.daily PARTITION BY order_date AS SELECT order_date, channel, COUNT(*) AS orders, SUM(quantity * unit_price) AS sales FROM `tsubame-public.bungu.orders` GROUP BY order_date, channel'
bq show sales.daily
```

`Created tsubame-shop.sales.daily` と出て、582 行のテーブルができました。元の 2183 行の注文が、304 日 × 2 経路（注文のなかった組を除く）にまとまっています。集計表を読むクエリは、元の注文を読むより処理するバイト数が少なくて済みます。

**ビュー**は、SQL に名前を付けて保存したものです。データは持たず、読まれるたびに中の SQL が実行されます。月ごとの売上のビューを作ります。

```sh run title="ビューを作って読む"
bq query --use_legacy_sql=false 'CREATE VIEW sales.monthly AS SELECT DATE_TRUNC(order_date, MONTH) AS month, SUM(sales) AS sales FROM sales.daily GROUP BY month'
bq ls sales
bq query --use_legacy_sql=false 'SELECT * FROM sales.monthly ORDER BY month LIMIT 3'
bq query --use_legacy_sql=false --dry_run 'SELECT month, sales FROM sales.monthly'
```

`bq ls sales` で、`monthly` の `Type` が `VIEW` になっています。`DATE_TRUNC(order_date, MONTH)` は日付を月の初日に切り詰める関数です。ビューを読むと、中の SQL が `sales.daily` を読みます。だから見積もりの 9312 バイトは、`daily` の `order_date` と `sales` の 2 列（8 + 8 バイト × 582 行）ぶんです。ビューにしても、料金は元のテーブルを読んだぶんだけかかります。

行を足したり書き換えたりするのは **DML**（データ操作言語。INSERT、UPDATE、DELETE など）です。BigQuery でも、ふつうの SQL と同じように書けます。

```sh run title="INSERT と UPDATE"
bq query --use_legacy_sql=false 'INSERT INTO sales.daily (order_date, channel, orders, sales) VALUES ("2026-11-01", "web", 12, 9800)'
bq query --use_legacy_sql=false 'UPDATE sales.daily SET sales = sales + 200 WHERE order_date = "2026-11-01"'
bq query --use_legacy_sql=false 'SELECT * FROM sales.daily WHERE order_date = "2026-11-01"'
```

`Number of affected rows: 1` が、変わった行の数です。BigQuery は大量の行をまとめて読むのが得意な一方、1 行ずつの書き込みを何度も繰り返す使い方は向きません。注文が来るたびに 1 行足すなら、第 14 章の Cloud SQL か第 13 章の Firestore に書き、BigQuery にはまとめて読み込みます。

テーブルのコピーは `bq cp`、有効期限は `bq update --expiration`（秒）、削除は `bq rm` です。

```sh run title="コピー、有効期限、削除"
bq cp sales.daily sales.daily_backup
bq update --expiration 3600 sales.daily_backup
bq rm -r -f sales_us
bq ls
```

`daily_backup` は 1 時間後に自動で消えます。`bq rm` は、`-f` で確認を省き、`-r` で中のテーブルごとデータセットを消します。`bq ls` に残ったのは `sales` だけです。

## 権限：データのプロジェクトと、ジョブのプロジェクト {#iam}

BigQuery の権限には、ほかのサービスにない特徴があります。**データを読む権限**と、**クエリを実行する権限**が、別のプロジェクトにあってよいのです。

```fig graph 公開データを読むとき。ジョブは自分のプロジェクトで実行し、データは公開側のプロジェクトから読む
{
  col: 220, row: 96,
  nodes: [
    { id: 'bob', label: 'bob@', sub: 'analysts グループ', x: 0, y: 0.5, kind: 'plain', mono: false },
    { id: 'job', label: 'クエリのジョブ', sub: 'bigquery.jobs.create が要る', x: 1, y: 0.5, kind: 'accent', mono: false },
    { id: 'bill', label: '請求先アカウント', sub: '料金は tsubame-shop に', x: 1, y: 1.6, kind: 'muted', mono: false },
    { id: 'ds', label: 'bungu', sub: 'bigquery.tables.getData が要る', x: 2.2, y: 0.5, kind: 'crate', mono: false },
  ],
  edges: [ { from: 'bob', to: 'job', label: '実行' }, { from: 'job', to: 'ds', label: '読む' }, { from: 'job', to: 'bill', label: '課金', style: 'dashed' } ],
  groups: [ { label: 'tsubame-shop（ジョブのプロジェクト）', nodes: ['job', 'bill'], kind: 'pkg' }, { label: 'tsubame-public（データのプロジェクト）', nodes: ['ds'], kind: 'ext' } ],
}
```

- **ジョブを作る権限** `bigquery.jobs.create`：クエリを実行するプロジェクトに要ります。料金はこのプロジェクトの請求先に付きます。事前定義ロールでは `roles/bigquery.jobUser` がこれだけを持ちます
- **データを読む権限** `bigquery.tables.getData`：データのあるテーブルやデータセットに要ります。`roles/bigquery.dataViewer` が持ちます。公開データセット `bungu` には、`allAuthenticatedUsers`（ログインしている人すべて）に `dataViewer` が付いています

売上分析の馬場さん（`bob@`）で試します。bob は `tsubame-shop` に何のロールも持っていません。

```sh run title="bob に切り替える"
gcloud auth login bob@tsubame.example
```

```sh run title="データは読めるのに、クエリを実行できない" error
bq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-public.bungu.orders`'
```

`Access Denied: Project tsubame-shop: User does not have bigquery.jobs.create permission in project tsubame-shop.` と出ました。止められたのはデータ（`tsubame-public`）ではなく、ジョブのプロジェクト（`tsubame-shop`）です。公開データは bob でも読めますが、「どこのお金でクエリを動かすか」が決まっていないのです。

あなた（`you@`）に戻って、analysts グループにジョブの実行だけを許します。

```sh run title="analysts に roles/bigquery.jobUser を付ける"
gcloud auth login you@tsubame.example
gcloud projects add-iam-policy-binding tsubame-shop --member=group:analysts@tsubame.example --role=roles/bigquery.jobUser --format=none
gcloud auth login bob@tsubame.example
bq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-public.bungu.orders`'
```

今度は 2183 が返りました。では、bob は `tsubame-shop` の `sales` も読めるでしょうか。

```sh run title="ジョブは作れても、データセットは読めない" error
bq query --use_legacy_sql=false 'SELECT * FROM sales.monthly ORDER BY month LIMIT 3'
```

`User does not have permission to query table tsubame-shop:sales.monthly, or perhaps it does not exist.` です。`jobUser` はジョブを作れるだけで、データを読む権限は含みません。「それとも存在しないのかもしれない」と付いているのは、権限のない人にテーブルがあるかどうかを教えないためです。データセット `sales` に、analysts の `dataViewer` を付けます。

```sh run title="データセットに dataViewer を付ける"
gcloud auth login you@tsubame.example
bq add-iam-policy-binding --member=group:analysts@tsubame.example --role=roles/bigquery.dataViewer tsubame-shop:sales
gcloud auth login bob@tsubame.example
bq query --use_legacy_sql=false 'SELECT * FROM sales.monthly ORDER BY month LIMIT 3'
```

bob が月ごとの売上を読めました。プロジェクト全体ではなく、データセット `sales` にだけ付けたので、bob はほかのデータセットを読めません。第 6 章の最小権限の考え方です。

### 請求先のないプロジェクト：BigQuery サンドボックス

請求先アカウント（第 4 章）がないプロジェクトでも、BigQuery は使えます。これを **BigQuery サンドボックス**と呼びます。クレジットカードを登録しなくても、無料枠の範囲でクエリを試せます。そのかわり、制限があります。テーブルは 60 日で期限切れになり、DML は使えません。

```sh run title="請求先のないプロジェクトで、データセットとテーブルを作る"
gcloud auth login you@tsubame.example
gcloud projects create tsubame-bq-sandbox --name="BigQuery の練習"
bq --project_id=tsubame-bq-sandbox mk --dataset --location=asia-northeast1 lab
bq --project_id=tsubame-bq-sandbox query --use_legacy_sql=false 'CREATE TABLE lab.cats AS SELECT DISTINCT category FROM `tsubame-public.bungu.products`'
```

新しいプロジェクトには請求先を付けていませんが、データセットの作成も CTAS も通りました。`--project_id` で、ジョブを実行するプロジェクトを `tsubame-bq-sandbox` にしています。料金はかかりません。

```sh run title="サンドボックスでは DML が拒否される" error
bq --project_id=tsubame-bq-sandbox query --use_legacy_sql=false 'INSERT INTO lab.cats (category) VALUES ("封筒")'
```

`Billing has not been enabled for this project.` と `DML queries are not allowed in the free tier.` が出ました。請求先がないので、DML は使えません。直し方はエラーの文のとおり、プロジェクトに請求先アカウントを付けることです（`gcloud billing projects link`、第 4 章）。

:::note サンドボックスのデータセット
サンドボックスで作ったデータセットには、テーブルの既定の有効期限として 60 日（`bq show --format=prettyjson` の `defaultTableExpirationMs` が `5184000000` ミリ秒）が付きます。請求先を付けると制限は外れますが、それまでに作ったテーブルの期限は自分で外す必要があります（本物の手順は公式ドキュメントを参照）。
:::

:::key まとめ
- BigQuery は列指向のデータウェアハウス。プロジェクト → データセット（場所と権限の単位）→ テーブル・ビューの 3 段
- `bq query` には `--use_legacy_sql=false` を付ける。付け忘れると `Invalid table name` になる
- 料金は処理したバイト数。読んだ列だけが数えられ、`LIMIT` では減らない。`COUNT(*)` は 0 バイト。参照したテーブルごとに最低 10 MB
- `--dry_run` で見積もり、`--maximum_bytes_billed` で上限、`INFORMATION_SCHEMA.JOBS` の `total_bytes_billed` と `cache_hit` で実績を見る
- パーティションの列を定数と比べると、読む区画が減る。列に関数をかけると効かない
- データセットは `--location` を決めて作る。場所の違うデータセットは 1 つのクエリでまたげない
- `bq load --autodetect --skip_leading_rows=1` で CSV を読み込む。CTAS で結果を表に、ビューで SQL に名前を付ける
- クエリには、ジョブのプロジェクトの `bigquery.jobs.create`（`jobUser`）と、データの `bigquery.tables.getData`（`dataViewer`）の両方が要る
- 請求先のないプロジェクトはサンドボックス。クエリは使えるが、DML は拒否される
:::

## 確認問題 {#quiz}

BigQuery のコマンドとクエリを、自分で書いて確かめます。問題の準備では、`tsubame-shop` に `asia-northeast1` のデータセット `sales` と、公開データの注文の一部を写したテーブル `sales.o`（`order_date` で日ごとのパーティション）を作ってあります。

:::quiz パーティションを効かせて見積もる
テーブル `sales.o` から、2026 年 4 月 1 日から 4 月 30 日までの注文の `customer_id` だけを読むクエリを考えます。このクエリを `--dry_run` で検査し、処理するバイト数を表示してください（`Query successfully validated. ...` の 1 行が出れば OK です）。

```sh prep
bq mk --dataset --location=asia-northeast1 sales
bq query --use_legacy_sql=false 'CREATE OR REPLACE TABLE sales.o PARTITION BY order_date AS SELECT * FROM `tsubame-public.bungu.orders` WHERE order_date < "2026-07-01"'
```

```sh vary
bq query --use_legacy_sql=false 'CREATE OR REPLACE TABLE sales.o PARTITION BY order_date AS SELECT * FROM `tsubame-public.bungu.orders` WHERE channel = "web"'
```

```sh starter
bq query --use_legacy_sql=false --dry_run '...'
```

```sh answer
bq query --use_legacy_sql=false --dry_run 'SELECT customer_id FROM sales.o WHERE order_date BETWEEN "2026-04-01" AND "2026-04-30"'
```

:::hint
`WHERE order_date BETWEEN "2026-04-01" AND "2026-04-30"` のように、パーティションの列を日付の定数と比べます。`SELECT *` にすると、すべての列を読むぶん大きくなります。
:::
:::

:::quiz カテゴリ別の売上を CSV で
テーブル `sales.o` と公開データの `` `tsubame-public.bungu.products` `` を `product_id` で結合し、カテゴリ（`category`）ごとの売上（`quantity * unit_price` の合計）を出してください。列は `category` と `sales` の 2 つ、売上の多い順に、`--format=csv` で表示します。

```sh prep
bq mk --dataset --location=asia-northeast1 sales
bq query --use_legacy_sql=false 'CREATE OR REPLACE TABLE sales.o PARTITION BY order_date AS SELECT * FROM `tsubame-public.bungu.orders` WHERE order_date < "2026-07-01"'
```

```sh vary
bq query --use_legacy_sql=false 'CREATE OR REPLACE TABLE sales.o PARTITION BY order_date AS SELECT * FROM `tsubame-public.bungu.orders` WHERE channel = "store"'
```

```sh starter
bq query --use_legacy_sql=false --format=csv '...'
```

```sh answer
bq query --use_legacy_sql=false --format=csv 'SELECT p.category, SUM(o.quantity * o.unit_price) AS sales FROM sales.o AS o JOIN `tsubame-public.bungu.products` AS p USING (product_id) GROUP BY p.category ORDER BY sales DESC'
```

:::hint
`JOIN ... USING (product_id)` で結合し、`GROUP BY p.category`、`ORDER BY sales DESC` とします。列の名前は `AS sales` で付けます。
:::
:::
