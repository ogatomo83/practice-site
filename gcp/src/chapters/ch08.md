## VM は何でできているか {#parts}

**Compute Engine**（コンピュート エンジン）は、Google のデータセンターにある計算機を、**VM**（仮想マシン。1 台の物理マシンを分けて作った、ソフトウェアの計算機）として借りるサービスです。第 1 章の分け方では IaaS にあたります。OS から上は、すべて自分で面倒を見ます。

VM を 1 台作るとき、決めることは次の図の部品です。

```fig graph VM（インスタンス）の部品。大きさはマシンタイプ、中身はイメージから作るブートディスク、外とのつながりはネットワーク インターフェース
{
  col: 230, row: 96,
  nodes: [
    { id: 'mt', label: 'マシンタイプ', sub: 'e2-micro：vCPU 2、メモリ 1 GB', x: 0, y: 0, mono: false },
    { id: 'img', label: 'イメージ', sub: 'debian-12（debian-cloud）', x: 0, y: 2, kind: 'ext', mono: false },
    { id: 'vm', label: 'VM（インスタンス）', sub: 'web-1', x: 1, y: 1, kind: 'accent', mono: false },
    { id: 'disk', label: 'ブートディスク', sub: '10 GB、イメージをコピーしたもの', x: 1, y: 2, kind: 'stack', mono: false },
    { id: 'nic', label: 'ネットワーク インターフェース', sub: '内部 IP と外部 IP', x: 2, y: 0, mono: false },
    { id: 'sa', label: 'サービスアカウント', sub: 'とアクセススコープ', x: 2, y: 1, mono: false },

  groups: [{ label: 'ゾーン asia-northeast1-b', nodes: ['vm', 'disk'], kind: 'plain' }],
}
```

- **マシンタイプ**：vCPU（仮想の CPU）の数とメモリの量の組み合わせ。料金はほぼこれで決まります
- **イメージ**：OS が入ったディスクのひな形。作るときに、イメージをコピーして**ブートディスク**（起動に使うディスク）を作ります
- **ゾーン**：VM とディスクは 1 つのゾーンに置かれます（第 3 章）。ゾーンをまたいで動くことはありません

まず、VM の一覧を見てみます。

```sh run title="Compute Engine API が無効" error
gcloud compute instances list
```

第 3 章で見たエラーです。`Compute Engine API has not been used in project 365600345236 before or it is disabled` は、「このプロジェクトでは Compute Engine の API が有効になっていない」という意味です。有効にして、ゾーンとリージョンの既定も決めておきます。

```sh run title="API を有効にして、既定のゾーンを決める"
gcloud services enable compute.googleapis.com
gcloud config set compute/region asia-northeast1
gcloud config set compute/zone asia-northeast1-b
gcloud compute instances list
```

今度は `Listed 0 items.` で、VM がまだ 1 台もないことが分かりました。Compute Engine API を有効にすると、裏で 2 つのものができます。`default` という VPC ネットワーク（第 9 章）と、**Compute Engine のデフォルトのサービスアカウント**（第 5 章）です。どちらもこの章で使います。

### マシンタイプとイメージを選ぶ

```sh run title="E2 のマシンタイプ"
gcloud compute machine-types list --zones=asia-northeast1-b --filter="name~^e2"
gcloud compute machine-types describe e2-micro --format="value(guestCpus,memoryMb,isSharedCpu)"
```

名前は「**シリーズ - 種類 - vCPU の数**」です。`e2-standard-2` は E2 シリーズの標準（vCPU 1 つあたりメモリ 4 GB）で、vCPU が 2 つです。`highmem` はメモリが多め、`highcpu` は少なめです。

`e2-micro`、`e2-small`、`e2-medium` の 3 つは**共有コア**です。`describe` の `True` がその印で、2 つの vCPU を、時間の一部だけ使えます。小さな Web サーバや試しの VM には十分で、料金も安くなります。

```sh run title="公開イメージ"
gcloud compute images list
gcloud compute images describe-from-family debian-12 --image-project=debian-cloud --format="value(name,diskSizeGb)"
```

`PROJECT` の列に注目してください。`debian-cloud`、`ubuntu-os-cloud` などは、Google が公開イメージを置いているプロジェクトです。イメージもプロジェクトの中のリソースなのです。

`FAMILY`（ファミリー）は、同じ OS の版をまとめた名前です。`--image-family=debian-12` と指定すると、そのファミリーの最新のイメージ（いまは `debian-12-bookworm-v20261111`）が使われます。日付の付いたイメージ名を覚える必要はありません。

## VM を作って、ssh で入る {#create}

VM を作るのは `gcloud compute instances create` です。まず、よくある書き間違いから見ます。

```sh run title="ないマシンタイプ" error
gcloud compute instances create vm-1 --machine-type=e2-nano --image-family=debian-12 --image-project=debian-cloud
```

`Machine type with name 'e2-nano' does not exist in zone 'asia-northeast1-b'` と断られました。名前の打ち間違いのほか、ゾーンによって使えないマシンタイプもあるので、このような文になっています。上の `machine-types list` で確かめた名前に直して、作り直します。

```sh run title="VM を作る"
gcloud compute instances create vm-1 --machine-type=e2-micro --image-family=debian-12 --image-project=debian-cloud
```

`Created [...]` のあとに、できた VM の 1 行が出ます。

| 列 | 値 | 意味 |
| --- | --- | --- |
| `ZONE` | `asia-northeast1-b` | 置いたゾーン。`compute/zone` の既定が使われた |
| `INTERNAL_IP` | `10.146.0.2` | **内部 IP**。VPC の中だけで使う住所（第 9 章） |
| `EXTERNAL_IP` | `34.86.52.231` | **外部 IP**。インターネットから届く住所 |
| `STATUS` | `RUNNING` | 動いている。この状態の間、料金がかかる |

詳しい情報は `describe` で見ます。そのままでは長い YAML が出るので、`--format` で欲しい項目だけを取り出します。

```sh run title="一覧と、項目を絞った describe"
gcloud compute instances list
gcloud compute instances describe vm-1 --format="yaml(name,status,machineType.basename())"
gcloud compute disks list
```

`machineType` は本当は URL です。`.basename()` で最後の部分（`e2-micro`）だけにしました。`disks list` には、VM と同じ名前のブートディスク `vm-1` が 10 GB で出ています。ディスクは VM とは別のリソースです。

VM の中に入るのは `gcloud compute ssh` です。

```sh run title="VM の中でコマンドを実行する"
gcloud compute ssh vm-1 --command="hostname; grep PRETTY_NAME /etc/os-release; uname -r"
```

最初の 1 回だけ、`WARNING` と `Generating public/private rsa key pair.` が出ます。gcloud が SSH の鍵を作り、公開鍵をプロジェクトのメタデータに登録したのです。VM の中のエージェントがそれを読み、ログインを許します。鍵を自分で配る必要はありません。

そのあとの 3 行は、VM の中で実行した結果です。名前が `vm-1` で、Debian 12 が動いていることが分かります。

:::note このサイトの GCP では
`gcloud compute ssh` は `--command="…"` で 1 回コマンドを実行する使い方だけに対応しています。本物では `gcloud compute ssh vm-1` だけで VM の端末に入れます。VM の中のシェルも小さく、使えるコマンドは限られています。
:::

## startup-script で Web サーバを立てる {#startup}

VM を作るたびに ssh で入って設定するのは手間です。**startup-script**（スタートアップ スクリプト）を使うと、VM が起動するたびに、決めたコマンドを root（管理者）として自動で実行できます。

```fig seq startup-script の流れ。VM はメタデータからスクリプトを受け取って実行する。外から届くかはファイアウォールが決める
{
  actors: [
    { id: 'cs', label: 'Cloud Shell' },
    { id: 'gce', label: 'Compute Engine', kind: 'stack' },
    { id: 'vm', label: 'VM web-1', kind: 'accent' },
    { id: 'md', label: 'メタデータサーバ', kind: 'ext' },
  ],
  msgs: [
    { from: 'cs', to: 'gce', label: 'instances create --metadata-from-file' },
    { from: 'gce', to: 'vm', label: '起動' },
    { from: 'vm', to: 'md', label: 'startup-script はある？' },
    { from: 'md', to: 'vm', label: 'スクリプトの中身' },
    { self: 'vm', label: 'root で実行：apt-get install nginx' },
    { from: 'cs', to: 'vm', label: 'curl：ファイアウォールで止まる', style: 'bad' },
    { note: 'allow-http のルールを作る', at: ['cs', 'vm'] },
    { from: 'cs', to: 'vm', label: 'curl：nginx が答える', style: 'accent' },
  ],
}
```

まず、スクリプトを Cloud Shell のファイルに書きます。

```sh run title="startup-script を書く"
cat > startup.sh <<'EOF'
#! /bin/bash
apt-get update
apt-get install -y nginx
echo "<h1>つばめ文具 $(hostname)</h1>" > /var/www/html/index.html
EOF
cat startup.sh
```

nginx（エンジン エックス。Web サーバのソフト）を入れて、トップページを書き換えるだけのスクリプトです。これを `--metadata-from-file=startup-script=ファイル` で VM に渡します。

```sh run title="startup-script つきで VM を作る"
gcloud compute instances create web-1 --machine-type=e2-micro --image-family=debian-12 --image-project=debian-cloud --tags=http-server --metadata-from-file=startup-script=startup.sh
```

`--tags=http-server` は**ネットワーク タグ**です。VM に付ける目印で、あとでファイアウォールのルールが「この目印の VM にだけ」と対象を選ぶのに使います。

スクリプトはうまく動いたでしょうか。VM の画面に出るはずの文字は、**シリアルポートの出力**として外から読めます。ssh できない VM の調べ物にも使います。

```sh run title="シリアルポートの出力で、スクリプトの結果を見る"
gcloud compute instances get-serial-port-output web-1 | grep startup-script
IP=$(gcloud compute instances describe web-1 --format="value(networkInterfaces[0].accessConfigs[0].natIP)")
echo $IP
```

`startup-script:` のあとに、スクリプトの出力が 1 行ずつ並んでいます。最後の `startup-script exit status 0` が、スクリプトが最後まで成功した印です。0 でなければ、その上の行に失敗の理由があります。

2 行目では、外部 IP を変数 `IP` に入れました。`--format="value(...)"` で取り出した値は、そのままシェルの変数に使えます。では、Cloud Shell から Web サーバにアクセスしてみます。

```sh run title="外から届かない" error
curl --connect-timeout 5 http://$IP
```

`Failed to connect to … port 80 after 5002 ms: Timeout was reached` で、5 秒待っても答えがありませんでした。nginx は動いているのに、届かないのです。

理由は**ファイアウォール**です。`default` ネットワークには、ssh（22 番）などを通すルールは最初からありますが、HTTP（80 番）を通すルールはありません。通さないものは、黙って捨てられます。だから「拒否」ではなく「時間切れ」になります。80 番を通すルールを 1 つ作ります。

```sh run title="80 番を通すルールを作って、もう一度"
gcloud compute firewall-rules create allow-http --allow=tcp:80 --target-tags=http-server
curl -s http://$IP
```

`<h1>つばめ文具 web-1</h1>` が返りました。startup-script が書いたページです。`--target-tags=http-server` で、タグ `http-server` の付いた VM にだけ、80 番を開けています。ファイアウォールの決まり（暗黙の拒否、優先度、送り元の範囲）は、[第 9 章](ch09.html)で詳しく扱います。

## メタデータサーバ：VM が自分のことを知る窓口 {#metadata}

startup-script は、どこから VM に渡ったのでしょうか。答えは**メタデータサーバ**です。どの VM からも `http://metadata.google.internal/` で届く、VM 専用の小さな Web サーバで、その VM の名前、ゾーン、IP、メタデータ、サービスアカウントのトークンなどを答えます。

まず、何も考えずにアクセスしてみます。

```sh run title="ヘッダーなしで聞く"
gcloud compute ssh web-1 --command="curl -s http://metadata.google.internal/computeMetadata/v1/instance/name"
```

`Missing required header "Metadata-Flavor": "Google"` と断られました。メタデータサーバは、`Metadata-Flavor: Google` というヘッダーが付いた問い合わせにしか答えません。ヘッダーを付けて、もう一度聞きます。

```sh run title="ヘッダーを付けて聞く"
gcloud compute ssh web-1 --command="curl -s -H 'Metadata-Flavor: Google' http://metadata.google.internal/computeMetadata/v1/instance/zone; echo"
gcloud compute ssh web-1 --command="curl -s -H 'Metadata-Flavor: Google' http://metadata.google.internal/computeMetadata/v1/instance/network-interfaces/0/ip; echo"
gcloud compute ssh web-1 --command="curl -s -H 'Metadata-Flavor: Google' http://metadata.google.internal/computeMetadata/v1/instance/attributes/startup-script"
```

- `instance/zone` は `projects/365600345236/zones/asia-northeast1-b`。プロジェクトは ID ではなく番号で書かれます
- `network-interfaces/0/ip` は内部 IP の `10.146.0.3` です
- `instance/attributes/startup-script` は、さっき渡したスクリプトそのものです。`--metadata` で渡したキーと値は、すべて `instance/attributes/` の下に並びます

答えの最後に改行が付かないので、`; echo` で改行を足しています。アプリは、ここから自分の名前や設定を読めます。設定ファイルを VM に配らなくても、メタデータに書いておけばよいのです。

メタデータサーバに届くのは、VM の中からだけです。Cloud Shell（VM の外）から聞いても、名前が引けません。

```sh run title="VM の外からは届かない" error
curl -H "Metadata-Flavor: Google" http://metadata.google.internal/computeMetadata/v1/instance/name
```

`curl: (6) Could not resolve host` は、「ホスト名が引けない」という意味です。`metadata.google.internal` という名前は、VM の中の DNS でだけ使えます。

:::deep なぜヘッダーが要るのか
メタデータサーバは、サービスアカウントのアクセストークンも答えます。もし VM の上の Web アプリに「指定した URL を取ってくる」機能があり、攻撃者が `http://metadata.google.internal/…/token` を指定したらどうなるでしょう。アプリがトークンを取ってきて、攻撃者に渡してしまいます（SSRF、サーバ側リクエスト フォージェリと呼ばれる攻撃です）。

ふつうの「URL を取ってくる」処理は、勝手に `Metadata-Flavor: Google` を付けません。ヘッダーを必須にすることで、こうした攻撃の多くを防いでいます。メタデータサーバは `169.254.169.254` という IP でも届きます。
:::

## VM はだれとして API を呼ぶか：サービスアカウントとアクセススコープ {#scopes}

VM の中で gcloud を使うと、だれとして API を呼ぶのでしょうか。VM に付いている**サービスアカウント**（第 5 章）です。

```sh run title="VM のサービスアカウントとスコープ"
gcloud compute instances describe web-1 --format="yaml(serviceAccounts)"
gcloud compute ssh web-1 --command="gcloud auth list"
```

- `email` は `365600345236-compute@developer.gserviceaccount.com`。プロジェクト番号から名前が決まる、**Compute Engine のデフォルトのサービスアカウント**です。何も指定しないと、VM にはこれが付きます
- VM の中の `gcloud auth list` でも、この名前が `ACTIVE` になっています。gcloud はメタデータサーバからこのアカウントのトークンをもらって使います。鍵のファイルはどこにもありません

`scopes` の 6 行が**アクセススコープ**です。トークンで呼べる API の範囲を、VM ごとに絞る仕組みです。`devstorage.read_only` は「Cloud Storage は読むだけ」という意味です。では、VM の中からバケットを作ってみます。

```sh run title="スコープで断られる" error
gcloud compute ssh web-1 --command="gcloud storage buckets create gs://tsubame-shop-ch08-vm --location=asia-northeast1"
```

`HTTPError 403: Provided scope(s) are not authorized` で断られました。「渡されたスコープでは許されていない」という意味です。

デフォルトのサービスアカウントは、プロジェクトの**編集者**（`roles/editor`）を持っています。IAM だけを見れば、バケットを作れるはずです。それでも断られたのは、IAM の手前にもう 1 つの関門があるからです。

```fig graph VM から API を呼ぶときの 2 つの関門。スコープ（トークンの範囲）と IAM（サービスアカウントのロール）の両方を通らないと届かない
{
  col: 210, row: 90,
  nodes: [{ id: 'vm', label: 'VM の中の gcloud', sub: 'メタデータサーバのトークン', x: 0, y: 0, mono: false }, { id: 'sc', label: '関門 1：スコープ', sub: 'devstorage.read_only など', x: 1, y: 0, kind: 'bad', mono: false }, { id: 'iam', label: '関門 2：IAM', sub: 'SA は roles/editor', x: 2, y: 0, mono: false }, { id: 'api', label: 'Cloud Storage', sub: 'buckets create', x: 3, y: 0, kind: 'ext', mono: false }],
  edges: [{ from: 'vm', to: 'sc' }, { from: 'sc', to: 'iam', style: 'muted' }, { from: 'iam', to: 'api', style: 'muted' }],
  steps: [
    { title: 'デフォルトのスコープ', say: 'デフォルトのスコープでは、Cloud Storage は読むだけです。バケットを作る呼び出しは、IAM を調べる前に、関門 1 で止まります。' },
    { title: 'cloud-platform', say: 'スコープを <code>cloud-platform</code>（すべての API）にすると、関門 1 は素通りになります。あとは IAM だけで決まります。いまの Google のおすすめは、この形です。権限はサービスアカウントのロールで絞ります。',
      nodes: [{ id: 'vm', label: 'VM の中の gcloud', sub: 'メタデータサーバのトークン', x: 0, y: 0, mono: false }, { id: 'sc', label: '関門 1：スコープ', sub: 'cloud-platform', x: 1, y: 0, kind: 'muted', mono: false }, { id: 'iam', label: '関門 2：IAM', sub: 'SA は roles/editor', x: 2, y: 0, kind: 'accent', mono: false }, { id: 'api', label: 'Cloud Storage', sub: 'buckets create', x: 3, y: 0, kind: 'ext', mono: false }],
      edges: [{ from: 'vm', to: 'sc', style: 'accent' }, { from: 'sc', to: 'iam', style: 'accent' }, { from: 'iam', to: 'api', style: 'accent' }] },
  ],
}
```

スコープは、IAM ができる前からある古い仕組みです。いまは、スコープを `cloud-platform` にして関門 1 を開けておき、権限は IAM（サービスアカウントに付けるロール）で絞るのがすすめられています。

スコープは、VM が動いている間は変えられません。止めてから `gcloud compute instances set-service-account` で変えるか、作り直します。ここでは、`--scopes=cloud-platform` を付けて作り直します。

```sh run title="cloud-platform スコープで作り直す"
gcloud compute instances delete web-1 --quiet
gcloud compute instances create web-1 --machine-type=e2-micro --image-family=debian-12 --image-project=debian-cloud --tags=http-server --metadata-from-file=startup-script=startup.sh --scopes=cloud-platform
```

`delete` には確認があるので、`--quiet` で答えを省きました。作り直した VM の外部 IP は、前と違います。外部 IP が変わる話は、次の節で扱います。

```sh run title="今度はバケットを作れる"
gcloud compute ssh web-1 --command="gcloud storage buckets create gs://tsubame-shop-ch08-vm --location=asia-northeast1"
gcloud storage ls
```

`Creating gs://tsubame-shop-ch08-vm/...` で成功しました。Cloud Shell の `gcloud storage ls` にも、VM が作ったバケットが出ています。

:::warn デフォルトのサービスアカウントは強すぎる
デフォルトのサービスアカウントは、プロジェクトの編集者です。スコープを `cloud-platform` にした VM は、プロジェクトのほとんどすべてを変えられます。VM が乗っ取られたら、プロジェクトごと乗っ取られます。

本番では、VM ごとに専用のサービスアカウントを作り（`--service-account=…`）、要るロールだけを付けます（第 5 章、第 6 章）。組織のポリシーで、デフォルトのサービスアカウントに編集者が自動で付かないようにもできます。
:::

## 止めると外部 IP は変わる：静的 IP {#ip}

VM を使わない間は、止めておけば CPU とメモリの料金はかかりません。ディスクは残るので、ディスクの料金はかかり続けます。止めてみます。

```sh run title="VM を止める"
gcloud compute instances stop web-1
gcloud compute instances list
```

`web-1` の `STATUS` が `TERMINATED`（停止）になり、`EXTERNAL_IP` の欄が空になりました。止めると、外部 IP は手放されるのです。動かし直してみます。

```sh run title="VM を動かし直す"
gcloud compute instances start web-1
echo "前の IP は $IP"
```

`Instance external IP is …` の新しい IP は、さっきの `$IP` と違います。何も指定せずに付く外部 IP は**エフェメラル IP**（一時的な IP）で、VM が動いている間だけ借りるものです。

なお、`start` のときも startup-script はもう一度動きます（「起動のたびに」動くからです）。nginx はもう入っているので、`apt-get install` は何もせずに終わります。何度実行しても同じ結果になるように書くのが、startup-script のコツです。

IP が変わると、DNS（名前から IP を引く仕組み）に書いた IP も書き直さなければなりません。お客さんに見せる Web サーバでは困ります。そこで、**静的 IP**（固定の外部 IP）を予約します。

```sh run title="静的 IP を予約して、VM に付ける"
gcloud compute addresses create web-ip
gcloud compute instances create web-2 --machine-type=e2-micro --image-family=debian-12 --image-project=debian-cloud --tags=http-server --metadata-from-file=startup-script=startup.sh --address=web-ip
gcloud compute addresses list
```

`addresses create` は、リージョン（`compute/region` の `asia-northeast1`）の外部 IP を 1 つ予約します。`--address=web-ip` で、その IP を `web-2` に付けました。`addresses list` の `STATUS` が `RESERVED`（予約だけ）ではなく `IN_USE`（使用中）なのは、VM が使っているからです。

```sh run title="止めて動かしても、同じ IP"
gcloud compute instances stop web-2
gcloud compute instances start web-2
gcloud compute instances list --format="table(name,status,networkInterfaces[0].accessConfigs[0].natIP:label=EXTERNAL_IP)"
```

`start` のあとの `Instance external IP is …` が、`addresses list` の `ADDRESS` と同じです。止めても変わりませんでした。

:::warn 静的 IP は、使っていないときも料金がかかる
静的 IP は、予約しているだけで料金がかかります（VM に付いていないときの方が高くなります。公式の料金ページを参照）。要らなくなったら `gcloud compute addresses delete` で手放します。VM に付いている間は消せないので、先に VM を消します。
:::

## ディスクとスナップショット {#snapshot}

VM の中身（OS、入れたソフト、データ）は、すべてブートディスクにあります。ディスクの**スナップショット**（ある時点の中身の写し）を取っておけば、壊れたときに戻せます。

```sh run title="ディスクのスナップショットを取る"
gcloud compute disks list
gcloud compute disks snapshot web-2 --snapshot-names=web-2-snap
gcloud compute snapshots list
```

- `disks list` には、VM と同じ名前のディスクが並んでいます。`vm-1`、`web-1`、`web-2` の 3 つです
- `disks snapshot` で、`web-2` のディスクの写しを `web-2-snap` という名前で取りました。VM を止めずに取れます
- スナップショットは、ゾーンではなく、もっと広い場所（リージョンやマルチリージョン）に保存されます。ゾーンが丸ごと使えなくなっても、別のゾーンでディスクを作り直せます

本物では、`gcloud compute disks create 新しいディスク --source-snapshot=web-2-snap` で、スナップショットからディスクを作ります。そのディスクから VM を起動すれば、写しを取ったときの状態に戻ります。毎日決まった時刻に取る**スナップショットのスケジュール**も作れます。

:::note ディスクの種類
`disks list` の `TYPE` の `pd-balanced` は、ディスクの種類です。`pd-standard`（HDD。安くて遅い）、`pd-balanced`（SSD。ふつうはこれ）、`pd-ssd`（速い SSD）などがあり、`--boot-disk-type` で選びます。種類と大きさ（GB）で料金が決まります。
:::

## Spot VM と無料枠で料金を抑える {#cost}

**Spot VM**（スポット VM）は、Google のデータセンターで余っている計算機を、ふつうよりずっと安く借りる VM です。そのかわり、Google の都合で、いつでも止められることがあります（**プリエンプション**、横取りと呼びます）。

```sh run title="Spot VM を作る"
gcloud compute instances create batch-1 --machine-type=e2-micro --image-family=debian-12 --image-project=debian-cloud --provisioning-model=SPOT --instance-termination-action=STOP
gcloud compute instances describe batch-1 --format="yaml(scheduling)"
```

- 一覧の `PREEMPTIBLE` の列が `true` になりました。止められることがある VM の印です
- `provisioningModel: SPOT` が Spot VM の印、`instanceTerminationAction: STOP` は「横取りされたら、消さずに止める」です（`DELETE` にもできます）
- `automaticRestart: false` で、止められても自動では動き出しません

Spot VM が向いているのは、途中で止まってもやり直せる仕事です。動画の変換、夜間の集計、テストなどです。Web サーバのように、止まると困るものには向きません。

:::hist プリエンプティブル VM から Spot VM へ
以前は、同じような VM を **プリエンプティブル VM**（`--preemptible`）と呼んでいました。こちらは、最長 24 時間で必ず止められる決まりでした。2022 年に Spot VM が出て、その上限がなくなりました。一覧の列の名前 `PREEMPTIBLE` は、そのころの名残です。
:::

**無料枠**（Free Tier）を使うと、小さな VM を 1 台、ずっと無料で動かせます。毎月の枠は次のとおりです（繰り越しはありません）。

| 項目 | 毎月の無料枠 |
| --- | --- |
| VM | `e2-micro` を 1 台。`us-west1`、`us-central1`、`us-east1` のどれか。Spot やプリエンプティブルでないもの |
| ディスク | 標準永続ディスク（`pd-standard`）30 GB-月 |
| 転送 | 北米からの外向き転送 1 GB |

東京（`asia-northeast1`）の VM は無料枠に入りません。無料枠に収めるなら、次のように作ります。

```sh norun
gcloud compute instances create free-1 --zone=us-central1-a --machine-type=e2-micro --boot-disk-type=pd-standard --boot-disk-size=30GB
```

最後に、この章で作ったものを片付けます。

```sh run title="片付け"
gcloud compute instances delete vm-1 web-1 web-2 batch-1 --quiet
gcloud compute addresses delete web-ip --quiet
gcloud compute firewall-rules delete allow-http --quiet
gcloud compute disks list
```

`disks list` が `Listed 0 items.` になりました。ブートディスクは、VM を消すと一緒に消えます（`autoDelete: true` だからです）。ただし、**スナップショットは VM を消しても残ります**。`gcloud compute snapshots list` で確かめられます。本物では `gcloud compute snapshots delete` で消します。消し忘れたスナップショットや静的 IP は、気づかないうちに料金がかかり続ける代表です。

:::try やってみよう
`startup.sh` の `apt-get install -y nginx` を `apt-get install -y nginxx` に書き換えて VM を作り、`get-serial-port-output` で `startup-script exit status` がどうなるかを見てみましょう。エラーの文（`Unable to locate package`）もその上に出ます。
:::

:::key まとめ
- VM は、マシンタイプ（大きさ）、イメージから作るブートディスク、ネットワーク インターフェース、サービスアカウント、メタデータでできている。VM とディスクは 1 つのゾーンにある
- `instances create` の `--image-family` と `--image-project` で OS を選ぶ。`describe` は `--format` で項目を絞る
- startup-script は起動のたびに root で動く。結果は `get-serial-port-output` で見る。外から届かせるには、ファイアウォールのルール（タグで対象を選ぶ）が要る
- メタデータサーバ（`metadata.google.internal`、ヘッダー `Metadata-Flavor: Google`）は VM の中からだけ届き、名前・IP・メタデータ・トークンを答える
- VM から API を呼ぶと、スコープと IAM の 2 つの関門を通る。スコープは `cloud-platform` にして、権限は専用のサービスアカウントのロールで絞る
- 止めるとエフェメラルな外部 IP は手放す。変わっては困るなら、静的 IP を予約して `--address` で付ける
- スナップショットでディスクを写す。Spot VM は安いが止められる。無料枠は米国の 3 リージョンの `e2-micro` 1 台
:::

## 確認問題 {#quiz}

この章のコマンドを、自分で組み立てて確かめます。どの問題も、Compute Engine API は有効で、既定のゾーンは `asia-northeast1-b` になっています。

:::quiz 動いている VM の名前
いくつかの VM があり、止まっているものもあります。**動いている（`RUNNING` の）VM の名前だけ**を、1 行に 1 つずつ出してください。

```sh prep
gcloud services enable compute.googleapis.com
gcloud config set compute/region asia-northeast1
gcloud config set compute/zone asia-northeast1-b
gcloud compute instances create app-1 app-2 batch-1 --machine-type=e2-micro
gcloud compute instances stop app-2
```

```sh vary
gcloud compute instances create app-3 --machine-type=e2-small
gcloud compute instances stop batch-1
gcloud compute instances start app-2
```

```sh starter
gcloud compute instances list
```

```sh answer unordered
gcloud compute instances list --filter="status=RUNNING" --format="value(name)"
```

:::hint
`--filter="status=…"` で行を絞り、`--format="value(name)"` で名前だけにします。
:::
:::

:::quiz VM のマシンタイプ
VM `web-1` のマシンタイプを、`e2-small` のような**名前だけ**で 1 行に出してください（URL のままではいけません）。

```sh prep
gcloud services enable compute.googleapis.com
gcloud config set compute/region asia-northeast1
gcloud config set compute/zone asia-northeast1-b
gcloud compute instances create web-1 --machine-type=e2-small
```

```sh vary
gcloud compute instances delete web-1 --quiet
gcloud compute instances create web-1 --machine-type=e2-standard-2
```

```sh answer
gcloud compute instances describe web-1 --format="value(machineType.basename())"
```

:::hint
`describe` の `machineType` は URL です。`.basename()` で最後の部分だけになります。
:::
:::

:::quiz 静的 IP の Web サーバ
Cloud Shell のホームに、nginx を入れる `startup.sh` があります。ファイアウォールのルール `allow-http`（タグ `http-server` の VM の 80 番を開ける）も作ってあります。

次の VM を作ってください。

- 静的 IP `web-ip` を予約する（リージョンは既定の `asia-northeast1`）
- VM の名前は `web-1`、マシンタイプは `e2-micro`
- `startup.sh` を startup-script として渡す
- タグ `http-server` を付け、外部 IP に `web-ip` を使う

```sh prep
gcloud services enable compute.googleapis.com
gcloud config set compute/region asia-northeast1
gcloud config set compute/zone asia-northeast1-b
gcloud compute firewall-rules create allow-http --allow=tcp:80 --target-tags=http-server
printf '#! /bin/bash\napt-get update\napt-get install -y nginx\n' > startup.sh
```

```sh answer
gcloud compute addresses create web-ip
gcloud compute instances create web-1 --machine-type=e2-micro --tags=http-server --metadata-from-file=startup-script=startup.sh --address=web-ip
```

```sh check
gcloud compute addresses list --format="value(name,status)"
gcloud compute instances describe web-1 --format="value(machineType.basename(),tags.items[0])"
sleep 30
curl -s http://$(gcloud compute addresses list --filter="name=web-ip" --format="value(address)") | grep title
```

:::hint
先に `gcloud compute addresses create` で予約し、`instances create` の `--address` にその名前を渡します。startup-script は `--metadata-from-file=startup-script=ファイル` です。
:::
:::

:::quiz VM の中からバケットを作れるようにする
VM `tool-1` は、デフォルトのアクセススコープで作られています。そのため、VM の中から `gcloud storage buckets create` を実行すると、スコープで断られます。

`tool-1` を（名前はそのままで）作り直すか設定を変えて、VM の中からバケットを作れるようにしてください。最後に `tool-1` が動いている（`RUNNING`）状態にしておきます。マシンタイプは `e2-micro` です。


:::hint
