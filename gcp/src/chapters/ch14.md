## Cloud SQL は何を引き受けてくれるか {#managed}

つばめ文具の店には、商品や注文の表が要ります。行を足し、更新し、集計する。こういう仕事には、PostgreSQL のような**リレーショナルデータベース**（表と SQL で扱うデータベース）が向いています。

PostgreSQL は、第 8 章の VM に自分で入れることもできます。けれども、それだと OS の更新、PostgreSQL の更新、バックアップ、ディスクが足りなくなったときの対応を、全部自分でやることになります。**Cloud SQL** は、そこを Google が引き受ける**マネージド**（管理を任せられる）なデータベースのサービスです。

Cloud SQL は PostgreSQL のほかに MySQL と SQL Server も選べます。この本では PostgreSQL だけを扱います。中身は本物の PostgreSQL なので、SQL の書き方はそのまま使えます。SQL そのものは [図解 PostgreSQL](../../postgresql/site/index.html) で詳しく扱っています。

まずは、いまのプロジェクトにインスタンス（Cloud SQL の 1 台ぶんのデータベースサーバー）があるかを見てみます。

```sh run title="Cloud SQL の API はまだ無効" error
gcloud sql instances list
```

`Cloud SQL Admin API has not been used in project … or it is disabled` は、第 3 章で見た「API が無効」のエラーです。Cloud SQL を操作する API は `sqladmin.googleapis.com` という名前です。有効にしてから、もう一度試します。

```sh run title="API を有効にする"
gcloud services enable sqladmin.googleapis.com
gcloud sql instances list
```

今度はエラーになりません。`Listed 0 items.` は「インスタンスは 1 つもない」という意味です。

:::note このサイトの GCP では
中身の PostgreSQL は、ブラウザで動く PGlite（本物の PostgreSQL 18 を WebAssembly にしたもの）です。インスタンスのつくり、IP アドレス、接続の許可は模型で、本物の Cloud SQL の振る舞いをまねています。
:::

## インスタンスを作る：エディションとティア {#create}

インスタンスを作るときに決める大事な項目は、**エディション**（機能と性能の等級）と**ティア**（マシンの大きさ）の 2 つです。

| エディション | `--edition` | ティアの例 | 向いている使い方 |
| --- | --- | --- | --- |
| Enterprise | `enterprise` | `db-f1-micro`、`db-g1-small`（共有コア）、`db-custom-1-3840`（1 vCPU、3.75 GB） | 開発、試し、小さなサービス |
| Enterprise Plus | `enterprise-plus` | `db-perf-optimized-N-2`（2 vCPU、16 GB）など | 性能と可用性が大事な本番 |

`db-f1-micro` は、CPU をほかと分け合う**共有コア**のいちばん小さいティアです。試すにはこれで十分です。ただし、組み合わせに決まりがあります。まず、エディションを指定せずに作ってみます。

```sh run title="エディションとティアが合わない" error
gcloud sql instances create shop-db --tier=db-f1-micro --region=asia-northeast1
```

エラーの文を読みます。`Invalid Tier (db-f1-micro) for (ENTERPRISE_PLUS) Edition` は「Enterprise Plus では db-f1-micro は使えない」という意味です。指定しなかったエディションが Enterprise Plus になったのは、PostgreSQL 16 以降の既定がそうなっているからです。いまの既定のバージョンは PostgreSQL 18 です。

直し方は 2 つあります。`--edition=enterprise` を付けるか、`db-perf-optimized-N-2` のような Enterprise Plus のティアを選ぶかです。ここでは安い方を選びます。

```sh run title="インスタンスを作る（数分かかる）"
date
gcloud sql instances create shop-db --edition=enterprise --tier=db-f1-micro --region=asia-northeast1 --root-password=Tsubame-root-1
date
```

前後の `date` を見比べてください。作成に 7 分ほどかかっています。本物でも、中で VM とディスクを用意して PostgreSQL を起動するので、数分かかります。`--region=asia-northeast1` は東京リージョンで、作った後で場所は変えられません。`--root-password` は、最初からいる管理用のユーザー `postgres` のパスワードです。

:::warn 本物ではパスワードを履歴に残さない
本文では分かりやすさのためにパスワードをコマンドに書いています。本物では、シェルの履歴に残らないように、gcloud に聞いてもらう（`gcloud sql users set-password` の `--prompt-for-password` など）か、Secret Manager（秘密の値を預けるサービス）を使ってください。
:::

### 接続名と IP アドレス

作ったインスタンスの情報は `describe` で見られます。全部を出すと長いので、`--format` で欲しいところだけを取り出します。

```sh run title="接続名と IP アドレス"
gcloud sql instances list
gcloud sql instances describe shop-db --format="value(connectionName)"
gcloud sql instances describe shop-db --format="yaml(ipAddresses)"
gcloud sql instances describe shop-db --format="value(settings.edition,settings.tier,databaseVersion,state)"
```

`tsubame-shop:asia-northeast1:shop-db` が**接続名**です。「プロジェクト:リージョン:インスタンス名」の形で、このあと Cloud Run や Auth Proxy からつなぐときに使います。

`ipAddresses` には 2 つ出ています。`PRIMARY` の `34.85.202.133` は、外からつなぐときの宛先です。`OUTGOING` は、インスタンスから外へ出ていくときの送り元のアドレスです。最後の行は、エディション、ティア、バージョン、状態（`RUNNABLE` は動いている）です。

## データベースとユーザーを足す {#databases-users}

1 つのインスタンスの中には、データベースをいくつも作れます。ユーザーはインスタンス全体で共通で、どのデータベースにも入れます。データベースもユーザーも、SQL の `create database` や `create role` ではなく、gcloud で作るのが Cloud SQL の作法です。gcloud で作ると、Cloud SQL がその存在を知っていて、一覧やコンソールに出せるからです。

```sh run title="データベースとユーザーを作る"
gcloud sql databases create shop --instance=shop-db
gcloud sql databases list --instance=shop-db
gcloud sql users create app --instance=shop-db --password=App-pass-1
gcloud sql users list --instance=shop-db --format="table(name,type)"
```

`databases list` には、最初からある `postgres` と、作った `shop` が出ます。`users list` の `TYPE` の `BUILT_IN` は、パスワードでログインする、PostgreSQL の中のユーザーという意味です。

## gcloud sql connect で SQL を流す {#connect}

いよいよ中に入ります。いちばん手軽なのは `gcloud sql connect` です。このコマンドは、裏で 2 つのことをしています。

```fig seq gcloud sql connect がしていること。まず API で自分の IP を一時的に許可し、それから psql でつなぐ
{
  colw: 230,
  actors: [
    { id: 'cs', label: 'Cloud Shell', kind: 'ext' },
    { id: 'api', label: 'Cloud SQL Admin API', kind: 'stack' },
    { id: 'db', label: 'shop-db（5432 番）', kind: 'accent' },
  ],
  msgs: [
    { from: 'cs', to: 'api', label: '自分の IP を 5 分だけ許可して', style: 'accent' },
    { from: 'api', to: 'db', label: '承認済みネットワークに一時的に足す' },
    { from: 'cs', to: 'db', label: 'psql でつなぐ（ユーザーとパスワード）', style: 'accent' },
    { from: 'db', to: 'cs', label: 'SQL の結果' },
    { note: '5 分たつと、許可は消える', at: ['api', 'db'] },
  ],
}
```

1 つ目は、API を呼んで、Cloud Shell の IP アドレスを 5 分だけ「つないでよい相手」に入れることです。2 つ目は、**psql**（PostgreSQL の標準のクライアント）を起動して、インスタンスにつなぐことです。

psql はパスワードを聞いてきます。ここでは環境変数 `PGPASSWORD` で先に渡しておき、実行する SQL は**ヒアドキュメント**（`<<'SQL'` から `SQL` までの行を、標準入力として渡す書き方）で流します。

まず、アプリ用のユーザー `app` で `shop` に入り、表を作ります。`--user` と `--database` を省くと、`--root-password` で決めたユーザー `postgres` でデータベース `postgres` に入ります。

```sh run title="app で shop に入り、表を作る"
PGPASSWORD=App-pass-1 gcloud sql connect shop-db --user=app --database=shop <<'SQL'
create table products (
  id    int primary key,
  name  text not null,
  price int not null
);
insert into products values
  (1, '方眼ノート A5', 380),
  (2, 'ボールペン 黒', 120),
  (3, '万年筆 青', 3200);
select * from products order by id;
SQL
```

`Allowlisting your IP for incoming connection for 5 minutes...done.` が 1 つ目の仕事です。その後の `CREATE TABLE`、`INSERT 0 3`、3 行の表は、本物の PostgreSQL の応答そのものです。

### psql のメタコマンド

psql には、`\` で始まる**メタコマンド**（SQL ではなく、psql 自身への命令）があります。よく使う 3 つを試します。

```sh run title="\dt、\l、\du"
PGPASSWORD=App-pass-1 gcloud sql connect shop-db --user=app --database=shop <<'SQL'
\dt
\l
\du
SQL
```

| メタコマンド | 出るもの |
| --- | --- |
| `\dt` | いまのデータベースの表の一覧。`products` の持ち主（Owner）は `app` |
| `\l` | インスタンスの中のデータベースの一覧。`postgres` と `shop` |
| `\du` | ユーザー（ロール）の一覧。`app` と `postgres` |

`\l` の `Owner` が `cloudsqlsuperuser` になっています。これは Cloud SQL が用意した管理用のロールです。Cloud SQL では、本当の意味での**スーパーユーザー**（何でもできるユーザー）は使わせてもらえません。OS やファイルに触れる操作は、Google の側の仕事だからです。

### パスワードを間違えると

```sh run title="パスワードが違う" error
PGPASSWORD=wrong-pass gcloud sql connect shop-db --user=app --database=shop <<'SQL'
select 1;
SQL
```

`FATAL:  password authentication failed for user "app"` は、PostgreSQL が「app のパスワードが違う」と断ったという意味です。IP の許可（1 つ目の仕事）はできているので、ネットワークの問題ではありません。

パスワードを忘れたら、gcloud で付け直せます。古いパスワードは要りません。

```sh run title="パスワードを付け直す"
gcloud sql users set-password app --instance=shop-db --password=App-pass-2
PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'
select count(*) from products;
SQL
```

新しいパスワード `App-pass-2` で入れて、`count` は `3` です。このあとは `App-pass-2` を使います。

### 承認済みネットワーク：IP で許可する

インスタンスの公開 IP に、psql で直接つないでみます。`gcloud sql connect` が開けた 5 分の許可は、時間がたてば消えます。それを過ぎた状態で、`-h` に IP を指定してつなぐとどうなるでしょう。

```sh run title="公開 IP に直接つなぐ" error
PGPASSWORD=App-pass-2 psql -h 34.85.202.133 -U app -d shop <<'SQL'
select 1;
SQL
```

`Connection timed out` です。パスワードのエラーではありません。インスタンスが、知らない IP からの接続を黙って捨てているので、待っても返事が来ないのです。

公開 IP に入れてよい相手は、**承認済みネットワーク**（authorized networks）という IP アドレスの一覧で決めます。最初は空なので、だれもつなげません。Cloud Shell の外向きの IP は `34.146.93.21` です。これを `/32`（その 1 つのアドレスだけ）で足します。

```sh run title="承認済みネットワークに Cloud Shell の IP を足す"
gcloud sql instances patch shop-db --authorized-networks=34.146.93.21/32
gcloud sql instances describe shop-db --format="value(settings.ipConfiguration.authorizedNetworks[].value)"
PGPASSWORD=App-pass-2 psql -h 34.85.202.133 -U app -d shop <<'SQL'
select name, price from products order by id;
SQL
```

今度はつながりました。`patch` は、インスタンスの設定を変えるコマンドです。`--authorized-networks` は一覧を**置き換える**ので、足すときは前からある IP も並べて書きます。

:::warn 0.0.0.0/0 は入れない
`0.0.0.0/0` を入れると、世界中のどこからでも 5432 番にたどり着けます。あとはパスワードだけが頼りになり、総当たりで試されます。承認済みネットワークには、決まった IP だけを入れてください。IP が決まらない機械からは、次の Auth Proxy を使います。
:::

:::note このサイトの GCP では
本物の `gcloud sql connect` は、承認済みネットワークに自分の IP を 5 分だけ書き足し、あとで消します。このサイトの模型は一覧を書き換えず、`gcloud sql connect` のときだけ通します。
:::

### Cloud SQL Auth Proxy：IP ではなく IAM で許可する

**Cloud SQL Auth Proxy** は、Google が配っている小さなプログラムです。手元の機械で動かすと、`127.0.0.1:5432` で待ち受けます。そこに psql でつなぐと、Proxy が IAM（第 6 章）で「この人は Cloud SQL につないでよいか」を確かめ、暗号化した通り道でインスタンスまで運びます。

```console
$ ./cloud-sql-proxy tsubame-shop:asia-northeast1:shop-db
… Listening on 127.0.0.1:5432
$ psql -h 127.0.0.1 -U app -d shop
```

引数は接続名です。必要な権限は `roles/cloudsql.client`（Cloud SQL Client）のロールです。IP が変わる手元のパソコンや、承認済みネットワークを使いたくないときは、こちらが勧められています。このサイトには `cloud-sql-proxy` のプログラムがないので、上の例は読むだけにしてください。

### プライベート IP：VPC の中だけでつなぐ

公開 IP を持たせず、VPC（第 9 章）の中のアドレスだけを持たせることもできます。`--network` で VPC を選び、`--no-assign-ip` で公開 IP をなくします。

```sh run title="プライベート IP だけのインスタンス"
gcloud sql instances create shop-db-private --edition=enterprise --tier=db-f1-micro --region=asia-northeast1 --network=default --no-assign-ip
gcloud sql instances describe shop-db-private --format="yaml(ipAddresses)"
```

`ipAddresses` には `10.25.0.3`、`type: PRIVATE` の 1 つだけが出ます。同じ VPC の中の VM からはこのアドレスでつなげますが、外からは道がありません。

```sh run title="Cloud Shell からはつなげない" error
gcloud sql connect shop-db-private
```

エラーの文は「インスタンスに IPv4 のアドレスがない」です。Cloud Shell は VPC の外にいるので、プライベート IP には届きません。本物では、プライベート IP を使う前に、VPC に「プライベート サービス アクセス」という接続を設定しておく必要があります（手順は公式ドキュメントを参照）。このサイトの模型は、その手順を省いています。

## Cloud Run からつなぐ {#cloud-run}

第 10 章の Cloud Run から、`shop` の表を読む API を作ります。Cloud Run では、接続名を Cloud Run に教えておくと、コンテナの中に `/cloudsql/接続名` という **Unix ソケット**（同じ機械の中でプロセスどうしがつなぐための、ファイルの形をした口）ができます。その裏で Auth Proxy と同じ仕組みが動きます。

```fig graph Cloud Run から Cloud SQL へ。アプリは /cloudsql/接続名 につなぐだけで、IP もプロキシも書かない
{
  col: 240, row: 90,
  nodes: [
    { id: 'u', label: 'curl', sub: '利用者', x: 0, y: 0, kind: 'ext' },
    { id: 'app', label: 'server.js', sub: 'pg の Pool', x: 1, y: 0, kind: 'crate' },
    { id: 'sock', label: '/cloudsql/tsubame-shop:\nasia-northeast1:shop-db', sub: 'Unix ソケット', x: 1, y: 1, kind: 'stack' },
    { id: 'db', label: 'shop-db', sub: 'shop データベース', x: 2, y: 1, kind: 'accent' },
  ],
  edges: [
    { from: 'u', to: 'app', label: 'HTTPS' },
    { from: 'app', to: 'sock', label: 'host に指定' },
    { from: 'sock', to: 'db', label: '--add-cloudsql-instances', style: 'accent' },
  ],
  groups: [ { label: 'Cloud Run のコンテナ', nodes: ['app', 'sock'] } ],

```

アプリは Node.js で書き、PostgreSQL につなぐのに **pg**（node-postgres）というモジュールを使います。`host` に `/cloudsql/` で始まるパスを書くと、pg は TCP ではなく Unix ソケットでつなぎます。

```sh run title="API のソースを書く"
mkdir -p ~/api
cat > ~/api/package.json <<'EOF'
{ "name": "api", "main": "server.js", "dependencies": { "pg": "^8.13.0" } }
EOF
cat > ~/api/server.js <<'EOF'
const http = require('http');
const { Pool } = require('pg');
const pool = new Pool({ host: '/cloudsql/' + process.env.INSTANCE, user: 'app', password: process.env.DB_PASS, database: 'shop' });
http.createServer(async (req, res) => {
  try {
    const r = await pool.query('select id, name, price from products order by id');
    res.end(JSON.stringify(r.rows) + '\n');
  } catch (e) { res.statusCode = 500; res.end('error: ' + e.message + '\n'); }
}).listen(process.env.PORT || 8080);
EOF
```

接続名とパスワードは、環境変数 `INSTANCE` と `DB_PASS` で渡します。まず、Cloud SQL のことを Cloud Run に教えずにデプロイしてみます。

```sh run title="接続名を教えずにデプロイする"
gcloud run deploy api --source ~/api --region=asia-northeast1 --allow-unauthenticated --set-env-vars=INSTANCE=tsubame-shop:asia-northeast1:shop-db,DB_PASS=App-pass-2 --quiet
curl -s https://api-365600345236.asia-northeast1.run.app
```

デプロイはできましたが、curl の答えは `connect ENOENT /cloudsql/…/.s.PGSQL.5432` です。`ENOENT` は「そのファイルがない」という意味です。Cloud Run が接続名を知らないので、ソケットを作っていないのです。

`--add-cloudsql-instances` で接続名を足して、デプロイし直します。

```sh run title="--add-cloudsql-instances を付けてデプロイし直す"
gcloud run deploy api --source ~/api --region=asia-northeast1 --add-cloudsql-instances=tsubame-shop:asia-northeast1:shop-db --quiet
curl -s https://api-365600345236.asia-northeast1.run.app
```

今度は `products` の 3 行が JSON で返りました。環境変数は前のリビジョンから引き継がれています。

つなぐときに使われるのは、Cloud Run のサービスアカウント（ここでは既定の Compute Engine のサービスアカウント）の権限です。専用のサービスアカウントにするときは、`roles/cloudsql.client` を付けてください。パスワードも、本物では環境変数に直接書かず、Secret Manager に預けて `--set-secrets` で渡すのがよいやり方です。

## バックアップと復元 {#backups}

Cloud SQL は、毎日決まった時刻に自動でバックアップを取ります（既定で 7 個まで残す）。大きな作業の前には、自分でも取れます。

```fig graph バックアップから復元すると、インスタンス全体が「取った時点」に戻る。後から足した行も消える
{
  col: 200, row: 80,
  nodes: [
    { id: 'now', label: 'shop-db', sub: 'products 3 行', x: 0, y: 0, kind: 'accent' },
    { id: 'bk', label: 'バックアップ', sub: '3 行の時点', x: 1, y: 0, kind: 'stack' },
  ],
  edges: [ { from: 'now', to: 'bk', label: 'backups create', style: 'accent' } ],
  steps: [
    { title: '取る', say: '<code>gcloud sql backups create</code> で、インスタンス全体（すべてのデータベース）の写しを取ります。' },
    { title: '消してしまう', say: 'うっかり <code>delete from products</code> を実行して、行が 0 になりました。バックアップは 3 行のままです。',
      nodes: [ { id: 'now', label: 'shop-db', sub: 'products 0 行', x: 0, y: 0, kind: 'bad' }, { id: 'bk', label: 'バックアップ', sub: '3 行の時点', x: 1, y: 0, kind: 'stack' } ],
      edges: [] },
    { title: '戻す', say: '<code>gcloud sql backups restore</code> で、バックアップの中身をインスタンスに書き戻します。行は 3 に戻ります。',
      nodes: [ { id: 'now', label: 'shop-db', sub: 'products 3 行', x: 0, y: 0, kind: 'accent' }, { id: 'bk', label: 'バックアップ', sub: '3 行の時点', x: 1, y: 0, kind: 'stack' } ],
      edges: [ { from: 'bk', to: 'now', label: 'backups restore', style: 'accent' } ] },
  ],
}
```

```sh run title="バックアップを取って、一覧を見る"
gcloud sql backups create --instance=shop-db
gcloud sql backups list --instance=shop-db --format="table(id,windowStartTime,status)"
```

`ID` の数字が、このバックアップの名前です。`STATUS` が `SUCCESSFUL` なら取れています。では、うっかり全部の行を消してしまいます。

```sh run title="うっかり全部消す"
PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'
delete from products;
select count(*) from products;
SQL
```

`DELETE 3` で、`count` は `0` になりました。バックアップから戻します。ID は手で写さずに、一覧のいちばん新しい 1 つを `--limit=1` と `value(id)` で取り出します。

```sh run title="バックアップから復元する"
BID=$(gcloud sql backups list --instance=shop-db --format="value(id)" --limit=1)
gcloud sql backups restore $BID --restore-instance=shop-db --quiet
PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'
select count(*) from products;
SQL
```

`count` は `3` に戻りました。`--quiet` を付けないと、`All current data on the instance will be lost when the backup is restored.` と確かめてきます。復元は**インスタンス全体**を戻すので、バックアップの後に足した行は、どのデータベースのものでも消えます。

:::deep 時刻を指定して戻す
本物の Cloud SQL には、**ポイントインタイム リカバリ**（PITR）もあります。WAL（変更の記録）を残しておき、「午前 10 時 12 分の状態」のように時刻を指定して、新しいインスタンスに戻せます。このサイトの模型にはありません。
:::

## 止めて料金を抑え、消せないように守る {#stop}

Cloud SQL のインスタンスは、使っていなくても動いている間はずっと料金がかかります。Compute Engine の e2-micro のような「いつも無料」の枠もありません（第 4 章の無料枠の一覧に Cloud SQL は入っていません）。夜や週末に使わない開発用のインスタンスは、止めておくのが基本です。

止めるには、**アクティベーション ポリシー**（いつ動かすか）を `NEVER` にします。

```sh run title="インスタンスを止める"
gcloud sql instances patch shop-db --activation-policy=NEVER
gcloud sql instances list
```

`shop-db` の `STATUS` が `STOPPED` になりました。止めている間は CPU とメモリの料金がかかりません。ただし、データを入れたディスクは残るので、その料金はかかり続けます（詳しくは公式の料金ページを参照）。

```sh run title="止まっているとつなげない" error
PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop
```

`Invalid request since instance is not running.` は「動いていないインスタンスには、その操作はできない」という意味です。### 削除の保護

本番のインスタンスは、うっかり消されないように守りたいものです。下のブロックでは、まず `ALWAYS` に戻してインスタンスを動かし、それから `--deletion-protection` で削除の保護を付けます。

```sh run title="また動かして、削除の保護を付ける"
gcloud sql instances patch shop-db --activation-policy=ALWAYS
gcloud sql instances patch shop-db --deletion-protection
gcloud sql instances describe shop-db --format="value(state,settings.deletionProtectionEnabled)"
```

```sh run title="保護されていると消せない" error
gcloud sql instances delete shop-db --quiet
```

`RUNNABLE` と `True` を確かめてから消そうとすると、`The instance is protected.` で止まりました。`--quiet` で確認を飛ばしても消えません。本当に消すときは、`--no-deletion-protection` で保護を外してからにします。

最後に、この章で作ったものを片付けます。

```sh run title="片付け"
gcloud sql instances patch shop-db --no-deletion-protection
gcloud sql instances delete shop-db --quiet
gcloud sql instances delete shop-db-private --quiet
gcloud run services delete api --region=asia-northeast1 --quiet
gcloud sql instances list
```

:::key まとめ
- Cloud SQL は、OS・更新・バックアップを Google が引き受ける PostgreSQL（ほかに MySQL、SQL Server）。API は `sqladmin.googleapis.com`
- インスタンスはエディションとティアで決まる。PostgreSQL 16 以降の既定は Enterprise Plus で、`db-f1-micro` を使うには `--edition=enterprise` が要る
- データベースとユーザーは `gcloud sql databases create` / `users create` で作る。パスワードは `users set-password` で付け直せる
- `gcloud sql connect` は、自分の IP を 5 分だけ許可してから psql でつなぐ。SQL はヒアドキュメントで流せる
- 公開 IP に直接つなぐには承認済みネットワークが要る（ないとタイムアウト）。IP が決まらないなら Auth Proxy、VPC の中だけならプライベート IP、Cloud Run からは `--add-cloudsql-instances` と `/cloudsql/接続名`
- `backups create` / `restore` はインスタンス全体を戻す。使わないときは `--activation-policy=NEVER` で止め、本番は `--deletion-protection` で守る
:::

## 確認問題 {#quiz}

Cloud SQL のインスタンスを、自分のコマンドで調べたり直したりします。どの問題も、準備で `shop-db` などのインスタンスが作ってあります。

:::quiz 300 円以上の商品
インスタンス `shop-db` のデータベース `shop` に、表 `products`（`id`、`name`、`price`）があります。ユーザー `app`（パスワード `App-pass-2`）で入り、`price` が 300 以上の商品の `name` だけを、`id` の順に表示してください。psql の表の形のままで構いません。

```sh prep
gcloud services enable sqladmin.googleapis.com
gcloud sql instances create shop-db --edition=enterprise --tier=db-f1-micro --region=asia-northeast1
gcloud sql databases create shop --instance=shop-db
gcloud sql users create app --instance=shop-db --password=App-pass-2
PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'
create table products (id int primary key, name text not null, price int not null);
insert into products values (1, '方眼ノート A5', 380), (2, 'ボールペン 黒', 120), (3, '万年筆 青', 3200);
SQL
```

```sh vary
PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'
insert into products values (4, '消しゴム', 100), (5, '手帳 2027', 1500), (0, '色鉛筆 12 色', 980), (6, '付箋 75mm', 300);
SQL
```

```sh answer
PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'
select name from products where price >= 300 order by id;
SQL
```

:::

:::quiz 止まっているインスタンス
プロジェクトにはインスタンスがいくつかあり、そのうちいくつかは止めてあります。**止まっている**インスタンスの名前だけを、1 行に 1 つ表示してください。

```sh prep
gcloud services enable sqladmin.googleapis.com
gcloud sql instances create shop-db --edition=enterprise --tier=db-f1-micro --region=asia-northeast1
gcloud sql instances create dev-db --edition=enterprise --tier=db-f1-micro --region=asia-northeast1
gcloud sql instances create test-db --edition=enterprise --tier=db-f1-micro --region=asia-northeast1
gcloud sql instances patch dev-db --activation-policy=NEVER
```

```sh vary
gcloud sql instances patch dev-db --activation-policy=ALWAYS
gcloud sql instances patch test-db --activation-policy=NEVER
gcloud sql instances patch shop-db --activation-policy=NEVER
```

```sh answer unordered
gcloud sql instances list --filter="settings.activationPolicy=NEVER" --format="value(name)"
```

:::hint
止めたインスタンスは、`settings.activationPolicy` が `NEVER` です。`--filter` で絞り、`--format="value(name)"` で名前だけを出します。
:::

SQL
gcloud sql backups create --instance=shop-db
PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'

gcloud sql backups create --instance=shop-db

PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'

:::hint
