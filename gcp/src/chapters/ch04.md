この章の準備で、請求先のない新しいプロジェクト `tsubame-trial`（つばめ 試用）を作ってあります。`tsubame-shop` との違いを比べながら進みます。

## 請求先アカウントは、プロジェクトの外にある財布 {#billing-account}

Google Cloud で使った分のお金は、**請求先アカウント**（Cloud Billing account）に請求されます。請求先アカウントは、支払い方法（クレジットカードや請求書払い）と通貨を持った「財布」です。プロジェクトは、どれか 1 つの請求先アカウントにつながると、有料のサービスを使えるようになります。

```fig graph 請求先アカウントは、組織 → フォルダ → プロジェクトの木の外にある。プロジェクトは 0 か 1 つの請求先アカウントにつながる。1 つの請求先アカウントには、いくつものプロジェクトをつなげる
{
  col: 210, row: 92,
  nodes: [
    { id: 'org', label: '組織', sub: 'tsubame.example', x: 0, y: 0, kind: 'stack', mono: false },
    { id: 'shop', label: 'tsubame-shop', sub: '請求先あり', x: 1, y: 0, kind: 'crate' },
    { id: 'pub', label: 'tsubame-public', sub: '請求先あり', x: 1, y: 1, kind: 'crate' },
    { id: 'trial', label: 'tsubame-trial', sub: '請求先なし', x: 1, y: 2, kind: 'muted' },
    { id: 'bill', label: '請求先アカウント', sub: '01A2B3-C4D5E6-F7A8B9（JPY）', x: 2, y: 1, kind: 'accent', mono: false },

  ],
  edges: [
    { from: 'org', to: 'shop' }, { from: 'org', to: 'pub' }, { from: 'org', to: 'trial' },

```

大事なのは、請求先アカウントが**リソースの階層（第 2 章）の外**にあることです。組織の下にプロジェクトがあるのとは別に、請求先アカウントは独立したリソースで、自分の IAM ポリシーを持ちます。だから「プロジェクトの持ち主」と「お金を払う人」を分けられます。

あなたが使える請求先アカウントを見てみます。

```sh run title="請求先アカウントの一覧"
gcloud billing accounts list
```

`ACCOUNT_ID` の `01A2B3-C4D5E6-F7A8B9` が請求先アカウントの ID です。6 文字ずつ 3 つに区切った形で、プロジェクトの ID とは見た目が違います。`OPEN` が `True` なら、いま使える（閉じられていない）請求先です。`MASTER_ACCOUNT_ID` は、販売代理店（リセラー）経由で契約したときの親アカウントで、ふつうは空です。

```sh run title="1 つの請求先アカウントの詳細"
gcloud billing accounts describe 01A2B3-C4D5E6-F7A8B9
```

`currencyCode: JPY` は、この請求先が日本円で請求されることを表します。通貨は請求先アカウントを作るときに決まり、あとの予算（この章の後半）もこの通貨で書きます。

### プロジェクトから見た請求先

プロジェクトの側から、「どの請求先につながっているか」を調べるのが `gcloud billing projects describe` です。

```sh run title="tsubame-shop の請求先"
gcloud billing projects describe tsubame-shop
```

見るのは 2 行です。`billingAccountName` がつながっている請求先、`billingEnabled: true` が「請求が有効」という意味です。逆向きに、1 つの請求先アカウントにつながっているプロジェクトの一覧も出せます。

```sh run title="請求先アカウントにつながっているプロジェクト"
gcloud billing projects list --billing-account=01A2B3-C4D5E6-F7A8B9
```

`tsubame-public` と `tsubame-shop` の 2 つです。準備で作った `tsubame-trial` は出てきません。

```sh run title="新しいプロジェクトの請求先"
gcloud billing projects describe tsubame-trial
```

`billingAccountName: ''`（空）、`billingEnabled: false` です。**`gcloud projects create` で作ったばかりのプロジェクトには、請求先がありません。** 作った人が自分でつなぐまで、このままです。

:::note 請求先アカウントの作り方
請求先アカウントそのものは、ふつうコンソール（Web の管理画面）で支払い方法を登録して作ります。この章の gcloud のコマンドは、できている請求先アカウントを使う側のものです。無料トライアルに申し込んだときにも 1 つ作られます。このサイトの GCP では、つばめ文具の請求先が最初から 1 つあります。
:::

## 請求先がないと、何が使えないか {#no-billing}

請求先のない `tsubame-trial` で、何ができて何ができないかを試します。まず、操作の対象をこのプロジェクトに切り替えます。

```sh run title="tsubame-trial に切り替えて、有効な API を見る"
gcloud config set project tsubame-trial
gcloud services list --enabled --format="value(config.name)"
```

新しいプロジェクトでも、`bigquery.googleapis.com`、`storage.googleapis.com`、`logging.googleapis.com` などはすでに有効です（第 3 章）。では、VM を動かす Compute Engine の API を有効にしてみます。

```sh run title="請求先がないと、Compute Engine を有効にできない" error
gcloud services enable compute.googleapis.com
```

エラーの 1 行目を読みます。

- `FAILED_PRECONDITION`：「前提が満たされていない」。権限の問題（`PERMISSION_DENIED`）ではありません
- `Billing account for project '…' is not found`：このプロジェクト（番号で書かれている）に請求先がない
- `Billing must be enabled for activation of service(s) 'compute.googleapis.com'`：この API を有効にするには請求が有効でなければならない

下に続く `reason: UREQ_PROJECT_BILLING_NOT_FOUND` も同じ意味です。直し方は 1 つで、**プロジェクトを請求先アカウントにつなぐ**ことです（次の次の節）。

Compute Engine、Cloud Run、Cloud Run functions、Cloud SQL、Pub/Sub など、使うとすぐにお金がかかりうるサービスの多くは、請求先がないと有効にできません。逆に、最初から有効な API の中には、請求先がなくても一部の機能を使えるものがあります。その代表が BigQuery です。

## BigQuery サンドボックス：請求先なしで試せる範囲 {#sandbox}

**BigQuery サンドボックス**は、請求先のないプロジェクトで BigQuery を使える仕組みです。申し込みは要りません。請求先がないプロジェクトで BigQuery を使うと、自動的にサンドボックスとして扱われます。そのかわり、いくつかの制限があります。

| | サンドボックス（請求先なし） | 請求先あり |
| --- | --- | --- |
| クエリ（SELECT） | 使える（無料枠の範囲） | 使える。無料枠を超えた分は有料 |
| テーブルの寿命 | 60 日で期限切れ | 決めなければ無期限 |
| DML（INSERT、UPDATE、DELETE、MERGE） | 使えない | 使える |

データセットを作って、確かめてみます。

```sh run title="サンドボックスでデータセットを作る"
bq mk --dataset --location=asia-northeast1 tsubame-trial:lab
bq show --format=prettyjson --dataset tsubame-trial:lab
```

`defaultTableExpirationMs` が `5184000000` になっています。単位はミリ秒で、5184000000 ÷ 1000 ÷ 86400 = 60 日です。このデータセットに作ったテーブルは、60 日たつと消えます。`--default_table_expiration` を指定していないのにこうなるのが、サンドボックスの印です。

SELECT は使えます。公開データセット（第 15 章）の商品の表を、カテゴリごとに数えてみます。

```sh run title="サンドボックスでも SELECT は動く"
bq query --use_legacy_sql=false 'SELECT category, COUNT(*) AS n FROM `tsubame-public.bungu.products` GROUP BY category ORDER BY category'
```

テーブルを作る（`CREATE TABLE`）こともできます。

```sh run title="テーブルを作る"
bq query --use_legacy_sql=false 'CREATE TABLE lab.memo (id INT64, body STRING)'
```

`Created tsubame-trial.lab.memo` と出ました。では、このテーブルに 1 行入れてみます。

```sh run title="サンドボックスでは DML が拒否される" error
bq query --use_legacy_sql=false "INSERT INTO lab.memo VALUES (1, 'hello')"
```

エラーの文に答えが全部書いてあります。

- `Billing has not been enabled for this project.`：このプロジェクトでは請求が有効になっていない
- `DML queries are not allowed in the free tier.`：無料の範囲（サンドボックス）では DML は使えない
- `Set up a billing account to remove this restriction.`：請求先を設定すれば、この制限はなくなる

サンドボックスは「BigQuery の SQL を試して、どれくらいのデータを読むかを知る」には十分です。データを入れたり書き換えたりする仕事に使うなら、請求先をつなぎます。

## 請求先をつなぐ：link と、要る権限 {#link}

プロジェクトを請求先アカウントにつなぐコマンドが `gcloud billing projects link` です。だれでもつなげるわけではなく、**2 つの側の権限**が要ります。

```fig graph プロジェクトを請求先につなぐには、請求先アカウントの側とプロジェクトの側の両方に権限が要る。片方だけでは失敗する
{
  col: 250, row: 96,
  nodes: [
    { id: 'who', label: 'あなた', sub: 'you@tsubame.example', x: 0, y: 1, kind: 'plain' },
    { id: 'bill', label: '請求先アカウント', sub: 'roles/billing.user\n（billing.resourceAssociations.create）', x: 1, y: 0, kind: 'accent', mono: false },
    { id: 'proj', label: 'プロジェクト', sub: 'roles/owner など\n（projects.createBillingAssignment）', x: 1, y: 2, kind: 'crate', mono: false },
    { id: 'ok', label: 'link できる', x: 2, y: 1, kind: 'stack', mono: false },
  ],
  edges: [
    { from: 'who', to: 'bill', label: '財布を使ってよいか', style: 'accent' },
    { from: 'who', to: 'proj', label: 'この箱を変えてよいか' },
    { from: 'bill', to: 'ok' }, { from: 'proj', to: 'ok' },
  ],

```

- **請求先アカウントの側**：`roles/billing.user`（請求先アカウント ユーザー）。「この財布にプロジェクトをつないでよい」という権限です。請求書を見たり、支払い方法を変えたりはできません
- **プロジェクトの側**：プロジェクトの `roles/owner`、または `roles/billing.projectManager`（プロジェクト 請求先管理者）

請求先アカウントの IAM ポリシーを、請求先の管理者（`admin@`）に切り替えて見てみます。

:::note このサイトの GCP では
`gcloud auth login` に、切り替えたいアカウントを引数で渡します。本物では、ブラウザでログインの画面が開きます。
:::

```sh run title="請求先アカウントの IAM ポリシー（管理者で見る）"
gcloud auth login admin@tsubame.example
gcloud billing accounts get-iam-policy 01A2B3-C4D5E6-F7A8B9
```

`admin@` が `roles/billing.admin`（請求先アカウント管理者。支払い方法や IAM も含めて何でもできる）、あなた（`you@`）が `roles/billing.user` です。アプリ開発の青木さん（`alice@`）は、どちらにも入っていません。

青木さんが自分で試用のプロジェクトを作り、請求先につなごうとすると、どうなるでしょう。

```sh run title="青木さんがプロジェクトを作る"
gcloud auth login alice@tsubame.example
gcloud projects create alice-lab-04
gcloud billing accounts list
```

プロジェクトは作れました（組織の全員が `roles/resourcemanager.projectCreator` を持っているため）。作った青木さんは、そのプロジェクトの owner です。ところが `billing accounts list` は `Listed 0 items.` で、使える請求先が 1 つも見えません。

```sh run title="請求先アカウントの権限がないと、つなげない" error
gcloud billing projects link alice-lab-04 --billing-account=01A2B3-C4D5E6-F7A8B9
```

`PERMISSION_DENIED: The caller does not have permission.` と、その後ろの `authenticated as alice@tsubame.example` を読みます。「alice@ として呼んだが、権限がない」です。プロジェクトの owner であっても、**請求先アカウントの側の権限がなければつなげません**。直すには、請求先の管理者に `roles/billing.user` をもらうか、権限のある人（ここではあなた）につないでもらいます。

あなたに戻って、`tsubame-trial` をつなぎます。

```sh run title="tsubame-trial を請求先につなぐ"
gcloud auth login you@tsubame.example
gcloud billing projects link tsubame-trial --billing-account=01A2B3-C4D5E6-F7A8B9
```

出力は `describe` と同じ形で、`billingEnabled: true` に変わりました。サンドボックスではなくなったので、さっき拒否された INSERT を、もう一度実行します。

```sh run title="請求先をつなぐと、DML が通る"
bq query --use_legacy_sql=false "INSERT INTO lab.memo VALUES (1, 'hello')"
bq query --use_legacy_sql=false 'SELECT * FROM lab.memo'
```

`Number of affected rows: 1` と出て、行が入りました。

:::tip 本番と試しで、請求先を分けるか
請求先アカウントは何個でも作れます。部署ごと、または本番と開発で請求先を分けると、請求書が分かれます。1 つの請求先にまとめて、プロジェクトごとの内訳をレポートで見る方法もあります。組織の規模で決めればよく、どちらが正しいというものではありません。
:::

## 料金のしくみと無料枠 {#pricing}

Google Cloud の料金は、ほとんどが**従量課金**です。使った量（VM が動いた時間、保存したバイト数と期間、処理したリクエストやバイト数）に単価を掛けて、月ごとに請求されます。前払いの契約や最低料金は、基本の使い方では要りません。

新しく Google Cloud を始める人には、2 つのお得な仕組みがあります（2026 年 11 月に公式ドキュメントで確認）。

- **無料トライアル**：$300 のクレジットを、登録から 90 日のあいだ使えます
- **無料枠**（Free Tier）：毎月、決まった量までは無料です。余っても翌月に繰り越されません

無料枠のうち、この本で使うサービスの主なものは次のとおりです。

| サービス | 毎月の無料枠（主なもの） |
| --- | --- |
| Compute Engine | e2-micro の VM 1 台（us-west1、us-central1、us-east1 のどれか）、標準永続ディスク 30 GB-月 |
| Cloud Storage | リージョンのストレージ 5 GB-月（US のリージョンのみ） |
| BigQuery | クエリ 1 TiB、ストレージ 10 GiB |
| Cloud Run | 200 万リクエスト |
| Pub/Sub | メッセージ 10 GiB |
| Firestore | ストレージ 1 GiB、1 日あたり読み取り 50,000 回・書き込み 20,000 回 |
| Cloud Logging | プロジェクトあたり 50 GiB のログ |

無料枠には、**場所の条件**が付いているものがあります。たとえば e2-micro の無料枠は米国の 3 つのリージョンだけで、東京（asia-northeast1）に作った e2-micro は無料枠に入りません。

### BigQuery の料金は「読んだバイト数」

従量課金のようすがいちばん見えやすいのが BigQuery です。オンデマンド料金は、クエリが**処理したバイト数**で決まります。US では 1 TiB あたり $6.25 で（リージョンで違います）、毎月最初の 1 TiB は無料です。実行する前に `--dry_run` で、処理するバイト数を調べられます。

```sh run title="読む列で、処理するバイト数が変わる"
bq query --use_legacy_sql=false --dry_run 'SELECT channel FROM `tsubame-public.bungu.orders`'
bq query --use_legacy_sql=false --dry_run 'SELECT * FROM `tsubame-public.bungu.orders`'
```

`running this query will process … bytes of data.` の数を比べてください。`channel` の 1 列だけなら 12295 バイト、`SELECT *` なら 117079 バイトです。BigQuery は列ごとにデータを持っているので、読む列が多いほど処理するバイト数が増えます。`SELECT *` は、全部の列を読みます。

:::deep 小さなクエリでも 10 MB
BigQuery のオンデマンド料金では、1 つのクエリで、参照したテーブルごとに最低 10 MB が課金されます。上の例のように 12295 バイトしか読まないクエリでも、課金されるのは 10 MB です。このサイトの GCP も同じ計算をします。処理したバイト数と課金されたバイト数の違いは、第 15 章で `bq show -j` を使って見ます。
:::

## unlink すると、動いているものが止まる {#unlink}

請求先をつないだので、`tsubame-trial` で Compute Engine を有効にして、小さな VM を 1 台作ります（VM は第 8 章で詳しく扱います）。

```sh run title="Compute Engine を有効にして、VM を作る"
gcloud services enable compute.googleapis.com
gcloud compute instances create web-1 --zone=asia-northeast1-b --machine-type=e2-micro
```

`STATUS` が `RUNNING` です。この VM は、動いているあいだずっと料金がかかります。

ここで、プロジェクトを請求先から外してみます。外すコマンドは `gcloud billing projects unlink` です。

```fig graph 請求先を外すと何が起きるか。ボタンで段階を切り替えてください
    { title: 'つなぎ直す', say: 'もう一度 <code>link</code> すれば、有料のサービスをまた使えます。ただし止まった VM は自動では動き出しません。自分で <code>start</code> します。',
      nodes: [
        { id: 'proj', label: 'tsubame-trial', sub: 'billingEnabled: true', x: 0, y: 0, kind: 'crate' },
        { id: 'bill', label: '請求先アカウント', sub: '01A2B3-…', x: 1, y: 0, kind: 'accent', mono: false },
        { id: 'vm', label: 'VM web-1', sub: 'start で RUNNING', x: 0, y: 1, kind: 'stack', mono: false },
      ],
      edges: [ { from: 'proj', to: 'bill', label: 'つながっている', style: 'accent' }, { from: 'proj', to: 'vm' } ] },
  ],
}
```

```sh run title="請求先を外すと、VM が止まる"
gcloud billing projects unlink tsubame-trial
gcloud compute instances list
```

`unlink` の出力は `billingEnabled: false` です。続く `instances list` で、`web-1` の `STATUS` が `TERMINATED` に変わっています。何も操作していないのに VM が止まりました。請求先がなくなると、お金のかかる仕事は続けられないからです。

外したままでは、有料の API を新しく有効にすることもできません。

```sh run title="請求先がないので、Cloud Run も有効にできない" error
gcloud services enable run.googleapis.com
```

最初に見たのと同じ `FAILED_PRECONDITION` の、`Billing account … is not found` です。つなぎ直して、VM を動かします。

```sh run title="つなぎ直して、VM を起動する"
gcloud billing projects link tsubame-trial --billing-account=01A2B3-C4D5E6-F7A8B9
gcloud compute instances start web-1 --zone=asia-northeast1-b
gcloud compute instances list --format="value(name,status)"
```

`web-1	RUNNING` に戻りました。つなぎ直しても、止まった VM は自分で `start` するまで止まったままです。

:::warn unlink は「非常ブレーキ」
unlink は、プロジェクトの中の有料のものを一度に止める、いちばん確実な方法です。そのかわり、本番のサービスも全部止まります。本物では、請求先のない状態が続くと、リソースやデータが消されることもあります（公式ドキュメントの「プロジェクトの課金を無効にする」を参照）。本番のプロジェクトで気軽に使うものではありません。
:::

## 予算とアラート：予算は使いすぎを止めない {#budgets}

使いすぎに早く気づくための仕組みが**予算**（budget）です。請求先アカウントに「月に いくらまで」という金額と、「その何 % に達したら知らせる」という**しきい値**（threshold）を決めておきます。

```fig seq 予算の働き。費用がしきい値を超えると通知が届く。通知が届いても、VM は動き続け、費用は増え続ける
{
  actors: [
    { id: 'vm', label: 'VM などのリソース' },
    { id: 'bill', label: '請求先アカウント' },
    { id: 'bud', label: '予算（5,000 円）' },
    { id: 'you', label: 'あなた' },
  ],
  msgs: [
    { from: 'vm', to: 'bill', label: '使った分の費用' },
    { from: 'bill', to: 'bud', label: '今月の費用を比べる' },
    { from: 'bud', to: 'you', label: '50 % を超えた（メール）', style: 'accent' },
    { from: 'vm', to: 'bill', label: 'まだ動いている。費用は増える' },
    { from: 'bud', to: 'you', label: '90 % を超えた（メール）', style: 'accent' },
    { from: 'vm', to: 'bill', label: '100 % を超えても動いている', style: 'bad' },
    { note: '予算は知らせるだけ。止めるのは人（か、自分で作った仕組み）', at: ['bud', 'you'] },
  ],
}
```

:::warn 予算は、使いすぎを止めない（通知だけ）
**予算を作っても、費用が予算を超えたときにリソースが止まることはありません。** 予算がするのは、しきい値を超えたことを**知らせる**ことだけです。予算が 5,000 円でも、VM を動かし続ければ 1 万円でも 10 万円でも請求されます。また、費用の集計はリアルタイムではなく遅れて届くので、通知が来た時点では、すでにしきい値より多く使っていることがあります。
:::

`tsubame-trial` に、月 5,000 円の予算を作ります。50 % と 90 % に達したとき、それに「このままだと今月 100 % を超えそう」（予測）のときに知らせます。

```sh run title="予算を作る"
gcloud billing budgets create --billing-account=01A2B3-C4D5E6-F7A8B9 --display-name="試用 月 5000 円" --budget-amount=5000JPY --threshold-rule=percent=0.5 --threshold-rule=percent=0.9 --threshold-rule=percent=1.0,basis=forecasted-spend --filter-projects=projects/tsubame-trial
```

フラグと出力の対応を見ます。

| フラグ | 出力 | 意味 |
| --- | --- | --- |
| `--budget-amount=5000JPY` | `amount.specifiedAmount` | 金額。通貨は請求先アカウントと同じにする |
| `--threshold-rule=percent=0.5` | `thresholdPercent: 0.5`、`spendBasis: CURRENT_SPEND` | いまの費用が 50 % に達したら |
| `…,basis=forecasted-spend` | `spendBasis: FORECASTED_SPEND` | 月末の予測が 100 % に達しそうなら |
| `--filter-projects` | `budgetFilter.projects` | 対象のプロジェクト。付けなければ請求先アカウント全体 |
| （なし） | `calendarPeriod: MONTH` | 毎月リセットされる |

`percent` は 0.5 のように 1 を 100 % とした小数で書きます。`50` と書くと 5000 % の意味になるので注意してください。予算は、プロジェクトではなく請求先アカウントの下にできます。

:::note 予算を作れる人
予算を作るには、請求先アカウントの `roles/billing.admin` か `roles/billing.costsManager`（費用の管理者）が要ります。`roles/billing.user`（プロジェクトをつなぐだけの権限）では作れません。あなたには、つばめ文具の請求先の `roles/billing.costsManager` が付いています。
:::

```sh run title="予算の一覧と、しきい値"
gcloud billing budgets list --billing-account=01A2B3-C4D5E6-F7A8B9
gcloud billing budgets list --billing-account=01A2B3-C4D5E6-F7A8B9 --flatten="thresholdRules[]" --format="value(displayName,thresholdRules.thresholdPercent,thresholdRules.spendBasis)"
```

1 つ目は一覧の表です。`BUDGET_ID` が予算の ID で、`describe` や `delete` に使います。2 つ目は `--flatten`（第 1 章）で、しきい値を 1 行に 1 つずつ並べました。

金額の通貨は、請求先アカウントの通貨と合わせなければなりません。

```sh run title="通貨が違うと作れない" error
gcloud billing budgets create --billing-account=01A2B3-C4D5E6-F7A8B9 --display-name="試用 50 ドル" --budget-amount=50USD
```

`Budget currency code USD does not match the billing account's currency code JPY.` 予算の通貨 USD が、請求先アカウントの通貨 JPY と合わない、と読みます。`5000JPY`、または通貨を省いて `5000` と書けば通ります。

通知の宛先は、本物では既定で請求先アカウントの管理者とユーザーへのメールです。Cloud Monitoring の通知チャンネルや Pub/Sub のトピックにも送れます（公式ドキュメントを参照）。Pub/Sub に送れば、通知を受けた関数がプログラムで VM を止めたり、請求先を unlink したりする仕組みを自分で作れます。**止める仕組みは、予算の外に自分で作るもの**です。

## 費用を本当に止めるには {#stop-costs}

予算が止めてくれないなら、費用を止めるのはあなたです。止め方は、止めたい範囲によって選びます。

| 方法 | 止まるもの | 残るもの |
| --- | --- | --- |
| リソースを止める（VM の `stop`） | VM の計算の料金 | ディスク、静的 IP など（これらは料金がかかり続ける） |
| リソースを消す（`delete`） | そのリソースの料金すべて | 何も残らない |
| 請求先を外す（`unlink`） | プロジェクトの中の有料のもの全部 | プロジェクトとデータ（消されることもある） |
| プロジェクトを消す（`projects delete`） | プロジェクトの中のもの全部 | 30 日のあいだは undelete で戻せる |

試しに作ったものは、使い終わったら消すのがいちばんです。VM を消します。

```sh run title="使い終わった VM を消す"
gcloud compute instances delete web-1 --zone=asia-northeast1-b --quiet
gcloud compute instances list
```

`Listed 0 items.` で、VM はなくなりました。プロジェクトごと要らなくなったら、プロジェクトを消します。プロジェクトを消すと、中のリソースはすべて止まり、そのプロジェクトの請求も止まります。

```sh run title="試用のプロジェクトごと消す"
gcloud config set project tsubame-shop
gcloud projects delete tsubame-trial --quiet
gcloud billing projects list --billing-account=01A2B3-C4D5E6-F7A8B9
```

先に `tsubame-shop` に戻してから消しています。消したプロジェクトは、請求先につながったプロジェクトの一覧から外れました。第 2 章で見たとおり、消したプロジェクトは 30 日のあいだ `gcloud projects undelete` で戻せます。

:::tip 試すときの習慣
- 試しのプロジェクトは、本番と分けて作る。終わったらプロジェクトごと消す
- 請求先をつないだら、すぐに予算を作る。しきい値は低め（50 %、90 %、予測 100 %）にしておく
- 無料枠の条件（リージョン、マシンタイプ）を確かめてから作る
:::

:::key まとめ
- 料金は**請求先アカウント**に請求される。請求先アカウントはリソースの階層の外にあり、プロジェクトは 0 か 1 つの請求先につながる
- 新しく作ったプロジェクトには請求先がない。Compute Engine などは `FAILED_PRECONDITION`（Billing account … is not found）で有効にできない
- 請求先がなくても BigQuery は**サンドボックス**で使える。テーブルは 60 日で期限切れ、DML は使えない
- `gcloud billing projects link` には、請求先アカウントの `roles/billing.user` と、プロジェクトの owner（か `roles/billing.projectManager`）の両方が要る
- `unlink` すると、VM などの有料のリソースは止まる。つなぎ直しても、VM は自分で `start` する
- **予算は使いすぎを止めない。** しきい値を超えたら知らせるだけ。止めるのは stop、delete、unlink、プロジェクトの削除
:::

:::quiz 請求先のないプロジェクトを探す
あなたが見られるすべてのプロジェクトのうち、請求が有効になっていない（`billingEnabled` が false の）プロジェクトの ID だけを、1 行に 1 つ表示してください。



```sh answer
for p in $(gcloud projects list --format="value(projectId)"); do gcloud billing projects describe $p --format="value(projectId,billingEnabled)"; done | grep False | cut -f1
```

:::hint
`gcloud billing projects describe プロジェクト --format="value(projectId,billingEnabled)"` は、ID と `True` / `False` をタブで区切って 1 行に出します。これを全部のプロジェクトについて繰り返し、`grep False` で絞って、`cut -f1` で 1 列目だけを取り出します。
:::
:::
