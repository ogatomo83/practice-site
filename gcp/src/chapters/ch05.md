## Google Cloud の「だれ」は何種類あるか {#kinds}

IAM（第 6 章）は「**だれに**、何を許すか」を決める仕組みです。この章は、その「だれ」の側を扱います。IAM で権限を受け取る相手を**プリンシパル**（principal）と呼びます。プリンシパルには、次の種類があります。

IAM のポリシーには、`user:you@tsubame.example` のように「種類:メールアドレス」の形で書きます。人もグループもサービスアカウントも、**メールアドレスの形の名前**を持っているのが共通点です。

いま gcloud がだれとして動いているかは、`gcloud auth list` で見られます。

```sh run title="いまのアカウント"
gcloud auth list
gcloud config get-value account
```

- `Credentialed Accounts` は、この端末が**認証情報**（ログインした証拠）を持っているアカウントの一覧です。いまは `you@tsubame.example` の 1 つだけです
- 左の `*` が付いているのが、いま使っているアカウントです。`gcloud config get-value account` が出すのと同じものです

## 人の Google アカウント：個人のものと、組織が管理するもの {#google-accounts}

人のアカウントは、どれも **Google アカウント**です。Gmail や YouTube にログインするのと同じ仕組みで、Google Cloud 専用のアカウントはありません。ただし、Google アカウントには 2 つの出自があります。

| | 個人の Google アカウント | 管理されたアカウント |
| --- | --- | --- |
| 例 | `taro@example.com`、`…@gmail.com` | `you@tsubame.example`、`alice@tsubame.example` |
| だれが作るか | 本人が自分で作る | 会社の管理者が、**Google Workspace** か **Cloud Identity** で作る |
| だれが管理するか | 本人だけ | 組織の管理者（パスワードの再設定、2 段階認証の強制、退職したら停止） |
| 組織との関係 | どの組織にも属さない | ドメインの組織に属する |

**Google Workspace** は、Gmail や Google ドライブを会社で使うための有料のサービスです。**Cloud Identity** は、そこからメールなどを抜いて、アカウントの管理だけを提供するサービスです（無料の版があります）。どちらも、会社のドメイン（`tsubame.example`）で、社員のアカウントをまとめて管理できます。

仕事で Google Cloud を使うなら、管理されたアカウントを使うのが原則です。個人のアカウントは、退職した人のアカウントを会社が止められません。

### alice と taro に切り替えて、見え方を比べる

同じコマンドでも、だれが打つかで結果が変わります。`gcloud auth login` で、ほかの人に切り替えてみます。

```sh run title="alice としてログインする"
gcloud auth login alice@tsubame.example
gcloud auth list
gcloud projects list
```

`gcloud auth list` に 2 人が並び、`*` が alice に移りました。`you@` の認証情報は消えていません。gcloud は**何人分でも認証情報を持てて、そのうち 1 人を「いまのアカウント」として使う**のです。

:::note このサイトの GCP では
本物の `gcloud auth login` は、ブラウザを開いて Google のログイン画面でアカウントを選び、パスワードを入れます。このサイトでは、ログインするアカウントを引数で指定すると、すぐにログインできます。
:::

最後の `gcloud projects list` は `Listed 0 items.` です。alice は組織の社員ですが、どのプロジェクトのロールも持っていません。**組織に属していることと、プロジェクトを使えることは別**です。使えるようにするには、IAM でロールを付けます（第 6 章）。

次は組織の外の taro です。

```sh run title="taro には組織も見えない。自分に戻して比べる"
gcloud auth login taro@example.com
gcloud organizations list
gcloud config set account you@tsubame.example
gcloud projects list --format="value(projectId)"
```

個人のアカウントの taro には、組織そのものが見えません（`Listed 0 items.`）。そのあと、いまのアカウントを自分に戻しました。ログインし直す必要はなく、`gcloud config set account` で選び直すだけです。you には 2 つのプロジェクトが見えます。同じ端末、同じコマンドでも、**API はいつも「だれが呼んだか」で答えを変える**のです。

## グループで人をまとめる {#groups}

5 人の開発者にそれぞれロールを付けると、人が入れ替わるたびに IAM を直すことになります。そこで、**グループ**（Google グループ）にロールを付け、人はグループに出し入れします。新しく入った人をグループに足すだけで、IAM のポリシーは変えずに済みます。

グループは IAM の機能ではなく、**Workspace（Cloud Identity）の機能**です。gcloud では `gcloud identity groups` で扱います。

```sh run title="dev-team のメンバー"
gcloud identity groups memberships list --group-email=dev-team@tsubame.example
```

メンバーは 2 人です。`preferredMemberKey.id` がメンバーのメールアドレスで、`roles` がグループの中での役割です。you には `OWNER` も付いています。グループの OWNER は、メンバーを出し入れできる人です。これは IAM のロールとは別のものなので、混ぜないでください。

alice を分析チームにも入れてみます。グループの名前だけを並べるには `--format` を使います。

```sh run title="analysts に alice を足す"
gcloud identity groups memberships add --group-email=analysts@tsubame.example --member-email=alice@tsubame.example --format=none
gcloud identity groups memberships list --group-email=analysts@tsubame.example --format="value(preferredMemberKey.id)"
```

`bob@` と `alice@` の 2 人になりました。このあと `analysts@` に付いているロールは、alice にも効きます。1 人が何個のグループに入っていてもかまいません。

存在しないアカウントは足せません。

```sh run title="いない人を足す" error
gcloud identity groups memberships add --group-email=analysts@tsubame.example --member-email=carol@tsubame.example
```

`NOT_FOUND: … Member carol@tsubame.example not found.` は「そのメールアドレスのアカウントが見つからない」という意味です。打ち間違いか、まだアカウントが作られていないかを確かめます。

## サービスアカウント：プログラムのためのアカウント {#service-accounts}

Cloud Run で動く注文の API が、Firestore に書き込むとします。このプログラムは「だれ」として Firestore を呼ぶのでしょうか。開発した alice のアカウントを使うと、alice が異動したときに API が止まります。そこで、**プログラム専用のアカウント**を作ります。これが**サービスアカウント**です。

サービスアカウントには、人のアカウントと違うところがあります。

- **パスワードがない。** ブラウザでログインはできません。代わりに、Google Cloud の中で動くものに「付けて」使います（VM、Cloud Run、関数など）
- **プロジェクトの中にある。** メールアドレスは `名前@プロジェクトID.iam.gserviceaccount.com` です
- **それ自体がリソースでもある。** 「だれがこのサービスアカウントを使ってよいか」を、サービスアカウントの IAM で決めます（あとの節）

いまあるものを見てから、注文の API のためのものを作ります。

```sh run title="サービスアカウントを作る"
gcloud iam service-accounts list
gcloud iam service-accounts create order-api --display-name="注文 API"
gcloud iam service-accounts list
```

最初の一覧は `Listed 0 items.` で、まだ 1 つもありませんでした。作った後の一覧では、`EMAIL` の列が `order-api@tsubame-shop.iam.gserviceaccount.com` になっています。IAM のポリシーには、`serviceAccount:` を前に付けたこの名前で書きます。

名前の決まりは、出力のエラーの文に書いてあります。短すぎる名前で試します。

```sh run title="名前が短すぎる" error
gcloud iam service-accounts create api
```

`must be between 6 and 30 characters` は「6〜30 文字」、`must begin with a lowercase letter` は「小文字の英字で始まる」です。使える文字は小文字の英字、数字、ハイフンです。同じ名前をもう一度作ろうとすると、`already exists within project` のエラーになります。

```sh run title="1 つのサービスアカウントの詳しい情報"
gcloud iam service-accounts describe order-api@tsubame-shop.iam.gserviceaccount.com
```

- `name` は `projects/tsubame-shop/serviceAccounts/…` です。サービスアカウントがプロジェクトの下のリソースだということが分かります
- `uniqueId` は、21 桁の番号です。同じ名前で消して作り直すと、メールアドレスは同じでも、この番号は変わります

### 既定のサービスアカウントと、サービスエージェント

サービスアカウントは、自分で作るものだけではありません。Compute Engine の API を有効にしてみます。

```sh run title="Compute Engine を有効にすると増えるもの"
gcloud services enable compute.googleapis.com
gcloud iam service-accounts list --format="table(displayName, email)"
gcloud projects get-iam-policy tsubame-shop --flatten="bindings[].members" --format="table(bindings.role, bindings.members)"
```

`Compute Engine default service account` が増えました。メールアドレスは `365600345236-compute@developer.gserviceaccount.com` で、先頭はプロジェクトの番号です。これが**既定のサービスアカウント**です。VM や Cloud Run でサービスアカウントを指定しないと、これが使われます（第 8 章、第 10 章）。

ブロックの最後の `get-iam-policy` は、プロジェクトの IAM を 1 行に 1 つの割り当てで並べたものです。`roles/owner` の you のほかに、2 つの行が増えています。

- 既定のサービスアカウントに `roles/editor`（ほとんど何でも変更できる強いロール）。既定のまま使うと、VM の上のプログラムがプロジェクト中のものを書き換えられることになります
- `service-365600345236@compute-system.iam.gserviceaccount.com` に `roles/compute.serviceAgent`。これは**サービスエージェント**です

**サービスエージェント**は、Google のサービスが、あなたのプロジェクトの中で仕事をするときに使うサービスアカウントです。Compute Engine が VM にディスクを付けるとき、そのサービス自身が「だれか」として API を呼ぶ必要があります。その「だれか」がサービスエージェントです。Google が作って管理し、`gcloud iam service-accounts list` には出ません。消したり、ロールを外したりしてはいけません。

:::warn 既定のサービスアカウントの Editor
既定のサービスアカウントに自動で Editor が付くのは、便利さを優先した昔の設計です。いまは、用途ごとにサービスアカウントを作り、必要なロールだけを付けるのが推奨です。新しく作られた組織では、この自動の付与を止める組織のポリシー（`iam.automaticIamGrantsForDefaultServiceAccounts`）が最初から有効になっています（詳しくは公式ドキュメントを参照）。
:::

## 鍵ファイルで、サービスアカウントとして動く {#keys}

Google Cloud の外（自分の PC、ほかのクラウド、CI）で動くプログラムを、サービスアカウントとして動かしたいときがあります。いちばん古いやり方が、**サービスアカウントの鍵**（JSON の鍵ファイル）です。

```sh run title="鍵ファイルを作って、サービスアカウントになる"
gcloud iam service-accounts keys create key.json --iam-account=order-api@tsubame-shop.iam.gserviceaccount.com
cat key.json
gcloud auth activate-service-account --key-file=key.json
gcloud auth list
```

`private_key` が秘密鍵、`client_email` がサービスアカウントです。このファイルを持っている人はだれでも、ここに書かれたサービスアカウントとして Google Cloud を操作できます。

続く `gcloud auth activate-service-account` が、この鍵で gcloud をサービスアカウントとして動かすコマンドです。`gcloud auth list` の `*` が `order-api@…` に移りました。ここで、プロジェクトのサービスアカウントの一覧を見てみます。

```sh run title="作ったばかりのサービスアカウントには、何の権限もない" error
gcloud iam service-accounts list
```

`Permission 'iam.serviceAccounts.list' denied` です。you がプロジェクトの Owner でも、you が作ったサービスアカウントは、**別のプリンシパル**です。作った人の権限は引き継ぎません。ロールを付けるまで、何もできません。

### 鍵ファイルを避ける理由

鍵の一覧を見ると、鍵ファイルの怖さが分かります。まず自分に戻ってから見ます。

```sh run title="鍵の一覧"
gcloud config set account you@tsubame.example
gcloud iam service-accounts keys list --iam-account=order-api@tsubame-shop.iam.gserviceaccount.com
```

鍵が 2 つあります。

- `EXPIRES_AT` が `2028-…` のものは、Google が管理する鍵です。Google が自動で取り替えるので、気にしなくてかまいません
- `EXPIRES_AT` が `9999-12-31` のものが、いま作った鍵です。**期限がありません**。消すまで、ずっと使えます

期限のない秘密が 1 つのファイルになっていると、次のことが起きます。

- **漏れやすい。** git に commit してしまう、チャットに貼ってしまう、PC ごと盗まれる。ファイルなので、コピーされても気づけません
- **だれが使ったか分からない。** 監査ログに残るのはサービスアカウントの名前だけで、鍵を持っていた人の名前は残りません
- **管理が要る。** 定期的に作り直し（ローテーション）、古い鍵を消す手間がかかります

使い終わった鍵は消します。消した鍵は、ファイルが手元に残っていても使えません。

```sh run title="鍵を消す"
gcloud iam service-accounts keys delete $(gcloud iam service-accounts keys list --iam-account=order-api@tsubame-shop.iam.gserviceaccount.com --managed --format="value(name.basename())") --iam-account=order-api@tsubame-shop.iam.gserviceaccount.com --quiet
```

`keys list` の `--managed` はユーザーが作った鍵だけに絞るフラグで、その ID を `delete` に渡しています。

```sh run title="消した鍵のファイルで、もう一度なろうとする" error
gcloud auth activate-service-account --key-file=key.json
```

`Invalid JWT Signature` は「この鍵の署名を、Google がもう受け付けない」という意味です。鍵は Google の側で無効になりました。本物では、手元のファイルも `rm key.json` で消しておきます。

:::note 鍵の作成は、組織で止められる
鍵の危険は大きいので、組織のポリシー `iam.disableServiceAccountKeyCreation` で、鍵の作成そのものを禁止できます。禁止されていると、`keys create` は `Key creation is not allowed on this service account.` で失敗します。鍵の代わりに、次の節の借用や、Google Cloud の外のための Workload Identity 連携を使います。
:::

## 借用：鍵を持たずにサービスアカウントになる {#impersonation}

```fig seq 借用の流れ。alice が自分の資格でトークンを頼み、IAM が「alice はこのサービスアカウントを借用してよいか」を調べる。返ってきた短命のトークンで、サービスアカウントとして API を呼ぶ
    { from: 'c', to: 'a', label: '短い時間で切れる、order-api のアクセストークン' },
    { from: 'a', to: 'api', label: 'order-api として呼ぶ', style: 'accent' },
    { note: '監査ログには order-api と、借用した alice の両方が残る', at: 'api' },
  ],
}
```

鍵との違いは 3 つです。秘密のファイルがない。トークンはすぐに期限が切れる。「だれが借りたか」がはっきりする。試すために、`order-api` にプロジェクトを見るロール（`roles/viewer`）を付けておきます。ロールの付け方は第 6 章で詳しく扱います。

そのあと alice に切り替えます。前の節で一度ログインしているので、`gcloud config set account` だけで切り替わります。

```sh run title="order-api に Viewer を付けて、alice に切り替える"
gcloud projects add-iam-policy-binding tsubame-shop --member=serviceAccount:order-api@tsubame-shop.iam.gserviceaccount.com --role=roles/viewer --format=none
gcloud config set account alice@tsubame.example
```

alice は、自分ではサービスアカウントの一覧を見られません。そこで、`--impersonate-service-account` を付けて、`order-api` を借りようとします。

```sh run title="借用の許可がない" error
gcloud iam service-accounts list --impersonate-service-account=order-api@tsubame-shop.iam.gserviceaccount.com
```

最初の `WARNING` は、「このコマンドの API 呼び出しは、すべて order-api として行う」という知らせです。その次のエラーが大事です。`Failed to impersonate [order-api@…]` は借用に失敗したということで、直し方が文に書いてあります。「借用する人に `roles/iam.serviceAccountTokenCreator` のロールを付けなさい」。

このロールは、プロジェクトにではなく、**サービスアカウントそのものに**付けます。「alice は、order-api だけを借りてよい」という意味になります。サービスアカウントの IAM を変えられるのは you なので、you に戻って付けます。

```sh run title="alice に、order-api を借用する許可を与える"
gcloud config set account you@tsubame.example
gcloud iam service-accounts add-iam-policy-binding order-api@tsubame-shop.iam.gserviceaccount.com --member=user:alice@tsubame.example --role=roles/iam.serviceAccountTokenCreator
```

出力の `bindings` は、order-api という**リソースの IAM**です。プロジェクトの IAM とは別に、サービスアカウントごとにポリシーがあります。

```sh run title="alice として、order-api を借りる"
gcloud iam service-accounts list --impersonate-service-account=order-api@tsubame-shop.iam.gserviceaccount.com --account=alice@tsubame.example
```

今度は一覧が出ました。`--account` は「このコマンドだけ、このアカウントで」という指定です。alice 自身には見えないものが、order-api の Viewer の権限で見えています。

:::warn TokenCreator と ServiceAccountUser を取り違えない
名前の似たロールがもう 1 つあります。**`roles/iam.serviceAccountUser`**（サービスアカウント ユーザー）は、VM や Cloud Run にサービスアカウントを**付ける**ための許可です（権限 `iam.serviceAccounts.actAs`）。トークンを作る権限は入っていないので、これだけでは `--impersonate-service-account` は使えません。「自分がなる」なら TokenCreator、「リソースに付ける」なら ServiceAccountUser です。
:::

毎回フラグを付けるのが面倒なら、設定にできます。

```sh run title="借用を設定にする（alice として）"
gcloud config set account alice@tsubame.example
gcloud config set auth/impersonate_service_account order-api@tsubame-shop.iam.gserviceaccount.com
gcloud projects describe tsubame-shop --format="value(projectId)"
gcloud config unset auth/impersonate_service_account
gcloud config set account you@tsubame.example
```

設定している間は、どのコマンドにも `WARNING: This command is using service account impersonation.` が出ます。借りたまま忘れないための目印です。使い終わったら `unset` で外します。

## allUsers と allAuthenticatedUsers {#all-users}

最初の図の下の段の 2 つは、特定のだれかではありません。

| 書き方 | 当てはまる人 | 例 |
| --- | --- | --- |
| `allUsers` | インターネットのだれでも。**ログインしていない人も含む** | Web サイトの画像を置くバケット、だれでも呼べる Cloud Run |
| `allAuthenticatedUsers` | Google アカウントかサービスアカウントでログインした、**世界中のだれでも** | 公開データセット |

`allAuthenticatedUsers` は「つばめ文具の社員」ではありません。個人の Gmail のアカウントでも当てはまります。名前から「社内だけ」と誤解しやすいので気をつけてください。社内だけにしたいなら `domain:tsubame.example` かグループを使います。

試しに、お知らせのファイルをバケットに置き、`allUsers` に読ませます。バケットは第 7 章で詳しく扱います。

```sh run title="お知らせを置いて、ログインなしで読む（まだ読めない）"
gcloud storage buckets create gs://tsubame-shop-ch05-notice --location=asia-northeast1
echo "本日のおすすめ：つばめノート A5" > notice.txt
gcloud storage cp notice.txt gs://tsubame-shop-ch05-notice/
curl https://storage.googleapis.com/tsubame-shop-ch05-notice/notice.txt
```

最後の `curl` で、ログインなしで読みに行きました。`curl` は gcloud の認証情報を使わないので、だれでもない「匿名」のアクセスです。結果は `Anonymous caller does not have storage.objects.get access` です。匿名の呼び出しに、読む権限がありません。`allUsers` に読むロールを付けます。

```sh run title="allUsers に読ませる"
gcloud storage buckets add-iam-policy-binding gs://tsubame-shop-ch05-notice --member=allUsers --role=roles/storage.objectViewer --format=none
curl https://storage.googleapis.com/tsubame-shop-ch05-notice/notice.txt
```

今度は中身が返りました。このバケットのファイルは、URL を知っているだれでも読めます。`allAuthenticatedUsers` の例は、最初からあります。公開データセット `tsubame-public.bungu` は、`allAuthenticatedUsers` に読むロールが付いています。組織の外の taro でも読めるかを確かめます。taro にも一度ログインしているので、`gcloud config set account` で切り替えられます。

```sh run title="組織の外の taro でも、公開データセットは読める"
gcloud config set account taro@example.com
bq head -n 3 tsubame-public:bungu.products
gcloud config set account you@tsubame.example
```

taro はつばめ文具と何の関係もありませんが、Google アカウントでログインしているので読めました。

:::warn 組織の外の人に付けられないようにする
いまの組織では、IAM に `allUsers` も `user:taro@example.com` も付けられます。うっかり公開するのを防ぐため、組織のポリシー **`iam.allowedPolicyMemberDomains`**（ドメインで制限された共有）で、「自分の組織のアカウントにしか付けられない」ようにできます。これを有効にすると、taro に付けようとしても失敗します。第 6 章で実際に設定します。
:::

## gcloud の認証情報と、ADC {#adc}

最後に、プログラムが使う認証情報です。Node.js や Python の Google Cloud のライブラリ（クライアント ライブラリ）は、**gcloud の認証情報を使いません**。**ADC**（Application Default Credentials、アプリケーションのデフォルト認証情報）という、別の仕組みで認証情報を探します。

```fig graph クライアント ライブラリが ADC を探す順番。上から見て、最初に見つかったものを使う。gcloud auth login でログインしたアカウントは、この中にない
{
  col: 250, row: 82,
  nodes: [
    { id: 'lib', label: 'クライアント ライブラリ', sub: 'new BigQuery() など', x: 0, y: 1, kind: 'accent', mono: false },
    { id: 'env', label: '① GOOGLE_APPLICATION_\nCREDENTIALS', sub: '環境変数が指すファイル', x: 1, y: 0, kind: 'stack' },
    { id: 'file', label: '② ~/.config/gcloud/\napplication_default_credentials.json', sub: 'auth application-default login', x: 1, y: 1, kind: 'stack' },
    { id: 'md', label: '③ メタデータサーバ', sub: 'VM や Cloud Run に付けた\nサービスアカウント', x: 1, y: 2, kind: 'crate', mono: false },
    { id: 'gc', label: 'gcloud の認証情報', sub: 'gcloud auth login', x: 2, y: 1, kind: 'ghost', mono: false },
  ],
  edges: [
    { from: 'lib', to: 'env' }, { from: 'lib', to: 'file' }, { from: 'lib', to: 'md' },
  ],
}
```

- Google Cloud の中（VM、Cloud Run、関数）では、③ の**メタデータサーバ**から、付けたサービスアカウントのトークンが取れます。コードに認証の処理を書かなくてよいのは、このおかげです（第 8 章）
- 自分の PC では、`gcloud auth application-default login` を打つと、② のファイルができます。gcloud のログインとは**別のログイン**です
- ① は鍵ファイルを指すのに使われてきた方法です。前の節の理由で、いまは避けます

商品の数を数える小さなプログラムで確かめます。まず、同じクエリを `bq` で打ってから、Node.js のライブラリで書いたものを用意します。`new BigQuery()` に認証情報を渡していないところを見てください。

```sh run title="bq で数えて、同じことをするプログラムを書く"
bq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-public.bungu.products`'
cat > count.js <<'JS'
const { BigQuery } = require('@google-cloud/bigquery');
async function main() {
  const bq = new BigQuery();
  const [rows] = await bq.query('SELECT COUNT(*) AS n FROM `tsubame-public.bungu.products`');
  console.log('商品の数:', rows[0].n);
}
main();
JS
```

`bq` の答えは 17 個です。次に ADC を作ってプログラムを動かし、そのあと gcloud だけを alice に切り替えます。

```sh run title="ADC を作って動かし、gcloud だけ alice にする"
gcloud auth application-default login
node count.js
gcloud config set account alice@tsubame.example
```

`Credentials saved to file: [/home/you/.config/gcloud/application_default_credentials.json]` が ② のファイルです。いま gcloud を使っていた you の認証情報が、ADC として保存されました。プログラムはそれを使って動き、`商品の数: 17` を出しました。最後の行で、gcloud のいまのアカウントは alice になりました。

```sh run title="bq は alice として動く" error
bq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-public.bungu.products`'
```

`bq` は gcloud の認証情報を使うので、alice として動きます。alice は tsubame-shop でクエリを実行する権限（`bigquery.jobs.create`）を持っていないので、失敗しました。では、プログラムはどうでしょう。

```sh run title="プログラムは you のまま"
node count.js
gcloud config set account you@tsubame.example
```

プログラムは成功しました。ADC は you のままだからです。「gcloud では動くのにプログラムでは権限がない」「その逆」が起きたら、**gcloud と ADC が別のアカウントになっていないか**を疑ってください。

:::key まとめ
- IAM のプリンシパルは、人の Google アカウント（`user:`）、グループ（`group:`）、サービスアカウント（`serviceAccount:`）、ドメイン（`domain:`）、`allAuthenticatedUsers`、`allUsers`
- 人のアカウントには、本人が作る個人のものと、Workspace / Cloud Identity で組織が管理するものがある。仕事では管理されたアカウントを使う
- Workspace の顧客が Google Cloud を使い始めると、ドメインの名前の組織が 1 つできる。人とグループは Workspace に、プロジェクトは組織にある
- ロールはグループに付け、人はグループに出し入れする（`gcloud identity groups memberships add`）
- サービスアカウントはプログラムのためのアカウント。作った人の権限は引き継がない。既定のサービスアカウントには強い Editor が付くことがあり、サービスエージェントは Google が使うもの
- 鍵ファイルは期限がなく漏れやすいので避ける。代わりに借用（`--impersonate-service-account`）を使い、借りる人にサービスアカウントの `roles/iam.serviceAccountTokenCreator` を付ける
- `allAuthenticatedUsers` は「社内」ではなく「Google にログインした世界中のだれでも」
- gcloud の認証情報と ADC（クライアント ライブラリが使うもの）は別々。`gcloud auth application-default login` で ADC を作る
:::

:::quiz bob に借用を許す
