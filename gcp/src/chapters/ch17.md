## 何を組み立てるか {#plan}

## 入れ物：フォルダとプロジェクトを作り、請求先と予算を付ける {#containers}

最初は入れ物です。[2.8](ch02.html#design) で考えた分け方のとおり、組織の下に店のチームのフォルダ `shop` を作り、その下を本番（`prod`）と開発（`dev`）に分けます。プロジェクトは環境ごとに 1 つずつです。

```fig tree この章で作る入れ物。フォルダで環境を分け、それぞれの段に付ける権限を決めておく
{
  root: { label: 'tsubame.example', kind: 'org', note: '組織のポリシー：社外のアカウントを禁止', children: [
    { label: 'shop', kind: 'folder', note: '店のチーム', children: [
      { label: 'prod', kind: 'folder', note: '本番。触れる人を絞る', hl: true, children: [{ label: 'tsubame-prod', kind: 'project', note: 'dev-team@ はログを読むだけ、analysts@ は BigQuery を読む' }] },
      { label: 'dev', kind: 'folder', note: 'dev-team@ に roles/editor', children: [{ label: 'tsubame-dev', kind: 'project', note: 'チームが自由に試す' }] },
    ] },
  ] },
}
```

フォルダを 3 つ作ります。フォルダの ID は作ったときに決まる数字なので、表示名から引いてシェルの変数に入れておきます（[2.4](ch02.html#folders)）。

```sh run title="フォルダ shop と、その下の prod / dev"
gcloud resource-manager folders create --display-name=shop --organization=405918273641
SHOP=$(gcloud resource-manager folders list --organization=405918273641 --filter="displayName=shop" --format="value(name.segment())")
gcloud resource-manager folders create --display-name=prod --folder=$SHOP
gcloud resource-manager folders create --display-name=dev --folder=$SHOP
```

`Created [<Folder …>]` が 3 回出ました。`parent` を見ると、`shop` の親は組織、`prod` と `dev` の親は `shop` のフォルダです。

次はプロジェクトです。prod と dev の ID も変数に入れてから、`--folder` で親を決めて作ります。ラベルで環境とチームを書いておきます（[2.5](ch02.html#create)）。ID の `tsubame-prod` は世界で 1 つの名前、`--name` の「つばめ文具 本番」は人が読むための名前です。

```sh run title="本番と開発のプロジェクト"
PROD=$(gcloud resource-manager folders list --folder=$SHOP --filter="displayName=prod" --format="value(name.segment())")
DEV=$(gcloud resource-manager folders list --folder=$SHOP --filter="displayName=dev" --format="value(name.segment())")
gcloud projects create tsubame-prod --name="つばめ文具 本番" --folder=$PROD --labels=env=prod,team=shop
gcloud projects create tsubame-dev --name="つばめ文具 開発" --folder=$DEV --labels=env=dev,team=shop
```

できたばかりのプロジェクトには、請求先がありません。その状態で Cloud Run の API を有効にしようとすると、どうなるでしょうか。

```sh run error title="請求先がないと、API を有効にできない"
gcloud services enable run.googleapis.com --project=tsubame-prod
```

`FAILED_PRECONDITION: Billing account for project '…' is not found` と断られました。`reason: UREQ_PROJECT_BILLING_NOT_FOUND` が理由です。Cloud Run のように料金がかかる API は、請求先がないと有効にできません（[3.7](ch03.html#billing)、[4.2](ch04.html#no-billing)）。エラーの中のプロジェクトが ID ではなく番号で書かれていることにも注意してください（[2.3](ch02.html#id-name-number)）。

請求先アカウントにつなぎ、予算を付けます。予算は本番が月 30,000 円、開発が月 5,000 円です。しきい値の 50% と 90% で知らせが届きます（[4.4](ch04.html#link)、[4.7](ch04.html#budgets)）。

```sh run title="請求先につなぎ、予算を付ける"
gcloud billing projects link tsubame-prod --billing-account=01A2B3-C4D5E6-F7A8B9 --format="value(billingEnabled)"
gcloud billing projects link tsubame-dev --billing-account=01A2B3-C4D5E6-F7A8B9 --format="value(billingEnabled)"
gcloud billing budgets create --billing-account=01A2B3-C4D5E6-F7A8B9 --display-name="本番 月 30000 円" --budget-amount=30000JPY --threshold-rule=percent=0.5 --threshold-rule=percent=0.9 --filter-projects=projects/tsubame-prod --format=none
gcloud billing budgets create --billing-account=01A2B3-C4D5E6-F7A8B9 --display-name="開発 月 5000 円" --budget-amount=5000JPY --threshold-rule=percent=0.5 --threshold-rule=percent=0.9 --filter-projects=projects/tsubame-dev --format=none
```

`link` の 2 行は `True` を出します。`billingEnabled` が真、つまり請求先につながったという意味です。予算のほうは `Created budget [...]` と、予算の ID が出ます。

:::warn 予算は止めない
[第 4 章](ch04.html#budgets)で見たとおり、予算は「知らせる」だけです。30,000 円を超えても、Cloud Run は動き続けます。本当に止めたいときは、請求先を外すか（[4.6](ch04.html#unlink)）、プロジェクトを消します。この章の最後の節で、プロジェクトを消します。
:::

入れ物ができたかを、まとめて確かめます。ラベル `team=shop` で絞ると、この章で作ったプロジェクトだけが出ます。

```sh run title="プロジェクトと予算の一覧"
gcloud projects list --filter="labels.team=shop" --format="table(projectId, name, parent.id)"
gcloud billing budgets list --billing-account=01A2B3-C4D5E6-F7A8B9 --format="table(displayName, amount.specifiedAmount.units:label=JPY, budgetFilter.projects)"
```

1 つ目の表の `ID` の列が親のフォルダの ID です。最初のブロックで出た `prod` と `dev` のフォルダの `name`（`folders/…`）の数字と、それぞれ同じになっています。変数 `$PROD` と `$DEV` は、このあとも使います。

## 人：グループにロールを配り、本番は絞る {#people}

入れ物ができたら、次は「だれが、どこで、何をしてよいか」を決めます。ロールは人ではなく**グループ**に付けます（[5.3](ch05.html#groups)）。人が入れ替わっても、グループのメンバーを変えるだけで済むからです。

| グループ | どこで | ロール | 理由 |
| --- | --- | --- | --- |
| `dev-team@`（alice、you） | フォルダ `dev` | `roles/editor` | 開発では自由に作って壊してよい |
| `dev-team@` | `tsubame-prod` | `roles/logging.viewer` | 本番は障害の調べのためにログを読むだけ |
| `analysts@`（bob） | `tsubame-prod` | `roles/bigquery.jobUser` | クエリのジョブを実行する。表を読む権限は、あとでデータセットに付ける |

フォルダに付けたロールは、その中のすべてのプロジェクトに引き継がれます（[6.4](ch06.html#inherit)）。開発のプロジェクトが増えても、付け直す必要はありません。本番には、基本ロールの Editor ではなく、仕事に必要な事前定義ロールだけを付けます。これが**最小権限**の考え方です（[6.2](ch06.html#roles)）。

```sh run title="グループにロールを付ける"
gcloud resource-manager folders add-iam-policy-binding $DEV --member=group:dev-team@tsubame.example --role=roles/editor --format=none
gcloud projects add-iam-policy-binding tsubame-prod --member=group:dev-team@tsubame.example --role=roles/logging.viewer --format=none
gcloud projects add-iam-policy-binding tsubame-prod --member=group:analysts@tsubame.example --role=roles/bigquery.jobUser --format=none
gcloud projects get-iam-policy tsubame-prod --flatten="bindings[].members" --format="table(bindings.role, bindings.members)"
```

本番の IAM ポリシーは 3 行です。`roles/owner` の `you@` は、プロジェクトを作った人に自動で付いたものです。dev フォルダの `roles/editor` は、プロジェクトのポリシーには出てきません。フォルダのポリシーに書いてあり、上から引き継がれるからです。

青木さん（alice）に切り替えて、開発と本番の違いを確かめます。開発ではバケットを作れるはずです。

```sh run title="alice は開発でバケットを作れる"
gcloud auth login alice@tsubame.example
gcloud storage buckets create gs://tsubame-shop-ch17-dev --project=tsubame-dev --location=asia-northeast1
```

`Creating gs://tsubame-shop-ch17-dev/...` と出て成功しました。フォルダ `dev` の `roles/editor` が効いています。本番では、どうでしょうか。

```sh run error title="本番では作れない"
gcloud storage buckets create gs://tsubame-shop-ch17-prod --project=tsubame-prod --location=asia-northeast1
```

`PERMISSION_DENIED: alice@tsubame.example does not have storage.buckets.create access` です。本番の alice は、`dev-team@` を通してログを読むロールしか持っていません。[6.8](ch06.html#denied) で見たとおり、エラーの文には「だれが」「どの権限を」持っていないかが書いてあります。

次は組織のポリシーです。社外のアカウントを IAM ポリシーに入れられないように、組織全体に**ドメイン制限**をかけます（[6.7](ch06.html#org-policy)）。`C03k8x2pq` は、つばめ文具の Workspace の顧客 ID です。組織のポリシーを書くには `roles/orgpolicy.policyAdmin` が要るので、自分に付けてから設定します。

```sh run title="組織のポリシーで、社外のアカウントを禁止する"
gcloud auth login you@tsubame.example
cat > domain.yaml <<'EOF'
name: organizations/405918273641/policies/iam.allowedPolicyMemberDomains
spec:
  rules:
  - values:
      allowedValues:
      - C03k8x2pq
EOF
gcloud organizations add-iam-policy-binding 405918273641 --member=user:you@tsubame.example --role=roles/orgpolicy.policyAdmin --format=none
gcloud org-policies set-policy domain.yaml --format="value(name)"
```

最後の行に、設定したポリシーの名前が出れば成功です。社外の協力者 taro に、開発のプロジェクトを見せようとしてみます。

```sh run error title="社外のアカウントは付けられない"
gcloud projects add-iam-policy-binding tsubame-dev --member=user:taro@example.com --role=roles/viewer
```

`FAILED_PRECONDITION: One or more users named in the policy do not belong to a permitted customer` と断られました。あなたは組織の管理者ですが、それでも付けられません。組織のポリシーは、IAM ポリシーを書き換える**前に**調べられる枠だからです。

## アプリ：注文 API を Cloud Run に載せる {#app}

土台ができたので、アプリを載せます。注文 API は、注文を受けると 2 つのことをします。Firestore に注文を保存し、Pub/Sub のトピック `orders` に「注文が来た」と知らせを出します。知らせを出したら、集計を待たずにお客さんに返事をします。これが [12.1](ch12.html#why) の「間に伝言板を置く」作りです。

```fig seq 1 つの注文の流れ。注文 API は保存と publish が済んだら返事をする。BigQuery へ書くのは、後ろで動く関数の仕事

  msgs: [
    { from: 'c', to: 'run', label: 'POST /orders（ID トークン付き）' }, { from: 'run', to: 'fs', label: 'orders に add' }, { from: 'run', to: 'ps', label: 'publish' },
    { from: 'run', to: 'c', label: '201 {"id": …}', style: 'sage' }, { from: 'ps', to: 'fn', label: 'CloudEvent', style: 'accent' }, { from: 'fn', to: 'bq', label: 'insert' },
  ],
  steps: [
    { title: '受け付け', say: 'お客さんが注文を POST します。Cloud Run の入口が ID トークンを調べ、呼んでよい人かを確かめてから、コンテナに渡します。', msgs: [{ from: 'c', to: 'run', label: 'POST /orders（ID トークン付き）', style: 'accent' }] },
```

まず、いまのプロジェクトを本番に切り替え、使う API をまとめて有効にします（[3.6](ch03.html#services)）。ソースからのデプロイには Cloud Build と Artifact Registry も要ります（[10.5](ch10.html#source)）。続けて、Firestore のデータベースと Pub/Sub のトピックを作ります（[13.2](ch13.html#database)、[12.2](ch12.html#topic-sub)）。

```sh run title="本番に切り替え、API を有効にし、データベースとトピックを作る"
gcloud config set project tsubame-prod
gcloud services enable run.googleapis.com cloudbuild.googleapis.com artifactregistry.googleapis.com firestore.googleapis.com pubsub.googleapis.com cloudfunctions.googleapis.com
gcloud firestore databases create --location=asia-northeast1 --format=none
gcloud pubsub topics create orders
```

プロンプトのかっこの中が `tsubame-prod` に変わり、これから先のコマンドは本番に向かいます。次は、注文 API が「だれとして」動くかを決めます。既定のサービスアカウントを使わず、**専用のサービスアカウント** `order-api` を作ります（[5.4](ch05.html#service-accounts)、[10.8](ch10.html#identity)）。付けるのは、Firestore に読み書きする `roles/datastore.user` と、トピック `orders` だけに publish できる `roles/pubsub.publisher` の 2 つです。publish の権限はプロジェクトではなく、トピックの IAM ポリシーに付けます（[6.5](ch06.html#resource)）。

```sh run title="専用のサービスアカウントと、最小限のロール"
gcloud iam service-accounts create order-api --display-name="注文 API"
gcloud projects add-iam-policy-binding tsubame-prod --member=serviceAccount:order-api@tsubame-prod.iam.gserviceaccount.com --role=roles/datastore.user --format=none
gcloud pubsub topics add-iam-policy-binding orders --member=serviceAccount:order-api@tsubame-prod.iam.gserviceaccount.com --role=roles/pubsub.publisher --format=none
```

注文 API のコードを書きます。[10.5](ch10.html#source) の express のサーバに、[13.3](ch13.html#sdk) の Firestore の SDK と、[12.8](ch12.html#sdk) の Pub/Sub の SDK を足したものです。

:::tip 鍵はコードに書かない
SDK は ADC（[5.8](ch05.html#adc)）で資格を探します。Cloud Run の中では、サービスに指定したサービスアカウントの資格が自動で使われるので、鍵ファイルは要りません。
:::

```sh run title="注文 API：server.js と package.json"
mkdir -p ~/order-api && cd ~/order-api
cat > server.js <<'EOF'
const express = require('express');
const { Firestore, FieldValue } = require('@google-cloud/firestore');
const { PubSub } = require('@google-cloud/pubsub');

const db = new Firestore();
const topic = new PubSub().topic('orders');
const app = express();
app.use(express.json());

// 注文を受ける：Firestore に保存し、トピックに知らせを出す
app.post('/orders', async (req, res) => {
  const { item, qty, price } = req.body;
  if (!item || !(qty > 0) || !(price > 0)) {
    console.error(JSON.stringify({ severity: 'ERROR', message: '注文の形が正しくありません', body: req.body }));
    return res.status(400).json({ error: 'item、qty、price が必要です' });
  }
  const ref = await db.collection('orders').add({ item, qty, price, status: 'received', at: FieldValue.serverTimestamp() });
  await topic.publishMessage({ json: { id: ref.id, item, qty, price } });
  console.log(`注文を受け付けました：${ref.id} ${item} x ${qty}`);
  res.status(201).json({ id: ref.id });
});

// 保存した注文の数
app.get('/orders', async (req, res) => {
  const snap = await db.collection('orders').get();
  res.json({ count: snap.size });
});

app.listen(process.env.PORT || 8080);
EOF
cat > package.json <<'EOF'
{ "name": "order-api", "version": "1.0.0", "scripts": { "start": "node server.js" },
  "dependencies": { "express": "^4.21.0", "@google-cloud/firestore": "^7.11.0", "@google-cloud/pubsub": "^4.9.0" } }
EOF
```

注文の形が正しくないときは、`console.error` で 1 行の JSON を書きます。これは**構造化ログ**で、あとの運用の節で `severity` と `message` を手がかりに探します（[16.5](ch16.html#structured)）。

デプロイします。`--service-account` で、さっき作ったサービスアカウントを指定します。お店の API なので、だれでも呼べるように `--allow-unauthenticated` を付けてみます。

```sh run title="デプロイする（--allow-unauthenticated を付けて）"
gcloud run deploy order-api --source=. --region=asia-northeast1 --service-account=order-api@tsubame-prod.iam.gserviceaccount.com --allow-unauthenticated --quiet
```

デプロイは成功し、`Service URL` が出ました。ところが途中に `WARNING: Setting IAM policy failed` という行があります。`--allow-unauthenticated` は、サービスの IAM ポリシーに `allUsers` へ `roles/run.invoker` を付ける指定です（[10.3](ch10.html#auth)）。前の節で組織にかけたドメイン制限は、`allUsers` も「顧客の外」として止めます。だから付けられませんでした。

:::note 組織のポリシーと、公開するサービス
ドメイン制限をかけた組織で、Cloud Run のサービスや Cloud Storage のバケットを公開したいことはよくあります。そのときは、公開するプロジェクトにだけ、組織のポリシーを上書きする設定を置くのがふつうです（`gcloud org-policies set-policy` で、プロジェクトの名前のポリシーを書く）。この章では公開せず、ID トークンで呼ぶことにします。
:::

呼んでみます。URL は `describe` で取り出します。トークンなしでは 403、ID トークンを付けると通るはずです。

```sh run title="トークンなしは 403。ID トークンで注文する"
URL=$(gcloud run services describe order-api --region=asia-northeast1 --format="value(status.url)")
curl -s -o /dev/null -w "%{http_code}\n" $URL/orders
TOKEN=$(gcloud auth print-identity-token)
curl -s -w "\n" -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"item":"ボールペン 黒","qty":3,"price":120}' $URL/orders
```

1 つ目の curl は `403` です。2 つ目は `{"id":"…"}` が返りました。Firestore が付けた注文の ID です。もう 1 つ注文し、形の正しくない注文も送ってみます。

```sh run title="もう 1 件と、形の正しくない注文。保存した数を見る"
curl -s -w "\n" -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"item":"ノート A5","qty":2,"price":180}' $URL/orders
curl -s -w "\n" -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"item":"ノート A5"}' $URL/orders
curl -s -w "\n" -H "Authorization: Bearer $TOKEN" $URL/orders
```

2 つ目は `qty` と `price` がないので、`{"error":"item、qty、price が必要です"}` が返りました（ステータスは 400）。最後の `{"count":2}` が、Firestore に保存された注文の数です。正しい注文 2 件だけが保存されています。

## 分析：Pub/Sub のトリガーで、注文を BigQuery へ {#analytics}

馬場さん（bob）は、売上を SQL で集計したいと言っています。Firestore は 1 件ずつの読み書きは得意ですが、全件を集計するのは BigQuery の仕事です（[13.8](ch13.html#cost)、[15.1](ch15.html#what)）。そこで、トピック `orders` に届いた注文を、関数で BigQuery の表に 1 行ずつ書きます。

まず書き先を作ります。データセット `shop` は、ほかのリソースと同じ東京（`asia-northeast1`）に置きます（[15.6](ch15.html#dataset)）。関数にも専用のサービスアカウント `order-sink` を用意し、このデータセットにだけ `roles/bigquery.dataEditor` を付けます。

```sh run title="データセット、表、関数のサービスアカウント"
bq mk --dataset --location=asia-northeast1 tsubame-prod:shop
bq mk --table tsubame-prod:shop.orders id:STRING,item:STRING,qty:INTEGER,price:INTEGER,ordered_at:TIMESTAMP
gcloud iam service-accounts create order-sink --display-name="注文を BigQuery へ"
bq add-iam-policy-binding --member=serviceAccount:order-sink@tsubame-prod.iam.gserviceaccount.com --role=roles/bigquery.dataEditor tsubame-prod:shop
```

最後のコマンドは、データセットの IAM ポリシーを JSON で出します。`bindings` に `order-sink` の 1 行があれば成功です。プロジェクト全体ではなく、データセット 1 つにだけ書けるサービスアカウントになりました。

関数を書きます。[11.7](ch11.html#pubsub-trigger) の Pub/Sub のイベント関数と同じ形です。メッセージの本文は `ce.data.message.data` に base64 で入っているので、戻してから JSON として読みます。BigQuery の SDK の `table.insert` で 1 行足します。

```sh run title="関数：index.js と package.json"
mkdir -p ~/order-sink && cd ~/order-sink
cat > index.js <<'EOF'
const functions = require('@google-cloud/functions-framework');
const { BigQuery } = require('@google-cloud/bigquery');

const table = new BigQuery().dataset('shop').table('orders');

// トピック orders のメッセージ 1 つで 1 回動く
functions.cloudEvent('toBigQuery', async (ce) => {
  const order = JSON.parse(Buffer.from(ce.data.message.data, 'base64').toString());
  await table.insert([{ ...order, ordered_at: ce.time }]);
  console.log(`BigQuery に書きました：${order.id}`);
});
EOF
cat > package.json <<'EOF'
{ "name": "order-sink", "main": "index.js",
  "dependencies": { "@google-cloud/functions-framework": "^3.0.0", "@google-cloud/bigquery": "^7.9.0" } }
EOF
```

`--trigger-topic=orders` でデプロイします。デプロイのときに、トピックに push のサブスクリプションが自動で作られます（[11.7](ch11.html#pubsub-trigger)）。関数の正体は Cloud Run のサービスなので（[11.4](ch11.html#run-service)）、`--service-account` の考え方も同じです。

```sh run title="Pub/Sub のトリガーで関数をデプロイする"
gcloud functions deploy order-sink --runtime=nodejs22 --region=asia-northeast1 --source=. --entry-point=toBigQuery --trigger-topic=orders --service-account=order-sink@tsubame-prod.iam.gserviceaccount.com --format="value(state)"
```

最後に `ACTIVE` と出れば、関数は動いています。注文を 2 件送り、関数のログを見ます。

```sh run title="注文を 2 件送り、関数のログを見る"
curl -s -w "\n" -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"item":"ボールペン 黒","qty":1,"price":120}' $URL/orders
curl -s -w "\n" -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"item":"マスキングテープ","qty":4,"price":260}' $URL/orders
gcloud functions logs read order-sink --region=asia-northeast1 --limit=2 --format="value(log)"
```

`BigQuery に書きました：…` が 2 行出ました。注文 API が publish した知らせを、関数が受け取って BigQuery に書いています。注文 API のコードは何も変えていません。受け手を後から足せるのが、間に Pub/Sub を置いた良さです。

では、Firestore と BigQuery の件数を比べてみます。比べ終わったら、集計を頼まれた馬場さん（bob）に切り替えておきます。

```sh run title="Firestore と BigQuery の件数を比べ、馬場さんに切り替える"
curl -s -w "\n" -H "Authorization: Bearer $TOKEN" $URL/orders
bq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-prod.shop.orders`'
gcloud auth login bob@tsubame.example
```

Firestore は `{"count":4}`、BigQuery は `4` ではなく `2` です。最初の 2 件は、関数をデプロイする**前**に publish しました。そのときトピックにはサブスクリプションが 1 つもなかったので、メッセージはどこにも届かずに捨てられています。Pub/Sub は、publish した時点にあるサブスクリプションにだけメッセージを配ります（[12.5](ch12.html#fanout)）。

:::tip 受け手は先に作る
本番では、受け手の関数やサブスクリプションを先に作ってから、送る側を動かします。後から受け手を足した場合、それより前のデータは、元の記録（ここでは Firestore）から読み込み直して埋めます。
:::

最後に、馬場さんが集計できるかを確かめます。いまは馬場さんとしてログインしています。

```sh run error title="ジョブは実行できても、表は読めない"
bq query --use_legacy_sql=false 'SELECT item, SUM(qty) AS qty, SUM(qty * price) AS sales FROM `tsubame-prod.shop.orders` GROUP BY item ORDER BY sales DESC'
```

`Access Denied: Table tsubame-prod:shop.orders: User does not have permission to query table` です。人の節で `analysts@` に付けたのは、ジョブを実行する `roles/bigquery.jobUser` だけでした。表のデータを読むには、データセットに `roles/bigquery.dataViewer` が要ります（[15.8](ch15.html#iam)）。

```sh run title="データセットに dataViewer を付けて、もう一度"
gcloud auth login you@tsubame.example
bq add-iam-policy-binding --member=group:analysts@tsubame.example --role=roles/bigquery.dataViewer tsubame-prod:shop
gcloud auth login bob@tsubame.example
bq query --use_legacy_sql=false 'SELECT item, SUM(qty) AS qty, SUM(qty * price) AS sales FROM `tsubame-prod.shop.orders` GROUP BY item ORDER BY sales DESC'
```

マスキングテープが 1,040 円、ボールペン 黒が 120 円と出ました。関数をデプロイした後の 2 件の注文です。馬場さんは、このデータセットを読めるだけで、書き換えることも、本番のほかのリソースに触ることもできません。

## 運用：ログで「何が起きたか」を確かめる {#operations}

載せたら終わりではありません。だれが何を変えたか、エラーは出ていないかを、ログで確かめます（[第 16 章](ch16.html)）。自分に戻して、まず**監査ログ**（管理アクティビティ）を見ます（[16.3](ch16.html#audit)）。IAM ポリシーを書き換えた記録だけに絞ります。

```sh run title="IAM を書き換えた記録、エラーのログ、断られた操作"
gcloud auth login you@tsubame.example
gcloud logging read 'logName:"cloudaudit.googleapis.com%2Factivity" AND protoPayload.methodName="SetIamPolicy"' --format="table(timestamp.date('%H:%M:%S'):label=TIME, protoPayload.authenticationInfo.principalEmail:label=WHO, protoPayload.resourceName:label=RESOURCE)"
gcloud logging read 'resource.type="cloud_run_revision" AND severity>=ERROR' --format="table(resource.labels.service_name:label=SERVICE, severity, jsonPayload.message)"
gcloud logging read 'protoPayload.status.code=7' --format="table(protoPayload.authenticationInfo.principalEmail:label=WHO, protoPayload.methodName:label=METHOD)"
```

- 1 つ目は、`tsubame-prod` の IAM ポリシーを書き換えた記録です。プロジェクト（`projects/tsubame-prod`）への 3 回と、トピック（`…/topics/orders`）への 1 回で、どれも `you@` が行っています
- 2 つ目は、Cloud Run のエラーのログです。注文 API が `console.error` で書いた構造化ログが `ERROR` のエントリになり、`jsonPayload.message` にコードに書いた文が入っています
- 3 つ目は、拒否された操作です（`status.code=7` は `PERMISSION_DENIED`）。人の節で alice が本番にバケットを作ろうとした記録です（[6.8](ch06.html#denied)）

形の正しくない注文が急に増えたら、どこかで画面やアプリが壊れているかもしれません。数を見張れるように、**ログベースの指標**を作ります（[16.8](ch16.html#alert)）。

```sh run title="形の正しくない注文を数える指標"
gcloud logging metrics create bad-orders --description="形の正しくない注文" --log-filter='resource.labels.service_name="order-api" AND jsonPayload.message="注文の形が正しくありません"'
gcloud logging metrics list --format="table(name, filter)"
```

指標 `bad-orders` ができました。この指標にアラートポリシーを付ければ、「5 分間に 3 件を超えたらメールで知らせる」といった見張りになります。作り方は [16.8](ch16.html#alert) と同じです。

```sh run title="開発のプロジェクトを消す"
gcloud projects delete tsubame-dev --quiet
gcloud projects describe tsubame-dev --format="value(lifecycleState)"
```

`DELETE_REQUESTED` になりました。[2.7](ch02.html#delete) で見たとおり、すぐには消えず、猶予期間（本物ではおよそ 30 日。正確には公式ドキュメントを参照）の間は `gcloud projects undelete tsubame-dev` で戻せます。alice が作ったバケットも、このプロジェクトと一緒に止まりました。

フォルダ `dev` は空になったように見えます。消せるでしょうか。

```sh run error title="猶予中のプロジェクトが入ったフォルダは消せない"
gcloud resource-manager folders delete $DEV
```

`FAILED_PRECONDITION` で断られます。猶予中のプロジェクトは、まだフォルダの中に残っているからです。フォルダは、中のプロジェクトが本当に消えてから消します。

本番のプロジェクトも消し、予算も外します。予算はプロジェクトではなく請求先アカウントのものなので、プロジェクトを消しても残ります。

```sh run title="本番を消し、予算を外す"
gcloud config set project tsubame-shop
gcloud projects delete tsubame-prod --quiet
for B in $(gcloud billing budgets list --billing-account=01A2B3-C4D5E6-F7A8B9 --format="value(name.basename())"); do gcloud billing budgets delete $B --billing-account=01A2B3-C4D5E6-F7A8B9 --quiet; done
gcloud billing projects list --billing-account=01A2B3-C4D5E6-F7A8B9
```

最後の一覧から `tsubame-prod` と `tsubame-dev` が消え、請求先につながっているのは最初からある 2 つだけになりました。消したプロジェクトには、もう料金がかかりません。

## この先へ {#next}

この本では、どのサービスにも共通する土台と、よく使うサービスに絞りました。次に学ぶとよいものを、1 行ずつ挙げます。どれもプロジェクトの中に作り、IAM で権限を決め、API を有効にしてから使う点は、この本で学んだとおりです。

- **Terraform などの IaC**（Infrastructure as Code、構成をコードで書くこと）：この章で gcloud で打った手順を設定ファイルに書き、レビューしてから適用し、何度でも同じ構成を作れるようにする
- **GKE**（Google Kubernetes Engine）：Kubernetes のクラスタを Google に管理してもらい、たくさんのコンテナをまとめて動かす。Cloud Run より細かく制御したいときに使う
- **Cloud Build の CI/CD**：リポジトリに push したら、テスト、イメージのビルド、Cloud Run へのデプロイまでを自動で流す
- **Secret Manager**：データベースのパスワードや API キーを保管し、IAM で読めるサービスアカウントを絞る。コードや環境変数に秘密を直接書かずに済む
- **VPC Service Controls**：BigQuery や Cloud Storage などのまわりに境界を作り、権限を持つ人でも境界の外へデータを持ち出せないようにする
- **Workload Identity 連携**：GitHub Actions など Google Cloud の外のシステムが、鍵ファイルを持たずにサービスアカウントとして動く
- **Cloud Load Balancing と Cloud Armor**：世界中からの要求を 1 つの IP で受けて振り分け、攻撃的な通信を手前で止める
- **Cloud Scheduler と Cloud Tasks**：決まった時刻にジョブを動かす、あとで実行する仕事を列に積む
- **Vertex AI**：機械学習のモデルを作り、BigQuery のデータで学習させ、API として呼べるようにする

:::key まとめ
- 入れ物は、フォルダで環境を分け、プロジェクトを請求先につなぎ、予算で使いすぎに気づけるようにする。予算は止めない
- ロールはグループに付ける。開発はフォルダで広く、本番はプロジェクトやリソースに必要なものだけを付ける。組織のポリシーは IAM より前に調べられる枠
- アプリには専用のサービスアカウントを作り、必要なロールだけを、できるだけ狭いリソース（トピック、データセット）に付ける
- Pub/Sub を間に置くと、受け手を後から足せる。ただし、publish した時点にサブスクリプションがないメッセージは届かない
- 監査ログで「だれが・何を」、構造化ログとログベースの指標で「何が起きたか」を見る
- 片付けはプロジェクトごと消す。猶予の間は戻せる。予算は請求先アカウントに残るので別に消す
:::

```sh answer
bq query --use_legacy_sql=false 'SELECT item, SUM(qty * price) AS sales FROM `tsubame-shop.shop.orders` GROUP BY item ORDER BY sales DESC'
```

:::hint
`SUM(qty * price) AS sales` で売上を出し、`GROUP BY item` で品物ごとにまとめ、`ORDER BY sales DESC` で多い順に並べます。数量（`qty`）だけの合計では、値段の高い品物の順位が変わります。
:::
:::
