## Google Cloud の「入れ物」は 4 段の木 {#tree}

Google Cloud で作るものは、すべて**リソース**（資源）と呼ばれます。バケット、VM、データセットなどです。リソースは、ばらばらに置かれているわけではありません。必ずどこかの「入れ物」に入っていて、入れ物は木の形につながっています。

```fig graph リソースの階層。上から組織、フォルダ、プロジェクト、リソース。線は「親 → 子」。フォルダは省くことも、何段にも重ねることもできる
{
```

4 つの段には、それぞれ役目があります。

| 段 | 何のための入れ物か | 数 |
| --- | --- | --- |
| **組織**（organization） | 会社そのもの。会社のドメイン（`tsubame.example`）と結び付く | 会社に 1 つ |
| **フォルダ**（folder） | 部署・チーム・環境で、プロジェクトをまとめる | 0 個でも、何段に重ねてもよい |
| **プロジェクト**（project） | リソースを入れる実際の箱。API の有効化と請求先はここで決める | いくつでも |
| **リソース** | バケット、VM、データセットなど | プロジェクトごとにいくつでも |

いちばん大事なのは**プロジェクト**です。リソースは必ずどれか 1 つのプロジェクトに入ります。「どの API を使えるか」（[第 3 章](ch03.html)）と「料金をどこに請求するか」（[第 4 章](ch04.html)）も、プロジェクトごとに決まります。

組織とフォルダは、プロジェクトを整理するための上の段です。上の段で決めた権限（IAM）は、下の段に**引き継がれます**（[第 6 章](ch06.html)）。木の形が、そのまま「だれが何をできるか」の形になるのです。

いまの木を見てみましょう。

```sh run title="いまあるプロジェクトと、その親"
gcloud projects list --format="table(projectId, parent.type, parent.id)"
```

`TYPE` と `ID` の列が、それぞれのプロジェクトの**親**です。いまは 2 つとも `organization` の `405918273641`、つまり組織の真下にあります。フォルダはまだありません。

親をたどって根まで出すのが `get-ancestors`（祖先を出す）です。

```sh run title="tsubame-shop の祖先"
gcloud projects get-ancestors tsubame-shop
```

1 行目が自分（`project`）、2 行目がその親（`organization`）です。下から上へ、根に着くまで並びます。この章では、ここにフォルダをはさみ、行が増えていくのを見ていきます。ページの上の「クラウドを見る」を開いておくと、木の変化が画面の下でも見えます。

## 組織：会社のドメインと結び付いた根 {#organization}

**組織**は木の根です。会社が Google Workspace か Cloud Identity（社員のアカウントを管理するサービス。[第 5 章](ch05.html)）を使っていると、そのドメインに 1 つだけ、組織が自動で作られます。

```sh run title="組織を調べる"
gcloud organizations list
gcloud organizations describe 405918273641
```

- `DISPLAY_NAME` の `tsubame.example` は、組織の名前です。会社のドメイン名がそのまま使われます
- `ID` の `405918273641` は、組織の番号です。コマンドで組織を指すときは、この番号を使います（`--organization=405918273641`）
- `DIRECTORY_CUSTOMER_ID` の `C03k8x2pq` は、Workspace / Cloud Identity の側の顧客 ID です。「この組織は、どのアカウント管理とつながっているか」を表します

`describe` の `name: organizations/405918273641` は、API の中での**リソース名**です。リソース名は「種類の複数形 / ID」の形をしています。フォルダは `folders/…`、プロジェクトは `projects/…` です。

### 組織がない場合

個人の Google アカウント（`@gmail.com` など）で Google Cloud を始めると、組織はありません。社外の協力者 `taro@example.com` は、そういうアカウントです。切り替えて同じことをしてみます。

```sh run title="個人のアカウントから見る"
gcloud auth login taro@example.com
gcloud organizations list
gcloud projects list
gcloud auth login you@tsubame.example
```

`Listed 0 items.` が 2 回出ました。taro さんには、見える組織もプロジェクトもありません。つばめ文具の組織の外にいるからです。最後の行で、あなた（`you@tsubame.example`）に戻しました。

組織がないアカウントでプロジェクトを作ると、そのプロジェクトは**親のない**プロジェクト（コンソールでは「組織なし」と出ます）になります。

| | 組織がある（会社のドメイン） | 組織がない（個人のアカウント） |
| --- | --- | --- |
| 木の根 | 組織 | プロジェクトがそれぞれ根 |
| フォルダ | 使える | 使えない（フォルダは組織の下にしか作れない） |
| 組織全体の IAM・ポリシー | かけられる | かけられない。プロジェクトごとに設定する |
| 社員が辞めたとき | プロジェクトは会社に残る | プロジェクトは個人のアカウントのもの |

会社で使うなら、組織を用意してからプロジェクトを作るのが基本です。

:::note このサイトの GCP では
本物の `gcloud auth login` はブラウザを開いてアカウントを選びます。このサイトでは、ログインするアカウントを引数で指定します。
:::

## プロジェクトの 3 つの呼び名：ID・名前・番号 {#id-name-number}

序章で、プロジェクトには 3 つの呼び名があると書きました。改めて並べて見ます。

```sh run title="ID・名前・番号"
gcloud projects describe tsubame-shop
gcloud projects describe 365600345236 --format="value(projectId, name)"
```

1 つ目の出力の、次の 3 行が呼び名です。

- `projectId: tsubame-shop` … **プロジェクト ID**
- `name: つばめ文具 オンライン店` … **プロジェクト名**
- `projectNumber: '365600345236'` … **プロジェクト番号**

2 つ目のコマンドは、ID の代わりに番号で同じプロジェクトを引いています。`tsubame-shop` と `つばめ文具 オンライン店` が出ました。どちらで指しても、同じ 1 つのプロジェクトです。


| 呼び名 | だれが決めるか | 後から変えられるか | 重なってよいか | 主に使う場所 |
| --- | --- | --- | --- | --- |
| ID | 作る人 | 変えられない | 世界で 1 つ | `gcloud` の `--project`、URL、リソース名 |
| 名前 | 作る人 | いつでも | 重なってよい | コンソールなど、人が読む表示 |
| 番号 | Google が自動で | 変えられない | 世界で 1 つ | API の内部、サービスアカウントの名前、エラーの文 |

ふだんコマンドで打つのは **ID** です。**名前**は人が読むための飾りで、検索や区別には向きません。**番号**は、自分で打つことは少ないのですが、エラーの文に出てきます。

```sh run error title="番号が出てくるエラー"
gcloud compute instances list
```

`Compute Engine API has not been used in project 365600345236 before or it is disabled.` と出ました。「プロジェクト 365600345236 では、この API が使われたことがないか、無効になっている」という意味です。ここに出ているのは ID ではなく**番号**です。番号を見て「どのプロジェクトのことか」が分かるように、`gcloud projects describe 番号` で引けることを覚えておきましょう。API の有効化は[第 3 章](ch03.html)で扱います。

### ID の決まり：小文字で始まり、世界で 1 つ {#project-id}

ID は、作るときに一度決めたら変えられません。だから決まりを知っておく必要があります。わざと決まりを破ってみます。

```sh run error title="ID の形が決まりに合わない"
gcloud projects create Tsubame-Dev
```

エラーの文 `Project IDs must start with a lowercase letter and can have lowercase ASCII letters, digits or hyphens. Project IDs must be between 6 and 30 characters.` を読むと、決まりがそのまま書いてあります。

- 英小文字で始まる（`T` は大文字なので不可）
- 使える文字は、英小文字、数字、ハイフン（`-`）
- 6 文字以上 30 文字以下

形が正しくても、作れないことがあります。

```sh run error title="ID がもう使われている"
gcloud projects create tsubame
gcloud projects create tsubame-shop
```

どちらも `The project ID you specified is already in use by another project.` です。`tsubame-shop` は自分たちのプロジェクトなので当然です。`tsubame` のほうは、つばめ文具のどのプロジェクトでもありません。**世界のどこかのだれかが**、すでにその ID を使っているのです。

プロジェクト ID は、Google Cloud を使う全員の間で 1 つしか存在できません。短くて分かりやすい ID ほど、先に取られています。会社名や用途、環境を組み合わせた ID（`tsubame-shop-dev` など）にすると、ぶつかりにくくなります。

:::note このサイトの GCP では
「世界のだれかが使っている ID」は、このサイトでは `tsubame`、`my-project`、`shop` などいくつかを決め打ちで用意しています。本物では、本当にほかの人のプロジェクトとぶつかります。
:::

## フォルダを作る {#folders}

プロジェクトが増えてくると、まとめる入れ物が欲しくなります。それが**フォルダ**です。組織の下に、店のチームのためのフォルダ `shop` を作ります。

```sh run title="組織の下にフォルダを作る"
gcloud resource-manager folders create --display-name=shop --organization=405918273641
```

フォルダのコマンドは `gcloud resource-manager folders` の下にあります。**Resource Manager**（リソース マネージャー）は、組織・フォルダ・プロジェクトの木を管理する API の名前です。

出力の `name: 'folders/…'` の数字が、フォルダの **ID** です。フォルダの ID は Google が付ける数字で、自分では決められません。自分で決めるのは `--display-name`（表示名）です。`parent: 'organizations/405918273641'` が親を表します。

同じ名前でもう 1 つ作ってみます。

```sh run error title="同じ親の下に、同じ名前のフォルダ"
gcloud resource-manager folders create --display-name=shop --organization=405918273641
```

`A folder with the same name already exists under the parent resource.`（同じ親の下に、同じ名前のフォルダがすでにある）です。下の `type: FOLDER_NAME_UNIQUENESS_VIOLATION` が、破った決まりの名前です。

フォルダの表示名は、**同じ親の下でだけ** 1 つです。親が違えば、同じ名前のフォルダを作れます。プロジェクト ID が「世界で 1 つ」なのとは、範囲がまったく違います。

### フォルダの ID を変数に入れる

フォルダを指すには、表示名ではなく数字の ID が要ります。毎回コピーするのは大変なので、シェルの変数に入れておきます。

```sh run title="表示名から ID を引く"
SHOP=$(gcloud resource-manager folders list --organization=405918273641 --filter="displayName=shop" --format="value(name.segment())")
echo $SHOP
```

`folders list` で組織の真下のフォルダを並べ、`--filter` で表示名が `shop` のものに絞り、`--format="value(name.segment())"` で `folders/…` の最後の部分（数字）だけを取り出しています。`$( … )` は、コマンドの出力をその場に埋め込むシェルの書き方です。`echo` で 12 桁の数字が出れば成功です。

フォルダの中に、さらにフォルダを作れます。本番用と開発用に分けます。

```sh run title="フォルダの中にフォルダ"
gcloud resource-manager folders create --display-name=prod --folder=$SHOP
gcloud resource-manager folders create --display-name=dev --folder=$SHOP
```

親の指定が `--organization` から `--folder` に変わりました。2 つとも `parent: 'folders/…'` が `$SHOP` の番号になっています。

```sh run title="shop の中を見て、ID を変数に"
gcloud resource-manager folders list --folder=$SHOP
PROD=$(gcloud resource-manager folders list --folder=$SHOP --filter="displayName=prod" --format="value(name.segment())")
DEV=$(gcloud resource-manager folders list --folder=$SHOP --filter="displayName=dev" --format="value(name.segment())")
```

`folders list` が出すのは、指定した親の**真下**のフォルダだけです。`PARENT_NAME` が 2 つとも `folders/…`（shop）になっています。これで木は「組織 → shop → prod / dev」の形になりました。

## プロジェクトを作り、ラベルを付ける {#create}

開発用のプロジェクトを、フォルダ `dev` の中に作ります。

```sh run title="フォルダの中にプロジェクトを作る"
gcloud projects create tsubame-shop-dev --name="つばめ文具 開発" --folder=$DEV --labels=env=dev,team=shop
```

- 最初の引数 `tsubame-shop-dev` が **ID** です
- `--name` が**名前**です。省くと、ID と同じ文字列になります
- `--folder` が**親**です。`--organization=405918273641` と書けば組織の真下に作られます
- `--labels` は**ラベル**（後で説明します）です

指定の書き方を間違えると、作る前に止まります。

```sh run error title="フラグの間違い"
gcloud projects create tsubame-shop-test --name="開発"
gcloud projects create tsubame-shop-test --folder=$DEV --organization=405918273641
```

1 つ目は `Project name must be between 4 and 30 characters.` で、名前が短すぎます（4 文字以上 30 文字以下）。2 つ目は `At most one of --folder | --organization can be specified.` で、親は 1 つしか選べません。どちらも `[exit 2]` で、API を呼ぶ前に gcloud が止めています。

できたプロジェクトを確かめます。

```sh run title="できたプロジェクト"
gcloud projects list
gcloud projects describe tsubame-shop-dev
```

`list` に `tsubame-shop-dev` が増えました。`PROJECT_NUMBER` の番号は、Google が自動で付けたものです。`describe` の `parent` が `type: folder` と `dev` のフォルダの ID になっています。

```sh run title="祖先が 1 段増える"
gcloud projects get-ancestors tsubame-shop-dev
```

`project` → `folder`（dev）→ `folder`（shop）→ `organization` の 4 行です。冒頭の `tsubame-shop` は 2 行でした。フォルダを重ねた分だけ、根までの道が長くなります。

### 名前は重なってもよい

名前は、いつでも変えられます。わざと本番と同じ名前にしてみます。

```sh run title="名前を本番と同じにする"
gcloud projects update tsubame-shop-dev --name="つばめ文具 オンライン店"
gcloud projects list --format="table(projectId, name)"
```

エラーにはならず、`NAME` が同じプロジェクトが 2 つ並びました。名前だけでは区別できないので、コマンドでは ID を使います。紛らわしいので元に戻し、ついでにラベルを足します。

```sh run title="名前を戻し、ラベルを足す"
gcloud projects update tsubame-shop-dev --name="つばめ文具 開発" --update-labels=owner=you
```

`labels` に `owner: you` が足されました。`--update-labels` は「このラベルを足す（あれば書き換える）」、`--remove-labels=キー` は「消す」です。

### ラベルで探す

**ラベル**は、`キー=値` の形でプロジェクトに付けるメモです。「どの環境か」「どのチームのものか」を書いておくと、探したり、料金を分けて集計したりできます。

```sh run title="ラベルで絞り込む"
gcloud projects list --filter="labels.env=dev" --format="value(projectId)"
gcloud projects list --filter="labels.env=prod" --format="value(projectId)"
```

`env=dev` で `tsubame-shop-dev`、`env=prod` で `tsubame-shop` が出ました。`tsubame-shop` には、最初から `env: prod` のラベルが付いていたのです（前の節の `describe` の出力にあります）。

ラベルは、プロジェクトのほかにバケットや VM など多くのリソースにも付けられます。請求のデータにもラベルが残るので、「env=dev の費用はいくらか」を後で集計できます（[第 4 章](ch04.html)）。

```sh run title="tsubame-shop を prod に移す"
gcloud projects move tsubame-shop --folder=$PROD
gcloud projects get-ancestors tsubame-shop
```

`Moved [tsubame-shop] to [folders/…]` の後に、移した後のプロジェクトが出ます。`parent` が `type: folder` に変わりました。ID・名前・番号は変わりません。`get-ancestors` は、冒頭の 2 行から 4 行になりました。

移動で変わるのは、親から引き継ぐものです。とくに IAM は、親のフォルダや組織で付けた権限が下に引き継がれるので、移した先のフォルダの権限が新しく効き、元の場所の権限は効かなくなります（[第 6 章](ch06.html)）。本番のプロジェクトを動かすときは、だれの権限が増え、だれのが減るかを先に確かめます。

フォルダも、`gcloud resource-manager folders move` で移動できます。ただし、木が輪にならないように止められます。

```sh run error title="自分の子の下には移せない"
gcloud resource-manager folders move $SHOP --folder=$DEV
```

`The folder move would create a cycle.`（この移動は循環を作る）です。`dev` は `shop` の子なので、`shop` を `dev` の下に入れると「shop の中の dev の中の shop…」と終わらなくなります。木は必ず根から枝分かれするだけの形でなければなりません。

## 削除：すぐには消えず、猶予がある {#delete}

まず、フォルダ `dev` を消してみます。

```sh run error title="中身があるフォルダは消せない"
gcloud resource-manager folders delete $DEV
```

`Folder … is not empty and cannot be deleted.`（フォルダが空ではないので削除できない）です。`type: FOLDER_TO_DELETE_NON_EMPTY_VIOLATION` が、破った決まりの名前です。`dev` の中には `tsubame-shop-dev` があります。フォルダを消すには、中のプロジェクトとフォルダを、先に消すか外へ移す必要があります。中身ごと一度に消すことはできません。うっかり本番を消さないための決まりです。

では、中のプロジェクトを消します。

```sh run title="プロジェクトを削除する"
gcloud projects delete tsubame-shop-dev --quiet
```

`--quiet` は、「本当に消しますか」という確認を省くフラグです。出力の `You can undo this operation for a limited period by running the command below.`（しばらくの間は、下のコマンドで取り消せる）に注目してください。プロジェクトの削除は、すぐには実行されません。

```fig graph プロジェクトの一生。削除するとまず DELETE_REQUESTED になり、猶予の間は undelete で戻せる。猶予が過ぎると本当に消える
{
  col: 210, row: 96,
  edges: [
    { from: 'a', to: 'r', label: 'delete' },
    { from: 'r', to: 'd', label: '約 30 日後' },
    { from: 'r', to: 'a', label: 'undelete', curve: 46, style: 'dashed' },
  ],
  steps: [
    { title: '使っている', say: 'ふつうの状態。projects list に出る。', nodes: [
      { id: 'a', label: 'ACTIVE', sub: '使える', x: 0, y: 0, kind: 'accent' }, { id: 'r', label: 'DELETE_REQUESTED', sub: '止まっている。戻せる', x: 1, y: 0, kind: 'plain' },
      { id: 'd', label: 'DELETED', sub: '中身ごと消える', x: 2, y: 0, kind: 'muted' } ] },
    { title: 'delete した', say: 'projects list から消え、中のリソースは止まる。ID は使われたまま。猶予の間は undelete で ACTIVE に戻せる。', nodes: [
      { id: 'a', label: 'ACTIVE', sub: '使える', x: 0, y: 0, kind: 'crate' }, { id: 'r', label: 'DELETE_REQUESTED', sub: '止まっている。戻せる', x: 1, y: 0, kind: 'accent' },

```

削除したプロジェクトは、まず **DELETE_REQUESTED**（削除を頼まれた）という状態になります。中のリソースは止まり、課金も止まります。そのまま猶予期間（本物ではおよそ 30 日。正確には公式ドキュメントを参照）が過ぎると、中身ごと本当に消えます。

```sh run title="削除したプロジェクトの状態"
gcloud projects list
gcloud projects describe tsubame-shop-dev --format="value(lifecycleState)"
```

`list` からは `tsubame-shop-dev` が消えました。`list` が出すのは `ACTIVE`（使える）のプロジェクトだけだからです。それでも `describe` では引けて、`lifecycleState`（一生の中の状態）が `DELETE_REQUESTED` になっています。まだ消えていないので、困ることが 2 つあります。

```sh run error title="消したのに、まだ残っているもの"
gcloud projects create tsubame-shop-dev
gcloud resource-manager folders delete $DEV
```

1 つ目は、同じ ID でプロジェクトを作り直せないことです。`already in use` が出ます。ID は削除を頼んだ後も使われたままで、本物では、完全に消えた後も同じ ID は二度と使えません。ID を使い捨てにしないよう、名前を付けるときに気を付けます。

2 つ目は、フォルダ `dev` がまだ消せないことです。削除を待っているプロジェクトも、フォルダの中身として数えられます。

猶予の間なら、削除を取り消せます。

```console
$ gcloud projects undelete tsubame-shop-dev
```

成功すると `lifecycleState` が `ACTIVE` に戻り、`projects list` にもまた出てきます。中のリソースも戻ってきます。

:::warn プロジェクトの削除は、いちばん強い片付け
プロジェクトを消すと、中のバケット、VM、データベース、ログが全部いっしょに消えます。猶予を過ぎたら戻せません。逆に言えば、「試しに作ったものを確実に全部片付けて、料金を止めたい」ときは、プロジェクトごと消すのがいちばん確実です。試すときは専用のプロジェクトを作る、という習慣はここから来ています。
:::

空のフォルダなら消せることも確かめます。

```sh run title="空のフォルダは消せる"
gcloud resource-manager folders create --display-name=tmp --folder=$SHOP
TMP=$(gcloud resource-manager folders list --folder=$SHOP --filter="displayName=tmp" --format="value(name.segment())")
gcloud resource-manager folders delete $TMP
gcloud resource-manager folders list --folder=$SHOP
```

`Deleted [folders/…].` と出て、最後の一覧は `dev` と `prod` だけに戻りました。中身のないフォルダは、待たずに消せます。

## フォルダをどう分けるか {#design}

フォルダの分け方に正解はありません。ただ、フォルダは**権限と規則を引き継ぐ単位**なので、「同じ人が同じ権限で触るものを、同じフォルダに入れる」のが基本です。よくある分け方は 2 つです。

```fig tree つばめ文具の分け方の例。上の段は部署（チーム）、その下を環境で分ける。それぞれの段に、そこで付ける権限を書いた
{
  root: { label: 'tsubame.example', kind: 'org', note: '全社の管理者、組織のポリシー', children: [
    { label: 'shop', kind: 'folder', note: '店のチーム（dev-team@）', children: [
      { label: 'prod', kind: 'folder', note: '本番。触れる人を絞る', hl: true, children: [{ label: 'tsubame-shop', kind: 'project', note: '本番の店' }] },
      { label: 'dev', kind: 'folder', note: '開発。チーム全員が自由に試す', children: [{ label: 'tsubame-shop-dev', kind: 'project', note: '開発用' }] },
    ] },
    { label: 'analytics', kind: 'folder', note: '分析のチーム（analysts@）', children: [{ label: 'tsubame-public', kind: 'project', note: '公開データセット' }] },
    { label: 'sandbox', kind: 'folder', note: '個人の実験。予算を小さく', children: [{ label: 'you-sandbox-01', kind: 'project', note: '試して、終わったら消す' }] },
  ] },
}
```

- **部署・チームで分ける**：上の図の 1 段目です。チームのグループに、そのフォルダの権限を 1 回付ければ、中のプロジェクト全部に効きます
- **環境で分ける**：上の図の 2 段目です。`prod`（本番）と `dev`（開発）を分けると、「本番は限られた人だけ、開発はチーム全員」と権限の強さを変えられます

フォルダは 2〜3 段で足りることがほとんどです。深いと、権限がどの段から来ているかを追うのが大変になります（重ねられる段の数にも上限があります。公式ドキュメントを参照）

プロジェクトの分け方は、もっと大事です。プロジェクトは API・請求・権限の境目なので、**本番と開発は必ず別のプロジェクト**にします。開発の実験が本番のデータを消す、開発のお試しの費用が本番の費用に混ざる、といった事故を、入れ物の段階で防げます。この本の最後の[第 17 章](ch17.html)で、つばめ文具の木を最後まで組み立てます。

:::key まとめ
- リソースは必ず 1 つのプロジェクトに入る。プロジェクトはフォルダか組織に入り、木の根は組織。上で付けた権限は下に引き継がれる
- 組織は Workspace / Cloud Identity のドメインに 1 つ。個人のアカウントには組織がなく、フォルダも使えない
- プロジェクトには ID（自分で決める・変えられない・世界で 1 つ）、名前（いつでも変えられる・重なってよい）、番号（Google が付ける）の 3 つの呼び名がある
- フォルダの ID は数字で、表示名は同じ親の下でだけ 1 つ。`folders list --filter --format="value(name.segment())"` で ID を引く
- `projects move` は親だけを付け替える。`get-ancestors` で根までの道が見える
- プロジェクトの削除は DELETE_REQUESTED を経て、猶予の後に本当に消える。その間 ID は使えず、フォルダも空にならない。中身のあるフォルダは消せない
:::

## 確認問題 {#quiz}

木を組み立てて、調べる問題です。フォルダは数字の ID で指すので、表示名から ID を引く書き方（`$( … )` と `--filter`、`--format="value(name.segment())"`）を使ってください。

:::quiz 祖先の種類
プロジェクト `tsubame-shop` の祖先を `gcloud projects get-ancestors` で調べ、**種類（`project`、`folder`、`organization`）だけ**を、コマンドが出す順に 1 行に 1 つ表示してください。

```sh vary
gcloud resource-manager folders create --display-name=shop --organization=405918273641
gcloud projects move tsubame-shop --folder=$(gcloud resource-manager folders list --organization=405918273641 --filter="displayName=shop" --format="value(name.segment())")
```

```sh starter
gcloud projects get-ancestors tsubame-shop
```

```sh answer
gcloud projects get-ancestors tsubame-shop --format="value(type)"
```

:::hint
表の `TYPE` の列は、`--format="value(type)"` で取り出せます。
:::
:::

:::quiz フォルダの中にプロジェクトを作る
組織の下に、フォルダ `dev` と `prod` が用意してあります。フォルダ **`dev`** の中に、次のプロジェクトを作ってください。

- ID：`tsubame-quiz-dev`
- 名前：`つばめ 検証`
- ラベル：`env=dev`

```sh prep
gcloud resource-manager folders create --display-name=prod --organization=405918273641
gcloud resource-manager folders create --display-name=dev --organization=405918273641
```

```sh starter
DEV=$(gcloud resource-manager folders list --organization=405918273641 --filter="displayName=dev" --format="value(name.segment())")
```

```sh answer
DEV=$(gcloud resource-manager folders list --organization=405918273641 --filter="displayName=dev" --format="value(name.segment())")
gcloud projects create tsubame-quiz-dev --name="つばめ 検証" --folder=$DEV --labels=env=dev
```

```sh check
gcloud projects describe tsubame-quiz-dev --format="value(name, parent.type, labels.env)"
gcloud resource-manager folders describe $(gcloud projects describe tsubame-quiz-dev --format="value(parent.id)") --format="value(displayName)"
```

:::hint
`--folder` には表示名ではなく数字の ID を渡します。starter の 1 行目で、`dev` の ID を変数 `DEV` に入れています。
:::
:::

:::quiz フォルダの直下にあるプロジェクト
フォルダ `shop` の**真下**にあるプロジェクトの ID を、1 行に 1 つ表示してください（組織の真下のプロジェクトや、`shop` の中のフォルダに入っているプロジェクトは含めません）。

```sh prep
gcloud resource-manager folders create --display-name=shop --organization=405918273641
SHOP=$(gcloud resource-manager folders list --organization=405918273641 --filter="displayName=shop" --format="value(name.segment())")
gcloud resource-manager folders create --display-name=team-a --folder=$SHOP
gcloud projects create tsubame-q3-app --folder=$SHOP
gcloud projects create tsubame-q3-web --folder=$SHOP
gcloud projects create tsubame-q3-other
gcloud projects create tsubame-q3-deep --folder=$(gcloud resource-manager folders list --folder=$SHOP --format="value(name.segment())")
```

```sh vary
gcloud projects create tsubame-q3-api --folder=$(gcloud resource-manager folders list --organization=405918273641 --filter="displayName=shop" --format="value(name.segment())")
```

```sh answer
SHOP=$(gcloud resource-manager folders list --organization=405918273641 --filter="displayName=shop" --format="value(name.segment())")
gcloud projects list --filter="parent.id=$SHOP" --format="value(projectId)"
```

:::hint
`gcloud projects list --format="table(projectId, parent.type, parent.id)"` で、それぞれの親が見えます。`--filter="parent.id=…"` で親を指定して絞り込めます。
:::
:::

:::quiz フォルダを片付ける
フォルダ `old` を削除してください。`old` の中には、空のフォルダ `archive` と、まだ使うプロジェクト `tsubame-q4-app` があります。**プロジェクトは消さずに、組織の真下へ移して**ください。

```sh prep
gcloud resource-manager folders create --display-name=keep --organization=405918273641
gcloud resource-manager folders create --display-name=old --organization=405918273641
OLD=$(gcloud resource-manager folders list --organization=405918273641 --filter="displayName=old" --format="value(name.segment())")
gcloud resource-manager folders create --display-name=archive --folder=$OLD
gcloud projects create tsubame-q4-app --folder=$OLD
```

```sh starter
OLD=$(gcloud resource-manager folders list --organization=405918273641 --filter="displayName=old" --format="value(name.segment())")
```

```sh answer
OLD=$(gcloud resource-manager folders list --organization=405918273641 --filter="displayName=old" --format="value(name.segment())")
gcloud projects move tsubame-q4-app --organization=405918273641
gcloud resource-manager folders delete $(gcloud resource-manager folders list --folder=$OLD --format="value(name.segment())")
gcloud resource-manager folders delete $OLD
```

```sh check
gcloud resource-manager folders list --organization=405918273641 --format="value(displayName)"
gcloud projects describe tsubame-q4-app --format="value(lifecycleState, parent.type)"
```

:::hint
中身のあるフォルダは消せません。中のフォルダは先に消し、中のプロジェクトは `gcloud projects move … --organization=405918273641` で外へ出します。プロジェクトを削除しても、削除を待つ間はフォルダの中身として数えられるので、フォルダは消せません。
:::
:::
