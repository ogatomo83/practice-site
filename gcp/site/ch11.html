第 11 章

Cloud Run functions

コンテナを作らずに、関数を 1 つ書くだけで動くプログラムを置きます。Functions Framework で HTTP 関数を書いてデプロイし、curl と functions call で呼び、Pub/Sub のメッセージや Cloud Storage のファイルで動くイベント関数を作ります。関数の正体が Cloud Run のサービスであることも、自分の目で確かめます。

11.1関数とは何か

第 10 章の Cloud Run では、コンテナ（プログラムと、動かすのに必要なものを 1 つにまとめた箱）を作ってデプロイしました。どのポートで待ち受けるか、どんな Web の仕組みを使うかは、自分で決めました。

Cloud Run functions（クラウド ラン ファンクションズ）は、そこをもっと省きます。書くのは関数だけです。「要求が来たら、この関数を呼ぶ」「メッセージが届いたら、この関数を呼ぶ」という形で、1 つの処理を 1 つの関数に書きます。コンテナを作るのも、待ち受けるのも、Google Cloud がやります。

関数を呼ぶきっかけをトリガーと呼びます。この章で扱うトリガーは 3 つです。

トリガー関数の種類関数が受け取るもの
HTTP の要求（--trigger-http）HTTP 関数要求（req）と応答（res）
Pub/Sub のトピックへの publish（--trigger-topic）イベント関数CloudEvent（できごとの記録）
Cloud Storage のバケットにファイルができた（--trigger-bucket）イベント関数CloudEvent

Cloud Run が向いているのは、Web アプリや API 全体のように、待ち受けるプログラムをまるごと置くときです。Cloud Run functions が向いているのは、「注文が来たら記録する」「ファイルが届いたら取り込む」といった小さな処理や、サービスどうしのつなぎです。

歴史名前の移り変わり

この製品は、以前は Cloud Functions という名前でした。いまの第 2 世代の関数は、中身が Cloud Run のサービスとして動くようになり、名前も Cloud Run functions に変わりました。コマンドは今も gcloud functions のままです。本物のドキュメントや記事で「Cloud Functions」「2nd gen」とあれば、この章と同じものを指していることが多いです。

11.2Functions Framework で HTTP 関数を書く

HTTP 関数は、(req, res) の 2 つを受け取る関数です。req（リクエスト）は届いた要求、res（レスポンス）は返す応答です。関数は req を読み、res に書いて終わります。

Functions Framework（ファンクションズ フレームワーク）は、Google が公開している小さなライブラリです。Node.js では @google-cloud/functions-framework という名前です。要求を待ち受けて、名前で登録した関数を呼びます。Cloud Run functions の中では、このライブラリがあなたの関数を包んで動きます。

作業用のディレクトリ ~/hello を作り、index.js に関数を書きます。

index.js：HTTP 関数を 2 つ⌘↵
mkdir ~/hello && cd ~/hellocat > index.js <<'EOF'const functions = require('@google-cloud/functions-framework');// GET /?name=… でも、POST の {"name": …} でも、あいさつを返すfunctions.http('helloHttp', (req, res) => {  const greeting = process.env.GREETING || 'Hello';  const name = req.query.name || req.body.name || 'World';  console.log(`hello: name=${name}`);  res.send(`${greeting}, ${name}!\n`);});// 注文の合計を JSON で返すfunctions.http('orderTotal', (req, res) => {  const items = req.body.items;  if (!Array.isArray(items)) {    res.status(400).json({ error: 'items がありません' });    return;  }  const total = items.reduce((sum, it) => sum + it.price * it.qty, 0);  res.json({ count: items.length, total });});EOF

読み方は次のとおりです。

  • functions.http('helloHttp', 関数) は、「helloHttp という名前で、この HTTP 関数を登録する」という意味です。この名前をエントリポイント（入口の関数の名前）と呼びます
  • req.query は URL の ? の後ろ（クエリ文字列）、req.body は POST で送られた本文です。本文が JSON なら、オブジェクトに直してから渡されます
  • res.send(文字列) は文字列を、res.json(オブジェクト) は JSON を返します。res.status(400) で、返す状態コードを変えられます。何も付けなければ 200 です
  • process.env.GREETING は環境変数です。あとで、デプロイのときに値を入れます

Node.js の関数には、もう 1 つ package.json が要ります。どのファイルが入口か（main）と、使うライブラリ（dependencies）を書きます。

package.json⌘↵
cat > package.json <<'EOF'{ "name": "hello", "main": "index.js",  "dependencies": { "@google-cloud/functions-framework": "^3.0.0" } }EOFls

index.js と package.json の 2 つが並びました。これで、デプロイするものはそろいました。

コツexports.名前 の書き方

functions.http(…) を使わずに、exports.helloHttp = (req, res) => { … }; と書くこともできます。モジュールが外に出した（export した）関数のうち、エントリポイントと同じ名前のものが呼ばれます。古い記事にはこの書き方が多く、どちらでも動きます。イベント関数では functions.cloudEvent(…) で登録すると、受け取るものが CloudEvent だとはっきりします。

11.3デプロイして、呼び出す

関数を置くコマンドは gcloud functions deploy です。さっそく打ってみます。

API が無効のままデプロイするエラーになる⌘↵
gcloud functions deploy hello-http --runtime=nodejs22 --region=asia-northeast1 --source=. --entry-point=helloHttp --trigger-http --allow-unauthenticated

PERMISSION_DENIED: Cloud Functions API has not been used in project 365600345236 before or it is disabled. は、第 3 章で見た「API が無効」のエラーです。数字はプロジェクト番号です。直し方は、文にあるとおり API を有効にすることです。

Cloud Functions API を有効にする⌘↵
gcloud services enable cloudfunctions.googleapis.comgcloud services list --enabled --format="value(config.name)" | grep -E "^(cloudfunctions|run|cloudbuild|artifactregistry|eventarc|pubsub)\."gcloud config set functions/region asia-northeast1

cloudfunctions.googleapis.com を 1 つ有効にしただけで、run、cloudbuild、artifactregistry、eventarc、pubsub も有効になりました。関数は、これらのサービスを組み合わせて動くからです（API の依存、第 3 章）。最後の行は関数の既定のリージョンの設定で、このあとは --region を省けます。

デプロイする

HTTP 関数をデプロイする⌘↵
gcloud functions deploy hello-http --runtime=nodejs22 --source=. --entry-point=helloHttp --trigger-http --allow-unauthenticated

標準エラーに、作業の段階が並びます。[Build] でコンテナを作り、[Service] で Cloud Run のサービスを作り、[Healthcheck] で起動を確かめています。最後に出る yaml が、できた関数の情報です。url は関数の URL で、「リージョン - プロジェクト ID」と関数の名前でできています。serviceConfig.uri は run.app で終わるもう 1 つの URL です（次の節）。buildConfig の entryPoint と runtime が、どの関数をどのランタイムで動かすかです。

hello-http は関数の名前です（プロジェクトとリージョンの中で 1 つ）。フラグの意味は次のとおりです。

フラグ意味
--runtime=nodejs22ランタイム（動かす言語と版）。Node.js 22
--source=.ソースのディレクトリ。. はいまのディレクトリ
--entry-point=helloHttp呼ぶ関数の名前。省くと、関数の名前（hello-http）が使われる
--trigger-httpHTTP の要求で呼ぶ
--allow-unauthenticatedだれでも（ログインしていない人も）呼べるようにする
メモこのサイトの GCP では

動かせるランタイムは Node.js（--runtime=nodejs22 など）だけです。本物は Python、Go、Java、Ruby、PHP、.NET も使えます。npm install も行わず、require できるのはこのサイトが用意したライブラリだけです。

呼び出す

関数の URL に、curl で要求を送ります。

GET、POST、functions call で呼ぶ⌘↵
curl "https://asia-northeast1-tsubame-shop.cloudfunctions.net/hello-http?name=Haruka"curl -X POST -H "Content-Type: application/json" -d '{"name":"Alice"}' https://asia-northeast1-tsubame-shop.cloudfunctions.net/hello-httpgcloud functions call hello-http --data='{"name":"Bob"}'

1 つめは req.query.name から Haruka、2 つめは req.body.name から Alice を読みました。POST の本文は Content-Type: application/json なので、req.body は JSON を直したオブジェクトです。3 つめの gcloud functions call は、URL を打たずに関数の名前で呼ぶコマンドで、--data が POST の本文になります。

認証が必要な関数

今度は --allow-unauthenticated を付けずに、orderTotal をデプロイします。出力は --format で状態だけにします。そのあと、トークンなしと、ID トークン付きで呼びます。

認証が必要な関数をデプロイして呼ぶ⌘↵
gcloud functions deploy order-total --runtime=nodejs22 --source=. --entry-point=orderTotal --trigger-http --format="value(state)"curl -s -o /dev/null -w "%{http_code}\n" -X POST -H "Content-Type: application/json" -d '{"items":[]}' https://asia-northeast1-tsubame-shop.cloudfunctions.net/order-totalcurl -H "Authorization: Bearer $(gcloud auth print-identity-token)" -X POST -H "Content-Type: application/json" -d '{"items":[{"price":120,"qty":3},{"price":450,"qty":1}]}' https://asia-northeast1-tsubame-shop.cloudfunctions.net/order-total

トークンなしでは 403（Forbidden、禁止）でした。--allow-unauthenticated は、関数の Cloud Run のサービスに「allUsers に roles/run.invoker（呼び出す権限）」を足すフラグです。付けなければ、呼べるのは権限を持つ人だけです。第 10 章と同じく、ID トークン（自分がだれかを示す、署名付きの短い文字列）を付けると通ります。120 × 3 + 450 × 1 = 810 が返りました。

gcloud functions call は、あなたのアカウントで呼ぶので、トークンなしで通ります。本文に items がないと、関数は res.status(400) で 400 を返します。

関数が 400 を返すエラーになる⌘↵
gcloud functions call order-total --data='{}'

ResponseError: status=[400] は、関数が 400 を返したことを示します。message=[…] には、関数が res.json で返した本文がそのまま入っています。functions call は 400 以上の応答を、エラーとして表示します。関数そのものが壊れたのではなく、関数が「入力がおかしい」と答えた、という読み方をします。

11.4関数の正体は Cloud Run のサービス

関数の一覧と、Cloud Run のサービスの一覧⌘↵
gcloud functions listgcloud run services list

関数が 2 つ、HTTP Trigger（HTTP のトリガー）で ACTIVE（動いている）です。ENVIRONMENT の GEN_2 は第 2 世代を表します。そして、Cloud Run のサービスの一覧にも、同じ名前の hello-http と order-total が出ています。第 10 章の gcloud run deploy で作ったものと同じ、Cloud Run のサービスです。

だから、run.app の URL でも呼べます。

サービスの URL で呼ぶ⌘↵
gcloud functions describe hello-http --format="yaml(url,serviceConfig.uri,serviceConfig.revision)"curl "$(gcloud functions describe hello-http --format='value(serviceConfig.uri)')?name=Run"

serviceConfig.revision は、いま動いているリビジョン（サービスの版）です。関数のコンテナのイメージ（コンテナの元になるファイル）は、Artifact Registry の gcf-artifacts というリポジトリに置かれます。デプロイの出力の buildConfig.dockerRepository が、その場所です。

再デプロイと環境変数

index.js の helloHttp は、環境変数 GREETING があれば、それをあいさつに使います。--set-env-vars で入れて、もう一度デプロイします。2 回目からは、--runtime やトリガーなど、前と同じものは省けます。

環境変数を入れて再デプロイし、リビジョンを見る⌘↵
gcloud functions deploy hello-http --source=. --set-env-vars=GREETING=Hi --format="value(serviceConfig.revision)"curl "https://asia-northeast1-tsubame-shop.cloudfunctions.net/hello-http?name=Haruka"gcloud run revisions list --service=hello-http --region=asia-northeast1

あいさつが Hi に変わり、リビジョンの番号が 00002 に進みました。Cloud Run と同じく、デプロイのたびに新しいリビジョンができて、要求はそちらへ向かいます。リビジョンの一覧で ACTIVE が yes なのも、新しい 00002 のほうです。第 10 章のトラフィック分割（リビジョンに割合で振り分けること）も、仕組みとしては同じものの上に乗っています。

深掘りなぜ Cloud Run の上に作ったのか

関数とコンテナのサービスは、「要求が来たらインスタンス（動いている 1 つの実体）を起こし、来なければ 0 まで減らす」という、同じ土台を必要とします。土台を 1 つにすれば、スケール、リビジョン、トラフィック分割、ログ、IAM の仕組みを、両方で共有できます。関数を使っていて Cloud Run の機能（同時実行の数、最小インスタンス数など）が欲しくなったら、それは Cloud Run の設定です。ただし、関数が作ったサービスは gcloud functions deploy で更新するのが基本です。gcloud run deploy で直接変えると、関数の設定とずれます。

11.5console.log はログになる

関数の中で console.log に書いたものは、Cloud Logging（Google Cloud のログの置き場）に 1 行ずつ残ります。関数のログを読むコマンドは gcloud functions logs read です。

関数のログを読む⌘↵
gcloud functions logs read hello-http

新しいものが上で、いままでに呼んだ回数だけ hello: name=… の行があります。

LEVEL は重大度の頭文字で、E がエラーです（console.log の行は空）。EXECUTION_ID は 1 回の実行の ID で、イベント関数では同じ実行のログに同じ ID が付きます。LOG の Default STARTUP TCP probe succeeded … は、インスタンスが起動したときに Cloud Run が書いた行です。

gcloud functions logs read は、Cloud Logging を関数向けに読みやすくしたものです。中身は、Cloud Run のサービスのログ（resource.type="cloud_run_revision"）です。下の 1 行めは --limit で行数を絞り、--format で中身だけにしたもの、2 行めは gcloud logging read で同じログを直接読んだものです。

行数を絞る、Cloud Logging から直接読む⌘↵
gcloud functions logs read hello-http --limit=2 --format="value(log)"gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="hello-http" AND textPayload:"hello"' --limit=2 --format="value(textPayload)"

logging read のほうは textPayload:"hello" で hello を含む行に絞ったので、起動の行が出ていません。ログのクエリの書き方は、第 16 章でくわしく扱います。

11.6失敗を読む：エントリポイントと例外

エントリポイントの書き間違い

関数でよく出る失敗を、わざと起こします。まず --entry-point=helloHtp（t が 1 つ足りない）でデプロイします。

エントリポイントを書き間違えるエラーになる⌘↵
gcloud functions deploy hello-typo --runtime=nodejs22 --source=. --entry-point=helloHtp --trigger-http

X [Service] Container Healthcheck failed. で止まりました。エラーの文の後ろに、理由が書いてあります。

Function 'helloHtp' is not defined in the provided module. は「helloHtp という関数が、モジュール（index.js）の中に見つからない」という意味です。コンテナを作るところ（[Build]）までは成功しています。コンテナを起動して、Functions Framework が関数を探したところで失敗しました。直し方は、--entry-point を index.js の functions.http('…') の名前と同じにすることです。大文字と小文字も区別されます。

失敗した関数も、一覧には残ります。

失敗した関数の状態とログ。そして消す⌘↵
gcloud functions list --format="table(name.basename(),state)"gcloud functions logs read hello-typogcloud functions delete hello-typo --quiet

hello-typo は FAILED です。ログには、起動に失敗したときの文がそのまま残っています。デプロイで失敗したら、まず functions logs read を見るのが近道です。最後の delete で、いらない関数を消しました。--quiet は「消してよいか」の確認を省くフラグです。

関数の中で例外を投げる

デプロイは通っても、呼ばれたときに失敗することがあります。index.js に、もう 1 つ関数を足します。>> は、ファイルの終わりに書き足すリダイレクトです。

例外を投げうる関数を書き足す⌘↵
cat >> index.js <<'EOF'// 品物の名前を大文字にして返す。item がないと例外になるfunctions.http('stock', (req, res) => {  const item = req.body.item;  res.send(`${item.toUpperCase()} の在庫を調べます\n`);});EOFgcloud functions deploy stock --runtime=nodejs22 --source=. --trigger-http --allow-unauthenticated --format="value(buildConfig.entryPoint)"

--entry-point を省いたので、関数の名前の stock がエントリポイントになりました。正しい本文と、item のない本文で呼び、ログを見ます。

item のない要求で 500 になる⌘↵
curl -X POST -H "Content-Type: application/json" -d '{"item":"pen"}' https://asia-northeast1-tsubame-shop.cloudfunctions.net/stockcurl -i -X POST -H "Content-Type: application/json" -d '{}' https://asia-northeast1-tsubame-shop.cloudfunctions.net/stockgcloud functions logs read stock --limit=6

2 つめは HTTP/2 500 と Internal Server Error が返りました。500 は「サーバの中で何かが壊れた」という状態コードで、呼んだ側には理由が知らされません。理由はログにあります。

E（エラー）の行に TypeError: Cannot read properties of undefined (reading 'toUpperCase') があります。「undefined（値がない）の toUpperCase を読もうとした」、つまり req.body.item がなかった、という意味です。関数が投げた例外は、Functions Framework が受け止めて 500 を返し、例外の中身をログに書きます。入力を調べて res.status(400) を返す orderTotal の書き方なら、呼んだ側にも理由を伝えられます。

11.7イベント関数：Pub/Sub のメッセージで動く

ここからは、HTTP ではなくイベント（何かが起きたこと）で動く関数です。まず Pub/Sub です。Pub/Sub（パブサブ）は、メッセージをトピック（宛先の名前）に送ると、そのトピックを購読しているところへ届ける仕組みです。第 12 章でくわしく扱います。

イベント関数が受け取るのは、CloudEvent（クラウドイベント）という決まった形のデータです。CloudEvent は、どのサービスでも共通の「できごとの記録」の形式です。Pub/Sub から届く CloudEvent の中身は、次のようになっています。

大事なのは、本文が ce.data.message.data に base64（バイト列を英数字と記号だけの文字列にする符号化）で入っていることです。そのままでは読めないので、Buffer.from(…, 'base64').toString() で元の文字列に戻します。

イベント関数用のディレクトリを作ります。onOrder は Pub/Sub 用、onUpload は次の節の Cloud Storage 用です。

イベント関数を書く⌘↵
mkdir ~/events && cd ~/eventscat > index.js <<'EOF'const functions = require('@google-cloud/functions-framework');functions.cloudEvent('onOrder', (ce) => {  console.log(`type: ${ce.type}`);  const msg = ce.data.message;  console.log(`data（base64）: ${msg.data}`);  const order = JSON.parse(Buffer.from(msg.data, 'base64').toString());  console.log(`注文 ${order.id}：${order.total} 円`);});functions.cloudEvent('onUpload', (ce) => {  const file = ce.data;  console.log(`type: ${ce.type}`);  console.log(`受け取ったファイル：${file.name}（${file.size} バイト、${file.contentType}）`);});EOFecho '{ "name": "events", "main": "index.js", "dependencies": { "@google-cloud/functions-framework": "^3.0.0" } }' > package.json

HTTP 関数との違いは、functions.cloudEvent で登録することと、引数が (ce) の 1 つだけで、応答を書かないことです。関数が例外を投げずに終われば、「受け取った」ことになります。

--trigger-topic=orders でデプロイします。トピック orders がまだなければ、作られます。

Pub/Sub のトリガーでデプロイする⌘↵
gcloud functions deploy on-order --runtime=nodejs22 --source=. --entry-point=onOrder --trigger-topic=orders --format="yaml(eventTrigger.eventType,eventTrigger.pubsubTopic)"

eventTrigger が、この関数を呼ぶきっかけです。eventType の google.cloud.pubsub.topic.v1.messagePublished は「トピックにメッセージが publish された」という種類です。サブスクリプション（トピックの購読）の一覧を見てから、メッセージを publish して、関数のログを見ます。

サブスクリプションを見て、注文を publish する⌘↵
gcloud pubsub subscriptions list --format="table(name.basename(),topic.basename())"gcloud pubsub topics publish orders --message='{"id":"A-1001","total":1200}'gcloud functions logs read on-order --limit=3

トピック orders に、eventarc-asia-northeast1-on-order-… というサブスクリプションができています。Eventarc（イベントアーク）は、イベントを集めて Cloud Run のサービスに届ける仕組みです。関数のデプロイのときに、Eventarc が「トピック orders に届いたメッセージを、関数のサービスへ push（相手に送り込む）する」サブスクリプションを作りました。

ログには、下から順に、type、data（base64）、注文 A-1001：1200 円 が並びました。eyJpZCI6… が base64 の本文で、関数がそれを戻して JSON として読みました。3 行の EXECUTION_ID が同じなので、1 回の実行で書いたものだと分かります。

11.8イベント関数：Cloud Storage にファイルを置くと動く

もう 1 つのイベントは、Cloud Storage です。バケットにオブジェクト（ファイル）ができたときに、関数を呼べます。領収書の画像が置かれたら処理する、取り込み用のファイルが届いたら読み込む、といった使い方をします。

トリガーにするバケットを作ってから（バケットの名前は世界で 1 つです）、--trigger-bucket にバケットの名前（gs:// は付けない）を渡してデプロイします。

バケットを作り、Cloud Storage のトリガーでデプロイする⌘↵
gcloud storage buckets create gs://tsubame-shop-receipts-ch11 --location=asia-northeast1gcloud functions deploy on-upload --runtime=nodejs22 --source=. --entry-point=onUpload --trigger-bucket=tsubame-shop-receipts-ch11 --format="yaml(eventTrigger.eventType,eventTrigger.eventFilters)"

eventType は google.cloud.storage.object.v1.finalized です。finalized（確定した）は、「オブジェクトの書き込みが終わって、読めるようになった」という意味です。eventFilters が、どのバケットのイベントかを絞っています。ファイルを置いてみます。

ファイルを置くと、関数が動く⌘↵
echo "えんぴつ 3 本 360 円" > receipt.txtgcloud storage cp receipt.txt gs://tsubame-shop-receipts-ch11/2026/11/receipt.txtgcloud functions logs read on-upload --limit=2 --format="value(log)"

cp しただけで、関数が動きました。CloudEvent の data は、オブジェクトの情報そのものです。name はバケットの中の名前（2026/11/receipt.txt）、size はバイト数です。ファイルの中身は入っていないので、中身が要るときは、関数の中から Cloud Storage を読みます。

ないバケットを指定すると、Bucket … not found（バケットが見つからない）でデプロイが止まります。

ないバケットをトリガーにするエラーになる⌘↵
gcloud functions deploy on-upload2 --runtime=nodejs22 --source=. --entry-point=onUpload --trigger-bucket=tsubame-shop-no-such-bucket

名前の書き間違いか、まだ作っていないかのどちらかです。本物では、バケットと関数のリージョンの組み合わせにも決まりがあります（公式ドキュメントを参照）。

注意関数が書いたファイルで、また関数が動く

トリガーのバケットに、関数の中からファイルを書くと、そのファイルでまた関数が動きます。処理の結果は、別のバケットに書くようにします。そうしないと、関数が自分を呼び続けて、呼び出しの回数と料金が増え続けます。

最後に片付けます。関数を消すと、Cloud Run のサービスと、Eventarc のサブスクリプションも一緒に消えます。

関数を消す⌘↵
gcloud functions delete on-order --quietgcloud functions delete on-upload --quietgcloud functions list --format="value(name.basename())"gcloud pubsub subscriptions list --format="value(name)"

一覧に残るのは HTTP 関数の 3 つです。eventarc-… のサブスクリプションもなくなりました。トピック orders とバケットは、関数とは別のリソースなので残ります。本物の Cloud Run functions には毎月の無料枠（200 万回の呼び出し、400,000 GB 秒と 200,000 GHz 秒、外向き転送 5 GB）があり、それを超えた分と、Cloud Build や Artifact Registry の分が料金になります。

要点まとめ
  • Cloud Run functions は、関数を 1 つ書けば動く。コンテナは gcloud functions deploy が Cloud Build で作り、Artifact Registry に置く
  • HTTP 関数は functions.http('名前', (req, res) => …)。req.query と req.body を読み、res.send / json / status で返す
  • --trigger-http で HTTP、--allow-unauthenticated でだれでも呼べる。付けなければ ID トークンが要る。gcloud functions call は自分のアカウントで呼ぶ
  • 関数の正体は Cloud Run のサービス。run services list に出て、デプロイのたびにリビジョンが増える
  • イベント関数は functions.cloudEvent('名前', (ce) => …)。--trigger-topic は Eventarc のサブスクリプション経由、--trigger-bucket はオブジェクトの finalized で動く。Pub/Sub の本文は ce.data.message.data に base64 で入っている
  • console.log は gcloud functions logs read で読める。エントリポイントの書き間違いはデプロイの失敗（is not defined in the provided module）、関数の中の例外は 500 とログの E 行になる

11.9確認問題

この章のコマンドを、自分で組み立てて確かめます。どの問題も、Cloud Functions API は有効で、関数の既定のリージョンは asia-northeast1 になっています。

問 1

HTTP 関数をデプロイする

正解済み

~/greet に、HTTP 関数の index.js と package.json が用意してあります。index.js は functions.http('greetUser', …) で関数を登録しています。

これを（index.js の中の名前と、関数の名前が違うことに注意）、関数の名前 greet、ランタイム nodejs22、HTTP のトリガーで、だれでも（トークンなしで）呼べるようにデプロイしてください。採点では、https://asia-northeast1-tsubame-shop.cloudfunctions.net/greet?name=… をトークンなしの curl で呼んだ結果と、関数のエントリポイントを調べます。

問 3

正解済み

~/ping に、Pub/Sub のメッセージで動くイベント関数を書いてデプロイし、メッセージを 1 つ publish してください。
