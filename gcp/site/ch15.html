BigQuery

何百万行の表でも、SQL を投げるだけで集計できるデータウェアハウス、BigQuery を使えるようにします。公開データセットを bq query で読み、料金を決める「処理したバイト数」を --dry_run で見積もり、列を絞る・パーティションで絞る・キャッシュを使うことで減らします。データセットの作成と CSV の読み込み、CTAS とビュー、DML、データのプロジェクトとジョブのプロジェクトが別だという権限の考え方、請求先のないサンドボックスまでを手で確かめます。

15.1BigQuery は何をするところか

BigQuery（ビッグクエリ）は、大量のデータを SQL で集計するためのサービスです。こうしたサービスをデータウェアハウス（分析用のデータの倉庫）と呼びます。サーバーを用意する必要はありません。テーブルにデータを入れて SQL を投げれば、Google の側で何台もの計算機が手分けして答えを返します。

第 14 章の Cloud SQL も SQL を使います。違いは得意なことです。Cloud SQL は「注文を 1 件ずつ書き込み、1 件ずつ読む」アプリの仕事に向きます。BigQuery は「1 年分の注文を月ごと・経路ごとに合計する」ような、たくさんの行をまとめて読む仕事に向きます。

BigQuery の入れ物は 3 段です。プロジェクトの中にデータセット（テーブルをまとめる入れ物。場所と権限の単位）があり、その中にテーブルとビューがあります。

この章では、つばめ文具が公開している練習用のデータ tsubame-public.bungu を使います。BigQuery には、Google や各団体がだれでも読めるように置いている公開データセットがあり、これはその模型です。中身は架空の販売データで、2026 年 1 月から 10 月までの注文が入っています。

コマンドは bq（ビーキュー）を使います。gcloud と同じく Cloud Shell に入っている、BigQuery 専用のコマンドです。

データセットとテーブルの一覧⌘↵
bq ls --project_id=tsubame-publicbq ls tsubame-public:bungu

1 つ目は tsubame-public のデータセットの一覧、2 つ目は bungu の中のテーブルの一覧です。orders の行には DAY (field: order_date) と channel が出ています。注文日で日ごとに分けてあり（パーティション）、経路で並べてある（クラスタ）という意味です。どちらも料金に関わるので、後の節で使います。

bq では、テーブルを プロジェクト:データセット.テーブル と書きます。SQL の中では ` プロジェクト.データセット.テーブル とバッククォートで囲み、すべて .` で区切ります。書き方が 2 通りあるのは歴史の名残です。

テーブルの形と、最初の数行⌘↵
bq show tsubame-public:bungu.ordersbq head -n 5 tsubame-public:bungu.orders

bq show の Schema が列の名前と型です。Total Rows が 2183 行、Total Bytes が 117079 バイトです。bq head は、SQL を使わずに最初の数行を見せます。本物では、bq head のようなテーブルのプレビューはクエリではないので、処理したバイト数の料金はかかりません（公式ドキュメントを参照）。

15.2bq query と、標準 SQL

SQL を投げるのは bq query です。注文の数を数えてみます。まず、よくある失敗から見ます。

フラグを付け忘れるエラーになる⌘↵
bq query 'SELECT COUNT(*) FROM `tsubame-public.bungu.orders`'

Invalid table name と出て、最後に [Try using standard SQL ...] とあります。テーブルの名前は正しいのに、なぜでしょうか。

bq の query は、何も指定しないとレガシー SQL（BigQuery の初期の独自の SQL）として読みます。レガシー SQL ではテーブルを [tsubame-public:bungu.orders] と書くので、バッククォートの名前が分からないのです。いまの SQL（GoogleSQL。以前は標準 SQL と呼ばれていました）で読ませるには、--use_legacy_sql=false を付けます。

GoogleSQL で数える⌘↵
bq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-public.bungu.orders`'

2183 が返りました。上の Waiting on bqjob_... Current status: DONE は、クエリが 1 つのジョブ（BigQuery に頼んだ仕事の単位）として実行されたという知らせです。ジョブには ID が付き、あとで記録を調べられます。

歴史レガシー SQL と GoogleSQL

BigQuery は、最初はレガシー SQL だけを使っていました。あとから、ほかのデータベースに近い標準の SQL が加わり、今はそちらが推奨です（名前は GoogleSQL になりました）。コンソールや SDK の既定は GoogleSQL ですが、bq query の既定は互換のためレガシー SQL のままです。本物では、ホームディレクトリの ~/.bigqueryrc に [query] と --use_legacy_sql=false を書いておくと、毎回付けずに済みます（このサイトの bq は ~/.bigqueryrc を読まないので、毎回付けます）。

月ごとに集計してみます。FORMAT_DATE は日付を文字列にする関数、COUNTIF は条件に合う行だけを数える関数です。どちらも GoogleSQL の関数です。

月ごとの注文数と売上⌘↵
bq query --use_legacy_sql=false 'SELECT FORMAT_DATE("%Y-%m", order_date) AS month, COUNT(*) AS orders, COUNTIF(channel = "web") AS web, SUM(quantity * unit_price) AS sales FROM `tsubame-public.bungu.orders` GROUP BY month ORDER BY month'

3 月と 4 月が多いのは、新学期の前だからでしょう。web の列は、Web の店からの注文の数です。GoogleSQL では文字列を "web" のように二重引用符でも書けるので、シェルの単一引用符の中に SQL を丸ごと入れられます。

SQL が長くなったら、ヒアドキュメント（<<'SQL' から SQL までを標準入力に渡す書き方）で渡すと読みやすくなります。bq query は、引数に SQL がなければ標準入力から読みます。

4 月のカテゴリ別の売上（テーブルを結合する）⌘↵
bq query --use_legacy_sql=false <<'SQL'SELECT p.category,       SUM(o.quantity * o.unit_price) AS salesFROM `tsubame-public.bungu.orders` AS oJOIN `tsubame-public.bungu.products` AS p USING (product_id)WHERE o.order_date BETWEEN '2026-04-01' AND '2026-04-30'GROUP BY p.categoryORDER BY sales DESCSQL

orders と products を product_id で結合しました。万年筆が 3,200 円と高いので、ペンの売上がいちばん大きくなっています。

メモこのサイトの GCP では

BigQuery の SQL は、GoogleSQL を DuckDB（ブラウザで動くデータベース）の SQL に書き換えて実行しています。この章で使った関数（COUNTIF、FORMAT_DATE、DATE_TRUNC、SAFE_DIVIDE、QUALIFY など）は動くことを確かめてあります。書き換えに対応していない書き方は、エラーになったり、本物と違う結果になったりすることがあります。

15.3料金は「読んだ列のバイト数」で決まる

BigQuery のオンデマンド料金（使った分だけ払う方式）は、クエリが処理したバイト数で決まります。返した行の数でも、かかった時間でもありません。そして、読むのはクエリで使った列だけです。これは、BigQuery がデータを列指向（列ごとにまとめて置く形）で持っているからです。

実行する前に、何バイト処理するかを知る方法があります。--dry_run（予行演習）を付けると、BigQuery はクエリを検査して、処理するバイト数だけを返します。実行はしないので、料金はかかりません。

SELECT * の見積もり。LIMIT を付けても変わらない⌘↵
bq query --use_legacy_sql=false --dry_run 'SELECT * FROM `tsubame-public.bungu.orders`'bq query --use_legacy_sql=false --dry_run 'SELECT * FROM `tsubame-public.bungu.orders` LIMIT 10'

どちらも 117079 バイトで、bq show の Total Bytes と同じです。SELECT * はすべての列を読むので、テーブル全体ぶんになります。

注意LIMIT では料金は減らない

LIMIT 10 は「結果を 10 行だけ返す」という意味で、読む量は減りません。列はまとめて読まれ、行を数えて止めることはしないからです。データの中身をのぞくだけなら、bq head を使うか、列を絞ります。

列を絞る。COUNT(*) は 0 バイト⌘↵
bq query --use_legacy_sql=false --dry_run 'SELECT channel, quantity FROM `tsubame-public.bungu.orders`'bq query --use_legacy_sql=false --dry_run 'SELECT COUNT(*) FROM `tsubame-public.bungu.orders`'

2 列だけにすると 29759 バイトになりました。4 分の 1 ほどです。COUNT(*) は 0 バイトです。行の数はテーブルの情報として持っているので、列を読まずに答えられます。

バイト数は、型ごとに決まった数え方で計算されます。INT64 と DATE は 1 つの値が 8 バイト、STRING は 2 バイトに UTF-8 のバイト数を足したものです。上の 29759 バイトは、次のように分けられます。

列型計算バイト数
quantityINT648 × 2183 行17464
channelSTRINGweb（2 + 3 = 5）× 1493 行 + store（2 + 5 = 7）× 690 行12295
合計29759

本物の料金は、US のリージョンで 1 TiB（約 1.1 兆バイト）あたり 6.25 ドルで、リージョンによって違います。毎月最初の 1 TiB は無料です。ただし、1 つのクエリで参照したテーブルごとに、最低 10 MB が課金されます。小さなテーブルを何度読んでも、1 回ごとに 10 MB ぶんとして数えられます。

使いすぎを止める：--maximum_bytes_billed

うっかり巨大なテーブルを SELECT * すると、1 回で大きな料金になります。--maximum_bytes_billed を付けると、課金されるバイト数がその値を超えるクエリは、実行せずに失敗させられます。試しに、上限を 100 万バイトにしてみます。

上限を超えるクエリは失敗するエラーになる⌘↵
bq query --use_legacy_sql=false --maximum_bytes_billed=1000000 'SELECT * FROM `tsubame-public.bungu.orders`'

Query exceeded limit for bytes billed: 1000000. 10485760 or higher required. と出ました。処理するのは 117079 バイトなのに、必要なのは 10485760 バイト（10 MB = 10 × 1024 × 1024）以上だと言っています。これが最低 10 MB の課金です。上限を 10485760 以上にすれば通ります。上限で止まったクエリには、料金はかかりません。

15.4パーティションとクラスタで、読む行を減らす

列を絞ると、読む「列」が減ります。読む「行」を減らすのがパーティションです。テーブルを、日付などの列の値で小さな区画（パーティション）に分けておきます。WHERE で区画を指定すれば、BigQuery はほかの区画を読みません。これをパーティションの刈り込み（プルーニング）と呼びます。

3 つの書き方で見積もりを比べます。

パーティションが効く書き方と、効かない書き方⌘↵
bq query --use_legacy_sql=false --dry_run 'SELECT channel, quantity FROM `tsubame-public.bungu.orders` WHERE order_date = "2026-03-15"'bq query --use_legacy_sql=false --dry_run 'SELECT order_id FROM `tsubame-public.bungu.orders` WHERE order_date BETWEEN "2026-03-01" AND "2026-03-31"'bq query --use_legacy_sql=false --dry_run 'SELECT order_id FROM `tsubame-public.bungu.orders` WHERE EXTRACT(MONTH FROM order_date) = 3'
  • 1 つ目は 172 バイトです。列を絞った 29759 バイトから、さらに 3 月 15 日の 8 行ぶんだけになりました。WHERE で使った order_date も読む列に入ります
  • 2 つ目は 4816 バイトです。3 月の 301 行 × （order_id と order_date の 8 + 8 バイト）です
  • 3 つ目は 34928 バイトで、2183 行全部を読んでいます。同じ「3 月」でも、列に関数をかけると区画を絞れません。日付の範囲で書くのがコツです

区画の様子は、データセットの INFORMATION_SCHEMA（テーブルの情報を SQL で読むための特別なビュー）で見られます。PARTITIONS は区画ごとの行数、COLUMNS は列の一覧です。

区画と列の情報⌘↵
bq query --use_legacy_sql=false 'SELECT table_name, partition_id, total_rows FROM `tsubame-public.bungu.INFORMATION_SCHEMA.PARTITIONS` ORDER BY partition_id LIMIT 3'bq query --use_legacy_sql=false 'SELECT column_name, data_type, is_partitioning_column, clustering_ordinal_position FROM `tsubame-public.bungu.INFORMATION_SCHEMA.COLUMNS` WHERE table_name = "orders"'

partition_id は 20260101 のような日付の文字列で、1 日に数行から十数行の注文があります。COLUMNS では、order_date の is_partitioning_column が YES、channel の clustering_ordinal_position が 1 です。

深掘りクラスタは、見積もりには出ない

クラスタは、区画の中の行を、指定した列（ここでは channel）の値の順に並べて保存しておく仕組みです。WHERE channel = "web" のように絞ると、BigQuery は関係のないブロックを読み飛ばせます。ただし、どれだけ読み飛ばせるかは実行してみないと分からないので、--dry_run の見積もりはクラスタの効果を含まない上限になります。実際に課金されたバイト数は、次の節の INFORMATION_SCHEMA.JOBS で確かめます（本物の細かい振る舞いは公式ドキュメントを参照）。このサイトの BigQuery は、クラスタで読む量を減らす計算はしていません。

15.5キャッシュと、ジョブの記録

同じクエリを 2 回実行すると、2 回目はキャッシュ（前の結果の保存）から返ります。テーブルが変わっていなければ、結果も同じはずだからです。キャッシュから返したクエリは、料金がかかりません。

同じクエリを 2 回。3 回目はキャッシュを使わない⌘↵
bq query --use_legacy_sql=false 'SELECT channel, SUM(quantity * unit_price) AS sales FROM `tsubame-public.bungu.orders` GROUP BY channel ORDER BY channel'bq query --use_legacy_sql=false 'SELECT channel, SUM(quantity * unit_price) AS sales FROM `tsubame-public.bungu.orders` GROUP BY channel ORDER BY channel'bq query --use_legacy_sql=false --nouse_cache 'SELECT channel, SUM(quantity * unit_price) AS sales FROM `tsubame-public.bungu.orders` GROUP BY channel ORDER BY channel'

3 回とも、結果は同じです。違いは、ジョブの記録を見ると分かります。--nouse_cache は「キャッシュを使わずに計算し直す」というフラグです。

ジョブの記録は、region-場所.INFORMATION_SCHEMA.JOBS というビューで読めます。ジョブはデータの場所（ここでは asia-northeast1）で実行されるので、その場所のビューを読みます。

最近のジョブ 3 つ⌘↵
bq query --use_legacy_sql=false 'SELECT statement_type, total_bytes_processed, total_bytes_billed, cache_hit FROM `region-asia-northeast1`.INFORMATION_SCHEMA.JOBS ORDER BY creation_time DESC LIMIT 3'bq ls -j -n 3

新しい順に並んでいます。いちばん上（3 回目、--nouse_cache）と、いちばん下（1 回目）は cache_hit が false で、total_bytes_billed が 10485760 です。処理したのは total_bytes_processed の 47223 バイトですが、最低の 10 MB が課金されています。真ん中（2 回目）は cache_hit が true で、課金は 0 です。

bq ls -j は、ジョブの一覧を bq の形で出します。どれも query の種類で、SUCCESS です。

コツ費用を確かめる習慣

大きなテーブルを読む前に --dry_run で見積もり、実行した後に INFORMATION_SCHEMA.JOBS の total_bytes_billed で確かめる。この 2 つを習慣にすると、料金で驚くことがなくなります。プロジェクト全体の使いすぎは、第 4 章の予算とアラートで見張ります。

15.6自分のデータセットを作り、CSV を読み込む

公開データは読めるだけです。自分の表を作るには、自分のプロジェクトにデータセットを作ります。データセットを作るときに大事なのは場所（--location）です。データセットの場所は、あとから変えられません。

データセットを 2 つ作る（場所を指定したものと、しないもの）⌘↵
bq mk --dataset --location=asia-northeast1 --description="つばめ文具の分析用" tsubame-shop:salesbq mk --dataset tsubame-shop:sales_usbq ls

sales は東京のリージョン（asia-northeast1）、sales_us は場所を指定しなかったので、既定の US（米国のマルチリージョン）にできます。データセットの名前に使えるのは英数字と _ だけで、- は使えません。

この章の準備最初の実行のときに、自動で流れるコマンド
cat > stores.csv <<'CSV'store_id,store_name,prefecture,opened_on1,渋谷店,東京都,2019-04-012,横浜店,神奈川県,2021-10-153,梅田店,大阪府,2023-03-20CSV

次に、手元の CSV ファイルを読み込みます。この章の準備で、店舗の一覧 stores.csv をホームディレクトリに置いてあります。読み込みは bq load です。--autodetect は列の型を中身から推測させるフラグ、--skip_leading_rows=1 は最初の 1 行（見出し）を飛ばすフラグです。

CSV を読み込む⌘↵
cat stores.csvbq load --source_format=CSV --autodetect --skip_leading_rows=1 sales.stores ./stores.csvbq show sales.stores

Upload complete. のあとに、読み込みのジョブが終わりました。bq show の Schema を見ると、store_id は integer、opened_on は date と、中身から型が判定されています。列の名前は見出しの行から取られました。型を自分で決めたいときは、--autodetect のかわりに store_id:INTEGER,store_name:STRING,... のようなスキーマを最後の引数に書きます。

自分のテーブルと公開データは、同じクエリで結合できます。店舗のある都道府県ごとに、顧客の数を数えます。

自分のテーブルと公開データを結合する⌘↵
bq query --use_legacy_sql=false 'SELECT s.store_name, COUNT(*) AS customers FROM sales.stores AS s JOIN `tsubame-public.bungu.customers` AS c ON s.prefecture = c.prefecture GROUP BY s.store_name ORDER BY customers DESC'

sales.stores のようにプロジェクトを省くと、いまのプロジェクト（tsubame-shop）のデータセットだと読まれます。渋谷店のある東京都の顧客がいちばん多く、27 人います。

では、US の sales_us に、公開データから表を作ろうとするとどうなるでしょうか。

場所の違うデータセットはまたげないエラーになる⌘↵
bq query --use_legacy_sql=false 'CREATE TABLE sales_us.products AS SELECT * FROM `tsubame-public.bungu.products`'

Not found: Dataset tsubame-public:bungu was not found in location US と出ました。データセットはあるのに「見つからない」と言われるのは、1 つのクエリ（ジョブ）が 1 つの場所で実行されるからです。US で動くジョブからは、asia-northeast1 のデータは見えません。公開データと組み合わせるデータセットは、同じ場所に作ります。

15.7CTAS、ビュー、DML

クエリの結果を、そのまま新しいテーブルにできます。CREATE TABLE ... AS SELECT の形で、頭文字を取って CTAS（シータス）と呼びます。日ごと・経路ごとの集計表を作り、PARTITION BY で日ごとのパーティションにしておきます。

CTAS で集計表を作る⌘↵
bq query --use_legacy_sql=false 'CREATE TABLE sales.daily PARTITION BY order_date AS SELECT order_date, channel, COUNT(*) AS orders, SUM(quantity * unit_price) AS sales FROM `tsubame-public.bungu.orders` GROUP BY order_date, channel'bq show sales.daily

Created tsubame-shop.sales.daily と出て、582 行のテーブルができました。元の 2183 行の注文が、304 日 × 2 経路（注文のなかった組を除く）にまとまっています。集計表を読むクエリは、元の注文を読むより処理するバイト数が少なくて済みます。

ビューは、SQL に名前を付けて保存したものです。データは持たず、読まれるたびに中の SQL が実行されます。月ごとの売上のビューを作ります。

ビューを作って読む⌘↵
bq query --use_legacy_sql=false 'CREATE VIEW sales.monthly AS SELECT DATE_TRUNC(order_date, MONTH) AS month, SUM(sales) AS sales FROM sales.daily GROUP BY month'bq ls salesbq query --use_legacy_sql=false 'SELECT * FROM sales.monthly ORDER BY month LIMIT 3'bq query --use_legacy_sql=false --dry_run 'SELECT month, sales FROM sales.monthly'

bq ls sales で、monthly の Type が VIEW になっています。DATE_TRUNC(order_date, MONTH) は日付を月の初日に切り詰める関数です。ビューを読むと、中の SQL が sales.daily を読みます。だから見積もりの 9312 バイトは、daily の order_date と sales の 2 列（8 + 8 バイト × 582 行）ぶんです。ビューにしても、料金は元のテーブルを読んだぶんだけかかります。

行を足したり書き換えたりするのは DML（データ操作言語。INSERT、UPDATE、DELETE など）です。BigQuery でも、ふつうの SQL と同じように書けます。

INSERT と UPDATE⌘↵
bq query --use_legacy_sql=false 'INSERT INTO sales.daily (order_date, channel, orders, sales) VALUES ("2026-11-01", "web", 12, 9800)'bq query --use_legacy_sql=false 'UPDATE sales.daily SET sales = sales + 200 WHERE order_date = "2026-11-01"'bq query --use_legacy_sql=false 'SELECT * FROM sales.daily WHERE order_date = "2026-11-01"'

Number of affected rows: 1 が、変わった行の数です。BigQuery は大量の行をまとめて読むのが得意な一方、1 行ずつの書き込みを何度も繰り返す使い方は向きません。注文が来るたびに 1 行足すなら、第 14 章の Cloud SQL か第 13 章の Firestore に書き、BigQuery にはまとめて読み込みます。

テーブルのコピーは bq cp、有効期限は bq update --expiration（秒）、削除は bq rm です。

コピー、有効期限、削除⌘↵
bq cp sales.daily sales.daily_backupbq update --expiration 3600 sales.daily_backupbq rm -r -f sales_usbq ls

daily_backup は 1 時間後に自動で消えます。bq rm は、-f で確認を省き、-r で中のテーブルごとデータセットを消します。bq ls に残ったのは sales だけです。

15.8権限：データのプロジェクトと、ジョブのプロジェクト

BigQuery の権限には、ほかのサービスにない特徴があります。データを読む権限と、クエリを実行する権限が、別のプロジェクトにあってよいのです。

  • ジョブを作る権限 bigquery.jobs.create：クエリを実行するプロジェクトに要ります。料金はこのプロジェクトの請求先に付きます。事前定義ロールでは roles/bigquery.jobUser がこれだけを持ちます
  • データを読む権限 bigquery.tables.getData：データのあるテーブルやデータセットに要ります。roles/bigquery.dataViewer が持ちます。公開データセット bungu には、allAuthenticatedUsers（ログインしている人すべて）に dataViewer が付いています

売上分析の馬場さん（bob@）で試します。bob は tsubame-shop に何のロールも持っていません。

bob に切り替える⌘↵
gcloud auth login bob@tsubame.example
データは読めるのに、クエリを実行できないエラーになる⌘↵
bq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-public.bungu.orders`'

Access Denied: Project tsubame-shop: User does not have bigquery.jobs.create permission in project tsubame-shop. と出ました。止められたのはデータ（tsubame-public）ではなく、ジョブのプロジェクト（tsubame-shop）です。公開データは bob でも読めますが、「どこのお金でクエリを動かすか」が決まっていないのです。

あなた（you@）に戻って、analysts グループにジョブの実行だけを許します。

analysts に roles/bigquery.jobUser を付ける⌘↵
gcloud auth login you@tsubame.examplegcloud projects add-iam-policy-binding tsubame-shop --member=group:analysts@tsubame.example --role=roles/bigquery.jobUser --format=nonegcloud auth login bob@tsubame.examplebq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-public.bungu.orders`'

今度は 2183 が返りました。では、bob は tsubame-shop の sales も読めるでしょうか。

ジョブは作れても、データセットは読めないエラーになる⌘↵
bq query --use_legacy_sql=false 'SELECT * FROM sales.monthly ORDER BY month LIMIT 3'

User does not have permission to query table tsubame-shop:sales.monthly, or perhaps it does not exist. です。jobUser はジョブを作れるだけで、データを読む権限は含みません。「それとも存在しないのかもしれない」と付いているのは、権限のない人にテーブルがあるかどうかを教えないためです。データセット sales に、analysts の dataViewer を付けます。

データセットに dataViewer を付ける⌘↵
gcloud auth login you@tsubame.examplebq add-iam-policy-binding --member=group:analysts@tsubame.example --role=roles/bigquery.dataViewer tsubame-shop:salesgcloud auth login bob@tsubame.examplebq query --use_legacy_sql=false 'SELECT * FROM sales.monthly ORDER BY month LIMIT 3'

bob が月ごとの売上を読めました。プロジェクト全体ではなく、データセット sales にだけ付けたので、bob はほかのデータセットを読めません。第 6 章の最小権限の考え方です。

請求先のないプロジェクト：BigQuery サンドボックス

請求先アカウント（第 4 章）がないプロジェクトでも、BigQuery は使えます。これを BigQuery サンドボックスと呼びます。クレジットカードを登録しなくても、無料枠の範囲でクエリを試せます。そのかわり、制限があります。テーブルは 60 日で期限切れになり、DML は使えません。

請求先のないプロジェクトで、データセットとテーブルを作る⌘↵
gcloud auth login you@tsubame.examplegcloud projects create tsubame-bq-sandbox --name="BigQuery の練習"bq --project_id=tsubame-bq-sandbox mk --dataset --location=asia-northeast1 labbq --project_id=tsubame-bq-sandbox query --use_legacy_sql=false 'CREATE TABLE lab.cats AS SELECT DISTINCT category FROM `tsubame-public.bungu.products`'

新しいプロジェクトには請求先を付けていませんが、データセットの作成も CTAS も通りました。--project_id で、ジョブを実行するプロジェクトを tsubame-bq-sandbox にしています。料金はかかりません。

サンドボックスでは DML が拒否されるエラーになる⌘↵
bq --project_id=tsubame-bq-sandbox query --use_legacy_sql=false 'INSERT INTO lab.cats (category) VALUES ("封筒")'

Billing has not been enabled for this project. と DML queries are not allowed in the free tier. が出ました。請求先がないので、DML は使えません。直し方はエラーの文のとおり、プロジェクトに請求先アカウントを付けることです（gcloud billing projects link、第 4 章）。

メモサンドボックスのデータセット

サンドボックスで作ったデータセットには、テーブルの既定の有効期限として 60 日（bq show --format=prettyjson の defaultTableExpirationMs が 5184000000 ミリ秒）が付きます。請求先を付けると制限は外れますが、それまでに作ったテーブルの期限は自分で外す必要があります（本物の手順は公式ドキュメントを参照）。

要点まとめ
  • BigQuery は列指向のデータウェアハウス。プロジェクト → データセット（場所と権限の単位）→ テーブル・ビューの 3 段
  • bq query には --use_legacy_sql=false を付ける。付け忘れると Invalid table name になる
  • 料金は処理したバイト数。読んだ列だけが数えられ、LIMIT では減らない。COUNT(*) は 0 バイト。参照したテーブルごとに最低 10 MB
  • --dry_run で見積もり、--maximum_bytes_billed で上限、INFORMATION_SCHEMA.JOBS の total_bytes_billed と cache_hit で実績を見る
  • パーティションの列を定数と比べると、読む区画が減る。列に関数をかけると効かない
  • データセットは --location を決めて作る。場所の違うデータセットは 1 つのクエリでまたげない
  • bq load --autodetect --skip_leading_rows=1 で CSV を読み込む。CTAS で結果を表に、ビューで SQL に名前を付ける
  • クエリには、ジョブのプロジェクトの bigquery.jobs.create（jobUser）と、データの bigquery.tables.getData（dataViewer）の両方が要る
  • 請求先のないプロジェクトはサンドボックス。クエリは使えるが、DML は拒否される

15.9確認問題

BigQuery のコマンドとクエリを、自分で書いて確かめます。問題の準備では、tsubame-shop に asia-northeast1 のデータセット sales と、公開データの注文の一部を写したテーブル sales.o（order_date で日ごとのパーティション）を作ってあります。

問 1

パーティションを効かせて見積もる

正解済み

テーブル sales.o から、2026 年 4 月 1 日から 4 月 30 日までの注文の customer_id だけを読むクエリを考えます。このクエリを --dry_run で検査し、処理するバイト数を表示してください（Query successfully validated. ... の 1 行が出れば OK です）。

bq query --use_legacy_sql=false --dry_run '...'
⌘↵標準出力で判定（行の順番も見る）
ヒント

WHERE order_date BETWEEN "2026-04-01" AND "2026-04-30" のように、パーティションの列を日付の定数と比べます。SELECT * にすると、すべての列を読むぶん大きくなります。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

bq mk --dataset --location=asia-northeast1 salesbq query --use_legacy_sql=false 'CREATE OR REPLACE TABLE sales.o PARTITION BY order_date AS SELECT * FROM `tsubame-public.bungu.orders` WHERE order_date < "2026-07-01"'
模範解答
bq query --use_legacy_sql=false --dry_run 'SELECT customer_id FROM sales.o WHERE order_date BETWEEN "2026-04-01" AND "2026-04-30"'
問 2

カテゴリ別の売上を CSV で

正解済み

テーブル sales.o と公開データの ` tsubame-public.bungu.products を product_id で結合し、カテゴリ（category）ごとの売上（quantity * unit_price の合計）を出してください。列は category と sales の 2 つ、売上の多い順に、--format=csv` で表示します。

bq query --use_legacy_sql=false --format=csv '...'
⌘↵標準出力で判定（行の順番も見る）
ヒント

JOIN ... USING (product_id) で結合し、GROUP BY p.category、ORDER BY sales DESC とします。列の名前は AS sales で付けます。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

bq mk --dataset --location=asia-northeast1 salesbq query --use_legacy_sql=false 'CREATE OR REPLACE TABLE sales.o PARTITION BY order_date AS SELECT * FROM `tsubame-public.bungu.orders` WHERE order_date < "2026-07-01"'
模範解答
bq query --use_legacy_sql=false --format=csv 'SELECT p.category, SUM(o.quantity * o.unit_price) AS sales FROM sales.o AS o JOIN `tsubame-public.bungu.products` AS p USING (product_id) GROUP BY p.category ORDER BY sales DESC'
問 3

CSV を読み込んでテーブルを作る

正解済み

ホームディレクトリの items.csv（1 行目が見出し）を、データセット sales のテーブル items に読み込んでください。列の型は中身から自動で判定させ、見出しの 1 行は飛ばします。

cat items.csv
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

bq load に --source_format=CSV、--autodetect、--skip_leading_rows=1 を付け、データセット.テーブル と ファイル の順に書きます。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

bq mk --dataset --location=asia-northeast1 salescat > items.csv <<'CSV'item_id,name,price,added_on1,つばめノート A5,280,2026-01-102,ボールペン 黒,120,2026-02-013,付箋 青,200,2026-03-05CSV

分析チームにクエリの実行を許す
