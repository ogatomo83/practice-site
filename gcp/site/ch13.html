Firestore

Firestore は、表ではなく「ドキュメント」と「コレクション」でデータを持つ、サーバーレスのデータベースです。データベースを gcloud で作り、Node の SDK で書いて読み、クエリとインデックス（複合インデックスのエラーの直し方）、サブコレクション、バッチとトランザクション、読み書きの回数で決まる料金までを、手を動かして身に付けます。

13.1Firestore は、表ではなく文書の木

Firestore（ファイアストア）は、Google Cloud のサーバーレスの NoSQL データベースです。NoSQL は「SQL の表を使わないデータベース」のまとめた呼び名です。サーバーを用意したり、容量を決めたりする必要はありません。使った読み書きの回数と、保存した量だけ料金がかかります。

Firestore のデータは、ドキュメント（文書）とコレクション（文書の入れ物）でできています。ドキュメントは「項目名と値」の組の集まりで、JSON のオブジェクトに近い形です。コレクションの中にドキュメントが並び、ドキュメントの下にまたコレクションを置けます。

リレーショナル データベース（第 14 章の Cloud SQL）と比べると、違いがはっきりします。

リレーショナル（Cloud SQL）Firestore
入れ物表（テーブル）コレクション
1 件行ドキュメント
形の決まり列を先に決める（スキーマ）決めない。文書ごとに項目が違ってよい
入れ子できない（別の表にして JOIN）地図（map）、配列、サブコレクション
結合（JOIN）できるできない。必要な値を文書に写しておく
読み方SQLSDK のメソッド（where、orderBy、limit）
料金インスタンスが動いている時間読み書きの回数と保存量

大事なのは最後の 2 行です。Firestore は SQL を持たず、クエリはインデックスで答えられる形のものだけが書けます。そのかわり、データが何倍に増えても、クエリの速さは「返す件数」だけで決まります。

13.2データベースを作る

Firestore を使うには、プロジェクトの中に データベース を 1 つ作ります。まず、何もしないで作ってみます。

API が無効なまま作るエラーになる⌘↵
gcloud firestore databases create --location=asia-northeast1

PERMISSION_DENIED: Cloud Firestore API has not been used in project 365600345236 before or it is disabled. と出ました。第 3 章で見た「API が無効」のエラーです。番号 365600345236 は tsubame-shop のプロジェクト番号です。API を有効にしてから、もう一度作ります。

API を有効にして、データベースを作る⌘↵
gcloud services enable firestore.googleapis.comgcloud firestore databases create --location=asia-northeast1

出力の response: の下が、できたデータベースです。見るところは 3 つです。

  • name: projects/tsubame-shop/databases/(default)：名前を付けないで作ると、(default) という名前になります。SDK は何も指定しないと、このデータベースにつなぎます
  • locationId: asia-northeast1：データを置く場所（東京）です。あとから変えられません。使う人やアプリの近くを選びます
  • type: FIRESTORE_NATIVE：ネイティブ モードのデータベースです（次の節）

describe で、いつでも同じ情報を見られます。

データベースの情報⌘↵
gcloud firestore databases describe --format="yaml(name,locationId,type,freeTier,concurrencyMode)"

freeTier: true は、このデータベースに無料枠が使われるという印です。無料枠は、プロジェクトの中の 1 つのデータベースにだけ付きます（料金は最後の節で扱います）。concurrencyMode: PESSIMISTIC はトランザクションのやり方で、7 節で意味が分かります。

ネイティブ モードと Datastore モード

--type で、データベースのモードを選べます。省略すると firestore-native（ネイティブ モード）です。

モード--type向いている使い方
ネイティブ モードfirestore-native新しく作るアプリ。Web やスマートフォンから直接読み書きでき、変更をすぐ受け取れる（リアルタイム更新）
Datastore モードdatastore-mode昔の Cloud Datastore の API を使うサーバーのアプリ。データの呼び方が違う（キンド、エンティティ）

1 つのプロジェクトに、名前を付けたデータベースを足せます。Datastore モードのものを 1 つ作って、並べて見ます。

Datastore モードのデータベースを足す⌘↵
gcloud firestore databases create --database=legacy --location=asia-northeast1 --type=datastore-mode --format="value(response.type)"gcloud firestore databases list --flatten=databases --format="table(databases.name.basename():label=DATABASE,databases.type,databases.locationId)"

(default) がネイティブ モード、legacy が Datastore モードで並びました。databases list の出力は databases: の下にリストが入る形なので、--flatten=databases で 1 つずつに分けてから表にしています。

データベースの名前は、英小文字、数字、- だけで 4〜63 文字です。Shop_Test のように大文字や _ を使うと、INVALID_ARGUMENT: Database ID 'Shop_Test' is not valid. で断られます。

歴史Datastore と Firestore

App Engine（2008 年）の時代から、Google には Cloud Datastore という NoSQL のデータベースがありました。そのあと、Firebase（スマートフォン アプリ向けの開発基盤）の流れから Firestore が生まれ、Datastore はその中の「Datastore モード」になりました。いまの Datastore モードは、中身は Firestore で、外から見える API だけが昔の Datastore の形です。

13.3SDK で書いて読む

Firestore のデータは、gcloud では読み書きしません。アプリのコードから、クライアント ライブラリ（SDK。言語ごとの部品）を通して読み書きします。この章では、Node.js 用の @google-cloud/firestore を使います。Cloud Shell でファイルを書き、node ファイル.js で実行します。

メモこのサイトの GCP では

本物の Cloud Shell では、最初に npm install @google-cloud/firestore で SDK を入れます。このサイトの node には、はじめから入っています。認証は、Cloud Shell にログインしている人（you@）の資格情報（第 5 章の ADC）がそのまま使われます。変更をすぐ受け取る onSnapshot はありません。

最初のプログラムは、文書を 1 つ書いて、読み戻すだけです。cat > ファイル <<'EOF' から EOF までが、ファイルの中身です（ヒアドキュメント）。

1 つ書いて、1 つ読む⌘↵
cat > hello.js <<'EOF'const { Firestore } = require('@google-cloud/firestore');const db = new Firestore();async function main() {  const ref = db.collection('products').doc('pen-001');  await ref.set({ name: 'ボールペン 黒', price: 120, stock: 50 });  const snap = await ref.get();  console.log(snap.id, snap.exists, snap.data());}main();EOFnode hello.js

pen-001 true { name: 'ボールペン 黒', price: 120, stock: 50 } と出ました。プログラムの中身はこうです。

  • new Firestore()：いまのプロジェクト（tsubame-shop）の (default) データベースにつなぐ
  • db.collection('products').doc('pen-001')：文書への参照（場所を指すもの）を作る。この時点では、まだ通信していない
  • ref.set({...})：文書を書く。なければ作り、あれば丸ごと置き換える
  • ref.get()：文書を読む。結果はスナップショット（その時点の写し）で、exists で、あったかどうかが分かる

コレクションは、先に作る必要がありません。products に最初の文書を書いた瞬間に、コレクションが現れます。「クラウドを見る」の木で、Firestore のデータベースの文書の数が 1 になっています。

Datastore モードのデータベースにつなぐと

SDK の databaseId で、つなぐデータベースを選べます。さきほど作った legacy（Datastore モード）を選んでみます。

legacy につなぐプログラム⌘↵
cat > legacy.js <<'EOF'const { Firestore } = require('@google-cloud/firestore');const db = new Firestore({ databaseId: 'legacy' });db.collection('products').doc('pen-001').get().then((s) => console.log(s.exists));EOF
Datastore モードには、Firestore の SDK でつなげないエラーになる⌘↵
node legacy.js

9 FAILED_PRECONDITION: The Cloud Firestore API is not available for Firestore in Datastore Mode database と出ました。先頭の 9 FAILED_PRECONDITION は、gRPC（SDK と Google の間の通信のやり方）のエラーの番号と名前で、「前提の条件が満たされていない」という意味です。Datastore モードのデータベースは、Datastore 用の SDK（@google-cloud/datastore）で使います。モードは作るときに選び、使い始めたら変えないものと考えてください。

自動の ID で足す add、一部だけ書き換える update

注文のように ID に意味がない文書は、add で足します。Firestore が 20 文字の ID を決めます。また、set は文書を丸ごと置き換えるので、一部の項目だけを変えるときは update を使います。FieldValue には、読まずに書き換える便利な印があります。

注文を足し、在庫を減らし、タグを足す⌘↵
cat > order.js <<'EOF'const { Firestore, FieldValue } = require('@google-cloud/firestore');const db = new Firestore();async function main() {  const o = await db.collection('orders').add({ item: 'pen-001', qty: 2, at: FieldValue.serverTimestamp() });  console.log(o.id.length, o.path);  const ref = db.doc('products/pen-001');  await ref.update({    stock: FieldValue.increment(-2),    tags: FieldValue.arrayUnion('pen', 'black'),    updated: FieldValue.serverTimestamp(),  });  await ref.update({ tags: FieldValue.arrayUnion('black', 'office') });  const d = (await ref.get()).data();  console.log(d.stock, d.tags, d.updated.toDate().toISOString());}main();EOFnode order.js

出力の読み方です。

  • 20 orders/…：自動の ID は 20 文字。時刻の順ではなく、ばらばらに散るように作られる（同じ場所に書き込みが集中しないため）
  • 48：increment(-2) で 50 から 2 減った。読んでから書くのではなくサーバーで足し算するので、2 人が同時に減らしても数が狂わない
  • [ 'pen', 'black', 'office' ]：arrayUnion は、まだ入っていない値だけを配列に足す。2 回目の black は重ならなかった
  • 最後の時刻：serverTimestamp() は「書き込んだときのサーバーの時刻を入れて」という印。アプリの計算機の時計がずれていても、時刻がそろう。updated は元の文書になかった項目だが、update で足せる

update は、文書がないと失敗します。ない文書を書き換えてみます。

ない文書を update するプログラム⌘↵
cat > missing.js <<'EOF'const { Firestore } = require('@google-cloud/firestore');const db = new Firestore();db.doc('products/pen-999').update({ stock: 1 });EOF
ない文書は update できないエラーになる⌘↵
node missing.js

5 NOT_FOUND: No document to update: の後ろに、文書の完全な名前（projects/…/databases/(default)/documents/products/pen-999）が出ます。ID の打ち間違いを疑います。「なければ作り、あれば一部だけ変える」ときは、set(データ, { merge: true }) を使います。

13.4クエリで探す

ここからは、商品をいくつか入れて探します。seed.js は、まず前の節の pen-001 を delete で消し、読んで確かめてから、6 件を書きます。

商品を 6 件入れる⌘↵
cat > seed.js <<'EOF'const { Firestore } = require('@google-cloud/firestore');const db = new Firestore();const items = [  ['pen-001', 'ボールペン 黒', 'pen', 120, 50],  ['pen-002', 'ボールペン 赤', 'pen', 150, 8],  ['pen-003', '万年筆', 'pen', 3200, 3],  ['note-001', 'ノート A5', 'note', 180, 40],  ['note-002', 'ノート B5', 'note', 220, 0],  ['tape-001', 'マスキングテープ', 'tape', 260, 25],];async function main() {  await db.doc('products/pen-001').delete();  const gone = await db.doc('products/pen-001').get();  console.log('消した後：', gone.exists, gone.data());  for (const [id, name, category, price, stock] of items) {    await db.collection('products').doc(id).set({ name, category, price, stock });  }  console.log(`${items.length} 件を書きました`);}main();EOFnode seed.js

消した後： false undefined の行に注目します。ない文書を読んでもエラーにはならず、exists が false、data() が undefined になります。そのあと、set で 6 件を書きました。

クエリ（条件で文書を探すこと）は、コレクションに where（条件）、orderBy（並べ替え）、limit（件数）をつないで、最後に get() で実行します。

等号、範囲、並べ替え、件数⌘↵
cat > query.js <<'EOF'const { Firestore } = require('@google-cloud/firestore');const db = new Firestore();const products = db.collection('products');async function main() {  const pens = await products.where('category', '==', 'pen').get();  console.log('pen：', pens.size, '件', pens.docs.map((d) => d.id));  const cheap = await products.where('price', '<', 200).orderBy('price').get();  cheap.forEach((d) => console.log('200 円未満', d.id, d.get('price')));  const top = await products.orderBy('price', 'desc').limit(2).get();  top.forEach((d) => console.log('高い順', d.id, d.get('price')));}main();EOFnode query.js

結果は文書のスナップショットの集まりで、size が件数、docs が文書の配列です（forEach でも 1 つずつ取り出せます）。

  • 1 つ目：category が pen の 3 件。並びを指定しないと、文書の ID の順になる
  • 2 つ目：price < 200 の 3 件が、安い順に出た
  • 3 つ目：全体を高い順に並べ、上から 2 件（pen-003 3200 円、tape-001 260 円）だけを取った

where で使える比べ方は、==、!=、<、<=、>、>= と、配列の中を探す array-contains、いくつかの値のどれかに当たる in などです。SQL の LIKE のような「部分一致」はありません。

13.5インデックス：単一は自動、複合は自分で作る

ここで、Firestore でいちばんよく見るエラーを出します。「pen の商品を、高い順に」です。

等号と並べ替えを組み合わせるプログラム⌘↵
cat > q-pen-desc.js <<'EOF'const { Firestore } = require('@google-cloud/firestore');const db = new Firestore();async function main() {  const snap = await db.collection('products').where('category', '==', 'pen').orderBy('price', 'desc').get();  snap.forEach((d) => console.log(d.id, d.get('price')));}main();EOF
複合インデックスがないエラーになる⌘↵
node q-pen-desc.js

9 FAILED_PRECONDITION: The query requires an index. と出ました。前の節のクエリは通ったのに、なぜでしょう。理由は、Firestore のクエリの答え方にあります。

Firestore は、クエリの答えをインデックス（項目の値で並べた目次）から、ひと続きに切り出して返します。表を端から全部読んで探すことはしません。だから、データが何百万件あっても、10 件を返すクエリは 10 件ぶんの手間で済みます。

  • 単一フィールドのインデックス：すべての項目について、昇順と降順（と配列の array-contains 用）のものが自動で作られる。1 つの項目だけで絞る・並べるクエリは、これで答えられる
  • 複合インデックス：2 つ以上の項目を組み合わせた並び。「category が同じものの中で、price の順」という並びは、category だけ、price だけの目次からは、ひと続きに切り出せない。自分で作る

エラーの文を読む

エラーの文は、次のように読みます。

  • 9 FAILED_PRECONDITION：前提（インデックス）が足りない
  • The query requires an index.：このクエリに合う複合インデックスがない
  • You can create it here: https://console.firebase.google.com/…?create_composite=…：このリンクを開くと、必要なインデックスが入力された状態の作成画面が開く。create_composite= の後ろは、プロジェクト、コレクション、項目の並びを符号にしたもの

コンソールを使わずに、gcloud で同じものを作れます。項目の並べ方は「等号で絞る項目を先に、並べ替え（範囲）の項目を後に」です。

複合インデックスを作る⌘↵
gcloud firestore indexes composite create --collection-group=products --field-config=field-path=category,order=ascending --field-config=field-path=price,order=descendinggcloud firestore indexes composite list --format="table(name.segment(-3):label=COLLECTION_GROUP,state,fieldsText:label=FIELDS)"

--collection-group が対象のコレクションの名前、--field-config を項目の数だけ並べます。一覧の STATE が READY なら使えます。本物では、作り始めてから READY になるまで、データの量に応じて数分かかることがあります（その間は CREATING）。

同じクエリを、もう一度⌘↵
node q-pen-desc.js

今度は通りました。pen の 3 件が、3200 円、150 円、120 円の順に出ています。等号と範囲の組み合わせ（「pen で、在庫が 10 未満」）も、同じように複合インデックスが要ります。確認問題で試します。

なお、1 つの項目だけの複合インデックスは作れません（Composite indexes must have at least 2 fields. Single field indexes are managed automatically. と断られます）。単一フィールドのものは自動で管理されるからです。

コツインデックスはコードと一緒に管理する

本物の開発では、必要な複合インデックスを firestore.indexes.json などのファイルに書き、Firebase CLI や Terraform でまとめて作ることが多いです。開発の環境でクエリを試し、エラーに出たインデックスをファイルに足していく、という流れです。

13.6サブコレクション：文書の下のコレクション

ドキュメントの下には、サブコレクションを置けます。「顧客 c001 の注文」のように、ある文書に属するデータをまとめるのに使います。

顧客の下に注文を置く⌘↵
cat > sub.js <<'EOF'const { Firestore } = require('@google-cloud/firestore');const db = new Firestore();async function main() {  const c = db.collection('customers').doc('c001');  await c.set({ name: '山田 花子', city: '札幌' });  await c.collection('orders').doc('o1').set({ total: 480 });  await c.collection('orders').doc('o2').set({ total: 1200 });  const orders = await c.collection('orders').get();  orders.forEach((d) => console.log(d.ref.path, d.get('total')));  console.log((await c.get()).data());  console.log((await db.listCollections()).map((x) => x.id));}main();EOFnode sub.js

見るところは 3 つです。

  • 注文のパスは customers/c001/orders/o1。コレクションとドキュメントが交互に並ぶ
  • 顧客の文書を読んでも、出るのは name と city だけ。サブコレクションは文書の中身ではないので、親を読んでも子は付いてこない（読み取りの回数も増えない）
  • いちばん上のコレクションは customers、orders、products。サブコレクションの orders は、トップの orders（3 節の add で作ったもの）とは別物

文書の中に配列で持つか、サブコレクションにするかは、最後の節で考えます。なお、親の文書を消しても、サブコレクションの文書は消えずに残ります。すべての顧客の注文を横断して探すには コレクション グループ クエリ（db.collectionGroup('orders')）を使います。

13.7バッチとトランザクション

注文を受けたら、「注文の文書を作る」と「在庫を減らす」の 2 つを書きます。片方だけ成功すると、在庫と注文が合わなくなります。Firestore には、いくつかの書き込みを全部成功か、全部なしにする方法が 2 つあります。

  • バッチ（一括書き込み）：書き込みだけを集めて、まとめて送る。読む必要がないときに使う
  • トランザクション：読んで、その値で判断してから書く。読んだ文書が途中でほかの人に変えられないようにする

まずバッチです。わざと、2 つ目の書き込みが失敗するようにします。

バッチは、1 つ失敗すると全部なし⌘↵
cat > batch.js <<'EOF'const { Firestore } = require('@google-cloud/firestore');const db = new Firestore();async function main() {  const b = db.batch();  b.set(db.doc('products/pen-004'), { name: 'シャープペン', category: 'pen', price: 300, stock: 10 });  b.update(db.doc('products/pen-999'), { stock: 1 });  try { await b.commit(); } catch (e) { console.log('失敗:', e.message.slice(0, 30)); }  console.log('pen-004 はあるか:', (await db.doc('products/pen-004').get()).exists);}main();EOFnode batch.js

pen-999 の update が NOT_FOUND で失敗し、同じバッチの pen-004 の set も書かれませんでした（false）。バッチは、送った書き込みを 1 つの単位として扱います。

次はトランザクションです。在庫を読み、足りるときだけ減らして、注文を作ります。

サーバー向けの SDK のトランザクションは、読んだ文書をロック（ほかの人が書けないように押さえること）します。describe で見た concurrencyMode: PESSIMISTIC（悲観的な同時実行制御）が、このやり方です。

在庫を減らすトランザクション⌘↵
cat > buy.js <<'EOF'const { Firestore, FieldValue } = require('@google-cloud/firestore');const db = new Firestore();async function buy(id, qty) {  const ref = db.collection('products').doc(id);  return db.runTransaction(async (t) => {    const snap = await t.get(ref);    const stock = snap.get('stock');    if (stock < qty) throw new Error(`在庫が足りません：${id} は残り ${stock}`);    t.update(ref, { stock: stock - qty });    t.create(db.collection('orders').doc(), { item: id, qty, at: FieldValue.serverTimestamp() });    return stock - qty;  });}async function main() {  for (const n of [1, 2]) {    try { console.log(`${n} 回目：残り`, await buy('pen-003', 2)); } catch (e) { console.log(`${n} 回目：`, e.message); }  }  const orders = await db.collection('orders').where('item', '==', 'pen-003').get();  console.log('pen-003 の注文：', orders.size, '件');}main();EOFnode buy.js

1 回目は在庫 3 から 2 を引いて 残り 1。2 回目は 在庫が足りません で、トランザクションの関数が例外を投げました。このときは何も書かれないので、注文は 1 件だけです。

トランザクションの書き方には決まりが 2 つあります。

  1. 読む（t.get）のを全部先に、書く（t.update、t.create）のを後に。 書いた後に読むと、SDK がエラーにする
  2. 関数は何度か呼ばれることがある。 本物では、ぶつかり合いがあると SDK が関数を最初からやり直す。だから関数の中で、画面に出す、メールを送る、といった「やり直されると困ること」をしない

13.8料金とデータの形

Firestore の料金は、主に次の 3 つで決まります。

  • 読み取り、書き込み、削除の回数：1 文書を読むと 1 回。クエリは「返した文書の数」だけ読み取りになる
  • 保存量：文書と、そのインデックスの大きさ
  • 外へ出したデータの量

無料枠（freeTier: true のデータベース 1 つ）は、ストレージ 1 GiB、1 日あたり読み取り 50,000 回・書き込み 20,000 回・削除 20,000 回、外向きの転送が月 10 GiB です。小さなアプリなら、この中に収まります。

この章のプログラムで数えてみます。query.js の 1 つ目のクエリは 3 件を返したので読み取り 3 回、seed.js は書き込み 6 回です。気を付けたいのは、画面を開くたびにコレクションを全部読むような作りです。1,000 件の商品を毎回全部読むと、50 回開いただけで 1 日の無料枠を使い切ります。必要なのが一部なら limit で区切り、件数だけが欲しいなら count()（集計のクエリ。(await q.count().get()).data().count）を使います。count() は、本物では文書を全部読むよりずっと少ない読み取りで数えられます（数え方は公式の料金のページを参照）。

データの形は、読み方から決める

リレーショナル データベースでは、データを重複なく分けて（正規化）、読むときに JOIN でつなげます。Firestore には JOIN がないので、考え方が逆になります。「どの画面で、何をまとめて読むか」から形を決め、そのために値を写して持つのがふつうです。

注文の明細は、注文の画面でいつも一緒に読み、注文の後に増えることもありません。だから注文の文書の中に配列で持ちます。商品名も明細に写しておきます。後で商品名が変わっても、注文したときの名前が残るので、むしろ都合がよいです。

明細と商品名を、注文の文書に写して持つ⌘↵
cat > model.js <<'EOF'const { Firestore, FieldValue } = require('@google-cloud/firestore');const db = new Firestore();async function main() {  const p = (await db.doc('products/note-001').get()).data();  const ref = db.doc('customers/c001/orders/o3');  const b = db.batch();  b.set(ref, { items: [{ id: 'note-001', name: p.name, price: p.price, qty: 3 }], total: p.price * 3 });  b.update(db.doc('customers/c001'), { orderCount: FieldValue.increment(1) });  b.update(db.doc('products/note-001'), { stock: FieldValue.increment(-3) });  await b.commit();  console.log((await ref.get()).data());  console.log((await db.doc('customers/c001').get()).get('orderCount'));}main();EOFnode model.js

1 回の読み取りで、明細と商品名と合計がそろう文書ができました。顧客の文書には、注文の数（orderCount）を increment で持たせています。「注文が何件か」を、毎回数えずに 1 回の読み取りで出すためです。

形を決めるときの目安です。

  • 一緒に読むものは、1 つの文書に入れる。 写した値は、変わったときに直す手間と引き換え
  • 増え続けるもの（注文、ログ、コメント）は、サブコレクションか別のコレクションにする。 1 つの文書の大きさには上限があり、全部を 1 つに詰めると、いずれ入らなくなる
  • 1 つの文書に、たくさんの人が同時に書き込む作りを避ける。 1 文書への書き込みの速さには限りがある（数値は公式ドキュメントを参照）
  • 先にクエリを決める。 どの where と orderBy を使うかが決まれば、必要な複合インデックスも決まる
注意使わないデータベースは消す

読み書きがなくても、保存量の料金はかかります。試しに作ったデータベースは消しておきましょう。gcloud firestore databases delete --database=名前 で消せます。消すと中の文書もすべてなくなります。

試しに作った legacy を消す⌘↵
gcloud firestore databases delete --database=legacy --quiet --format="value(name)"gcloud firestore databases list --flatten=databases --format="value(databases.name.basename())"

残ったのは (default) だけです。

要点まとめ
  • Firestore はサーバーレスの NoSQL データベース。データはコレクションとドキュメントの木で、パスは products/pen-001 のように書く
  • gcloud firestore databases create --location=… でデータベースを作る。場所は後から変えられない。モードはネイティブ（firestore-native）と Datastore（datastore-mode）で、Firestore の SDK はネイティブ モードにだけつながる
  • 読み書きは SDK で行う。set（丸ごと）、add（自動 ID）、update（一部。increment、arrayUnion、serverTimestamp）、delete、get
  • クエリは where、orderBy、limit。単一フィールドのインデックスは自動、等号と並べ替え・範囲の組み合わせには複合インデックスが要る。エラーが出たら indexes composite create で、等号の項目を先に並べて作る
  • 全部成功か全部なしにするには、バッチ（書くだけ）かトランザクション（読んでから書く）
  • 料金は読み書きの回数と保存量。データの形は、画面でどう読むかから決める
