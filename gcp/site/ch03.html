第 3 章

リージョン、ゾーン、API

Google Cloud のリソースは、どこか 1 つの「場所」に置かれます。リージョン・ゾーン・マルチリージョンの違いと、障害やデータの所在地との関係を押さえ、gcloud config で既定の場所と本番・開発の設定を切り替え、サービスを使う前に必要な「API の有効化」と、そのときに出るエラーを読めるようにします。

3.1リージョンとゾーン：リソースを置く場所

Google Cloud の計算機は、世界のあちこちにあるデータセンターに並んでいます。VM やバケットを作るときは、どこに置くかを選びます。その「どこ」を表す単位が、リージョンとゾーンです。

  • リージョン（region）：地理的な地域です。asia-northeast1 は東京、asia-northeast2 は大阪です。名前は「大陸や地域 + 方角 + 番号」の形をしています
  • ゾーン（zone）：リージョンの中の、互いに独立した区画です。電源、冷却、ネットワークが分かれています。名前はリージョンの後ろに -a -b のような文字を付けたものです
  • グローバル：場所を選ばないリソースもあります。プロジェクト、IAM、VPC ネットワーク（第 9 章）などです

まず一覧を出してみる

リージョンの一覧は gcloud compute regions list で出せます。打ってみましょう。

リージョンの一覧（まだ失敗する）エラーになる⌘↵
gcloud compute regions list

失敗しました。エラーの文は Compute Engine API has not been used in project 365600345236 before or it is disabled. です。「このプロジェクトでは、Compute Engine の API がまだ使われていないか、無効になっている」という意味です。

Google Cloud では、サービスごとの API（プログラムから操作するための窓口）を、プロジェクトごとに有効にしてから使います。リージョンとゾーンの一覧は Compute Engine の API が答えるので、それが無効だと一覧も出ません。仕組みはこの章の後半で説明します。いまは有効にしてしまいます。

Compute Engine API を有効にする⌘↵
gcloud services enable compute.googleapis.com

Operation "operations/acf.…" finished successfully. と出れば、有効になりました。もう一度、一覧を出します。

リージョンの一覧⌘↵
gcloud compute regions list

NAME の列がリージョンの名前です。asia-northeast1（東京）と asia-northeast2（大阪）が、日本にあるリージョンです。CPUS の 0/24 は、このプロジェクトがそのリージョンでいま使っている vCPU の数と、使ってよい上限（割り当て、quota）です。STATUS が UP なら、そのリージョンは動いています。

メモこのサイトの GCP では

小さな GCP にあるリージョンは 15 個だけです。本物にはもっと多くのリージョンがあり、今も増えています（最新の一覧は公式ドキュメントの「リージョンとゾーン」を参照）。割り当ての数字も、模型の値です。

ゾーンは、リージョンの中にいくつかある

ゾーンの一覧は gcloud compute zones list です。全部だと長いので、--filter で東京のリージョンだけに絞ります。

東京のゾーン⌘↵
gcloud compute zones list --filter="region:asia-northeast1"gcloud compute regions describe asia-northeast1 --format="yaml(name,status,zones)"

東京には asia-northeast1-a、-b、-c の 3 つのゾーンがあります。regions describe の zones にも、同じ 3 つが並んでいます。ゾーンは、どれか 1 つのリージョンに必ず属します。

ゾーンの文字は、いつも a から順とは限りません。アイオワのリージョンを見てみます。

アイオワのゾーンと、全体の数⌘↵
gcloud compute zones list --filter="region:us-central1" --format="value(name)"gcloud compute regions list --format="value(name)" | wc -lgcloud compute zones list --format="value(name)" | wc -l

us-central1 のゾーンは a、b、c、f です。ゾーンの名前は「並び順」ではなく、ただの名札だと考えてください。小さな GCP の全体では、リージョンが 15、ゾーンが 46 あります。1 つのリージョンに、ゾーンはふつう 3 つ以上あります。

3.2障害の範囲：ゾーン、リージョン、マルチリージョン

ゾーンを分けてあるのは、障害を閉じ込めるためです。ある建物の電源が落ちても、同じリージョンのほかのゾーンは動き続けるように作られています。だから「どの範囲に置いたか」で、「どの障害に耐えられるか」が決まります。

リソースには、それぞれ「どの範囲のものか」が決まっています。この本で使うものを並べると、次のとおりです。

範囲例作るときに指定するもの
ゾーンVM（Compute Engine）、ふつうの永続ディスク--zone
リージョンCloud Run のサービス、Cloud Run functions、サブネット、Cloud SQL のインスタンス、静的な外部 IP--region
リージョン / デュアルリージョン / マルチリージョンCloud Storage のバケット、BigQuery のデータセット--location
グローバルプロジェクト、IAM、VPC ネットワーク、ファイアウォールのルール（なし）
  • マルチリージョン：ASIA、EU、US のような大きな地域です。その中の複数のリージョンにデータを持つので、1 つのリージョンが止まっても読めます
  • デュアルリージョン：決まった 2 つのリージョンの組です。たとえば ASIA1 は東京と大阪の組です

VM のようなゾーンのリソースで止まらないサービスを作るには、別々のゾーンに 2 台以上置くのが基本です。リージョンのリソース（Cloud Run など）は、Google が複数のゾーンに散らして動かしてくれます。

深掘り近いほうが速い：レイテンシ

場所は、障害だけでなく速さにも効きます。東京の利用者から見ると、東京のリージョンの VM は数ミリ秒で返事が来ますが、アイオワのリージョンでは、光が太平洋を往復する時間がかかります。さらに、リージョンをまたぐ通信や、インターネットへ出ていく通信（外向きの転送）は、料金がかかることがあります。利用者の近くに、そして互いに話すリソースどうしは同じリージョンに置くのが、基本の考え方です。

3.3データの所在地：場所は後から変えにくい

場所を選ぶ理由は、もう 1 つあります。データをどの国に置くかです。会社の決まりや法律で「顧客のデータは国内に置く」と決まっていることがあります。そのときは、データを持つリソースを日本のリージョンに作ります。

つばめ文具の注文データは、日本の中に置くことにします。試しに、場所の違うバケットを 2 つ作ってみます（バケットの詳しい話は第 7 章です）。

東京のバケットと、アジアのマルチリージョンのバケット⌘↵
gcloud storage buckets create gs://tsubame-shop-ch03-tokyo --location=asia-northeast1gcloud storage buckets create gs://tsubame-shop-ch03-asia --location=asiagcloud storage buckets list --format="table(name,location)"

LOCATION の列を見てください。tsubame-shop-ch03-tokyo は ASIA-NORTHEAST1（東京のリージョンだけ）、tsubame-shop-ch03-asia は ASIA（アジアの複数のリージョン）です。「データを国内に置く」という決まりがあるなら、ASIA は選べません。アジアの、日本以外のリージョンにもデータが置かれるからです。

場所の名前を書き間違えると、作る前に断られます。

場所の名前の間違いエラーになる⌘↵
gcloud storage buckets create gs://tsubame-shop-ch03-x --location=tokyo

Invalid location: TOKYO は「そういう場所はない」という意味です。場所は、都市名ではなく asia-northeast1 のようなリージョンの名前か、asia のようなマルチリージョンの名前で書きます。

注意場所は、作った後に変えられない

バケットや BigQuery のデータセットの場所は、作るときに決まり、後から変更できません。変えたいときは、新しい場所にもう 1 つ作って、データをコピーし直すことになります。作る前に、どこに置くかを決めておきましょう。

3.4gcloud config：既定のプロジェクトと場所

ゾーンのリソースを作るたびに --zone=asia-northeast1-b と打つのは面倒です。gcloud には、よく使う値をプロパティ（設定の項目）として覚えさせておく仕組みがあります。それが gcloud config です。

いまの設定と、既定のリージョンとゾーン⌘↵
gcloud config listgcloud config get-value compute/regiongcloud config set compute/region asia-northeast1gcloud config set compute/zone asia-northeast1-b

config list の [core] の下に account と project があります。これまで --project を付けなくても tsubame-shop が操作できたのは、ここに書いてあったからです。プロパティは セクション/名前 で呼びます。project は core/project、既定のリージョンは compute/region、既定のゾーンは compute/zone です。

get-value compute/region は (unset)（設定されていない）と答えました。set すると Updated property [compute/region]. と出ます。これで、--region や --zone を省いた gcloud のコマンドは、東京のリージョンの asia-northeast1-b を使います。

設定を確かめる⌘↵
gcloud config listgcloud config get compute/zone

[compute] のセクションが増えました。config get と config get-value は、どちらも 1 つのプロパティの値を出します（get は新しい名前です）。core/ は省けるので、gcloud config get-value project とも書けます。

プロパティの名前を間違えると、set は受け付けません。

プロパティの名前の間違いエラーになる⌘↵
gcloud config set compute/zonee asia-northeast1-a

Section [compute] has no property [zonee]. は「compute のセクションに zonee という項目はない」という意味です。名前を直して打ち直します。

消すときは unset です。

既定のゾーンを消す⌘↵
gcloud config unset compute/zonegcloud config get-value compute/zone

Unset property [compute/zone]. の後、get-value はまた (unset) に戻りました。既定のリージョン（compute/region）は残してあります。

コツ優先順位：フラグ ＞ 設定

コマンドに --project や --zone を付けると、そのコマンドだけは設定よりフラグが優先されます。設定は「書かなかったときの値」です。ふだんは設定に任せ、別のプロジェクトを 1 回だけ触るときに --project を付ける、という使い分けをします。

3.5構成（configurations）で本番と開発を切り替える

設定のまとまりを、gcloud は構成（configuration）と呼びます。いままで使っていたのは default という名前の構成です。構成は何個でも作れて、1 つだけが有効（active）になります。本番用と開発用の構成を作っておけば、1 行で丸ごと切り替えられます。

いまある構成の一覧を見てから、開発用の構成 dev を作ります。

構成の一覧と、開発用の構成を作る⌘↵
gcloud config configurations listgcloud config configurations create devgcloud config list

最初の一覧では default が 1 つだけで、IS_ACTIVE が True です。COMPUTE_DEFAULT_REGION に、さっき決めた asia-northeast1 が見えます。続く create で Created [dev]. と Activated [dev]. の 2 行が出ました。作った構成は、すぐに有効になります。config list は空で、Your active configuration is: [dev] とだけ出ます。プロンプトのかっこも消えました。新しい構成には、account も project もまだないからです。

開発用のプロジェクト tsubame-shop-dev を作り、dev の構成に値を入れます。開発は大阪のリージョンで試すことにします。

dev の構成に値を入れる⌘↵
gcloud config set account you@tsubame.examplegcloud projects create tsubame-shop-dev --name="つばめ文具 開発"gcloud config set project tsubame-shop-devgcloud config set compute/region asia-northeast2

プロンプトが (tsubame-shop-dev) に変わりました。プロジェクトの作り方は第 2 章で見たとおりです。ここで作った tsubame-shop-dev には、まだ請求先アカウントがつながっていません。この点は最後の節で効いてきます。

2 つの構成を並べる⌘↵
gcloud config configurations listgcloud config configurations describe dev

dev の行の IS_ACTIVE が True になり、PROJECT と COMPUTE_DEFAULT_REGION が default と違う値になっています。describe で、1 つの構成の中身を YAML で見られます。

本番に戻すのは 1 行です。

default に戻す⌘↵
gcloud config configurations activate defaultgcloud config get-value projectgcloud config get-value compute/region

project は tsubame-shop、compute/region は asia-northeast1 に戻りました。account、project、compute/region を 1 つずつ戻す必要はありません。

ない構成を指定すると、切り替えは失敗します。

ない構成を有効にするエラーになる⌘↵
gcloud config configurations activate prod

Cannot activate configuration [prod], it does not exist. です。構成の名前は configurations list で確かめます。名前は英小文字で始め、英小文字・数字・ハイフンだけで付けます。

注意本番で打つつもりのないコマンドを、本番で打たない

構成の切り替えは便利ですが、「いまどの構成か」を忘れると、開発のつもりで本番のリソースを消すことになります。Cloud Shell のプロンプトのかっこに出るプロジェクトを、コマンドを打つ前に見る習慣を付けましょう。消すコマンドには、--project をはっきり書くのも安全な方法です。

3.6API の有効化：services list / enable / disable

最初の節で、Compute Engine の API が無効だったために一覧が出ませんでした。Google Cloud のどのサービスも、操作は API（compute.googleapis.com のような名前の窓口）への呼び出しです。そして呼び出しは、サービスに届く前に、いくつかの関門を通ります。

API を有効にするのは、プロジェクトごとの「このサービスを使います」という宣言です。使わないサービスは無効のままにしておけば、間違って動かすことも、そこから料金が発生することもありません。

有効な API の一覧

有効になっている API⌘↵
gcloud services list

gcloud services list は、いまのプロジェクトで有効な API を並べます（--enabled を付けたのと同じです）。NAME が API の名前、TITLE が表示名です。最初の節で有効にした compute.googleapis.com があり、bigquery.googleapis.com や storage.googleapis.com のように、新しいプロジェクトで最初から有効になっているものもあります。oslogin.googleapis.com（VM へのログインの API）は、Compute Engine の API と一緒に有効になったものです。この「一緒に有効になる」仕組みは、この節の後半で見ます。

有効にできる API を探すときは --available です。

有効にできる API を探す⌘↵
gcloud services list --available --filter="config.title~SQL"

表示名に SQL を含む API が 2 つ出ました。Cloud SQL（第 14 章）を使うときに有効にするのは、sqladmin.googleapis.com のほうです。

無効な API を呼ぶと

Pub/Sub（第 12 章）の API は、まだ有効にしていません。トピックの一覧を出してみます。

無効な API を呼ぶエラーになる⌘↵
gcloud pubsub topics list

エラーの文を、前から読みます。

  • PERMISSION_DENIED：断られた、という大まかな種類です。権限のエラーと同じ言葉ですが、続きを読むと理由が違います
  • Cloud Pub/Sub API has not been used in project 365600345236 before or it is disabled.：理由はこれです。API が無効です
  • Enable it by visiting https://console.developers.google.com/…：直し方です。コンソールで有効にするか、gcloud services enable で有効にします
Pub/Sub の API を有効にする⌘↵
gcloud services enable pubsub.googleapis.comgcloud pubsub topics list

今度は Listed 0 items.（0 件でした）と返ってきました。トピックはまだないので 0 件ですが、エラーではありません。

メモ有効にしてから効くまで

エラーの文の最後に If you enabled this API recently, wait a few minutes … とあるとおり、本物では、有効にしてから使えるようになるまで数分かかることがあります。有効にした直後に同じエラーが出たら、少し待ってから打ち直します。このサイトの GCP では、すぐに使えます。

API は、プロジェクトごとに有効にする

有効にしたのは tsubame-shop の API です。--project で別のプロジェクトを指すと、そちらでは無効のままです。

別のプロジェクトでは無効のままエラーになる⌘↵
gcloud compute zones list --project=tsubame-public

エラーの中のプロジェクト番号が 214441484921（tsubame-public）に変わっています。エラーが出たら、まずどのプロジェクトの話かを、この番号で確かめます。

API の名前を間違えると

ない API を有効にするエラーになる⌘↵
gcloud services enable foo.googleapis.com

Not found or permission denied for service(s): foo.googleapis.com. は「その API が見つからないか、権限がない」です。理由の欄（reason）は SERVICE_CONFIG_NOT_FOUND_OR_PERMISSION_DENIED です。たいていは名前の書き間違いなので、gcloud services list --available で正しい名前を確かめます。

一緒に有効になる API と、無効にするとき

API の中には、ほかの API を使って動くものがあります。たとえば Cloud Run functions（cloudfunctions.googleapis.com）は、Cloud Run、Cloud Build、Artifact Registry などの上で動きます。有効にすると、それらも一緒に有効になります。

Cloud Run functions の API を有効にする⌘↵
gcloud services enable cloudfunctions.googleapis.comgcloud services list --enabled --format="value(config.name)"

cloudfunctions.googleapis.com のほかに、run.googleapis.com、cloudbuild.googleapis.com、artifactregistry.googleapis.com、eventarc.googleapis.com が増えました。1 つ有効にしただけで、依存する API が並びます。

逆に、ほかの API が頼っている API は、そのままでは無効にできません。

頼られている API を無効にするエラーになる⌘↵
gcloud services disable run.googleapis.com

The service run.googleapis.com is depended on by the following active service(s): cloudfunctions.googleapis.com は「Cloud Run の API には、有効な Cloud Run functions の API が頼っている」という意味です。頼っている側も一緒に無効にしてよいなら --force を付けます。ここでは、頼っている側から無効にします。

頼っている側から無効にする⌘↵
gcloud services disable cloudfunctions.googleapis.comgcloud services disable run.googleapis.com

どちらも finished successfully. で終わりました。API を無効にすると、その API で作ったリソースが使えなくなることがあります。本物で無効にするのは、そのサービスを使っていないと確かめてからにしましょう。

3.7請求先がないと有効にできない API

関門の ② は、請求先アカウント（料金を払う先）です。Compute Engine のように使った分だけ料金がかかるサービスは、プロジェクトに請求先がつながっていないと、API を有効にすることさえできません。さっき作った開発用のプロジェクトで試します。

請求先のないプロジェクトで Compute Engine を有効にするエラーになる⌘↵
gcloud config configurations activate devgcloud services enable compute.googleapis.com

エラーの文を読みます。

  • FAILED_PRECONDITION：前提の条件を満たしていない、という種類です。権限の問題ではありません
  • Billing account for project '…' is not found.：このプロジェクトには請求先アカウントがありません
  • Billing must be enabled for activation of service(s) 'compute.googleapis.com' to proceed.：Compute Engine を有効にするには、請求先が必要です
  • reason: UREQ_PROJECT_BILLING_NOT_FOUND：理由を短く表した名前です。検索するときはこれを使います

請求先の状態は、gcloud billing projects describe で確かめられます。

請求先の状態と、請求先なしで有効にできる API⌘↵
gcloud billing projects describe tsubame-shop-dev --format="value(billingEnabled)"gcloud services enable iam.googleapis.com

billingEnabled は False です。それでも IAM の API（iam.googleapis.com）は有効にできました。料金のかからない API は、請求先がなくても有効にできます。

請求先アカウントをプロジェクトにつなぐ方法（gcloud billing projects link）、料金の仕組み、予算の立て方は第 4 章で扱います。ここでは本番の構成に戻しておきます。

本番の構成に戻す⌘↵
gcloud config configurations activate defaultgcloud config configurations list

default の IS_ACTIVE が True に戻りました。

要点まとめ
  • リージョンは地域（asia-northeast1 は東京）、ゾーンはその中の独立した区画（asia-northeast1-b）。グローバルなリソース（プロジェクト、IAM、VPC）もある
  • 置いた範囲で、耐えられる障害が決まる。ゾーンのリソース（VM）は別のゾーンに 2 台以上、データはマルチリージョンやデュアルリージョンも選べる
  • バケットやデータセットの場所は後から変えられない。データを置く国の決まりも考えて選ぶ
  • gcloud config set / get-value / unset / list で既定の値を決める。compute/region と compute/zone。フラグは設定より優先される
  • gcloud config configurations create / activate / list で、本番と開発の設定を丸ごと切り替える
  • サービスを使う前に、プロジェクトごとに gcloud services enable で API を有効にする。無効だと has not been used … or it is disabled、請求先がないと Billing account … is not found

3.8確認問題

この章のコマンドを、自分で組み立ててみます。

問 1

既定のリージョンのゾーン

正解済み

Compute Engine の API は有効で、compute/region に既定のリージョンが設定されています。いま設定されている既定のリージョンにあるゾーンの名前を、1 行に 1 つずつ表示してください（名前だけ）。

# ここにコマンドを書く
⌘↵標準出力で判定（行の順番も見る）
ヒント

ゾーンの一覧は gcloud compute zones list、絞り込みは --filter="region:リージョン"、名前だけなら --format="value(name)" です。リージョンの名前は $(gcloud config get-value compute/region) で取り出せます。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud services enable compute.googleapis.comgcloud config set compute/region asia-northeast1
模範解答
gcloud compute zones list --filter="region:$(gcloud config get-value compute/region)" --format="value(name)"
問 2

開発用の構成を作る

正解済み

次のような構成 dev を作ってください。

  • account は you@tsubame.example
  • project は tsubame-public
  • compute/region は asia-northeast2

最後に、default の構成を有効に戻してください。採点では、gcloud config configurations list で構成の名前・有効か・アカウント・プロジェクト・リージョンを調べます。

# ここにコマンドを書く
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

configurations create で作った構成は、すぐに有効になります。その後の config set は、dev に書き込まれます。

確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

gcloud config configurations list --format="value(name,is_active,properties.core.account,properties.core.project,properties.compute.region)"
模範解答
gcloud config configurations create devgcloud config set account you@tsubame.examplegcloud config set project tsubame-publicgcloud config set compute/region asia-northeast2gcloud config configurations activate default
問 3

有効な API の数

正解済み

いまのプロジェクトで Compute Engine の API（compute.googleapis.com）を有効にしてから、有効になっている API の数を、数字だけで表示してください。

# ここにコマンドを書く
⌘↵標準出力で判定（行の順番も見る）
ヒント

gcloud services list の表には見出しの行があるので、そのまま wc -l で数えると 1 つ多くなります。--format="value(config.name)" で名前だけにしてから数えます。有効にした API に依存する API も、一緒に有効になることを思い出してください。

模範解答
gcloud services enable compute.googleapis.comgcloud services list --enabled --format="value(config.name)" | wc -l
