第 12 章

Pub/Sub

注文を受けた API が、発送・請求・在庫の処理を待たずに返事をするには、間に「伝言板」を置きます。Pub/Sub のトピックとサブスクリプションを作り、publish、pull、確認応答（ack）を自分の手で回して、期限が切れると同じメッセージがもう一度届く「少なくとも 1 回の配信」、ファンアウト、フィルタ、デッドレター、Cloud Run への push、Node の SDK までを確かめます。

12.1なぜ間に Pub/Sub を置くのか

つばめ文具の注文 API は、注文を受けると、発送の手配、請求、在庫の引き当ての 3 つを動かします。いちばん素直な作りは、API がこの 3 つを順に呼ぶことです。でもこの作りでは、請求の仕組みが止まると注文 API もエラーを返します。発送が遅いと、お客さんは画面の前で待たされます。新しく「メールを送る」処理を足すたびに、注文 API の書き換えも要ります。呼ぶ側と呼ばれる側が、強く結び付いているのです。

そこで、間に Pub/Sub（パブサブ。publish / subscribe、「出す」と「購読する」の略）を置きます。注文 API は「注文が入った」というメッセージを Pub/Sub に置くだけで、すぐにお客さんへ返事をします。発送・請求・在庫は、それぞれ自分の都合のよいときにメッセージを取りに来ます。

このように、送る側と受ける側が同じ瞬間に動いていなくてもよい連携を、非同期（ひどうき）の連携と呼びます。請求の仕組みが止まっていても、メッセージは Pub/Sub が預かっています。直ったときに、たまっていた分を取りに来れば済みます。Pub/Sub の料金は主にやりとりしたメッセージの量で決まり、無料枠は毎月 10 GiB です。

12.2トピックとサブスクリプションを作る

Pub/Sub には、2 種類の入れ物があります。

  • トピック（topic）：メッセージの宛先の名前です。送る側（パブリッシャー）は、トピックにメッセージを出します。トピック自体はメッセージをためません
  • サブスクリプション（subscription）：トピックに付ける「受け取り口」です。トピックに届いたメッセージは、そのトピックのサブスクリプションごとにコピーされ、受け取られるまでたまります。受ける側をサブスクライバーと呼びます

この章の準備（push の節の折りたたみ）で Cloud Build の API を有効にしたとき、Cloud Build が使う Pub/Sub の API（pubsub.googleapis.com）も一緒に有効になっています。第 3 章で見た、API の「依存」です。

有効になっていないプロジェクトで使うと、どうなるかも見ておきます。--project で、プロジェクト tsubame-public を指定します。

API が有効になっていないプロジェクトエラーになる⌘↵
gcloud pubsub topics list --project=tsubame-public

Cloud Pub/Sub API has not been used in project 214441484921 before or it is disabled とあります。214441484921 は tsubame-public のプロジェクト番号です。このプロジェクトで使うなら、gcloud services enable pubsub.googleapis.com --project=tsubame-public で有効にします。

tsubame-shop で、トピックを作ります。

トピックを作って、一覧と詳しい情報を見る⌘↵
gcloud pubsub topics create ordersgcloud pubsub topics listgcloud pubsub topics describe orders

Created topic [projects/tsubame-shop/topics/orders]. と出ました。トピックの正式な名前は projects/プロジェクト/topics/名前 の形です。コマンドでは名前（orders）だけを書けば、いまのプロジェクトのものとして扱われます。同じ名前のトピックは、1 つのプロジェクトに 1 つしか作れません。

同じ名前でもう一度作るエラーになる⌘↵
gcloud pubsub topics create orders

Resource already exists in the project (resource=orders). が理由です。2 行目の Failed to create the following: [orders]. は、いくつかまとめて作ったときに、どれが失敗したかの一覧です。

次に、発送の係が使うサブスクリプション shipping を作ります。どのトピックに付けるかを --topic で指定します。

サブスクリプションを作る⌘↵
gcloud pubsub subscriptions create shipping --topic=ordersgcloud pubsub subscriptions describe shipping

describe の出力で、いまは次の 3 つを見ておきます。

項目値意味
topicprojects/tsubame-shop/topics/ordersどのトピックの受け取り口か
ackDeadlineSeconds10確認応答の期限（秒）。次の次の節で使う
pushConfig{}空なら pull（受ける側が取りに来る）。push は後の節で扱う

messageRetentionDuration: 604800s は、受け取られないメッセージを何秒預かるかです。604800 秒は 7 日です。付ける先のトピックがないと、サブスクリプションは作れません。

トピックの名前を間違えるエラーになる⌘↵
gcloud pubsub subscriptions create billing --topic=order

Resource not found (resource=order). の order は、サブスクリプションではなくトピックの名前です。「付ける先のトピック order が見つからない」と読みます。

12.3publish して pull する

メッセージを出すのは gcloud pubsub topics publish です。本文は --message に、本文とは別の小さな「名札」は --attribute に キー=値 で書きます。名札は 属性（attributes）と呼び、カンマで区切っていくつでも付けられます。

メッセージを 2 つ出す⌘↵
gcloud pubsub topics publish orders --message='{"order":1001}' --attribute=shop=tokyo,channel=webgcloud pubsub topics publish orders --message='{"order":1002}' --attribute=shop=osaka

messageIds に出る数字が、Pub/Sub が付けた メッセージ ID です。出した側はこれで終わりです。受ける側がいるかどうかを待ちません。

受け取るのは gcloud pubsub subscriptions pull です。何も付けないと、1 件だけ受け取ります。

1 件だけ受け取る⌘↵
gcloud pubsub subscriptions pull shipping

pull の表の読み方

結果は、┌ から ┘ までの罫線で囲んだ表で出ます。1 行が 1 件のメッセージです。属性が 2 つ以上あると、1 件が 2 行以上に折り返されます。上の例では、shop=tokyo と channel=web が縦に並んでいますが、これで 1 件です。罫線が横に引かれるのは、見出しの下と表の最後だけです。

列意味
DATA本文（--message に書いたもの）
MESSAGE_IDpublish したときに出たメッセージ ID と同じ番号
ORDERING_KEY順序指定キー。この章では使わないので空
ATTRIBUTES属性。1 つが 1 行
DELIVERY_ATTEMPT何回目の配信か。デッドレターを設定したサブスクリプションでだけ数字が入る
ACK_ID確認応答の ID。「受け取って、処理を済ませた」と Pub/Sub に伝えるときに使う

ACK_ID は、次の節の主役です。ACK_ID の列があるということは、まだ確認応答をしていない、という意味でもあります。

--limit で、一度に受け取る数の上限を決められます。--auto-ack を付けると、受け取ったその場で確認応答も済ませます。

まとめて受け取り、その場で確認応答する⌘↵
gcloud pubsub subscriptions pull shipping --limit=5 --auto-ack

上限は 5 件なのに、出てきたのは {"order":1002} の 1 件だけです。最後の列も ACK_ID ではなく ACK_STATUS に変わり、SUCCESS（確認応答に成功した）と出ています。

1001 はどこへ行ったのでしょう。1 つ前の pull で受け取ったまま、まだ確認応答をしていません。Pub/Sub は「いま、だれかが処理している途中」とみなして、ほかの pull には渡さないのです。

12.4確認応答の期限：同じメッセージがもう一度届く

Pub/Sub は、メッセージを渡しただけでは消しません。受ける側が 確認応答（ack、アック。acknowledge の略）を返したときに、はじめて消します。決めた時間のうちに確認応答が来なければ、「受け手が処理の途中で倒れた」とみなして、もう一度配ります。この時間が確認応答の期限（ack deadline）で、既定は 10 秒です。

1001 を受け取ってから、もう 10 秒以上たっています。もう一度 pull してみます。sleep 11 は「11 秒待つ」コマンドです。

期限が過ぎてから、もう一度 pull する⌘↵
sleep 11gcloud pubsub subscriptions pull shipping

{"order":1001} がまた届きました。MESSAGE_ID は最初の pull と同じです。ACK_ID は、最初の pull のときとは途中の 1 文字が変わっています（…MTox… が …MToy… に）。確認応答の ID は、配るたびに新しく付け直されます。古い ACK_ID で確認応答しても、いまの配信には効きません。

今度は、受け取った ACK_ID を変数に入れて、gcloud pubsub subscriptions ack で確認応答します。--format="value(ackId)" を付けると、表ではなく ACK_ID だけが出ます。

ACK_ID を取り出して確認応答する⌘↵
sleep 11ACK=$(gcloud pubsub subscriptions pull shipping --format="value(ackId)")echo $ACKgcloud pubsub subscriptions ack shipping --ack-ids=$ACK

ack の出力の ackIds に、確認応答した ID が並びます。これで 1001 は消えたはずです。期限が過ぎるまで待って、確かめます。

確認応答したメッセージは、もう届かない⌘↵
sleep 11gcloud pubsub subscriptions pull shipping

Listed 0 items. は「0 件だった」という意味です。表は出ません。ack には、どれに確認応答するかを必ず指定します。

ACK_ID を付け忘れるエラーになる⌘↵
gcloud pubsub subscriptions ack shipping

argument --ack-ids: Must be specified. は「--ack-ids という引数が要る」という意味です。フラグの間違いは終了ステータス 2 で終わり、Usage: から正しい書き方が続きます。

期限は、サブスクリプションを作るときに --ack-deadline=60 のように変えられます。決められる範囲は 10 秒から 600 秒です。処理に時間がかかる受け手は、期限を長くしておきます。

注意同じメッセージを 2 回受けても困らない作りにする

Pub/Sub の配信は、少なくとも 1 回（at-least-once）です。「必ず届く。ただし 2 回以上届くこともある」という約束で、「ちょうど 1 回」ではありません。受け手が処理を終えた直後、ack を返す前に倒れれば、同じ注文がもう一度届きます。

だから受け手は、同じメッセージを 2 回処理しても結果が変わらないように作ります。たとえば「注文番号ごとに、発送済みかを記録しておき、済んでいたら何もせずに ack する」。このような性質を 冪等（べきとう）と呼びます。最後の節で、Node で書いてみます。

12.5ファンアウトとフィルタ

1 つのトピックには、いくつでもサブスクリプションを付けられます。トピックに届いたメッセージは、サブスクリプションごとに 1 通ずつ コピーされます。これを ファンアウト（fan-out、扇形に広がる）と呼びます。

請求の係のサブスクリプション billing を足します。足したらすぐに pull してみます。

2 つ目のサブスクリプションを作って pull する⌘↵
gcloud pubsub subscriptions create billing --topic=ordersgcloud pubsub subscriptions pull billing

Listed 0 items. です。1001 と 1002 は、billing を作る前に出したメッセージでした。サブスクリプションが受け取るのは、作った後にトピックに届いたメッセージだけです。作る前のメッセージは、さかのぼって届きません。トピックにサブスクリプションが 1 つもないときに出したメッセージは、だれにも届かずに捨てられます。新しく 1 つ出すと、今度は両方に届きます。

1 通出すと、両方に 1 通ずつ届く⌘↵
gcloud pubsub topics publish orders --message='{"order":1003}' --attribute=shop=tokyogcloud pubsub subscriptions pull shipping --auto-ackgcloud pubsub subscriptions pull billing --auto-ackgcloud pubsub topics list-subscriptions orders

同じ MESSAGE_ID が、shipping と billing の両方に出ました。shipping で確認応答しても、billing の分は消えません。サブスクリプションごとに、別々に ack します。list-subscriptions は、トピックに付いているサブスクリプションの一覧です。

フィルタ：属性で受け取るものを選ぶ

東京店の在庫だけを扱う係は、大阪店の注文を受け取っても捨てるだけです。サブスクリプションに フィルタ を付けると、条件に合うメッセージだけがそのサブスクリプションに入ります。条件には属性を使い、attributes.キー = "値" と書きます。書き方を間違えると、作るときに止まります。

shop が tokyo のメッセージだけを受け取るサブスクリプション⌘↵
gcloud pubsub subscriptions create tokyo-only --topic=orders --message-filter='attributes.shop = "tokyo"'gcloud pubsub subscriptions describe tokyo-only --format="value(filter)"
attributes. を付け忘れるエラーになる⌘↵
gcloud pubsub subscriptions create bad-filter --topic=orders --message-filter='shop = "tokyo"'

Invalid filter expression. は「フィルタの式として読めない」という意味です。フィルタが見られるのは属性だけで、attributes. で始めます。本文（data）の中身では選べません。東京と大阪の注文を 1 つずつ出して、tokyo-only に何が入ったかを見ます。

tokyo の注文だけが入る⌘↵
gcloud pubsub topics publish orders --message='{"order":1004}' --attribute=shop=tokyogcloud pubsub topics publish orders --message='{"order":1005}' --attribute=shop=osakagcloud pubsub subscriptions pull tokyo-only --limit=10 --auto-ack

--limit=10 で 10 件まで受け取れるのに、出たのは {"order":1004} だけです。1005 はフィルタで外され、tokyo-only には最初から入っていません。フィルタのないサブスクリプション（shipping、billing）には、1004 と 1005 の両方が届いています。

コツ属性に何を入れるか

フィルタで使いたい値（店、種類、版など）は、本文の JSON の中だけでなく、属性にも入れておきます。受け手が本文を開かなくても振り分けられ、フィルタで外されたメッセージの分は、受け取る手間もかかりません。

12.6何度やっても処理できないメッセージ：デッドレター

本文が壊れている注文が 1 つ紛れ込むと、受け手は処理できずに ack を返しません。期限が切れるたびに同じメッセージがまた届き、いつまでも繰り返されます。こういうメッセージを、決めた回数だけ配ったら別のトピックへ移すのが デッドレター（dead letter、配達できない手紙）です。移す先を デッドレタートピック と呼びます。

配る回数の上限は --max-delivery-attempts で決めます。決められるのは 5 回から 100 回です。

上限を 3 回にするエラーになる⌘↵
gcloud pubsub subscriptions create stock --topic=orders --dead-letter-topic=orders-dead --max-delivery-attempts=3

Value must be greater than or equal to 5 and less than or equal to 100. は「5 以上 100 以下にしてください」です。5 回にして作ります。移す先のトピック orders-dead と、その中を見るためのサブスクリプション dead-check も作ります。

デッドレターを設定したサブスクリプションを作る⌘↵
gcloud pubsub topics create orders-deadgcloud pubsub subscriptions create dead-check --topic=orders-deadgcloud pubsub subscriptions create stock --topic=orders --dead-letter-topic=orders-dead --max-delivery-attempts=5gcloud pubsub topics add-iam-policy-binding orders-dead --member=serviceAccount:service-365600345236@gcp-sa-pubsub.iam.gserviceaccount.com --role=roles/pubsub.publishergcloud pubsub subscriptions add-iam-policy-binding stock --member=serviceAccount:service-365600345236@gcp-sa-pubsub.iam.gserviceaccount.com --role=roles/pubsub.subscriber

作ったときの知らせに書いてあるとおり、メッセージを移す作業は、Pub/Sub のサービスエージェント（第 5 章。Google がプロジェクトごとに用意するサービスアカウント）service-プロジェクト番号@gcp-sa-pubsub.iam.gserviceaccount.com が行います。そのため、デッドレタートピックへの publish と、元のサブスクリプションからの受け取りの 2 つの権限を、このアカウントに与えます。

壊れた注文を 1 つ出して、ack を返さずに pull を繰り返します。--format="value(deliveryAttempt)" は、何回目の配信かだけを出します。

ack せずに 6 回 pull して、デッドレターの側を見る⌘↵
gcloud pubsub topics publish orders --message='{"order":"???"}'for i in 1 2 3 4 5 6; do gcloud pubsub subscriptions pull stock --format="value(deliveryAttempt)"; sleep 11; donegcloud pubsub subscriptions pull dead-check --auto-ack

1 から 5 まで数えた後、6 回目は Listed 0 items. です。5 回配っても ack が来なかったので、Pub/Sub はこのメッセージを stock から外し、orders-dead へ移しました。

dead-check で受け取ったメッセージには、元の本文のほかに CloudPubSubDeadLetterSource… で始まる属性が付いています。どのサブスクリプションで（…Subscription=stock）、何回配って（…DeliveryCount=5）、いつ出されたものか（…TopicPublishTime）が分かります。デッドレタートピックにたまったものは、人が中身を調べ、受け手のバグを直してから出し直します。

12.7push：Pub/Sub から Cloud Run へ届けてもらう

ここまでは、受ける側が pull で取りに行きました。逆に、Pub/Sub の側から受ける側の URL へ HTTP の POST で届けてもらうこともできます。これを push と呼びます。受け手が Cloud Run（第 10 章）のように、HTTP のリクエストで起きるサービスなら、push が向いています。

この節の準備（すぐ下の折りたたみ）で、メールを送る係のサービス mailer を Cloud Run にデプロイしてあります。第 10 章と同じ、ソースからのデプロイです。--no-allow-unauthenticated を付けたので、だれでも呼べるわけではありません。

この章の準備最初の実行のときに、自動で流れるコマンド
gcloud services enable run.googleapis.com cloudbuild.googleapis.com artifactregistry.googleapis.comgcloud config set run/region asia-northeast1mkdir -p ~/mailercat > ~/mailer/package.json <<'EOF'{ "name": "mailer", "main": "server.js", "scripts": { "start": "node server.js" }, "dependencies": { "express": "^4.21.0" } }EOFcat > ~/mailer/server.js <<'EOF'const express = require('express');const app = express();app.use(express.json());// Pub/Sub の push は、メッセージを JSON にして POST してくるapp.post('/', (req, res) => {  const m = req.body.message;  const data = Buffer.from(m.data, 'base64').toString();  console.log(`受け取った：${data} (${m.messageId})`);  res.status(204).send();});app.listen(process.env.PORT || 8080);EOFgcloud run deploy mailer --source ~/mailer --no-allow-unauthenticated --quiet

受け手の本体は server.js です。Pub/Sub の push は、{"message": {"data": "…", "messageId": "…", "attributes": {…}}, "subscription": "…"} という形の JSON を POST します。data は base64（バイト列を英数字で表す書き方）なので、Buffer.from(m.data, 'base64') で元に戻しています。204 を返すと、Pub/Sub はそれを確認応答とみなします。200 番台以外を返したり、応答しなかったりすると、失敗として後でもう一度送ります。

mailer を呼べるのは、roles/run.invoker（Cloud Run の起動元）を持つ相手だけです。push のためのサービスアカウントを作り、このロールを与えます。

push 用のサービスアカウントに、呼び出す権限を与える⌘↵
gcloud iam service-accounts create pubsub-push --display-name="Pub/Sub の push"gcloud run services add-iam-policy-binding mailer --member=serviceAccount:pubsub-push@tsubame-shop.iam.gserviceaccount.com --role=roles/run.invoker --format="value(bindings[0].role)"

push のサブスクリプションは、--push-endpoint に URL を、--push-auth-service-account に、そのとき名乗るサービスアカウントを指定して作ります。Pub/Sub はこのアカウントの ID トークン（第 10 章）を付けて POST するので、mailer は「pubsub-push からの呼び出し」として受け入れます。

push のサブスクリプションを作る⌘↵
URL=$(gcloud run services describe mailer --format="value(status.url)")gcloud pubsub subscriptions create mail --topic=orders --push-endpoint=$URL --push-auth-service-account=pubsub-push@tsubame-shop.iam.gserviceaccount.comgcloud pubsub subscriptions describe mail --format="yaml(pushConfig)"

pushConfig に、送り先（pushEndpoint）と名乗るアカウント（oidcToken）が入りました。注文を 1 つ出して、mailer のログを見ます。

publish すると、Cloud Run に届く⌘↵
gcloud pubsub topics publish orders --message='{"order":1006}' --attribute=shop=tokyogcloud run services logs read mailer --limit=5

ログに 受け取った：{"order":1006} と、Pub/Sub からの POST 204 が出ました。だれも pull していないのに、publish しただけで mailer が動いています。受け手のサービスは、メッセージがないときは 0 台まで縮み、届いたときだけ起きます。

メモこのサイトの GCP では

本物の Pub/Sub の push は、送り先が失敗を返すと、間隔を少しずつ空けながら送り直します。このサイトの GCP でも送り直しますが、認証に失敗した（403 の）push の要求は、Cloud Run のログに出ません。

12.8Node の SDK で送る・受ける

アプリからは、Google が出している Node のライブラリ @google-cloud/pubsub を使います。gcloud と同じことが、関数の呼び出しでできます。認証は、Cloud Shell や Cloud Run では ADC（第 5 章）が自動で使われます。

メモこのサイトの GCP では

本物では npm install @google-cloud/pubsub で入れてから使います。このサイトの node では、入れなくても require できます。

まず、受け手のサブスクリプション ship-app を作っておきます。前の節で見たとおり、作る前に出したメッセージは届かないからです。それから、注文を 3 つ出すプログラムを書いて動かします。

publishMessage で 3 つ出す⌘↵
gcloud pubsub subscriptions create ship-app --topic=ordersmkdir -p ~/shop && cd ~/shopcat > publish.js <<'EOF'const { PubSub } = require('@google-cloud/pubsub');const topic = new PubSub().topic('orders');async function main() {  for (const order of [2001, 2002, 2003]) {    const id = await topic.publishMessage({ json: { order }, attributes: { shop: 'tokyo' } });    console.log(`送った：注文 ${order}（メッセージ ID ${id}）`);  }}main();EOFnode publish.js
  • topic('orders') が、トピックを指すものです。ここではまだ通信しません
  • publishMessage に、本文（json に渡すと JSON の文字列にしてくれる。バイト列なら data）と attributes を渡します。戻り値はメッセージ ID です

受けて ack する。2 回届いても困らないように

確認応答の節で見たとおり、同じメッセージが 2 回届くことがあります。発送の係が同じ注文を 2 回発送しては困ります。そこで、発送した注文の番号をファイル done.txt に記録し、記録にあれば何もせずに ack するようにします。

受ける側は、サブスクリプションに on('message', …) で関数を登録します。メッセージが届くたびに、その関数が呼ばれます。処理が済んだら message.ack() を呼びます。message.data はバイト列（Buffer）なので、toString() で文字列にしてから JSON として読みます。本物のプログラムは受け続けるのがふつうですが、ここでは 3 秒たったら close() で止めます。

わざと「発送はしたが、ack する前に倒れた」場合も作れるようにします。node ship.js crash と打つと、ack を呼びません。

subscription.on('message') で受ける。ただし ack しないまま終わる⌘↵
cat > ship.js <<'EOF'const fs = require('fs');const { PubSub } = require('@google-cloud/pubsub');const subscription = new PubSub().subscription('ship-app');const crash = process.argv[2] === 'crash';const done = fs.existsSync('done.txt') ? fs.readFileSync('done.txt').trim().split('\n') : [];subscription.on('message', (message) => {  const { order } = JSON.parse(message.data.toString());  if (done.includes(String(order))) {    console.log(`注文 ${order} は発送済み。何もせずに ack する`);    message.ack();    return;  }  console.log(`注文 ${order} を発送した`);  done.push(String(order));  fs.writeFileSync('done.txt', done.join('\n') + '\n');  if (!crash) message.ack();});setTimeout(() => subscription.close(), 3000);EOFnode ship.js crashcat done.txt

publish.js で出した 2001〜2003 を受け取って発送し、done.txt に記録しました。でも ack はしていません。期限が過ぎてから、ふつうに動かします。

同じ注文がもう一度届いても、2 回は発送しない⌘↵
sleep 11node ship.js

3 つの注文がもう一度届きました。少なくとも 1 回の配信が、実際に起きたわけです。でも done.txt に記録があるので、発送はせずに ack だけを返しています。本物のアプリでは、記録はファイルではなく、Firestore（第 13 章）や Cloud SQL（第 14 章）のようなデータベースに置きます。最後に、サブスクリプションの名前を間違えると、on('error', …) に登録した関数が呼ばれます。

サブスクリプションの名前を間違えるエラーになる⌘↵
cat > typo.js <<'EOF'const { PubSub } = require('@google-cloud/pubsub');const subscription = new PubSub().subscription('ship-ap');subscription.on('message', (message) => message.ack());subscription.on('error', (err) => { console.error(err.message); process.exitCode = 1; });EOFnode typo.js

5 NOT_FOUND の 5 は、gRPC（Google の API が使う通信の方式）のエラーの番号で、NOT_FOUND（見つからない）と同じ意味です。権限がなければ 7 PERMISSION_DENIED になります。error の関数を登録しておかないと、こうした失敗に気づけません。

要点まとめ
  • Pub/Sub は、送る側と受ける側の間でメッセージを預かる。送る側は publish したら終わりで、受ける側を待たない（非同期）
  • トピックは宛先の名前、サブスクリプションは受け取り口。メッセージはサブスクリプションごとにコピーされる（ファンアウト）。作る前に出したメッセージは届かない
  • pull は既定で 1 件。--limit で上限、--auto-ack でその場で確認応答。表の ACK_ID を subscriptions ack --ack-ids に渡す
  • 確認応答の期限（既定 10 秒）までに ack が来ないと、同じメッセージがもう一度届く。配信は少なくとも 1 回なので、受け手は冪等に作る
  • --message-filter='attributes.shop = "tokyo"' で、属性による振り分け。--dead-letter-topic と --max-delivery-attempts（5〜100）で、処理できないメッセージを別のトピックへ移す
  • push は Pub/Sub が URL へ POST する。Cloud Run には、roles/run.invoker を持つサービスアカウントを --push-auth-service-account に指定する
  • Node では topic.publishMessage() で出し、subscription.on('message') で受けて message.ack()

正解済み
