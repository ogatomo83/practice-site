第 14 章

Cloud SQL

Cloud SQL は、Google が面倒を見てくれる PostgreSQL です。インスタンスを作り、データベースとユーザーを足し、gcloud sql connect で SQL を流します。Cloud Shell、外の機械、Cloud Run からのつなぎ方の違いと、バックアップと復元、止めて料金を抑える方法までを、本物の PostgreSQL 18 で確かめます。

14.1Cloud SQL は何を引き受けてくれるか

つばめ文具の店には、商品や注文の表が要ります。行を足し、更新し、集計する。こういう仕事には、PostgreSQL のようなリレーショナルデータベース（表と SQL で扱うデータベース）が向いています。

PostgreSQL は、第 8 章の VM に自分で入れることもできます。けれども、それだと OS の更新、PostgreSQL の更新、バックアップ、ディスクが足りなくなったときの対応を、全部自分でやることになります。Cloud SQL は、そこを Google が引き受けるマネージド（管理を任せられる）なデータベースのサービスです。

Cloud SQL は PostgreSQL のほかに MySQL と SQL Server も選べます。この本では PostgreSQL だけを扱います。中身は本物の PostgreSQL なので、SQL の書き方はそのまま使えます。SQL そのものは 図解 PostgreSQL で詳しく扱っています。

まずは、いまのプロジェクトにインスタンス（Cloud SQL の 1 台ぶんのデータベースサーバー）があるかを見てみます。

Cloud SQL の API はまだ無効エラーになる⌘↵
gcloud sql instances list

Cloud SQL Admin API has not been used in project … or it is disabled は、第 3 章で見た「API が無効」のエラーです。Cloud SQL を操作する API は sqladmin.googleapis.com という名前です。有効にしてから、もう一度試します。

API を有効にする⌘↵
gcloud services enable sqladmin.googleapis.comgcloud sql instances list

今度はエラーになりません。Listed 0 items. は「インスタンスは 1 つもない」という意味です。

メモこのサイトの GCP では

中身の PostgreSQL は、ブラウザで動く PGlite（本物の PostgreSQL 18 を WebAssembly にしたもの）です。インスタンスのつくり、IP アドレス、接続の許可は模型で、本物の Cloud SQL の振る舞いをまねています。

14.2インスタンスを作る：エディションとティア

インスタンスを作るときに決める大事な項目は、エディション（機能と性能の等級）とティア（マシンの大きさ）の 2 つです。

エディション--editionティアの例向いている使い方
Enterpriseenterprisedb-f1-micro、db-g1-small（共有コア）、db-custom-1-3840（1 vCPU、3.75 GB）開発、試し、小さなサービス
Enterprise Plusenterprise-plusdb-perf-optimized-N-2（2 vCPU、16 GB）など性能と可用性が大事な本番

db-f1-micro は、CPU をほかと分け合う共有コアのいちばん小さいティアです。試すにはこれで十分です。ただし、組み合わせに決まりがあります。まず、エディションを指定せずに作ってみます。

エディションとティアが合わないエラーになる⌘↵
gcloud sql instances create shop-db --tier=db-f1-micro --region=asia-northeast1

エラーの文を読みます。Invalid Tier (db-f1-micro) for (ENTERPRISE_PLUS) Edition は「Enterprise Plus では db-f1-micro は使えない」という意味です。指定しなかったエディションが Enterprise Plus になったのは、PostgreSQL 16 以降の既定がそうなっているからです。いまの既定のバージョンは PostgreSQL 18 です。

直し方は 2 つあります。--edition=enterprise を付けるか、db-perf-optimized-N-2 のような Enterprise Plus のティアを選ぶかです。ここでは安い方を選びます。

インスタンスを作る（数分かかる）⌘↵
dategcloud sql instances create shop-db --edition=enterprise --tier=db-f1-micro --region=asia-northeast1 --root-password=Tsubame-root-1date

前後の date を見比べてください。作成に 7 分ほどかかっています。本物でも、中で VM とディスクを用意して PostgreSQL を起動するので、数分かかります。--region=asia-northeast1 は東京リージョンで、作った後で場所は変えられません。--root-password は、最初からいる管理用のユーザー postgres のパスワードです。

注意本物ではパスワードを履歴に残さない

本文では分かりやすさのためにパスワードをコマンドに書いています。本物では、シェルの履歴に残らないように、gcloud に聞いてもらう（gcloud sql users set-password の --prompt-for-password など）か、Secret Manager（秘密の値を預けるサービス）を使ってください。

接続名と IP アドレス

作ったインスタンスの情報は describe で見られます。全部を出すと長いので、--format で欲しいところだけを取り出します。

接続名と IP アドレス⌘↵
gcloud sql instances listgcloud sql instances describe shop-db --format="value(connectionName)"gcloud sql instances describe shop-db --format="yaml(ipAddresses)"gcloud sql instances describe shop-db --format="value(settings.edition,settings.tier,databaseVersion,state)"

tsubame-shop:asia-northeast1:shop-db が接続名です。「プロジェクト:リージョン:インスタンス名」の形で、このあと Cloud Run や Auth Proxy からつなぐときに使います。

ipAddresses には 2 つ出ています。PRIMARY の 34.85.202.133 は、外からつなぐときの宛先です。OUTGOING は、インスタンスから外へ出ていくときの送り元のアドレスです。最後の行は、エディション、ティア、バージョン、状態（RUNNABLE は動いている）です。

14.3データベースとユーザーを足す

1 つのインスタンスの中には、データベースをいくつも作れます。ユーザーはインスタンス全体で共通で、どのデータベースにも入れます。データベースもユーザーも、SQL の create database や create role ではなく、gcloud で作るのが Cloud SQL の作法です。gcloud で作ると、Cloud SQL がその存在を知っていて、一覧やコンソールに出せるからです。

データベースとユーザーを作る⌘↵
gcloud sql databases create shop --instance=shop-dbgcloud sql databases list --instance=shop-dbgcloud sql users create app --instance=shop-db --password=App-pass-1gcloud sql users list --instance=shop-db --format="table(name,type)"

databases list には、最初からある postgres と、作った shop が出ます。users list の TYPE の BUILT_IN は、パスワードでログインする、PostgreSQL の中のユーザーという意味です。

14.4gcloud sql connect で SQL を流す

いよいよ中に入ります。いちばん手軽なのは gcloud sql connect です。このコマンドは、裏で 2 つのことをしています。

1 つ目は、API を呼んで、Cloud Shell の IP アドレスを 5 分だけ「つないでよい相手」に入れることです。2 つ目は、psql（PostgreSQL の標準のクライアント）を起動して、インスタンスにつなぐことです。

psql はパスワードを聞いてきます。ここでは環境変数 PGPASSWORD で先に渡しておき、実行する SQL はヒアドキュメント（<<'SQL' から SQL までの行を、標準入力として渡す書き方）で流します。

まず、アプリ用のユーザー app で shop に入り、表を作ります。--user と --database を省くと、--root-password で決めたユーザー postgres でデータベース postgres に入ります。

app で shop に入り、表を作る⌘↵
PGPASSWORD=App-pass-1 gcloud sql connect shop-db --user=app --database=shop <<'SQL'create table products (  id    int primary key,  name  text not null,  price int not null);insert into products values  (1, '方眼ノート A5', 380),  (2, 'ボールペン 黒', 120),  (3, '万年筆 青', 3200);select * from products order by id;SQL

Allowlisting your IP for incoming connection for 5 minutes...done. が 1 つ目の仕事です。その後の CREATE TABLE、INSERT 0 3、3 行の表は、本物の PostgreSQL の応答そのものです。

psql のメタコマンド

psql には、\ で始まるメタコマンド（SQL ではなく、psql 自身への命令）があります。よく使う 3 つを試します。

\dt、\l、\du⌘↵
PGPASSWORD=App-pass-1 gcloud sql connect shop-db --user=app --database=shop <<'SQL'\dt\l\duSQL
メタコマンド出るもの
\dtいまのデータベースの表の一覧。products の持ち主（Owner）は app
\lインスタンスの中のデータベースの一覧。postgres と shop
\duユーザー（ロール）の一覧。app と postgres

\l の Owner が cloudsqlsuperuser になっています。これは Cloud SQL が用意した管理用のロールです。Cloud SQL では、本当の意味でのスーパーユーザー（何でもできるユーザー）は使わせてもらえません。OS やファイルに触れる操作は、Google の側の仕事だからです。

パスワードを間違えると

パスワードが違うエラーになる⌘↵
PGPASSWORD=wrong-pass gcloud sql connect shop-db --user=app --database=shop <<'SQL'select 1;SQL

FATAL: password authentication failed for user "app" は、PostgreSQL が「app のパスワードが違う」と断ったという意味です。IP の許可（1 つ目の仕事）はできているので、ネットワークの問題ではありません。

パスワードを忘れたら、gcloud で付け直せます。古いパスワードは要りません。

パスワードを付け直す⌘↵
gcloud sql users set-password app --instance=shop-db --password=App-pass-2PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'select count(*) from products;SQL

新しいパスワード App-pass-2 で入れて、count は 3 です。このあとは App-pass-2 を使います。

14.5つなぎ方は 1 つではない

gcloud sql connect は手軽ですが、毎回 API で IP を許可する、人が手で使うための道具です。アプリや外の機械からは、別の方法でつなぎます。

承認済みネットワーク：IP で許可する

インスタンスの公開 IP に、psql で直接つないでみます。gcloud sql connect が開けた 5 分の許可は、時間がたてば消えます。それを過ぎた状態で、-h に IP を指定してつなぐとどうなるでしょう。

公開 IP に直接つなぐエラーになる⌘↵
PGPASSWORD=App-pass-2 psql -h 34.85.202.133 -U app -d shop <<'SQL'select 1;SQL

Connection timed out です。パスワードのエラーではありません。インスタンスが、知らない IP からの接続を黙って捨てているので、待っても返事が来ないのです。

公開 IP に入れてよい相手は、承認済みネットワーク（authorized networks）という IP アドレスの一覧で決めます。最初は空なので、だれもつなげません。Cloud Shell の外向きの IP は 34.146.93.21 です。これを /32（その 1 つのアドレスだけ）で足します。

承認済みネットワークに Cloud Shell の IP を足す⌘↵
gcloud sql instances patch shop-db --authorized-networks=34.146.93.21/32gcloud sql instances describe shop-db --format="value(settings.ipConfiguration.authorizedNetworks[].value)"PGPASSWORD=App-pass-2 psql -h 34.85.202.133 -U app -d shop <<'SQL'select name, price from products order by id;SQL

今度はつながりました。patch は、インスタンスの設定を変えるコマンドです。--authorized-networks は一覧を置き換えるので、足すときは前からある IP も並べて書きます。

注意0.0.0.0/0 は入れない

0.0.0.0/0 を入れると、世界中のどこからでも 5432 番にたどり着けます。あとはパスワードだけが頼りになり、総当たりで試されます。承認済みネットワークには、決まった IP だけを入れてください。IP が決まらない機械からは、次の Auth Proxy を使います。

メモこのサイトの GCP では

本物の gcloud sql connect は、承認済みネットワークに自分の IP を 5 分だけ書き足し、あとで消します。このサイトの模型は一覧を書き換えず、gcloud sql connect のときだけ通します。

Cloud SQL Auth Proxy：IP ではなく IAM で許可する

Cloud SQL Auth Proxy は、Google が配っている小さなプログラムです。手元の機械で動かすと、127.0.0.1:5432 で待ち受けます。そこに psql でつなぐと、Proxy が IAM（第 6 章）で「この人は Cloud SQL につないでよいか」を確かめ、暗号化した通り道でインスタンスまで運びます。

ターミナル
$ ./cloud-sql-proxy tsubame-shop:asia-northeast1:shop-db… Listening on 127.0.0.1:5432$ psql -h 127.0.0.1 -U app -d shop

引数は接続名です。必要な権限は roles/cloudsql.client（Cloud SQL Client）のロールです。IP が変わる手元のパソコンや、承認済みネットワークを使いたくないときは、こちらが勧められています。このサイトには cloud-sql-proxy のプログラムがないので、上の例は読むだけにしてください。

プライベート IP：VPC の中だけでつなぐ

公開 IP を持たせず、VPC（第 9 章）の中のアドレスだけを持たせることもできます。--network で VPC を選び、--no-assign-ip で公開 IP をなくします。

プライベート IP だけのインスタンス⌘↵
gcloud sql instances create shop-db-private --edition=enterprise --tier=db-f1-micro --region=asia-northeast1 --network=default --no-assign-ipgcloud sql instances describe shop-db-private --format="yaml(ipAddresses)"

ipAddresses には 10.25.0.3、type: PRIVATE の 1 つだけが出ます。同じ VPC の中の VM からはこのアドレスでつなげますが、外からは道がありません。

Cloud Shell からはつなげないエラーになる⌘↵
gcloud sql connect shop-db-private

エラーの文は「インスタンスに IPv4 のアドレスがない」です。Cloud Shell は VPC の外にいるので、プライベート IP には届きません。本物では、プライベート IP を使う前に、VPC に「プライベート サービス アクセス」という接続を設定しておく必要があります（手順は公式ドキュメントを参照）。このサイトの模型は、その手順を省いています。

14.6Cloud Run からつなぐ

第 10 章の Cloud Run から、shop の表を読む API を作ります。Cloud Run では、接続名を Cloud Run に教えておくと、コンテナの中に /cloudsql/接続名 という Unix ソケット（同じ機械の中でプロセスどうしがつなぐための、ファイルの形をした口）ができます。その裏で Auth Proxy と同じ仕組みが動きます。

アプリは Node.js で書き、PostgreSQL につなぐのに pg（node-postgres）というモジュールを使います。host に /cloudsql/ で始まるパスを書くと、pg は TCP ではなく Unix ソケットでつなぎます。

API のソースを書く⌘↵
mkdir -p ~/apicat > ~/api/package.json <<'EOF'{ "name": "api", "main": "server.js", "dependencies": { "pg": "^8.13.0" } }EOFcat > ~/api/server.js <<'EOF'const http = require('http');const { Pool } = require('pg');const pool = new Pool({ host: '/cloudsql/' + process.env.INSTANCE, user: 'app', password: process.env.DB_PASS, database: 'shop' });http.createServer(async (req, res) => {  try {    const r = await pool.query('select id, name, price from products order by id');    res.end(JSON.stringify(r.rows) + '\n');  } catch (e) { res.statusCode = 500; res.end('error: ' + e.message + '\n'); }}).listen(process.env.PORT || 8080);EOF

接続名とパスワードは、環境変数 INSTANCE と DB_PASS で渡します。まず、Cloud SQL のことを Cloud Run に教えずにデプロイしてみます。

接続名を教えずにデプロイする⌘↵
gcloud run deploy api --source ~/api --region=asia-northeast1 --allow-unauthenticated --set-env-vars=INSTANCE=tsubame-shop:asia-northeast1:shop-db,DB_PASS=App-pass-2 --quietcurl -s https://api-365600345236.asia-northeast1.run.app

デプロイはできましたが、curl の答えは connect ENOENT /cloudsql/…/.s.PGSQL.5432 です。ENOENT は「そのファイルがない」という意味です。Cloud Run が接続名を知らないので、ソケットを作っていないのです。

--add-cloudsql-instances で接続名を足して、デプロイし直します。

--add-cloudsql-instances を付けてデプロイし直す⌘↵
gcloud run deploy api --source ~/api --region=asia-northeast1 --add-cloudsql-instances=tsubame-shop:asia-northeast1:shop-db --quietcurl -s https://api-365600345236.asia-northeast1.run.app

今度は products の 3 行が JSON で返りました。環境変数は前のリビジョンから引き継がれています。

つなぐときに使われるのは、Cloud Run のサービスアカウント（ここでは既定の Compute Engine のサービスアカウント）の権限です。専用のサービスアカウントにするときは、roles/cloudsql.client を付けてください。パスワードも、本物では環境変数に直接書かず、Secret Manager に預けて --set-secrets で渡すのがよいやり方です。

14.7バックアップと復元

Cloud SQL は、毎日決まった時刻に自動でバックアップを取ります（既定で 7 個まで残す）。大きな作業の前には、自分でも取れます。

バックアップを取って、一覧を見る⌘↵
gcloud sql backups create --instance=shop-dbgcloud sql backups list --instance=shop-db --format="table(id,windowStartTime,status)"

ID の数字が、このバックアップの名前です。STATUS が SUCCESSFUL なら取れています。では、うっかり全部の行を消してしまいます。

うっかり全部消す⌘↵
PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'delete from products;select count(*) from products;SQL

DELETE 3 で、count は 0 になりました。バックアップから戻します。ID は手で写さずに、一覧のいちばん新しい 1 つを --limit=1 と value(id) で取り出します。

バックアップから復元する⌘↵
BID=$(gcloud sql backups list --instance=shop-db --format="value(id)" --limit=1)gcloud sql backups restore $BID --restore-instance=shop-db --quietPGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'select count(*) from products;SQL

count は 3 に戻りました。--quiet を付けないと、All current data on the instance will be lost when the backup is restored. と確かめてきます。復元はインスタンス全体を戻すので、バックアップの後に足した行は、どのデータベースのものでも消えます。

深掘り時刻を指定して戻す

本物の Cloud SQL には、ポイントインタイム リカバリ（PITR）もあります。WAL（変更の記録）を残しておき、「午前 10 時 12 分の状態」のように時刻を指定して、新しいインスタンスに戻せます。このサイトの模型にはありません。

14.8止めて料金を抑え、消せないように守る

Cloud SQL のインスタンスは、使っていなくても動いている間はずっと料金がかかります。Compute Engine の e2-micro のような「いつも無料」の枠もありません（第 4 章の無料枠の一覧に Cloud SQL は入っていません）。夜や週末に使わない開発用のインスタンスは、止めておくのが基本です。

止めるには、アクティベーション ポリシー（いつ動かすか）を NEVER にします。

インスタンスを止める⌘↵
gcloud sql instances patch shop-db --activation-policy=NEVERgcloud sql instances list

shop-db の STATUS が STOPPED になりました。止めている間は CPU とメモリの料金がかかりません。ただし、データを入れたディスクは残るので、その料金はかかり続けます（詳しくは公式の料金ページを参照）。

止まっているとつなげないエラーになる⌘↵
PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop

Invalid request since instance is not running. は「動いていないインスタンスには、その操作はできない」という意味です。### 削除の保護

本番のインスタンスは、うっかり消されないように守りたいものです。下のブロックでは、まず ALWAYS に戻してインスタンスを動かし、それから --deletion-protection で削除の保護を付けます。

また動かして、削除の保護を付ける⌘↵
gcloud sql instances patch shop-db --activation-policy=ALWAYSgcloud sql instances patch shop-db --deletion-protectiongcloud sql instances describe shop-db --format="value(state,settings.deletionProtectionEnabled)"
保護されていると消せないエラーになる⌘↵
gcloud sql instances delete shop-db --quiet

RUNNABLE と True を確かめてから消そうとすると、The instance is protected. で止まりました。--quiet で確認を飛ばしても消えません。本当に消すときは、--no-deletion-protection で保護を外してからにします。

最後に、この章で作ったものを片付けます。

片付け⌘↵
gcloud sql instances patch shop-db --no-deletion-protectiongcloud sql instances delete shop-db --quietgcloud sql instances delete shop-db-private --quietgcloud run services delete api --region=asia-northeast1 --quietgcloud sql instances list
要点まとめ
  • Cloud SQL は、OS・更新・バックアップを Google が引き受ける PostgreSQL（ほかに MySQL、SQL Server）。API は sqladmin.googleapis.com
  • インスタンスはエディションとティアで決まる。PostgreSQL 16 以降の既定は Enterprise Plus で、db-f1-micro を使うには --edition=enterprise が要る
  • データベースとユーザーは gcloud sql databases create / users create で作る。パスワードは users set-password で付け直せる
  • gcloud sql connect は、自分の IP を 5 分だけ許可してから psql でつなぐ。SQL はヒアドキュメントで流せる
  • 公開 IP に直接つなぐには承認済みネットワークが要る（ないとタイムアウト）。IP が決まらないなら Auth Proxy、VPC の中だけならプライベート IP、Cloud Run からは --add-cloudsql-instances と /cloudsql/接続名
  • backups create / restore はインスタンス全体を戻す。使わないときは --activation-policy=NEVER で止め、本番は --deletion-protection で守る

14.9確認問題

Cloud SQL のインスタンスを、自分のコマンドで調べたり直したりします。どの問題も、準備で shop-db などのインスタンスが作ってあります。

問 1

300 円以上の商品

正解済み

インスタンス shop-db のデータベース shop に、表 products（id、name、price）があります。ユーザー app（パスワード App-pass-2）で入り、price が 300 以上の商品の name だけを、id の順に表示してください。psql の表の形のままで構いません。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番も見る）
この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud services enable sqladmin.googleapis.comgcloud sql instances create shop-db --edition=enterprise --tier=db-f1-micro --region=asia-northeast1gcloud sql databases create shop --instance=shop-dbgcloud sql users create app --instance=shop-db --password=App-pass-2PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'create table products (id int primary key, name text not null, price int not null);insert into products values (1, '方眼ノート A5', 380), (2, 'ボールペン 黒', 120), (3, '万年筆 青', 3200);SQL
模範解答
PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'select name from products where price >= 300 order by id;SQL
問 2

止まっているインスタンス

正解済み

プロジェクトにはインスタンスがいくつかあり、そのうちいくつかは止めてあります。止まっているインスタンスの名前だけを、1 行に 1 つ表示してください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番は問わない）
ヒント

止めたインスタンスは、settings.activationPolicy が NEVER です。--filter で絞り、--format="value(name)" で名前だけを出します。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud services enable sqladmin.googleapis.comgcloud sql instances create shop-db --edition=enterprise --tier=db-f1-micro --region=asia-northeast1gcloud sql instances create dev-db --edition=enterprise --tier=db-f1-micro --region=asia-northeast1gcloud sql instances create test-db --edition=enterprise --tier=db-f1-micro --region=asia-northeast1gcloud sql instances patch dev-db --activation-policy=NEVER
模範解答
gcloud sql instances list --filter="settings.activationPolicy=NEVER" --format="value(name)"
問 3

消した行を取り戻す

正解済み

インスタンス shop-db にはバックアップが 2 つあります。その後で、だれかが products の行を全部消してしまいました。いちばん新しいバックアップから shop-db を復元して、行を取り戻してください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

backups list は新しい順に並びます。--limit=1 と --format="value(id)" で ID を 1 つだけ取り出し、backups restore に渡します。確認を飛ばすには --quiet です。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud services enable sqladmin.googleapis.comgcloud sql instances create shop-db --edition=enterprise --tier=db-f1-micro --region=asia-northeast1gcloud sql databases create shop --instance=shop-dbgcloud sql users create app --instance=shop-db --password=App-pass-2PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'create table products (id int primary key, name text not null, price int not null);insert into products values (1, '方眼ノート A5', 380), (2, 'ボールペン 黒', 120), (3, '万年筆 青', 3200);SQLgcloud sql backups create --instance=shop-dbPGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'insert into products values (4, '消しゴム', 100);SQLgcloud sql backups create --instance=shop-dbPGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'delete from products;SQL
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

PGPASSWORD=App-pass-2 gcloud sql connect shop-db --user=app --database=shop <<'SQL'select count(*) from products;SQL
模範解答
gcloud sql backups restore $(gcloud sql backups list --instance=shop-db --format="value(id)" --limit=1) --restore-instance=shop-db --quiet
