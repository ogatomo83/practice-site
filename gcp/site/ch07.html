Cloud Storage

ファイルを置いておく場所、Cloud Storage を使えるようにします。バケットとオブジェクト、世界で 1 つのバケット名、場所とストレージクラス、cp・ls・cat・mv・rm、フォルダがない理由、allUsers で公開して curl で読むことと、公開アクセス防止、バージョニングの世代、ライフサイクルで古いものを自動で片付けるところまでを、手を動かして確かめます。

7.1バケットとオブジェクト

Cloud Storage（クラウド ストレージ。略して GCS）は、ファイルを置いておくサービスです。商品の写真、Web サイトの HTML、ログ、バックアップ、BigQuery に読み込む CSV など、どんな中身でも置けます。大きさの上限を気にせず、置いた分だけ料金を払います。

  • バケット（bucket、バケツ）は、オブジェクトを入れる入れ物です。かならず 1 つのプロジェクトに属し、料金はそのプロジェクトの請求先に付きます。置く場所（リージョン）、既定のストレージクラス、だれが読めるか（IAM）は、バケットごとに決めます
  • オブジェクト（object）は、置いた 1 つ 1 つのファイルです。中身のバイト列と、名前、大きさ、種類（Content-Type）などのメタデータ（中身についての情報）でできています

バケットとオブジェクトは、gs://バケット/オブジェクト という URL で指します。操作するコマンドは gcloud storage です。まず、バケットを 1 つ作ります。

バケットを作る⌘↵
gcloud storage buckets create gs://tsubame-shop-ch07-assets --location=asia-northeast1 --uniform-bucket-level-accessgcloud storage ls

Creating gs://tsubame-shop-ch07-assets/... と出れば、できています。引数なしの gcloud storage ls は、いまのプロジェクト（tsubame-shop）のバケットの一覧です。--location は置く場所、--uniform-bucket-level-access は権限の決め方で、どちらもあとの節で説明します。

メモAPI と権限

Cloud Storage の API（storage.googleapis.com）は、新しいプロジェクトで最初から有効になっています。バケットを作るには、プロジェクトに対する storage.buckets.create の権限が要ります。あなた（you@）は組織の管理者なので持っています。権限の考え方は第 6 章のとおりです。

7.2バケットの名前は世界で 1 つ

プロジェクトの ID と同じく（第 2 章）、バケットの名前は、世界中のすべての利用者で 1 つの名前空間を分け合っています。あなたの組織の中だけでなく、ほかの会社がすでに使っている名前も使えません。

試しに、tsubame-images という、いかにもありそうな名前で作ってみます。

ほかのだれかが使っている名前エラーになる⌘↵
gcloud storage buckets create gs://tsubame-images --location=asia-northeast1

HTTPError 409 は「衝突（Conflict）」です。The bucket namespace is shared by all users of the system（バケットの名前空間は、すべての利用者で共有されている）と、理由がそのまま書いてあります。この世界では、どこかの別の会社が tsubame-images を先に取っています。直し方は 1 つで、別の名前にすることです。

名前の決まりにも気を付けます。使えるのは英小文字、数字、-、_、. で、先頭と末尾は英小文字か数字です。大文字は使えません。長さにも決まりがあります（公式ドキュメントを参照）。

大文字の入った名前エラーになる⌘↵
gcloud storage buckets create gs://Tsubame_Shop --location=asia-northeast1

HTTPError 400: Invalid bucket name は「名前の形が正しくない」です。だれかに取られているのではなく、そもそも作れない名前です。

コツ名前の付け方

ぶつかりにくく、見て分かる名前にするには、プロジェクト ID を先頭に付けるのが定番です（tsubame-shop-assets、tsubame-shop-logs）。プロジェクト ID 自体が世界で 1 つなので、ぶつかる心配がほぼなくなります。この本でも、章ごとに tsubame-shop-ch07-… のような名前を使います。バケットの名前は URL に出て、だれにでも見えます。顧客の名前や社内の秘密を名前に入れないでください。

7.3場所とストレージクラス

バケットを作るときに決める大事な設定が 2 つあります。場所（location）とストレージクラス（storage class）です。

場所：どこにデータを置くか

場所は 3 種類です。第 3 章のリージョンの考え方と同じです。

種類例意味
リージョン（region）asia-northeast1（東京）1 つのリージョンの中の、複数のゾーンに置く
デュアルリージョン（dual-region）ASIA1（東京と大阪）決まった 2 つのリージョンに置く
マルチリージョン（multi-region）ASIA、US、EU大きな地域の中の、複数のリージョンに置く

広い場所ほど、1 つのリージョン全体が止まっても読めますが、保存の料金は高くなります。--location を書かないと US（アメリカのマルチリージョン）になるので、日本の店のデータなら、いつも明示して作るのが安全です。場所は、あとから変えられません。

ストレージクラス：どのくらいの頻度で読むか

ストレージクラスは、「保存は安いが、読むと高い」度合いの選択です。

クラス向いているもの
STANDARDよく読むもの（Web の画像、処理中のデータ）。最低保存期間なし
NEARLINE月に 1 回くらい読むもの（バックアップ）
COLDLINE年に数回くらい読むもの（災害対策の写し）
ARCHIVEほぼ読まないが、消せないもの（法律で残す記録）

下に行くほど保存の料金は安くなり、そのかわり、読み出すときの料金と、最低保存期間（それより早く消しても、その期間分の料金がかかる）が付きます。具体的な金額と期間は、本物の料金ページ（公式ドキュメント）を見てください。どのクラスでも、読み出す速さはほとんど変わりません。テープのように「取り出しに何時間も待つ」ことはありません。

バックアップ用に、アジアのマルチリージョンで、既定のクラスを NEARLINE にしたバケットを作ってみます。

場所とクラスを指定して作る⌘↵
gcloud storage buckets create gs://tsubame-shop-ch07-archive --location=ASIA --default-storage-class=NEARLINEgcloud storage buckets list --format="table(name,location,location_type,default_storage_class)"

一覧の LOCATION_TYPE が region と multi-region、DEFAULT_STORAGE_CLASS が STANDARD と NEARLINE に分かれています。既定のクラスは、オブジェクトを置くときにクラスを指定しなかったときに使われる値です。オブジェクトごとに別のクラスにもできます。本物の無料枠（毎月、リージョンのストレージ 5 GB-月など）は US のリージョンだけが対象で、東京リージョンに置いたものは含まれません。

7.4オブジェクトを置いて、読む

オブジェクトを置く・取り出す・一覧するコマンドは、Linux の cp、ls、cat とよく似た名前です。まず、手元（Cloud Shell のホームディレクトリ）に店の Web サイトの材料を作り、1 つを置きます。

手元にファイルを作って、1 つ置く⌘↵
mkdir -p shop/products shop/cssecho '<h1>つばめ文具</h1>' > shop/index.htmlecho 'body { color: navy; }' > shop/css/site.cssecho '万年筆 2800' > shop/products/pen.txtecho 'ノート 300' > shop/products/note.txtgcloud storage cp shop/index.html gs://tsubame-shop-ch07-assets/

cp：置く

gcloud storage cp 元 先 で置きます。先に gs:// の URL を書くとアップロード、元に書くとダウンロードです。上のブロックの最後の行の出力 Copying file:///home/you/shop/index.html to gs://tsubame-shop-ch07-assets/index.html が、1 つ置いた記録です。先を gs://バケット/ で終えると、元のファイル名（index.html）がそのままオブジェクトの名前になります。ディレクトリごと置くときは -r（recursive、中身ごと）を付けます。

ディレクトリごと置く⌘↵
gcloud storage cp -r shop gs://tsubame-shop-ch07-assets/

4 つのファイルが、shop/css/site.css、shop/products/pen.txt のような名前で置かれました。最後の Completed files 4/4 | 76.0B/76.0B が、置いた数と合計のバイト数です。

ls：一覧する

一覧する⌘↵
gcloud storage ls gs://tsubame-shop-ch07-assetsgcloud storage ls gs://tsubame-shop-ch07-assets/shop

1 行目の ls には、index.html と shop/ の 2 行が出ます。shop/ の中身は出ません。2 行目のように shop を付けると、その一段下が出ます。/ で終わる行は、「この名前で始まるオブジェクトがまだある」という印です（次の節）。-l（long）を付けると大きさと作った時刻が、-r を付けると下の階層まで全部が出ます。

ls -l と ls -r⌘↵
gcloud storage ls -l gs://tsubame-shop-ch07-assets/shop/productsgcloud storage ls -r gs://tsubame-shop-ch07-assets

ls -l の 1 列目がバイト数、2 列目が作った時刻（UTC）です。最後の TOTAL: 2 objects, 29 bytes が合計です。pen.txt が 15 バイトなのは、万年筆 が UTF-8 で 1 文字 3 バイト（9 バイト）、空白、2800、改行で 15 バイトだからです。ls -r では、下の階層のオブジェクトまで、すべての名前が出ます。

cat と du：中身と大きさを見る

中身を表示し、大きさを数える⌘↵
gcloud storage cat gs://tsubame-shop-ch07-assets/shop/products/pen.txtgcloud storage du gs://tsubame-shop-ch07-assets/shopgcloud storage du -s gs://tsubame-shop-ch07-assets/shop

cat はオブジェクトの中身を、ダウンロードせずに画面に出します。du（disk usage）は 1 つずつのバイト数を、du -s（summarize）は合計の 1 行だけを出します。合計の 76 は、さっきの cp -r の 76.0B と同じです。ないオブジェクトを指すと、エラーになります。

ないオブジェクトエラーになる⌘↵
gcloud storage cat gs://tsubame-shop-ch07-assets/shop/products/eraser.txt

The following URLs matched no objects or files: の次の行に、見つからなかった URL が出ます。名前の打ち間違いか、バケットの違いを疑います。

7.5フォルダはなく、名前の接頭辞がある

ここまでの ls は、まるでフォルダがあるように見えました。しかし Cloud Storage のバケットの中は、名前の一覧が 1 段に並んでいるだけです。shop/products/pen.txt は、「shop フォルダの中の products フォルダの中の pen.txt」ではなく、shop/products/pen.txt という 21 文字の名前の、1 つのオブジェクトです。

ls は、名前を / までの接頭辞（名前の先頭の部分）でまとめて、フォルダのように見せているだけです。このことから、Linux のフォルダとは違う振る舞いが 2 つ出てきます。

1 つ目。名前を変える（mv）は、写して消すことです。フォルダの中身をまとめて移す、という操作はありません。

名前を変える⌘↵
gcloud storage mv gs://tsubame-shop-ch07-assets/shop/products/note.txt gs://tsubame-shop-ch07-assets/shop/items/note.txtgcloud storage ls gs://tsubame-shop-ch07-assets/shop

mv の出力に Copying … と Removing … の 2 行が出ています。新しい名前で写してから、元を消しています。shop/items/ というフォルダを作っていないのに、ls には shop/items/ が出ました。shop/items/ で始まる名前のオブジェクトができたからです。

2 つ目。最後の 1 つを消すと、フォルダも消えます。

最後の 1 つを消す⌘↵
gcloud storage rm gs://tsubame-shop-ch07-assets/shop/items/note.txtgcloud storage ls gs://tsubame-shop-ch07-assets/shopgcloud storage rm gs://tsubame-shop-ch07-assets/index.html

shop/items/ の行がなくなりました。空のフォルダ、というものは残りません。rm の出力の Completed 1/1 は、消したオブジェクトの数です。最後の行では、shop/index.html と重複している、いちばん上の index.html も消しました。

深掘りなぜフォルダがないのか

Cloud Storage は、何十億ものオブジェクトを置けるように、名前をキーにした大きな表として作られています。本物のフォルダ（中身の一覧を持つ入れ物）があると、フォルダの中身を書き換えるたびに、その一覧も書き換える必要があり、同時にたくさん書き込むときの詰まりになります。名前だけにしておけば、どのオブジェクトも独立に書けます。そのかわり「フォルダの名前を変える」は、オブジェクトを 1 つずつ写して消す操作になります。本物には、本当のフォルダを持つ「階層型名前空間」のバケットもあります（公式ドキュメントを参照）。

7.6公開と公開アクセス防止

店の Web サイトの HTML や商品の画像は、だれでも読めるようにしたいものです。Cloud Storage のオブジェクトには、https://storage.googleapis.com/バケット/オブジェクト という URL があります。まず、ブラウザの代わりに curl で、ログインしていない人として読んでみます。

ログインしていない人として読む⌘↵
curl -s -w '\n' https://storage.googleapis.com/tsubame-shop-ch07-assets/shop/index.htmlcurl -s -H "Authorization: Bearer $(gcloud auth print-access-token)" https://storage.googleapis.com/tsubame-shop-ch07-assets/shop/index.html

1 つ目は AccessDenied の XML が返りました。Anonymous caller does not have storage.objects.get access は「名前のない呼び出し元（ログインしていない人）は、storage.objects.get の権限を持っていない」です。2 つ目は、gcloud auth print-access-token であなたのアクセストークン（ログインの証明）を取り出し、Authorization ヘッダーに付けて送りました。あなたには権限があるので、中身が返ります。-w '\n' は、改行で終わらない XML のエラーのあとに、改行を足すための指定です。

allUsers に objectViewer を与える

ログインしていない人を含む「だれでも」は、IAM では allUsers というプリンシパル（権限を受け取る相手）で表します（第 5 章）。バケットの IAM に、allUsers と、オブジェクトを読むロール roles/storage.objectViewer の組を足します。

バケットを公開する⌘↵
gcloud storage buckets add-iam-policy-binding gs://tsubame-shop-ch07-assets --member=allUsers --role=roles/storage.objectViewer --format=nonegcloud storage buckets get-iam-policy gs://tsubame-shop-ch07-assets --flatten="bindings[]" --format="table(bindings.role,bindings.members)"

最後の行に roles/storage.objectViewer と allUsers の組が入りました（足した結果の長いポリシーは --format=none で隠し、get-iam-policy で表にしています）。上の 4 行は、バケットを作ったときに自動で入る組です。projectOwner:tsubame-shop は「tsubame-shop のオーナー全員」という、Cloud Storage だけの便利な書き方です。もう一度、ログインせずに読みます。

公開したあとで読む⌘↵
curl -s https://storage.googleapis.com/tsubame-shop-ch07-assets/shop/index.htmlcurl -si https://storage.googleapis.com/tsubame-shop-ch07-assets/shop/products/pen.txt

今度は中身が返りました。-i を付けた 2 つ目では、応答のヘッダーも見えます。HTTP/2 200 が成功、content-type: text/plain は名前の .txt から決まった種類、x-goog-storage-class: STANDARD がクラスです。cache-control: public, max-age=3600 は「だれでもキャッシュしてよい」という意味で、公開されたオブジェクトに付きます。

注意公開は、バケットの中身すべてに効く

バケットの IAM に allUsers を足すと、いま入っているものも、これから入れるものも、すべてが世界中から読めます。顧客の名簿や注文の CSV を、うっかり同じバケットに置いてはいけません。公開するものだけを入れたバケットを分けて作るのが基本です。

均一なバケットレベルのアクセス

最初にバケットを作るとき、--uniform-bucket-level-access を付けました。これは均一なバケットレベルのアクセス（UBLA）で、「だれが読めるかは、バケットの IAM だけで決める」という設定です。Cloud Storage には、IAM より古い ACL（アクセス制御リスト。オブジェクト 1 つ 1 つに付ける許可の表）もあります。ACL があると「バケットは非公開なのに、1 つだけ ACL で公開されていた」ということが起こります。UBLA を有効にすると ACL が使えなくなり、IAM だけを見れば済みます。

バケットの設定を確かめる⌘↵
gcloud storage buckets describe gs://tsubame-shop-ch07-assets --format="yaml(uniform_bucket_level_access,public_access_prevention)"

uniform_bucket_level_access: true が UBLA です。public_access_prevention: inherited は、次に説明する公開アクセス防止が「このバケットでは指定せず、組織のポリシーに従う」という意味です。

公開アクセス防止

逆に、「このバケットは絶対に公開させない」と決めておく設定が、公開アクセス防止（public access prevention）です。社内のデータを置くバケットは、作るときに --public-access-prevention を付けておきます。

公開アクセス防止つきで作る⌘↵
gcloud storage buckets create gs://tsubame-shop-ch07-private --location=asia-northeast1 --uniform-bucket-level-access --public-access-preventiongcloud storage buckets describe gs://tsubame-shop-ch07-private --format="value(public_access_prevention)"

enforced（強制）になりました。このバケットに、さっきと同じように allUsers を足そうとすると、止められます。

公開しようとすると止まるエラーになる⌘↵
gcloud storage buckets add-iam-policy-binding gs://tsubame-shop-ch07-private --member=allUsers --role=roles/storage.objectViewer

HTTPError 412 は「前提条件が満たされていない（Precondition Failed）」です。allUsers and allAuthenticatedUsers are not allowed since public access prevention is enforced（公開アクセス防止が強制されているので、allUsers と allAuthenticatedUsers は使えない）と、理由が書いてあります。権限がないのではなく、バケットの設定が許さない、というエラーです。本当に公開したいなら、公開用の別のバケットを使います。

公開アクセス防止は、あとから buckets update でも付けられます。さっきの NEARLINE のバックアップ用バケットに付けます。

あとから公開アクセス防止を付ける⌘↵
gcloud storage buckets update gs://tsubame-shop-ch07-archive --public-access-preventiongcloud storage buckets describe gs://tsubame-shop-ch07-archive --format="value(public_access_prevention)"

enforced になったので、このバケットでも allUsers を足すと同じ 412 で止まります。組織全体で強制するには、組織のポリシー storage.publicAccessPrevention を使います（第 6 章の組織のポリシー）。そうすると、組織の中のどのバケットも、inherited のままで公開できなくなります。

7.7バージョニングと世代

Cloud Storage では、同じ名前でオブジェクトを置き直すと、古い中身は上書きされて消えます。誤って上書きしたり消したりしたときに戻せるようにするのが、バージョニング（versioning）です。

オブジェクトの 1 つ 1 つの版を世代（generation）と呼びます。世代には、置いた時刻から決まる 16 桁ほどの番号が付きます。非公開のバケットでバージョニングを有効にして、値段の表を 2 回置いてみます。

バージョニングを有効にして、2 回置く⌘↵
gcloud storage buckets update gs://tsubame-shop-ch07-private --versioningecho '万年筆 2800' > price.txtgcloud storage cp price.txt gs://tsubame-shop-ch07-private/price.txtecho '万年筆 3000' > price.txtgcloud storage cp price.txt gs://tsubame-shop-ch07-private/price.txtgcloud storage ls gs://tsubame-shop-ch07-privategcloud storage ls -a gs://tsubame-shop-ch07-privategcloud storage cat gs://tsubame-shop-ch07-private/price.txt

ふつうの ls には price.txt が 1 つだけ出ます。-a（all-versions、すべての世代）を付けると、price.txt#… が 2 行出ます。# の後ろの数が世代の番号で、小さいほうが古い世代です。cat は、何も指定しなければ最新の世代（万年筆 3000）を読みます。

消してみます。

消しても、世代は残る⌘↵
gcloud storage rm gs://tsubame-shop-ch07-private/price.txtgcloud storage ls gs://tsubame-shop-ch07-privategcloud storage ls -a gs://tsubame-shop-ch07-private

ふつうの ls は何も出しません。しかし ls -a には、2 つの世代がそのまま残っています。バージョニングが有効なバケットの rm は、最新の世代を「最新でない」にするだけです。

古い世代は、gs://バケット/名前#世代 の形で指せます。本物の端末では ls -a の出力から番号を写して打ちますが、ここでは head -1 で最初の行（いちばん古い世代）を取り出して、変数に入れます。

古い世代を読んで、戻す⌘↵
OLD=$(gcloud storage ls -a gs://tsubame-shop-ch07-private/price.txt | head -1)gcloud storage cat $OLDgcloud storage cp $OLD gs://tsubame-shop-ch07-private/price.txtgcloud storage cat gs://tsubame-shop-ch07-private/price.txt

cat $OLD で、最初に置いた 万年筆 2800 が読めました。それを同じ名前へ cp すると、新しい最新の世代になります。最後の cat が 万年筆 2800 を返せば、戻せています。ls -a で見ると、世代は 3 つになっているはずです。

古い世代を本当に消すには、世代を指定するか、-a を付けて rm します。世代も 1 つ 1 つ保存の料金がかかるので、バージョニングを有効にしたバケットでは、次の節のライフサイクルで古い世代を片付けるのが定番です。

バケットはオブジェクトが残っていると消せないエラーになる⌘↵
gcloud storage buckets delete gs://tsubame-shop-ch07-private

HTTPError 409: The bucket you tried to delete is not empty. です。古い世代も「中身」に数えます。バケットごと消すときは、gcloud storage rm -r -a gs://バケット で、すべての世代とバケットをまとめて消します（最後の節で使います）。

7.8ライフサイクルで、古いものを自動で片付ける

ログや一時ファイルは、放っておくと増え続けます。ライフサイクル（lifecycle、オブジェクトの一生）の設定は、「作ってから何日たったら消す」「何日たったら安いクラスに移す」といった規則を、バケットに書いておく仕組みです。Cloud Storage が定期的に調べて、自動で実行します。

規則は JSON で書きます。1 つの規則は、action（何をするか）と condition（どのオブジェクトに）の組です。

規則を JSON で書いて、バケットに付ける⌘↵
cat > lifecycle.json <<'EOF'{  "rule": [    { "action": { "type": "Delete" }, "condition": { "age": 7, "matchesPrefix": ["tmp/"] } },    { "action": { "type": "SetStorageClass", "storageClass": "COLDLINE" }, "condition": { "age": 30, "matchesStorageClass": ["STANDARD"] } }  ]}EOFgcloud storage buckets create gs://tsubame-shop-ch07-logs --location=asia-northeast1 --uniform-bucket-level-accessgcloud storage buckets update gs://tsubame-shop-ch07-logs --lifecycle-file=lifecycle.jsongcloud storage buckets describe gs://tsubame-shop-ch07-logs --format="json(lifecycle_config)"

describe の lifecycle_config の下に、書いた 2 つの規則が入っています。

書き方意味
"type": "Delete"消す
"type": "SetStorageClass", "storageClass": "COLDLINE"クラスを COLDLINE に変える
"age": 7作ってから 7 日以上たった
"matchesPrefix": ["tmp/"]名前が tmp/ で始まる（フォルダではなく接頭辞で選ぶ）
"matchesStorageClass": ["STANDARD"]いまのクラスが STANDARD

ほかに、バージョニングと組み合わせて使う isLive（最新の世代か）や numNewerVersions（自分より新しい世代がいくつあるか）もあります。条件を複数書くと、全部を満たしたものだけが選ばれます。では、ログを 2 つ置いて、時間を進めます。

ログを置く⌘↵
echo 'cache 1' > a.loggcloud storage cp a.log gs://tsubame-shop-ch07-logs/tmp/a.loggcloud storage cp a.log gs://tsubame-shop-ch07-logs/2026/11/16.loggcloud storage ls -r gs://tsubame-shop-ch07-logs
メモこのサイトの GCP では

時計は仮想なので、sleep で日を進められます。sleep 691200 は 8 日（691,200 秒）です。本物の sleep で 8 日待つのは現実的ではありません。本物でライフサイクルを確かめるときは、規則を付けてから数日おいて見ます。規則の実行は、条件を満たしてから少し遅れることがあります。

8 日進める⌘↵
sleep 691200dategcloud storage ls -r gs://tsubame-shop-ch07-logs

date が 11 月 24 日になりました。tmp/a.log が消え、2026/11/16.log だけが残っています。2026/11/16.log は tmp/ で始まらないので、1 つ目の規則に当たりません。さらに 30 日進めます。

さらに 30 日進める⌘↵
sleep 2592000gcloud storage objects describe gs://tsubame-shop-ch07-logs/2026/11/16.log --format="value(name,storage_class)"

クラスが COLDLINE に変わりました。置いてから 30 日以上たち、STANDARD だったので、2 つ目の規則に当たったからです。中身はそのままで、cat でも読めます。

注意消す規則は取り消せない

ライフサイクルの Delete で消えたものは、バージョニングが無効なら戻せません。matchesPrefix を書き忘れると、バケットの全部が対象になります。新しい規則は、まず中身の少ないバケットで試してください。

最後に、この章で作ったバケットを片付けます。rm -r はバケットの中身とバケット自身を、-a は古い世代も消します。

片付け⌘↵
gcloud storage rm -r -a gs://tsubame-shop-ch07-logs gs://tsubame-shop-ch07-privategcloud storage ls

gcloud storage ls に、assets と archive の 2 つだけが残りました。

要点まとめ
  • Cloud Storage は、プロジェクトの中のバケットに、オブジェクトを置く。gs://バケット/名前 で指し、gcloud storage で操作する
  • バケットの名前は世界で 1 つ。使われていると 409、形が正しくないと 400。プロジェクト ID を先頭に付けるとぶつかりにくい
  • バケットごとに場所（リージョン / デュアル / マルチ）と既定のストレージクラス（STANDARD → ARCHIVE の順に、保存は安く、読み出しは高く）を決める
  • cp（-r でディレクトリごと）、ls（-l 大きさ、-r 全部、-a 世代）、cat、du、mv、rm
  • フォルダはない。名前は平らな一覧で、ls は / までの接頭辞でまとめて見せているだけ
  • allUsers に roles/storage.objectViewer を与えると、だれでも https://storage.googleapis.com/… で読める。公開アクセス防止を強制したバケットでは、412 で止まる
  • バージョニングを有効にすると、上書きや削除で古い世代が残る。#世代 で指して読んだり戻したりできる
  • ライフサイクルの JSON で、日数・接頭辞・クラスを条件に、消す・クラスを変えるを自動にできる
