第 5 章

アカウントの種類

Google Cloud の「だれ」には、人の Google アカウント、グループ、サービスアカウントがあります。個人と組織のアカウントの違い、組織とドメインの関係、グループの使い方、サービスアカウントの作り方と鍵・借用、allUsers と allAuthenticatedUsers、gcloud と ADC の 2 つの認証情報を、alice や taro に切り替えて確かめます。

5.1Google Cloud の「だれ」は何種類あるか

IAM（第 6 章）は「だれに、何を許すか」を決める仕組みです。この章は、その「だれ」の側を扱います。IAM で権限を受け取る相手をプリンシパル（principal）と呼びます。プリンシパルには、次の種類があります。

IAM のポリシーには、user:you@tsubame.example のように「種類:メールアドレス」の形で書きます。人もグループもサービスアカウントも、メールアドレスの形の名前を持っているのが共通点です。

いま gcloud がだれとして動いているかは、gcloud auth list で見られます。

いまのアカウント⌘↵
gcloud auth listgcloud config get-value account
  • Credentialed Accounts は、この端末が認証情報（ログインした証拠）を持っているアカウントの一覧です。いまは you@tsubame.example の 1 つだけです
  • 左の * が付いているのが、いま使っているアカウントです。gcloud config get-value account が出すのと同じものです

5.2人の Google アカウント：個人のものと、組織が管理するもの

人のアカウントは、どれも Google アカウントです。Gmail や YouTube にログインするのと同じ仕組みで、Google Cloud 専用のアカウントはありません。ただし、Google アカウントには 2 つの出自があります。

個人の Google アカウント管理されたアカウント
例taro@example.com、…@gmail.comyou@tsubame.example、alice@tsubame.example
だれが作るか本人が自分で作る会社の管理者が、Google Workspace か Cloud Identity で作る
だれが管理するか本人だけ組織の管理者（パスワードの再設定、2 段階認証の強制、退職したら停止）
組織との関係どの組織にも属さないドメインの組織に属する

Google Workspace は、Gmail や Google ドライブを会社で使うための有料のサービスです。Cloud Identity は、そこからメールなどを抜いて、アカウントの管理だけを提供するサービスです（無料の版があります）。どちらも、会社のドメイン（tsubame.example）で、社員のアカウントをまとめて管理できます。

仕事で Google Cloud を使うなら、管理されたアカウントを使うのが原則です。個人のアカウントは、退職した人のアカウントを会社が止められません。

組織は、ドメインから生まれる

第 2 章で見た組織 tsubame.example は、どこから来たのでしょうか。

Workspace や Cloud Identity を契約した会社は、Google から見ると 1 つの顧客（customer）です。顧客がドメインを持っていることを確かめ（ドメインの確認）、そのドメインで Google Cloud を使い始めると、組織のリソースが 1 つ自動でできます。組織の名前はドメイン名です。

組織と、その持ち主の顧客⌘↵
gcloud organizations listgcloud organizations describe 405918273641 --format="yaml(displayName, name, owner)"

DIRECTORY_CUSTOMER_ID と owner.directoryCustomerId の C03k8x2pq が、Workspace の顧客 ID です。組織は、この顧客の持ち物だということが分かります。人のアカウントとグループは Workspace の側に、プロジェクトは組織の側にある、という分かれ方を覚えておいてください。

alice と taro に切り替えて、見え方を比べる

同じコマンドでも、だれが打つかで結果が変わります。gcloud auth login で、ほかの人に切り替えてみます。

alice としてログインする⌘↵
gcloud auth login alice@tsubame.examplegcloud auth listgcloud projects list

gcloud auth list に 2 人が並び、* が alice に移りました。you@ の認証情報は消えていません。gcloud は何人分でも認証情報を持てて、そのうち 1 人を「いまのアカウント」として使うのです。

メモこのサイトの GCP では

本物の gcloud auth login は、ブラウザを開いて Google のログイン画面でアカウントを選び、パスワードを入れます。このサイトでは、ログインするアカウントを引数で指定すると、すぐにログインできます。

最後の gcloud projects list は Listed 0 items. です。alice は組織の社員ですが、どのプロジェクトのロールも持っていません。組織に属していることと、プロジェクトを使えることは別です。使えるようにするには、IAM でロールを付けます（第 6 章）。

次は組織の外の taro です。

taro には組織も見えない。自分に戻して比べる⌘↵
gcloud auth login taro@example.comgcloud organizations listgcloud config set account you@tsubame.examplegcloud projects list --format="value(projectId)"

個人のアカウントの taro には、組織そのものが見えません（Listed 0 items.）。そのあと、いまのアカウントを自分に戻しました。ログインし直す必要はなく、gcloud config set account で選び直すだけです。you には 2 つのプロジェクトが見えます。同じ端末、同じコマンドでも、API はいつも「だれが呼んだか」で答えを変えるのです。

5.3グループで人をまとめる

5 人の開発者にそれぞれロールを付けると、人が入れ替わるたびに IAM を直すことになります。そこで、グループ（Google グループ）にロールを付け、人はグループに出し入れします。新しく入った人をグループに足すだけで、IAM のポリシーは変えずに済みます。

グループは IAM の機能ではなく、Workspace（Cloud Identity）の機能です。gcloud では gcloud identity groups で扱います。

dev-team のメンバー⌘↵
gcloud identity groups memberships list --group-email=dev-team@tsubame.example

メンバーは 2 人です。preferredMemberKey.id がメンバーのメールアドレスで、roles がグループの中での役割です。you には OWNER も付いています。グループの OWNER は、メンバーを出し入れできる人です。これは IAM のロールとは別のものなので、混ぜないでください。

alice を分析チームにも入れてみます。グループの名前だけを並べるには --format を使います。

analysts に alice を足す⌘↵
gcloud identity groups memberships add --group-email=analysts@tsubame.example --member-email=alice@tsubame.example --format=nonegcloud identity groups memberships list --group-email=analysts@tsubame.example --format="value(preferredMemberKey.id)"

bob@ と alice@ の 2 人になりました。このあと analysts@ に付いているロールは、alice にも効きます。1 人が何個のグループに入っていてもかまいません。

存在しないアカウントは足せません。

いない人を足すエラーになる⌘↵
gcloud identity groups memberships add --group-email=analysts@tsubame.example --member-email=carol@tsubame.example

NOT_FOUND: … Member carol@tsubame.example not found. は「そのメールアドレスのアカウントが見つからない」という意味です。打ち間違いか、まだアカウントが作られていないかを確かめます。

5.4サービスアカウント：プログラムのためのアカウント

Cloud Run で動く注文の API が、Firestore に書き込むとします。このプログラムは「だれ」として Firestore を呼ぶのでしょうか。開発した alice のアカウントを使うと、alice が異動したときに API が止まります。そこで、プログラム専用のアカウントを作ります。これがサービスアカウントです。

サービスアカウントには、人のアカウントと違うところがあります。

  • パスワードがない。 ブラウザでログインはできません。代わりに、Google Cloud の中で動くものに「付けて」使います（VM、Cloud Run、関数など）
  • プロジェクトの中にある。 メールアドレスは 名前@プロジェクトID.iam.gserviceaccount.com です
  • それ自体がリソースでもある。 「だれがこのサービスアカウントを使ってよいか」を、サービスアカウントの IAM で決めます（あとの節）

いまあるものを見てから、注文の API のためのものを作ります。

サービスアカウントを作る⌘↵
gcloud iam service-accounts listgcloud iam service-accounts create order-api --display-name="注文 API"gcloud iam service-accounts list

最初の一覧は Listed 0 items. で、まだ 1 つもありませんでした。作った後の一覧では、EMAIL の列が order-api@tsubame-shop.iam.gserviceaccount.com になっています。IAM のポリシーには、serviceAccount: を前に付けたこの名前で書きます。

名前の決まりは、出力のエラーの文に書いてあります。短すぎる名前で試します。

名前が短すぎるエラーになる⌘↵
gcloud iam service-accounts create api

must be between 6 and 30 characters は「6〜30 文字」、must begin with a lowercase letter は「小文字の英字で始まる」です。使える文字は小文字の英字、数字、ハイフンです。同じ名前をもう一度作ろうとすると、already exists within project のエラーになります。

1 つのサービスアカウントの詳しい情報⌘↵
gcloud iam service-accounts describe order-api@tsubame-shop.iam.gserviceaccount.com
  • name は projects/tsubame-shop/serviceAccounts/… です。サービスアカウントがプロジェクトの下のリソースだということが分かります
  • uniqueId は、21 桁の番号です。同じ名前で消して作り直すと、メールアドレスは同じでも、この番号は変わります

既定のサービスアカウントと、サービスエージェント

サービスアカウントは、自分で作るものだけではありません。Compute Engine の API を有効にしてみます。

Compute Engine を有効にすると増えるもの⌘↵
gcloud services enable compute.googleapis.comgcloud iam service-accounts list --format="table(displayName, email)"gcloud projects get-iam-policy tsubame-shop --flatten="bindings[].members" --format="table(bindings.role, bindings.members)"

Compute Engine default service account が増えました。メールアドレスは 365600345236-compute@developer.gserviceaccount.com で、先頭はプロジェクトの番号です。これが既定のサービスアカウントです。VM や Cloud Run でサービスアカウントを指定しないと、これが使われます（第 8 章、第 10 章）。

ブロックの最後の get-iam-policy は、プロジェクトの IAM を 1 行に 1 つの割り当てで並べたものです。roles/owner の you のほかに、2 つの行が増えています。

  • 既定のサービスアカウントに roles/editor（ほとんど何でも変更できる強いロール）。既定のまま使うと、VM の上のプログラムがプロジェクト中のものを書き換えられることになります
  • service-365600345236@compute-system.iam.gserviceaccount.com に roles/compute.serviceAgent。これはサービスエージェントです

サービスエージェントは、Google のサービスが、あなたのプロジェクトの中で仕事をするときに使うサービスアカウントです。Compute Engine が VM にディスクを付けるとき、そのサービス自身が「だれか」として API を呼ぶ必要があります。その「だれか」がサービスエージェントです。Google が作って管理し、gcloud iam service-accounts list には出ません。消したり、ロールを外したりしてはいけません。

注意既定のサービスアカウントの Editor

既定のサービスアカウントに自動で Editor が付くのは、便利さを優先した昔の設計です。いまは、用途ごとにサービスアカウントを作り、必要なロールだけを付けるのが推奨です。新しく作られた組織では、この自動の付与を止める組織のポリシー（iam.automaticIamGrantsForDefaultServiceAccounts）が最初から有効になっています（詳しくは公式ドキュメントを参照）。

5.5鍵ファイルで、サービスアカウントとして動く

Google Cloud の外（自分の PC、ほかのクラウド、CI）で動くプログラムを、サービスアカウントとして動かしたいときがあります。いちばん古いやり方が、サービスアカウントの鍵（JSON の鍵ファイル）です。

鍵ファイルを作って、サービスアカウントになる⌘↵
gcloud iam service-accounts keys create key.json --iam-account=order-api@tsubame-shop.iam.gserviceaccount.comcat key.jsongcloud auth activate-service-account --key-file=key.jsongcloud auth list

private_key が秘密鍵、client_email がサービスアカウントです。このファイルを持っている人はだれでも、ここに書かれたサービスアカウントとして Google Cloud を操作できます。

続く gcloud auth activate-service-account が、この鍵で gcloud をサービスアカウントとして動かすコマンドです。gcloud auth list の * が order-api@… に移りました。ここで、プロジェクトのサービスアカウントの一覧を見てみます。

作ったばかりのサービスアカウントには、何の権限もないエラーになる⌘↵
gcloud iam service-accounts list

Permission 'iam.serviceAccounts.list' denied です。you がプロジェクトの Owner でも、you が作ったサービスアカウントは、別のプリンシパルです。作った人の権限は引き継ぎません。ロールを付けるまで、何もできません。

鍵ファイルを避ける理由

鍵の一覧を見ると、鍵ファイルの怖さが分かります。まず自分に戻ってから見ます。

鍵の一覧⌘↵
gcloud config set account you@tsubame.examplegcloud iam service-accounts keys list --iam-account=order-api@tsubame-shop.iam.gserviceaccount.com

鍵が 2 つあります。

  • EXPIRES_AT が 2028-… のものは、Google が管理する鍵です。Google が自動で取り替えるので、気にしなくてかまいません
  • EXPIRES_AT が 9999-12-31 のものが、いま作った鍵です。期限がありません。消すまで、ずっと使えます

期限のない秘密が 1 つのファイルになっていると、次のことが起きます。

  • 漏れやすい。 git に commit してしまう、チャットに貼ってしまう、PC ごと盗まれる。ファイルなので、コピーされても気づけません
  • だれが使ったか分からない。 監査ログに残るのはサービスアカウントの名前だけで、鍵を持っていた人の名前は残りません
  • 管理が要る。 定期的に作り直し（ローテーション）、古い鍵を消す手間がかかります

使い終わった鍵は消します。消した鍵は、ファイルが手元に残っていても使えません。

鍵を消す⌘↵
gcloud iam service-accounts keys delete $(gcloud iam service-accounts keys list --iam-account=order-api@tsubame-shop.iam.gserviceaccount.com --managed --format="value(name.basename())") --iam-account=order-api@tsubame-shop.iam.gserviceaccount.com --quiet

keys list の --managed はユーザーが作った鍵だけに絞るフラグで、その ID を delete に渡しています。

消した鍵のファイルで、もう一度なろうとするエラーになる⌘↵
gcloud auth activate-service-account --key-file=key.json

Invalid JWT Signature は「この鍵の署名を、Google がもう受け付けない」という意味です。鍵は Google の側で無効になりました。本物では、手元のファイルも rm key.json で消しておきます。

メモ鍵の作成は、組織で止められる

鍵の危険は大きいので、組織のポリシー iam.disableServiceAccountKeyCreation で、鍵の作成そのものを禁止できます。禁止されていると、keys create は Key creation is not allowed on this service account. で失敗します。鍵の代わりに、次の節の借用や、Google Cloud の外のための Workload Identity 連携を使います。

5.6借用：鍵を持たずにサービスアカウントになる

鍵ファイルの代わりに、いまは借用（impersonation、なりすましとも訳されます）を使います。人は自分のアカウントでログインしたまま、「このサービスアカウントの、短い時間だけ使えるトークンをください」と IAM に頼みます。

鍵との違いは 3 つです。秘密のファイルがない。トークンはすぐに期限が切れる。「だれが借りたか」がはっきりする。試すために、order-api にプロジェクトを見るロール（roles/viewer）を付けておきます。ロールの付け方は第 6 章で詳しく扱います。

そのあと alice に切り替えます。前の節で一度ログインしているので、gcloud config set account だけで切り替わります。

order-api に Viewer を付けて、alice に切り替える⌘↵
gcloud projects add-iam-policy-binding tsubame-shop --member=serviceAccount:order-api@tsubame-shop.iam.gserviceaccount.com --role=roles/viewer --format=nonegcloud config set account alice@tsubame.example

alice は、自分ではサービスアカウントの一覧を見られません。そこで、--impersonate-service-account を付けて、order-api を借りようとします。

借用の許可がないエラーになる⌘↵
gcloud iam service-accounts list --impersonate-service-account=order-api@tsubame-shop.iam.gserviceaccount.com

最初の WARNING は、「このコマンドの API 呼び出しは、すべて order-api として行う」という知らせです。その次のエラーが大事です。Failed to impersonate [order-api@…] は借用に失敗したということで、直し方が文に書いてあります。「借用する人に roles/iam.serviceAccountTokenCreator のロールを付けなさい」。

このロールは、プロジェクトにではなく、サービスアカウントそのものに付けます。「alice は、order-api だけを借りてよい」という意味になります。サービスアカウントの IAM を変えられるのは you なので、you に戻って付けます。

alice に、order-api を借用する許可を与える⌘↵
gcloud config set account you@tsubame.examplegcloud iam service-accounts add-iam-policy-binding order-api@tsubame-shop.iam.gserviceaccount.com --member=user:alice@tsubame.example --role=roles/iam.serviceAccountTokenCreator

出力の bindings は、order-api というリソースの IAMです。プロジェクトの IAM とは別に、サービスアカウントごとにポリシーがあります。

alice として、order-api を借りる⌘↵
gcloud iam service-accounts list --impersonate-service-account=order-api@tsubame-shop.iam.gserviceaccount.com --account=alice@tsubame.example

今度は一覧が出ました。--account は「このコマンドだけ、このアカウントで」という指定です。alice 自身には見えないものが、order-api の Viewer の権限で見えています。

注意TokenCreator と ServiceAccountUser を取り違えない

名前の似たロールがもう 1 つあります。roles/iam.serviceAccountUser（サービスアカウント ユーザー）は、VM や Cloud Run にサービスアカウントを付けるための許可です（権限 iam.serviceAccounts.actAs）。トークンを作る権限は入っていないので、これだけでは --impersonate-service-account は使えません。「自分がなる」なら TokenCreator、「リソースに付ける」なら ServiceAccountUser です。

毎回フラグを付けるのが面倒なら、設定にできます。

借用を設定にする（alice として）⌘↵
gcloud config set account alice@tsubame.examplegcloud config set auth/impersonate_service_account order-api@tsubame-shop.iam.gserviceaccount.comgcloud projects describe tsubame-shop --format="value(projectId)"gcloud config unset auth/impersonate_service_accountgcloud config set account you@tsubame.example

設定している間は、どのコマンドにも WARNING: This command is using service account impersonation. が出ます。借りたまま忘れないための目印です。使い終わったら unset で外します。

5.7allUsers と allAuthenticatedUsers

最初の図の下の段の 2 つは、特定のだれかではありません。

書き方当てはまる人例
allUsersインターネットのだれでも。ログインしていない人も含むWeb サイトの画像を置くバケット、だれでも呼べる Cloud Run
allAuthenticatedUsersGoogle アカウントかサービスアカウントでログインした、世界中のだれでも公開データセット

allAuthenticatedUsers は「つばめ文具の社員」ではありません。個人の Gmail のアカウントでも当てはまります。名前から「社内だけ」と誤解しやすいので気をつけてください。社内だけにしたいなら domain:tsubame.example かグループを使います。

試しに、お知らせのファイルをバケットに置き、allUsers に読ませます。バケットは第 7 章で詳しく扱います。

お知らせを置いて、ログインなしで読む（まだ読めない）⌘↵
gcloud storage buckets create gs://tsubame-shop-ch05-notice --location=asia-northeast1echo "本日のおすすめ：つばめノート A5" > notice.txtgcloud storage cp notice.txt gs://tsubame-shop-ch05-notice/curl https://storage.googleapis.com/tsubame-shop-ch05-notice/notice.txt

最後の curl で、ログインなしで読みに行きました。curl は gcloud の認証情報を使わないので、だれでもない「匿名」のアクセスです。結果は Anonymous caller does not have storage.objects.get access です。匿名の呼び出しに、読む権限がありません。allUsers に読むロールを付けます。

allUsers に読ませる⌘↵
gcloud storage buckets add-iam-policy-binding gs://tsubame-shop-ch05-notice --member=allUsers --role=roles/storage.objectViewer --format=nonecurl https://storage.googleapis.com/tsubame-shop-ch05-notice/notice.txt

今度は中身が返りました。このバケットのファイルは、URL を知っているだれでも読めます。allAuthenticatedUsers の例は、最初からあります。公開データセット tsubame-public.bungu は、allAuthenticatedUsers に読むロールが付いています。組織の外の taro でも読めるかを確かめます。taro にも一度ログインしているので、gcloud config set account で切り替えられます。

組織の外の taro でも、公開データセットは読める⌘↵
gcloud config set account taro@example.combq head -n 3 tsubame-public:bungu.productsgcloud config set account you@tsubame.example

taro はつばめ文具と何の関係もありませんが、Google アカウントでログインしているので読めました。

注意組織の外の人に付けられないようにする

いまの組織では、IAM に allUsers も user:taro@example.com も付けられます。うっかり公開するのを防ぐため、組織のポリシー iam.allowedPolicyMemberDomains（ドメインで制限された共有）で、「自分の組織のアカウントにしか付けられない」ようにできます。これを有効にすると、taro に付けようとしても失敗します。第 6 章で実際に設定します。

5.8gcloud の認証情報と、ADC

最後に、プログラムが使う認証情報です。Node.js や Python の Google Cloud のライブラリ（クライアント ライブラリ）は、gcloud の認証情報を使いません。ADC（Application Default Credentials、アプリケーションのデフォルト認証情報）という、別の仕組みで認証情報を探します。

  • Google Cloud の中（VM、Cloud Run、関数）では、③ のメタデータサーバから、付けたサービスアカウントのトークンが取れます。コードに認証の処理を書かなくてよいのは、このおかげです（第 8 章）
  • 自分の PC では、gcloud auth application-default login を打つと、② のファイルができます。gcloud のログインとは別のログインです
  • ① は鍵ファイルを指すのに使われてきた方法です。前の節の理由で、いまは避けます

商品の数を数える小さなプログラムで確かめます。まず、同じクエリを bq で打ってから、Node.js のライブラリで書いたものを用意します。new BigQuery() に認証情報を渡していないところを見てください。

bq で数えて、同じことをするプログラムを書く⌘↵
bq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-public.bungu.products`'cat > count.js <<'JS'const { BigQuery } = require('@google-cloud/bigquery');async function main() {  const bq = new BigQuery();  const [rows] = await bq.query('SELECT COUNT(*) AS n FROM `tsubame-public.bungu.products`');  console.log('商品の数:', rows[0].n);}main();JS

bq の答えは 17 個です。次に ADC を作ってプログラムを動かし、そのあと gcloud だけを alice に切り替えます。

ADC を作って動かし、gcloud だけ alice にする⌘↵
gcloud auth application-default loginnode count.jsgcloud config set account alice@tsubame.example

Credentials saved to file: [/home/you/.config/gcloud/application_default_credentials.json] が ② のファイルです。いま gcloud を使っていた you の認証情報が、ADC として保存されました。プログラムはそれを使って動き、商品の数: 17 を出しました。最後の行で、gcloud のいまのアカウントは alice になりました。

bq は alice として動くエラーになる⌘↵
bq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-public.bungu.products`'

bq は gcloud の認証情報を使うので、alice として動きます。alice は tsubame-shop でクエリを実行する権限（bigquery.jobs.create）を持っていないので、失敗しました。では、プログラムはどうでしょう。

プログラムは you のまま⌘↵
node count.jsgcloud config set account you@tsubame.example

プログラムは成功しました。ADC は you のままだからです。「gcloud では動くのにプログラムでは権限がない」「その逆」が起きたら、gcloud と ADC が別のアカウントになっていないかを疑ってください。

要点まとめ
  • IAM のプリンシパルは、人の Google アカウント（user:）、グループ（group:）、サービスアカウント（serviceAccount:）、ドメイン（domain:）、allAuthenticatedUsers、allUsers
  • 人のアカウントには、本人が作る個人のものと、Workspace / Cloud Identity で組織が管理するものがある。仕事では管理されたアカウントを使う
  • Workspace の顧客が Google Cloud を使い始めると、ドメインの名前の組織が 1 つできる。人とグループは Workspace に、プロジェクトは組織にある
  • ロールはグループに付け、人はグループに出し入れする（gcloud identity groups memberships add）
  • サービスアカウントはプログラムのためのアカウント。作った人の権限は引き継がない。既定のサービスアカウントには強い Editor が付くことがあり、サービスエージェントは Google が使うもの
  • 鍵ファイルは期限がなく漏れやすいので避ける。代わりに借用（--impersonate-service-account）を使い、借りる人にサービスアカウントの roles/iam.serviceAccountTokenCreator を付ける
  • allAuthenticatedUsers は「社内」ではなく「Google にログインした世界中のだれでも」
  • gcloud の認証情報と ADC（クライアント ライブラリが使うもの）は別々。gcloud auth application-default login で ADC を作る

5.9確認問題

この章のコマンドを、自分で書いて確かめます。どの問題も、you@tsubame.example として始まります。

問 1

グループのメンバーだけを並べる

正解済み

グループ dev-team@tsubame.example のメンバーのメールアドレスだけを、1 行に 1 つずつ表示してください（name や roles は出さない）。

gcloud identity groups memberships list --group-email=dev-team@tsubame.example
⌘↵標準出力で判定（行の順番は問わない）
ヒント

メールアドレスは preferredMemberKey の下の id にあります。--format="value(…)" で、その項目だけを取り出せます。

模範解答
gcloud identity groups memberships list --group-email=dev-team@tsubame.example --format="value(preferredMemberKey.id)"
問 2

売上レポートのためのサービスアカウント

正解済み

プロジェクト tsubame-shop に、名前が report-bot、表示名が 売上レポート のサービスアカウントを作ってください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

gcloud iam service-accounts create 名前 --display-name="表示名" です。

確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

gcloud iam service-accounts describe report-bot@tsubame-shop.iam.gserviceaccount.com --format="value(email, displayName)"
模範解答
gcloud iam service-accounts create report-bot --display-name="売上レポート"
問 3

bob に借用を許す

正解済み

サービスアカウント order-api@tsubame-shop.iam.gserviceaccount.com が用意されていて、プロジェクトの Viewer が付いています。bob（bob@tsubame.example）が、鍵ファイルを使わずに、--impersonate-service-account でこのサービスアカウントを借りられるようにしてください。bob に付ける許可は、必要な最小限にしてください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

借用に要るロールは roles/iam.serviceAccountTokenCreator です。プロジェクトではなく、サービスアカウントの IAM（gcloud iam service-accounts add-iam-policy-binding）に付けます。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud iam service-accounts create order-api --display-name="注文 API"gcloud projects add-iam-policy-binding tsubame-shop --member=serviceAccount:order-api@tsubame-shop.iam.gserviceaccount.com --role=roles/viewer --format=nonegcloud auth login bob@tsubame.examplegcloud config set account you@tsubame.example
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

gcloud projects describe tsubame-shop --account=bob@tsubame.example --impersonate-service-account=order-api@tsubame-shop.iam.gserviceaccount.com --format="value(projectId)"
模範解答
gcloud iam service-accounts add-iam-policy-binding order-api@tsubame-shop.iam.gserviceaccount.com --member=user:bob@tsubame.example --role=roles/iam.serviceAccountTokenCreator
問 4

ログインなしで読めるようにする

正解済み

バケット gs://tsubame-shop-ch05-quiz に price.txt が置いてあります。このバケットのオブジェクトを、ログインしていない人も含めてだれでも読めるようにしてください（curl https://storage.googleapis.com/tsubame-shop-ch05-quiz/price.txt で中身が返るようにする）。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

「ログインしていない人も含めて」なので、allAuthenticatedUsers では足りません。読むためのロールは roles/storage.objectViewer です。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud storage buckets create gs://tsubame-shop-ch05-quiz --location=asia-northeast1echo "つばめノート A5 は 280 円" > price.txtgcloud storage cp price.txt gs://tsubame-shop-ch05-quiz/rm price.txt
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

curl -s https://storage.googleapis.com/tsubame-shop-ch05-quiz/price.txt
模範解答
gcloud storage buckets add-iam-policy-binding gs://tsubame-shop-ch05-quiz --member=allUsers --role=roles/storage.objectViewer
