第 6 章

IAM の基本

だれに、何を、どこで許すか。プリンシパル・ロール・権限・ポリシーの関係から、ロールの付け外し、フォルダからの継承、バケットへの IAM、期限付きの条件、組織のポリシーまでを動かし、「Permission … denied」のエラーを自分で読めるようにします。

この章の準備最初の実行のときに、自動で流れるコマンド
gcloud resource-manager folders create --display-name=dev --organization=405918273641gcloud projects create tsubame-dev --folder=183663902618gcloud storage buckets create gs://tsubame-shop-ch06 --location=asia-northeast1printf 'item,price\npen,120\nnote,250\n' > price.csvgcloud storage cp price.csv gs://tsubame-shop-ch06/

この章の準備で、組織の下にフォルダ dev（ID 183663902618）を作り、その中にプロジェクト tsubame-dev を作りました。tsubame-shop には、価格表 price.csv の入ったバケット gs://tsubame-shop-ch06 があります。

6.1IAM は「だれに・何を・どこで」を書いた表

IAM（Identity and Access Management）は、Google Cloud の「だれが、何をしてよいか」を決める仕組みです。登場するものは 4 つだけです。

  • プリンシパル（権限を受け取る相手）：user:、group:、serviceAccount:、domain: などの接頭辞を付けて書きます（第 5 章）
  • 権限（permission）：サービス.リソース.動詞 の形の、いちばん小さな許可です。storage.objects.get は「Cloud Storage のオブジェクトを読む」です
  • ロール：権限の束です。人に権限を 1 つずつ渡すことはできず、必ずロールで渡します
  • IAM ポリシー：リソース（組織、フォルダ、プロジェクト、バケット…）に 1 つずつ付いている表です。「このロールを、この人たちに」というバインディングの並びです

では、tsubame-shop のポリシーを見てみます。

プロジェクトの IAM ポリシー⌘↵
gcloud projects get-iam-policy tsubame-shop

bindings の下が、バインディングの並びです。いまは「roles/owner を user:you@tsubame.example に」の 1 つだけです。プロジェクトを作った人には、自動で Owner が付きます。etag はポリシーの版を表す値で、書き換えるたびに変わります。

--flatten で 1 行に 1 人

ポリシーの yaml は、人が増えると読みにくくなります。--flatten="bindings[].members" を付けると、bindings の配列を展開して、1 つのバインディングの 1 人を 1 行にした表にできます。--filter を足せば、特定の人の行だけを残せます。組織のポリシーで、you が持っているロールを調べてみます。

組織で you が持つロール⌘↵
gcloud organizations get-iam-policy 405918273641 --flatten="bindings[].members" --filter="bindings.members:you@" --format="table(bindings.role)"

you は組織で 3 つのロールを持っています。請求先を使う（billing.user）、フォルダを管理する（folderAdmin）、組織を管理する（organizationAdmin）です。この章で you がフォルダを作れたのも、プロジェクトのポリシーを書き換えられるのも、このロールのおかげです。

6.2ロールは権限の束。3 つの種類がある

ロールには 3 つの種類があります。

種類名前の形例向いている使い方
基本ロールroles/owner など 3 つroles/viewer、roles/editor、roles/owner試しのプロジェクト。範囲が広すぎるので本番では避ける
事前定義ロールroles/サービス.名前roles/storage.objectViewerふだんはこれ。Google がサービスごとに用意している
カスタムロールprojects/ID/roles/名前projects/tsubame-shop/roles/priceReader事前定義ロールでは広すぎるとき、自分で権限を選んで作る

基本ロールは、Google Cloud ができたころからある大まかなロールです。事前定義ロールは、サービスごとに細かく分かれています。gcloud iam roles describe でロールの中身を、gcloud iam roles list でロールの一覧を見られます。

基本ロールと事前定義ロール⌘↵
gcloud iam roles describe roles/viewer --format="value(title,description)"gcloud iam roles describe roles/owner --format="value(title,description)"gcloud iam roles list --filter="name:roles/storage.object" --format="table(name, title)"gcloud iam roles describe roles/storage.objectViewer

基本ロールは Viewer ⊂ Editor ⊂ Owner の順に広がります。Editor はほとんどのリソースを作り・変え・消せ、Owner はさらに IAM ポリシーそのものを書き換えられます。プロジェクトのすべてのサービスに効くので、「バケットを 1 つ読みたいだけの人」に付けるには大きすぎます。

事前定義ロールの includedPermissions が、ロールに入っている権限の一覧です。roles/storage.objectViewer は、storage.objects.get（読む）と storage.objects.list（一覧を見る）だけです。書き込みや削除は入っていません。

ロールの名前は大文字と小文字を区別します。roles/storage.objectviewer のように 1 文字違うと、NOT_FOUND: The role named … was not found.（その名前のロールはない）になります。gcloud iam roles list --filter で正しい綴りを確かめます。

カスタムロールを作る

馬場さん（bob@）に、価格表を読むだけの権限を渡したいとします。権限を自分で選んで、ロールを作れます。

カスタムロールを作る⌘↵
gcloud iam roles create priceReader --project=tsubame-shop --title="Price Reader" --description="価格表を読むだけ" --permissions=storage.objects.get,storage.objects.list --stage=GA

できたロールの名前は projects/tsubame-shop/roles/priceReader です。プロジェクトに作ったカスタムロールは、そのプロジェクトの中でだけ使えます（組織に作れば --organization、組織全体で使えます）。--stage を省くと ALPHA になります。

ロールの ID に使える文字は、英数字、_、. だけです。price-reader のようにハイフンを入れると、can contain only alphanumeric characters, underscores and periods と断られます。

注意カスタムロールは手入れが要る

事前定義ロールは、サービスに新しい機能が増えると Google が権限を足します。カスタムロールは、だれも足してくれません。まず事前定義ロールで足りないかを探し、どうしても広すぎるときだけ作ります。

6.3ロールを付ける、外す

青木さん（alice@）が、価格表を読もうとしています。gcloud auth login で alice に切り替えて、試してみます。

alice に切り替える⌘↵
gcloud auth login alice@tsubame.example
メモこのサイトの GCP では

本物の gcloud auth login はブラウザを開いて、その人がパスワードでログインします。このサイトでは、引数に書いたアカウントにすぐ切り替わります。プロンプトの you@cloudshell は Cloud Shell の端末の持ち主の名前なので、切り替えても変わりません。いまのアカウントは gcloud auth list の * で分かります。

alice は読めないエラーになる⌘↵
gcloud storage cat gs://tsubame-shop-ch06/price.csv

alice@tsubame.example does not have storage.objects.get access は、「alice は storage.objects.get の権限を持っていない」です。alice は同じ組織の人ですが、tsubame-shop のポリシーには何も書かれていません。書かれていないことは、すべて拒否です。

you に戻って、alice にロールを付けます。add-iam-policy-binding は、ポリシーにバインディングを 1 つ足すコマンドです。

you に戻り、alice にロールを付ける⌘↵
gcloud config set account you@tsubame.examplegcloud projects add-iam-policy-binding tsubame-shop --member=user:alice@tsubame.example --role=roles/storage.objectViewer

gcloud config set account は、ログイン済みのアカウントの間で切り替えるコマンドです。Updated IAM policy for project [tsubame-shop]. のあとに、書き換えた後のポリシー全体が出ます。roles/storage.objectViewer のバインディングが増え、etag が変わりました。

alice で読む⌘↵
gcloud config set account alice@tsubame.examplegcloud storage cat gs://tsubame-shop-ch06/price.csvgcloud storage ls gs://tsubame-shop-ch06

今度は読めました。storage.objects.list も入っているので、ls もできます。でも、削除の権限は入っていません。

消すことはできないエラーになる⌘↵
gcloud storage rm gs://tsubame-shop-ch06/price.csv

足りない権限は storage.objects.delete だと、エラーの文に書いてあります。ロールは「できること」の一覧で、そこにない動詞はできません。

確かめ終わったので、外します。remove-iam-policy-binding は、付けたときと同じ --member と --role を書きます。

ロールを外す⌘↵
gcloud config set account you@tsubame.examplegcloud projects remove-iam-policy-binding tsubame-shop --member=user:alice@tsubame.example --role=roles/storage.objectViewer --format="value(bindings.role)"

残ったロールは roles/owner だけです。--format で、ポリシーのロールの名前だけを出しました。

よくある書き間違いは、--member の種類の書き忘れです。

user: を書き忘れるエラーになる⌘↵
gcloud projects add-iam-policy-binding tsubame-shop --member=alice@tsubame.example --role=roles/storage.objectViewer

INVALID_ARGUMENT（引数がおかしい）の Invalid member type です。メールアドレスの前に、user: や group: の種類が要ります。同じように --role=storage.objectViewer と roles/ を書き忘れると、Role storage.objectViewer is not supported for this resource. になります。どちらもポリシーは変わりません。

6.4上の階層で付けたロールは、下のすべてに効く

IAM ポリシーは、組織、フォルダ、プロジェクト、リソースのどこにでも付けられます。そして、上に付けたロールは、その下のすべてに効きます。これを継承と呼びます。

いまの alice は tsubame-dev について何の権限もなく、gcloud projects describe tsubame-dev は does not have permission to access projects instance [tsubame-dev] (or it may not exist) で断られます。「権限がないか、存在しないか」のどちらかで、どちらなのかは教えてくれません。権限のない人に「そういう名前のプロジェクトがある」と知られないためです。

tsubame-dev の上に何があるかを get-ancestors で確かめてから、フォルダ dev に、開発チームのグループ dev-team@（alice と you）で roles/viewer を付けます。人ではなくグループに付けておくと、メンバーが入れ替わってもポリシーを書き換えずに済みます。

フォルダにロールを付ける⌘↵
gcloud config set account you@tsubame.examplegcloud projects get-ancestors tsubame-devgcloud resource-manager folders add-iam-policy-binding 183663902618 --member=group:dev-team@tsubame.example --role=roles/viewergcloud projects get-iam-policy tsubame-dev --flatten="bindings[].members" --format="table(bindings.role, bindings.members)"

祖先は下から順に、プロジェクト、フォルダ 183663902618（dev）、組織です。IAM は、この並びのポリシーを全部見ます。フォルダのポリシーには dev-team@ が増えましたが、最後の tsubame-dev 自身のポリシーには出てきません。

get-iam-policy が出すのは、そのリソースに直接付いたポリシーだけです。継承された分は、上の階層のポリシーを見ないと分かりません（「クラウドを見る」のパネルでは、上から継承したものもまとめて出ます）。それでも、alice は見られるようになっています。

alice に切り替えて確かめる⌘↵
gcloud config set account alice@tsubame.examplegcloud projects describe tsubame-dev --format="value(projectId,parent.type,parent.id)"gcloud projects listgcloud config set account you@tsubame.example

tsubame-dev は見られます。gcloud projects list にも、tsubame-dev だけが出ます。フォルダの外の tsubame-shop は出てきません。確かめたら、you に戻しておきます。

継承は外せない（許可の和）

効いている許可は、組織からリソースまでのポリシーの和（どれか 1 つで許されれば許可）です。下の階層で「上から来たロールを打ち消す」ことはできません。試しに、tsubame-dev から外そうとしてみます。

下からは外せないエラーになる⌘↵
gcloud projects remove-iam-policy-binding tsubame-dev --member=group:dev-team@tsubame.example --role=roles/viewer

Policy binding with the specified principal, role, and condition not found! と言われます。tsubame-dev のポリシーには、もともとその行がないからです。外すなら、付けた場所（フォルダ dev）で外します。だから、上の階層ほど慎重に付けます。組織に Editor を付けると、すべてのプロジェクトの Editor になります。

深掘り拒否ポリシー

本物の Google Cloud には、許可の和とは別に拒否ポリシー（deny policy）があり、「この権限だけは、だれにも使わせない」を上の階層から強制できます。拒否は許可より先に評価されます。この本では扱いません（公式ドキュメントの「IAM 拒否ポリシー」を参照）。

6.5プロジェクトより狭く：バケットに付ける

プロジェクトに roles/storage.objectViewer を付けると、そのプロジェクトのすべてのバケットが読めます。価格表のバケットだけで十分なら、バケットのポリシーに付けます。必要な人に、必要な場所で、必要な権限だけを渡す。これを最小権限の原則と呼びます。

さきほど作ったカスタムロールを、bob にバケットだけで付けます。

バケットの IAM ポリシーに付ける⌘↵
gcloud storage buckets add-iam-policy-binding gs://tsubame-shop-ch06 --member=user:bob@tsubame.example --role=projects/tsubame-shop/roles/priceReader --format=nonegcloud storage buckets get-iam-policy gs://tsubame-shop-ch06 --format="yaml(bindings)"

bob のバインディングの下に、roles/storage.legacyBucketOwner などの行があります。バケットを作ると自動で付くもので、projectOwner:tsubame-shop（このプロジェクトの Owner 全員）のような便宜上のプリンシパルに、プロジェクトの基本ロールに見合うロールを渡しています。you が自分のバケットを読めるのは、これのおかげです。

bob で確かめる⌘↵
gcloud auth login bob@tsubame.examplegcloud storage cat gs://tsubame-shop-ch06/price.csvgcloud config set account you@tsubame.example

いちいち切り替えるのが面倒なときは、gcloud のどのコマンドにも付けられる --account で、その 1 回だけ別のアカウントとして実行できます（ログイン済みのアカウントに限ります）。

bob にバケットの一覧は見られないエラーになる⌘↵
gcloud storage ls --account=bob@tsubame.example

価格表は読めますが、プロジェクトのバケットの一覧（storage.buckets.list）は見られません。bob の権限は、このバケットの中だけで効いています。

6.6条件付きのロール：期限を付ける

「棚卸しの日だけ、bob に読ませたい」。こういうときは、バインディングに条件（IAM Conditions）を付けます。条件は CEL という小さな式の言語で書き、式が真のときだけロールが効きます。request.time はリクエストの時刻（UTC）です。

18:00（UTC）までの期限付きで付ける⌘↵
gcloud projects add-iam-policy-binding tsubame-shop --member=user:bob@tsubame.example --role=roles/storage.objectViewer --condition='expression=request.time < timestamp("2026-11-16T18:00:00Z"),title=until-1800,description=棚卸しの日だけ'

バインディングに condition が付き、ポリシーの version が 3 になりました。条件を含むポリシーは version 3 です。

比べるために、もう期限が過ぎた条件で alice にも付けてみます。いまはこの世界の時計で 2026 年 11 月 16 日です。

期限切れの条件で付ける⌘↵
gcloud projects add-iam-policy-binding tsubame-shop --member=user:alice@tsubame.example --role=roles/storage.objectViewer --condition='expression=request.time < timestamp("2026-11-01T00:00:00Z"),title=expired' --format=nonegcloud projects get-iam-policy tsubame-shop --flatten="bindings[].members" --format="table(bindings.role, bindings.members, bindings.condition.title)"

TITLE の欄が、条件の名前です。ポリシーの上では、bob も alice も同じロールを持っています。

期限切れの alice は読めないエラーになる⌘↵
gcloud storage cat gs://tsubame-shop-ch06/price.csv --account=alice@tsubame.example

条件が偽なので、ロールは効いていません。期限付きのロールは、期限が来たら自動で効かなくなります。外し忘れを防げます。ただし、バインディングそのものはポリシーに残るので、あとで片付けます。

条件には title が必須です。書き忘れると argument --condition: condition must have both expression and title で止まります。

条件付きのバインディングを外すときは、どの条件のものかを --condition で指定するか、--all で全部外します。

条件付きのバインディングを外す⌘↵
gcloud projects remove-iam-policy-binding tsubame-shop --member=user:alice@tsubame.example --role=roles/storage.objectViewer --all --format=nonegcloud projects get-iam-policy tsubame-shop --flatten="bindings[].members" --format="table(bindings.role, bindings.members, bindings.condition.title)"
メモこのサイトの GCP では

条件の式は、request.time < timestamp("…") と resource.name.startsWith("…") の 2 つの形だけを解釈します。本物は日時の関数、リソースの種類、タグなど、もっと多くを書けます。

6.7組織のポリシー：社外の人を付けさせない

IAM は「だれに何を許すか」です。これとは別に、組織のポリシー（Organization Policy）は「この組織では、だれであってもこれはさせない」という枠を決めます。たとえば iam.allowedPolicyMemberDomains（ドメインで制限された共有）は、IAM ポリシーに書けるプリンシパルを、指定した組織のアカウントだけに限ります。

組織のポリシーは、yaml のファイルに書いて gcloud org-policies set-policy で設定します。allowedValues には、許す組織の顧客 ID（Workspace / Cloud Identity の ID、第 5 章）を書きます。下のブロックでは、まだ縛りのない今のうちに社外の個人アカウント taro@example.com にロールを付けてから（通ってしまいます）、ファイルを作ります。

社外の人を付けてから、ポリシーのファイルを作る⌘↵
gcloud projects add-iam-policy-binding tsubame-shop --member=user:taro@example.com --role=roles/viewer --format=nonecat > domain.yaml <<'EOF'name: organizations/405918273641/policies/iam.allowedPolicyMemberDomainsspec:  rules:  - values:      allowedValues:      - C03k8x2pqEOF
設定しようとすると拒否されるエラーになる⌘↵
gcloud org-policies set-policy domain.yaml

you は組織の管理者（Organization Administrator）ですが、orgpolicy.policies.create を持っていません。組織のポリシーを変えるには、別のロール Organization Policy Administrator（roles/orgpolicy.policyAdmin）が要ります。組織の管理者は組織の IAM ポリシーを書き換えられるので、自分に付けます。

自分に付けてから設定する⌘↵
gcloud organizations add-iam-policy-binding 405918273641 --member=user:you@tsubame.example --role=roles/orgpolicy.policyAdmin --format=nonegcloud org-policies set-policy domain.yaml

これで、組織の下のどこにも、社外のアカウントを付けられなくなりました。

社外の人を付けようとするエラーになる⌘↵
gcloud projects add-iam-policy-binding tsubame-dev --member=user:taro@example.com --role=roles/viewer

One or more users named in the policy do not belong to a permitted customer, perhaps due to an organization policy. は、「許された顧客（組織）に属さない人が入っている。組織のポリシーのせいかもしれない」です。PERMISSION_DENIED ではなく FAILED_PRECONDITION（前提条件を満たさない）なのが目印です。you の権限は足りていて、組織の決まりに反しているのです。

組織のポリシーも、IAM と同じように下へ継承されます。--effective で、プロジェクトに実際に効いているものを見られます。ただし、ルールはこれからの書き換えを止めるだけで、すでにある割り当ては消しません。下のブロックの 2 つ目と 3 つ目で、最初に付けた taro が残っていることを確かめ、自分で外します。

効いているポリシーと、前からある割り当て⌘↵
gcloud org-policies describe iam.allowedPolicyMemberDomains --project=tsubame-dev --effectivegcloud projects get-iam-policy tsubame-shop --flatten="bindings[].members" --filter="bindings.members:taro" --format="value(bindings.role)"gcloud projects remove-iam-policy-binding tsubame-shop --member=user:taro@example.com --role=roles/viewer --format=none

組織に付けたルールが、tsubame-dev にも効いています。taro の roles/viewer は、ルールを設定する前に付けたので残っていました。

6.8「Permission … denied」を読み、監査ログで確かめる

権限のエラーは、どれも同じ 3 つを教えてくれます。だれが、どの権限で、どのリソースにです。alice に、自分で自分にロールを付けさせてみます。

alice が自分にロールを付けようとするエラーになる⌘↵
gcloud projects add-iam-policy-binding tsubame-shop --member=user:alice@tsubame.example --role=roles/storage.admin --account=alice@tsubame.example

エラーの文を部分に分けて読みます。Cloud Storage のエラー（alice@tsubame.example does not have storage.objects.get access …）も、並び順が違うだけで同じ 3 つが入っています。

エラーの部分意味
PERMISSION_DENIED / HTTPError 403認証（だれか）は済んでいて、認可（してよいか）で止まった
Permission 'resourcemanager.projects.setIamPolicy'足りない権限。これを含むロールを探す
on resource '//cloudresourcemanager.googleapis.com/projects/tsubame-shop'どのリソースで確かめたか。この場所か、その上に付ける
(or it may not exist)リソースがないときも同じ文になる。名前の打ち間違いも疑う
alice@tsubame.example does not have …だれとして呼んだか。gcloud auth list で思っていたアカウントかを確かめる

直し方は、「足りない権限を含むロールを、そのリソースか上の階層で、その人に付けてもらう」です。権限の名前からロールを探すには、gcloud iam roles describe で中身を見比べます。

監査ログに残る

拒否された操作は、プロジェクトの監査ログ（Cloud Audit Logs）の管理アクティビティのログに残ります。管理者は、だれが何をしようとして止められたかを、あとから調べられます。gcloud logging read にフィルタを付けて読みます（詳しくは第 16 章）。

拒否の記録を読む⌘↵
gcloud logging read 'protoPayload.status.code=7' --format="table(protoPayload.authenticationInfo.principalEmail, protoPayload.methodName, protoPayload.authorizationInfo[0].permission)"gcloud logging read 'protoPayload.status.code=7 AND protoPayload.methodName="SetIamPolicy"' --limit=1 --format="yaml(protoPayload)"

status.code=7 は gRPC の PERMISSION_DENIED の番号です。1 つ目の表には、いま試した alice の SetIamPolicy と、さきほど bob がバケットの一覧を見ようとした storage.buckets.list が、権限の名前つきで出ています。2 つ目で 1 件を詳しく見ると、エラーの 3 つの要素がそのまま入っています。authenticationInfo.principalEmail がだれ、authorizationInfo の permission と granted: false が拒否された権限、resourceName がどこです。alice が price.csv を読もうとして断られた記録は、ここには出ません。オブジェクトの読み取りはデータアクセスの監査ログの側で、既定では記録されないからです（第 16 章）。

要点まとめ
  • IAM は「プリンシパルに、ロール（権限の束）を、リソースで」。その組（バインディング）を、リソースごとの IAM ポリシーに書く
  • get-iam-policy に --flatten="bindings[].members" を付けると、1 人 1 行の表で読める
  • ロールは基本（広すぎる）、事前定義（ふだんはこれ）、カスタム（自分で権限を選ぶ）の 3 種類。中身は gcloud iam roles describe
  • 上の階層のロールは下のすべてに効き、効く許可は和になる。下からは外せないので、上ほど慎重に、グループに付ける
  • バケットなどリソースに付ければ範囲を狭められ、--condition で期限も付けられる（最小権限）
  • 組織のポリシーは、IAM の外側の枠。iam.allowedPolicyMemberDomains で社外のアカウントを付けられなくなる（FAILED_PRECONDITION）
  • 「Permission … denied」は、だれが・どの権限で・どのリソースに、を読む。拒否は監査ログに残る

6.9確認問題

ロールを付け、ポリシーを読む問題です。どの問題も、章の準備（フォルダ dev、プロジェクト tsubame-dev、バケット gs://tsubame-shop-ch06）が済んだ状態から始まります。

問 1

ロールを持つ人を一覧にする

正解済み

tsubame-shop の IAM ポリシーで、roles/storage.objectViewer を持っているプリンシパルを、user:alice@tsubame.example の形で 1 行に 1 つ表示してください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番は問わない）
ヒント

--flatten="bindings[].members" で 1 人 1 行にし、--filter="bindings.role=…" でロールを絞ります。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud projects add-iam-policy-binding tsubame-shop --member=user:alice@tsubame.example --role=roles/storage.objectViewer --format=nonegcloud projects add-iam-policy-binding tsubame-shop --member=user:bob@tsubame.example --role=roles/viewer --format=none
模範解答
gcloud projects get-iam-policy tsubame-shop --flatten="bindings[].members" --filter="bindings.role=roles/storage.objectViewer" --format="value(bindings.members)"
問 2

バケットだけで読ませる

正解済み

bob（bob@tsubame.example）が gs://tsubame-shop-ch06 のオブジェクトを読めるように、バケットの IAM ポリシーに roles/storage.objectViewer を付けてください。プロジェクトのポリシーには付けないでください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

gcloud storage buckets add-iam-policy-binding gs://… --member=user:… --role=… です。

確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

gcloud storage buckets get-iam-policy gs://tsubame-shop-ch06 --flatten="bindings[].members" --filter="bindings.members:bob" --format="value(bindings.role)"echo "project: $(gcloud projects get-iam-policy tsubame-shop --flatten="bindings[].members" --filter="bindings.members:bob" --format="value(bindings.role)")"
模範解答
gcloud storage buckets add-iam-policy-binding gs://tsubame-shop-ch06 --member=user:bob@tsubame.example --role=roles/storage.objectViewer
問 3

在庫を見るだけのカスタムロール

正解済み

tsubame-shop に、ID が stockViewer、権限が storage.objects.list だけのカスタムロールを作ってください。タイトルは自由です。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

gcloud iam roles create ID --project=… --permissions=… です。権限が 1 つなら、カンマは要りません。

確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

gcloud iam roles describe projects/tsubame-shop/roles/stockViewer --format="value(name, includedPermissions)"
模範解答
gcloud iam roles create stockViewer --project=tsubame-shop --title="Stock Viewer" --permissions=storage.objects.list
問 4

フォルダに付けて、中のプロジェクトに効かせる

正解済み

分析チームのグループ analysts@tsubame.example が tsubame-dev を見られるように、フォルダ dev（ID 183663902618） に roles/viewer を付けてください。プロジェクトのポリシーには付けないでください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

gcloud resource-manager folders add-iam-policy-binding フォルダID --member=group:… --role=… です。

確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

gcloud resource-manager folders get-iam-policy 183663902618 --flatten="bindings[].members" --format="value(bindings.role, bindings.members)"echo "project: $(gcloud projects get-iam-policy tsubame-dev --flatten="bindings[].members" --filter="bindings.members:analysts" --format="value(bindings.role)")"gcloud auth login bob@tsubame.example 2>/dev/nullgcloud projects describe tsubame-dev --format="value(projectId)"
模範解答
gcloud resource-manager folders add-iam-policy-binding 183663902618 --member=group:analysts@tsubame.example --role=roles/viewer
