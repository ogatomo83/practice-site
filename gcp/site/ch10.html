10.1Cloud Run は何をしてくれるか

第 8 章の Compute Engine では、VM を作り、OS に入り、アプリを起動しました。台数を決めるのも、止めるのも自分です。Cloud Run（クラウド ラン）は、そこをまとめて引き受けるサービスです。渡すのはコンテナのイメージだけです。

コンテナは、アプリと、それが動くのに要るもの（ライブラリ、設定）を 1 つに包んだ箱です。その箱の設計図を固めたファイルをイメージと呼びます。Cloud Run にイメージを渡すと、次のものができます。

  • サービス：Cloud Run の 1 つのアプリです。名前と、HTTPS の URL を持ちます
  • リビジョン：イメージと設定（環境変数、メモリ、ポート番号など）の組の「版」です。設定を変えるたびに新しいリビジョンができます
  • インスタンス：リビジョンのコンテナを実際に動かしている 1 台ぶんです。要求が来ないときは 0 台まで減ります

VM と違い、サーバの台数も OS も見えません。こういう使い方をサーバーレスと呼びます。サーバがないのではなく、サーバのことを考えなくてよい、という意味です。

まず、サンプルのイメージ us-docker.pkg.dev/cloudrun/container/hello（Google が公開している「動いたよ」と返すだけのアプリ）を置いてみます。

場所を指定しないでデプロイするエラーになる⌘↵
gcloud run deploy hello --image=us-docker.pkg.dev/cloudrun/container/hello

Missing required argument [--region] は「リージョンを決めてください」です。Cloud Run のサービスはリージョンの中に作ります（第 3 章）。--region を付けて、もう一度試します。

リージョンを付けて、もう一度エラーになる⌘↵
gcloud run deploy hello --image=us-docker.pkg.dev/cloudrun/container/hello --region=asia-northeast1

今度は Cloud Run Admin API has not been used in project … or it is disabled です。第 3 章で見た「API が無効」のエラーです。run.googleapis.com を有効にします。あわせて、毎回 --region を付けなくて済むように、run/region の設定に既定値を入れておきます。

API を有効にし、既定のリージョンを決める⌘↵
gcloud services enable run.googleapis.comgcloud config set run/region asia-northeast1

10.2最初のデプロイ：イメージを渡すと URL が返る

もう一度デプロイします。途中で 1 つ質問が出るので、N（いいえ）と答えます。

hello をデプロイする入力：N ⏎⌘↵
gcloud run deploy hello --image=us-docker.pkg.dev/cloudrun/container/hello

出力を上から読みます。

  • Allow unauthenticated invocations to [hello] (y/N)?：「認証なしの呼び出しを許しますか」。いまは N と答えました。意味は次の節で確かめます
  • Creating Revision... Routing traffic...：リビジョンを作り、要求をそこへ流す設定をしています
  • revision [hello-00001-…]：最初のリビジョンの名前です。サービス名、通し番号、短い乱数のような文字の 3 つでできています
  • Service URL: https://hello-365600345236.asia-northeast1.run.app：このサービスの URL です。サービス名、プロジェクト番号、リージョンが入っています

数十秒で HTTPS の URL ができました。証明書もロードバランサも、自分では何も用意していません。

サービスの一覧と、詳しい情報⌘↵
gcloud run services listgcloud run services describe hello

describe の Traffic: の 100% LATEST は「要求の 100% を最新のリビジョンへ流す」です。その下に、リビジョンの中身が並びます。Port: 8080、Memory: 512Mi、CPU: 1000m（1 vCPU）、Concurrency: 80、Max instances: 100 は、何も指定しなかったときの値です。この節の後で 1 つずつ変えていきます。

メモこのサイトの GCP では

本物の gcloud run deploy は、Cloud Run がイメージを取り込み、コンテナを起動して、待ち受けを確かめるまで待ちます。このサイトでは、サンプルのイメージ（hello、hello-app、nginx）と、あなたが書いた Node.js のコードだけを動かせます。どれもこのページの中で動き、仮想の時計が本物と同じくらい進みます。

10.3だれが呼べるか：run.invoker と ID トークン

URL を curl で開いてみます。URL は describe の --format で取り出して、変数に入れておきます。

URL を開く⌘↵
URL=$(gcloud run services describe hello --format="value(status.url)")curl $URL

403 Forbidden、Your client does not have permission to get URL / from this server. が返りました。さきほど認証なしの呼び出しを許さなかったので、だれでも開けるわけではないのです。

サービスを呼ぶのに要る権限は run.routes.invoke で、それを含むロールが roles/run.invoker（Cloud Run 起動元）です。サービスを作った人は、プロジェクトのオーナーなので、この権限を持っています。ただ、それを証明するものを curl に持たせていません。証明には ID トークン（「わたしはだれか」を Google が署名した短い文字列）を使います。

ID トークンを付けて呼ぶ。アクセス トークンではだめ⌘↵
curl -H "Authorization: Bearer $(gcloud auth print-identity-token)" $URLcurl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer $(gcloud auth print-access-token)" $URL

1 つめは It's running! のページが返りました。Service: hello と Revision: hello-00001-… は、コンテナが自分の名前を環境変数から読んで出しています。

2 つめは 401 です。gcloud auth print-access-token のアクセス トークンは「API を呼んでよい」という券で、Cloud Run のサービスの入口では受け付けません。Cloud Run には ID トークンを渡す、と覚えてください。

だれでも呼べるようにする

お店の Web サイトのように、だれにでも開いてほしいサービスもあります。それには allUsers（インターネットのだれでも。第 5 章）に roles/run.invoker を付けます。サービスの IAM ポリシーに割り当てを足すのは、第 6 章と同じ add-iam-policy-binding です。

allUsers に run.invoker を付ける⌘↵
gcloud run services add-iam-policy-binding hello --member=allUsers --role=roles/run.invokercurl $URL

トークンなしの curl $URL でも、ページが返るようになりました。デプロイのときに --allow-unauthenticated を付けるのは、この割り当てを一緒に作ることです。最初の質問に y と答えても同じになります。

注意公開は「だれでも」の意味

allUsers に roles/run.invoker を付けると、URL を知っている世界中のだれもが呼べます。社内だけで使う API は公開せず、使う人やサービスアカウントにだけ roles/run.invoker を付けます。外すには gcloud run services remove-iam-policy-binding を使います。

10.4リビジョンとトラフィック：変更は新しい版になる

アプリに設定を渡すいちばん簡単な方法は、環境変数です。hello のイメージは、NAME という環境変数があると、それもページに出します。

環境変数を足して、リビジョンを見る⌘↵
gcloud run services update hello --update-env-vars=NAME=tsubamecurl $URLgcloud run revisions list --service=hello
  • services update の出力に、新しいリビジョン hello-00002-… ができたと出ました。環境変数を変えただけでも、新しい版になります
  • curl のページに NAME: tsubame が出ました
  • revisions list には 2 つのリビジョンが並び、ACTIVE が yes なのは新しいほうだけです。古い版は消えずに残っています

--update-env-vars は「足す・書き換える」で、ほかの変数は残します。--set-env-vars は「全部をこれにする」で、書かなかった変数は消えます。

いくつかの名前は Cloud Run が使うので、自分では付けられません。

PORT は自分で付けられないエラーになる⌘↵
gcloud run services update hello --update-env-vars=PORT=9000

The following reserved env names were provided: PORT. は「予約された名前です」です。PORT（待ち受けるポート番号）、K_SERVICE（サービス名）、K_REVISION（リビジョン名）は、Cloud Run がコンテナに渡します。ポート番号を変えたいときは、後で見る --port を使います。

トラフィックを分けて、少しずつ切り替える

リビジョンが残っているので、要求をどのリビジョンにどれだけ流すかを選べます。これをトラフィック分割と呼びます。

試しやすいように、Version: 1.0.0 と返す gcr.io/google-samples/hello-app:1.0 と、Version: 2.0.0 と返す :2.0 を使います。--revision-suffix でリビジョンの名前の後ろを決めておくと、名前が web-v1 のように読みやすくなります。

1.0 を公開し、2.0 を 0% で置く⌘↵
gcloud run deploy web --image=gcr.io/google-samples/hello-app:1.0 --revision-suffix=v1 --allow-unauthenticatedgcloud run deploy web --image=gcr.io/google-samples/hello-app:2.0 --revision-suffix=v2 --tag=green --no-trafficWEB=$(gcloud run services describe web --format="value(status.url)")curl $WEB; curl https://green---web-365600345236.asia-northeast1.run.app
  • 2 回目のデプロイは is serving 0 percent of traffic です。--no-traffic で、置くだけにしました
  • --tag=green で、web-v2 だけに届く URL https://green---web-….run.app ができました（サービス名の前に タグ--- が付きます）
  • ふつうの URL は Version: 1.0.0、タグの URL は Version: 2.0.0 を返しました

お客さんに見せる前に、タグの URL で新しい版を確かめられます。よさそうなら、半分を流してみます。

半分ずつ流してから、1.0 に戻す⌘↵
gcloud run services update-traffic web --to-revisions=web-v2=50for i in 1 2 3 4; do curl -s $WEB | grep Version; donegcloud run services update-traffic web --to-revisions=web-v1=100
  • 1 つめの出力の Traffic: は 50% web-v2、50% web-v1 です。指定しなかった残りの 50% は、それまでのリビジョンに残りました
  • 4 回の curl は、2.0.0 と 1.0.0 が交互に返りました
  • 最後のコマンドで、すべてが web-v1 に戻りました。新しい版を消したわけではないので、--to-latest でいつでも最新に戻せます
コツLATEST とリビジョン名

最初の 100% LATEST は「いちばん新しいリビジョンに流す」という指定です。この状態で deploy すると、新しいリビジョンにすぐ 100% が流れます。--to-revisions=web-v1=100 のように名前で決めると、その後に deploy しても、指定し直すまで web-v1 のままです。

10.5自分のコードを載せる：ソースから、Dockerfile から

サンプルではなく、自分の Node.js のアプリを載せます。つばめ文具の注文 API の芽にあたる、小さな express のアプリです。Cloud Run は、ソースのディレクトリからイメージを組み立てて、そのままデプロイできます。組み立ては Cloud Build（ビルドを代わりに実行するサービス）が、できたイメージの置き場は Artifact Registry（イメージの倉庫）が受け持ちます。どちらの API も有効にしておきます。

API を有効にして、アプリを書く⌘↵
gcloud services enable cloudbuild.googleapis.com artifactregistry.googleapis.commkdir -p ~/shop && cd ~/shopcat > server.js <<'EOF'const express = require('express');const app = express();let count = 0;   // このインスタンスのメモリの中にある数app.get('/', (req, res) => {  count++;  console.log(`request ${count}`);  res.send(`count=${count} revision=${process.env.K_REVISION}\n`);});const port = process.env.PORT || 8080;app.listen(port, () => console.log(`listening on port ${port}`));EOFcat > package.json <<'EOF'{  "name": "shop",  "version": "1.0.0",  "scripts": { "start": "node server.js" },  "dependencies": { "express": "^4.21.0" }}EOF

server.js は、/ への要求ごとに数を 1 つ増やして返します。大事なのは最後の 2 行で、PORT の環境変数のポート番号で待ち受けます。package.json の scripts.start が、起動のコマンドです。

ソースからデプロイする入力：Y ⏎⌘↵
gcloud run deploy shop --source=. --allow-unauthenticated
  • A repository named [cloud-run-source-deploy] in region [asia-northeast1] will be created.：イメージの置き場がまだないので作ります、という確認です。Y と答えました
  • Building using Buildpacks：Dockerfile がないので、Buildpacks（ソースを見て、言語に合わせたイメージを自動で組み立てる仕組み）を使いました。package.json があるので Node.js のアプリだと分かります
  • Uploading sources... Building Container...：ソースを送り、Cloud Build で組み立てています

できたものを確かめます。

動かして、イメージの置き場を見る⌘↵
SHOP=$(gcloud run services describe shop --format="value(status.url)")curl $SHOP; curl $SHOPgcloud artifacts repositories listgcloud artifacts docker images list asia-northeast1-docker.pkg.dev/tsubame-shop/cloud-run-source-deploy
  • count=1、count=2 と、自分のコードが返しました。revision=shop-00001-… は K_REVISION の値です
  • repositories list に、cloud-run-source-deploy（DOCKER 形式、asia-northeast1）ができています
  • docker images list に、イメージ …/cloud-run-source-deploy/shop が 1 つあります。DIGEST の sha256:… は、イメージの中身から計算した指紋です

Dockerfile を書いて、自分で組み立てる

組み立て方を細かく決めたいときは、Dockerfile（イメージの作り方を 1 行ずつ書いたファイル）を書きます。ディレクトリに Dockerfile があると、--source も Buildpacks のかわりにそれを使います。ここでは、組み立てだけを gcloud builds submit で行い、イメージを自分で作ったリポジトリに置きます。

Dockerfile を書く⌘↵
cat > Dockerfile <<'EOF'FROM node:22-slimWORKDIR /appCOPY package.json ./RUN npm install --omit=devCOPY . .CMD ["node", "server.js"]EOF

FROM が土台のイメージ（Node.js 22 の入った小さな Linux）、RUN が組み立てのときに実行するコマンド、CMD が起動のコマンドです。Artifact Registry のイメージの名前は 場所-docker.pkg.dev/プロジェクト/リポジトリ/イメージ:タグ の形です。

置き場がないまま組み立てるエラーになる⌘↵
gcloud builds submit --tag=asia-northeast1-docker.pkg.dev/tsubame-shop/shop-images/shop:v1

BUILD の段は、Dockerfile の Step 1/6 から Step 6/6 まで進みました。失敗したのは最後の PUSH で、name unknown: Repository "shop-images" not found です。--source のときと違い、置き場のリポジトリは自分で作ります。

リポジトリを作って、組み立て直す⌘↵
gcloud artifacts repositories create shop-images --repository-format=docker --location=asia-northeast1gcloud builds submit --tag=asia-northeast1-docker.pkg.dev/tsubame-shop/shop-images/shop:v1

今度は PUSH の後に DONE、最後の表の STATUS が SUCCESS です。できたイメージを --image で渡せば、ソースなしでデプロイできます。

組み立てたイメージをデプロイする⌘↵
gcloud run deploy shop --image=asia-northeast1-docker.pkg.dev/tsubame-shop/shop-images/shop:v1curl $SHOP

同じサービス shop に、2 つめのリビジョン shop-00002-… ができました。URL は変わりません。新しいリビジョンは新しいインスタンスで動くので、count=1 から数え直しています。

メモこのサイトの GCP では

gcloud builds submit は --tag の使い方だけに対応し、Dockerfile は FROM node:… かサンプルのイメージのものだけを組み立てます。RUN npm install は実際には実行せず、require('express') はこのページの中の小さな express が受けます。本物では、cloudbuild.yaml で何段ものビルドを書けます。

10.6PORT：コンテナは決まった番号で待つ

Cloud Run は、コンテナに PORT の環境変数（既定では 8080）を渡し、そのポート番号に要求を送ります。だから、アプリは PORT の番号で待ち受けなければなりません。server.js の process.env.PORT || 8080 はそのための 1 行です。

決まった番号で待つアプリを、そのまま置くとどうなるかを見てみます。Web サーバの nginx の公式イメージは、80 番で待ちます。

80 番で待つ nginx を、そのまま置くエラーになる⌘↵
gcloud run deploy nginx --image=nginx --allow-unauthenticated

The user-provided container failed to start and listen on the port defined provided by the PORT=8080 environment variable は、「PORT=8080 で待ち受けるはずのコンテナが、時間内に待ち受けを始めなかった」です。Cloud Run は、新しいリビジョンの 8080 番につながるかを確かめ（起動プローブ）、つながらないリビジョンには要求を流しません。理由はログにも残ります。

ログで理由を見て、--port=80 で作り直す⌘↵
gcloud run services logs read nginxgcloud run services delete nginx --quietgcloud run deploy nginx --image=nginx --port=80 --allow-unauthenticatedcurl -s $(gcloud run services describe nginx --format="value(status.url)") | grep title
  • ログの Default STARTUP TCP probe failed 1 time consecutively for container "nginx-1" on port 8080. が、起動プローブの失敗です。その前の行で、nginx 自身は起動を終えています
  • 一度も動かなかったサービスなので消して、--port=80 を付けて作り直しました。--port は「コンテナはこの番号で待つ」と Cloud Run に教えるフラグで、PORT の値も 80 になります
  • Welcome to nginx! のページが返りました

自分で書くアプリは PORT を読むようにし、読めない既製のイメージには --port を付ける、と覚えてください。

10.7スケール：0 まで減り、要求で増える

Cloud Run は、要求の量に合わせてインスタンスの数を増やしたり減らしたりします。要求がなければ 0 台です。0 台のときに要求が来ると、まずインスタンスを起動してから応えます。これをコールドスタートと呼びます。

shop の count で確かめます。sleep 16m は、仮想の時計を 16 分進めます。

しばらく使わないと、数え直しになる⌘↵
curl $SHOP; curl $SHOPsleep 16mcurl $SHOP

count=2、count=3 と続いた後、16 分あけた要求は count=1 に戻りました。インスタンスが止められ、新しいインスタンスで動き直したからです。かかった時間はリクエストのログの httpRequest.latency に残ります。

コールドスタートの遅れをログで見る⌘↵
gcloud logging read 'resource.type=cloud_run_revision AND resource.labels.service_name=shop AND httpRequest.status=200' --order=asc --format="table(timestamp, resource.labels.revision_name, httpRequest.latency)"

インスタンスを起こした要求（各リビジョンの最初と、16 分あけた後）だけ、LATENCY が 1 秒を超えています。ほかは数ミリ秒です。同じ時刻の行は、表の中で順番が前後することがあります。

ここから 2 つのことが分かります。

  1. メモリの中に、残したいデータを置かない。 注文や在庫のような残すべきデータは、Firestore（第 13 章）や Cloud SQL（第 14 章）に書きます
  2. 最初の要求の遅れが困るなら、--min-instances で最低の台数を決める。 その台数は要求がなくても動き続けるので、そのぶんの料金がかかります
最低 1 台を残し、上限と同時実行も決める⌘↵
gcloud run services update shop --min-instances=1 --max-instances=3 --concurrency=80curl $SHOPsleep 30mcurl $SHOP

--min-instances=1 にした後は、30 分あけても count=2 と続きました。インスタンスが止められずに残ったからです。

  • --max-instances：台数の上限です。急な要求の山で料金が膨らむのを防いだり、つなぐ先のデータベースを守ったりします
  • --concurrency：1 台が同時に受ける要求の数の上限です（既定は 80）。上限を超えそうになると、台数を増やします。1 にすると「1 台は 1 つずつ」になります
メモこのサイトの GCP では

インスタンスは、リビジョンごとに 1 台だけ動かします。15 分使われないと止まり、次の要求でコールドスタートします（--min-instances が 1 以上なら止まりません）。本物は、要求の量に応じて同時に何台も動き、使われないインスタンスをいつ止めるかも Cloud Run が決めます。

料金は、既定の「リクエスト単位の課金」では、要求を処理している間の vCPU とメモリと、要求の数で決まります。0 台の間はかかりません。毎月の無料枠は、200 万リクエスト、メモリ 360,000 GB 秒、vCPU 180,000 秒、北米からの外向き転送 1 GB です。組み立てに使う Cloud Build には毎月 2,500 ビルド分（e2-standard-2 での分数）、Artifact Registry にはストレージ 0.5 GB の無料枠があります。古いイメージが溜まると、Artifact Registry のストレージ料金がかかります。

10.8サービスアカウントとログ

コンテナの中のコードが、Cloud Storage や Firestore の API を呼ぶとき、だれとして呼ぶのでしょうか。答えはリビジョンのサービスアカウントです。何も指定しないと、describe で見たとおり、Compute Engine の既定のサービスアカウント（365600345236-compute@developer.gserviceaccount.com）になります。第 5 章で見たように、これは権限が広すぎることが多いので、サービスごとに専用のものを作って付けます。

専用のサービスアカウントで動かす⌘↵
gcloud iam service-accounts create shop-run --display-name="shop の Cloud Run"gcloud run services update shop --service-account=shop-run@tsubame-shop.iam.gserviceaccount.comgcloud run services describe shop --format="value(spec.template.spec.serviceAccountName)"

新しいリビジョンから、shop-run@tsubame-shop.iam.gserviceaccount.com として動きます。このサービスアカウントにロールを付ければ（たとえば第 13 章で Firestore の roles/datastore.user）、コードはその範囲だけを使えます。

デプロイする人に要る権限

アプリ開発の青木さん（alice@）にも、デプロイを任せます。Cloud Run のサービスを作り変えるロールは roles/run.developer です。

run.developer を付けて、alice としてデプロイするエラーになる⌘↵
gcloud projects add-iam-policy-binding tsubame-shop --member=user:alice@tsubame.example --role=roles/run.developer --format=nonegcloud auth login alice@tsubame.examplegcloud run deploy api --image=us-docker.pkg.dev/cloudrun/container/hello --service-account=shop-run@tsubame-shop.iam.gserviceaccount.com --no-allow-unauthenticated

Permission 'iam.serviceaccounts.actAs' denied on service account shop-run@… です。サービスアカウントを付けてデプロイすると、そのサービスアカウントの権限でコードを動かせます。だから、そのサービスアカウントを「使ってよい」（iam.serviceAccounts.actAs）という許可が別に要ります。それを含むロールが roles/iam.serviceAccountUser です（第 5 章の借用と同じ考え方）。

サービスアカウントを使う許可を付ける⌘↵
gcloud auth login you@tsubame.examplegcloud iam service-accounts add-iam-policy-binding shop-run@tsubame-shop.iam.gserviceaccount.com --member=user:alice@tsubame.example --role=roles/iam.serviceAccountUser --format=nonegcloud auth login alice@tsubame.examplegcloud run deploy api --image=us-docker.pkg.dev/cloudrun/container/hello --service-account=shop-run@tsubame-shop.iam.gserviceaccount.com --no-allow-unauthenticated

今度は api がデプロイできました。許可は、プロジェクト全体ではなく shop-run 1 つだけに付けています。--no-allow-unauthenticated は、最初の質問に「いいえ」と答えるのと同じです。

ログを読む

コンテナが標準出力（console.log）に書いたものは、自動で Cloud Logging（第 16 章）に送られます。

shop のログを読む⌘↵
gcloud auth login you@tsubame.examplegcloud run services logs read shop --limit=8

listening on port 8080（インスタンスの起動）、Default STARTUP TCP probe succeeded …（起動プローブの成功）、request 1（console.log の行）、GET 200 https://shop-….run.app/（Cloud Run が残すリクエストのログ）が、時刻の順に並びます。ファイルにログを書く必要はありません。標準出力に書けば集まります。

要点まとめ
  • Cloud Run は、コンテナのイメージから、HTTPS の URL を持つサービスを作る。設定を変えるたびに新しいリビジョンができ、古い版は残る
  • 呼べるのは roles/run.invoker を持つ人。公開は allUsers に付ける（--allow-unauthenticated）。非公開のサービスは ID トークン（gcloud auth print-identity-token）で呼ぶ
  • update-traffic --to-revisions で、リビジョンごとに要求の割合を決める。--tag と --no-traffic で、新しい版を 0% で置いて試せる
  • --source は Cloud Build で組み立て、Artifact Registry の cloud-run-source-deploy に置く。Dockerfile と gcloud builds submit --tag でも作れる
  • コンテナは PORT（既定 8080）で待つ。違う番号で待つイメージには --port
  • インスタンスは 0 台まで減り、次の要求でコールドスタートする。メモリの中のデータはインスタンスごとで、消える。--min-instances、--max-instances、--concurrency で調整する
  • コードはリビジョンのサービスアカウントとして動く。付けるには、そのサービスアカウントの actAs（roles/iam.serviceAccountUser）が要る

10.9確認問題

Cloud Run のサービスを、自分のコマンドで変えてみます。どの問題も、Cloud Run の API と既定のリージョン（asia-northeast1）は準備してあります。

問 1

だれでも呼べるようにする

正解済み

サービス hello は、いまは認証のある要求しか受け付けません。トークンなしの curl でも開けるように、サービス hello の IAM ポリシーを変えてください（サービスをデプロイし直さずに）。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

インターネットのだれでも、を表すメンバーは allUsers です。呼び出しのロールは roles/run.invoker です。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud services enable run.googleapis.comgcloud config set run/region asia-northeast1gcloud run deploy hello --image=us-docker.pkg.dev/cloudrun/container/hello --no-allow-unauthenticated
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

gcloud run services get-iam-policy hello --flatten="bindings[].members" --format="value(bindings.role,bindings.members)"
模範解答
gcloud run services add-iam-policy-binding hello --member=allUsers --role=roles/run.invoker
問 2

環境変数を 1 つ足す

正解済み

サービス hello には、環境変数 NAME=tsubame が付いています。これを残したまま、環境変数 STAGE=prod を足してください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

--set-env-vars は、書かなかった変数を消します。足すだけのフラグはどちらでしたか。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud services enable run.googleapis.comgcloud config set run/region asia-northeast1gcloud run deploy hello --image=us-docker.pkg.dev/cloudrun/container/hello --set-env-vars=NAME=tsubame --no-allow-unauthenticated
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

gcloud run services describe hello --format="value(spec.template.spec.containers[0].env)"
模範解答
gcloud run services update hello --update-env-vars=STAGE=prod
問 3

新しい版に 2 割だけ流す

正解済み

サービス web には、リビジョン web-v1（hello-app 1.0）と web-v2（hello-app 2.0）があり、いまは web-v2 に 100% が流れています。web-v1 に 80%、web-v2 に 20% を流すようにしてください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定（行の順番は問わない）
ヒント

gcloud run services update-traffic サービス --to-revisions=リビジョン=割合,リビジョン=割合 の形です。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud services enable run.googleapis.comgcloud config set run/region asia-northeast1gcloud run deploy web --image=gcr.io/google-samples/hello-app:1.0 --revision-suffix=v1 --allow-unauthenticatedgcloud run deploy web --image=gcr.io/google-samples/hello-app:2.0 --revision-suffix=v2
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

gcloud run services describe web --flatten=status.traffic --format="value(status.traffic.revisionName,status.traffic.percent)"
模範解答
gcloud run services update-traffic web --to-revisions=web-v1=80,web-v2=20
