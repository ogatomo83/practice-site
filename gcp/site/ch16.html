Cloud Logging と Monitoring

クラウドで起きたことは、すべてログエントリとして Cloud Logging に集まります。ログエントリの形、監査ログで「だれが・いつ・何を」を調べる方法、logging read のクエリ、構造化ログ、保持期間、シンクで BigQuery に送って集計する方法、ログベースの指標からアラートを出すまでを、手を動かして身に付けます。

16.1ログはどこから来て、どこへ行くのか

この章の準備で、第 10 章と同じように Cloud Run に小さな注文 API orders をデプロイしてあります（下の「準備」を開くと中身が見えます）。まず、ログがどう流れるかの全体を描きます。

この章の準備最初の実行のときに、自動で流れるコマンド
gcloud services enable run.googleapis.com cloudbuild.googleapis.com artifactregistry.googleapis.commkdir -p ~/orders && cd ~/orderscat > server.js <<'EOF'const http = require('http');http.createServer((req, res) => {  if (req.url === '/fail') {    console.error('在庫の取得に失敗しました');    console.error(JSON.stringify({ severity: 'ERROR', message: '注文できません', orderId: 'A-1002', reason: 'stock' }));    res.writeHead(500); res.end('error\n'); return;  }  if (req.url === '/low') {    console.log(JSON.stringify({ severity: 'WARNING', message: '在庫が残りわずかです', item: 'ノート A5', stock: 3 }));  } else {    console.log('注文を受け付けました');  }  res.end('ok\n');}).listen(process.env.PORT || 8080);EOFcat > package.json <<'EOF'{ "name": "orders", "version": "1.0.0", "main": "server.js", "scripts": { "start": "node server.js" } }EOFgcloud run deploy orders --source . --region=asia-northeast1 --allow-unauthenticated --quietcd ~

Cloud Logging（クラウド ロギング）は、プロジェクトの中で生まれたログを 1 か所に集めるサービスです。ログを書く側は、宛先を考えません。Cloud Run は標準出力を、Google Cloud の API は監査ログ（だれが何をしたかの記録）を、勝手に送ってきます。

集まったログは、ログルーターがシンク（振り分けの規則）に従って行き先を決めます。最初からあるシンクは _Required と _Default の 2 つで、ログを同じ名前のログバケット（ログの保存場所）に入れます。自分でシンクを足すと、BigQuery や Cloud Storage にも送れます。

注文 API を 3 回呼んで、ログを生ませてみます。

注文 API を呼ぶ⌘↵
URL=$(gcloud run services describe orders --region=asia-northeast1 --format='value(status.url)')curl -s $URL/curl -s $URL/lowcurl -s $URL/failgcloud logging logs list

ok、ok、error が返りました。最後の gcloud logging logs list は、ログの名前の一覧です。4 つのログがあります。cloudaudit.googleapis.com%2Factivity は準備のデプロイで残った監査ログ、run.googleapis.com%2F… の 3 つが Cloud Run のログです。%2F は / を URL の書き方にしたもので、run.googleapis.com/stdout のように読みます。この末尾の部分をログ ID と呼びます。

ログ中身
run.googleapis.com/requestsCloud Run が書く、リクエスト 1 回につき 1 行の記録（URL、ステータス、かかった時間）
run.googleapis.com/stdoutコンテナが標準出力（console.log）に書いた行
run.googleapis.com/stderrコンテナが標準エラー（console.error）に書いた行
cloudaudit.googleapis.com/activity設定を変える API の呼び出し（管理アクティビティの監査ログ）

16.2ログエントリの形

ログの 1 行をログエントリ（LogEntry）と呼びます。どのサービスのログも、同じ形をしています。gcloud logging read で、新しいものから 1 つだけ読みます。

いちばん新しいログエントリ⌘↵
gcloud logging read --limit=1

最後の /fail のリクエストの記録（requests のログ）が出ました。主な欄を表にします。

欄意味いまの出力では
logNameどのログか。projects/プロジェクト/logs/ログ ID…/logs/run.googleapis.com%2Frequests
resourceどのリソースから来たか。type が種類、labels が名前などcloud_run_revision、service_name: orders
timestamp出来事の時刻（UTC）。receiveTimestamp は Logging が受け取った時刻2026-11-16T…Z
severity重大度ERROR（500 を返したので）
textPayload / jsonPayload / protoPayload中身。文字列、JSON、監査ログなどの決まった形のどれかなし。リクエストのログは、代わりに httpRequest に URL やステータスが入る

severity（重大度）は、低いほうから DEFAULT、DEBUG、INFO、NOTICE、WARNING、ERROR、CRITICAL、ALERT、EMERGENCY の 9 段階です。この順に大小があるので、あとで severity>=ERROR のように比べられます。

ログは自分でも書けます。gcloud logging write ログ ID 中身 です。

自分でログを書く⌘↵
gcloud logging write ops-memo "棚卸しを始めます" --severity=NOTICEgcloud logging read 'logName:"logs/ops-memo"' --format="yaml(logName, resource.type, severity, textPayload)"

resource.type が global（特定のリソースに結び付かない）になりました。中身は文字列なので textPayload です。--format="yaml(…)" で、見たい欄だけに絞っています。

重大度の書き間違いエラーになる⌘↵
gcloud logging write ops-memo "棚卸しが終わりました" --severity=SEVERE
エラーargument --severity: Invalid choice: 'SEVERE'.

--severity に、9 段階にない名前を渡しました。Invalid choice（選べない値）は、gcloud がフラグの値を API に送る前に調べて断ったという意味です。SEVERE は Java のログの言葉で、Cloud Logging では ERROR か CRITICAL にあたります。

16.3監査ログ：だれが・いつ・何をしたか

Google Cloud の API を呼ぶと、その記録が監査ログ（Cloud Audit Logs）に残ります。この本でここまで打ってきた gcloud のコマンドも、裏ではすべて API の呼び出しでした。監査ログは、次の種類に分かれます。

いちばんよく見るのは管理アクティビティ（activity）です。バケットを作る、IAM を変える、デプロイするといった「変える」操作が、必ず記録されます。準備で行ったデプロイの記録を、表の形で見てみます。

管理アクティビティの監査ログ⌘↵
gcloud logging read 'logName:"cloudaudit.googleapis.com%2Factivity"' --format="table(timestamp.date('%H:%M:%S'):label=TIME, protoPayload.authenticationInfo.principalEmail:label=WHO, protoPayload.methodName:label=METHOD)"

WHO がだれが、TIME がいつ、METHOD が何をしたかです。準備で打った API の有効化（EnableService）と、Cloud Run のサービスの作成（CreateService）が、あなた（you@）の操作として残っています。

監査ログの中身は protoPayload に入っています。読むときに使う欄は次のとおりです。

欄意味
protoPayload.authenticationInfo.principalEmail呼び出したプリンシパル（人やサービスアカウント）
protoPayload.methodName呼んだ API のメソッド
protoPayload.resourceName対象のリソース
protoPayload.serviceNameAPI の名前（run.googleapis.com など）
protoPayload.status結果。空なら成功、code: 7 は権限がなくて断られた（PERMISSION_DENIED）

断られた呼び出しも残る

権限のない人が操作すると、どうなるでしょう。青木さん（alice@）は tsubame-shop に何のロールも持っていません。青木さんとしてバケットを作ってみます。

青木さんに切り替える⌘↵
gcloud auth login alice@tsubame.example
権限がないので断られるエラーになる⌘↵
gcloud storage buckets create gs://tsubame-shop-ch16-alice --location=asia-northeast1
自分に戻して、監査ログを見る⌘↵
gcloud auth login you@tsubame.examplegcloud logging read 'protoPayload.methodName="storage.buckets.create"' --format="yaml(severity, protoPayload.authenticationInfo.principalEmail, protoPayload.resourceName, protoPayload.status)"

断られた呼び出しも、severity: ERROR、status.code: 7 の監査ログとして残りました。「だれかが権限のないことを試みた」ことが、あとから分かります。

データアクセスの監査ログ

データアクセス（data_access）の監査ログは、データや設定を読む呼び出しの記録です。読む操作はとても多いので、既定ではオフです。例外は BigQuery で、クエリの記録が最初から残ります。

BigQuery のクエリは、データアクセスの監査ログに残る⌘↵
bq query --use_legacy_sql=false 'SELECT COUNT(*) AS n FROM `tsubame-public.bungu.orders`'gcloud logging read 'logName:"cloudaudit.googleapis.com%2Fdata_access"' --format="value(protoPayload.authenticationInfo.principalEmail, protoPayload.methodName)"

jobservice.jobcompleted（ジョブが終わった）の記録が 1 つあります。一方、さっきの gcloud logging read や gcloud run services describe は読む操作なので、どこにも記録されていません。

データアクセスの監査ログには、だれがどのデータを読んだかという機密に近い情報が入ります。そのため、ふつうのログ閲覧者（roles/logging.viewer）には見えません。見るにはプライベート ログ閲覧者（roles/logging.privateLogViewer）が要ります。馬場さんに roles/logging.viewer だけを付けて確かめます。

馬場さんにログ閲覧者を付けて、読んでもらう⌘↵
gcloud projects add-iam-policy-binding tsubame-shop --member=user:bob@tsubame.example --role=roles/logging.viewer --condition=None --format=nonegcloud auth login bob@tsubame.examplegcloud logging read 'logName:"cloudaudit.googleapis.com%2Factivity"' --limit=1 --format="value(protoPayload.methodName)"gcloud logging read 'logName:"cloudaudit.googleapis.com%2Fdata_access"' --format="value(protoPayload.methodName)"gcloud auth login you@tsubame.example

1 つ目の読み取り（管理アクティビティ）は結果が出ましたが、2 つ目（データアクセス）は何も出ません。エラーにもならず、ただ見えないだけです。ふつうのログと管理アクティビティは見えても、データアクセスの監査ログは隠されています。最後の行で、自分（you@）に戻しています。

メモデータアクセスの監査ログをオンにするには

本物では、プロジェクトの IAM ポリシーの auditConfigs という欄で、サービスごとに読み取り（DATA_READ）や書き込み（DATA_WRITE）の記録をオンにします。量が多くなると Logging の料金が増えるので、必要なサービスだけにします。このサイトの GCP では、auditConfigs は扱っていません。また、システムイベントとポリシー拒否の監査ログは出てきません。

16.4logging read のクエリ

gcloud logging read の最初の引数は、Logging のクエリ言語で書いたフィルタです。よく使う書き方を表にします。

書き方意味例
欄="値"等しいresource.type="cloud_run_revision"
欄:"値"含む（部分一致）logName:"run.googleapis.com"
>= > < <=大小。重大度や時刻、数にも使えるseverity>=ERROR、httpRequest.status>=500
AND OR NOT組み合わせ。並べただけなら ANDseverity>=WARNING AND NOT textPayload:"棚卸し"
欄.欄入れ子の欄をたどるresource.labels.service_name="orders"、jsonPayload.orderId="A-1002"

いちばんよく打つのは「このサービスのエラーだけ」です。

Cloud Run のエラーだけ⌘↵
gcloud logging read 'resource.type="cloud_run_revision" AND severity>=ERROR' --format="table(timestamp.date('%H:%M:%S'):label=TIME, severity, logName.basename():label=LOG, textPayload, jsonPayload.message)"

3 つ出ました。stderr の文字列、stderr の JSON、そして 500 を返したリクエストの記録です。リクエストのログは、ステータスが 500 番台なら ERROR になります。

部分一致の : と、数の比べ方も試します。

文字を含む、ステータスで絞る⌘↵
gcloud logging read 'textPayload:"失敗"' --format="value(textPayload)"gcloud logging read 'httpRequest.status>=500' --format="value(httpRequest.requestMethod, httpRequest.status, httpRequest.requestUrl)"

textPayload:"失敗" は、失敗 を含む文字列のエントリを探します。httpRequest はリクエストのログにだけある欄で、URL、ステータス、応答の大きさ、かかった時間が入っています。

件数と期間と並び順

gcloud logging read には、フィルタのほかに大事なフラグが 3 つあります。--limit=N は最大 N 件、--freshness=期間 はどれだけ前までさかのぼるか（10m、1h、7d など。既定は 1d）、--order=asc は古い順（既定は新しい順）です。

管理アクティビティを、古い順に 2 件⌘↵
gcloud logging read 'logName:"cloudaudit.googleapis.com%2Factivity"' --order=asc --limit=2 --format="table(timestamp.date('%H:%M:%S'):label=TIME, protoPayload.methodName:label=METHOD)"

いちばん古い EnableService（準備の API の有効化）から並びました。--limit は並べた後に効くので、「最初の 2 件」になります。

--freshness の既定が 1 日なのは大事な点です。「昨日の夜のエラーを探したい」なら、そのままで届きます。先週のことを調べるときは --freshness=7d のように広げないと、フィルタが正しくても何も出ません。

コツまずは広く読んで、欄の名前を確かめる

フィルタに書く欄の名前は、実際のエントリを 1 つ --limit=1 で読んで、そこから写すのが確実です。欄の名前やつづりを間違えると、エラーにならずに、ただ何も出ないことがあります。何も出ないときは、まずフィルタを短くしてみます。

16.5構造化ログ：1 行の JSON を書く

準備の server.js を見ます。/low の行は、文字列ではなく JSON を 1 行で書いています。

注文 API のソース⌘↵
cat ~/orders/server.js

Cloud Run（と Cloud Run functions）は、コンテナが書いた 1 行が JSON のオブジェクトなら、それを jsonPayload に入れます。そのとき、JSON の中の severity を、ログエントリの重大度として読みます。これを構造化ログと呼びます。

構造化ログのエントリ⌘↵
gcloud logging read 'jsonPayload.item="ノート A5"' --format="yaml(logName, severity, jsonPayload.message, jsonPayload.item, jsonPayload.stock)"gcloud logging read 'jsonPayload.orderId="A-1002"' --format="value(severity, jsonPayload.message, jsonPayload.reason)"

1 つ目のコマンドの出力を見ます。console.log で書いたので stdout のログですが、重大度は WARNING になりました。item や stock は、それぞれ別の欄として残っています。

構造化ログのよいところは、中身の欄でそのまま絞り込めることです。上の 2 つ目のコマンドは、jsonPayload.orderId="A-1002" で注文番号を名指しして探しました。文字列のログで textPayload:"A-1002" と探すと、番号がたまたま文の中に出てきたものも拾ってしまいます。gcloud logging write でも、--payload-type=json を付けると構造化ログを書けます。

注意ふつうの文字列の行は、重大度が付かない

console.log('注文を受け付けました') のような文字列の行は、severity: DEFAULT（重大度なし）になります。すると severity>=WARNING で探しても、アラートでも拾えません。エラーを知らせたい行は、構造化ログにして severity を書くのが確実です。

16.6保持期間とログバケット

ログはどこに、いつまで残るのでしょうか。最初の図の _Required と _Default を、シンクの一覧で確かめます。

最初からある 2 つのシンク⌘↵
gcloud logging sinks list --format="table(name, destination.basename():label=BUCKET)"gcloud logging sinks list --filter="name=_Required" --format="value(filter)"

_Required シンクは、管理アクティビティ・システムイベントなどの監査ログを _Required バケットへ送ります。_Default シンクは、それ以外のほとんど（Cloud Run のログ、データアクセスの監査ログ、自分で書いたログ）を _Default バケットへ送ります。2 つ目のコマンドは、_Required シンクのフィルタだけを出しています。LOG_ID("cloudaudit.googleapis.com/activity") のように、ログ ID で選んでいます。_Default のフィルタは、これらの「NOT」です。2 つのシンクで、すべてのログがどちらか一方に入ります。

バケット入るもの保持期間変えられるか
_Required管理アクティビティ、システムイベントの監査ログ長めに固定変えられない。消せない。料金はかからない
_Defaultそれ以外のほとんど短めの既定値期間を延ばせる（延ばした分は料金がかかる）

具体的な日数は、公式ドキュメントの「Cloud Logging の割り当てと上限」で確認してください。大事なのは、_Default のログは、ある日数が過ぎると消えることです。何か月も前のログを調べたいことがあるなら、保持期間を延ばすか、次の節のシンクで BigQuery や Cloud Storage に送っておきます。

メモ料金と無料枠

Cloud Logging の料金は、主にログバケットに取り込んだ量で決まります。無料枠は、プロジェクトあたり毎月 50 GiB です。_Required バケットに入る監査ログは、この量に数えません。データアクセスの監査ログをオンにしたり、アクセスの多いサービスがすべてのリクエストを書いたりすると、この量に近づきます。要らないログは、_Default シンクに除外のフィルタを足して取り込まないこともできます。

16.7シンクで BigQuery に送って集計する

「先月、どのエラーが何回起きたか」を数えたいときは、ログを BigQuery に送って SQL で集計するのが便利です。そのためのシンクを作ります。

まず宛先のデータセットを作り、シンクを作ります。宛先は bigquery.googleapis.com/projects/プロジェクト/datasets/データセット の形で書きます。

データセットとシンクを作る⌘↵
bq mk --location=asia-northeast1 --dataset tsubame-shop:app_logsgcloud logging sinks create orders-errors bigquery.googleapis.com/projects/tsubame-shop/datasets/app_logs --log-filter='resource.type="cloud_run_revision" AND severity>=WARNING' --use-partitioned-tables

出力の Please remember to grant … の行が大事です。「service-365600345236@gcp-sa-logging.iam.gserviceaccount.com というサービスアカウントに、データセットの BigQuery データ編集者のロールを付けるのを忘れないで」という意味です。シンクは作れましたが、まだログを書き込めません。忘れたまま API を呼ぶとどうなるかを確かめます。

権限を付ける前に、エラーを起こす⌘↵
curl -s $URL/failbq ls app_logs

bq ls は何も出しません。ログはシンクに合いましたが、書き込みが断られて届いていません。エラーも出ないので、気付きにくい失敗です。書き込みのサービスアカウントは、シンクの writerIdentity に入っています。

書き込みのサービスアカウントを確かめて、権限を付ける⌘↵
gcloud logging sinks describe orders-errors --format="value(writerIdentity)"gcloud projects add-iam-policy-binding tsubame-shop --member="$(gcloud logging sinks describe orders-errors --format='value(writerIdentity)')" --role=roles/bigquery.dataEditor --condition=None --format=none

writerIdentity は serviceAccount: 付きで出るので、そのまま --member に渡せます。ここではプロジェクトに付けましたが、データセットだけに付けるほうが、権限は小さくて済みます。

もう一度エラーを起こして、テーブルを見ます。

権限を付けた後のログは届く⌘↵
curl -s $URL/failcurl -s $URL/failcurl -s $URL/lowbq ls app_logs

テーブルが 3 つできました。シンクは、ログ ID ごとにテーブルを作ります（/ や . は _ に変わります）。stderr のテーブルを SQL で集計します。

BigQuery でエラーを数える⌘↵
bq query --use_legacy_sql=false 'SELECT severity, textPayload, COUNT(*) AS n FROM `tsubame-shop.app_logs.run_googleapis_com_stderr` GROUP BY severity, textPayload ORDER BY n DESC'

NULL の行は、textPayload のない JSON の行（注文できません）です。どちらも 2 件で、権限を付ける前の 1 回は数に入らず、後の 2 回だけが数えられました。シンクは、作った後（正確には書けるようになった後）に流れたログだけを送ります。

同じ名前のシンクは作れないエラーになる⌘↵
gcloud logging sinks create orders-errors bigquery.googleapis.com/projects/tsubame-shop/datasets/app_logs
エラーALREADY_EXISTS: Sink orders-errors already exists

シンクの名前は、プロジェクトの中で 1 つです。フィルタや宛先を変えたいときは、作り直さずに gcloud logging sinks update を使うか、gcloud logging sinks delete orders-errors --quiet で消してから作ります。

メモこのサイトの GCP では

本物の BigQuery のシンクは、ログエントリの形をそのまま列にします（resource や jsonPayload は入れ子の RECORD の列）。このサイトの GCP では、timestamp、severity、logName、textPayload などの主な欄を、平らな列にしています。上の SQL で使った列は、本物でも同じ名前です。

16.8ログベースの指標とアラート

ログを探すのは、何か起きたと気付いた後です。気付くためには、Cloud Monitoring（クラウド モニタリング）に見張らせます。流れは次のとおりです。

ログベースの指標を作る

ログベースの指標は、フィルタに合うログエントリの数を、時間ごとの数（時系列）にしたものです。注文 API のエラーを数える指標を作ります。

エラーを数える指標⌘↵
gcloud logging metrics create order-errors --description="注文 API のエラー" --log-filter='resource.labels.service_name="orders" AND severity>=ERROR'gcloud logging metrics describe order-errors --format="value(metricDescriptor.type, metricDescriptor.metricKind)"

指標の名前は logging.googleapis.com/user/order-errors になりました。アラートポリシーからは、この名前で指します。DELTA は「その期間に増えた数」という種類です。

フィルタを忘れたエラーになる⌘↵
gcloud logging metrics create order-warnings
エラーargument --log-filter: Must be specified.

ログベースの指標は「どのログを数えるか」がすべてなので、--log-filter は省けません。フィルタは gcloud logging read で試してから書くと、数え漏れを防げます。

通知チャネルとアラートポリシー

通知チャネルは、知らせる先です。運用チームのメールアドレスを登録します。アラートポリシーは、「どの指標が、どんな条件になったら、どこへ知らせるか」です。条件の書き方が細かいので、ファイルに書いて --policy-from-file で渡します。

通知チャネルと、アラートポリシーのファイル⌘↵
gcloud monitoring channels create --display-name="運用チーム" --type=email --channel-labels=email_address=ops@tsubame.example --format="value(name)"cat > ~/order-alert.yaml <<'EOF'displayName: 注文 API のエラーが多いcombiner: ORconditions:- displayName: 5 分間のエラーが 3 件を超える  conditionThreshold:    filter: metric.type="logging.googleapis.com/user/order-errors" AND resource.type="cloud_run_revision"    comparison: COMPARISON_GT    thresholdValue: 3    duration: 0s    aggregations:    - alignmentPeriod: 300s      perSeriesAligner: ALIGN_SUMEOF

filter でさっきのログベースの指標を選び、aggregations で 5 分（300s）ごとに合計（ALIGN_SUM）し、comparison と thresholdValue で「3 を超えたら」と決めています。duration は、その状態がどれだけ続いたら知らせるかで、0s はすぐです。

アラートポリシーを作る⌘↵
gcloud monitoring policies create --policy-from-file=$HOME/order-alert.yaml --notification-channels=$(gcloud monitoring channels list --format="value(name)") --format="value(name)"gcloud monitoring policies list

ENABLED が True で、条件が 1 つのポリシーができました。これで、5 分間に注文 API のエラーが 4 件以上出ると、インシデント（起きている問題の記録）が開き、ops@tsubame.example にメールが届きます。エラーが収まると、インシデントは自動で閉じます。

メモこのサイトの GCP では

アラートポリシーは --policy-from-file だけで作れます。条件の評価とインシデント、通知は、画面に出てきません（上の図のとおりに動くものとして読んでください）。本物の gcloud では、版によって gcloud beta monitoring policies create のように beta の下にあることがあります。

稼働時間チェック

ログベースの指標は「エラーが出た」ことに気付けますが、サービスが丸ごと止まってログすら出ないときは気付けません。そこで、外から定期的にアクセスして確かめる稼働時間チェック（uptime check）を足します。

稼働時間チェックを作る⌘↵
gcloud monitoring uptime create orders-top --resource-type=uptime-url --resource-labels=host=orders-365600345236.asia-northeast1.run.app --path=/ --period=5 --format="yaml(displayName, httpCheck, monitoredResource.labels.host, period)"

period: 300s は 5 分ごとに確かめるという意味です。本物では、世界のいくつかの場所から https://ホスト/ に GET を送り、応答が返るかを記録します。失敗したら知らせるには、この稼働時間チェックの指標を条件にしたアラートポリシーを、上と同じように作ります。

要点まとめ
  • どこで生まれたログも、ログエントリ（logName、resource、timestamp、severity、textPayload / jsonPayload / protoPayload）の形で Cloud Logging に集まる
  • 監査ログは、管理アクティビティ（常に記録）、システムイベント、データアクセス（既定は BigQuery 以外オフ）などに分かれる。protoPayload の principalEmail、methodName、status で「だれが・何を・成功したか」を読む
  • gcloud logging read 'フィルタ' で探す。resource.type=、severity>=ERROR、logName:、--limit、--freshness（既定 1 日）、--format
  • 1 行の JSON を書くと構造化ログになり、severity が読まれ、中身の欄で絞り込める
  • ログは _Required と _Default のバケットに入る。_Default には保持期間がある。無料枠は毎月 50 GiB
  • シンクで BigQuery に送れる。シンクの書き込みのサービスアカウント（writerIdentity）に権限を付けるまで、ログは届かない
  • ログベースの指標 → アラートポリシー → 通知チャネル で気付く。止まったことは稼働時間チェックで気付く

16.9確認問題

この章の内容を、自分でコマンドを書いて確かめます。どの問題も、章の準備（注文 API のデプロイ）が済んだ状態から始まります。

問 1

警告以上のログを読む

正解済み

ログ ops-check（ログ ID）に、いくつかのエントリが書いてあります。この中から、重大度が WARNING 以上のエントリの textPayload だけを、新しい順に 1 行に 1 つ表示してください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番も見る）
この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud logging write ops-check "点検を始めます" --severity=INFOgcloud logging write ops-check "棚 3 の温度が高め" --severity=WARNINGgcloud logging write ops-memo "別のログの警告" --severity=WARNINGgcloud logging write ops-check "冷房の停止" --severity=ERRORgcloud logging write ops-check "点検を終えます" --severity=NOTICE
模範解答
gcloud logging read 'logName:"logs/ops-check" AND severity>=WARNING' --format="value(textPayload)"
問 2

だれがバケットを作ろうとしたか

正解済み

準備で、何人かがバケットの作成（storage.buckets.create）を試みました。成功した人も、断られた人もいます。監査ログから、storage.buckets.create を呼んだプリンシパルのメールアドレスを、新しい順に 1 行に 1 つ表示してください（成功・失敗の両方）。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番も見る）
この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

gcloud auth login alice@tsubame.examplegcloud storage buckets create gs://tsubame-shop-q16-a --location=asia-northeast1 || truegcloud auth login you@tsubame.examplegcloud storage buckets create gs://tsubame-shop-q16-b --location=asia-northeast1
模範解答
gcloud logging read 'protoPayload.methodName="storage.buckets.create"' --format="value(protoPayload.authenticationInfo.principalEmail)"
問 3

エラーだけを BigQuery へ送る

正解済み

データセット tsubame-shop:app_logs は準備で作ってあります。重大度が ERROR 以上のログだけをこのデータセットへ送るシンク errors-only を作り、ログが実際に届くように、シンクの書き込みのサービスアカウントへ roles/bigquery.dataEditor を tsubame-shop のプロジェクトで付けてください。

答え合わせでは、あなたのコマンドの後にログを 3 つ（ERROR、WARNING、CRITICAL）書き、BigQuery のテーブル app_logs.ops_check に届いた行を表示します。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

gcloud logging sinks create 名前 宛先 --log-filter='…' で作ります。宛先は bigquery.googleapis.com/projects/tsubame-shop/datasets/app_logs の形です。サービスアカウントは gcloud logging sinks describe errors-only --format='value(writerIdentity)' で分かります。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

bq mk --location=asia-northeast1 --dataset tsubame-shop:app_logs
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

gcloud logging sinks describe errors-only --format="value(destination)"gcloud logging write ops-check "確かめのエラー 1" --severity=ERRORgcloud logging write ops-check "確かめの警告" --severity=WARNINGgcloud logging write ops-check "確かめのエラー 2" --severity=CRITICALbq head --format=csv --selected_fields=severity,textPayload app_logs.ops_check
模範解答
gcloud logging sinks create errors-only bigquery.googleapis.com/projects/tsubame-shop/datasets/app_logs --log-filter='severity>=ERROR' --use-partitioned-tablesgcloud projects add-iam-policy-binding tsubame-shop --member="$(gcloud logging sinks describe errors-only --format='value(writerIdentity)')" --role=roles/bigquery.dataEditor --condition=None --format=none
問 4

5xx を数える指標

正解済み

注文 API（Cloud Run のサービス orders）が 500 番台のステータスを返したリクエストを数える、ログベースの指標 orders-5xx を作ってください。リクエストのログの httpRequest.status を使います。

答え合わせでは、指標のフィルタで gcloud logging read を実行し、数えられるリクエストのステータスを表示します。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

gcloud logging metrics create 名前 --log-filter='…' で作ります。フィルタは、先に gcloud logging read '…' で試して、500 のリクエストだけが出ることを確かめてから使います。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

URL=$(gcloud run services describe orders --region=asia-northeast1 --format='value(status.url)')curl -s $URL/curl -s $URL/fail
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

gcloud logging metrics list --format="value(name)"gcloud logging read "$(gcloud logging metrics describe orders-5xx --format='value(filter)')" --format="value(httpRequest.status)"
模範解答
gcloud logging metrics create orders-5xx --log-filter='resource.labels.service_name="orders" AND httpRequest.status>=500'
