## SQL が実行されるまで {#pipeline}

第 1 章で「SQL は何が欲しいかだけを書き、どうやるかはデータベースが決める」と説明しました。その「どうやるか」を決めているのが**プランナ**（オプティマイザとも呼ぶ）です。SQL の文字列は、次の 5 つの段階を経て結果になります。

```fig graph 問い合わせの処理の流れ。プランナが、いくつもある実行方法の中からコストが最も小さいものを選ぶ
{
  col: 150, row: 86,
  nodes: [
    { id: 'sql', label: 'SQL の文字列', x: 0, y: 0, kind: 'muted', mono: false },
    { id: 'p', label: 'パーサ', sub: '文法を解析', x: 1, y: 0, kind: 'stack', mono: false },
    { id: 'a', label: 'アナライザ', sub: '名前と型を解決', x: 2, y: 0, kind: 'stack', mono: false },
    { id: 'r', label: 'リライタ', sub: 'ビューを展開', x: 3, y: 0, kind: 'stack', mono: false },
    { id: 'pl', label: 'プランナ', sub: '実行計画を選ぶ', x: 3, y: 1, kind: 'accent', mono: false },
    { id: 'e', label: 'エグゼキュータ', sub: '計画どおりに実行', x: 2, y: 1, kind: 'ext', mono: false },
    { id: 'st', label: '統計情報', sub: 'pg_statistic', x: 4, y: 1, kind: 'crate', mono: false },
    { id: 'res', label: '結果', x: 1, y: 1, kind: 'muted', mono: false },
  ],

  ],

```

| 段階 | すること | ここで出るエラーの例 |
| --- | --- | --- |
| パーサ | 文字列を文法に従って木（構文木）にする | `syntax error at or near ...`（42601） |
| アナライザ | テーブル名・列名・関数・型を、システムカタログで確かめる | `relation ... does not exist`（42P01） |
| リライタ | ビュー（第 18 章）やルールを、元のテーブルへの問い合わせに展開する | |
| プランナ | 実行方法の候補を作り、コストを見積もって一番安いものを選ぶ | |
| エグゼキュータ | 選ばれた計画（木）を下から実行し、行を上に流す | 実行時エラー（0 除算など） |

この章では、次の 2 つの表を使います。

```sql setup
create table users (
  id    int primary key,
  pref  text not null,
  plan  text not null
);
insert into users
select g, (array['東京都','大阪府','愛知県','福岡県'])[1 + g % 4],
       case when g % 20 = 0 then 'pro' else 'free' end
from generate_series(1, 10000) g;

create table events (
  id         bigint primary key,
  user_id    int not null references users(id),
  kind       text not null,
  amount     int not null,
  created_at timestamptz not null
);
insert into events
select g,
       1 + (g * 7) % 10000,
       case when g % 50 = 0 then 'purchase' when g % 5 = 0 then 'click' else 'view' end,
       (g % 97) * 100,
       timestamptz '2026-01-01 00:00+09' + (g || ' seconds')::interval * 60
from generate_series(1, 200000) g;
create index events_user_idx on events (user_id);
create index events_created_idx on events (created_at);
analyze users;
analyze events;
```

## EXPLAIN を読む {#read}

`explain` を前に付けると、SQL を実行せずに、プランナが選んだ計画を表示します。

```sql run
explain select * from events where user_id = 42;
```

計画は**木**になっていて、字下げと `->` が親子関係を表します。エグゼキュータは、一番深い（右に寄った）ノードから実行し、結果の行を親に渡していきます。

各ノードの括弧の中は、プランナの**見積もり**です。

| 項目 | 例 | 意味 |
| --- | --- | --- |
| `cost=4.45..` | 起動コスト | 最初の 1 行を返すまでのコスト |
| `..77.73` | 総コスト | 全部の行を返し終えるまでのコスト |
| `rows=20` | 行数 | このノードが返すと見積もった行数 |
| `width=29` | 幅 | 1 行の平均バイト数 |

コストの単位は「ページを 1 枚順番に読む手間 = 1」という、抽象的なものです。秒ではありません。

### EXPLAIN ANALYZE

`explain analyze` は**実際に実行して**、見積もりと実際の値を並べて表示します。

```sql run
explain analyze select * from events where user_id = 42;
```

`actual time=0.02..0.05` はミリ秒、`rows=20` は実際の行数、`loops=1` はこのノードが何回実行されたかです。見積もりの `rows` と実際の `rows` を比べるのが、計画を調べるときの第一歩です。

:::warn EXPLAIN ANALYZE は本当に実行する
`explain analyze delete from ...` は、本当に行を消します。更新系の文の計画を実際の値つきで見たいときは、`begin; explain analyze ...; rollback;` のようにトランザクションで囲みます。
:::

## コストを手で計算する {#cost}

プランナがどうやってコストを出しているのか、Seq Scan で確かめてみましょう。Seq Scan のコストは、次の式で計算されます。

```text
総コスト = ページ数 × seq_page_cost  +  行数 × cpu_tuple_cost  +  行数 × 条件の数 × cpu_operator_cost
```

| パラメータ | 既定値 | 意味 |
| --- | --- | --- |
| `seq_page_cost` | 1.0 | ページを順番に 1 枚読むコスト |
| `random_page_cost` | 4.0 | ページを飛び飛びに 1 枚読むコスト |
| `cpu_tuple_cost` | 0.01 | 1 行を処理するコスト |
| `cpu_index_tuple_cost` | 0.005 | インデックスの項目を 1 つ処理するコスト |
| `cpu_operator_cost` | 0.0025 | 演算子や関数を 1 回評価するコスト |

`events` のページ数と行数は、`pg_class` にあります。

```sql run
select relpages, reltuples,
       relpages * 1.0 + reltuples * 0.01                  as 条件なしの見積もり,
       relpages * 1.0 + reltuples * 0.01 + reltuples * 0.0025 as "条件1つの見積もり"
from pg_class where relname = 'events';
```

```sql run
explain select * from events;
```

```sql run
explain select * from events where amount > 5000;
```

`explain` の総コストが、手で計算した値と一致しているはずです。プランナは魔法ではなく、こうした式の積み重ねで計画を比べています。

:::deep random_page_cost が 4 である理由
回転式のハードディスクでは、飛び飛びに読むとヘッドの移動が必要で、順番に読むより何十倍も遅くなります。4 という値は、キャッシュに当たる割合も考えて決められた歴史的な値です。SSD では飛び飛びの読み込みもほとんど遅くならないので、`random_page_cost` を 1.1 程度に下げると、インデックスを使う計画が選ばれやすくなります。
:::

## 統計情報 {#stats}

コストの式には「何行が条件に合うか」の見積もりが必要です。これを支えるのが**統計情報**で、`analyze` コマンド（autovacuum も自動で実行する）がテーブルの一部の行をサンプリングして集めます。

```sql run
select attname as 列, null_frac as null率, n_distinct as 異なる値の数,
       most_common_vals as 最頻値, most_common_freqs as 最頻値の割合
from pg_stats
where tablename = 'events' and attname in ('kind', 'user_id');
```

| 列 | 意味 |
| --- | --- |
| `null_frac` | NULL の割合 |
| `n_distinct` | 異なる値の数。負の数は「行数に対する割合」（−1 なら全部違う） |
| `most_common_vals` / `most_common_freqs` | よく出る値と、その割合 |
| `histogram_bounds` | 最頻値以外の値を、同じ件数ずつに区切った境目 |
| `correlation` | 値の順番と、ディスク上の行の順番がどれだけ揃っているか（−1〜1） |

`kind = 'purchase'` の行数を、プランナは「全体の行数 × purchase の割合」で見積もります。

```sql run
explain select * from events where kind = 'purchase';
```

```sql run
select count(*) as 実際の行数 from events where kind = 'purchase';
```

見積もりと実際がほぼ一致しています。

### 見積もりが外れるとき

統計は**列ごと**に集められます。そのため、列どうしに関係があると見積もりが外れます。市と都道府県の表で試してみます。

```sql run
create table addr (city text, pref text);
insert into addr
select c, p from (values ('横浜市', '神奈川県'), ('大阪市', '大阪府'), ('名古屋市', '愛知県'), ('福岡市', '福岡県')) v(c, p),
     generate_series(1, 5000);
analyze addr;
explain analyze select * from addr where city = '横浜市' and pref = '神奈川県';
```

見積もりの `rows` が約 1,250、実際は 5,000 です。プランナは「横浜市である確率 1/4」と「神奈川県である確率 1/4」を**独立**とみなして掛け合わせ、1/16 と見積もりました。実際には横浜市なら必ず神奈川県なので、1/4 が正解です。

**拡張統計**を作ると、列の組み合わせの関係も集めてくれます。

```sql run
create statistics addr_city_pref (dependencies) on city, pref from addr;
analyze addr;
explain analyze select * from addr where city = '横浜市' and pref = '神奈川県';
```

見積もりが 5,000 に近づきました。見積もりの誤りは、結合の方法や順番の選択を誤らせ、問い合わせを何倍も遅くする最大の原因です。

:::key 遅い問い合わせを調べる手順
1. `explain (analyze, buffers)` を取る
2. 各ノードの見積もりの `rows` と実際の `rows` を比べ、**大きく外れている一番下のノード**を探す
3. 外れの原因（統計が古い、列どうしの相関、関数をかけた条件など）を直す：`analyze`、拡張統計、式インデックス
4. それでも遅ければ、読んでいるページ数（Buffers）が多いノードを、インデックスで減らせないか考える
:::

## 結合の方法を比べる {#joins}

第 7 章で紹介した 3 つの結合方法を、実際の計画で見てみます。

```sql run
explain analyze
select u.pref, count(*)
from events e join users u on u.id = e.user_id
where e.kind = 'purchase'
group by u.pref;
```

`Hash Join` が選ばれているはずです。`Hash` の下にあるのが、ハッシュ表を作る側（小さいほう）です。

`enable_hashjoin` などの設定を off にすると、その方法を（なるべく）使わないようにプランナに指示できます。ほかの方法だとコストがいくつになるか、比べてみましょう。

```sql run
set enable_hashjoin = off;
explain
select u.pref, count(*)
from events e join users u on u.id = e.user_id
where e.kind = 'purchase'
group by u.pref;
```

```sql run
set enable_mergejoin = off;
explain
select u.pref, count(*)
from events e join users u on u.id = e.user_id
where e.kind = 'purchase'
group by u.pref;
```

```sql run
reset enable_hashjoin;
reset enable_mergejoin;
```

それぞれの総コストを比べると、プランナが最初に Hash Join を選んだ理由が分かります。`enable_*` の設定は、計画を調べるための道具です。本番で常に off にするものではありません。

### 1 人のユーザの場合

条件で行が少なく絞れるときは、別の方法が選ばれます。

```sql run
explain analyze
select u.pref, e.kind, e.amount
from users u join events e on e.user_id = u.id
where u.id = 42;
```

`Nested Loop` の外側で users を 1 行だけ取り、内側で events をインデックスで引いています。外側が 1 行なので、内側は 1 回（`loops=1`）しか実行されません。外側の行が多いと、内側の `loops` が増えていきます。

### 結合の順番

3 つ以上の表を結合するとき、結合の順番の組み合わせは表の数とともに爆発的に増えます。PostgreSQL は、表が少ないうちはすべての順番を調べ（動的計画法）、`geqo_threshold`（既定 12）個以上になると、遺伝的アルゴリズムで近似的に探します。

## そのほかのノード {#nodes}

| ノード | すること |
| --- | --- |
| `Sort` | 並べ替える。`work_mem` に収まらなければディスクを使う（`external merge`） |
| `Incremental Sort` | すでに一部の列で並んでいる入力を、残りの列で並べ替える |
| `HashAggregate` | ハッシュ表で group by する |
| `GroupAggregate` | 並んだ入力を、前から順に group by する |
| `Limit` | 指定の件数で止める。下のノードも途中で止まる |
| `Memoize` | 入れ子ループの内側の結果を、引数ごとにキャッシュする |
| `Gather` | 並列ワーカの結果を集める（パラレルクエリ） |
| `Materialize` | 下の結果をメモリに保存して、何度も読み直す |

並べ替えで使えるメモリ（`work_mem`）を減らすと、ディスクを使う並べ替えに変わる様子が見られます。

```sql run
set work_mem = '64kB';
explain (analyze, costs off) select * from events order by amount, id;
```

```sql run
set work_mem = '32MB';
explain (analyze, costs off) select * from events order by amount, id;
reset work_mem;
```

`Sort Method: external merge  Disk: ...kB` が、`quicksort  Memory: ...kB` に変わります。既定の `work_mem`（4 MB）では、この 20 万行の並べ替えはメモリに収まらず、ディスクを使います。`work_mem` は並べ替えやハッシュの 1 回ごとに使える量なので、大きくしすぎると、同時に動く問い合わせの数だけメモリを使ってしまう点に注意します。

`order by` と `limit` の組み合わせでは、全部を並べ替えずに上位だけを保つ `top-N heapsort` が使われます。

```sql run
explain (analyze, costs off) select * from events order by amount desc limit 5;
```

:::note パラレルクエリ
サーバ版の PostgreSQL は、大きな表の Seq Scan や集計を、複数のプロセス（ワーカ）で分担できます。計画に `Gather` と `Parallel Seq Scan` が出てきます。ブラウザの PGlite は 1 プロセスで動いているので、この本の環境では並列の計画は出ません。
:::

## プリペアドステートメントと計画のキャッシュ {#prepared}

アプリケーションは、同じ形の SQL を値だけ変えて何度も実行します。毎回計画を立てるのは無駄なので、`prepare` で計画を使い回せます。

```sql run
prepare by_kind(text) as select count(*) from events where kind = $1;
execute by_kind('purchase');
```

```sql run
explain execute by_kind('view');
```

最初の 5 回は、渡された値ごとに計画を立てます（**カスタムプラン**）。その後、値によらない**汎用プラン**のコストがカスタムプランと大差なければ、汎用プランに切り替えて使い回します。値によって最適な計画が大きく変わる列（偏りのある列）では、汎用プランが遅くなることがあり、`plan_cache_mode` で制御します。

```sql run
deallocate by_kind;
```

## 遅い問い合わせを見つける {#find}

本番のデータベースでは、どの問い合わせが遅いかを見つけるところから始まります。

| 道具 | 何が分かるか |
| --- | --- |
| `pg_stat_statements` 拡張 | 問い合わせの形ごとの実行回数・合計時間・平均時間。まずはこれを入れる |
| `log_min_duration_statement` 設定 | 指定時間より遅かった文をログに出す |
| `auto_explain` 拡張 | 遅かった文の実行計画を、自動でログに出す |
| `pg_stat_activity` ビュー | いま実行中の文と、その待ち状態 |

```sql run
select pid, state, wait_event_type, left(query, 60) as 実行中の文
from pg_stat_activity
where state is not null;
```

:::try 
1. `events` の `created_at` で、2026 年 2 月 1 日の 1 日分を検索する問い合わせを書き、`explain analyze` で計画と見積もりを確かめてください
2. `random_page_cost` を 1.1 にして、同じ問い合わせの計画やコストが変わるか見てください（`set random_page_cost = 1.1;`）
:::

```sql run title="練習用"
explain analyze
select count(*), sum(amount) from events
where created_at >= '2026-02-01' and created_at < '2026-02-02';
```

:::key この章のまとめ
- SQL はパーサ → アナライザ → リライタ → プランナ → エグゼキュータの順に処理される
- EXPLAIN は木。下から実行される。`cost=起動..総` は抽象的な単位で、見積もりの `rows` が肝心
- コストは「ページ数 × ページのコスト + 行数 × CPU のコスト」の積み重ね。手で計算すれば一致する
- 見積もりは `analyze` が集めた列ごとの統計に基づく。列の相関は拡張統計で教える
- 遅い問い合わせは、見積もりと実際の行数が大きく外れたノードから調べる
:::

## 確認問題 {#quiz}

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

:::quiz プランナのコストの単位
プランナのコスト計算に使われる 3 つの設定 `seq_page_cost`、`random_page_cost`、`cpu_tuple_cost` について、名前と値を出してください。

```sql answer
select name, setting from pg_settings where name in ('seq_page_cost', 'random_page_cost', 'cpu_tuple_cost');
```

:::hint
設定の一覧は `pg_settings` ビューにあります。`name` と `setting` の列を使います。
:::
:::

:::quiz 列の相関をプランナに教える
`addr` テーブルの `city` と `pref` には強い相関（市が決まれば県が決まる）があります。これをプランナに教える**拡張統計**を作ってください。

```sql prep
create table addr (city text, pref text);
insert into addr
select c, p from (values ('横浜市', '神奈川県'), ('大阪市', '大阪府')) v(c, p), generate_series(1, 100);
```

```sql answer
create statistics addr_dep (dependencies) on city, pref from addr;
```

```sql check
select (select array_agg(a.attname::text order by a.attname)
        from pg_attribute a where a.attrelid = s.stxrelid and a.attnum = any (s.stxkeys)) as 列,
       'f' = any (s.stxkind) as 関数従属
from pg_statistic_ext s
where s.stxrelid = 'addr'::regclass;
```

:::hint
`create statistics 名前 (dependencies) on 列, 列 from テーブル;`。関数従属は `dependencies` です。
:::
:::

:::quiz プリペアドステートメント
`kind` を引数に取り、その `kind` の `events` の件数を返すプリペアドステートメント `count_kind` を作り、`'click'` で実行してください。

```sql prep
deallocate all;
```

```sql answer
prepare count_kind(text) as select count(*) from events where kind = $1;
execute count_kind('click');
```

:::hint
`prepare 名前(引数の型) as SQL;` で作り、`execute 名前(値);` で実行します。SQL の中では引数を `$1` と書きます。
:::
:::
