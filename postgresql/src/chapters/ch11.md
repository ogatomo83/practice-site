## 悪い設計で起きること {#anomalies}

まず、何も考えずに作った「注文の一覧表」を見てみます。表計算ソフトで管理しているような形です。

```sql setup
create table order_sheet (
  order_id     int,
  ordered_on   date,
  customer     text,
  customer_pref text,
  product      text,
  category     text,
  price        int,
  qty          int
);
insert into order_sheet values
  (1, '2025-01-05', '佐藤 葵', '東京都', 'つばめ万年筆 細字', '万年筆', 12000, 1),
  (1, '2025-01-05', '佐藤 葵', '東京都', 'ボトルインク 夜空', 'インク', 2200, 1),
  (2, '2025-01-18', '鈴木 蓮', '大阪府', 'さらさらボールペン 0.5', 'ボールペン', 180, 5),
  (2, '2025-01-18', '鈴木 蓮', '大阪府', '方眼ノート A5', 'ノート', 450, 2),
  (3, '2025-02-02', '佐藤 葵', '東京都', '方眼ノート A5', 'ノート', 450, 3);
```

```sql run
select * from order_sheet;
```

1 つの表にすべてが入っていて、一見わかりやすく見えます。しかしこの表には、3 種類の**異常**が潜んでいます。

### 更新異常

佐藤さんが神奈川県に引っ越しました。注文 1 の行だけを直すと、どうなるでしょうか。

```sql run
update order_sheet set customer_pref = '神奈川県' where order_id = 1;
select distinct customer, customer_pref from order_sheet where customer = '佐藤 葵';
```

佐藤さんの住所が 2 つになってしまいました。同じ事実（佐藤さんの住所）が 3 行に重複して書かれているので、全部を直し忘れると食い違いが生まれます。これが**更新異常**です。

### 挿入異常

新商品「ガラスペン」を登録したいと思います。しかしこの表は 1 行が「注文の明細」なので、まだ誰も注文していない商品を入れる場所がありません。注文番号を NULL にして無理やり入れるしかなくなります。これが**挿入異常**です。

### 削除異常

鈴木さんの注文 2 がキャンセルになったので、行を消します。

```sql run
delete from order_sheet where order_id = 2;
select distinct product, category, price from order_sheet order by product;
```

「さらさらボールペン 0.5 は 180 円のボールペン」という情報まで消えてしまいました。注文を消したかっただけなのに、商品の情報も失われます。これが**削除異常**です。

:::key 3 つの異常の原因は同じ
どれも、**1 つの表に複数の種類の事実が混ざっている**ことが原因です。この表には「注文」「顧客」「商品」「分類」という 4 種類の事実が入っています。正規化とは、事実の種類ごとに表を分けることです。
:::

## 関数従属 {#fd}

正規化の道具になるのが**関数従属**という考え方です。「列 A の値が決まれば、列 B の値が 1 つに決まる」とき、「B は A に関数従属する」と言い、`A → B` と書きます。

order_sheet の関数従属を書き出してみます。

| 従属 | 意味 |
| --- | --- |
| `order_id → ordered_on, customer` | 注文が決まれば、日付と顧客が決まる |
| `customer → customer_pref` | 顧客が決まれば、住所が決まる |
| `product → category, price` | 商品が決まれば、分類と価格が決まる |
| `(order_id, product) → qty` | 注文と商品の組が決まれば、個数が決まる |

この表の主キーは `(order_id, product)` です。正規化は、この関数従属の矢印を見ながら、表を分けていく作業です。

## 第 1 正規形 {#1nf}

**第 1 正規形**の条件は、「すべての列の値が、それ以上分けられない 1 つの値（原子値）であること」です。

| 違反の例 | 直し方 |
| --- | --- |
| `電話番号` 列に `03-1111-2222, 090-3333-4444` と 2 つ入れる | 電話番号の表を別に作り、1 行に 1 つ |
| `商品1`, `商品2`, `商品3` という列を並べる（繰り返し項目） | 明細の表を作り、1 行に 1 商品 |
| 住所を 1 つの文字列に入れる | 問題になるかは用途次第。都道府県で集計するなら分ける |

最後の例のように、「原子的」かどうかは使い方で決まります。日付を年・月・日の 3 列に分ける必要はありません。日付は 1 つの値として扱うのが普通だからです。**検索や集計で中身を分けて使うなら、分けて持つ**、と考えるとよいでしょう。

:::note 配列と JSON は第 1 正規形違反か
PostgreSQL の配列や jsonb の列は、厳密には第 1 正規形に反します。ただし、中身で検索しない（丸ごと読み書きするだけ）なら問題は起きません。`products.tags` のように中身で絞り込みや集計をするなら、本来は別の表にすべきです。この章の最後でその形に直してみます。
:::

## 第 2 正規形 {#2nf}

**第 2 正規形**の条件は、第 1 正規形を満たし、さらに「主キーの**一部だけ**に従属する列がないこと」です。

order_sheet の主キーは `(order_id, product)` ですが、`ordered_on` は `order_id` だけで決まり、`price` は `product` だけで決まります。これらが**部分関数従属**で、第 2 正規形に違反しています。

主キーの一部に従属する列を、その部分をキーにした別の表に移します。

```fig graph 第 2 正規形への分解。主キーの一部（order_id、product）に従属していた列を、それぞれの表に移す

}
```

## 第 3 正規形 {#3nf}

**第 3 正規形**の条件は、第 2 正規形を満たし、さらに「主キー以外の列に従属する列がないこと」です。

第 2 正規形の `orders` では、`customer_pref` は `customer` に従属し、`customer` は `order_id` に従属しています。`order_id → customer → customer_pref` と、主キーから間接的に（推移的に）決まっています。これが**推移関数従属**で、佐藤さんの住所が 2 つになった更新異常の原因でした。

これも同じように、`customer` をキーにした表に移します。商品の分類も、分類名以外の情報（親の分類など）を持つなら同じように分けます。

```sql run
-- 正規化した結果を、サンプルの文具店のテーブルと見比べる
select table_name, string_agg(column_name, ', ' order by ordinal_position) as 列
from information_schema.columns
where table_schema = 'public' and table_name in ('customers', 'orders', 'order_items', 'products', 'categories')
group by table_name
order by table_name;
```

文具店のテーブルは、ほぼこの手順で分けた形になっています。

:::key 正規化の合言葉
第 1〜第 3 正規形をまとめて、英語圏では次のように言います。「すべての列は、**キー**に、**キー全体**に、そして**キー以外の何物でもないもの**に依存すること」。キーに依存（1NF の前提）、キー全体に依存（2NF）、キー以外には依存しない（3NF）、という意味です。
:::

:::deep ボイス・コッド正規形とその先
第 3 正規形でも、候補キーが複数あって重なっている特殊な場合に異常が残ることがあります。それを取り除いたものが**ボイス・コッド正規形（BCNF）**で、「すべての関数従属の左辺が候補キーであること」が条件です。さらに多値従属を扱う第 4 正規形、結合従属を扱う第 5 正規形もありますが、実務ではまず第 3 正規形（できれば BCNF）を目指せば十分です。
:::

## 関係の種類 {#relationships}

表と表の関係は、相手の行の数で 3 種類に分けられます。

| 関係 | 例 | 実現のしかた |
| --- | --- | --- |
| 1 対 1 | 顧客と、その顧客の詳しいプロフィール | 片方の主キーを、もう片方の主キー兼外部キーにする |
| 1 対多 | 顧客と注文（1 人が何件も注文する） | 「多」の側に外部キーを置く（`orders.customer_id`） |
| 多対多 | 注文と商品（1 注文に何商品、1 商品は何注文にも） | 間に**中間テーブル**を置く（`order_items`） |

```fig graph 文具店の ER 図。中間テーブル order_items が、注文と商品の多対多を 2 つの 1 対多に分けている
{
```

多対多の関係は、中間テーブルなしには表せません。中間テーブルは、2 つの外部キーの組を主キーにするのが基本です。そして中間テーブルには、その組み合わせに固有の情報（`quantity`、`unit_price`）を置けます。

## 非正規化 {#denormalize}

正規化は異常を防ぎますが、表が増えるぶん、読むときに結合が必要になります。読む速さのために、あえて正規化を崩すことを**非正規化**と呼びます。

ただし、文具店のデータには、非正規化に**見えるが正しい**例があります。`order_items.unit_price` です。商品の価格は `products.price` にあるのに、なぜ明細にも価格を持っているのでしょうか。

```sql run
select oi.order_id, p.name, oi.unit_price as 注文時の価格, p.price as 今の価格
from order_items oi join products p on p.id = oi.product_id
where oi.unit_price <> p.price;
```

注文 19 の手帳は、セール中の 1,700 円で売られていました。明細の `unit_price` は「**注文した時点での**価格」という、商品の価格とは別の事実です。価格を変えても過去の注文の金額は変わってはいけないので、明細に持つのが正しい設計です。

:::key 本当の非正規化かどうかの見分け方
「その値は、ほかの表から**いつでも**計算し直せるか」を考えます。注文時の価格は、商品の価格が変われば計算し直せないので、独立した事実です。一方、「注文の合計金額」を orders に持つのは、明細から計算し直せるので非正規化です。非正規化した値は、元の値と食い違わないよう、トリガ（第 18 章）やマテリアライズドビューで同期を保つ必要があります。
:::

## よくある設計の失敗 {#antipatterns}

| アンチパターン | 何が問題か | 代わりに |
| --- | --- | --- |
| **カンマ区切りの列** `tags = '定番,ギフト'` | 検索も集計も外部キーもできない | 中間テーブル |
| **EAV**（属性名と値を縦に持つ汎用表） `(entity_id, attr_name, attr_value)` | 型も制約も効かない。1 件読むのに大量の結合 | 普通の列、または jsonb |
| **ポリモーフィック関連** `(target_type, target_id)` で複数の表を指す | 外部キーを張れない | 指す相手ごとに外部キー列を分ける |
| **何でも NULL 可** | 三値論理の落とし穴が全部の列に | 基本は `not null` |
| **ID だけの自然キー無視** | 同じ顧客が重複して登録される | 自然キーに `unique` |
| **論理削除フラグの乱用** `deleted = true` | すべての問い合わせに条件が要る。一意制約が壊れる | 履歴の表に移す、または部分一意索引（第 14 章） |

## タグを正しく設計し直す {#tags}

最後に、`products.tags` 配列を、中間テーブルを使う形に直してみます。

```sql run
create table tags (
  id   int generated always as identity primary key,
  name text not null unique
);
create table product_tags (
  product_id int not null references products(id) on delete cascade,
  tag_id     int not null references tags(id) on delete cascade,
  primary key (product_id, tag_id)
);
-- 配列から移し替える
insert into tags (name)
select distinct unnest(tags) from products order by 1;
insert into product_tags (product_id, tag_id)
select p.id, t.id from products p cross join lateral unnest(p.tags) as u(tag) join tags t on t.name = u.tag;
select (select count(*) from tags) as タグ数, (select count(*) from product_tags) as 対応数;
```

これで、タグ名の変更は `tags` の 1 行を直すだけで済み、存在しないタグを付けることもできなくなりました。タグで商品を探すには結合を使います。

```sql run
select t.name as タグ, string_agg(p.name, '、' order by p.id) as 商品
from tags t
join product_tags pt on pt.tag_id = t.id
join products p on p.id = pt.product_id
group by t.id
order by count(*) desc;
```

:::try 
次の要件を満たす表を設計し、`create table` を書いてください。

- 商品にはレビューを何件でも付けられる。レビューには顧客、星の数（1〜5）、本文、投稿日時がある
- 1 人の顧客は、1 つの商品に 1 件しかレビューを書けない
- 商品が削除されたら、そのレビューも消える
:::

```sql run title="練習用"
create table reviews (
  id          bigint generated always as identity primary key,
  product_id  int not null references products(id) on delete cascade,
  customer_id int not null references customers(id),
  stars       int not null check (stars between 1 and 5),
  body        text not null default '',
  posted_at   timestamptz not null default now(),
  unique (product_id, customer_id)
);
insert into reviews (product_id, customer_id, stars, body) values (1, 1, 5, '書き味がなめらか');
select * from reviews;
```

:::key この章のまとめ
- 1 つの表に複数の種類の事実が混ざると、更新・挿入・削除の 3 つの異常が起きる
- 関数従属 `A → B` を書き出し、キー以外に従属する列を別の表に移すのが正規化
- 第 1 正規形は原子値、第 2 は部分従属なし、第 3 は推移従属なし
- 多対多は中間テーブルで 2 つの 1 対多に分ける
- 「いつでも計算し直せる値」を持つのが非正規化。注文時の価格は独立した事実なので正規化の範囲内
:::

## 確認問題 {#quiz}

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

:::quiz 顧客の表の材料
`order_sheet` から、顧客と都道府県の組を重複なく出してください（顧客の表に切り出すときの中身です）。

```sql answer
select distinct customer, customer_pref from order_sheet;
```
:::

:::quiz 注文ごとの合計金額
`order_sheet` から、注文（`order_id`）ごとの合計金額（`price * qty` の合計）を出してください。

```sql answer
select order_id, sum(price * qty) as 合計 from order_sheet group by order_id;
```
:::

:::quiz 商品とタグの中間テーブル
商品とタグの多対多を表す中間テーブル `product_tags` を作ってください。

- `product_id`：`products` の `id` を参照する
- `tag`：タグの文字列
- 同じ商品に同じタグを 2 回付けられない

```sql answer
create table product_tags (
  product_id int  not null references products (id),
  tag        text not null,
  primary key (product_id, tag)
);
```

```sql check
select try_sql($$insert into product_tags (product_id, tag) values (1, '定番')$$) as 追加,
       try_sql($$insert into product_tags (product_id, tag) values (1, 'ギフト')$$) as 別のタグ,
       try_sql($$insert into product_tags (product_id, tag) values (1, '定番')$$) as 同じタグ,
       try_sql($$insert into product_tags (product_id, tag) values (999, '定番')$$) as ない商品;
```

:::hint
「同じ組を 2 回入れられない」は、2 つの列を合わせた主キー `primary key (product_id, tag)` で表せます。
:::
:::
