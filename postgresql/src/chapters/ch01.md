## データベース以前 {#before}

コンピュータが会社で使われ始めた 1950 年代、データは**ファイル**に入っていました。給与計算のプログラムは給与のファイルを、在庫管理のプログラムは在庫のファイルを、それぞれ自分の決めた形式で読み書きしていました。

この方式には、すぐに 3 つの問題が見えてきます。

| 問題 | 具体例 |
| --- | --- |
| 同じデータがあちこちに重複する | 社員の住所が、給与のファイルと人事のファイルの両方にある。引っ越すと片方だけ直り、食い違う |
| ファイルの形式がプログラムに埋め込まれる | 項目を 1 つ足すと、そのファイルを読む全プログラムを書き直す必要がある |
| 同時に使えない | 2 つのプログラムが同じファイルを同時に書き換えると、片方の変更が消える |

これらをまとめて解決するために生まれたのが**データベース管理システム（DBMS）**です。データを 1 か所にまとめて管理し、プログラムはデータの置き方を知らなくても、DBMS に頼めばデータを読み書きできる。この「データとプログラムを切り離す」考え方が、データベースの出発点です。

## 階層型とネットワーク型 {#navigational}

1960 年代に登場した最初の DBMS は、データを**ポインタでつないだレコード**として扱いました。

```fig graph 階層型データベースのイメージ。親から子へのポインタをたどって目的のレコードにたどり着く。「顧客から注文を探す」のは得意だが、「ある商品を買った顧客」を探すには全部をたどる必要がある
{
  col: 150, row: 80,
  nodes: [
    { id: 'c1', label: '顧客 佐藤', x: 1, y: 0, kind: 'stack', mono: false },
    { id: 'o1', label: '注文 1', x: 0, y: 1, mono: false },
    { id: 'o2', label: '注文 3', x: 1, y: 1, mono: false },
    { id: 'o3', label: '注文 9', x: 2, y: 1, mono: false },
    { id: 'i1', label: '万年筆', x: 0, y: 2, kind: 'crate', mono: false },
    { id: 'i2', label: 'ノート', x: 1, y: 2, kind: 'crate', mono: false },
    { id: 'i3', label: '手帳', x: 2, y: 2, kind: 'crate', mono: false },
  ],
  edges: [
    { from: 'c1', to: 'o1' }, { from: 'c1', to: 'o2' }, { from: 'c1', to: 'o3' },
    { from: 'o1', to: 'i1' }, { from: 'o2', to: 'i2' }, { from: 'o3', to: 'i3' },
  ],

```

- **階層型**：データを親子の木で表す。代表は IBM の IMS（1960 年代後半）で、アポロ計画の部品管理のために作られた
- **ネットワーク型**：子が複数の親を持てるように、木を網に広げたもの。Charles Bachman の IDS が元になり、CODASYL という団体が仕様をまとめた。Bachman は 1973 年にチューリング賞を受けている

どちらも、プログラムは「このレコードの次のポインタをたどる」という命令を並べてデータを探します。こうしたデータベースは、**ナビゲーショナル（道案内型）**と呼ばれます。

道案内型には大きな弱点がありました。データの**探し方**がプログラムに書き込まれてしまうのです。「顧客ごとの注文」という道筋で作ったデータベースから「ある商品を買った顧客」を探そうとすると、全部の木をたどるプログラムを新しく書かなければなりません。データのつなぎ方を変えれば、プログラムも全部書き直しです。ファイルの時代の問題は、まだ半分しか解決していませんでした。

## Codd のリレーショナルモデル {#codd}

1970 年、IBM の研究所にいた数学者 Edgar F. Codd が、論文「A Relational Model of Data for Large Shared Data Banks（大規模な共有データバンクのためのリレーショナルモデル）」を発表します。

Codd の提案の中心は、次の 2 点です。

1. **データはすべて「表」で表す。** ポインタは使わない。つながりは、値どうしの一致（顧客 ID が同じ、など）で表す
2. **欲しいデータは「何が欲しいか」で頼む。** 「どうたどるか」は書かない。たどり方はシステムが考える

```fig graph リレーショナルモデルでは、つながりは値の一致で表す。ポインタがないので、どの方向からでも同じように探せる
{
  col: 230, row: 90,
  nodes: [
    { id: 'cu', label: 'customers', sub: 'id = 1, 佐藤', x: 0, y: 0, kind: 'stack' },
    { id: 'or', label: 'orders', sub: 'customer_id = 1', x: 1, y: 0, kind: 'stack' },
    { id: 'oi', label: 'order_items', sub: 'order_id, product_id', x: 2, y: 0, kind: 'stack' },
    { id: 'pr', label: 'products', sub: 'id = 1, 万年筆', x: 2, y: 1, kind: 'stack' },
  ],
  edges: [
    { from: 'cu', to: 'or', label: 'id が一致', both: true, style: 'muted' },
    { from: 'or', to: 'oi', label: 'id が一致', both: true, style: 'muted' },
    { from: 'oi', to: 'pr', label: 'id が一致', both: true, style: 'muted' },
  ],
}
```

2 番目の考え方は、**宣言的**と呼ばれます。手続きを書くのではなく、結果の条件を宣言する。この考え方のおかげで、データの置き方（どこにどう保存するか、どんな索引を作るか）を後から変えても、プログラムは書き直さずに済みます。ファイル時代から続いた問題に対する、根本的な答えでした。

ただし Codd の論文は数学の言葉で書かれていて、実際に速く動くのかを疑う声も多くありました。「ポインタをたどらずに、値を比べて探していたら遅すぎる」という批判です。この疑いを晴らすために、1970 年代に 2 つの大きな研究プロジェクトが始まります。

:::hist Codd の 12 の規則
Codd は 1985 年に、「リレーショナルと名乗る製品が満たすべき 12 の規則」を発表しました。当時、中身は道案内型のままで「リレーショナル」と宣伝する製品が多かったためです。Codd は 1981 年にチューリング賞を受けています。
:::


**System R**（IBM）は、リレーショナルモデルが実用的な速さで動くことを証明したプロジェクトです。ここで生まれた技術の多くが、今の PostgreSQL にも残っています。

- **SEQUEL**：Donald Chamberlin と Raymond Boyce が作った問い合わせ言語。英語に近い書き方で、数学を知らない人にも書けることを目指した。商標の問題で後に **SQL** と改名される
- **コストベースの最適化**：1979 年の Selinger らの論文で、いくつかの実行方法のコストを見積もって一番安いものを選ぶ方法が示された。第 15 章の実行計画は、この考え方の直系の子孫
- **トランザクションとロック**：Jim Gray らによる、複数の利用者が同時に使っても壊れない仕組み

**Ingres**（UC Berkeley）は、Michael Stonebraker と Eugene Wong が大学で始めたプロジェクトです。問い合わせ言語は SQL ではなく **QUEL** という別の言語でした。Ingres はソースコードが大学の外に配られ、多くの製品（Sybase、そこから派生した Microsoft SQL Server など）の元になりました。

:::note SQL の読み方
SQL は「エス・キュー・エル」と読むのが標準規格の立場ですが、元の名前にちなんで「シークェル」と読む人もいます。どちらも通じます。
:::

## SQL の標準化 {#standard}

1980 年代、各社が SQL を元にした製品を出し、方言が増えていきました。そこで ANSI（米国の標準化団体）と ISO（国際標準化機構）が SQL を規格にします。

| 規格 | 主な追加 |
| --- | --- |
| SQL-86 / SQL-89 | 最初の規格。SELECT、INSERT、UPDATE、DELETE、基本的な制約 |
| SQL-92 | 大改訂。`JOIN ... ON` の書き方、外部結合、CASE 式、日付時刻型、トランザクション分離レベル |
| SQL:1999 | 再帰問い合わせ（`WITH RECURSIVE`）、トリガ、BOOLEAN 型、正規表現、ユーザ定義型 |
| SQL:2003 | ウィンドウ関数、`MERGE`、シーケンスと識別列、XML |
| SQL:2008 | `TRUNCATE`、`FETCH FIRST`、INSTEAD OF トリガ |
| SQL:2011 | 時間を扱うテーブル（システム時間・適用時間） |
| SQL:2016 | JSON の関数、行パターン認識（`MATCH_RECOGNIZE`） |
| SQL:2023 | JSON 型、プロパティグラフ問い合わせ（SQL/PGQ） |

規格は巨大で、全部を実装しているデータベースはありません。PostgreSQL は規格への準拠を重視していて、多くの機能を規格どおりの書き方で使えます。そのうえで、配列型や `RETURNING`、`DISTINCT ON` のような独自の便利な拡張も持っています。

この本では、規格どおりの書き方と PostgreSQL 独自の書き方が両方あるときは、まず規格の書き方を紹介します。

## POSTGRES の誕生 {#postgres}

Ingres を商用化したあと、Stonebraker は Berkeley に戻り、1986 年に新しいプロジェクトを始めます。名前は **POSTGRES**。「Ingres の後（post）」という意味です。

POSTGRES の目標は、当時のリレーショナルデータベースの弱点を克服することでした。

- **ユーザが型を追加できる**：数値と文字列だけでなく、図形や時系列のような複雑なデータを扱えるようにする。そのための関数や演算子、索引の種類もユーザが追加できるようにする
- **ルールとトリガ**：データの変更に反応して処理を動かす
- **時間をさかのぼる**：データを上書きせずに古い版も残し、過去の時点のデータを問い合わせられるようにする

この「ユーザが型や索引を追加できる」という設計思想は、30 年以上たった今の PostgreSQL の最大の特徴になっています。第 19 章で紹介する JSON、全文検索、地理情報（PostGIS）、ベクトル検索（pgvector）などの機能は、どれもこの仕組みの上に作られています。

「データを上書きせずに古い版を残す」という考え方も、形を変えて残っています。第 13 章で学ぶ **MVCC** では、`UPDATE` は行を上書きせず、新しい版の行を追加します。

1994 年、Berkeley の大学院生だった Andrew Yu と Jolly Chen が、POSTQUEL の代わりに SQL を使えるようにしたものを **Postgres95** として公開しました。1996 年に名前を **PostgreSQL** に変え、Berkeley の手を離れて、世界中のボランティアが開発するオープンソースのプロジェクトになります。

:::note PostgreSQL の読み方
「ポストグレス・キュー・エル」と読みます。短く「ポスグレ」「Postgres」とも呼ばれ、公式にも Postgres という呼び方が認められています。
:::

いま動いているのが何の版か、確かめてみましょう。

```sql run
select version();
```

`show` コマンドで、設定値を 1 つだけ取り出すこともできます。

```sql run
show server_version;
```

PostgreSQL 18 で追加された `uuidv7()` 関数も試してみましょう。UUID は世界中で重ならない ID で、version 7 は先頭に時刻が入っているので、作った順に並びます。

```sql run
select uuidv7() as id1, uuidv7() as id2, uuidv7() as id3;
```

3 つの値の先頭の部分がほぼ同じで、後ろが違うことがわかります。先頭の 12 桁ほどがミリ秒単位の時刻です。

:::deep 版番号の付け方が 10 で変わった理由
9.6 までは「9.6」の 2 つ目の数字までがメジャーバージョンで、3 つ目（9.6.24 の 24）がマイナーバージョンでした。「9.5 と 9.6 は別のメジャー版」というのが分かりにくかったため、10 からは 1 つ目の数字だけがメジャーバージョンになりました。17.2 なら、メジャーが 17、マイナー（バグ修正）が 2 回目という意味です。マイナーバージョンの更新はデータの形式を変えないので、気軽に当ててよいものです。
:::

## ほかのデータベースとの関係 {#others}

今よく使われるリレーショナルデータベースを、PostgreSQL との違いで並べると次のようになります。

| データベース | 生まれ | PostgreSQL との主な違い |
| --- | --- | --- |
| Oracle Database | 1979 年、商用 | 有償。大企業の基幹系で長い実績。PL/SQL という手続き言語 |
| IBM Db2 | 1983 年、商用 | System R の直系。メインフレームでの実績 |
| Microsoft SQL Server | 1989 年、商用 | Sybase（Ingres の流れ）が元。Windows との統合 |
| MySQL | 1995 年、オープンソース | Web で広まった。ストレージエンジンを選べる。標準準拠より手軽さを重視してきた |
| SQLite | 2000 年、パブリックドメイン | サーバを持たず、1 つのファイルがデータベース。スマホやアプリに組み込む |
| PostgreSQL | 1996 年、オープンソース | 標準準拠と拡張性を重視。型・索引・言語を追加できる |

最近は、PostgreSQL と通信方式（プロトコル）だけを合わせた別のデータベースも増えています。分散データベースの CockroachDB や YugabyteDB、クラウドの Amazon Aurora PostgreSQL などです。「PostgreSQL の SQL と接続方法」が、業界の共通語の 1 つになりつつあります。

:::key この章のまとめ
- データベースは、データとプログラムを切り離すために生まれた
- 道案内型（階層型・ネットワーク型）は、探し方がプログラムに埋め込まれていた
- Codd のリレーショナルモデルは、データを表で表し、「何が欲しいか」だけを書く宣言的な方式を提案した
- SQL は IBM の System R で生まれ、1986 年から規格になった
- PostgreSQL は Berkeley の POSTGRES が元で、「型や索引を追加できる」設計思想を今も受け継いでいる
:::

## 確認問題 {#quiz}

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

:::quiz 動いている PostgreSQL の版
いまブラウザの中で動いている PostgreSQL の**メジャーバージョンの番号**（`18` のような数）だけを、1 行 1 列で出してください。

```sql answer
select current_setting('server_version_num')::int / 10000 as メジャーバージョン;
```

:::hint
`show server_version` の結果は `18.0` のような文字列です。`split_part(文字列, '.', 1)` で最初の部分を取り出せます。
:::

:::hint
`show` は SELECT の中に書けません。SELECT の中では `current_setting('server_version')` を使います。
:::
:::
