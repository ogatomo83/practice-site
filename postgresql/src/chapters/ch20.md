## サーバの全体像 {#architecture}

まず、本番の PostgreSQL がどんなプロセスで動いているかを整理しておきます。ブラウザの PGlite は 1 つのプロセスですが、サーバ版は複数のプロセスが共有メモリを介して協力しています。

```fig graph サーバ版 PostgreSQL のプロセス構成。接続ごとにバックエンドプロセスが 1 つ作られ、共有バッファと WAL バッファを共有する

  nodes: [
    { id: 'cl1', label: 'クライアント', x: 0, y: 0, kind: 'muted', mono: false },
    { id: 'cl2', label: 'クライアント', x: 0, y: 1, kind: 'muted', mono: false },
    { id: 'pm', label: 'postmaster', sub: '接続を受けて子を作る', x: 1, y: -0.2, kind: 'accent', mono: false },
    { id: 'be1', label: 'バックエンド', sub: '接続 1 つに 1 プロセス', x: 2, y: 0, kind: 'stack', mono: false },
    { id: 'be2', label: 'バックエンド', x: 2, y: 1, kind: 'stack', mono: false },
    { id: 'shm', label: '共有メモリ', sub: '共有バッファ・WAL バッファ・ロック表', x: 3, y: 0.5, kind: 'crate', mono: false },

```

| プロセス | 役割 | 関係する章 |
| --- | --- | --- |
| postmaster | 起動し、接続を受けるたびにバックエンドを fork する | |
| バックエンド | 1 つの接続の SQL を処理する | 第 15 章 |
| checkpointer | チェックポイントを行う | 第 16 章 |
| background writer | 汚れたページを少しずつ書き出す | 第 12 章 |
| walwriter | WAL バッファを WAL ファイルに書く | 第 16 章 |

| WAL sender | スタンバイに WAL を送る | 第 16 章 |

「1 接続 = 1 プロセス」という設計のため、PostgreSQL は数千の接続を直接受けるのが苦手です。これが後で出てくる**接続プーリング**が必要な理由です。

## ロールと権限 {#roles}

PostgreSQL では、ユーザもグループも**ロール**という 1 つの仕組みで表します。ログインできるロールがユーザ、ほかのロールをまとめるロールがグループです。

```sql run
select current_user as 今のロール, rolsuper as スーパーユーザ
from pg_roles where rolname = current_user;
```

今は、何でもできるスーパーユーザ `postgres` で接続しています。本番のアプリケーションをスーパーユーザで接続させてはいけません。必要な権限だけを持つロールを作ります。

```sql run
create role shop_reader nologin;                 -- 読むだけのグループ
create role shop_writer nologin;                 -- 書けるグループ
create role app_user login password 'dummy' in role shop_writer;
create role analyst  login password 'dummy' in role shop_reader;

grant usage on schema public to shop_reader, shop_writer;
grant select on all tables in schema public to shop_reader;
grant select, insert, update, delete on orders, order_items to shop_writer;
grant select on customers, products, categories to shop_writer;

select grantee, table_name, string_agg(privilege_type, ', ' order by privilege_type) as 権限
from information_schema.role_table_grants
where grantee in ('shop_reader', 'shop_writer') and table_name in ('orders', 'customers', 'employees')
group by grantee, table_name
order by grantee, table_name;
```

`set role` で、別のロールとして振る舞ってみます。

```sql run
set role analyst;
select current_user, count(*) as 読める from customers;
reset role;
```

```sql run error
set role analyst;
delete from orders where id = 1;
```

:::pgerr 42501 permission denied for table orders
`42501` は権限が足りないエラーです。analyst は shop_reader の一員なので、SELECT だけが許されています。
:::

```sql run
reset role;
select current_user;
```

:::key 権限の設計の基本
- アプリケーション用、分析用、管理用など、**役割ごとにロールを分ける**
- 権限はグループのロールに付け、ユーザのロールはグループに入れる
- テーブルを作るロール（オーナー）と、アプリケーションが接続するロールを分ける。オーナーは DROP や ALTER ができてしまうため
- 新しく作るテーブルにも権限が付くよう、`alter default privileges` を設定しておく
:::

### 列の権限

テーブル全体ではなく、列ごとに権限を付けることもできます。

```sql run
create role hr_viewer nologin;
grant select (id, name, dept) on employees to hr_viewer;   -- salary は見せない
set role hr_viewer;
select id, name, dept from employees limit 3;
reset role;
```

```sql run error
set role hr_viewer;
select name, salary from employees;
```

```sql run
reset role;
```

## 行レベルセキュリティ {#rls}

列ではなく**行**ごとに、誰が見られるかを決めたいことがあります。たとえば、複数の会社が使うサービス（マルチテナント）で、自分の会社のデータだけを見せたい場合です。

**行レベルセキュリティ**（RLS、9.5 から）を有効にすると、テーブルに**ポリシー**として行の条件を付けられます。条件は、そのロールが実行するすべての SQL に、自動的に付け加えられます。

```sql run
create table tenant_notes (
  id     int generated always as identity primary key,
  tenant text not null,
  body   text not null
);
insert into tenant_notes (tenant, body) values
  ('tsubame', '棚卸しは月末'), ('tsubame', '万年筆の入荷'), ('kamome', '新店舗の準備');

create role tenant_app nologin;
grant select, insert on tenant_notes to tenant_app;

alter table tenant_notes enable row level security;
create policy tenant_isolation on tenant_notes
  using (tenant = current_setting('app.tenant'))            -- 見える行
  with check (tenant = current_setting('app.tenant'));      -- 書ける行
```

アプリケーションは、接続したときに `app.tenant` という設定に自分のテナント名を入れてから SQL を実行する、という約束にします。

```sql run
set app.tenant = 'tsubame';
set role tenant_app;
select * from tenant_notes;
reset role;
```

```sql run
set app.tenant = 'kamome';
set role tenant_app;
select * from tenant_notes;
reset role;
```

同じ `select * from tenant_notes` なのに、見える行が違います。`where` を書き忘れても、ほかのテナントのデータは漏れません。

```sql run error
set app.tenant = 'kamome';
set role tenant_app;
insert into tenant_notes (tenant, body) values ('tsubame', '他社のデータに書き込む');
```

```sql run
reset role;
explain (costs off) select * from tenant_notes;
```

スーパーユーザとテーブルのオーナーには、既定ではポリシーが適用されません（`alter table ... force row level security` で適用させられます）。ここで `explain` を見ても条件が出ないのはそのためです。

## バックアップ {#backup}

バックアップには 3 つの方式があり、それぞれ得意なことが違います。

| 方式 | 道具 | 取れるもの | 戻せる時点 | 向いている場面 |
| --- | --- | --- | --- | --- |
| **論理バックアップ** | `pg_dump` / `pg_dumpall` | SQL や独自形式のダンプ | ダンプを取った時点 | 小〜中規模、一部のテーブルだけ、別のバージョンへの移行 |
| **物理バックアップ** | `pg_basebackup` | データディレクトリのコピー | バックアップの時点 | 大規模、丸ごと素早く戻す |
| **PITR** | 物理バックアップ + WAL アーカイブ | 上記 + その後の全 WAL | **任意の時点** | 誤操作からの復旧が必要な本番 |

```console norun
$ pg_dump -Fc -d shop -f shop.dump          # 独自形式（圧縮・並列リストア可）でダンプ
$ pg_restore -d shop_new -j 4 shop.dump     # 4 並列でリストア
$ pg_dump -d shop -t orders --data-only     # orders のデータだけを SQL で
$ pg_basebackup -D /backup/base -Ft -z -P   # 物理バックアップ（tar、圧縮、進捗表示）
```

`pg_dump` は、第 13 章の REPEATABLE READ と同じ**1 つのスナップショット**でデータを読むので、ダンプ中に書き込みがあっても、一貫した時点のデータになります。

PostgreSQL 17 からは、前回のバックアップからの変更だけを取る**増分バックアップ**（`pg_basebackup --incremental`）もできるようになりました。

:::warn バックアップは戻せて初めてバックアップ
バックアップのファイルが壊れていた、手順書がなくて戻せなかった、という事故は珍しくありません。**定期的に、実際に別のサーバへ戻す訓練**をして、戻るまでの時間を測っておきます。
:::

## 設定とチューニング {#tuning}

PostgreSQL の設定は `postgresql.conf` に書きます。現在の値は `pg_settings` で見られます。

```sql run
select name, setting, unit, short_desc
from pg_settings
where name in ('shared_buffers', 'effective_cache_size', 'work_mem', 'maintenance_work_mem',
               'max_connections', 'random_page_cost', 'checkpoint_timeout', 'max_wal_size')
order by name;
```

まず見直す設定と、出発点の目安は次のとおりです（メモリ 16 GB、SSD のサーバの例）。

| 設定 | 既定値 | 出発点の目安 | 意味と関係する章 |
| --- | --- | --- | --- |
| `shared_buffers` | 128MB | メモリの 25%（4GB） | 共有バッファの大きさ（第 12 章） |
| `effective_cache_size` | 4GB | メモリの 50〜75%（12GB） | OS のキャッシュも含めた、使えるキャッシュの見込み。プランナの見積もりに使うだけで、確保はしない |
| `work_mem` | 4MB | 16〜64MB | 並べ替え・ハッシュ 1 回あたりのメモリ（第 15 章）。接続数 × 同時の操作数だけ使われうるので注意 |
| `maintenance_work_mem` | 64MB | 512MB〜1GB | VACUUM や CREATE INDEX が使うメモリ |
| `random_page_cost` | 4 | 1.1（SSD） | 飛び飛びの読み込みのコスト（第 15 章） |
| `max_wal_size` | 1GB | 4〜16GB | チェックポイントの間隔（第 16 章） |
| `max_connections` | 100 | 必要最小限 | 接続数の上限。増やすより、接続プーリングを使う |

```conf norun title="postgresql.conf の例"
shared_buffers = 4GB
effective_cache_size = 12GB
work_mem = 32MB
maintenance_work_mem = 1GB
random_page_cost = 1.1
max_wal_size = 8GB
checkpoint_completion_target = 0.9
```

設定には、その場で変えられるもの、設定ファイルを読み直せば効くもの（`select pg_reload_conf()`）、再起動が必要なもの（`shared_buffers` など）があります。`pg_settings` の `context` 列で分かります。

```sql run
select name, context from pg_settings
where name in ('work_mem', 'random_page_cost', 'shared_buffers', 'max_connections', 'log_min_duration_statement');
```

| context | いつ効くか |
| --- | --- |
| `user` | `set` でその接続だけ変えられる |
| `sighup` | 設定ファイルを直して `pg_reload_conf()` |
| `postmaster` | サーバの再起動が必要 |

:::key チューニングの順番
設定値を変える前に、まず**遅い問い合わせ**を見つけて直すほうが、ずっと大きな効果があります。第 15 章の `pg_stat_statements` で上位の問い合わせを見つけ、インデックスや書き方を見直してから、設定に手を付けます。
:::

## 接続プーリング {#pooling}

PostgreSQL は接続ごとにプロセスを作るので、接続を作るのに数ミリ秒かかり、1 接続あたり数 MB のメモリを使います。Web アプリケーションが、リクエストのたびに接続したり、数千の接続を張りっぱなしにしたりすると、データベースが接続の管理だけで疲れてしまいます。

**接続プーラ**は、アプリケーションとデータベースの間に立ち、少数の接続を使い回します。

```fig graph 接続プーリング。アプリケーションの 1000 の接続を、プーラが 20 本ほどの実際の接続に束ねる
{
  col: 200, row: 76,
  nodes: [
    { id: 'a1', label: 'アプリ × 1000 接続', x: 0, y: 0, kind: 'muted', mono: false },
    { id: 'pb', label: 'PgBouncer', sub: 'トランザクション単位で貸し出す', x: 1, y: 0, kind: 'accent', mono: false },
    { id: 'pg', label: 'PostgreSQL', sub: '実際の接続は 20 本', x: 2, y: 0, kind: 'stack', mono: false },
  ],
  edges: [ { from: 'a1', to: 'pb', label: '多い' }, { from: 'pb', to: 'pg', label: '少ない', style: 'accent' } ],
}
```

代表的なのは PgBouncer です。トランザクションが終わるたびに接続を別のクライアントに貸し出す**トランザクションモード**が最も効率的ですが、その代わり、接続に結び付いた状態（`set` した設定、一時テーブル、プリペアドステートメントの一部）は使えなくなる点に注意します。

## パーティショニング {#partitioning}

何億行もある表は、VACUUM やインデックスの再作成に時間がかかり、古いデータを消すのも大変です。**パーティショニング**は、1 つの論理的な表を、範囲ごとの複数の物理的な表に分けます。

```sql run
create table access_logs (
  at   timestamptz not null,
  path text not null
) partition by range (at);

create table access_logs_2026_01 partition of access_logs
  for values from ('2026-01-01') to ('2026-02-01');
create table access_logs_2026_02 partition of access_logs
  for values from ('2026-02-01') to ('2026-03-01');
create table access_logs_2026_03 partition of access_logs
  for values from ('2026-03-01') to ('2026-04-01');

insert into access_logs
select timestamptz '2026-01-01 00:00+09' + (g || ' minutes')::interval * 120, '/p/' || g
from generate_series(1, 1000) g;

select tableoid::regclass as 物理的な表, count(*) from access_logs group by 1 order by 1;
```

親の表 `access_logs` に INSERT すると、値に応じて正しいパーティションに振り分けられます。検索の条件にパーティションのキーがあれば、関係のないパーティションは読みません（**パーティションプルーニング**）。

```sql run
explain (costs off) select count(*) from access_logs where at >= '2026-02-10' and at < '2026-02-20';
```

`access_logs_2026_02` だけが読まれています。古いデータを消すときは、DELETE の代わりにパーティションごと切り離して DROP します。何百万行の DELETE と違い、一瞬で終わり、VACUUM も要りません。

```sql run
alter table access_logs detach partition access_logs_2026_01;
drop table access_logs_2026_01;
select tableoid::regclass, count(*) from access_logs group by 1 order by 1;
```

| 方式 | 分け方 | 例 |
| --- | --- | --- |
| `range` | 値の範囲 | 月ごとのログ |
| `list` | 値の一覧 | 国ごと、テナントごと |
| `hash` | ハッシュ値で均等に | 偏りなく分けたいとき |

## 監視 {#monitoring}

本番で見ておくべき指標と、それを見るビューをまとめます。

| 見るもの | ビュー・関数 | 何に気づけるか |
| --- | --- | --- |
| 実行中の問い合わせ、待ち | `pg_stat_activity` | 長時間のトランザクション、ロック待ち（第 13・17 章） |
| 問い合わせごとの統計 | `pg_stat_statements` | 遅い・回数の多い問い合わせ（第 15 章） |
| テーブルごとの統計 | `pg_stat_user_tables` | Seq Scan の多さ、死んだ行、最後の VACUUM（第 13 章） |
| インデックスの使用状況 | `pg_stat_user_indexes` | 使われていないインデックス（第 14 章） |
| キャッシュヒット率 | `pg_stat_database` | 共有バッファが足りているか（第 12 章） |
| レプリケーションの遅れ | `pg_stat_replication` | スタンバイの遅延（第 16 章） |
| XID の年齢 | `age(datfrozenxid)` | 周回の危険（第 13 章） |
| I/O | `pg_stat_io`（16 から） | どの処理がどれだけ読み書きしているか |

```sql run
select datname,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) as キャッシュヒット率,
       xact_commit as コミット数, xact_rollback as ロールバック数,
       (select age(datfrozenxid) from pg_database d where d.datname = s.datname) as XIDの年齢
from pg_stat_database s
where datname = current_database();
```

```sql run
select relname, seq_scan, idx_scan, n_live_tup, n_dead_tup, last_autovacuum
from pg_stat_user_tables
order by seq_scan desc
limit 5;
```

## バージョンアップ {#upgrade}

PostgreSQL は毎年メジャーバージョンが出て、各版は 5 年間サポートされます（第 1 章）。

| 種類 | 例 | 方法 | 停止時間 |
| --- | --- | --- | --- |
| マイナー | 18.1 → 18.2 | バイナリを入れ替えて再起動 | 再起動の数秒 |
| メジャー（ダンプ） | 16 → 18 | `pg_dump` → 新しいサーバへ `pg_restore` | データ量に比例して長い |
| メジャー（pg_upgrade） | 16 → 18 | `pg_upgrade --link` でデータファイルを流用 | 数分 |
| メジャー（論理レプリケーション） | 16 → 18 | 新しいサーバへ論理レプリケーションで同期し、切り替える | 切り替えの数秒（第 16 章） |

マイナーバージョンはセキュリティとバグの修正だけで、データの形式も変わりません。**マイナーバージョンの更新はすぐに当てる**のが原則です。

:::try 
1. `shop_reader` に `employees` の SELECT 権限がある状態で、analyst ロールから `salary` 列が見えないようにするには、どうすればよいか考えてください（ヒント：表への権限を取り消し、列の権限だけを付ける）
2. `access_logs` に 2026 年 4 月のパーティションを追加し、4 月のデータを INSERT してください。パーティションのない 5 月のデータを入れるとどうなるかも試してください
:::

```sql run title="練習用"
create table access_logs_2026_04 partition of access_logs
  for values from ('2026-04-01') to ('2026-05-01');
insert into access_logs values ('2026-04-15 12:00+09', '/april');
select tableoid::regclass, count(*) from access_logs group by 1 order by 1;
```

:::key この章のまとめ
- サーバ版は 1 接続 1 プロセス。補助プロセスがチェックポイント、WAL、autovacuum を担う
- ロールで権限を設計し、アプリケーションは最小限の権限で接続する。列や行（RLS）の単位でも制御できる
- バックアップは論理（pg_dump）、物理（pg_basebackup）、PITR の 3 方式。戻す訓練をする
- 設定は `shared_buffers`、`work_mem`、`random_page_cost`、`max_wal_size` から。その前に遅い問い合わせを直す
- 接続が多いなら接続プーラ。巨大な表はパーティショニングで分け、古いデータはパーティションごと消す
- 監視は pg_stat_* のビューで。マイナーバージョンはすぐに当てる
:::

## 確認問題 {#quiz}

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

:::quiz 一部の列だけ読めるロール
ログインしないロール `hr_reader` を作り、`employees` の `id` と `name` の 2 列**だけ**を読めるようにしてください（`salary` などは読めない）。

```sql answer
create role hr_reader nologin;
grant select (id, name) on employees to hr_reader;
```

```sql check
select has_column_privilege('hr_reader', 'employees', 'name', 'select')   as name,
       has_column_privilege('hr_reader', 'employees', 'salary', 'select') as salary,
       has_table_privilege('hr_reader', 'employees', 'select')            as テーブル全体;
```

:::hint
`grant select (列, 列) on テーブル to ロール;` で列の単位で権限を付けられます。
:::
:::

:::quiz パーティションを足す
月ごとにパーティションを分けた `logs`（`at timestamptz`, `path text`）が用意されていて、いまは 2026 年 1 月のパーティションだけがあります。2026 年 2 月のパーティションを追加し、`('2026-02-14 12:00+09', '/valentine')` を入れてください。

```sql prep
create table logs (at timestamptz not null, path text not null) partition by range (at);
create table logs_2026_01 partition of logs for values from ('2026-01-01') to ('2026-02-01');
insert into logs values ('2026-01-05 09:00+09', '/new-year');
```

```sql answer
create table logs_2026_02 partition of logs
  for values from ('2026-02-01') to ('2026-03-01');
insert into logs values ('2026-02-14 12:00+09', '/valentine');
```

```sql check
select (select count(*) from logs) as 行数,
       (select count(*)
          from pg_inherits i join pg_class c on c.oid = i.inhrelid
         where i.inhparent = 'logs'::regclass
           and pg_get_expr(c.relpartbound, c.oid) like '%2026-02-01%2026-03-01%') as 二月のパーティション;
```

:::hint
`create table 名前 partition of 親 for values from (開始) to (終わり);`。終わりの値は含みません。
:::
:::

:::quiz テナントごとに行を見せ分ける
テナントのメモ `notes`（`tenant`, `body`）と、読み取り用のロール `note_app` が用意されています。`note_app` からは、設定 `app.tenant` と同じ `tenant` の行だけが見えるように、行レベルセキュリティを設定してください。

```sql prep
create table notes (tenant text not null, body text not null);
insert into notes values ('tsubame', '棚卸しは月末'), ('tsubame', '万年筆の入荷'), ('kamome', '新店舗の準備');
create role note_app nologin;
grant select on notes to note_app;
```

```sql answer
alter table notes enable row level security;
create policy tenant_only on notes
  using (tenant = current_setting('app.tenant'));
```

```sql check
set local app.tenant = 'kamome';
set local role note_app;
select tenant, body from notes;
```

:::hint
`alter table ... enable row level security;` で有効にし、`create policy 名前 on テーブル using (条件);` で見える行の条件を書きます。
:::

:::hint
答え合わせでは `app.tenant` を `kamome` にして `note_app` として `select` し、1 行だけ見えるかを確かめます。
:::
:::
