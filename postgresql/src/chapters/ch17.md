## MVCC でも残る問題 {#why}

第 13 章の MVCC のおかげで、**読む人は書く人を待たず、書く人は読む人を待ちません**。それでも、次の場面では順番を決める必要があります。

| 場面 | 問題 |
| --- | --- |
| 2 人が同じ行を同時に UPDATE する | 両方の新しい版ができると、どちらが正しいか決められない |
| 行を読んで、それをもとに判断して書く | 判断している間に、ほかの人に書き換えられる |
| テーブルを DROP している最中に、誰かがそのテーブルを読む | 読んでいる途中でファイルが消える |

これらを防ぐのが**ロック**です。PostgreSQL のロックは大きく 2 種類あります。

- **テーブルレベルのロック**：テーブル全体に対するもの。共有メモリのロック表で管理される
- **行レベルのロック**：個々の行に対するもの。**タプルのヘッダ**に記録される

## テーブルレベルのロック {#table-locks}

テーブルのロックには 8 つのモードがあり、どのモードどうしが衝突するか（同時に持てないか）が決まっています。

| モード | 主に取る操作 | 衝突する相手（の例） |
| --- | --- | --- |
| ACCESS SHARE | `select` | ACCESS EXCLUSIVE だけ |
| ROW SHARE | `select ... for update / for share` | EXCLUSIVE、ACCESS EXCLUSIVE |
| ROW EXCLUSIVE | `insert`、`update`、`delete`、`merge` | SHARE 以上 |
| SHARE UPDATE EXCLUSIVE | `vacuum`、`analyze`、`create index concurrently` | 自分自身、SHARE 以上 |
| SHARE | `create index`（concurrently なし） | ROW EXCLUSIVE（書き込み）以上 |
| SHARE ROW EXCLUSIVE | `create trigger` など | ROW EXCLUSIVE 以上 |
| EXCLUSIVE | `refresh materialized view concurrently` | ROW SHARE 以上 |
| ACCESS EXCLUSIVE | `drop table`、`truncate`、`vacuum full`、多くの `alter table` | **すべて**（select も） |

覚えておくべきは両端です。

- 普通の SELECT（ACCESS SHARE）は、ACCESS EXCLUSIVE 以外の何とも衝突しない
- ACCESS EXCLUSIVE は、SELECT も含めてすべてと衝突する

自分が持っているロックは `pg_locks` ビューで見られます。

```sql run
begin;
select count(*) from products;
update customers set prefecture = prefecture where id = 1;
select l.locktype, c.relname as 対象, l.mode, l.granted
from pg_locks l
left join pg_class c on c.oid = l.relation
where l.pid = pg_backend_pid() and l.locktype = 'relation' and c.relname not like 'pg_%'
order by c.relname;
```

products には `AccessShareLock`（読んだだけ）、customers には `RowExclusiveLock`（行を書いた）が付いています。主キーのインデックスにもロックが取られています。テーブルのロックは、**トランザクションが終わるまで**解放されません。

```sql run
commit;
select count(*) as 残っているロック
from pg_locks l join pg_class c on c.oid = l.relation
where l.pid = pg_backend_pid() and c.relname not like 'pg_%';
```

明示的にロックを取ることもできます。

```sql run
begin;
lock table products in access exclusive mode;
select c.relname, l.mode from pg_locks l join pg_class c on c.oid = l.relation
where l.pid = pg_backend_pid() and c.relname = 'products';
rollback;
```

### ロック待ちの行列

ロックで一番怖いのは、**待ち行列**ができることです。

```fig seq ALTER TABLE がロック待ちの行列を作る例。長い SELECT の後ろで ACCESS EXCLUSIVE を待つ ALTER のさらに後ろで、普通の SELECT まで全部止まってしまう
{
  colw: 170,
  actors: [ { id: 'a', label: '長い集計 A', kind: 'stack' }, { id: 't', label: 'orders 表', kind: 'crate' }, { id: 'b', label: 'ALTER TABLE B', kind: 'accent' }, { id: 'c', label: '普通の SELECT C', kind: 'ext' } ],
  msgs: [
    { from: 'a', to: 't', label: 'ACCESS SHARE を取得' },
    { note: '10 分かかる集計', at: 'a' },
    { from: 'b', to: 't', label: 'ACCESS EXCLUSIVE を要求', style: 'accent' },
    { note: 'A と衝突するので待つ', at: 'b', style: 'accent' },
    { from: 'c', to: 't', label: 'ACCESS SHARE を要求' },
    { note: 'B が先に並んでいるので、C も待つ', at: 'c', style: 'accent' },
    { note: 'アプリの全リクエストが止まる', at: ['b', 'c'], style: 'accent' },
  ],
}
```

C の SELECT は、A とは衝突しません。しかし PostgreSQL のロックは**先に並んだ要求を優先する**ので、B の後ろに並んだ C も待たされます。一瞬で終わるはずの `alter table ... add column` が、サービス全体を止めてしまう典型的な事故です。

:::key DDL には lock_timeout を付ける
本番でテーブルの定義を変えるときは、`set lock_timeout = '3s';` を先に実行します。3 秒以内にロックが取れなければ、ALTER はエラーで諦め、後ろに並んだ人たちを解放します。その後、時間をおいてやり直します。
:::

```sql run
set lock_timeout = '3s';
begin;
lock table products in access exclusive mode nowait;
select 'ロックを取得できた' as 結果;
rollback;
reset lock_timeout;
```

`nowait` は、ロックがすぐに取れなければ待たずにエラー（`55P03`）にする指定です。ここでは自分以外にロックを持つ人がいないので成功します。`lock_timeout` は待つ時間の上限、`nowait` は待たない、という違いです。

## 行レベルのロック {#row-locks}

UPDATE や DELETE は、対象の行に**行ロック**をかけます。同じ行を UPDATE しようとした 2 人目は、1 人目のトランザクションが終わるまで待ちます。

```fig seq 同じ行への 2 つの UPDATE。B は A のコミットを待ち、A がコミットした後の最新の版に対して、条件を確かめ直してから更新する（READ COMMITTED）
{
  colw: 220,
  actors: [ { id: 'a', label: 'トランザクション A', kind: 'stack' }, { id: 'r', label: '在庫の行 stock=5', kind: 'crate' }, { id: 'b', label: 'トランザクション B', kind: 'ext' } ],
  msgs: [
    { from: 'a', to: 'r', label: 'UPDATE stock = stock - 1' },

    { from: 'b', to: 'r', label: 'UPDATE stock = stock - 1', style: 'accent' },
    { note: 'A の行ロックを待つ', at: 'b', style: 'accent' },
    { from: 'a', to: 'r', label: 'COMMIT' },
    { from: 'r', to: 'b', label: '最新版 stock=4 を読み直す' },

```

### SELECT ... FOR UPDATE

「読んでから判断して書く」処理では、読む時点で行をロックしておく必要があります。`select ... for update` は、読んだ行に UPDATE と同じ行ロックをかけます。

```sql run
begin;
select id, name, stock from products where id = 1 for update;
-- ここでアプリが「在庫があるか」を判断する。この間、ほかの人はこの行を変更できない
update products set stock = stock - 1 where id = 1;
commit;
select id, stock from products where id = 1;
```

行ロックには 4 つの強さがあります。

| 指定 | 防ぐもの | 使いどころ |
| --- | --- | --- |
| `for update` | ほかの更新・削除・for update / share | 行を変更するつもりで読む |
| `for no key update` | 同上。ただし外部キーのチェック（key share）とは衝突しない | 主キー以外を変更する（UPDATE が自動で取るのはこれ） |
| `for share` | 更新・削除 | 読んだ値が変わらないことを保証したい |
| `for key share` | 削除と主キーの変更 | 外部キーのチェックが、参照先の行に自動で取る |

### 行ロックはどこにあるか

テーブルのロックは共有メモリのロック表にありますが、行ロックは違います。何百万行をロックしても共有メモリがあふれないよう、行ロックは**タプルのヘッダ**に書き込まれます。第 12 章の `t_xmax` を使うのです。

```sql run
create extension if not exists pageinspect;
create table lockdemo (id int, v text);
insert into lockdemo values (1, 'a'), (2, 'b');
begin;
select txid_current() as 自分のXID;
select * from lockdemo where id = 1 for update;
select lp, t_xmin, t_xmax, raw_flags
from heap_page_items(get_raw_page('lockdemo', 0)),
     lateral heap_tuple_infomask_flags(t_infomask, t_infomask2);
```

ロックした行（lp 1）の `t_xmax` に自分の XID が入り、`HEAP_XMAX_LOCK_ONLY`（xmax はロックのためだけで、削除ではない）と `HEAP_XMAX_EXCL_LOCK` のフラグが立っています。2 人目がこの行を変えようとすると、`t_xmax` の XID がまだ動いていることを見て、そのトランザクションの終了を待ちます。

```sql run
rollback;
```

:::note 行ロックはページを書き換える
行ロックをかけると、タプルのヘッダが書き換わるので、ページが汚れて WAL も書かれます。`select ... for update` は読むだけの SELECT より重い処理です。大量の行に for update をかけるのは避けましょう。
:::

## デッドロック {#deadlock}

2 つのトランザクションが、互いに相手の持っているロックを待つと、永遠に終わりません。これが**デッドロック**です。

```fig seq デッドロック。A は口座 1 → 2、B は口座 2 → 1 の順にロックを取ろうとして、互いを待ち合う
{
  colw: 210,
  actors: [ { id: 'a', label: 'トランザクション A', kind: 'stack' }, { id: 'r1', label: '口座 1', kind: 'crate' }, { id: 'r2', label: '口座 2', kind: 'crate' }, { id: 'b', label: 'トランザクション B', kind: 'ext' } ],
  msgs: [
    { from: 'a', to: 'r1', label: 'UPDATE（ロック取得）' },
    { from: 'b', to: 'r2', label: 'UPDATE（ロック取得）' },
    { from: 'a', to: 'r2', label: 'UPDATE → B を待つ', style: 'accent' },
    { from: 'b', to: 'r1', label: 'UPDATE → A を待つ', style: 'accent' },
    { note: '1 秒後、PostgreSQL が輪を検出し、片方を中止する', at: ['a', 'b'], style: 'accent' },
  ],
}
```

PostgreSQL は、ロックを `deadlock_timeout`（既定 1 秒）待っても取れないと、待ちの関係をたどって輪ができていないか調べます。輪があれば、片方のトランザクションをエラーにして中止します。

:::pgerr 40P01 deadlock detected
DETAIL に、どのプロセスがどのトランザクションを待っていたかが書かれます。中止された側はやり直す必要があります。
:::

```sql norun title="psql を 2 つ開いて試す場合"
-- セッション A                           -- セッション B
begin;                                    begin;
update account set balance = balance - 100 where id = 1;
                                          update account set balance = balance - 100 where id = 2;
update account set balance = balance + 100 where id = 2;  -- 待つ
                                          update account set balance = balance + 100 where id = 1;  -- デッドロック
```

:::key デッドロックを防ぐ
**ロックを取る順番を全員で揃える**のが根本的な対策です。振り込みなら、送金元・送金先の順ではなく、「口座番号の小さいほうから」ロックするように決めておけば、輪はできません。それでも起きる可能性はあるので、`40P01` と `40001` を受け取ったら再試行するコードにしておきます。
:::

## ジョブキューと SKIP LOCKED {#skip-locked}

「未処理のジョブを 1 件取り出して処理する」ワーカを何台も動かす場面を考えます。単純に `for update` すると、全員が同じ先頭の 1 件を取り合って、順番待ちになります。

`for update skip locked` は、**ほかの人がロックしている行を飛ばして**、取れる行だけを返します。

```sql run
create table jobs (id int primary key, payload text, done boolean not null default false);
insert into jobs select g, 'job ' || g, false from generate_series(1, 5) g;

-- ワーカが 1 件取り出して処理する
begin;
select id, payload from jobs
where not done
order by id
limit 1
for update skip locked;
update jobs set done = true where id = 1;
commit;
select * from jobs order by id;
```

{
  col: 170, row: 72,
  nodes: [
    { id: 'w1', label: 'ワーカ 1', x: 0, y: 0, kind: 'stack', mono: false },
    { id: 'w2', label: 'ワーカ 2', x: 0, y: 1, kind: 'stack', mono: false },
    { id: 'w3', label: 'ワーカ 3', x: 0, y: 2, kind: 'stack', mono: false },
    { id: 'j1', label: 'job 1', sub: 'ロック中', x: 1, y: 0, kind: 'accent', mono: false },
    { id: 'j2', label: 'job 2', sub: 'ロック中', x: 1, y: 1, kind: 'accent', mono: false },

PostgreSQL をジョブキューとして使うライブラリ（Ruby の GoodJob、Python の Procrastinate、Go の River など）は、この仕組みで作られています。`nowait` は、ロックが取れなければ待たずにすぐエラーにする指定です。

## 勧告的ロック {#advisory}

**勧告的ロック**（advisory lock）は、テーブルや行とは関係なく、アプリケーションが決めた**数値**に対して取るロックです。PostgreSQL はロックを管理するだけで、何を守るかはアプリケーションが決めます。

```sql run
select pg_try_advisory_lock(42) as 取れた;
select pg_try_advisory_lock(42) as 同じ接続ならもう一度取れる;
select locktype, objid, mode, granted from pg_locks where locktype = 'advisory';
select pg_advisory_unlock(42), pg_advisory_unlock(42);
```

「夜間バッチが 2 重に起動しないようにする」「同じ顧客の処理を同時に走らせない」といった、データベースの外側の処理の排他に使えます。`pg_advisory_xact_lock` を使うと、トランザクションの終わりに自動で解放されます。

## ロック待ちを調べる {#monitor}

本番で「何かが詰まっている」ときは、誰が誰を待っているかを調べます。`pg_blocking_pids(pid)` は、そのプロセスを止めているプロセスの一覧を返します。

```sql norun title="ロック待ちの一覧（サーバ版で使う）"
select a.pid,
       pg_blocking_pids(a.pid) as 待っている相手,
       a.wait_event_type, a.wait_event,
       now() - a.xact_start as トランザクション時間,
       left(a.query, 60) as 文
from pg_stat_activity a
where cardinality(pg_blocking_pids(a.pid)) > 0;
```

待たせている側のプロセスは、`pg_cancel_backend(pid)`（実行中の文だけを止める）か、`pg_terminate_backend(pid)`（接続ごと切る）で止められます。

:::try 
1. トランザクションの中で `jobs` から 2 件を `for update skip locked` で取り出し、`pg_locks` で行ロックが見えるか確かめてください（行ロックはタプルにあるので、普通は `pg_locks` に出ないことに注目）
2. `pg_advisory_xact_lock(7)` をトランザクションの中で取り、commit した後に `pg_locks` から消えることを確かめてください
:::

```sql run title="練習用"
begin;
select pg_advisory_xact_lock(7);
select locktype, objid, mode from pg_locks where locktype = 'advisory';
commit;
select count(*) as commit後 from pg_locks where locktype = 'advisory';
```

:::key この章のまとめ
- MVCC でも、書く人どうしと DDL には順番が必要。それがロック
- テーブルのロックは 8 モード。SELECT は ACCESS SHARE、DROP や多くの ALTER は ACCESS EXCLUSIVE
- ロック待ちは行列になる。DDL には `lock_timeout` を付ける
- 行ロックはタプルの xmax に書かれる。読んで判断して書くなら `for update`
- デッドロックは 1 秒後に検出され、片方が `40P01` で中止される。ロックの順番を揃える
- ジョブキューには `skip locked`。アプリの排他には勧告的ロック
:::

## 確認問題 {#quiz}

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

:::quiz 明示的にテーブルをロックする
`products` を SHARE モードでロックしてから、自分のセッションが `products` に対して持っているロックのモードを `pg_locks` から出してください。

```sql answer
lock table products in share mode;
select mode from pg_locks
where relation = 'products'::regclass and pid = pg_backend_pid();
```

:::hint
`lock table テーブル in モード mode;`
:::

:::hint
`pg_locks` の `relation` はテーブルの OID です。`'products'::regclass` と比べます。
:::
:::

:::quiz UPDATE が取るロック
`customers` の `id = 1` の行を UPDATE（都道府県を同じ値で上書き）してから、自分のセッションが `customers`（テーブル本体）に対して持っているロックのモードを出してください。

```sql answer
update customers set prefecture = prefecture where id = 1;
select mode from pg_locks
where relation = 'customers'::regclass and pid = pg_backend_pid();
```

:::hint
インデックスにもロックがかかりますが、ここではテーブル本体（`'customers'::regclass`）だけを見ます。
:::
:::

:::quiz トランザクションの間だけの勧告的ロック
トランザクションが終わると自動で外れる勧告的ロックを、キー `100` で取ってください。そのあと `pg_locks` から勧告的ロックの `objid` と `mode` を出してください。

```sql answer
select pg_advisory_xact_lock(100);
select objid, mode from pg_locks where locktype = 'advisory';
```

:::hint
`pg_advisory_lock` はセッションが終わるまで残ります。トランザクションの間だけなら `pg_advisory_xact_lock` です。
:::
:::
