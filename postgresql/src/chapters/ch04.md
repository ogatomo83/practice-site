## 型はなぜ大事か {#why}

PostgreSQL のすべての値には**型**があります。型は次の 3 つを決めます。

1. **入れられる値の範囲**：`int` には 21 億を超える数は入らない
2. **使える演算**：日付から日付を引くと日数になる。文字列どうしは引けない
3. **ディスク上のサイズ**：`int` は 4 バイト、`bigint` は 8 バイト

`pg_typeof` で値の型を、`pg_column_size` でその値が何バイトになるかを調べられます。

```sql run
select pg_typeof(42)          as t1, pg_column_size(42)          as b1,
       pg_typeof(42.0)        as t2, pg_column_size(42.0)        as b2,
       pg_typeof('42')        as t3,
       pg_typeof(now())       as t4, pg_column_size(now())       as b4,
       pg_typeof(true)        as t5, pg_column_size(true)        as b5;
```

`'42'` の型が `unknown` になっているのは、クォートで囲んだ値は、使われる場所によって型が決まるからです。`'42'::int` と書けば整数に、`'2026-01-01'::date` と書けば日付になります。

## 数値 {#numeric}

| 型 | サイズ | 範囲・精度 | 使いどころ |
| --- | --- | --- | --- |
| `smallint`（`int2`） | 2 バイト | −32,768 〜 32,767 | 小さな数を大量に持つとき |
| `integer`（`int`, `int4`） | 4 バイト | 約 ±21 億 | 普通の整数 |
| `bigint`（`int8`） | 8 バイト | 約 ±922 京 | ID、大きな集計値 |
| `numeric(p, s)` | 可変 | 最大 1000 桁程度まで正確 | **お金**、正確さが必要な値 |
| `real`（`float4`） | 4 バイト | 約 6 桁の精度 | 測定値など、誤差を許せる値 |
| `double precision`（`float8`） | 8 バイト | 約 15 桁の精度 | 科学計算 |

### 整数のあふれ

範囲を超えるとエラーになります。PostgreSQL は黙って値を丸めたり、桁あふれして負の数にしたりしません。

```sql run error
select 2147483647::int + 1;
```

:::pgerr 22003 integer out of range
`22003` は「数値が範囲外」です。`int` の上限は 2,147,483,647 です。ID に `int` を使っていて、何年も運用するうちに 21 億を超えてしまう事故は実際に起きています。増え続ける ID には最初から `bigint` を使うのが安全です。
:::

### 浮動小数点の誤差

`real` と `double precision` は、2 進数で近似した値を持ちます。10 進数の 0.1 は 2 進数では割り切れないので、誤差が出ます。

```sql run
select 0.1::float8 + 0.2::float8         as float8,
       0.1::float8 + 0.2::float8 = 0.3   as "float8 で 0.3 と等しい？",
       0.1::numeric + 0.2::numeric       as numeric,
       0.1::numeric + 0.2::numeric = 0.3 as "numeric で 0.3 と等しい？";
```

`numeric` は 10 進数のまま正確に計算します。その代わり、`float8` より計算が遅くなります。**お金は必ず `numeric` か、円単位の整数で持つ**、と覚えておきましょう。文具店の価格は円単位の `int` で持っています。

`numeric(p, s)` の `p` は全体の桁数、`s` は小数点以下の桁数です。

```sql run
select 123.456::numeric(5, 2) as "numeric(5,2)",
       round(2.5)  as "round(2.5)",
       round(-2.5) as "round(-2.5)",
       7 / 2       as "整数どうしの割り算",
       7 / 2.0     as "片方が numeric",
       7 % 2       as "余り";
```

:::warn 整数どうしの割り算は切り捨て
`7 / 2` は `3` です。整数どうしの割り算の結果は整数になります。平均や割合を計算するときは、片方を `numeric` にするか、`::numeric` で変換してから割ります。
:::

## 文字列 {#text}

| 型 | 意味 |
| --- | --- |
| `text` | 長さ制限のない文字列。PostgreSQL ではこれが基本 |
| `varchar(n)` | 最大 n 文字の文字列。n を超えるとエラー |
| `char(n)` | ちょうど n 文字。足りない分は空白で埋める。ほぼ使わない |

PostgreSQL では、`text` と `varchar(n)` の内部の扱いは同じで、速さも変わりません。長さを制限したいときだけ `varchar(n)` か、`check (length(x) <= n)` 制約を使います。迷ったら `text` で構いません。

### よく使う文字列関数

```sql run
select name,
       length(name)                 as 文字数,
       octet_length(name)           as バイト数,
       left(name, 3)                as 先頭3文字,
       replace(name, 'ノート', 'NOTE') as 置換,
       position('ノート' in name)   as 位置
from products
where name like '%ノート%';
```

日本語は UTF-8 で 1 文字 3 バイトなので、文字数とバイト数が違います。

```sql run
select upper('postgres')                         as 大文字,
       initcap('hello world')                    as 先頭大文字,
       trim('  余白  ')                           as 前後の空白を除く,
       split_part('aoi@example.com', '@', 2)     as ドメイン,
       format('%s さんの注文は %s 件', '佐藤', 4) as 書式,
       concat('a', null, 'b')                    as concat,
       'a' || null || 'b'                        as "||";
```

最後の 2 列に注目してください。`||` は NULL が混じると全体が NULL になりますが、`concat` は NULL を無視します。

### 正規表現

PostgreSQL は POSIX 正規表現を標準で使えます。

```sql run
select email,
       email ~ '^[a-z]+@example\.com$' as 形式チェック,
       regexp_replace(email, '@.*', '@***') as 伏せ字,
       (regexp_match(email, '^([^@]+)@'))[1] as ユーザ名
from customers
limit 4;
```

## 真偽値 {#boolean}

`boolean` は `true`、`false`、そして NULL（UNKNOWN）の 3 つの値を取ります。サイズは 1 バイトです。

```sql run
select name, stock = 0 as 在庫切れ, price >= 10000 as 高級品
from products
order by id
limit 5;
```

比較の結果はそのまま boolean です。`where 在庫切れ = true` と書く必要はなく、`where stock = 0` で十分です。

## 日付と時刻 {#datetime}

日付と時刻の型は種類が多く、間違えやすいところです。

| 型 | 例 | 意味 |
| --- | --- | --- |
| `date` | `2026-04-01` | 日付だけ |
| `time` | `09:30:00` | 時刻だけ |
| `timestamp` | `2026-04-01 09:30:00` | 日付と時刻。**タイムゾーンの情報を持たない** |
| `timestamptz` | `2026-04-01 09:30:00+09` | 日付と時刻。**世界で 1 つの瞬間を表す** |
| `interval` | `3 days 04:00:00` | 期間 |

### timestamp と timestamptz

ここが一番大事です。`timestamptz`（timestamp with time zone）は名前に反して、タイムゾーンを保存しません。保存するのは **UTC での瞬間** です。表示するときに、接続の設定（`timezone`）に合わせて変換します。

```fig graph timestamptz は、入力を UTC の瞬間に変換して保存し、表示のときに接続のタイムゾーンへ戻す。timestamp は文字どおりの日時をそのまま保存する
{
  col: 220, row: 86,
  nodes: [
    { id: 'in', label: "'2026-04-01 09:30+09'", sub: '入力', x: 0, y: 0, kind: 'muted' },

    { id: 'jp', label: '09:30+09', sub: 'timezone = Asia/Tokyo で表示', x: 2, y: 0, kind: 'stack' },
    { id: 'ny', label: '20:30-04（前日）', sub: 'timezone = America/New_York', x: 2, y: 1, kind: 'stack' },
  ],
  edges: [

```

試してみましょう。このページの接続は `Asia/Tokyo` に設定してあります。

```sql run
select ordered_at from orders where id = 1;
```

```sql run
set timezone = 'America/New_York';
select ordered_at from orders where id = 1;
```

同じ行が、ニューヨーク時間で表示されました。保存されている瞬間は同じです。設定を戻しておきます。

```sql run
set timezone = 'Asia/Tokyo';
select ordered_at, ordered_at at time zone 'UTC' as "UTC での時刻" from orders where id = 1;
```

:::key 時刻は timestamptz で持つ
「何かが起きた瞬間」（注文日時、ログイン日時、更新日時）は、必ず `timestamptz` を使います。`timestamp` はタイムゾーンを知らないので、サーバのある場所や利用者の国が変わったときに意味がずれます。`timestamp` を使うのは「毎朝 9 時に開店」のように、場所によらない暦の上の日時だけです。
:::

### 日付の計算

```sql run
select current_date                           as 今日,
       current_date + 7                        as 一週間後,
       current_date - date '2026-01-01'        as 元日からの日数,
       now()                                   as 現在時刻,
       now() + interval '1 month 2 hours'      as 一か月と二時間後,
       age(date '2026-04-01', date '1990-12-25') as 年齢;
```

`date_trunc` は日時を指定の単位で切り捨て、`extract` は一部分を取り出します。月ごとの集計でよく使います。

```sql run
select ordered_at,
       date_trunc('month', ordered_at) as 月の初め,
       extract(year from ordered_at)   as 年,
       extract(dow from ordered_at)    as 曜日番号,
       to_char(ordered_at, 'YYYY年MM月DD日 HH24:MI') as 書式つき
from orders
where id <= 4;
```

`extract(dow ...)` は日曜日が 0、土曜日が 6 です。

`generate_series` を日付に使うと、連続した日付の表を作れます。集計で「注文のなかった日」も 0 として出したいときに役立ちます。

```sql run
select d::date as 日付, to_char(d, 'Dy') as 曜日
from generate_series(date '2026-04-01', date '2026-04-07', interval '1 day') as d;
```

## 配列 {#array}

PostgreSQL では、どの型でも配列にできます。`products.tags` は `text[]`（文字列の配列）です。

```sql run
select name, tags, cardinality(tags) as 個数, tags[1] as 最初
from products
where cardinality(tags) > 0;
```

配列の添え字は **1 から**始まります。配列を検索する演算子もあります。

```sql run
-- 'ギフト' タグを含む商品（どちらも同じ意味）
select name, tags from products where 'ギフト' = any(tags);
```

```sql run
-- 'ギフト' と '定番' の両方を含む（@> は「左が右を含む」）
select name, tags from products where tags @> array['ギフト', '定番'];
```

`unnest` は配列を行に展開し、`array_agg` は行を配列にまとめます。2 つは逆の操作です。

```sql run
select tag, count(*) as 商品数
from products, unnest(tags) as tag
group by tag
order by 商品数 desc;
```

:::warn 配列は便利だが、正規化を崩す
配列に入れた値には外部キーを張れず、「このタグを全商品から消す」ような操作も面倒です。タグのように独立して管理したい値は、第 11 章で学ぶように別のテーブルに分けるのが基本です。配列は、それ自体が 1 つの値として意味を持つもの（座標の組、小さな選択肢の集まり）に向いています。
:::

## JSON {#json}

PostgreSQL には `json` と `jsonb` の 2 つの JSON 型があります。

| 型 | 保存のしかた | 特徴 |
| --- | --- | --- |
| `json` | 入力の文字列をそのまま保存 | 空白やキーの順番も保たれる。読むたびに解析し直す |
| `jsonb` | 解析して、2 進数の形式で保存 | 検索が速い。索引を張れる。重複キーは最後の 1 つだけ残る |

ほとんどの場合は `jsonb` を使います。`products.attrs` は `jsonb` です。

```sql run
select name,
       attrs,
       attrs -> 'color'  as "-> は jsonb を返す",
       attrs ->> 'color' as "->> は text を返す"
from products
where attrs ? 'color';
```

`?` は「このキーを持っているか」、`@>` は「この JSON を含むか」を調べます。

```sql run
select name, attrs from products where attrs @> '{"size": "A5"}';
```

JSON の詳しい使い方と索引は、第 19 章で扱います。

## その他の便利な型 {#others}

### UUID

`uuid` は 128 ビット（16 バイト）の、世界中で重ならない ID です。

```sql run
select gen_random_uuid() as v4_ランダム, uuidv7() as v7_時刻順;
```

ID を主キーにするなら、作った順に並ぶ v7 のほうが索引の効率がよくなります（第 14 章）。

### 列挙型

決まった選択肢だけを取る値には、列挙型（enum）を作れます。

```sql run
create type mood as enum ('sad', 'ok', 'happy');
select 'happy'::mood > 'sad'::mood as 定義順で比べられる,
       enum_range(null::mood) as すべての値;
```

```sql run error
select 'angry'::mood;
```

:::pgerr 22P02 invalid input value for enum mood: "angry"
`22P02` は「入力の形式が正しくない」というエラーです。`'abc'::int` のような変換に失敗したときにも出ます。
:::

列挙型は値の追加はできますが、削除や並べ替えは簡単にできません。選択肢が変わりそうなら、`check` 制約か、選択肢を入れた別テーブル（外部キーで参照）を使います。文具店の `orders.status` は `check` 制約で実現しています。

### 範囲型

範囲型は「開始と終了」の組を 1 つの値として扱います。予約の重なりのチェックに強力です。

```sql run
select daterange('2026-04-01', '2026-04-10') as 範囲,
       daterange('2026-04-01', '2026-04-10') && daterange('2026-04-08', '2026-04-15') as 重なる,
       daterange('2026-04-01', '2026-04-10') @> date '2026-04-05' as 含む,
       upper(daterange('2026-04-01', '2026-04-10')) as 終わり;
```

`[2026-04-01,2026-04-10)` の `[` は「その値を含む」、`)` は「その値を含まない」という意味です。範囲は「開始を含み、終わりを含まない」形に正規化されます。第 5 章で、範囲型を使って「予約が重ならない」ことを制約で保証する方法を紹介します。

## 型の選び方 {#choose}

| 保存したいもの | 選ぶ型 | 避けたい型 |
| --- | --- | --- |
| 増え続ける ID | `bigint`（identity）、`uuid` | `int`（21 億で尽きる） |
| 金額 | `numeric(12, 2)`、円なら `bigint` | `real`、`double precision`、`money` |
| 名前や説明 | `text` | `char(n)` |
| 起きた瞬間 | `timestamptz` | `timestamp`、文字列 |
| 日付だけ | `date` | `timestamp` |
| はい / いいえ | `boolean` | `int` の 0 / 1、`'Y'` / `'N'` |
| 構造が決まっていない属性 | `jsonb` | `json`、`text` に JSON を入れる |
| 期間・予約 | `tstzrange`、`daterange` | 開始と終了の 2 列（重なりの制約が書きにくい） |

:::try 
`select pg_column_size(1::smallint), pg_column_size(1::int), pg_column_size(1::bigint), pg_column_size(1::numeric), pg_column_size(123456789.123::numeric);` を実行して、型ごとのサイズを比べてください。`numeric` は桁数によってサイズが変わります。
:::

```sql run title="練習用"
select pg_column_size(1::smallint) as smallint, pg_column_size(1::int) as int,
       pg_column_size(1::bigint) as bigint, pg_column_size(1::numeric) as numeric_1,
       pg_column_size(123456789.123::numeric) as numeric_長い;
```

:::key この章のまとめ
- 範囲を超えた整数はエラーになる。増え続ける ID は `bigint`
- お金は `numeric` か整数。`float` は誤差が出る。整数どうしの割り算は切り捨て
- 文字列は `text` が基本。`||` は NULL を伝染させ、`concat` は無視する
- 起きた瞬間は `timestamptz`。中身は UTC の瞬間で、表示時に変換される
- 配列・JSON・範囲型は強力だが、使う場所を選ぶ
:::

## 確認問題 {#quiz}

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

:::quiz 税込み価格（切り捨て）
商品の名前と、価格に 8% の消費税を足して**小数点以下を切り捨てた**値を出してください（180 円なら 194.4 → 194 円）。

```sql answer
select name, price * 108 / 100 as 税込 from products;
```

:::hint
整数どうしの割り算は切り捨てになります。`floor(price * 1.08)` でも同じ値になります。
:::
:::

:::quiz 登録した年
顧客の名前と、登録日（`joined_on`）の**年**を出してください。

```sql answer
select name, extract(year from joined_on) as 登録年 from customers;
```

:::hint
`extract(year from 日付)` か `date_part('year', 日付)` を使います。
:::
:::

:::quiz タグで探す
タグ（`tags`、`text[]` 型）に `ギフト` を含む商品の名前を出してください。

```sql answer
select name from products where 'ギフト' = any(tags);
```

:::hint
`値 = any(配列)` か、配列の包含 `tags @> array['ギフト']` を使います。
:::
:::

:::quiz JSON の中の値で探す
`attrs`（`jsonb` 型）の `color` が `黒` の商品の名前を出してください。

```sql answer
select name from products where attrs ->> 'color' = '黒';
```

:::hint
`->` は jsonb のまま、`->>` は text で取り出します。文字列と比べるなら `->>` です。
:::
:::
