## なぜ結合が必要か {#why}

文具店のデータは、顧客・注文・明細・商品と、別々のテーブルに分かれています。「誰が・いつ・何を・いくつ買ったか」を一覧にするには、4 つのテーブルをつなぎ直す必要があります。

データを分けて持つ理由は、第 11 章の正規化で詳しく説明します。一言でいえば、**同じ事実を 1 か所にだけ書くため**です。顧客の名前は `customers` にだけあるので、名前を変えるときは 1 行を直せば済みます。その代わり、読むときには結合が必要になります。

この章では、次の小さな 2 つのテーブルで結合の動きを確かめます。

```sql setup
create table l (id int, name text);
create table r (id int, color text);
insert into l values (1, 'A'), (2, 'B'), (3, 'C');
insert into r values (2, '赤'), (3, '青'), (3, '緑'), (4, '黄');
```

```sql run
select * from l;
```

```sql run
select * from r;
```

`l` と `r` は `id` でつながります。`id = 3` は `r` に 2 行あり、`id = 1` は `r` に、`id = 4` は `l` にありません。この「片方にしかない行」と「複数ある行」の扱いが、結合の種類を分けるポイントです。

## 直積 CROSS JOIN {#cross}

すべての結合の出発点は**直積**です。左の各行と、右のすべての行を組み合わせます。

```sql run
select * from l cross join r;
```

3 行 × 4 行 = 12 行になりました。直積は、組み合わせをすべて並べたものです。

```fig layout 直積。左の 3 行それぞれに、右の 4 行すべてが組み合わされる。結合はここから条件に合う組だけを残したもの
{
  unit: 28,
  rows: [
    { label: 'l.1 A', cells: [{ w: 3, kind: 'plain', t: '2 赤' }, { w: 3, kind: 'plain', t: '3 青' }, { w: 3, kind: 'plain', t: '3 緑' }, { w: 3, kind: 'plain', t: '4 黄' }] },
    { label: 'l.2 B', cells: [{ w: 3, kind: 'accent', t: '2 赤' }, { w: 3, kind: 'plain', t: '3 青' }, { w: 3, kind: 'plain', t: '3 緑' }, { w: 3, kind: 'plain', t: '4 黄' }], note: '← id が一致' },
    { label: 'l.3 C', cells: [{ w: 3, kind: 'plain', t: '2 赤' }, { w: 3, kind: 'accent', t: '3 青' }, { w: 3, kind: 'accent', t: '3 緑' }, { w: 3, kind: 'plain', t: '4 黄' }], note: '← id が一致（2 組）' },
  ],
}
```

直積そのものを使う場面は、「全店舗 × 全日付」のような組み合わせ表を作るときくらいです。しかし、結合を理解するには「直積を作って、条件で絞る」と考えるのが一番の近道です。

:::warn 結合条件の書き忘れ
`from a, b` とカンマで並べると直積になります。結合条件を `where` に書き忘れると、100 万行と 100 万行の表から 1 兆行の結果を作ろうとします。古い書き方のカンマ結合より、`join ... on` を使うほうが書き忘れに気づきやすくなります。
:::

## 内部結合 INNER JOIN {#inner}

**内部結合**は、直積のうち `on` の条件が真になる組だけを残します。

```sql run
select l.id, l.name, r.color
from l
join r on r.id = l.id;
```

`join` は `inner join` の省略形です。結果は 3 行で、上の図の色の付いたマスと一致します。

- `l.1` は相手がいないので、結果に出てこない
- `l.3` は相手が 2 行あるので、結果に 2 回出てくる
- `r.4` は相手がいないので、出てこない

「相手が複数いると行が増える」という性質は、集計のときに大事になります（第 8 章）。

### 文具店で試す

注文ごとに顧客の名前を出してみます。

```sql run
select o.id as 注文, o.ordered_at::date as 日付, c.name as 顧客
from orders o
join customers c on c.id = o.customer_id
order by o.id
limit 8;
```

`orders o` の `o` は**テーブルの別名**です。列名の前に別名を付けて、どのテーブルの列かをはっきりさせます。両方のテーブルにある列名（ここでは `id`）は、別名を付けないと曖昧だというエラーになります。

```sql run error
select id, name from orders o join customers c on c.id = o.customer_id;
```

:::pgerr 42702 column reference "id" is ambiguous
`42702` は「その列名がどのテーブルを指すか決められない」というエラーです。`o.id` か `c.id` と書けば解決します。
:::

### 3 つ以上の表をつなぐ

`join` は何個でも続けられます。注文の明細を、顧客名と商品名つきで出します。

```sql run
select o.id as 注文, c.name as 顧客, p.name as 商品, oi.quantity as 数, oi.quantity * oi.unit_price as 小計
from orders o
join customers   c  on c.id = o.customer_id
join order_items oi on oi.order_id = o.id
join products    p  on p.id = oi.product_id
where o.id <= 6
order by o.id, p.id;
```

### USING と NATURAL

結合する列の名前が両方のテーブルで同じなら、`using` で短く書けます。

```sql run
select * from l join r using (id);
```

`using` を使うと、`id` 列は結果に 1 つだけ出てきます。

`natural join` は、同じ名前の列すべてで自動的に結合します。便利そうですが、後からどちらかのテーブルに同じ名前の列（たとえば `created_at`）が増えると、結合の条件が勝手に変わってしまいます。**`natural join` は使わない**のが無難です。

## 外部結合 OUTER JOIN {#outer}

### LEFT JOIN

`left join` は、**左のテーブルの行をすべて残します**。

```sql run
select l.id, l.name, r.color
from l
left join r on r.id = l.id
order by l.id;
```

`l.1` には相手がいないので、`color` が NULL になりました。

### RIGHT JOIN と FULL JOIN

`right join` は右を全部残します。`a right join b` は `b left join a` と同じ意味なので、実際には `left join` に書き直して使うことがほとんどです。`full join` は両方を全部残します。

```sql run
select l.id as l_id, l.name, r.id as r_id, r.color
from l
full join r on r.id = l.id
order by coalesce(l.id, r.id);
```

### 文具店で：注文していない顧客も出す

「顧客ごとの注文数」を出したいとき、内部結合では注文のない顧客が消えてしまいます。

```sql run
select c.name, count(o.id) as 注文数
from customers c
left join orders o on o.customer_id = c.id
group by c.id, c.name
order by 注文数, c.id;
```

加藤さんは注文が 0 件ですが、`left join` なので結果に残っています。`count(o.id)` は NULL を数えないので、0 になります。`count(*)` にすると、NULL で埋めた 1 行を数えて 1 になってしまうので注意してください。

### ON と WHERE の違い

外部結合で一番の落とし穴がこれです。「キャンセル以外の注文の数」を、顧客ごとに出したいとします。

```sql run
-- 間違い：WHERE に書くと、注文のない顧客が消える
select c.name, count(o.id) as 注文数
from customers c
left join orders o on o.customer_id = c.id
where o.status <> 'cancelled'
group by c.id, c.name
order by c.id;
```

加藤さんが消えてしまいました。`where` は結合の**後**に評価されます。注文のない加藤さんの行は `o.status` が NULL なので、`NULL <> 'cancelled'` は UNKNOWN になり、`where` で捨てられたのです。

```sql run
-- 正しい：相手側の条件は ON に書く
select c.name, count(o.id) as 注文数
from customers c
left join orders o on o.customer_id = c.id and o.status <> 'cancelled'
group by c.id, c.name
order by c.id;
```

:::key 外部結合の条件の置き場所
- **ON** に書いた条件：「どの相手と組むか」を決める。左の行は条件にかかわらず残る
- **WHERE** に書いた条件：結合が終わった結果から行を捨てる
- 外部結合で、NULL で埋まる側（left join の右側）のテーブルの条件は、ON に書く
:::

## 半結合と反結合 {#semi-anti}

「注文したことのある顧客」のように、相手が**いるかどうか**だけを知りたいときがあります。内部結合で書くと、注文が 4 件ある顧客は 4 回出てきてしまいます。

```sql run
select c.name from customers c join orders o on o.customer_id = c.id where c.id = 1;
```

存在するかどうかだけを調べるには `exists` を使います。これを**半結合**（semi join）と呼びます。

```sql run
select c.name from customers c
where exists (select 1 from orders o where o.customer_id = c.id)
order by c.id;
```

逆に「相手が**いない**行」を探すのが**反結合**（anti join）です。書き方は 2 通りあります。

```sql run
-- 1. not exists
select p.name from products p
where not exists (select 1 from order_items oi where oi.product_id = p.id);
```

```sql run
-- 2. left join して、相手が NULL の行を残す
select p.name from products p
left join order_items oi on oi.product_id = p.id
where oi.product_id is null;
```

どちらも「一度も売れていない商品」で、結果は同じです。PostgreSQL はどちらも同じ「Anti Join」という実行方法に変換します。第 2 章で見たとおり、`not in` は NULL の落とし穴があるので避けます。

## 自己結合 {#self}

同じテーブルを 2 回使って結合することもできます。`employees` の `manager_id` は、同じ `employees` の `id` を指しています。従業員と上司の名前を並べてみます。

```sql run
select e.name as 従業員, e.dept as 部署, m.name as 上司
from employees e
left join employees m on m.id = e.manager_id
order by e.id;
```

同じテーブルに `e`（employee）と `m`（manager）という 2 つの別名を付けて、別のテーブルのように扱っています。店長には上司がいないので、`left join` で NULL になっています。

```fig tree employees の上司と部下の関係。自己結合で 1 段ずつたどれる。何段でもたどるには、第 9 章の再帰 CTE を使う
{
  root: { label: '燕 店長', kind: '本部', children: [
    { label: '石田 健', kind: '店舗', children: [ { label: '岡 拓海', kind: '店舗' }, { label: '原 美月', kind: '店舗' } ] },
    { label: '森 千尋', kind: '通販', children: [
      { label: '西 翔', kind: '通販', children: [ { label: '木村 涼', kind: '通販' } ] },
      { label: '松井 葉月', kind: '通販' },
    ] },
  ] },
}
```

:::try 
自己結合をもう 1 段増やして、「従業員・上司・上司の上司」を並べてください。`left join employees mm on mm.id = m.manager_id` を足します。
:::

```sql run title="練習用"
select e.name as 従業員, m.name as 上司
from employees e
left join employees m on m.id = e.manager_id
order by e.id;
```

## LATERAL {#lateral}

普通の結合では、右側のサブクエリから左側の列を参照できません。`lateral` を付けると、**左の各行ごとに右側のサブクエリを実行**できるようになります。「顧客ごとに、最新の注文 2 件」のような問い合わせが書けます。

```sql run
select c.name, recent.id as 注文, recent.ordered_at::date as 日付
from customers c
cross join lateral (
  select o.id, o.ordered_at
  from orders o
  where o.customer_id = c.id          -- 左の行の c.id を使っている
  order by o.ordered_at desc
  limit 2
) recent
order by c.id, recent.ordered_at desc;
```

`cross join lateral` は、右側が 0 行の顧客を消します。注文のない顧客も残したいなら、`left join lateral (...) on true` と書きます。


## 結合はどう実行されるか {#algorithms}

最後に、PostgreSQL が結合を実際にどう処理しているかを覗いておきます。方法は 3 つあり、プランナがデータの量や索引を見て選びます。詳しくは第 15 章で扱います。

| 方法 | やり方 | 得意な場面 |
| --- | --- | --- |
| **Nested Loop**（入れ子ループ） | 左の各行について、右から相手を探す | 左が少なく、右に索引がある |
| **Hash Join**（ハッシュ結合） | 右の全行でハッシュ表を作り、左の各行でそれを引く | 索引がなく、両方が大きい。等号の条件だけ |
| **Merge Join**（マージ結合） | 両方を結合キーで並べ、前から突き合わせる | 両方がすでに並んでいる（索引がある） |

```fig graph ハッシュ結合のイメージ。小さいほうの表からハッシュ表を作り、大きいほうの表を 1 回なめながら相手を探す
{
  col: 200, row: 80,
  nodes: [
    { id: 'r', label: 'customers（小）', x: 0, y: 0, kind: 'stack' },
    { id: 'h', label: 'ハッシュ表\nid → 行', x: 1, y: 0, kind: 'accent', mono: false },
    { id: 'l', label: 'orders（大）', x: 0, y: 1, kind: 'stack' },
    { id: 'o', label: '結合結果', x: 2, y: 1, kind: 'ext', mono: false },
  ],
  edges: [
    { from: 'r', to: 'h', label: '① 全部入れる' },
    { from: 'l', to: 'h', label: '② 1 行ずつ引く', style: 'accent' },
    { from: 'h', to: 'o', label: '③ 一致したら出力' },
  ],
}
```

実際に PostgreSQL がどれを選んだか、`explain` で見てみましょう。

```sql run
explain
select o.id, c.name
from orders o join customers c on c.id = o.customer_id;
```

`Hash Join` と書かれていれば、上の図の方法が選ばれています。`Hash` の下にある表がハッシュ表を作る側です。

:::key この章のまとめ
- 結合は「直積を作って、条件に合う組だけを残す」と考える。相手が複数いれば行は増える
- 内部結合は両方にある行だけ。`left join` は左を全部残し、相手がいなければ NULL で埋める
- 外部結合で、NULL で埋まる側の条件は ON に書く。WHERE に書くと内部結合と同じになってしまう
- 存在の有無だけなら `exists` / `not exists`（半結合・反結合）
- 自己結合で階層を 1 段たどれる。行ごとにサブクエリを動かすなら `lateral`
:::

## 確認問題 {#quiz}

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

:::quiz 注文と顧客名
すべての注文について、注文 ID と、注文した顧客の名前を出してください。

```sql answer
select o.id, c.name
from orders o
join customers c on c.id = o.customer_id;
```
:::

:::quiz 一度も注文されていない商品
一度も注文されたことのない（`order_items` に出てこない）商品の名前を出してください。

```sql answer
select p.name
from products p
where not exists (select 1 from order_items oi where oi.product_id = p.id);
```

:::hint
反結合です。`not exists (...)` か、`left join` して相手が `is null` の行を残します。
:::
:::

:::quiz 従業員と上司
従業員の名前と、その上司の名前を並べてください。上司のいない従業員も出し、その場合の上司の名前は NULL にします。

```sql answer
select e.name as 従業員, m.name as 上司
from employees e
left join employees m on m.id = e.manager_id;
```

:::hint
`employees` を 2 回、別名を付けて結合します（自己結合）。上司のいない人も残すので `left join` です。
:::
:::

:::quiz 全顧客と 2026 年の注文
**すべての顧客**について、顧客の名前と、その顧客の 2026 年の注文 ID（`ordered_at >= '2026-01-01'`）を出してください。2026 年に注文していない顧客は、注文 ID を NULL にして 1 行出します。

```sql answer
select c.name, o.id
from customers c
left join orders o on o.customer_id = c.id and o.ordered_at >= '2026-01-01';
```

:::hint
日付の条件を `where` に書くと、NULL で埋まった行まで消えて内部結合と同じになります。条件は `on` に書きます。
:::
:::
