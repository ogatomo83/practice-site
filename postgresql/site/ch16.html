第 16 章

WAL・リカバリ・レプリケーション

コミットした変更が電源断でも消えないのは、データより先にログを書く「先行書き込みログ（WAL）」のおかげです。pg_walinspect で自分の INSERT や UPDATE のログを読み、チェックポイント、全ページ書き込み、クラッシュリカバリ、レプリケーションへとつなげます。

16.1なぜログを先に書くのか

第 12 章で、UPDATE はまず共有バッファの中のページを書き換え、ディスクのファイルへは後でまとめて書き出す、と説明しました。では、書き出す前に電源が落ちたら、コミットしたはずの変更は消えてしまうのでしょうか。

コミットのたびに、変更したページをすべてディスクに書けば安全です。しかしそれでは遅すぎます。

  • 1 行の変更でも、8 KB のページを丸ごと書く必要がある
  • 変更したページはディスクのあちこちに散らばっていて、飛び飛びの書き込みになる
  • インデックスのページも一緒に書く必要がある

そこで PostgreSQL は、ページそのものではなく、「何をどう変えたか」という小さな記録を、1 本のログファイルに追記していきます。これが WAL（Write-Ahead Log、先行書き込みログ）です。

WAL の決まりはただ 1 つです。

要点先行書き込みのルール

データファイルのページを書き出す前に、そのページへの変更を記録した WAL を、必ず先にディスクに書いておく。

このルールさえ守れば、電源が落ちても、再起動時に WAL を頭から読み直して変更をやり直す（再生する）ことで、コミットした変更をすべて復元できます。WAL への書き込みはファイルの末尾への追記だけなので、ページを飛び飛びに書くよりずっと速く済みます。

16.2LSN：WAL の中の位置

WAL の中の位置は LSN（Log Sequence Number）で表します。WAL の先頭からのバイト数で、0/1757630 のように 16 進数 2 つで書きます。

SQL⌘↵
select pg_current_wal_lsn() as 今のLSN,
       pg_walfile_name(pg_current_wal_lsn()) as WALファイル名;

WAL は 16 MB ごとのファイル（セグメント）に分かれて、pg_wal ディレクトリに置かれます。ファイル名の 24 桁の数字は、タイムライン番号と、LSN の上位の桁から作られています。

1 つの文が、どれだけの WAL を書いたかを測ってみましょう。

SQL⌘↵
create table w (id int primary key, v text);
select pg_current_wal_lsn() as 開始;
SQL⌘↵
insert into w select g, md5(g::text) from generate_series(1, 10000) g;
select pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0')) as WALの総量,
       pg_size_pretty(pg_relation_size('w') + pg_relation_size('w_pkey')) as テーブルとインデックス;

第 12 章で見たページヘッダの lsn は、「このページを最後に変えた WAL の位置」でした。データファイルを書き出すとき、PostgreSQL はこの LSN までの WAL がディスクに書かれていることを確かめます。これが先行書き込みのルールの実装です。

SQL⌘↵
create extension if not exists pageinspect;
select lsn as ページ0を最後に変えたLSN from page_header(get_raw_page('w', 0));

16.3WAL の中身を読む

拡張機能 pg_walinspect を使うと、WAL のレコードを 1 つずつ読めます。小さな変更をして、それがどう記録されたかを見てみます。

SQL⌘↵
create extension if not exists pg_walinspect;
create table wal_demo (id int primary key, v text);
checkpoint;

あとで「どこからどこまでの WAL を読むか」を指定できるように、開始位置の LSN を表に保存してから、行を追加・更新・削除します。

SQL⌘↵
create table marks (name text primary key, lsn pg_lsn);
insert into marks values ('start', pg_current_wal_lsn());
insert into wal_demo values (1, 'あ');
update wal_demo set v = 'い' where id = 1;
delete from wal_demo where id = 1;
select start_lsn, resource_manager as rm, record_type, record_length as 長さ, fpi_length as ページ画像, xid, left(description, 50) as 説明
from pg_get_wal_records_info((select lsn from marks where name = 'start'), pg_current_wal_lsn())
where resource_manager in ('Heap', 'Btree', 'Transaction');
rm と record_type意味
Heap / INSERTテーブルのページに行を追加した。off は行ポインタの番号
Btree / INSERT_LEAFインデックスの葉ページに項目を追加した
Transaction / COMMITトランザクションをコミットした。これが WAL に書かれた瞬間がコミットの瞬間
Heap / HOT_UPDATEHOT 更新（第 12 章）。インデックスのレコードがない
Heap / DELETE行を削除した（xmax を設定した）

最初の 4 行は、開始位置を記録した marks への INSERT 自身の記録です。その後に、wal_demo への INSERT、UPDATE、DELETE が、それぞれ COMMIT と組になって並んでいます。文 1 つごとにトランザクションが分かれているからです。UPDATE は HOT 更新だったので、インデックスの WAL レコードがありません。HOT がインデックスの更新を省いていることが、WAL からも確かめられます。

レコードの種類ごとの集計も見られます。

SQL⌘↵
select "resource_manager/record_type" as 種類, count, record_size as レコード, fpi_size as ページ画像
from pg_get_wal_stats((select lsn from marks where name = 'start'), pg_current_wal_lsn())
where count > 0;

16.4チェックポイント

WAL を再生すればデータを復元できますが、何日分もの WAL を頭から再生していては、再起動に何時間もかかります。また、WAL のファイルも無限に溜まってしまいます。

そこで PostgreSQL は、定期的にチェックポイントを行います。

  1. その時点で共有バッファにある汚れた（dirty）ページを、すべてデータファイルに書き出す
  2. 「ここより前の WAL は、もう再生しなくてよい」という位置（REDO ポイント）を記録する
  3. REDO ポイントより古い WAL ファイルは、削除または再利用できるようになる

チェックポイントは次のどちらかで起きます。

設定既定値意味
checkpoint_timeout5 分前回から一定時間たった
max_wal_size1 GBWAL がこれだけ溜まった
SQL⌘↵
select name, setting, unit from pg_settings
where name in ('checkpoint_timeout', 'max_wal_size', 'checkpoint_completion_target', 'wal_level', 'synchronous_commit', 'full_page_writes');

チェックポイントで一気にページを書き出すと、ディスクが急に忙しくなり、ほかの問い合わせが遅くなります。checkpoint_completion_target（既定 0.9）は、次のチェックポイントまでの時間の 90% をかけて、ゆっくり書き出すための設定です。

16.5全ページ書き込み

ここに 1 つ落とし穴があります。PostgreSQL のページは 8 KB ですが、OS やディスクが一度に書ける単位は 4 KB や 512 バイトのことがあります。8 KB のページを書いている最中に電源が落ちると、前半だけ新しく、後半は古いという壊れたページ（torn page）ができる可能性があります。WAL のレコードは「行ポインタ 3 番を変えた」という差分なので、土台のページが壊れていては正しく再生できません。

そこで PostgreSQL は、チェックポイントの後で、あるページを初めて変更するとき、WAL にページの全体の画像（FPI、Full Page Image）を書きます。再生するときは、まずこの画像でページを丸ごと上書きしてから、続きの差分を当てます。

SQL⌘↵
insert into marks values ('fpi', pg_current_wal_lsn());
checkpoint;                                            -- チェックポイント
update w set v = 'x' where id = 1;                     -- チェックポイント後、初めての変更
update w set v = 'y' where id = 2;                     -- 同じページへの 2 回目の変更
select record_type, record_length as 長さ, fpi_length as ページ画像の長さ
from pg_get_wal_records_info((select lsn from marks where name = 'fpi'), pg_current_wal_lsn())
where resource_manager = 'Heap';

1 回目の UPDATE のレコードだけ、ページ画像（数 KB）が付いて大きくなっています。2 回目は同じページなので、差分だけです。チェックポイントの直後に WAL の量が急に増えるのは、このためです。チェックポイントの間隔を延ばすと FPI は減りますが、クラッシュ後の再生に時間がかかるようになります。

16.6クラッシュリカバリ

ここまでの仕組みをまとめると、クラッシュ後の再起動では次のことが起きます。

  • コミットの記録（Transaction / COMMIT）が WAL にあるトランザクションの変更は、再生されて残る
  • コミットの記録がないトランザクションの変更も再生されるが、コミットされていないので MVCC（第 13 章）によって誰からも見えない。ROLLBACK と同じ扱いになる

UNDO（取り消しのログ）を持たずに済むのは、MVCC が「見えない版」として処理してくれるからです。

16.7耐久性と速さの取引

コミットのたびに WAL を fsync するのは、安全ですが遅い処理です。PostgreSQL には、ここを調整する仕組みがあります。

方法効果失うもの
synchronous_commit = offWAL の fsync を待たずにコミット完了を返すクラッシュ時に、直近（最大でおよそ 0.6 秒分）のコミットが消える。データは壊れない
アンログテーブル create unlogged tableそのテーブルの WAL を書かない。書き込みが非常に速いクラッシュするとテーブルが空になる。レプリカに複製されない
fsync = offfsync をしないデータベース全体が壊れうる。本番では絶対に使わない

synchronous_commit はトランザクションごとに変えられます。ログやアクセス数の記録のように、多少失っても困らない書き込みだけを速くできます。

SQL⌘↵
create unlogged table access_log (at timestamptz default now(), path text);
insert into marks values ('unlogged', pg_current_wal_lsn());
insert into access_log (path) select '/page/' || g from generate_series(1, 10000) g;
select pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), (select lsn from marks where name = 'unlogged'))) as 書かれたWAL;

1 万行を入れても、WAL はほとんど増えていません。

16.8バックアップと PITR

WAL はクラッシュリカバリだけでなく、バックアップにも使えます。

  1. ある時点で、データディレクトリ全体のコピー（ベースバックアップ）を取る
  2. その後に作られた WAL のファイルを、すべて別の場所に保存し続ける（WAL アーカイブ）
  3. 復旧するときは、ベースバックアップを戻し、アーカイブした WAL を好きな時点まで再生する

これを PITR（Point-In-Time Recovery、時点を指定した復旧）と呼びます。「午後 3 時 12 分に誰かが大事なテーブルを DROP した」なら、3 時 11 分まで戻せます。

postgresql.conf（WAL アーカイブの設定例）ここでは実行できない例
wal_level = replicaarchive_mode = onarchive_command = 'cp %p /mnt/archive/%f'      # WAL ファイルを保存する命令
復旧時の設定例ここでは実行できない例
restore_command = 'cp /mnt/archive/%f %p'recovery_target_time = '2026-04-01 15:11:00+09'

バックアップの取り方の全体は、第 20 章で扱います。

16.9レプリケーション

WAL を再生すればデータを再現できるなら、WAL をリアルタイムで別のサーバに送り、そこで再生し続ければ、まったく同じデータベースがもう 1 つできます。これがストリーミングレプリケーション（物理レプリケーション）です。PostgreSQL 9.0 から標準機能になりました。

方式特徴
非同期（既定）プライマリは WAL を送るが、スタンバイの受信を待たずにコミットを返す。速いが、プライマリが壊れると直近の変更がスタンバイに届いていないことがある
同期 synchronous_standby_namesスタンバイが WAL を受け取った（書いた、再生した）ことを確かめてからコミットを返す。データは失われないが、ネットワークの往復の分だけコミットが遅くなる

プライマリが故障したら、スタンバイを昇格（promote）させて新しいプライマリにします。これがフェイルオーバーです。

論理レプリケーション

物理レプリケーションは、ページの変更をそのまま再現するので、データベース全体が丸ごと同じになり、バージョンも同じである必要があります。

PostgreSQL 10 から入った論理レプリケーションは、WAL を「この表にこの行が INSERT された」という論理的な変更に変換（論理デコーディング）して送ります。

  • 特定のテーブルだけを複製できる
  • 違うメジャーバージョンの間でも複製できる（バージョンアップに使える）
  • 受け取る側は、普通の読み書きできるデータベース
論理レプリケーションの例ここでは実行できない例
-- 送る側create publication shop_pub for table orders, order_items;-- 受け取る側create subscription shop_sub  connection 'host=primary dbname=shop user=repl'  publication shop_pub;

論理デコーディングの仕組みは、Debezium のような変更データキャプチャ（CDC）のツールが、PostgreSQL の変更を Kafka などに流すのにも使われています。

やってみよう
  1. w の全行を UPDATE する前と後の LSN の差を測り、1 行あたり何バイトの WAL が書かれたかを計算してください
  2. 同じことをアンログテーブルで試し、WAL の量を比べてください
練習用⌘↵
insert into marks values ('try', pg_current_wal_lsn());
update w set v = upper(v);
select pg_wal_lsn_diff(pg_current_wal_lsn(), (select lsn from marks where name = 'try')) as 書いたバイト数,
       round(pg_wal_lsn_diff(pg_current_wal_lsn(), (select lsn from marks where name = 'try')) / 10000.0) as 一行あたり;
要点この章のまとめ
  • データファイルより先に WAL を書く。コミットは WAL の fsync で確定する
  • WAL は追記だけなので速い。LSN は WAL の中の位置で、ページヘッダにも記録される
  • チェックポイントで汚れたページを書き出し、再生の起点（REDO ポイント）を進める
  • チェックポイント後の最初の変更では、壊れたページに備えてページ全体の画像（FPI）を書く
  • クラッシュリカバリは REDO ポイントから WAL を再生する。未コミットの変更は MVCC で見えなくなる
  • ベースバックアップ + WAL アーカイブで PITR。WAL を送り続ければレプリケーション

16.10確認問題

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

問 1

LSN の差

正解済み

LSN 0/3000060 と 0/3000000 の差が何バイトかを出してください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵出力の値で判定（行の順番と列名は問わない）
ヒント

pg_wal_lsn_diff(LSN, LSN) を使うか、pg_lsn 型どうしの引き算 '0/3000060'::pg_lsn - '0/3000000' でも求められます。

模範解答
select pg_wal_lsn_diff('0/3000060', '0/3000000') as バイト;
問 2

LSN が入る WAL ファイル

正解済み

LSN 0/16B3748 の WAL が書かれる WAL ファイルの名前を出してください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵出力の値で判定（行の順番と列名は問わない）
ヒント

pg_walfile_name(LSN) が、その位置を含むファイル名を返します。

模範解答
select pg_walfile_name('0/16B3748');
問 3

耐久性に関わる設定

正解済み

wal_level、synchronous_commit、full_page_writes の 3 つの設定の名前と値を出してください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵出力の値で判定（行の順番と列名は問わない）
模範解答
