第 5 章

テーブル定義と制約

CREATE TABLE でテーブルを作り、NOT NULL・主キー・一意・CHECK・外部キー・排他制約で「入ってはいけないデータ」を締め出します。ALTER TABLE での変更と、スキーマによる名前空間も扱います。

5.1CREATE TABLE

テーブルは create table で作ります。列の名前と型を、カンマで区切って並べます。

SQL⌘↵
create table memo (
  id    bigint,
  title text,
  body  text
);
insert into memo values (1, '買い物', '方眼ノートを 3 冊');
select * from memo;

このテーブルには何の制約もありません。そのため、次のような「おかしなデータ」もすんなり入ってしまいます。

SQL⌘↵
insert into memo values (1, null, null);   -- id が重複し、題名もない
insert into memo (body) values ('id のないメモ');
select * from memo;

データベースに守ってほしいルールを、制約（constraint）としてテーブルに書いておくと、ルールに反するデータは入る前に拒否されます。アプリケーションのコードでチェックするだけでは、別のプログラムや手作業の SQL からの書き込みを防げません。データベース自身に守らせるのが一番確実です。

作り直すために、いったんテーブルを消します。

SQL⌘↵
drop table memo;

5.2制約の種類

制約守るルール違反したときの SQLSTATE
not nullNULL を入れない23502
unique値が重複しない23505
primary keynot null かつ unique。テーブルに 1 つ23502 / 23505
check (条件)条件が偽にならない23514
references参照先に値が存在する（外部キー）23503
exclude指定した演算子で衝突する行がない23P01

制約をひととおり付けて、メモのテーブルを作り直します。

SQL⌘↵
create table memo (
  id         bigint generated always as identity primary key,
  title      text not null check (length(title) between 1 and 100),
  body       text not null default '',
  priority   int  not null default 3 check (priority between 1 and 5),
  author_id  int  references employees(id),
  created_at timestamptz not null default now()
);
insert into memo (title, author_id) values ('棚卸し', 4);
select * from memo;

id、body、priority、created_at は指定しなかったので、既定値（default）が入りました。ひとつずつ見ていきます。

NOT NULL

SQLエラーになる⌘↵
insert into memo (title) values (null);
ERRORnull value in column "title" of relation "memo" violates not-null constraint23502

どの列で違反したかがメッセージに入っています。DETAIL には、失敗した行の値が表示されます。

実務では、ほとんどの列に not null を付けるのがよい習慣です。NULL を許す列は、第 2 章で見た三値論理の落とし穴を持ち込みます。「本当に値がないことがある」列だけ NULL を許します。

CHECK

check には、行の値を使った任意の条件を書けます。条件が偽になると拒否されます。

SQLエラーになる⌘↵
insert into memo (title, priority) values ('至急', 9);
ERRORnew row for relation "memo" violates check constraint "memo_priority_check"23514

制約名は、名前を付けなければ テーブル_列_check の形で自動的に付けられます。constraint 名前 check (...) と書けば、自分で名前を付けられます。分かりやすい名前を付けておくと、エラーを見たときに原因がすぐ分かります。

check は条件が UNKNOWN（NULL を含む比較）のときは通します。偽のときだけ拒否するからです。check (price >= 0) は、price が NULL の行を拒否しません。NULL も拒否したいなら not null を併用します。

UNIQUE

SQL⌘↵
create table member (
  id    bigint generated always as identity primary key,
  email text unique
);
insert into member (email) values ('a@example.com');
SQLエラーになる⌘↵
insert into member (email) values ('a@example.com');
ERRORduplicate key value violates unique constraint "member_email_key"23505

unique 制約の裏では、PostgreSQL が自動的に B-tree 索引を作っています（第 14 章）。重複のチェックは、この索引を引いて行われます。

unique は NULL どうしを「別の値」として扱います。NULL は何度でも入ります。

SQL⌘↵
insert into member (email) values (null), (null);
select * from member;

NULL も 1 つしか許したくないときは、PostgreSQL 15 から使える nulls not distinct を付けます。

SQL⌘↵
create table coupon (
  code text unique nulls not distinct
);
insert into coupon values ('SPRING'), (null);
SQLエラーになる⌘↵
insert into coupon values (null);

主キーと ID の作り方

主キーは「行を見分ける代表のキー」でした（第 2 章）。自動で番号を振る方法は 2 つあります。

書き方説明
id bigint generated always as identitySQL 標準の書き方（識別列）。PostgreSQL 10 から。こちらを使う
id bigserialPostgreSQL 独自の古い書き方。裏でシーケンスを作り、既定値に設定する

generated always は、手で値を指定すると拒否します。generated by default なら、手での指定も受け付けます。

SQLエラーになる⌘↵
insert into memo (id, title) values (100, '手で番号を付ける');

どちらの方式でも、番号はシーケンスという専用のカウンタから取り出されます。シーケンスの番号は、トランザクションが取り消されても戻りません。そのため番号には欠けが出ます。主キーの連番に欠けがないことを期待してはいけません。

SQL⌘↵
select nextval(pg_get_serial_sequence('memo', 'id')) as 次の番号,
       currval(pg_get_serial_sequence('memo', 'id')) as 今の番号;

5.3外部キー

外部キーは、参照先に存在する値しか入れさせない制約でした。では、参照されている側の行を消したらどうなるでしょうか。

SQLエラーになる⌘↵
delete from customers where id = 1;
ERRORupdate or delete on table "customers" violates foreign key constraint "orders_customer_id_fkey" on table "orders"23503

佐藤さんには注文があるので、消すと注文が「存在しない顧客」を指すことになります。そのため削除が拒否されました。

この振る舞いは、外部キーを作るときに on delete で選べます。

指定参照先が消されたとき向いている例
no action（既定）/ restrict削除を拒否する顧客と注文（注文があるなら消させない）
cascade参照している行も一緒に消す注文と注文明細（注文を消したら明細も不要）
set null参照している列を NULL にする従業員と担当者（退職したら担当者なしに）
set default参照している列を既定値にする
SQL⌘↵
create table thread (id int primary key, title text not null);
create table post (
  id        int primary key,
  thread_id int not null references thread(id) on delete cascade,
  body      text not null
);
insert into thread values (1, '万年筆の話'), (2, 'ノートの話');
insert into post values (1, 1, 'インクは何色？'), (2, 1, '青黒です'), (3, 2, '方眼派');
delete from thread where id = 1;
select * from post;

スレッド 1 を消すと、その投稿 2 件も一緒に消えました。

注意cascade は慎重に

on delete cascade は便利ですが、1 行の削除が連鎖して大量の行を消すことがあります。「親がなければ子に意味がない」関係（注文と明細、記事とその添付）だけに使いましょう。

深掘り外部キー列に索引を張る

外部キーを作ると、参照先（主キー側）には必ず索引がありますが、参照元（外部キー列）には自動で索引が作られません。親の行を消すとき、PostgreSQL は「この親を参照している子がいないか」を子のテーブルで探します。子の外部キー列に索引がないと、毎回テーブル全体を読むことになり、削除がとても遅くなります。外部キー列には、ほとんどの場合索引を張っておきます。

5.4排他制約

unique は「同じ値が 2 つあってはいけない」制約でした。排他制約（exclude）はそれを一般化して、「指定した演算子で比べて衝突する行が 2 つあってはいけない」制約です。範囲型と組み合わせると、予約の重複を防げます。

SQL⌘↵
create table room_booking (
  id     int generated always as identity primary key,
  room   text not null,
  during tstzrange not null,
  exclude using gist (during with &&)
);
insert into room_booking (room, during) values
  ('会議室A', '[2026-04-01 10:00+09, 2026-04-01 11:00+09)');
SQLエラーになる⌘↵
-- 10:30〜11:30 は、10:00〜11:00 と重なる
insert into room_booking (room, during) values
  ('会議室A', '[2026-04-01 10:30+09, 2026-04-01 11:30+09)');
ERRORconflicting key value violates exclusion constraint "room_booking_during_excl"23P01

&& は「範囲が重なる」演算子です。新しい予約と重なる予約がすでにあるので、拒否されました。アプリケーションで「重なる予約がないか SELECT してから INSERT する」と書くと、2 人が同時に予約したときにすり抜けてしまいます。制約なら、同時に来ても必ず片方が拒否されます。

11:00 ちょうどから始まる予約は、範囲の終わり ) が「含まない」なので重なりません。

SQL⌘↵
insert into room_booking (room, during) values
  ('会議室A', '[2026-04-01 11:00+09, 2026-04-01 12:00+09)');
select room, during from room_booking order by lower(during);

この例は部屋を区別していないので、会議室 B の予約も会議室 A と衝突してしまいます。部屋ごとに判定するには exclude using gist (room with =, during with &&) と書き、= を GiST 索引で扱うための拡張機能 btree_gist を入れます。

5.5生成列

ほかの列から計算できる値は、生成列として定義できます。

SQL⌘↵
create table line (
  qty        int not null,
  unit_price int not null,
  amount     int generated always as (qty * unit_price)
);
insert into line (qty, unit_price) values (3, 450);
select * from line;

PostgreSQL 18 からは、生成列は既定で仮想列（virtual）になりました。値は保存されず、読むたびに計算されます。stored を付けると、書き込み時に計算してディスクに保存します。

5.6ALTER TABLE

作ったテーブルは alter table で変更できます。

SQL⌘↵
alter table memo add column due_on date;                      -- 列を足す
alter table memo rename column body to content;               -- 列名を変える
alter table memo alter column priority set default 2;         -- 既定値を変える
alter table memo add constraint memo_due_check check (due_on >= created_at::date);
select column_name, data_type, is_nullable, column_default
from information_schema.columns
where table_name = 'memo'
order by ordinal_position;

最後の SELECT は、テーブルの定義を SQL で調べる方法です。information_schema は SQL 標準で決まっている、データベースの「目次」です。psql では \d memo と打てば同じ情報が見られます。

既存のデータがある表への制約

制約を後から追加すると、PostgreSQL は既存の全行をチェックします。違反する行が 1 つでもあれば、追加は失敗します。

SQLエラーになる⌘↵
alter table products add constraint price_under_10000 check (price < 10000);

not valid を付けると、既存の行はチェックせず、これから入る行だけをチェックする制約として追加できます。大きなテーブルに制約を足すとき、全行のチェックで長時間ロックがかかるのを避けるのに使います。後で validate constraint を実行すると、既存の行もチェックされます。

SQL⌘↵
alter table products add constraint price_under_100000 check (price < 100000) not valid;
alter table products validate constraint price_under_100000;
注意本番のテーブルを変えるとき

alter table の多くは、テーブルに強いロック（第 17 章）をかけます。たとえば列の型を変えると、テーブル全体が書き直され、その間は読み書きが止まります。列の追加（既定値が定数のもの）や not valid での制約追加のように、すぐに終わる操作を選ぶのが、止められないシステムでの定石です。

5.7スキーマ

PostgreSQL のデータベースの中には、スキーマという名前空間があります。テーブルは必ずどれかのスキーマに属します。何も指定しないと public スキーマに作られます。

SQL⌘↵
create schema archive;
create table archive.orders (like public.orders including all);
insert into archive.orders select * from public.orders where ordered_at < '2025-04-01';
select count(*) as アーカイブ, (select count(*) from public.orders) as 現役 from archive.orders;

スキーマ名を省略したとき、どのスキーマから探すかは search_path という設定で決まります。

SQL⌘↵
show search_path;

"$user" は「ユーザ名と同じ名前のスキーマ」、その次が public です。順に探して、最初に見つかったテーブルが使われます。

5.8一時テーブルと削除

create temporary table で作ったテーブルは、接続を切ると自動的に消えます。途中の計算結果を置いておくのに便利です。

SQL⌘↵
create temporary table tokyo_customers as
  select * from customers where prefecture = '東京都';
select name from tokyo_customers;

テーブルを消すのは drop table です。ほかのオブジェクト（外部キーやビュー）から参照されていると、消すのを拒否されます。cascade を付けると、参照しているものも一緒に消します。

SQL⌘↵
drop table if exists post, thread;
drop table if exists line;

if exists を付けると、テーブルがなくてもエラーになりません。

やってみよう

本の貸し出しを記録するテーブルを設計してみましょう。条件は次のとおりです。

  • 貸し出しには ID、本の ISBN（13 桁の数字の文字列）、借りた人の ID（customers を参照）、貸出日、返却日（未返却なら NULL）がある
  • ISBN は必ず 13 桁の数字（check (isbn ~ '^\d{13}$')）
  • 返却日は貸出日より前にならない
  • 同じ本が同時に 2 人に貸し出されることはない（ヒント：daterange(貸出日, 返却日) と排他制約。ただし本ごとに判定するには btree_gist が必要）
練習用⌘↵
create table loan (
  id         bigint generated always as identity primary key,
  isbn       text not null check (isbn ~ '^\d{13}$'),
  member_id  int not null references customers(id),
  lent_on    date not null default current_date,
  returned_on date,
  check (returned_on is null or returned_on >= lent_on)
);
insert into loan (isbn, member_id) values ('9784000000001', 1);
select * from loan;
要点この章のまとめ
  • 制約はデータベースの入口に立つ門番。どの経路からの書き込みも止められる
  • ほとんどの列に not null。check は UNKNOWN を通す
  • ID は bigint generated always as identity。番号には欠けが出る
  • 外部キーの on delete で、親を消したときの振る舞いを選ぶ。外部キー列には索引を張る
  • 排他制約と範囲型で「重ならない」ことを保証できる
  • 大きな表への制約追加は not valid → validate constraint の 2 段階で

5.9確認問題

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

問 1

会員のテーブルを作る

正解済み

次の条件を満たすテーブル members を作ってください。

  • id：整数で主キー
  • email：文字列。必ず値があり、ほかの会員と重ならない
  • age：整数。0 以上
-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行後のテーブルの中身で判定
ヒント 1

not null、unique、check (条件) を列に付けます。

ヒント 2

答え合わせでは、作ったテーブルに 5 行を入れてみて、1 行目だけが入り、残りがそれぞれの制約で止められるかを確かめます。

模範解答
create table members (  id    int primary key,  email text not null unique,  age   int check (age >= 0));

答え合わせでは、実行したあとに次の SQL で中身を調べて比べています。

select try_sql($$insert into members (id, email, age) values (1, 'a@example.com', 20)$$) as 普通の行,       try_sql($$insert into members (id, email, age) values (2, 'a@example.com', 30)$$) as 同じメール,       try_sql($$insert into members (id, email, age) values (3, null, 30)$$) as メールなし,       try_sql($$insert into members (id, email, age) values (4, 'b@example.com', -1)$$) as 負の年齢,       try_sql($$insert into members (id, email, age) values (1, 'c@example.com', 40)$$) as 同じID;
問 2

消すと一緒に消える外部キー

正解済み

著者の表 authors（id, name）が用意されています。本の表 books を作ってください。

  • id：整数で主キー
  • title：文字列
  • author_id：authors の id を参照する。著者を削除したら、その著者の本も一緒に消える
-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行後のテーブルの中身で判定
ヒント

references 親テーブル (列) の後ろに on delete ... を付けます。一緒に消すのは cascade です。

模範解答
create table books (  id        int primary key,  title     text,  author_id int references authors (id) on delete cascade);

答え合わせでは、実行したあとに次の SQL で中身を調べて比べています。

select try_sql($$insert into books (id, title, author_id) values (1, 'こころ', 1)$$) as 本を追加,       try_sql($$insert into books (id, title, author_id) values (2, '幻の本', 99)$$) as いない著者,       try_sql($$delete from authors where id = 1$$) as 著者を削除,       try_sql($$select count(*) from books$$) as 残った本;

あとから列を足す

正解済み
