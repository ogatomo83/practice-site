第 13 章

トランザクションと MVCC

読む人と書く人が互いを待たずに済む、PostgreSQL の多版型同時実行制御（MVCC）。xmin・xmax とスナップショットで「どの版が見えるか」が決まる仕組み、4 つの分離レベル、VACUUM とトランザクション ID の周回までを追いかけます。

13.1ACID

第 6 章で、begin 〜 commit で複数の変更を「全部か、ゼロか」にできることを見ました。トランザクションが守るべき性質は、頭文字を取って ACID と呼ばれます。

性質意味PostgreSQL での実現
Atomicity（原子性）全部成功するか、全部なかったことになるコミット状態の記録（pg_xact）と MVCC
Consistency（一貫性）制約を破った状態にはならない制約（第 5 章）
Isolation（独立性）同時に動くトランザクションが互いに干渉しないMVCC とスナップショット（この章）、ロック（第 17 章）
Durability（永続性）コミットしたら、電源が落ちても消えないWAL（第 16 章）

この章では、主に A と I を支える MVCC を扱います。

13.2読む人と書く人の問題

銀行の口座の表があるとします。A さんが残高の合計を集計している最中に、B さんが口座 1 から口座 2 へ 1 万円を振り込みました。集計が口座 1 を読んだのが振り込みの前で、口座 2 を読んだのが振り込みの後だったら、合計は 1 万円多くなってしまいます。

古いデータベースは、これをロックで防ぎました。読んでいる行には書けず、書いている行は読めない。正しくはなりますが、長い集計が走っている間、書き込みが全部止まってしまいます。

PostgreSQL の答えは、第 12 章で見た「UPDATE は上書きせず、新しい版を足す」という仕組みです。行の古い版と新しい版が同時にページに存在するので、

  • 集計をしている A さんには、集計を始めた時点の版を見せる
  • 振り込みをしている B さんは、新しい版を作って書き込む

ことができます。読む人は書く人を待たず、書く人は読む人を待ちません。これが MVCC（Multi-Version Concurrency Control、多版型同時実行制御）です。

13.3トランザクション ID

MVCC の土台は、すべてのトランザクションに振られるトランザクション ID（XID）です。32 ビットの通し番号で、書き込みを行ったトランザクションに順に振られます。

SQL⌘↵
select txid_current() as 今のトランザクションID;

begin しないで実行した文は、それ自体が 1 つのトランザクションです。もう一度実行すると、番号が 1 つ進みます。

SQL⌘↵
select txid_current() as 次のトランザクションID;

第 12 章で見たように、タプルのヘッダには t_xmin（作った XID）と t_xmax（消した XID）が入っています。普通の SELECT でも、隠れた列 xmin と xmax として読めます。

SQL⌘↵
create table account (id int primary key, owner text, balance int not null);
insert into account values (1, '佐藤', 50000), (2, '鈴木', 30000);
select xmin, xmax, ctid, * from account;

2 行とも、同じ XID で作られています。1 つの INSERT 文（1 つのトランザクション）で入れたからです。

SQL⌘↵
begin;
select txid_current() as このトランザクション;
update account set balance = balance - 10000 where id = 1;
update account set balance = balance + 10000 where id = 2;
select xmin, xmax, ctid, * from account;

更新した 2 行の xmin が、このトランザクションの番号に変わり、ctid も新しい場所になっています。まだコミットしていないので、ほかの接続からは見えません。取り消してみます。

SQL⌘↵
rollback;
select xmin, xmax, ctid, * from account;

元の版（元の xmin、元の ctid）が見えています。ROLLBACK は何も書き戻していません。作りかけの新しい版は、ページの中に残ったままです。ただ「この XID は中止された」と記録されたので、誰からも見えなくなっただけです。PostgreSQL の ROLLBACK が一瞬で終わるのはこのためです。

13.4可視性のルール

ある行の版が、あるトランザクションから見えるかどうかは、xmin と xmax を使って次のように決まります。

ここで「自分より前」「まだコミットされていない」を判断するのに使うのが、スナップショットです。

スナップショット

スナップショットは、ある瞬間に「どのトランザクションが終わっていて、どれがまだ動いているか」を記録したものです。

SQL⌘↵
select pg_current_snapshot();

752:752: のような 3 つの部分からなる値が返ります。

部分意味
xminこれより小さい XID は、すべて終わっている（コミットか中止）
xmaxこれ以上の XID は、スナップショットを取った時点でまだ始まっていない
xipxmin と xmax の間で、まだ動いていた XID の一覧

スナップショットから見て、行の xmin が「終わっていて、かつコミットされた」XID なら、その版は作られています。xmax が同じ条件を満たせば、その版はもう消されています。

コミットされたか中止されたかは、pg_xact というディレクトリに、XID ごとに 2 ビットで記録されています（第 12 章のヒントビットは、この記録を毎回見に行かずに済ませるためのキャッシュです）。

SQL⌘↵
select pg_xact_status(pg_current_xact_id()) as 実行中の自分,
       pg_xact_status((pg_current_xact_id()::text::bigint - 1)::text::xid8) as "1つ前のXID";

13.52 つのトランザクションで見る

ここからは、2 つの接続が同時に動く場面を図で追います。ブラウザの PostgreSQL は接続が 1 つしかないので、サーバ版の psql を 2 つ開いて試したときの様子として読んでください。

A は同じトランザクションの中で同じ行を 2 回読んで、違う値（50000 と 40000）を得ました。これを反復不能読み取り（non-repeatable read）と呼びます。READ COMMITTED では、文ごとにスナップショットを取り直すので、これが起こります。

REPEATABLE READ の A が、B に更新された行をさらに更新しようとすると、PostgreSQL はエラーを返します。

ERRORcould not serialize access due to concurrent update40001

40001 は直列化の失敗です。「あなたが見ている版は、もう誰かに更新されている。このまま書くと B の変更を無視することになる」という意味です。アプリケーションは、このエラーを受け取ったらトランザクションを最初からやり直す必要があります。

1 つの接続でも、スナップショットが固定される様子は確かめられます。now() はトランザクションの開始時刻、clock_timestamp() は本当の現在時刻を返します。

SQL⌘↵
begin isolation level repeatable read;
select pg_current_snapshot() as スナップショット1, now() as 開始時刻, clock_timestamp() as 今;
select pg_sleep(0.5);
select pg_current_snapshot() as スナップショット2, now() as 開始時刻, clock_timestamp() as 今;
commit;

13.6分離レベル

SQL 標準は、同時実行で起こりうる問題（アノマリー）と、それを防ぐ 4 つの分離レベルを決めています。

アノマリー内容
ダーティリード他人の未コミットの変更が見える
反復不能読み取り同じ行を 2 回読むと、間に他人がコミットした変更で値が変わる
ファントム同じ条件で 2 回検索すると、他人が追加した行が増えている
直列化アノマリー並べて実行した結果が、どの順番で 1 つずつ実行した結果とも一致しない

PostgreSQL での実際の振る舞いは次のとおりです（○ = 起こらない）。

分離レベルダーティリード反復不能読み取りファントム直列化アノマリー
READ UNCOMMITTED○（PostgreSQL では READ COMMITTED と同じ）起こる起こる起こる
READ COMMITTED（既定）○起こる起こる起こる
REPEATABLE READ○○○（標準より強い）起こる
SERIALIZABLE○○○○

PostgreSQL は MVCC なので、未コミットの版を見せることがそもそもありません。そのため、どのレベルでもダーティリードは起きません。

書き込みスキュー

REPEATABLE READ でも防げないのが書き込みスキューです。病院の当直で「少なくとも 1 人は当直に残っていなければならない」というルールがあるとします。

SERIALIZABLE にすると、PostgreSQL は SSI（Serializable Snapshot Isolation、9.1 から）という方法で、トランザクションどうしの読み書きの依存関係を追跡します。危険な依存の輪ができると、片方を 40001 で失敗させます。ロックで待たせるのではなく、事後に検出して片方をやり直させる、楽観的な方式です。

要点分離レベルの選び方
  • 普段は既定の READ COMMITTED で十分。ただし「読んでから書く」処理は、select ... for update（第 17 章）や、条件付きの UPDATE（update ... where balance >= 10000）で守る
  • 集計やレポートなど、一貫した時点のデータを何度も読むなら REPEATABLE READ
  • 複雑なルールを確実に守りたいなら SERIALIZABLE。ただし 40001 での再試行をアプリケーションに組み込むこと

失われた更新

READ COMMITTED でよく起きる事故が失われた更新です。アプリケーションが「残高を読む → 計算する → 書き戻す」を別々の文で行うと、同時に動いた片方の更新が消えます。

危ない書き方ここでは実行できない例
-- A と B が同時に実行すると、片方の入金が消えるselect balance from account where id = 1;           -- 50000 を読む-- アプリで 50000 + 1000 = 51000 を計算update account set balance = 51000 where id = 1;    -- 計算結果で上書き
安全な書き方⌘↵
-- 計算をデータベースの中で行えば、UPDATE が行をロックして順番に処理される
update account set balance = balance + 1000 where id = 1
returning balance;

balance = balance + 1000 の形なら、2 つ目の UPDATE は 1 つ目のコミットを待ち、コミット後の最新の値に対して計算をやり直します（READ COMMITTED の再評価）。そのため更新は失われません。

13.7VACUUM

MVCC には代償があります。古い版の行（死んだタプル）がページに溜まっていくことです。誰からも見えなくなった古い版を片付けるのが VACUUM です。

実際に溜まっていく様子を見てみましょう。

SQL⌘↵
create table bloat (id int primary key, v int) with (autovacuum_enabled = off);
insert into bloat select g, 0 from generate_series(1, 10000) g;
select pg_size_pretty(pg_relation_size('bloat')) as 最初のサイズ;
SQL⌘↵
-- 全行を 5 回更新する
update bloat set v = v + 1;
update bloat set v = v + 1;
update bloat set v = v + 1;
update bloat set v = v + 1;
update bloat set v = v + 1;
select pg_stat_force_next_flush();
select pg_size_pretty(pg_relation_size('bloat')) as 更新後のサイズ,
       n_live_tup as 生きた行, n_dead_tup as 死んだ行
from pg_stat_user_tables where relname = 'bloat';

行は 1 万行のままなのに、ファイルが何倍にも膨らみました。各 UPDATE が新しい版を足したからです。これを膨張（bloat）と呼びます。

SQL⌘↵
vacuum (verbose) bloat;
select pg_stat_force_next_flush();
select pg_size_pretty(pg_relation_size('bloat')) as vacuum後のサイズ,
       n_live_tup as 生きた行, n_dead_tup as 死んだ行
from pg_stat_user_tables where relname = 'bloat';

死んだ行は 0 になりましたが、ファイルのサイズは（末尾の空きページを除いて）ほとんど縮みません。通常の VACUUM は、死んだタプルの場所を再利用できるようにするだけで、ファイルを小さくはしないからです。空いた場所は、次の INSERT や UPDATE で使われます。

ファイル自体を小さくしたいときは vacuum full を使います。テーブルを丸ごと新しいファイルに書き直すので、その間はテーブル全体がロックされ、読み書きできません。

SQL⌘↵
vacuum full bloat;
select pg_size_pretty(pg_relation_size('bloat')) as vacuum_full後のサイズ;
vacuumvacuum full
すること死んだタプルの場所を再利用可能にする。FSM と VM を更新するテーブルを新しいファイルに書き直す
ファイルサイズほぼ変わらない最小になる
ロック読み書きを止めない読み書きをすべて止める
使いどころ日常的に（autovacuum が自動でやる）膨張しきった表を一度だけ縮めるとき

autovacuum

本番の PostgreSQL では、autovacuum というバックグラウンドのプロセスが、死んだ行の数が一定を超えたテーブルに自動で VACUUM と ANALYZE（統計の更新、第 15 章）を実行します。既定では、テーブルの 20% + 50 行が死んだら VACUUM が走ります。

注意長いトランザクションは VACUUM を止める

VACUUM が回収できるのは、「どのトランザクションからも見えなくなった」古い版だけです。何時間も開きっぱなしのトランザクション（BEGIN したまま放置された接続など）があると、そのスナップショットから見える可能性のある古い版は、すべて回収できません。データベース全体の膨張の原因の多くは、こうした長いトランザクションです。pg_stat_activity で xact_start が古い接続を探して対処します。

13.8トランザクション ID の周回

XID は 32 ビットなので、約 42 億で一周して 0 に戻ります。PostgreSQL は XID を「円」の上で比べていて、ある XID から見て前方の約 21 億は「未来」、後方の約 21 億は「過去」とみなします。

何もしなければ、21 億トランザクション前に作られた行の xmin は、ある日突然「未来」のものと判定され、見えなくなってしまいます。これを防ぐのが凍結（freeze）です。VACUUM は十分に古い行に「凍結済み」の印を付け、どの XID よりも過去のものとして扱わせます。

SQL⌘↵
select relname, age(relfrozenxid) as 凍結されていないXIDの年齢
from pg_class
where relname in ('bloat', 'account', 'customers', 'orders');

age が autovacuum_freeze_max_age（既定 2 億）を超えると、autovacuum は止められていても強制的に凍結の VACUUM を始めます。それでも周回の危険が迫ると、PostgreSQL はデータを守るために新しい書き込みを拒否します。大規模なシステムの運用では、この「年齢」の監視が欠かせません。

SQL⌘↵
vacuum freeze account;
select relname, age(relfrozenxid) as 年齢 from pg_class where relname = 'account';
やってみよう
  1. bloat で、5 回の更新の代わりに delete from bloat where id % 2 = 0 をしてから vacuum し、pg_freespace で空き容量がどう記録されたかを見てください（第 12 章の pg_freespacemap を使います）
  2. トランザクションの中で行を INSERT し、xmin が txid_current() と同じになることを確かめてから rollback してください
練習用⌘↵
begin;
insert into account values (3, '高橋', 1000);
select txid_current() as 自分のXID, xmin, * from account where id = 3;
rollback;
要点この章のまとめ
  • ACID の A と I は MVCC が支える。UPDATE は新しい版を足し、ROLLBACK は何も書き戻さない
  • 行の可視性は xmin・xmax と、スナップショット（終わったトランザクションの一覧）で決まる
  • READ COMMITTED は文ごと、REPEATABLE READ はトランザクションごとにスナップショットを取る
  • REPEATABLE READ / SERIALIZABLE では、衝突すると 40001 になる。再試行を前提に作る
  • 「読んで計算して書き戻す」は失われた更新を招く。計算は UPDATE の中で行う
  • 死んだタプルは VACUUM が回収する。ファイルは縮まない。長いトランザクションは VACUUM を妨げる
  • XID は 32 ビットで周回する。VACUUM の凍結がそれを防ぐ

13.9確認問題

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

問 1

UPDATE で版はいくつになるか

正解済み

口座の表 acc に 2 行が入っています。id = 1 の残高を 1,000 増やしてから、0 ページ目にあるタプルの数（古い版も含む）を数えてください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵出力の値で判定（行の順番と列名は問わない）
ヒント

UPDATE は古い版を残したまま新しい版を足します。数えるのは heap_page_items(get_raw_page('acc', 0)) の行数です。

模範解答
update acc set balance = balance + 1000 where id = 1;select count(*) from heap_page_items(get_raw_page('acc', 0));
問 2

自分が作った行の xmin

正解済み

acc に (3, '高橋', 1000) を追加し、その行の xmin がいまのトランザクション ID（txid_current()）と等しいかどうかを真偽値で出してください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵出力の値で判定（行の順番と列名は問わない）
ヒント

xmin は xid 型、txid_current() は bigint です。xmin::text::bigint で揃えて比べます。

模範解答
insert into acc values (3, '高橋', 1000);select xmin::text::bigint = txid_current() as 自分が作った from acc where id = 3;
問 3

失われた更新を起こさない書き方

正解済み

acc の id = 1 の残高から 10,000 を引き、引いた後の残高を返してください。読んでから計算して書き戻すのではなく、1 つの文で行います。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵出力の値で判定（行の順番と列名は問わない）
ヒント

計算は UPDATE の中で balance = balance - 10000 と書きます。変更後の値は returning で受け取れます。

模範解答
update acc set balance = balance - 10000 where id = 1 returning balance;
