第 12 章

ストレージ：ページとタプル

テーブルの行は、ディスクの上で 8 KB の「ページ（ブロック）」に詰められています。ファイルの置き場所から、ページの内部構造、タプルのヘッダ、TOAST、空き領域マップ、共有バッファまで、pageinspect で実物を覗きながら学びます。

12.1テーブルはファイルである

ここからは、PostgreSQL の内部に入ります。最初の問いは「テーブルのデータは、どこにどんな形で保存されているのか」です。

答えは単純で、テーブルは普通のファイルです。PostgreSQL のデータディレクトリ（PGDATA と呼ばれる）の下に、テーブルごとのファイルがあります。

SQL⌘↵
select pg_relation_filepath('products') as ファイルの場所,
       pg_relation_size('products')     as バイト数,
       current_setting('block_size')    as ブロックサイズ;

base/5/16404 のようなパスが表示されます。base の下の数字はデータベースの OID（内部の番号）、その下の数字がテーブルのファイルの番号（relfilenode）です。

1 つのテーブルには、用途の違う複数のファイル（フォーク）があります。

フォークファイル名中身
main16404行のデータそのもの
fsm16404_fsm各ページの空き容量（Free Space Map）
vm16404_vm各ページの行が全部「見える」か（Visibility Map）

本体のファイルは 1 GB を超えると、16404.1、16404.2 と分割されます。

12.2ページ（ブロック）

テーブルのファイルは、8 KB（8,192 バイト）ごとの区画に分けて使われます。この区画をページまたはブロックと呼びます。PostgreSQL がディスクとメモリの間でデータをやりとりする単位は、常にこのページです。1 行だけ読みたくても、その行を含む 8 KB のページを丸ごと読みます。

ページの中身を見るために、拡張機能 pageinspect を入れ、小さなテーブルを作ります。

SQL⌘↵
create extension if not exists pageinspect;
create table t (id int, name text);
insert into t values (1, 'あ'), (2, 'いい'), (3, 'ううう');
select ctid, * from t;

ctid は、PostgreSQL がすべての行に持たせている行の物理的な住所です。(0,1) は「0 番のページの、1 番目の行ポインタ」という意味です。

まず、ページのヘッダを見てみます。

SQL⌘↵
select * from page_header(get_raw_page('t', 0));
列意味
lsnこのページを最後に変更した WAL の位置（第 16 章）
lower行ポインタの並びの終わり（空き領域の始まり）
upperタプルの並びの始まり（空き領域の終わり）
special特殊領域の始まり。テーブルでは使わないので 8192
pagesize8192

lower が 36、upper が 8080 になっているはずです。この 2 つの間が空き領域です。

行ポインタとタプル

ページの中の行を一覧にします。

SQL⌘↵
select lp, lp_off, lp_flags, lp_len, t_xmin, t_xmax, t_ctid, t_hoff
from heap_page_items(get_raw_page('t', 0));
列意味
lp行ポインタの番号。ctid の 2 つ目の数字
lp_offタプルがページの何バイト目から始まるか
lp_flags1 = 普通、2 = 転送（HOT）、3 = 死んでいて空き
lp_lenタプルのバイト数
t_xminこの行を作ったトランザクションの番号
t_xmaxこの行を消した（更新した）トランザクションの番号。0 なら生きている
t_ctidこの行の最新版の場所。更新されていなければ自分自身
t_hoffタプルヘッダの長さ（データの始まり）

lp_off が 8160、8120、8080 と、後ろから詰められていることが分かります。なぜ 2 方向から詰めるのでしょうか。行ポインタは数が増えるだけで大きさは一定（4 バイト）、タプルは大きさがまちまちです。両端から使えば、どちらがどれだけ増えるか分からなくても、空き領域を無駄なく使えます。

要点なぜ行ポインタを挟むのか

インデックス（第 14 章）は、行を ctid (ページ, 行ポインタ番号) で指します。もしインデックスがタプルのバイト位置を直接指していたら、ページの中でタプルを詰め直すたびに、インデックスを全部書き換える必要があります。行ポインタを 1 段挟んでおけば、タプルをページ内で動かしても、行ポインタの lp_off を直すだけで済みます。

12.3タプルの中身

1 つのタプルは、ヘッダとデータからなります。ヘッダは 23 バイトで、ここに MVCC（第 13 章）のための情報が入っています。

フィールドサイズ意味
t_xmin4 バイトこの版を作ったトランザクション ID
t_xmax4 バイトこの版を削除・更新したトランザクション ID
t_cid4 バイトトランザクションの中の何番目のコマンドで作られたか
t_ctid6 バイト自分または新しい版の場所
t_infomask22 バイト列の数と、HOT などのフラグ
t_infomask2 バイトNULL を含むか、xmin がコミット済みか、などのフラグ
t_hoff1 バイトヘッダの長さ

1 行あたり最低でも 23 バイトのヘッダと、4 バイトの行ポインタが付きます。int 1 列だけの表でも、1 行に約 30 バイト使います。

SQL⌘↵
select pg_column_size(t.*) as 行全体, pg_column_size(t.id) as id, pg_column_size(t.name) as name
from t;

フラグを読む

t_infomask のビットを、人間が読める形に変換する関数もあります。

SQL⌘↵
select lp, t_xmin, raw_flags
from heap_page_items(get_raw_page('t', 0)),
     lateral heap_tuple_infomask_flags(t_infomask, t_infomask2);

HEAP_XMIN_COMMITTED が付いていれば、「この行を作ったトランザクションはコミット済み」と一度確認され、記録されたことを意味します（ヒントビット）。付いていなければ、次に読む人がコミットログ（pg_xact）を調べ、その結果をここに書き込みます。

列の順番とパディング

CPU は、8 バイトの値を 8 の倍数の番地に置いたほうが速く読めます。そのため PostgreSQL は、型ごとに決まった境界に値を揃え、間に詰め物（パディング）を入れます。列の順番によって、行の大きさが変わります。

SQL⌘↵
create table pad_bad  (a boolean, b bigint, c boolean, d bigint, e boolean, f bigint);
create table pad_good (b bigint, d bigint, f bigint, a boolean, c boolean, e boolean);
insert into pad_bad  values (true, 1, true, 2, true, 3);
insert into pad_good values (1, 2, 3, true, true, true);
select (select pg_column_size(pad_bad.*)  from pad_bad)  as 悪い順番,
       (select pg_column_size(pad_good.*) from pad_good) as 良い順番;

boolean（1 バイト）の後ろに bigint（8 バイト境界）が来ると、7 バイトの詰め物が入ります。大きい型から順に並べると、詰め物が減ります。何億行もある表では、この差がディスクの使用量に効いてきます。

12.41 ページに何行入るか

10 万行の表を作って、ページの数を数えてみます。

SQL⌘↵
create table big as
select g as id, md5(g::text) as hash
from generate_series(1, 100000) g;
analyze big;
select relpages as ページ数,
       reltuples::bigint as 行数,
       round(reltuples / relpages) as "1 ページの行数",
       pg_size_pretty(pg_relation_size('big')) as サイズ
from pg_class where relname = 'big';

1 行は、ヘッダ 24 バイト（23 + 境界合わせ）、id 4 バイト、hash（32 文字）33 バイト、境界合わせ、そして行ポインタ 4 バイトで、およそ 70 バイトになります。8,192 バイトのページに 100 行あまり入る計算です。

SQL⌘↵
select ctid, id from big where id between 110 and 115 or id = 100000;

ctid を見ると、何行目でページが変わったかが分かります。

12.5UPDATE は上書きしない

PostgreSQL の大きな特徴が、ここで見えてきます。行を update すると、どうなるでしょうか。

SQL⌘↵
update t set name = 'あ（更新）' where id = 1;
select ctid, * from t;

id = 1 の行の ctid が (0,1) から (0,4) に変わりました。ページの中身を見てみます。

SQL⌘↵
select lp, lp_off, t_xmin, t_xmax, t_ctid
from heap_page_items(get_raw_page('t', 0));
  • 古い版（lp 1）は消えていません。t_xmax に、更新したトランザクションの番号が入っただけです
  • 古い版の t_ctid は (0,4)、つまり新しい版を指しています
  • 新しい版（lp 4）の t_xmin は、更新したトランザクションの番号です

delete も同じで、行を消さずに t_xmax を埋めるだけです。

SQL⌘↵
delete from t where id = 2;
select lp, t_xmin, t_xmax, t_ctid from heap_page_items(get_raw_page('t', 0));

なぜ上書きしないのか。それは、更新している最中にも、ほかのトランザクションが古い版を読めるようにするためです。この仕組みが MVCC で、次の第 13 章の主題です。

古い版はやがて誰からも見えなくなり、死んだタプル（dead tuple）になります。死んだタプルの場所は、VACUUM が回収して再利用できるようにします。

SQL⌘↵
vacuum t;
select lp, lp_off, lp_flags, t_xmin, t_xmax, t_ctid from heap_page_items(get_raw_page('t', 0));

lp 1 の lp_flags は 2（転送。次の節の HOT）、lp 2 は 0（未使用）に変わり、タプルの中身が消えました。行ポインタそのものは残っていて、新しい行が入るときに再利用されます。

もう 1 つ注目してほしいのが lp 3 の lp_off です。VACUUM の前は 8080 でしたが、空いた場所を詰めたため 8152 に動いています。それでも ctid (0,3) は変わりません。行ポインタを 1 段挟んでいるおかげです。

12.6HOT 更新

更新のたびに新しい版を作ると、インデックスも新しい版を指すように項目を追加しなければなりません。これは重い処理です。

そこで PostgreSQL 8.3 で HOT（Heap-Only Tuple）という最適化が入りました。次の 2 つの条件を満たす更新では、インデックスを触りません。

  1. インデックスが張られた列を変更していない
  2. 新しい版を、同じページに置ける空きがある

HOT 更新では、インデックスは古い版を指したままです。古い版から t_ctid をたどって新しい版にたどり着きます。

HOT 更新が使われた回数は、統計情報で確かめられます。

SQL⌘↵
create table hot_demo (id int primary key, counter int) with (fillfactor = 70);
insert into hot_demo select g, 0 from generate_series(1, 100) g;
update hot_demo set counter = counter + 1;   -- counter にはインデックスがない
select pg_stat_force_next_flush();           -- 統計をすぐに反映させる
select n_tup_upd as 更新, n_tup_hot_upd as うちHOT
from pg_stat_user_tables where relname = 'hot_demo';

with (fillfactor = 70) は「ページを 70% までしか埋めない」という設定です。残りの 30% を、同じページの中での更新（HOT）のために空けておきます。更新の多い表では、fillfactor を下げると HOT が効きやすくなります。

メモ統計の反映について

pg_stat_user_tables の数字は、各接続が溜めた統計をまとめて共有メモリに書き出したときに更新されるので、少し遅れて反映されます。ここでは pg_stat_force_next_flush() で、すぐに書き出させています。

12.7TOAST：大きな値の置き場所

1 行は 1 ページ（8 KB）に収まらなければなりません。では、何 MB もある文章や JSON はどうするのでしょうか。

PostgreSQL は、行がおよそ 2 KB を超えると TOAST（The Oversized-Attribute Storage Technique）という仕組みを使います。

  1. まず大きな値を圧縮する
  2. それでも大きければ、値を約 2 KB ごとの断片に切って、別の TOAST テーブルに保存する
  3. 元の行には、TOAST テーブルの場所を指す 18 バイトほどのポインタだけを残す
SQL⌘↵
create table doc (id int, body text);
insert into doc values
  (1, repeat('あ', 100)),             -- 小さい
  (2, repeat('あいうえお', 10000)),    -- 大きいが、繰り返しなのでよく縮む
  (3, (select string_agg(md5(g::text), '') from generate_series(1, 2000) g)); -- 大きく、縮みにくい
select id,
       octet_length(body)   as 本当のバイト数,
       pg_column_size(body) as 保存されたバイト数,
       pg_column_compression(body) as 圧縮方式
from doc;

2 番目は 150,000 バイトの文字列が、圧縮で 1,744 バイトほどになっています。3 番目はランダムな文字列なので縮まず、64,000 バイトのまま TOAST テーブルに追い出されています。

SQL⌘↵
select c.relname as テーブル, t.relname as "TOAST テーブル",
       pg_size_pretty(pg_relation_size(c.oid)) as 本体,
       pg_size_pretty(pg_relation_size(t.oid)) as TOAST
from pg_class c join pg_class t on t.oid = c.reltoastrelid
where c.relname = 'doc';

本体のテーブルは小さいまま、TOAST テーブルのほうが大きくなっています。大きな列を select しなければ、TOAST テーブルは読まれません。これが「select * を避けて、必要な列だけを読む」ことのもう 1 つの理由です。

12.8空き領域マップと可視性マップ

新しい行を入れるとき、PostgreSQL は空きのあるページを探す必要があります。全ページを調べていたら遅すぎるので、各ページの空き容量を記録した 空き領域マップ（FSM） を使います。

SQL⌘↵
create extension if not exists pg_freespacemap;
delete from big where id % 2 = 0;   -- 半分の行を消す
vacuum big;
select blkno as ページ, avail as 空きバイト
from pg_freespace('big')
limit 5;

VACUUM のあとで、各ページにおよそ半分の空きができたことが記録されています。次の INSERT は、ファイルの末尾を伸ばす前に、この空きを使います。

もう 1 つの 可視性マップ（VM） は、ページごとに 2 つのビットを持ちます。

ビット意味使い道
all-visibleこのページの行は、すべてのトランザクションから見えるVACUUM がこのページを飛ばせる。インデックスオンリースキャン（第 14 章）でヒープを読まずに済む
all-frozenこのページの行は、すべて凍結済み周回防止の VACUUM（第 13 章）が飛ばせる
SQL⌘↵
create extension if not exists pg_visibility;
select all_visible, all_frozen, count(*) as ページ数
from pg_visibility_map('big')
group by 1, 2;

12.9共有バッファ

ここまで「ページを読む」と言ってきましたが、PostgreSQL は毎回ディスクを読むわけではありません。読んだページは、共有バッファというメモリ上の置き場所にしばらく残ります。次に同じページが必要になったら、メモリから読みます。

explain (analyze, buffers) で、問い合わせが何ページをバッファから読み（hit）、何ページを外から読んだ（read）かが分かります。

SQL⌘↵
explain (analyze, buffers, costs off)
select count(*) from big;

Buffers: shared hit=... の数が、読んだページの数です。テーブルの全ページを読む Seq Scan（順次走査）では、ページ数とほぼ同じ数字になります。

共有バッファの中に、今どのテーブルのページが何枚あるかも覗けます。

SQL⌘↵
create extension if not exists pg_buffercache;
select c.relname, count(*) as バッファ内のページ数
from pg_buffercache b
join pg_class c on c.relfilenode = b.relfilenode
where c.relname in ('big', 'products', 'customers', 't', 'doc')
group by c.relname
order by 2 desc;
深掘り変更されたページはいつディスクに書かれるか

UPDATE でページを変更すると、共有バッファの中のページが書き換わり、「汚れた（dirty）」状態になります。この時点ではまだディスクのファイルは変わっていません。それでも電源が落ちてデータが消えないのは、変更内容を先に WAL（先行書き込みログ）に書いてからコミットを返しているからです。汚れたページは、バックグラウンドライタやチェックポイントがまとめてディスクに書き出します。この流れは第 16 章で詳しく扱います。

やってみよう
  1. t に新しい行を 3 行追加して、VACUUM で空いた行ポインタ（lp 1 や lp 2）が再利用されるかを heap_page_items で確かめてください
  2. create table wide (a char(2000)); に 10 行入れ、relpages がいくつになるか予想してから確かめてください（1 ページに何行入るでしょうか）
練習用⌘↵
insert into t values (4, 'え'), (5, 'おお'), (6, 'かかか');
select lp, lp_flags, t_xmin, t_xmax, t_ctid from heap_page_items(get_raw_page('t', 0));
要点この章のまとめ
  • テーブルは base/<DB の OID>/<番号> のファイル。本体のほかに FSM と VM のフォークがある
  • ファイルは 8 KB のページ（ブロック）単位で読み書きされる。ページは前から行ポインタ、後ろからタプルで埋まる
  • 行の住所は ctid = (ページ番号, 行ポインタ番号)。インデックスは ctid で行を指す
  • タプルには 23 バイトのヘッダがあり、xmin / xmax で「どのトランザクションが作り、消したか」を持つ
  • UPDATE は上書きせず新しい版を足す。古い版は VACUUM が回収する。条件を満たせば HOT でインデックス更新を省ける
  • 約 2 KB を超える値は TOAST で圧縮・別テーブルに追い出される
  • ページは共有バッファに読み込まれて使われる

12.10確認問題

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

問 1

更新した行の住所

正解済み

テーブル q に 3 行を入れたあと、id = 2 の行を UPDATE してあります。いま id = 2 の行の ctid を出してください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵出力の値で判定（行の順番と列名は問わない）
ヒント 1

ctid はどのテーブルにもあるシステム列です。select ctid, * from q で全体を見てから考えてもかまいません。

ヒント 2

UPDATE は行を上書きせず、新しい版をページの空きに足します。

模範解答
select ctid from q where id = 2;
問 2

古い版を探す

正解済み

同じテーブル q（3 行を入れ、id = 2 を UPDATE 済み）の 0 ページ目を heap_page_items で調べ、xmax が入っている（0 でない）タプルの行ポインタ番号 lp を出してください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵出力の値で判定（行の順番と列名は問わない）
ヒント

heap_page_items(get_raw_page('テーブル', ページ番号)) で、ページの中のタプルが 1 行ずつ出ます。xmax は t_xmax 列です。

模範解答
select lp from heap_page_items(get_raw_page('q', 0)) where t_xmax <> 0;
問 3

何ページになったか

正解済み

1,000 行のテーブル q2 が用意されています。q2 が何ページを使っているかを、ファイルのバイト数とブロックサイズから計算して出してください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
