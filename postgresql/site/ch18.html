第 18 章

ビュー・関数・トリガ

問い合わせに名前を付けるビューとマテリアライズドビュー、SQL と PL/pgSQL で書く関数とプロシージャ、データの変更に反応して動くトリガ。データベースの中にロジックを置くための道具と、その使いどころを学びます。

18.1ビュー

ビューは、SELECT 文に名前を付けて、テーブルのように使えるようにしたものです。

SQL⌘↵
create view order_summary as
select o.id as order_id,
       c.name as customer,
       o.ordered_at,
       o.status,
       sum(oi.quantity * oi.unit_price) as amount,
       count(*) as items
from orders o
join customers c on c.id = o.customer_id
join order_items oi on oi.order_id = o.id
group by o.id, c.name;

select * from order_summary where amount >= 10000 order by ordered_at;

ビューはデータを持ちません。ビューを使った問い合わせは、第 15 章のリライタで元の SELECT に展開されてから計画が立てられます。

SQL⌘↵
explain select * from order_summary where order_id = 6;

order_id = 6 の条件がビューの中まで押し込まれて、orders の主キーで 1 件を探していることが分かります。ビューを使っても、遅くなるわけではありません。

ビューの使い道は主に 3 つです。

  1. 複雑な問い合わせに名前を付ける：何度も書く結合や集計を 1 か所にまとめる
  2. 見せる列を絞る：給与の列を除いたビューだけを、一部の利用者に見せる（第 20 章の権限と組み合わせる）
  3. 表の構造を隠す：テーブルを分割しても、ビューで元の形に見せればアプリケーションを変えずに済む

更新できるビュー

1 つのテーブルから列と行を選んだだけの単純なビューは、INSERT・UPDATE・DELETE ができます。

SQL⌘↵
create view tokyo_customers as
select id, name, email, prefecture, joined_on
from customers where prefecture = '東京都'
with check option;

update tokyo_customers set name = '佐藤 あおい' where id = 1;
select id, name from customers where id = 1;

with check option を付けると、ビューの条件から外れる変更を拒否します。

SQLエラーになる⌘↵
update tokyo_customers set prefecture = '大阪府' where id = 1;
ERRORnew row violates check option for view "tokyo_customers"44000

44000 は WITH CHECK OPTION の違反です。東京都の顧客だけを見せるビューから、大阪府に変えることはできません。

18.2マテリアライズドビュー

普通のビューは、使うたびに元の SELECT を実行します。重い集計なら、毎回待たされます。マテリアライズドビューは、SELECT の結果を実際に保存しておくビューです。

SQL⌘↵
create materialized view monthly_sales as
select date_trunc('month', o.ordered_at)::date as month,
       sum(oi.quantity * oi.unit_price) as amount
from orders o join order_items oi on oi.order_id = o.id
where o.status <> 'cancelled'
group by 1;

create unique index on monthly_sales (month);
select * from monthly_sales order by month desc limit 3;

保存されているので、元のデータを変えても、マテリアライズドビューの中身は変わりません。

SQL⌘↵
insert into orders values (30, 1, '2026-02-10 10:00+09', 'paid');
insert into order_items values (30, 1, 2, 12000);
select * from monthly_sales where month = '2026-02-01';

refresh で作り直します。concurrently を付けると、作り直している間も古い中身を読めます（一意インデックスが必要です）。

SQL⌘↵
refresh materialized view concurrently monthly_sales;
select * from monthly_sales where month = '2026-02-01';
ビューマテリアライズドビュー
データ持たない持つ（テーブルと同じくページに保存）
鮮度常に最新refresh した時点
速さ元の問い合わせと同じ保存した結果を読むだけなので速い
インデックス張れない張れる

18.3関数

PostgreSQL では、自分で関数を作れます。最も簡単なのは、SQL で中身を書くSQL 関数です。

SQL⌘↵
create function tax_included(price int) returns int
language sql immutable
return round(price * 1.1);

select name, price, tax_included(price) as 税込 from products limit 4;

表を返す関数も作れます。

SQL⌘↵
create function orders_of(cust int)
returns table (order_id int, ordered_at timestamptz, amount bigint)
language sql stable
as $$
  select o.id, o.ordered_at, sum(oi.quantity * oi.unit_price)
  from orders o join order_items oi on oi.order_id = o.id
  where o.customer_id = cust
  group by o.id
  order by o.ordered_at
$$;

select * from orders_of(1);

$$ ... $$ はドル引用符で、関数の本体のような長い文字列を、中の ' をエスケープせずに書くための記法です。

揮発性

関数には、同じ引数で呼んだときに同じ結果を返すかどうかの区分（揮発性）を付けます。プランナはこれを見て最適化します。

区分意味例
immutable引数が同じなら、いつ呼んでも同じ結果lower()、tax_included()
stable1 つの文の中では同じ結果。テーブルを読んでよいnow()、orders_of()
volatile（既定）呼ぶたびに結果が変わりうる。副作用があってよいrandom()、nextval()

式インデックス（第 14 章）や生成列に使えるのは immutable な関数だけです。間違って immutable を付けると、インデックスと実際の値が食い違う原因になるので注意します。

18.4PL/pgSQL

条件分岐やループが必要なときは、PL/pgSQL という手続き型の言語で関数を書きます。

SQL⌘↵
create function stock_label(p_id int) returns text
language plpgsql stable
as $$
declare
  v_stock int;
  v_name  text;
begin
  select stock, name into v_stock, v_name from products where id = p_id;
  if not found then
    raise exception '商品 % は存在しません', p_id using errcode = 'no_data_found';
  end if;

  if v_stock = 0 then
    return v_name || '：在庫切れ';
  elsif v_stock < 10 then
    return v_name || '：残り ' || v_stock || ' 個';
  else
    return v_name || '：在庫あり';
  end if;
end;
$$;

select stock_label(id) from products where id in (1, 2, 8, 3);
SQLエラーになる⌘↵
select stock_label(999);
構文意味
declare変数を宣言する
select ... into 変数問い合わせの結果を変数に入れる
found直前の SQL が 1 行以上を処理したか
if ... elsif ... else ... end if条件分岐
for r in select ... loop ... end loop問い合わせの結果を 1 行ずつ処理する
raise notice / exceptionメッセージを出す / エラーにする
begin ... exception when ... then ... endエラーを捕まえる

raise notice のメッセージは、実行結果の上に表示されます。

SQL⌘↵
do $$
declare
  r record;
  total int := 0;
begin
  for r in select name, stock from products order by stock desc limit 3 loop
    raise notice '% は在庫 % 個', r.name, r.stock;
    total := total + r.stock;
  end loop;
  raise notice '上位 3 商品の在庫の合計は % 個', total;
end;
$$;

do は、名前のない関数をその場で 1 回だけ実行する文です。

18.5プロシージャ

関数は 1 つのトランザクションの中で動き、途中で commit できません。PostgreSQL 11 から入ったプロシージャは、call で呼び出し、中で commit や rollback ができます。大量のデータを少しずつ処理して、こまめにコミットしたいときに使います。

SQL⌘↵
create table archive_log (id int, archived_at timestamptz default now());

create procedure archive_in_batches(batch int)
language plpgsql
as $$
declare
  n int;
begin
  loop
    insert into archive_log (id)
    select id from orders
    where id not in (select id from archive_log) and status = 'shipped'
    order by id limit batch;
    get diagnostics n = row_count;
    exit when n = 0;
    raise notice '% 件をアーカイブ', n;
    commit;   -- ここまでを確定させる
  end loop;
end;
$$;

call archive_in_batches(5);
select count(*) from archive_log;

18.6トリガ

トリガは、テーブルへの INSERT・UPDATE・DELETE に反応して、自動で関数を実行する仕組みです。

種類動く回数できること
before ... for each row1 行ごとnew を書き換える。null を返すとその行の処理を取りやめる
after ... for each row1 行ごとold と new を見て、別の表に記録する
before / after ... for each statement1 文に 1 回文全体の前後の処理
instead of ... for each row1 行ごとビューへの変更を、元の表への変更に置き換える

更新日時を自動で記録する

最もよく使われるトリガが、updated_at 列を自動で更新するものです。

SQL⌘↵
alter table products add column updated_at timestamptz not null default now();

create function set_updated_at() returns trigger
language plpgsql
as $$
begin
  new.updated_at := now();   -- 書き込まれる行（new）を書き換える
  return new;
end;
$$;

create trigger products_updated_at
before update on products
for each row execute function set_updated_at();

select pg_sleep(1);
update products set price = price + 10 where id = 3;
select id, name, price, updated_at from products where id in (3, 4);

id 3 だけ、updated_at が 1 秒進んでいます。アプリケーションのどこから UPDATE しても、更新日時の付け忘れが起きません。

変更の履歴を残す

AFTER トリガで、変更前と変更後の行を JSON にして、履歴の表に記録します。

SQL⌘↵
create table audit_log (
  id        bigint generated always as identity primary key,
  table_name text not null,
  op        text not null,
  old_row   jsonb,
  new_row   jsonb,
  at        timestamptz not null default now()
);

create function audit() returns trigger
language plpgsql
as $$
begin
  insert into audit_log (table_name, op, old_row, new_row)
  values (tg_table_name, tg_op,
          case when tg_op <> 'INSERT' then to_jsonb(old) end,
          case when tg_op <> 'DELETE' then to_jsonb(new) end);
  return null;   -- AFTER トリガの戻り値は使われない
end;
$$;

create trigger customers_audit
after insert or update or delete on customers
for each row execute function audit();

update customers set prefecture = '神奈川県' where id = 1;
select op, old_row ->> 'prefecture' as 変更前, new_row ->> 'prefecture' as 変更後, at from audit_log;

tg_table_name、tg_op はトリガ関数の中で使える特別な変数で、どの表のどの操作で呼ばれたかが入っています。

業務ルールを守らせる

BEFORE トリガで、制約では書きにくいルールを守らせることもできます。「注文の明細を追加したら、商品の在庫を減らす。在庫が足りなければ拒否する」をやってみます。

SQL⌘↵
create function reserve_stock() returns trigger
language plpgsql
as $$
begin
  update products set stock = stock - new.quantity
  where id = new.product_id and stock >= new.quantity;
  if not found then
    raise exception '在庫が足りません（商品 %、必要数 %）', new.product_id, new.quantity
      using errcode = 'check_violation';
  end if;
  return new;
end;
$$;

create trigger order_items_reserve
before insert on order_items
for each row execute function reserve_stock();

insert into orders values (31, 2, now(), 'pending');
insert into order_items values (31, 10, 2, 3500);   -- ガラスペン 在庫 5 → 3
select id, name, stock from products where id = 10;
SQLエラーになる⌘↵
insert into order_items values (31, 2, 99, 12000);  -- 在庫 3 の万年筆を 99 本
注意トリガは見えないロジック

トリガは強力ですが、SQL を書いた人からは動いていることが見えません。「UPDATE したら、なぜか別の表も変わった」という混乱の元になります。

  • 更新日時、監査ログ、非正規化した値の同期など、機械的で例外のない処理に使う
  • 業務の判断（割引の計算、通知の送信）は、アプリケーションに置く
  • トリガの中でトリガを呼ぶ連鎖は避ける
やってみよう
  1. products の価格が変わったときだけ、price_history（product_id, old_price, new_price, changed_at）に記録するトリガを作ってください（ヒント：when (old.price is distinct from new.price) をトリガに付けると、価格が変わったときだけ動きます）
  2. order_summary ビューを使って、顧客ごとの合計金額を出してください
練習用⌘↵
create table price_history (product_id int, old_price int, new_price int, changed_at timestamptz default now());
create function log_price() returns trigger language plpgsql as $$
begin
  insert into price_history (product_id, old_price, new_price) values (new.id, old.price, new.price);
  return null;
end; $$;
create trigger products_price_log after update of price on products
for each row when (old.price is distinct from new.price) execute function log_price();
update products set price = price + 100 where id in (1, 2);
update products set stock = stock + 1 where id = 3;   -- 価格は変わらないので記録されない
select * from price_history;
要点この章のまとめ
  • ビューは SELECT に付けた名前。展開されてから計画されるので遅くならない。with check option で条件外の変更を防ぐ
  • マテリアライズドビューは結果を保存する。refresh ... concurrently で読みを止めずに更新
  • 関数は SQL か PL/pgSQL で書く。揮発性（immutable / stable / volatile）を正しく付ける
  • プロシージャは call で呼び、中で commit できる
  • トリガは変更に反応して動く。BEFORE で行を書き換え、AFTER で記録する。見えないロジックなので使いどころを絞る

18.7確認問題

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

問 1

顧客ごとの注文回数のビュー

正解済み

顧客の名前と注文回数（キャンセルも含む。注文のない顧客は 0）を返すビュー customer_order_counts を作ってください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行後のテーブルの中身で判定
ヒント

注文のない顧客も 0 で出すには left join して、count(*) ではなく count(o.id) で数えます。

模範解答
create view customer_order_counts asselect c.name, count(o.id) as ordersfrom customers cleft join orders o on o.customer_id = c.idgroup by c.id, c.name;

答え合わせでは、実行したあとに次の SQL で中身を調べて比べています。

select * from customer_order_counts;
問 2

税込み価格の関数

正解済み

整数の価格を受け取り、10% の消費税を足して四捨五入した整数を返す関数 with_tax(price int) を作ってください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行後のテーブルの中身で判定
ヒント 1

create function 名前(引数 型) returns 型 language sql immutable return 式;

ヒント 2

455 × 1.1 = 500.5 は 501 になります。整数の割り算（切り捨て）では 500 になってしまいます。

問 3

価格の変更を記録するトリガ

正解済み

price_history（product_id, old_price, new_price）が用意されています。products の価格が変わったときだけ、変更前と変更後の価格を price_history に記録するトリガを作ってください。価格以外の列だけが変わった UPDATE では記録しません。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行後のテーブルの中身で判定
ヒント 1

トリガ関数（returns trigger）を作ってから、create trigger ... after update on products for each row execute function ... で結び付けます。

ヒント 2

「価格が変わったときだけ」は、トリガに when (old.price is distinct from new.price) を付けるか、関数の中で if で調べます。

模範解答
