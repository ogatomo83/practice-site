インデックス

全ページを読む代わりに、目的の行の住所（ctid）を素早く引くための索引。B-tree の木の形を pageinspect で覗き、複合・式・部分・カバリングインデックス、GIN・GiST・BRIN の使い分け、インデックスの代償までを学びます。

14.1インデックスがないと

この章では、10 万人分の会員の表を使います。

準備この節で使うテーブルを作る SQL（実行ボタンを押すと自動で流れます）
create table members (  id         bigint primary key,  email      text not null,  pref       text not null,  age        int  not null,  status     text not null,  joined_at  timestamptz not null,  tags       text[] not null default '{}',  profile    jsonb not null default '{}');insert into membersselect g,       'user' || g || '@example.com',       (array['東京都','大阪府','愛知県','福岡県','北海道','京都府','神奈川県','埼玉県'])[1 + g % 8],       18 + (g * 7919) % 60,       case when g % 100 = 0 then 'banned' when g % 10 = 0 then 'pending' else 'active' end,       timestamptz '2020-01-01 00:00+09' + (g || ' minutes')::interval * 30,       case when g % 3 = 0 then array['coffee'] when g % 5 = 0 then array['pen', 'note'] else array['note'] end,       jsonb_build_object('plan', case when g % 4 = 0 then 'pro' else 'free' end, 'score', g % 1000)from generate_series(1, 100000) g;analyze members;

まだ主キー以外にインデックスがありません。メールアドレスで 1 人を探してみます。

SQL⌘↵
explain (analyze, buffers, costs off)
select * from members where email = 'user77777@example.com';

Seq Scan（順次走査）が選ばれ、Buffers: shared hit=... の数字が千を超えています。たった 1 行を探すのに、テーブルの全ページ（第 12 章）を読んだということです。Rows Removed by Filter には、読んで捨てた行の数が出ています。

本の巻末の索引と同じように、「この値の行はこのページにある」という対応表を作っておけば、全ページを読まずに済みます。それがインデックスです。

SQL⌘↵
create index members_email_idx on members (email);
explain (analyze, buffers, costs off)
select * from members where email = 'user77777@example.com';

Index Scan に変わり、読んだページ数が数ページに減りました。

14.2B-tree の形

create index で何も指定しないと、B-tree インデックスが作られます。B-tree は、値を並べた状態で保持する、背の低い木です。

  • インデックスもテーブルと同じく、8 KB のページの集まりです
  • 葉ページには、インデックスにした値と、その行の ctid（第 12 章の行の住所）が、値の順に並んでいます
  • 内部ページと根ページは、「この範囲の値なら、この子ページを見よ」という道しるべです
  • 葉ページどうしは左右にリンクされていて、範囲検索（between や order by）では葉を横にたどります

1 ページに数百の項目が入るので、木はとても背が低くなります。この 10 万件のメールアドレスで 3 段、数億行でも 4〜5 段ほどです。どの値を探すときも、たどるページ数はこの段数だけです。

実物を覗いてみましょう。

SQL⌘↵
create extension if not exists pageinspect;
select root as 根のページ, level as 根の高さ, fastroot
from bt_metap('members_email_idx');

level は根の高さで、2 なら「根 → 内部ページ → 葉」の 3 段の木です。根ページの中身を見ます。

SQL⌘↵
select itemoffset, ctid as 子ページ, data
from bt_page_items('members_email_idx', (select root from bt_metap('members_email_idx')))
limit 6;

根ページの ctid の 1 つ目の数字が、子ページの番号です。data は区切りの値を 16 進数で表したものです。葉ページの 1 つを見ると、値と、テーブルの行の ctid が並んでいます。

SQL⌘↵
select itemoffset, ctid as テーブルの行, data
from bt_page_items('members_email_idx', 1)
limit 5;

インデックスが使われる条件

B-tree は値の大小関係で並んでいるので、次の演算子で使えます。

使える例
=、<、<=、>、>=、between、inage between 20 and 29
is null、is not null
like 'abc%'（前方一致、C ロケールまたは text_pattern_ops）
order by（インデックスの順に読めば並べ替えが要らない）order by joined_at desc limit 10

逆に、使えないのは次のような場合です。

SQL⌘↵
-- 列に関数をかけると、インデックスの値と比べられない
explain (costs off)
select * from members where lower(email) = 'user77777@example.com';

インデックスには email の値がそのまま並んでいます。lower(email) の値の順には並んでいないので、使えません。この問題は、後で出てくる式インデックスで解決します。

14.3スキャンの種類

インデックスを使った読み方には 3 種類あります。

スキャン動き向いている場面
Index Scanインデックスで 1 件見つけるたびに、テーブルのページを読みに行くヒットする行が少ない
Bitmap Heap Scanまずインデックスで該当する ctid を全部集めてページ順に並べ、テーブルのページを 1 回ずつ読むヒットする行がそこそこ多い
Index Only Scanインデックスの値だけで答え、テーブルを読まない必要な列がすべてインデックスにある
SQL⌘↵
create index members_age_idx on members (age);
explain (costs off) select * from members where age = 30;

年齢 30 歳は約 1,700 行あります。1 行ずつテーブルに読みに行くと、同じページを何度も読むことになるので、PostgreSQL は Bitmap を選びました。

選択率

ヒットする行が多すぎると、インデックスは使われなくなります。

SQL⌘↵
explain (costs off) select * from members where age > 20;

20 歳より上は、ほぼ全員です。インデックスをたどってから行を 1 件ずつ読むより、全ページを前から順に読むほうが速いので、Seq Scan が選ばれます。条件に合う行の割合を選択率と呼び、プランナは統計情報（第 15 章）から選択率を見積もって、スキャン方法を決めています。

要点インデックスがあれば速くなるとは限らない

インデックスが効くのは、全体のごく一部（目安として数 % 以下）を取り出すときです。ディスクを順番に読むのは、あちこちを飛び飛びに読むよりずっと速いので、多くの行を読むなら Seq Scan のほうが速くなります。

Index Only Scan と可視性マップ

必要な列がすべてインデックスに入っていれば、テーブルを読まずに答えられます。

SQL⌘↵
vacuum members;
explain (analyze, buffers, costs off)
select age, count(*) from members where age between 30 and 32 group by age;

Index Only Scan と Heap Fetches: 0 が出ています。ただし、インデックスには行の可視性の情報（xmin・xmax）がありません。そのため PostgreSQL は、第 12 章の可視性マップを見て、「このページの行は全員から見える」と分かっているページについてだけ、テーブルを読むのを省きます。VACUUM の直後なので、全ページが all-visible になっていて、Heap Fetches が 0 になりました。

14.4複合インデックス

複数の列をまとめたインデックスも作れます。列の順番が大事です。

SQL⌘↵
create index members_pref_age_idx on members (pref, age);
explain (costs off) select * from members where pref = '京都府' and age = 25;

(pref, age) のインデックスは、電話帳のように「まず pref で並べ、同じ pref の中で age で並べた」形をしています。

  • where pref = '京都府' and age = 25 → 1 か所にまとまっているので速い
  • where pref = '京都府' → 先頭の列だけでも使える
  • where age = 25 → 各 pref の中に散らばっている。従来は使えなかった

PostgreSQL 18 では、先頭の列の種類が少ないときに、先頭の列の値ごとに飛び飛びに探すスキップスキャンができるようになりました。

SQL⌘↵
drop index members_age_idx;
explain (analyze, costs off) select * from members where age = 25;

先頭の列ではない age だけの条件なのに、members_pref_age_idx が使われています。Index Searches が 1 より大きいのは、pref の値ごとに、age = 25 の位置を探しに行ったからです（これがスキップスキャンです）。それでも、先頭に age を置いたインデックスほど効率はよくありません。等号で絞る列を先に、範囲で絞る列を後に並べるのが、複合インデックスの基本です。

14.5いろいろなインデックス

式インデックス

列に関数をかけた値でインデックスを作れます。

SQL⌘↵
create index members_lower_email_idx on members (lower(email));
explain (costs off) select * from members where lower(email) = 'user77777@example.com';

問い合わせの式と、インデックスの式がまったく同じであることが条件です。

部分インデックス

where を付けると、条件に合う行だけのインデックスになります。全体の一部だけを頻繁に探すなら、インデックスが小さく済みます。

SQL⌘↵
create index members_pending_idx on members (joined_at) where status = 'pending';
select pg_size_pretty(pg_relation_size('members_pending_idx')) as 部分インデックス,
       pg_size_pretty(pg_relation_size('members_email_idx'))   as 全体のインデックス;
SQL⌘↵
explain (costs off)
select id, joined_at from members where status = 'pending' order by joined_at limit 10;

部分インデックスは、論理削除の表で「生きている行の中だけで一意」にしたいときにも使えます。

SQLここでは実行できない例
create unique index users_email_alive on users (email) where deleted_at is null;

カバリングインデックス

include で、検索には使わないが結果に必要な列をインデックスに含めておくと、Index Only Scan にできます。

SQL⌘↵
create index members_joined_cover on members (joined_at) include (email);
vacuum members;
explain (costs off)
select joined_at, email from members where joined_at >= '2025-01-01' order by joined_at limit 5;

14.6B-tree 以外のインデックス

PostgreSQL のインデックスの種類（アクセスメソッド）は、第 1 章で紹介した「型や索引を追加できる」設計のおかげで、たくさんあります。

種類仕組み向いているもの演算子の例
B-tree値を並べた木ほとんどの場合= < > between
Hash値のハッシュ等号だけで探す長い値=
GIN値を要素に分解した転置索引配列、jsonb、全文検索@> ? @@
GiST範囲を囲む箱の木範囲型、図形、近傍検索&& @> <->
SP-GiST空間を重ならずに分割する木電話番号、IP アドレス、点
BRINブロックの範囲ごとの最小値と最大値時系列のような、物理的に並んだ巨大な表< >

GIN：配列と JSON

GIN（Generalized Inverted Index）は、配列や JSON を要素に分解し、「この要素はどの行に含まれるか」を記録します。本の巻末の索引に最も近い形です。

SQL⌘↵
create index members_tags_gin on members using gin (tags);
explain (costs off) select count(*) from members where tags @> array['pen'];
SQL⌘↵
create index members_profile_gin on members using gin (profile);
explain (costs off) select count(*) from members where profile @> '{"plan": "pro"}';

BRIN：巨大な時系列

BRIN（Block Range Index）は、テーブルの 128 ページごとに「この範囲の最小値と最大値」だけを記録します。行がその列の順に物理的に並んでいる（ログのように追記していく）表なら、極めて小さいインデックスで範囲を絞り込めます。

SQL⌘↵
create index members_joined_brin on members using brin (joined_at);
select pg_size_pretty(pg_relation_size('members_joined_brin')) as brin,
       pg_size_pretty(pg_relation_size('members_joined_cover')) as btree;

B-tree が数 MB あるのに対して、BRIN は数十 KB です。

14.7インデックスの代償

インデックスはタダではありません。

  1. 書き込みが遅くなる：INSERT のたびに、すべてのインデックスに項目を追加する。UPDATE で HOT が使えないとき（第 12 章）も同じ
  2. ディスクとメモリを使う：インデックスも共有バッファに載る
  3. プランナの選択肢が増える：計画を立てる時間が少し延びる
SQL⌘↵
select pg_stat_force_next_flush();
select indexrelname as インデックス,
       pg_size_pretty(pg_relation_size(indexrelid)) as サイズ,
       idx_scan as 使われた回数
from pg_stat_user_indexes
where relname = 'members'
order by pg_relation_size(indexrelid) desc;

本番のデータベースで idx_scan が長い間 0 のままのインデックスは、使われていないので削除の候補になります（ただし一意制約のためのインデックスは、検索に使われなくても必要です）。

UUID とインデックス

主キーに UUID を使うとき、バージョンによってインデックスの振る舞いが大きく変わります。

UUID v4（ランダム）UUID v7（時刻順）
新しい値の入る場所B-tree の葉のあちこち常に右端の葉
ページ分割あちこちで起き、ページが半分ずつ空く右端でだけ起きる
キャッシュ全部の葉ページが頻繁に触られる右端の数ページだけが触られる

連番や UUID v7 のように増えていく値は、B-tree にとって最も扱いやすい値です。第 1 章で紹介した 18 の uuidv7() は、この問題を解決するために入りました。

注意本番でインデックスを作るとき

create index は、作っている間テーブルへの書き込みを止めます（読み込みは止めません）。大きなテーブルでは何十分もかかることがあるので、本番では create index concurrently を使います。時間は 2 倍ほどかかりますが、書き込みを止めません。途中で失敗すると「無効な（INVALID）インデックス」が残るので、確認して作り直します。

やってみよう
  1. members で、pref = '東京都' and status = 'pending' の行を探す問い合わせを explain で見て、どのインデックスが使われるか確かめてください
  2. その問い合わせに最適なインデックスを考えて作り、計画がどう変わるか見てください
練習用⌘↵
explain (analyze, costs off)
select id, email from members where pref = '東京都' and status = 'pending';
要点この章のまとめ
  • インデックスは「値 → ctid」の対応表。B-tree は値を並べた背の低い木で、葉は左右にリンクされている
  • 列に関数をかけるとインデックスは使えない。式インデックスで解決する
  • ヒットが少なければ Index Scan、そこそこなら Bitmap Heap Scan、多ければ Seq Scan
  • Index Only Scan は可視性マップに助けられている。VACUUM が大事
  • 複合インデックスは列の順番が大事。等号の列を先に。18 からはスキップスキャンもある
  • 部分インデックス、カバリングインデックス、GIN（配列・JSON）、BRIN（時系列）を使い分ける
  • インデックスは書き込みを遅くし、容量を使う。使われていないものは削る

14.8確認問題

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

問 1

大文字小文字を区別しない検索を速くする

正解済み

members で where lower(email) = 'user77777@example.com' の検索がインデックスを使えるように、インデックスを作ってください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行後のテーブルの中身で判定
ヒント

列に関数をかけた条件には、普通のインデックスは使えません。lower(email) そのものにインデックスを張ります（式インデックス）。

模範解答
create index on members (lower(email));

答え合わせでは、実行したあとに次の SQL で中身を調べて比べています。

select bool_or(p like '%Index%') as インデックスを使う from plan($$select * from members where lower(email) = 'user77777@example.com'$$) p;
問 2

2 つの条件をまとめて引く

正解済み

members で where pref = '東京都' and status = 'pending' を探すとき、2 つの条件の両方をインデックスで絞れるように、インデックスを作ってください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行後のテーブルの中身で判定
ヒント 1

複合インデックスです。create index on members (列1, 列2);

ヒント 2

答え合わせでは、実行計画の Index Cond に 2 つの列が両方出てくるかを見ます。

模範解答
create index on members (status, pref);

答え合わせでは、実行したあとに次の SQL で中身を調べて比べています。

select bool_or(p like '%Index Cond:%pref%' and p like '%Index Cond:%status%') as 両方で絞るfrom plan($$select * from members where pref = '東京都' and status = 'pending'$$) p;
問 3

一部の行だけのインデックス

正解済み

status = 'banned' の会員だけを対象にした、joined_at のインデックスを作ってください。

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行後のテーブルの中身で判定
ヒント

部分インデックスは、create index ... on テーブル (列) where 条件; と、最後に where を付けます。

模範解答
create index on members (joined_at) where status = 'banned';

答え合わせでは、実行したあとに次の SQL で中身を調べて比べています。
