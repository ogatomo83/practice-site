第 2 章

リレーショナルモデル

表、行、列、キーという言葉の正確な意味と、表どうしを組み合わせる「関係代数」の 5 つの操作。そして SQL で一番つまずきやすい NULL と三値論理を、実行しながら確かめます。

2.1表の正式な名前

リレーショナルモデルでは、表のことをリレーション（関係）と呼びます。データベースの名前の「リレーショナル」は、表どうしの関係ではなく、この数学の用語から来ています。

リレーショナルモデルSQL普段の言葉意味
リレーションテーブル表同じ形をした行の集まり
タプル行（row）レコード1 件分のデータ
属性列（column）項目、フィールド行の中の 1 つの値の名前
定義域（ドメイン）型（type）属性が取りうる値の範囲
次数列の数
濃度行の数件数

PostgreSQL の内部や公式文書でも、行のことをタプルと呼ぶ場面がよくあります。第 12 章でディスクの上の行を見るときにも、「ヒープタプル」という言葉が出てきます。

リレーションは集合

数学のリレーションは集合です。集合なので、次の 2 つの性質があります。

  1. 同じタプルが 2 回現れない（重複がない）
  2. タプルに順番がない（1 行目、2 行目という区別がない）

2 つ目は特に大事です。テーブルの行には、決まった順番がありません。select * from products の結果が id の順に並んで見えるのは、たまたまその順で保存されているからです。順番が欲しいときは、必ず order by で指定します（第 3 章）。

ところが、SQL のテーブルは 1 つ目の性質を守りません。主キーを付けなければ、まったく同じ行を何度でも入れられます。SQL のテーブルは、数学の集合ではなく多重集合（バッグ）です。

SQL⌘↵
create table bag (x int);
insert into bag values (1), (1), (2);
select * from bag;

1 が 2 回入っています。集合として扱いたいときは、distinct で重複を取り除きます。

SQL⌘↵
select distinct x from bag;
注意重複を許した理由

Codd は「SQL は重複を許したのが失敗だ」と批判しています。重複を取り除くには並べ替えなどの処理が要り、当時は遅かったために、SQL は重複を許すほうを選びました。実務上は、すべてのテーブルに主キーを付けることで、集合としての性質を取り戻します。

2.2キー

キーとは、行を見分けるための列（または列の組み合わせ）です。

用語意味文具店の例
スーパーキー値が決まれば行が 1 つに決まる列の組(id)、(id, name)、(email)
候補キースーパーキーのうち、列を 1 つでも減らすとキーでなくなる最小のもの(id)、(email)
主キー候補キーの中から、代表として 1 つ選んだものcustomers.id
代替キー主キーに選ばれなかった候補キーcustomers.email（unique 制約を付ける）
外部キーほかのテーブルの主キーを指す列orders.customer_id
複合キー2 つ以上の列からなるキーorder_items の (order_id, product_id)

外部キーの値は、参照先のテーブルに必ず存在しなければなりません。存在しない注文番号を指す明細は作れない、ということです。これを参照整合性と呼びます。試してみましょう。

SQLエラーになる⌘↵
insert into order_items values (999, 1, 1, 12000);
ERRORinsert or update on table "order_items" violates foreign key constraint "order_items_order_id_fkey"23503

SQLSTATE が 23 で始まるエラーは、すべて「整合性制約の違反」です。23503 は外部キー違反、23505 は一意性違反、23502 は NOT NULL 違反、23514 は CHECK 違反です。DETAIL の行に、どの値が見つからなかったかが書かれます。

制約の詳しい書き方は第 5 章で扱います。

自然キーと代理キー

主キーには、2 つの流儀があります。

  • 自然キー：もともとデータの中にある、意味のある値を使う。メールアドレス、ISBN、社員番号など
  • 代理キー：意味のない連番や UUID を新しく付ける。文具店の id 列がこれ

自然キーは「メールアドレスを変えたい」と言われた瞬間に困ります。主キーを変えると、それを参照している外部キーもすべて変える必要があるからです。そのため実務では、代理キーを主キーにして、自然キーには unique 制約を付ける方法がよく使われます。customers テーブルもその形になっています。

2.3関係代数

Codd は、リレーションを組み合わせて新しいリレーションを作る演算を定義しました。これを関係代数と呼びます。足し算や掛け算が数から数を作るように、関係代数の演算は表から表を作ります。

SQL の SELECT 文は、関係代数の演算を組み合わせたものです。主な 5 つと、それに対応する SQL を見てみましょう。

選択：行を絞る

条件に合う行だけを取り出します。SQL では where です。

SQL⌘↵
select * from customers where prefecture = '東京都';

射影：列を絞る

必要な列だけを取り出します。SQL では select の後ろに並べる列です。

SQL⌘↵
select name, prefecture from customers;

関係代数の射影は集合を返すので、重複は消えます。SQL の射影は重複を残します。都道府県だけを射影すると、東京都が何度も出てきます。

SQL⌘↵
select prefecture from customers;

関係代数と同じ結果にするには distinct を付けます。

SQL⌘↵
select distinct prefecture from customers order by prefecture;

結合：表をつなぐ

2 つの表の行を、条件に合うものどうし組み合わせます。第 7 章でじっくり扱うので、ここでは形だけ見ておきます。

SQL⌘↵
select o.id as 注文, c.name as 顧客, o.status
from orders o
join customers c on c.id = o.customer_id
where o.id <= 5;

和・差・積：同じ形の表を足し引きする

列の数と型がそろった 2 つの表は、集合として足したり引いたりできます。

SQL⌘↵
-- 東京都の顧客（集合 A）
select id from customers where prefecture = '東京都'
except
-- 注文したことのある顧客（集合 B）
select customer_id from orders
order by id;

結果の 10 は「東京都に住んでいるが、まだ 1 度も注文していない顧客」です。except を intersect に変えると「東京都に住んでいて注文したことがある顧客」に、union に変えると「どちらかに当てはまる顧客」になります。

やってみよう

上の SQL の except を intersect と union に書き換えて、結果の違いを確かめてください。union は重複を取り除き、union all は重複を残します。union all にすると何行になるでしょうか。

閉包性

関係代数の演算は、どれも表を受け取って表を返します。この性質を閉包性と呼びます。結果も表なので、それをまた別の演算に渡せます。SQL で SELECT の結果を FROM に書いたり（サブクエリ）、結果に名前を付けて使い回したり（ビュー、CTE）できるのは、この性質のおかげです。

2.4NULL と三値論理

リレーショナルデータベースで一番の難所が NULL です。NULL は「値が分からない」または「値が当てはまらない」ことを表す特別な印です。

文具店の顧客のうち 2 人は、生まれ年が登録されていません。

SQL⌘↵
select name, birth_year from customers where id in (3, 7, 8);

NULL は 0 でも空の文字列でもありません。「値がない」ことを示す印です。そして、NULL と何かを比べた結果は「真」でも「偽」でもなく、3 つ目の値である UNKNOWN（不明） になります。

SQL⌘↵
select null = null as "null = null",
       null <> 1    as "null <> 1",
       null > 0     as "null > 0",
       1 = 1        as "1 = 1";

結果の NULL は、論理値の UNKNOWN を表しています。「分からない値」と「分からない値」が等しいかどうかは、やはり分からない、という理屈です。

WHERE は真だけを通す

where は条件が真の行だけを残します。偽の行も UNKNOWN の行も捨てられます。そのため、次の 2 つを合わせても全員にはなりません。

SQL⌘↵
select count(*) as "1990 年以降" from customers where birth_year >= 1990;
SQL⌘↵
select count(*) as "1990 年より前" from customers where birth_year < 1990;

4 + 4 = 8 人で、全 10 人より 2 人少なくなります。生まれ年が NULL の 2 人は、どちらの条件でも UNKNOWN になって捨てられたからです。

NULL かどうかを調べるには、= ではなく is null を使います。

SQL⌘↵
select name from customers where birth_year is null;
SQL⌘↵
-- = null は常に UNKNOWN なので、1 行も返らない
select name from customers where birth_year = null;

三値論理の真理値表

AND、OR、NOT も 3 つの値で考えます。UNKNOWN を「真か偽のどちらかだが、どちらかは分からない」と考えると、表を覚えなくても答えを出せます。

aba AND ba OR bNOT a
真UNKNOWNUNKNOWN真偽
偽UNKNOWN偽UNKNOWN真
UNKNOWNUNKNOWNUNKNOWNUNKNOWNUNKNOWN

たとえば「偽 AND UNKNOWN」は、UNKNOWN が真でも偽でも結果は偽なので、偽と決まります。

SQL⌘↵
select (false and null) as "偽 AND 不明",
       (true or null)   as "真 OR 不明",
       (true and null)  as "真 AND 不明",
       not null::boolean as "NOT 不明";

NOT IN の落とし穴

三値論理で最も事故が多いのが、not in とサブクエリの組み合わせです。「どの部下の上司にもなっていない従業員」、つまり部下のいない従業員を探してみます。

SQL⌘↵
select name from employees
where id not in (select manager_id from employees);

0 行になってしまいます。部下のいない従業員は何人もいるはずです。原因は、店長の manager_id が NULL であることです。x not in (1, 2, NULL) は x <> 1 and x <> 2 and x <> NULL と同じ意味で、最後の x <> NULL が必ず UNKNOWN になるため、全体が真になることがありません。

対策は 2 つあります。NULL を除くか、not exists を使うかです。

SQL⌘↵
select name from employees e
where not exists (select 1 from employees s where s.manager_id = e.id);
要点NULL と付き合う 3 つのルール
  1. NULL かどうかは is null / is not null で調べる。= null は使わない
  2. NULL どうしを「同じ」とみなして比べたいときは、is not distinct from を使う
  3. サブクエリに NULL が混じる可能性があるなら、not in ではなく not exists を使う

is distinct from は、NULL も普通の値のように比べる演算子です。

SQL⌘↵
select null is not distinct from null as "NULL と NULL は同じ？",
       1 is distinct from null       as "1 と NULL は違う？";

NULL を別の値に置き換える

表示のときに NULL を別の値にしたいときは、coalesce（最初の NULL でない値を返す）を使います。

SQL⌘↵
select name, coalesce(birth_year::text, '未登録') as 生まれ年
from customers
order by id;
深掘りNULL は 1 種類で足りるのか

Codd は後に「値が分からない（例：生まれ年を聞いていない）」と「値が当てはまらない（例：法人の顧客には生まれ年がない）」を区別するため、2 種類の NULL を提案しました。しかし 4 値論理は複雑すぎるとして、SQL には取り入れられていません。設計で 2 つを区別したいときは、NULL の代わりに「法人かどうか」を表す列を別に持つのが普通です。

2.5宣言的であることの意味

最後に、第 1 章で紹介した「宣言的」という考え方を、実際の PostgreSQL で確かめておきます。次の SQL は「2 万円以上の注文をした顧客」を求めます。

SQL⌘↵
select distinct c.name
from customers c
join orders o on o.customer_id = c.id
join order_items oi on oi.order_id = o.id
group by c.name, o.id
having sum(oi.quantity * oi.unit_price) >= 20000;

この SQL には、どのテーブルから読み始めるか、どの索引を使うか、どう結合するかは一切書いてありません。それを決めるのは PostgreSQL のプランナです。explain を前に付けると、PostgreSQL が選んだ実行方法を見られます。

SQL⌘↵
explain
select distinct c.name
from customers c
join orders o on o.customer_id = c.id
join order_items oi on oi.order_id = o.id
group by c.name, o.id
having sum(oi.quantity * oi.unit_price) >= 20000;

今はまだ読めなくて構いません。第 15 章で、この出力を 1 行ずつ読めるようになります。大事なのは、SQL を書く人は「何が欲しいか」だけを書き、「どうやるか」はデータベースが決めているということです。データが増えて最適なやり方が変われば、同じ SQL のまま、PostgreSQL は別の実行方法を選びます。

要点この章のまとめ
  • テーブル = リレーション、行 = タプル、列 = 属性。数学のリレーションは集合だが、SQL のテーブルは重複を許す
  • 主キーは行を見分ける代表のキー。外部キーは別のテーブルの主キーを値で指す
  • SQL は関係代数（選択・射影・結合・和・差）の組み合わせで、結果も必ず表になる
  • NULL との比較は UNKNOWN になる。WHERE は真の行だけを通す。not in に NULL が混じると 0 行になる

2.6確認問題

この章で学んだことを使って、自分で SQL を書いてみましょう。「答え合わせ」を押すと、出力が模範解答と同じになっているかを判定します。列名や行の順番は（順番を指定した問題を除いて）問いません。答え合わせは本文とは別のデータベースで毎回取り消しながら行うので、何度でも試せます。

両方に入っている顧客

-- ここに SQL を書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵出力の値で判定（行の順番と列名は問わない）
