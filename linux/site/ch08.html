第 8 章

シグナルとジョブ

Ctrl-C を押すとコマンドが止まるのは、カーネルがプロセスに「シグナル」を届けるからです。kill で送り、trap で受け取り、strace で届く瞬間を見ます。後半では、&、jobs、fg、bg でいくつもの仕事を切り替える「ジョブ制御」の仕組みを、プロセスグループから理解します。

8.1シグナルとは

第 7 章で、プロセスを終わらせるのに kill を使いました。kill がしているのは、プロセスにシグナル（signal）を送ることです。

シグナルは、プロセスへの短い知らせです。中身は番号 1 つだけで、「終わってください」「止まってください」「子プロセスが終わりました」といった決まった意味があります。知らせは、プロセスが何をしている最中でも届きます。電話の呼び出し音のようなものです。

シグナルには、番号と名前があります。kill -l（list）で一覧が出ます。

シグナルの一覧⌘↵
kill -l

名前は SIG で始まります。31 個ありますが、よく出会うのは 10 個ほどです。

番号名前意味よくある送り手
1SIGHUP端末が切れた（hang up）端末を閉じたとき
2SIGINT割り込み（interrupt）Ctrl-C
3SIGQUIT終了して、メモリの中身を残すCtrl-\
9SIGKILL強制終了。防げないkill -9
11SIGSEGV不正なメモリ参照カーネル（プログラムのバグ）
13SIGPIPE読み手のいないパイプに書いたカーネル
15SIGTERM終わってください（terminate）kill（何も指定しないとき）
17SIGCHLD子プロセスが終わった、止まったカーネル
18SIGCONT再開（continue）fg、bg
19SIGSTOP一時停止。防げないkill -STOP
20SIGTSTP端末からの一時停止Ctrl-Z
メモ番号は CPU の種類で少し違う

1、2、3、9、15 はどの Linux でも同じですが、SIGCHLD や SIGSTOP などの番号は、CPU の種類によって違います（上の表は x86 と ARM のもの）。スクリプトでは、番号ではなく名前で書くのが安全です。

8.2kill：シグナルを送る

kill は、名前に反して「シグナルを送る」コマンドです。kill PID は、そのプロセスに SIGTERM（15 番）を送ります。

kill は、何も指定しなければ SIGTERM を送る⌘↵
sleep 300 &kill $!

Terminated（終了させられた）と表示されました。別のシグナルを送るには、-名前 か -番号 をつけます。次の 3 つは、どれも SIGKILL を送ります。

ターミナル
$ kill -KILL 1234$ kill -9 1234$ kill -s KILL 1234

シェルの kill は、システムコールの kill を呼んでいるだけです。この本の Linux は、シェル自身のシステムコールも表示できます。

まず、相手を用意する⌘↵
sleep 300 &
シェルが kill システムコールを呼ぶstrace：システムコールも表示⌘↵
kill -TERM $!

1 行目の kill(数, SIGTERM) = 0 が、シグナルを送るシステムコールです。次の wait4 が返した WIFSIGNALED(s) && WTERMSIG(s) == SIGTERM は、「子はシグナルで終わった。そのシグナルは SIGTERM」と読めます。シェルは、これを見て Terminated と表示しています。

シグナルで終わったときの終了ステータス

シグナルで終わったプロセスの終了ステータスは、シェルでは 128 + シグナルの番号になります。

SIGKILL（9）で終わると、終了ステータスは 137⌘↵
sleep 300 &kill -KILL $!wait $!; echo "終了ステータス $?"

128 + 9 = 137 です。kill -l に終了ステータスを渡すと、シグナルの名前に直してくれます。

終了ステータスから、シグナルの名前を調べる⌘↵
kill -l 137kill -l 143

だれにでも送れるわけではない

シグナルを送れるのは、自分のプロセスに対してだけです（root は、だれにでも送れます）。

他人のプロセスには送れない。ないプロセスにも送れないエラーになる⌘↵
kill 1kill 99999

PID 1 の init は root のプロセスなので、Operation not permitted（許可されていない）です。99999 番のプロセスは存在しないので、No such process です。

8.3デフォルトの動作：終了、コア、無視、停止

プロセスが何も用意していないとき、シグナルを受け取るとデフォルトの動作が起きます。動作は、シグナルごとに決まっていて、5 種類あります。

コア（core dump）は、終了するときに、プロセスのメモリの中身を core というファイルに書き出す動作です。あとでデバッガで開いて、どこで何が起きたかを調べるためのものです。プログラムのバグで起きるシグナル（SIGSEGV など）は、この動作になっています。

3 つの動作を、同じ sleep に送って確かめます。

SIGQUIT はコア、SIGCHLD は無視、SIGTERM は終了⌘↵
sleep 300 &kill -CHLD $!jobskill -QUIT $!wait $!; echo "終了ステータス $?"

SIGCHLD を送っても、jobs（& で起動した仕事の一覧）は Running のままで、何も起きていません。SIGQUIT を送ると、Quit (core dumped) と表示されて終わりました。終了ステータスは 128 + 3 = 131 です。

メモこの本の Linux は、core ファイルを作らない

(core dumped) と表示されますが、この本の小さな Linux は、実際には core ファイルを書きません。本物の Linux でも、多くの環境では core ファイルの大きさの上限が 0 に設定されていて（ulimit -c で確かめられます）、そのままでは書かれません。

停止と再開は、第 7 章で状態 T を作るのに使いました。もう一度、状態の変化を追います。

SIGSTOP で止めて、SIGCONT で再開する⌘↵
sleep 300 &kill -STOP $!ps -o pid,stat,commkill -CONT $!ps -o pid,stat,commkill $!

STAT が T（停止）になり、SIGCONT で S（待ち）に戻りました。

8.4Ctrl-C と Ctrl-Z：端末のキーがシグナルになる

コマンドを実行中に Ctrl-C を押すと、止まります。これもシグナルです。端末は、Ctrl-C が押されたことをカーネルに伝え、カーネルが、いま端末を使っているプロセスに SIGINT を送ります。

次のブロックは、sleep 100 を実行して、0.5 秒後に Ctrl-C を押します（押す操作は、この本の Linux が代わりにやります。実験場の端末では、自分で押せます）。

sleep 100 を実行して、0.5 秒後に Ctrl-CCtrl-C で止める例⌘↵
sleep 100
終了ステータスは 130⌘↵
echo $?kill -l 130

100 秒待たずに、プロンプトに戻りました。終了ステータスは 128 + 2 = 130。SIGINT で終わった、という意味です。

シグナルが届く瞬間は、strace で見えます。

strace で、SIGINT が届くところを見るCtrl-C で止める例strace：システムコールも表示⌘↵
sleep 100

--- SIGINT {si_signo=SIGINT, si_code=SI_KERNEL} --- の行が、シグナルの到着です。--- で囲まれた行は、システムコールではなく、シグナルが届いたことを表します。si_code=SI_KERNEL は、送り手がカーネル（端末のドライバ）だという印です。最後の +++ killed by SIGINT +++ は、そのシグナルで終わったことを示します。

端末のキーが送るシグナルは、3 つあります。

キーシグナルデフォルトの動作
Ctrl-CSIGINT終了
Ctrl-\SIGQUIT終了してコア
Ctrl-ZSIGTSTP停止
メモCtrl-D はシグナルではない

Ctrl-D は「入力の終わり（EOF）」を端末に伝えるキーで、シグナルは送りません。cat などが「もう読むものがない」と知って、自分で終わるだけです。

Ctrl-Z は、終わらせずに一時停止させます。

sleep 100 を実行して、0.5 秒後に Ctrl-ZCtrl-Z で止める例⌘↵
sleep 100
止まっているだけで、終わってはいない⌘↵
echo $?ps -o pid,stat,comm

Stopped と表示されて、プロンプトに戻りました。終了ステータスは 128 + 20 = 148 です。ps で見ると、sleep は状態 T で残っています。止めたプロセスをどう再開するかは、ジョブ制御の節で扱います。ここでは終わらせておきます。

後片づけ⌘↵
kill %1

8.5ハンドラ：シグナルを捕まえる

プロセスは、シグナルごとに「受け取ったら、この関数を実行する」と、カーネルに登録できます。この関数をシグナルハンドラ（signal handler）と呼び、登録することを「シグナルを捕まえる」と言います。ハンドラを登録したシグナルでは、デフォルトの動作は起きません。

練習用のコマンド sigwait は、SIGINT、SIGHUP、SIGUSR1、SIGUSR2、SIGTERM にハンドラを登録し、受け取るたびに名前を表示します。SIGTERM を受け取ったときだけ、表示してから自分で終わります。

捕まえたシグナルでは、終わらない⌘↵
sigwait &kill -INT $!kill -HUP $!kill -USR1 $!jobs

SIGINT も SIGHUP も、デフォルトの動作は「終了」ですが、sigwait は名前を表示するだけで、動き続けています。

メモSIGUSR1 と SIGUSR2

この 2 つには、決まった意味がありません。プログラムが好きな用途に使えます。たとえば「設定ファイルを読み直す」「ログファイルを開き直す」といった合図に使われます。

どのシグナルを捕まえているかは、/proc/PID/status の SigCgt（caught）でわかります。

捕まえているシグナル、無視しているシグナル⌘↵
grep Sig /proc/$!/status

値は 16 進数で、n 番のシグナルが、右から n 番目のビットに対応します。4a03 を 2 進数にすると 100 1010 0000 0011 で、右から 1、2、10、12、15 番目が 1 です。HUP、INT、USR1、USR2、TERM の 5 つです。SigIgn は無視しているシグナル、SigBlk は一時的に受け取りを止めているシグナル、SigPnd は届いたがまだ処理されていないシグナルです。

SIGKILL と SIGSTOP は捕まえられない

すべてのシグナルを捕まえられるなら、「絶対に終わらないプログラム」が作れてしまいます。そこで、SIGKILL（9）と SIGSTOP（19）の 2 つだけは、捕まえることも無視することもできない決まりになっています。

SIGSTOP と SIGKILL は、sigwait にも防げない⌘↵
kill -STOP $!jobskill -USR1 $!kill -CONT $!kill -KILL $!

順に何が起きたかを見ます。

  1. SIGSTOP で、sigwait は止まった（Stopped）
  2. 止まっているあいだに SIGUSR1 を送ったが、何も表示されない。プロセスが止まっているので、ハンドラを実行できない。シグナルは保留されている
  3. SIGCONT で再開すると、保留されていた SIGUSR1 のハンドラが動いて、got SIGUSR1 と表示された
  4. SIGKILL で、sigwait は終わった（Killed）。名前を表示する間もない
コツkill -9 は最後の手段

プログラムを終わらせたいときは、まず何もつけない kill（SIGTERM）を使ってください。行儀のよいプログラムは、SIGTERM を捕まえて、書きかけのファイルを保存し、一時ファイルを消してから終わります。SIGKILL は、その後片づけの機会を与えません。SIGTERM で終わらないときにだけ、kill -9 を使います。

strace で、ハンドラの登録と実行を見る

sigwait を strace つきで実行して、シグナルを 2 つ送ります。

登録（rt_sigaction）と、到着（--- SIGUSR1 ---）strace：システムコールも表示⌘↵
sigwait & sleep 1; kill -USR1 $!; sleep 1; kill -TERM $!; wait

sleep の行も混ざっていますが、sigwait の行だけを追うと、次の順になっています。

行意味
rt_sigaction(SIGUSR1, {sa_handler=0x…}, …) = 0 など 5 行ハンドラの登録。sa_handler がハンドラの関数の場所
pause()シグナルが来るまで眠るシステムコール
--- SIGUSR1 {…, si_code=SI_USER, si_pid=2, …} ---SIGUSR1 が届いた。SI_USER は「ほかのプロセスが kill で送った」、si_pid=2 は送り手がシェルだという意味
pause() = -1 EINTR眠っていたシステムコールが、シグナルで中断されて戻った
write(1, "got SIGUSR1\n", 12)ハンドラが覚えておいたシグナルの名前を、表示した

SIGTERM でも同じことが起き、そのあと exit_group(0) で自分から終わっています。終了ステータスは 0 です。シグナルで「終わらされた」のではなく、シグナルを合図に「自分で終わった」からです。

8.6trap：シェルスクリプトでシグナルを捕まえる

シェルスクリプトでは、trap 'コマンド' シグナル名 でハンドラを登録します。

SIGINT と SIGTERM を捕まえるスクリプト⌘↵
cat > loop.sh <<'EOF'#!/bin/shtrap 'echo "SIGINT を受け取りました。続けます"' INTtrap 'echo "SIGTERM を受け取りました。終わります"; exit 0' TERMi=0while [ $i -lt 5 ]; do  i=$((i + 1))  echo "$i 回目"  sleep 1doneEOFchmod +x loop.sh

1 秒ごとに数を表示するループです。実行して、1.5 秒後に Ctrl-C を押します。

Ctrl-C を押しても、スクリプトは終わらないCtrl-C で止める例⌘↵
./loop.sh

2 回目のあとで Ctrl-C が押されましたが、スクリプトはメッセージを出して、5 回目まで続きました。今度は、バックグラウンドで実行して、SIGTERM を送ります。

SIGTERM では、メッセージを出して終わる⌘↵
./loop.sh &sleep 2; kill -TERM $!wait $!; echo "終了ステータス $?"
メモシェルは、実行中のコマンドが終わってから trap を実行する

上の例で、Ctrl-C を押した瞬間に sleep 1 は SIGINT で終わっています（sleep は SIGINT を捕まえていないので、デフォルトの動作で終わります）。シェルは、その sleep が終わったあとで、trap のコマンドを実行します。

後片づけに使う：EXIT

trap でいちばん役に立つのは、後片づけです。シグナル名の代わりに EXIT と書くと、「スクリプトが終わるとき」に実行するコマンドを登録できます。一時ファイルを作るスクリプトの定番の書き方です。

途中で止められても、一時ファイルを消すスクリプト⌘↵
cat > work.sh <<'EOF'#!/bin/shtmp=/tmp/work.$$trap 'rm -f "$tmp"; echo "一時ファイルを消しました"' EXITtrap 'exit 130' INTtrap 'exit 143' TERMsort fruits.txt > "$tmp"echo "$(wc -l < "$tmp") 行を並べ替えて、$tmp に置きました"sleep 30echo "ここまで来れば、ふつうの終了"EOFchmod +x work.sh

$$ はシェル自身の PID なので、/tmp/work.$$ は実行のたびに違う名前になります。実行して、0.5 秒後に Ctrl-C で止めます。

Ctrl-C で止めても、後片づけが走るCtrl-C で止める例⌘↵
./work.sh
一時ファイルは残っていない⌘↵
ls /tmp

SIGINT を受け取ると exit 130 が実行され、スクリプトが終わるので、EXIT に登録した後片づけが実行されます。

注意SIGKILL では、後片づけも走らない

kill -9 で終わらされたスクリプトは、trap を実行できません。一時ファイルは残ります。kill -9 を最後の手段にする理由の 1 つです。

無視する、元に戻す

コマンドを空文字列にすると、そのシグナルを無視します。- にすると、デフォルトの動作に戻します。

trap '' で無視する。SIGKILL は無視できない⌘↵
sh -c 'trap "" TERM; kill -TERM $$; echo "SIGTERM を無視して、生きています"'sh -c 'trap "" KILL; kill -KILL $$; echo "ここには来ない"'; echo "終了ステータス $?"

sh -c で起動した子のシェルが、自分自身（$$）にシグナルを送っています。SIGTERM は無視できましたが、SIGKILL は trap で無視するように書いても効かず、137 で終わりました。

8.7SIGCHLD と SIGPIPE：カーネルが送るシグナル

シグナルは、人が kill で送るものだけではありません。カーネルが、できごとを知らせるために送るものがあります。

SIGCHLD：子が終わった

子プロセスが終わると、カーネルは親に SIGCHLD を送ります。デフォルトの動作は「無視」なので、ふつうは何も起きません。親がハンドラを登録しておけば、子が終わった瞬間を知ることができます。

子が終わると、親に SIGCHLD が届くstrace：システムコールも表示⌘↵
sh -c 'trap "echo child exited" CHLD; sleep 1 & wait; echo end'

sleep の +++ exited with 0 +++ の直後に、親の sh に --- SIGCHLD … --- が届いています。si_pid が、終わった子の PID です。親の wait4 はシグナルで中断され（EINTR）、trap に登録した echo が実行されました。

第 7 章で、「親が wait で回収しないと、子はゾンビになる」ことを見ました。いつ wait を呼べばよいかを親に教えるのが、SIGCHLD です。たくさんの子を抱えるサーバのプログラムは、SIGCHLD のハンドラの中で wait を呼んで、ゾンビを残さないようにしています。

メモ本物の strace では

本物の Linux の strace は、この行を --- SIGCHLD {si_signo=SIGCHLD, si_code=CLD_EXITED, si_pid=…, si_status=0, …} --- と表示します。CLD_EXITED は「子がふつうに終了した」という意味で、終了ステータスも一緒に運ばれます。この本の Linux では、si_code が SI_USER と簡単になっています。

SIGPIPE：読み手がいないパイプ

yes は、止められるまで y を出力し続けるコマンドです。head -3 につなぐと、3 行で終わります。

yes は無限に出力するのに、3 行で終わる⌘↵
yes | head -3

head は 3 行読んだら終わります。しかし、yes はなぜ終わるのでしょうか。strace で見ます。

読み手がいなくなったパイプに書くと、SIGPIPEstrace：システムコールも表示⌘↵
yes | head -1

[pid 数] を手がかりに追うと、次のことが起きています（2 つ目のプロセスが現れるまでは区別が要らないので、最初の数行には [pid 数] がつきません。そこは yes の行です）。

  1. yes は、4096 バイトずつ write している。head が読むのを待たずに、パイプへ何回ぶんもためていく
  2. head は 1 回 read して、1 行だけ書き出し、exit_group(0) で終わる
  3. yes の次の write は、-1 EPIPE (Broken pipe) で失敗する。パイプの読み手が、もうだれもいないから
  4. 同時に、カーネルは yes に SIGPIPE を送る。デフォルトの動作は「終了」なので、yes は +++ killed by SIGPIPE +++ で終わる

SIGPIPE があるおかげで、パイプの左側のコマンドは、「右側がもう読まない」ことを自分で調べなくても、自動的に止まります。第 5 章で sort … | head のようなパイプラインが無駄なく終わっていたのは、この仕組みによるものです。

8.8ジョブ制御：&、jobs、fg、bg

ここまで、& を説明なしに使ってきました。シェルには、1 つの端末でいくつもの仕事を切り替える仕組みがあります。ジョブ制御（job control）です。

ジョブは、シェルに 1 行で頼んだ仕事の単位です。sleep 300 も、sort a.txt | uniq -c | head も、1 つのジョブです（プロセスは 3 つでも、ジョブは 1 つ）。

  • フォアグラウンド（前景）のジョブ：シェルは、終わるのを待つ。キー入力はこのジョブに届く。同時に 1 つだけ
  • バックグラウンド（背景）のジョブ：シェルは待たずに、すぐ次のプロンプトを出す。いくつでも

コマンドの終わりに & をつけると、バックグラウンドで始まります。

バックグラウンドのジョブを 2 つ作る⌘↵
sleep 300 &sleep 400 &jobs

[1] 数 の [1] がジョブ番号、右の数が PID です。jobs は、ジョブの一覧を出します。+ は「いちばん最近のジョブ」、- はその 1 つ前の印です。

ジョブは、%番号 で指定できます。kill、fg、bg、wait で使えます。PID を調べなくて済みます。

%2 で、2 番目のジョブを指定する⌘↵
kill %2jobs

fg と bg、そして Ctrl-Z

fg（foreground）は、バックグラウンドのジョブをフォアグラウンドに移します。bg（background）は、止まっているジョブをバックグラウンドで再開します。Ctrl-Z と組み合わせると、実行中のコマンドを「いったん止めて、後ろに回す」ことができます。

やってみます。まず、1 番のジョブ（sleep 300）を fg で前に出し、0.5 秒後に Ctrl-Z で止めます。

fg で前に出して、Ctrl-Z で止めるCtrl-Z で止める例⌘↵
fg %1
止まったジョブを、bg で後ろに回す⌘↵
jobsbg %1jobs

Stopped だったジョブが、bg で Running に戻りました。bg は、ジョブに SIGCONT を送っています。もう一度 fg で前に出して、今度は Ctrl-C で終わらせます。

fg で前に出して、Ctrl-C で終わらせるCtrl-C で止める例⌘↵
fg %1
ジョブはなくなった⌘↵
jobs

時間のかかるコマンドを & なしで始めてしまったときは、Ctrl-Z で止めて bg と打てば、最初から & をつけたのと同じになります。

wait：ジョブが終わるのを待つ

スクリプトでは、いくつかの仕事を & で同時に始めて、wait で全部が終わるのを待つ、という使い方をします。

2 つの仕事を同時に走らせて、両方を待つ⌘↵
sleep 3 &sleep 2 &waitecho "両方終わりました"

順に実行すれば 5 秒かかるところが、3 秒で終わります（この本の Linux の時計で）。

8.9プロセスグループと前景グループ

Ctrl-C を押したとき、カーネルはどのプロセスに SIGINT を送るのでしょうか。「フォアグラウンドのジョブ」ですが、カーネルは「ジョブ」という言葉を知りません。カーネルが知っているのは、プロセスグループです。

  • プロセスグループは、プロセスの集まり。番号（PGID）を持つ。シェルは、ジョブ 1 つにつき、プロセスグループを 1 つ作る。パイプラインの全員が、同じグループに入る
  • セッションは、プロセスグループの集まり。1 回のログイン（1 つの端末）で動くものすべて。番号（SID）は、ログインシェルの PID
  • 端末は、「いまの前景グループはどれか」を 1 つ覚えている。Ctrl-C や Ctrl-Z のシグナルは、前景グループの全員に送られる

ps の -o に pgid と sid を足すと見えます。バックグラウンドに sleep 300 を置いて、フォアグラウンドでパイプラインを実行します。

プロセスグループ（PGID）とセッション（SID）⌘↵
sleep 300 &sleep 5 | ps -o pid,pgid,sid,stat,comm
  • SID は全員同じ（シェルの PID）。1 つのセッションに入っている
  • sleep 5 と ps は、PGID が同じ。パイプラインなので、同じプロセスグループ。STAT に + がついていて、これが前景グループ
  • sleep 300 は、自分だけのプロセスグループ。+ がないので、バックグラウンド
  • シェルは、自分だけのプロセスグループ。STAT の s は、セッションのリーダーの印

確かめます。パイプラインを実行して Ctrl-C を押し、strace で SIGINT の届き先を見ます。

Ctrl-C は、パイプラインの全員に届くCtrl-C で止める例strace：システムコールも表示⌘↵
sleep 100 | sleep 200

--- SIGINT … --- が 2 回、別々の PID に届いています。1 回の Ctrl-C で、パイプラインの両方が終わりました。

バックグラウンドの sleep 300 は、生きている⌘↵
jobs

バックグラウンドのジョブには、Ctrl-C は届いていません。

シェルがしていること

第 7 章で ls notes のシステムコールの列を見たとき、説明を後回しにした行がありました。あれがジョブ制御の準備です。もう一度見ます。

フォアグラウンドのコマンドを実行するときの、ジョブ制御の準備strace：システムコールも表示⌘↵
true | true
行意味
setpgid(子, 子) = 0子を、新しいプロセスグループに入れる。パイプラインの 2 人目は、1 人目のグループに入れる
ioctl(255, TIOCSPGRP, [数]) = 0端末に「前景グループはこれ」と伝える
rt_sigaction(SIGINT, {sa_handler=SIG_DFL, …}) など子の側で、シグナルの扱いをデフォルトに戻す。シェル自身は SIGINT などを無視しているので、そのままでは子も無視してしまう
最後の ioctl(255, TIOCSPGRP, [2]) = 0コマンドが終わったら、前景グループをシェル自身に戻す

Ctrl-C を押してもシェル自身が終わらないのは、シェルが SIGINT を無視しているからです。

後片づけ⌘↵
kill %1
メモ本物の Linux では：バックグラウンドのジョブが端末を読もうとすると

バックグラウンドのジョブは、キー入力を読めません。読もうとすると、カーネルがそのプロセスグループに SIGTTIN を送り、ジョブは止まります。fg で前に出すと、読めるようになります。

ターミナル
$ cat &[1] 4321$ jobs[1]+  Stopped                 cat

この本の Linux では、バックグラウンドのコマンドは入力の終わり（EOF）を受け取って、すぐ終わります。

8.10SIGHUP と nohup：端末を閉じても動かし続ける

リモートのサーバにログインして、時間のかかるコマンドを & で走らせ、端末を閉じて帰りました。翌朝見ると、コマンドは途中で終わっています。原因は SIGHUP です。

端末が閉じられる（回線が切れる）と、カーネルは、その端末のセッションのリーダー（ログインシェル）に SIGHUP を送ります。シェルは、終わる前に、自分のジョブすべてに SIGHUP を送ります。SIGHUP のデフォルトの動作は「終了」なので、バックグラウンドのジョブも一緒に終わります。

この本の Linux では、端末を閉じることはできません。代わりに、kill -HUP で同じシグナルを送ってみます。

SIGHUP を受け取ると、終わる⌘↵
sleep 300 &kill -HUP $!

Hangup と表示されて、終わりました。

nohup：SIGHUP を無視させて起動する

nohup（no hang up）は、SIGHUP を無視する設定にしてから、コマンドを起動します。本物の Linux では、こう使います。

ターミナル
$ nohup ./long-job.sh &[1] 4321nohup: ignoring input and appending output to 'nohup.out'$ exit

端末を閉じても、long-job.sh は動き続けます。端末がなくなると出力の行き先もなくなるので、nohup は標準出力を nohup.out というファイルに付け替えます。

nohup の仕組みは単純です。「シグナルを無視する」という設定は、exec で別のプログラムに入れ替わっても引き継がれます（ハンドラは引き継がれません。ハンドラの関数は、入れ替わる前のプログラムの中にあったものだからです）。nohup は、SIGHUP を無視に設定して、指定されたコマンドを exec しているだけです。

この本の Linux には nohup コマンドがないので、同じことをシェルで書いて確かめます。trap "" HUP で無視に設定し、exec で sleep に入れ替わります。

nohup と同じこと：SIGHUP を無視に設定してから exec する⌘↵
sh -c 'trap "" HUP; exec sleep 300' &sleep 1; grep SigIgn /proc/$!/statuskill -HUP $!jobs

SigIgn の右端のビット（1 番 = SIGHUP）が立っています。プロセスは sleep に入れ替わっていますが、「SIGHUP を無視」の設定は残っています。SIGHUP を送っても、Running のままです。

SIGTERM は無視していないので、終わる⌘↵
kill %1
メモ本物の Linux では：ほかの方法
  • bash の組み込みコマンド disown は、すでに & で始めたジョブを、シェルのジョブの表から外す。シェルは、終わるときにそのジョブへ SIGHUP を送らなくなる
  • setsid コマンド は、コマンドを新しいセッションで起動する。端末とのつながりが切れるので、端末が閉じても SIGHUP は届かない
  • 長い作業には、tmux や screen を使うことが多い。サーバの側に「閉じない端末」を作っておき、いつでもつなぎ直せる
  • ずっと動かし続けるプログラム（サービス）は、端末から起動せず、init（systemd）に起動させる（第 17 章）

8.11確認問題

この章の内容を、自分でコマンドを書いて確かめます。どの問題も、状況を少し変えた状態でも試されます。

問 1

1 つだけ終わらせる

正解済み

バックグラウンドで sleep 600、sleep 700、sleep 800 の 3 つのジョブが動いています（ほかにもあるかもしれません）。このうち、sleep 700 だけを終わらせてください。ほかのジョブは、動いたままにします。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

jobs で、sleep 700 のジョブ番号を確かめます。kill %番号 で、そのジョブに SIGTERM を送れます。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

sleep 600 &sleep 700 &sleep 800 &
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

ps -e -o stat,args | grep 'sleep [0-9]'
模範解答
kill %2
問 2

終わらせずに止める

正解済み

バックグラウンドで spin（1 番のジョブ）と sleep 600（2 番のジョブ）が動いています。spin は CPU を使い続けています。spin を終わらせずに、一時停止させてください。sleep 600 には何もしません。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

一時停止させるシグナルは SIGSTOP です。kill -STOP で送ります。確かめのコマンドは、spin の状態が T になっているかを見ます。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

spin &sleep 600 &
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

ps -e -o stat,comm | grep -E 'spin|sleep'
模範解答
kill -STOP %1
問 3

シグナルに答えるスクリプト

正解済み

ホームディレクトリに guard.sh を作ってください。次のように動くスクリプトです。

  • SIGUSR1 を受け取るたびに、ping と 1 行表示する（終わらない）
  • SIGTERM を受け取ったら、bye と 1 行表示して、終了ステータス 0 で終わる
  • それまでは、sleep 1 をくり返して待ち続ける

確かめのコマンドは、guard.sh をバックグラウンドで起動し、SIGUSR1 を何回か送り、最後に SIGTERM を送って、出力と終了ステータスを調べます。

cat > guard.sh <<'EOF'#!/bin/shwhile true; do sleep 1; doneEOF
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

trap 'コマンド' シグナル名 を 2 行書きます。SIGTERM のほうは、echo bye のあとに exit 0 が要ります。exit がないと、表示したあともループが続きます。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

echo 2 > /home/you/count.txt
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

sh /home/you/guard.sh &sleep 2; for i in $(seq 1 $(cat /home/you/count.txt)); do kill -USR1 $!; sleep 2; done; kill -TERM $!; sleep 2; kill -KILL $! 2>/dev/null; wait $!; echo "status $?"
模範解答
cat > guard.sh <<'EOF'#!/bin/shtrap 'echo ping' USR1trap 'echo bye; exit 0' TERMwhile true; do sleep 1; doneEOF
問 4

どのシグナルで終わったか

正解済み

ホームディレクトリの mystery.sh は、実行すると、何かのシグナルで終わります。sh mystery.sh を実行して、それを終わらせたシグナルの名前（kill -l が答える形。SIG はつかない）を 1 行で出力してください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番も見る）
ヒント

シグナルで終わったコマンドの終了ステータスは、128 + シグナルの番号です。kill -l 数 は、終了ステータスをシグナルの名前に直してくれます。$? は、次のコマンドを実行すると上書きされるので、すぐに使います。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

cat > mystery.sh <<'EOF'n=$(wc -l < /home/you/fruits.txt)case $((n % 3)) in 0) s=TERM ;; 1) s=USR1 ;; 2) s=HUP ;; esackill -$s $$EOF
模範解答
sh mystery.shkill -l $?
要点この章のまとめ
  • シグナルは、プロセスへの短い知らせ。番号と名前がある（kill -l）。送り手は、端末のキー、kill、カーネル自身
  • kill PID は SIGTERM を送る。kill -名前 PID でほかのシグナル。シグナルで終わったプロセスの終了ステータスは 128 + 番号
  • 受け取ったプロセスの反応は、デフォルトの動作（終了、コア、無視、停止、再開）、ハンドラの実行、無視のどれか
  • SIGKILL と SIGSTOP は、捕まえることも無視することもできない。kill -9 は後片づけの機会を与えないので、最後の手段
  • Ctrl-C は SIGINT、Ctrl-Z は SIGTSTP、Ctrl-\ は SIGQUIT。strace では、シグナルの到着が --- SIGINT … --- の行で見える
  • シェルスクリプトでは trap 'コマンド' シグナル で捕まえる。trap … EXIT は後片づけの定番。trap '' で無視
  • 子が終わると親に SIGCHLD。読み手のいないパイプに書くと SIGPIPE（yes | head が終わる理由）
  • ジョブ制御：& でバックグラウンド、jobs で一覧、fg で前へ、bg で後ろで再開、%1 で指定、wait で待つ
  • シェルは、ジョブごとにプロセスグループを作る。端末のキーのシグナルは、前景グループの全員に届く
  • 端末が閉じると SIGHUP がジョブに届いて終わる。nohup は SIGHUP を無視に設定してから exec する。無視の設定は exec をまたいで引き継がれる
