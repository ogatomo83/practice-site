第 10 章

システムコール

プログラムは、ファイルにも画面にもほかのプロセスにも、自分では触れません。触れるのはカーネルだけで、プログラムはカーネルに「頼む」ことしかできません。その頼みごとがシステムコールです。strace で cat と ls の頼みごとを 1 行ずつ読み、エラー番号 errno の正体まで降ります。

10.1プログラムは、自分では何もできない

前の章で、cat が openat、read、write、close を呼ぶ様子を見ました。なぜ cat は、わざわざカーネルに頼むのでしょうか。自分でディスクを読めばよさそうです。

答えは、読めないようになっているからです。CPU には、少なくとも 2 つの動作モードがあります。

  • カーネルモード（特権モード）… すべての命令を実行でき、すべてのメモリと装置に触れる。カーネルだけがこのモードで動く
  • ユーザーモード（非特権モード）… 装置を操作する命令や、ほかのプログラムのメモリへのアクセスが禁じられている。シェルも cat もブラウザも、ふつうのプログラムはすべてこのモードで動く

ユーザーモードのプログラムが禁じられた命令を実行しようとすると、CPU がそれを止めて、カーネルに知らせます。これはソフトウェアの約束ではなく、CPU というハードウェアの機能です。

この分け方には、はっきりした理由があります。

  • 守る… あるプログラムの誤りや悪意が、ほかのプログラムやシステム全体を壊さない。第 4 章の権限の検査も、プログラムがディスクを直接読めたら意味がなくなる
  • 分け合う… 1 つのディスク、1 つの画面、限られたメモリを、たくさんのプロセスが使う。順番や取り分を決める審判が要る
  • 隠す… ディスクの種類やネットワーク機器の違いをカーネルが引き受ける。プログラムは「ファイルを読む」とだけ言えばよい

10.2システムコールは、カーネルへの頼みごと

ユーザーモードのプログラムが、カーネルに仕事を頼む。その決まった入口がシステムコール（system call）です。「ファイルを開いて」「このバイト列を書いて」「子プロセスを作って」のように、頼める仕事の種類は決まっていて、1 つ 1 つに名前と番号がついています。今の Linux には、400 個近くあります。

呼び出しは、ふつうの関数呼び出しとは違います。プログラムは、頼みたい仕事の番号と引数を CPU のレジスタに置き、モードを切り替える特別な命令を実行します。すると CPU はカーネルモードに切り替わり、カーネルの中の決まった場所へ飛びます。カーネルは番号を見て仕事をし、結果をレジスタに置いて、ユーザーモードに戻します。

「モードを切り替える命令」は、CPU の種類ごとに違います。x86-64 では syscall、ARM では svc、RISC-V では ecall です。姉妹サイト「図解 CPU」の第 19 章「例外・割り込み・OS へ」では、RISC-V の ecall を使って、この切り替えを自分の手で動かせます。この本では、切り替えの向こう側、つまりカーネルが何を頼まれ、何を返すのかを見ていきます。

10.3strace の読み方

strace は、プログラムが呼んだシステムコールを、1 回につき 1 行で表示する道具です。前の章では実行ブロックの「strace」欄で見ましたが、strace はふつうのコマンドでもあります。調べたいコマンドの前に strace と書きます。

strace をコマンドとして使う⌘↵
strace cat /etc/hostname

cat 本来の出力（zukai）に混ざって、システムコールの行が出ます。strace の行は標準エラー出力に出るので、色が違って見えます。1 行の形は、いつも同じです。

openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3~~~~~~ ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~   ~名前    引数                                   戻り値
  • 名前… システムコールの名前
  • 引数… かっこの中。数、文字列、O_RDONLY のような名前つきの定数。長い文字列は 32 バイトで切られ、"..." がつく
  • 戻り値… = の右。成功なら 0 以上の数（fd、バイト数など）。失敗なら -1 で、そのあとにエラーの名前と説明が続く

最後の +++ exited with 0 +++ はシステムコールではなく、「このプロセスは終了ステータス 0 で終わった」という strace からの知らせです。

混ざると読みにくいので、-o ファイル で strace の出力をファイルに分けられます。

-o でファイルに記録する⌘↵
strace -o trace.log cat /etc/hostnamecat trace.log

これなら、あとから grep や wc で調べられます。見たいシステムコールが決まっているなら、-e trace=名前 で絞れます。

-e trace= で絞る⌘↵
strace -e trace=openat,close cat /etc/hostname /etc/os-release > /dev/null
オプション意味
-o ファイル記録をファイルに書く
-e trace=名前,…そのシステムコールだけを表示する
-f子プロセスも追う（fork した先も記録する。行の頭に [pid 番号] がつく）

10.4cat がしていること

記録した trace.log を、1 行ずつ読みましょう。cat という名前から想像する仕事は「ファイルの中身を表示する」ですが、カーネルから見た cat は、次の 8 行がすべてです。

行意味
execve("/usr/bin/cat", ["cat", "/etc/hostname"], … /* 8 vars */) = 0シェルが作った子プロセスが、/usr/bin/cat というプログラムに入れ替わる（第 7 章）。引数の配列と、環境変数 8 個が渡された。ここからが cat
openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3ファイルを読み取り専用で開く。fd 3 が返った
read(3, "zukai\n", 4096) = 6fd 3 から最大 4096 バイト読む。6 バイト読めた。引数の文字列は、読めた中身
write(1, "zukai\n", 6) = 6読んだ 6 バイトを fd 1（標準出力）に書く。6 バイト書けた
read(3, "", 4096) = 0もう一度読む。0 バイト = ファイルの終わり
close(3) = 0fd 3 を閉じる
exit_group(0) = ?終了ステータス 0 で終わる。戻ってこないので、戻り値は ?
+++ exited with 0 +++（strace の知らせ）

AT_FDCWD は、「相対パスなら、カレントディレクトリから探す」という印です。openat は「この fd のディレクトリを起点に開く」というシステムコールで、起点に AT_FDCWD を渡すと、昔の open と同じ動きになります。

read の 4096 は、cat が用意した入れ物（バッファ）の大きさです。ファイルが 4096 バイトより大きければ、read と write の組が何度もくり返されます。cat は、ファイルの大きさを前もって調べません。「0 が返るまで読む」だけです。だから、大きさのわからないパイプや端末が相手でも、同じプログラムで動きます。

ファイルを 2 つ渡すと、openat から close までが 2 回くり返されます。

ファイルを 2 つ渡すstrace：システムコールも表示⌘↵
cat /etc/hostname numbers.txt

cat（concatenate、つなげる）の「つなげる」は、同じ fd 1 に続けて書く、というだけのことです。fd は 2 回とも 3 です。1 つ目を閉じたので、空いたいちばん小さい番号がまた 3 になりました。

深掘り本物の Linux では、もっと長い

本物の Linux で同じことをすると、strace は 50 行ほどになります（Debian で試したところ 48 行でした）。増えるのは、ほとんどが execve の直後の行です。

ターミナル
$ strace cat /etc/hostnameexecve("/usr/bin/cat", ["cat", "/etc/hostname"], 0x7ffd… /* 5 vars */) = 0brk(NULL)                               = 0x55d0c4b1e000openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3mmap(NULL, …, PROT_READ, MAP_PRIVATE|MAP_DENYWRITE, 3, 0) = 0x7f3a5be00000…（共有ライブラリを読み込んで配置する行が 30 行ほど）…openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3fstat(3, {st_mode=S_IFREG|0644, st_size=6, ...}) = 0read(3, "zukai\n", 262144)              = 6write(1, "zukai\n", 6)                  = 6read(3, "", 262144)                     = 0close(3)                                = 0close(1)                                = 0close(2)                                = 0exit_group(0)                           = ?+++ exited with 0 +++

前半は、プログラムが使う共有ライブラリ（libc）をメモリに読み込む作業です（第 18 章）。この本の小さな Linux には共有ライブラリの仕組みがないので、その部分がありません。後半の「開く、読む、書く、0 が返るまでくり返す、閉じる」という骨組みは、本物も同じです。本物の cat は、バッファが 262144 バイト（256 KiB）と大きくなっています。

10.5ls がしていること

次は ls です。ディレクトリの一覧は、どうやって作るのでしょうか。

ls notesstrace：システムコールも表示⌘↵
ls notes

ioctl の 2 行は、出力先が端末かどうかと、端末の幅を調べています（端末なら横に並べ、パイプやファイルなら 1 行に 1 つずつ出すためです）。本題は、そのあとの 4 行です。

  1. stat("notes", {st_mode=S_IFDIR|0755, …}) = 0 … notes が何者かを調べる。S_IFDIR なのでディレクトリ
  2. openat(AT_FDCWD, "notes", O_RDONLY|O_DIRECTORY) = 3 … ディレクトリを開く。ディレクトリも fd になる
  3. getdents64(3, … /* 4 entries */, 32768) = 144 … ディレクトリの中身（エントリ）を読む。4 個読めた
  4. close(3) = 0

getdents64（get directory entries）が、ディレクトリを読むシステムコールです。ディレクトリは read では読めず、専用のこれを使います。4 個というのは、ideas.txt、todo.txt と、.（自分）、..（親）です。ls は . で始まる名前を表示から除いているだけで、カーネルはいつも全部を返しています。

getdents64 が返すのは、名前と inode 番号（と種類）だけです。大きさや権限は入っていません。ls -l はどうしているのでしょうか。

ls -l notesstrace：システムコールも表示⌘↵
ls -l notes

getdents64 のあとに、lstat("notes/todo.txt", …) と lstat("notes/ideas.txt", …) が増えました。ls -l は、名前の一覧を手に入れたあと、ファイル 1 つにつき 1 回 lstat を呼んで、権限・持ち主・大きさ・時刻を聞いています（lstat は、シンボリックリンクをたどらない stat です）。さらに、uid を名前に直すために、最初のほうで /etc/passwd と /etc/group を開いて読んでいます。you という表示は、カーネルではなく ls がこのファイルを引いて作ったものです。

ファイルが 1 万個あるディレクトリで ls -l が遅くなるのは、このためです。ls だけなら getdents64 で済みますが、ls -l は 1 万回の lstat が要ります。

10.6失敗は -1 と errno で返る

システムコールは、失敗することがあります。ファイルがない、権限がない、ディスクが一杯。失敗したとき、カーネルはエラーの種類を表す番号を返します。この番号を errno（エラーナンバー）と呼びます。

ないファイルを開くエラーになる⌘↵
strace cat nope

openat(…) = -1 ENOENT (No such file or directory) の行を見てください。戻り値は -1（失敗）で、ENOENT が errno の名前、かっこの中がその説明文です。

そして次の行で、cat は write(2, "cat: nope: No such file or direc"..., 37) と、fd 2（標準エラー出力）にエラー文を書いています。見慣れた cat: nope: No such file or directory は、次のように組み立てられています。

cat: nope: No such file or directory~~~  ~~~~  ~~~~~~~~~~~~~~~~~~~~~~~~~|    |     errno（ENOENT）に対応する決まった文|    失敗した相手コマンドの名前

最後の部分は、コマンドが自分で考えた文ではありません。errno ごとに決まっている文です。だから、どのコマンドでも、どの Linux でも、同じ原因なら同じ文が出ます。エラー文の最後の部分を読めば、どのシステムコールがなぜ失敗したかの見当がつきます。

いくつかの失敗を、続けて見てみましょう。

いろいろな失敗エラーになる⌘↵
cat /home/alice/diary.txtmkdir notescat fruits.txt/xcat notesrmdir notes

それぞれの裏で失敗したシステムコールを、strace で確かめます。失敗の行には = -1 が入っているので、grep で拾えます。

失敗したシステムコールだけを拾う⌘↵
strace -o t.log cat /home/alice/diary.txt 2> /dev/null; grep ' = -1 ' t.logstrace -o t.log mkdir notes 2> /dev/null; grep ' = -1 ' t.logstrace -o t.log cat fruits.txt/x 2> /dev/null; grep ' = -1 ' t.logstrace -o t.log cat notes 2> /dev/null; grep ' = -1 ' t.logstrace -o t.log rmdir notes 2> /dev/null; grep ' = -1 ' t.log

cat notes だけ、失敗の場所が違うことに注目してください。ディレクトリを openat で開くのは成功し、そのあとの read が EISDIR で失敗しています。ディレクトリは開けるが、read では読めない（getdents64 を使う）、という前の節の話のとおりです。

EPERM と EACCES は、どちらも「許されていない」ですが、別物です。EACCES はファイルの権限ビットで断られたとき、EPERM は「そもそもその操作をする資格がない」ときです。

PID 1（init）は root のプロセスなので、you からシグナルは送れません（EPERM）。PID 9999 は、いません（ESRCH）。

EPIPE：読み手がいなくなった

EPIPE は、パイプならではのエラーです。yes は y を永遠に出し続けるコマンド、head -1 は 1 行読んだら終わるコマンドです。つなぐと、どうなるでしょうか。

yes | head -1strace：システムコールも表示⌘↵
yes | head -1

head が 1 行出して終わると、パイプの読む側の fd がすべて閉じられます。そこへ yes が write すると、戻り値は -1 EPIPE (Broken pipe) です。同時に、カーネルは yes に SIGPIPE というシグナルを送ります（--- SIGPIPE … --- の行）。SIGPIPE の既定の動作は「終了」なので、yes は +++ killed by SIGPIPE +++ で終わります。

無限に出力するコマンドをパイプにつないでも止まるのは、この仕組みのおかげです。「読み手がいないのに書き続ける」という無駄を、カーネルが止めてくれます。

ENOSYS：そんなシステムコールはない

システムコールは、カーネルの版が上がるたびに少しずつ増えます。新しいシステムコールを、それを知らない古いカーネルで呼ぶと、ENOSYS が返ります。プログラムは、ENOSYS を見て古いやり方に切り替えることがあります。

ターミナル
$ strace -e trace=clone3,clone ./programclone3({flags=CLONE_VM|…}, 88)          = -1 ENOSYS (Function not implemented)clone(child_stack=0x7f…, flags=CLONE_VM|…) = 12345

この本の小さな Linux は、本物の 400 個近いシステムコールのうち、およそ 80 個だけを持っています。メモリの mmap や brk（第 13 章）、ネットワークの socket（第 16 章）などは、その章で部品が入るまで ENOSYS を返します。

10.7ライブラリ関数とシステムコールは別物

C 言語でプログラムを書くとき、ふつうはシステムコールを直接は呼びません。printf や fopen のようなライブラリ関数を使います。これらは C の標準ライブラリ（libc。Linux では glibc など）の中にある、ふつうの関数です。ユーザーモードで動き、必要になったときに、中でシステムコールを呼びます。

C
#include <stdio.h> int main(void) {    printf("hello\n");   /* ライブラリ関数。カーネルは printf を知らない */    return 0;}
ライブラリ関数システムコール
例printf、fopen、fgets、malloc、strlenwrite、openat、read、mmap
動く場所ユーザーモード（プログラムの一部）カーネルモード
呼ぶ手間ふつうの関数呼び出し（速い）モードの切り替えが要る（遅い）
strace に出ない出る

strlen（文字列の長さを数える）のように、システムコールを 1 回も呼ばないライブラリ関数もたくさんあります。逆に、write という名前の C の関数も libc にありますが、これは「システムコールの write を呼ぶだけ」の薄い包みです。

バッファ：システムコールを減らす工夫

システムコールは、モードの切り替えがあるぶん、ふつうの関数呼び出しより何十倍も時間がかかります。そこでライブラリは、出力をバッファにためて、まとめて 1 回の write で出します。

seq 1 2000 は、1 から 2000 までを 1 行ずつ出すコマンドです。2000 行ありますが、write は何回でしょうか。

2000 行を、何回の write で出すか⌘↵
strace -o t.log seq 1 2000 > /dev/nullgrep -c '^write' t.loggrep '^write' t.log

3 回です。4096 バイトたまるごとに 1 回書き、最後に残りの 701 バイトを書いています（合計 8893 バイト）。2000 回のシステムコールが、3 回で済みました。

反対に、バッファを使わないと、どうなるでしょうか。シェルの read は、1 行読むために、1 バイトずつ read システムコールを呼びます（行の終わりより先を読みすぎると、次のコマンドが読むぶんを取ってしまうからです）。

1 バイトずつ読むと⌘↵
wc -c < fruits.txtstrace -o t.log sh -c 'while read line; do :; done < fruits.txt'grep -c '^read' t.logstrace -o t.log cat fruits.txt > /dev/nullgrep -c '^read' t.log

58 バイトのファイルを読むのに、シェルの while read は 59 回（58 バイト + 終わりの確認 1 回）、cat は 2 回です。シェルのループで大きなファイルを 1 行ずつ処理すると遅いのは、このためです。grep や sort のような専用のコマンドに任せるほうが、桁違いに速くなります。

注意本物との違い：バッファの大きさと、出すタイミング
  • 本物の libc は、出力先が端末のときは 1 行ごとに write し（行バッファ）、ファイルやパイプのときはバッファが一杯になるまでためます。この本の小さな Linux のコマンドは、端末でも 4096 バイトたまるか終了するまでためます
  • バッファの大きさも違います。本物の seq 1 2000 > /dev/null は、8192 バイトと 701 バイトの 2 回の write になります
  • プログラムが異常終了すると、バッファにたまっていて、まだ write されていない出力は消えます。「printf したはずの文が出ない」ときは、これを疑います

10.8数えて比べる

本物の strace には、システムコールを名前ごとに数えて表にする -c というオプションがあります。

ターミナル
$ strace -c ls / > /dev/null% time     seconds  usecs/call     calls    errors syscall------ ----------- ----------- --------- --------- ---------------- 23.98    0.000117           5        21           mmap  7.58    0.000037           5         7           openat  7.17    0.000035           5         6           read  6.56    0.000032          16         2           getdents64…100.00    0.000488           5        96        10 total

小さな Linux の strace に -c はありませんが、同じことは第 5 章の道具でできます。記録の各行から、最初の ( より前（システムコールの名前）を切り出して、数えます。

ls -l /etc のシステムコールを数える⌘↵
strace -o t.log ls -l /etc > /dev/nullgrep -v '^+++' t.log | cut -d'(' -f1 | sort | uniq -c | sort -rn

いちばん多いのは lstat です。/etc の中のファイル 1 つにつき 1 回（と、/etc 自身に 1 回）、という前の節の話が、数字で見えます。

-f をつけると、子プロセスも追えます。シェルのループの中で cat を 3 回起動してみましょう。

-f で子プロセスも追う⌘↵
strace -f -o t.log sh -c 'for i in 1 2 3; do cat memo.txt; done' > /dev/nullgrep -c 'clone(' t.loggrep -c 'execve(' t.logwc -l < t.log

clone（fork）が 3 回、execve が 4 回（最初の sh と、cat が 3 回）です。同じ 3 つを 1 回の cat に渡した場合と比べます。

1 回の cat で済ませると⌘↵
strace -f -o t.log cat memo.txt memo.txt memo.txt > /dev/nullwc -l < t.log

行数は、およそ半分になりました。プロセスを 1 つ作る（clone、execve、wait4）のは、ファイルを 1 つ開いて読むより、ずっと手間がかかります。この小さな Linux では差は数十行ですが、本物では execve のたびに共有ライブラリの読み込み（先ほどの 30 行あまり）もくり返されます。「ループの中でコマンドを何千回も起動するスクリプトは遅い」理由が、ここにあります。

コツstrace は、調べものの最初の一手

プログラムが「設定ファイルを読んでくれない」「なぜか Permission denied になる」「止まったまま動かない」。そういうとき、strace は最初の手がかりになります。openat の行を見れば、どのパスを開こうとして失敗したかがわかります。最後の行が read(0, で止まっていれば、入力を待っています。プログラムのソースコードがなくても、カーネルとの会話は必ず見えます（第 20 章）。

要点この章のまとめ
  • CPU にはユーザーモードとカーネルモードがある。ふつうのプログラムはユーザーモードで動き、装置にもほかのプロセスのメモリにも直接は触れない
  • システムコールは、プログラムがカーネルに仕事を頼む決まった入口。番号と引数を置いて、モードを切り替える命令（x86-64 の syscall、RISC-V の ecall）を実行する
  • strace は、システムコールを 名前(引数) = 戻り値 の形で 1 行ずつ見せる。-o でファイルへ、-e trace= で絞り、-f で子プロセスも追う
  • cat は openat → read → write を、read が 0 を返すまでくり返して close。ls は getdents64 でディレクトリを読み、-l ならファイルごとに lstat を呼ぶ
  • 失敗すると戻り値は -1 で、原因は errno（ENOENT、EACCES、EEXIST …）で伝わる。エラー文の最後の部分は、errno ごとに決まった文
  • 読み手のいないパイプに書くと EPIPE と SIGPIPE。カーネルにないシステムコールは ENOSYS
  • printf などのライブラリ関数は、ユーザーモードで動くふつうの関数。バッファにためてから write を呼び、システムコールの回数を減らす
  • システムコールの数を数えると、プログラムの手間が見える。1 バイトずつの read や、ループの中でのコマンドの起動は高くつく

10.9確認問題

strace を使って、コマンドの中をのぞきます。どの問題も、新しい Linux から始まります。

問 1

ls -l が呼ぶ lstat を数える

正解済み

ls -l notes が lstat を何回呼ぶかを調べて、その数だけを表示してください。ls 自身の出力は表示しません。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番も見る）
ヒント

strace -o ファイル で記録して、grep -c で行を数えます。ls の出力は > /dev/null で捨てます。

模範解答
strace -o t.log ls -l notes > /dev/nullgrep -c '^lstat' t.log
問 2

失敗したシステムコールを突き止める

正解済み

cat box/key.txt は失敗します。strace を使って、失敗したシステムコールの行（= -1 を含む行）だけを表示してください。cat のエラー文は表示しません。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番も見る）
ヒント

strace -o t.log コマンド 2> /dev/null で記録だけを残し、grep ' = -1 ' t.log で失敗の行を拾います。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

mkdir boxecho 'open sesame' > box/key.txtchmod 000 box
模範解答
strace -o t.log cat box/key.txt 2> /dev/nullgrep ' = -1 ' t.log
問 3

シェルの read は何回 read を呼ぶか

正解済み

sh -c 'while read x; do :; done < numbers.txt' が、read システムコールを何回呼ぶかを調べて、その数だけを表示してください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番も見る）
ヒント

記録の中で、行の頭が read の行を数えます。答えは「ファイルのバイト数 + 1」になるはずです。

模範解答
strace -o t.log sh -c 'while read x; do :; done < numbers.txt'grep -c '^read' t.log
問 4

スクリプトが起動するプログラムの数

正解済み

count.sh は、パイプでいくつかのコマンドをつないだスクリプトです。sh count.sh を、子プロセスも含めて strace で追い、execve が何回呼ばれたかを表示してください。スクリプトの出力は表示しません。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番も見る）
ヒント

-f をつけないと、最初の sh の execve しか記録されません。答えは「sh 自身の 1 回 + 起動したコマンドの数」になるはずです。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

echo 'cat fruits.txt | sort | uniq -c | sort -rn | head -3' > count.sh
模範解答
strace -f -o t.log sh count.sh > /dev/nullgrep -c 'execve(' t.log
