第 9 章

ファイルディスクリプタ

プログラムは、開いたファイルを 0、1、2、3 … という小さな整数で呼びます。この番号がファイルディスクリプタです。番号の先にあるカーネルの 3 段の表を見て、リダイレクトとパイプが「番号のつなぎ替え」にすぎないことを、strace と /proc で確かめます。

9.1開いたファイルは、小さな整数で呼ばれる

第 5 章で、コマンドには 3 つの出入口があると学びました。標準入力、標準出力、標準エラー出力です。そして 2> err.txt のように、標準エラー出力を「2」という番号で呼びました。この番号は、いったい何の番号でしょうか。

答えは、ファイルディスクリプタ（file descriptor。以下 fd）です。fd は、プロセスが「いま開いているもの」につけた通し番号で、0 から始まる小さな整数です。プログラムが read や write をカーネルに頼むときは、ファイルの名前ではなく、この番号で相手を指定します。

fd名前ふつうのつなぎ先
0標準入力（stdin）端末（キーボード）
1標準出力（stdout）端末（画面）
2標準エラー出力（stderr）端末（画面）

0、1、2 に特別な仕組みはありません。「プログラムは 0 から読み、1 に結果を書き、2 にエラーを書く」という約束があるだけです。カーネルから見れば、どれもただの番号です。

自分の fd を見る

プロセスがいま持っている fd は、/proc/PID/fd というディレクトリで見られます。$$ はシェル自身の PID でした（第 6 章）。シェルの fd を見てみましょう。

シェルが開いているもの⌘↵
ls -l /proc/$$/fd

名前が番号になっているシンボリックリンクが並びます。矢印の先が、その fd のつなぎ先です。0、1、2 はどれも /dev/pts/0 を指しています。これが、いま使っている端末です。端末も、ファイルと同じように「開いて、読み書きするもの」として扱われています。

255 は、シェルが自分のために取っておいた端末の控えです（本物の bash も、同じ 255 番を使います）。あとで出てくるリダイレクトで fd 0〜2 をつなぎ替えても、シェル自身は端末を見失わずに済みます。

メモ/proc/self

/proc/self は、「これを読んでいるプロセス自身」の /proc/PID を指す特別なリンクです。ls -l /proc/self/fd と打つと、シェルではなく、ls 自身の fd が見えます。この章では、これを何度も使います。

ls 自身の fd⌘↵
ls -l /proc/self/fd

0、1、2 は、シェルと同じ端末です。子プロセスは、親の fd をそのまま受け継ぐからです（あとの節で確かめます）。3 は、ls が一覧を作るために開いた /proc/…/fd というディレクトリそのものです。ディレクトリも、開けば fd がつきます。

9.2open は、空いているいちばん小さい番号を返す

fd は、ファイルを開いたときに決まります。開くのは openat というシステムコール（カーネルへの頼みごと。次の章でくわしく見ます）の仕事です。cat がファイルを開く様子を、strace で見てみましょう。実行ブロックの「strace」の欄に、cat が呼んだシステムコールが 1 行ずつ出ます。

cat が呼ぶシステムコールstrace：システムコールも表示⌘↵
cat fruits.txt > /dev/null

2 行目の openat(AT_FDCWD, "fruits.txt", O_RDONLY) = 3 を見てください。= の右が戻り値で、これが fd です。cat は「fruits.txt を読み取り専用（O_RDONLY）で開いてください」と頼み、カーネルは「3 番です」と答えました。

そのあとの行は、すべて番号で話が進みます。

  • read(3, …, 4096) = 58 … 3 番から最大 4096 バイト読む。58 バイト読めた
  • write(1, …, 58) = 58 … 1 番（標準出力）に 58 バイト書く
  • read(3, "", 4096) = 0 … もう一度読むと 0 バイト。ファイルの終わり（EOF）
  • close(3) = 0 … 3 番を閉じる

なぜ 3 だったのでしょうか。カーネルは、空いているいちばん小さい番号を返す決まりだからです。0、1、2 は埋まっているので、最初に開いたものは 3 になります。この単純な決まりが、あとでリダイレクトの仕組みに効いてきます。

シェルで fd を開く：exec 3<

シェルにも、好きな番号で fd を開く書き方があります。exec にコマンドを書かず、リダイレクトだけを書きます。

fd 3 で fruits.txt を開く⌘↵
exec 3< fruits.txtls -l /proc/$$/fd

シェルの fd 表に 3 が増え、/home/you/fruits.txt を指しています。開いた fd からは、<&3（「標準入力を fd 3 と同じものにする」）で読めます。read は 1 行読んで変数に入れる組み込みコマンドでした。

fd 3 から 1 行ずつ読む⌘↵
read line <&3echo "1 回目：$line"read line <&3echo "2 回目：$line"

1 回目は apple、2 回目は banana です。2 回目が先頭に戻らないのは、カーネルが「どこまで読んだか」を覚えているからです。この覚え書きが、次の節の主役です。

書き方意味
exec 3< filefile を読み取り用に開いて、fd 3 にする
exec 3> filefile を書き込み用に開いて（中身は空にして）、fd 3 にする
exec 3>> filefile を追記用に開いて、fd 3 にする
コマンド <&3コマンドの標準入力を fd 3 と同じものにする
コマンド >&3コマンドの標準出力を fd 3 と同じものにする
exec 3<&-fd 3 を閉じる

開いていない番号を使うと、エラーになります。

開いていない fdエラーになる⌘↵
echo hi >&7

Bad file descriptor は、カーネルのエラー番号 EBADF の文です。「その番号の fd は開いていません」という意味です。

9.3番号の先にある 3 段の表

fd の番号から、ディスクの上のファイルまでは、カーネルの中で 3 段になっています。

  1. fd 表（プロセスごと）… fd の番号 → 「開いているファイル」への矢印。それだけの表
  2. オープンファイル記述（open file description。システム全体で共有）… open 1 回につき 1 つ作られる。いまの位置（オフセット）と、開いたときのフラグ（読み取り専用か、追記か、など）を持つ
  3. inode（アイノード）… ファイルそのもの。大きさ、権限、データの場所を持つ（第 11 章）

「オープンファイル記述」は耳慣れない言葉ですが、POSIX の用語です。この本では、短くファイル記述と呼びます。ファイル「ディスクリプタ」（番号）と、ファイル「記述」（カーネルの中の覚え書き）は別物です。

2 段目の中身は、/proc/PID/fdinfo/番号 で見られます。

fd 3 のファイル記述⌘↵
cat /proc/$$/fdinfo/3

pos: 13 が、いまの位置です。apple と改行で 6 バイト、banana と改行で 7 バイト。合わせて 13 バイト読んだので、次の read は 14 バイト目の cherry から始まります。flags は開いたときのフラグ（8 進数）で、00 は O_RDONLY です。ino は inode の番号です。

メモこのサイトの Linux だけの行

ofd（ファイル記述の通し番号）と refs（そのファイル記述を指している fd の数）の 2 行は、本物の Linux にはありません。本物ではファイル記述に番号がなく、外から見分ける手段が限られるので、この本のために足してあります。

位置を持っているのが「fd 表」でも「inode」でもなく、真ん中のファイル記述だ、というところが大事です。同じファイルをもう一度開くと、ファイル記述がもう 1 つでき、位置は別々に進みます。

同じファイルを 2 回開くと、位置は別々⌘↵
exec 4< fruits.txtread line <&4echo "fd 4 の 1 行目：$line"grep -E 'pos|ofd' /proc/$$/fdinfo/3 /proc/$$/fdinfo/4

fd 4 は先頭の apple から読み始めました。fd 3 の pos は 13 のまま、fd 4 の pos は 6 です。ofd の番号も違います。inode は同じ fruits.txt でも、ファイル記述は 2 つあります。

反対に、1 つのファイル記述を 2 つの fd から指すこともできます。exec 5<&3 は、「fd 5 を、fd 3 と同じファイル記述を指すようにする」という意味です。

fd を複製すると、位置は共有⌘↵
exec 5<&3read line <&5echo "fd 5 から：$line"grep -E 'pos|ofd' /proc/$$/fdinfo/3 /proc/$$/fdinfo/5exec 4<&-exec 5<&-

fd 5 から読んだのに、出てきたのは 3 行目の cherry です。fd 3 と fd 5 は ofd が同じで、pos も一緒に 20 へ進みました。fd を複製しても、できるのは矢印だけで、ファイル記述は増えません。

この「矢印の複製」をするシステムコールが dup2 です。そして、リダイレクトの正体は、この dup2 です。

9.4リダイレクトの正体は dup2

echo hi > out.txt と書くと、echo の出力がファイルに入ります。けれども echo は、出力先がファイルに変わったことを知りません。いつもどおり fd 1 に書いているだけです。シェルが、fd 1 の指す先を、先に取り替えているのです。

シェル自身が呼ぶシステムコールも含めて見てみましょう（このブロックは、シェルのシステムコールも表示する設定にしてあります）。

echo hi > out.txt の裏側strace：システムコールも表示⌘↵
echo hi > out.txt

上から順に読みます（最後の wait4 は、終わった子プロセスがいないかの確認で、ここでは関係ありません）。

システムコールしていること
openat(…, "out.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 4out.txt を書き込み用に開く。なければ作り（O_CREAT）、あれば空にする（O_TRUNC）。fd 3 は fruits.txt で使用中なので、空いているいちばん小さい 4 になった
fcntl(1, F_DUPFD_CLOEXEC, 10) = 10いまの fd 1（端末）を、10 番以降の空き番号に控えておく
dup2(4, 1) = 1fd 1 を、fd 4 と同じファイル記述を指すように取り替える
close(4) = 0fd 4 はもう要らないので閉じる。out.txt は fd 1 から届く
write(1, "hi\n", 3) = 3echo の本体。いつもどおり fd 1 に書く。行き先は out.txt
dup2(10, 1) = 1控えから fd 1 を端末に戻す
close(10) = 0控えを閉じる

dup2(古い fd, 新しい fd) は、「新しい fd を、古い fd と同じものを指すようにする」システムコールです。新しい fd がすでに何かを指していたら、先にそれを閉じます。

echo はシェルの組み込みコマンドなので、シェルは自分の fd 1 を取り替え、終わったら元に戻しました。外部コマンドの場合は、もっと単純です。fork で作った子プロセスの中で取り替えてから execve するので、元に戻す必要がありません。

外部コマンドのリダイレクトstrace：システムコールも表示⌘↵
cat fruits.txt > out.txt

行が多いですが、[pid …] がついた子プロセスの行のうち、次の 4 行を探してください。rt_sigaction や setpgid は、シグナルとジョブ（第 8 章）の準備です。

  1. openat(AT_FDCWD, "out.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) … 子が out.txt を開く
  2. dup2(…, 1) = 1 … fd 1 を out.txt に取り替える
  3. close(…) … 余った fd を閉じる
  4. execve("/usr/bin/cat", …) … ここで初めて cat になる

cat が動き出したときには、もう fd 1 は out.txt を指しています。execve でプログラムが入れ替わっても、fd 表はそのまま残るからです。「fork と exec が別々になっている」という Unix の作り（第 7 章）は、このすき間でリダイレクトを仕込むためにあります。

仕込んだ結果は、/proc/self/fd で確かめられます。3 つの出入口を全部つなぎ替えて、ls に自分の fd を報告させます。

3 つともつなぎ替える⌘↵
ls -l /proc/self/fd < fruits.txt > out.txt 2> err.txtcat out.txt

0 は fruits.txt、1 は out.txt、2 は err.txt になっています。ls 本人は何も知らずに、fd 1 に一覧を書きました。3 は、さきほどシェルで開いた fd 3 が、子プロセスの ls にそのまま受け継がれたものです（この話は、あとの節でします）。4 が、ls が自分で開いたディレクトリです。

9.52>&1 は、書く順番で意味が変わる

2>&1 は「fd 2 を、いまの fd 1 と同じものを指すようにする」です。つまり dup2(1, 2) です。「いまの」が大事で、シェルはリダイレクトを左から順に実行します。

存在するファイルと、しないファイルを ls に渡して、出力とエラーの両方を出させてみます。

> out.txt 2>&1（両方ファイルへ）エラーになる⌘↵
ls fruits.txt nope > out.txt 2>&1cat out.txt

端末には何も出ず、エラー文と fruits.txt の両方が out.txt に入りました。順番を逆にすると、結果が変わります。

2>&1 > out.txt（エラーは端末に残る）エラーになる⌘↵
ls fruits.txt nope 2>&1 > out.txtecho "--- out.txt の中身 ---"cat out.txt

今度は、エラー文が端末に出て、out.txt には fruits.txt だけが入りました。矢印の動きを 1 手ずつ追うと、理由がわかります。

> out.txt 2>&12>&1 > out.txt
最初1 → 端末、2 → 端末1 → 端末、2 → 端末
1 手目> out.txt：1 → out.txt2>&1：2 → 端末（いまの 1 と同じ。変わらない）
2 手目2>&1：2 → out.txt（いまの 1 と同じ）> out.txt：1 → out.txt
結果1 も 2 も out.txt1 は out.txt、2 は端末のまま

2>&1 は「2 を 1 に結びつける」のではありません。その瞬間の 1 の行き先を、2 に写すだけです。あとで 1 を動かしても、2 はついてきません。

コツエラーだけをパイプに流す

この性質を使うと、標準エラー出力だけを次のコマンドに渡せます。コマンド 2>&1 > /dev/null | 次のコマンド と書きます。パイプは最初につながれるので、2>&1 の時点の fd 1 はパイプです。そのあとで fd 1 だけを /dev/null（何を書いても捨てられる場所。第 12 章）へ向けます。

エラーの行数だけを数える⌘↵
ls fruits.txt nope poem.txt zzz 2>&1 > /dev/null | wc -l

nope と zzz の 2 つがないので、エラー文は 2 行です。

9.6fork すると、ファイル記述を親子で共有する

fork は、プロセスをまるごと複製します（第 7 章）。fd 表も複製されます。ただし、複製されるのは矢印だけです。矢印の先のファイル記述は複製されず、親と子が同じものを指します。

ということは、位置（オフセット）も親子で共有されるはずです。確かめましょう。丸かっこ ( … ) は、中身を子プロセス（サブシェル）で実行する書き方でした。fd 3 はいま、3 行目まで読んだところです。

子が読むと、親の位置も進む⌘↵
( read x <&3; echo "子が読んだ：$x" )read y <&3echo "親が読んだ：$y"grep -E 'pos|refs' /proc/$$/fdinfo/3

子が 4 行目の apple を読み、そのあと親が読むと、5 行目の orange が出ました。親は 4 行目を読んでいないのに、位置が進んでいます。子が進めた位置を、親も見ているからです。

共有は、ふだんから役に立っている

この共有は、変わった実験のためだけのものではありません。次の例がうまく動くのは、位置を共有しているおかげです。

2 つのコマンドの出力を、1 つのファイルに⌘↵
{ echo "1 行目"; ls notes; echo "最後の行"; } > list.txtcat list.txt

{ …; } > list.txt は、list.txt を 1 回だけ開き、中のコマンド全部がその fd 1 を受け継ぎます。ls は子プロセスですが、親と同じファイル記述に書くので、位置が進み、次の echo はその続きに書きます。上書きし合うことはありません。

コマンドごとに > を書くと、そのたびに開き直し（O_TRUNC で空にし）、位置は 0 に戻ります。

開き直すと、前の中身は消える⌘↵
echo "1 行目" > list.txtecho "最後の行" > list.txtcat list.txt

>>（追記）が要るのは、こうして開き直すときです。>> で開くと O_APPEND というフラグがつき、書くたびに位置がファイルの終わりへ動きます。

9.7パイプは、2 つの fd の組

パイプ | も、fd のつなぎ替えでできています。pipe というシステムコールは、カーネルの中に小さなバッファ（一時的な置き場。この Linux でも本物でも 64 KiB）を作り、その両端を 2 つの fd として返します。片方は読む専用、もう片方は書く専用です。

echo a | cat の裏側strace：システムコールも表示⌘↵
echo a | cat

長いので、要点だけを拾います。

  1. pipe([4, 5]) = 0 … シェルがパイプを作る。fd 4 が読む側、fd 5 が書く側（fd 3 は fruits.txt で使用中です）
  2. clone(…) が 2 回 … 子を 2 つ作る（clone は fork の本名です）。どちらの子も、fd 4 と fd 5 を受け継ぐ
  3. 左の子：dup2(5, 1) … 標準出力を、パイプの書く側にする。そのあと 5 と 4 を閉じる
  4. 右の子：dup2(4, 0) … 標準入力を、パイプの読む側にする。そのあと execve で cat になる
  5. 親のシェル：close(5)、close(4) … 自分は使わないので、両方閉じる

リダイレクトと同じ手口です。fork で fd を受け継がせ、dup2 で 0 や 1 に付け替え、余りを閉じる。cat は、自分の fd 0 がパイプだとは知らずに読みます。

パイプにつながった fd は、/proc ではこう見えます。

パイプにつながった fd⌘↵
ls -l /proc/self/fd | cat

ls の fd 1 が pipe:[番号] になっています（3 は、ここでもシェルから受け継いだ fruits.txt です）。パイプには名前（パス）がないので、こういう表示になります。

余った fd を閉じないと、終わらない

手順の 3〜5 で、使わない fd をこまめに閉じていました。これは行儀の問題ではありません。パイプを読む側が「終わり（EOF）」を受け取るのは、書く側の fd が、どのプロセスからも全部閉じられたときだけだからです。

書き手がいるあいだ、読み手は待つ⌘↵
sleep 1 | catecho "cat が終わった"

sleep は何も書きません。それでも cat は 1 秒待ちます。sleep がパイプの書く側（fd 1）を持っているあいだは、「まだ何か来るかもしれない」からです。sleep が終わって fd が閉じられると、cat の read が 0 を返し、cat も終わります。もしシェルが、自分の持っている書く側の fd を閉じ忘れたら、書き手が残り続け、cat は永遠に終わりません。

9.8exec をまたぐ fd、またがない fd

execve でプログラムが入れ替わっても fd 表は残る、と書きました。シェルで開いた fd 3 も、そこから起動したコマンドに受け継がれます。別の sh を起動して、その fd を見てみましょう。

子のプログラムにも fd 3 がある⌘↵
sh -c 'ls -l /proc/$$/fd'

新しい sh にも、fd 3（fruits.txt）があります。頼んでいないのに、開いたままのファイルが渡っています。一方、255 はありません。

受け継がれたくない fd には、O_CLOEXEC（close-on-exec。「exec のときに閉じる」）という印をつけます。印のついた fd は、execve の瞬間にカーネルが自動で閉じます。シェルの 255 番や、リダイレクトのときに作った控え（fcntl(1, F_DUPFD_CLOEXEC, 10) の CLOEXEC）には、この印がついています。

255 番には close-on-exec の印がある⌘↵
grep flags /proc/$$/fdinfo/255 /proc/$$/fdinfo/3

255 番の flags には 02000000 のビットが立っています。これが O_CLOEXEC です。fd 3 にはありません。

注意fd の漏れ

長く動くプログラム（サーバなど）が、開いた fd を子プロセスに漏らすと、困ったことが起きます。子が持ち続けるかぎり、ファイルやパイプやソケットは閉じられません。「パイプの相手が終わったのに EOF が来ない」「ポートが空かない」といった不具合の原因になります。そのため、今のプログラムは、開くときに最初から O_CLOEXEC をつけるのがふつうです。

使い終わった fd は閉じます。

fd 3 を閉じるstrace：システムコールも表示⌘↵
exec 3<&-

exec 3<&- は、close(3) そのものです。

9.9消したファイルを、開いたまま読む

3 段の表から、もう 1 つ不思議な性質が出てきます。開いているファイルは、消しても読めるのです。

開いてから、消すエラーになる⌘↵
printf 'とても大事なデータ\n2 行目\n' > precious.txtexec 4< precious.txtrm precious.txtls precious.txt

rm は成功し、ls は「そんなファイルはない」と言っています。では、fd 4 はどうなったでしょうか。

fd 4 は生きている⌘↵
ls -l /proc/$$/fdcat <&4

fd 4 の先は /home/you/precious.txt (deleted) と表示されます。そして、cat <&4 で中身が全部読めました。

rm が消したのは、ディレクトリにあった「precious.txt という名前」です。ファイルの本体（inode とデータ）は、名前がなくなっても、それを指すファイル記述が残っているあいだは消されません。最後の fd が閉じられたときに、初めて本体が解放されます。くわしい仕組みは第 11 章で見ます。

/proc/PID/fd/番号 は、ただの表示ではなく、そのファイル記述への入口としても働きます。別のプロセスが消してしまったファイルを、ここから救い出せます。

/proc から救い出す⌘↵
cat /proc/$$/fd/4 > rescued.txtcat rescued.txt

lsof：だれが何を開いているか

lsof（list open files）は、プロセスが開いているファイルを一覧にするコマンドです。中身は、/proc/PID/fd を読みやすく並べたものです。

シェルが開いているファイルの一覧⌘↵
lsof -p $$exec 4<&-
列意味
FDfd の番号と、開き方（r 読み取り、w 書き込み、u 両方）。cwd はカレントディレクトリ、rtd はルートディレクトリ、txt は実行中のプログラム本体
TYPEREG 通常のファイル、DIR ディレクトリ、CHR キャラクタデバイス（端末など）
SIZE/OFF大きさ、または位置
NODEinode の番号
NAMEパス。消されていれば (deleted)

4r の行に (deleted) がついています。実務では、「ファイルを消したのにディスクの空きが増えない」ときに、lsof でこの印を探します（第 11 章と第 20 章）。カレントディレクトリやプログラム本体も、fd と同じように「使用中」として数えられていることもわかります。

注意本物との違い
  • 本物の Linux の ls -l /proc/PID/fd は、読み取り専用の fd を lr-x------、書き込み専用を l-wx------ と表示して、開き方がわかるようになっています。このサイトの Linux では、どれも lrwx------ と表示されます
  • /proc/PID/fdinfo の ofd と refs の行は、このサイトの Linux だけのものです
  • 本物の strace には、シェル自身を追うための「strace="all"」のような設定はありません。本物では strace -f sh -c '…' のようにして、シェルごと追います
要点この章のまとめ
  • ファイルディスクリプタ（fd）は、プロセスが開いているものにつけた小さな整数。0 = 標準入力、1 = 標準出力、2 = 標準エラー出力は約束にすぎない。/proc/PID/fd で見られる
  • open は、空いているいちばん小さい番号を返す。そのあとの read、write、close は、すべて番号で相手を指す
  • 番号の先は 3 段。fd 表（プロセスごと）→ ファイル記述（位置とフラグ。open 1 回につき 1 つ）→ inode（ファイル本体）
  • リダイレクトの正体は dup2。シェルが fork と execve のあいだで fd 0・1・2 の指す先を取り替える。コマンド本人は何も知らない
  • 2>&1 は「いまの fd 1 の行き先を fd 2 に写す」。左から順に実行されるので、> file 2>&1 と 2>&1 > file は結果が違う
  • fork は fd 表を複製するが、ファイル記述は親子で共有する。だから位置も共有される
  • パイプは pipe が返す 2 つの fd の組。書く側の fd が全部閉じられると、読む側に EOF が届く
  • fd は execve をまたいで受け継がれる。受け継がせたくない fd には O_CLOEXEC をつける
  • ファイルを消しても、開いているファイル記述があるあいだは本体が残る。lsof で (deleted) を探せる

9.10確認問題

この章の内容を、自分でコマンドを打って確かめます。どの問題も、新しい Linux（この章の本文で作ったファイルはない状態）から始まります。

問 1

fd 3 から 3 行目を読む

正解済み

fruits.txt を fd 3 で開き、read を使って 3 行目まで読み進めて、3 行目だけを表示してください。

exec 3< fruits.txt
⌘↵標準出力で判定（行の順番も見る）
ヒント

read 変数 <&3 を 1 回実行するたびに、ファイル記述の位置が 1 行ぶん進みます。

模範解答
exec 3< fruits.txtread a <&3read a <&3read a <&3echo "$a"
問 2

出力とエラーを 1 つのファイルに

正解済み

ls fruits.txt nope poem.txt を実行し、標準出力と標準エラー出力の両方を all.txt に入れてください。端末には何も出ないようにします。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

リダイレクトは左から順に実行されます。先に fd 1 を all.txt に向け、そのあとで fd 2 を「いまの fd 1」に合わせます。

確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

cat /home/you/all.txt
模範解答
ls fruits.txt nope poem.txt > all.txt 2>&1
問 3

エラーの行数だけを数える

正解済み

ls fruits.txt nope poem.txt zzz memo.txt qqq が標準エラー出力に出す行数を表示してください。標準出力の行は数えません。wc -l を使います。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番も見る）
ヒント

パイプにつないだあとで、2>&1 で fd 2 をパイプに向け、それから fd 1 だけを /dev/null に向けます。順番が逆だと、エラーも /dev/null に行ってしまいます。

模範解答
ls fruits.txt nope poem.txt zzz memo.txt qqq 2>&1 > /dev/null | wc -l
問 4

消されたファイルを救い出す

正解済み

sleep が、secret.txt を標準入力として開いたまま、バックグラウンドで動いています。ところが、secret.txt はもう消されてしまいました。sleep の fd から中身を取り出して、rescued.txt に保存してください。sleep の PID は、$! か jobs -p か ps でわかります。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

標準入力は fd 0 です。/proc/PID/fd/0 を cat すれば、そのファイル記述から中身を読めます。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

printf 'password=tanuki42\n' > secret.txtsleep 1000 < secret.txt &rm secret.txt
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

cat /home/you/rescued.txt
模範解答
cat /proc/$!/fd/0 > rescued.txt
