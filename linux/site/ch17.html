起動と init

電源を入れてからプロンプトが出るまでに、何が起きているのでしょうか。ファームウェア、ブートローダ、カーネル、そして最初のプロセス PID 1 へと、バトンが渡っていきます。dmesg で起動の記録を読み、自分でサービスを書いて起こし、殺しても生き返る様子と、再起動で何が残るかを確かめます。

17.1電源を入れてから、PID 1 まで

第 7 章で、すべてのプロセスは fork で生まれる、と学びました。親をたどっていくと、最後は PID 1 の init に行き着きます。では、その init はだれが起動したのでしょうか。さらに、その前のカーネルは、だれがメモリに読み込んだのでしょうか。

電源を入れた瞬間、メモリは空です。カーネルはディスクの上のファイルで、まだ動いていません。「ファイルを読む」という仕事をしてくれるカーネルがいないのに、カーネルのファイルを読まなければなりません。この問題を、小さなプログラムが、次の少し大きなプログラムを読み込むというリレーで解きます。自分の靴ひも（bootstrap）を引っぱって自分を持ち上げる、というたとえから、ブート（boot）と呼ばれます。

順に見ていきます。

  1. ファームウェア。電源が入ると、CPU は決まった番地から命令を実行し始めます。そこにあるのが、基板のチップに書き込まれたファームウェアです。昔の PC では BIOS、今は UEFI と呼ばれます。メモリや装置を点検し（POST）、起動できるディスクを探して、そこにあるブートローダを読み込みます
  2. ブートローダ。Linux では GRUB がよく使われます。ファイルシステムを読める程度の小さなプログラムで、/boot にあるカーネルのファイル（vmlinuz-…）と initramfs をメモリに読み込み、カーネルにコマンドライン（起動時の引数）を渡して、制御を移します
  3. カーネル。ここからが Linux です。メモリの量を調べ、ページ表を作り、スケジューラ、VFS、ドライバを初期化します
  4. initramfs。カーネルは、まずメモリの上の小さなファイルシステムを仮のルートにして、その中の /init を実行します。この /init が、本当のルートのディスクに必要なドライバを読み込み、ディスクをマウントします
  5. init。本当のルートがマウントできたら、その中の /sbin/init が PID 1 として動き始めます。ここから先は、ふつうのプロセスの世界です

カーネルの置き場所と、渡されたコマンドラインは、動いている Linux から見られます。

カーネルのファイルと、起動時の引数⌘↵
ls /bootcat /proc/cmdline

root=/dev/sda1 が「本当のルートはこのディスク」という指定です。ro は、最初は読み取り専用でマウントする、という意味です。

深掘りinitramfs は、なぜ要るのか

カーネルがルートのディスクをマウントするには、そのディスクを読むドライバが要ります。ところが、ドライバのファイルは、そのディスクの中にあります。ディスクが暗号化されていたり、ネットワークの向こうにあったりすると、準備はもっと複雑です。そこで、必要なドライバと道具だけを詰めた小さなファイルシステムを、ブートローダがカーネルと一緒にメモリへ読み込んでおきます。これが initramfs（initial RAM filesystem）です。カーネル本体を小さく保ったまま、いろいろな機械で起動できます。

注意このサイトの Linux では

小さな Linux は、ブラウザの中のシミュレータです。ファームウェア、ブートローダ、initramfs は実際には動かず、「起動の記録の行」としてだけあります。カーネルが動き始めてから PID 1 が動き出すまでは、いつも 1 秒です。本物の機械では、ファームウェアだけで数秒かかることもあります。

17.2dmesg：カーネルの起動の記録

カーネルは、起動のあいだにしたことを、自分の中のバッファに 1 行ずつ書き残します。まだディスクもマウントしていないので、ファイルには書けないからです。このバッファを読むコマンドが dmesg です。

起動の記録の最初の部分⌘↵
dmesg | head -9

行の先頭の [ 0.012000] は、カーネルが動き始めてからの秒数です。1 行目にカーネルの版、2 行目にブートローダから受け取ったコマンドライン（さっき /proc/cmdline で見たもの）があります。そのあと、使えるメモリの量、CPU の数と続きます。

大事な節目だけを抜き出します。

initramfs からルートのマウント、init の起動まで⌘↵
dmesg | grep -E 'initramfs|Run /init|EXT4|init\['

上の図と見比べてください。

  • Trying to unpack rootfs image as initramfs... … initramfs をメモリの上に展開している
  • Run /init as init process … initramfs の中の /init を実行した
  • EXT4-fs (sda1): mounted filesystem … … 本当のルート（/dev/sda1、ext4）をマウントできた
  • init[1]: … で始まる行 … PID 1 が動き始めてからの記録。最後の行で、multi-user.target に着いたと言っています（この章の最後で説明します）

dmesg は、起動のときだけのものではありません。カーネルは、動いているあいだも、装置の抜き差しや、メモリ不足でプロセスを殺したこと（第 13 章）などをここに書きます。「機械の調子がおかしい」と思ったら、まず dmesg | tail を見ます。

メモ本物の Linux では

本物の dmesg は、数百行から数千行あります。また、多くのディストリビューションでは、ふつうのユーザーには dmesg を読ませません（dmesg: read kernel buffer failed: Operation not permitted）。カーネルの中の番地などが、攻撃の手がかりになるからです。そのときは sudo dmesg とします。

17.3PID 1 の役目

カーネルが自分で起動するプロセスは、PID 1 だけです。ほかのプロセスはすべて、PID 1 の子孫です。

最初のプロセス⌘↵
ps -p 1 -o pid,ppid,user,comm,argspstree -p

PID 1 の PPID は 0 です。親プロセスはいません。カーネルが直接作ったからです。いま打っているシェル（PID 2）も、init の子です。

PID 1 には、ほかのプロセスにない役目が 3 つあります。

  • システムを立ち上げる。必要なファイルシステムをマウントし、ホスト名を決め、サービス（常駐するプログラム）を起こし、ログインを受け付ける
  • サービスを見張る。起こしたサービスが死んだら、気づいて、必要なら起こし直す。止める、再起動するのも PID 1 の仕事
  • 孤児を引き取る。親をなくしたプロセスの親になり、終わったら回収する

3 つめは、第 7 章の「孤児と init」で見ました。もう一度、手短に確かめます。

親をなくしたプロセスは、PID 1 の子になる⌘↵
orphan 30ps -o pid,ppid,stat,comm

残った orphan の PPID が 1 です。30 秒後にこのプロセスが終わると、init が wait4 で回収するので、ゾンビは残りません。

注意PID 1 は、死んではいけない

PID 1 が終わると、孤児を引き取る者も、サービスを見張る者もいなくなります。本物の Linux では、PID 1 が終了するとカーネルは Kernel panic - not syncing: Attempted to kill init! と表示して、止まります。そのためカーネルは PID 1 を特別に守っていて、PID 1 が自分でハンドラを用意していないシグナルは、SIGKILL であっても届けません。root が kill -9 1 と打っても、何も起きません。

小さな Linux には、この保護がありません。 kill -9 1 は試さないでください（試してしまったら、ページ上部の「リセット」で戻せます）。

17.4systemd とサービス、unit ファイル

init というのは「PID 1 として動くプログラム」の役の名前で、中身はいくつか種類があります。今のほとんどのディストリビューション（Debian、Ubuntu、Fedora、Arch など）では、systemd が PID 1 です。/sbin/init は、systemd へのシンボリックリンクになっています。

systemd が管理する対象の 1 つ 1 つを unit（ユニット）と呼びます。いちばんよく使うのがサービス（常駐するプログラム）の unit で、名前.service というunit ファイルに、「何を、どう起動するか」を書きます。

用意されている unit ファイル⌘↵
systemctl list-unit-filescat /usr/lib/systemd/system/ticker.service

unit ファイルは、[節] と 名前=値 でできた、ただのテキストです。

節キー意味
[Unit]Description=人が読むための説明
[Service]ExecStart=起動するコマンド。絶対パスで書く（PATH は探さない）
Restart=終わったとき起こし直すか。no（既定）、on-failure（失敗したときだけ）、always（いつも）
RestartSec=起こし直すまでに待つ秒数
User=どのユーザーで動かすか（書かなければ root）
[Install]WantedBy=enable したとき、どの段階で自動的に起こすか

ticker は、10 秒ごとに 1 行書くだけの練習用のプログラムです。

unit ファイルの置き場所は 2 つあります。

  • /usr/lib/systemd/system/ … パッケージが置く。自分では書き換えない
  • /etc/systemd/system/ … その機械の管理者が置く。同じ名前のファイルがあれば、こちらが勝つ

「配られたものは /usr、自分の設定は /etc」という分け方は、第 3 章で見たディレクトリの役割そのままです。

歴史SysV init から systemd へ

2010 年ごろまでの Linux の init は、Unix System V の流れをくむ SysV init でした。サービスごとに /etc/init.d/名前 というシェルスクリプトがあり、init はそれを番号の順に 1 つずつ start の引数つきで実行するだけでした。単純ですが、起動が遅い（1 つずつ順番に実行する）、サービスが死んでも気づかない、スクリプトの書き方がばらばら、という弱点がありました。2010 年に登場した systemd は、起動の手順をスクリプトではなく宣言（unit ファイル）で書かせ、依存関係を見て並行に起こし、起こしたプロセスを自分の子として見張ります。「PID 1 が多くを抱えすぎる」という批判もあり、大きな論争になりましたが、2015 年ごろまでに主なディストリビューションが採用しました。

注意このサイトの Linux では

小さな Linux の PID 1 は、systemd そのものではなく、unit ファイルの一部のキーだけがわかる小さな init です。systemctl と journalctl の表示は本物の systemd に似せてありますが、細かい書式は違うことがあります。この章では、表示の細部ではなく、何が起きているかを見てください。

17.5systemctl：起こす、止める、状態を見る

サービスを操作するコマンドが systemctl です。ticker を起こしてみます。

ふつうのユーザーには起こせないエラーになる⌘↵
systemctl start ticker

断られました。サービスの多くは root で動くので、起こす・止めるは root の仕事です。ここからは、root のシェルで実行します（プロンプトが # になります）。

root で起こして、状態を見るroot で実行⌘↵
systemctl start tickersystemctl status ticker

start は、うまくいくと何も表示しません。status の出力から、次のことが読み取れます。

  • Loaded … どの unit ファイルを読んだか
  • Active … いまの状態。active (running) は、動いている
  • Main PID … サービスの本体のプロセスの PID
  • CGroup … このサービスに属するプロセスの一覧（cgroup は第 19 章）
  • 最後の数行 … このサービスが出したログ

状態を見るだけなら、root でなくてもかまいません。動いている unit の一覧は list-units です。

動いている unit と、プロセスの木⌘↵
systemctl list-unitspstree -p

ticker は init の直接の子として動いています。シェルの子ではありません。systemctl を打ったシェルを閉じても、ticker は動き続けます。

systemctl は、init に頼んでいるだけ

systemctl 自身は、サービスを fork していません。していることを strace で見ます。

systemctl のシステムコールstrace：システムコールも表示⌘↵
systemctl is-active ticker

socket、connect で /run/systemd/private というソケットにつなぎ、頼みごとを write して、返事を read しています。ソケットの向こうにいるのが PID 1 です。systemctl は伝言役で、実際に fork と execve でサービスを起こすのは init です（ソケットは第 16 章）。だからサービスの親は、いつも PID 1 になります。

止めるのは stop です。

止める。止まっていると、is-active は 0 以外を返すエラーになるroot で実行⌘↵
systemctl stop tickersystemctl is-active ticker

stop は、サービスのプロセスに SIGTERM を送ります（第 8 章）。しばらく待っても終わらなければ、SIGKILL で強制的に終わらせます。is-active は、動いていなければ終了ステータス 3 を返すので、スクリプトの if で使えます。

コマンドすること
systemctl start 名前いま起こす
systemctl stop 名前いま止める
systemctl restart 名前止めて、起こす
systemctl status 名前状態と、最近のログ
systemctl is-active 名前動いているかを 1 語で
systemctl list-units動いている unit の一覧
systemctl list-unit-filesunit ファイルの一覧と、enable されているか
systemctl enable 名前 / disable 名前起動時に自動で起こす / 起こさない（あとの節）
systemctl daemon-reloadunit ファイルを読み直させる

17.6自分のサービスを書く

サービスにするプログラムは、何でもかまいません。ここでは、5 秒ごとに 1 行書くシェルスクリプトを作ります。

サービスにするプログラムを書くroot で実行⌘↵
cat > /usr/local/bin/hello-daemon <<'EOT'#!/bin/shecho "hello-daemon started (PID $$)"while true; do  sleep 5  echo "still alive"doneEOTchmod +x /usr/local/bin/hello-daemon

特別なことは何もしていません。バックグラウンドに回る処理も、ログファイルを開く処理もありません。標準出力に書いて、ずっと動き続けるだけです。

次に、unit ファイルを /etc/systemd/system/ に書きます。

unit ファイルを書いて、読み直させ、起こすroot で実行⌘↵
cat > /etc/systemd/system/hello.service <<'EOT'[Unit]Description=Hello daemon[Service]ExecStart=/usr/local/bin/hello-daemonRestart=always[Install]WantedBy=multi-user.targetEOTsystemctl daemon-reloadsystemctl start hellosystemctl status hello

daemon-reload を忘れないでください。init は unit ファイルを起動時に読んで覚えているので、ファイルを足したり書き換えたりしたら、読み直すよう頼む必要があります。忘れると、新しい unit は「見つからない」と言われ、書き換えた unit は古い内容のまま動きます。

status の CGroup のところに、プロセスが 2 つ見えます。/bin/sh /usr/local/bin/hello-daemon（#! の行によって起動された sh。次の章でくわしく見ます）と、その子の sleep 5 です。systemd は、サービスが作った子や孫も、cgroup という仕組みで「このサービスのもの」として把握しています。

メモデーモン

端末につながらずに裏で動き続けるプログラムを、デーモン（daemon）と呼びます。httpd、sshd、crond のように、名前の最後に d がつくものが多くあります。昔のデーモンは、自分で 2 回 fork して端末から離れ、標準入出力を閉じ、PID をファイルに書く、という決まった手順を踏む必要がありました。systemd のもとでは、その手順は init が引き受けます。プログラムは、ふつうに前面で動き続ければよいのです。

17.7journalctl：サービスの出力は、どこへ行くのか

hello-daemon は echo で標準出力に書いています。しかし、このプロセスには端末がありません。書いた文字は、どこへ行くのでしょうか。サービスの fd を見ます（第 9 章）。

サービスの fd 0・1・2root で実行⌘↵
pid=$(systemctl show hello | grep MainPID | cut -d= -f2)ls -l /proc/$pid/fd
  • fd 0（標準入力）は /dev/null。読んでも、すぐ EOF
  • fd 1 と fd 2（標準出力と標準エラー出力）は、同じパイプ

パイプの反対側を持っているのは init です。init は、サービスを fork したあと、execve の前に、子の fd 1 と 2 をパイプにつなぎ替えています。第 9 章で見た、リダイレクトと同じ手口です。init はパイプから読んだ行に、時刻と、書いたプロセスの名前と PID をつけて、ジャーナル（journal）というログに保存します。

ジャーナルを読むコマンドが journalctl です。-u 名前 で、その unit の分だけを取り出します。

hello のログを読むroot で実行⌘↵
sleep 12journalctl -u hello

1 行目は init が書いた「起こした」という記録、2 行目からが hello-daemon の標準出力です。プログラムは echo しただけなのに、時刻と PID がついて、あとから検索できる形で残っています。

コマンド意味
journalctl -u 名前その unit のログ
journalctl -u 名前 -n 20最後の 20 行
journalctl -b今回の起動からのログ
journalctl -kカーネルのログ（dmesg と同じもの）
journalctl -f新しい行が来るのを待って、出し続ける（tail -f と同じ。本物で使う）

ジャーナルには、システム全体の記録が入っています。そのため、ふつうのユーザーには、ほかのユーザーやシステムの分を見せません。

ふつうのユーザーには見えない⌘↵
journalctl -u hello
メモ/var/log のテキストファイルとの関係

systemd より前は、ログは syslogd というデーモンが集めて、/var/log/syslog や /var/log/messages といったテキストファイルに書いていました。いまでも、ジャーナルと並行してこれらのファイルを書いているディストリビューションは多くあります。第 5 章で grep の練習に使った /var/log のファイルは、その形式です。本物の systemd のジャーナルは、検索を速くするためにバイナリ形式で、cat では読めません。journalctl を通して読みます。

17.8Restart=：死んだサービスを起こし直す

サーバのプログラムは、バグやメモリ不足で、ある日とつぜん死ぬことがあります。夜中に人が起こし直すのは大変です。hello.service には Restart=always と書きました。本当に起こし直されるか、殺して確かめます。

サービスを kill するroot で実行⌘↵
systemctl show hello | grep MainPIDkill $(systemctl show hello | grep MainPID | cut -d= -f2)sleep 2systemctl show hello | grep -E 'MainPID|NRestarts'

MainPID が変わりました。別のプロセスとして、生き返っています。NRestarts は、起こし直した回数です。何が起きたかは、ジャーナルに残っています。

起こし直しの記録root で実行⌘↵
journalctl -u hello -n 5

init は、サービスの親です。子が死ぬと、カーネルから SIGCHLD が届き、wait4 で終了の理由（ここでは SIGTERM で殺された）を受け取ります（第 7 章、第 8 章）。そこで unit ファイルの Restart= を見て、もう一度 fork + execve します。特別な監視の仕組みがあるわけではなく、親だから、子の死がわかるのです。

systemctl stop で止めたときは、起こし直されません。「止めて」と頼まれて止めたことを、init は知っているからです。

起こしても、すぐ死ぬとき

では、起動した直後に必ず失敗するサービスに Restart=always をつけたら、どうなるでしょうか。/usr/bin/false は、何もせずに終了ステータス 1 で終わるコマンドです。

必ず失敗するサービスroot で実行⌘↵
cat > /etc/systemd/system/broken.service <<'EOT'[Unit]Description=Always fails[Service]ExecStart=/usr/bin/falseRestart=alwaysEOTsystemctl daemon-reloadsystemctl start brokensleep 3journalctl -u broken -n 6

Start request repeated too quickly.（起動の要求が、短い間にくり返されすぎた）という行があります。init は、短い時間に何度も起こし直すことになった unit を、あきらめます。そうしないと、fork と失敗を全速力でくり返して、CPU とログを食いつぶすからです。

あきらめられた unit は failed になる⌘↵
systemctl list-units --all

broken.service の ACTIVE の列が failed です。こうなったら、ジャーナルで原因を調べ、unit ファイルかプログラムを直して、もう一度 start します。

メモ本物の systemd では

あきらめるまでの回数と時間は、unit ファイルの StartLimitBurst=（既定 5 回）と StartLimitIntervalSec=（既定 10 秒）で変えられます。また、RestartSec= の既定は 100 ミリ秒です。失敗をくり返すサービスには、RestartSec=5 のように間を空けるのがふつうです。

17.9再起動で、何が残り、何が消えるか

機械を再起動すると、カーネルはメモリの上のすべてを捨てて、最初からやり直します。何が残って、何が消えるのかを、実際に再起動して確かめます。まず、消えるかどうかを見たいものを用意します。

再起動の前に、目印を置く⌘↵
echo "一時ファイル" > /tmp/scratch.txtecho "ホームのファイル" > keep.txtX=42sleep 1000 &jobs

/tmp のファイル、ホームディレクトリのファイル、シェルの変数、バックグラウンドのプロセスの 4 つです。

サービスのほうも準備します。start は「いま起こす」だけで、次の起動のことは何も決めません。起動のたびに自動で起こすには、enable します。

hello を、起動時に自動で起こすようにするroot で実行⌘↵
systemctl enable hellols -l /etc/systemd/system/multi-user.target.wants/

enable がしたのは、シンボリックリンクを 1 つ作ることだけです（第 11 章）。multi-user.target.wants というディレクトリに、unit ファイルへのリンクが置かれました。unit ファイルの [Install] に WantedBy=multi-user.target と書いたので、この場所になります。init は起動のとき、このディレクトリにリンクのある unit を起こします。設定が、ただのファイルとして見えているのが、Unix らしいところです。

ticker は、さっき start して stop しましたが、enable はしていません。では、再起動します。

再起動するroot で実行⌘↵
reboot

reboot は、init に「サービスを順に止めて、ディスクに書き戻して（第 15 章）、再起動して」と頼みます。新しく起動した機械で、目印を調べます。

再起動のあと⌘↵
uptimels /tmpcat keep.txtecho "X=$X"jobs
  • uptime の up が 0 分に戻った
  • /tmp/scratch.txt は消えた。/tmp は tmpfs で、中身はメモリの上にあるから（第 12 章）
  • keep.txt は残った。ディスクの上のファイルだから
  • 変数 X は消えた。シェルのプロセスのメモリにあったから
  • バックグラウンドの sleep も消えた。プロセスはすべて終わり、新しく作り直された

サービスはどうでしょうか。

enable した unit だけが、起きている⌘↵
systemctl list-unitspstree -p

enable した hello は動いています。だれも start と打っていません。ticker は動いていません。

再起動のあと理由
ディスクの上のファイル（/home、/etc …）残るディスクは電源が切れても消えない
unit ファイルと、enable のリンク残る/etc の下のファイルだから
ジャーナル残る/var/log/journal の下のファイルだから
/tmp、/run のファイル消えるtmpfs。メモリの上にある
プロセス、シェルの変数、ジョブ消えるメモリの上にある
start しただけのサービス止まったまま「いま動いている」という状態は、メモリの上にしかない
/proc の中身、dmesg作り直されるカーネルが動きながら作るもの

ジャーナルは残るので、再起動の前のことを調べられます。

前の起動のログも読めるroot で実行⌘↵
journalctl --list-bootsjournalctl -u hello -n 6

hello のログには、再起動の前に init が hello を止めた記録、起動の境目、そして新しい起動で hello が起こされた記録が並んでいます。「昨夜なぜ落ちたのか」を調べられるのは、ログがディスクにあるからです。

コツstart と enable は別のこと
  • start … いま起こす。再起動したら元に戻る
  • enable … 次の起動から自動で起こす。いまは何も起きない

新しいサービスを入れたら、ふつうは両方します。本物の systemd では systemctl enable --now 名前 と 1 回で書けます。「設定したのに、再起動したら動いていない」は enable 忘れ、「enable したのに動いていない」は start 忘れです。

17.10ランレベルとターゲット

起動のとき、どこまで立ち上げるかには、いくつかの段階があります。サーバなら「ネットワークと各種のサービスまで」、デスクトップなら「さらにグラフィカルなログイン画面まで」、修理のときは「root のシェル 1 つだけ」です。

SysV init では、この段階を 0 から 6 の番号で表し、ランレベル（runlevel）と呼びました。systemd では、番号の代わりに名前のついた ターゲット（target）という unit を使います。ターゲットは、それ自身は何も実行しない、unit をまとめるための目印です。

ランレベルsystemd のターゲット意味
0poweroff.target電源を切る
1rescue.target修理用。root のシェルだけ（シングルユーザーモード）
3multi-user.targetふつうのサーバ。ネットワークとサービス、文字のログイン
5graphical.target3 に加えて、グラフィカルなログイン画面
6reboot.target再起動する

起動のとき、どのターゲットを目指すかは決まっています。

この機械が目指すターゲットroot で実行⌘↵
systemctl get-defaultrunlevel

multi-user.target です。runlevel は昔からのコマンドで、同じことを番号で 3 と答えます（前の N は「その前のランレベルはない」の意味です）。

これで、いくつかの話がつながります。

  • dmesg の最後にあった Reached target multi-user.target は、「目指していた段階に着いた」という init の報告
  • unit ファイルの WantedBy=multi-user.target は、「multi-user.target を目指すときに、一緒に起こしてほしい」という希望
  • enable が作った multi-user.target.wants/hello.service のリンクは、その希望を登録したもの

reboot や poweroff も、ターゲットで説明できます。reboot は「reboot.target を目指す」ことで、そのためには、動いているサービスをすべて止める必要があります。だから、再起動の前にサービスが順に止められたのです。

注意本物との違い
  • 本物の systemd には、サービスのほかに、ソケット、タイマー、マウント、デバイスなど 11 種類の unit があります。unit のあいだの順序（After=、Requires=）を見て、並行に起こします。小さな Linux の init は、サービスと multi-user.target だけを扱い、順序は見ません
  • 本物では、動いている最中に systemctl isolate rescue.target のようにターゲットを切り替えられます。小さな Linux ではできません
  • 小さな Linux の再起動は、一瞬で終わります。時刻は進み続けますが、起動にかかる時間は 2 秒ほどとして扱われます
要点この章のまとめ
  • 起動は、ファームウェア → ブートローダ → カーネル → initramfs → init のリレー。小さなプログラムが、次のプログラムをメモリに読み込む
  • dmesg は、カーネルが書き残した記録。起動の様子も、動いている最中の異常も、ここに出る
  • PID 1（init） は、カーネルが直接起動する唯一のプロセス。システムを立ち上げ、サービスを見張り、孤児を引き取る。死んではいけない
  • 今の init は、ほとんど systemd。サービスは unit ファイル（/etc/systemd/system/名前.service）に ExecStart= などを書いて定義する。書き換えたら daemon-reload
  • systemctl は、ソケットで init に頼む伝言役。start・stop・status・list-units。サービスを fork するのは init なので、サービスの親は PID 1
  • サービスの標準出力は、パイプで init に渡り、ジャーナルに保存される。journalctl -u 名前 で読む
  • Restart= があれば、死んだサービスは起こし直される。短い間にくり返し死ぬと、Start request repeated too quickly であきらめて failed になる
  • start はいま、enable は次の起動から。enable は、ターゲットの .wants ディレクトリにシンボリックリンクを作るだけ
  • 再起動で、ディスクの上のもの（ファイル、unit、ジャーナル）は残り、メモリの上のもの（プロセス、変数、/tmp）は消える
  • ターゲットは、昔のランレベルにあたる、起動の段階の目印。サーバは multi-user.target

17.11確認問題

サービスを自分で操作する問題です。どの問題も、新しい Linux から始まります。サービスを操作するコマンドは root で実行する必要があるので、sudo systemctl … のように、前に sudo をつけてください。

問 1

起こして、次の起動でも起きるようにする

正解済み

用意されている httpd.service を、いま起動し、さらに次の起動からも自動で起きるようにしてください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

「いま起こす」と「起動時に自動で起こす」は、別のコマンドです。start と enable の両方が要ります。

確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

systemctl is-active httpdsystemctl is-enabled httpd
模範解答
sudo systemctl start httpdsudo systemctl enable httpd
問 2

unit ファイルを書く

正解済み

/usr/local/bin/beat というプログラムが置いてあります。これを beat.service という名前のサービスにして、起動してください。死んだときは、いつも起こし直されるようにします。unit ファイルは /etc/systemd/system/beat.service に書きます。

ふつうのユーザーは /etc に書けないので、sudo tee ファイル を使います。tee は、標準入力をファイルに書くコマンドでした（第 5 章）。

sudo tee /etc/systemd/system/beat.service > /dev/null <<'EOT'[Unit]Description=Beat[Service]EOT
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

[Service] の節に、ExecStart=/usr/local/bin/beat と Restart=always の 2 行を書きます。ファイルを書いたら sudo systemctl daemon-reload、それから sudo systemctl start beat です。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

printf '#!/bin/sh\nwhile true; do echo beat; sleep 3; done\n' | sudo tee /usr/local/bin/beat > /dev/nullsudo chmod +x /usr/local/bin/beat
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

systemctl is-active beatsystemctl show beat | grep -E '^(ExecStart|Restart)='
模範解答
sudo tee /etc/systemd/system/beat.service > /dev/null <<'EOT'[Unit]Description=Beat [Service]ExecStart=/usr/local/bin/beatRestart=alwaysEOTsudo systemctl daemon-reloadsudo systemctl start beat
問 3

何回、起こし直されたか

正解済み

ticker.service が動いています。このサービスは、起動してから何度か死んで、そのたびに起こし直されました。起こし直された回数を、数字だけで表示してください。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵標準出力で判定（行の順番も見る）
ヒント

systemctl show ticker は、unit の情報を 名前=値 の形で並べます。その中の NRestarts が、起こし直した回数です。grep で行を選び、cut -d= -f2 で値だけを取り出します。ジャーナルの Scheduled restart の行を数える方法もあります（sudo journalctl -u ticker | grep -c …）。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

sudo systemctl start tickersudo pkill ticker; sleep 2sudo pkill ticker; sleep 2
模範解答
systemctl show ticker | grep NRestarts | cut -d= -f2
問 4

起動に失敗するサービスを直す

正解済み

report.service を起動しようとしましたが、failed になってしまいました。原因を調べて unit ファイルを直し、report.service が動いている状態にしてください。

原因は、systemctl status report か sudo journalctl -u report でわかります。ファイルの中の文字を置き換えるには、sudo sed -i 's/古い/新しい/' ファイル が使えます。

# ここにコマンドを書いて「答え合わせ」（Ctrl / ⌘ + Enter）
⌘↵実行した後の状態（下の「確かめ方」のコマンドの出力）で判定
ヒント

ログに Failed to execute /usr/bin/tiker: No such file or directory とあります。ExecStart= のコマンドの名前が、1 文字抜けています（正しくは ticker）。unit ファイルを直したら、daemon-reload してから start します。

この問題の準備

答え合わせのたびに、章の最初の状態にこの準備をしてから、あなたのコマンドを実行します。

printf '[Unit]\nDescription=Report\n\n[Service]\nExecStart=/usr/bin/tiker 5\nRestart=on-failure\n' | sudo tee /etc/systemd/system/report.service > /dev/nullsudo systemctl daemon-reloadsudo systemctl start reportsleep 2
確かめ方

あなたのコマンドを実行した後に、root でこのコマンドを実行して、その出力を模範解答のときと比べます。

systemctl is-active reportsystemctl show report | grep '^ExecStart='
模範解答
sudo sed -i 's/tiker/ticker/' /etc/systemd/system/report.servicesudo systemctl daemon-reloadsudo systemctl start report
