## 同じ番地に、別のものが入っている {#virtual}

第 7 章で、プロセスは「自分のメモリ」を持つと書きました。その中身を、この章で開けます。まず、同じプログラムを 2 つ動かして、メモリのどこに置かれているかを比べます。`/proc/PID/maps` は、そのプロセスのメモリの配置を見せるファイルです（読み方は、あとで説明します）。

```sh run title="2 つの sleep は、メモリのどこにいるか"
sleep 100 &
sleep 200 &
grep -h stack /proc/[0-9]*/maps
```

`[stack]` と書かれた行が、プロセスの数だけ出ました。init も、シェルも、2 つの `sleep` も、**全員が `7ffffffde000` から `7ffffffff000` という同じ番地**を使っています。

これは不思議です。スタックは、関数の呼び出しのたびに書き換わる場所です。4 つのプロセスが本当に同じ場所を使っていたら、互いの中身を壊し合ってしまいます。

答えは、**この番地が、本物のメモリの番地ではない**ことです。プロセスが使う番地を**仮想アドレス**（virtual address）、メモリの部品の上の本当の番地を**物理アドレス**（physical address）と呼びます。プロセスが仮想アドレスを使うたびに、CPU の中の **MMU**（Memory Management Unit）という回路が、それを物理アドレスに変換します。変換のための対応表は、カーネルがプロセスごとに 1 つずつ用意します。

```fig graph 2 つのプロセスが同じ仮想アドレスを使っても、対応表が別なので、物理メモリの別の場所に行き着く
{

    { id: 'b', label: 'sleep（PID 4）', sub: '0x7ffffffde000 に書く', x: 0, y: 1.3, kind: 'accent' },

    { id: 'tb', label: 'PID 4 の対応表', sub: 'ページ表', x: 1.15, y: 1.3, kind: 'stack', mono: false },
    { id: 'm1', label: '物理メモリ', sub: 'フレーム 1571', x: 2.3, y: 0, kind: 'ext', mono: false },
```

プロセスごとの「番地の世界」を、**アドレス空間**（address space）と呼びます。この仕組み全体が**仮想メモリ**（virtual memory）です。仮想メモリには、3 つの効き目があります。

- **隔離**：ほかのプロセスのメモリは、自分の対応表に載っていないので、番地を指定することさえできません。バグのあるプログラムが、ほかのプログラムを壊せません
- **単純さ**：どのプログラムも、「自分だけが、広いメモリを端から端まで使える」つもりで書けます
- **節約**：対応表を工夫すると、同じ中身を何人かで共有したり、使うまで本物のメモリを渡さずにおいたりできます。この章の後半は、ほとんどがこの話です

:::note 本物の Linux では、番地が毎回変わる
本物の Linux で同じことをすると、スタックの番地はプロセスごとに違います。攻撃者に番地を予想させないために、起動のたびに配置をずらしているからです（**ASLR**。Address Space Layout Randomization）。この小さな Linux は、説明しやすいように、いつも同じ番地に置きます。
:::

```sh run title="後片づけ"
kill %1 %2
```

## ページとページ表 {#page}

対応表を 1 バイトごとに持つと、表のほうがメモリより大きくなってしまいます。そこで、メモリを **4 KiB（4096 バイト）** ごとに区切って、区切りの単位で対応させます。仮想アドレスの側の区切りを**ページ**（page）、物理メモリの側の区切りを**フレーム**（frame。ページフレーム）と呼びます。対応表は、**ページ表**（page table）です。

4096 は 2 の 12 乗なので、番地を 16 進数で書くと、**下 3 桁がページの中の位置、それより上がページの番号**になります。

| 仮想アドレス | ページの番号 | ページの中の位置（オフセット） |
| --- | --- | --- |
| `0x7ffffffde000` | `0x7ffffffde` | `0x000` |
| `0x7ffffffde123` | `0x7ffffffde` | `0x123` |
| `0x7ffffffdf000` | `0x7ffffffdf` | `0x000`（次のページ） |

MMU は、ページの番号でページ表を引いてフレームの番号を得て、オフセットはそのまま付け直します。`maps` に出てくる番地の下 3 桁が、どれも `000` なのは、領域がページの単位で作られるからです。

ページ表の 1 行（**ページ表エントリ**）には、フレームの番号のほかに、いくつかの印がついています。

```fig pagetable ページ表は、仮想ページごとに「どのフレームか」と「何をしてよいか」を持つ。対応のないページもある
{
  pages: [
    { vpn: '0x555555554', name: 'text', frame: 3, flags: 'r-x' },
    { vpn: '0x555555562', name: 'data', frame: 5, flags: 'rw-' },
    { vpn: '0x555555563', name: 'heap', frame: 6, flags: 'rw-' },
    { vpn: '0x555555564', name: 'heap', state: 'none' },
    { vpn: '0x7fffffffe', name: 'stack', frame: 8, flags: 'rw-' },
  ],
  frames: [ { n: 3, label: 'プログラムの命令' }, { n: 4 }, { n: 5 }, { n: 6 }, { n: 7 }, { n: 8 } ],
}
```

- **存在**：そのページに、いまフレームが割り当てられているか。割り当てのないページに触ると、CPU は実行を中断して、カーネルを呼び出します。これが**ページフォルト**（page fault）です
- **権限**：読めるか（r）、書けるか（w）、命令として実行できるか（x）。権限のない使い方をしても、ページフォルトになります

ページフォルトは、名前に反して、ふつうは「故障」ではありません。カーネルに「このページの用意を頼む」ための、正常な通り道です。カーネルが用意できれば、プロセスは何も気づかずに続きを実行します。用意できない（そもそも領域の外だった、書けない場所に書いた）ときだけ、カーネルは `SIGSEGV` を送ります。第 8 章の表にあった「不正なメモリへのアクセス」は、ここから来ます。

:::deep ページ表そのものは、どのくらい大きいか
64 ビットの Linux（x86-64）の仮想アドレスは 48 ビットで、ページは 2 の 36 乗個あります。全部のページの行を並べた表は、置けません。本物のページ表は 4 段の木になっていて、使っている範囲の枝だけを作ります。使っていない広い範囲には、枝そのものがありません。ページ表のために使っているメモリは、`/proc/PID/status` の `VmPTE` と、`/proc/meminfo` の `PageTables` に出ます。
:::

## アドレス空間の地図：/proc/PID/maps {#maps}

ページ表は細かすぎるので、ふだんは、もう少し粗い地図を見ます。`/proc/PID/maps` です。`/proc/self` は「読んでいるプロセス自身」を指すので、次のコマンドは `cat` 自身の地図を表示します。

```sh run title="cat 自身のアドレス空間"
cat /proc/self/maps
```

1 行が、性質のそろったページの並び（**領域**）です。左から順に、次の意味です。

| 列 | 例 | 意味 |
| --- | --- | --- |
| 範囲 | `555555554000-555555561000` | 仮想アドレスの始まりと終わり（終わりは含まない） |
| 権限 | `r-xp` | r 読める、w 書ける、x 実行できる。4 文字目は p（private。自分だけ）か s（shared。共有） |
| オフセット | `0000d000` | ファイルを写した領域なら、ファイルの何バイト目からか |
| デバイス | `08:01` | そのファイルのあるデバイス（メジャー:マイナー。第 12 章） |
| inode | `48` | そのファイルの inode 番号（第 11 章）。ファイルでなければ 0 |
| 名前 | `/usr/bin/cat` | 写しているファイル。`[heap]` などは特別な領域 |

9 行は、下の番地から順に、次のものです。

| 領域 | 権限 | 中身 |
| --- | --- | --- |
| `/usr/bin/cat`（1 行目） | `r-xp` | プログラムの命令（**text**）。書けない |
| `/usr/bin/cat`（2 行目） | `r--p` | 書き換えない定数（文字列など） |
| `/usr/bin/cat`（3 行目） | `rw-p` | 初期値のある変数（**data**） |
| `[heap]` | `rw-p` | **ヒープ**。実行中に `malloc` で確保するメモリ。上に伸びる |
| `/usr/lib/libc.so.6`（3 行） | 同上 | C の標準ライブラリ。`cat` と同じく、命令・定数・変数の 3 つ |
| `[vdso]` | `r-xp` | カーネルが全プロセスに置いてくれる小さな命令（時刻を読むための近道） |
| `[stack]` | `rw-p` | **スタック**。関数の呼び出しごとの変数。下に伸びる |

命令の領域には w がなく、データの領域には x がありません。プログラムが自分の命令を書き換えたり、データを命令として実行したりすると、ページフォルトで止められます。

ヒープとスタックのあいだは、大きく空いています。`555555584000` から `7ffff7d8a000` までは、およそ 42 TiB あります。空いているところにはページ表の行がないので、メモリは 1 バイトも使いません。

同じ情報を、大きさつきで見やすくするのが `pmap` です。

```sh run title="pmap：領域ごとの大きさ"
pmap $$
```

シェル（`$$`）のアドレス空間は、合計 352 KiB です。`[ anon ]` は、ファイルと結びついていない領域（**無名**メモリ。anonymous）を表します。

## メモリを増やす：brk と mmap {#brk-mmap}

プログラムは、動いている途中でメモリが足りなくなったら、カーネルに領域を増やしてもらいます。そのためのシステムコールは 2 つあります。

- **`brk`**：ヒープの終わりの番地を動かす。ヒープを上に伸ばす、昔からの方法
- **`mmap`**：アドレス空間の空いているところに、新しい領域を作る

`memtouch` は、指定した大きさのメモリを確保して、そこに書き込む練習用のコマンドです。16 KiB（4 ページ）を確保させて、システムコールを見ます。

```sh run strace title="メモリの確保は mmap"
memtouch 16k
```

`mmap(NULL, 16384, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0x7ffff7d86000` が、確保の瞬間です。引数は、順に次の意味です。

| 引数 | 値 | 意味 |
| --- | --- | --- |
| 番地 | `NULL` | 場所はカーネルに任せる |
| 長さ | `16384` | 16 KiB |
| 保護 | `PROT_READ\|PROT_WRITE` | 読み書きできる（`maps` の `rw-`） |
| フラグ | `MAP_PRIVATE\|MAP_ANONYMOUS` | 自分だけのもので、ファイルと結びつかない |
| fd、オフセット | `-1`、`0` | ファイルを写さないので、使わない |

戻り値の `0x7ffff7d86000` が、新しい領域の始まりです。libc のすぐ下に置かれました。確保したままのプロセスを作って、地図で確かめます。`memtouch` の最後の引数は、終わる前に待つ秒数です。

```sh run title="mmap した領域が、地図に 1 行増える"
memtouch 16k 30 > /dev/null &
grep -B1 -A1 '7ffff7d86000' /proc/$!/maps
kill $!
```

`[heap]` と libc のあいだに、名前のない `rw-p` の行が増えています。

C のプログラムは、ふつうこれらのシステムコールを直接は呼びません。`malloc` を呼びます。`malloc` はライブラリ関数で（第 10 章）、小さな確保は、手元のヒープから切り分けて渡します。手元が尽きたときだけ、`brk` でヒープを伸ばします。大きな確保（glibc では 128 KiB 以上）は、`mmap` で別の領域を作ります。本物の Linux で `strace` をかけると、次のように見えます。

```console
$ strace ls 2>&1 | grep -E 'brk|mmap' | tail -3
brk(NULL)                               = 0x55d0c6a4f000      ← いまのヒープの終わりを聞く
brk(0x55d0c6a70000)                     = 0x55d0c6a70000      ← 132 KiB 伸ばす
mmap(NULL, 3055616, PROT_READ, MAP_PRIVATE, 3, 0) = 0x7f3a1c200000
```

この小さな Linux にも `brk` はあり、`[heap]` は最初から 132 KiB あります。ただ、コマンドは JavaScript で書かれていて `malloc` を持たないので、`strace` に `brk` は出てきません。

## 確保しただけでは、メモリは減らない {#demand}

ここからが、仮想メモリのいちばん大事なところです。`memtouch` に `-n` をつけると、確保だけして、**触りません**。8 MiB を確保させます。

```sh run title="確保するだけ"
memtouch -n 8M
```

`VmSize`（アドレス空間の大きさの合計）は 388 kB から 8580 kB に増えました。8 MiB = 8192 kB ぶんです。ところが `VmRSS`（**実際に割り当てられているフレーム**の合計）は、52 kB のままです。

`mmap` は、「この範囲を使ってよい」と地図に書き込むだけで、フレームを 1 つも割り当てません。ページ表の行も作りません。今度は `-n` をつけずに、確保した全部のページに書き込ませます。

```sh run title="触ると、そのときに割り当てられる"
memtouch 8M
```

2048 ページに書き込むと、**ページフォルトがちょうど 2048 回**起きて、`VmRSS` は 52 kB から 8244 kB に増えました。1 ページに初めて触るたびに、次のことが起きています。

1. プロセスが、まだフレームのないページに書こうとする。CPU がページフォルトを起こして、カーネルに切り替わる
2. カーネルは地図（領域の一覧）を見て、そこが「使ってよい範囲」だと確かめる
3. 空いているフレームを 1 つ選び、0 で埋めて、ページ表に行を作る
4. プロセスに戻って、中断した書き込みをやり直す。今度は成功する

```fig pagetable 確保した直後は、ページ表に行がない。触ったページから、1 つずつフレームがつく
{
  frames: [ { n: 20 }, { n: 21 }, { n: 22 }, { n: 23 } ],
  steps: [
    {
      title: 'mmap の直後',
      say: '4 ページぶんの領域を確保しました。地図には載りましたが、どのページにもフレームはありません。<code>VmSize</code> だけが増えます。',
      pages: [
        { vpn: '0x7ffff7d86', name: 'mmap', state: 'none' },
        { vpn: '0x7ffff7d87', name: 'mmap', state: 'none' },
        { vpn: '0x7ffff7d88', name: 'mmap', state: 'none' },
        { vpn: '0x7ffff7d89', name: 'mmap', state: 'none' },
      ],
    },
    {
      title: '1 ページ目に書く',
      say: 'ページフォルトが起きて、カーネルがフレーム 20 を割り当てます。<code>VmRSS</code> が 4 kB 増えます。',
      pages: [
        { vpn: '0x7ffff7d86', name: 'mmap', frame: 20, flags: 'rw-', hl: true },
        { vpn: '0x7ffff7d87', name: 'mmap', state: 'none' },
        { vpn: '0x7ffff7d88', name: 'mmap', state: 'none' },
        { vpn: '0x7ffff7d89', name: 'mmap', state: 'none' },
      ],
    },
    {
      title: '全部に書く',
      say: '4 回のページフォルトで、4 つのフレームがつきました。触らなかったページがあれば、そこは最後まで「行なし」のままです。',
      pages: [
        { vpn: '0x7ffff7d86', name: 'mmap', frame: 20, flags: 'rw-' },
        { vpn: '0x7ffff7d87', name: 'mmap', frame: 21, flags: 'rw-' },
        { vpn: '0x7ffff7d88', name: 'mmap', frame: 22, flags: 'rw-' },
        { vpn: '0x7ffff7d89', name: 'mmap', frame: 23, flags: 'rw-', hl: true },
      ],
    },
  ],
}
```

必要になったときに初めて割り当てるこの方式を、**デマンドページング**（demand paging。要求時ページング）と呼びます。大きな配列を確保して一部しか使わないプログラムは多いので、これでメモリがずいぶん節約できます。

カーネルの中の出来事を、そのまま見ることもできます。次のブロックは、実行結果の下に「メモリの観察」がつきます。

```sh run trace="mem" title="ページフォルトを 1 回ずつ見る"
memtouch 16k
```

`alloc`（`mmap` で領域が増えた）のあとに、`fault` が 4 つ並びます。番地は `0x7ffff7d86000` から 4096（`0x1000`）ずつ進み、それぞれに別のフレームがついています。最後の `free` は、プロセスが終わって、使っていたフレームが返されたところです。

### ページフォルトを数える

ページフォルトの回数は、プロセスごとに数えられています。`/usr/bin/time -v` は、コマンドを実行して、使った資源をくわしく報告します（シェルの `time` とは別のコマンドなので、パスで呼びます）。

```sh run title="コマンド 1 回ぶんのページフォルト"
/usr/bin/time -v memtouch 4M 2>&1 | grep -E 'Maximum resident|page faults'
/usr/bin/time -v cat /etc/hostname 2>&1 | grep -E 'Maximum resident|page faults'
```

`memtouch 4M` は、minor が 1037 回です。4 MiB ぶんの 1024 回に、起動のための 13 回が足されています。`cat` のような小さなコマンドでも、13 回のページフォルトが起きます。プログラムの命令も、ライブラリも、スタックも、最初に触ったときに割り当てられるからです。`Maximum resident set size` は、RSS がいちばん大きかったときの値です。

ページフォルトには、2 種類あります。

- **minor**（軽い）：ディスクを読まずに済んだもの。空きフレームを 0 で埋めて渡す、すでにメモリにあるものを対応づける、など
- **major**（重い）：ディスクから読む必要があったもの。桁違いに遅い

major のほうは、ファイルを写す話のところで出会います。

## VSZ と RSS {#rss}

`ps` には、メモリの列が 2 つあります。確保だけしたプロセスと、全部に触ったプロセスを並べて、見比べます。

```sh run title="確保だけの 8 MiB と、触った 8 MiB"
memtouch -n 8M 60 > /dev/null &
memtouch 8M 60 > /dev/null &
ps -o pid,vsz,rss,comm
```

| 列 | 名前 | 意味 |
| --- | --- | --- |
| `VSZ` | Virtual Set Size | アドレス空間の領域の合計。「使ってよい」と言われた量。単位は KiB |
| `RSS` | Resident Set Size | いまフレームが割り当てられている量。本当に物理メモリを使っている量 |

2 つの `memtouch` の VSZ は、どちらも 8580 です。RSS は、52 と 8244 です。**メモリを食っているプロセスを探すときに見るのは、RSS です**。VSZ が大きくても、それだけでは何も困りません。

もう少し細かい内訳は、`/proc/PID/status` にあります。

```sh run title="触ったほうのプロセスの内訳"
grep -E '^(Vm|Rss)' /proc/$!/status
```

| 行 | 意味 |
| --- | --- |
| `VmSize` | `ps` の VSZ と同じ |
| `VmRSS` | `ps` の RSS と同じ。`RssAnon` + `RssFile` |
| `RssAnon` | 無名メモリ（ヒープ、スタック、`mmap` した領域）のぶん |
| `RssFile` | ファイルを写したページ（プログラムとライブラリ）のぶん |
| `VmPeak`、`VmHWM` | VmSize と VmRSS の、これまでの最大値 |
| `VmData`、`VmStk`、`VmExe`、`VmLib` | データ、スタック、プログラム、ライブラリの領域の大きさ |

`RssAnon` の 8212 kB のうち、8192 kB が `memtouch` の書き込んだ 8 MiB です。

## free と /proc/meminfo：機械全体のメモリ {#free}

プロセスごとではなく、機械全体のメモリを見るのが `free` です。2 つの `memtouch` が動いているうちに、実行します。

```sh run title="機械全体の使用量"
free
```

単位は KiB です。この小さな Linux の物理メモリは 64 MiB で、カーネル自身が使う 6 MiB を除いた 59392 KiB が `total` です。

| 列 | 意味 |
| --- | --- |
| `total` | 使える物理メモリの全体 |
| `used` | プロセスなどが使っている量 |
| `free` | だれも使っていない量 |
| `buff/cache` | ファイルの中身をメモリに置いているぶん（**ページキャッシュ**。第 15 章） |
| `available` | 新しくプログラムを動かすときに、使える見込みの量 |

`used` は 8292 です。触ったほうの `memtouch` の 8 MiB が、ほぼそのまま出ています。確保だけのほうは、`used` を増やしていません。

`free` と `available` の違いには、注意が要ります。ページキャッシュは、ディスクにあるファイルの写しです。メモリが足りなくなったら捨ててかまわないので（必要になれば、また読めばよい）、`available` には、キャッシュのうち捨てられるぶんが足されています。**メモリが足りるかどうかを見るときは、`free` の列ではなく `available` の列を見ます**。本物の Linux を長く動かしていると、`free` はとても小さくなり、`buff/cache` が大きくなります。空いているメモリをキャッシュに使うのは無駄ではないので、これは正常です。

`free` は、`/proc/meminfo` を読んで形を整えているだけです。

```sh run title="free の元になっているファイル"
grep -E '^(MemTotal|MemFree|MemAvailable|Cached|AnonPages|PageTables)' /proc/meminfo
```

`AnonPages` は、全プロセスの無名メモリの合計です。プロセスを終わらせると、フレームはすぐに返されます。

```sh run title="プロセスが終わると、メモリは返る"
kill %1 %2
free
```

`used` は 60 に戻りました。

### 約束しすぎる：オーバーコミット

「確保しただけでは減らない」ということは、カーネルは、**物理メモリより多くの量を約束できる**ということです。40 MiB を確保するプロセスを、2 つ動かします。

```sh run title="59 MiB の機械で、80 MiB を約束する"
memtouch -n 40M 60 > /dev/null &
memtouch -n 40M 60 > /dev/null &
ps -o pid,vsz,rss,comm
free
kill %1 %2
```

2 つの VSZ を足すと 80 MiB を超えますが、どちらの `mmap` も成功しています。`free` の `used` は 100 で、ほとんど増えていません。これを**オーバーコミット**（overcommit。約束しすぎ）と呼びます。飛行機の座席を、来ない客を見込んで多めに売るのと同じ考えです。全員が本当に触りに来たらどうなるかは、この章の最後で見ます。

明らかに無理な量は、その場で断られます。

```sh run error title="物理メモリより大きい確保は、断られる"
memtouch -n 100M
```

`mmap` が `ENOMEM`（Cannot allocate memory）を返しました。

## fork とコピーオンライト {#cow}

第 7 章で、`fork` は親の複製を作ると説明しました。メモリも複製されます。けれども、そのときに「実際には、すぐにはコピーしない」と予告しました。それを確かめます。

`memfork` は、メモリに書き込んでから `fork` し、子がその一部だけを書き換える練習用のコマンドです。4 MiB（1024 ページ）を使い、子は 16 ページだけ書き換えます。

```sh run title="fork しても、空きメモリは減らない"
memfork 4M 16
```

4 行を、順に読みます。

1. 親が 4 MiB に書き込み、先頭に `parent` と書きました。このときの空きメモリが基準です
2. `fork` の直後、子が同じ番地を読むと `parent` と読めます。**空きメモリは、1 kB も減っていません**。4 MiB を持つプロセスが 2 つになったのに、です
3. 子が 16 ページに書くと、**ページフォルトが 16 回**起きて、空きメモリが 64 kB（16 ページぶん）減りました。子の側では、先頭が `child!` に変わりました
4. 子が終わったあと、親が同じ番地を読むと、`parent` のままです

`fork` のとき、カーネルは**ページ表だけ**を複製します。親と子のページ表は、同じフレームを指します。そして、書けるページを、親と子の両方で「読み取り専用」にして、**コピーオンライト**（copy-on-write。CoW。書くときにコピー）の印をつけます。

```fig pagetable fork はページ表だけを複製する。書こうとした側が、そのページだけを自分用に複製する
{
  frames: [ { n: 30 }, { n: 31 }, { n: 32 }, { n: 33 } ],
  steps: [
    {
      title: 'fork の前',
      say: '親が 3 ページに書き込んであります。どのページも、親だけのもので、書けます。',
      tables: [
        { label: '親', pages: [
          { vpn: '0x7ffff7d87', name: 'mmap', frame: 30, flags: 'rw-' },
```

小さな例で、カーネルの中の出来事を見ます。4 ページを使い、子は 1 ページだけ書きます。

```sh run trace="mem" title="コピーオンライトの瞬間"
memfork 16k 1
```

観察の中に、`forkmm`（`fork` でページ表を複製した）と、`cow` が 1 つあります。`cow` の `from` が元のフレーム、`frame` が新しく割り当てられたフレームです。`copied: true` は、中身を写したことを表します。

この仕組みのおかげで、シェルがコマンドを実行するたびの `fork` は、とても安く済みます。`fork` の直後に `execve` すれば、アドレス空間はまるごと新しいプログラムのものに作り直されるので、結局 1 ページもコピーされません。第 7 章の「なぜ fork と exec に分かれているのか」が成り立つのは、コピーオンライトがあるからです。

## ファイルを mmap する {#mmap-file}

`mmap` には、もう 1 つの使い方があります。**ファイルを、アドレス空間に写す**ことです。写したあとは、`read` を呼ばなくても、メモリを読むだけでファイルの中身が読めます。

`mmapcat` は、`cat` と同じことを `mmap` でする練習用のコマンドです。

```sh run strace title="read を使わない cat"
mmapcat /etc/hostname
```

`read` が、どこにもありません。代わりに `mmap(NULL, 6, PROT_READ, MAP_PRIVATE, 3, 0)` があります。5 つ目の引数が fd の 3、つまり開いた `/etc/hostname` です。`mmap` のあとは、fd を `close` してしまってかまいません。領域がファイルを覚えています。

写した領域に初めて触ると、やはりページフォルトが起きます。このときカーネルは、0 で埋めたフレームではなく、**ファイルのその部分の中身が入ったフレーム**を対応づけます。

実は、この章の最初から、ファイルの `mmap` を見ていました。`maps` の `/usr/bin/cat` や `/usr/lib/libc.so.6` の行です。プログラムの起動（`execve`）とは、実行ファイルとライブラリをアドレス空間に `mmap` することです。ファイルをまるごと読み込むのではないので、大きなプログラムも、使う部分だけがメモリに載ります。

そして、同じファイルを写したページは、**プロセスのあいだで同じフレームを共有**します。libc の命令は、動いている全部のプロセスが使いますが、物理メモリには 1 つしかありません。

### major と minor を見分ける

ファイルを写したページのフォルトが重いか軽いかは、その中身が、すでにメモリ（ページキャッシュ）にあるかどうかで決まります。少し大きなファイルを作って、確かめます。

```sh run title="キャッシュにあれば minor"
seq 1 3000 > big.txt
/usr/bin/time -v mmapcat big.txt 2>&1 > /dev/null | grep 'page faults'
```

`big.txt` は 13893 バイトなので、4 ページにまたがります。作ったばかりのファイルは、中身がまだページキャッシュに残っているので、major は 0 回です。minor が、起動の 13 回に 4 回足されて、17 回になりました。

root として `/proc/sys/vm/drop_caches` に 3 を書くと、ページキャッシュを捨てられます（第 15 章）。捨ててから、同じことをします。

```sh run title="キャッシュになければ major"
echo 3 | sudo tee /proc/sys/vm/drop_caches > /dev/null
/usr/bin/time -v mmapcat big.txt 2>&1 > /dev/null | grep 'page faults'
/usr/bin/time -v mmapcat big.txt 2>&1 > /dev/null | grep 'page faults'
```

1 回目は、**major が 4 回**です。4 ページぶんを、ディスクから読みました。2 回目は、もうキャッシュにあるので、major は 0 回に戻ります。「起動したばかりのプログラムは遅く、2 回目は速い」のは、このためです。

### 写したメモリに書くと、ファイルが変わる

フラグを `MAP_SHARED` にして写すと、メモリへの書き込みが、ファイルに反映されます。`mmapcat -w` は、写した領域の先頭に文字列を書き込みます。

```sh run title="write を呼ばずに、ファイルを書き換える"
cp /etc/hostname h.txt
mmapcat -w ZU h.txt
cat h.txt
```

`h.txt` の中身が、`ZUkai` に変わりました。`mmapcat` は `write` を呼んでいません。メモリに書いただけです。データベースなどは、この方法で大きなファイルを扱います。

`MAP_PRIVATE` と `MAP_SHARED` の違いをまとめます。`maps` の権限の 4 文字目（p と s）が、これです。

| フラグ | 書き込むと | 使いどころ |
| --- | --- | --- |
| `MAP_PRIVATE` | コピーオンライトで自分用のページができる。ファイルは変わらない | プログラムとライブラリの読み込み |
| `MAP_SHARED` | ファイルに反映され、同じファイルを写しているほかのプロセスからも見える | ファイルの編集、プロセス間の共有メモリ |

## メモリが足りなくなったら：OOM killer {#oom}

オーバーコミットのつけを払うときが来ました。`memhog` は、8 MiB ずつ確保して書き込むことを、止められるまで繰り返します。

```sh run error title="メモリを食い尽くす"
memhog 8M
echo "終了ステータス: $?"
```

56 MiB まで進んだところで、`Killed` と表示されて終わりました。終了ステータスは 137、つまり 128 + 9 です（第 8 章）。だれかが **`SIGKILL`** を送りました。送ったのはカーネルです。カーネルのログを見る `dmesg` で、記録を読みます。

```sh run title="カーネルのログ"
dmesg | grep -A2 'oom-killer'
```

`Out of memory: Killed process …（memhog）`。空きフレームがなくなり、捨てられるキャッシュも捨て終わると、カーネルは **OOM killer**（Out Of Memory killer）を動かします。OOM killer は、プロセスを 1 つ選んで `SIGKILL` で終わらせ、そのメモリを取り返します。`anon-rss` が、殺されたときに持っていた無名メモリの量です。

だれを選ぶかは、おおまかに言うと「**いちばんメモリを使っているプロセス**」です。プロセスごとの点数が `/proc/PID/oom_score` にあり、点数の高いものが選ばれます。

```sh run title="oom_score：殺されやすさの点数"
memhog 8M > /dev/null &
sleep 0.5
ps -o pid,rss,comm
cat /proc/$!/oom_score /proc/$$/oom_score
wait
```

メモリを 48 MiB ほど使っている `memhog` の点数は 966、シェルは 1 です。`wait` で待っていると、`memhog` はまた殺されます。

OOM killer について、覚えておくことが 3 つあります。

- **殺されるのは、メモリを要求したプロセスとは限りません**。たまたま最後の 1 ページを要求したのが小さなプロセスでも、選ばれるのは点数の高いプロセスです
- **`malloc` や `mmap` の戻り値を調べても、防げません**。確保は成功していて、足りなくなるのは、あとで触ったときだからです。`SIGKILL` は捕まえられないので、後片づけもできません
- 本物の Linux で「プログラムが、何も言わずに突然消えた」ときは、まず `dmesg` か `journalctl -k` で `Out of memory` を探します

:::note スワップ
本物の Linux の多くは、**スワップ**（swap）を持っています。メモリが足りなくなったら、しばらく使われていない無名ページの中身をディスクに書き出して、フレームを空けます。あとでそのページに触ると、major のページフォルトでディスクから読み戻します。スワップがあると OOM は遠のきますが、ディスクはメモリより桁違いに遅いので、読み書きが続くと機械全体がひどく遅くなります。`free` の `Swap:` の行が、その使用量です。この小さな Linux には、スワップがありません。
:::

:::warn 本物との違い
- 番地は毎回同じです（ASLR がない）。物理メモリは 64 MiB だけです
- 本物の `maps` には、もっと多くの行があります（動的リンカ `ld-linux`、`[vvar]`、ライブラリごとの行など）
- 本物のカーネルは、無名ページを「読むだけ」なら、0 で埋まった共通のフレームを全員に見せて、書かれるまでフレームを割り当てません。この小さな Linux は、読んだときにも割り当てます
- 本物の `fork` で実際に複製されるのは、ページ表です。ページ表も大きいので、巨大なプロセスの `fork` には時間がかかります
- 練習用の `memtouch`、`memfork`、`memhog`、`mmapcat` は、本物の Linux にはありません。`/usr/bin/time`、`pmap`、`free`、`dmesg` は本物のコマンドです
:::

:::key この章のまとめ
- プロセスが使う番地は**仮想アドレス**。MMU が、プロセスごとの**ページ表**で**物理アドレス**に変換する。だから、別のプロセスのメモリには触れない
- メモリは 4 KiB の**ページ**（仮想）と**フレーム**（物理）の単位で対応づける。対応のないページや、権限のない使い方は**ページフォルト**になる
- アドレス空間の地図は `/proc/PID/maps`、`pmap`。text、data、ヒープ、ライブラリ、スタック
- メモリを増やすのは `brk`（ヒープを伸ばす）と `mmap`（新しい領域）。`malloc` は、その上のライブラリ関数
- **デマンドページング**：確保しただけではフレームは割り当てられない。初めて触ったときのページフォルトで割り当てる
- **VSZ** は約束された量、**RSS** は本当に使っている量。機械全体は `free` と `/proc/meminfo`。足りるかどうかは `available` を見る
- **コピーオンライト**：`fork` はページ表だけを複製し、書かれたページだけを、そのときにコピーする
- ファイルも `mmap` で写せる。プログラムとライブラリは、そうやって読み込まれ、プロセスのあいだで共有される。ディスクから読むフォルトが **major**、読まずに済むのが **minor**
- 物理メモリを使い切ると、**OOM killer** が、いちばんメモリを使っているプロセスを `SIGKILL` する。記録は `dmesg` に残る
:::

## 確認問題 {#quiz}

メモリを数字で調べる問題です。どの問題も、新しい Linux から始まります。

:::quiz 本当に使っているメモリ
`memtouch` というプロセスが 1 つ、バックグラウンドで動いています。このプロセスの **VSZ と RSS** を、この順に、空白 1 つで区切って 1 行で表示してください（例：`8580 52`。単位は KiB のまま。見出しは要りません）。

```sh prep
memtouch -n 6M 600 > /dev/null &
```

```sh answer
echo $(ps -o vsz=,rss= -p $(pgrep memtouch))
```

```sh vary
kill %1
memtouch 3M 600 > /dev/null &
```

```sh vary
kill %1
memtouch 1M 600 > /dev/null &
memtouch -n 2M 0 > /dev/null
```

:::hint
`pgrep memtouch` で PID がわかります。`ps -o vsz=,rss= -p PID` のように列名のあとに `=` をつけると、見出しが出ません。`ps` は数字を右にそろえるために空白を入れるので、`echo $(…)` で包むと、空白 1 つの区切りにそろえられます（第 6 章）。`ps -o vsz,rss,comm | grep memtouch` から `awk '{print $1, $2}'` で取り出してもかまいません。
:::
:::

:::quiz 書ける領域はいくつあるか
`target` という名前のプロセスが 1 つ動いています。そのアドレス空間の領域（`/proc/PID/maps` の行）のうち、**書き込める**もの（権限が `rw` で始まるもの）の数を表示してください。

```sh prep
cp /usr/bin/sleep /tmp/target
/tmp/target 600 &
```

```sh answer
grep -c ' rw' /proc/$(pgrep target)/maps
```

```sh vary
kill %1
cp /usr/bin/memtouch /tmp/target
/tmp/target -n 1M 600 > /dev/null &
```

:::hint
`pgrep target` で PID がわかります。`maps` の 2 列目が権限です。`grep -c` は、合う行の数を数えます。
:::
:::

:::quiz ページフォルトを数える
`job.sh` というスクリプトがあります。`sh job.sh` を実行したときに起きる **minor のページフォルトの回数**を、数字だけで表示してください。`job.sh` 自身の出力は、表示しないでください。

```sh prep
echo 'memtouch 2M' > job.sh
```

```sh answer
/usr/bin/time -v sh job.sh 2>&1 > /dev/null | grep Minor | awk '{print $NF}'
```

```sh vary
echo 'memtouch 5M' > job.sh
```

```sh vary
echo 'memtouch -n 5M; cat /etc/hostname' > job.sh
```

:::hint
`/usr/bin/time -v` の報告は標準エラー出力に出ます。`2>&1 > /dev/null` と書くと、標準エラー出力だけをパイプに流して、`job.sh` の標準出力を捨てられます（第 9 章）。`Minor` の行の最後の語が回数です。`awk '{print $NF}'` は、行の最後の語を表示します。
:::

:::quiz OOM killer の記録
この機械では、少し前に、メモリが足りなくなってプロセスが殺されました。カーネルのログから、OOM killer に**殺されたプロセスの名前と、そのときの anon-rss の値**を調べて、`名前 値` の形で 1 行ずつ表示してください（例：`memhog 59288kB`）。

```sh prep
memhog 8M > /dev/null 2>&1 || true
```

```sh answer
dmesg | grep 'Killed process' | sed -E 's/.*\(([a-z]+)\).*anon-rss:([0-9]+kB).*/\1 \2/'
```

```sh vary
cp /usr/bin/memhog /tmp/eater
/tmp/eater 3M > /dev/null 2>&1 || true
```

:::hint
`dmesg | grep 'Killed process'` で、その行が取り出せます。名前は `(` と `)` のあいだ、値は `anon-rss:` のあとにあります。`sed -E 's/.*\((.*)\).*anon-rss:([0-9]+kB).*/\1 \2/'` のように、`\(` と `\)` でかっこそのものに合わせます。`awk` や `cut`、`tr` を組み合わせてもかまいません。
:::
