## プログラムとプロセス {#process}

`/usr/bin/sleep` は、ディスクの上に置いてあるファイルです。これが**プログラム**です。プログラムは、置いてあるだけでは何もしません。

プログラムを実行すると、カーネルはそれをメモリに読み込み、CPU に走らせます。この「実行中のプログラム」1 つ 1 つを**プロセス**（process）と呼びます。料理にたとえると、プログラムはレシピ、プロセスは「いま台所で作っている最中の料理」です。同じレシピから、同時に何皿でも作れます。

確かめましょう。`sleep 300` は 300 秒待つだけのコマンドです。行の終わりに `&` をつけると、終わるのを待たずに次のコマンドを打てます（`&` は第 8 章でくわしく扱います）。

```sh run title="同じプログラムから、プロセスを 2 つ作る"
sleep 300 &
sleep 300 &
ps
```

`ps`（process status）は、いま動いているプロセスの一覧を出すコマンドです。`sleep` が 2 行あります。プログラムのファイルは 1 つですが、プロセスは 2 つです。

```fig graph プログラムはファイル、プロセスは実行中のもの。1 つのプログラムから、いくつでもプロセスを作れる。プロセスはそれぞれ自分の番号と状態を持つ
{
  col: 260, row: 100,
  nodes: [
    { id: 'f', label: '/usr/bin/sleep', sub: 'プログラム（ディスクの上のファイル）', x: 0, y: 0.5, kind: 'ext' },
    { id: 'p1', label: 'sleep 300', sub: 'プロセス。番号と、自分のメモリを持つ', x: 1, y: 0, kind: 'accent' },
    { id: 'p2', label: 'sleep 300', sub: 'プロセス。別の番号、別のメモリ', x: 1, y: 1, kind: 'accent' },

```

カーネルは、プロセスごとに次のようなものを覚えています。この章と、このあとの章で、1 つずつ中を見ていきます。

| プロセスが持つもの | 中身 | 扱う章 |
| --- | --- | --- |
| PID と PPID | 自分の番号と、親の番号 | この章 |
| 状態 | 走っている、待っている、止まっている、終わった | この章 |
| ユーザーとグループ | だれの権限で動いているか | 第 4 章 |
| いまいるディレクトリ、環境変数 | 相対パスの起点と、名前つきの設定 | この章 |

| メモリ | プログラムとデータを置く場所 | 第 13 章 |

## PID と PPID、ps {#ps}

カーネルは、プロセスを作るたびに、新しい番号を 1 つ割り当てます。これが **PID**（process ID）です。上の `ps` の出力の左端の列です。`sleep 300 &` と打ったときに表示された `[1]` の右の数も、その `sleep` の PID でした。

シェル自身もプロセスです。シェルの PID は、特別な変数 `$$` に入っています。

```sh run title="シェル自身の PID と、その親の PID"
echo $$
echo $PPID
```

2 つ目の `$PPID` は、**親プロセスの PID**（parent PID）です。Linux のプロセスは、必ずほかのプロセスから作られます。作ったほうを**親**、作られたほうを**子**と呼びます。どのプロセスも、自分の親がだれかを覚えています。

`ps` に `-o` をつけると、表示する列を選べます。親の PID を並べてみます。

```sh run title="-o で列を選ぶ：PID、親の PID、コマンド名"
ps -o pid,ppid,comm
```

`sleep` も `ps` も、PPID がシェルの PID（`$$` の値）になっています。シェルから打ったコマンドは、**シェルの子プロセス**です。

何もつけない `ps` は、自分の端末で動いているプロセスだけを出します。システム全体を見るには `-e`（every）、くわしく見るには `-f`（full）をつけます。

```sh run title="すべてのプロセスを、くわしく"
ps -ef
```

| 列 | 意味 |
| --- | --- |
| UID | だれの権限で動いているか |
| PID、PPID | 自分の番号と、親の番号 |
| C、STIME、TIME | CPU の使用率、始まった時刻、これまでに使った CPU 時間 |
| TTY | つながっている端末。`?` は端末なし |
| CMD | 起動したときのコマンド行 |

いちばん上の PID 1 が **init** です。カーネルが起動の最後に作る最初のプロセスで、PPID は 0（親はいない）です。ほかのすべてのプロセスは、init の子孫です。シェルの CMD が `-sh` と表示されているのは、「ログインしたときに起動されたシェル」という印です。

:::note 本物の Linux では
本物の Linux で `ps -ef` を実行すると、ふつう数十から数百行が出ます。PID 1 は多くの場合 `systemd` です（第 17 章）。PPID が 0 のプロセスがもう 1 つあり（PID 2 の `kthreadd`）、その子として、カーネルの中で動く「カーネルスレッド」が `[kworker/0:1]` のように角かっこつきで並びます。この本の小さな Linux には、カーネルスレッドはありません。
:::

## プロセスの木：pstree {#tree}

親と子の関係をたどると、init を根とする 1 本の木になります。`pstree` は、それを木の形で表示します。`-p` をつけると PID も出ます。

```sh run title="プロセスの木"
pstree -p
```


`pstree` 自身も木の中にいます。`ps` も `pstree` も、「自分が動いている瞬間」のプロセスを表示するからです。

## /proc/PID を覗く {#proc}

`ps` は、プロセスの情報をどこから得ているのでしょうか。答えは `/proc` です。`/proc` は、ディスクの上にはない特別なディレクトリで、カーネルが「いまの自分の中身」をファイルの形で見せています（第 12 章）。

```sh run title="/proc の中。数字の名前のディレクトリが、プロセス 1 つ 1 つ"
ls /proc
```

数字の名前が、PID です。その中に、そのプロセスの情報が入っています。直前に `&` で起動したプロセスの PID は `$!` に入っているので、2 つ目の `sleep` を覗いてみます。

```sh run title="status：名前、状態、PID、親の PID"
echo $!
head -6 /proc/$!/status
```

`Name` がコマンド名、`State` が状態（`S` は待っている。後の節で説明します）、`Pid` と `PPid` が自分と親の番号です。

```sh run title="cmdline、cwd、exe、fd"
tr '\0' ' ' < /proc/$!/cmdline; echo
ls -l /proc/$!/cwd /proc/$!/exe
ls -l /proc/$!/fd
```

| ファイル | 中身 |
| --- | --- |
| `cmdline` | 起動したときの引数。引数の区切りは空白ではなく、値が 0 のバイト。上では `tr` で空白に変えて表示した |
| `cwd` | そのプロセスがいまいるディレクトリへのシンボリックリンク |
| `exe` | 実行しているプログラムのファイルへのシンボリックリンク |
| `fd/` | 開いているファイル。0、1、2 は標準入力、標準出力、標準エラー出力で、どれも端末（`/dev/pts/0`）につながっている（第 9 章） |

`/proc/self` は、「これを読んでいるプロセス自身」を指す特別な名前です。

```sh run title="/proc/self は、読んでいる本人"
head -1 /proc/self/status
```

`head` が自分自身の `status` を読んだので、`Name` は `head` です。

`ps` が `/proc` を読んでいることも、確かめられます。`strace` は、コマンドが呼んだシステムコールを表示するコマンドです（第 10 章）。`-e trace=openat` で、ファイルを開く `openat` だけに絞ります。

```sh run title="ps は /proc の中のファイルを開いて読んでいる"
strace -e trace=openat ps 2>&1 | head -6
```

`ps` は特別な方法を使っていません。`/proc` を一覧して、数字の名前のディレクトリの中を、1 つずつ開いて読んでいるだけです。

2 つの `sleep` は、ここで終わらせておきます。`kill` はプロセスを終わらせるコマンドで、`%1` と `%2` は `&` で起動した 1 番目と 2 番目のジョブを指します（第 8 章）。

```sh run title="後片づけ"
kill %1 %2
ps
```

## fork と exec：シェルがコマンドを実行する仕組み {#fork}

シェルに `ls notes` と打つと、`ls` のプロセスが生まれ、仕事をして、消えます。このとき Linux は、「新しいプロセスを作って、そこで ls を走らせる」という 1 つの操作を使いません。**2 つの操作**に分けます。

1. **fork**（フォーク）：自分の**複製**を作る。メモリも、開いているファイルも、いまいるディレクトリも、そっくり同じ子プロセスができる。違うのは PID だけ
2. **exec**（エグゼク）：自分の中身を、**別のプログラムに入れ替える**。PID はそのまま。プロセスは新しく作られない

そして親は、**wait** で子が終わるのを待ちます。ボタンで段階を切り替えて見てください。

### システムコールの列で確かめる

この本の Linux は、シェル自身が呼んだシステムコールも表示できます。次のブロックを実行すると、コマンドの出力の下に、システムコールの列が出ます。

```sh run strace="all" title="ls notes を実行したときの、シェルと子プロセスのシステムコール"
ls notes
```

行が多いですが、見てほしいのは次の 4 つです。

| 行 | 意味 |
| --- | --- |
| `clone(…) = 数` | シェルが子プロセスを作った。Linux では、fork は `clone` というシステムコールで実現されている。戻り値が子の PID |
| `[pid 数] execve("/usr/bin/ls", ["ls", "notes"], …) = 0` | 子が、自分を `ls` に入れ替えた。`[pid 数]` は、その行がどのプロセスのものかを表す |
| `[pid 数] exit_group(0) = ?` と `+++ exited with 0 +++` | `ls` が終了ステータス 0 で終わった |
| `[pid 2] wait4(-1, [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], …) = 数` | シェルが、子の終了を受け取った。「ふつうに終わった、終了ステータスは 0」と読める。戻り値が、終わった子の PID |

`clone` と `execve` のあいだにある `setpgid` と `rt_sigaction` は、ジョブとシグナルの準備です（第 8 章）。`execve` のあとの `openat` や `getdents64`、`write` は、`ls` の本来の仕事（ディレクトリを読んで、名前を書き出す）です。

時間の流れに沿って描くと、次のようになります。

### なぜ 2 つに分かれているのか

「複製してから入れ替える」は、遠回りに見えます。しかし、この**すき間**が大事です。fork のあと、exec の前に、子は「まだシェルの複製」として好きな準備ができます。たとえば `ls > out.txt` のリダイレクトは、子が exec の前に標準出力を out.txt に付け替えることで実現されています（第 9 章）。`ls` のプログラムは、リダイレクトのことを何も知りません。

:::deep fork は、メモリを本当に全部コピーするのか
しません。すぐに exec で捨ててしまうものを全部コピーするのは無駄です。カーネルは、親と子に同じメモリを**共有**させておき、どちらかが書き換えようとしたページだけを、そのときにコピーします。これを**コピーオンライト**（copy-on-write）と呼びます。第 13 章で、実際にページの数を数えて確かめます。
:::

### exec だけを使う

シェルの組み込みコマンド `exec` は、fork をせずに、シェル自身を別のプログラムに入れ替えます。子のシェルを 1 つ起動して、その中で試します。

```sh run title="exec すると、同じ PID のまま別のプログラムになる"
sh -c 'echo "sh の PID は $$"; exec ps -o pid,ppid,comm'
```

`sh -c '…'` で起動した子のシェルが、自分の PID を表示してから、`exec` で `ps` に入れ替わりました。`ps` の PID は、直前に表示された `sh` の PID と同じです。プロセスは作られていません。

### 組み込みコマンドは fork しない

`cd` のような**組み込みコマンド**（第 2 章）は、シェル自身が実行します。fork も exec も起きません。

```sh run strace="all" title="cd は、シェル自身が chdir を呼ぶ"
cd /tmp
```

```sh run title="戻っておく"
cd
```

`clone` も `execve` もなく、シェル（PID 2）が自分で `chdir("/tmp")` を呼んでいます。`cd` が組み込みでなければならない理由は、この章の最後の節でわかります。

## 終了ステータスと wait、ゾンビ {#zombie}

### 終了ステータスは、親が受け取る

プロセスは、終わるときに終了ステータス（第 6 章）を残します。それを受け取るのは、**親**です。親が `wait4` を呼ぶと、カーネルは終わった子の終了ステータスを渡します。シェルは、受け取った値を `$?` に入れます。

```sh run title="子の終了ステータスが、親のシェルの $? に入る"
sh -c 'exit 3'; echo $?
```

`&` で起動したプロセスは、シェルの組み込みコマンド `wait` で待てます。`wait PID` は、そのプロセスが終わるまで待ち、その終了ステータスを自分の終了ステータスにします。

```sh run title="バックグラウンドのプロセスを wait で待つ"
sh -c 'sleep 2; exit 5' &
wait $!; echo "終了ステータス $?"
```

### 親が受け取らないと、ゾンビになる

では、子が終わったのに、親が `wait` を呼ばなかったら、どうなるでしょうか。

カーネルは、終了ステータスを捨てるわけにいきません。親があとで聞きに来るかもしれないからです。そこで、終わったプロセスは、メモリや開いていたファイルをすべて手放したうえで、**プロセス表の 1 行（PID と終了ステータス）だけ**を残します。この「終わったのに、まだ回収されていないプロセス」を**ゾンビ**（zombie）と呼びます。

練習用のコマンド `zombie` で、わざと作ってみます。`zombie 60` は、子プロセスを 1 つ作り、子はすぐ終わりますが、親は `wait` を呼ばずに 60 秒待ち続けます。

```sh run title="ゾンビを作る"
zombie 60 &
ps -o pid,ppid,stat,comm
```

STAT の列が `Z` で、名前に `<defunct>`（機能していない）とついた行が、ゾンビです。その PPID は、もう 1 つの `zombie`（親）の PID になっています。

ゾンビは、すでに終わっています。だから、**終わらせることができません**。どんなプロセスも強制的に終わらせる `kill -9`（第 8 章）を、ゾンビに送ってみます。

```sh run title="ゾンビに kill -9 を送っても、消えない"
ps -o pid,stat | grep Z | while read pid stat; do kill -9 $pid; done
ps -o pid,ppid,stat,comm
```

`Z` の行は、そのままです。ゾンビを消す方法は 2 つしかありません。

1. 親が `wait` を呼んで、回収する
2. 親が終わる。すると、ゾンビは init に引き取られ、init が回収する（次の節）

2 つ目を試します。親の `zombie` を終わらせます。

```sh run title="親を終わらせると、ゾンビも消える"
kill %1
ps -o pid,ppid,stat,comm
```

:::note ゾンビは害があるのか
ゾンビは、メモリも CPU も使いません。使っているのはプロセス表の 1 行と、PID が 1 つだけです。ですから、数個のゾンビは害がありません。問題になるのは、長く動き続けるプログラムが子を作っては回収し忘れ、ゾンビが何万もたまる場合です。PID を使い切ると、新しいプロセスを作れなくなります。ゾンビを見つけたら、直すべきなのはゾンビではなく、**回収しない親**です。
:::

## 孤児と init {#orphan}

逆の順番を考えます。**親が、子より先に終わったら**、どうなるでしょうか。親をなくしたプロセスを**孤児**（orphan）と呼びます。

練習用のコマンド `orphan 60` は、60 秒待つ子プロセスを 1 つ作って、親はすぐに終わります。

```sh run title="孤児を作る"
orphan 60
ps -o pid,ppid,stat,comm
pstree -p
```

残った `orphan` の **PPID が 1** になっています。`pstree` でも、シェルの下ではなく、init の直接の子になっています。カーネルは、親をなくしたプロセスの親を、**init（PID 1）に付け替えます**。

```fig tree 孤児は init に引き取られる。ボタンで、親が終わる前とあとを切り替えて見てください
{
  root: { label: 'init', note: 'PID 1', children: [] },
  steps: [
    {
      title: '親が終わる前',

      root: {
        label: 'init', note: 'PID 1',
        children: [
          { label: 'sh', note: 'PID 2', children: [

              { label: 'orphan', note: '子。60 秒待つ', hl: true },

      },

    {
      title: '親が終わったあと',

      root: {
        label: 'init', note: 'PID 1。孤児の新しい親',
```

init の大事な仕事の 1 つが、これです。init は、ずっと `wait` を呼び続けていて、引き取った子が終わると、すぐに回収します。だから、孤児は終わってもゾンビとして残りません。前の節で「親を終わらせるとゾンビも消える」と書いたのは、ゾンビが孤児になって init に引き取られ、init がすぐ回収したからです。

孤児を終わらせておきます。

```sh run title="後片づけ"
ps -o pid,comm | grep orphan | while read pid comm; do kill $pid; done
ps -o pid,ppid,stat,comm
```

:::note 本物の Linux では
孤児の引き取り先は、いつも PID 1 とは限りません。本物の Linux では、プロセスが「自分の子孫の孤児は、自分が引き取る」と宣言できます（subreaper）。デスクトップ環境では、`systemd --user` というプロセスがこの役をしていることが多く、そのとき孤児の PPID は 1 ではなく、そのプロセスの PID になります。
:::

## プロセスの状態：R、S、T、Z {#state}

`ps` の STAT の列の最初の 1 文字は、プロセスの**状態**です。主なものは 4 つあります。

| 文字 | 状態 | 意味 |
| --- | --- | --- |
| `R` | 実行可能（running / runnable） | CPU で走っている、または CPU の順番を待っている |
| `S` | 待ち（sleeping） | 何かが起きるのを待って眠っている。キー入力、時間の経過、子の終了など |
| `T` | 停止（stopped） | シグナルで一時停止させられている（第 8 章） |
| `Z` | ゾンビ（zombie） | 終わったが、親にまだ回収されていない |

```fig graph プロセスの状態の移り変わり。ほとんどのプロセスは、ほとんどの時間を S（待ち）で過ごす
{
  col: 230, row: 110,
  nodes: [
    { id: 'new', label: 'fork', sub: '生まれる', x: 0, y: 0, kind: 'ext' },
    { id: 'R', label: 'R', sub: '実行可能', x: 1, y: 0, kind: 'accent' },
    { id: 'S', label: 'S', sub: '待ち', x: 2, y: 0 },
    { id: 'T', label: 'T', sub: '停止', x: 1, y: 1, kind: 'stack' },
    { id: 'Z', label: 'Z', sub: 'ゾンビ', x: 2, y: 1, kind: 'muted' },
    { id: 'gone', label: '消える', sub: '親が wait で回収', x: 3, y: 1, kind: 'ghost', mono: false },
  ],
  edges: [
    { from: 'new', to: 'R' },
    { from: 'R', to: 'S', label: '待つ（read、sleep、wait）', curve: -26 },

    { from: 'T', to: 'R', label: 'SIGCONT', curve: -22 },
    { from: 'R', to: 'Z', label: 'exit' },
    { from: 'Z', to: 'gone' },
  ],
}
```

4 つの状態を、同時に作ってみます。`spin` は、CPU を使い続けるだけの練習用のコマンドです。`kill -STOP` は、プロセスを一時停止させます。

```sh run title="R、S、T、Z を 1 つの画面に並べる"
spin &
sleep 300 &
zombie 60 &
kill -STOP %2
ps -o pid,ppid,stat,comm
```

| コマンド | STAT | なぜ |
| --- | --- | --- |
| `sh` | `S` | 子の `ps` が終わるのを `wait4` で待っている |
| `spin` | `R` | 計算を続けていて、何も待っていない |
| `sleep` | `T` | `kill -STOP` で止められた |
| `zombie`（親） | `S` | 時間がたつのを待っている |
| `zombie <defunct>` | `Z` | 終わったが、親が回収していない |
| `ps` | `R` | いま、まさに走っている |

2 文字目は補足です。`s` は**セッションリーダー**（端末にログインしたシェル）、`+` は**前景**（いま端末を使っている）のプロセスを表します。どちらも第 8 章で説明します。

`R` は「走っている」とは限りません。この小さな Linux の CPU は 1 つなので、`ps` が走っている瞬間、`spin` は CPU の順番を待っています。「走れる状態にある」のが `R` です。CPU をどう分け合うかは、第 14 章で見ます。

```sh run title="後片づけ"
kill %1 %2 %3
wait
ps -o pid,ppid,stat,comm
```

## 環境変数は、子にコピーされる {#env}

fork は親の複製を作るので、子は親の**環境変数**（第 2 章）も受け継ぎます。ただし、受け継ぐのは `export` した変数だけです。`export` していないシェルの変数は、シェルの中だけのもので、exec で別のプログラムに入れ替わるときに渡されません。

```sh run title="export した変数だけが、子に渡る"
color=red
export FRUIT=apple
sh -c 'echo "子: color=[$color] FRUIT=[$FRUIT]"'
```

大事なのは、渡るのが**コピー**だということです。子が変数を書き換えても、親の変数は変わりません。

```sh run title="子が変えても、親には戻らない"
sh -c 'FRUIT=banana; echo "子: $FRUIT"'
echo "親: $FRUIT"
```

逆に、子を作った**あと**で親が変数を変えても、すでに動いている子には届きません。プロセスが起動したときの環境変数は、`/proc/PID/environ` で見られます（区切りは `cmdline` と同じく、値が 0 のバイトです）。

```sh run title="起動したあとの親の変更は、子に届かない"
sleep 300 &
FRUIT=cherry
tr '\0' '\n' < /proc/$!/environ | grep FRUIT
sh -c 'echo "新しい子: $FRUIT"'
kill %1
```

先に起動した `sleep` の環境は `FRUIT=apple` のままで、あとから起動した子は `cherry` を受け取りました。


この「親から子へ、一方通行」という性質は、環境変数に限りません。いまいるディレクトリも、umask（第 4 章）も、同じです。**子は、親の状態を変えられません。**

## サブシェル ( ) と cd {#subshell}

### ( ) は、シェルを fork して実行する

コマンドを丸かっこ `( )` で囲むと、シェルは自分を fork して、**子のシェル**の中でそれを実行します。これを**サブシェル**（subshell）と呼びます。子の中で起きたことは、親に戻りません。

```sh run title="( ) の中の cd と代入は、外に影響しない"
(cd /tmp; pwd; x=5; echo "中: x=$x")
pwd
echo "外: x=[$x]"
```

かっこの中では `/tmp` に移って `x` に 5 を入れましたが、かっこを出ると、いまいるディレクトリは元のままで、`x` は空です。システムコールの列で、fork が起きていることを確かめます。

```sh run strace="all" title="( ) は clone で子を作り、子が chdir する"
(cd /tmp; pwd)
```

`clone` で子ができ、`chdir("/tmp")` の行には `[pid 数]` がついています。ディレクトリを移ったのは、子です。親のシェル（PID 2）は、`wait4` で待っていただけです。

サブシェルは、「一時的に別のディレクトリで作業して、終わったら元の場所にいたい」ときに便利です。

```sh run title="元の場所を動かずに、別のディレクトリで作業する"
(cd /var/log && wc -l access.log)
pwd
```

第 6 章で、「パイプの右側の `while` の中で変えた変数は、外に戻らない」という例を見ました。あれも同じ理由です。パイプの両側は、それぞれ fork した子の中で実行されます。

### スクリプトの中の cd は、呼んだシェルを動かさない

スクリプトを実行するときも、シェルは fork して、子に実行させます。だから、スクリプトの中で `cd` しても、呼んだ側のシェルは動きません。

```sh run title="スクリプトの中の cd"
cat > gotmp.sh <<'EOF'
cd /tmp
echo "スクリプトの中: $(pwd)"
EOF
sh gotmp.sh
pwd
```

呼んだシェルの中でファイルを実行したいときは、`.`（ドット）コマンドを使います（`source` と書いても同じです）。`.` は fork せず、いまのシェル自身がファイルを読んで実行します。

```sh run title=". で読み込むと、いまのシェルが実行する"
. ./gotmp.sh
pwd
cd
```

今度は、シェル自身が `/tmp` に移りました。`~/.profile` のような設定ファイルが `.` で読み込まれるのは、そこで設定した変数を、シェル自身に残すためです。

### だから cd は組み込みコマンド

ここまで来ると、`cd` が組み込みコマンドである理由がわかります。もし `cd` が `/usr/bin/cd` という外部コマンドだったら、シェルは fork して、子が exec して、子が `chdir` して、子が終わります。親のシェルは、1 歩も動きません。**自分の状態を変えるコマンドは、自分で実行するしかない**のです。`export`、`umask`、`exit` が組み込みなのも、同じ理由です。

## 確認問題 {#quiz}

この章の内容を、自分でコマンドを書いて確かめます。どの問題も、プロセスの数や場所を少し変えた状態でも試されるので、答えを直接 `echo` しただけでは通りません。

:::quiz ゾンビを数える
いま、ゾンビのプロセスがいくつかあります。システム全体のプロセスのうち、状態が `Z` のものの数を、数だけ 1 行で出力してください。

```sh prep
zombie 600 &
```

```sh answer
ps -e -o stat | grep -c Z
```

```sh vary
zombie 600 &
zombie 600 &
```

:::hint
`ps -e -o stat` で、すべてのプロセスの状態の列だけを出せます。`grep -c` は、合った行の数を数えます。
:::
:::

:::quiz プロセスがいるディレクトリ
直前にバックグラウンドで起動したプロセス（PID は `$!`）が、どのディレクトリにいるかを調べて、そのパスを 1 行で出力してください。

```sh prep
cd /var/log
sleep 600 &
cd
```

```sh answer
readlink /proc/$!/cwd
```

```sh vary
cd /usr/bin
sleep 700 &
cd
```

:::hint
`/proc/PID/cwd` は、そのプロセスがいまいるディレクトリへのシンボリックリンクです。リンクの先は `readlink` で読めます。
:::
:::

:::quiz 子に変数を渡す
ホームディレクトリの `show.sh` は、環境変数 `GREETING` の値を使って挨拶を表示するスクリプトです。`GREETING` の値を `ohayo` にして、`sh show.sh` を実行してください。

```sh prep
echo 'echo "$GREETING, $(cat name.txt)!"' > show.sh
echo taro > name.txt
```

```sh answer
export GREETING=ohayo
sh show.sh
```

```sh vary
echo hanako > name.txt
```

:::hint
`GREETING=ohayo` と代入しただけでは、子プロセスには渡りません。`export` するか、`GREETING=ohayo sh show.sh` のようにコマンドの前に書きます。
:::
:::

:::quiz init の子を数える
親が init（PID 1）であるプロセスの数を、数だけ 1 行で出力してください。ログインシェルのほかに、孤児になったプロセスがいくつかいます。

```sh prep
orphan 600
```

```sh answer
ps -e -o ppid | grep -c '^ *1$'
```

```sh vary
orphan 600
orphan 600
for i in 1 2 3 4 5 6; do /usr/bin/true; done
sh -c 'sleep 600; true' &
sleep 1
```

:::hint
`ps -e -o ppid` で、すべてのプロセスの「親の PID」の列だけを出せます。その中から、ちょうど `1` の行を数えます。`grep 1` では `10` や `21` にも合ってしまうので、行頭 `^` と行末 `$` を使います。列は右寄せなので、数の前に空白があります。
:::
:::

:::key この章のまとめ
- **プログラム**はファイル、**プロセス**は実行中のプログラム。1 つのプログラムから、いくつでもプロセスを作れる
- プロセスには **PID** があり、親の **PPID** を覚えている。すべてのプロセスは **init（PID 1）** の子孫で、`pstree` で木として見える
- `ps` は一覧を出す。`-e` ですべて、`-f` でくわしく、`-o` で列を選ぶ。情報のもとは **`/proc/PID/`**（status、cmdline、cwd、exe、fd、environ）
- シェルはコマンドを **fork**（複製）→ **exec**（入れ替え）で実行し、**wait** で終わるのを待つ。Linux のシステムコールでは `clone`、`execve`、`wait4`
- fork と exec のあいだのすき間で、子はリダイレクトなどの準備ができる。組み込みコマンドは fork しない
- 終わった子の終了ステータスは、親が `wait` で受け取る。受け取られるまでの子が**ゾンビ**（`Z`）。ゾンビは kill できない。直すべきは回収しない親
- 親が先に終わった子は**孤児**。init が引き取り、終わったら回収する
- 状態は **R**（実行可能）、**S**（待ち）、**T**（停止）、**Z**（ゾンビ）
- 環境変数、いまいるディレクトリは、fork で親から子へ**コピー**される。子が変えても親には戻らない。だから `( )` の中の `cd` は外に影響せず、`cd` は組み込みコマンドでなければならない
:::
