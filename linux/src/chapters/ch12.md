## 1 本の木に、いくつものファイルシステム {#one-tree}

前の章で、`/tmp` へのハードリンクや `rename` が `EXDEV`（Invalid cross-device link）で失敗しました。`/` も `/tmp` も同じ 1 本の木の中にあるのに、「別の装置」だと言われたのです。

Linux のディレクトリの木は、1 つのファイルシステムでできているのではありません。**いくつものファイルシステムを、つなぎ合わせて 1 本に見せています**。どこにどのファイルシステムがつながっているかは、`mount` コマンドを引数なしで実行すると見られます。

```sh run title="つながっているファイルシステムの一覧"
mount
```

1 行が、1 つのファイルシステムです。形は「**何を** on **どこに** type **種類**（オプション）」です。

| 何を | どこに | 種類 | 中身 |
| --- | --- | --- | --- |
| `/dev/sda1` | `/` | ext4 | ディスクの上のファイルシステム。木の根 |
| `proc` | `/proc` | proc | プロセスとカーネルの情報（procfs） |
| `udev` | `/dev` | devtmpfs | 装置への入口（デバイスファイル） |
| `tmpfs` | `/tmp` | tmpfs | メモリの上のファイルシステム |

ファイルシステムを木のどこかのディレクトリにつなぐことを**マウント**（mount）、つないだ場所のディレクトリを**マウントポイント**と呼びます。Windows のように `C:` `D:` とドライブごとに木が分かれるのではなく、Unix では全部が `/` から始まる 1 本の木に収まります。

```fig tree 1 本の木に見えるが、4 つのファイルシステムがつながっている。色のついたディレクトリがマウントポイント
{
  root: { label: '/', kind: 'ext4', note: '/dev/sda1。ディスクの上', children: [
    { label: 'etc', note: 'ext4 の中' },
    { label: 'home', note: 'ext4 の中', children: [ { label: 'you' } ] },
    { label: 'proc', kind: 'proc', hl: true, note: 'procfs。プロセスとカーネルの情報', children: [ { label: '1' }, { label: 'uptime' } ] },
    { label: 'dev', kind: 'devtmpfs', hl: true, note: 'devtmpfs。装置への入口', children: [ { label: 'null' }, { label: 'tty' } ] },
    { label: 'tmp', kind: 'tmpfs', hl: true, note: 'tmpfs。メモリの上' },
    { label: 'mnt', note: 'ext4 の中。あとで、ここにつなぐ' },
  ] },
}
```

カーネルが同じ内容を見せているファイルが、`/proc/mounts` です。`mount` コマンドは、これを読んで形を整えています。

```sh run title="カーネルの持っているマウント表"
cat /proc/mounts
```

### どのファイルシステムにあるかを調べる

あるファイルがどのファイルシステムに載っているかは、`df` にパスを渡すとわかります。`-T` をつけると、種類も表示します。

```sh run title="このファイルは、どのファイルシステムの上か"
df -T /home/you/memo.txt /tmp /dev/null
```

前の章の `stat` に出ていた `Device` も、同じことを番号で表しています。

```sh run title="デバイス番号で見分ける"
stat -c '%n: dev=%d inode=%i' / /home /proc /dev /tmp
```

`/` と `/home` は同じデバイス番号、`/proc`、`/dev`、`/tmp` はそれぞれ別の番号です。そして、`/proc`、`/dev`、`/tmp` の inode 番号は、どれも 1 です。inode 番号はファイルシステムごとの通し番号なので、別のファイルシステムなら同じ番号があってかまいません。マウントポイントをまたいだ先は、そのファイルシステムの「根」です。

カーネルは、パスをたどる途中でマウントポイントに来ると、そこから先を、つながれたファイルシステムの根に切り替えます。`EXDEV` は、「その 2 つのパスは、デバイス番号が違う」という意味でした。

## VFS：同じ read が、どこでも動く {#vfs}

ext4 はディスクのブロックを読み、procfs はカーネルの中のデータから文字列を作り、tmpfs はメモリに置きます。中身の作りは、まったく違います。それでも、`cat` は相手を気にしません。

```sh run strace title="/proc のファイルを cat する"
cat /proc/uptime
```

`openat`、`read`、`write`、`read`（0 が返る）、`close`。第 10 章で `/etc/hostname` を読んだときと、同じ列です。`cat` は、相手が procfs だと知りません。

これを可能にしているのが、カーネルの中の **VFS**（Virtual File System。仮想ファイルシステム）という層です。VFS は、「ファイルシステムなら、これらの操作ができること」という共通の約束を決めています。開く、読む、書く、ディレクトリを一覧する、名前から inode を探す、といった操作です。それぞれのファイルシステムは、この約束に合わせて、自分なりのやり方を用意します。


第 9 章の 3 段の表（fd 表、ファイル記述、inode）は、この VFS の持ちものです。inode には「私は procfs のファイルです」という印がついていて、`read` が呼ばれると、VFS は procfs の読み方を呼び出します。同じ `read` というシステムコールが、ファイルごとに違う仕事をします。

新しい種類のファイルシステムを足したいときは、VFS の約束に合う操作をひとそろい書けば済みます。`cat` も `ls` も `cp` も、何も直さずに、その上で動きます。カーネルが知っている種類は、`/proc/filesystems` に並んでいます。

```sh run title="カーネルが知っているファイルシステムの種類"
cat /proc/filesystems
```

`nodev` は、「ディスクなどの装置を必要としない」という印です。印のない ext4 だけが、装置の上に作られます。本物の Linux では、ここに xfs、btrfs、vfat（USB メモリでよく使う）、nfs（ネットワーク越し）など、数十種類が並びます。

## procfs：ファイルではないファイル {#procfs}

`/proc` は、これまで何度も使ってきました。`/proc/PID/fd`、`/proc/PID/status`、`/proc/mounts`。ここで、その正体をはっきりさせます。**`/proc` のファイルは、ディスクのどこにもありません**。

```sh run title="大きさ 0 なのに、中身がある"
ls -l /proc/version
cat /proc/version
cat /proc/version | wc -c
```

`ls -l` の大きさは 0 です。けれども `cat` すると 105 バイトの中身が出てきます。procfs のファイルには、ためてある中身がありません。**`read` されたその瞬間に、カーネルが自分の中のデータから文字列を作って返します**。大きさは、読んでみるまでわからないので、0 と表示されます。

だから、読むたびに中身が違うこともあります。`/proc/uptime` は、起動してからの秒数です。

```sh run title="読むたびに変わる"
cat /proc/uptime
sleep 3
cat /proc/uptime
```

3 秒待つと、1 つ目の数字がおよそ 3 増えます。ファイルを書き換えた人は、だれもいません。

### プロセスごとのディレクトリ

`/proc` の中の数字の名前は、PID です。プロセスが生まれるとディレクトリが現れ、終わると消えます。

```sh run title="プロセスが生まれると現れ、終わると消える"
sleep 100 &
ls -d /proc/[0-9]*
kill $!
wait
ls -d /proc/[0-9]*
```

`mkdir` も `rmdir` も、だれも呼んでいません。procfs が、「いまのプロセス表」をディレクトリの形で見せているだけです。`ps` は、ここを読んで一覧を作っています（第 7 章、第 20 章）。

| パス | 中身 |
| --- | --- |
| `/proc/PID/status` | 名前、状態、親の PID、uid など |
| `/proc/PID/cmdline` | 起動したときのコマンドライン |
| `/proc/PID/cwd` | カレントディレクトリへのリンク |
| `/proc/PID/exe` | 実行しているプログラムへのリンク |
| `/proc/PID/fd/` | 開いている fd（第 9 章） |
| `/proc/PID/maps` | メモリの配置（第 13 章） |
| `/proc/self` | 読んでいるプロセス自身の `/proc/PID` へのリンク |
| `/proc/mounts`、`/proc/meminfo`、`/proc/loadavg`、`/proc/uptime` | システム全体の情報 |

```sh run title="プロセスのカレントディレクトリと、プログラム本体"
readlink /proc/$$/cwd
readlink /proc/$$/exe
```

### 書き込める /proc

`/proc/sys` の下には、**書き込むとカーネルの設定が変わる**ファイルがあります。ホスト名を、ファイルへの書き込みで変えてみます（root の仕事です）。

```sh run root title="ファイルに書いて、カーネルの設定を変える"
cat /proc/sys/kernel/hostname
echo tanuki > /proc/sys/kernel/hostname
hostname
echo zukai > /proc/sys/kernel/hostname
```

`echo` がしたのは、ただの `write` です。procfs は、その `write` を受け取って、カーネルの中のホスト名を書き換えました。設定を変えるための専用のコマンドやシステムコールを覚えなくても、`cat` と `echo` で用が足ります。本物の Linux には、こうした設定が `/proc/sys` の下に千個以上あります。

:::note ふつうのユーザーは書けない
`/proc` のファイルにも、権限があります。`/proc/uptime` は `-r--r--r--` で、だれにも書けません。`/proc/sys` の下は root だけが書けます。他人のプロセスの `/proc/PID/environ`（環境変数）や `/proc/PID/fd` は、本人と root にしか読めません。ファイルの形をしているので、第 4 章の権限の仕組みが、そのまま使えます。
:::

## /dev：装置も、ファイルとして開く {#dev}

`/dev` には、**デバイスファイル**が並んでいます。装置への入口を、ファイルの形にしたものです。

```sh run title="/dev の中"
ls -l /dev
```

行の先頭が `c` のものは、**キャラクタデバイス**（1 バイトずつ読み書きする装置）です。大きさの代わりに、`1, 3` のような 2 つの数字が出ています。これは**メジャー番号**（どのドライバか）と**マイナー番号**（そのドライバの何番目の装置か）です。カーネルは、名前ではなく、この番号で相手のドライバを決めます。`/dev/null` は「1, 3」、`/dev/zero` は「1, 5」です。

本物の Linux では、ディスクを表す**ブロックデバイス**（先頭が `b`。`/dev/sda`、`/dev/nvme0n1` など）もここに並びます。

装置といっても、実体のある機器とは限りません。カーネルが用意している、便利な「にせの装置」がいくつかあります。

### /dev/null：何でも捨てる

```sh run error title="書けば消え、読めばすぐ終わる"
echo "この文は、どこにも残らない" > /dev/null
cat /dev/null | wc -c
ls nope poem.txt 2> /dev/null
```

`/dev/null` に書いたものは、すべて捨てられます（`write` は成功を返します）。読むと、すぐに EOF（0 バイト）です。いらない出力を捨てる（`2> /dev/null`）、空の入力を渡す（`< /dev/null`）ために使います。3 行目では、`nope` がないというエラー文だけが捨てられ、`poem.txt` は表示されています。

### /dev/zero と /dev/full

```sh run error title="0 を出し続ける装置と、いつも一杯の装置"
head -c 8 /dev/zero | hexdump -C
echo test > /dev/full
```

`/dev/zero` は、読むと 0 のバイトがいくらでも出てきます。前の章で、大きなファイルを作るのに使いました。`/dev/full` は、書くと必ず `ENOSPC`（No space left on device）で失敗します。「ディスクが一杯のとき、自分のプログラムが正しくエラーを扱うか」を試すための装置です。

### /dev/random と /dev/urandom

```sh run title="乱数の出てくる装置"
head -c 8 /dev/urandom | hexdump -C
head -c 8 /dev/urandom | hexdump -C
```

読むたびに、違うバイト列が出てきます。暗号の鍵やパスワードを作るときの乱数の出どころです。本物の Linux では、キーボードやディスクの動作のタイミングなど、予測できない出来事を材料にして作ります。

:::warn このサイトの Linux では
この小さな Linux の乱数は、決まった種（シード）から作っています。ページを開き直して同じ順に実行すると、同じバイト列が出ます。本物の `/dev/urandom` は、実行するたびに違う値を返します。
:::

### /dev/tty：自分の端末

```sh run title="端末もデバイスファイル"
tty
ls -l /dev/pts/0
echo "端末に直接書く" > /dev/pts/0
echo "標準出力を捨てても、端末には出せる" > /dev/tty
```

`tty` コマンドは、標準入力につながっている端末の名前を表示します。`/dev/pts/0` が、いま使っている端末です。第 9 章で、fd 0・1・2 が指していたファイルです。ここに `write` すれば、画面に文字が出ます。

`/dev/tty` は、「このプロセスの端末」を指す特別な名前です。標準出力がリダイレクトされていても、端末に直接書けます。パスワードを聞くプログラムなどが使います。

`/dev/stdin`、`/dev/stdout`、`/dev/stderr` は、`/proc/self/fd/0` などへのシンボリックリンクです。「ファイル名を渡さないといけないコマンド」に、標準入出力を渡したいときに使えます。

## tmpfs：メモリの上のファイルシステム {#tmpfs}

`/tmp` は **tmpfs** です。ファイルの中身を、ディスクではなく**メモリ**に置きます。使い方は、ふつうのファイルシステムと変わりません。

```sh run title="/tmp は tmpfs"
echo "一時的なメモ" > /tmp/note.txt
ls -li /tmp
df -hT /tmp
rm /tmp/note.txt
```

inode もあり、権限もあり、`df` には大きさ（8.0M）と使用量が出ます。違いは 2 つです。

- **速い**… ディスクに書かないので、読み書きが速い
- **消える**… 電源を切る（再起動する）と、中身は残らない。メモリの上にしかないから

一時ファイルの置き場所として、ちょうどよい性質です。本物の Linux でも、`/run`（動いているサービスの情報）や `/dev/shm` などが tmpfs です。使ったぶんだけメモリを消費するので、大きなファイルを置くと、メモリが足りなくなることがあります（第 13 章）。

## mount：ファイルシステムを木につなぐ {#mount}

今度は、自分でつないでみましょう。マウントは、root だけができる操作です。

```sh run error title="ふつうのユーザーにはできない"
mount -t tmpfs tmpfs /mnt/usb
```

root になって、`/mnt/usb` というディレクトリを作り、その中にファイルを 1 つ置いておきます。

```sh run root title="準備：マウントポイントにするディレクトリ"
mkdir /mnt/usb
echo "ext4 の上にあるファイル" > /mnt/usb/under.txt
ls /mnt/usb
```

ここに、新しい tmpfs をマウントします。書き方は `mount -t 種類 何を どこに` です。tmpfs には装置がないので、「何を」には、ただの目印として `tmpfs` と書きます。

```sh run root strace title="tmpfs を /mnt/usb にマウントする"
mount -t tmpfs tmpfs /mnt/usb
```

`mount("tmpfs", "/mnt/usb", "tmpfs", 0, NULL) = 0`。`mount` コマンドの仕事は、同じ名前のシステムコールを 1 回呼ぶことです。

```sh run root title="マウントしたあと"
ls -a /mnt/usb
mount | tail -1
stat -c '%n: dev=%d inode=%i' /mnt /mnt/usb
```

3 つのことが起きています。

- `/mnt/usb` の中身が**空**になった。さっき置いた `under.txt` が見えない
- `mount` の一覧に、1 行増えた
- `/mnt/usb` のデバイス番号が、`/mnt` と違うものになり、inode 番号は 1（新しいファイルシステムの根）になった

`under.txt` は、消えたのではありません。**隠れた**だけです。パスをたどるカーネルは、`/mnt/usb` まで来ると、そこにマウントされた tmpfs の根へ切り替えます。下にあった ext4 のディレクトリの中身には、たどり着けなくなります。

```fig tree マウントの前と後。/mnt/usb にマウントすると、パスはそこで新しいファイルシステムの根に切り替わり、下にあったファイルは隠れる
{
  root: { label: '/', kind: 'ext4', children: [
    { label: 'mnt', children: [
      { label: 'usb', note: 'ext4 のふつうのディレクトリ', children: [ { label: 'under.txt', note: 'ext4 の上にあるファイル' } ] },
    ] },
  ] },
  steps: [
    { title: 'マウントの前', say: '<code>/mnt/usb</code> は ext4 のふつうのディレクトリで、中に <code>under.txt</code> があります。' },
    {
      title: 'mount のあと',
      say: '<code>/mnt/usb</code> から先は tmpfs です。新しいファイルシステムは空なので、中には何もありません。<code>under.txt</code> は ext4 の上に残っていますが、パスではたどり着けません。',
      root: { label: '/', kind: 'ext4', children: [
        { label: 'mnt', children: [
          { label: 'usb', kind: 'tmpfs', hl: true, note: 'ここから tmpfs（inode 1）。under.txt は隠れている' },
        ] },
      ] },
    },
    {
      title: 'ファイルを作る',
      say: 'ここに作ったファイルは、tmpfs の上（メモリ）に置かれます。ext4 のディスクは使いません。',
      root: { label: '/', kind: 'ext4', children: [
        { label: 'mnt', children: [
          { label: 'usb', kind: 'tmpfs', hl: true, note: 'tmpfs', children: [ { label: 'top.txt', note: 'tmpfs の上のファイル' } ] },
        ] },
      ] },
    },
    {
      title: 'umount のあと',
      say: 'マウントを外すと、<code>/mnt/usb</code> は元の ext4 のディレクトリに戻り、<code>under.txt</code> がまた見えます。tmpfs の <code>top.txt</code> は、tmpfs ごと消えます。',
    },
  ],
}
```

マウントした先に、ファイルを作ってみます。

```sh run root title="マウントした先に書く"
echo "tmpfs の上にあるファイル" > /mnt/usb/top.txt
ls -li /mnt/usb
df -hT /mnt/usb
```

`top.txt` は、tmpfs の上にあります。`df` に渡したパスが、どのファイルシステムに載っているかも確かめられました。

### 本物のディスクをマウントする

本物の Linux で USB メモリやディスクをつなぐときも、同じ形です。「何を」のところに、ブロックデバイスのファイルを書きます。

```console
# mount -t ext4 /dev/sdb1 /mnt/usb        ← /dev/sdb1（2 台目のディスクの 1 番目の区画）を /mnt/usb に
# mount -o ro /dev/sdb1 /mnt/usb          ← 読み取り専用で（種類は自動で見分けてくれる）
# mount --bind /home/you/notes /mnt/n     ← すでに木の中にあるディレクトリを、別の場所にも見せる（バインドマウント）
```

起動のたびに自動でマウントしたいものは、`/etc/fstab` というファイルに、「何を、どこに、種類、オプション」を 1 行ずつ書いておきます（第 17 章）。バインドマウントは、コンテナが「ホストのディレクトリを、コンテナの中に見せる」ために使っています（第 19 章）。この小さな Linux には、ブロックデバイスとバインドマウントはありません。

## umount：外すときは、だれも使っていないこと {#umount}

マウントを外すのは **`umount`** です（`unmount` ではなく、`n` が 1 つ少ない名前です）。外す前に、わざと「使用中」にしてみましょう。`top.txt` を `sleep` に開かせたままにします。

```sh run root error title="使っているプロセスがいると、外せない"
sleep 300 < /mnt/usb/top.txt &
umount /mnt/usb
```

`target is busy` と断られました。システムコールで見ると、こうです。

```sh run root error strace title="umount が受け取るエラー"
umount /mnt/usb
```

`umount2("/mnt/usb", 0) = -1 EBUSY (Device or resource busy)`。第 10 章の表にあった `EBUSY` です。そのファイルシステムの上のファイルを開いているプロセスがいるあいだは、外せません。外してしまうと、そのプロセスの fd の先がなくなってしまうからです。

「使用中」になるのは、ファイルを開いているときだけではありません。**カレントディレクトリがその中にある**だけでも、使用中です。

```sh run root error title="中に cd しているだけでも、外せない"
kill $!
cd /mnt/usb
umount /mnt/usb
```

`sleep` を終わらせても、今度はシェル自身が `/mnt/usb` の中にいるので、まだ外せません。「USB メモリを安全に取り外せません」と言われるのは、たいていこのどちらかです。だれが使っているかは、`lsof` で探せます（第 9 章）。

外に出てから、外します。

```sh run root title="外に出てから umount する"
cd /
umount /mnt/usb
ls /mnt/usb
mount | wc -l
```

`umount` は成功し、`ls` には **`under.txt` が戻ってきました**。隠れていただけ、ということが確かめられました。tmpfs に作った `top.txt` は、tmpfs ごとなくなっています。`mount` の一覧も、最初の 4 行に戻りました。

:::warn 外す前に、書き終える
本物のディスクでは、`write` したデータは、すぐにはディスクに書かれません。いったんメモリにためられ、あとでまとめて書かれます（第 15 章のページキャッシュ）。`umount` は、たまっているデータを全部書き出してから外します。`umount` せずに USB メモリを引き抜くと、まだ書かれていないデータが失われ、ファイルシステムが壊れることがあります。
:::

## 「すべてはファイル」の範囲と限界 {#everything}

第 1 章で、Unix の考え方の 1 つとして「すべてはファイル」を紹介しました。ここまで読んだ今なら、その中身を正確に言えます。

**いろいろなものに、fd を通して、同じ `open`・`read`・`write`・`close` で触れる。** そして、その多くに、**木の中の名前（パス）がついている**。これが「すべてはファイル」の実際の意味です。

| もの | パスがある | fd で読み書きできる | 章 |
| --- | --- | --- | --- |
| 通常のファイル、ディレクトリ | ○ | ○（ディレクトリは `getdents64`） | 3、11 |
| 端末 | ○（`/dev/pts/0`） | ○ | 9 |
| パイプ | ×（名前つきパイプ FIFO なら ○） | ○ | 9 |
| プロセスやカーネルの情報 | ○（`/proc`） | ○ | 7、この章 |
| 装置（ディスク、乱数、null） | ○（`/dev`） | ○ | この章 |
| ネットワークのソケット | ×（Unix ドメインソケットは ○） | ○ | 16 |

この統一のおかげで、`cat`、`grep`、`>`、`|` といった少ない道具が、どの相手にも使えます。プロセスの状態を調べるのに専用の道具が要らず、`cat /proc/PID/status` で済むのは、この設計の成果です。

けれども、「すべて」は言いすぎです。ファイルの形に収まらないものも、たくさんあります。

- **`read` と `write` だけでは足りない操作がある**。端末の幅を聞く、ディスクを取り出す、といった装置ごとの操作は、`ioctl` という「その他なんでも」のシステムコールで行います。第 10 章で、`ls` が `ioctl(1, TIOCGWINSZ, …)` で端末の幅を聞いていました
- **ソケットは、パスでは開けない**。ネットワークの接続は、`open` ではなく `socket`、`connect`、`accept` という専用のシステムコールで作ります。できあがったものは fd なので、そこから先は `read` と `write` が使えます（第 16 章）
- **プロセスへの操作は、ファイル操作ではない**。プロセスを作る（`fork`）、シグナルを送る（`kill`）、終わりを待つ（`wait`）は、PID を使う専用のシステムコールです。`/proc/PID` に `echo` してもプロセスは止まりません
- **ネットワークの装置は、`/dev` にない**。ネットワークカード（`eth0` など）には、デバイスファイルがありません
- **「ファイル」でも、できないことがある**。パイプや端末は、位置を動かす `lseek` ができません（`ESPIPE`）。`/proc` のファイルは、大きさが 0 と表示されます

:::hist Plan 9：もっと徹底した後継
Unix を作ったベル研究所の人たちは、この「言いすぎ」が気になっていました。1980 年代の後半から、彼らは **Plan 9** という新しい OS を作り、ネットワークも、画面のウィンドウも、プロセスの操作も、本当にすべてをファイルとして見せる設計を試しました。Plan 9 そのものは広まりませんでしたが、Linux の `/proc` は、Plan 9 の考え方を取り入れたものです。プロセスを fd で扱う `pidfd` のように、Linux は今でも少しずつ「ファイルで扱えるもの」を増やしています。
:::

:::warn 本物との違い
- この小さな Linux でマウントできるのは、tmpfs、proc、devtmpfs だけです。ディスク（ブロックデバイス）のマウント、バインドマウント（`mount --bind`）、読み取り専用のマウント（`-o ro`）は使えません
- 本物の Linux には、`/sys`（sysfs。装置とドライバの情報）、`/run`、`/dev/shm` など、もっと多くの「ディスクにないファイルシステム」がマウントされています
- 本物の `/proc` には、この小さな Linux よりずっと多くのファイルがあります
:::

:::key この章のまとめ
- Linux の木は、いくつもの**ファイルシステム**を**マウント**でつなぎ合わせた 1 本の木。`mount`、`/proc/mounts`、`df -T` で見られる。マウントポイントをまたぐと、デバイス番号が変わる
- **VFS** は、システムコールと個々のファイルシステムのあいだの層。同じ `open`・`read`・`write` を、ファイルごとに、そのファイルシステムのやり方へ振り分ける
- **procfs**（`/proc`）は、カーネルの中のデータを、読まれた瞬間に文字列にして見せる。ディスクには何もない。`/proc/sys` に書くと、カーネルの設定が変わる
- **devtmpfs**（`/dev`）は、装置への入口。`/dev/null`（捨てる）、`/dev/zero`（0 を出す）、`/dev/full`（いつも一杯）、`/dev/urandom`（乱数）、`/dev/tty`（自分の端末）。メジャー番号とマイナー番号でドライバが決まる
- **tmpfs** は、メモリの上のファイルシステム。速いが、再起動で消える
- `mount -t 種類 何を どこに` でつなぐ（root だけ）。マウントポイントの下にあったファイルは、隠れる。`umount` で外すと、また見える
- 開いているファイルや、中にいるプロセスがあると、`umount` は **`EBUSY`** で失敗する
- 「**すべてはファイル**」とは、いろいろなものに fd と同じ 4 つの操作で触れる、ということ。`ioctl`、ソケット、プロセスの操作など、収まらないものもある
:::

## 確認問題 {#quiz}

マウントと、`/proc`・`/dev` を使った問題です。どの問題も、新しい Linux から始まります。

:::quiz どの種類のファイルシステムか
`/data` というディレクトリがあります。`/data` が載っているファイルシステムの**種類**（ext4、tmpfs、proc など）だけを、1 語で表示してください。

```sh prep
sudo mkdir /data
sudo mount -t tmpfs tmpfs /data
```

```sh answer
df -T /data | tail -1 | tr -s ' ' | cut -d' ' -f2
```

```sh vary
sudo umount /data
```

```sh vary
sudo umount /data
sudo mount -t proc proc /data
```

:::hint
`df -T パス` の 2 列目が種類です。見出しの行を `tail -1` で除き、空白を `tr -s ' '` で 1 つにまとめてから、`cut` で 2 列目を取り出します。
:::
:::

:::quiz 大きさを決めて tmpfs をマウントする
root として、`/mnt/work` というディレクトリを作り、そこに**大きさ 1024 KiB** の tmpfs をマウントしてください。大きさは、オプション `-o size=1024k` で指定します。

```sh answer root
mkdir /mnt/work
mount -t tmpfs -o size=1024k tmpfs /mnt/work
```

```sh check
df -T /mnt/work | tail -1
```

:::hint
`mount -t 種類 -o オプション 何を どこに` の形です。tmpfs の「何を」は `tmpfs` と書きます。
:::
:::

:::quiz プロセスのカレントディレクトリを調べる
バックグラウンドで `sleep` が動いています。この `sleep` の**カレントディレクトリ**を、`/proc` を使って表示してください。`sleep` の PID は `$!` でわかります。

```sh prep
cd /var/log
sleep 1000 &
cd /home/you
```

```sh answer
readlink /proc/$!/cwd
```

```sh vary
kill %1
cd /home/you/notes
sleep 1000 &
cd /home/you
```

:::hint
`/proc/PID/cwd` は、そのプロセスのカレントディレクトリへのシンボリックリンクです。リンクの指す先は `readlink` で表示できます。
:::
:::

:::quiz 外せないマウントを外す
`/mnt/usb` に tmpfs がマウントされています。外したいのですが、バックグラウンドの `sleep` が、その中のファイルを開いたままです。`/mnt/usb` のマウントを外してください。`umount` は root の仕事なので、`sudo umount …` のように実行します。

```sh prep
sudo mkdir /mnt/usb
sudo mount -t tmpfs tmpfs /mnt/usb
sudo chmod 777 /mnt/usb
echo data > /mnt/usb/file.txt
sleep 1000 < /mnt/usb/file.txt &
```

```sh answer
kill $!
wait
sudo umount /mnt/usb
```

```sh check
grep -c ' /mnt/usb ' /proc/mounts
ls -a /mnt/usb
```

:::hint
先に、使っているプロセスを終わらせます。`kill $!` のあと `wait` で終わるのを待ってから、`sudo umount /mnt/usb` を実行します。
:::
:::
