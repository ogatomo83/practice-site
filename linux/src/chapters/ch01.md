## タイムシェアリングと Multics {#multics}

Linux は 1991 年に生まれましたが、その形の大部分は、1969 年に生まれた **Unix**（ユニックス）から受け継いだものです。そして Unix は、さらに前の 2 つのシステムへの反応として生まれました。まず、この章で通る道筋を年表で見ておきましょう。

### 1 台の計算機をみんなで使う

1950 年代の計算機は、1 度に 1 つの仕事しかしませんでした。利用者はプログラムをカードの束にして係に渡し、順番を待ち、何時間もあとに結果の紙を受け取ります。プログラムに 1 文字の誤りがあれば、直してまた並び直しです。

これを変えたのが**タイムシェアリング**（時分割）です。計算機が、何人もの利用者の仕事を短い時間ずつ順番に切り替えて実行します。切り替えが十分に速ければ、端末の前にいる 1 人 1 人には、計算機をひとり占めしているように見えます。

最初期のタイムシェアリングシステムの 1 つが、MIT（マサチューセッツ工科大学）の **CTSS**（Compatible Time-Sharing System）です。フェルナンド・コルバト（Fernando Corbató）らが作り、1961 年 11 月に、改造した IBM 709 の上で初めて実演されました。利用者どうしがメッセージを送り合う仕組み（電子メールの先駆け）や、文書を整形する RUNOFF というプログラムも、CTSS の上で生まれています。

「短い時間ずつ切り替える」という仕組みは、今の Linux にもそのまま残っています。第 14 章のスケジューラで、切り替えの様子を自分の目で見ます。

### Multics：大きすぎた計画

CTSS の成功を受けて、1964 年に、もっと野心的な計画が始まりました。**Multics**（マルティクス）です。MIT の Project MAC、計算機メーカーの GE（General Electric）、そして AT&T の研究所である**ベル研究所**の 3 者が共同で開発しました。

Multics は、大勢の利用者が同時に使える大きなシステムを目指し、当時としては新しい仕組みを数多く取り入れました。

| Multics の仕組み | 今の Linux では |
| --- | --- |
| 階層型のファイルシステム（ディレクトリの中にディレクトリを入れられる。Multics が最初） | 第 3 章のディレクトリの木 |
| 利用者ごとの保護（他人のファイルを勝手に読めない） | 第 4 章のユーザーと権限 |
| コマンドを読んで実行するプログラム（シェル） | 第 2 章のシェル |
| 実行中に必要な部品をつなぐ（動的リンク） | 第 18 章の共有ライブラリ |

ところが、開発は長引きました。専用に設計された計算機 GE 645 が MIT に届いたのは 1967 年で、使えるシステムはなかなかできあがりません。ベル研究所は 1969 年に、この計画から手を引きました。

:::note Multics は失敗作ではない
Multics はその後も開発が続き、製品として長く使われました。最後の 1 台（カナダの国防省のもの）が止められたのは 2000 年 10 月 30 日です。上の表のとおり、Unix と Linux は Multics から多くの考えを受け継いでいます。受け継がなかったのは、その大きさと複雑さでした。
:::

## ベル研究所の Unix：PDP-7 から PDP-11 へ {#unix}

Multics から手を引いたベル研究所には、Multics の便利さを知ってしまった研究者たちが残されました。**ケン・トンプソン**（Ken Thompson）、**デニス・リッチー**（Dennis Ritchie）、ダグラス・マキルロイ（Douglas McIlroy）、オサナ（J. F. Ossanna）らです。彼らは 1969 年を通して、自分たちの OS を書くための計算機を買ってほしいと求め続けましたが、認められませんでした。

### 使われていなかった PDP-7

きっかけは、ゲームでした。トンプソンは 1969 年に、太陽系の中を宇宙船で飛び回る「Space Travel」というゲームを書いていました。しかし大型計算機の上では画面の動きがぎこちなく、しかも 1 回遊ぶのに約 75 ドルぶんの計算機の時間がかかりました。

そこでトンプソンは、研究所の中でほとんど使われていなかった小型の計算機 **PDP-7** を見つけ、リッチーと一緒にゲームを移します。これが、PDP-7 のためのプログラムの作り方を覚える練習になりました。

続いてトンプソンは、以前からリッチーやカナデイ（R. H. Canaday）と黒板の上で設計していた**ファイルシステム**を、PDP-7 の上に実際に作り始めます。ファイルシステムだけでは試せないので、プロセスの仕組みを足し、ファイルをコピーする・表示する・消す・編集するための小さなプログラムと、簡単なシェルを足しました。アセンブラ（プログラムを機械の命令に直す道具）ができたところで、このシステムは自分の上で自分を作れるようになりました。

リッチーはのちに、この時点で「今日知られている OS が生まれた」と書いています。1969 年のことです。名前が付いたのは 1970 年に入ってからで、**ブライアン・カーニハン**（Brian Kernighan）が Multics をもじって「Unix」と提案しました。「multi（多くの）」に対する「uni（1 つの）」という、少し皮肉な言葉遊びです。

:::note 今と同じ形が、最初からあった
リッチーによれば、PDP-7 の Unix のファイルシステムは、構造としては今のものとほとんど同じでした。ファイルを表す **i-node**（アイノード）の表、名前と i-node の番号を並べた**ディレクトリ**、装置を表す**特殊ファイル**の 3 つです。`fork` でプロセスを作る仕組みも、この PDP-7 の時代に入りました。i-node は第 11 章で、`fork` は第 7 章で、実際に動かして確かめます。
:::

### PDP-11 と、特許の書類

PDP-7 は借り物で、すでに古い機種でした。1970 年のはじめ、研究者たちは新しく発売された **PDP-11** を買う提案を出します。今度は「OS を書きたい」ではなく、「文書を編集して整形するシステムを作る」という具体的な目的を掲げました。金額も約 65,000 ドルと、それまでの提案より 1 桁小さいものでした。この提案は通りました。

PDP-11 の本体は 1970 年の夏の終わりに届き、ディスクは 12 月に届きました。そこへ PDP-7 の Unix が移されます。当時の大きさを、今の計算機と比べてみましょう。

| | 最初の PDP-11 の Unix（1970〜1971 年） | 参考：今のノートパソコンの例 |
| --- | --- | --- |
| メモリ | 24 K バイト（OS に 16 K、利用者のプログラムに 8 K） | 16 G バイト（約 70 万倍） |
| ディスク | 512 K バイト | 512 G バイト（約 100 万倍） |
| 1 つのファイルの上限 | 64 K バイト | 事実上なし |

1971 年の後半には、約束どおり、AT&T の特許部門の 3 人のタイピストが、この Unix の上で特許の出願書類を打ち、編集し、整形していました。Unix の最初の「お客さん」は、プログラマではなく、書類を作る人たちだったのです。

Unix の最初のマニュアル（第 1 版）の日付は、1971 年 11 月 3 日です。ベル研究所の Unix は、このマニュアルの版の番号で「第 6 版」「第 7 版」のように呼ばれます。外の世界への最初の正式な発表は 1973 年の学会で、1974 年には論文として雑誌に載りました。トンプソンとリッチーは、Unix を作った功績で 1983 年のチューリング賞を受けています。

## C 言語で書き直す {#c}

PDP-7 の Unix も、最初の PDP-11 の Unix も、**アセンブリ言語**で書かれていました。アセンブリ言語は、CPU の命令を 1 つずつ書いていく言語です。速くて小さいプログラムが書けますが、ある機種の命令で書いたプログラムは、命令が違う別の機種では動きません。当時、OS はアセンブリ言語で書くのが当たり前でした。

トンプソンは PDP-7 の時代に、**B** という小さな言語を作っていました。BCPL という言語をもとに、小さなメモリに収まるように切り詰めたものです。ただ、B で書いたプログラムは遅く、PDP-11 の「バイト」という単位ともかみ合いませんでした。

そこでリッチーは 1971 年に、B を作り直す仕事を始めます。これが **C 言語**になりました。1973 年、Unix のカーネル（OS の中心部分）は C で書き直されます。同じ年の 11 月に出た第 4 版が、C で書かれた最初の Unix です。

C で書き直したことには、3 つの意味がありました。

1. **移せる。** C で書いたプログラムは、その機種用の C コンパイラ（C を機械の命令に直すプログラム）さえあれば、別の機種でも動く。OS が特定の機種の付属品ではなくなった
2. **読める、直せる。** アセンブリ言語より短く、意図が読み取りやすい。ソースコードを受け取った大学の人たちが、中を読んで学び、手を入れることができた
3. **仕組みが整った。** リッチーは、この書き直しで Unix が「今の形になった」と書いている。複数のプログラムを同時にメモリに置いて切り替える仕組みも、このとき入った

リッチーはのちに、Unix の成功の多くは、ソフトウェアが読みやすく、直しやすく、移しやすいことから来ていて、それは高水準の言語で書いたことから来ている、と振り返っています。

この選択は、今も生きています。Linux のカーネルも大部分が C で書かれていて、そのおかげで、パソコンの x86 でも、スマートフォンの ARM でも、RISC-V でも動きます。この本の「小さな Linux」の説明に出てくるシステムコールの形（`open`、`read`、`write` など）も、C の関数の形で書くのが習慣になっています。

## Unix の哲学：小さな道具をつなぐ {#philosophy}

Unix は、仕組みだけでなく、**プログラムの作り方についての考え方**も残しました。これは「Unix の哲学」と呼ばれています。

### 1 つのことを、うまくやる

マキルロイは 1965 年から 1986 年まで、Unix が生まれた研究部門の長でした。1978 年、彼は Unix の特集号の序文に、Unix の作り手たちが身につけた流儀を 4 つ書いています。はじめの 2 つが、とくによく引用されます。

> 1. 1 つのプログラムには、1 つのことをうまくやらせよ（Make each program do one thing well）。
> 2. どのプログラムの出力も、まだ見ぬ別のプログラムの入力になると考えよ（Expect the output of every program to become the input to another, as yet unknown, program）。

残りの 2 つは、「ソフトウェアは早く、できれば数週間のうちに試せるように作れ」と、「仕事を楽にするには、人手に頼るより道具を使え」です。

大きな万能のプログラムを 1 つ作るのではなく、小さな道具をたくさん作り、組み合わせて使う。Multics の大きさへの反省が、ここに表れています。

### パイプ：出力を次の入力へ

「組み合わせる」ための仕組みが**パイプ**です。あるプログラムの出力を、ファイルに書き出さずに、そのまま次のプログラムの入力へ流します。

パイプを強く求め続けたのもマキルロイでした。プログラムを「つなぐ」という考えを何年も前から説いていて、その粘りに押される形で、トンプソンがパイプを Unix に入れます。リッチーの回想では 1972 年のことで、マニュアルには 1973 年 2 月の第 3 版から載っています。マキルロイによれば、トンプソンはこの仕事を一晩で仕上げました。

パイプが入ると、それまでのプログラムの多くが「入力を読んで、加工して、出力する」形に直されました。こういうプログラムを**フィルタ**と呼びます。今の `|`（縦棒）の書き方は、そのあとすぐにトンプソンが決めたものです。

たとえば、果物の名前が 1 行に 1 つずつ入ったファイルから、「どの果物が何回出てくるか」を多い順に数えてみます。

```sh setup
printf 'apple\nbanana\napple\ncherry\nbanana\napple\n' > /home/you/basket.txt
```

```sh run title="小さな道具をパイプでつなぐ"
cat basket.txt
sort basket.txt | uniq -c | sort -rn
```

### すべてはファイル

もう 1 つの柱が、「**すべてはファイル**（everything is a file）」という考え方です。

Unix では、ディスクの上のファイルだけでなく、端末、プリンタ、ディスクそのものといった**装置**も、ファイルと同じ方法で扱います。装置をファイルとして見せるという案は、PDP-7 の時代にリッチーが出したものでした。

この考え方のおかげで、プログラムは相手を区別せずに書けます。`sort` は、入力がファイルなのか、キーボードなのか、パイプなのかを気にしません。だからこそ、パイプで自由につなげるのです。

正確には、「すべて」は言いすぎです。たとえばネットワークの接続は、開くときだけ特別な手順が要ります。それでも、開いたあとは、**ファイルディスクリプタ**という同じ種類の番号で扱い、同じ `read` と `write` で読み書きできます。ファイルディスクリプタは第 9 章で、`/dev` や `/proc` のような「ディスクの上にないファイル」は第 12 章で扱います。

:::hist のちの要約
Unix の哲学は、1994 年にピーター・サラス（Peter H. Salus）が著書の中でまとめた、次の 3 行でもよく知られています。「1 つのことをうまくやるプログラムを書け。協調して動くプログラムを書け。テキストの流れを扱うプログラムを書け。それが万能のインタフェースだからだ。」
:::

## AT&T のライセンスと BSD {#bsd}

Unix が大学に広まった理由の 1 つは、意外なことに、法律でした。

ベル研究所の親会社 AT&T は、米国の電話をほぼ独占していた会社です。1956 年に米国政府と結んだ取り決め（同意審決）で、AT&T は電話などの通信の事業以外に手を出すことを禁じられていました。そのため、Unix を製品として売ることができません。ベル研究所は Unix を、テープと送料ていどの実費で、**ソースコードごと**大学に渡しました。

- 1974 年の第 5 版は、教育機関にライセンスされた
- 1975 年の第 6 版は、企業にも初めてライセンスされた
- 1979 年の第 7 版は、ベル研究所の研究用の Unix として広く配られた最後の版になった

ソースコードが手に入るので、大学では Unix を読んで学び、直し、足すことができました。その中心になったのが、**カリフォルニア大学バークレー校**です。

### バークレーの BSD

バークレー校に Unix が届いたのは 1974 年です。翌 1975 年には、トンプソン本人が休暇を使って客員教授として滞在しました。

大学院生だった**ビル・ジョイ**（Bill Joy）は、自分たちが書いたプログラムをテープにまとめ、1978 年 3 月 9 日に **1BSD**（Berkeley Software Distribution）として配り始めます。最初は Unix に足して使うプログラムの集まりでしたが、版を重ねるうちに、カーネルを含む完全な OS になっていきました。

| 版 | 時期 | 加わったもの |
| --- | --- | --- |
| 1BSD | 1978 年 3 月 | バークレー校で書いたプログラムの集まり |
| 2BSD | 1979 年 5 月 | ジョイの C シェルと、エディタの vi |
| 3BSD | 1979 年の終わり | 新しいカーネルを含む、完全な OS |
| 4.2BSD | 1983 年 8 月 | TCP/IP のネットワークと、速いファイルシステム |

とくに大きかったのは 4.2BSD です。インターネットの通信の決まりである TCP/IP を、**ソケット**という形でプログラムから使えるようにしました。BSD のこの仕事には、米国の国防総省の研究機関 DARPA が 1979 年から資金を出しています。ソケットは今の Linux でも同じ形で使われていて、第 16 章で扱います。

### 閉じていく Unix

1980 年代の前半に AT&T が分割されると、AT&T は 1956 年の取り決めから自由になり、Unix を製品として売れるようになりました。1983 年には商用の **System V**（システムファイブ）が出ます。

売り物になった Unix のソースコードは、気軽に見せ合えるものではなくなりました。計算機メーカーは System V や BSD をもとに自社の Unix（IBM の AIX、HP の HP-UX、Sun の Solaris など）を作り、それぞれが少しずつ違うものになっていきます。

BSD の側も、困っていました。BSD には AT&T が書いたコードが混ざっていたので、使うには AT&T のライセンスが必要だったのです。バークレー校は AT&T のコードを取り除いて書き直す作業を進め、1991 年 6 月に、ほぼ完全な OS を自由に配れる形で公開しました（Net/2）。ところが 1992 年に、Unix の権利を持つ AT&T の子会社が訴訟を起こします。和解したのは 1994 年 1 月でした。

パソコン用の自由な BSD（1993 年に始まった FreeBSD と NetBSD）は、この訴訟のあいだ、先行きがはっきりしませんでした。Linux が広まり始めたのは、ちょうどこの時期です。

:::note BSD は今も身近にある
FreeBSD、NetBSD、OpenBSD は今も開発が続いています。Apple の macOS や iOS の土台（Darwin）にも、BSD のコードが使われています。
:::

## GNU プロジェクトと GPL {#gnu}

Unix が閉じていくのを、別の場所から見ていた人がいました。MIT の人工知能研究所にいたプログラマ、**リチャード・ストールマン**（Richard Stallman）です。

ストールマンのいた研究所では、プログラムのソースコードを見せ合い、直し合うのが当たり前でした。ところが 1980 年代に入ると、ソフトウェアは会社の持ち物になり、ソースコードは隠され、直すことも分け合うことも禁じられるようになります。研究所のプリンタの制御プログラムを直したくても、ソースコードをもらえない、という出来事もありました。

1983 年 9 月 27 日、ストールマンはネットワーク上の掲示板で、ある計画を発表します。**Unix と互換性のある OS を一から全部書き、だれもが自由に使えるようにする**、というものです。名前は **GNU**（グヌー）。「GNU's Not Unix（GNU は Unix ではない）」の頭文字で、説明の中に自分の名前が入っている言葉遊びです。Unix と同じように使えるが、Unix のコードは 1 行も含まない、という意味が込められています。

開発は 1984 年 1 月に始まりました。1985 年 3 月には考え方をまとめた「GNU 宣言」を発表し、同じ年の 10 月には、活動を支える団体 **Free Software Foundation**（FSF、フリーソフトウェア財団）を作っています。

### 自由なソフトウェアと GPL

ストールマンの言う「自由（free）」は、値段が無料という意味ではありません。利用者が、次のことを自由にできるという意味です。

- プログラムを、どんな目的でも実行できる
- ソースコードを読んで、仕組みを調べられる
- コピーして、ほかの人に配れる
- 手を加えて、直したものを配れる

この自由を守るために、ストールマンは 1989 年に **GPL**（GNU General Public License、GNU 一般公衆利用許諾書）というライセンスを書きました。第 1 版は 1989 年 2 月 25 日、第 2 版は 1991 年 6 月に出ています。

GPL の中心にあるのは、**コピーレフト**という仕組みです。GPL のプログラムを直して配る人は、直したもののソースコードも、同じ GPL の条件で渡さなければなりません。だれかが改良を持ち去って、閉じた製品にしてしまうことができないのです。「自由に使ってよい。ただし、受け取った自由を、次の人からも奪ってはいけない」という約束だと言えます。

### 欠けていた最後の部品

Unix は小さな部品の集まりなので、GNU は部品を 1 つずつ書き直していくことができました。1990 年ごろまでに、主な部品はほぼそろいます。

| GNU の部品 | 役割 | この本では |
| --- | --- | --- |
| GCC | C のコンパイラ | 第 18 章 |
| glibc | C のプログラムが使うライブラリ。システムコールへの入口 | 第 10 章 |
| Bash | シェル | 第 2 章、第 6 章 |
| coreutils | `ls`、`cp`、`cat`、`sort` などの基本のコマンド | 第 2〜5 章 |
| Emacs | エディタ | — |

## MINIX から Linux へ {#linux}

### 教科書の OS、MINIX

1987 年、アムステルダム自由大学の教授**アンドリュー・タネンバウム**（Andrew S. Tanenbaum）は、OS の授業のために **MINIX**（ミニックス）という小さな OS を書きました。Unix と同じように使えますが、Unix のコードは含みません。当時の安いパソコン（Intel 8086 系の CPU）で動き、教科書『Operating Systems: Design and Implementation』には、約 12,000 行のソースコードが載っていました。

MINIX は、学生が OS の中身を最初から最後まで読める、という点で画期的でした。ただし、当時のライセンスには、改変と再配布についての制限がありました。

### 1991 年 8 月のメール

ヘルシンキ大学の学生だった**リーナス・トーバルズ**（Linus Torvalds）は、1991 年に、Intel 80386 という新しい CPU を載せたパソコンで MINIX を使っていました。80386 の機能をもっと使いこなしたいと考えた彼は、自分でカーネルを書き始めます。

1991 年 8 月 25 日、トーバルズは MINIX の利用者が集まるネットニュース（comp.os.minix）に、次の文で始まる投稿をしました。

> Hello everybody out there using minix -
>
> I'm doing a (free) operating system (just a hobby, won't be big and professional like gnu) for 386(486) AT clones. This has been brewing since April, and is starting to get ready.

日本語にすると、こうなります。

> minix を使っているみなさん、こんにちは。
>
> 386（486）の AT 互換機のための（自由な）オペレーティングシステムを作っています（ただの趣味で、gnu のような大きくて本格的なものにはなりません）。4 月から温めてきて、形になり始めたところです。

投稿は、MINIX の好きな点と嫌いな点を教えてほしい、という頼みに続きます。そして、GNU のシェル bash（1.08）とコンパイラ gcc（1.40）をすでに移してあり、動いているようだ、と書かれています。カーネルは新しく書き、その上の道具は GNU のものを使う。図 1-5 の組み合わせは、最初の投稿のときから始まっていたのです。

「大きくて本格的なものにはならない」という予想は、外れました。

| 時期 | 出来事 |
| --- | --- |
| 1991 年 9 月 17 日 | バージョン 0.01 を公開。ソースコードは約 1 万行 |
| 1991 年 10 月 5 日 | バージョン 0.02 を発表 |
| 1992 年 1 月 | バージョン 0.12。ライセンスを GPL に変えると発表 |
| 1994 年 3 月 14 日 | バージョン 1.0。176,250 行 |
| 2025 年 1 月 | ソースコードが 4,000 万行を超える |

:::note Linux という名前
トーバルズ自身は「Freax」という名前を考えていました。公開用のサーバを管理していたアリ・レムケ（Ari Lemmke）がその名前を気に入らず、置き場所に「Linux」と名付けました。トーバルズもあとでこの名前を受け入れています。
:::

### GPL を選んだこと

最初の Linux には、トーバルズが自分で書いた利用条件が付いていました。お金を取って配ることを禁じる、というものです。

1992 年 1 月のバージョン 0.12 で、トーバルズは Linux のライセンスを **GPL**（第 2 版）に変えると発表しました。この選択は、Linux のその後を決めました。

- **だれでも使える。** 会社が製品に組み込んで売ってもよい
- **改良が戻ってくる。** 直して配る人は、直したソースコードも GPL で公開しなければならない。ある会社の改良を、ほかの全員が使える
- **持ち去れない。** だれかが Linux を閉じた製品に変えてしまうことができない

競い合う会社どうしが、同じ 1 つのカーネルに改良を持ち寄る。今の Linux の開発の形は、このライセンスの上に成り立っています。

:::hist 「Linux は時代遅れだ」
1992 年 1 月、タネンバウムは同じネットニュースに「Linux is obsolete（Linux は時代遅れだ）」という題の投稿をしました。カーネルの機能を小さな部品に分けて別々に動かす作り（マイクロカーネル。MINIX はこの作り）が新しい設計で、全部を 1 つの大きなプログラムにまとめる Linux の作り（モノリシックカーネル）は古い、という批判です。トーバルズは反論し、議論は長く続きました。Linux は今も、1 つの大きなカーネルという作りのままです。
:::

## ディストリビューションと POSIX {#distro}

### カーネルだけでは使えない

ここで、言葉を整理しておきます。厳密には、**Linux はカーネルの名前**です。カーネルは、プロセスを切り替え、メモリを配り、ファイルを管理し、装置を動かします。しかし、カーネルだけでは `ls` すら実行できません。シェルも、コマンドも、ライブラリも、別のプロジェクトが作っているからです。

カーネルに、GNU の道具をはじめとする多くのソフトウェアを組み合わせ、すぐに使える形にまとめて配るものを、**ディストリビューション**（配布物）と呼びます。ふつう「Linux を入れる」と言うときに入れているのは、このディストリビューションです。ディストリビューションには、ソフトウェアを足したり更新したりする道具（**パッケージ管理**）も含まれています。

| ディストリビューション | 始まり | 特徴 |
| --- | --- | --- |
| Slackware | 1993 年 7 月 17 日 | パトリック・フォルカーディング（Patrick Volkerding）が作った。今も保守されている中で、いちばん古い |
| Debian | 1993 年 8 月 16 日 | イアン・マードック（Ian Murdock）が始めた。会社ではなく、ボランティアの集まりが作る |
| Red Hat Linux | 1995 年 5 月（バージョン 1.0） | 会社が作り、サポートを売る。2003 年に、企業向けの Red Hat Enterprise Linux と、コミュニティの Fedora に分かれた |
| Ubuntu | 2004 年 10 月 20 日（バージョン 4.10） | Debian をもとに、Canonical 社が作る。半年ごとに新しい版を出す |

Slackware より前にも、1992 年に出た MCC Interim Linux や SLS（Softlanding Linux System）などがありました。Slackware は、その SLS をもとにしています。

:::note 「GNU/Linux」という呼び方
カーネルは Linux でも、その上の道具の多くは GNU のものです。そのため FSF は、システム全体を「GNU/Linux」と呼ぶよう勧めています。Debian も、自分たちの OS を「Debian GNU/Linux」と呼んでいます。この本では、広く使われている呼び方に合わせて、全体を単に「Linux」と書きます。
:::

図の点線に注目してください。GNU も、MINIX も、Linux も、Unix のコードを 1 行も受け継いでいません。受け継いだのは、コマンドの名前、システムコールの名前と意味、ファイルの扱い方といった、**外から見た振る舞い**です。こういう OS を「Unix 系」「Unix 風」（Unix-like）と呼びます。

### POSIX：振る舞いの約束

1980 年代、各社の Unix は少しずつ違うものになっていました。ある Unix のために書いたプログラムが、別の Unix では直さないと動きません。

そこで、「Unix 系の OS なら、最低限これだけは同じに振る舞う」という約束が、規格としてまとめられました。それが **POSIX**（ポジックス、Portable Operating System Interface）です。最初の規格は 1988 年の IEEE Std 1003.1-1988 で、その後も改訂が続いています（2024 年 6 月に最新の版が出ました）。POSIX という名前を提案したのは、ストールマンです。

POSIX が決めているのは、大きく 2 つです。

- **プログラムから見た OS の入口**：`open`、`read`、`write`、`fork`、`exec` の仲間、`wait`、`kill`、`pipe` など、C の関数の名前と、引数と、意味
- **シェルとコマンド**：`sh` の文法と、`ls`、`cp`、`grep`、`sort` などのコマンドの名前とオプション

図の点線が成り立つのは、この約束があるからです。中身がまったく違うカーネルでも、同じ約束を守っていれば、同じプログラムが動き、同じコマンドが使えます。あなたが Linux で覚えたコマンドの多くは、macOS や FreeBSD でもそのまま通じます。

:::note Linux は「UNIX」ではない
「UNIX」という名前は、今は The Open Group という団体の登録商標です。決められた規格（Single UNIX Specification）の認証を受けた OS だけが、UNIX を名乗れます。macOS は認証を受けています。Linux のディストリビューションの多くは、POSIX にほぼ沿っていますが、認証は受けていません。Linux は、Unix によく似た、Unix ではない OS です。
:::

## Linux の広がりと、この本の「小さな Linux」 {#today}

### 趣味の OS が、どこにでもある OS に

「ただの趣味」として始まったカーネルは、30 年あまりで、計算機のほとんどの分野に広がりました。

| 分野 | Linux の使われ方 |
| --- | --- |
| サーバ | Web サイトやクラウドのサービスの多くが、Linux の上で動いている |
| スーパーコンピュータ | 世界の上位 500 台の一覧（TOP500）は、2017 年 11 月から、500 台すべてが Linux |
| スマートフォン | Android は、Linux カーネルに手を加えたものの上に作られている。2011 年から、世界でいちばん使われているスマートフォンの OS |
| 組み込み | 家庭用のルータ、テレビ、車の中の機器など、「計算機に見えない計算機」の中でも動いている |

Android の最初のスマートフォン（HTC Dream）が発表されたのは、2008 年 9 月です。今では、月に 30 億人を超える人が Android を使っています。

おもしろいのは、Android が GNU の道具をほとんど使っていないことです。C のライブラリは glibc ではなく Bionic という独自のもので、シェルや基本のコマンドも GNU のものではありません。カーネルは同じ Linux で、その上に載せるものが違う。前の節で見た「カーネル」と「ディストリビューション」の区別が、ここでも役に立ちます。

なぜここまで広がったのか。この章で見てきたことが、そのまま答えになります。

- **C で書かれている**ので、新しい CPU にも移せる
- **小さな道具とファイル**という Unix の作りが、小さな機器から巨大な計算機まで通用した
- **GPL** のおかげで、だれでも使え、改良が 1 か所に集まる
- **POSIX** という約束のおかげで、ほかの Unix のために書かれたプログラムがそのまま動いた

### この本の「小さな Linux」がまねているもの

この本では、ブラウザの中で動く「小さな Linux」を使います。これは本物の Linux カーネルではなく、**この本のために書いた、Linux と同じように振る舞う小さなシミュレータ**です。図 1-6 でいえば、点線がもう 1 本増えたことになります。Linux のコードは受け継がず、外から見た振る舞いをまねています。

本物を動かさない理由は 2 つあります。本物の Linux をブラウザで動かすと、読み込みと起動に時間がかかります。そして何より、本物のカーネルの中は、外から見えません。この本の目的は、カーネルの中で何が起きているかを見せることです。

小さな Linux がまねているのは、この章に出てきた「約束」の部分です。

| まねているもの | 中身 | 扱う章 |
| --- | --- | --- |
| シェル | POSIX の `sh` の主な文法。パイプ、リダイレクト、変数、`if`、`for` | 第 2 章、第 5〜6 章 |
| コマンド | `ls`、`cat`、`grep`、`sort`、`ps` など。出力の形は GNU のものに合わせてある | 第 2〜5 章ほか |
| システムコール | `fork`、`execve`、`wait4`、`open`、`read`、`write`、`pipe`、`dup2`、`kill` など。本物と同じ名前、同じ意味 | 第 7〜10 章 |
| ファイルシステム | i-node、ディレクトリ、リンク、権限、`/proc` と `/dev` | 第 3〜4 章、第 11〜12 章 |
| カーネルの仕組み | プロセスの切り替え、仮想メモリ、ページキャッシュ、名前空間 | 第 13〜15 章、第 19 章 |

その代わり、本物にはできないことができます。プロセスの表、ファイルディスクリプタの表、i-node、ページ表といった**カーネルの中のデータ**を、そのまま画面に出せます。時間も、本物の時計ではなく、シミュレータの中の時計で進むので、何度実行しても同じ結果になります。

:::warn 本物との違い
小さな Linux は、本物の Linux の全部を再現してはいません。コマンドのオプションは主なものだけですし、カーネルの中の仕組みは、考え方がわかるところまで単純にしてあります。本物と違うところは、それぞれの章で「このサイトの Linux では」と断って書きます。付録にも、違いの一覧を載せます。
:::

1969 年のトンプソンは、ファイルシステムを作り、それを試すためにプロセスを足し、シェルと小さなコマンドを足しました。この本も、ほぼ同じ順番で進みます。次の章では、その入口であるシェルに、最初のコマンドを打ち込みます。

:::key この章のまとめ
- **タイムシェアリング**は、1 台の計算機を何人もが同時に使う仕組み。CTSS（1961 年）で実演され、Multics（1964 年〜）は階層型のファイルシステムなど多くの考えを生んだが、大きく複雑になりすぎた
- **Unix** は 1969 年に、ベル研究所のトンプソンとリッチーらが、使われていなかった PDP-7 の上で作り始めた。ファイルシステム、プロセス、シェルという今と同じ骨組みが、最初からあった
- 1973 年に Unix は **C 言語**で書き直された。OS が特定の機種から切り離され、読める・直せる・移せるものになった
- **Unix の哲学**は、「1 つのことをうまくやる小さなプログラム」を**パイプ**でつなぐこと（マキルロイ）と、装置もファイルと同じ方法で扱う「**すべてはファイル**」
- AT&T は Unix を売れなかったので、ソースコードごと大学に渡した。バークレー校はそこから **BSD** を作り、TCP/IP のソケットを加えた。AT&T の分割のあと、Unix は売り物になり、閉じていった
- ストールマンの **GNU プロジェクト**（1983 年）は、自由な Unix 互換の OS を一から書いた。**GPL** は、改良したものも同じ条件で公開させる（コピーレフト）。カーネルだけが欠けていた
- **Linux** は、1991 年にトーバルズが書き始めたカーネル。1992 年に GPL を選び、GNU の道具と組み合わさって、自由な OS が完成した
- カーネルと道具をまとめて配るのが**ディストリビューション**（Slackware、Debian、Red Hat、Ubuntu）。**POSIX** は、Unix 系の OS が守る振る舞いの約束
- この本の「小さな Linux」は、Linux のコードではなく、シェル・コマンド・システムコールの**振る舞い**をまねたシミュレータ。その代わりに、カーネルの中を見せられる
:::

## 確認問題 {#quiz}

歴史の章なので、問題は 1 問だけです。次の章から使う「コマンドを書いて、答え合わせをする」枠の練習を兼ねています。

:::quiz いちばん多い果物
「Unix の哲学」の節で使った `basket.txt` から、**いちばん多く出てくる果物を、数と一緒に 1 行だけ**出してください。出力は `sort basket.txt | uniq -c | sort -rn` の 1 行目と同じ形です。

入力欄には、節で使ったパイプが最初から入っています。最後にもう 1 つ道具をつなぎます。先頭の何行かだけを出す `head` に `-1` を付けると、1 行目だけが出ます（くわしくは第 5 章で扱います）。

答え合わせでは、`basket.txt` の中身を少し変えたものでも試します。ファイルを見て答えを直接書いても通りません。

```sh answer
sort basket.txt | uniq -c | sort -rn | head -1
```

```sh vary
printf 'banana\nbanana\n' >> basket.txt
```

```sh starter
sort basket.txt | uniq -c | sort -rn
```

:::hint
`コマンド | head -1` で、前のコマンドの出力の 1 行目だけが残ります。
:::
:::
