## inode：ファイルの本体 {#inode}

第 3 章では、ファイルを「名前のついた入れ物」として扱いました。この章では、その中に降ります。まず、驚くかもしれない事実から始めます。**ファイルの本体は、自分の名前を知りません**。

ファイルシステムは、ファイル 1 つにつき 1 つ、**inode**（アイノード。index node）という小さな記録を持っています。inode には、そのファイルについてのほとんどすべてが書かれています。種類、権限、持ち主、大きさ、時刻、そしてデータがディスクのどこにあるか。書かれていないのは、**名前**だけです。

inode の中身は、`stat` コマンドで読めます。

```sh run title="memo.txt の inode を読む"
stat memo.txt
```

| 表示 | 意味 |
| --- | --- |
| `Size: 55` | 中身の大きさ（バイト） |
| `Blocks: 8` | 使っているディスクの量（512 バイト単位。8 × 512 = 4096 バイト） |
| `IO Block: 4096` | このファイルシステムのブロックの大きさ（バイト） |
| `regular file` | 種類。通常のファイル。ほかに `directory`、`symbolic link`、`character special file` など |
| `Device: 801h/2049d` | どのファイルシステム（装置）にあるか |
| `Inode: 139` | **inode 番号**。そのファイルシステムの中での通し番号 |
| `Links: 1` | **リンク数**。この inode を指している名前の数 |
| `Access: (0644/-rw-r--r--)` | 権限（第 4 章）。種類と合わせて「モード」と呼ぶ |
| `Uid`、`Gid` | 持ち主とグループ（番号で持っている。名前は `/etc/passwd` から引いたもの） |
| `Access`（atime） | 最後に中身を**読んだ**時刻 |
| `Modify`（mtime） | 最後に中身を**書き換えた**時刻。`ls -l` が表示するのはこれ |
| `Change`（ctime） | 最後に **inode を書き換えた**時刻。権限や持ち主、リンク数が変わったとき |
| `Birth` | 作られた時刻（記録しないファイルシステムでは `-`） |

1 行目の `File: memo.txt` は、inode の中身ではありません。`stat` が、あなたが打った引数をそのまま表示しているだけです。

カーネルにとって、ファイルを特定するものは「デバイス番号と inode 番号の組」です。名前ではありません。`ls -i` で、名前の横に inode 番号を表示できます。

```sh run title="inode 番号を並べる"
ls -li
```

いちばん左の列が inode 番号です。必要な項目だけを取り出したいときは、`stat -c` に書式を渡します。

```sh run title="stat -c で項目を選ぶ"
stat -c '%n: inode=%i links=%h size=%s blocks=%b mode=%a owner=%U' memo.txt fruits.txt
```

| 書式 | 意味 | 書式 | 意味 |
| --- | --- | --- | --- |
| `%n` | 名前 | `%s` | 大きさ（バイト） |
| `%i` | inode 番号 | `%b` | ブロック数（512 バイト単位） |
| `%h` | リンク数 | `%a` | 権限（8 進） |
| `%F` | 種類 | `%U` | 持ち主の名前 |

ctime は「作成時刻（create）」ではなく、「inode の変更時刻（change）」です。中身に触らず、権限だけを変えてみます。

```sh run title="権限を変えると、ctime だけが動く"
chmod 600 memo.txt
stat -c 'mtime: %y' memo.txt
stat -c 'ctime: %z' memo.txt
chmod 644 memo.txt
```

mtime は 3 月 28 日のまま、ctime だけが今（4 月 1 日）になりました。権限は inode に書かれているので、`chmod` は inode の書き換えです。中身のデータには触っていません。

## ディレクトリは「名前 → inode 番号」の表 {#directory}

では、名前はどこにあるのでしょうか。**ディレクトリ**の中です。ディレクトリも 1 つのファイル（inode を持つ）で、その中身は「名前と inode 番号の組」が並んだ表です。この 1 行 1 行を**ディレクトリエントリ**と呼びます。

`ls -a` は隠れた名前も表示し、`-i` は inode 番号を添えます。合わせると、ディレクトリの表がそのまま見えます。

```sh run title="notes ディレクトリの表"
ls -ai notes
```

`notes` の表には、4 つのエントリがあります。`ideas.txt` と `todo.txt`、そして `.` と `..` です。前の章の `getdents64` が「4 entries」と答えたのは、これでした。

`.` と `..` も、特別扱いの記号ではなく、表に書かれたふつうのエントリです。どの inode を指しているか、確かめましょう。

```sh run title=". と .. の指す先"
ls -di notes . /home
```

`-d` は、ディレクトリの中身ではなく、ディレクトリ自身を表示するオプションです。`notes` の中の `.` は `notes` 自身と同じ番号、`..` は親（ホームディレクトリ）と同じ番号です。「親に戻る」は、この `..` というエントリをたどるだけのことです。

### パスをたどる

`/home/you/notes/todo.txt` というパスを開くとき、カーネルは表を 1 段ずつ引いていきます。

1. `/`（ルートディレクトリ。inode 番号は決まっていて 2）の表から `home` を探す → inode 番号がわかる
2. `home` の表から `you` を探す
3. `you` の表から `notes` を探す
4. `notes` の表から `todo.txt` を探す → 目的の inode にたどり着く

途中のディレクトリごとに、「このディレクトリを通ってよいか（x の権限）」も調べます（第 4 章）。途中の名前が表になければ `ENOENT`、途中がディレクトリでなければ `ENOTDIR` です（第 10 章）。

```sh run title="たどる道すじの inode"
ls -di / /home /home/you /home/you/notes /home/you/notes/todo.txt
```

## ハードリンク：1 つの inode に、名前を 2 つ {#hardlink}

名前が inode の外にあるのなら、**1 つの inode に名前を 2 つつける**こともできるはずです。できます。それが**ハードリンク**で、`ln` で作ります。

```sh run title="memo.txt に、もう 1 つ名前をつける"
ln memo.txt memo2.txt
ls -li memo.txt memo2.txt
```

2 つの名前の inode 番号が**同じ**です。そして、権限の右の数字（リンク数）が 1 から 2 に増えました。`ln` は、ファイルをコピーしたのではありません。ホームディレクトリの表に「memo2.txt → 139」という 1 行を足し、inode のリンク数を 1 増やしただけです。

```sh run strace title="ln が呼ぶシステムコール"
ln fruits.txt fruits2.txt
```

`link("fruits.txt", "fruits2.txt") = 0` が、その 1 行を足すシステムコールです。データを読み書きする `read` や `write` は、どこにもありません。

同じ inode なので、片方の名前で書き換えると、もう片方の名前でも変わって見えます。

```sh run title="どちらの名前でも、同じ中身"
echo "たまご 6 個" >> memo2.txt
cat memo.txt
```

`memo.txt` と `memo2.txt` に、「本物」と「リンク」の区別はありません。どちらも、同じ inode を指す対等な名前です。ですから、先にあった `memo.txt` のほうを消しても、何も困りません。

```sh run title="片方の名前を消す"
rm memo.txt
cat memo2.txt
stat -c 'links=%h' memo2.txt
mv memo2.txt memo.txt
```

中身は残り、リンク数が 1 に戻りました（最後の行で、名前を元の `memo.txt` に戻しています）。

### ディレクトリのリンク数

`ls -l` で、ディレクトリのリンク数が 2 や 3 になっているのを見たことがあるでしょう。あれも、同じ数え方です。

```sh run title="ディレクトリのリンク数を数える"
mkdir proj
stat -c '%h' proj
mkdir proj/src proj/doc
stat -c '%h' proj
```

作ったばかりのディレクトリのリンク数は 2 です。親の表にある `proj` という名前と、自分の中の `.` の 2 つが、この inode を指しています。サブディレクトリを 2 つ作ると 4 になりました。それぞれのサブディレクトリの中の `..` が、`proj` を指すからです。つまり、**ディレクトリのリンク数 − 2 が、サブディレクトリの数**です。

### ハードリンクにできないこと

```sh run error title="ハードリンクの制限"
ln proj proj2
ln fruits.txt /tmp/fruits-link
```

- **ディレクトリにはハードリンクを作れません**。作れると、ディレクトリの木に輪ができ、`..` がどちらの親を指すのか決まらなくなるからです（`.` と `..` だけが例外で、これはカーネルが自分で作ります）
- **別のファイルシステムにまたがるハードリンクは作れません**。`/tmp` は、`/` とは別のファイルシステムです（第 12 章）。inode 番号は 1 つのファイルシステムの中だけの通し番号なので、「よそのファイルシステムの 140 番」を表に書く方法がありません。エラーは `EXDEV`（Invalid cross-device link）です

## シンボリックリンク：パスを書いた小さなファイル {#symlink}

この 2 つの制限がないのが、**シンボリックリンク**です（第 3 章）。`ln -s` で作ります。仕組みは、ハードリンクとまったく違います。

```sh run title="シンボリックリンクを作って、inode を見る"
ln -s notes/todo.txt todo
ls -li todo notes/todo.txt
stat -c '%n: %F、%s バイト' todo
```

`todo` は、`notes/todo.txt` とは**別の inode** を持っています。種類は `symbolic link` で、大きさは 14 バイトです。この 14 バイトは、`notes/todo.txt` という**パスの文字数**です。シンボリックリンクは、「行き先のパスを書いた、小さなファイル」なのです。

カーネルは、パスをたどる途中でシンボリックリンクに出会うと、中に書かれたパスを読み、そこからたどり直します。`cat todo` と打った `cat` は、何も知らずに `openat("todo")` を呼ぶだけです。

書かれているのはただの文字列なので、行き先が実在するかどうかは、作るときには調べられません。

```sh run error title="行き先のないシンボリックリンク"
ln -s nowhere.txt broken
ls -l broken
cat broken
```

リンクは作れますが、たどった先がないので `ENOENT` になります。エラー文には `broken` と出るので、「あるのに、ない」と混乱しがちです。

| | ハードリンク | シンボリックリンク |
| --- | --- | --- |
| 正体 | ディレクトリの表の 1 行（同じ inode を指す） | 行き先のパスを書いた、別の inode |
| 作る | `ln 元 名前`（`link`） | `ln -s 行き先 名前`（`symlink`） |
| 元の名前を消すと | 中身は残る（リンク数が 1 減るだけ） | 行き先を失う（切れたリンク） |
| ディレクトリに | 作れない | 作れる |
| 別のファイルシステムに | 作れない（`EXDEV`） | 作れる |
| `ls -l` | 見分けがつかない（リンク数が 2 以上） | `l` で始まり、`-> 行き先` が出る |

## 消すとは、リンクを外すこと {#unlink}

ここまで来ると、`rm` が本当は何をしているかがわかります。

```sh run strace title="rm が呼ぶシステムコール"
rm fruits2.txt
```

呼ばれているのは **`unlink`** です。「delete」でも「remove」でもなく、「リンクを外す」。`unlink` がするのは、次の 2 つだけです。

1. ディレクトリの表から、その名前の行を消す
2. inode のリンク数を 1 減らす

inode とデータが本当に解放されるのは、次の 2 つが**両方**そろったときです。

- リンク数が 0 になった（どのディレクトリからも指されていない）
- その inode を開いているプロセスがいない（第 9 章のファイル記述が 1 つも残っていない）

:::note 権限の話が、これでつながる
第 4 章で、「ファイルを消せるかどうかは、ファイルの権限ではなく、**ディレクトリ**の書き込み権限で決まる」と学びました。消すとはディレクトリの表を書き換えることなので、当然そうなります。ファイル本体（inode）には、何も書き込んでいません。
:::

### 消したのに、空きが増えない

2 つ目の条件のせいで、実務でよく出会う現象が起きます。大きなファイルを消したのに、ディスクの空きが増えない。試してみましょう。`/tmp` に 300 KB ほどのファイルを作り、`sleep` に開かせたままにします（`/dev/zero` は、0 のバイトがいくらでも読めるファイルです。第 12 章）。

```sh run title="大きなファイルを、開いたまま消す"
head -c 300000 /dev/zero > /tmp/big.log
sleep 500 < /tmp/big.log &
df /tmp
rm /tmp/big.log
ls /tmp
df /tmp
```

`rm` のあと、`ls /tmp` は空です。けれども `df` の Used は、296（KiB）のまま減っていません。名前は消えてリンク数は 0 になりましたが、`sleep` がまだ開いているので、inode とデータは残っています。

```sh run title="開いているプロセスが終わると、解放される"
lsof -p $! | grep deleted
kill $!
df /tmp
```

`lsof` には `(deleted)` の印つきで見えています。`sleep` を終わらせると、最後のファイル記述が閉じられ、Used が 0 に戻りました。

サーバで「ログファイルを消したのにディスクが空かない」というとき、原因はほとんどこれです。ログを書いているプログラムが、消されたファイルを開いたまま書き続けています。そのプログラムを再起動する（または、ログを開き直させる）と、空きが戻ります。

## rename は、名前の付け替え {#rename}

`mv` も、データを動かしません。

```sh run title="動かす前の inode 番号"
ls -i poem.txt
```

```sh run strace title="mv が呼ぶシステムコール"
mv poem.txt verse.txt
```

```sh run title="動かしたあとの inode 番号"
ls -i verse.txt
```

データに触るシステムコールはなく、`rename("poem.txt", "verse.txt") = 0` の 1 回だけです。inode 番号も、前後で変わっていません。`rename` は、ディレクトリの表の「poem.txt → 141」という行を「verse.txt → 141」に書き換えるだけです。別のディレクトリへの移動でも同じで、片方の表から行を消し、もう片方の表に行を足します。だから、何ギガバイトのファイルでも、`mv` は一瞬で終わります。

ただし、それは**同じファイルシステムの中**での話です。別のファイルシステムへ動かすと、どうなるでしょうか。

```sh run strace title="別のファイルシステムへ mv する"
mv verse.txt /tmp/verse.txt
```

`rename` は `EXDEV` で失敗します。ハードリンクのときと同じ理由です。そこで `mv` は、やり方を切り替えています。行き先に新しいファイルを作り（`openat` … `O_CREAT`）、中身を `read` と `write` でコピーし、権限と時刻を合わせ、最後に元を `unlink` します。こちらは本当にデータが動くので、大きなファイルでは時間がかかります。

```sh run title="戻すと、inode 番号が変わっている"
mv /tmp/verse.txt poem.txt
ls -i poem.txt
```

名前は元どおりですが、inode 番号は変わりました。中身は同じでも、別の inode に作り直されたファイルです。

:::tip rename は「一瞬で入れ替わる」
`rename` には、もう 1 つ大事な性質があります。行き先の名前がすでにあっても、**途中の状態を見せずに**一度で置き換わります（アトミックといいます）。設定ファイルを安全に書き換えたいプログラムは、別名の一時ファイルに全部書いてから、`rename` で本来の名前に付け替えます。書いている途中で電源が落ちても、古い内容か新しい内容のどちらかが必ず残り、半分だけ書かれたファイルにはなりません。
:::

## ブロック：大きさと、使っている量は違う {#blocks}

inode の `Size` と `Blocks` に戻ります。ディスクは、**ブロック**という決まった大きさの区画に分けて使われます。この Linux の `/` も、本物の ext4 の既定も、1 ブロックは 4096 バイト（4 KiB）です。ファイルのデータは、ブロック単位で割り当てられます。

そのため、ファイルには 2 つの「大きさ」があります。

- **中身の大きさ**（`Size`。`ls -l` が表示する）… 何バイト書かれているか
- **使っているディスクの量**（`Blocks`。`du` が表示する）… 何ブロック割り当てられているか

```sh run title="1 バイトのファイル"
printf 'x' > one.txt
ls -l one.txt
du -h one.txt
stat -c 'size=%s blocks=%b' one.txt
```

中身は 1 バイトですが、ディスクは 4.0K（1 ブロック）使っています。`Blocks` が 8 なのは、`stat` のブロック数が昔からの習慣で **512 バイト単位**だからです（8 × 512 = 4096）。

```sh run title="大きさと、使っている量"
: > empty.txt
seq 1 2000 > big.txt
stat -c '%n: size=%s blocks=%b' empty.txt one.txt big.txt
du empty.txt one.txt big.txt
```

| ファイル | 中身 | 割り当て |
| --- | --- | --- |
| empty.txt | 0 バイト | 0 ブロック（データがないので、inode だけ） |
| one.txt | 1 バイト | 1 ブロック（4 KiB） |
| big.txt | 8893 バイト | 3 ブロック（12 KiB。2 ブロックでは 8192 バイトしか入らない） |

`du` の数字は KiB 単位です。小さなファイルがたくさんあると、`ls -l` の大きさの合計より、ディスクはずっと多く使われます。`du -sh` は、ディレクトリ全体で実際に使っている量を合計します。

```sh run title="ディレクトリ全体の使用量"
du -sh .
du -a notes
rm one.txt empty.txt big.txt
```

`notes` には 68 バイトと 81 バイトのファイルしかありませんが、それぞれ 1 ブロックずつ、ディレクトリ自身の表にも 1 ブロックで、合計 12 KiB です。

### 穴のあるファイル

逆に、`Size` より `Blocks` のほうが**小さい**こともあります。本物の Linux で、`truncate` コマンドを使って「大きさだけ 1 MiB」のファイルを作ってみます。

```console
$ truncate -s 1M hole.bin
$ ls -l hole.bin
-rw-r--r-- 1 you you 1048576 Apr  1 09:00 hole.bin
$ du hole.bin
0	hole.bin
$ stat -c 'size=%s blocks=%b' hole.bin
size=1048576 blocks=0
```

大きさは 1048576 バイトなのに、ブロックは 0 です。inode の `Size` だけを書き換え、データブロックは 1 つも割り当てていません。こういう、ブロックが割り当てられていない部分を**穴**（ホール）、穴のあるファイルを**スパースファイル**と呼びます。穴を読むと、0 のバイトが返ってきます。書き込んだ場所にだけ、そのとき初めてブロックが割り当てられます。仮想マシンのディスクイメージやデータベースのファイルで、よく使われます。

`ls -l` で 100 GB と表示されるファイルが、実際には 1 GB しか使っていない、ということが起こりえます。ディスクの使用量を知りたいときは、`ls -l` ではなく `du` を見ます。

## ディスクが一杯になるとき {#full}

ブロックを使い切ると、どうなるでしょうか。試すために、root で、64 KiB しかない小さなファイルシステムを `/mnt/small` に用意します（`mount` は次の章でくわしく扱います）。

```sh run root title="準備：64 KiB の小さなファイルシステム"
mkdir /mnt/small
mount -t tmpfs -o size=64k tmpfs /mnt/small
chmod 777 /mnt/small
df /mnt/small
```

16 ブロックしかありません。ここに 40000 バイトのファイルを置きます。

```sh run title="40000 バイトのファイルを置く"
head -c 40000 /dev/zero > /mnt/small/a.bin
df /mnt/small
```

10 ブロック（40 KiB）使い、残りは 6 ブロック（24 KiB）です。このファイルを、同じ場所にコピーしてみます。

```sh run error strace title="空きが足りない"
cp /mnt/small/a.bin /mnt/small/b.bin
```

`read` と `write` の組が 6 回成功したあと、7 回目の `write` が `-1 ENOSPC (No space left on device)` で失敗しています。空いていた 6 ブロックを使い切ったからです。

```sh run error title="一杯になったあと"
df /mnt/small
ls -l /mnt/small
echo "1 行だけ" >> /mnt/small/b.bin
```

`df` の Use% は 100% です。`b.bin` は、書けたところまでの 24576 バイト（6 ブロック）で残っています。`cp` は失敗しましたが、途中まで書いたファイルを片づけてはくれません。そして一杯になると、1 行の追記すらできません。

**`df`**（disk free）は、ファイルシステムごとの使用量を表示します。`-h` をつけると、単位を読みやすくします。

```sh run title="df で空きを見る"
rm /mnt/small/b.bin
df -h
```

| 列 | 意味 |
| --- | --- |
| `Filesystem` | 装置（または種類の名前） |
| `Size` / `Used` / `Avail` | 全体、使用中、空き |
| `Use%` | 使用率 |
| `Mounted on` | 木のどこにつながっているか（第 12 章） |

「ディスクが一杯」と言われたら、`df -h` でどのファイルシステムが一杯かを確かめ、`du -sh ディレクトリ/*` で大きいものを探す。これが定番の手順です（第 20 章）。

### inode が一杯になる

空きブロックがあるのに、`No space left on device` と言われることがあります。**inode を使い切った**ときです。多くのファイルシステム（ext4 など）では、inode の数は、ファイルシステムを作ったときに決まります。小さなファイルを何百万個も作ると、ブロックより先に inode がなくなります。

inode の使用量は、`df -i` で見られます。

```sh run title="inode の数と、使っている数"
df -i /
touch one two three
df -i / | tail -1
rm one two three
```

ファイルを 3 つ作ると、IUsed が 3 増えます。ファイル 1 つに、inode が 1 つ要るからです。本物の Linux で inode を使い切ると、次のようになります。

```console
$ touch newfile
touch: cannot touch 'newfile': No space left on device
$ df -h .
Filesystem      Size  Used Avail Use% Mounted on
/dev/sdb1       976M  210M  700M  24% /data
$ df -i .
Filesystem     Inodes IUsed IFree IUse% Mounted on
/dev/sdb1       65536 65536     0  100% /data
```

`df -h` では 24% しか使っていないのに、`df -i` では 100% です。エラーは同じ `ENOSPC` なので、`df -i` を見るまで原因に気づけません。

## ext4：ディスクの上の配置 {#ext4}

最後に、これらがディスクの上にどう並んでいるかを見ます。Linux でいちばん広く使われているファイルシステムは **ext4** です。この小さな Linux の `/` も、ext4 のように見せてあります（中身は、仕組みを学べるところまで単純にしたものです）。

ディスク（正しくはパーティション）は、先頭からブロック 0、1、2 … と番号のついたブロックの列です。ext4 は、それを**ブロックグループ**というまとまりに分け、それぞれの中を次のように使います。

```fig layout ext4 の配置（単純にしたもの）。全体の情報を持つスーパーブロックのあとに、ブロックグループが並ぶ。それぞれのグループが、自分の inode 表とデータブロックを持つ
{
  unit: 30,
  rows: [
    { label: 'ディスク全体', cells: [
      { t: 'SB', w: 2, kind: 'accent' },
      { t: 'グループ 0', w: 7, kind: 'stack' },
      { t: 'グループ 1', w: 7, kind: 'stack' },
      { t: 'グループ 2', w: 7, kind: 'stack' },
      { t: '…', w: 2, kind: 'empty' },
    ] },
    { label: 'グループの中', cells: [
      { t: 'GD', w: 2, kind: 'static' },
      { t: 'B 地図', w: 3, kind: 'heap' },
      { t: 'I 地図', w: 3, kind: 'heap' },
      { t: 'inode 表', w: 6, kind: 'accent' },
      { t: 'データブロック', w: 11, kind: 'plain' },
    ] },
  ],
}
```

| 部分 | 中身 |
| --- | --- |
| **スーパーブロック**（SB） | ファイルシステム全体の情報。ブロックの大きさ、ブロックと inode の総数と空きの数、状態。`df` が表示する数字の出どころ。壊れると全体が読めなくなるので、控えが何か所かに置かれる |
| グループ記述子（GD） | そのグループの地図や inode 表が、どのブロックにあるか |
| ブロックビットマップ（B 地図） | データブロック 1 つにつき 1 ビット。使用中なら 1、空きなら 0 |
| inode ビットマップ（I 地図） | inode 1 つにつき 1 ビット。使用中か、空きか |
| **inode 表** | inode が番号順に並んだ表。1 つ 256 バイト（既定）。**ここの大きさが決まっているので、inode の数に上限がある** |
| **データブロック** | ファイルの中身と、ディレクトリの表が入る |

この章で見てきた操作を、この配置の上で言い直すと、こうなります。

- **ファイルを作る**… inode ビットマップで空きを探して 1 にし、inode 表のその場所に書き込み、ディレクトリのデータブロックに「名前 → 番号」の行を足す
- **データを書く**… ブロックビットマップで空きを探して 1 にし、データブロックに書き、inode に「何番のブロックを使っているか」を記録する
- **消す**（リンク数が 0 になり、だれも開いていない）… 2 つのビットマップの該当するビットを 0 に戻す。**データブロックの中身は、上書きされるまでそのまま残る**
- **`ENOSPC`**… ブロックビットマップか inode ビットマップに、0 のビットがもうない

```fig graph inode からデータブロックへ。ext4 は「何番から何個続き」という範囲（エクステント）で場所を記録する。穴の部分には、ブロックが割り当てられない
{
  col: 230, row: 84,
  nodes: [
    { id: 'i', label: 'inode', sub: 'モード、uid、gid、大きさ、リンク数、時刻', x: 0, y: 0.5, kind: 'accent' },

    { id: 'x2', label: 'ファイルの 100〜101 ブロック目', sub: '→ ディスクの 9000 番から 2 個', x: 1, y: 1, mono: false },
    { id: 'b1', label: '5120 5121 5122', sub: 'データブロック', x: 2, y: 0, kind: 'ext' },

    { from: 'x1', to: 'b1' },
    { from: 'x2', to: 'b2' },
  ],

```

inode は、データの場所を「ファイルの何ブロック目から何個ぶんは、ディスクの何番から」という範囲（**エクステント**）で覚えています。上の図の例では、ファイルの 3〜99 ブロック目にはどの範囲も対応していません。そこが穴です。

:::deep ジャーナル：途中で電源が落ちたら
ファイルを 1 つ作るだけでも、inode ビットマップ、inode 表、ディレクトリのブロックと、ディスクの何か所もを書き換えます。その途中で電源が落ちると、「inode は使用中になったのに、どのディレクトリからも指されていない」といった食い違いが残ります。

ext4 は、これを防ぐために**ジャーナル**を持っています。書き換える前に、「これから何をどう書き換えるか」をジャーナルという専用の場所に先に書き、それから本来の場所を書き換えます。途中で落ちても、次に起動したときにジャーナルを読めば、やりかけの書き換えをやり直せます。データベースの WAL（先行書き込みログ）と同じ考え方です。この小さな Linux には、ジャーナルはありません。
:::

:::warn 本物との違い
- この小さな Linux の `/` は、ext4 と表示されますが、本物の ext4 のディスク上の形式（ブロックグループ、ビットマップ、エクステントの木、ジャーナル）は持っていません。inode、ディレクトリエントリ、リンク数、ブロックの割り当てという考え方だけをまねています
- 本物の Linux では、ファイルを読むと atime が更新されることがあります（`relatime` という設定で、頻度は抑えられています）。この小さな Linux では、読んでも atime は動きません
- `truncate` コマンド（穴のあるファイルを作る）はありません。inode の数の上限に当たる実験もできないので、実行しない例で示しました
:::

:::key この章のまとめ
- **inode** がファイルの本体。種類、権限、持ち主、大きさ、時刻、リンク数、データの場所を持つ。**名前だけは持たない**。`stat` で読める
- **ディレクトリ**は「名前 → inode 番号」の表。`.` と `..` も、その表のふつうの行。パスは、表を 1 段ずつ引いてたどる
- **ハードリンク**は、同じ inode を指す名前をもう 1 つ足すこと（`link`）。名前どうしは対等。ディレクトリと、別のファイルシステムには作れない
- **シンボリックリンク**は、行き先のパスを書いた別の inode。行き先がなくても作れる
- **消す**（`unlink`）とは、表から名前を外してリンク数を 1 減らすこと。リンク数が 0 で、かつだれも開いていないときに、初めて解放される
- **`rename`** は表の行の付け替え。データは動かない。別のファイルシステムへは `EXDEV` になり、`mv` はコピーして消す
- データは**ブロック**（4 KiB）単位で割り当てられる。`ls -l` は中身の大きさ、`du` は使っているブロックの量。穴のあるファイルでは、大きさよりブロックが少ない
- ブロックか inode を使い切ると **`ENOSPC`**。`df -h` と `df -i` の両方を見る
- ext4 は、スーパーブロック、ビットマップ、inode 表、データブロックをブロックグループごとに並べる
:::

## 確認問題 {#quiz}

`stat`、`ln`、`df` を使って、ファイルシステムの中を確かめます。どの問題も、新しい Linux から始まります。

:::quiz リンク数を表示する
`report.txt` には、いくつかのハードリンクが作られています。`report.txt` の**リンク数**だけを表示してください。

```sh prep
echo '4 月の報告' > report.txt
mkdir archive
ln report.txt archive/2026-04.txt
ln report.txt latest.txt
```

```sh answer
stat -c '%h' report.txt
```

```sh vary
ln report.txt archive/copy.txt
ln report.txt notes/report.txt
```

:::hint
`stat -c` の書式で、リンク数は `%h` です。
:::
:::

:::quiz ハードリンクを作る
`backup` というディレクトリを作り、その中に、`memo.txt` と**同じ inode を指す** `memo.bak` という名前を作ってください。コピーやシンボリックリンクではいけません。

```sh answer
mkdir backup
ln memo.txt backup/memo.bak
```

```sh check
stat -c 'links=%h type=%F' /home/you/backup/memo.bak
test "$(stat -c %i /home/you/memo.txt)" = "$(stat -c %i /home/you/backup/memo.bak)" && echo 同じinode
```

:::hint
`ln 元の名前 新しい名前` です。`-s` はつけません。
:::
:::

:::quiz サブディレクトリの数を、リンク数から求める
`site` というディレクトリの直下に、サブディレクトリが**いくつ**あるかを表示してください。`site` のリンク数から計算できます（`ls` で数えてもかまいません）。

```sh prep
mkdir site site/css site/js site/img
touch site/index.html site/about.html
```

```sh answer
echo $(( $(stat -c %h site) - 2 ))
```

```sh vary
mkdir site/fonts site/data
touch site/contact.html
```

:::hint
ディレクトリのリンク数は、「親の表の名前」と「自分の中の `.`」で 2、それにサブディレクトリの `..` の数が足されます。
:::
:::

:::quiz 消えないディスク使用量を取り戻す
`/tmp/app.log` は消されましたが、`df /tmp` の Used は減っていません。バックグラウンドの `sleep` が、このファイルを開いたままだからです。`/tmp` の使用量が 0 に戻るようにしてください。

```sh prep
head -c 200000 /dev/zero > /tmp/app.log
sleep 1000 < /tmp/app.log &
rm /tmp/app.log
```

```sh answer
kill $!
```

```sh check
df /tmp | tail -1
```

:::hint
開いているプロセスが終われば、最後のファイル記述が閉じられて解放されます。PID は `$!`、`jobs -p`、`ps` でわかります。`kill %1` でも送れます。
:::
:::
