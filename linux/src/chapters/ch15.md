## ディスクは遅い {#slow}

第 11 章で、ファイルの中身はディスクのブロックに入っていることを見ました。第 13 章では、メモリが 4 KiB の**ページ**に区切られていることを見ました。この章は、その 2 つのあいだの話です。

まず、装置の速さを比べます。データを 1 か所読むのにかかる時間の、おおよその目安です。

```fig bars データを 1 回読むのにかかる時間の目安。棒の長さは桁数（10 倍ごとに同じ長さだけ伸びる）で描いている。ふつうの目盛りで描くと、ハードディスク以外は見えなくなる
{

  items: [
    { label: 'CPU の中のキャッシュ', value: 1, text: '約 1 ナノ秒' },
    { label: 'メモリ', value: 3, text: '約 100 ナノ秒' },
    { label: 'SSD', value: 6, text: '約 0.1 ミリ秒' },
    { label: 'ハードディスク', value: 8, text: '約 10 ミリ秒' },
    { label: 'この小さな Linux のディスク', value: 7.7, text: '5 ミリ秒', hl: true },
  ],

```

1 ナノ秒は、10 億分の 1 秒です。メモリと SSD のあいだには 1,000 倍、メモリとハードディスクのあいだには 10 万倍の差があります。メモリを読むのに 1 秒かかるとしたら、SSD は 17 分、ハードディスクは丸 1 日以上かかる計算です。

この小さな Linux の `/`（`/dev/sda1`）は、**1 ページ（4 KiB）を読むのに 5 ミリ秒、書くのにも 5 ミリ秒**かかるディスクです。古いハードディスクくらいの遅さにしてあります。

ホームディレクトリに、400 KiB のファイル `big.dat` を用意しました。100 ページぶんです。これを読んで、時間を計ります。`time` は、後ろのコマンドにかかった時間を表示します。中身は乱数なので、`/dev/null` に捨てます。

```sh run title="1 回目"
ls -l big.dat
time cat big.dat > /dev/null
```

`real` が、実際にかかった時間です。0.623 秒でした。もう一度、同じコマンドを実行します。

```sh run title="2 回目"
time cat big.dat > /dev/null
```

今度は 0.221 秒です。同じファイルを、同じコマンドで読んだのに、0.4 秒ほど速くなりました。`cat` もファイルも変わっていません。変わったのは、カーネルの中です。

:::note この Linux の時間
この小さな Linux では、システムコール 1 回に 1 ミリ秒かかります（本物はその 1,000 分の 1 以下です）。`cat` は 4 KiB ずつ `read` と `write` を 100 回ずつ呼ぶので、ディスクを待たなくても 0.2 秒かかります。2 回目の 0.221 秒は、ほぼ全部がこの時間です。
:::

## ページキャッシュ：一度読んだものは、メモリに残す {#pagecache}

カーネルは、ディスクから読んだファイルの中身を、すぐには捨てません。**メモリに残しておきます**。次に同じ場所を読まれたら、ディスクには行かず、メモリから返します。この置き場所を、**ページキャッシュ**（page cache）と呼びます。ファイルの中身を、メモリと同じ 4 KiB のページ単位で持つので、この名前です。

```fig graph read の通り道。ページキャッシュにあれば（ヒット）、メモリから写して終わり。なければ（ミス）、ディスクから読んでキャッシュに入れ、そこから写す。ディスクを待つのは、ミスのときだけ
{
  col: 210, row: 100,
  nodes: [
    { id: 'p', label: 'cat', sub: 'read(3, buf, 4096)', x: 0, y: 0, kind: 'accent' },
    { id: 'c', label: 'ページキャッシュ', sub: 'メモリの中。ファイルごとに、ページの番号で引く', x: 1, y: 0, w: 300, kind: 'heap', mono: false },
    { id: 'd', label: 'ディスク', sub: '/dev/sda1。1 ページ 5 ミリ秒', x: 1, y: 1, w: 300, kind: 'ext', mono: false },
  ],
  edges: [
    { from: 'p', to: 'c', label: 'あれば、ここから写す', style: 'accent' },
    { from: 'c', to: 'd', label: 'なければ読みに行く（待つ）' },
  ],

```

第 12 章の VFS の図で言えば、ページキャッシュは、VFS と ext4 のあいだに入っています。`cat` は、キャッシュがあることを知りません。同じ `read` を呼ぶだけです。

ファイルのどれだけがキャッシュに載っているかは、`fincore` で見られます（file in core。core は、メモリの古い呼び名です）。

```sh run title="big.dat のうち、キャッシュに載っている量"
fincore big.dat
```

`PAGES` が 100、`RES` が 400K です。`big.dat` の 100 ページ全部が、メモリに載っています。さっきの 2 回目が速かったのは、このためです。

### キャッシュを捨てて、もう一度

キャッシュのおかげだと確かめるには、キャッシュを捨てて、また遅くなるかを見ればわかります。`/proc/sys/vm/drop_caches` に 1 を書くと、カーネルはページキャッシュを捨てます。第 12 章で見た「書き込める `/proc`」の 1 つで、root だけが書けます。

```sh run root title="ページキャッシュを捨てる"
echo 1 > /proc/sys/vm/drop_caches
fincore /home/you/big.dat
```

`PAGES` が 0 になりました。ファイルそのものは、ディスクの上に無事に残っています。消えたのは、メモリの上の写しだけです。

今度は、`/usr/bin/time -v` で計ります。シェルの `time` とは別のコマンドで、時間のほかに、使った資源を細かく報告します。必要な行だけを `grep` で抜き出します。

```sh run title="キャッシュがないとき"
/usr/bin/time -v cat big.dat 2>&1 > /dev/null | grep -E 'Elapsed|File system inputs'
```

```sh run title="キャッシュがあるとき"
/usr/bin/time -v cat big.dat 2>&1 > /dev/null | grep -E 'Elapsed|File system inputs'
```

1 回目は 0.64 秒、2 回目は 0.21 秒です。`File system inputs` は、**ディスクから読んだ量**です（単位は 512 バイトのブロック）。1 回目は 840、2 回目は 0 です。2 回目の `cat` は、ディスクに 1 回も触っていません。

:::note 840 の内わけ
`big.dat` は 100 ページ = 800 ブロックです。残りの 40 ブロック（5 ページ）は、`cat` のプログラムそのものです。`/usr/bin/cat` もディスクの上のファイルなので、実行するときにページキャッシュを通して読まれます。`drop_caches` で、それも捨てられていました。一度使ったコマンドの 2 回目の起動が速いのも、ページキャッシュのおかげです。
:::

### ヒットとミスを見る

キャッシュは、ファイル単位ではなく、ページ単位です。キャッシュを捨ててから、`dd` で先頭の 3 ページだけを読んでみます。`dd` は、決まった大きさのかたまりを、決まった回数だけ写すコマンドです（後の節で詳しく使います）。ここでは「4 KiB を 3 回」です。

実行結果の下の「ページキャッシュの観察」に、カーネルの中で起きたことが並びます。同じコマンドを 2 回実行して、比べてください。

```sh run root title="もう一度、捨てる"
echo 1 > /proc/sys/vm/drop_caches
```

```sh run trace="pagecache" title="先頭の 3 ページだけを読む（1 回目と 2 回目）"
dd if=big.dat of=/dev/null bs=4k count=3 status=none
dd if=big.dat of=/dev/null bs=4k count=3 status=none
```

1 回目の最後の 3 行は、`/home/you/big.dat` の page 0、1、2 の **miss** です。キャッシュになかったので、ディスクから読みました。`ms 5` は、5 ミリ秒待ったという意味です。2 回目は、同じ 3 ページが **hit** に変わります。その前に並んでいる `/usr/bin/dd` と `/usr/lib/libc.so.6` は、プログラムを読み込んだときのものです。

```sh run title="載っているのは、読んだ 3 ページだけ"
fincore big.dat
```

`PAGES` は 3 です。読んでいない残りの 97 ページは、ディスクにあるだけです。大きなファイルの一部だけを読むプログラムは、その一部だけがメモリに載ります。

## free の buff/cache {#free}

ページキャッシュは、メモリを使います。どれだけ使っているかは、第 13 章で使った `free` に出ています。`big.dat` を全部読む前と後で、比べます。

```sh run title="読む前と、読んだ後"
free
cat big.dat > /dev/null
free
```

`buff/cache` の列が、ページキャッシュの大きさです（単位は KiB）。`big.dat` の残りの 97 ページ（と、`cat` のプログラム）を読んだので、400 ほど増えました。そのぶん `free`（空き）が減っています。

ここで大事なのは、右端の `available` です。こちらは、ほとんど変わっていません。

| 列 | 意味 |
| --- | --- |
| `used` | プログラムが使っていて、取り上げられないメモリ |
| `free` | 何にも使っていないメモリ |
| `buff/cache` | ページキャッシュ。ファイルの写し |
| `available` | 新しいプログラムが使えるメモリ。`free` と、すぐ捨てられるキャッシュの合計に近い |

ページキャッシュは、ディスクにあるものの写しです。捨てても、何も失いません。だからカーネルは、メモリが足りなくなったら、キャッシュのページを捨てて、そのフレームをプログラムに回します。**キャッシュに使われているメモリは、実質的には「空き」です**。

Linux をしばらく動かすと、`free` の列はどんどん小さくなり、`buff/cache` が大きくなります。「メモリが足りない」と心配する人がいますが、これは正常です。空いているメモリは、何の役にも立っていません。キャッシュに使えば、次の読み込みが速くなります。足りないかどうかは、`free` ではなく `available` で判断します。

同じ数字は、`/proc/meminfo` にもあります。`free` は、これを読んで表にしています。

```sh run title="/proc/meminfo の、キャッシュに関係する行"
grep -E '^(MemFree|MemAvailable|Cached|Dirty|Writeback):' /proc/meminfo
```

`Cached` がページキャッシュです。その下の `Dirty` と `Writeback` が、次の節の主役です。

## 書き込みは、遅らせる {#dirty}

読み込みは、2 回目から速くなりました。書き込みは、どうでしょうか。ディスクに 1 ページ書くのに 5 ミリ秒かかるなら、100 ページで 0.5 秒かかるはずです。

`dd` で、100 ページぶんのファイルを書いてみます。`dd` は、終わると、写した量とかかった時間を報告します。

```sh run title="400 KiB を書く"
dd if=/dev/urandom of=out.dat bs=4k count=100
```

0.201 秒でした。`read` と `write` が 100 回ずつで 0.2 秒ですから、**ディスクを待った時間は、ほぼ 0** です。5 ミリ秒 × 100 ページの 0.5 秒は、どこにもありません。

種明かしをします。`write` システムコールは、ディスクに書いていません。**ページキャッシュのページを書き換えて、「このページは、ディスクとまだ違う」という印をつけて、すぐ戻ります**。この印のついたページを、**ダーティページ**（dirty page。汚れたページ）と呼びます。

```sh run title="まだディスクに書かれていない量"
grep -E '^(Dirty|Writeback):' /proc/meminfo
fincore out.dat
```

`Dirty` が 400 kB あります。`out.dat` の中身は、いまメモリの上にしかありません。`ls` で見えるし、`cat` で読めますが、ディスクの上の `out.dat` は、まだ空です。

ダーティページをディスクに書き出すことを、**書き戻し**（writeback）と呼びます。`sync` コマンドは、すべてのダーティページを書き戻して、終わるまで待ちます。

```sh run title="sync：いますぐ全部書く"
time sync
grep -E '^(Dirty|Writeback):' /proc/meminfo
```

`sync` に 0.5 秒あまりかかりました。さっき消えていた「5 ミリ秒 × 100 ページ」は、ここで払っています。`Dirty` は 0 に戻りました。

```fig seq 書き込みの流れ。write はページキャッシュに書いて、すぐ戻る。ディスクに届くのは、sync や fsync を呼んだときか、カーネルが後で見回ったとき
{
  colw: 250,
  actors: [
    { id: 'p', label: 'プロセス' },
    { id: 'c', label: 'ページキャッシュ', kind: 'heap' },
    { id: 'd', label: 'ディスク', kind: 'ext' },
  ],
  msgs: [
    { from: 'p', to: 'c', label: 'write(fd, …)', style: 'accent' },
    { note: 'ページを書き換えて、ダーティの印', at: 'c' },
    { from: 'c', to: 'p', label: 'すぐ戻る（ディスクは待たない）' },
    { note: 'この間、データはメモリにしかない', at: ['p', 'd'], style: 'accent' },
    { from: 'c', to: 'd', label: '書き戻し（sync、fsync、30 秒後の見回り）' },
    { note: '印を消す（きれいなページ）', at: 'c' },
  ],
}
```

### なぜ遅らせるのか

理由は 3 つあります。

- **プログラムを待たせない**。`write` のたびに 5 ミリ秒待つより、メモリに書いて先へ進むほうが速い
- **まとめて書ける**。同じページに 100 回書いても、ディスクに書くのは最後の 1 回で済む
- **書かずに済むこともある**。作ってすぐ消した一時ファイルは、ディスクに 1 度も届かない

### 放っておいても、30 秒ほどで書かれる

`sync` を呼ばなくても、カーネルは定期的に見回って、古くなったダーティページを書き戻します。この Linux でも本物でも、既定では「**ダーティになって 30 秒たったページを、5 秒ごとの見回りで書く**」です。設定は `/proc/sys/vm` にあります（単位は 100 分の 1 秒）。

```sh run title="見回りの設定"
cat /proc/sys/vm/dirty_expire_centisecs
cat /proc/sys/vm/dirty_writeback_centisecs
```

小さなファイルを書いて、何もせずに 40 秒待ってみます。

```sh run title="書いた直後"
echo "下書き" > draft.txt
grep '^Dirty:' /proc/meminfo
```

```sh run trace="pagecache" title="40 秒待つ"
sleep 40
grep '^Dirty:' /proc/meminfo
```

「ページキャッシュの観察」に、`writeback`（`reason expire`。期限が来た）と、そのあとの `clean`（書き終わって、きれいになった）が出ます。`Dirty` は 0 に戻りました。だれも `sync` を呼んでいません。

## fsync：このファイルだけ、いま書く {#fsync}

「30 秒以内に、たぶん書かれる」では困るプログラムがあります。銀行の振り込みを記録するデータベースは、「記録しました」と答える前に、データが確実にディスクに届いていなければなりません。

そのためのシステムコールが **`fsync(fd)`** です。その fd のファイルのダーティページを書き戻して、終わるまで待ちます。`sync` がシステム全体なのに対して、`fsync` は 1 つのファイルだけです。

`dd` に `conv=fsync` をつけると、書き終わった後に `fsync` を呼びます。`strace` で確かめます。

```sh run title="最後に fsync を呼ぶ"
strace -e trace=openat,write,fsync dd if=/dev/zero of=safe.dat bs=4k count=2 conv=fsync status=none
```

`write` 2 回の後に、`fsync(4) = 0` があります。`fsync` が 0 を返したときには、`safe.dat` の中身はディスクの上にあります。

かかる時間を、100 ページで比べます。

```sh run title="fsync なしと、fsync あり"
dd if=/dev/urandom of=a.dat bs=4k count=100
dd if=/dev/urandom of=b.dat bs=4k count=100 conv=fsync
```

`fsync` なしは 0.201 秒、ありは 0.701 秒です。差の 0.5 秒が、ディスクに 100 ページ書く時間です。`fsync` は、安全と引き換えに、遅さを引き受けます。

| | 何を書き戻すか | だれが呼ぶか |
| --- | --- | --- |
| `sync` | すべてのファイル | 人がコマンドで。シャットダウンの手順の中で |
| `fsync(fd)` | そのファイルだけ | プログラムが、大事な書き込みの後で |
| 見回り | 30 秒たったページ | カーネルが自分で |

テキストエディタは、保存のたびに `fsync` を呼びます。データベースは、取引を確定するたびに呼びます。データベースの速さが、ディスクの `fsync` の速さで決まることが多いのは、このためです。

## 電源が切れると、消える {#powercut}

書き戻す前に電源が切れたら、ダーティページはどうなるでしょうか。メモリの中身は、電源が切れると消えます。ディスクにまだ届いていないデータは、**なくなります**。

実験します。2 つのファイルを用意します。`keep.txt` は、書いてから `sync` します。その後で、`keep.txt` に 1 行を追記し、新しいファイル `lost.txt` を作ります。こちらは `sync` しません。

```sh run title="sync したものと、していないもの"
echo "1 行目：sync した" > keep.txt
sync
echo "2 行目：sync していない" >> keep.txt
echo "これも sync していない" > lost.txt
cat keep.txt lost.txt
grep '^Dirty:' /proc/meminfo
```

`cat` では、3 行とも読めます。ページキャッシュに入っているからです。`Dirty` が 8 kB（2 ページ）あります。

ここで、電源を切ります。`reboot -ff` は、`sync` もせず、プロセスも止めずに、いきなり再起動します。コンセントを抜くのと同じです。

```sh run root title="いきなり電源を切る"
reboot -ff
```

機械が起動し直しました。ファイルを見ます。

```sh run title="再起動の後"
uptime
ls -l keep.txt lost.txt
cat keep.txt
cat lost.txt
```

- `keep.txt` には、`sync` した 1 行目だけが残りました。追記した 2 行目は、消えました
- `lost.txt` は、**名前はあるのに、中身が空**（0 バイト）です

`lost.txt` の名前が残ったのは、ファイルを作るという操作（ディレクトリに名前を足す、inode を作る）が、中身とは別に、先にディスクへ記録されるからです。その結果、「空のファイルだけが残る」という、いちばん紛らわしい壊れ方になります。設定ファイルを書き換えている途中で電源が落ちて、空のファイルになっていた、という事故は、本物の Linux でも起きます。

それより前に `sync` や `fsync` で書いたファイル（`big.dat`、`out.dat`、`b.dat`）や、30 秒の見回りで書かれた `draft.txt` は、無事です。

```sh run title="無事だったファイルと、起動時の記録"
ls -l big.dat out.dat b.dat draft.txt
dmesg | grep -i journal
```

`dmesg`（カーネルのログ）に、`recovering journal` とあります。第 11 章で触れた**ジャーナル**です。ファイルシステムは、起動のときに「前回、正しく止められなかった」ことに気づき、ジャーナルを読んで、ディレクトリや inode のつじつまを合わせました。ジャーナルが守るのは、**ファイルシステムの構造**です。`fsync` していないファイルの中身までは、守ってくれません。

:::tip ふだんの終わり方では、消えない
ふつうの `reboot` や `poweroff` は、プロセスを止めて、`sync` してから電源を切ります。だから、ふだんは何も失いません。消えるのは、停電、電源ボタンの長押し、カーネルの異常停止のように、`sync` する間もなく止まったときです。USB メモリを「取り外し」の操作をせずに抜くと壊れることがあるのも、同じ理由です。
:::

:::deep 大事なファイルを安全に書き換える
設定ファイルを直接書き換えると、途中で電源が切れたときに、空や半分のファイルが残ります。慎重なプログラムは、次の手順を踏みます。

1. 別の名前（`config.tmp`）で、新しい中身を書く
2. `fsync` して、ディスクに届くのを待つ
3. `rename("config.tmp", "config")` で、名前を付け替える

第 11 章で見たように、`rename` は一瞬で切り替わります。どの時点で電源が切れても、`config` は「古い中身の全部」か「新しい中身の全部」のどちらかです。
:::

## dd：かたまりの大きさを決めて写す {#dd}

ここまで道具として使ってきた `dd` を、整理します。`dd` は、入力から出力へ、**決まった大きさのかたまり（ブロック）を、決まった回数だけ**写します。引数の形が、ほかのコマンドと違って `名前=値` です。

| 引数 | 意味 |
| --- | --- |
| `if=ファイル` | 入力（input file）。省くと標準入力 |
| `of=ファイル` | 出力（output file）。省くと標準出力 |
| `bs=大きさ` | 1 回に読み書きする大きさ（block size）。`4k`、`1M` と書ける。既定は 512 バイト |
| `count=回数` | 何回写すか。省くと、入力の終わりまで |
| `skip=N` | 入力の先頭の N ブロックを飛ばす |
| `conv=fsync` | 最後に `fsync` する |
| `status=none` | 終わりの報告を出さない |

`/dev/zero`（第 12 章）と組み合わせると、好きな大きさのファイルが作れます。

```sh run title="1 KiB を 8 回 = 8 KiB のファイル"
dd if=/dev/zero of=zero.dat bs=1k count=8
ls -l zero.dat
```

報告の読み方です。

- `8+0 records in`：`bs` ちょうどの大きさで読めたのが 8 回、足りなかった（半端な）のが 0 回
- `8+0 records out`：書いたほうも同じ
- 最後の行：写したバイト数、かかった時間、速さ

`bs` より入力が短いと、半端なブロックになります。400 KiB の `big.dat` を、64 KiB ずつ読みます。

```sh run title="半端なブロック"
dd if=big.dat of=/dev/null bs=64k
```

`6+1 records in` です。64 KiB が 6 回（384 KiB）と、残りの 16 KiB が 1 回でした。再起動でキャッシュが空になっていたので、ディスクから読んでいます。

### bs で、システムコールの数が変わる

`dd` は、ブロック 1 つにつき、`read` を 1 回と `write` を 1 回呼びます。同じ量を写すなら、`bs` が小さいほど、システムコールが増えます。いまキャッシュに載っている `big.dat` の先頭 2,000 バイトを、2 通りに読みます。

```sh run title="1 バイトずつ 2,000 回と、2,000 バイトを 1 回"
dd if=big.dat of=/dev/null bs=1 count=2000
dd if=big.dat of=/dev/null bs=2000 count=1
```

1 バイトずつだと 4 秒、まとめて読むと 0.003 秒です。どちらもディスクは待っていません。違いは、システムコールの回数（4,000 回と 2 回）だけです。第 10 章で、ライブラリがバッファを使ってシステムコールを減らす話をしました。ページキャッシュがあっても、システムコールそのものの手間は残ります。

:::warn dd は、確かめずに書く
`dd` は、`of=` に書いた先を、何も聞かずに上書きします。本物の Linux では、`of=/dev/sda` と書けば、ディスクをまるごと壊せます。`if` と `of` を逆に書く間違いは、昔から数えきれないほど起きています。実行する前に、`of=` をもう一度読んでください。
:::

## STAT の D：ディスクを待っている {#dstate}

ディスクを待っているあいだ、プロセスはどういう状態でしょうか。第 7 章で `ps` の `STAT` を見ました。`R` は実行中か順番待ち、`S` は何かを待って眠っている、でした。ディスクを待っているプロセスには、別の文字がつきます。**`D`** です。

`big.dat` をキャッシュから追い出して、1 回の `read` で全部読ませます（`bs=1M`）。100 ページぶん、0.5 秒待つはずです。そのあいだに `ps` で見ます。

```sh run title="ディスクを待っているプロセス"
sudo sh -c 'echo 1 > /proc/sys/vm/drop_caches'
dd if=big.dat of=/dev/null bs=1M & sleep 0.2; ps -o pid,stat,comm; wait
```

`dd` の `STAT` が `D` です。`D` は、**割り込めない眠り**（uninterruptible sleep）と呼ばれます。`S` の眠りはシグナルで起こせますが、`D` のプロセスは、ディスクの返事が来るまで、シグナルを受け取りません。`kill -9` も、待ちが終わるまで効きません。

`sync` で書き戻しを待っているプロセスも、同じ `D` になります。

```sh run title="書き戻しを待っている sync"
dd if=/dev/zero of=c.dat bs=4k count=100 status=none
sync & sleep 0.2; ps -o pid,stat,comm; wait
```

ふつう、`D` は一瞬で終わるので、`ps` で見かけることはまれです。`D` のプロセスがいつも何個も見えるなら、ディスクが追いついていないか、壊れかけているか、ネットワーク越しのファイルシステムの相手が返事をしていません。第 14 章の**負荷平均**（load average）は、CPU の順番待ちだけでなく、`D` のプロセスも数えます。CPU が暇なのに負荷平均が高いときは、ディスクを疑います。

:::warn 本物との違い
- 本物の Linux は、ファイルを先頭から順に読んでいると気づくと、頼まれる前に先のページも読んでおきます（**先読み**）。この小さな Linux には、先読みがありません
- 本物の `free` の `buff/cache` には、ページキャッシュのほかに、ディレクトリや inode のキャッシュなども含まれます。`drop_caches` に 1 を書くとページキャッシュ、2 でそれ以外、3 で両方を捨てます。この小さな Linux では、1 と 3 は同じ働きです
- 本物の書き戻しはページ単位で進み、ダーティページが増えすぎると、`write` を呼んだプロセスを待たせて調整します。この小さな Linux では、ファイル単位でまとめて書きます
- 本物のディスクは、`fsync` に答えた後も、自分の中のメモリにデータを持っていることがあります。安いディスクや設定によっては、`fsync` が成功しても電源断で消えることがあります
- SSD や NVMe は、この章の「5 ミリ秒」より 50 倍以上速く、`D` を目にする機会はさらに減ります。それでも、メモリとの差は 1,000 倍あり、ページキャッシュの大切さは変わりません
:::

:::key この章のまとめ
- ディスクは、メモリより数千倍から数十万倍遅い。この遅さを隠すのが**ページキャッシュ**
- 一度読んだファイルのページは、メモリに残る。2 回目からは、ディスクに行かない（**ヒット**）。なければディスクから読む（**ミス**）。`fincore` で、載っているページ数がわかる
- `free` の `buff/cache` と、`/proc/meminfo` の `Cached` が、ページキャッシュの大きさ。メモリが足りなくなれば捨てられるので、実質は空き。使えるメモリは `available` で見る
- `write` は、ページキャッシュに書いて**ダーティ**の印をつけるだけで、すぐ戻る。ディスクには後で書く（**書き戻し**）。`/proc/meminfo` の `Dirty` が、まだ書いていない量
- 書き戻しが起きるのは、`sync`（全部）、`fsync(fd)`（そのファイル）、30 秒ほど後のカーネルの見回り
- 書き戻す前に電源が切れると、そのデータは消える。新しく作ったファイルは、空のファイルとして残る。大事なデータは `fsync` する
- `dd if= of= bs= count=` は、ブロック単位で写す。`bs` が小さいと、システムコールが増えて遅くなる
- ディスクを待っているプロセスは、`ps` の `STAT` が **`D`**。シグナルで起こせない
:::

## 確認問題 {#quiz}

ページキャッシュと `dd` を使った問題です。どの問題も、新しい Linux から始まります。

:::quiz キャッシュに載っているページ数
ホームディレクトリに `report.dat` があります。だれかが、その一部だけを読みました。`report.dat` のうち、いまページキャッシュに載っている**ページ数**だけを、数字で表示してください。

```sh prep
dd if=/dev/urandom of=report.dat bs=4k count=40 status=none
sync
sudo sh -c 'echo 1 > /proc/sys/vm/drop_caches'
dd if=report.dat of=/dev/null bs=4k count=7 status=none
```

```sh answer
fincore report.dat | tail -1 | awk '{print $2}'
```

```sh vary
dd if=report.dat of=/dev/null bs=4k count=23 status=none
```

```sh vary
cat report.dat > /dev/null
```

:::hint
`fincore ファイル` の 2 列目（`PAGES`）がページ数です。見出しの行を `tail -1` で除き、`awk '{print $2}'` で 2 列目を取り出します。
:::
:::

:::quiz dd でファイルの一部を切り出す
`data.bin` は、512 バイトのブロックが何個も並んだファイルです。先頭から数えて **3 つ目のブロック**（1,025 バイト目から 1,536 バイト目まで）だけを、`part.bin` という名前のファイルに取り出してください。

```sh prep
dd if=/dev/urandom of=data.bin bs=512 count=10 status=none
```

```sh answer
dd if=data.bin of=part.bin bs=512 skip=2 count=1
```

```sh check
wc -c < /home/you/part.bin
od -A x -t x1 /home/you/part.bin
```

:::hint
`bs=512` でブロックの大きさを決め、`skip=N` で先頭の N ブロックを飛ばし、`count=1` で 1 ブロックだけ写します。3 つ目を取り出すには、2 つ飛ばします。
:::
:::

:::quiz 電源が切れても残るように保存する
`/home/you/account.txt` に、`balance=100` という 1 行を書いてください。ただし、書いた直後に電源が切れても中身が残るように、**ディスクに届くところまで**済ませてください。

```sh prep
sync
```

```sh answer
echo balance=100 > account.txt
sync
```

```sh check
cat /home/you/account.txt
grep '^Dirty:' /proc/meminfo
```

:::hint
`echo … > ファイル` だけでは、中身はページキャッシュにあるだけです（`Dirty` が 0 でなくなります）。その後で `sync` を実行すると、ディスクに書き戻されます。
:::
:::

:::quiz ディスクから読むことになるページ数
ホームディレクトリに `log.dat` があります。一部はページキャッシュに載っていて、残りは載っていません。いま `cat log.dat` を実行したら、**ディスクから読むことになるページ数**（= キャッシュに載っていないページ数）を、数字で表示してください。`log.dat` の大きさは、4,096 バイトの倍数です。

```sh prep
dd if=/dev/urandom of=log.dat bs=4k count=50 status=none
sync
sudo sh -c 'echo 1 > /proc/sys/vm/drop_caches'
dd if=log.dat of=/dev/null bs=4k count=12 status=none
```

```sh answer
total=$(( $(stat -c %s log.dat) / 4096 ))
cached=$(fincore log.dat | tail -1 | awk '{print $2}')
echo $(( total - cached ))
```

```sh vary
dd if=log.dat of=/dev/null bs=4k count=31 status=none
```

```sh vary
dd if=/dev/urandom of=log.dat bs=4k count=20 status=none
sync
sudo sh -c 'echo 1 > /proc/sys/vm/drop_caches'
dd if=log.dat of=/dev/null bs=4k count=5 status=none
```

:::hint
全体のページ数は、ファイルの大きさ（`stat -c %s log.dat`）を 4096 で割ったものです。そこから、`fincore` の `PAGES`（載っているページ数）を引きます。シェルの計算は `$(( … ))` です。
:::
:::
