## プログラムファイルとは {#file}

第 2 章で、コマンドの実体は `/usr/bin` にあるファイルだと学びました。第 7 章では、シェルが fork して、子が `execve` でそのファイルに「入れ替わる」様子を見ました。この章では、その `execve` の中に入ります。カーネルは、渡されたファイルをどう読んで、どうやって動く状態にするのでしょうか。

まず、ファイルそのものを見ます。**`file`** は、ファイルの中身を調べて、種類を答えるコマンドです。

```sh run title="実行できるファイルは、2 種類ある"
ls -l /usr/bin/cat hello.sh
file /usr/bin/cat hello.sh memo.txt
```

`/usr/bin/cat` は **ELF** という形式のファイル、`hello.sh` はシェルスクリプト（文字で書かれたファイル）です。Linux で「実行できるファイル」は、大きく分けてこの 2 種類です。

- **ELF**… CPU がそのまま実行できる機械語の命令と、データを収めたファイル。C や Rust、Go などのコンパイラが作る
- **スクリプト**… 1 行目が `#!` で始まるテキスト。別のプログラム（インタプリタ）が読んで実行する

`file` は、拡張子ではなく**中身**を見て判断しています。Linux では、ファイル名の `.sh` や `.exe` に意味はありません。カーネルも、ファイルの先頭の数バイトだけを見て、種類を決めます。

```sh run title="先頭の 4 バイト"
head -c 4 /usr/bin/cat | od -c
head -c 9 hello.sh
```

ELF のファイルは、かならず `177 E L F`（8 進数の 177 = 16 進数の 7f）の 4 バイトで始まります。こういう「種類を示す決まった先頭のバイト列」を**マジックナンバー**と呼びます。スクリプトのマジックナンバーは、`#!` の 2 バイトです。

:::warn このサイトの Linux では
小さな Linux は機械語を実行しません。`/usr/bin` のファイルは、先頭に ELF のマジックナンバーと、いくつかの文字列を持つだけの「**ELF 風の印**」で、本当の命令は入っていません（コマンドの本体は、シミュレータの中の JavaScript です）。大きさも、それらしく見せた数字です。そこで、ELF の中身と共有ライブラリについては、本物の Debian で実行した結果を、実行しない例として載せます。`execve` の前後で起きること、`#!`、PATH の検索、`exec` は、小さな Linux で実際に動かせます。
:::

## ELF の中身 {#elf}

ELF（Executable and Linkable Format）は、1990 年代から Unix 系の OS で広く使われている形式です。実行ファイルだけでなく、共有ライブラリ（`.so`）や、コンパイルの途中のファイル（`.o`）も ELF です。

本物の Debian で、`cat` を調べます。

```console
$ file /usr/bin/cat
/usr/bin/cat: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked,
 interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=8ff77e55…, for GNU/Linux 3.2.0, stripped
```

- `64-bit`、`x86-64` … どの CPU のための命令か。ARM の機械なら `ARM aarch64` になる。別の CPU 用の ELF は実行できない
- `LSB` … 数を下の桁のバイトから並べる（リトルエンディアン）
- `dynamically linked`、`interpreter /lib64/ld-linux-x86-64.so.2` … 共有ライブラリを使う。その読み込みを担当するプログラムの名前（あとの節）
- `stripped` … デバッグ用の名前の表を取り除いてある

ファイルの先頭には、**ELF ヘッダ**という 64 バイトの表があります。**`readelf -h`** で読めます。

```console
$ readelf -h /usr/bin/cat
ELF Header:
  Magic:   7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00
  Class:                             ELF64
  Data:                              2's complement, little endian
  Type:                              DYN (Position-Independent Executable file)
  Machine:                           Advanced Micro Devices X86-64
  Entry point address:               0x35a0
  Start of program headers:          64 (bytes into file)
  Number of program headers:         14
  Start of section headers:          45672 (bytes into file)
  Number of section headers:         30
  （一部の行を省略）
```

大事なのは 2 つです。

- **Entry point address**（エントリポイント）… 最初に実行する命令の番地。`main` ではなく、その前の準備をする `_start` という場所
- **program headers**（プログラムヘッダ）… 「ファイルのどの部分を、メモリのどこに、どの権限で置くか」の表。カーネルが `execve` のときに読むのは、この表

プログラムヘッダの 1 行 1 行が指す、ファイルの中のひとかたまりを**セグメント**と呼びます。

```console
$ readelf -lW /usr/bin/cat
  Type     Offset   VirtAddr           FileSiz  MemSiz   Flg Align
  INTERP   0x000394 0x0000000000000394 0x00001c 0x00001c R   0x1
      [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]
  LOAD     0x000000 0x0000000000000000 0x001a08 0x001a08 R   0x1000
  LOAD     0x002000 0x0000000000002000 0x005a89 0x005a89 R E 0x1000
  LOAD     0x008000 0x0000000000008000 0x002458 0x002458 R   0x1000
  LOAD     0x00a9f0 0x000000000000b9f0 0x0006d0 0x0008b0 RW  0x1000
  （PhysAddr の列と、ほかの行を省略）
```

`LOAD` の行が、メモリに置かれるセグメントです。`Flg` の `R E` は読めて実行できる（命令）、`R` は読めるだけ（定数）、`RW` は読み書きできる（変数）です。


最後の `RW` のセグメントは、`FileSiz`（ファイルの中の大きさ）より `MemSiz`（メモリの上の大きさ）のほうが大きくなっています。差の部分は、初期値が 0 の変数（**.bss**）です。0 が並ぶだけの場所をファイルに持っておく必要はないので、「メモリではこれだけ広げて、0 で埋めて」と大きさだけを書いてあります。

第 13 章の「[アドレス空間の地図](ch13.html#maps)」で、`/proc/PID/maps` の最初の 3 行が `r-xp`、`r--p`、`rw-p` の `/usr/bin/cat` だったのを思い出してください。あの 3 行は、ELF の LOAD セグメントを写したものです。

小さな Linux のファイルも、先頭の何バイトかは ELF の形をしています。

```sh run title="小さな Linux の /usr/bin/cat の先頭"
hexdump -C /usr/bin/cat | head -8
```

1 行目が `7f 45 4c 46`（`\x7fELF`）で始まり、少し先に `/lib64/ld-linux-x86-64.so.2` と `libc.so.6` の文字が見えます。そのあいだの `zukai:cat` が、「このファイルの本体は、シミュレータの中の cat」という印です。本物の ELF に、この印はありません。

:::deep セクションとセグメント
ELF には、中身を区切る表が 2 つあります。**セクション**（`.text`、`.rodata`、`.data`、`.bss`、`.symtab` …）は、コンパイラとリンカが使う細かい区切りです。**セグメント**は、実行のときにカーネルが使う粗い区切りで、同じ権限のセクションをいくつかまとめたものです。プログラムを実行するだけなら、セクションヘッダ表は要りません（取り除いても動きます）。
:::

## execve：プロセスの中身を入れ替える {#execve}

`execve` は、「このプロセスの中身を、このファイルのプログラムに入れ替えて」とカーネルに頼むシステムコールです。strace で見ます。

```sh run strace title="cat を実行したときのシステムコール"
cat /etc/hostname
```

1 行目が `execve` です。引数は 3 つあります。

```text
execve("/usr/bin/cat", ["cat", "/etc/hostname"], 0x7ffd3c2a1b40 /* 8 vars */) = 0
        ~~~~~~~~~~~~~~  ~~~~~~~~~~~~~~~~~~~~~~~~  ~~~~~~~~~~~~~~~~~~~~~~~~~~~~
        ファイルのパス     引数の配列（argv）          環境変数の配列（envp。8 個ある）
```

`execve` が成功すると、カーネルは次のことをします。

1. ファイルを開き、実行の権限（x）を調べ、先頭を読んで種類を決める
2. いまの**アドレス空間を捨てる**。text も、ヒープも、スタックも、すべて
3. ELF のプログラムヘッダに従って、新しいアドレス空間を作る。ファイルのセグメントを写し、新しいスタックを用意する
4. スタックに、引数と環境変数を積む（あとの節）
5. エントリポイントから、実行を始める

大事なのは、**プロセスは作られない**ことです。PID は変わりません。入れ替わったことを、`/proc/PID/maps` で確かめます。`exec` は、シェルが fork せずに自分自身で `execve` を呼ぶ組み込みコマンドです（第 7 章）。

```sh run title="同じ PID のまま、アドレス空間が入れ替わる"
sh -c 'echo "PID $$"; head -1 /proc/$$/maps; exec head -1 /proc/self/maps'
sh -c 'echo "PID $$"; exec readlink /proc/self'
```

1 つめ。`exec` の前は、アドレス空間の先頭に `/usr/bin/sh` が写っていました。`exec head` のあとは、`/usr/bin/head` です。2 つめ。`/proc/self` は「自分の PID」へのシンボリックリンクなので、`readlink /proc/self` は `readlink` 自身の PID を表示します。`exec` の前に `sh` が表示した PID と同じです。


| execve をまたいで残るもの | 作り直されるもの |
| --- | --- |
| PID、PPID、uid、gid | アドレス空間（text、data、ヒープ、スタック、mmap した領域） |
| fd 表（`O_CLOEXEC` の印つきを除く。第 9 章） | シグナルのハンドラ（既定の動作に戻る。「無視」の設定は残る。第 8 章） |
| カレントディレクトリ、umask | プログラムの中の変数すべて |
| `execve` に渡した引数と環境変数 | |

fd 表が残るから、シェルが fork のあと `execve` の前に仕込んだリダイレクトが、新しいプログラムでも効きます。ハンドラが戻されるのは、ハンドラの関数が古いアドレス空間にあって、もう存在しないからです。

`execve` は、成功すると**戻ってきません**。戻る先のプログラムが、もうないからです。strace の `= 0` は、便宜上の表示です。失敗したときだけ、元のプログラムに -1 が返ります。

```sh run error title="execve が失敗する例"
./memo.txt
mkdir -p box
./box
```

どちらも、シェルが fork した子で `execve` が失敗し、子のシェルがエラーを表示して 126 で終わっています。`memo.txt` には x の権限がありません（`EACCES`）。ディレクトリは、プログラムとして実行できません。

## #! とインタプリタ {#shebang}

ファイルの先頭が ELF のマジックナンバーではなく `#!` だったら、カーネルは 1 行目の残りを読んで、**そこに書いてあるプログラムのほうを実行します**。第 6 章の「[スクリプトファイルと #!](ch06.html#script)」で見た仕組みです。もう少し中まで見ます。

```sh run title="スクリプトを動かして、その正体を見る"
printf '#!/bin/sh\nsleep 100\n' > nap.sh
chmod +x nap.sh
./nap.sh &
sleep 1
ps -o pid,ppid,comm,args
readlink /proc/$!/exe
```

`./nap.sh` と打って起動したプロセスの、引数の列（`args`）は `/bin/sh ./nap.sh` になっています。`/proc/PID/exe` は「このプロセスが実行しているプログラムのファイル」を指すリンクで、`/usr/bin/sh` です（`/bin` は `/usr/bin` へのリンクです）。`nap.sh` ではありません。

カーネルがしたのは、引数の書き換えです。

```text
execve("./nap.sh", ["./nap.sh"])
  ↓ 先頭が #! なので、1 行目の「/bin/sh」を取り出し、引数の前に足す
execve("/bin/sh", ["/bin/sh", "./nap.sh"])
```

`sh` から見ると、「`sh ./nap.sh` と起動された」のと同じです。`sh` は引数のファイルを開いて、上から読んで実行します。1 行目の `#!/bin/sh` は、`sh` にとってはコメントなので、無視されます。

この仕組みに、シェルは関係ありません。`#!` の後ろには、**ファイルの名前を引数に取るプログラムなら何でも**書けます。`awk -f ファイル` は、ファイルに書いた awk のプログラムを実行する形でした（第 5 章）。

```sh run strace title="awk のスクリプトを、名前で実行する"
printf '#!/usr/bin/awk -f\n{ n++ }\nEND { print n }\n' > lines.awk
chmod +x lines.awk
./lines.awk fruits.txt
```

カーネルは `./lines.awk fruits.txt` を `/usr/bin/awk -f ./lines.awk fruits.txt` に書き換えました。strace で、起動された `awk` が、まず `./lines.awk` を開いてプログラムを読み、次に `fruits.txt` を開いて行を数えているのが見えます。`#!` の行のオプションは、1 つだけ書けます（空白で区切っても、全体が 1 つの引数として渡されます）。

Python のスクリプトの `#!/usr/bin/python3` も、Perl や Ruby も、同じ仕組みです。カーネルは、どの言語のことも知りません。

### #! が間違っているとき

```sh run error title="インタプリタが、ない"
printf '#!/usr/bin/nothing\necho hi\n' > bad.sh
chmod +x bad.sh
ls -l bad.sh
./bad.sh
```

`bad.sh` は確かにあるのに、`No such file or directory` と言われます。「ない」のは、`#!` に書いた `/usr/bin/nothing` のほうです。`execve` は、どのファイルがなかったのかを教えてくれません（返ってくるのは `ENOENT` という番号だけです）。「あるはずのスクリプトが、ないと言われる」ときは、1 行目を疑います。Windows で編集したファイルで、行末に見えない `\r` が入って `/bin/sh\r` を探しに行ってしまう、というのもよくある原因です。

:::note #! がないテキストファイルに x をつけると
カーネルは、ELF でも `#!` でもないファイルを `ENOEXEC`（実行できる形式ではない）で断ります。ただし、シェルはこの失敗を見ると、親切に「シェルスクリプトだろう」と考えて、自分で読んで実行します。動いてしまうので気づきにくいのですが、どのシェルで実行されるかが呼び出し元しだいになります。スクリプトには、かならず `#!` を書きます。
:::

後片づけをします。

```sh run title="nap.sh を終わらせる"
kill %1
```

## PATH を探すのは、シェルの仕事 {#path}

`execve` の第 1 引数は、ファイルの**パス**です。カーネルは、`cat` という名前だけを渡されても、探してくれません。`cat` を `/usr/bin/cat` にするのは、`execve` を呼ぶ側、つまりシェル（と libc）の仕事です。第 2 章の「[PATH](ch02.html#path)」で見た検索を、システムコールで確かめます。

```sh run strace="all" error title="ないコマンドを探す"
nosuchcmd
```

シェルが、PATH のディレクトリを左から順に、`stat` で「このファイルはあるか」と尋ねています。3 つとも `ENOENT` だったので、fork もせずに `command not found` を表示しました。終了ステータスは 127 です。

見つかる場合を見ます。`strace -f` は、子プロセスも追います。

```sh run title="あるコマンドを探す"
echo $PATH
strace -f -o t.log sh -c 'cat /etc/hostname'
grep -E 'stat|execve' t.log
```

`/usr/local/bin/cat` は `ENOENT`、次の `/usr/bin/cat` で見つかり、そのパスで `execve` しています。PATH の 3 番目の `/bin` は、調べていません。**最初に見つかったものを使う**からです。

名前に `/` が入っていれば、シェルは PATH を探しません。そのままパスとして `execve` に渡します。`./hello.sh` に `./` が要るのは、このためでした。

| 打った名前 | シェルがすること |
| --- | --- |
| `cat` | PATH のディレクトリを順に探して、見つかったパスを `execve` に渡す |
| `/usr/bin/cat`、`./nap.sh`、`bin/tool` | `/` があるので、そのまま `execve` に渡す |
| `cd`、`echo`、`exec` | 組み込みコマンド。`execve` しない |

:::tip 同じ名前のコマンドが 2 つあるとき
PATH の前のほうにあるものが勝ちます。「入れ直したのに、古い版が動く」ときは、`which 名前` か `type 名前` で、どのファイルが実行されているかを確かめます。`/usr/local/bin` が `/usr/bin` より前にあるのは、自分で入れたものを、配布されたものより優先するためです。
:::

## 引数と環境変数は、スタックに積まれる {#stack}

`execve` でアドレス空間が捨てられるなら、引数の `"/etc/hostname"` という文字列は、どうやって新しいプログラムに届くのでしょうか。カーネルが、古いアドレス空間から**コピーして、新しいスタックのいちばん上に積んでおきます**。

C のプログラムの `main(int argc, char *argv[])` が受け取る `argc` と `argv` は、これです。プログラムは、起動した瞬間に、スタックの先頭を見れば、引数の数と中身がわかります。環境変数も同じ場所にあり、`getenv("HOME")` は `envp` の表を順に探しているだけです。

カーネルは、この場所を覚えているので、`/proc` から見られます。区切りは、値が 0 のバイトです。

```sh run title="プロセスが受け取った引数と環境変数"
tr '\0' '\n' < /proc/self/cmdline
tr '\0' '\n' < /proc/self/environ
```

`ps` が表示するコマンドラインは、`/proc/PID/cmdline`、つまり、そのプロセスのスタックの上の文字列を読んだものです。

環境変数は、第 7 章で「[子にコピーされる](ch07.html#env)」と学びました。その「コピー」の実体は、`execve` の第 3 引数です。**`env`** は、環境変数を足して（または空にして）から、コマンドを `execve` するだけのコマンドです。

```sh run strace title="env が環境変数を 1 つ足して、execve する"
env GREETING=hi sh -c 'echo $GREETING'
```

`execve` が 2 回あります。1 回めはシェルが `env` を起動したもので、環境変数は 8 個です。2 回めは `env` が `sh` に入れ替わったもので、**9 個**に増えています。`env` は fork していません。自分の環境に `GREETING=hi` を足して、そのまま `sh` に入れ替わりました。

```sh run title="env -i：環境を空にして起動する"
env -i A=1 B=2 /usr/bin/env
```

`-i` をつけると、受け継いだ環境を捨てて、指定したものだけを渡します。PATH もなくなるので、コマンドは絶対パスで書いています。環境変数は、特別な仕組みではなく、「`execve` のときに渡す文字列の配列」にすぎません。

:::note 引数の長さには、上限がある
引数と環境変数は、スタックにコピーされます。だから、合計の大きさに上限があります（本物の Linux では、ふつうスタックの上限の 4 分の 1 で、2 MiB ほど）。`rm *` で何十万ものファイル名を渡すと、`execve` が `E2BIG` で失敗して、`Argument list too long` と表示されます。そのときは、`find … | xargs rm` のように、何回かに分けて渡します（第 5 章）。
:::

## 動的リンクと共有ライブラリ {#dynlink}

`cat` は、ファイルを開くのに `open`、書くのに `write` という libc の関数を使います（第 10 章）。その関数の命令は、どこにあるのでしょうか。`cat` のファイルの中には、**入っていません**。

`printf` や `malloc` のような、ほとんどのプログラムが使う関数を、全部のプログラムのファイルに 1 つずつ入れておくのは、ディスクの無駄です。そこで、共通の関数は**共有ライブラリ**（shared library。`.so` ファイル）という別のファイルにまとめておき、プログラムが**動き始めるとき**に、アドレス空間へつなぎ込みます。これが**動的リンク**（dynamic linking）です。

あるプログラムがどの共有ライブラリを必要とするかは、**`ldd`** でわかります。本物の Debian での結果です。

```console
$ ldd /usr/bin/cat
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007fffff5c2000)
	/lib64/ld-linux-x86-64.so.2 (0x00007ffffffc8000)
$ ldd /usr/bin/ls
	libselinux.so.1 => /lib/x86_64-linux-gnu/libselinux.so.1 (0x00007fffff766000)
	libcap.so.2 => /lib/x86_64-linux-gnu/libcap.so.2 (0x00007fffff75a000)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007fffff566000)
	libpcre2-8.so.0 => /lib/x86_64-linux-gnu/libpcre2-8.so.0 (0x00007fffff4b7000)
	/lib64/ld-linux-x86-64.so.2 (0x00007ffffffc8000)
```

`cat` が必要とするのは、`libc.so.6`（C の標準ライブラリ）だけです。`ls` は、ほかに 3 つ使います。かっこの中は、読み込まれる番地で、実行のたびに変わります（機械によっては、カーネルが用意する `linux-vdso.so.1` の行も出ます）。

どちらにも出てくる `/lib64/ld-linux-x86-64.so.2` が、**動的リンカ**（dynamic linker。`ld.so` とも呼ぶ）です。`file` や `readelf -l` の出力で `interpreter` と書かれていたものです。共有ライブラリを探して、読み込んで、つなぐ仕事をするのは、カーネルではなく、このプログラムです。

写された結果は、小さな Linux の地図にも出ています。

```sh run title="アドレス空間の中の libc"
grep libc /proc/self/maps
```

`libc.so.6` も ELF なので、`cat` 本体と同じく、命令・定数・変数の 3 つの領域になります。命令と定数の領域は、ファイルを写しただけで、書き換えません。だから、**同じ物理メモリを、すべてのプロセスで共有できます**（第 13 章の「[ファイルを mmap する](ch13.html#mmap-file)」）。プロセスが 100 個あっても、libc の命令は、メモリの上に 1 つしかありません。「共有」ライブラリという名前は、ここから来ています。

### ライブラリを探す場所

動的リンカは、`libc.so.6` という名前だけを頼りに、ファイルを探します。探す順番は、おおよそ次のとおりです。

1. 環境変数 **`LD_LIBRARY_PATH`** に並んだディレクトリ（`:` 区切り。PATH と同じ形）
2. `/etc/ld.so.cache`（`ldconfig` コマンドが作っておく、「名前 → パス」の早見表）
3. 既定のディレクトリ（`/lib`、`/usr/lib` など）

本物の動的リンカに、探している様子を表示させたものです（`LD_DEBUG=libs` は、動的リンカへの指示です）。

```console
$ LD_LIBRARY_PATH=/tmp/mylib LD_DEBUG=libs cat /dev/null
       116:	find library=libc.so.6 [0]; searching
       116:	 search path=…:/tmp/mylib		(LD_LIBRARY_PATH)
       116:	  trying file=/tmp/mylib/libc.so.6
       116:	 search cache=/etc/ld.so.cache
       116:	  trying file=/lib/x86_64-linux-gnu/libc.so.6
```

まず `/tmp/mylib` を見て、なかったので、早見表から `/lib/x86_64-linux-gnu/libc.so.6` を見つけています。コマンドは PATH で、ライブラリは `LD_LIBRARY_PATH` で探す、と対にして覚えられます。どちらも環境変数なので、`execve` でスタックに積まれて、動的リンカに届きます。

必要なライブラリが見つからないと、プログラムは `main` に着く前に終わります。

```console
$ ./myapp
./myapp: error while loading shared libraries: libfoo.so.1: cannot open shared object file: No such file or directory
```

このエラーを出しているのは、シェルでもカーネルでもなく、動的リンカです。

:::note 静的リンク
ライブラリの命令を、コンパイルのときにプログラムのファイルへ全部コピーしておく方法もあります。**静的リンク**（static linking）です。ファイルは大きくなりますが、そのファイル 1 つだけで動きます。`file` は `statically linked` と表示し、`ldd` は `not a dynamic executable` と答えます。Go 言語のプログラムや、コンテナに入れる小さな道具（第 19 章の busybox）で、よく使われます。
:::

:::warn このサイトの Linux では
小さな Linux は、動的リンクをしません。`execve` のとき、プログラムと `libc.so.6` の領域を、いつも同じ番地に、最初から置きます。動的リンカ（`ld.so`）の領域は地図になく、`ldd`、`readelf`、`LD_LIBRARY_PATH` もありません。本物の `cat` の地図は 20 行ほどあり、番地は実行のたびに変わります（ASLR。攻撃者に番地を当てさせないための仕組み）。
:::

## exec：シェル自身が入れ替わる {#exec}

シェルは、ふつう fork してから子で `execve` します。組み込みコマンドの **`exec`** は、fork を省いて、**シェル自身**が `execve` します。シェルは、そのコマンドに入れ替わって、いなくなります。

```sh run title="exec のあとの行は、実行されない"
sh -c 'echo before; exec echo replaced; echo after'
```

`after` は表示されません。`exec` の時点で `sh` は `echo` に入れ替わり、3 つめのコマンドを読む者が、もういないからです。

:::warn ログインシェルで exec しない
いま打っているシェルで `exec ls` とすると、シェルが `ls` に入れ替わり、`ls` が終わった時点でログアウトになります。試すときは、上のように `sh -c '…'` の中で実行します。
:::

`exec` がいちばん役に立つのは、**準備をしてから本体を起動するスクリプト**です。前の章の `hello-daemon` のように、スクリプトからプログラムを起動すると、ふつうは `sh` が親として残ります。

```sh run title="exec しないスクリプトと、するスクリプト"
./nap.sh &
printf '#!/bin/sh\nexec sleep 100\n' > nap2.sh
chmod +x nap2.sh
./nap2.sh &
sleep 1
ps -o pid,ppid,comm,args
```

`nap.sh` のほうは、`sh`（`/bin/sh ./nap.sh`）と、その子の `sleep` の 2 つのプロセスがあります。`nap2.sh` のほうは、`sleep 100` が 1 つだけで、それがシェルの直接の子です。`sh` は `sleep` に入れ替わりました。

これには、プロセスが 1 つ減る以上の意味があります。`nap.sh` に SIGTERM を送ると、死ぬのは `sh` だけで、`sleep` は孤児として残ります。ここでは `pgrep -f nap.sh` で `sh` の PID だけを選んで送ります（`kill %1` と書くと、ジョブのプロセスグループ全体、つまり `sleep` にも届いてしまいます。第 8 章）。

```sh run title="kill すると、どうなるか"
kill $(pgrep -f nap.sh) %2
sleep 1
ps -o pid,ppid,comm,args
```

`nap.sh` の子だった `sleep 100` が、PPID 1 で生き残っています。`nap2.sh` のほうは、シグナルが `sleep` 本人に届いたので、何も残りません。サービスの起動スクリプトを「環境変数を設定して、最後に `exec 本体`」と書くのは、このためです。systemd が見張る Main PID が、`sh` ではなく、プログラム本人になります。

```sh run title="残った sleep を片づける"
pkill sleep
```

`exec` には、もう 1 つの使い方があります。コマンドを書かずにリダイレクトだけを書くと、入れ替わらずに、**シェル自身の fd を付け替えます**（第 9 章で `exec 3< ファイル` を使いました）。

```sh run title="exec でシェル自身の標準出力を付け替える"
sh -c 'exec > out.txt; echo "これはファイルに入る"; date'
cat out.txt
```

`exec > out.txt` のあとは、その `sh` が実行するすべてのコマンドの出力が、ファイルに入ります。スクリプトの先頭に書けば、スクリプト全体のログが取れます。

## 終わり方：exit_group {#exit}

最後に、プログラムの終わりを見ます。

```sh run strace error title="終了ステータス 3 で終わる"
sh -c 'exit 3'
```

`exit_group(3)` が、プロセスを終わらせるシステムコールです（`exit` ではなく `exit_group` なのは、プロセスの中のスレッドをすべて終わらせる、という意味です）。戻り値が `?` なのは、このシステムコールが**決して戻らない**からです。

C のプログラムでは、`main` から `return` すると終わります。しかし、CPU にとって「プログラムの終わり」というものはありません。命令が尽きたら、その先のメモリにあるでたらめなものを実行してしまいます。終わるには、カーネルに頼むしかありません。`main` を呼び出したのは libc の準備のコードで、`main` が戻ると、次のことをします。

1. `atexit` で登録された後始末の関数を呼ぶ
2. **出力のバッファに残っているものを `write` する**（第 10 章。`cat` の strace で、`exit_group` の直前に `write` があるのはこのため）
3. `main` の戻り値を引数にして、`exit_group` を呼ぶ

`exit_group` を受けたカーネルは、アドレス空間を捨て、開いている fd をすべて閉じ、子がいれば init に引き取らせ（第 7 章）、親に SIGCHLD を送ります。プロセスは**ゾンビ**になり、親が `wait4` で終了ステータスを受け取ると、プロセス表から消えます。

これで、輪が閉じました。`cat /etc/hostname` と打ってから、次のプロンプトが出るまでを、最初から並べます。

:::key この章のまとめ
- 実行できるファイルは、**ELF**（機械語。先頭が `\x7fELF`）と、**スクリプト**（先頭が `#!`）の 2 種類。カーネルは、拡張子ではなく先頭のバイトで見分ける。`file` で調べられる
- ELF は、**ELF ヘッダ**（エントリポイントなど）と、**プログラムヘッダ**（どの部分を、メモリのどこに、どの権限で置くか）を持つ。`/proc/PID/maps` の最初の数行は、そのセグメントを写したもの
- **`execve`** は、プロセスの**アドレス空間を作り直す**。PID、fd 表、カレントディレクトリは残る。成功すると戻ってこない
- **`#!`** のファイルを `execve` すると、カーネルは 1 行目のプログラムを起動し、スクリプトのパスを引数に足す。`/proc/PID/exe` はインタプリタを指す
- **PATH を探すのはシェル**。カーネルの `execve` は、パスをそのまま使う。名前に `/` があれば、探さない
- 引数と環境変数は、`execve` のときにカーネルが**新しいスタックにコピー**する。`/proc/PID/cmdline` と `environ` で見られる
- 本物のプログラムの多くは**動的リンク**。カーネルは**動的リンカ**（`ld.so`）を一緒に読み込み、動的リンカが `libc.so.6` などの**共有ライブラリ**を探して `mmap` でつなぐ。`ldd` で必要なライブラリがわかる。探す場所は `LD_LIBRARY_PATH` で足せる
- 組み込みの **`exec`** は、fork せずにシェル自身を入れ替える。起動スクリプトの最後に使うと、余分な `sh` が残らない
- プログラムは **`exit_group`** で終わる。その前に libc がバッファを書き出す
:::

## 確認問題 {#quiz}

プログラムの起動のしくみを、手を動かして確かめます。どの問題も、新しい Linux から始まります。

:::quiz スクリプトを、名前で実行できるようにする
ホームディレクトリに、awk のプログラム `count.awk` があります。いまは `awk -f count.awk fruits.txt` としないと動きません。これを、`./count.awk fruits.txt` と打つだけで動くようにしてください（ファイルを作り直してかまいません。awk のプログラムの部分は変えないでください）。

```sh prep
printf '{ n++ }\nEND { print n " lines" }\n' > count.awk
```

```sh answer
printf '#!/usr/bin/awk -f\n{ n++ }\nEND { print n " lines" }\n' > count.awk
chmod +x count.awk
```

```sh check
cd /home/you
./count.awk fruits.txt
./count.awk scores.csv fruits.txt
```

:::hint
必要なことは 2 つです。1 行目に `#!/usr/bin/awk -f` を足すことと、`chmod +x` で実行の権限をつけることです。1 行目を足すには、`printf` で全体を書き直すか、`{ echo '#!/usr/bin/awk -f'; cat count.awk; } > tmp` のように新しいファイルを作ってから `mv` します。
:::
:::

:::quiz このプロセスは、どのプログラムか
`./job` というスクリプトが、バックグラウンドで動いています。このプロセスが**実際に実行しているプログラムのファイル**のパスを表示してください。プロセスの PID は `$!` でわかります。

```sh prep
printf '#!/bin/sh\nwhile true; do sleep 50; done\n' > job
chmod +x job
./job &
sleep 1
```

```sh answer
readlink /proc/$!/exe
```

```sh vary
kill %1
printf '#!/usr/bin/tail -f\nwaiting\n' > job
./job > /dev/null &
sleep 1
```

```sh vary
kill %1
printf '#!/bin/sh\nexec sleep 500\n' > job
./job &
sleep 1
```

:::hint
`/proc/PID/exe` は、そのプロセスが実行しているプログラムへのシンボリックリンクです。`readlink` で、指す先を表示できます。スクリプトの場合、指す先はスクリプトではなく、`#!` に書かれたインタプリタです。
:::
:::

:::quiz どちらの greet が動くのか
`greet` という名前のコマンドが、いくつかのディレクトリに置いてあります。いまのシェルで `greet` と打ったときに**実際に実行されるファイル**のパスを、1 行で表示してください。

```sh prep
mkdir -p bin tools
printf '#!/bin/sh\necho "home"\n' > bin/greet
printf '#!/bin/sh\necho "tools"\n' > tools/greet
chmod +x bin/greet tools/greet
printf '#!/bin/sh\necho "local"\n' | sudo tee /usr/local/bin/greet > /dev/null
sudo chmod +x /usr/local/bin/greet
PATH=$HOME/tools:$PATH:$HOME/bin
```

```sh answer
which greet
```

```sh vary
rm tools/greet
```

```sh vary
chmod -x tools/greet
sudo rm /usr/local/bin/greet
```

:::hint
シェルは、PATH のディレクトリを左から順に探して、最初に見つかった「実行できるファイル」を使います。`which 名前` は、同じ探し方をして、見つかったパスを表示します。
:::
:::

:::quiz 余分な sh を残さない
`/home/you/svc` は、あいさつを表示してから `sleep 1000` を起動するスクリプトです。いまは、起動すると `sh` と `sleep` の 2 つのプロセスになります。スクリプトを書き直して、**`sh` が `sleep` に入れ替わる**ようにしてください（あいさつの行は残します）。

```sh prep
printf '#!/bin/sh\necho "svc starting"\nsleep 1000\n' > svc
chmod +x svc
```

```sh starter
printf '#!/bin/sh\necho "svc starting"\nsleep 1000\n' > svc
```

```sh answer
printf '#!/bin/sh\necho "svc starting"\nexec sleep 1000\n' > svc
```

```sh check
cd /home/you
./svc &
sleep 1
readlink /proc/$!/exe
kill $!
```

:::hint
最後の行を `exec sleep 1000` にします。`exec` は、fork せずに、シェル自身をそのコマンドに入れ替えます。
:::
:::
