## 調子の悪いサーバを渡された {#first}

この章の Linux は、いつもと違います。ページを開いた時点で、いくつかの問題を抱えています（章の準備で仕込んであります）。あなたは、このサーバを引き継いだ管理者です。「なんだか遅い」「昨夜のバッチが終わっていない」「Web ページが開かない」と言われています。

```sh setup root
# CPU を使い続けるプロセス
cp /usr/bin/spin /usr/local/bin/imgconv
su alice -c 'imgconv &'
# メモリを使い切って殺されるサービス
cat > /etc/systemd/system/batch.service <<'EOF'
[Unit]
Description=Nightly batch job

[Service]
ExecStart=/usr/bin/memhog 4M
EOF
systemctl daemon-reload
systemctl start batch
sleep 5
# メモリを抱えたままのプロセス
cp /usr/bin/memtouch /usr/local/bin/cached
sh -c 'cached 24M 100000 > /dev/null &'
# 来ない入力を待ち続けるプロセス
mkfifo /run/queue
cp /usr/bin/cat /usr/local/bin/worker
sh -c 'worker /run/queue > /dev/null &'
# SIGTERM を無視するプロセス
cat > /usr/local/bin/stuckd <<'EOF'
#!/bin/sh
trap '' TERM
while :; do sleep 1000; done
EOF
chmod +x /usr/local/bin/stuckd
sh -c 'stuckd &'
# ディスクを埋めるファイルと、消されたのに開かれたままのファイル
mkdir -p /var/log/app /var/cache/app
dd if=/dev/zero of=/var/log/app/debug.log bs=1M count=30 status=none
dd if=/dev/zero of=/var/log/app/app.log.1 bs=1M count=20 status=none
dd if=/dev/zero of=/var/cache/app/thumbs.db bs=1M count=6 status=none
cp /usr/bin/sleep /usr/local/bin/applogd
sh -c 'applogd 100000 >> /var/log/app/app.log.1 &'
sleep 0.1
rm /var/log/app/app.log.1
sync
sleep 60
```

何から始めればよいでしょう。**いきなり原因を当てようとしないこと**です。まず、機械全体を 3 つのコマンドで眺めます。CPU、メモリ、ディスクです。

```sh run title="最初に打つ 3 つ"
uptime
free -m
df -h
```

これだけで、気になる点が 3 つ見つかります。

- `uptime` の **load average**（負荷平均。第 14 章）が 1 前後ある。CPU が 1 つのこの機械で、いつも 1 つのプロセスが CPU を使いたがっている
- `free` の `used` が 24 MiB。58 MiB のうち 4 割を、だれかが使っている
- `df` の `/` が **96%**。ディスクが一杯になりかけている

調査は、こうして「全体 → あやしい資源 → あやしいプロセス → そのプロセスの中」と、範囲を狭めていきます。

プロセスの一覧も見ておきます。

```sh run title="だれが動いているか"
ps aux
```

`init` と、ログインシェル 2 つのほかに、見慣れないプロセスが並んでいます。`imgconv`、`cached`、`worker`、`stuckd`、`applogd`。この章で、順に調べます。`%CPU`、`RSS`、`STAT` の列が、手がかりです。

## /proc を読む：道具の元 {#proc}

`ps` も `top` も `free` も `lsof` も、自分では何も知りません。**全部、`/proc` を読んで、形を整えているだけ**です（第 7 章、第 12 章）。道具が手元になくても、`cat` さえあれば、同じことが調べられます。`imgconv` を例に、プロセスごとのディレクトリを読みます。

```sh run title="/proc/PID の中身"
P=$(pgrep imgconv)
echo $P
ls /proc/$P
```

よく使うものを、表にまとめます。

| ファイル | 中身 | 出てきた章 |
| --- | --- | --- |
| `status` | 名前、状態、親、uid、メモリの量、シグナルの扱い | 7、8、13 |
| `cmdline`、`exe`、`cwd` | 起動したときの引数、実行ファイル、カレントディレクトリ | 7、12 |
| `fd/` | 開いているファイル（fd → 行き先） | 9 |
| `maps` | アドレス空間の地図 | 13 |
| `sched` | スケジューラの記録（使った CPU 時間、切り替えの回数） | 14 |
| `cgroup`、`ns/` | 属している cgroup と名前空間 | 19 |

```sh run title="status：プロセスの身上書"
grep -E '^(Name|State|PPid|Uid|VmRSS)' /proc/$P/status
readlink /proc/$P/exe /proc/$P/cwd
```

`State` は `R (running)`。持ち主は uid 1001（alice）で、親は PID 1 です。起動したシェルはもう終わっていて、init に引き取られています（第 7 章の孤児）。実行ファイルは `/usr/local/bin/imgconv` だとわかりました。

```sh run title="sched：どれだけ CPU を使ったか"
head -4 /proc/$P/sched
grep sum_exec /proc/$P/sched; sleep 2; grep sum_exec /proc/$P/sched
```

`se.sum_exec_runtime` が、これまでに使った CPU 時間（ミリ秒）です。2 秒待つと、およそ 2000 増えています。**2 秒のうち、ほぼ 2 秒ぶん CPU を使った**、つまり休みなく走り続けています。

```sh run error title="fd と maps は、持ち主か root にしか見せない"
ls /proc/$P/fd
sudo ls -l /proc/$P/fd
sudo head -3 /proc/$P/maps
```

ほかのユーザーのプロセスの `fd` は、`Permission denied` です。開いているファイルは、のぞかれたくない情報だからです。調査では、`sudo` をつけて root として読むことが多くなります。`imgconv` が開いているのは `/dev/null` と端末だけで、ファイルもソケットも使っていません。入出力をせずに、ただ計算しています。

## 「サーバが遅い」：CPU を使っているのはだれか {#slow}

`/proc` を 1 つずつ読む代わりに、全員ぶんをまとめて並べてくれるのが `top` です。

```sh run title="top：CPU を使っている順"
top -b -n 1 | head -12
```

上の 5 行が、機械全体のようすです。

- 1 行目は `uptime` と同じ。**load average** は、1 分・5 分・15 分の平均で、「CPU を使っている、または使いたくて待っているプロセスの数」
- 3 行目の `%Cpu(s)` は、CPU 時間の内訳。`us`（ユーザーモード）がほぼ 100、`id`（何もしていない）が 0。**CPU は休みなく働いている**。`wa` は、ディスクなどの I/O 待ち

その下が、プロセスごとの行です。`top` 自身を除くと、`imgconv` が 1 つで CPU をほぼ全部使っています。

:::note load average の読み方
load average は、CPU の数と比べて読みます。CPU が 1 つなら 1.00 で「ちょうど一杯」、4 つなら 4.00 で一杯です。CPU の数は `nproc` でわかります。Linux の load average は、ディスク待ち（状態 `D`）のプロセスも数えます。だから、「load は高いのに `%Cpu` の `id` が大きい」ときは、CPU ではなく、ディスクが詰まっています（そのときは `wa` が大きくなります）。
:::

だれが、いつ起動したのかを確かめます。

```sh run title="そのプロセスについて、もう少し"
ps -o pid,ppid,user,lstart,etime,time,comm -p $P
```

`ELAPSED`（起動してからの時間）と `TIME`（使った CPU 時間）が、ほぼ同じです。起動してからずっと、CPU を使い続けています。alice に聞くと、「画像の変換を試して、止め忘れた」とのことでした。止めます。

```sh run title="止めて、確かめる"
sudo kill $P
sleep 30
pgrep imgconv | wc -l
uptime
```

`imgconv` はいなくなり（0 個）、load average の 1 分の値が下がりはじめました。load average は平均なので、原因がなくなっても、すぐには 0 に戻りません。

:::tip 止める前に、弱める
本当に必要な仕事なら、止めずに `renice`（第 14 章）で優先度を下げる手があります。`sudo renice -n 19 -p PID` とすれば、ほかのプロセスが CPU を使いたいときには、そちらが優先されます。
:::

## 動かないプロセス：何を待っているのか {#stuck}

CPU を使いすぎるのとは逆に、「何もしていないように見える」プロセスもあります。`worker` は、仕事を処理するはずのプロセスですが、起動してから 1 件も処理していないそうです。

まず、状態を見ます。第 7 章の `STAT` の 1 文字目です。

| 状態 | 意味 | 調べること |
| --- | --- | --- |
| `R` | 走っている、または CPU を待っている | CPU を使いすぎていないか（前の節） |
| `S` | 何かを待って眠っている（シグナルで起こせる） | **何を待っているか** |
| `D` | ディスクなどの I/O を待っている（シグナルでも起こせない） | ディスクが遅くないか |
| `T` | 止められている（`SIGSTOP`、Ctrl-Z） | だれが止めたか。`SIGCONT` で再開 |
| `Z` | ゾンビ。もう終わっている | 親が `wait` していない（第 7 章） |

```sh run title="状態と、待っているシステムコール"
ps -eo pid,stat,wchan,comm
```

ほとんどのプロセスは `S` です。**眠っていること自体は、異常ではありません**。サーバのプロセスは、仕事が来るまで眠っているのがふつうです。大事なのは、**何を待って眠っているか**です。`WCHAN` の列が、それを教えてくれます。

- `init` は `poll`（どれかの fd に何か来るのを待つ）、シェルは `wait4`（子が終わるのを待つ）
- `cached`、`sleep`、`applogd` は `nanosleep`（時間がたつのを待つ）
- **`worker` は `read`**。何かを読もうとして、データが来るのを待っている

何を読もうとしているのかは、fd を見ればわかります。

```sh run title="worker は、何を読もうとしているか"
sudo ls -l /proc/$(pgrep worker)/fd
ls -l /run/queue
```

fd 3 が `/run/queue` です。`ls -l` の先頭が `p` なので、名前つきパイプ（FIFO。第 9 章）です。`worker` は、このパイプに仕事が書き込まれるのを待っています。**止まっているのではなく、仕事が来ていない**のです。原因は `worker` ではなく、仕事を送る側にあります。試しに、1 件書いてみます。

```sh run title="待っていたものを、与える"
sudo sh -c 'echo job1 > /run/queue'
sleep 0.1
pgrep worker | wc -l
```

`worker` は 1 件読んで、仕事を終えて終了しました（0 個）。

### 本物では：strace -p

本物の Linux では、`ps` の `WCHAN` には、システムコールの名前ではなく、カーネルの中の関数の名前（`pipe_read`、`do_wait`、`hrtimer_nanosleep` など）が出ます。待っているシステムコールを知るには、**動いているプロセスに `strace` をつなぐ** `strace -p PID` を使います。

```console
# strace -p 12              ← パイプを読んでいる cat
strace: Process 12 attached
read(0,                     ← ここで止まっている。fd 0 からの read が、まだ返ってきていない

# strace -p 1               ← 子を待っているシェル
wait4(-1,

# strace -p 27              ← 接続を待っているサーバ
accept4(3,
```

行が途中で切れているのは、システムコールが**まだ終わっていない**からです。`read(0,` なら fd 0 にデータが来るのを、`wait4(-1,` なら子が終わるのを、`accept4(3,` なら fd 3 のソケットに接続が来るのを待っています。fd の行き先は `/proc/PID/fd` で調べます。この小さな Linux の `strace` は、コマンドを起動して追うことしかできないので、代わりに `WCHAN` に名前を出しています。

### 状態 D：ディスクを待っている

`D` は、ふだんは一瞬しか見えません。ディスクに直接書き込むコマンドを動かして、その最中を見ます。

```sh run title="ディスクへの書き込みを待つプロセス"
dd if=/dev/zero of=test.bin bs=1M count=2 oflag=sync status=none & sleep 0.3; ps -o pid,stat,wchan,comm; wait
rm test.bin
```

`dd` が `D` です。`oflag=sync` は、「ディスクに書き終わるまで `write` から戻らない」という指定で（第 15 章）、`dd` はディスクの仕事が終わるのを待っています。`D` のプロセスは、`SIGKILL` でも、その待ちが終わるまで死にません。本物のサーバで `D` のプロセスがたまっていたら、ディスクが壊れかけているか、ネットワーク越しのファイルシステム（NFS）の相手が応答していないことを疑います。

### 終わらせる順番：TERM、だめなら KILL

`stuckd` は、もう使っていない古いデーモンだそうです。止めます。

```sh run title="kill しても、終わらない"
sudo pkill stuckd
sleep 0.2
pgrep -l stuckd
grep SigIgn /proc/$(pgrep stuckd)/status
```

`pkill`（名前で `kill` するコマンド）は、`kill` と同じく `SIGTERM` を送ります。けれども、`stuckd` はまだいます。`status` の `SigIgn` が、理由を教えてくれます。これは「無視しているシグナル」を 16 進数のビットで表したもので、`4000` は 15 番目のビット、つまりシグナル 15（`SIGTERM`）です。このプロセスは、`SIGTERM` を無視しています（第 8 章の `trap ''`）。

```sh run title="最後の手段：SIGKILL"
sudo pkill -KILL stuckd
sleep 0.1
pgrep stuckd | wc -l
ps -eo pid,ppid,stat,comm | grep sleep
sudo pkill -x sleep
```

`SIGKILL` は無視できないので、今度は消えました（0 個）。ただし、`stuckd` が起動していた `sleep` が、親を失って init（PPID 1）の子として残っています。`SIGKILL` されたプロセスは、子を片づける暇がないからです。これも止めました。

:::warn いきなり kill -9 しない
`SIGTERM` は「終わってください」というお願いで、受け取ったプログラムは、書きかけのファイルを閉じ、一時ファイルを消し、子を止めてから終われます。`SIGKILL` は、その機会を与えません。データベースなら、次の起動で修復が走ることになります。**まず `SIGTERM`、数秒待って、だめなら `SIGKILL`**。systemd がサービスを止めるときも、この順番です（第 17 章）。
:::

## 「ディスクが一杯」：何が場所を使っているか {#disk}

最初の `df` で、`/` が 96% でした。放っておくと、ログも書けなくなり、いろいろなプログラムが `No space left on device`（第 11 章）で失敗しはじめます。

`df` は「ファイルシステムごとの空き」、`du` は「ディレクトリごとの使用量」です。**`df` で、どのファイルシステムかを決め、`du` で、木を上から下へたどります**。

```sh run title="du で、大きいディレクトリをたどる"
sudo du -sh /* 2>/dev/null | sort -rh | head -4
sudo du -sh /var/* | sort -rh | head -3
sudo du -ah /var/log | sort -rh | head -4
```

`du -sh /*` は、`/` の直下のディレクトリごとの合計です（`-s` は合計だけ、`-h` は読みやすい単位）。`sort -rh` は、`31M` や `4.0K` のような単位つきの数を、大きい順に並べます。`/var` → `/var/log` → `/var/log/app` とたどって、30 MiB の `debug.log` に行き着きました。デバッグ用のログを、出しっぱなしにしていたようです。

ここで `rm` したくなりますが、少し待ってください。このファイルを、だれかが開いて書き込み続けているかもしれません。その場合、`rm` しても空きは増えません（第 11 章）。ログファイルは、**消さずに、中身だけ空にする**のが安全です。

```sh run title="消さずに、空にする"
sudo sh -c ': > /var/log/app/debug.log'
ls -l /var/log/app
df -h /
```

`: > ファイル` は、何も出力しないコマンド `:` の出力をリダイレクトして、ファイルを長さ 0 に切り詰めます（`O_TRUNC`。第 9 章）。inode はそのままなので、開いているプログラムがいても、そのまま書き続けられます。`/` は 49% まで下がりました。

### df と du が合わない

まだ、おかしな点があります。`df` は 31 MiB 使っていると言っています。`du` で `/` 全体を合計してみます。

```sh run title="du の合計と、df の Used を比べる"
sudo du -sh / 2>/dev/null | tail -1
df -h /
```

`du` の合計は 11 MiB ほどしかありません。**20 MiB が、どのディレクトリにも見つかりません**。

`du` は、ディレクトリの木をたどって、名前のついたファイルを数えます。`df` は、ファイルシステムが使っているブロックを数えます。この 2 つがずれるのは、**名前がないのに、ブロックを使っているファイル**があるときです。第 11 章で見た、「消されたけれど、まだ開かれているファイル」です。`lsof` で探します。

```sh run title="消されたのに、開かれたままのファイル"
sudo lsof | grep deleted
```

`applogd`（PID は 2 列目）が、fd 1 で `/var/log/app/app.log.1` を開いています。大きさは 20971520 バイト（20 MiB）。末尾の `(deleted)` が、名前はもう消されている印です。だれかが古いログを `rm` したのに、`applogd` が開いたままなので、inode もブロックも解放されていません。

```fig fdtable 消されたファイル。ディレクトリの表からは名前が消え、リンク数は 0。それでもファイル記述が inode を指しているあいだ、ブロックは解放されない。du には見えず、df には数えられる
{
  procs: [ { label: 'applogd', fds: [ { fd: 0, to: 'null' }, { fd: 1, to: 'log', hl: true }, { fd: 2, to: 'tty' } ] } ],
  files: [
    { id: 'null', flags: 'O_RDONLY', pos: 0, to: 'n' },
    { id: 'log', flags: 'O_WRONLY|O_APPEND', pos: 20971520, to: 'f', hl: true },
    { id: 'tty', flags: 'O_RDWR', pos: 0, to: 't' },
  ],
  inodes: [
    { id: 'n', label: '/dev/null' },
    { id: 'f', label: 'app.log.1 (deleted)', sub: 'リンク数 0・20 MiB', hl: true },
    { id: 't', label: '/dev/pts/1', sub: '端末' },
  ],
}
```

空きを取り戻すには、開いているプロセスに、ファイルを閉じさせます。いちばん確実なのは、そのプロセスを終わらせる（サービスなら再起動する）ことです。

```sh run title="開いているプロセスを終わらせると、空きが戻る"
sudo pkill applogd
sleep 0.1
sudo lsof | grep deleted | wc -l
df -h /
```

`/` は 17% になりました。`du` の合計と、合うようになっています。

:::tip 消す前に、中身だけ空にする手もある
終わらせられないプロセスが開いている場合は、`/proc/PID/fd/番号` を通して、消されたファイルを切り詰められます（`: > /proc/PID/fd/1`）。`/proc/PID/fd` の中のリンクは、名前が消えていても、inode に直接つながっているからです。
:::

## 「メモリが足りない」：free と OOM {#memory}

昨夜のバッチ（`batch.service`）が終わっていない、という話がありました。まず、サービスの状態を見ます（第 17 章）。

```sh run title="バッチは、どうなったか"
systemctl status batch | head -5
```

`failed`、そして `code=killed, signal=KILL`。自分で終わったのではなく、**だれかに `SIGKILL` で殺されています**。`kill -9` を打った人がいないなら、犯人はカーネルの **OOM killer**（第 13 章）です。カーネルは、殺したことを必ずログに残します。

```sh run title="カーネルのログで、OOM を探す"
dmesg | grep -i -E 'oom|out of memory' | cut -c1-110
```

`memhog invoked oom-killer` は、「`memhog` がメモリを要求したときに、足りなくなった」。`Out of memory: Killed process … (memhog)` が、殺された相手です。`anon-rss` は、そのとき使っていたメモリで、59200 kB。58 MiB しかない機械のメモリを、1 つのプロセスがほぼ全部使っていました。バッチが、メモリを使い切って殺されたのです。

「あるはずのプロセスが、いつの間にか消えている」ときは、まず `dmesg` で `Out of memory` を探します。

今のメモリも見ます。

```sh run title="今のメモリ"
free -m
ps -eo rss,vsz,pid,comm | sort -rn | head -3
```

`free` の列の読み方は、第 13 章と第 15 章のとおりです。

- **`free` が小さいことは、問題ではない**。章の最初に見たとき、`free` は 0 でした。空いているメモリを、カーネルがページキャッシュ（`buff/cache`）に使っていただけで、必要になれば、すぐに明け渡される。大きなログを空にした今は、そのぶんのキャッシュが捨てられて、`free` が増えている
- 見るのは **`available`**。「新しいプログラムが、あとどれだけ使えるか」の見積もり

`ps` を `RSS`（実際に使っている物理メモリ。kB）の大きい順に並べると、`cached` が 24 MiB を抱えています。OOM killer は、足りなくなったとき、原則としてメモリをいちばん使っているプロセスを選びます。次に危ないのは、このプロセスです。その「選ばれやすさ」は、`/proc/PID/oom_score` に出ています。

```sh run title="OOM killer に選ばれやすさ"
cat /proc/$(pgrep cached)/oom_score
cat /proc/$$/oom_score
```

数字が大きいほど、先に選ばれます。メモリの 4 割を使う `cached` は 400 台、シェルはほぼ 0 です。

:::note バッチを直すには
調査でわかるのは、「メモリを使い切って殺された」までです。直し方は、プログラムの使うメモリを減らす、機械のメモリを増やす、の 2 つです。ほかのサービスを巻き込まないためには、第 19 章の cgroups で上限をつける手もあります（systemd の unit に `MemoryMax=` と書くと、そのサービスの cgroup の `memory.max` になります）。
:::

## ログと、「Web サーバにつながらない」 {#logs}

最後の苦情です。「Web ページが開かない」。まず、自分で再現します。

```sh run error title="再現する"
curl -s -S localhost/hello.txt
```

`Could not connect`、終了ステータスは 7。相手に接続できていません。HTTP の応答（404 や 500）が返ってきたのではなく、その手前の、TCP の接続（第 16 章）で失敗しています。ポート 80 で、だれかが待ち受けているでしょうか。

```sh run error title="待ち受けているソケットと、サービスの状態"
ss -tln
systemctl status httpd
```

`ss -tln`（TCP の、待ち受け中のソケットを、番号のまま表示）は、見出しだけです。**だれも待ち受けていません**。`systemctl status` は `inactive (dead)`。Web サーバが、動いていないのです。`Loaded:` の行に `disabled` とあります。自動起動が設定されておらず、昨夜の再起動のあと、だれも起動していなかったようです。

```sh run title="起動して、確かめる"
sudo systemctl start httpd
sleep 0.1
sudo ss -tlnp
curl -s localhost/hello.txt
sudo systemctl enable httpd 2>&1
```

`ss -tlnp` の `-p` は、そのソケットを持っているプロセスも表示します。`httpd` が、ポート 80 で `LISTEN` しています。`curl` も成功しました。`enable` で、次の再起動からは自動で起動します。

:::note 接続の失敗の見分け方
- **すぐに断られる**（Connection refused）… 相手の機械には届いたが、そのポートで待ち受けているプロセスがいない。サーバが落ちているか、ポート番号が違う
- **長く待ってから失敗する**（タイムアウト）… パケットが届いていないか、捨てられている。番地の間違い、途中のファイアウォール
- **つながるが、エラーの応答が返る**（404、500）… ネットワークは正常。サーバの中の問題なので、サーバのログを見る
:::

### ログ：何が起きたかを、あとから知る

ここまでの調査で、`dmesg` と `systemctl status` が決め手になりました。どちらも、**起きたことの記録**、つまりログです。Linux のログは、主に 3 か所にあります。

| 場所 | 中身 | 読み方 |
| --- | --- | --- |
| カーネルのログ | 装置、OOM、cgroup など、カーネルが出したもの | `dmesg` |
| ジャーナル | systemd が集めたもの。サービスの標準出力と、カーネルのログも入る | `journalctl` |
| `/var/log` の下のファイル | 昔からの形。プログラムが自分で書くテキストファイル | `tail`、`grep`、`less` |

ジャーナルは、サービスごとに絞って読めます。

```sh run title="サービスのログ"
sudo journalctl -u httpd --no-pager
sudo journalctl -p err --no-pager | cut -c1-90
```

`-u httpd` は、そのサービスの記録だけ。起動したことと、さっきの `curl` のアクセスが残っています。`-p err` は、重要度が「エラー」以上のものだけです。OOM の記録が出てきました。何が起きたかわからないときは、`journalctl -p err` で、エラーだけを眺めるのが早道です。

`/var/log` のファイルは、第 5 章の道具がそのまま使えます。

```sh run title="/var/log を、テキストの道具で読む"
ls -l /var/log
grep -c ' 404 ' /var/log/access.log
cut -d' ' -f1 /var/log/access.log | sort | uniq -c | sort -rn | head -3
```

404（見つからない）の応答は 2 件。アクセスの多い番地の上位 3 つも、`cut`、`sort`、`uniq -c` の組み合わせで出せます。`syslog` と `auth.log` は、持ち主と特定のグループにしか読めません（ログインの記録などが入っているからです）。

:::tip ログを読むときの 3 つのこつ
- **時刻を合わせる**。「遅くなったのは 9 時ごろ」とわかっていれば、その前後だけを読む（`journalctl --since`、`grep '09:0'`）
- **最初のエラーを探す**。エラーは連鎖する。最後の行ではなく、いちばん最初におかしくなった行が原因に近い
- **流しながら再現する**。本物の Linux では `tail -f ファイル` や `journalctl -f` でログを流しておいて、別の端末で問題を再現すると、その瞬間の行がわかる
:::

## 調べ方の型 {#method}

この章でしたことを、ふり返ります。5 つの問題は、どれも同じ進め方で解けました。

1. **症状を、自分で再現する**（`curl` してみる。`df` を見る）。人から聞いた話は、あいまいなことが多い
2. **全体から始めて、狭める**。機械全体 → 資源 → プロセス → そのプロセスの fd やシステムコール
3. **推測する前に、見る**。Linux は、ほとんどのことを `/proc`、ログ、`strace` で見せてくれる
4. **1 つ直したら、確かめる**。直したつもりで終わらない。同じコマンドをもう一度打つ

| 症状 | まず見る | 次に見る | よくある原因 |
| --- | --- | --- | --- |
| 遅い | `uptime`、`top` | `ps -o pid,pcpu,etime,time,comm`、`/proc/PID/sched` | 止め忘れたプロセス、無限ループ。`wa` が高ければディスク |
| 動かない、応答しない | `ps -o stat,wchan` | `/proc/PID/fd`、`strace -p` | 来ない入力を待っている。相手が落ちている。`T` で止められている |
| 終わらない | `kill`（TERM） | `SigIgn`、だめなら `kill -KILL` | シグナルを無視している。`D` や `Z` は kill では消えない |
| ディスクが一杯 | `df -h`、`df -i` | `du -sh ディレクトリ/*`、`lsof \| grep deleted` | ログの出しすぎ。消したのに開かれたままのファイル。inode の使い切り |
| プロセスが消えた、メモリ不足 | `free`、`dmesg` | `ps -o rss`、`journalctl -k` | OOM killer。`free` ではなく `available` を見る |
| つながらない | `curl`、`ss -tlnp` | `systemctl status`、`journalctl -u` | サーバが動いていない。ポートが違う。自動起動していない |

この表の右の列は、ここまでの章で学んだ仕組みそのものです。load average はスケジューラ（第 14 章）、`wchan` はシステムコール（第 10 章）、消したのに減らないディスクは inode とファイル記述（第 9 章、第 11 章）、OOM は仮想メモリ（第 13 章）、Connection refused はソケット（第 16 章）。**仕組みを知っていれば、道具の出力が読めます**。道具の使い方を暗記するよりも、そのほうがずっと遠くまで行けます。

:::warn 本物との違い
- 本物の `strace -p PID` は、動いているプロセスにつないで、いま待っているシステムコールを見せます。この小さな Linux の `strace` は、コマンドを起動して追うことしかできません。代わりに、`ps` の `WCHAN` にシステムコールの名前を出しています（本物の `WCHAN` は、カーネルの中の関数名か `-` です）
- 本物の `top` は、画面を数秒ごとに書き換えながら動き続けます（`q` で終了）。ここでは 1 回表示して終わります。`ps` の `--sort`、`du` の `-x`（ほかのファイルシステムに入らない）は使えません
- 本物の `lsof` は、ソケットや、メモリに写したファイルの行も出します。本物には、ほかにも `vmstat`、`iostat`、`pidstat`、`perf`、`tcpdump`、`ltrace`、`gdb` など、たくさんの道具があります
- 本物の `/proc/PID` には、`io`（読み書きした量）、`limits`（資源の上限）、`stack`、`smaps` など、もっと多くのファイルがあります
- OOM で殺されたサービスを、本物の systemd は `Result: oom-kill` と表示します
:::

:::key この章のまとめ
- 調査は、**全体 → 資源 → プロセス → プロセスの中**の順に狭める。最初に `uptime`、`free`、`df`、`ps`
- `ps`、`top`、`free`、`lsof` は、どれも **`/proc`** を読んでいる。`/proc/PID/status`（状態、メモリ、シグナル）、`fd/`（開いているファイル）、`maps`、`sched`
- **遅い**ときは、load average と `top` で、CPU を使っているプロセスを探す
- **動かない**ときは、状態（`S` は待ち、`D` はディスク待ち）と、**何を待っているか**（`wchan`、本物では `strace -p`）を見る。眠っていること自体は、異常ではない
- 終わらせるときは、**`SIGTERM`、だめなら `SIGKILL`**
- **ディスクが一杯**のときは、`df` でファイルシステムを決め、`du` でたどる。`df` と `du` が合わなければ、`lsof | grep deleted`
- **プロセスが消えた**ときは、`dmesg` で `Out of memory` を探す。`free` は `available` を見る
- **つながらない**ときは、`curl` で再現し、`ss -tlnp` で待ち受けを確かめ、`systemctl status` と `journalctl -u` を読む
- 道具の出力は、仕組みを知っていれば読める
:::

これで、この本は終わりです。シェルにコマンドを打つところから始めて、プロセス、ファイルディスクリプタ、システムコール、ファイルシステム、仮想メモリ、スケジューラ、ネットワーク、コンテナまで降りてきました。次に本物の Linux で何かがうまくいかなくなったとき、この章の表から始めてみてください。

## 確認問題 {#quiz}

原因を突き止めて、答えを出す問題です。どの問題も、この章の最初と同じ「調子の悪いサーバ」から始まります（本文で直したものも、元に戻っています）。root の仕事は、`sudo コマンド` で実行できます。

:::quiz 何を待っているのか
あるプロセスが、動いていないように見えます。その PID は、ファイル `/tmp/job.pid` に書いてあります。このプロセスが**待っているシステムコールの名前**だけを表示してください。

```sh prep
nc -l 7000 > /dev/null &
echo $! > /tmp/job.pid
sleep 0.2
```

```sh answer
ps -o wchan= -p $(cat /tmp/job.pid)
```

```sh vary
kill $(cat /tmp/job.pid)
sleep 5000 &
echo $! > /tmp/job.pid
sleep 0.2
```

```sh vary
kill $(cat /tmp/job.pid)
mkfifo /tmp/in
cat /tmp/in > /dev/null &
echo $! > /tmp/job.pid
sleep 0.2
```

:::hint
`ps -o wchan -p PID` で、そのプロセスが待っているシステムコールが出ます。列の名前のあとに `=` をつけて `wchan=` とすると、見出しの行が出ません。PID は `$(cat /tmp/job.pid)` で取り出せます。
:::
:::

:::quiz いちばん大きいファイルを探す
`/var` の下のどこかに、ディスクを埋めている大きなファイルがあります。`/var` の下で**いちばん大きいファイルのパス**だけを表示してください。

```sh answer
sudo find /var -type f | sudo xargs du | sort -rn | head -1 | cut -f2
```

```sh vary
sudo rm /var/log/app/debug.log
```

```sh vary
sudo rm /var/log/app/debug.log /var/cache/app/thumbs.db
sudo mkdir -p /var/lib/db/tmp
sudo dd if=/dev/zero of=/var/lib/db/tmp/sort.tmp bs=1M count=3 status=none
```

:::hint
`find /var -type f` でファイルだけを並べ、`xargs du` で 1 つずつの大きさ（タブ区切りで「大きさ　パス」）を出します。`sort -rn | head -1` でいちばん大きい行を選び、`cut -f2` でパスだけにします。`du -a /var` を使う方法もありますが、ディレクトリの行も混ざるので、除く工夫が要ります。
:::
:::

:::quiz 消されたファイルを開いているのはだれか
`df` と `du` の数字が合いません。どこかのプロセスが、消されたファイルを開いたままにしています。その**プロセスの PID** だけを表示してください。

```sh answer
sudo lsof | grep deleted | tr -s ' ' | cut -d' ' -f2
```

```sh vary
sudo pkill applogd
dd if=/dev/zero of=/tmp/work.dat bs=1M count=1 status=none
sleep 3000 < /tmp/work.dat &
rm /tmp/work.dat
sleep 0.2
```

:::hint
`sudo lsof` の出力で、行の最後に `(deleted)` とあるものが、消されたのに開かれているファイルです。2 列目が PID です。空白を `tr -s ' '` で 1 つにまとめてから、`cut -d' ' -f2` で取り出します。`awk '{print $2}'` でもかまいません。
:::
:::

:::quiz 終わらないプロセスを終わらせる
`stuckd` という古いデーモンが動いています。`sudo pkill stuckd` では終わりません。`stuckd` を終わらせてください。

```sh answer
sudo pkill -KILL stuckd
sleep 0.1
```

```sh check
pgrep -x stuckd | wc -l
```

:::hint
`stuckd` は `SIGTERM` を無視しています（`/proc/PID/status` の `SigIgn`）。無視できないシグナル `SIGKILL` を送ります。`pkill -KILL 名前`、または `kill -9 PID` です。
:::
:::
