# 実行環境の作り方

本文のコードをその場で動かす仕組み。手本は `postgresql/src/assets/`（`sql.js`、`dbview.js`、`quiz.js`、`sqlhl.js`）と `build.mjs`。

## 前提（どの題材でも守る）

- **サーバなしで動かす。** `site/index.html` を file:// で開いて動くこと。ES モジュールの import ではなく、クラシックスクリプトと動的 `import()` で読み込む。
- **WebAssembly などの本物を CDN から読む。** バージョンは固定する（例：`@electric-sql/pglite@0.5.12`）。初回の実行時に読み込み、入力欄にフォーカスした時点で先読み（warm）する。
- **ページごとに独立した環境にする。** 章の準備（`setup`）は最初の実行時に自動で流す。上部の「リセット」で初期状態に戻せるようにする。
- **実行は 1 つずつ順番に行う**（`serial`）。本文の実行、状態ビュー、採点の問い合わせが混ざらないようにする。
- 暴走対策として、タイムアウト（`statement_timeout` など）と表示行数の上限を設ける。
- エラーは本物のメッセージ・コード・位置をそのまま見せる。

## 段階（どこまで作るか）

| 段階 | 内容 | postgresql での実装 |
| --- | --- | --- |
| 0 | 読むだけ。図とハイライトのみ | rust サイト |
| 1 | 本文のブロックを実行・編集できる。⌘↵ で実行、元に戻す、コピー。前のブロックを飛ばしたときは「前を順に実行」を出す | `sql.js`、` ```sql run ` |
| 2 | 状態ビュー。いまの中身を表で見せ、直前の実行が変えた所に色を付ける | `dbview.js`（「DB を見る」） |
| 3 | 確認問題の自動採点。別インスタンスで実行し、毎回取り消して出力を比べる | `quiz.js`、`:::quiz` |
| 4 | 実験場。データセットを選んで自由に試すページ。履歴を残す | `playground.html` |

「実行環境を作って」と頼まれたら、1〜4 をすべて作るのが既定。題材の都合で省くものがあれば、先にそう伝える。

## 題材ごとの候補

まず実際に動かして、制約を確かめる。確かめた制約は README の末尾に書く。

| 題材 | 候補 | 取り消し（採点の独立性）の方法 |
| --- | --- | --- |
| PostgreSQL | PGlite | トランザクション + ROLLBACK |
| SQLite | sql.js / wa-sqlite | トランザクション、またはメモリ上の DB を作り直す |
| 分析 SQL | DuckDB-Wasm | トランザクション、またはインスタンスを作り直す |
| Python | Pyodide | 採点ごとに新しい名前空間（globals）で実行する |
| JavaScript | Web Worker + `new Function` | 採点ごとに Worker を作り直す |
| Rust / Go などのコンパイル言語 | ブラウザ内で完結する手段が乏しい | 段階 0（図中心）にして、ユーザーに相談する |

## 採点の考え方（段階 3）

- 比べるのは「出力の値」。列名・行の順番・列の順番・数値の書き方は問わず、順番を指定した問題だけ順番も見る。
- 状態を変える問題は、実行後の状態を調べるクエリ（`check`）の結果を比べる。
- 読者の答えが採点の仕組みを壊せないようにする。PostgreSQL では `begin` / `commit` を書いた答えは判定せずに返した。
- 検査は Node 上で同じ採点コア（`QZCORE`）を読み込んで回す（`scripts/verify-quiz.mjs`）。そのため、採点の中心部分は DOM に依存させない。
