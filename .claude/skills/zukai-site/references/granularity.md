# 粒度の目安

「図解 ○○ を作って」と頼まれたときに、どこまで・どの細かさで書くかの基準。数字は既存 2 サイトの実測（2026-11 時点）。迷ったらこの範囲に合わせ、外れるときは理由を章立ての提案に書く。

## サイト全体：本 1 冊ぶん

- **序章 + 本編 20 章前後 + 付録**。合計で 20〜30 時間ほどで読み切れる分量にする。
- 入門だけで終わらせない。本編の流れは次のとおり。
  1. 歴史・背景
  2. 基本
  3. 応用
  4. 内部の仕組み
  5. 運用・実務
- PostgreSQL の例：
  - 歴史
  - SQL（SELECT、型、制約、変更、JOIN、集約、サブクエリ、ウィンドウ関数）
  - 設計
  - 内部（8 KB のページとタプル、MVCC、インデックス、EXPLAIN、WAL、ロック）
  - 機能（ビュー・関数、JSON、全文検索）
  - 運用
- 公式の本がある題材（Rust の The Book など）は、その章立てに沿って図を中心に書き直す。
- **内部まで降りる。** 抽象的な説明で止めず、本物を見せる。PostgreSQL では pageinspect でページの中身を、ctid と xmin でタプルの版を、LSN で WAL の位置を見せた。

## 1 章：1 つの話題を 1 回で読み切る

| 項目 | 目安 | 実測 |
| --- | --- | --- |
| 読む時間（front matter の `time`） | 50〜90 分 | 序 10〜15 分、プロジェクト章は最大 150 分 |
| 節（`##`） | 5〜10 | pg 5〜10、rust 4〜8 |
| 小見出し（`###`） | 必要なだけ | rust は 10〜20 と多い |
| 原稿の行数 | 350〜500 行 | pg 250〜500、rust 400〜950 |
| 図 | 実行できる題材は 1〜6、読むだけの題材は 4〜15 | pg 平均 2.6、rust 平均 7 |
| 実行できるブロック | 15〜25（内部・運用の章は 8〜20） | pg 合計 379 |
| 確認問題 | 3〜4 問（序・歴史は 1 問、付録はなし） | pg 合計 64 |

- 章が 120 分を超えそうなら 2 章に分ける。逆に 30 分に満たない章は、隣の章とまとめる。
- 章の分け方の目安は「この章を読み終えたら何ができるか」を 1 文で言えること。front matter の `lead` がその 1 文になる。

## 1 節：1 つの問いに答える

- 見出しは問いか答えにする。「行の物理的な場所 ctid」はよく、「その他」はよくない。
- 1 節は、本文 2〜5 段落と、実行例か図を 1〜4 個にする。
- 新しい概念は 1 節に 1 つまでにする。2 つ出てきたら節を分ける。

## 図と実行例の配分

- **動かして見えるものは動かす。動かしても見えないものは描く。**
  - SELECT の結果は実行で見せる。ページの中の配置、MVCC の版の連鎖、ロックの待ち合いは図にする。
  - 実行環境がない題材（Rust）は、メモリ・所有権・ライフタイムをすべて図で見せるので、図が多くなる。
- 実行環境の制約で再現できないもの（PGlite では 2 セッションの競合や並列クエリ）は、図と実行しない例（`norun`）で説明する。その制約は README に書く。
- 状態が段階的に変わる話は `steps` 付きの図にする。1 図あたり 3〜6 段階が目安。

## 頼まれ方と範囲

| 頼まれ方 | 作るもの |
| --- | --- |
| 「図解 X を作って」 | 上の全体の粒度。章立て案を先に出して合意を取る |
| 「X の章を足して」 | 1 章ぶん（上の 1 章の目安）と確認問題。前後の章とのつながりも直す |
| 「例題・確認問題を足して」 | 既存の章の末尾に足す。本文は変えない |
| 「実行環境も作って」 | [runtime.md](runtime.md) の段階の 1〜4 まで。どこまで作るかを先に示す |
| 「図をもっと」 | 文で説明している仕組みを図に置き換える。飾りの図は足さない |
